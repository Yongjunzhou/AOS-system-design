## 一、单元导读

### 主题

需求的"标尺"从哪来——需求工程、需求开发、需求管理是什么关系？为什么"加强需求管理"救不了恒信？规定需求为什么是验证的参照？ConOps 在整条链的什么位置？

### 开场破题（对应章首误解现场）

念出 IT 总监在管理层会上的拍板："需求最近总是变来变去，合同评审、财务对账、法务条款，改一版崩一版。**我们要加强需求管理。** 谁负责？Ada，你来。"

让各组表态：这句话你们信吗？Ada 没接话，先反问："需求为什么会变？变之前，我们的需求**开发**做到位了吗？——需求调研做了吗？需求分析做了吗？每条需求写得可验证吗？"IT 总监皱眉："这些不都是'需求管理'的一部分吗？管好需求，自然就都做了。"——这句"管好需求，自然就都做了"，你们觉得对吗？

### 本单元要反转的直觉

- **需求乱，是因为管理没跟上；加强需求管理，需求就稳了**（× 需求工程 = 需求开发 + 需求管理；需求是开发出来的，不是管出来的）
- **需求管理包含需求开发，管好需求自然就开发好了**（× 并列不是包含；开发管"生"、管理管"养"）
- **客户说了'页面要快一点'，就是需求**（× 是明示需求，不是规定需求——没成文、不可验证）
- **ConOps 是给运营部门看的故事，跟开发没关系**（× 它是问题域到解空间的桥；跳过它 SRS 条款悬空）
- **需求变更多，说明需求管理没做好**（× 先分清"需求变了"还是"当初没说清楚"——后者是开发欠账）
- **验证和确认是一回事**（× 验证对照规定需求、确认对照用户意图）
- **版本文件名改一改，就是需求管理**（× 那是版本不是基线；没有基线，变更不可描述）
- **没有文档的环节，口头说说就够了**（× 没有文档的环节，就是不可追溯的环节）

### 本轮题卡的内在逻辑（10 题 2×5）

**第一组 · 概念与原理（先立概念）**：Q1 需求工程定义（概念本身）→ Q2 工程/开发/管理关系（概念关系）→ Q3 规定需求（验证的参照）→ Q4 ConOps 位置（分析之后、规格之前）→ Q5 验证 vs 确认（双参照）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 恒信困境诊断（欠账二分）→ Q7 合同的"隐需求"（隐含需求主动挖）→ Q8 电子签章 CR（变更闭环）→ Q9 "另存为 v2"（骨架五份 + 追溯）→ Q10 回部门标尺体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。恒信合同审批系统（流程软件）与冰链 M3 温控箱（硬件 × 软件）是同一个概念的两面——需求工程 = 开发 + 管理、规定需求、ConOps 的"故事"、变更闭环在两边都能验，这正是"需求工程"领域中立的证据。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"加强需求管理"为什么救不了恒信？**
"IT 总监拍板：『需求最近改一版崩一版——我们要加强需求管理。』Ada 反问：『需求为什么会变？变之前，需求开发做到位了吗？』需求管理、需求开发、需求工程，这三个词到底是什么关系？『加强需求管理』为什么救不了恒信？"

追问：① "需求管理包含需求开发"错在哪——两个词各是什么性质的活动（创造性 / 控制性）？② 开发管"生"、管理管"养"——"养"能不能替"生"？管理再严，为什么照样出烂需求？③ 你们最近一次说"要加强需求管理"的时候，做的是开发的事，还是管理的事？

**Q2｜三个词什么关系？**
"请给出 需求工程、需求开发、需求管理 三者的关系（一句话），再把 规定需求、ConOps 放进整条链——它们分别在什么位置？"

追问：① "需求工程 ⊃ 需求管理 ⊃ 需求开发"——这个式子对吗？错在哪？② 规定需求是验证的参照——它站在链的哪一段（开发输出、管理输入）？③ ConOps 为什么不能在流程最前、也不能在最后，而偏偏在"分析之后、规格之前"？

**Q3｜"页面要快一点"是需求吗？**
"客户说：『页面要快一点。』——这算不算一条需求？『算』和『不算』都对，差在哪？"

追问：① 明示需求 vs 规定需求差在哪三个要件（成文 / 具体 / 可验证）？② "能设计测试证明"为什么是规定需求的判据——"要快一点"为什么测不了？③ 把"重要合同要审批"澄清成"金额 ≥ 500 万或三年期以上"——这是从需求开发的哪一步（获取 / 分析 / 规格）走出来的？

**Q4｜三百条条款为什么悬空？**
"法务负责人翻了两页 SRS 就发问：『审批通过后自动通知相关方——哪个相关方？审批链上有几个人？通知不到会怎样？』三百条条款为什么悬空？ConOps 和 SRS 到底差在哪？"

追问：① ConOps 讲"故事"、SRS 讲"条款"——"故事"比"条款"多了什么（上下文 / 场景 / 异常 / 应急 / 角色）？② 为什么 ConOps 必须在"分析之后、规格之前"——跳过它，等于从什么跳到什么（问题域 → 解空间）？③ "让不熟悉系统的人读完能画出流程图"——你们写完 SRS 后，有人能画出来吗？画不出来说明缺了什么？

**Q5｜"写对了"和"是要的"一样吗？**
"把需求写得很正确、但完全不是用户要的东西——这是需求开发最常见的失败。怎么防？『验证』和『确认』为什么必须分开？"

追问：① 验证对照规定需求（写对了吗）、确认对照用户意图（是要的吗）——各自问的问题是什么？② 只验证不确认 vs 只确认不验证，各自死于什么？③ 隐含需求为什么只能靠确认兜得住（验证对照规定需求，够不着没写出来的）？

### 第二组 · 落地与实践

**Q6｜你们的需求乱，是"变了"还是"没说清"？**
"恒信『改一版崩一版』，IT 总监说加强需求管理，Ada 翻了三个月变更记录：一大半『变更』根本不是需求变了，是当初没说清楚。你们最近一次『需求乱』，是需求变了，还是当初没说清楚？"

追问：① 开发欠账 vs 管理欠账怎么分——两张单子各装什么？② "先清源（开发）、再修渠（管理）"——恒信先补什么、后建什么？③ 你们最近一次需求混乱，属于哪张单子？当时做了什么、没做什么？

**Q7｜随口一句话暴露了什么？**
"财务随口一句：『月底要对账，合同 25 号之后签的能不能算到下个月？』——这句话暴露了什么？为什么访谈三次、每次问『还有别的吗』都答『没有了』，这句却出现在随口闲聊里？"

追问：① 隐含需求为什么不会自己开口——它靠什么被挖到（访谈随口一句 / 业务流程惯例 / 前代产品教训）？② 挖出来之后要做什么（显性化 → 写进规格 → 变成规定需求）？不做会怎样（验证够不着，只有确认兜得住）？③ 你们最近一次返工，是不是某条"大家都懂、没人写"的隐含需求漏了？

**Q8｜一次变更，走到哪一步停的？**
"电子签章的合同也要走审批流——这是一条 CR。影响分析经 RTM 反查发现 3 处模块、CCB 通过、实施、再验证、关闭，六份记录。你们团队最近一次需求变更，走到哪一步停的？"

追问：① 闭环五步（CR → 影响分析 → CCB → 再验证 → 关闭）——每一步"必须可判定"的关卡是什么？② 任何一环断了，这条变更就成了什么（查无实据的暗改）？③ 口头改需求为什么是最危险的变更形式（没有凭证）？④ 你们最近一次变更，有 CR 吗？影响分析做了吗？关闭了吗？

**Q9｜文件名和基线差在哪？**
"合同需求改了六版，版本靠文件名管：『合同需求 v2.doc』『合同需求 最终版 v3.doc』『合同需求 真最终版 v4.doc』。李工承认：『我们不是需求变太多，是根本没建基线。』——文件名和基线差在哪？"

追问：① 版本是刻度、基线是参照——"每一次变更说不清从什么变到什么"，缺的是哪个？② 追溯矩阵 RTM 的终极检验：任取一条需求双向走通（往上游知道从哪来、往下游知道影响谁）——没有基线，RTM 建得起来吗？③ 骨架五份（SRS / 需求池 / RTM / 评审报告 / 基线）缺一份，需求工程链哪里有断点？④ 你们的需求基线在哪？最近一次变更"从什么变到什么"说得清吗？

**Q10｜给你们的部门做一次标尺体检**
"结合你们部门现状，用六把尺子（并列判据 / 规定需求判据 / ConOps 位置 / 验证确认 / 变更三铁律 / 骨架五份）给最近一次需求做一次标尺体检——给出最该改进的三个事项，每个落到一个动作。"

追问：先做哪把尺子？为什么？两周后回来报告什么？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 "加强需求管理"为什么救不了恒信？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "需求乱就是管理没跟上，加强管理、加人加流程就稳了。" | 正是要翻的——把开发欠账当成管理漏洞 |
| 中 | "需求工程 = 需求开发 + 需求管理，并列。" 结论对，但说不出为什么"管理管不了" | 定义能复述，机制缺 |
| 好 | 并列不是包含 + 开发管"生"（创造性）、管理管"养"（控制性）+ "养"替不了"生"（管理再严，来源没摸清、分析没做透一样出烂需求）+ 恒信一大半"变更"是开发欠账 | 定义 + 机制 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"M3 温度记录乱，加强数据管理"；IT 组答"合同需求乱，加强需求管理"。同一个病：把开发欠账当管理漏洞，都是"给没有清源的水流修水渠"。

**反转话术**（对应章末认知反转·需求是开发出来的）：IT 总监说错了一半。需求工程 = 需求开发 + 需求管理，**并列**，不是包含。开发管"生"（获取、分析、规格、验证——创造性），管理管"养"（基线、变更、追溯、状态度量——控制性）。**管理管的是已经说清楚的需求；没说清楚的需求，管理管不了，只能开发。** 恒信"改一版崩一版"，一大半是当初没说清楚（"重要合同"没定义、"对账报表"口径没说清）——这是开发欠账。加强管理，等于给没有清源的水流修水渠，水还是脏的。**先清源（开发）、再修渠（管理），顺序不能反。**

**参考答案要点**：需求工程定义与两过程见 §1.1；为什么并列不是包含见 §1.2；案例进展①（Ada 的两张单子）。

### Q2 三个词什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "需求工程包含需求管理，需求管理包含需求开发（一条包含链）。" | 正是要翻的——把并列画成包含 |
| 中 | "需求工程 = 需求开发 + 需求管理，并列。" 关系对，规定需求/ConOps 放不准 | 总称关系对，链条位置缺 |
| 好 | 并列公式 + 规定需求站在"开发输出 / 管理治理对象 / 验证参照"三岔口 + ConOps 在"分析之后、规格之前"（问题域→解空间桥）+ 接口咬合在"批准 → 基线" | 关系 + 位置全到位，能证明"为什么偏偏在那" |

**产品侧 vs IT侧**：两组都能套同一句并列公式——冰链的 ConOps 是"疫苗出库→接种温度不断链"，恒信的 ConOps 是"合同从发起到归档的审批叙事"。内容不同，链结构纹丝不动。

**反转话术**（对应"术语三不混用"）："需求工程 ⊃ 需求管理 ⊃ 需求开发"——这个式子错。"⊃"把并列关系画成了包含关系，正是本书的词汇病：**需求工程 = 需求开发 + 需求管理（并列）**，需求管理不包含需求开发。规定需求站在整条链的枢纽：它是需求开发的**输出**（规格说明的成果）、**验证的参照**、也是需求管理的**治理对象**（基线/变更/追溯都围着它转）。ConOps 在"分析之后、规格之前"——先讲清"系统怎么被用"（问题域），才谈得上"系统必须做什么"（解空间）。开发与管理的接口咬合在**"批准 → 基线"处**：批准前需求流动（开发负责）、批准后一切变更走 CR（管理负责）。

**参考答案要点**：三词定义见 §1.1/§1.3；规定需求枢纽见 §2.3；ConOps 位置见 §3.2；铰链见 §4.5。

### Q3 "页面要快一点"是需求吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "客户说了就是需求，照做就行。" | 把明示需求当规定需求，正踩"规定需求"误区 |
| 中 | "算需求，但还不算规定需求。" 结论对，三要件说不全 | 判据有了，要件缺 |
| 好 | 算——明示需求；不算——规定需求（成文 + 具体 + 可验证）+ "能设计测试证明"判据 + "要快一点"无法验证 + 澄清"重要合同"→"金额≥500 万或三年期以上"出自分析 | 定义 + 判据 + 出处全到位 |

**产品侧 vs IT侧**：产品组答"客户说'断电保温要够久'"；IT 组答"客户说'页面要快一点'"。都是明示但未规定——说了不等于规定。

**反转话术**（对应规定需求概念卡片）："客户说了'页面要快一点'"——**算需求，但不是规定需求**。明示需求 ≠ 规定需求：规定需求要三个要件——**成文 + 具体 + 可验证**。"要快一点"没说清多快、没写成条文、没法设计测试证明。判据一句话：**能设计测试证明 → 是规定需求；只能"感觉" → 还不是。** 恒信"重要合同要审批"为什么烂？"重要"没定义（违反无歧义）、没法测（违反可验证）。把它澄清成"金额 ≥ 500 万或三年期以上"——那是需求分析里**澄清**这一步的活（分析四动作之一），不是获取的记录。

**参考答案要点**：术语三不混用见 §1.3；规定需求判据见 §2.3 + 概念卡片；澄清是分析四动作之一见 §2.2；无歧义/可验证见 §5.1。

### Q4 三百条条款为什么悬空？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "是 SRS 没写全，补几条需求就行。" | 只见条款缺、不见"故事"缺——正是要翻的 |
| 中 | "没人写过 ConOps，缺上下文。" 结论对，说不出位置原理 | 判据用了一层，机制缺 |
| 好 | ConOps 讲"故事"、SRS 讲"条款"+ 跳过 ConOps = 从问题域直接跳解空间 + "可画流程图"判据 + 三百条一半需改写（顺序反了） | 机制 + 判据 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"M3 没人写 ConOps——应急场景'疫苗运输车在高速上抛锚 2 小时'直接决定'断电保温时长'这条硬需求"；IT 组答"恒信没人写 ConOps——三百条 SRS 悬空"。**ConOps 写不出来的场景，就是将来要出事故的场景。**

**反转话术**（对应"先讲故事，才谈得上条款"）：法务翻两页就看出问题，因为三百条 SRS 悬在半空、每一条都缺上下文——**没人写过 ConOps**。"法务、财务、业务三方怎么用这套系统审批一份合同"这个叙事，从没被写成过文档。ConOps 讲"故事"（系统怎么被用），SRS 讲"条款"（系统必须做什么）——"故事"比"条款"多的是上下文、场景、异常、应急、角色。为什么 ConOps 必须在"分析之后、规格之前"？因为它的完整定稿必须建立在已摸清需要的基础上；**跳过它直接写 SRS，等于从"问题域"直接跳到"解空间"，中间的桥没了。** 判据：让不熟悉系统的人读完能画出流程图——画得出来才合格。恒信补了 ConOps 后三百条 SRS 有一半需要改写——先写条款后补故事，顺序反了。

**参考答案要点**：为什么需要 ConOps 见 §3.1；位置见 §3.2；六部分与可画图诀窍见 §3.3；案例进展③。

### Q5 "写对了"和"是要的"一样吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "一回事，都是确认需求没问题。" | 正是要翻的——把两个参照不同的活动混成一个 |
| 中 | "验证对照规定需求、确认对照用户意图。" 结论对，说不出为什么必须分开 | 定义对，机制缺 |
| 好 | 验证 = "写对了吗"（对照规定需求）、确认 = "是要的吗"（对照用户意图）+ 写得很正确但完全不是用户要的 = 最常见的失败 + 只验证不确认/只确认不验证各死于什么 + 隐含需求只能确认兜得住 | 机制 + 判据 + 关联全到位 |

**产品侧 vs IT侧**：产品组答"M3 验证对照温控规格、确认对照接种真实场景"；IT 组答"恒信验证对照规定需求、确认对照法务财务真实意图"。同一个双参照。

**反转话术**（对应"验证与确认两个必须分开的环节"）：验证回答"我们把需求写对了吗"——**对照规定需求**；确认回答"我们写的是用户要的吗"——**对照用户真实意图**。两者必须分开，因为**把需求写得很正确、但完全不是用户要的东西，是需求开发最常见的失败**——根源是隐含需求。只验证不确认：需求可能写得很漂亮、但根本没人要；只确认不验证：需求可能是用户要的、但没法执行。**两道关，缺一不可。** 隐含需求为什么只能靠确认兜得住？因为验证对照规定需求——**验证够不着没写出来的东西**；只有确认（真实场景）兜得住它。

**参考答案要点**：验证/确认对照见 §2.4；隐含需求与确认兜底见 §2.4 + 案例进展②；第7章（评审验证确认）预告。

### Q6 你们的需求乱，是"变了"还是"没说清"？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "需求变太多，就是管理没做好。" | 归因到"管理"，没到"当初没说清"——正是要翻的 |
| 中 | "先分清是变了还是没说清。" 结论对，两张单子装什么说不全 | 判据用了一层，细节缺 |
| 好 | 开发欠账（没调研/没分析/没写可验证规格）= 源头脏 vs 管理欠账（没基线/没变更流程/没追溯）= 过程乱 + 先清源再修渠 + "补欠账"与"加强管理"是两件事 | 机制 + 判据 + 动作全到位 |

**产品侧 vs IT侧**：产品组答"M3 温度精度口径没说清（开发欠账）"；IT 组答"恒信'重要合同'没定义、'对账报表'口径没说清（开发欠账）"。同一个病。

**反转话术**（对应案例进展① + 章末第二反转）：Ada 翻了三个月变更记录，发现一大半"变更"根本不是需求变了，是**当初就没说清楚**。开发欠账 = 源头脏（没调研、没分析、没写可验证的规格）——再好的管理只是把脏水存进干净的罐子；管理欠账 = 过程乱（没基线、没变更流程、没追溯）——再好的开发也被无序变更慢慢腐蚀。**先清源（开发）、再修渠（管理），顺序不能反。** Ada 先补需求调研和需求池（两周），再建第一版基线——两周后"需求好像稳了一点"，不是需求变了，是欠账开始还了。**当一个团队说"要管起来"的时候，先问一句：源头清了吗？**

**参考答案要点**：欠账二分见 §1.2；案例进展①；章末认知反转。

### Q7 随口一句话暴露了什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "财务临时加了个需求。" | 把隐含需求当成"新增需求"——没看到它一直都在 |
| 中 | "这是一条隐含需求。" 结论对，怎么挖、挖完做什么说不全 | 概念对，链路缺 |
| 好 | 隐含需求不会自己开口（通常隐含 = 行业惯例默认）+ 主动挖（访谈随口一句/业务流程惯例/前代产品教训）+ 挖出 → 显性化 → 写进规格 → 变成规定需求 + 否则验证够不着、只有确认兜得住 | 机制 + 动作 + 后果全到位 |

**产品侧 vs IT侧**：产品组答"护士'一手抱孩子一手开箱'、疫苗运输车塞得下吗"；IT 组答"财务'25 号之后签的合同算下个月'"。都是"大家都懂、没人写"的隐含需求，漏了客户用一天就认定"这产品不行"。

**反转话术**（对应"隐含需求不会自己开口"）：财务那句"25 号之后签的合同能不能算到下个月"暴露了一条**隐含需求**——合同审批的"统计归属月份"规则。没人把它写进任何需求文档，它是行业惯例默认。为什么访谈三次每次问"还有别的吗"都答"没有了"，这句却出现在随口闲聊里？因为**隐含需求不会自己开口**——它需要主动去挖：访谈里的随口一句、业务流程里的惯例、前代产品的教训。挖出来要显性化、写进规格、变成规定需求——否则**验证够不着它**（验证对照规定需求），只有**确认**（真实场景）兜得住它。

**参考答案要点**：隐含需求原理见 §2.4 + 案例进展②；无来源需求不得入需求池见 §2.2。

### Q8 一次变更，走到哪一步停的？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "变更很常见，口头说一声就改了。" | 正是要翻的——口头变更 = 没有凭证的变更 |
| 中 | "要按流程走，不能口头改。" 结论对，闭环五步/关卡说不全 | 动作对，机制缺 |
| 好 | 闭环五步各配"必须可判定"关卡 + 任何一环断 = 查无实据的暗改 + 口头变更最危险（没有凭证）+ "变更日志只追加不修改" | 机制 + 判据 + 后果全到位 |

**产品侧 vs IT侧**：产品组答"M3 改断电告警阈值要走 CR"；IT 组答"恒信电子签章合同走审批流要走 CR"。同一个闭环，名字不同。

**反转话术**（对应"变更控制：需求管理的核心战场"）：一条 CR 走完整闭环——影响分析经 RTM 反查发现 3 处模块、CCB 通过、实施、再验证、关闭，六份记录。**任何一环断了，这条变更就成了"查无实据"的暗改。** 为什么变更是核心战场？因为大多数团队的需求管理问题都出在这里。三条铁律：**无 CR 不得变更；不分析不得上会；验证通过方可关闭。** 每个节点都是"必须可判定"的关卡——CR 有没有立案、影响分析有没有做、CCB 有没有结论、验证有没有通过，任何一个答不上来，变更就在流程外流窜。**口头改需求是最危险的变更形式**——落到文档层面，就是"没有凭证的变更"。变更日志只追加不修改，审计时调取。

**参考答案要点**：变更控制闭环见 §4.2；三铁律见 §4.2；口头变更最危险见 §4.5；变更日志见 §4.5。

### Q9 文件名和基线差在哪？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "改名也是管理版本的一种方式，够用就行。" | 把"文件名"当"基线"，正踩版本≠基线 |
| 中 | "文件名不是基线，没基线变更说不清。" 结论对，说不清缺了什么后果 | 判据对，机制浅 |
| 好 | 版本是刻度、基线是参照（被批准冻结）+ 没基线 → 每次变更说不清"从什么变到什么" + RTM 建不起来 + 骨架五份缺一份链有断点 + 补基线后失控率降七成（不是变少是留痕） | 机制 + 判据 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"M3 固件版本号/参数表版本"；IT 组答"合同需求 v2/最终版/真最终版"。同一个病：把版本当基线、靠文件名管版本。

**反转话术**（对应"基线是分界线" + 第12章预告）：文件名管的是版本，不是基线。**版本是刻度**（时间轴上的演进），**基线是参照**（被批准冻结、作为全生命周期参照的配置信息）。"另存为 v2"靠文件名——没有基线，**每一次变更都说不清"从什么变到什么"**，追溯矩阵没法建、验证没有参照。**基线是分界线**：线左是需求开发的产物（还在流动）、线右进入需求管理（一切改动走变更控制）。从基线出发一切变更可描述，离开基线一切变化不可言说。RTM 的终极检验：**任取一条需求，双向走通**——往上游知道它从哪来、往下游知道它影响谁；没有基线，RTM 建不起来。恒信补了基线后变更失控率降七成——**不是需求变少了，是每次变更都留下了痕迹。**（"版本顺着流、基线垂直切"第12章专门讲。）

**参考答案要点**：基线 = 被批准冻结的参照见 §4.3；版本 vs 基线见案例进展④ + 第12章预告；RTM 终极检验见 §5.2；骨架五份见 §5.2。

### Q10 给你们的部门做一次标尺体检

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强需求管理、要写需求文档"。 | 没落到六把尺子任何一把，不可检查 |
| 中 | 用一把尺子查出缺口（如"需求没基线"） | 有判据，但只照了一面 |
| 好 | 六把尺子逐项打勾，挑出三个缺口各配一个可检查动作，说出先做哪把、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**参考答案要点**：六把尺子见"本章判据"；作业指南见课后作业。

## 四、知识卡片

### 一页图（书"本章概念总图"）

```
需求工程 = 需求开发（生·创造性）+ 需求管理（养·控制性）—— 并列，不是包含

需求开发四活动：获取 → 分析 → 规格（SRS·规定需求）→ 验证（对照规定需求 / 确认·对照用户意图）
ConOps：分析之后、规格之前 —— ConOps 讲"故事"，SRS 讲"条款"
需求管理四活动：基线 → 变更控制（CR→影响分析→CCB→再验证→关闭）→ 追溯 → 状态度量
规定需求 = 验证的参照；需求质量六性 = 完整·一致·无歧义·可验证·可追溯·有优先级
骨架五份：SRS · 需求池 · RTM · 评审报告 · 基线
```

### 金句（书"本章判据"提炼）

- 需求工程 = 需求开发 + 需求管理，**并列不是包含**——开发管"生"（创造）、管理管"养"（控制）。
- **需求是开发出来的，不是管出来的**——管理管的是已经说清楚的需求；没说清楚的需求，只能开发。
- **先清源（开发），再修渠（管理），顺序不能反。**
- 规定需求 = 验证的参照——**能设计测试证明的，才是规定需求；只能"感觉"的，还不是。**
- ConOps 讲"故事"，SRS 讲"条款"——**先讲清楚系统怎么被用，才谈得上系统必须做什么。**
- 验证对照规定需求（写对了吗），确认对照用户意图（是要的吗）——**只验证不确认，需求写得很漂亮但根本没人要；只确认不验证，需求是用户要的但没法执行。**
- **无 CR 不得变更，不分析不得上会，验证通过方可关闭。**
- **基线是分界线**——线左是开发的产物（还在流动），线右进入管理（一切改动走变更控制）。
- 版本是刻度、基线是参照——**每一次变更都说不清"从什么变到什么"，是因为没建基线。**
- **没有文档的环节，就是不可追溯的环节**——裁掉文档不是省事，是把追溯链砍断。
- 隐含需求不会自己开口——**ConOps 写不出来的场景，就是将来要出事故的场景。**

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，2 小时内完成一次体检：
>
> 1. **查并列（尺1）**：你们说"需求乱"时，说的是开发欠账（没调研/没分析/没写可验证规格）还是管理欠账（没基线/没变更流程/没追溯）？最近一次混乱属于哪张单子？
> 2. **查规定需求（尺2）**：拿一条你们最近的需求——"能设计测试证明吗"？不能 → 那还是明示需求、不是规定需求，验证无从参照。改写出一条可验证条文。
> 3. **查 ConOps（尺3）**：写 SRS 前，有人写过"系统怎么被用"的叙事吗？让不熟悉系统的人读完，能画出流程图吗？画不出来 → 条款悬空。
> 4. **查验证确认（尺4）**：最近一次需求评审，"对照规定需求写对了吗"和"对照用户意图是要的吗"两道关都过了吗？只过一道 → 缺的那道是隐患。
> 5. **查变更闭环（尺5）**：最近一次需求变更——有 CR 吗？影响分析做了吗？CCB 有结论吗？再验证了吗？关闭记录了吗？哪一环断了？
> 6. **查骨架五份（尺6）**：SRS / 需求池 / RTM / 评审报告 / 基线，缺哪份？缺的那份让哪个问题答不上来？
>
> 卡住时：找到第一个"否"就能开工，不必打完全部。产出三件最该改进事项（每条 = 一个可检查动作）。
