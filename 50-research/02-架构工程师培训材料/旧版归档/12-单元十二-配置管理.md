## 一、单元导读

### 主题

"版本号不是有吗？怎么就不算配置管理了？"——**配置**是"实体被记录下来的形态"（配置项=被管起来的实体、配置=形态、配置信息=记录，都锚定在"实体"上），不是参数文件；**版本**是时间轴上的演进刻度，回答"走到第几步"；**基线**是被批准冻结的参照，回答"哪一版被盖章"——**版本顺着流、基线垂直切**，一个管流动、一个管冻结。**没有基线，变化就不可言说**；变更控制（冻结→变更→再冻结）守住基线的门。配置管理守护的正是第11章那些"不可逆决策"——它是那些决策的保险丝。

### 开场破题（对应章首误解现场）

念出冰链科技那场审计：M3 冷链温控箱在市场上跑了一年多，约五千台。春天修了一个丢读数 bug，老周发了一版固件 v2.3，通过 App 推送给已出厂的箱子。三个月里分批升级了约三千八百台。然后疾控中心来审计一批疫苗运输记录。

审计员问了一个以前从没人问过的问题："这批疫苗四月运输，全程温度记录正常。你们要证明——这批记录，是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？"

老周觉得这问题简单："查一下这批箱子当时跑的固件版本。"结果查不清。升级记录只有一句"已推送 v2.3"，没有"哪台箱子、哪个时间、从哪一版升到哪一版"的明细。更麻烦的是：修丢读数的 bug，动的是采集算法——v2.1 采的温度记录和 v2.3 采的，断链判定的逻辑不一样。追溯链在"固件"这一环断了。

老周觉得冤："我们有版本号啊。v2.1、v2.2、v2.3，都标着呢。升级也走流程了，小赵也验证过了。怎么就不算配置管理了？"小林："版本号是有了，可哪一版是'被批准、被冻结、全生命周期拿它对照'的？……我们把'版本号'当成了'基线'——版本只是刻度，基线才是参照。"

让各组表态：如果你坐在冰链这间会议室里，你会觉得冤吗？"版本号不是有吗？流程不是走了吗？"——版本管理做好了，就等于配置管理做好了吗？

### 本单元要反转的直觉

- **配置就是设置页里那些参数**（× 参数是零件，配置是装好的整机——配置是"实体被记录下来的形态"，参数只是配置信息里的条目）
- **版本管理做好了=配置管理做好了**（× 版本只是刻度；配置管理=标识+控制+状态记录+审计四活动，缺了基线和变更控制，版本也管不住）
- **我们有版本号，所以有基线**（× 版本是刻度、基线是资格——被批准、被冻结、作参照三特征全有才是基线；把版本当基线=把里程桩当收费站）
- **基线一旦建立就永远不能改**（× 基线可以变更，但必须走变更控制，改完建立新基线——"冻结"不是"死锁"）
- **没有基线，变化也说得清——反正有 git 历史**（× git 历史是记录，基线是被批准、被冻结、被全项目认可的参照；没有批准动作，历史只是流水账）
- **版本号就是文件名（final_2.zip）**（× 文件名版本不可回溯、不可复现——版本必须精确对应到"哪一次完整构建"）
- **配置管理是文档/文员的活**（× 配置管理是第11章那些不可逆决策的保险丝——决策做对了靠它守住、做错了靠它早止损）
- **小团队、小产品，配置管理是大公司的负担**（× 配置管理可剪裁——小团队至少"版本可指认、变更可追溯"；负担大头来自"查不清"的返工和事故）

### 本轮题卡的内在逻辑（10 题 2×5）

**第一组 · 概念与原理（先立概念）**：Q1 配置是什么（概念本身·破题·那页设置）→ Q2 配置/配置项/配置信息/参数/实体 + 版本/变体/修订/基线的双层关系（概念关系）→ Q3 版本是刻度（版本管理≠配置管理·真悖论）→ Q4 基线三特征 + 版本顺着流基线垂直切（真悖论）→ Q5 没有基线变化就不可言说（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 冰链固件事故四大活动诊断（四洞·案例进展①③）→ Q7 恒信 final_2.zip（版本是刻度·真悖论·案例进展②）→ Q8 契约链（基线=冻结端版本=交付端·真悖论）→ Q9 编号事故复盘·配置管理是保险丝（守护·真悖论·案例进展④）→ Q10 回部门"配置管理体检"（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。冰链 M3 温控箱（硬件 × 软件）与恒信合同审批系统（流程软件）是同一个概念的两面——冰链把"固件版本"当"基线"，批次追溯查不清（配置管理缺失）；恒信把"文件名的版本"当"版本"、把"版本"当"基线"，回滚连"回滚到哪"都指不出来（final_2.zip）。这正是"配置/版本/基线"领域中立的证据。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜小赵指的那一页，是配置吗？什么才算"配置"？**
"小赵指着 App 设置页上的开关和数字框，给新来的测试员讲解：'这就是咱们的配置。温度上报间隔、超温告警阈值、断电告警开关……客户能改的，都在这页。改参数不用动固件、不用重编译，服务端一推就行。'——小赵指的那一页，是配置吗？什么才算'配置'？"

追问：① 配置三问：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？三问全"是"才是配置？② 参数 vs 配置：上报间隔这个参数是"配置信息里的一个条目"；配置是"上报间隔、告警阈值、断链判定逻辑、采集算法关联在一起塑成的 M3 行为形态"——为什么"参数是零件，配置是装好的整机"？③ 案例进展①：老周问"那页设置到底是不是配置"，小林反问他"你改那个告警阈值，改的是什么"——改一个参数，为什么整台箱子的"形态"就变了、采出来的温度记录含义都跟着变？④ 你们产品里"客户能改的参数"，用配置三问逐个验一遍——有几个是配置，几个只是配置信息里的条目？

**Q2｜配置/配置项/配置信息/参数/实体，和版本/变体/修订/基线，各是什么关系？**
"请给出 配置 / 配置项 / 配置信息 / 参数 / 实体 的关系（一句话），再把 版本 / 变体 / 修订 / 基线 放进去——两组概念各管什么？为什么说'配置提供内容、版本提供位置、批准提供资格'？"

追问：① 三词解耦：ISO 10007 三个术语互相定义、首尾相连成环——为什么引入"实体"做锚点就能解耦？② 辨析：设计图纸既是"配置信息"又是"配置项"——两个层面怎么不冲突？③ 变体×版本：标准版/医疗加强版/工业版是变体（空间、并存），v1.0→v2.4 是版本（时间、先后）——正交；"医疗加强版 v2.4"这个形态被批准冻结，怎么就成了基线？④ 配置提供"内容"、版本提供"位置"、批准提供"资格"——三者齐备才成一个基线，为什么一个都不能少？

**Q3｜版本号有了、流程走了、验证过了，为什么还是查不清？**
"老周说：'我们有版本号啊。v2.1、v2.2、v2.3，都标着呢。升级也走流程了，小赵也验证过了。怎么就不算配置管理了？'——版本号有了、流程走了、验证过了，为什么疾控审计还是查不清？版本管理和配置管理，到底差在哪？"

追问：① 版本是刻度：版本回答"走到第几步"，它没回答"哪一版是'被批准、被冻结、作参照'的"——版本只是时间轴上的刻度？② 版本四用途：追踪演进/回溯/并行/复现——版本解决这四个问题，但解决不了"参照"问题；缺了基线和变更控制，版本也管不住？③ "版本管理做好了=配置管理做好了（版本号有、流程走了、验证过了）" vs "配置管理=标识+控制+状态记录+审计四大活动（版本只是刻度）"——两个都对，靠什么判据分清？④ 你们团队"版本管理"和"配置管理"是分开的吗？版本号能对应到"哪一次完整构建"吗？

**Q4｜版本和基线差在哪？基线一旦建立，是不是就永远不能改了？**
"老周看着版本链：'v2.3 都发布三个月了，还不是基线？'小林：'版本只是刻度，基线才是参照。'——版本和基线差在哪？'版本顺着流、基线垂直切'是什么意思？基线一旦建立，是不是就永远不能改了？"

追问：① 三特征：被批准（资格，有权威的盖章）/被冻结（状态，任何人不能随意改）/作参照（用途，全生命周期拿它对照）——为什么一个都不能少？② 横竖分工：版本与时间同向（尺子上的刻度，流动，只描述位置）；基线垂直插入时间（横在路中间的闸门，冻结，制造分界）——为什么"把版本当基线=把里程桩当收费站"？③ "基线一旦建立就永远不能改（神圣不可侵犯）" vs "基线可以变更（必须走变更控制，改完建立新基线，冻结不是死锁）"——两个都对，靠什么判据分清？④ 你们产品"哪一版被批准、被冻结、全生命周期拿它对照"？答不出——你们只有版本链，没有基线？

**Q5｜"没有基线，变化就不可言说"——为什么？git 历史里不是什么都查得到吗？**
"疾控审计员问：'这批疫苗四月运输，全程温度记录正常。你们要证明——这批记录，是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？'老周说：'查一下当时跑的固件版本。'结果查不清。小林：'没有基线，变化就不可言说。'——为什么？git 历史里不是什么都查得到吗？"

追问：① 原点：要描述一个变化，必须有"从哪变起"的原点——"从 v1.0 变到 v1.1"这句话有意义，是因为 v1.0 是所有人都认的、被冻结的、不会动的原点；没有原点，像在茫茫大海上说"我在动"，却没有岸标？② 对照：git 历史是记录（流水账），基线是被批准、被冻结、被全项目认可的参照——没有批准动作，历史只是流水账？③ "没有基线变化也说得清（git 历史都在，diff 一查就知道改了什么）" vs "离开基线，一切变化都不可言说（没有'从什么变起'的原点）"——两个都对，靠什么判据分清？④ 配置管理核心目的三问——应该是什么（as-designed）/实际是什么（as-built）/怎么变成这样的（变更历史）——老周答不上的"这批记录是哪一版固件采的"，是哪一问？

### 第二组 · 落地与实践

**Q6｜那场审计四个洞各缺什么？哪一洞最关键？**
"冰链那次审计，老周复盘：固件升级'走了流程'、版本号'都有'、小赵也'验证过了'——可追溯链还是断了。用配置管理的尺子，那场事故四个洞各缺什么？哪一洞最关键？"

追问：① 四大活动对照：配置标识（固件是配置项，但从没立过基线）/配置控制（"走了流程"但没有影响评估——没问采集逻辑变没变）/状态记录（只有一句"已推送 v2.3"，没有哪台箱子哪个时间升到哪一版的台账）/配置审计（从没抽查实物与记录一致）——四个洞哪个最关键？② 影响评估：修丢读数的 bug 动的是采集算法——影响评估一问，为什么"固件行为变化，历史温度记录的采集与判定逻辑随之变化"就该被写进评估单？③ 案例进展③：老周这次升级 v2.4 走完 CR→影响评估→CCB→实施→建立新基线——每一步拦住或显形了什么？为什么"版本号只是刻度，基线是参照，流程是守护，三样都有，变化才说得清"？④ 用四大活动诊断你们团队——标识/控制/状态记录/审计，各打一个"有/缺/半吊子"？缺的那一洞，最近一次追溯里断在哪？

**Q7｜文件名不算版本，什么才算？"版本是回滚的地址"是什么意思？**
"恒信小王把部署包扔进日期文件夹：'2026-05-18'里躺着'合同系统_final.zip'和'合同系统_final_2.zip'，分不清哪个是哪个。李工：'我们有版本号啊。'Ada：'你连"版本"都算不上。'——文件名不算版本，什么才算？'版本是回滚的地址'是什么意思？"

追问：① 版本判据：一个编号能精确对应到"哪一次完整构建"（哪个代码提交编译出来的、包含哪几条变更）吗？不能——它连版本都算不上？② 回滚地址：出问题要回滚，"回滚到哪"都指不出来——日期文件夹为什么既没地址、也没参照？③ "文件名=版本（final_2.zip 也是版本号，至少能区分新旧两个包）" vs "版本必须精确对应到完整构建（final_2 既不知道哪次构建、也不知道有没有经批准）"——两个都对，靠什么判据分清？④ 第4章合同需求靠"v2.doc""最终版 v3.doc"管版本，现在是系统部署靠"final_2.zip"管版本——同一个病，换了个文件后缀再犯一遍，为什么文件命名永远管不住版本？

**Q8｜契约链的基线和版本，是某一级专属，还是每级都重复？**
"Ada 说：'配置管理给契约链每一级都配了两样东西——基线是每一级契约的冻结端，版本是交付端。'李工：'可我们日常就一句话：按基线开发，提交版本。这不是说基线和版本各有归属吗？'——契约链的基线和版本，到底是某一级专属，还是每级都重复？"

追问：① 契约链：需求→方案→实现，链上每一对相邻环节都是一组局部的"甲方-乙方"关系——甲方把要求冻结成基线、乙方按基线开发、乙方产出的版本交付甲方验收、验收通过又成为下一环的基线，机制怎么逐级重复？② "基线对甲方、版本对乙方——基线和版本各有归属（需求阶段功能基线、实现阶段产品基线）" vs "基线和版本在每一层都在（契约链每级都重复同一机制）"——两个都对，靠什么判据分清？③ 开发链内部的"甲乙方"是技术契约（要求-兑现，管"对不对得上"）；完整的外部甲乙方多一层商务契约（法律合同、付款、责任，管"赔不赔得起"）——为什么"把'合同'和'契约链'当成一回事"是越界？④ 画出你们开发链三层（需求→设计→实现），每层的"基线（冻结端）"和"版本（交付端）"分别是什么？

**Q9｜第11章说改字段前三问是个人尺子，配置管理把它变成了什么？**
"编号事故复盘会上，李工说：'如果当时有这套东西，我改编号规则会先填 CR。影响评估一查——编号规则被财务、台账、审计、电子签章四个下游引用；评估单上会写"该变更影响全部历史合同数据，不可逆性高"——这一行字写出来，我当天就不敢"今天就能上"了。'——第11章说改字段前三问是一把个人尺子，配置管理把它变成了什么？为什么说配置管理是第11章那些不可逆决策的保险丝？"

追问：① 同构表：决策记录↔配置信息 / 不可逆决策识别↔基线冻结 / 推迟决策↔变与不变的分离 / 变更影响分析↔变更控制——四行各对什么？② 尺子变流程：第11章三问是个人尺子（靠自觉），配置管理的变更控制是组织流程（靠结构）——为什么"个人尺子靠自觉，流程靠结构"是守护的本质？你不是自觉不够，是一个人扛不住那么多"顺手改动"的记忆？③ "配置管理是文员的活、是文档的活（负担，跟核心决策无关）" vs "配置管理是第11章那些不可逆决策的保险丝（决策做对了靠它守住、做错了靠它让你早发现早止损）"——两个都对，靠什么判据分清？④ "决策记录是决策的配置信息"——第11章的六问记录把决策从"当事人脑子里的知识"变成"组织的资产"，配置管理怎么把这件个人动作变成组织级动作？

**Q10｜给你们的部门做一次"配置管理体检"**

### Q1 小赵指的那一页，是配置吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "设置页就是配置，客户能改的就是配置。" | 正是要翻的——把"配置信息里的条目"当"配置" |
| 中 | "配置是实体被记录的形态。" 结论对，三问/参数零件整机说不清 | 结论对，机制缺 |
| 好 | 配置三问（被记录了吗/功能物理特性吗/关联成整体了吗）+ 参数是零件配置是整机（上报间隔是条目，关联起来的行为形态才是配置）+ 改参数=整机形态变、历史记录含义变 | 判据 + 机制 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"冰链设置页那几个开关是配置信息里的条目，采集算法+断链判定+告警逻辑关联成的行为形态才是配置"；IT 组答"恒信合同审批流里'审批人可配'的那些参数是条目，审批链+编号规则+状态枚举关联成的形态才是配置"。同一个"配置是形态不是参数"。

**反转话术**（对应 §1.1~1.4 + 案例进展①）：小赵那句话，在座没人觉得有问题——"参数、配置，不是一个意思吗？"这一章的第一个病根就藏在"不是一个意思吗"里。**把"配置"当成"那页设置里的参数"，是配置管理领域流传最广的误解——它把一个重量级的概念，压缩成了一个轻量级的词：参数文件。** 用第1章的话说，这又是一次**近邻混用**：参数（parameter）和配置（configuration）长得像（都跟"可变的东西"有关）、其实不是一层（参数是单个的值，配置是一整套"被记录的形态"）。**参数是零件，配置是装好的整机。** 配置三问：**它被记录了吗**（记录边界——没被写下来就无从核对无从追溯）、**它是功能/物理特性吗**（类别边界——成本、责任人、批次这些管理属性不算配置）、**它和其他特性关联成整体了吗**（关联边界——"这里一个阈值、那里一个开关"凑不成配置）。案例进展①里小林的反问最见功力——老周改"告警阈值"，改的不是一个参数，是"这台箱子当时是什么样"：采集逻辑+断链判定逻辑组合成的行为形态变了，采出来的温度记录含义都跟着变。**参数是变了就变了的开关；配置是"这台箱子被记录下来的样子"——你永远要知道，它当时是哪副样子。**

**参考答案要点**：配置三问见"本章判据"1；三个隐形过滤器见 §1.4；案例进展①；概念卡片·配置。

### Q2 配置/配置项/配置信息 + 版本/变体/修订/基线，各是什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "配置项就是配置，版本就是基线，改个名字而已。" | 正是要翻的——对象/属性/记录不分，变体/版本/基线混用 |
| 中 | "配置项/配置/配置信息锚定实体。" 结论对，实体怎么解耦/变体×版本说不清 | 结论对，机制缺 |
| 好 | 三词解耦（ISO 10007 循环定义→引入实体锚点：对象/属性/记录）+ 文档既是配置信息又是配置项（两个层面）+ 变体×版本正交（空间/时间）、交叉点被批准冻结成基线 + 配置提供内容/版本提供位置/批准提供资格 | 解耦 + 辨析 + 口诀全到位 |

**产品侧 vs IT侧**：产品组答"M3 的配置项=固件/板卡/设计图纸，配置=采集算法+判定逻辑关联成的形态，配置信息=固件源码/规格/变更记录"；IT 组答"恒信的配置项=需求文档/编号规则/部署包，配置=审批链关联成的形态，配置信息=规格/变更记录"。同一个"三分离 + 实体锚点"。

**反转话术**（对应 §1.2 + §2.5 + 概念卡片）：配置管理里三个纠缠在一起的概念——**配置项、配置、配置信息**。打开权威标准 ISO 10007，你会发现三个术语互相引用、首尾相连，形成一个循环定义：你要懂一个就得先懂另外两个。**解耦的方法，是往这个环里引入一个不依赖任何配置术语的锚点——"实体"**，让三个概念全部锚定在实体上：配置项是"被管起来的那个东西"（对象）、配置是"它被记录下来的该有的样子"（属性）、配置信息是"记录它的那些资料"（记录）。用体检打比方：**配置项是"人"，配置是"这个人的身高体重"，配置信息是"他的体检档案"**——不是同一层的东西，谈不上真循环。最大的坑：**文档既是"配置信息"，又可以是"配置项"**——设计图纸是描述 M3 的配置信息；但图纸本身也要被管理、要管版本、要走变更，那时它就是配置项。两个层面，不冲突。再看第二组：**变体**回答"有几种形态"（空间、并存：标准版/医疗加强版/工业版）、**版本**回答"走到第几步"（时间、先后：v1.0→v2.4）、**修订**回答"内部改了几次"（更细粒度：Rev A/B/C）。一个配置可以有很多版本；一个版本下也可以有多个配置。**基线，是变体 × 版本的交叉点被盖章的结果**——"医疗加强版 v2.4"这个形态，被批准、被冻结，就成了基线。判断口诀：**配置提供"内容"，版本提供"位置"，批准提供"资格"——三者齐备，才成一个基线。**

**参考答案要点**：三词解耦见 §1.2；变体×版本见 §2.5；三分工见"本章判据"13；概念卡片·配置/版本/基线。

### Q3 版本号有了、流程走了、验证过了，为什么还是查不清？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "版本管理做好了，配置管理就做好了。" | 正是要翻的——把"版本"当"配置管理"的全部 |
| 中 | "版本只是刻度，配置管理是四大活动。" 结论对，基线/变更控制说不清 | 结论对，机制缺 |
| 好 | 版本是刻度（回答走到第几步，不回答哪一版被批准冻结）+ 版本四用途（追踪/回溯/并行/复现，解决不了"参照"）+ 配置管理=标识+控制+状态记录+审计（缺基线和变更控制，版本也管不住） | 判据 + 机制 + 四活动全到位 |

**产品侧 vs IT侧**：产品组答"冰链有 v2.1~v2.3 三个版本号，但没有一个固件基线，追溯温度记录找不到参照"；IT 组答"恒信有 final.zip 和 final_2.zip，但不知道哪个是哪个，回滚找不到地址"。同一个"版本管理≠配置管理"。

**反转话术**（对应 §2.1 + §3.3 + 章首）：老周"我们有版本号啊"——版本号是有了，但配置管理不是版本管理。**版本是什么？** 产品从诞生到退役，是一个连续的过程；但"沟通"必须是离散的——你没法在报障电话里跟客户说"我们的固件现在是'改过 17 次、其中第 9 次动了采集算法'的固件"。**版本，就是把"连续的时间"切成"可指认的格子"的那把刀。** 它解决四个问题：**追踪演进**（走到哪一步、每步改了什么）、**回溯**（出问题能回到旧版本）、**并行**（v1 在服役、v2 已开发）、**复现**（"你跑的是 v2.1"是沟通的最小公约数）。但注意——**这四个问题都解决不了"参照"问题**：版本只回答"走到第几步"，它没回答"哪一版是'被批准、被冻结、作参照'的"。而配置管理是完整的四大活动：**配置标识**（说不清"产品是什么"）、**配置控制**（变更失控）、**状态记录**（设计与实物对不上账）、**配置审计**（复现不了、责任推诿）。把四个活动套回冰链事故，一眼看出四个洞：固件是配置项但从没立过基线、走了流程但没有影响评估、只有一句"已推送 v2.3"没有台账、从没抽查实物与记录一致。**不是做了版本号就等于做了配置管理——四大活动一个都不能少。**

**参考答案要点**：版本定义见 §2.1；版本四用途见 §2.1；四大活动见 §3.3 + 冰链四洞表；概念卡片·版本。

### Q4 版本和基线差在哪？基线一旦建立就永远不能改吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "v2.3 发布三个月了，还不是基线？基线不能改。" | 正是要翻的——把"版本"当"基线"、把"冻结"当"死锁" |
| 中 | "基线三特征：被批准、被冻结、作参照。" 结论对，横竖分工/可变更说不清 | 结论对，机制缺 |
| 好 | 三特征（批准是资格/冻结是状态/参照是用途）+ 版本顺着流基线垂直切（里程桩 vs 收费站，横管流动竖管冻结）+ 冻结非死锁（基线可变更但必须走变更控制，改完立新基线） | 判据 + 横竖分工 + 非死锁全到位 |

**产品侧 vs IT侧**：产品组答"冰链 v2.3 是刻度，没有固件基线=有里程桩没收费站，任何固件都能随意改道"；IT 组答"恒信 final_2 连版本都算不上，更谈不上基线"。同一个"版本是刻度、基线是资格"。

**反转话术**（对应 §2.2~2.3 + 自查 #4）：基线在"让变化说得清"这件事上，比版本更重要——却更容易被忽略。ISO 10007 定义：**基线——经批准、确立了产品在某一时点的特性、并作为全生命周期各项活动参照的配置信息。** 拆开看三个特征，一个都不能少：**被批准**（不是"版本号到 v1.0 了所以它是基线"，而是组织正式批准、盖章确认的结果——从"流动状态"升级为"受控状态"，需要一个有权威的动作）；**被冻结**（基线一旦建立，任何人都不能随意改）；**作参照**（它是全生命周期所有活动的基准——"这版需求和基线的差别在哪？"没有基线，这个问题无从问起）。**一句话：基线是被批准冻结的参照。批准是资格，冻结是状态，参照是用途。** 再看这一章核心的反直觉命题——"版本顺着流、基线垂直切"：**横 = 与时间同向（版本）**——像尺子上的刻度，沿着时间轴排列，告诉你走到哪一步，只描述位置、不改变时间轴性质，是流动的；**竖 = 与时间垂直（基线）**——像横在路中间的闸门，垂直插入时间轴把时间切断：闸门左边是"自由区"（版本随便流动），右边是"受控区"（任何变化必须停下来接受批准），它制造分界、改变时间轴性质，是冻结的。**版本是高速公路上的里程桩——沿路排开，告诉你走了多远；基线是收费站——横在路中间，把路截断，过站要检查。** 一个顺着路，一个挡住路。那基线能不能改？**能。但必须走变更控制，改完建立新基线。** 基线可以变更——"冻结"不是"死锁"；随意改基线，等于把参照系拆了，那跟没有基线没有区别。

**参考答案要点**：基线定义与三特征见 §2.2；横竖分工见 §2.3；冻结非死锁见自查 #4；概念卡片·基线。

### Q5 "没有基线，变化就不可言说"——为什么？git 历史不够吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "git 历史都在，diff 一查就知道改了什么，不需要基线。" | 正是要翻的——把"记录"当"参照" |
| 中 | "没有基线就答不出'从什么变到什么'。" 结论对，原点/三问说不清 | 结论对，机制缺 |
| 好 | 原点原理（要描述变化必须有"从哪变起"的原点，海上说"我在动"没有岸标）+ git 历史是记录、基线是被批准冻结的参照（没有批准动作历史只是流水账）+ 三问（应该是什么/实际是什么/怎么变成这样，审计问的是第三问） | 原点 + 记录/参照对照 + 三问全到位 |

**产品侧 vs IT侧**：产品组答"冰链追溯温度记录，必须知道'从什么基线出发、经哪些变更、落在哪一版'——没有固件基线，一切变更查无实据"；IT 组答"恒信补了发布基线后，'上上个版本'才从猜测变成可执行指令"。同一个"没有基线变化不可言说"。

**反转话术**（对应 §3.1~3.4 + 案例进展②）：这一部分第一句就把基线的地位钉死：**从基线出发，一切变更都可描述；离开基线，一切变化都不可言说。** 为什么？——因为要描述一个变化，你必须有一个"从哪变起"的原点。"从 v1.0 变到 v1.1"这句话之所以有意义，是因为 v1.0 是一个所有人都认的、被冻结的、不会动的原点。没有这个原点，"变了"就没有参照——**像在茫茫大海上说"我在动"，却没有岸标。** 那 git 历史不是都在吗？注意：**git 历史是记录，基线是被批准、被冻结、被全项目认可的参照**。git 帮你记下了每次 diff，但它没有"批准"这个动作——没有批准动作，历史只是流水账，不是参照。老周有一条连续流动的版本链，却没有一个可以参照的冻结点——**变化在发生，但每一步都查无实据。** 配置管理的核心目的三问：**它应该是什么**（as-designed——设计规定的样子，由需求/设计配置和基线回答）、**它实际是什么**（as-built——实物真正长成的样子，由实物配置和状态记录回答）、**它是怎么变成这样的**（变更历史——每一次变更从哪来、到哪去，由变更控制和审计回答）。审计员问冰链的"这批记录是哪一版固件采的"，正是第三问——**它是怎么变成这样的**。老周答不上来，因为状态记录缺位、变更历史散乱。**配置管理的全部工作，就是让这三个问题在任何时刻都有答案。**

**参考答案要点**：原点原理见 §3.1；git vs 基线见自查 #5；三问见 §3.4；案例进展②。

### Q6 那场审计四个洞各缺什么？哪一洞最关键？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "缺个台账/缺个记录，补上就行。" | 正是要翻的——四个洞是系统性的，不是补一个文件 |
| 中 | "四大活动各缺一项：没基线/没评估/没台账/没审计。" 结论对，哪洞最关键/影响评估说不清 | 结论对，机制缺 |
| 好 | 四洞对照（标识：从没立基线/控制：没影响评估/记录：只有一句已推送/审计：从没抽查）+ 影响评估是那个"写下来就拦住"的洞（采集逻辑变没变写出来，追溯才有据）+ 合规升级走完五步（CR→评估→CCB→实施→新基线）每一步拦住显形什么 | 四洞 + 关键洞 + 五步全到位 |

**产品侧 vs IT侧**：产品组答"冰链固件升级四个洞——立基线/写影响评估/记台账/抽查实物"；IT 组答"恒信发布流程四个洞——没版本基线/没影响评估/只有日期文件夹/没审计"。同一个"四大活动一个都不能少"。

**反转话术**（对应 §3.3 + 案例进展①③）：老周说"我们配置管理做得挺好啊"——那是错觉。把四个活动套回冰链的固件事故，一眼就能看出缺在哪：**配置标识**——固件是配置项，但从没立过固件基线（该有的样子：固件是配置项，立过固件基线）；**配置控制**——"走了流程"，但没有影响评估，没问采集逻辑变没变（该有的样子：走 CR→评估→批准→新基线）；**状态记录**——只有一句"已推送 v2.3"，没有哪台箱子、哪个时间、升到哪一版的台账（该有的样子：版本台账）；**配置审计**——从来没做过（该有的样子：抽查实物，核实记录与实物一致）。**四个活动，四个洞。** 其中最关键的洞，往往是"影响评估"——修丢读数的 bug，动的是采集算法。影响评估一问，就该写出来："固件行为变化，历史温度记录的采集与判定逻辑随之变化，需知悉在役设备批次分布。"——**这一行字写出来，追溯就有据；不写，追溯就断。** 案例进展③里，老周这次升级 v2.4 走完了完整五步：影响评估（先写清这版改了什么、影响哪些配置项哪些批次）→ CCB 批准（影响全量在役设备，提到变更控制会）→ 实施（改完重新验证）→ 建立新基线（v2.4 升为新的固件基线）→ 状态记录（每台箱子从哪一版升到 v2.4、升级时间、结果，进版本台账）→ 三个月后配置审计（抽查二十台，一台台账写 v2.4、实物还是 v2.3，修正补推送）。疾控再问，老周打开台账——**答案有据可查。版本号只是刻度，基线是参照，流程是守护。三样都有，变化才说得清。**

**参考答案要点**：四活动见 §3.3 + 冰链四洞表；合规升级见案例进展③；作业指南尺 8/9/10。

### Q7 文件名不算版本，什么才算？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "final_2.zip 也是版本号，能区分新旧两个包。" | 正是要翻的——文件名版本不可回溯、不可复现 |
| 中 | "版本要精确对应到完整构建。" 结论对，回滚地址/同病复发说不清 | 结论对，机制缺 |
| 好 | 版本判据（对应到哪次完整构建：哪个提交编译、含哪几条变更）+ 版本是回滚的地址（有地址才能说"回滚到哪"）+ 同病复发（v2.doc→final_2.zip，文件命名永远管不住版本） | 判据 + 地址 + 同病全到位 |

**产品侧 vs IT侧**：产品组答"冰链固件版本要能对应到哪次构建、哪个提交——否则报障说'你跑的是 v2.1'也复现不了"；IT 组答"恒信 final_2.zip 既不知道哪次构建、也没经批准——回滚连地址都没有"。同一个"版本=回滚的地址"。

**反转话术**（对应 §2.1 + 案例进展②）：恒信小王"版本靠另存为 v2"——日期文件夹里躺着 final.zip 和 final_2.zip。李工说"我们有版本号啊"，Ada 说："**你把'文件名的版本'当成了'版本'，把'版本'当成了'基线'——三层都差一点。** 真正的版本号，要能精确对应到'哪一次完整构建'：这份产物是哪个代码提交编译出来的、包含哪几条变更。你这 final_2，既不知道它是哪次构建，也不知道它有没有经过批准，更不知道它和上一版差在哪——**它连'版本'都算不上，遑论'基线'。**" 版本判据一句话：**这个编号，能精确对应到"哪一次完整构建"吗？** 能——是版本；不能（比如只有文件名）——它还不算版本。李工看着那个文件夹问"所以出问题要回滚，我连'回滚到哪'都指不出来"——对。**版本是回滚的地址，基线是变更的参照。** 你只有日期文件夹，既没地址、也没参照——两个月前还能说的"变了"，两个月后就"不可言说"了。后来 Ada 帮恒信补了发布基线：每次发布，一个包 = 一个版本号 + 对应代码提交号 + 对应需求基线 + 变更记录，一次一张发布记录。从此"上上个版本"变成了一句可执行的指令。最扎心的是那句——第4章合同需求靠"v2.doc""最终版 v3.doc"管版本，现在是系统部署靠"final_2.zip"管版本，**同一个病，换了个文件后缀再犯一遍。** 为什么文件命名永远管不住版本？因为文件名是给"人眼"看的标签，版本号是给"追溯链"用的地址——标签只回答"这是第几个文件"，地址才回答"这是哪一次构建、从哪变来、能回到哪"。

**参考答案要点**：版本判据见"本章判据"4；案例进展②；版本四用途见 §2.1。

### Q8 契约链的基线和版本，是某一级专属还是每级都重复？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "基线对甲方、版本对乙方，各有归属。" | 正是要翻的——把"某级专属"当"机制全貌" |
| 中 | "契约链每级都是局部甲乙方。" 结论对，怎么逐级重复/边界说不清 | 结论对，机制缺 |
| 好 | 契约链（需求→方案→实现每对相邻环节都是局部甲乙方）+ 每级重复（甲方批准基线、乙方交付版本、验收又成下一环基线——不是某级专属）+ 技术契约 vs 商务契约边界（管对不对得上 vs 管赔不赔得起，勿混） | 契约链 + 逐级重复 + 边界全到位 |

**产品侧 vs IT侧**：产品组答"M3 固件需求立功能基线→固件实现发布产品基线，每级都是甲方冻结基线乙方交付版本"；IT 组答"恒信需求 Ada 批准立功能基线→设计立分配基线→系统发布产品基线"。同一个"契约链每级都重复"。

**反转话术**（对应 §4.2）：回想第6章的设计链：需求 → 方案 → 实现，一层层往下。如果给这条链加上"谁要求谁、谁兑现谁"的视角——**链上每一对相邻环节，都是一组局部的"甲方-乙方"关系**：需求方对方案方是甲方（要求"按这个需求做"）、方案方对实现方是甲方（约束"按这个设计做"）、每一环的乙方就是下一环的甲方。这是系统工程里成熟的思想——ISO/IEC/IEEE 15288 把每一级接口定义为"需方-供方协议"。而配置管理，给这条契约链提供了每一环都需要的两个东西：**基线，是每一级契约的"冻结端"；版本，是每一级契约的"交付端"。** 甲方把要求冻结成基线，乙方按基线开发；乙方产出的版本，交付给甲方验收；甲方验收通过，又成为下一环的基线。用恒信举个例：合同审批需求被 Ada 批准，立**功能基线**——这是对设计方的要求；设计方产出的设计，立**分配基线**——这是对实现方的约束；实现方产出的系统，发布**产品基线**。每一环的机制完全相同。所以日常说法"按基线开发，提交版本"完全成立——但注意：**它不是某一级专属，而是每一级都重复出现的通用机制。** 需求阶段有功能基线，实现阶段有产品基线——基线和版本在每一层都在，只是因为视角不同，看起来"属于"不同的人。一个边界要分清：**开发链内部的"甲乙方"是技术契约**（要求-兑现，管"对不对得上"）；**完整的外部甲乙方还多一层商务契约**（法律合同、付款、责任，管"赔不赔得起"）。机制同构，勿混为一谈——把"合同"和"契约链"当成一回事，是常见的越界。

**参考答案要点**：契约链见 §4.2；技术/商务契约边界见 §4.2 末；作业指南尺 12。

### Q9 第11章改字段前三问是个人尺子，配置管理把它变成了什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "配置管理是文员的活、文档的活，跟核心决策无关。" | 正是要翻的——配置管理是架构决策的保险丝 |
| 中 | "配置管理守护不可逆决策。" 结论对，同构表/尺子变流程说不清 | 结论对，机制缺 |
| 好 | 同构表四行（决策记录↔配置信息/不可逆识别↔基线冻结/推迟决策↔变与不变分离/影响分析↔变更控制）+ 尺子变流程（个人尺子靠自觉、流程靠结构）+ 决策基线化（六问记录变组织级动作）+ 保险丝（做对了守住、做错了早止损） | 同构 + 流程 + 保险丝全到位 |

**产品侧 vs IT侧**：产品组答"冰链'数据所有权归追溯域'是最不可逆决策——受控导出靠配置管理守护"；IT 组答"恒信编号规则被财务/台账/审计/电子签章引用——CR+影响评估拦住'今天就能上'"。同一个"配置管理守护架构决策"。

**反转话术**（对应 §4.1 + 案例进展④）：第11章回答"什么决策值得认真做"，这一章回答"认真做出的决策，怎么在持续的变化中被守护"。把两张图叠起来看，几乎一一对应：**决策记录六问 ↔ 配置信息**——都是"把决定写下来"，决策记录是决策的配置信息；**不可逆决策识别 ↔ 基线冻结**——识别出"不可逆"，所以把它冻结成参照，不让它被随手改掉；**推迟决策 ↔ 变与不变的分离**——推迟=把"可变的部分"外置，核心不变、变化的部分可替换；**变更影响分析 ↔ 变更控制**——改一个决策前，先评估波及范围。李工说的那个场景就是活教材：如果当时有这套东西，他改编号规则会先填 CR——影响评估一查，编号规则被财务、台账、审计、电子签章四个下游引用；评估单上会写"该变更影响全部历史合同数据，不可逆性高"——**这一行字写出来，当天就不敢"今天就能上"了。** 为什么？第11章你学的是"改字段前三问"——一把**个人尺子**；配置管理把它变成了**流程**：CR 必填影响评估、高不可逆必走 CCB。**个人尺子靠自觉，流程靠结构。** 你不是自觉不够，是一个人扛不住那么多"顺手改动"的记忆。所以——**配置管理是第11章那些不可逆决策的保险丝。决策做对了，靠它守住；决策做错了，靠它让你早发现、早止损。** 而"决策记录是决策的配置信息"——第11章的六问记录把一次决策从"当事人脑子里的知识"变成"组织的资产"；配置信息做的是同一件事，把它变成组织级动作：**让每一条关键信息，都落在某一份配置信息里，而不是某个人的脑子里。**

**参考答案要点**：同构表见 §4.1；案例进展④；守护判据见"本章判据"11。

## 四、知识卡片

### 一页图（配置 · 版本 · 基线 · 配置管理）

```
配置 = 实体被记录下来的形态（配 + 置 = 组合成形）
  配置项 = 被纳入管理的实体（对象——被管起来的那个东西）
  配置   = 实体被记录的关联功能+物理特性（形态——它该有的样子）
  配置信息 = 记录那些特性的资料（记录——拿什么核对）
  三个隐形过滤器：类别 / 记录 / 关联
  参数是零件，配置是装好的整机——改一个参数，整机形态就变

版本 = 时间轴上的演进刻度（横 · 与时间同向）——回答"走到第几步"
  主.次.修订（SemVer）；修订 Rev A/B/C = 更细粒度的内部次数
  版本 = 回滚的地址、沟通的最小公约数
  变体 = 空间并存形态（标准版/医疗加强版）——与版本正交

基线 = 被批准冻结的参照（竖 · 垂直切断时间）——回答"哪一版被盖章"
  三特征：被批准（资格）· 被冻结（状态）· 作参照（用途）
  三种正式基线：功能（要做什么）→ 分配（由谁实现）→ 产品（实际是什么）
  版本顺着流，基线垂直切：里程桩顺着路排，收费站横在路中间

没有基线，变化就不可言说
  变更控制：冻结 → 变更 → 再冻结（CR → 影响评估 → CCB → 实施 → 新基线）
  四大活动：配置标识 → 配置控制 → 状态记录 → 配置审计
  核心目的三问：应该是什么 / 实际是什么 / 怎么变成这样的

配置管理 = 架构决策的守护者（保险丝）
  决策记录↔配置信息 · 不可逆识别↔基线冻结 · 推迟↔变与不变分离 · 影响分析↔变更控制
  契约链：基线 = 每一级契约的冻结端，版本 = 交付端
  可剪裁：复杂度与责任等级匹配；底线"版本可指认、变更可追溯"
  价值：省钱（返工/报废/精确召回）· 赚钱（变体/资质/速度）· 保钱（责任/知识）
```

### 金句（书"本章判据"提炼）

- **配置不是参数文件——参数是零件，配置是装好的整机：参数只是记录形态的图纸，形态才是配置。**
- **版本只是时间轴上的刻度；基线才是被批准冻结的参照——版本顺着流、基线垂直切：里程桩顺着路排，收费站横在路中间。**
- **把版本当基线，等于把里程桩当成收费站——你确实知道路走了多远，但没人拦着检查，任何车都能随意改道。**
- **没有基线，变化就不可言说——要描述一个变化，必须有"从哪变起"的原点；离开基线，每一步都查无实据。**
- **版本是回滚的地址，基线是变更的参照——你只有日期文件夹，既没地址、也没参照。**
- **配置管理不是做了版本号就等于做完了——标识、控制、状态记录、审计四大活动，一个都不能少。**
- **配置管理是第11章那些不可逆决策的保险丝——决策做对了，靠它守住；决策做错了，靠它让你早发现、早止损。**
- **决策记录是决策的配置信息——让每一条关键信息，都落在某一份配置信息里，而不是某个人的脑子里。**
- **个人尺子靠自觉，流程靠结构——你不是自觉不够，是一个人扛不住那么多"顺手改动"的记忆。**
- **配置管理的复杂度，应该与产品的责任等级匹配——但"版本可指认、变更可追溯"这条底线，谁也不能省。**

## 五、课后作业

1. **书练习（与题卡同源）**：找出你们产品里"客户/用户能改的参数"，逐个用"配置三问"检验——它是配置，还是配置信息里的一个条目？（书练习 1）
2. **书练习**：检查你们当前最大的配置项——有版本号吗？版本号能对应到"哪一次完整构建"吗？有基线吗（被批准+被冻结+作参照）？（书练习 3）
3. **回部门落地**：结合现状，用十三把尺子（配置三问 / 变与不变分离 / 三分离 / 版本是刻度 / 基线三特征 / 版本顺着流基线垂直切 / 没有基线不可言说 / 变更控制循环 / 四大活动 / 三问 / 守护 / 契约链 / 三分工）给部门产品做一次"配置管理体检"——给出最该改进的三个事项，每个落到一个可检查动作。**两周后回来报告**：哪一项做成了、哪一项卡住了、卡在哪把尺子上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，1~2 小时内完成一次体检：
>
> 1. **配置三问（尺1）**：挑一个"客户能改的参数"，跑三问——被记录了吗？功能/物理特性吗？关联成整体了吗？三问全"是"才是配置。
> 2. **查变与不变分离（尺2）**：改这个参数，要不要动代码、重编译、重发布？要——可变部分没外置，核心资产写死了。
> 3. **查三分离（尺3）**：列五个配置项，每个问：它"该有的样子"（配置）和"记录它的资料"（配置信息）都有吗？
> 4. **查版本是刻度（尺4）**：版本号能对应到"哪一次完整构建"吗？不能——文件名不算版本。
> 5. **查基线三特征（尺5）**：被批准了吗？被冻结了吗？全生命周期拿它作参照吗？三问全"是"才是基线。
> 6. **查垂直切（尺6）**：画出版本链，标应该竖切的基线点（需求批准→功能基线、分配定案→分配基线、产品定型→产品基线）。
> 7. **查不可言说（尺7）**：最近一次变更，答得出"从什么基线变到什么基线"吗？答不出——还没有基线。
> 8. **查变更控制（尺8）**：变更走 CR→影响评估→CCB→实施→新基线吗？哪一步被跳过，代价是什么？
> 9. **查四大活动（尺9）**：标识/控制/状态记录/审计，各打"有/缺/半吊子"——四个洞哪个缺？
> 10. **查三问（尺10）**：应该是什么/实际是什么/怎么变成这样的——答不出的那一问，缺哪个活动？
> 11. **查守护（尺11）**：高不可逆的决策（数据模型/编号规则/数据所有权）被冻结成基线了吗？谁动它必须走变更控制吗？
> 12. **查契约链（尺12）**：画需求→设计→实现三层，每层标"基线（冻结端）+版本（交付端）"。
> 13. **查三分工（尺13）**：变体/版本/基线分开用了吗？"医疗加强版 v2.4"说得清是哪个吗？
>
> 卡住时：找到第一个"否"就能开工，不必打完全部。产出三件最该改进事项（每条 = 一个可检查动作）。
