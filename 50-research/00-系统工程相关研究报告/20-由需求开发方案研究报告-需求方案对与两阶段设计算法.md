## 〇、内核一句话

**设计与开发落地的本质，是逐对生成产品数据。** 把"从规定的需求到产品方案"之间的一串产品数据，切成相邻的"需求方案对"；对每一对执行同一个两阶段算法——**阶段一"需求 → 方案概要"**、**阶段二"方案概要分解"**——把上一份产品数据完整地开发成下一份。链上每一对都走同一算法，最后一份产品数据的方案树叶，就是开发线直接消费的输入。设计与开发由此统一为：**由需求到方案的一对产品数据的生成**。

```mermaid

    subgraph pair["一对产品数据（需求方案对）"]
        N["需求树叶<br/>（产品数据 N 的本体）"]
        A["方案概要末级节点<br/>（产品数据 N+1 的概要）"]
        S["方案树叶<br/>（产品数据 N+1 的本体）"]
        N -->|"阶段一 承接<br/>单承接约束 · 自下而上调树"| A
        A -->|"阶段二 分解<br/>承接覆盖检查"| S
    end
```

## 一、基础概念

### 1.1 产品数据

设计过程中每个环节的产出物。在 EOS 链路上即：规范化的相关方需求（01）、业务流程概要（02/03）、业务流程方案（04）、系统需求概要（05/06）、平台产品架构（07）等。

产品数据是设计开发加工的对象（见 [14 号文档 §1](14-产品数据研究报告-从产品定义到企业数字资产.md)）：设计与开发（ISO 9000 §3.4.8）的输入和输出都是需求，落成文档即产品数据。每份产品数据同时是上一轮的"方案"、又是下一轮的"需求"——这是"需求方案对"能连续推进的前提。

### 1.2 树形结构

每一份产品数据的内容都能组织成一棵树：

- 根节点为 **0 级**，一般是系统
- 逐级往下：1 级、2 级、……，最后是**树叶层级**
- 层级数量按产品数据实际情况确定，不预设固定深度
- 每一级节点和树叶都可以定义**物理意义**——物理意义主要由人类负责研究和制定（AI 辅助），是承接、构建、分解、审查的共同依据

### 1.3 概要与本体

同一棵树的两种形态：

- **概要**（xx概要）：不含树叶的树 = 树结构 + 各级节点 + 末级节点
- **本体**（xx）：含树叶的树 = 概要 + 树叶
- 例：需求概要 / 需求；方案概要 / 方案

"概要"不是另一份产品，而是同一份产品数据的**骨架形态**——先产出骨架（阶段一），再填充树叶（阶段二），同一份产品数据由概要演进为本体。

### 1.4 概要末级节点

概要中最深一层的节点，是概要的"骨架终点"。它同时承担两个角色：

- **承接方**（向上）：接受需求树叶的分配
- **分解源**（向下）：被分解为方案树叶

因此其物理意义必须**双向可用**——既写"可承接的需求类型"（承接判据），又写"分解产出的树叶类型"（分解源判据）。两条规则共享这一锚点，避免"承接说能来、分解实现不了"的结构性空洞。承接判据还进一步作为**对侧**分解规则（规则一）的制定输入——见 §二 承接锚定分解元规则。

### 1.5 需求方案对

取**一对上下序连续的产品数据**：上序 = **需求**，下序 = **方案**。整条链拆成若干对逐对推进，例如：

```
(规范化需求, 业务流程概要) → (业务流程概要, 业务流程方案)
→ (业务流程方案, 系统需求概要) → (系统需求概要, 产品架构)
```

每对之间是完整的"需求 → 方案"关系：方案方的每一份产出，都是对需求方某一组内容的设计与开发结果。

### 1.6 树形假设的边界

本方法有一个基础假设：**需求或方案类产品数据都可以被组织成树形结构**。该假设**成立，但依据是组织性的，不是内容性的**——"组织成树"指每条内容有一个唯一的归属位置，不指内容之间只有父子关系。

需求/方案的语义本质是**图**，有四类内容纯树放不下：

| 内容类型 | 现象 | 树形处理 |
|---------|------|---------|
| **横切** | 一条约束影响多个分支（如"可用性 ≥ 99.9%""所有操作需审计留痕"） | 给它独立的树位置（如 NFR 分支），用**影响面标注**勾连被影响的节点 |
| **共享** | 一个定义被多处引用（如"客户"贯穿多个流程、接口契约被多个组件消费） | 归属到一处，其余**引用**（跨文档引用只记录引用、不复制正文） |
| **多维** | 同一批需求可按功能/场景/性能/相关方多个维度切分 | 选一个稳定的**主组织维度**作树的轴，其余维度降为节点属性 |
| **循环/递归** | 业务流程自调用、嵌套，调用拓扑是环 | 树按归属组织层级，调用拓扑记在节点内容里（分形：每级元素的设计开发都是一个完整的 3.4.8） |

由此得出本方法对"树"的读法：**树是存储骨架，引用/追溯是关系载体**。相应地，承接分两种形态并存：

- **归属式承接**（功能性分配）：受单承接约束（§2.4、§3.2）
- **横切式承接**（NFR、约束、安全策略等）：留在独立分支作树叶，对多个方案节点的承接用**影响面标注**表达，不走归属分配

假设在两种情况下不成立：**①**要求树同时表达全部关系（把横切、共享也塞进分支结构）——方法已给出路：横切走独立分支 + 标注；**②**选不出稳定的主组织维度——树组织变成任意的，内容增长时会反复重构。对②的解法是：每一对在定义四套规则（§二）前，先定死主组织维度（对应"用户角色架构锚定法 / 输出产品架构锚定法"的选择）。

## 二、每对产品数据先定义四套规则

对每一对（需求 N，方案 N+1），**先定义以下四套规则，然后才能执行两阶段算法**。规则是这一对的本钱，定义不足则阶段一、阶段二都没有可执行的依据。四套规则**主要由人类负责研究和制定**（AI 辅助）：主组织维度的选择、各级节点的物理意义、父子节点关系规则，都是判断性工作，制定权在人；AI 辅助候选生成、一致性检查与反例检验，并按规则执行两阶段算法与机械验收。

两条分解规则（规则一、规则二）共同遵循一条**元规则——承接锚定分解**：制定"末级节点 → 树叶"的分解规则时，必须把**消费方承接结构的末级节点物理意义及其特征**作为分解规则的构成性输入——切点与粒度由消费方语义域锚定，使树叶**按构造**可被消费方单点承接/消费；本侧语义原子性退居下界守护（树叶保有独立语义、可独立验证）。消费方语义域切不动的语义整体（一致性约束、接口语义等关系性内容）是唯一合法余数，走锚侧出口（§2.4 节点拆分、§1.6 横切式承接）。由此，单承接不再是迭代试错的目标，而是分解规则的内置保证。"先定义规则"指对当前锚的初始立法；锚在阶段一被扩展（§3.3）时，受影响的分解规则随影响面复查同步修订——立法随锚演进。

### 2.1 规则一：需求概要末级节点 → 需求树叶的分解规则

决定需求树叶的粒度与边界——**不是需求方内部的自足规则**，而是元规则在需求侧的实例化：把**方案概要末级节点的物理意义及其特征**（§1.4 承接判据）作为制定分解规则的构成性输入。

- **切点判据（承接锚定）**：需求树叶沿方案概要末级节点语义域的边界切分，切点落在消费方语义域边界上——**单承接由构造保证**，每片树叶天然可分配到单个末级节点
- **下界守护（语义原子性）**：树叶必须保有独立语义、可独立验证；锚语义域切不动、再分即碎的语义整体不硬切（真余数，走锚侧出口：§2.4 节点拆分、§1.6 横切式承接）
- 用途：进入分配的需求树叶按构造可单点承接，粒度均匀、边界清晰

### 2.2 规则二：方案概要末级节点 → 方案树叶的分解规则

决定方案概要末级节点如何分解为方案树叶，是**阶段二执行的依据**。与规则一同构，是元规则在方案侧的实例化：方案树叶的消费方是下一对的承接结构（§5.2 上一份的本体=下一份的输入），末对的消费方是开发线（§5.4）。

- **切点判据（承接锚定）**：方案树叶沿消费方承接语义域的边界切分——**按构造**是下一轮可承接、开发可消费的最小单元（组件、配置单元、操作活动等）
- **下界守护（语义原子性）**：每片方案树叶保有独立语义、可独立交付；锚语义域切不动的语义整体不硬切（真余数，走锚侧出口）
- 用途：方案树叶直接决定下一轮承接与开发的输入形态，也决定本对覆盖检查（§4.2）的比对粒度

### 2.3 规则三：方案概要各级节点的构建规则

决定各级父节点的语义、层级划分、兄弟节点边界，是**阶段一"自下而上调树"的依据**。

**由子节点生成父节点，主要由人类负责研究和制定（AI 辅助）**：在定死的主组织维度上归组子节点、归纳公共类、为父节点写物理意义、定父子边界——这是判断性工作，不存在机械的父节点生成算法；AI 辅助候选生成、一致性检查与反例检验。人类制定的父语义按三条质量判据自查，AI 据此辅助检查：**独立可定义**——父语义能独立于子节点清单表述，回答"这一组共同是什么"，不是清单的拼接；**非兜底**——"其他/杂项"式语义筐不合格，无独立语义域的父节点会在后续承接中变成语义黑洞；**最小泛化**——选能覆盖子语义之并的最小类域，父语义域贴近子并，只留生长余量、不留模糊空间。

- **收敛判据**（两条机械可查）：
  - **覆盖完整**：每个非叶节点语义 ⊇ 其子节点语义之并
  - **兄弟互斥**：同层兄弟节点语义两两不重叠
- 两者满足即收敛；新末级节点归不进任何现有父节点的语义域时，才在更高层新增父节点

### 2.4 规则四：方案概要末级节点承接需求树叶的规则

决定需求树叶如何分配到概要末级节点（语义匹配判据），是**阶段一的分配依据**。

- **核心约束（单承接）**：一条需求只能被一个概要末级节点承接——可 N:1，不可 1:N
- **对称约束（承载量）**：一个末级节点承接的需求超限（粒度不匹配/数量过多）时，触发节点拆分（Split）

## 三、阶段一：需求 → 方案概要

**目标**：把需求树叶分配到位，产出完整的方案概要（树结构 + 末级节点）。

### 3.1 步骤流程

```mermaid
flowchart TD
    A["挑选几条未分配的需求树叶"] --> B{"现有末级节点<br/>可直接承接？"}
    B -- 是 --> C["直接分配 → Reuse"]
    B -- 否 --> D{"现有末级节点<br/>改进后能承接？"}
    D -- 是 --> E["分配到拟改进节点 → Improve<br/>（登记改进意图）"]
    D -- 否 --> F["生成新末级节点 → Add"]
    C --> G["自下而上调树<br/>收敛 = 覆盖完整 + 兄弟互斥"]
    E --> G
    F --> G
    G --> H{"单承接约束成立？<br/>一条需求只归一个末级节点"}
    H -- 否 --> I["回规则一重切需求树叶<br/>切点带进锚语义（元规则）"]
    I --> A
    I -.->|"真余数"| K["锚侧出口<br/>节点拆分 / 横切式承接"]
    K --> G
```

1. **挑选几条未分配的需求树叶**作为本轮对象
2. **查直接承接**：方案概要中有没有现成末级节点可直接承接
   - 有 → 分配需求树叶到该节点
   - 没有 → 进入 3
3. **查改进承接**：基于需求语义和概要末级节点语义，看有没有末级节点**改进后能承接**
   - 能 → 分配需求到拟改进的末级节点（登记改进意图，待后续执行改进）
   - 不能 → 进入 4
4. **新增承接**：基于需求语义和末级节点的物理意义，**生成新的末级节点**承接需求
5. **自下而上调树**：若产生新增/改进的末级节点，由人类主导、AI 辅助，归组子节点并归纳/修订各级父节点的物理意义，自下而上调整或新增各级节点，直至机械收敛（覆盖完整 + 兄弟互斥）

### 3.2 单承接约束与余数处理

- **约束**：一条需求只能被一个概要末级节点承接（可 N:1，不可 1:N）。单承接**由构造保证**——规则一按元规则以锚语义定切点，树叶天然可单点分配，迭代试错不是常态机制
- **违规处理**：仍出现 1:N 时先判类型——分解规则未按元规则制定（切点未带进锚语义）属**程序违规**，回炉重制定后重切；**真余数**（消费方语义域切不动的语义整体）走锚侧出口：承载量超限触发节点拆分（§2.4），约束/策略类内容走横切式承接（§1.6）
- **下界守护**：语义原子性——树叶保有独立语义、可独立验证，防止为迁就锚的切法把语义整体切碎
- **方向是单向的**：概要末级节点是锚，需求是适配方——锚不只被动接收分配，还通过规则一**预先整形**需求侧的切法；违反时重切需求，而不是迁就需求改概要

这与"需求分解分配分析"的单分配约束同构：需求方负责把树叶切到可单点分配，方案方概要保持稳定，只在必要时（§3.4）调整。

### 3.3 改进的涟漪效应

"改进后承接"不是局部操作。对末级节点的 Extend/Split/Merge 会扰动**已承接**的其他需求树叶：

- Split 后，原已承接的需求要重分配到子节点
- Merge 后，语义域收敛，某些既有需求可能失配

**任何改进操作后必须执行"影响面复查"**：重新核对既有承接，失配则批量重分配或回退改进。否则会在阶段一留下隐性失配，到符合性审查才暴露。改进同时改变规则一/规则二的制定输入（新增或改动的末级节点物理意义进入锚语义），受影响的分解规则须随影响面复查同步修订——立法随锚演进。

### 3.4 与资产优先原则同构

| 阶段一动作 | 资产优先原则 | 说明 |
|-----------|-------------|------|
| **直接承接** | Reuse（复用） | 现有末级节点语义域直接覆盖需求 |
| **改进后承接** | Improve（Extend/Split/Merge） | 扩展/拆分/合并现有末级节点后承接 |
| **新增承接** | Add（新增） | 现有节点改进后也无法承接，才新增 |

优先级始终：**复用 → 改进 → 新增**。改进的代价（涟漪、影响面复查）决定了它排在新增之前——能复用就不改进，能改进就不新增。

## 四、阶段二：方案概要分解

**目标**：把方案概要末级节点分解为方案树叶，产出完整方案（本体）。

### 4.1 步骤

1. **选择拟改进的或新增的概要末级节点**作为本轮对象
2. 基于语义和末级节点及树叶的物理意义，**对末级节点分解**，产出方案树叶
3. 执行承接覆盖检查（§4.2）

### 4.2 承接覆盖检查（阶段门禁）

每个末级节点分解完成后，检查：

> **该末级节点承接的所有需求树叶的语义 ⊆ 其方案树叶语义之并**（满足度）

这是需求符合性审查第 3 层（满足度）的**设计期预演**。未覆盖 → 回阶段二补树叶，或回阶段一调整承接关系。这防止"承接了但没实现"的空洞。

覆盖检查是两阶段之间的门禁：阶段一决定"谁承接谁"，阶段二决定"承接的有没有被实现"，两者在此对上。

---

## 五、两阶段的衔接与整链推进

### 5.1 追溯边贯穿

- 阶段一每次承接建立"需求树叶 → 概要末级节点"追溯边
- 阶段二延伸为"需求树叶 → 概要末级节点 → 方案树叶"

**追溯矩阵是设计过程自然生成的**，不需要另起炉灶——每一对的两阶段跑完，追溯边就落一条完整的链。

### 5.2 上一份的本体 = 下一份的输入（不复制）

- 每一份产品数据的本体视图（树叶）直接作为下一份概要的承接输入
- 链条连续、无中间态冗余
- 例：业务流程方案（04）既是业务流程概要的本体，又是系统需求概要（05）的承接对象

这保证整条链不需要额外的"交接文档"或"中间状态"，上一份的树叶就是下一份的需求。

### 5.3 整链逐对推进（EOS 链路实例化）

在 EOS 当前链路上：

```mermaid
flowchart LR
    A["spr 01<br/>规范化的相关方需求"] -->|"对①"| B["bph 概要 02/03<br/>业务流程概要"]
    B -->|"对②"| C["bpd 方案 04<br/>业务流程方案"]
    C -->|"对③"| D["srh 概要 05/06<br/>系统需求概要"]
    D -->|"对④"| E["pa 架构 07<br/>平台产品架构"]
    E -->|"方案树叶 = 开发输入"| F["开发线"]
```

每对都执行"两阶段算法"。概要类产品数据由**架构级**（定树结构 + 末级节点清单）+ **详细级**（定末级节点内容，为承接提供判断依据）两档构成，合起来是一份概要产品数据——即"概要"这份产品数据的树形骨架（架构级）与末级节点的内容深度（详细级），两者共同支撑阶段一的承接判断。

### 5.4 与开发对接

- 最后一份产品数据的**方案树叶**就是开发线可消费的最小单元（组件、配置单元、引擎模型等）
- 设计终点通过方案树叶直接对接开发输入，不需要再造一份"开发需求"
- 设计与开发统一为：**由需求到方案的一对产品数据的生成**

## 六、与现有方法论的关系

本算法不是凭空新造，而是把仓库里已定案的方法论落实为可执行流程：

| 本算法概念 | 现有方法论 | 对应关系 |
|-----------|-----------|---------|
| 承接 → 改进 → 新增 | 资产优先原则 Reuse > Improve > Add | 阶段一的分配策略 |
| 单承接约束 | 需求分解分配分析的单分配约束 | 一条需求只归一个末级节点 |
| 阶段一 / 阶段二 | 概要 → 方案两阶段工作法 | 先出骨架再填树叶 |
| 承接覆盖检查 | 需求符合性审查第 3 层（满足度） | 阶段二的门禁 |
| 概要末级节点识别 | 架构末级节点识别方法 | 概要骨架的终点 |
| 自下而上调树收敛 | 覆盖完整 + 兄弟互斥 | 树自洽的两条机械判据 |
| 追溯边贯穿 | 追溯矩阵 | 设计过程自然生成，不另起炉灶 |
| 承接锚定分解元规则 | 概要末级节点双向可用·承接判据（§1.4）+ 锚定法同型推广 | 分解规则以消费方语义域为构成性输入，单承接由构造保证 |

---

## 七、结论

由需求开发方案，落地为**需求方案对的逐对生成**：

1. 每对先定义四套规则——需求分解规则、方案分解规则、方案概要各级节点构建规则、方案概要末级承接需求树叶规则；两条分解规则统一遵循**承接锚定分解元规则**：制定时把消费方末级节点的物理意义及其特征带进来，切点与粒度由消费方语义域锚定。规则（含各级节点物理意义与父子关系规则）主要由人类负责研究和制定，AI 辅助；执行与机械验收交给算法
2. 阶段一以概要末级节点为锚，用"承接 → 改进 → 新增"把需求树叶分配到位，自下而上调出方案概要的树形骨架；单承接由构造保证，违规仅剩程序违规（回炉重制定）与真余数（锚侧出口：节点拆分/横切式承接）两种情形
3. 阶段二把概要末级节点分解为方案树叶，以承接覆盖检查为门禁，保障"承接了的一定被实现"
4. 追溯边贯穿每一对，上一份的本体直接成为下一份的输入，链条连续无冗余
5. 最后一份产品数据的方案树叶对接开发线——**设计与开发由此统一为：由需求到方案的一对产品数据的生成**
