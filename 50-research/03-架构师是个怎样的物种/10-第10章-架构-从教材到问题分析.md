## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：架构到底是什么？为什么"画一张框图"不算做架构？系统、架构、架构描述这三个词，为什么混着说会让一个团队三个月都答不出三个问题、甚至丢一笔冷链订单？

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：10.2.1 三个词三层（弗雷格）→ 10.2.2 权威定义逐词拆（ISO 42010）→ 10.2.3 "不可还原"三判据 → 10.2.4 元素与关系 → 10.2.5 元素可换，本质不可换（体现与本质的分界）—— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：10.3.1 不是一张图（先看病）→ 10.3.2 不是一个而是一堆"XX 架构"（一个系统一个架构 + 两套维度）→ 10.3.3 不是框架（风格/框架/构架一条链）→ 10.3.4 不是静态图（设计准则 + 演进准则 = 免疫系统）→ 10.3.5 不是详细设计（分界 + 评审标的）—— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：10.4.1 为什么需要架构描述 → 10.4.2 相关方与关注点（天然冲突）→ 10.4.3 视点与视图（相机）→ 10.4.4 4+1 视图模型（场景是胶水）→ 10.4.5 架构是压缩 → 10.4.6 决策/变更/组织三回报 → 10.4.7 约束即解放 → 10.4.8 架构师的理论 → 10.4.9 架构师首先是一个工程师 —— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念（含根概念标注）

> 标注规则（v2.1）：按第1章 §1.2.4 根概念四标准（原子性/生成性/不可替代性/递归性）标出本章档案中的**承重柱**——先抓根、再展骨架。本章的承重柱 = **架构**（见头注论证）；核心概念为骨架层枢纽。

1. **架构**（architecture）**【根概念 · 本章承重柱】**：系统在其环境中的基本概念或属性，体现在其元素、关系以及设计演进原则之中（ISO/IEC/IEEE 42010:2011）。= 系统不可还原的涵义。判据：三问（去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗）。**承重柱证据**：原子性（ISO 定义不再依赖域内其他概念，fundamental=地基级）/ 生成性（架构描述=对架构的表达、设计准则与演进准则内嵌于架构定义"设计演进原则"、三判据辨认架构，全部从它派生或围绕它）/ 不可替代性（去掉"架构"，本章方法论不成立）/ 递归性（开篇枢纽→三幕→章末反转层层生效；到第11章架构设计、第12章架构决策、第16章架构师继续作枢纽）。与框架（"这一个" vs "这一类"）、与详细设计（不可还原 vs 可还原）的辨析见 §10.3.3 / §10.3.5；体现与本质的分界（元素/关系/准则是"体现"不是"等于"）见 §10.2.5。
2. **架构描述**（architecture description）【骨架 · 枢纽】：对架构的表达——按"相关方 → 关注点 → 视点 → 视图"组织起来的制品集合（ISO 42010）。判据：链条完整吗？每个视图能说出"在回答谁的什么问题"吗？它从架构派生（没有架构就没有"对架构的表达"），是本章第二承重概念。
3. **系统**（system，近界·非档案）：实际存在的那个东西（M3 实物）——弗雷格的"指称"。有生命周期（会报废、会换代）；架构（那组不可还原的决定）活得比系统长。
4. **相关方 / 关注点**（stakeholder / concern）：对系统有利益关系的任何个人/团队/组织 / 对系统的任何兴趣（功能性/非功能性/约束性）；关注点天然冲突、只能权衡。
5. **视点 / 视图**（viewpoint / view）：怎么看的规则（镜头设置）/ 按规则画出来的产物（照片）。每个视图是刻意的"不完整"。
6. **设计准则 / 演进准则**（design principle / evolution principle）：怎么造 / 怎么变——合起来是架构的免疫系统。
7. **框架**（framework，辨析概念）：对某一类事物/活动预制的"骨架 + 位置 + 组织规则"，内容后填——用框架 ≠ 有架构（骨架 ≠ 决策）。
8. **构架**（skeleton，辨析概念）：名词的动词化，本义"搭建承重骨架"——《说文》"构=盖也，从木"；三词分工：构架立骨架、架构定决策、框架给半成品。
9. **架构风格 / 模式**（architecture style / pattern，辨析概念）：架构决策的套路（微服务/事件驱动/分层）——结构体系的选择，不是建筑本身。

### 关联概念（近界 · 辨析）

- **系统 ≠ 架构 ≠ 架构描述 = 弗雷格模型（第1章补充）**：指称（系统）≠ 涵义（架构）≠ 符号（架构描述）——"晨星 / 暮星"都是金星，两个词不同、呈现方式不同、指向同一个东西；架构领域翻版成 M3 的箱子 / 那组决定 / 水忠的图。
- **架构 ↔ 概要定义（第6章）**：第6章那棵树的树干树枝是概要定义，管结构、管承接；架构是那棵树里不可还原的部分——"概要定义是架构的一种描述；架构是概要定义背后那些'去掉就不是它'的决定"（§10.2.1 末）。
- **架构 ↔ 元素 / 关系 / 原则（体现）**：架构本身是那组基本概念/属性（本质定义），元素/关系/准则是这份定义落在地上的形态——"体现在"≠"等于"；元素可换，本质不可换（传感器换灵敏的还是 M3，把"全程可追溯"换成"温度控得准就行"就不是 M3）；职责线：元素=模块工程师、本质=系统架构师（§10.2.5）。
- **三判据 ↔ 第1章反事实检验**：第1章用"去掉它，这个领域还成立吗"识别领域枢纽；本章用同一动作识别系统架构——同一个动作，换个对象（§10.2.3）。
- **架构 ↔ 涌现属性（第2章）**：第2章讲飞机"部件全对未必能飞"；本章落到架构层面——可靠性瓶颈通常在组件交互模式，不在单个组件（§10.2.4）。
- **架构 ↔ 压缩学习（第1章）**：压缩学习的对象是知识（人脑是压缩机器），架构压缩的对象是系统——同一个原理：用结构消化复杂度；架构是**保真**压缩（§10.4.5）。
- **架构 ↔ 评审对目标（第8章）**：架构评审审的是架构描述是否对得起系统的不可还原涵义（第8章"评审对目标"的延伸，§10.4.9 前 + 章末）。
- **架构 ↔ 不可逆（第12章种子）**：一个决定"去掉就不是这个系统"，是因为改它的代价几乎不可逆——架构，是对不可逆决策的提前投资（第12章展开）。
- **架构师 ↔ 工程师（第9章）**：架构师首先是一个工程师——第9章六项底座一项不能少；在底座上再长四项系统级能力 → 十项清单第16章收全（§10.4.9）。
- **架构框架 ↔ 架构描述（严口径）**：4+1、TOGAF 等是"预定义的视点集合"——同一种"骨架+规则"，填进去的是架构描述，不是架构本身（§10.3.3 注 / §10.4.4 末）。
- **构架 / 架构 / 框架 三词分工**：构架立骨架（骨架可见=构架验收标准）、架构定决策（决策与演化原则=架构灵魂）、框架给半成品——"构架思维"做架构最易产出"骨架立起来了、理由还悬在空中"的画图匠作品（§10.3.3 末 / 第16章）。
- **架构风格 → 框架 → 架构 一条链**：风格（抽象的决策套路）→ 固化成框架（套路的具体化）→ 应用到具体系统 + 叠加独特决策 → 架构（这个系统的本质属性）——框架给你骨架，不是决策（§10.3.3）。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 架构是系统不可还原的涵义——"断链即报废的疫苗，能从出库一路撑到接入冷库、全程可追溯"那组决定；概要定义是架构的一种描述，架构是概要定义背后那些"去掉就不是它"的决定（§10.2.1）。
2. 三个词三层 = 弗雷格模型（指称 ≠ 涵义 ≠ 符号）：系统（指称）/ 架构（涵义）/ 架构描述（符号）（§10.2.1）。
3. 推论一：同一个架构可以有无数种描述；反过来同一张图可能根本没描述对架构（水忠的图只画了元素，没画关系，更没画原则）（§10.2.1）。
4. 推论二：系统不等于架构——系统有生命周期（会报废、会换代），架构（那组不可还原的决定）活得比系统长（作为经验、教训、下一代设计前提继续存在）（§10.2.1）。
5. "基本"（fundamental ← fundus 地基）是整句定义的核心——地基一动，整栋楼都动；从本义推出三判据（不可再分 / 不可缺失 / 不可替代）（§10.2.3）。
6. 定义里是"概念**或**属性"（or）不是"概念和属性"（and）——中文翻译常写成"和"；"或"更宽松：从概念切入或从属性切入，两条路都能到架构，不必同时具备（§10.2.2）。
7. "在它的环境中"——环境决定哪些属性才算"基本"：同一个温控设备，实验室台架上可以是"温度控制单元"，冷链运输里必须包括"断链检测与补传"；环境变了，什么算"基本"就变了（§10.2.2）。
8. 关系比元素更要紧——系统的涌现属性来自关系，不来自单个元素；可靠性的瓶颈，通常不在单个组件，而在组件之间的交互模式（§10.2.4）。
9. 三判据 = 第1章三步识别法里最狠的一步（反事实检验）用在系统上——同一个动作，换个对象（§10.2.3）。

**第二幕 · 磨边弧的机制（不是什么）**
10. 架构和图不在同一个世界——图是纸上的、可见的、会过时的；架构是系统里那组不可还原的决定，真实存在但不因你没更新图就消失；"架构不长什么样"（视觉范畴 vs 逻辑范畴——宪法 / DNA / 组织架构类比：只有投影，没有"原图"）（§10.3.1）。
11. 一个系统只有一个架构——所有"XX 架构"都是对同一个架构的描述（视图），来自两套独立分类维度：关注域（业务/数据/应用/技术，按"看什么"切分）× 抽象层次（概念/逻辑/物理，按"多详细"切分），交叉出每一个具体视图（§10.3.2）。
12. 架构风格 / 模式 = 架构决策的套路（微服务/事件驱动/分层——结构体系的选择，不是建筑本身）；框架 = 把套路"物化"成的可复用制品（骨架 + 位置 + 组织规则，内容后填）——用框架 ≠ 有架构（骨架 ≠ 决策），试金石一句"删掉它，系统还在吗"（§10.3.3）。
13. 架构不是静态快照——它自带"怎么造"和"怎么变"两套规则：设计准则（约束从无到有的创建过程）+ 演进准则（约束随时间变化的过程）= 免疫系统；缺一个：只有设计准则→系统一改就坏（微服务退化成分布式单体）；只有演进准则→建出来就不对（§10.3.4）。
14. 架构是活的学习系统——免疫系统两点（定义什么是"自我" + 主动防御变化）；每次架构层面的变更失误，沉淀为一条架构原则的更新（§10.3.4）。
15. 构架三词分工——构架立骨架（"构架出来"默认验收=骨架可见）、架构定决策（决策与演化原则才是灵魂）、框架给半成品；用"构架思维"做架构最易产出图漂亮、框齐、问"为什么这么分、被否掉的备选死在哪"没人答得上的东西——骨架立起来了，理由还悬在空中（§10.3.3 末 / 第16章"画图匠 vs 架构师"）。
16. 架构 × 详细设计的分界 = 不可还原——改它花多大代价、影响多大范围、几乎不可逆；三问皆"是"是架构、三问答"否"是详细设计；**架构评审的标的，从来不是"所有重要的决定"，而是"那组去掉就不是它的决定"**（把采集间隔当架构评审=拿大炮打蚊子）（§10.3.5）。

**第三幕 · 往哪去的机制（运用）**
17. 涵义锁在脑子里，没有用——架构必须被表达出来，才能被共享、被讨论、被检查、被传承；架构描述就是这个"表达"（§10.4.1）。
18. 关注点天然冲突（*The concerns of stakeholders are frequently broad, varied, and conflicting*）——冲突不可消除，只能权衡；权衡有一个前提：你得先能看到每个方面（看不见安全就不会为安全取舍）（§10.4.2）。
19. 视点（怎么看的规则）× 视图（产物）= 相机比喻（角度/镜头/滤镜 vs 照片）；每个视图是刻意的"不完整"——把不关心的部分剥离掉、只保留本质，视图就是架构的概念化切片（§10.4.3）。
20. 视图的完备性由相关方及其关注点决定，不由方法论决定——三步白板推导（识别重要相关方 → 明确核心关注点 → 按语言聚类 → 查有没有漏）；"我们需要几个视图"是方法论之争，"我们的相关方是谁"是项目分析（§10.4.3）。
21. 4+1 视图模型的场景（+1）不是第五个视图，是胶水——拿一条真实使用场景横穿四个视图，检验它们是否互相矛盾；走不通，说明四个视图是四个系统（§10.4.4）。
22. 架构是保真压缩（不是丢信息）——把 500 个服务 × 200 个接口 × 50 个数据对象压成"12 个业务域 × 每域 5-8 个构件"的骨架；共享心智模型让新成员入门、跨团队协作、决策讨论有共同语言（§10.4.5）。
23. 架构在三个更硬的维度上起作用——决策层面（划定解空间，削减的不是工作量而是决策量）/ 变更层面（事前预判影响、事中吸收不崩溃、事后从变更中学习）/ 组织层面（康威定律：组织设计出来的系统结构是其沟通结构的副本；构件边界=团队边界）（§10.4.6）。
24. 约束即解放——消极自由（freedom from，没人拦）vs 积极自由（freedom to，知道怎么做对）；架构只约束"不改就会造成灾难"的东西，把团队从无穷的重复决策里解放出来；"管得最准"好过"管得最多"（§10.4.7）。
25. 架构师的核心能力，不是"做出正确的决策"，而是"识别哪些决策如果不正确，后果会很严重"——对不重要的事情不决策，本身就是一种好的架构决策；前提是架构师首先是一个工程师（第9章六项底座一项不能少）（§10.4.7 / §10.4.9）。
26. "什么是重要的"，本身需要判断——架构师对系统的理论（靠什么成功 / 最大压力在哪 / 什么做错了最致命）决定"什么重要"（Ralph Johnson：*Architecture is about the important stuff. Whatever that is.*）；而"不可还原"指向不可逆——架构，是对不可逆决策的提前投资（第12章展开）（§10.4.8 / 章末）。
27. 目的判据——"基本"是对系统在其环境中的**目的**而言必要且充分（IEV 831-01-01 Note 2；ISO/IEC/IEEE 42030:2019 背书"以目的检验架构"——确认/评审以目的为依据、验证以规定需求为参照，§10.2.3 术语注）；目的变了，"基本"就变了；目的悄悄漂移，是架构失效的第一病因（§10.4.8 埋种子、第14章展开）（§10.2.3 / §10.3.4）。
28. "基本"与"粗细"正交——共识算法很复杂但可以是基本，变量命名很简单但永远不是；架构分布在"基本"这一行，与粒度无关（§10.3.2 误区提醒 / 自查 15）。

### 本章判据（九条）

> 九条判据里，"架构描述组织链""关注点天然冲突"两条直接出于 ISO 42010；"一个系统一个架构"是本书从 42010 视图链推出的读法（§10.2.1 已自注）；其余六条是本书凝练（其中架构三问的判据锚"对目的而言必要且充分"出自 IEV 831-01-01 Note 2，三问形式为本书凝练）——不是标准条文，但都当场可检验：欢迎检验、欢迎校准。

1. **架构三问**：这个决定"去掉还是这个系统吗 / 缺少系统垮吗 / 换掉性质变吗"——三问都答"是"，才是架构；答"否"的，是详细设计，不是架构。**三问同一锚：是否还服务于系统在其环境中的目的**（目的变了，"基本"就变了；防误用三关——目的关 / 角色关 / 层级关，见 §10.2.3 术语注）。**违反即崩：把"采集间隔 1 分钟改 5 分钟"当架构来评审——三问答"否"，它只是详细设计；真正要命的"数据所有权归云端还是归硬件"，反而没人当成架构审。**
2. **三个词三层**：系统（指称，实际存在的那个东西）≠ 架构（涵义，不可还原的本质）≠ 架构描述（对涵义的表达）。图过时了 ≠ 架构过时了——决策可以一直有效。**违反即崩：把那张四层方块图当成了架构——图三个月没更新，团队就以为"架构烂了"；可他们真正守着的"老规矩"（数据所有权归追溯域）图里从没画出来过，图烂了决定还活着。**
3. **一个系统一个架构**："业务/数据/应用/技术"是关注域视角，"概念/逻辑/物理"是描述层次，"微服务/事件驱动"是架构风格——都不是多个架构（42010:2022：被架对象扩展为 EoI，分析/权衡阶段可有多个候选架构，被采纳的只有一个，§10.3.2 术语注）。**违反即崩：万辉的四张图各画各的——同一份"合同"在业务图里是一条流程、在数据图里是三个实体、在应用图里是一个流程实例、在技术图里干脆没有——一条场景走不完四张图，四张图就是四个系统。**
4. **架构描述组织链**：相关方 → 关注点 → 视点（怎么看的规则）→ 视图（产出的切片）→ 组合成完整架构描述。每个视图要能说出"它在回答谁的什么问题"。**违反即崩：视图答不出"在回答谁的什么问题"——水忠团队从没摆出过"M3 有哪些相关方、各关心什么"，架构评审只能对着四层方块图走过场，监管、司机、维修、制造各要的东西全漏了。**
5. **关注点天然冲突**：相关方的关注点是宽泛、多样、且相互冲突的——冲突不可消除，只能权衡；权衡的前提是看到每个方面。**违反即崩：去找"让所有相关方都满意"的方案——监管要更多加密留存、老板要快上线，天然对冲，没有任何架构能让"快、便宜、安全、全功能"同时到顶。**
6. **约束即解放**：架构只约束"不改会灾难"的决定，把团队从重复决策里解放出来，回收积极自由。"管得最准"好过"管得最多"。**违反即崩：什么都不约束——每次加需求都重新吵"数据放哪个库、要不要拆服务"，7 个库 × 3 种模式 = 21 种可能，选择瘫痪。**
7. **设计准则 + 演进准则 = 免疫系统**：设计准则管"怎么造"，演进准则管"怎么变"；缺一个，系统要么一改就坏，要么建出来就不对。架构不是静态图，是活的学习系统。**违反即崩：只有设计准则、没有演进准则——第二个月有人直接改同事服务的内部实现，架构还标着"服务独立部署"、实际已耦合，微服务退化成"分布式单体"。**
8. **框架 ≠ 架构**：框架是"这一类"的组织方式（骨架+位置+组织规则，内容后填），架构是"这一个"的组织本质。用框架 ≠ 有架构——框架给骨架，决策得自己做。**违反即崩：以为"用了 Spring Cloud 就是微服务架构"——换掉 Spring Cloud，系统还是那个系统；改动服务边界，系统就不是那个系统了。**
9. **构架立骨架，架构定决策，框架给半成品**：构架是名词的动词化，本义"搭建承重骨架"（《说文》"构=盖也，从木"），口语"把 XX 构架出来"干的是把主干结构从无到有立起来；"构架出来"的默认验收标准是"骨架可见"，但架构定型的灵魂是决策与演化原则——用"构架思维"做架构，骨架立起来了、理由还悬在空中。**违反即崩：图很漂亮、框很齐，问"为什么这么分、被否掉的备选死在哪"没人答得上来——这正是"画图匠"和"架构师"的分界线。**

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能答全四问，三档标注）

> v2.1：概念层掌握标准提为**四问**（定义/辨析/溯源/致用）；档位先抓根——本章根概念（架构）与最狠判据入"必须脱口"，溯源/致用维度至少入"能解释"。

1. **架构**【根概念 · 必须脱口】：能定义（ISO 42010：系统在其环境中的基本概念或属性，体现在元素、关系以及设计演进原则之中；= 系统不可还原的涵义）；能辨析（≠ 图，≠ 详细设计，≠ 框架，≠ 技术选型，≠ 组织架构/产品形态）；能溯源（建筑学→软件→ISO 42010 四阶段；architecture ← architekton、fundamental ← fundus）；能致用（压复杂度/不可逆决策前/变更影响评估/团队边界；失效 = 图会过时、决策可一直有效）。
2. **架构描述**【必须脱口】：能定义（对架构的表达——相关方→关注点→视点→视图的制品集合）；能辨析（≠ 架构：涵义 vs 符号；≠ 某一张视图；≠ 一张总图）；能溯源（IEEE 1471→ISO 42010；description ← de-+scribere=写下来）；能致用（共享/讨论/检查/传承；失效 = 图过时 ≠ 架构过时）。
3. **系统**【能解释】：能定义（指称，实际存在的那个东西）；能辨析（≠ 架构，系统有生命周期）；能溯源（弗雷格模型【薄格】）；能致用（系统会报废，架构活得比系统长）。
4. **相关方 / 关注点**【必须脱口】：能定义（任何个体/团队/组织 / 对系统的任何兴趣）；能辨析（关注点天然冲突、只能权衡；权衡前提=看到每个方面）；能溯源（ISO 42010 原文【薄格】）；能致用（架构描述组织链第一环；相关方清单+核心关注点表摆出来）。
5. **视点 / 视图**【能解释】：能定义（规则/产物，相机比喻）；能辨析（视点 ≠ 视图；视图=刻意的"不完整"）；能溯源（相机比喻【薄格】）；能致用（每个视图说出"在回答谁的什么问题"；完备性由相关方决定）。
6. **设计准则 / 演进准则**【必须脱口】：能定义（怎么造/怎么变）；能辨析（缺一个的后果——一改就坏 vs 建出来就不对）；能溯源（ISO 42010 最后半句【薄格】）；能致用（免疫系统 + 活的学习系统；M3 演进准则三条）。
7. **框架**【必须脱口】：能定义（骨架+位置+组织规则，内容后填）；能辨析（≠ 架构："这一类"vs"这一个"；≠ 架构风格）；能溯源（本书凝练的跨领域定义【薄格】）；能致用（用框架 ≠ 有架构；试金石"删掉它，系统还在吗"）。
8. 能说出"一个系统只有一个架构"，及"XX 架构"的四类各是什么（关注域视角 / 描述层次 / 架构风格 / 框架）。
9. 能说出构架三词分工（构架立骨架 / 架构定决策 / 框架给半成品）+ "构架出来"默认验收=骨架可见的陷阱（骨架立起来、理由悬在空中=画图匠）。
10. 能说出 4+1 视图模型的五个视图及"+1 场景"为什么是胶水不是第五个视图（真实场景横穿验证一致性）。

### 原理层（应能解释为什么）

1. 能解释为什么"基本"（fundamental ← 地基）是定义的核心（地基一动整栋楼都动）。
2. 能解释定义里"概念或属性"为什么是 or 不是 and（两条路都能到架构，不必同时具备）。
3. 能解释为什么"在它的环境中"决定什么算"基本"（实验室台架 vs 冷链——环境变了基本就变了）。
4. 能解释为什么关系比元素更要紧（涌现属性来自关系；可靠性瓶颈在交互模式）。
5. 能解释三判据 = 第1章反事实检验用在系统上（同一个动作，换个对象）。
6. 能解释为什么架构"不长什么样"（视觉范畴 vs 逻辑范畴；宪法 / DNA / 组织架构类比）。
7. 能解释为什么一个系统只有一个架构（日常用语把"架构描述/架构视图"简称成"架构"；一副骨骼多张影像）。
8. 能解释为什么用框架 ≠ 有架构（框架给骨架不给决策；试金石"删掉它，系统还在吗"）。
9. 能解释为什么设计准则 + 演进准则缺一不可（只有设计准则→一改就坏 / 分布式单体；只有演进准则→建出来就不对）。
10. 能解释为什么架构是免疫系统（定义什么是"自我" + 主动防御变化）和活的学习系统（变更失误沉淀为原则更新）。
11. 能解释为什么构架三词分工（构架立骨架、架构定决策、框架给半成品）——"骨架可见"只是构架验收，不是架构定型。
12. 能解释架构 × 详细设计的分界为什么是"不可还原"（改它代价/影响/不可逆）——评审标的=那组去掉就不是它的决定，不是所有重要决定。
13. 能解释为什么涵义锁在脑子里没有用（必须被表达才能共享/讨论/检查/传承）。
14. 能解释为什么关注点天然冲突且只能权衡（快便宜安全全功能不能同时到顶；权衡前提是看到每个方面）。
15. 能解释为什么每个视图是刻意的"不完整"（完整=把一切糊在一张图上=对谁都没用；视图是架构的概念化切片）。
16. 能解释为什么视图完备性由相关方决定不由方法论决定（方法论之争 vs 项目分析）。
17. 能解释为什么 4+1 的场景是胶水不是第五个视图（真实场景横穿验证一致性；走不通就是四个系统）。
18. 能解释为什么架构是保真压缩（不需要一次记住全部、需要时能定位到；共享心智模型）。
19. 能解释架构在三个时间维度的回报（决策划解空间 / 变更免疫 / 组织康威定律）。
20. 能解释为什么约束即解放（消极 vs 积极自由；只约束要命的地方、回收积极自由）。
21. 能解释为什么架构师的核心能力是识别后果严重的决策（对不重要的事不决策是好的架构决策；架构师首先是一个工程师）。
22. 能解释"什么是重要的需要判断"（架构师的理论；*Whatever that is.*）与"架构 = 对不可逆决策的提前投资"。
23. 能解释为什么"基本"是对系统在其环境中的**目的**而言必要且充分（目的变了，"基本"就变了；三问同一锚 = 是否还服务于系统在其环境中的目的）。
24. 能解释为什么"基本"与"粗细"正交（共识算法很复杂但可以是基本，变量命名很简单但永远不是——架构分布在"基本"这一行，与粒度无关）。

### 判据层（应会用）

1. **架构三问**：去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗——三问皆"是"才是架构；答"否"的是详细设计。**三问同一锚：是否还服务于系统在其环境中的目的**（目的变了，"基本"就变了）。对任何一条"重要的事"当场打勾。
2. **三个词三层**：系统（指称）/ 架构（涵义）/ 架构描述（符号）分得开；图过时 ≠ 架构过时（决策可以一直有效）。
3. **一个系统一个架构**：业务/数据/应用/技术 = 关注域视角；概念/逻辑/物理 = 描述层次；微服务/事件驱动 = 架构风格；框架 = 可复用制品——用一条真实场景横穿，走不完 = 多个架构的病根。
4. **架构描述组织链**：相关方 → 关注点 → 视点 → 视图 → 完整描述——链条完整吗？每个视图能说出"在回答谁的什么问题"吗？
5. **关注点天然冲突**：冲突不可消除只能权衡；权衡前提是看到每个方面（相关方清单 + 核心关注点表摆出来）。
6. **约束即解放**：架构只约束"不改会灾难"的决定；每条约束能说出它解放了什么重复决策——写不出解放的是"管得最多"。
7. **免疫系统**：设计准则（怎么造）+ 演进准则（怎么变）两栏齐吗？缺一个，系统要么一改就坏要么建出来就不对。
8. **框架 ≠ 架构**：用框架 ≠ 有架构——框架给骨架，决策得自己做；试金石"删掉它，系统还在吗"。
9. **构架三词分工**："构架出来"默认验收=骨架可见，但架构灵魂=决策与演化原则——问得出"为什么这么分、被否掉的备选死在哪"，才算架构定型。

### 纠错红线十条

1. **先表态后翻案**：先让学员说"架构就是那张图啊，画完就完事""把架构构架出来就是画好图"，再翻，不让结论先入。
2. **反转精确不造新误解**："架构≠框图"别翻成"架构描述 / 画图没用"（描述仍是必须的，只是不是架构本身）；"约束即解放"别翻成"约束越多越好"（管得最准，不是管得最多）；"架构≠详细设计"别翻成"详细设计不重要"（详细设计仍是"改了还是它"的细节，值得做）；"构架≠架构"别翻成"别立骨架"（构架立骨架仍有用，只是骨架可见不等于架构定型）。
3. **判据配机制**：每条反转带"为什么"（弗雷格模型 / 免疫系统机制 / 涌现属性 / 不可还原分界）+ "怎么当场验证"（三问 / 链条 / 场景横穿 / 试金石）。
4. **归责到可对照动作**："你们没在做架构"落到"图没画关系、没画原则、说不清每个视图回答谁的什么问题 / 三问一测就倒 / 被否掉的备选说不上来"，不归咎"人不行"。
5. **教机制不教断言**：教"为什么关系承载架构最硬部分"（涌现属性：可靠性瓶颈在交互模式），不教"多画箭头"。
6. **先立尺子再翻案**：先给三问 / 三个词三层 / 免疫系统 / 构架三词分工判据，再翻水忠"图就是架构"、万辉"四张图"。
7. **拉开强度层次**：★★★ 常识（架构=框图 / 四个架构 / 框架=架构 / 约束=枷锁 / 评审标的=所有重要决定）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（用三问筛一条决定 / 拿一条真实场景横穿一次视图 / 把老规矩写下来 / 对最漂亮的图逐问三遍）。
9. **单一权威不另立标准**：判据引用书（九条判据）+ ISO 42010，不发明新尺子；术语统一「设计准则 / 演进准则」，不另立"设计原则 / 演进原则"。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给你们的系统写一份"老规矩"清单

> 目标：用本章判据（架构三问 / 三个词三层 / 免疫系统 / 约束即解放 / 场景是胶水 / 构架三词分工），把团队"从没写下来但大家都在守"的决定，写成 M3 式的老规矩清单，区分"不可还原（架构）"与"只是习惯（非架构）"。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑系统（先立枢纽）**：选一个"最近做、你心里最有底"的系统——最有底的，往往是那张图最老、老规矩最没人写下来的。**话术**："你最熟的那个系统，把它的架构说给我们听——三分钟，不许画图。"
2. **项目一 · 三问筛决定（架构三问）**：把团队所有"重要的事"列出来（数据归属 / 接口契约 / 告警策略 / 部署方式 / 技术选型……），逐条用三问筛："去掉它还是这个系统吗？缺了它系统垮吗？换掉它性质变吗？"三问都答"是"的，才是架构；三问答"否"的是详细设计（可调参数不是架构）。**话术**："少了这条规矩，M3 还是 M3 吗？""采集间隔改 5 分钟，M3 还是 M3——那是详细设计。"
3. **项目二 · 图和决定分开（三个词三层）**：把那张"架构图"翻出来，和筛出的决定对比——图里画了什么、没画什么？"图过时了"和"决定过时了"是不是两回事？**话术**："图可以烂掉，决策可以活着。"
4. **项目三 · 分两栏（免疫系统）**：把筛出的决定分成两栏——设计准则（怎么造：数据归属、断链刚性）+ 演进准则（怎么变：新增传感器不得破坏追溯链、固件升级向后兼容）。缺演进准则的那栏，就是"一改就坏"的高危区。
5. **项目四 · 一条场景横穿（场景是胶水）**：拿一条真实使用场景（如"一批疫苗从出库到接入冷库"），横穿你所有叫"XX 架构"的图/文档——走不通的地方，就是"多个架构"的病根，也是视图没对齐的缝。
6. **项目五 · 相关方补漏（关注点冲突）**：列出至少五个相关方及各自核心关注点（司机可用 / 客户可追溯 / 维修可维修 / 监管合规 / 老板成本 / 制造可生产）——有没有哪个关注点从没考虑过（运维玉杰问"有给运维看的图吗"就是漏的典型）？冲突不可消除，只能权衡；权衡的前提是看到每个方面。
7. **项目六 · 约束即解放复核**：对每条筛出的约束，写下它把团队从什么重复决策里解放了出来——写不出来的约束，多半是"管得最多"不是"管得最准"。
8. **项目七 · 构架复核（构架三词分工）**：挑一张你们团队最"漂亮"的架构图，逐问三遍——它在回应谁的什么关注点？决策的理由写得出来吗？被否掉的备选死在哪？——答不上来的那一问，就是"构架思维"欠下的债（骨架立起来了，理由还悬在空中）。
9. **出清单**：哪些是"少了它就不是它"（架构，写进老规矩），哪些只是习惯（非架构，标注即可）；最后一条建议照书抄——把"架构评审"的标的，从"那张图 / 所有重要决定"换成"那组不可还原的决定"。

**卡住怎么判断**：三问答不上来的那条，就是最该补的；一条真实场景横穿不动的地方，就是最该修的缝；约束写不出"解放了什么"的，就是最该砍的；图答不出"被否掉的备选死在哪"的，就是构架思维欠的债。不用全做完，找到第一个卡住的地方就能开工。

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"冰链的架构评审会上，水忠把那张四层方块图投上投影——硬件层、固件层、云端层、App 层，一根箭头标着'温度数据'——说：'这就是我们 M3 的架构。'产品开发经理永兵指了指那张图：'先记一个问题——客户问"M3 是什么系统"，我们能拿这张图答吗？'制造侧的逸人举手问：'这图里怎么没有怎么造它——哪道工序测什么、哪个批次装哪个固件？'水忠答：'架构图是讲系统长什么样的。'三个月后三个问题找上门：改采集间隔（1 分钟改 5 分钟）影响什么，会议室没人能答；加断电补传，云端和固件互相推'重连逻辑在谁那边'；客户问'M3 到底是什么系统'，三个团队三个答案——温控箱、追溯平台、冷链管理 App，那笔冷链订单没了下文。水忠翻出图想维护，忽然意识到：这张图从来没有描述过真正的 M3。永兵那句'我们能拿这张图答吗'，为什么三个月后客户当面再问一遍，团队还是答不上来？为什么说那张图不是 M3 的架构？架构到底是什么？用'架构三问'把 M3 不可还原的涵义筛出来。"
追问：① 三个问题各证明那张图缺了什么（采集间隔→关系/定在哪一环、断电补传→关系与原则、三个人三个答案→视角没对齐）——为什么'可靠性瓶颈在交互模式'？② 三判据对'断链即报废还能撑到接入冷库、全程可追溯'逐条打勾——为什么它是架构，而采集间隔不是？分界线画在哪（不可还原 vs 可还原；改它代价多大、影响多大范围、几乎不可逆）？三问同一锚：是否还服务于系统在其环境中的目的（目的变了，'基本'就变了）？定义里'概念或属性'为什么是 or 不是 and？③ 为什么'在它的环境中'决定什么算基本（同一台温控设备，实验室台架 vs 冷链运输）？M3 相关方关注点为什么天然冲突、只能权衡（司机可用/客户可追溯/维修可维修/监管合规/老板成本/制造可生产）？④ 反身：你们最近一次'架构评审'，审的是一张图，还是把关注点摆出来权衡？审的是所有重要决定，还是那组去掉就不是它的决定？

**Q2（见树见林② · 概念关系）**
"请给出 系统、架构、架构描述 三个词的关系，并说明：为什么说它们是弗雷格模型的翻版（指称 ≠ 涵义 ≠ 符号）？为什么'图过时了'不等于'架构过时了'？"
追问：① 各给一个 M3 的例子（产线上的箱子 / 那组决定 / 水忠的图）？② 推论一：同一个架构可以有无数种描述（四层框图/数据流图/时序图/合规视图都在描述同一个 M3 架构）；反过来同一张图可能根本没描述对架构——水忠的图为什么属于后者？推论二：系统有生命周期，架构为什么活得比系统长？③ 架构描述按'相关方 → 关注点 → 视点 → 视图'链条组织——这和'三个词三层'什么关系？④ 反身：你们平时说'架构'，说的是系统、架构还是架构描述？三个层面混着说会怎样？

**Q3（真悖论 · 架构是一张图 vs 架构是不可还原的涵义）**
"有人觉得：架构就是那张图——画出来了、评审了、存档了，架构工作就完成了。这一章说：架构不是一张图，是系统不可还原的涵义；图会过时，决定活着。哪个对？什么判据分清'图'和'架构'？"
追问：① 如果图就是架构，图过时了系统应该怎样？——可 M3 温控箱一直在正常工作，温度一直在采集、断链依然会告警，这说明什么？② 架构是静态快照吗？如果不是，它怎么'活'？（设计准则 + 演进准则 = 免疫系统；每次变更失误沉淀为原则更新）③ 为什么架构'不长什么样'？（宪法 / DNA / 组织架构类比——你看到的永远是文本/双螺旋/组织图，只有投影，没有'原图'）④ 反身：你们有没有'图早就烂了、规矩一直活着'的时刻？

**Q4（真悖论 · 一个架构还是四个架构）**
"恒信的万辉把合同审批系统的架构画成四张图：业务架构、数据架构、应用架构、技术架构，挂满一面墙。运维玉杰问：'我最想看它部署在哪、坏了从哪查——你这四张图里，有给运维看的吗？'万辉指着技术架构图，里面只有服务清单，没有'一个合同从发起到归档，部署在哪台机器、监控什么指标'。软件圈还有'微服务架构''事件驱动架构'，水忠团队有人张嘴就是'用了 Spring Cloud'。这些到底是不是多个架构？什么判据能把它们分清楚？"
追问：① 两套分类维度（关注域 × 抽象层次）+ 架构风格 + 框架，四类各是什么（一栋楼的平面图+结构图+管线图+立面图 vs 概念草图→施工图 vs 框架结构/剪力墙结构 vs 预制构件+装配手册）？是不是越抽象越高层就越像架构（'基本'与'粗细'正交：共识算法很复杂但可以是基本，变量命名很简单但永远不是）？② 徐漾用一条真实场景横穿四张图（法务的同事在 App 上审批一份 500 万的合同）——为什么走不完四张图，就是四个系统？③ 构架、架构、框架三词怎么分工？'把架构构架出来'的默认验收标准是骨架可见——这算不算架构定型？④ 反身：你们团队叫'XX 架构'的图/文档，用一条真实场景横穿过吗？

**Q5（真悖论 · 约束是枷锁还是解放）**
"有人抱怨：架构是给团队上枷锁——定了数据所有权、定了断链刚性、定了兼容规则，这不是绑住手脚吗？约束越少越灵活。这一章说：约束即解放——约束把团队从无穷的重复决策里解放出来。两个都对吗？什么判据分清'束缚'和'解放'？"
追问：① 消极自由（freedom from）和积极自由（freedom to）差在哪？没有架构时你拥有哪种自由、丧失哪种自由？② 水忠的约束（数据所有权/断链刚性/追溯完整性）各自把团队从什么重复决策里解放了出来（改采集间隔不用开会、加新传感器不用重新吵架构）？③ '管得最准'和'管得最多'怎么区分？④ 反身：你们系统里有没有'管得最准'的约束？有没有'管得最多'的约束？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 框架 ≠ 架构 + 构架三词分工）**
"软件圈几乎每天都能听见一句话：'用了 Spring Cloud，所以我们系统是微服务架构。'水忠团队也有人张嘴就是'M3 用的某某嵌入式框架'。这句话错在哪？框架和架构差在哪？用'删掉它，系统还在吗'测一测。口语里还有'把 XX 构架出来'——构架、架构、框架三词怎么分工？'构架出来'的默认验收标准是骨架可见，这够不够？"
追问：① 框架的三特征（骨架性/位置性/规则性）各是什么意思？② 为什么'骨架搭起来不等于架构有了'——服务边界、数据归属、接口契约，Spring Cloud 一个都没替你决定，为什么？③ 架构风格、框架、构架、架构怎么排成一条链（套路 → 物化 → 立骨架 → 定决策）？④ 反身：你们用过的框架，替你们定了什么、没替你们定什么？没替你们定的那些，是不是正好是架构决策？

**Q7（判据运用 · 免疫系统：设计准则 + 演进准则）**
"水忠那天晚上把'老规矩'写了下来：温度数据归属追溯域，传感器只管采、云端只管传、追溯平台管存管管看；断链必须实时告警并记录，不得吞掉、不得延迟；固件升级必须向后兼容已出厂的设备。前两条是设计准则，第三条是演进准则。为什么两类准则缺一不可？只有设计准则、没有演进准则的微服务，会退化成什么？"
追问：① 设计准则（怎么造）和演进准则（怎么变）各管什么？② 为什么说架构是免疫系统（定义什么是'自我' + 主动防御变化）？③ 分布式单体是怎么形成的？④ 反身：你们系统的演进准则写下来了吗？缺演进准则的那次变更，后来怎样了？

**Q8（判据运用 · 相关方 → 关注点 → 视点 → 视图 + 场景是胶水）**
"恒信的万辉把合同审批系统的架构画成四张图，挂满一面墙。徐漾问他：'一份合同，在这四张图里分别是什么？'——业务架构里是一条审批流程，数据架构里是'合同主表 + 审批记录 + 附件'三个实体，应用架构里是审批引擎的一个流程实例，技术架构里没画合同。'就凭这最后一句，'徐漾说，'你的四张图是四个系统。'为什么？什么判据能让四张图对得上？"
追问：① 相关方 → 关注点 → 视点 → 视图这条链，四环各是什么（谁想看 → 关心什么 → 按什么规则看 → 看到什么）？玉杰想看部署、坏了从哪查——这是哪个环节没被服务？② 为什么每个视图是刻意的'不完整'？把一切糊在一张图上会怎样？③ 4+1 的场景为什么是胶水不是第五个视图？④ 反身：你们每个视图能说出'在回答谁的什么问题'吗？

**Q9（方法时刻 · 规则 15 · 勤校准 + 转述 + 跨域变体）**
"水忠把'架构'从'一张框图'修正为'不可还原的涵义'——第1章说，勤校准是正常纠偏，不是失败；概念是活的、可修正的。这一章的方法底座时刻，就是勤校准：完成一次枢纽修正。请亲手把'架构 = 一张框图'这个旧枢纽，修正成'架构 = 系统不可还原的涵义'——你靠什么动作完成这次修正？修正之后，'图过时了'意味着什么？再用三五句话，把修正后的'架构'讲给一个完全外行的人——讲到哪卡住，缺口就在哪（转述=压缩测试：讲不清说明结构没成型）。"
追问（跨域变体 + 溯源）：① 冰链的老规矩（数据所有权/断链刚性/追溯完整性）和恒信的四张图（业务/数据/应用/技术），是同一个修正的两面吗？把'架构=框图'的修正用到恒信——判据变没变？② §10.2.2 那段行业史，本身就是'架构'被一路校准的轨迹——早期'架构=图纸'→1970s 结构化设计→1990s 软件架构热→2011 ISO 42010 定稿。每个阶段'架构'被用来指什么？这和你完成的那次枢纽修正，是什么关系（从哪来 = 一路校准的轨迹）？③ 架构师的核心能力不是'做出正确的决策'，而是'识别哪些决策如果不正确，后果会很严重'——水忠这次修正，识别出了什么后果严重的错误？'什么是重要的'本身需要判断（架构师对系统的理论：靠什么成功/最大压力在哪/什么做错最致命；Ralph Johnson：*Architecture is about the important stuff. Whatever that is.*）——修正'架构'的定义，本质上是不是在修正'什么重要'的判断？为什么说架构师首先是一个工程师（第9章六项底座）？④ 反身：你上次把某个概念从'见过的框图'推到'拥有的涵义'，是什么时候？你转述时卡住的那一处，是不是正好是你还没拥有的那一格？

**Q10（落地生根 · 回部门）**
"结合你们部门现状，给你们的系统写一份'老规矩'清单（参照水忠那天晚上把老规矩写下来）：先用架构三问筛出'少了它就不是这个系统'的决定，再分设计准则/演进准则两栏，再用一条真实场景横穿检验，最后用'约束即解放'复核每条约束解放了什么重复决策——给出最该补的三件事，每个落到一个动作。"
追问：① 三问筛的时候，最容易把哪一类'重要的事'误当架构？（可调参数 / 团队习惯 / 技术选型——'重要的事'不是架构，'去掉就不是它'才是；架构评审的标的=那组去掉就不是它的决定，不是所有重要决定）先写下系统的目的，再用三问检验——答不上来，说明还没把'目的'当成判据（书练习 14）？② 架构是保真压缩（共享心智模型）——新成员入门、跨团队协作、决策讨论时，你们的'架构'提供共同语言吗？康威定律：构件边界 = 团队边界——你们的构件边界和团队边界对齐吗？③ 恒信四张图对不上——你们团队有没有类似的对不上（玉杰问"有给运维看的图吗"）？④ 用四问的'它从哪来'量一次你们系统的'架构'——从建筑学到软件，这个词经历了哪几个阶段？每个阶段它被用来指什么？答不出这一问，你对架构就只是'见过'，不是'拥有'（书练习 12）。⑤ 两周后回来报告：哪条决定用三问筛出是/不是架构？
