# 案例设定：全书两条贯穿案例线

> 本文件是教材书全书的"案例圣经"——两个虚构案例支撑所有章节的"误解现场"、"双域镜照"与"章末反转"。均为虚构但现实的设定，不指涉真实公司。
> 用途：作者写作时对照本文件取素材；读者无需单独阅读本文件（案例随章节自然展开）。

---

## 案例A · 冰链科技 —— 医疗冷链运输温控箱

**产品**：M3 医疗冷链温控箱。硬件 + 嵌入式 + 云端 + App 一体，用于疫苗/药品 -20℃~8℃ 冷链运输，要求全程温度可追溯、断链可告警。

**团队**：
| 角色 | 姓名 | 职责 |
|---|---|---|
| 产品经理 | 小林 | 需求、评审、对客户 |
| 嵌入式硬件工程师 | 老周 | 温控硬件、固件 |
| 云端软件团队 | 阿凯等 3 人 | 数据采集、App、追溯平台 |
| 测试 | 小赵 | 验证与确认 |
| 制造/供应链 | 老陈 | 量产、物料、批次 |

> 冰链配角（散见各章具名）：销售小冯（第3章案例①）、疾控中心刘主任（第3章案例③·采购方代表）、App 负责人老李、硬件组新人小陈（第9章起具名）。

**词汇病清单（各章触发点）**：
| 章 | 触发点 | 词汇病 |
|---|---|---|
| 第3章 | 评审会上"精度规格比竞品高得多，质量绝对没问题" | 把**等级**当**质量** |
| 第3章 | "技术方案做完了，设计开发结束" | 漏掉七个方案，不知终点是**可实现** |
| 第4章 | 口头改需求"精度差不多就行" | 最危险的变更形式——偷换需求 |
| 第5章 | 原理样机通过，小林宣布"产品成功"；量产翻车八条 | 把**样机**当**产品**——漏掉可实现性需求 |
| 第6章 | 把方案的结构文档叫"架构定义" | **概要定义** ≠ **架构**——用一个重量级词命名轻量文档（ch6 改名伏笔，ch9 主场） |
| 第7章 | 需求评审做成"逐条核对需求" | 忘了评审对**目标** |
| 第8章 | 老周是"手艺的极致"，判断换个人做不出来 | 把**手艺**当**工程**——工程师=可复现的方法+守得住的底线（双线判词） |
| 第9章 | "架构 = 一张框图"，画完没人维护 | 把**架构描述**当**架构** |
| 第10章 | 设计 M3 二代带图、选型、老规矩三样东西开会 | 把**画图/选型/定规矩**当**架构设计**——忘了五块设计：概念/属性/准则/关系 |
| 第11章 | 温度记录的数据所有权随意改 | 把高不可逆决策当低可逆 |
| 第12章 | 把固件版本当基线；批次追溯查不清 | 版本 ≠ 基线；配置管理缺失 |
| 第13章 | 冷链断链事故归咎"技术问题" | 不追治理——框架级问题 |
| 第15章 | 老周被叫"架构师"，说不清架构师到底该干嘛 | 把**头衔**当**能力**——架构师=职级/画图匠（双线合流续判词） |

**走位**：主案例章节 3 / 5 / 9 / 10 / 12；镜照 2 / 4 / 6 / 7 / 11 / 13；第8章双线判词（老周手艺极致缺②⑥）；第15章双线合流续（老周无架构师头衔、做架构工作、缺②⑥，写老规矩长成）。

## 案例B · 恒信集团 —— 跨部门合同审批系统

**产品**：合同审批数字化系统。业务流程系统，覆盖法务 / 财务 / 业务三部门审批链，含合同版本管理、审批流、台账。

**团队**：
| 角色 | 姓名 | 职责 |
|---|---|---|
| 需求分析师 | Ada | 需求获取、ConOps、SRS |
| 架构师 | 李工 | 系统架构、数据模型 |
| 开发 | 3 人 | 前后端、接口 |
| 运维 | 小王 | 部署、监控、版本发布 |
| 业务方 | 配角（财务老王 / 法务张总） | 法务 / 财务 / 业务审批人 |

**词汇病清单（各章触发点）**：
| 章 | 触发点 | 词汇病 |
|---|---|---|
| 第2章 | "系统上线了 = 工程成功" | 把**技术系统**当**工程系统**验收 |
| 第4章 | ConOps 没人写，各部门怎么审批没人描述 | 跳过了问题域，直接写 SRS 条款 |
| 第6章 | 设计方案写成一篇大文章，评审找不到结构 | 设计文档是**散文**不是**树**——没做分解分配，方案没法被承接 |
| 第7章 | "UAT 跑了就是确认过了" | 混**验证**与**确认** |
| 第8章 | 李工有"高级工程师"头衔，研发却靠手艺和流程壳 | 把**头衔**当**能力**——工程师=六项能力一项不能少（双线判词） |
| 第11章 | 合同数据结构想改就改 | 高不可逆决策没走审查 |
| 第12章 | 合同版本靠"另存为 v2" | 没有**基线**，版本乱 |
| 第13章 | 采购"数据治理平台"当清洗工具 | **术语膨胀**——用治理的名字干管理的活 |
| 第15章 | 李工当选年度架构师，四张图当全部工作 | 把**画图**当**架构**——架构师=画图匠（双线合流续判词） |

**走位**：主案例章节 2 / 4 / 6 / 7 / 11 / 13；镜照 3 / 5 / 9 / 10 / 12；第8章双线判词（李工伪工程缺①④⑥）；第15章双线合流续（李工有"架构师"头衔、缺①④⑥，四张图被 Ada 点醒）。

## 两条案例线的关系

1. **一个造"有形设备"，一个造"无形系统"**——全书最好的"工程系统 vs 技术系统"演示对（第2章）。
2. **同一套概念在两个世界长一个样**——每个概念至少一条线深度演示，另一条线做"镜照"段落（200-400 字）。
3. **案例团队的行为模式**：先因"词汇病"做错（各章章首"误解现场"），经正确概念纠正（各章"认知反转"）——读者看着团队犯自己也在犯的错。
4. **第8章工程师**在链的中段先把"谁是工程师"的人判词立起来（李工伪工程缺①④⑥、老周手艺极致缺②⑥）；**第14章整合**：两条线各走一遍完整变更闭环，最后合起来收束"系统"；**第15章架构师**继续收束到"人"——给两条线里做架构工作的人（李工有头衔缺底座、老周无头衔有一半底座）落定"是不是架构师"的判词。
