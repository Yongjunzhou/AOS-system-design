## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：评审、验证、确认三个词到底差在哪？为什么中文看起来像近亲？评审为什么以"目标"为参照、验证以"规定需求"、确认以"预期用途"？只做验证不做确认，为什么会"测试全过、没人用"？

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：1.1 翻译伪朋友先看病 → 1.2 ISO 9000 分家（3.11 vs 3.8）→ 1.3 三个参照对象（目标/规定需求/预期用途）→ 1.4 五维表并排 → 1.5 评审三问 → 1.6 验证三要素 → 1.7 确认三要素 —— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：2.1 评审不是核对需求（三理由）→ 2.2 测试通过≠验证通过 → 2.3 业务方点了≠确认过了 → 2.4 验证够不着隐含需求 → 2.5 确认的尺子在场景里（冰山）—— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：3.1 三关接力 → 3.2 六个把关节点 → 3.3 复盘=检测器 → 3.4 因果链 → 3.5 评审手法（目标具体化）→ 3.6 系统性三属性+五大目的 → 3.7 验证手法（V模型右半边）→ 3.8 确认手法（仿真/灰度/试运行）—— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **评审**（review，ISO 9000:2015 §3.11.2）：对客体实现所规定目标的适宜性、充分性或有效性的确定。判据：评审三问（适宜/充分/有效）+ 系统性三属性（团队参与、结果文档化、过程文档化）——没记录的评审不算评审，最多算聊天。
2. **验证**（verification，§3.8.12）：通过提供客观证据，对规定需求已得到满足的认定。判据：验证三要素（对照规定需求 + 客观证据 + 做出认定）；测试只是证据之一；逐级回收（V 模型右半边）。
3. **确认**（validation，§3.8.13）：通过提供客观证据，对特定的预期用途或应用要求已得到满足的认定。判据：确认三要素（真实用户 + 真实任务 + 真实场景）；参照在场景里不在文档里。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 评审 | 验证 | 判断（确定·对目标）vs 证明（认定·对需求）——动作对立 |
| 验证 | 确认 | 参照在文档（规定需求）vs 参照在场景（预期用途）——参照对立 |
| 评审 | 核对需求 | 抬头看目标（唯一）vs 低头对规格（验证的姿势） |
| 评审/验证/确认（三件） | 中文"评/验/认"近亲（一件） | 翻译伪朋友——英文一眼能看出的不同，中文形近字糊了四十年 |
| 评审 | 复盘 | 把关（过程关卡）vs 改进（事后回顾）——复盘不在 IEEE 1028 五类 |
| 复盘（检测器） | 治理（裁决者） | 例行显影偏差 vs 对偏差做裁决（第13章） |

### 关联概念（近界 · 辨析）

- **评审 × 验证 × 确认 = 一条接力链**：评审站在开工前抬头看方向，验证站在交付时低头对规格，确认站在交给用户时走进真实场景——一条需求从起点到上线走这三关（3.1）。
- **评审 × 目标（objective，3.7.1）**：评审对"所规定目标"——目标 = 对象 + 时限 + 可衡量结果（3.5）；战略目标负责激励、操作目标负责评审。
- **验证 × 规定需求（specified requirement，3.6.4 注2，第4章枢纽）**：同一个词三个看门人都绕不开——评审审它（评审的对象）、验证对它（验证的参照）、确认兜它（验收与责任的依据）；它没成文，三个看门人全闭门（2.1）。
- **验证 × 测试**：测试只是提供客观证据的手段之一（注1：试验/变换方法计算/文件评审）；验证 ≠ 测试——测试报告是验证的输入，不是验证本身（2.2）。
- **验证 × 检验（inspection）**：检验盯"特性"（单条，温度波动 ≤±0.5℃），验证盯"规定需求"（一条需求可能含多条特性）——粒度不同（2.2）。
- **验证 × 符合性分析（第6章）**：符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）——都满足验证三要素，只是证据不同；同一个动作，在"看它对不对"时是评审的输入，在"证明它满足需求"时是验证的证据（2.2）。
- **确认 × 预期用途（intended use）**：三构成 = 目标用户 + 使用场景/任务 + 环境与条件（1.7）；UAT = 真实用户 + 真实任务 + 真实场景（2.3）。
- **确认 × 隐含需求**：冰山比喻——水面下占大半；验证是量吃水线的尺子（只管浮在水面上的），确认是把船开进真实水域的试航（水下撞没撞到试航才知道）（2.5）。
- **三关 × 第3章"程度"三步**：第三步"认定"动作上正是验证和确认——没有验证确认，连感觉都算不上，因为没人认定（3.1）。
- **评审 × IEEE 1028 五类**：管理/技术/检查/走查/审计——谱系从轻到重，但无论轻重三属性不变（有团队、有结论、有记录）（3.6）。
- **六个把关节点**：需求/设计/代码/测试/发布评审 + 复盘——评审类把关节点都是同一个三问在具体关口的一次落地（复盘除外）（3.2）。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 三个词是三个词源、构词、归属完全不同的英文词（review / verification / validation），中文翻译恰好都带一个"评/验/认"字——这是第1章第三种词汇病"翻译伪朋友"的教科书案例，"把三件事糊成一件"的根源（1.1）。
2. ISO 9000 把评审归 3.11"有关确定的术语"组（与确定、监视、测量、检验一家），把验证/确认归 3.8"有关规范的术语"组（与规范、要求、符合性一家）——标准分家不是随便分的："确定"和"认定"是两种动作，判断和证明是两回事（1.2）。
3. 判 vs 证：评审的动作是"确定"（主动调查，从"没有结论"到"有结论"，不要求客观证据）；验证/确认的动作是"认定"（结果已经在那儿了，去证实，必须有客观证据）——判靠判断力，证靠客观证据（1.2）。
4. 三个看门人看向三个不同的参照物：目标（要实现的结果，3.7.1）/ 规定需求（明示成文，3.6.4注2）/ 预期用途（真实使用情境）——参照不同是决定性的差异，决定射程和命运（1.3）。
5. 判据主义：三把尺子各带一套可检验判据——评审三问、验证三要素、确认三要素；不给没有判据的尺子（1.4/枢纽）。
6. 评审三问层层递进：适宜性（对症吗）→ 充分性（够全吗）→ 有效性（管用吗）——方向不对做得再全白费；覆盖不全方向对了翻车；前两个过了还要结果说话（1.5）。
7. 目标具体化配方：目标 = 对象（谁/什么）＋ 时限（何时）＋ 可衡量结果（多少）——抽象目标评不了；目标还分层级（战略目标激励人用、操作目标评审用，评审要挂可判定那一层）（3.5）。
8. 验证三要素缺一不可：① 对照规定需求（有白纸黑字的尺子吗——口头"大概要快一点"无法验证）② 客观证据（有可复核的证据吗——"我认为满足"不算）③ 结论/认定（有明确结论吗——"差不多吧"不是验证）（1.6）。
9. "规定需求可验证"不是标准直接写的，是从"验证要求客观证据 + 验证以规定需求为参照"推出来的——可验证是规定需求当验证参照的资格证；这是第4章"需求质量六性"里"可验证"一性的真正出处（1.6）。
10. 确认和验证共享同一套三要素，唯一区别在第一个要素：验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）——就这一个词的区别，决定两个看门人完全不同的射程和命运（1.7）。

**第二幕 · 磨边弧的机制（不是什么）**
11. 评审不是核对需求，三个理由每一条都足以让"以需求为参照"破产：① 需求本身可能是错的（需求评审的本质恰是审"需求对目标是否适宜充分有效"）；② 否则评审和验证就重复了（ISO 分家塌了）；③ 满足所有需求 ≠ 达成目标（目标错了，需求再对也是白做；评审是整条链上唯一"抬头看目标"的环节）（2.1）。
12. 规定需求一个词三个看门人都绕不开：评审审它、验证对它、确认兜它——它没成文，三个看门人就全都闭门（章首"口头补的需求"的下场）（2.1）。
13. 测试只是提供客观证据的手段之一（ISO 9000 注1：试验结果、变换方法计算、文件评审等）——测试报告是验证的输入，不是验证本身；验证是拿着全部证据对全部规定需求做出认定（2.2）。
14. 符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）——都满足验证三要素，只是证据不同；同一个动作，在哪个门里用决定了它是评审的输入还是验证的证据（2.2）。
15. UAT 不是"让业务方点一遍测试环境"，而是"真实用户 + 真实任务 + 真实场景"的确认——让业务方点测试环境，是把确认做成了验证：业务方替你打勾的，还是需求清单上的格子（2.3）。
16. 验证的尺子在文档里，确认的尺子在场景里：没写进文档的需求验证够不着（没文档 = 没参照）；真实场景自带答案，场景兜得住文档够不着——隐含需求像冰山，水面下占大半；验证是量吃水线的尺子、确认是把船开进真实水域的试航（2.4/2.5）。

**第三幕 · 往哪去的机制（运用）**
17. 三个看门人串起来，是第3章"程度"三步得出法的第三步落地——验证认定"特性满足规定需求"，确认认定"客体满足预期用途"；没有验证确认，连感觉都算不上，因为没人认定（3.1）。
18. 三关缺任何一关后果完全不同：缺评审 = 需求错了没人发现，白做；缺验证 = 做错了没人知道，返工；缺确认 = 做对了也没人用，白做（3.1）。
19. 六个把关节点把"把关"从终点挪到全程——问题越早发现修复成本越低（需求阶段缺陷修复成本是 1，发布后是 30~70 倍）；评审类把关节点都是同一个三问在具体关口的一次落地（复盘除外）（3.2）。
20. 通过标准会前定、会后逐条打勾——评审的尺子不是评审会当天造出来的，是方案出生时就该有的；通过标准全部由"数字 + 动作"构成，没有"质量要好"这种形容词（3.2）。
21. 评审 ≠ 复盘：评审管"把关"（干活之前/之中），复盘管"改进"（干完了，事后总结）——复盘不在 IEEE 1028 五类里，也不是 ISO 9000 的"评审"（3.3）。
22. 复盘是检测器——它像传感装置一样例行运行、把偏差显影出来（对不上账、漏了场景、口头变更没记录）；但复盘发现偏差 ≠ 治理裁决——显影是检测，裁决（要不要改字段、谁有资格批准）才是治理（第13章）；只诊断不闭环的复盘，是把同样的错再复一遍（3.3）。
23. 因果链：只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用——不是运气问题，是因果问题（三段：隐含需求没进文档 → 只做验证的团队全漏在体系外连被检验的机会都没有 → 上线后用户行动上"不用"）（3.4）。
24. 确认的存在价值恰恰建立在非明示需求上——如果所有需求都能写下来被验证，确认就不需要存在了；确认还兜一类"文字说不清的需求"（体验类：手感要高级/用起来要顺）——确认是这类需求的唯一裁判（3.4）。
25. 确认把"漏掉的隐含需求"变成"可发现的缺陷"——隐性缺失看不见，显影出来的缺陷看得见；章首李工的 UAT 报告没有一条缺陷，不是因为没有缺陷，是因为把产品放进了一个造不出缺陷的场景（测试环境）（3.4）。
26. 系统性评审三属性：团队参与、评审结果文档化、评审过程文档化——缺一个就是"非系统性评审"，说人话：没记录的评审不算评审，最多算聊天；评审的职责是主动暴露问题，不是汇报成果（3.6）。
27. 评审五大目的（质量把关/风险识别/对齐共识/决策推进/经验沉淀）——最容易被轻视的是决策推进：明确结论（通过/有条件通过/不通过）＋ 有条件通过必须写明条件、复核人、期限 ＋ 记录留档；评审的终点不是散会（3.6）。
28. V 模型左右镜像：需求从哪一级分解下去，验证就从哪一级收回来——"需求在哪一级被规定，验证就在哪一级证明"；只做最后一次性验证，中间断掉的层级恰是缺陷藏身的地方（3.7）。
29. 确认的手段谱系（仿真测试→灰度发布→试运行）——ISO 9000 注3"使用条件可以是真实的或模拟的"给了合法性；灰度是确认不是缩小版的验证（放 10% 真实流量 = 真实场景当裁判）；冰山下面不只有隐含，还有强制（法规/安全强制要求）；确认站在工程系统门口：技术系统上线了 ≠ 工程系统成功；确认不能后补到上线后——上线后补确认，就叫"上线事故"（3.8）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "评审就是开会过一遍需求。"（评审对目标，不是核对需求）
2. "UAT 跑了就是确认过了。"（让业务方当测试员）
3. "测试全绿 = 验证过了。"（测试只是证据之一）
4. "验证和确认差不多，都是证明没问题。"（翻译伪朋友）
5. "满足所有需求 = 达成目标。"（需求本身可能错；评审是唯一抬头看目标）
6. "确认是验证的加强版，范围更大而已。"（参照不同：文档 vs 场景）
7. "把评审通过标准写出来太形式化。"（目标不具体就评不了）
8. "复盘也是评审，都带'评'字。"（评审管把关，复盘管改进）
9. "测试全过、没人用是运气问题——多用心就能避免。"（因果问题）
10. "隐含需求写进文档、排进用例，就能被验证。"（验证的尺子在文档里，很多隐含需求写不出来）
11. "验证最后做一次、系统级全量跑一遍就够了。"（V 模型左右镜像，逐级回收）
12. "评审目标太抽象，评不了——先看方案再定标准。"（目标具体化配方）
13. "评审是开工前/上线前做一次就完了。"（六个把关节点洒全程）
14. "让业务方点一下测试环境，就是确认过了。"（把确认做成验证）
15. "灰度发布没出问题 = 验证通过了。"（灰度是确认初步通过）
16. "确认可以上线后补，上线后补确认不迟。"（上线后补确认 = 上线事故）
17. "复盘发现偏差，就是治理裁决了。"（复盘是检测器，裁决才是治理）
18. "口头补的需求，大家记得就行。"（没成文 = 三个看门人全闭门）
19. "测试用例照着需求清单写，就是验证做全了。"（验证要对全部规定需求做认定，隐含需求够不着）
20. "评审人够多、开够会，就是评审过了。"（没结论没记录 = 聊天）

### 重要分界

- **动作分界（评审 × 验证/确认）**：确定（判·主动调查·不要求证据）vs 认定（证·结果已存在·必须证据）。
- **参照分界（评审 × 验证 × 确认）**：目标（方向）vs 规定需求（做对）vs 预期用途（做对的东西）。
- **射程分界（验证 × 确认）**：验证的尺子在文档里（够不着隐含），确认的尺子在场景里（兜得住隐含）。
- **归属分界（评审 × 复盘）**：评审管把关（在流程链条上），复盘管改进（绕回起点）；复盘是检测器，裁决是治理。

### 落点

- 反直觉命题①：评审对目标（不是对需求）。
- 反直觉命题②：只做验证不做确认 → 测试全过、没人用（因果链）。
- 方法底座时刻：**判据主义**（三把尺子各带可检验判据：评审三问 / 验证三要素 / 确认三要素）。

### 重要度分层

- **核心（必须脱口）**：三定义（评审/验证/确认）、三把尺子判据（对目标/对需求/对用途）、评审三问（适宜/充分/有效）、验证三要素（对照/证据/认定）、确认三要素（真实用户+真实任务+真实场景）、因果链（只验证不确认→测试全过没人用）、评审≠复盘。
- **重要（能解释）**：ISO 9000 分家（3.11 vs 3.8）、判 vs 证机制、测试只是证据之一、V 模型左右镜像、六个把关节点、系统性三属性（没记录=聊天）、目标具体化配方、复盘=检测器、灰度=确认不是缩小版验证。
- **知道即可**：词源溯源（review←re+view / verification←verus / validation←validus）、IEEE 1028 五类名、ISO 条款号、确认手段谱系名。

### 本章判据（七把尺子）

1. **三把尺子**：评审对目标（方向对不对）、验证对规定需求（做对了吗）、确认对预期用途（做对的东西了吗）。
2. **评审三问**：适宜性（对症吗）→ 充分性（够全吗）→ 有效性（管用吗），层层递进；目标具体化配方 = 对象 + 时限 + 可衡量结果；通过标准会前定、会后逐条打勾。
3. **评审系统性三属性**：团队参与、评审结果文档化、评审过程文档化——没记录的评审不算评审，最多算聊天。
4. **验证三要素**：对照规定需求 + 提供客观证据 + 做出认定；测试只是提供证据的手段之一；逐级回收（单元 → 集成 → 系统）。
5. **确认三要素**：对照预期用途 + 客观证据 + 认定；参照在场景里不在文档里；UAT = 真实用户 + 真实任务 + 真实场景。
6. **因果链**：只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用。确认的存在价值建立在非明示需求上。
7. **评审 ≠ 复盘**：评审管把关（过程关卡），复盘管改进（事后回顾）。复盘是检测器——它例行地显影偏差；复盘触发的裁决才是治理（第13章的事）。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"评审"（对客体实现所规定目标的适宜性、充分性或有效性的确定，ISO 9000:2015 §3.11.2），并说出动作是"确定"（判断、主动调查）不要求客观证据。
2. 能定义"验证"（通过提供客观证据，对规定需求已得到满足的认定，§3.8.12），并说出三要素（对照规定需求 + 客观证据 + 认定）。
3. 能定义"确认"（通过提供客观证据，对特定的预期用途已得到满足的认定，§3.8.13），并说出与验证的唯一区别在参照（文档 vs 场景）。
4. 能辨析 评审 vs 验证 vs 确认 三个词（动作：判 vs 证；参照：目标 vs 需求 vs 用途；证据：不要求 vs 必须有；时机：事前/事中 vs 对结果证实 vs 真实/模拟场景）——五维表。
5. 能辨析 评审 vs 核对需求（评审对目标；核对需求是验证的姿势；评审是整条链上唯一"抬头看目标"的环节）。
6. 能辨析 验证 vs 测试（测试是提供客观证据的手段之一；验证对全部规定需求做认定）；验证 vs 检验（特性粒度 vs 需求粒度）。
7. 能辨析 确认 vs UAT 走流程（UAT = 真实用户 + 真实任务 + 真实场景；让业务方点测试环境 = 把确认做成验证）。
8. 能辨析 评审 vs 复盘（评审管把关、复盘管改进；复盘不在 IEEE 1028 五类里）；复盘 vs 治理（检测器 vs 裁决者）。
9. 能说出 ISO 9000 分家（评审在 3.11"确定"组、验证/确认在 3.8"规范"组）及"判 vs 证"的机制。
10. 能说出"翻译伪朋友"（第1章第三种词汇病）在这三个词上的表现（英文词源/构词/归属完全不同，中文形近字糊了四十年）。

### 原理层（应能解释为什么）

1. 能解释为什么这三个词被糊成一个（翻译伪朋友：三个英文词词源/构词/归属完全不同，中文恰好都带"评/验/认"形近字）。
2. 能解释为什么标准把评审和验证/确认分家（"确定"和"认定"是两种动作，判断和证明是两回事）。
3. 能解释为什么三个看门人看向三个不同的参照物（目标/规定需求/预期用途），以及参照不同为什么是决定性的（决定射程和命运）。
4. 能解释为什么评审三问层层递进（适宜→充分→有效；方向不对白费、覆盖不全翻车、结果说话）。
5. 能解释为什么评审不是核对需求（三个理由：需求本身可能错 / 否则与验证重复 / 满足所有需求≠达成目标）。
6. 能解释为什么"规定需求可验证"是推导不是定义原话（验证要求客观证据 + 以规定需求为参照 → 作为验证参照的规定需求必须可验证）。
7. 能解释为什么测试通过≠验证通过（测试只是提供客观证据的手段之一；96% = 4% 没有证据）。
8. 能解释为什么验证够不着隐含需求、确认兜得住（验证的尺子在文档里、确认的尺子在场景里；真实场景自带答案；冰山比喻——验证量吃水线、确认试航）。
9. 能解释为什么确认的存在价值建立在非明示需求上（写不下来的需求 + 体验类需求只有真实场景能裁决）。
10. 能解释为什么只做验证不做确认 → 测试全过、没人用（三段因果：隐含需求没进文档 → 只验证的团队全漏在体系外 → 上线后行动上"不用"）。
11. 能解释为什么复盘是检测器不是裁决者（例行显影偏差是检测，对偏差做裁决才是治理）。
12. 能解释为什么六个把关节点把"把关"从终点挪到全程（问题越早发现修复成本越低：需求 1 → 发布后 30~70 倍）。
13. 能解释为什么通过标准会前定（评审的尺子不是评审会当天造出来的，是方案出生时就该有的）。
14. 能解释 V 模型左右镜像（需求在哪一级被规定，验证就在哪一级证明；只做最后一次性验证 = 中间断掉层级藏缺陷）。
15. 能解释为什么灰度发布是确认不是缩小版的验证（放真实流量 = 真实场景当裁判）。

### 判据层（应会用）

1. **三把尺子判据**：评审对目标/验证对需求/确认对用途——能当场给一张 UAT 报告、一场评审会、一次月底对账分栏。
2. **评审三问判据**：适宜（对症吗）/充分（够全吗）/有效（管用吗）三问层层递进 + 目标具体化配方（对象 + 时限 + 可衡量结果）+ 通过标准会前定、会后逐条打勾。
3. **系统性三属性判据**：团队参与、评审结果文档化、评审过程文档化——没记录的评审不算评审，最多算聊天；当场打勾。
4. **验证三要素判据**：对照规定需求 + 客观证据 + 认定；测试只是证据之一；逐级回收（V 模型右半边）。
5. **确认三要素判据**：真实用户 + 真实任务 + 真实场景；参照在场景里不在文档里；UAT/灰度/试运行各在哪一档。
6. **因果链判据**：只验证不确认 → 隐含需求系统性漏失 → 测试全过没人用；确认的存在价值建立在非明示需求上。
7. **评审≠复盘判据**：把关 vs 改进；复盘是检测器（例行显影偏差），复盘触发的裁决才是治理（第13章）。

### 纠错红线十条

1. **先表态后翻案**：先让学员说出"UAT 跑了就是确认过了，这还用讨论吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："评审≠核对需求"别翻成"评审不需要看需求"；"测试≠验证"别翻成"不要测试"；"确认≠让业务方点环境"别翻成"不用业务方参与"；"评审≠复盘"别翻成"复盘没用"。
3. **判据配机制**：每条反转都有"为什么"（判 vs 证 / 参照不同 / 场景自带答案 / 因果链）和"怎么当场验证"（三问 / 三要素）。
4. **归责到可对照动作**："你没做确认"落到"月底对账的真实场景从没测过 / 口头补的需求没进文档"，不归咎"不用心"。
5. **教机制不教断言**：教"为什么验证够不着隐含需求"（尺子在文档里、没文档=没参照），不教"验证没用"。
6. **先立尺子再翻案**：先给三把尺子判据，再翻李工"验收合格，可以上线"。
7. **拉开强度层次**：★★★ 常识（UAT 跑了=确认过了 / 测试全绿=验证过了 / 满足所有需求=达成目标 / 测试全过没人用是运气）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（用确认三要素设计一次真实确认 / 用验证三要素拆一张测试报告）。
9. **单一权威不另立标准**：判据引用书（本章判据七条）+ ISO 9000/9001 + IEEE 1028，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给一次最近上线/交付做一次"三个看门人体检"

> 目标：用本章三把尺子（评审三问 / 验证三要素 / 确认三要素）+ 因果链，给团队最近一次"验收合格、可以上线"的交付做一次完整体检，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑对象（先立枢纽）**：选一次最近"验收合格、可以上线"的交付——最自信的，往往是三关缺得最狠的（对照章首李工那句"验收合格，可以上线"）。
2. **第一关 · 评审对目标**：那次评审的通过标准，是会后现想的还是会前定的？评审前有没有先把目标摆出来（对象 + 时限 + 可衡量结果）？评的是目标，还是核对需求清单？**话术**："如果只核对需求清单，你会说'全部覆盖，通过'——你的尺子是目标吗？" 没结论、没记录，最多算聊天。
3. **第二关 · 验证对需求**：验证三要素齐吗——对照（规定需求成文了吗？口头补的算不算？）／证据（客观证据可复核吗？测试通过率是全量还是抽验？）／认定（有结论吗？"已验证/未验证"，不是"跑完了"）。验证是逐级回收的吗（V 模型：需求从哪一级分解、验证从哪一级回收）？
4. **第三关 · 确认对用途**：上线前有没有把产品放进真实场景（真实用户 + 真实任务 + 真实场景 + 真实数据）？UAT 是让业务方当测试员跑用例，还是跑真实业务任务？灰度/仿真算确认，但只算"初步通过"。
5. **因果链查漏**：有没有"没写进文档的需求"（口头补的 / 隐含的 / 强制的）？它验证够不着——它有没有被放进确认的场景里？**话术**："25 号之后签的合同算哪个月——这条在你们系统里，谁测过？"
6. **复盘闭环**：上线后复盘产出的行动项，有负责人 + 截止日期吗？上轮行动项关闭率 ≥ 80% 吗？复盘显影的偏差，由谁做了裁决（裁决是治理，第13章的棒）？
7. **出体检报告**：三关各下结论（通过 / 有条件通过 / 不通过），**最该先补最不过的一关**；最后一条建议照书抄——把"验收"从一句话改回"三个看门人依次签字"。

**卡住怎么判断**：答不上来的那一关就是最该补的——评审没判据就查第一关；测试全绿但没人用就查第三关（因果链）；口头需求一堆就查第二、三关。不用三关全做完，找到第一个答不出的关卡就能开工。

| UAT 是让业务方跑真实任务，还是跑用例？（UAT 真实三件套） | □ | 前一种测的是场景，后一种测的还是需求 |
| 隐含需求放进确认场景了吗？（验证射程 vs 确认射程） | □ | 隐含需求像冰山，水面下占大半——只有确认能兜住 |
| 复盘行动项有负责人 + 期限 + 上轮关闭率 ≥80% 吗？（复盘=检测器+闭环） | □ | 只诊断不闭环的复盘，是把同样的错再复一遍 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"章首那场评审会上，李工举着 UAT 报告说：'UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。我们验收合格，可以上线。'Ada 只问了一句：'月底对账的场景测了吗？'李工答：'测试用例是照着需求清单写的，需求清单里没有这条。'Ada 说：'你把三件事当成一件事办了。'——是哪三件事？评审、验证、确认各自是什么、各看什么？为什么三个词在中文里看起来像近亲？"
追问：① 三把尺子各带什么可检验判据（评审三问 / 验证三要素 / 确认三要素）？评审为什么不要求客观证据、却必须记录（系统性三属性：团队参与 + 结果文档化 + 过程文档化——没记录=聊天）？② 李工话里"测试通过率 96%"是哪件事的证据？它证明不了另外两件事的什么？③ 反身：你们最近一次说"验收通过了"，是三个看门人依次签字的，还是把三件事当成一件事办了？

**Q2（见树见林② · 概念关系）**
"请给出 评审、验证、确认 三个词的关系——用一张五维表（定义 / 参照 / 动作 / 证据 / 时机）把三把尺子并排钉死，再说出三个看门人怎么接力（评审站在哪、验证站在哪、确认站在哪）。为什么三个参照物（目标 / 规定需求 / 预期用途）不是同一个？"
追问：① 参照不同为什么是决定性的（决定射程和命运）？② 规定需求一个词为什么三个看门人都绕不开（评审审它 / 验证对它 / 确认兜它）？③ 反身：你们平时把"验证"和"确认"糊着用吗？哪次糊出过事？

**Q3（真悖论 · 评审对目标 vs 核对需求）**
"冰链的需求评审会开了一下午：小林拿着需求清单逐条念、逐条打勾——'有编号 ✓、有来源 ✓、可测吗 ✓、验收标准有 ✓'，三十条念完，宣布评审通过。这不是更省事、更客观吗？可书里说评审以'目标'为参照。'逐条核对需求'和'评审对目标'，哪个对？什么判据能分清？"
追问：① 评审不是核对需求的三个理由（需求本身可能错 / 否则与验证重复 / 满足所有需求≠达成目标）？② "需求满足得越彻底，目标的偏离走得越远"——为什么把评审做成了"最后一小时核对"，就是最失败的评审？③ 反身：你们最近一次评审，问过"这套需求还朝那个目标吗"吗？

**Q4（真悖论 · 测试通过 vs 验证通过）**
"'测试全绿'不就是'验证通过'吗？测试都跑了，证据还不够吗？可书里说'测试通过≠验证通过'。那什么才算验证通过？测试在验证里到底算什么？"
追问：① 验证三要素（对照规定需求 + 客观证据 + 认定）——测试满足了哪个？② 96% 通过率剩下的 4% 说明什么（那 4% 对应的需求没有证据）？③ 反身：你上次说"测试全绿"，验证三要素齐了吗？

**Q5（真悖论 · 业务方点了 ≠ 确认过了）**
"李工让法务、财务、业务在测试环境点了一圈，'业务方都验收了，这还不是确认？'可书里说这是'让业务方当测试员'。让业务方参与，怎么反而不是确认？"
追问：① 确认三要素（真实用户 + 真实任务 + 真实场景）——李工的 UAT 缺了什么？② 为什么"让业务方点测试环境"是把确认做成了验证？③ 只做验证不做确认，那些没进文档的隐含需求会怎样（因果链：系统性漏失 → 测试全过、没人用）？④ 反身：你们上次的 UAT，业务方是在跑用例，还是在跑真实任务？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 三关 + 因果链 + 复盘 · 案例⑤）**
"恒信上线两周后第一个月底，财务老王对账对不上了——25 号之后签的合同，合同编号全落在当月。Ada 在白板上写了六个字：'验证做了，其余没做。'——这句话怎么拆？为什么说'三个看门人只来了一个，剩下两个在等一场事故'？"
追问：① 三关接力（评审开工前 / 验证交付时 / 确认交给用户）——这次事故缺了哪两关？② 缺每一关的代价是什么（缺评审白做 / 缺验证返工 / 缺确认没人用白做）？③ 复盘显影了偏差（两条行动项："变更必须先过评审对目标一关"+"UAT 改真实场景跑"），但裁决（合同编号归属规则要不要定、归谁定）为什么不是复盘能给的？④ 反身：用三关走一遍你们最近一次上线，缺的那关代价是什么？

**Q7（判据运用 · 评审三问 · 目标具体化 · 六个把关节点 · 案例①）**
"Ada 重开上线评审会，李工说'上线前评审，目标就是系统能上线'。Ada 说：'能上线评不了。目标要有对象、有时限、有可衡量结果。'——为什么'能上线'评不了？目标具体化配方是什么？通过标准为什么要会前定、会后逐条打勾？"
追问：① 目标具体化配方（对象 + 时限 + 可衡量结果）+ 检验三问（通过标准是什么 / 有没有可观察可测量的判定 / 两个人理解不一致看什么裁决）？② 评审是洒在全程的六个把关节点（需求 / 设计 / 代码 / 测试 / 发布 / 复盘），为什么不是只在上线前做一次（问题越早发现修复成本越低：需求 1 → 发布后 30~70 倍）？③ 评审和复盘有什么区别（把关 vs 改进；复盘是检测器）？④ 反身：你们最近一次评审的通过标准是会后现想的吗？

**Q8（判据运用 · 验证/确认三要素 · 案例③④）**
"恒信的李工说'业务方点了测试环境，通过了'；冰链的小赵组织了一场真实运输测试——用例全过，但车厢一颠簸，温度记录仪断档 30 秒，测试台架复现不了。用验证三要素和确认三要素拆开这两场：各满足验证吗？各满足确认吗？为什么'用例全过，说明不了上路能过'？"
追问：① Ada 三问（月底对账的数据真实还是造？真实月底时间点真实并发下做的吗？法务电子签章审批链业务方验证过"谁审谁签"吗？）——李工的 UAT 全答不上 ② 断档 30 秒为什么测试台架复现不了（测试环境里没有路；用例的参照是需求文档，真实场景的参照是"疫苗能不能安全送到"）③ 隐含需求（振动下温度记录连续 / 月底对账口径）为什么只有确认兜得住（验证的尺子在文档、确认的尺子在场景；冰山比喻）④ 反身：你们最近一次"全绿"，放进真实场景会现出什么形？

**Q9（方法时刻 · 规则 15 · 判据主义 · 判据运用形态）**
"这一章的方法底座时刻是判据主义——不给没有判据的尺子。李工混了三个词，因为他从没给每把尺子立过可检验判据。请亲手给'评审 / 验证 / 确认'各立一条可检验判据：参照是什么、证据要不要、结论记不记录？再用你立的判据，当场拆一张你们自己的 UAT 报告或一场评审会。"
追问：① 你的判据符合判据主义三问吗（是什么 / 失效边界 / 反例）？② 你给三把尺子立的判据，换到冰链 M3（硬件侧：零部件试验 / 整机低温试验 / 真实运输车跑全程）还成立吗？判据变没变——这说明了什么（概念不挑行业）？③ 反身：你们最近一次"验收通过"，是三条可检验判据都打勾，还是靠"报告绿了"？——有判据才算拥有，有标签只是见过。

**Q10（落地生根 · 回部门三个看门人体检）**
"结合你们部门现状，用评审三问、验证三要素、确认三要素三把尺子，给你们最近一次上线/交付做一次'三个看门人体检'——给出最该改进的三件事，每个落到一个动作。"
追问：① 先查哪一关（评审对目标 / 验证对需求 / 确认对用途）？为什么？② 你们最近一次"验收通过"，三个看门人谁没站到门口（对照因果链：只验证不确认 → 测试全过没人用）？③ 两周后回来报告：哪个看门人补上了、哪个还虚着、卡在哪个判据上？
