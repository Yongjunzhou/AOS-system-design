## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：标尺怎么被造——第4章产出规定需求、第5章把标尺立全，这一章看三百条需求怎么被"种"进一棵一棵设计树里，靠分解、分配、分析三个动作接力，从原始需求一路种到产品架构。设计文档为什么必须是树不是散文？方案为什么是分解出来的、不是想出来的？

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：1.1 设计文档是树不是散文（散文三宗罪 / 树的三个构件）→ 1.2 为什么必须是树：织关系（内涵推导：条目化→树→概详两层）→ 1.3 树干树枝是概要、叶子是详细 → 1.4 概要定义 ≠ 架构定义—— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：2.1 三个动作在哪儿做（树内 vs 树间）→ 2.2 分解不是"多列几条"（语义四查 + 指标三场景 + 七种反模式 + 分解规则两层）→ 2.3 分配不是"简单分派"（1:1 + 三自检 + 悬空叶子）→ 2.4 符合性分析不是"空话"（语义三问 + 指标符合 + 时机）→ 2.5 概详不焊死—— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：3.1 五层链（需求/方案相对 + 文档结对 + 三动作每层重复）→ 3.2 一棵树的可靠性：验收与追溯（五维）—— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **概要定义**（preliminary definition）：设计树的枝干——从根到末级的树形结构 + 映射表，回答"结构是什么、承接了谁"。判据：**挂枝问**（任取一条需求，能说出它挂在哪根枝梢上吗；说不出的，树还没种全）。对立=详细定义；辨析=概要定义 ≠ 架构定义（词汇病）。
2. **详细定义**（detailed definition）：设计树的叶子——长在末级节点下的条目列表，每条可独立定义、独立验证。判据：**五件套**（编号、需求描述、性能指标、验收标准、映射目标，缺一叶子不完整）。
3. **分解**（decomposition）：在枝梢上长叶子——把概要定义的末级节点展开成详细定义的条目（树内动作）。判据：**语义四查 + 指标三场景**。
4. **分配**（allocation）：把叶子 1:1 搬到下一棵树的枝梢——详细条目映射到下层方案概要末级（树间动作）。判据：**分配三自检**（全覆盖 / 1:1 / N:1 合理）。
5. **符合性分析**（compliance analysis）：检查叶子挂得对不对——每个方案枝梢是否充分满足所承接的全部需求（语义 + 指标）。判据：**满足句式**（"针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"）。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 设计文档（树） | 散文（文章） | 可定位/可承接/可追溯 vs 线性通读、无处查询 |
| 概要定义（枝干） | 详细定义（叶子） | 管结构（组织与承接） vs 管内容（定义与验证） |
| 分解 | 分配 | 树内（枝干 ↔ 叶子） vs 树间（叶子 → 下一树枝梢） |
| 符合性分析 | 需求分析（第4章） | 检查（往后看，方案接没接住） vs 加工（往前看，需求清不清楚） |
| 概要定义 | 架构 | 结构骨架（一份文档） vs 系统不可还原的涵义（第9章） |
| 切法（内容规则） | 判据（形式判据） | 怎么切（结对特有、领域经验） vs 切得好不好（全链通用、逻辑要求） |

### 关联概念（近界 · 辨析）

- **分解 × 分配（树内/树间）**：一棵树内部只能发生分解；一旦到了分配，你已经站在两棵树之间了。新手把三个动作当成同一棵树的三个步骤，是本章最容易被混过的点。
- **需求分析（第4章）× 符合性分析（第6章）**：同一个"分析"，两件事——第4章是加工（往前看，问需求清不清楚），本章是检查（往后看，问方案接没接住）。近亲混用，正是第1章说的词汇病。
- **符合性分析 × 评审（第7章）**：符合性分析是设计动作（每层分配后立刻做），评审是门禁；分析是评审的输入。第7章把"验证"纳入更完整框架时，符合性分析会归位。
- **概要定义 × 架构（第9章）**：文档层面≠（结构骨架 vs 不可还原涵义）；描述层面可作架构的一种描述（把系统结构写下来，本身就是架构描述的一种）。两层划线，不把话说满。
- **一棵树 × 五层链**：设计树不是一棵，是五层链上每一对"需求-方案"都有一棵；树不挑角色——需求是树，方案也是树。
- **概详分离 × 第4章需求变更控制 / 第12章配置管理**：枝干管结构、叶子管内容，变更频率与原因不同；枝干和叶子是两个配置项，分别纳入基线（第12章）。
- **分解规则 × 解耦**：切法业务化（结对独有）× 判据统一（全链共用）× 契约共享（候选声明 + 骨架先行）——分解与分配解耦，从"猜谜"变"对账"。
- **树 × 第1章织关系**：导航路径与承接路径合一——把散点织成结构，让导航和承接走同一条路；方案是结构，不是堆。
- **验收五维 × 追溯**：枝干/叶子/映射/分析验"一棵树"，追溯把五层树串成一条总验证（正向从需求到组件、反向从组件到需求）。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 散文三宗罪：不可定位（文章线性流动，方案是给五类人分别"查询"的）、不可承接（文章没有叶子，需求没地方落）、不可追溯（文章没有映射，变更没法定位到具体位置）——李工写得"太像文章"是失败的根源（§6.2.1）。
2. 树的关键是枝梢和叶子怎么咬合：枝梢（末级节点）= 需求挂靠的落脚点（一根枝梢可挂多条，N:1）；叶子（详细条目）= 能 1:1 搬走的原子条目（一片叶子只能属于下一棵树的一根枝梢）（§6.2.1）。
3. 树为什么行：内涵推导三步骤——设计开发的本质（把"尚未存在"变成"可建造"）要求可验证、可落实 → 内容必须条目化 → 条目化带来数量爆炸 → 必须组织成树 → 管理理解要概要、落实验证要详细 → 概详两层（§6.2.2）。
4. 树是唯一能让"导航路径"与"承接路径"合一的形态——列表没有层次、表格是映射不是内容组织、网状没有唯一根回答不了"这条需求归谁"（§6.2.2）。
5. 形态是为动作服务的：条目化→为了能逐片搬走（分配）；有树→为了有地方承接（分配与分析）；概详→正是分解的对象与产物（§6.2.2）。
6. 概要定义 ≠ 架构定义的三个理由：与"架构"撞车（重量级词命名轻量文档是词汇病）；不对称（孪生叫"详细定义"，"详概分离"原则自证）；名实相符（它比架构轻，是结构骨架）（§6.2.4）。
7. 两层划线：文档层面≠（结构骨架 vs 不可还原涵义）；描述层面可作架构的一种描述（把系统结构写下来就是架构描述的一种）——不等于，在文档与涵义之间划线；可作描述，在描述与涵义之间搭桥（§6.2.4）。

**第二幕 · 磨边弧的机制（不是什么）**
8. 三个动作各有发生地：分解在树内（一棵树内部，枝干 ↔ 叶子），分配、分析在树间（两棵树之间）；一棵树内部只能发生分解（§6.3.1）。
9. 分解四查各防一类错：覆盖完整防漏、不超出防多、逻辑一致防矛盾、约束继承防丢——一漏一多是方向相反的两个错误，但都让树偏离它该承接的需求（§6.3.2）。
10. 指标分解三场景按顺序判断：可拆分（子指标存在函数关系，如串联可加、串联乘积）→ 下放（所有子需求同值继承）→ 暂不分解（系统级耦合算不清，标注"向下一层传递"，不做假分解）——最忌讳假装能拆（§6.3.2）。
11. 七种反模式；"过分解"最值得说：把实现步骤当功能拆，把 How 混进 What——第4章说需求回答 What、方案回答 How，分解是需求侧的动作，只切 What、不写 How（§6.3.2）。
12. 分解规则分两层：切法（内容规则）必须业务化（结对特有、领域经验，全项目通用切法是自欺欺人）；判据（形式判据）必须统一（全链共用，是解耦的根基——分配对账需要所有结对都认的账本语言）（§6.3.2）。
13. 解耦 = 判据统一 × 切法业务化 × 契约共享：候选声明（分解"声明我归谁"，分配"验证对不对"——分解与分配之间唯一的耦合点）+ 骨架先行（水电点位图：两拨工人各自施工、共享一张图）（§6.3.2）。
14. 1:1 约束三个理由：避免重复实现（同一逻辑两处实现，改一处漏一处）；保证验证有唯一对象；让变更可定位（§6.3.3）。
15. 枝梢承接叶子是 N:1（聚合），叶子归宿枝梢是 1:1（定位）——两个方向别搞反：让叶子挂多个枝梢违反 1:1，让一个枝梢只挂一片叶子浪费聚合能力（§6.3.3）。
16. 一片叶子需要两个枝梢才能承接，本身就是该拆片的信号——1:1 约束真正的作用是逼你拆得足够细；悬空叶子两分：欠分解（该拆片）or 方案树没种全（该加枝），分配检出的问题一半是上游的错（§6.3.3）。
17. 符合性分析不是空话：语义符合三问（覆盖度/映射正确性/分析具体性）+ 指标符合（满足/降级/丢失）——"本节点满足上述需求"什么都没说（§6.3.4）。
18. 第4章"分析"是加工（往前看），本章"分析"是检查（往后看）——同一场评审会上听到"我们做一下需求分析"，先问对需求做加工还是对承接做检查（§6.3.4）。
19. 分析时机：每层分配完立刻做，不是末次全量验证——分析越晚，发现的缺陷离源头越远，返工越贵；逐层清账，不是最后算总账（§6.3.4）。
20. 概详不焊死：修剪枝条（调整分类层级）只动概要定义、叶子一片不用动；长新叶（新增需求挂已有枝梢）只动详细定义 + 映射表补一行承接；只有枝梢本身变了才同时动（§6.3.5）。

**第三幕 · 往哪去的机制（运用）**
21. 五层链：原始需求 → 相关方需求 → 业务流程 → 系统需求 → 产品架构，从"一句话"到"可开发的组件"；每层之间都是一个"需求-方案"结对（§6.4.1）。
22. 需求/方案相对：中间层是双面人——对上是方案、对下是需求；接力棒是同一份文档只是换了角色；这也是三个动作能接力工作的前提（上一对"分析"刚结束，下一对"分解"从同一份文档开始）（§6.4.1）。
23. 文档结对：有需求必有方案、有方案必有需求；两阶段工作法——骨架阶段（先约定下层方案的概要树 + 建立初步映射）、填充阶段（上下层并行填充）；骨架先行让"缺枝"问题最早暴露而不是最晚（§6.4.1）。
24. 三个动作在每一对结对上重复执行：三动作不是三个步骤——步骤是串行的一次性流程，动作是每一层都要重复的固定功课；五层链是四遍"长叶子、搬叶子、查叶子"（§6.4.1）。
25. 验收五维：枝干（概要定义完整）、叶子（详细定义原子、指标完整）、映射（分配 1:1 满足率）、分析（每个枝梢语义+指标都过、无空话）、追溯（正向从原始需求走到组件、反向从组件走回需求）——追溯是把五层树串起来的总验证（§6.4.2）。
26. 设计开发止于可实现（第3章）：叶子细化到能被 1:1 分配、枝梢具体到能被开发承接、每个枝梢都做过符合性分析；一棵树的可靠性不靠写得长，靠每一对"需求-方案"咬合得好（§6.4.2）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "设计方案写得越长越详细越好，六十页比一页树强。"
2. "方案是写出来的，靠文笔和篇幅。"
3. "方案是一篇文章，从头读到尾就完了。"
4. "概要定义就是架构定义，换个名字而已。"
5. "架构都'定义'了，还动什么——画完即定型。"
6. "分解就是多列几条。"
7. "'分解规则'应该全项目统一，一套切法拆所有结对。"
8. "把实现步骤写进需求，写得更具体就是更好。"
9. "指标拆不动的就先不管。"

18. "树就是画一张结构图。"

### 本章判据（八把尺子）

1. **设计文档是一棵树**：枝干（概要定义）+ 叶子（详细定义），缺一不完整；枝干管结构、叶子管内容，分开维护——结构不轻易变，内容随时长。
2. **概要定义回答"结构是什么、承接了谁"；详细定义回答"每个模块具体做什么"**——每片叶子都有编号、描述、指标、验收标准、映射目标。
3. **分解四查**：覆盖完整（不漏）、不超出（不多）、逻辑一致（不矛盾）、约束继承（不丢）；指标三场景：可拆分 / 下放 / 暂不分解（标注"向下一层传递"）。
4. **分配三自检**：全覆盖（都搬了）、1:1（一片叶子一个归宿）、N:1 合理（每个枝梢挂 2~5 片较优，以语义为准）。
5. **符合性分析**：每个方案枝梢语义+指标都过；"本节点满足上述需求"是空话。
6. **每个文档结对都走"分解→分配→分析"**；骨架先行、填充并行；五层链是四遍"长叶子、搬叶子、查叶子"。
7. **分解规则分两层**：切法（内容规则）必须业务化——每个结对按领域经验定义怎么切；判据（形式判据）必须统一——四查、三场景全链共用；候选声明 + 骨架先行，让分解与分配解耦。
8. **概要定义 ≠ 架构定义**：文档层面——概要定义是结构骨架（一份文档），架构是系统不可还原的涵义（第9章）；描述层面——把系统结构写下来的概要定义，可以作为架构的一种描述。两层划线，不把话说满。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"一棵树"（设计文档 = 树：枝干概要 + 叶子详细），并辨析 树 vs 散文（散文三宗罪：不可定位 / 不可承接 / 不可追溯）。
2. 能定义"概要定义"（设计树的枝干：根到末级树形结构 + 映射表，回答"结构是什么、承接了谁"），并说出判据（挂枝问）。
3. 能定义"详细定义"（设计树的叶子：长在末级节点下的条目列表，每条可独立定义、独立验证），并说出判据（五件套）。
4. 能辨析 概要定义 vs 架构定义（文档层面≠、描述层面可作架构的一种描述；词汇病 = 用重量级词命名轻量文档）。
5. 能定义"分解"（在枝梢上长叶子：概要末级 → 详细条目，树内动作），并辨析 分解 vs 分配（树内 vs 树间）。
6. 能定义"分配"（叶子 1:1 搬到下一棵树的枝梢，树间动作），并说清 1:1 约束（一片叶子一个归宿）与 N:1（一根枝梢挂多片）两个方向。
7. 能定义"符合性分析"（检查每个方案枝梢是否充分满足所承接的需求，语义 + 指标），并辨析 符合性分析 vs 需求分析（第4章：加工 vs 检查）。
8. 能辨析 分解规则两层：切法（内容规则·结对特有·领域经验）vs 判据（形式判据·全链通用·逻辑要求）。
9. 能说出散文三宗罪各自对应树的哪个回答（定位 → 枝梢/查询；承接 → 叶子/任务单；追溯 → 需求→枝梢映射）。
10. 能说出五层链（原始需求→相关方需求→业务流程→系统需求→产品架构）与"需求/方案相对"（中间层是双面人），以及"动作"与"步骤"的区别。

### 原理层（应能解释为什么）

1. 能解释为什么树是唯一能让"导航路径"与"承接路径"合一的形态（列表无层次、表格是映射、网状无唯一根）。
2. 能解释为什么设计内容必须条目化（设计开发的内涵要求可验证、可落实 → 最小单元）。
3. 能解释为什么树必须分成概详两层（管理理解要概要、落实验证要详细；"既要看懂、又要做实"逼出来的）。
4. 能解释为什么"形态是为动作服务的"（条目化→分配；有树→承接；概详→分解的对象与产物）。
5. 能解释为什么概要定义 ≠ 架构定义的三个理由（撞车 / 不对称 / 名实相符）。
6. 能解释为什么"一漏一多"是方向相反的两个错误（漏了需求在方案里消失，多了长出没被授权的影子需求）。
7. 能解释指标分解三场景的判断顺序（可拆分→下放→暂不分解标注传递），以及为什么"假装能拆"最忌讳（M3 可靠度 0.995×0.995×0.999≈0.989 < 0.99，数字落纸立刻回炉）。
8. 能解释为什么过分解是需求被过度约束最常见的形式（只切 What 不写 How；需求回答 What、方案回答 How）。
9. 能解释为什么判据必须统一、切法必须业务化（解耦的根基：分配对账需要所有结对都认的账本语言）。
10. 能解释解耦 = 判据统一 × 切法业务化 × 契约共享（候选声明是唯一耦合点，有它分配不用猜；骨架先行 = 水电点位图）。
11. 能解释 1:1 约束的三个理由（避免重复实现 / 保证验证有唯一对象 / 让变更可定位）。
12. 能解释为什么"一片叶子需要两个枝梢"是该拆片的信号（1:1 约束逼你拆得足够细）。
13. 能解释为什么"本节点满足上述需求"是空话（什么都没说；要逐片叶子说清怎么满足、指标多少）。
14. 能解释为什么分析是每层分配后立刻做、不是末次全量验证（分析越晚，缺陷离源头越远，返工越贵）。
15. 能解释"需求/方案相对"为什么是三个动作能接力工作的前提（接力棒是同一份文档只是换了角色）。
16. 能解释为什么骨架先行让"缺枝"问题最早暴露（骨架阶段就要约定有哪些枝梢、哪些叶子挂哪些枝）。
17. 能解释为什么三动作不是三个步骤（步骤是串行的一次性流程，动作是每一层都要重复的固定功课）。
18. 能解释验收五维与追溯的关系（枝干/叶子/映射/分析验一棵树，追溯把五层树串成总验证；设计开发止于可实现）。

### 判据层（应会用）

1. **挂枝问**：任取一条需求，能说出它挂在哪根枝梢（末级节点）上吗？说不出的，树还没种全；失效边界：最上游原始需求无树、桥（业务流程层）无叶子。
2. **五件套**：每条叶子都有编号、需求描述、性能指标、验收标准、映射目标吗？缺一，叶子还不完整。
3. **语义分解四查**：覆盖完整（父里有的叶子缺了吗）/ 不超出（叶子引入父范围外新内容了吗）/ 逻辑一致（叶子之间矛盾吗）/ 约束继承（父的非功能约束至少一片叶子承接了吗）。
4. **指标分解三场景**：可拆分（子指标函数关系，串联合成）/ 下放（同值继承）/ 暂不分解（标注"向下一层传递"）。
5. **分配三自检**：全覆盖（叶子数对账）/ 1:1（一片一个归宿）/ N:1 合理（每枝梢 2~5 片较优，以语义相关为准）。
6. **悬空叶子判断**：欠分解（该拆片）vs 方案树缺枝梢（该加枝）——用"拆得开吗"区分。
7. **符合性分析满足句式**："针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"——写不出这句的，等于没分析。
8. **分解终止判据**：叶子细化到"每片都能被 1:1 搬到下一棵树的唯一一根枝梢"为止；拆到还需两个枝梢才能承接——继续拆；每片恰好落在一个枝梢——停。
9. **概详分离维护判据**：修剪枝条只动概要定义、长新叶只动详细定义（+ 映射表补一行承接）、枝梢本身变了才同时动。
10. **验收五维**：枝干（树完整、枝梢四要素齐）、叶子（分解完成、叶子原子、指标完整）、映射（1:1 满足率、覆盖 100%）、分析（语义+指标都过、无空话）、追溯（正向/反向走通）各 100% 合格线。

### 纠错红线十条

1. **先表态后翻案**：先让学员说"六十页当然比一页树负责，这还用讨论吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："树不是散文"别翻成"不要写详细"（详细要落在叶子上）；"分解≠多列几条"别翻成"分解越少越好"（欠分解一样错）；"概要定义≠架构"别翻成"概要定义没用"（它是架构的一种描述）。
3. **判据配机制**：每条反转都有"为什么"（机制）和"怎么当场验证"（判据）。
4. **归责到可对照动作**："你没在种树"落到"挂枝问答不上 / 五件套缺三样 / 四查漏一查 / 满足句式写不出"，不归咎"文笔不好"。
5. **教机制不教断言**：教"为什么必须条目化"（可验证、可落实的内在要求），不教"条目化就是好"。
6. **先立尺子再翻案**：先给挂枝问/四查/三自检/满足句式，再翻李工"我已经写得很全了"。
7. **拉开强度层次**：★★★ 常识（写长=负责 / 概要=架构 / 一条需求分两个模块双保险）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（如把一份散文式方案拆成树，任取一条需求点出位置）。
9. **单一权威不另立标准**：判据引用书（八把尺子），不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：把一份"散文式"设计文档种成树

> 目标：用本章八把尺子，把团队一份"散文式"设计文档改造成一棵树（枝干概要 + 叶子详细），产出改造成果 + 三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑文档（先立枢纽）**：选一份"最近交付、你还是觉得讲不清结构"的方案——最像散文的那份。最自信"写得很全"的，往往是最没种成树的。
2. **立枝干（概要定义）**：把文档内容归纳成 根 → 枝 → 枝梢 三级；标出分类节点（文件夹，无实体含义）与末级节点（枝梢，承接需求）。**话术**："这份方案有几大块？每块到哪一层才算'一件事'？"
3. **挂需求（挂枝问）**：从文档里取出前 20 条需求，任取一条问"挂在哪根枝梢"——答不上的，就是散文没种全的证据。**话术**："这条需求，在这棵树上有家吗？"
4. **长叶子（详细定义 · 五件套）**：取一根枝梢，把它的内容拆成 3~5 片叶子，每片补五件套：编号、需求描述、性能指标、验收标准、映射目标。**话术**："这片叶子，能 1:1 搬到下一棵树的唯一一根枝梢吗？"
5. **分解四查**：覆盖完整（父里有的叶子缺了吗）/ 不超出（长出影子需求了吗）/ 逻辑一致（叶子打架吗）/ 约束继承（系统级约束至少一片叶子承接了吗）。
6. **分配三自检**：全覆盖（叶子数对账）/ 1:1（一片一个归宿）/ N:1 合理（每枝梢 2~5 片较优）。有悬空叶子？先判断是欠分解（该拆片）还是方案缺枝（该加枝）。
7. **符合性分析句式**：对每个枝梢写一句"针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"——写不出的枝梢，就是没接住。
8. **出报告**：树 vs 散文结论 + 最该补的三个动作；最后一条建议照书抄——先把"概要定义"从"架构定义"的名字里正名出来。

**卡住怎么判断**：挂枝问答不上 = 树还没种全；五件套缺 = 叶子不完整；四查漏 = 一漏一多方向相反的错误；写不出满足句式 = 该枝梢没接住；悬空叶子 = 先判断欠分解还是缺枝。不必八步全做完，找到第一个卡住的地方就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 任取一条需求能说出挂在哪根枝梢？（挂枝问） | □ | 树还没种全——散文不可定位 |
| 每条叶子有编号/描述/指标/验收/映射？（五件套） | □ | 叶子不完整，散落的条目只是段落 |
| 分解四查过了？（覆盖/不超出/一致/继承） | □ | 一漏一多是方向相反的错误：漏了需求消失、多了影子需求 |
| 指标三场景判定了？（可拆分/下放/传递） | □ | 指标可能假装能拆、或悄悄消失 |
| 分配三自检过了？（全覆盖/1:1/N:1） | □ | 重复实现或需求遗漏，验证无对象 |
| 悬空叶子判断了？（欠分解 vs 缺枝） | □ | 一半是上游的错：分配检出的问题要找分解或找方案 |
| 每个枝梢写得出符合性分析句式？ | □ | "本节点满足上述需求"是空话 |
| 骨架先行了吗？（先约枝梢清单再填内容） | □ | 缺枝问题最晚才暴露 |
| 概要定义和架构分开了吗？（文档 ≠ 涵义） | □ | 词汇病：重量级词命名轻量文档，画完即定型 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"恒信评审会，李工打开六十页《合同审批系统总体设计方案》：『我写了两个月，覆盖了全部三百条需求，下面按章节过一遍——』法务张总翻到第 23 页找『谁能驳回』，财务老王翻到第 31 页找『对账口径』，业务小周问『上线先点哪里』，李工答不上来。Ada 合上文档说：『这不是一篇方案，这是一本小说。』为什么六十页文章是『小说』？树和散文的区别到底是什么？用散文三宗罪给李工的方案逐条定罪。"
追问：① 散文三宗罪（不可定位/不可承接/不可追溯）各是什么？树的三个构件（根与层级/分类节点/末级节点）各怎么回答它们？② 末级节点（枝梢）挂需求是 N:1、叶子（详细条目）搬走是 1:1——为什么枝梢可以挂多条、叶子只能有一个归宿？③ 为什么人天然写散文（写作是线性的，树是种出来的——没人教过怎么种树）？④ 反身：你们最近一份"总体设计"，是树还是散文？任取一条需求，能一步点到它的位置吗？

**Q2（见树见林② · 概念关系）**
"请给出 概要定义、详细定义、分解、分配、符合性分析 这五个概念在一棵『设计树』上的关系；再给出『一棵树』和『五层链』的关系——设计树是一棵，还是每对『需求-方案』都有一棵？"
追问：① 枝干（概要定义）和叶子（详细定义）各回答什么问题？为什么必须两样都有（枯树 vs 落叶）？② 三个动作各发生在哪儿（树内/树间）？『形态是为动作服务的』怎么理解（条目化→分配、有树→承接、概详→分解的对象与产物）？③ 概要定义和『架构』是什么关系？为什么叫『概要』不叫『架构』（词汇病：重量级词命名轻量文档）？④ 五层链的中间层为什么是『双面人』（对上是方案、对下是需求）？⑤ 反身：你们说的『架构定义』，到底是树形文档，还是系统不可还原的涵义？

**Q3（真悖论 · 写得长 vs 写得对）**
"李工写六十页方案，自认是负责任——写得越详细越全面，不是越好吗？六十页难道不比一页树更负责吗？可这一章说：方案不是写出来的，是种出来的；文章装不下三百条需求——文章没有叶子。哪个对？什么判据分清『写得长』和『写得对』？"
追问：① 一篇文章为什么『装不下三百条需求』（文章没有叶子、没有映射、没有承接）？② 树为什么行——『导航路径与承接路径合一』是怎么从设计开发的内涵推出来的（可验证、可落实→条目化→组织成树→概详两层）？③ 六十页 vs 一页树，差的不是『长度』是什么（有没有叶子/映射/可验证）？④ 反身：你们见过『写得越长越负责』的方案吗？它最后在哪一环漏了需求？

**Q4（真悖论 · 分解：多列几条 vs 精确切分）**
"有人说：分解就是把一条需求多列几条，列得越多越细越好。可这一章说：分解是精确切分，不是顺手多列——漏了是『覆盖完整性』失败，多了是『影子需求』。多和漏哪个更危险？什么判据能同时防住这两个方向相反的错误？"
追问：① 语义分解四查（覆盖完整/不超出/逻辑一致/约束继承）各防什么？② 指标分解三场景怎么判断（可拆分函数关系→下放同值继承→暂不分解标注『向下一层传递』）？冰链 M3 可靠度 0.99 拆出 0.995×0.995×0.999≈0.989<0.99 说明什么？『指标拆不动的就先不管』错在哪？③ 『分解规则』该不该全项目统一？——切法（内容规则）为什么必须业务化？判据（形式判据）为什么必须统一？候选声明 + 骨架先行怎么把分解与分配解耦？④ 反身：你们拆需求时，默认是『多拆几条保险』还是『精确切分』？

**Q5（真悖论 · 三个动作是三个步骤还是一遍遍重复的功课）**
"设计总有个先后：先分解、再分配、再分析——这难道不是三个步骤吗？可这一章说『三个动作不是三个步骤』：一棵树内部只能发生分解；符合性分析要每层分配完立刻做、不是留到最后做一次总检查。哪个对？什么判据分清『步骤』和『动作』？"
追问：① 三个动作各在哪儿做（分解树内、分配分析树间）？为什么『一棵树内部只能发生分解』？② 五层链是几遍『长叶子、搬叶子、查叶子』（四对结对、每遍三动作）？文档结对为什么『骨架先行、填充并行』——先约枝梢清单，怎么让『缺枝』问题最早暴露而不是最晚？③ 符合性分析为什么必须『每层分配完立刻做』（分析越晚，缺陷离源头越远，返工越贵）？④ 反身：你们做设计是『四个大阶段一次走完』，还是每一层都反复对账？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 挂枝问 + 五件套 · 案例进展①）**
"李工熬了一夜，把六十页文章揉成一页树：合同审批系统 = 三个枝（审批业务域 / 平台服务 / 数据与接口）、十根枝梢。第二天拿给 Ada 看，Ada 点头说『好多了』，又问了两句：『法务关心的审批规则，在哪个枝上？』——李工指了『审批流程』；『那这根枝梢上挂了哪几条需求？』——李工愣住了：枝梢上还没有叶子。为什么树还只是骨架就不算方案？用挂枝问 + 五件套检验：李工的一页树缺什么？"
追问：① 一棵树为什么必须枝干叶子两样都有（枯树 vs 落叶）？枝干和叶子为什么要分开维护（结构不轻易变、内容随时长）——修剪枝条动什么、长新叶动什么？② 挂枝问：任取一条需求，能说出挂在哪根枝梢吗？③ 五件套：一片完整的叶子要有哪五样（编号/描述/指标/验收/映射）？④ 反身：你们最近一张『系统结构图』，是树，还是一张没有映射表的图？

**Q7（判据运用 · 语义四查 + 指标三场景 · 案例进展②）**
"李工第一次分解『合同校验』拆了一下午：金额校验、条款校验、资格校验三片。Ada 只问了一句：『父需求里金额 ≥ 500 万或三年期以上要重点审，你的叶子都覆盖了吗？』——李工回去一查：期限校验漏了。他还顺手长了一片『合同打印』。用语义分解四查给李工把关：他犯了哪两查？再把冰链 M3 的『全程可靠度 ≥ 0.99』做一次指标分解三场景判断。"
追问：① 语义四查（覆盖完整/不超出/逻辑一致/约束继承）各防什么？为什么『覆盖完整』和『不超出』是姊妹对（一漏一多、方向相反）？② 指标三场景怎么按顺序判断（可拆分函数关系→下放同值继承→暂不分解标注『向下一层传递』）？M3 拆出硬件 0.995 × 固件 0.995 × 云端 0.999 ≈ 0.989 < 0.99，账算不过来怎么办？③ 『过分解』为什么是需求被过度约束最常见的形式（只切 What 不写 How）？分解终止判据是什么（每片能 1:1 搬到唯一一根枝梢）？④ 『分解规则』怎么定——切法（怎么切）是结对特有还是全项目统一？判据（切得好不好）统一了吗？为什么？⑤ 反身：你们最近一次拆需求，漏了哪片叶子？多长了几片？

**Q8（辨边界 · 分配 vs 符合性分析 · 案例进展③+④）**
"李工把系统需求的叶子往产品架构上搬，搬到最后剩下一片没人要：SYS-004.01 合同全文检索。Ada 让他先别硬塞。过了几天，符合性分析评审上，李工又卡住：Ada 在第4章澄清的那条『重要合同要审批』（金额 ≥ 500 万或三年期以上）——分配时归到了『合同校验』，但『审批引擎』的定义里没有『承接重点审触发』。这两件事分别是什么动作没做到？分配和符合性分析各自检查什么？一片叶子没有归宿、一个枝梢没接住需求，各怎么判断、各找谁？"
追问：① 1:1 约束的三个理由（避免重复实现/验证有唯一对象/变更可定位）？② 枝梢挂叶子是 N:1（聚合）、叶子归枝梢是 1:1（定位）——方向搞反会怎样？③ 悬空叶子两分：欠分解（该拆片）vs 方案缺枝（该加枝）——用『拆得开吗』区分；为什么说『分配检出来的问题一半是上游的错』？④ 第4章的『需求分析』（澄清/分解/排序/协商）和第6章的『符合性分析』，同一个『分析』——哪个是加工（往前看，需求清不清楚）、哪个是检查（往后看，方案接没接住）？评审会上听到『我们做一下需求分析』，先问哪句？『本节点满足上述需求』为什么是空话？满足句式怎么补？⑤ 反身：你们系统里有没有一片叶子被两个模块同时实现（重复实现）？有没有一个枝梢写着『满足上述需求』？

**Q9（方法时刻 · 规则 15 · 织关系，方法操作类独立成题 + 跨域变体）**
"李工原来把三百条需求排成一列（堆），Ada 教他把它们织成树（结构）——这是第1章的『织关系』：方案是结构，不是堆。方法底座时刻不让你们背『树』的定义，请亲手织一次：把下面这段『散文』改造成一棵树——先立枝干（概要定义：根 → 枝梢，标出分类节点与末级节点），再让每条需求长成一片叶子（详细定义：编号 / 需求描述 / 指标 / 映射目标）。改完回答：这棵树的『导航路径』和『承接路径』为什么是同一条路？"
散文素材（取书内现成）：审批驳回的规则（法务关心）、对账的统计口径（财务关心）、上线先点哪里（业务关心）；树的现成形态：三个枝（审批业务域 / 平台服务 / 数据与接口）+ 十根枝梢。
追问（跨域变体）：① 恒信把六十页散文织成一棵树，换到冰链 M3——老周把方案结构文档叫『架构定义』的词汇病，正名后它的『概要定义』该回答什么（结构是什么、承接了谁）？同一个概念（树 = 结构不是堆）换到硬件世界，判据变没变？——这说明什么（概念不挑行业）？② 你织出的这棵树，任取一条需求能不能『一步点到位置』（导航）又『一步点到承接方』（承接）？③ 反身：你们部门最近一份方案，是排成一列的文章，还是织成树的结构？有没有『没人教过怎么种树』这回事？

**Q10（落地生根 · 回部门设计树体检）**
"结合你们部门现状，用本章的挂枝问、五件套、分解四查、分配三自检、符合性分析句式，给一份最近的设计文档做一次『设计树体检』——给出最该改进的三件事，每个落到一个动作。"
追问：① 几把尺子先查哪两把（先挂枝问还是先五件套）？② 你们最近一次评审『找不到结构』，是不是就是文章没有叶子的证据？③ 你们系统里有没有『概要定义被叫成架构定义』的词汇病？④ 案例进展⑤里，Ada 从『金额 ≥ 500 万要重点审』一路画到『审批引擎』：『过了四道分解、四道分配、四道分析。中间任何一道断了，这条需求就丢了。』你们部门能任取一条需求，从原始需求一路点到产品组件吗？⑤ 两周后回来报告：哪把尺子测出不合格、补了哪个动作。
