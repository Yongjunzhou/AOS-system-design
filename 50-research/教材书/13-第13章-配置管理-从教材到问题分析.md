### 核心概念（含根概念标注）

> 标注规则（v2.1）：按第1章 §1.2.4 根概念四标准（原子性/生成性/不可替代性/递归性）标出本章档案中的**承重柱**——先抓根、再展骨架。本章的承重柱 = **配置**（见头注论证，正文依据：开篇枢纽"配置……是这一切的地基"）；版本/基线为骨架层枢纽。

1. **配置**（configuration）**【根概念 · 本章承重柱】**：实体被记录在配置信息里、相互关联的功能特性与物理特性——实体"被记录下来的样子"（ISO 10007）。判据：配置三问（类别边界/记录边界/关联边界——三问全"是"才是配置）。它提供"内容"。**承重柱证据**：原子性（在配置家族内最不可再归约——版本/基线分别以"配置项/配置信息"为前提，配置锚定外部锚点"实体"后独立成立）/ 生成性（版本=配置项的演进刻度、基线=被批准冻结的配置信息、配置管理=对配置的管理，全从它派生）/ 不可替代性（去掉配置，版本失去"谁的演进"、基线失去"什么的参照"，整章地基崩塌）/ 递归性（需求配置→设计配置→实物配置→运行/部署配置，同一"组合成形"层层生效）。
2. **版本**（version）【骨架 · 枢纽】：配置项的初始发布或其后基于完整构建的重新发布（ISO/IEC/IEEE 24765）——时间轴上的演进刻度，回答"走到第几步"。判据：版本判据一问（这一个编号能精确对应到"哪一次完整构建"吗？能——是版本；不能——还不算版本）。它提供"位置"。
3. **基线**（baseline）【骨架 · 枢纽】：经批准、确立了产品在某一时点的特性、作为全生命周期各项活动参照的配置信息（ISO 10007:2017）——被批准冻结的参照。判据：基线三问（被批准了吗/被冻结了吗/全生命周期拿它作参照吗——三问全"是"才是基线）。它提供"资格"。

### 关联概念（近界 · 辨析）

- **配置项 / 配置 / 配置信息 三分离**：三者都锚定"实体"，不再互引——配置项=被纳入管理的实体（对象·管哪些）、配置=实体被记录的关联功能+物理特性（属性·它是什么样）、配置信息=记录特性的资料（记录·拿什么核对）。体检比方：人是配置项、身高体重是配置、体检档案是配置信息。最大坑：文档既是"配置信息"（它描述谁）又可以是"配置项"（它自己要不要被管）——两个层面不冲突。
- **版本 / 修订 / 变体 / 基线 四词**：版本=时间先后（走到第几步，对外整体编号）、修订=内部变更次数（Rev A/B/C，更细）、变体=空间并存（有几种形态，与版本正交）、基线=被批准冻结的参照（哪一版被盖章）。基线 = 变体 × 版本的交叉点被盖章。
- **配置 × 版本 × 基线 三分工**：配置提供"内容"、版本提供"位置"、批准提供"资格"——三者齐备，才成一个基线。
- **四把尺子防撞名**：配置三问验"一个东西算不算配置"（记录了吗/功能物理特性吗/关联成整体了吗）；版本判据一问验"是不是版本"（能精确对应完整构建吗）；基线三问验"这一版够不够格当基线"（被批准/被冻结/作参照）；配置管理三问验"整个产品配置管理做到位没有"（应该是什么/实际是什么/怎么变成这样的）。一把管单个概念、一把管单版资格、一把管整体目的，各量各的。
- **配置信息 ↔ 第7章产品数据**：配置信息——记录实体功能与物理特性的资料——正是产品数据里被纳入管理的那一部分；产品数据是全集（六类），配置信息是被基线化、被变更控制的那一档。一条需求是草稿=产品数据；被批准纳入基线=配置信息。
- **变与不变的分离 ↔ 第12章推迟决策**：可变的部分（参数/开关/选项）外置、不变的核心（代码/逻辑/功能）只写一遍——正是第12章"显式推迟"的工程形态（让还可能变的东西保持可替换）。
- **配置管理 ↔ 第12章架构决策**：决策记录六问↔配置信息、不可逆决策识别↔基线冻结、推迟决策↔变与不变的分离、变更影响分析↔变更控制——第12章的尺子，第13章给它们配了流程；架构基线尤其要纳管：AD+ADR 一起进配置管理（ISO 10007），评审通过后定格、改动走基线变更流程（"不受变更控制的 AD 不是架构，是草图堆"，第11章）。
- **契约链 ↔ 第6章设计链**：需求→方案→实现，每一对相邻环节都是一组局部"甲方-乙方"——基线是每一级契约的冻结端、版本是交付端（ISO/IEC/IEEE 15288 需方-供方协议）；在结对处的具体形态=候选声明+骨架先行。技术契约（要求-兑现）vs 商务契约（法律/付款/责任）勿混。
- **基线 ↔ 第4章需求基线**：第4章讲"基线是变更的出发原点"（需求管理视角）；本章把原点推广到所有配置项（固件/硬件/代码/图纸/数据）。
- **配置管理 ↔ 第14章治理**：谁有资格批准基线、谁有资格裁决变更——超出配置管理本身，是治理的领地（本章结尾抛给第14章）。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 配置 | 参数文件 | 装好的整机 vs 零件清单——参数是零件，配置是装好的整机 |
| 配置 | 实体的全部客观特性 | 被管理起来的那部分特性 vs 全部特性（三个隐形过滤器切出子集） |
| 配置 | 配置项 / 配置信息 | 属性 vs 对象 vs 记录——不是同一层的东西 |
| 版本 | 基线 | 刻度（流动） vs 参照（冻结）——把版本当基线 = 把里程桩当收费站 |
| 版本 | 变体 | 时间（先后因果） vs 空间（并存差异）——二者正交 |
| 版本 | 修订 | 对外整体编号（较粗） vs 内部变更次数（更细） |
| 版本 | 发布 | 编号 vs 交付动作——发布的东西通常取自基线，但两者不是一个概念 |
| 基线 | 流动状态 | 受控（线右变化必须走变更控制） vs 自由（线左版本自由流动） |
| 基线 | 快照 | 批准+冻结+参照三合一 vs 纯记录 |

| 配置管理 | 文档管理 / 资产管理 | 守护产品全部历史与未来的可答性 vs 归档文件 / 登记财务价值 |

### 核心原理

**第一幕 · 是什么的底层机制**
1. 配置项/配置/配置信息三词互相引用、首尾相连形成循环定义——解耦的方法：往环里引入不依赖任何配置术语的锚点"实体"，让三个概念全部锚定实体、彼此不再互引（§13.2.1）。
2. 配置是实体的全部特性里被三个隐形过滤器切出来的子集：类别边界（只认功能+物理特性）/ 记录边界（只有被配置信息记录/规定下来的才算）/ 关联边界（相互关联的特性整体，不是零散清单）（§13.2.2）。
3. 配置的本质是"组合成形"——configuration ← con-（共同）+ figurare（塑造成形）；中文"配+置"＝配合+安置。它天然是"多体"概念，单个孤立的东西没有配置可言；"从多到一"是 configuration 的全部旅程（即时结果=形 / 正式结果=基线 / 交付结果=实例）（§13.2.1）。
4. 变化是连续的，沟通必须是离散的——版本是把连续的时间切成"可指认的格子"的那把刀（§13.2.3）。
5. 版本解决四个问题：追踪演进（走到哪一步）/ 回溯（回到旧版本）/ 并行（多代共存）/ 复现（版本号是沟通的最小公约数）（§13.2.3）。
6. 基线不是自动生成——从"流动状态"升级为"受控状态"需要一个有权威的动作（被批准）；三特征一个都不能少：被批准（资格）/ 被冻结（状态）/ 作参照（用途）（§13.2.4）。
7. 三种正式基线层层递进：功能基线冻结"目标"（要做什么）/ 分配基线冻结"方案"（由谁实现）/ 产品基线冻结"实物"（实际是什么）；再往下有运行/部署配置——部署的本质就是给某个版本配上某个环境，塑成一个可复现的形态（§13.2.5）。

**第二幕 · 磨边弧的机制（不是什么）**
8. 变与不变的分离：可变的部分（参数）被外置、不变的核心（固件逻辑）只写一遍——所以客户改参数不用重编译；"改一个参数就要改代码、重编译、重发布"是变与不变没分离的信号（§13.3.1）。
9. 版本与时间轴同向（横·流动·刻度），基线与时间轴垂直（竖·切断·闸门）——"横"与"竖"不是上下方向，而是与时间轴的关系：里程桩顺着路排、收费站横在路中间挡住路（§13.3.2）。
10. 变体与版本正交：变体管空间（有几种形态·并存差异）、版本管时间（走到第几步·先后因果）；基线 = 变体 × 版本的交叉点被批准冻结（§13.3.3）。
11. 没有基线，变化就不可言说——描述一个变化必须有一个"从哪变起"的原点；没有原点，"变了"就像在茫茫大海上说"我在动"却没有岸标（§13.3.4）。

**第三幕 · 往哪去的机制（运用）**
12. 变更控制 = 冻结 → 变更 → 再冻结的循环；基线建立之后，任何变化都是"对基线的偏离"，必须走一条正式的路：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线。基线是变更控制的前提，变更控制是基线的守护者（§13.4.1）。
13. 四大活动循环咬合：配置标识管"是什么"（选配置项、立基线）、配置控制管"怎么变"（变更申请→评估→批准→实施）、状态记录管"现在什么样"（记录并报告配置与变更状态）、配置审计管"实物和记录对不对得上"（对照基线核验）——发现不一致，回到标识去修正（§13.4.2）。
14. 核心目的三问：它应该是什么（as-designed，靠需求/设计配置和基线回答）/ 它实际是什么（as-built，靠实物配置和状态记录回答）/ 它是怎么变成这样的（变更历史，靠变更控制和审计回答）——配置管理的全部工作就是让这三个问题在任何时刻都有答案（§13.4.3）。
15. 配置管理 = 架构决策的守护者：决策记录六问↔配置信息（把决定写下来）、不可逆决策识别↔基线冻结（识别出不可逆所以冻结成参照）、推迟决策↔变与不变的分离（保持可变部分可替换）、变更影响分析↔变更控制（个人尺子流程化）——第12章的尺子，第13章给它们配了流程；架构基线（AD+ADR）纳管（§13.4.4）。
16. 契约链：链上每一对相邻环节都是一组局部"甲方-乙方"；基线是每一级契约的"冻结端"、版本是"交付端"——这是每一级都重复出现的通用机制，不是某一级专属（§13.4.5）。
17. 两个易混场景一把判据：场景一"从需求里选子集做开发输入"=需求配置，冻结即功能基线；场景二"同一设计号多个实体选一个做部件"——选 A 选 B 特性/形态变了吗？变了=配置（实例级按序列号管），没变=只是分配（类型级按型号管）（§13.4.6）。
18. 三条铁律：产品开发是协作，协作需要共同事实（配置基线）；是长周期，长周期需要组织记忆（配置信息是组织唯一带不走的资产）；要担责，担责需要可答的账（精确召回 vs 全量召回差一个数量级的钱）。配置管理可剪裁——复杂度与产品责任等级匹配，但"版本可指认、变更可追溯"这条底线谁也不能省（§13.4.7）。
19. 四个维度：质量（做对/测准/修快）、效率（少返工/少扯皮/快交付）、合规（可追溯/可追责/过审计）、信任（客户能复现、能修复、敢用）（§13.4.8）。
20. 经济价值：省钱（返工约 1:10:100:1000 / 报废 / 精确召回）、赚钱（多变体多收入 / 资质=订单 / 交付速度=赢单）、保钱（责任清晰 / 知识资产不流失）——配置管理管的是"这个产品现在是什么、过去怎么变成这样、将来还能变成什么样"（§13.4.9）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "配置 = 系统设置里那页参数 / 个性化设置。"
2. "版本管理做好了 = 配置管理做好了。"
3. "有版本号 = 有基线。"
4. "基线一旦建立就永远不能改。"
5. "没有基线，变化也说得清——反正有 git 历史。"
6. "配置管理是文档的事，跟代码、硬件没关系。"
7. "小团队、小产品，配置管理是大公司的负担。"
8. "变更控制就是多开会，拖慢交付。"
9. "配置管理管的是'现在是什么'，跟历史没关系。"
10. "变体就是版本，改个名字而已。"
11. "改一个参数就要改代码、重编译、重发布——这是正常的，参数本来就长在代码里。"
12. "配置项、配置、配置信息是同一件事的三个叫法，换个角度而已。"
13. "基线和版本各有归属——需求阶段的功能基线归需求方，实现阶段的产品版本归开发方。"
14. "版本号就是文件名。"
15. "版本号越大越好。"
16. "配置就是客户能改的那几个开关。"
17. "同一设计号的板卡，装这块还是那块无所谓——反正都一样。"（场景二陷阱：类型级 vs 实例级）
18. "AD 评审通过就定格了，不用进配置管理。"（架构基线纳管缺失——不受变更控制的 AD 是草图堆）

### 四问萃取（溯源 · 致用，含薄格标注）

> v2.1 第 1 步第六样：每个核心概念从概念卡四问化过一遍四问——是什么 / 不是什么 / **从哪来（②背景·③演化，溯源）** / **往哪去（④拟解决问题·⑤适应场景/失效边界，致用）**。溯源与致用是显式萃取目标（§1.7.2"能答全四问才算拥有"）；薄格标注"可省"，不得默认跳过（§1.7.5"跳过的格往往是误解潜伏的地方"）。四问有书内依据的为非薄格，正文着墨薄的标薄格。

| 核心概念 | 它是什么 | 它不是什么 | 从哪来（溯源） | 往哪去（致用） | 薄格 |
|---|---|---|---|---|---|
| **配置**【根】 | 实体被记录在配置信息里、相互关联的功能特性+物理特性——"被记录下来的样子"（ISO 10007）；判据=配置三问 | 不是参数文件（参数是零件，配置是装好的整机）；不是配置项（对象）/配置信息（记录）；不是实体的全部客观特性（三过滤器切出子集） | 硬件工业"组件选配"→软件"参数文件"→数据"元数据治理"的漂移（§1.7.4）；ISO 10007 钉回；英文 con-+figurare=共同塑成的形态、中文"配+置"=搭配并安置成形，两语同源（§13.2.1） | 回答"这台产品被记录下来的该有的样子"——没被记录就无从核对、无从追溯；在标识配置项、核对实物与文档、追溯"当时那台设备是什么样"时用；失效边界=被当参数文件/个性化设置/客户能改的那几个开关时 | 均非薄格 |

### 本章判据（十三把尺子）

1. **配置三问**：它是功能/物理特性吗（类别边界）？它被记录了吗（记录边界）？它和其他特性关联成整体了吗（关联边界）？三问全"是"，才是配置。参数文件只是记录形态的图纸，形态才是配置。**违反即崩：把"那页设置"当成配置——客户改个参数就以为配置变了，可没被记录的形态，追溯时无据可查。**
2. **变与不变的分离**：核心资产只写一遍，变化的部分外置——"改一个参数就要改代码、重编译、重发布"是变与不变没分离的信号。**违反即崩：客户一改"上报间隔"就得改代码、重编译、重发布——可变的部分焊死在不变的核心里，改一次发一次。**
3. **配置项/配置/配置信息三分离**：配置项是"被管的那个东西"，配置是"它被记录下来的该有的样子"，配置信息是"记录它的那些资料"——都锚定在"实体"上。**违反即崩：把"被管起来的实体"当"被记录的形态"——审计问配置是什么，答成"就是我们管的那些板卡和文档"，对象和形态对不上账。**
4. **版本是刻度**：版本回答"走到第几步"；一个版本号必须能精确对应到"哪一次完整构建"（文件名不算）。**违反即崩：文件名加个 final_2 就当版本——玉杰回滚时，分不清哪个包对应哪次构建。**
5. **基线三特征**：被批准（有权威的盖章）+ 被冻结（任何人不能随意改）+ 作参照（全生命周期拿它对照）——三问全"是"才是基线。**违反即崩：版本号到 v2.3 就当基线——没被批准、没被冻结，疾控审计时找不到可参照的冻结点。**
6. **版本顺着流、基线垂直切**：版本沿时间轴排开（流动），基线垂直插入切断时间（受控）；把版本当基线，等于把里程桩当收费站。**违反即崩：只有里程桩没有收费站——版本一直在流，却没有一版被批准冻结，改了什么查无实据。**
7. **没有基线，变化就不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。**违反即崩：审计问"这批记录是哪一版固件采的"——版本链连续流动，却找不到"从什么变起"的原点。**
8. **变更控制循环**：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线——基线建立后，任何变化必须走这条线。**违反即崩："先推 v2.3 再说"——没有 CR、没有影响评估，改采集算法动了断链判定，批次追溯全错。**
9. **配置管理四大活动**：配置标识（是什么）→ 配置控制（怎么变）→ 状态记录（现在什么样）→ 配置审计（实物与记录一致吗）——一个都不能少。**违反即崩：只做版本号（标识的一半），缺状态记录和配置审计——"已推送 v2.3"一句笼统的话，哪台设备在哪一版说不清。**
10. **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。**违反即崩：只能答"应该是什么"，答不出"实际是什么"和"怎么变成这样"——疾控一问"这批记录是哪版固件采的"，当场卡壳。**
11. **配置管理守护架构决策**：决策记录↔配置信息、不可逆决策识别↔基线冻结、推迟决策↔变与不变的分离、变更影响分析↔变更控制——第12章的尺子，第13章给它们配了流程；架构基线（AD+ADR）纳管，不受变更控制的 AD 是草图堆。**违反即崩：决策做对了没有基线冻结、做错了没有变更控制早止损——万辉改编号"今天就能上"，三个月连环三爆。**
12. **契约链**：需求对方案、方案对实现，每一对相邻环节都是局部甲乙方——基线是每一级契约的冻结端，版本是交付端。**违反即崩：基线版本各归一方——需求方只管冻结、开发方只管交付，验收时对不上"哪版需求对应哪版交付"。**
13. **配置 × 版本 × 基线三分工**：变体管空间（有几种形态）、版本管时间（走到第几步）、基线管资格（哪一版被盖章）——配置提供"内容"，版本提供"位置"，批准提供"资格"；三者齐备，才成一个基线。**违反即崩：只有配置和版本、没有批准——变体形态一直在变，没有一版被盖章定格，主循环转不起来。**

2. 能解释为什么配置是"被管理起来的那部分特性"（三个隐形过滤器：类别/记录/关联边界）。
3. 能解释为什么"configuration"的本质是"组合成形"（con-+figurare / 配+置），为什么它天然是"多体"概念。

5. 能解释为什么基线必须"被批准"（流动→受控需要一个有权威的动作）、"被冻结"（随意改基线=拆参照系）、"作参照"（全生命周期拿它对照）。

11. 能解释为什么四大活动一个都不能少（用冰链固件事故四个洞：标识没立基线/控制没影响评估/记录只有一句/审计从没做）。

### 判据层（应会用）

1. **配置三问**：记录了吗（记录边界）/ 功能物理特性吗（类别边界）/ 关联成整体了吗（关联边界）——三问全"是"才是配置。
2. **版本判据一问**：这一个编号能精确对应到"哪一次完整构建"吗？能——是版本；不能（如只有文件名）——还不算版本。
3. **基线三问**：被批准了吗？被冻结了吗（任何人不能随意改）？全生命周期拿它作参照吗？——三问全"是"才是基线。
4. **一横一竖判据**：它顺着流（版本）还是竖着切（基线）？问一句"这一版有没有被批准、被冻结、拿它作参照"。
5. **变体/版本/基线判断口诀**：问"有几种形态"→变体；问"改到第几版"→版本；问"这个版本的这个形态"→基线。
6. **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
7. **变更控制五步**：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线——哪一步跳过了、代价是什么。
8. **四大活动**：标识（是什么）/ 控制（怎么变）/ 记录（现在什么样）/ 审计（实物与记录一致吗）——逐活动打勾"有/缺/半吊子"。
9. **变与不变的分离判据**："改一个参数就要改代码、重编译、重发布" = 没分离的信号。
10. **契约链判据**：每一级契约都有冻结端（基线）和交付端（版本）；开发链内部是技术契约，完整外部甲乙方多一层商务契约。
11. **场景二判据**：选 A 选 B，产品的特性/形态变了吗？变了——它们本就是不同配置；没变——只是分配问题。

### 纠错红线十条

1. **先表态后翻案**：先让学员说"版本号不是有吗？配置管理不就做好了吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："基线不能改"别翻成"基线可以随便改"——要分清"冻结"与"死锁"（改必须走变更控制、改完建新基线）；"配置≠参数文件"别翻成"参数不重要"；"没有基线变化不可言说"别翻成"版本没用"；"类型级不是配置"别翻成"板卡批次不重要"（分配和序列号追溯仍要做）。
3. **判据配机制**：每条反转都有"为什么"（机制）和"怎么当场验证"（判据）——如基线三问的"为什么"是"从流动升格受控需要一个权威动作"。
4. **归责到可对照动作**："你没在做配置管理"落到"四大活动缺哪几个 / 基线三问哪一问答不上 / 版本号能不能对应完整构建"，不归咎"人不上心"。
5. **教机制不教断言**：教"为什么没有基线变化就不可言说"（描述变化需要"从哪变起"的原点、没有岸标），不教"要有基线"。
6. **先立尺子再翻案**：先给基线三问/版本判据/配置三问，再翻水忠"我们有版本号啊"、玉杰"我有日期文件夹"。
7. **拉开强度层次**：★★★ 常识（配置=参数 / 版本管理=配置管理 / 有版本号=有基线 / git 历史=基线）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（如给最大配置项过一遍基线三问、四活动打勾）。
9. **单一权威不另立标准**：判据引用书（本章判据 13 条 + ISO 10007 / ISO/IEC/IEEE 24765 / ISO/IEC/IEEE 15288 / SemVer），不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"佐证，药与判据全在书内；有超出书处须标注由作者裁决。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给团队最大的配置项做一次"配置管理体检"

> 目标：用本章的配置三问、版本判据、基线三问、四大活动、配置管理三问，对团队最大的一个配置项做一次完整配置管理体检，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑配置项（先立枢纽）**：选一个"你心里最有底、天天在用"的配置项——产品的主程序 / 固件 / 核心服务 / 数据表定义。最自信的，往往是基线三问最没打勾的。
2. **过配置三问（这算不算配置）**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——确认它是配置，不是零散参数。**话术**："你说的'配置'，是那页参数，还是那整套关联成形的形态？"
3. **查版本判据（有版本吗）**：当前的版本号能精确对应到"哪一次完整构建"吗（哪个代码提交、哪次构建、包含哪几条变更）？答不出——它连版本都不算，更遑论基线。
4. **过基线三问（有基线吗）**：有没有一版被批准（谁批的、有没有记录）？被冻结（改它不能随手改、必须走变更控制）？全生命周期拿它作参照？——三问缺一，只是刻度不是基线。
5. **四活动打勾（标识/控制/记录/审计）**：配置标识——它在配置项清单里吗、有基线定义吗？配置控制——最近一次变更走 CR → 影响评估 → CCB 批准 → 实施 → 新基线了吗？状态记录——现在跑的是哪一版、升级历史有台账吗？配置审计——线上/实物 vs 记录对得上吗、抽查过吗？
6. **答配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——三问任一答不出，就是最该补的活动。
7. **出体检报告**：四活动各下结论（有 / 缺 / 半吊子），**最该先补的是"答不出三问"对应的那个活动**；最后一条建议照书抄——先给最大的配置项补一版"被批准、被冻结、作参照"的基线，把"这一版"从刻度升级成参照。

**卡住怎么判断**：答不上来的那一问就是最该补的；基线三问一问答不出 = 只是版本不是基线；"没有记录"的地方就是配置审计失守可能潜伏的地方。不用四活动全查完，找到第一个答不出的项目就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 配置三问：被记录了吗 / 功能物理特性吗 / 关联成整体了吗 | □ | 答不出 = 它只是参数，不是配置 |
| 版本判据：版本号能精确对应哪一次完整构建吗 | □ | 只有文件名/日期文件夹 = 还不算版本 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"疾控审计员问水忠：这批疫苗四月运输、全程温度记录正常——你们要证明，这批记录是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？水忠说：这简单，查版本号，v2.1、v2.2、v2.3 都标着呢。可结果查不清。为什么'版本号是有了'，'这批记录是哪一版采的'还是答不上来？这一章要钉的三个词——配置、版本、基线——各管什么？各自从哪来、往哪去？"
追问：① 配置提供"内容"、版本提供"位置"、批准提供"资格"——三者为什么谁也不能替谁？② 水忠的 v2.3 是版本还是基线？基线三问一答就穿帮，穿在哪一问？③ 配置这个词从哪来（硬件工业组件选配 + con-/figurare 组合成形）？为什么说配置是"这一切的地基"？④ 反身：你们产品里"被批准、被冻结、全生命周期拿它对照"的那一版，能一指就指出来吗？

**Q2（见树见林② · 概念关系）**
"请给出 配置、配置项、配置信息 三词的关系；再给出 版本、修订、变体、基线 四词的关系——说明为什么'版本顺着流、基线垂直切'，为什么变体与版本正交，为什么基线是变体 × 版本的交叉点被盖章？"
追问：① 三个配置术语互相引用、首尾相连，为什么锚定'实体'后就不循环了？② 一份文档为什么既是'配置信息'又是'配置项'——两个层面怎么不冲突？③ 契约链：需求对方案、方案对实现，为什么说基线是每一级契约的'冻结端'、版本是'交付端'？它在第6章的结对处怎么长（候选声明 + 骨架先行）？④ 反身：你平时说的'版本'，到底指的是四词里的哪一个？

**Q3（真悖论 · 参数文件是配置吗）**
"李旭指着 App 设置页说：这就是咱们的配置，客户能改的都在这页——温度上报间隔、超温告警阈值、断电告警开关、蜂鸣器音量。文正却说：配置不是这个参数，是那整套关联在一起塑成的'M3 的行为形态'。参数文件到底是不是配置？什么判据分清'配置'和'配置信息里的一个条目'？"
追问：① 变与不变的分离——为什么客户改上报间隔不用动固件、不用重编译（可变部分被外置），反过来改一个参数就要改代码、重编译、重发布是什么信号？② 三个隐形过滤器（类别/记录/关联边界）怎么从'实体的全部特性'切出'配置'子集？③ 配置这个术语为什么会被当成参数文件（硬件'组件选配'→软件'参数文件'→数据'元数据治理'的漂移，ISO 10007 把它钉回）？④ 反身：你们产品里'客户能改的那几个开关'，到底是配置，还是配置信息里的条目？

**Q4（真悖论 · 版本有了就有基线吗）**
"水忠觉得冤：我们有 v2.1、v2.2、v2.3，版本号都标着呢，升级也走流程了、李旭也验证过了，怎么就不算配置管理了？这一章说：版本只是刻度，基线才是参照；版本顺着流、基线垂直切。既然版本和基线都跟时间有关，为什么说它们方向完全不同？什么判据一眼分清'它是版本还是基线'？"
追问：① 里程桩 vs 收费站——为什么版本'顺着路'、基线'挡住路'？版本为什么诞生（变化连续、沟通必须离散——报障时说不出口'改过17次的固件'）？② 基线三问（被批准/被冻结/作参照）一问答不出会怎样？基线这个词从哪来（军品工程'版本失控、改坏了找不回来'的教训→受控快照→ISO 10007 凝结）？③ 变体与版本为什么正交（有几种形态 vs 走到第几步）？④ 第12章说不可逆决策要提前投资——这一章给'投资之后'配了什么守护（基线冻结 / 变更控制）？

**Q5（原理 · 没有基线变化就不可言说）**
"『从基线出发，一切变更都可描述；离开基线，一切变化都不可言说。』这句话凭什么成立？为什么'有 git 历史'替代不了基线？"
追问：① 描述一个变化必须有一个'从哪变起'的原点——没有原点像什么（在茫茫大海上说'我在动'，却没有岸标）？② git 历史是记录，基线是批准+冻结+作参照——两者差在哪一个动作（批准）？③ 基线建立之后，变化怎么走（变更控制五步在守什么）？配置管理的全部工作为什么是让'三问'任何时刻都有答案？
