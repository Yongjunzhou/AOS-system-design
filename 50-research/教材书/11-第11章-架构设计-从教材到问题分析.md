## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：架构设计到底是什么？为什么画图、选型、定规矩三样加在一起仍然不算架构设计？架构设计的工作清单（五块设计）各是什么、每一块各自是怎么被"设计"出来的？

### 核心概念

1. **架构设计**（architecture design）：把需求翻译成系统结构的活动——决定系统怎么切分、怎么连接、守什么规矩；产品开发中最不可逆、返工代价最高的一组决策。判据：三问（它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计）。
2. **基本概念**（fundamental concepts）：系统在其环境中"怎么想"的根源——组织范式 / 核心抽象 / 根本机制 / 根隐喻；90% 从概念库选 + 10% 被需求/质量属性逼出，候选→检验→幸存，命名是概念化的完成仪式。判据：自查四问（组织范式还是核心抽象？走哪条生成路径？过检验了吗？有名字吗？）。
3. **基本属性**（fundamental properties）：系统"具备什么"的本质特征——可观察、可度量的表现；涌现属性，不能直接设计，只能设计结构让涌现。判据：自查四问（目标属性场景化了吗 QAS？选了哪个战术？战术落在哪个结构位置？度量过、涌现达标了吗？）。
4. **设计准则**（principles of design）：架构师自愿的自我限制——约束被迫、决策自选、原则自加；句式 = 必须/禁止/应当 + 理由。判据：可判定 / 有理由 / 少而精（5~15 条）/ 可入评审。
5. **演进准则**（principles of evolution）：设计准则 × 时间轴——怎么变而不破坏对（防漂移 / 侵蚀 / 技术债）；与配置管理（第13章）是同一套制度的两层皮（管"形" vs 管"物"）。判据：主语全是"变"的是演进准则。
6. **元素关系**（relationships）：关系是成本——n 个要素全互联是 n² 条关系，每条都是未来变更时的一处牵动；设计第一原则是"克制"、核心动作是降耦合。判据：五判据（有方向 / 够稀疏 / 尽量弱 / 要显式 / 不穿越）。
7. **架构设计的输入**（输入五类 + 规定需求 + 关注点识别）：不是"全部需求原文"，而是功能 / 非功能 / 约束 / 环境 / 关注点 / 资产六类，且要吃规定需求（系统级：已验证、可追溯、未分配）；其中非功能需求（质量属性）才是主要驱动，关注点是识别出来的不是设计出来的。

### 关联概念（近界 · 辨析）

- **五块设计 ↔ 42010 定义的拆解**：第10章用同一条定义回答"架构是什么"（concepts/properties/elements/relationships/principles）；这一章回答"架构怎么被设计出来"——第10章"概念或属性"or 两条路（认知切入点）vs 本章五块一块都不能少（完整工作清单）。
- **非功能需求 ↔ 质量属性**（Bass / Clements / Kazman）：功能需求是骨架、质量属性是体重——骨架决定长相、体重决定能不能站起来；"质量属性才是架构的主要驱动"。
- **关注点 ↔ 相关方**：stakeholder × concern 矩阵——空格 = 有相关方没任何视图回答；冲突格 = 权衡点 = 架构决策的主战场。
- **演进准则 ↔ 配置管理（第13章）**：配置管理管"物"（configuration item 怎么受控），演进准则管"形"（架构怎么在受控下变形）；基线是演进的地板、版本是演进的足迹。
- **命名 = 完成仪式 ↔ 第1章"概念是共同体酿出来的"**：一旦结构被命名，就从想法变成可共享、可讨论、可传承的概念。
- **概念幸存 ↔ 第10章"不可还原" / 第12章"不可逆"**：基本概念=对"不变性"的承诺——它"基本"正因为它是全部决策里最难改的那一层；五块设计是把最难撤销的决策尽量想清楚、定形。
- **内部输入链 ↔ ADR**：ADR 是这条输入链的书面凭证（第12章决策记录六问展开）；反向校验答不出的就是"无源之水"。
- **三样东西（图/选型/老规矩）↔ 前章概念**：图=第10章架构描述；老规矩=第10章立、第11章承接、第16章长成（贯穿物件回声登记）。
- **架构设计 ↔ 概要定义（第6章）**：第6章那棵树的树干树枝管"结构是什么、承接了谁"；架构是那棵树上不可还原的部分——架构设计正是要做出那组"不可还原的决定"。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 翻译必然做选择——同一份需求可以翻译成不同的结构；翻译的每一个选择都是架构决策的种子（§10.2.1）。
2. 设计是"转化"（transform）——输入是已定义好的需求，输出是解决方案的特性描述；设计不负责说"系统是什么"，负责说"系统怎么兑现承诺"（§10.2.2）。
3. 定义 = 划界 + 陈述（de-finis，求真：准确/无歧义/可验证）；设计 = 怎么做（how，求优：满足需求/权衡取舍/可实现）——设计本质上也是"定义"的一种，只是对象换成了解决方案（§10.2.3）。
4. 过程以产出物命名——15288 只有"架构定义过程""设计定义过程"，没有"架构设计过程"；构思无法评审，描述才能评审、验证、基线化（§10.2.3）。
5. 设计是动词（构思），定义是完成时（定形）——设计得再好，没定形就等于没设计（§10.2.3）。
6. 五块一块都不能少——一旦要做架构设计，五块（概念/属性/设计准则/演进准则/关系）一块都不能少（§10.2.4）。
7. 横切决定错了，纵挖挖得再深也是白挖——先横后纵（§10.2.5）。
8. 架构设计是概要定义背后那一层——比概要定义更深、更不可逆（§10.2.5）。

**第二幕 · 磨边弧的机制（不是什么）**
9. 三样东西——图（架构描述/产物）、选型（候选）、老规矩（设计准则/五块之一）——没有一样是"把需求翻译成系统结构"这个动作（§10.3.1）。
10. 非功能需求（质量属性）才是架构的主要驱动——功能需求告诉你"做什么"，质量属性告诉你"做到什么程度"，而"做到什么程度"才真正决定结构形态（§10.3.2）。
11. 功能需求是骨架，质量属性是体重——骨架决定长相，体重决定能不能站起来（§10.3.2）。
12. 架构设计吃规定需求——在流沙上画结构图，等于开局自损一目：需求一变结构就得跟着动，而结构一动代价是指数级的（§10.3.3）。
13. 需求分配是架构设计自己的工作，不是输入；"下一层吃的，是上一层产出的"——设计链是接力关系，不是并行关系（§10.3.3）。
14. 质量属性是涌现属性（emergent property）——"可用性 99.99%"是整系统的属性，不能切碎分给某个部件，只能被架构机制满足、再翻译成部件级的设计约束；"质量属性不能分，只能译"（§10.3.4）。
15. 关注点是识别出来的，不是设计出来的——concern 是 stakeholder 的 interest，已存在于其头脑、组织和契约里；42010 从头到尾用的是 identify 不是 design（§10.3.5）。
16. 漏掉一个 stakeholder，就是漏掉一整类 concern（§10.3.5）。
17. 基本概念是"选出来 + 逼出来 + 幸存下来"的——90% 从已验证的概念库中选择，10% 被需求和质量属性逼着生成；生成出来的只是"候选"，要经过检验活下来才配叫"基本"（§10.3.6）。
18. 基本概念 = 对"不变性"的承诺——它之所以"基本"，正因为它是全部决策里最难改的那一层（呼应第10章"不可还原"、第12章"不可逆"）（§10.3.6）。
19. 命名就是概念化的完成仪式——一旦结构被命名，它就从想法变成了可共享、可讨论、可传承的概念（§10.3.6）。
20. 基本属性不是"设计"出来的，是"涌现"出来的——你设计的是结构，属性是结构运转之后的宏观效果（§10.3.7）。
21. 不能直接设计"强度"，只能设计微观晶格让强度涌现；不能直接设计"可用性"，只能设计冗余机制让可用性涌现（§10.3.7）。
22. 属性四步流水线：QAS 场景化 → 战术选择 → 结构落位 → 验证度量；没度量过的属性承诺等于没有（§10.3.7）。
23. 基本属性 = 生命线属性——系统可以平庸但不能没有的那些；关键性分析（criticality analysis）决定权衡时的优先级与资源投向（§10.3.7）。
24. 原则是"决策的决策"（meta-decision）——不是替你做决策，是让你不用重新想（§10.3.8）。
25. 原则是自愿的自我限制；标准句式 = 必须/禁止/应当 + 规则 + 理由（rationale）；没有理由的原则是教条，有理由的原则是纪律（§10.3.8）。
26. 原则四判据：可判定 / 有理由 / 少而精（5~15 条）/ 可入评审；"用原则代替思考"是原则最大的诱惑——原则负责"不需要重新想的事"，权衡负责"必须重新想的事"（§10.3.8）。
27. 演进准则 = 设计准则的"时间维"延伸——架构在无人管束时必然退化（架构漂移 / 架构侵蚀 / 技术债）；演进准则就是给"变"上的制度保险（§10.3.9）。
28. 判别设计准则与演进准则最快方法：这条规矩是关于"怎么建"的，还是关于"怎么改"的——主语全是"变"的是演进准则（§10.3.9）。
29. 关系是成本——n 个要素全互联是 n² 条关系，每一条都是未来变更时的一处牵动；关系稀疏，独立性才强，可演进性才高（§10.3.10）。
30. 关系设计的核心动作是降耦合——强关系降级为弱关系（同步调用 → 异步消息 / 直接调用 → 事件发布订阅 / 共享状态 → 消息传递）；每降一级，变更的牵动范围就小一圈（§10.3.10）。
31. 概念定"有哪些骨架"，属性定"骨架要有什么性质"，关系定"骨架怎么连起来才具备这些性质"——关系是概念的具身化、属性的实现通道（§10.3.10）。

**第三幕 · 往哪去的机制（运用）**
32. 只有"基本概念"直接面对外部原始输入，越往后的块，输入里"内部成分"占比越高——五块输入分外部原始输入 + 内部派生输入两个来源（§10.4.1）。
33. 只有概念是"翻译"，其余是"翻译的翻译"——概念直接接触需求原文、约束、市场；属性、原则、关系吃的是提炼物；概念设计错了，后面四块全部跟着错，而且错得越来越远（§10.4.2）。
34. 内部链是一条"失信放大器"——每一层的输出质量 = 上一层输入质量 × 本层加工质量；评审时发现原则跟概念对不上，基本可以断定链断过（§10.4.2）。
35. 反向校验是免费的架构体检——从后往前核查（这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念/教训提炼？），答不出来的就是架构里的"无源之水"；ADR 是这条输入链的书面凭证（§10.4.2）。
36. 从"见过"到"拥有"——图、选型、规矩是架构设计的"见过"；五块一块一块做出来、定了形，才是"拥有"（章末·认知反转）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "架构设计 = 画架构图 + 做技术选型 + 定老规矩。"
2. "我们做了架构设计 = 我们有架构描述。"
3. "架构设计就是选技术栈。"
4. "功能需求决定架构形态。"
5. "架构设计的输入 = 全部需求原文。"
6. "关注点是可以'设计'出来的。"
7. "基本概念是架构师发明出来的。"
8. "直接设计可用性，把 99.99% 分配给每个模块。"
9. "原则越多越严谨，把能想到的规矩都写上。"
10. "设计准则定了就够了，演进准则是运维的事。"
11. "关系越多系统越强，大家尽量互联互通。"
12. "五块设计是五份并列的需求文档。"

### 本章判据（十一把尺子）

1. **架构设计 = 翻译**：把需求翻译成系统结构（切分、连接、规矩）；画图、选型、定规矩都只是这个翻译的产物/素材/规则，不是翻译本身。
2. **设计是动词，定义是完成时**：定义 = 划界 + 陈述（de-finis）；过程以产出物命名——构思无法评审，描述才能评审、验证、基线化。没定形，就等于没设计。
3. **横切先于纵挖**：架构设计横向切（切成几块、怎么对接），详细设计纵向挖（每块内部挖多深）——先横后纵。
4. **非功能需求才是主要驱动**：功能需求告诉"做什么"，质量属性告诉"做到什么程度"，而"做到什么程度"才真正决定结构形态。
5. **输入必须是规定需求**：架构设计吃系统需求（已验证、可追溯、未分配），在流沙上画图等于自损一目；需求分配是架构设计自己的工作，不是输入。
6. **质量属性不能分，只能译**：涌现属性是整个系统的属性，只能被架构机制满足、再翻译成部件级约束。
7. **关注点是识别出来的，不是设计出来的**：识别五步（相关方 → 提取 → 划界 → 编排 → 验证）；好 concern 五判据（有主 / 有界 / 可权衡 / 可追溯 / 完备 = 矩阵无空行空列）。
8. **概念幸存、属性涌现**：基本概念 90% 选 + 10% 逼，候选→检验→幸存，命名是概念化的完成仪式；基本属性不能直接设计，只能设计结构让属性涌现，且必须度量验证。
9. **原则是自愿的自我限制**：约束被迫、决策自选、原则自加；句式 = 必须/禁止/应当 + 理由；可判定 / 有理由 / 少而精 / 可入评审；演进准则 = 设计准则 × 时间轴。
10. **关系是成本**：关系稀疏才可演进；依赖无环、往弱推、契约化；五判据（有方向 / 够稀疏 / 尽量弱 / 要显式 / 不穿越）。
11. **只有概念直面世界**：五块输入是外部原始输入 + 内部级联；概念错了后面全错——反向校验（这条关系服务哪个属性？这个属性被哪个概念限幅？）答不出的就是无源之水。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"架构设计"（把需求翻译成系统结构的活动——决定切分 / 连接 / 规矩），并说出三问判据。
2. 能辨析 架构设计 vs 画架构图（产物/描述）vs 技术选型（候选）vs 定老规矩（规则/五块之一）。
3. 能辨析 定义 vs 设计（划界 + 陈述·求真 vs 怎么做·求优；完成时 vs 动词）。
4. 能辨析 架构设计 vs 详细设计（横向切 vs 纵向挖；先横后纵）+ 架构设计 vs 概要定义（更深、更不可逆）。
5. 能说出五块设计清单（基本概念 / 基本属性 / 设计准则 / 演进准则 / 元素关系）+ 各自 42010 出处 + "系统怎么……"一句话（怎么想 / 具备什么 / 怎么设计对 / 怎么变不破坏对 / 怎么连）。
6. 能定义"基本概念"（四副面孔：组织范式 / 核心抽象 / 根本机制 / 根隐喻）+ 五条生成路径 + 幸存者逻辑 + 命名 = 完成仪式。
7. 能定义"基本属性"（涌现属性）+ 四步流水线（QAS 场景化 → 战术选择 → 结构落位 → 验证度量）+ 生命线属性 / 关键性分析。
8. 能辨析 约束 / 决策 / 原则（外部强加·接受 / 架构师选择 / 自愿自加）+ 设计准则句式 + 四判据。
9. 能定义"演进准则"（设计准则 × 时间轴）+ 八类（兼容 / 可替换 / 渐进 / 可逆 / 受控 / 审查关口 / 留痕 / 技术债）+ 与配置管理的关系（管形 vs 管物）。
10. 能定义"元素关系"（关系是成本）+ 五类型（结构 / 行为 / 接口 / 部署 / 时序）+ 强度光谱（强 / 中 / 弱）+ 五判据。
11. 能说出架构设计输入五类（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产）+ 为什么非功能需求排第一位。
12. 能说出为什么输入必须是规定需求（吃系统需求：已验证 / 可追溯 / 未分配）。
13. 能说出关注点识别五步 + 好 concern 五判据（有主 / 有界 / 可权衡 / 可追溯 / 完备）。

### 原理层（应能解释为什么）

1. 能解释为什么翻译必然做选择（同一需求 → 不同结构；每个选择都是架构决策的种子）。
2. 能解释为什么设计是"转化"（输入 = 已定义需求，输出 = 解决方案特性描述；设计不负责说"系统是什么"）。
3. 能解释为什么过程以产出物命名（构思无法评审，描述才能评审、验证、基线化）。
4. 能解释为什么设计得再好没定形等于没设计（设计是动词，定义是完成时）。
5. 能解释为什么非功能需求才是主要驱动（功能决定长相，质量属性决定能不能站起来）。
6. 能解释为什么在流沙上画图自损一目（架构设计是设计链最不可逆的一环，结构一动代价指数级）。
7. 能解释为什么需求分配是架构设计自己的工作不是输入（设计链是接力关系，不是并行关系）。
8. 能解释为什么质量属性不能分只能译（涌现属性是整系统属性，没有哪个模块"负责可用性"）。
9. 能解释为什么关注点是识别出来的不是设计出来的（concern 已存在于相关方头脑 / 组织 / 契约里）。
10. 能解释为什么基本概念是幸存下来的（90% 选 + 10% 逼；候选→检验→幸存）。
11. 能解释为什么命名是概念化的完成仪式（从想法变成可共享、可讨论、可传承的概念）。
12. 能解释为什么基本属性只能设计结构让涌现（材料科学类比：不能设计强度只能设计晶格）。
13. 能解释为什么没度量过的属性承诺等于没有（验证度量是四步最后一步，是 verification 的主场）。
14. 能解释为什么原则是"决策的决策"（让你不用重新想；原则负责不需重新想的事、权衡负责必须重新想的事）。
15. 能解释为什么演进准则必要（架构熵增：漂移 / 侵蚀 / 技术债；制度保险——系统不是不变，而是变的方式受约束）。
16. 能解释为什么关系是成本（n²；关系稀疏才可演进）。
17. 能解释为什么只有基本概念直面世界（内部输入链：外部原始输入 → 概念 → 属性 → 准则 → 演进）。
18. 能解释为什么概念错了后面全错且越错越远（翻译的翻译 + 失信放大器）。
19. 能解释为什么反向校验是免费架构体检（答不出的就是无源之水；ADR 是书面凭证）。

### 判据层（应会用）

1. **架构设计三问判据**：它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计。
2. **定义 vs 设计判据**：没定形的构思等于没设计（能评审 / 验证 / 基线化才算定形）。
3. **横切先于纵挖判据**：横切决定错了，纵挖挖得再深也是白挖。
4. **非功能主导判据**：做到什么程度（质量属性）决定结构形态——99.99% 和 99% 是两个架构。
5. **规定需求判据**：已验证 / 可追溯 / 未分配（系统级）；"下一层吃的，是上一层产出的"。
6. **质量属性只能译判据**：QAS 场景化 → 翻译成部件级设计约束（"本模块必须无状态，状态存外部存储"）。
7. **关注点识别判据**：五步识别 + 好 concern 五判据（有主 / 有界 / 可权衡 / 可追溯 / 完备 = 矩阵无空行空列）。
8. **概念幸存自查四问**：它是组织范式还是核心抽象？走哪条生成路径来的？过了检验吗？它有名字吗？
9. **属性涌现自查四问**：目标属性场景化了吗（QAS）？选了哪个战术？战术落在哪个结构位置？度量过、涌现达标了吗？
10. **原则四判据**：可判定（能对一个具体决策判定"它违反了吗"）/ 有理由 / 少而精（5~15 条）/ 可入评审。
11. **演进准则判别**：这条规矩是关于"怎么建"的还是"怎么改"的——主语全是"变"的是演进准则。
12. **关系五判据**：有方向（依赖无环 DAG）/ 够稀疏（关系少而必要）/ 尽量弱（能异步不同步）/ 要显式（依赖抽象不依赖实现）/ 不穿越（迪米特法则）。
13. **反向校验判据**：这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念 / 教训提炼？答不出 = 无源之水。

### 纠错红线十条

1. **先表态后翻案**：先让学员说出"这三样凑齐不就是架构设计吗 / 这还用讨论吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："概念是幸存下来的"别翻成"概念不用设计"——设计负责把候选摆上桌、定检验；"关系是成本"别翻成"关系越少越好"——是满足需求前提下的克制。
3. **判据配机制**：每条反转都有"为什么"（翻译必然做选择 / 涌现属性是整系统属性 / 原则是决策的决策）+ "怎么当场验证"（三问 / 四步 / 四关 / 五判据）。
4. **归责到可对照动作**："你没做架构设计"落到"你拿不出五块里能定形的任何一块"，不归咎"你不会画图 / 不懂技术"。
5. **教机制不教断言**：教"为什么质量属性只能译（涌现属性没有哪个模块负责可用性）"，不教"属性不能分"当口号。
6. **先立尺子再翻案**：先给三问 / 五块 / 四判据，再翻章首三样东西。
7. **拉开强度层次**：★★★ 常识（画图 = 架构设计 / 选型 = 架构设计 / 功能决定形态 / 原则越多越好）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一次五块设计体检"。
9. **单一权威不另立标准**：判据引用书（本章判据 11 条）+ ISO 42010 / 15288 / 9000，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给现有系统做一次"五块设计体检"

> 目标：用五块设计 + 反向校验，给自己正在设计 / 维护的系统（或最近一次架构变更）做一次架构体检，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑系统 / 挑变更（先立尺子）**：挑一个你正在设计或维护的系统，或最近一次架构变更（对应书练习 1 / 3）。
2. **分三样东西的层次（先看病）**：列出这次架构工作的"图 / 选型 / 规矩"各是什么——它们只是表达 / 候选 / 规则，不是架构设计本身。图是架构描述、选型是候选、规矩是设计准则（五块之一）。
3. **逐块答五块（五块设计）**：
   - **基本概念**：它"怎么想"——组织范式 / 核心抽象 / 根本机制 / 根隐喻是什么？"去掉就不是它"的是什么？答不出 = 概念缺口。
   - **基本属性**：它要涌现什么本质特征——生命线属性是什么？目标属性场景化（QAS）了吗（刺激 / 环境 / 响应 / 度量）？
   - **设计准则**：你自加哪些规矩——用"必须 / 禁止 / 应当 + 理由"句式写，过四关（可判定 / 有理由 / 少而精 / 可入评审）。
   - **演进准则**：每条设计准则做时间维化——"这条规矩在变更时怎么执行"？用"变"字句式（如"接口变更必须双版本并行期"）。
   - **元素关系**：关键模块依赖图——有环吗？几条不必要？强关系能往弱推吗（同步 → 异步 / 调用 → 事件）？
4. **反向校验（免费体检）**：随机挑一条设计准则向上追——它从哪个概念 / 属性提炼来的？答不出 = 无源之水（输入链断过）。
5. **产出三件最该做的事**：每条 = 一个可检查动作 + 一条判据（三问 / 四步 / 四关 / 五判据）。

**卡住怎么判断**：答不出的那一块就是设计缺口（书练习 1）；先钉基本概念——只有概念直面世界，概念错了后面全错（先问"它还是不是它"）。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 这次变更动的是五块里的哪一块？动基本概念了吗（系统本质变了）？ | □ | 动基本概念 = 换了系统——团队是否意识到 |
| 目标属性场景化了吗（QAS 四要素齐全）？ | □ | 没场景化 = 属性承诺无法验收 |
| 设计准则能过四关吗（可判定 / 有理由 / 少而精 / 可入评审）？ | □ | 过不了 = 那是教条，不是原则 |
| 设计准则做时间维化了吗（演进准则）？ | □ | 缺演进 = 架构会漂移 / 侵蚀 / 技术债 |
| 依赖图无环吗（DAG）？ | □ | 有环 = 循环依赖，架构腐蚀头号元凶 |
| 关系往弱推了吗？契约化了吗（显式契约）？ | □ | 强关系多 = 变更牵动整片 |
| 反向校验：每条准则 / 关系追得到概念 / 属性吗？ | □ | 追不到 = 无源之水（输入链断过） |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 章首破题）**
"水忠带三样东西进会议室——一张新的四层方块图、一页技术选型、一页老规矩，以为架构设计做完了。这三样东西各是什么（产物 / 候选 / 规则）？架构设计本身是什么？为什么三样加在一起，仍然不算架构设计？"
追问：① 三问判据（决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？）——水忠三样东西各自答得出哪一问？② "设计是动词，定义是完成时"——水忠拿不出什么？③ 架构设计与详细设计怎么分工（横向切 vs 纵向挖）？为什么先横后纵？④ 反身：你们最近一次"做架构设计"，带的是哪几样？过得了三问吗？

**Q2（见树见林② · 概念关系）**
"画出 基本概念、基本属性、设计准则、演进准则、元素关系 的关系图，标出：哪一块直接面对需求？为什么说只有基本概念直面世界，其余四块都是'翻译的翻译'？"
追问：① 内部输入链怎么串（外部原始输入 → 概念 → 属性 → 准则 → 演进；概念 + 属性 → 关系）？② 概念错了为什么后面全错、而且越错越远（失信放大器）？③ "外部原始输入"具体是什么（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产）？为什么概念吃的必须是规定需求？五块里哪一块是"识别出来的不是设计出来的"（关注点）？哪一块说"关系是成本"要克制？④ 反身：你们系统的五块是并列的五份文档，还是按输入链串起来的？

**Q3（真悖论 · 定义 vs 设计）**
""我们做过架构设计"和"我们有架构描述"，是同一件事吗？为什么标准里只有'架构定义过程'和'设计定义过程'，没有'架构设计过程'？"
追问：① 定义 = 划界 + 陈述（de-finis，求真），设计 = 怎么做（how，求优）——为什么过程以产出物命名？② 构思为什么无法评审、验证、基线化？③ 反身：你们团队的架构设计，有可以评审的定形产物吗，还是停在某个人的脑子里？

**Q4（真悖论 · 概念幸存 vs 属性涌现）**
"这一章说：基本概念不是设计出来的，是幸存下来的；基本属性不是设计出来的，是涌现出来的。那架构师设计的到底是什么？五块里到底有没有'设计'？"
追问：① 概念四副面孔（组织范式 / 核心抽象 / 根本机制 / 根隐喻）+ 五条生成路径（选 / 提 / 逼 / 借 / 推）；"候选→检验→幸存"——检验靠什么（原型 spike / ATAM / 架构评审）？② 命名 = 概念化的完成仪式——"边缘预警输入"这个名字意味着什么？③ 属性四步流水线（QAS 场景化 → 战术 → 结构落位 → 验证度量）——为什么不能直接画个"及时性"模块？"99.99% 可用"怎么逼出"冗余 + 故障域"（路径③ = 非功能需求才是主要驱动）？④ 反身：你最近一次"加概念"，是选出来的、逼出来的，还是拍板发明的？

**Q5（真悖论 · 原则自加 vs 约束被迫）**
""约束是外部强加的，原则是自愿的自我限制"——那架构师为什么要自己给自己上规矩？自加束缚怎么反而是解放（第10章'约束即解放'）？规矩越多越严谨，还是越少越好？"
追问：① 约束 / 决策 / 原则三词辨析（被迫接受 / 架构师选择 / 自愿自加）？② 原则四判据（可判定 / 有理由 / 少而精 5~15 条 / 可入评审）——"追求优雅"为什么不是原则？③ 演进准则 = 设计准则 × 时间轴——"主语全是变"怎么判别？④ 反身：你们团队的"老规矩"过得了四关吗？有理由吗？能入评审吗？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 输入与驱动）**
"水忠面对'要能提前告警'——功能上就是'算风险、发告警'六个字。为什么这六个字决定不了预判逻辑放硬件还是云端？什么才真正决定？架构设计的输入到底是什么？"
追问：① 输入五类（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产）各是什么？为什么非功能需求排第一位（"做到什么程度"才决定结构形态）？② 为什么输入必须是规定需求（已验证 / 可追溯 / 未分配）？③ 在流沙上画图 = 自损一目——需求一变结构跟着动，代价是指数级的。④ 反身：你们上次架构设计吃的输入，是"文正嘴里那句话"还是规定需求？

**Q7（判据运用 · 关注点识别）**
""架构设计的第一步不是画，是听——听那些'在乎'的人，到底在乎什么。"恒信万辉第一次做出 stakeholder × concern 矩阵，发现四格是空的。那四个空格告诉他什么？"
追问：① 关注点识别五步（相关方 → 提取 → 划界 → 编排 → 验证）？② 好 concern 五判据（有主 / 有界 / 可权衡 / 可追溯 / 完备 = 矩阵无空行空列）？③ 漏掉一个 stakeholder = 漏掉一整类 concern——万辉漏了谁（监管 / 运维 / 合同相对方 / 未来的维护者）？④ 反身：你们最近一次架构评审，从"谁在乎什么"出发了吗，还是从"我要画什么"出发？

**Q8（真悖论 · 关系强 vs 关系弱）**
"强关系（同步调用 / 共享状态）直接、直观、容易理解；弱关系（异步 / 事件 / 契约）解耦、可替换、但要绕。哪个更好？'关系是成本'到底在说什么？"
追问：① 关系五类型（结构 / 行为 / 接口 / 部署 / 时序）+ 强度光谱（强 / 中 / 弱）——为什么强关系变更牵动整片？② 关系设计六步（识别 / 分类 / 定方向 / 降耦合 / 契约化 / 检查）——头号决策为什么是依赖方向（DAG 无环）？③ 五判据（有方向 / 够稀疏 / 尽量弱 / 要显式 / 不穿越）——迪米特法则"talk to your friends, not strangers"？④ 反身：画你们系统关键模块依赖图，有环吗？几条不必要？能往弱推吗？

**Q9（方法时刻 · 规则 15 · 从见过到拥有 + 跨域变体）**
"水忠第二次带进会议室的不是图、选型和老规矩，而是五样能'定形'的东西。把你们系统正在设计 / 维护的一个系统（或一次要加的架构能力），亲手做一遍五块设计：基本概念（它还是不是它？）、基本属性（要涌现什么、怎么场景化？）、设计准则（自加什么规矩？）、演进准则（变而不破坏对的规矩？）、元素关系（怎么连、往弱推？）——哪一块卡住了？"
追问（跨域变体）：① 冰链 M3 的五块（边缘预警 = 追溯机制的新输入，候选 B 幸存、命名"边缘预警输入"）↔ 恒信合同平台的五块（合同数据所有权归合同域、审批引擎通过契约访问）——同一个五块，换一个世界判据变没变？"这个概念换个世界还成立吗？"② 冰链的"候选 B 幸存"和恒信的"关系降耦合"，是不是同一套判据在起作用（概念跨域 = 概念是刀、系统是大象）？③ 反身：把"画图 / 选型 / 定规矩 = 见过"和"五块设计定形 = 拥有"对到你们自己的变更上——你们到哪一步了？哪一块还停在"见过"？

**Q10（落地生根 · 回部门五块体检）**
"结合你们部门现状，挑一个正在设计或维护的系统，用五块设计做一次体检：五块各答得出吗？答不出的那一块是不是就是设计缺口？给出最该做的三件事，每个落到一个可检查动作。"
追问：先答哪一块？为什么（只有概念直面世界，先钉基本概念）？这次体检动的是横切（架构）还是纵挖（详细）？两周后回来报告什么？
