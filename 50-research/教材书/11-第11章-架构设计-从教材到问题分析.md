### 核心概念（含根概念标注）

> 标注规则（v2.1）：按正文根概念四标准（原子性/生成性/不可替代性/递归性）标出本章档案中的**承重柱**——先抓根、再展骨架。本章的承重柱 = **架构设计**（见头注论证）；五块清单里"基本概念"为骨架承重柱（唯一直面世界），目的判据是其成员资格裁决者。

1. **架构设计**（architecture design）**【根概念 · 本章承重柱】**：把需求翻译成系统结构的活动——决定系统怎么切分、怎么连接、守什么规矩；产品开发中最不可逆、返工代价最高的一组决策。判据：三问（它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计）。**承重柱证据**：原子性（一个动作不可再归约）/ 生成性（五块设计、三动词链、六步、创新评分席全部从它派生）/ 不可替代性（去掉它本章方法论不成立）/ 递归性（第10章架构之上、第12章架构决策之下层层生效，五块内部可递归细分）。三问判据入"必须脱口"。
2. **基本概念**（fundamental concepts）**【骨架 · 清单承重柱】**：系统在其环境中"怎么想"的根源——组织范式 / 核心抽象 / 根本机制 / 根隐喻（42010 定义第一块）；90% 从概念库选 + 10% 被需求/质量属性逼出，候选→检验→幸存，命名是概念化的完成仪式。判据：自查四问（组织范式还是核心抽象？走哪条生成路径？过检验了吗？有名字吗？）。**检验的最高判据 = 目的判据**：fundamental 由系统对其环境中的**目的**单独裁决（IEV 831-01-01 Note 2，等同采用 42010:2011 §3.2），操作化为不变量判据——判别问句「这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统？」；问句后半问的是同一性（目的论的同一性，回指第10章 §10.3.4 忒修斯之船；李旭"M3 还是 M3 吗" = "M3 的目的还在吗"）。目的判据之下还有从属判据（改动代价，Ralph Johnson），只在根本集合内排优先级/时机、不产生新架构成员；顺序不可颠倒：先过目的关、再过代价关（两种错位都是病，第12章 §12.3.1）。**五块里唯一直面世界的层——清单承重柱**。
3. **基本属性**（fundamental properties）：系统"具备什么"的本质特征——可观察、可度量的表现；涌现属性（emergent property），由结构决定。判据：自查四问（目标属性场景化了吗 QAS？选了哪个战术？战术落在哪个结构位置？度量过、涌现达标了吗？）。
4. **设计准则**（principles of design）：架构师自愿的自我限制——约束被迫、决策自选、原则自加；原则是"决策的决策"（meta-decision）。判据：四判据（可判定 / 有理由 / 少而精 5~15 条 / 可入评审）；句式 = 必须/禁止/应当 + 规则 + 理由。
5. **演进准则**（principles of evolution）：设计准则的"时间维"延伸——怎么变而不破坏对（防漂移/侵蚀/技术债）；与配置管理（第13章）是同一套制度的两层皮（管"形" vs 管"物"）。判据：判别法——主语全是"变"的是演进准则；八类。含目的漂移（目的悄悄变化而架构未跟随，执行对、判据过期、无症状、更危险；目的变更=架构重审强制触发器）。
6. **元素关系**（relationships）：元素之间怎么连——关系是成本（n 个要素全互联是 n² 条关系，每条都是未来变更时的一处牵动）；第一原则"克制"、核心动作降耦合。判据：五判据（有方向 / 够稀疏 / 尽量弱 / 要显式 / 不穿越）。
7. **构思 / 定义 / 设计**（conceiving / defining / design）【动词链三概念】：构思=打开可能性（con-capere 收进来+握取，从关注点生成候选）；定义=终结漂浮（de-finis 划界+陈述，求真）；设计=转换到底（how，求优；一词两义：广义=ABET 容器 ⊃ 构思+定义 vs 狭义=15288 §6.4.5 基线生效后的下游）。三句话钉住：构思打开可能性，定义终结漂浮，设计转换到底。
8. **架构生成六步**（architecture generation）：三动词链的工程化流程——（前置入场券·《系统目的或任务理解确认单》）定驱动（ASR）→ 生成备选（≥2）→ 权衡选定（效用树+ADR）→ 分配与接口（ICD）→ 表达与基线 → 评审与背书（TR2/TR3）。判据：缺一步不闭环；三纪律（驱动先于图/决策先于图/基线先于图）。入场券 = 判据侧首类输入「目的与任务」的确认形态：业务方原话（只引不改）+ 架构师复述理解 + 业务方确认签字；纯理解、零架构（复述里不出现元素/方案/需求等架构语言）；签字之前，后续一切产物都没有判据锚点。
9. **创新**（innovation）：链尾的评分席——结果义名词（ISO 56000:2020"创造或重新分配价值的新对象或变更对象"）；新 × 成，缺一归零。判据：够新吗？成了吗？主导动作是构思/定义/设计？架构式创新主导动作恰是"定义"。
10. **架构设计的输入**（输入六类 + 规定需求 + 关注点 + 目的判据）：不是"全部需求原文"，而是六类——**目的与任务** ⭐（判据侧首位，系统为什么存在）/ **需求** ⭐（功能：what；非功能：质量属性）/ 约束 / 环境 / 关注点 / 资产；两组职能——**判据侧**（目的与任务 / 关注点 / 需求）供给"什么是根本"的判据、内部有严格位次（目的与任务居首位、起决定作用，是 fundamental 成员资格的裁决者；目的为纲、关切与需求为目，与目的冲突的需求要么澄清要么拒绝），**选项空间**（约束 / 环境 / 资产）圈定"在什么范围内选"。且要吃系统级规定需求（已验证、可追溯、未分配）；非功能需求（质量属性）才是主要驱动；关注点是识别出来的不是设计出来的。
11. **系统基本概念和基本属性清单**（目的判据的裁决产物）：六步走完，目的判据把"什么配得上基本"裁出来，落成受控枚举清单——每条注明三件事（定义 / 对目的的必要性论证〔不变量判别问句的答案〕/ 到目的·需求的追溯链）；五块设计的总纲、评审的第一张核对单；清单本身基线化、增删走变更控制。分工：确认单是锚（目的进场）、清单是纲（裁决什么是根本的）、架构描述·决定清单·接口契约是目（表达、留痕、落地）。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 架构设计 | 详细设计 | 横向切（系统/子系统级）vs 纵向挖（部件内部）；先横后纵——横切错了纵挖白挖 |
| 架构设计 | 画架构图（架构描述） | 动作 vs 产物——图是表达，不是翻译本身 |
| 架构设计 | 技术选型 | 翻译 vs 候选——选型是待检验的选项 |
| 架构设计 | 定老规矩 | 动作 vs 规则候选——老规矩是设计准则的候选/雏形（过四关才升格） |
| 定义 definition | 设计 design | 划界+陈述（求真）vs 怎么做/怎么造（求优）；完成时 vs 动词 |
| 构思 conceiving | 定义 defining | 打开可能性（发散）vs 终结漂浮（定形） |
| 创新 innovation | 发明/点子 | 结果义（新×成）vs 想法诞生（只有新） |
| 基本概念 | 详细实现 | 去掉就不是它（不可还原）vs 改了系统还是它 |
| 基本属性 | 基本概念 | 系统"具备什么"（涌现，只能让结构催生）vs 系统"是什么"（可切可选） |
| 约束 constraints | 原则 principles | 外部强加（接受）vs 自愿自加（自我限制）；决策 decisions 是第三极（架构师选择） |
| 设计准则 | 演进准则 | 怎么设计对 vs 怎么变不破坏对——同一原则体系，一个管当下一个管未来 |
| 涌现属性 | 需求指标 | 结构运转后的宏观结果 vs 目标；QAS 场景化是两者的桥 |
| 目的判据（成员资格） | 代价判据（从属） | 裁决"谁是 fundamental"（对目的必要且充分）vs 只在根本集合内排优先级/时机（不产生新成员）——先过目的关再过代价关 |
| 架构设计 | 概要定义（第6章） | 架构是那棵树上不可还原的部分，比概要定义更深、更不可逆 |

### 关联概念（近界 · 辨析）

- **五块设计 ↔ 42010 定义的拆解**：第10章用同一条定义回答"架构是什么"（concepts or properties/elements/relationships/principles）；这一章回答"架构怎么被设计出来"——第10章"概念或属性"or 两条路（认知切入点）vs 本章五块一块都不能少（完整工作清单）。
- **三动词链 ↔ 架构生成六步 ↔ 创新评分席**：构思（①②生成候选）→ 定义（③④画边界定形）→ 设计（基线生效后转换到底）→ 六步（工程化，补⑤表达+⑥认证）→ 创新（链尾追认，新×成）。
- **三动词链 ↔ architecting 七动词链母词（R-04）**：architecting = 构思→定义→表达→记录→沟通→认证恰当实现→维护改进（42010 §3.1），是架构师能力增量的母词（ch16 用）；本章三动词链是它的前段工程化。
- **目的判据 ↔ 不变量 ↔ 同一性**：目的判据（fundamental=对目的必要且充分）操作化为不变量判别问句；问句后半"还是不是为那个目的的这个系统"= 目的论的同一性（第10章 §10.3.4 忒修斯之船）；李旭"M3 还是 M3 吗" = "M3 的目的还在吗"。与第12章"不可逆"（§12.3.1 目的关/代价关）同锚。
- **非功能需求 ↔ 质量属性 ↔ 基本属性**（Bass/Clements/Kazman）：功能需求是骨架、质量属性是体重——骨架决定长相、体重决定能不能站起来；质量属性（需求侧目标）以基本属性（结构运转结果）的形式涌现，QAS 是桥。
- **关注点 ↔ 相关方**：stakeholder × concern 矩阵——空格 = 有相关方没任何视图回答；冲突格 = 权衡点 = 架构决策的主战场。
- **演进准则 ↔ 配置管理（第13章）**：配置管理管"物"（configuration item 怎么受控），演进准则管"形"（架构怎么在受控下变形）；基线是演进的地板、版本是演进的足迹。
- **确认单 ↔ 清单 ↔ 目的判据**：确认单是锚（目的进场）、清单是纲（裁决什么配得上基本）、架构描述·决定清单·接口契约是目（表达、留痕、落地）——锚不定则纲不举、目不张。
- **命名 = 完成仪式 ↔ 第1章"概念是共同体酿出来的"**：一旦结构被命名，就从想法变成可共享、可讨论、可传承的概念。
- **概念幸存 ↔ 第10章"不可还原" / 第12章"不可逆"**：基本概念=对"不变性"的承诺——它"基本"正因为它是全部决策里最难改的那一层。
- **内部输入链 ↔ ADR**：ADR 是这条输入链的书面凭证（第12章决策记录六问展开）；反向校验答不出的就是"无源之水"。
- **三样东西（图/选型/老规矩）↔ 前章概念**：图=第10章架构描述；老规矩=第10章立、第11章承接（过四关升格）、第16章长成（贯穿物件回声登记）。
- **设计一词两义 ↔ 过程以产出物命名**：广义（ABET 容器）把构思装进去、狭义（15288 §6.4.5）排在基线生效后——不声明取哪一义，"设计"就在容器与下游之间漂移。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 翻译必然做选择——同一份需求可以翻译成不同的结构；翻译的每一个选择都是架构决策的种子（§11.2.1）。
2. 设计是"转化"（transform）——输入是已定义好的需求，输出是解决方案的特性描述；设计不负责说"系统是什么"，负责说"系统怎么兑现承诺"（§11.2.2）。
3. 定义 = 划界 + 陈述（de-finis，求真：准确/无歧义/可验证）；构思 = 收进来+握取（con-capere，发散）；设计 = 怎么做（how，求优）——设计本质上也是"定义"的一种，只是对象换成了解决方案（§11.2.3）。
4. 过程以产出物命名——15288 只有"架构定义过程""设计定义过程"，没有"架构设计过程"；构思无法评审，描述才能评审、验证、基线化（§11.2.3）。
5. 设计是动词（构思），定义是完成时（定形）——设计得再好，没定形就等于没设计（§11.2.3）。
6. 设计一词两义必须声明——广义（ABET engineering design 容器过程：构思/定义/表达装在里面）vs 狭义（15288 §6.4.5 以已生效架构基线为输入的下游流程）；不声明，词就在容器与下游之间漂移（§11.2.3）。
7. 五块一块都不能少——一旦要做架构设计，五块（概念/属性/设计准则/演进准则/关系）一块都不能少；"基本"二字凭什么裁决——由系统对其环境中**目的**的必要且充分（IEV 831-01-01 Note 2）（§11.2.4）。
8. 横切决定错了，纵挖挖得再深也是白挖——先横后纵（§11.2.5）。
9. 架构设计是概要定义背后那一层——比概要定义更深、更不可逆（§11.2.5）。
10. 系统有架构、模块也有架构——详细设计（纵挖）之前模块先有自己的"概要定义"（内部结构/依赖方向/实现策略，归模块工程师自己），每一层都先定义"它是什么"再实现（§11.2.5）。

**第二幕 · 磨边弧的机制（不是什么）**
11. 三样东西——图（架构描述/产物）、选型（候选）、老规矩（规则候选）——没有一样是"把需求翻译成系统结构"这个动作（§11.3.1）。
12. 非功能需求（质量属性）才是架构的主要驱动——功能需求告诉你"做什么"，质量属性告诉你"做到什么程度"，而"做到什么程度"才真正决定结构形态（§11.3.2）。
13. 功能需求是骨架，质量属性是体重——骨架决定长相，体重决定能不能站起来（§11.3.2）。
14. 目的与任务居判据侧首位——它是 fundamental 成员资格的裁决者；目的为纲、关切与需求为目（与目的冲突的需求，要么澄清、要么拒绝）；以《系统目的或任务理解确认单》锚定进入设计（§11.3.2 / §11.4.3）。
15. 架构设计吃规定需求——在流沙上画结构图等于开局自损一目；需求一变结构就得跟着动，代价指数级（§11.3.3）。
16. 需求分配是架构设计自己的工作，不是输入；"下一层吃的，是上一层产出的"——设计链是接力关系不是并行关系（§11.3.3）。
17. 质量属性是涌现属性——"可用性 99.99%"是整系统的属性，不能切碎分给部件，只能被架构机制满足、再翻译成部件级约束；"不能分，只能译"（§11.3.4）。
18. 关注点是识别出来的，不是设计出来的——concern 是 stakeholder 的 interest，已存在于其头脑、组织和契约里；42010 用的动词是 identify（§11.3.5）。
19. 漏掉一个 stakeholder，就是漏掉一整类 concern（§11.3.5）。
20. 基本概念是"选出来 + 逼出来 + 幸存下来"的——90% 从已验证概念库选、10% 被需求和质量属性逼着生成；候选要过检验活下来才配叫"基本"（§11.3.6）。
21. 基本概念 = 对"不变性"的承诺——它"基本"正因为它是全部决策里最难改的那一层（呼应第10章"不可还原"、第12章"不可逆"）（§11.3.6）。
22. 检验的最高判据是目的判据——fundamental = 对系统在其环境中的目的必要且充分（IEV 831-01-01 Note 2），操作化为不变量判别问句「这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统？」（§11.3.6）。
23. 目的判据问句后半问的是同一性——人造系统的同一性是目的论的（第10章 §10.3.4 忒修斯之船）；李旭"M3 还是 M3 吗"问的其实是"M3 的目的还在吗"（§11.3.6）。
24. 目的判据是成员资格判据、代价判据是从属判据——代价判据只在根本集合之内排优先级/时机、不产生新成员；顺序不可颠倒：先过目的关、再过代价关（两种错位都是病，第12章 §12.3.1）（§11.3.6）。
25. 命名就是概念化的完成仪式——一旦被命名，就从想法变成可共享、可讨论、可传承的概念（§11.3.6）。
26. 基本属性是"涌现"出来的——你设计的是结构，属性是结构运转之后的宏观效果（§11.3.7）。
27. 不能直接设计"强度"，只能设计微观晶格让强度涌现；不能直接设计"可用性"，只能设计冗余机制让可用性涌现（材料科学类比）（§11.3.7）。
28. 属性四步流水线：QAS 场景化 → 战术选择 → 结构落位 → 验证度量；没度量过的属性承诺等于没有（§11.3.7）。
29. 基本属性 = 生命线属性——系统可以平庸但不能没有的那些；关键性分析（criticality analysis）决定权衡时的优先级与资源投向（§11.3.7）。
30. 原则是"决策的决策"（meta-decision）——不是替你做决策，是让你不用重新想（§11.3.8）。
31. 原则是自愿的自我限制；标准句式 = 必须/禁止/应当 + 规则 + 理由；没有理由的原则是教条，有理由的原则是纪律（§11.3.8）。
32. 原则四判据：可判定/有理由/少而精（5~15 条）/可入评审；"用原则代替思考"是最大的诱惑——原则负责不需重新想的事、权衡负责必须重新想的事（§11.3.8）。
33. 演进准则 = 设计准则的"时间维"延伸——架构在无人管束时必然退化（架构漂移/架构侵蚀/技术债）；演进准则就是给"变"上的制度保险（§11.3.9）。
34. 目的漂移——目的悄悄变化而架构未跟随（方向与架构漂移相反：架构漂移=实现偏离架构、执行歪；目的漂移=目的偏离架构、执行对但判据过期），更危险、无症状，发现时不变量集合已整体过期；防架构漂移靠合规评审，防目的漂移靠以目的为参照的定期检视；目的变更 = 架构重审的强制触发器（§11.3.9）。
35. 判别设计准则与演进准则最快方法：这条规矩是关于"怎么建"的还是"怎么改"的——主语全是"变"的是演进准则（§11.3.9）。
36. 关系是成本——n 个要素全互联是 n² 条关系，每一条都是未来变更时的一处牵动；关系稀疏，独立性才强，可演进性才高（§11.3.10）。
37. 关系设计的核心动作是降耦合——强关系降级为弱关系（同步调用→异步消息/直接调用→事件发布订阅/共享状态→消息传递）；每降一级，变更的牵动范围就小一圈（§11.3.10）。
38. 关系是概念的具身化、属性的实现通道——概念定"有哪些骨架"，属性定"骨架要有什么性质"，关系定"骨架怎么连起来才具备这些性质"（§11.3.10）。

**第三幕 · 往哪去的机制（运用）**
39. 只有"基本概念"直接面对外部原始输入，越往后的块，输入里"内部成分"占比越高——五块输入分外部原始输入 + 内部派生输入两个来源（§11.4.1）。
40. 只有概念是"翻译"，其余是"翻译的翻译"——概念错了，后面四块全部跟着错、错得越来越远；概念阶段值得最重的人力（§11.4.2）。
41. 内部链是"失信放大器"——每一层输出质量 = 上一层输入质量 × 本层加工质量；评审时发现原则跟概念对不上，基本可以断定链断过（§11.4.2）。
42. 反向校验是免费的架构体检——从后往前核查（这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念/教训提炼？），答不出的就是"无源之水"；ADR 是这条输入链的书面凭证（§11.4.2）。
43. 三动词链：构思打开可能性，定义终结漂浮，设计转换到底——接力关系；构思无法评审，描述才能评审、验证、基线化（§11.2.3）。
44. 架构生成六步 = 动词链的工程化——（前置入场券·目的确认单）定驱动→生成备选≥2→权衡选定→分配接口→表达基线→评审背书；三纪律（驱动先于图/决策先于图/基线先于图）（§11.4.3）。
45. 不能说"架构构思 + 架构定义 + 架构设计"——"架构定义"是 15288 流程名（覆盖全程）、"架构设计"排在基线生效之后；生成 = 构思（①②）+ 定义动作义（③④）+ 表达（⑤）+ 认证（⑥）（§11.4.3）。
46. 没有背书的架构，只是架构师的个人意见——六步里最易跳过的是②（直接从需求跳到唯一解画图，架构层的 Cowboy Coding）和⑥（只评审不背书）；评审四看缺一看材料就是半成品（§11.4.3）。
47. 入场券《系统目的或任务理解确认单》——目的或任务原文（业务方原话，只引不改）+ 架构师复述理解 + 业务方确认签字；它同时是「理解」职责的产品数据：纯理解、零架构（复述里不出现元素/方案/需求等架构语言）；签字之前，后续一切产物都没有判据锚点；目的模糊或关注点冲突时向上游回溯澄清，不带着模糊目的硬架（§11.4.3）。
48. 《系统基本概念和基本属性清单》= 目的判据的裁决产物——fundamental 成员资格登记表，每条注明三件事（定义 / 对目的的必要性论证〔不变量判别问句的答案〕/ 到目的·需求的追溯链）；五块总纲、评审第一核对单（评审先问"这条概念配得上基本吗"）、受控枚举（清单本身基线化、增删走变更控制）；分工：确认单是锚、清单是纲、架构描述·决定清单·接口契约是目（§11.4.4）。
49. 创新不在动词链上——它是名词（结果义），是对动作结果的追认；"我们去创新吧"和"我们去成功吧"是同一类语病（§11.4.5）。
50. 创新判据只有一条：新 × 成，缺一归零——只有新没成是点子/发明（熊彼特），只有成没新是优化/复现；架构式创新主导动作恰是"定义"（元件不动、连接重排，Henderson & Clark）（§11.4.5）。
51. 创新可以工程化，但要精确到对象——流程（Stage-Gate）/方法（TRIZ）/组织（ISO 56001）/组合（漏斗下注）可工程化；不可工程化的是单点结果的确定性（§11.4.5）。
52. 从"见过"到"拥有"——图、选型、规矩是架构设计的"见过"；五块一块一块做出来、定了形，才是"拥有"；用第1章四问尺子量，每块答得全才算拥有（章末·认知反转）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "架构设计 = 画架构图 + 做技术选型 + 定老规矩。"

3. "架构设计就是选技术栈。"
4. "功能需求决定架构形态。"
5. "架构设计的输入 = 全部需求原文。"
6. "架构设计的输入就是需求，目的和任务跟设计没关系。"
7. "《系统目的或任务理解确认单》是设计做完之后补的文档。"
8. "关注点是可以'设计'出来的。"
9. "基本概念是架构师发明出来的。"
10. "直接设计可用性，把 99.99% 分配给每个模块。"
11. "原则越多越严谨，把能想到的规矩都写上。"

13. "关系越多系统越强，大家尽量互联互通。"

### 四问萃取（溯源 · 致用，含薄格标注）

> v2.1 第 1 步第六样：每个核心概念从概念卡四问化过一遍四问——是什么 / 不是什么 / **从哪来（②背景·③演化，溯源）** / **往哪去（④拟解决问题·⑤适应场景/失效边界，致用）**。溯源与致用是显式萃取目标；薄格标注"可省"，不得默认跳过。四问有书内依据的为非薄格，正文着墨薄的标薄格。

| 核心概念 | 它是什么 | 它不是什么 | 从哪来（溯源） | 往哪去（致用） | 薄格 |
|---|---|---|---|---|---|
| **架构设计**【根】 | 把需求翻译成系统结构的活动（切分/连接/规矩）；最不可逆、返工代价最高的一组决策 | 不是画图（图是架构描述/产物）；不是选型（选型是候选）；不是定规矩（规矩是设计准则候选/雏形）；不是详细设计（横切 vs 纵挖）；不是概要定义（更深更不可逆） | 系统复杂度超过一个人能装下，得先把需求"翻译"成结构、定形后再谈实现；ISO 9000:2015 §3.4.8 先定"设计开发=需求→详细特性"；15288 把系统层过程命名为"架构定义"——过程以产出物命名；英文 design ← de（做）+ signare（标记）（§11.2.2~11.2.3） | 回答"如何把需求翻译成结构、让后续设计与演进都有边界可依"；在系统级切分/连接/守规矩决策上使用（部件内部是详细设计，模块内部先有模块级概要定义）；失效边界=三样东西（图/选型/规矩）被当架构设计时（概念卡⑧） | 均非薄格 |
| **基本概念** | 系统"怎么想"的根源——四副面孔（组织范式/核心抽象/根本机制/根隐喻） | 不是详细实现（去掉就不是它 vs 改了还是它）；不是技术选型（选型是候选，概念是幸存下来的承诺）；不是发明出来的（90%选+10%逼） | 90% 从已验证概念库选、10% 被需求/质量属性逼出——候选过检验才配叫"基本"；五条路径（①模式选择②领域抽象③质量属性反推④类比迁移⑤第一原理）；ISO/IEC/IEEE 42020 把生成候选叫"架构综合"；检验最高判据=目的判据（fundamental=对目的必要且充分，IEV 831-01-01 Note 2，操作化为不变量判别问句）；英文 fundamental ← fundus（底部）、concept ← concipere（一起抓住）（§11.3.6） | 决定后续所有决策的锚（对"不变性"的承诺）；在设计之初或需求/质量属性逼出候选时使用；命名=概念化的完成仪式（"边缘预警输入"）；成员资格由目的判据裁决、优先级/时机由代价判据排（先过目的关再过代价关）；失效边界=把画图当定义了概念（概念长在决策里，不长在图上）（§11.3.6） | 均非薄格 |
| **基本属性** | 系统"具备什么"的本质特征——可观察、可度量的表现；涌现属性，由结构决定 | 不是基本概念（概念可切可选 vs 属性只能让结构催生）；不是质量属性（质量属性是需求侧目标，属性是结构运转后涌现的结果；QAS 是桥）；不能直接设计（不能设计强度只能设计晶格） | 系统级质量属性没法像功能需求那样逐条分配，只能靠设计结构催生——于是单列一块，用四步流水线管理；emergent property 溯源至 1960s 系统动力学/涌现论传统；英文 property ← proprius（自身的、固有的）（§11.3.4/§11.3.7） | 回答"系统具备什么本质特征、怎么把它变成可验收的承诺"；设计结构让属性涌现，再用度量验证（QAS→战术→落位→验证）；基本属性=生命线属性（关键性分析筛选）；失效边界=直接设计属性或把属性分给某个模块（§11.3.7） | 均非薄格 |

### 本章判据（十四把尺子）

1. **架构设计 = 翻译**：把需求翻译成系统结构（切分、连接、规矩）；画图、选型、定规矩都只是这个翻译的产物/候选/规则，不是翻译本身。**违反即崩：水忠带了三样东西进会议室——没有一样是"把需求翻译成系统结构"这个动作，架构设计等于没做。**
2. **设计是动词，定义是完成时**：定义 = 划界 + 陈述（de-finis）；过程以产出物命名——构思无法评审，描述才能评审、验证、基线化。没定形，就等于没设计。**违反即崩：构思停在脑子里，拿不出可评审、可验证、可基线化的产物——"我们做过架构设计"被当成"我们有架构描述"。**
3. **横切先于纵挖**：架构设计横向切（切成几块、怎么对接），详细设计纵向挖（每块内部挖多深）——先横后纵。**违反即崩：横切错了，纵挖挖得再深也是白挖——墙砌错了要拆楼，装修错了刷一遍就行。**
4. **非功能需求才是主要驱动**：功能需求告诉"做什么"，质量属性告诉"做到什么程度"，而"做到什么程度"才真正决定结构形态。**违反即崩：功能相同的系统，质量属性不同，架构可以完全不同——"提前 30 秒还是 5 分钟"不定，预判逻辑放硬件还是云端就无从定。**
5. **输入是六类、且必须是规定需求**：六类里目的与任务居判据侧首位（以《系统目的或任务理解确认单》锚定进入），需求必须是系统级规定需求（已验证、未分配），在流沙上画图等于自损一目；需求分配是架构设计自己的工作，不是输入。**违反即崩：拿"要能提前预判断链"这句话直接设计，水忠在第一版结构上反复返工——需求一变，结构跟着动，代价指数级。**
6. **质量属性不能分，只能译**：涌现属性是整个系统的属性，只能被架构机制满足、再翻译成部件级约束。**违反即崩：把"可用性 99.99%"切碎了分给每个模块——根本没有哪个模块"负责可用性"，只能设计冗余机制让属性涌现。**
7. **关注点是识别出来的，不是设计出来的**：识别五步（相关方 → 提取 → 划界 → 编排 → 验证）；好 concern 四判据（有主/有界/可权衡/可追溯）+ 清单级完备（矩阵无空行空列）。**违反即崩：从"我要画什么"出发——先定好画哪几张图、再往回填关注点，相关方真正在乎的被漏在矩阵外；改从关注点出发，空格才会暴露（案例进展②）。**
8. **概念幸存、属性涌现**：基本概念 90% 选 + 10% 逼，候选→检验→幸存，命名是概念化的完成仪式；基本属性不能直接设计，只能设计结构让属性涌现，且必须度量验证。**违反即崩：候选画进了图里，检验不过照样死——"边缘预判"没成为新本质，只是追溯机制的新输入；"及时性"画不进去，只能设计"双路采样 + 边缘计算"让结构催生。**
9. **原则是自愿的自我限制**：约束被迫、决策自选、原则自加；句式 = 必须/禁止/应当 + 规则 + 理由；可判定/有理由/少而精/可入评审；演进准则 = 设计准则 × 时间轴。**违反即崩：老规矩过不了四关——没有理由、不能判定、多如牛毛、入不了评审，它就不是纪律，是教条。**
10. **关系是成本**：关系稀疏才可演进；依赖无环、往弱推、契约化；五判据（有方向/够稀疏/尽量弱/要显式/不穿越）。**违反即崩：n 个要素全互联是 n² 条关系，每条都是未来变更的一处牵动——循环依赖是架构腐蚀的头号元凶。**
11. **只有概念直面世界**：五块输入是外部原始输入 + 内部级联；概念错了后面全错——反向校验（这条关系服务哪个属性？这个属性被哪个概念限幅？）答不出的就是无源之水。**违反即崩：概念设计错了，后面四块全部跟着错、错得越来越远——概念说"无状态"，原则却是抄来的"共享缓存"，评审对不上账。**
12. **构思打开可能性，定义终结漂浮，设计转换到底**：三动词链是接力——构思生成 ≥2 候选、定义画边界定形、设计（狭义）基线生效后转换到底；"设计"一词两义必须声明。**违反即崩：只有一个候选就"定义"——唯一解 = 未审视的解，没有权衡可言。**
13. **生成六步，缺一步不闭环**：（前置入场券·目的确认单）定驱动 → 生成备选 → 权衡选定 → 分配接口 → 表达基线 → 评审背书；三纪律（驱动先于图/决策先于图/基线先于图）。**违反即崩：没有背书的架构只是架构师的个人意见——评审是验证关，绕过去等于没验证。**
14. **创新 = 新 × 成，坐链尾评分席**：创新不在动词链上；够新又成了才追认；架构式创新主导动作恰是"定义"。**违反即崩：把"点子"当"创新"——只有新没成是点子/发明，没落地不算创新（奥斯陆手册）。**

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能答全四问，三档标注）

> v2.1：概念层掌握标准提为**四问**（定义/辨析/溯源/致用）；档位先抓根——本章根概念（架构设计）与最狠判据入"必须脱口"，溯源/致用维度至少入"能解释"。

1. **架构设计**【根概念 · 必须脱口】：能定义（把需求翻译成系统结构的活动——切分/连接/规矩）；能辨析（≠图/选型/规矩，≠详细设计，≠概要定义）；能溯源（ISO 9000 §3.4.8 + 15288 命名 + design 词源）；能致用（三问判据 + 后续设计与演进的边界依凭）。
2. **基本概念**【必须脱口】：能定义（四副面孔）；能辨析（≠详细实现，≠技术选型，不是发明）；能溯源（五条路径 + 90%选10%逼 + 42020 架构综合 + 目的判据 IEV 831-01-01）；能致用（决策锚 + 命名=完成仪式 + 目的判据=成员资格裁决 + 自查四问）。
3. **基本属性**【必须脱口】：能定义（涌现属性，可观察可度量）；能辨析（≠基本概念，≠质量属性，不能直接设计）；能溯源（系统级质量属性没法分配→单列 + emergent 溯源 1960s + property 词源）；能致用（四步流水线 + 生命线属性/关键性分析 + 可验收承诺）。
4. **设计准则**【必须脱口】：能定义（原则=自愿自加）；能辨析（≠约束，≠决策，不是抄来的）；能溯源（三生成源 + 两路径对撞 + 宪法判例互驯）；能致用（四判据 + 句式 + 不用重新想）。
5. **演进准则**【能解释】：能定义（设计准则×时间轴）；能辨析（≠设计准则，≠运维的事）；能溯源（四条源 + 架构熵增 + 目的漂移）；能致用（八类 + 判别法主语全是变 + 与配置管理两层皮 + 防漂移法）。
6. **元素关系**【能解释】：能定义（关系是成本）；能辨析（≠越多越好，≠独立存在）；能溯源（42010 relationships + 邓巴数 + 迪米特法则【薄格】）；能致用（六步 + 五判据 + 具身化/实现通道）。
7. **构思 / 定义 / 设计（三动词链）**【必须脱口】：能定义（打开可能性/终结漂浮/转换到底）；能辨析（一词两义必须声明；≠并列词）；能溯源（词源 con-capere/de-finis/de+signare + ABET/15288/24765）；能致用（设计是动词定义是完成时 + 六步工程化 + 过程以产出物命名）。
8. **架构生成六步**【能解释】：能定义（前置入场券·目的确认单 + 定驱动→备选→权衡→分配→表达→背书）；能辨析（≠画图，≠"架构构思+架构定义+架构设计"并列）；能溯源（三动词链工程化 + 15288 架构定义过程内部第一件事【薄格】）；能致用（缺一步不闭环 + 三纪律 + 评审四看 + 入场券纯理解零架构）。
9. **创新**【能解释】：能定义（结果义新×成）；能辨析（≠点子/发明，≠构思，不在动词链上）；能溯源（ISO 56000 + 熊彼特 + Henderson & Clark + 奥斯陆手册）；能致用（四种进来方式 + 架构式创新主导定义 + 可工程化边界）。
10. **架构设计的输入**【能解释】：能定义（六类：目的与任务⭐/需求⭐/约束/环境/关注点/资产）；能辨析（≠全部需求原文，需求分配不是输入，目的与任务不是无关输入）；能溯源（业界无统一口径，本书归拢 + Bass + IEV 831-01-01【薄格】）；能致用（目的与任务居判据侧首位以确认单锚定 + 非功能主导 + 规定需求 + 系统级）。
11. **关注点（concern）**【能解释】：能定义（stakeholder 的 interest）；能辨析（≠设计出来的，≠requirement）；能溯源（42010 identify）；能致用（五步识别 + 四判据+清单级完备 + 权衡点主战场）。
12. **系统基本概念和基本属性清单**【能解释】：能定义（目的判据的裁决产物、成员资格登记表）；能辨析（≠随意笔记，受控枚举）；能溯源（目的判据落纸形态）；能致用（三要素 + 五块总纲 + 评审第一核对单 + 确认单是锚/清单是纲/AD·决定清单·接口是目）。
13. 能说出五块设计清单（基本概念/基本属性/设计准则/演进准则/元素关系）+ 各自 42010 出处 + "系统怎么……"一句话（怎么想/具备什么/怎么设计对/怎么变不破坏对/怎么连）。
14. 能说出架构设计三问判据（切分/连接/规矩）与概念卡自查四问（基本概念/基本属性各四问）。

### 原理层（应能解释为什么）

1. 能解释为什么翻译必然做选择（同一需求 → 不同结构；每个选择都是架构决策的种子）。
2. 能解释为什么设计是"转化"（输入 = 已定义需求，输出 = 解决方案特性描述；设计不负责说"系统是什么"）。
3. 能解释为什么定义 = 划界 + 陈述、构思 = 打开可能性、设计 = 怎么做（三个词源）。
4. 能解释为什么过程以产出物命名（构思无法评审，描述才能评审、验证、基线化）。
5. 能解释为什么设计得再好没定形等于没设计（设计是动词，定义是完成时）。
6. 能解释为什么"设计"一词两义必须声明（广义 ABET 容器 vs 狭义 15288 下游——不声明词就在容器与下游之间漂移）。
7. 能解释为什么非功能需求才是主要驱动（功能决定长相，质量属性决定能不能站起来）。
8. 能解释为什么目的与任务居判据侧首位（它是 fundamental 成员资格的裁决者；目的为纲、关切与需求为目；以确认单锚定进入）。
9. 能解释为什么在流沙上画图自损一目（架构设计是设计链最不可逆的一环，结构一动代价指数级）。
10. 能解释为什么需求分配是架构设计自己的工作不是输入（设计链是接力关系，不是并行关系）。
11. 能解释为什么质量属性不能分只能译（涌现属性是整系统属性，没有哪个模块"负责可用性"）。
12. 能解释为什么关注点是识别出来的不是设计出来的（concern 已存在于相关方头脑/组织/契约里；identify 不是 design）。
13. 能解释为什么基本概念是幸存下来的（90% 选 + 10% 逼；候选→检验→幸存）。
14. 能解释为什么检验的最高判据是目的判据（fundamental = 对目的必要且充分；操作化为不变量判别问句「它还是不是为那个目的的这个系统」）。
15. 能解释为什么目的判据问句后半问的是同一性（人造系统同一性是目的论的，第10章 §10.3.4 忒修斯之船；"M3 还是 M3 吗" = "M3 的目的还在吗"）。
16. 能解释为什么目的判据是成员资格判据、代价判据是从属判据（代价判据只在根本集合内排优先级/时机、不产生新成员；先过目的关再过代价关，两种错位都是病）。
17. 能解释为什么命名是概念化的完成仪式（从想法变成可共享、可讨论、可传承的概念）。
18. 能解释为什么基本属性只能设计结构让涌现（材料科学类比：不能设计强度只能设计晶格）。
19. 能解释为什么没度量过的属性承诺等于没有（验证度量是四步最后一步，是 verification 的主场）。
20. 能解释为什么原则是"决策的决策"（让你不用重新想；原则负责不需重新想的事、权衡负责必须重新想的事）。
21. 能解释为什么演进准则必要（架构熵增：漂移/侵蚀/技术债；制度保险——系统不是不变，而是变的方式受约束）。
22. 能解释为什么目的漂移比架构漂移更危险（目的漂移=目的偏离架构、执行对但判据过期、无症状；防架构漂移靠合规评审、防目的漂移靠以目的为参照的定期检视）。
23. 能解释为什么关系是成本（n²；关系稀疏才可演进）。
24. 能解释为什么只有基本概念直面世界（内部输入链：外部原始输入 → 概念 → 属性 → 准则 → 演进）。
25. 能解释为什么概念错了后面全错且越错越远（翻译的翻译 + 失信放大器）。
26. 能解释为什么反向校验是免费架构体检（答不出的就是无源之水；ADR 是书面凭证）。
27. 能解释为什么三动词链是接力关系（构思打开可能性、定义终结漂浮、设计转换到底）。
28. 能解释为什么不能说"架构构思+架构定义+架构设计"（"架构定义"是 15288 流程名覆盖全程、"架构设计"排在基线生效后）。
29. 能解释为什么确认单是入场券（判据侧首类输入「目的与任务」的确认形态；纯理解、零架构；签字之前后续一切产物都没有判据锚点）。
30. 能解释为什么《系统基本概念和基本属性清单》是评审第一核对单（目的判据的裁决产物；答不出必要性论证 = 无源之水；受控枚举）。
31. 能解释为什么没有背书的架构只是架构师的个人意见（⑥评审背书是验证关口；绕过去等于没验证）。
32. 能解释为什么创新不在动词链上（它是结果义名词；新×成缺一归零）。
33. 能解释为什么架构式创新主导动作是定义（元件不动、连接重排，Henderson & Clark）。
34. 能解释为什么创新可工程化但单点结果不可工程化（工程化管漏斗的形状与流量，不管哪一滴水通过）。

### 判据层（应会用）

1. **架构设计三问判据**：它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计。
2. **定义 vs 设计判据**：没定形的构思等于没设计（能评审/验证/基线化才算定形）。
3. **横切先于纵挖判据**：横切决定错了，纵挖挖得再深也是白挖；系统有架构、模块也有架构，模块详细设计前先有模块概要定义。
4. **非功能主导判据**：做到什么程度（质量属性）决定结构形态——99.99% 和 99% 是两个架构。
5. **输入六类判据**：六类（目的与任务⭐/需求⭐/约束/环境/关注点/资产）；目的与任务居判据侧首位、以《系统目的或任务理解确认单》锚定进入；需求吃系统级规定需求（已验证/可追溯/未分配）；"下一层吃的，是上一层产出的"。
6. **目的判据（成员资格）**：fundamental = 对目的必要且充分（IEV 831-01-01）——操作化为不变量判别问句「这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统？」；先过目的关（是不是根本的），再过代价关（值不值得现在定死），顺序不可颠倒。
7. **质量属性只能译判据**：QAS 场景化 → 翻译成部件级设计约束（"本模块必须无状态，状态存外部存储"）。
8. **关注点识别判据**：五步识别 + 好 concern 四判据（有主/有界/可权衡/可追溯）+ 清单级完备（矩阵无空行空列）。
9. **概念幸存自查四问**：它是组织范式还是核心抽象？走哪条生成路径来的？过了检验吗（目的判据）？它有名字吗？
10. **属性涌现自查四问**：目标属性场景化了吗（QAS）？选了哪个战术？战术落在哪个结构位置？度量过、涌现达标了吗？
11. **原则四判据**：可判定（能对一个具体决策判定"它违反了吗"）/有理由/少而精（5~15 条）/可入评审。
12. **演进准则判别**：这条规矩是关于"怎么建"的还是"怎么改"的——主语全是"变"的是演进准则。
13. **关系五判据**：有方向（依赖无环 DAG）/够稀疏（关系少而必要）/尽量弱（能异步不同步）/要显式（依赖抽象不依赖实现）/不穿越（迪米特法则）。
14. **反向校验判据**：这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念/教训提炼？答不出 = 无源之水。
15. **三动词链判据**：构思生成 ≥2 候选吗？定义画边界定形了吗（ADR 记录被否备选死因）？设计等基线生效才动吗？
16. **确认单判据**：业务方原话（只引不改）+ 复述理解 + 确认签字？复述里有没有出现架构语言（出现 = 越界）？签字之前 = 没有判据锚点？
17. **清单判据**：每条概念/属性有定义 + 对目的的必要性论证 + 到目的/需求的追溯链吗？答不出必要性论证 = 无源之水，不进清单。
18. **六步闭环判据**：六步哪一步被跳过？（最易②生成备选——架构层 Cowboy Coding、⑥评审背书——只评审不背书。）
19. **创新判据**：够新吗？成了吗？主导动作是构思/定义/设计？——元件不动、连接重排的是架构式创新，主导动作是定义。

### 纠错红线十条

1. **先表态后翻案**：先让学员说出"这三样凑齐不就是架构设计吗 / 这还用讨论吗 / 想到好点子不就是创新吗 / 输入就是需求，目的任务跟设计有什么关系"，再翻，不让结论先入。
2. **反转精确不造新误解**："概念是幸存下来的"别翻成"概念不用设计"——设计负责把候选摆上桌、定检验；"关系是成本"别翻成"关系越少越好"——是满足需求前提下的克制；"创新是结果义"别翻成"创新不重要 / 不用做"——它决定追认时机，不否定创造；"目的与任务居判据侧首位"别翻成"功能需求不重要"——非功能主导不等于功能可省略，功能是骨架。
3. **判据配机制**：每条反转都有"为什么"（翻译必然做选择 / 涌现属性是整系统属性 / 原则是决策的决策 / 过程以产出物命名 / 目的判据=成员资格裁决 / 确认单=入场券）+ "怎么当场验证"（三问 / 四步 / 四关 / 五判据 / 六步 / 不变量判别问句）。
4. **归责到可对照动作**："你没做架构设计"落到"你拿不出五块里能定形的任何一块、没签确认单、清单答不出必要性论证"，不归咎"你不会画图 / 不懂技术"。
5. **教机制不教断言**：教"为什么质量属性只能译（涌现属性没有哪个模块负责可用性）"，不教"属性不能分"当口号。
6. **先立尺子再翻案**：先给三问 / 五块 / 四判据 / 六步 / 目的判据，再翻章首三样东西。
7. **拉开强度层次**：★★★ 常识（画图 = 架构设计 / 选型 = 架构设计 / 功能决定形态 / 原则越多越好 / 创新 = 点子 / 目的任务跟设计无关 / 确认单是补记）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一次五块设计体检 + 六步体检 + 写一份目的确认单"。
9. **单一权威不另立标准**：判据引用书（本章判据 14 条）+ ISO 42010 / 42020 / 15288 / 9000 / 56000 / IEV 831-01-01，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给现有系统做一次"五块设计体检"（含六步体检 + 入场券）

> 目标：用五块设计 + 反向校验 + 三动词链/六步闭环 + 目的判据/确认单/清单，给自己正在设计 / 维护的系统（或最近一次架构变更）做一次架构体检，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑系统 / 挑变更（先立尺子）**：挑一个你正在设计或维护的系统，或最近一次架构变更（对应书练习 1 / 3 / 13）。
2. **写目的确认单（先锚目的，入场券）**：写一份《系统目的或任务理解确认单》——业务方原话（只引不改）+ 你的复述理解 + 确认记录；检查复述里有没有出现架构语言（元素/方案/需求，出现 = 越界）。**签字之前，后续一切产物都没有判据锚点**；目的模糊或关注点冲突时，先向上游回溯澄清，不带着模糊目的硬架（书练习 15）。
3. **分三样东西的层次（先看病）**：列出这次架构工作的"图 / 选型 / 规矩"各是什么——它们只是表达 / 候选 / 规则候选，不是架构设计本身。图是架构描述、选型是候选、规矩是设计准则的候选（过四关才升格）。
4. **逐块答五块（五块设计）**：
   - **基本概念**：它"怎么想"——组织范式 / 核心抽象 / 根本机制 / 根隐喻是什么？"去掉就不是它"的是什么？走哪条生成路径（选/提/逼/借/推）？**过目的判据了吗**（不变量判别问句——"这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统"）？先过目的关、再过代价关（顺序不可颠倒）？它有名字吗？答不出 = 概念缺口。
   - **基本属性**：它要涌现什么本质特征——生命线属性是什么？目标属性场景化（QAS）了吗（刺激/环境/响应/度量）？
   - **设计准则**：你自加哪些规矩——用"必须/禁止/应当 + 理由"句式写，过四关（可判定/有理由/少而精/可入评审）。
   - **演进准则**：每条设计准则做时间维化——"这条规矩在变更时怎么执行"？用"变"字句式（如"接口变更必须双版本并行期"）；顺带查一次目的漂移（目的变了吗？判据过期了吗？）。
   - **元素关系**：关键模块依赖图——有环吗？几条不必要？强关系能往弱推吗（同步→异步/调用→事件）？
5. **反向校验（免费体检）**：随机挑一条设计准则向上追——它从哪个概念/属性提炼来的？答不出 = 无源之水（输入链断过）。
6. **三动词链 + 六步体检（动词链工程化）**：把最近一个架构决策拆三动词链——构思阶段生成过几个候选（≥2 吗）？定义阶段被否掉的备选"死因"记录了吗（ADR）？设计（狭义）是等基线生效才动的吗？再用六步查——六步里哪一步被跳过了？（最易②生成备选——直接从需求跳到唯一解画图，架构层 Cowboy Coding；⑥评审背书——只评审不背书。）
7. **落清单（目的判据的裁决产物）**：把"什么配得上基本"落成《系统基本概念和基本属性清单》——每条注明 定义 / 对目的的必要性论证（不变量判别问句的答案）/ 到目的·需求的追溯链；答不出必要性论证的就是"无源之水"，不进清单。它是评审的第一张核对单、五块设计的总纲。
8. **创新判定（链尾评分席）**：最近一次被叫"创新"的事——够新吗？成了吗？主导动作是构思、定义还是设计？元件不动、连接重排的是架构式创新，主导动作是定义。
9. **产出三件最该做的事**：每条 = 一个可检查动作 + 一条判据（三问 / 四步 / 四关 / 五判据 / 六步 / 目的判据）。

**卡住怎么判断**：答不出的那一块就是设计缺口（书练习 1）；先钉基本概念——只有概念直面世界，概念错了后面全错（先问"它还是不是它"）；开工前先问"确认单签了吗、目的是不是已经确认可判定"。

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 章首破题）**
"水忠带三样东西进会议室——一张新的四层方块图（在固件层和云端层之间加了一个框'边缘预判模块'）、一页技术选型、一页老规矩，以为架构设计做完了。文正三个问题——预判跑硬件还是云端？'提前告警'要提前多久？加进来之后 M3 还是 M3 吗？——水忠一个都答不上。散会时，产品开发经理永兵问了一句：'咱们做了这么多年 M3，怎么被问到它是什么，一句话都说不上来？'这三样东西各是什么（产物/候选/规则）？架构设计本身是什么？为什么三样加在一起，仍然不算架构设计，连'M3 是什么'都答不上来？"
追问：① 三问判据（决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？）——水忠三样东西各自答得出哪一问？② "设计是动词，定义是完成时"——水忠拿不出什么？③ 架构设计与详细设计怎么分工（横向切 vs 纵向挖）？架构设计和第6章概要定义什么关系（架构是那棵树上不可还原的部分）？为什么先横后纵？系统有架构、模块也有架构——模块的详细设计之前先有什么？④ 反身：你们最近一次"做架构设计"，带的是哪几样？过得了三问吗？答得出"它是什么"吗？

**Q2（见树见林② · 概念关系）**
"画出 基本概念、基本属性、设计准则、演进准则、元素关系 的关系图，标出：哪一块直接面对需求？为什么说只有基本概念直面世界，其余四块都是'翻译的翻译'？"
追问：① 内部输入链怎么串（外部原始输入 → 概念 → 属性 → 准则 → 演进；概念 + 属性 → 关系）？② 概念错了为什么后面全错、而且越错越远（失信放大器）？反向校验怎么当场用（答不出的就是无源之水）？③ "外部原始输入"具体是什么（目的与任务/功能/非功能/约束/环境/关注点/资产）？为什么概念吃的必须是规定需求？目的与任务为什么居判据侧首位？④ 反身：你们系统的五块是并列的五份文档，还是按输入链串起来的？

**Q3（真悖论 · 定义 vs 设计 · 三动词链 · 创新坐链尾）**
""我们做过架构设计"和"我们有架构描述"，是同一件事吗？为什么标准里只有'架构定义过程'和'设计定义过程'，没有'架构设计过程'？构思、定义、设计是一条什么链？创新在这条链的什么位置？"
追问：① 定义 = 划界 + 陈述（de-finis，求真），构思 = 打开可能性（con-capere，发散），设计 = 怎么做（how，求优）——为什么过程以产出物命名？② 设计一词两义：广义（ABET 容器）vs 狭义（15288 §6.4.5 基线生效后的下游）——为什么说"设计"前必须声明取哪一义？③ 创新为什么不在动词链上——"我们去创新吧"和"我们去成功吧"为什么是同一类语病？新×成缺一归零——架构式创新的主导动作为什么恰是"定义"（电动车滑板底盘）？④ 反身：你们团队的架构设计，有可以评审的定形产物吗，还是停在某个人的脑子里？最近一次被叫"创新"的事，够新吗？成了吗？

**Q4（真悖论 · 概念幸存 vs 属性涌现）**
"这一章说：基本概念不是设计出来的，是幸存下来的；基本属性不是设计出来的，是涌现出来的。那架构师设计的到底是什么？五块里到底有没有'设计'？"
追问：① 概念四副面孔（组织范式/核心抽象/根本机制/根隐喻）+ 五条生成路径（选/提/逼/借/推）；"候选→检验→幸存"——检验靠什么（原型 spike/ATAM/架构评审）？② 检验的最高判据是目的判据——fundamental = 对目的必要且充分（IEV 831-01-01），操作化为不变量判别问句"这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统"？李旭问"M3 还是 M3 吗"问的其实是"M3 的目的还在吗"（同一性·忒修斯之船）？③ 目的判据是成员资格判据、代价判据是从属判据——为什么顺序不可颠倒（先过目的关、再过代价关；用代价判据越过目的判据 = 把难改但无关紧要的误当架构）？④ 命名 = 概念化的完成仪式——"边缘预警输入"这个名字意味着什么？⑤ 属性四步流水线（QAS 场景化→战术→结构落位→验证度量）——为什么不能直接画个"及时性"模块？"99.99% 可用"怎么逼出"冗余 + 故障域"（路径③ = 非功能需求才是主要驱动）？⑥ 反身：你最近一次"加概念"，是选出来的、逼出来的，还是拍板发明的？过目的判据了吗？

**Q5（真悖论 · 原则自加 vs 约束被迫 · 演进准则）**
""约束是外部强加的，原则是自愿的自我限制"——那架构师为什么要自己给自己上规矩？自加束缚怎么反而是解放（第10章'约束即解放'）？规矩越多越严谨，还是越少越好？设计准则和演进准则怎么分？"
追问：① 约束/决策/原则三词辨析（被迫接受/架构师选择/自愿自加）？② 原则四判据（可判定/有理由/少而精 5~15 条/可入评审）——"追求优雅"为什么不是原则？"用原则代替思考"为什么是教条？③ 演进准则 = 设计准则 × 时间轴——"主语全是变"怎么判别？架构熵增（漂移/侵蚀/技术债）怎么防？目的漂移为什么比架构漂移更危险（执行对、判据过期、无症状），防法各是什么（合规评审 vs 以目的为参照的定期检视）？④ 反身：你们团队的"老规矩"过得了四关吗？有理由吗？能入评审吗？最近一次架构变更，目的变了吗？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 输入与驱动）**
"水忠面对'要能提前告警'——功能上就是'算风险、发告警'六个字。为什么这六个字决定不了预判逻辑放硬件还是云端？什么才真正决定？架构设计的输入到底是什么？"
追问：① 输入六类（目的与任务/需求[功能+非功能]/约束/环境/关注点/资产）各是什么？为什么目的与任务居判据侧首位（fundamental 成员资格的裁决者，以《系统目的或任务理解确认单》锚定进入）？为什么非功能需求才是第一驱动（"做到什么程度"才决定结构形态——功能决定长相、质量属性决定能不能站起来）？② 为什么输入必须是规定需求（已验证/可追溯/未分配）？在流沙上画图 = 自损一目——代价为什么是指数级？③ 质量属性为什么不能"分"，只能"译"（涌现属性，没有哪个模块负责可用性）？④ 反身：你们上次架构设计吃的输入，是"文正嘴里那句话"还是规定需求？目的确认单签了吗？

**Q7（判据运用 · 关注点识别）**
""架构设计的第一步不是画，是听——听那些'在乎'的人，到底在乎什么。"恒信万辉第一次做出 stakeholder × concern 矩阵，发现四格是空的。那四个空格告诉他什么？"
追问：① 关注点识别五步（相关方→提取→划界→编排→验证）？② 好 concern 四判据（有主/有界/可权衡/可追溯）+ 清单级完备（矩阵无空行空列）？③ 漏掉一个 stakeholder = 漏掉一整类 concern——万辉漏了谁（监管/运维/合同相对方/未来的维护者）？④ 反身：你们最近一次架构评审，从"谁在乎什么"出发了吗，还是从"我要画什么"出发？

**Q8（真悖论 · 关系强 vs 关系弱）**
"强关系（同步调用/共享状态）直接、直观、容易理解；弱关系（异步/事件/契约）解耦、可替换、但要绕。哪个更好？'关系是成本'到底在说什么？"
追问：① 关系五类型（结构/行为/接口/部署/时序）+ 强度光谱（强/中/弱）——为什么强关系变更牵动整片？② 关系设计六步（识别/分类/定方向/降耦合/契约化/检查）——头号决策为什么是依赖方向（DAG 无环）？③ 五判据（有方向/够稀疏/尽量弱/要显式/不穿越）——迪米特法则"talk to your friends, not strangers"？④ 反身：画你们系统关键模块依赖图，有环吗？几条不必要？能往弱推吗？

**Q9（方法时刻 · 规则 15 · 从见过到拥有 · 转述 + 跨域变体）**
"水忠第二次带进会议室的不是图、选型和老规矩，而是五样能'定形'的东西。把你们系统正在设计 / 维护的一个系统（或一次要加的架构能力），亲手做一遍五块设计：基本概念（它还是不是它？过目的判据了吗？）、基本属性（要涌现什么、怎么场景化？）、设计准则（自加什么规矩？过四关？）、演进准则（变而不破坏对的规矩？）、元素关系（怎么连、往弱推？）——哪一块卡住了？"
追问（转述 + 跨域变体）：① 转述（压缩测试）：把"架构设计到底是什么"用三五句话讲给一个完全外行的人——讲到哪卡住，缺口就在哪（五块里的哪一块还没定形）？② 冰链 M3 的五块（边缘预警 = 追溯机制的新输入，候选 B 幸存、命名"边缘预警输入"）↔ 恒信合同平台的五块（合同数据所有权归合同域、审批引擎通过契约访问）——同一个五块，换一个世界判据变没变？"这个概念换个世界还成立吗？"③ 五块定形后，目的判据把"什么配得上基本"裁出来，落成《系统基本概念和基本属性清单》——为什么它是评审的第一张核对单（评审先问"这条概念配得上基本吗"）？④ 把"画图/选型/定规矩 = 见过"和"五块设计定形 = 拥有"对到你们自己的变更上——你们到哪一步了？哪一块还停在"见过"？

**Q10（落地生根 · 回部门五块体检 + 六步）**
"结合你们部门现状，挑一个正在设计或维护的系统，用五块设计做一次体检：五块各答得出吗？答不出的那一块是不是就是设计缺口？再顺着六步查：最近一次架构活动，六步里哪一步被跳过了？最近一次被叫'创新'的事，够新吗、成了吗？给出最该做的三件事，每个落到一个可检查动作。"
追问：① 先答哪一块？为什么（只有概念直面世界，先钉基本概念）？开工前《系统目的或任务理解确认单》签了吗（业务方原话 + 复述 + 签字，复述里有没有出现架构语言）？② 这次体检动的是横切（架构）还是纵挖（详细）？③ 六步里最容易被跳过的是哪两步（②生成备选——直接从需求跳到唯一解画图，架构层的 Cowboy Coding；⑥评审背书——只评审不背书，评审变汇报）？评审先从《系统基本概念和基本属性清单》问起吗（"这条概念配得上基本吗"）？④ 两周后回来报告：哪一块补上了、哪一块还卡着、卡在哪个判据上？
