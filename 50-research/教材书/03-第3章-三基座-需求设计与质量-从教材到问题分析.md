## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：需求、设计开发、质量三个词各是什么？为什么它们是"三基座"？设计开发从哪开始、到哪结束？"等级高"为什么不等于"质量好"？"质量 vs 进度"的冲突本质是什么？三兄弟怎么咬合成一个拆不掉的基座？

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：1.1 需求（三种形态）→ 1.2 需要/期望/需求三量级 → 1.3 设计开发（四个构件）→ 1.4 质量（三个关键词）→ 1.5 三张概念卡 —— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：2.1 起点边界（需求 × 设计开发：研究先于需求 / 可转化四闸门 / 特性是否被规定）→ 2.2 终点边界（设计开发 × 质量：止于"可实现" / 八方案 / 可验证是循环倒置 / 声明 ≠ 事实）→ 2.3 参照边界（需求 × 质量：等级 ≠ 质量 ≠ 符合性 / 过度设计）—— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：3.1 读标尺（程度三步）→ 3.2 质量能有具体分值吗（85 分 / 关键特性不可摊平）→ 3.3 冲突（质量 vs 进度 = 需求集合内部打架 / 与相关方一起剪裁）→ 3.4 咬合（基座三角）—— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **需求**（requirement，ISO 9000:2015 §3.6.4）：明示的、通常隐含的或必须履行的需要或期望——定标尺，定义"要什么"。判据：起点"可转化"——完整、无歧义、不冲突、隐含需求已识别（2.1）。
2. **设计开发**（design and development，§3.4.8）：将客体的需求转换为对其更详细的需求的一组过程——造标尺，把需求变成规格。判据：终点止于"可实现"——"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束"（2.2）。
3. **质量**（quality，§3.6.2）：客体的一组固有特性满足需求的程度——读标尺，读出"满足到什么程度"。判据：判据主义——质量 = 特性满足需求的程度，可检验；特性超出需求范围的不是质量加分，是过度设计（1.4 / 2.3）。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 需求 | 点子 / 创意 | 表述为需求才进流程 vs 不表述就进不去 |
| 需求 | 目标 | 做成什么样 vs 为什么做 |
| 设计开发 | 走流程 | 输入输出不同（更详细）vs 输入输出一个样 |
| 设计开发 | 画图 / 创意活动 | 需求转化 vs 画图 |
| 质量 | 等级 | 满足需求的程度 vs 按哪套需求分类 |
| 质量 | 赋予特性 | 固有特性（设计开发管）vs 价格/品牌/交付时间（设计开发管不着） |
| 质量 | "计算" | 被认定（程度·形容词）vs 被计算（分数·数字） |
| 单方面砍需求 | 与相关方一起剪裁 | 偷换 vs 变更 |

### 关联概念（近界 · 辨析）

- **需要（need）/ 期望（expectation）/ 需求（requirement）**：需要 = 内容·硬性（缺了会痛），期望 = 内容·软性（缺了会失望），需求 = 需要或期望 × 呈现方式——两维交叉才是完整图景。
- **明示（stated）/ 通常隐含（generally implied）/ 必须履行（obligatory）**：三个词并列，三个都是需求，没有主次——隐含需求漏了是缺陷。
- **符合性（conformity·满足了吗·二元）/ 质量（quality·满足到什么程度·程度）/ 等级（grade·按哪套需求分类·分级）**：三个词回答三个问题，都锚定"需求"为参照。
- **需求开发（8.2）/ 设计开发（8.3）**：概念上同构（同一个 3.4.8），标准上可合可分（职责组织方式），实用判据看"特性是否被规定"。
- **设计（design）/ 开发（development）/ 设计开发（design and development）**：设计开发是 3.4.8 的完整术语，别拆成"设计+开发"两件事。
- **验证（verification）/ 确认（validation）**：验证对照"规定需求"（明示成文的），确认对照"预期用途"（真实场景）——隐含需求没进文档，验证够不着，只有确认兜得住（埋线第7章）。
- **原理可实现（层1）/ 方案可实现（层2·设计开发终点）/ 事实可实现（层3·验证确认）**：三个层次，纸面可行 ≠ 真能跑。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 需求三个词（stated / generally implied / obligatory）是并列的，三个都是需求、没有主次——隐含需求漏了是缺陷，不是"没写文档所以不算"（1.1）。
2. 需要/期望是内容，明示/隐含/必须履行是呈现方式——两个维度交叉才是需求的完整图景；把三个词糊成一个，等于把最重要的一半需求扔出视野（1.2）。
3. 目标定方向、需求定规格——目标可以激励人，需求必须可判定（1.2）。
4. 设计开发的动词是"转换"——输入输出必须是不同的东西；"更详细"是唯一判定标准，不是"更正确""更优化"（1.3）。
5. 一个项目可有多个设计开发阶段——设计开发在项目内部是递归的，每级都在执行同一个 3.4.8，直到需求足以支撑实现和验证（1.3）。
6. "更详细"不等于"更窄"——输入一句"低温设备"，输出几十条规格，是信息量的扩张（1.3 注脚二）。
7. 需求通常以特性来规定——需求不落到特性上，验证就没有对象；特性可区分 → 可测量 → 需求可验证（1.3 注脚三）。
8. 质量是"满足"（符合性判定），不是除法——两边不同质，除不了（1.4）。
9. 质量被认定出来，不被计算出来——程度可用客观证据认定，因此可以争论、可以复核、可以裁决，第一次成为工程上的一把尺子（1.4）。
10. "质量"从日常的"档次、用料"漂移到"符合需求的程度"——这一漂是本章要立的最大一个反转（1.4）。

**第二幕 · 磨边弧的机制（不是什么）**
11. 设计开发不始于点子，而始于"被研究确认过的需求"——需求（3.6.4 注 1）"通常是研究的结果"；起点没收好，转化的是错误需求，终点越完美偏离越远（2.1）。
12. 起点四闸门：完整 / 无歧义 / 不冲突 / 隐含需求已识别——一道都不能松（2.1）。
13. 需求开发与设计开发同构（同一个 3.4.8），只是转化发生在更靠前、更粗的层级；8.2 / 8.3 分条只是职责组织方式不同，两种策划都合规（2.1）。
14. 实用边界判据：特性还没开始规定，是需求开发（8.2）；特性开始被规定，才是设计开发（8.3）——需求规格就是那道闸门（2.1）。
15. "可验证"不能当设计开发终点——验证的参照是规定需求（设计开发的输出），拿"可验证"当终点等于让设计开发结束在验证的起跑线上，循环倒置；且几乎所有写清楚的需求都可验证，判据区分不了完成与未完成（2.2）。
16. 设计开发止于"可实现"——需求被细化到足以支撑客体实现、生产和服务提供可直接执行的程度；终点由"最后一个配齐的方案"决定，不由"第一个完成的技术方案"决定（2.2）。
17. 八方案是一个东西的八个面向——技术 / 物料采购 / 制造（工艺）/ 测试 / 交付 / 部署 / 操作 / 运维，每个方案是给一个下游环节的"可实现需求"（2.2）。
18. 只到技术方案就宣布终点，后果是连环空转——采购、制造、测试、交付/部署/操作/运维全部空转（2.2）。
19. 设计开发交付的不是事实，而是声明——一份"可信的可实现声明"；守住"诚实边界"，别把"我们觉得能做"当成"我们做完了"（2.2）。
20. 等级高 ≠ 质量好——高档车可以是差质量，低档车可以是好质量；因为等级是"按不同需求分类"，质量是"满足各自需求的程度"（2.3）。
21. 特性超出需求范围的，不是质量加分，是过度设计——只加成本，不加质量；砍过度设计是唯一"既省时间又不伤质量"的操作（2.3）。
22. 概念靠正例活、靠反例定型——每条边都有一条可检验的判据在收口（判据主义）（2.3）。

**第三幕 · 往哪去的机制（运用）**
23. 质量"程度"三步得出法：确定特性值（3.11.1）→ 与需求比对（3.6.11）→ 认定满足程度（3.6.2）——工具在 3.11、标尺在 8.3.5（接收准则）、动作在 3.8.12 / 3.8.13，一步不缺程度才出得来（3.1）。
24. 单项是二元（符合/不符合），整体是程度（差/好/优秀）——整体程度按特性重要度综合评价，关键特性优先（8.3.5 d）（3.1）。
25. 接收准则让"质量好"从一句感觉变成一次可复核的认定——没有接收准则，质量永远只能"感觉"，不能"认定"（3.1）。
26. 标准层面质量没有单点分值——特性多维不同质、加不成一个数；隐含需求无法完整数值化；注 1 明确质量用形容词修饰（3.2）。
27. 打分 = 定权重 → 单项评分 → 加权汇总，三个前提缺一个分就是假的；最要命的是关键特性不能被摊平——加权把安全性、可靠性这种一票否决的特性摊进平均数，是"一个精确的错误"（3.2）。
28. 质量 vs 进度不是两个系统拔河，是同一份需求集合内部打架——进度本身就是一种需求（ISO 9001 §8.2.2 交付时间和交付条件也是顾客要求的一部分）（3.3）。
29. 解法不是二选一，是重新平衡需求集合：判真伪 → 用需求谈判不用质量谈判（走正式变更）→ 分清可妥协与不可妥协 → 度量环节可缩不可砍（3.3）。
30. 口头"差不多就行"是最危险的变更形式——需求被悄悄偷换，验证确认全在跟一个没被承认的靶子打（3.3）。
31. 砍验证/确认赶进度最贵——等于不度量就宣布合格，风险全部后移成现场返工（失败成本是质量成本里最贵的）（3.3）。
32. 单方面砍需求叫偷换，和顾客一起剪裁才叫变更——需求的所有权在相关方手里；剪裁的正确动作是"排序"不是"删减"；剪下来的需求是"挂账"不是消失（3.3）。
33. 进度冲突是隐含需求的显影剂——平时问"你还有什么要求"他答不出，你说"进度不够，必须砍一样"他立刻知道答案（3.3）。
34. 三兄弟互为定义、拆不掉——设计开发引用需求，质量引用需求和特性；需求与质量是"元概念"，设计开发是架在中间的桥（3.4）。
35. "每一个为什么都能从三角推出来"是基座的终极检验——V 模型为什么是 V、IPD 为什么有 TR、为什么需求要追溯矩阵、为什么变更要控制（3.4）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "参数比竞品高，质量绝对没问题。"（等级当质量）
2. "技术方案做完了，设计开发就结束了。"（漏七个方案，不知终点是可实现）
3. "客户没写进合同，就不用做。"（隐含需求漏了是缺陷）
4. "质量进度冲突，砍掉测试先上线，后面再补。"（砍验证赶进度）
5. "把'成为行业第一'写进需求规格，设计开发就知道怎么做了。"（目标当需求）
6. "质量 85 分，客观、精确，就是结论。"（关键特性被摊平）
7. "需求开发是需求的事，设计开发是画图的事，两不相干。"（特性是否被规定）
8. "质量 = 东西做得比人强、指标压过竞品。"（质量 = 指标碾压）
9. "需求 = 用户说出来的话。"（需求 = 明示）
10. "需要/期望/需求一个意思，糊着用。"（三词糊成一）
11. "设计开发做完 = 东西就能跑起来。"（方案可实现 = 事实可实现）
12. "多给三个月，质量就自动变好。"（质量是时间的函数）
13. "质量 vs 进度只能二选一：保质量砍进度，或保进度降质量。"（两系统拔河）
14. "口头改需求最方便，散会说定了就行。"（口头变更偷换需求）
15. "和客户一起砍需求，就是降低质量。"（剪裁 = 降质量）
16. "质量 = 档次高、用料好。"（词源漂移残留）
17. "设计开发交付的是能跑的东西。"（声明 = 事实）
18. "改个颜色/改个界面，不算变更，直接改就行。"（输入输出同样详细 = 没发生设计开发——此条本身对，陷阱在"一切改动都算设计开发"）
19. "八方案是八件独立的事，技术方案最重要，做完它就看得到终点。"（把八方案当并列清单，终点看技术方案）
20. "砍需求 = 把需求从清单上划掉，划掉的就没了。"（剪裁 = 销毁，不是挂账）

### 重要分界

- **起点分界（需求 × 设计开发）**：特性是否被规定——需求规格是那道闸门。
- **终点分界（设计开发 × 质量）**："可实现"——还有哪个环节反问"这到底怎么做"。
- **参照分界（需求 × 质量）**：等级 ≠ 质量 ≠ 符合性——超出需求区的特性是过度设计。

### 落点

- 反直觉命题①：设计开发止于可实现（终点边界）。
- 反直觉命题②：等级 ≠ 质量（参照边界）。
- 方法底座时刻：**判据主义**（质量 = 满足需求的程度，可检验；设计开发止于可实现，可检验）。

### 重要度分层

- **核心（必须脱口）**：三定义（需求 / 设计开发 / 质量）、三判据（可转化 / 可实现 / 程度三步）、等级 ≠ 质量、过度设计、质量 vs 进度 = 需求集合内部打架。
- **重要（能解释）**：三形态并列、内容 × 呈现方式两维图景、特性是否被规定、八方案、可验证循环倒置、85 分陷阱、与相关方一起剪裁（排序 / 留痕 / 挂账）。
- **知道即可**：词源溯源（拉丁 requirere / designare / qualitas）、ISO 条款号、设计开发递归链。

### 本章判据（十把尺子）

1. **起点判据**：需求"可转化"——完整、无歧义、不冲突、隐含需求已识别；起点没收好，转化的是错误需求，终点越完美偏离越远。
2. **需求开发/设计开发边界判据**：特性是否被规定——特性还没开始规定是需求开发（8.2），特性开始被规定才是设计开发（8.3）。
3. **终点判据**：设计开发止于"可实现"——"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束"；终点由最后一个配齐的方案决定。
4. **质量判据**：质量 = 特性满足需求的程度，可检验；特性超出需求范围 = 过度设计，只加成本不加质量；砍过度设计是唯一既省时间又不伤质量的操作。
5. **等级 ≠ 质量 ≠ 符合性判据**：一个回答"按哪套需求分类"、一个回答"满足到什么程度"、一个回答"满足了吗"；高档车可以是差质量。
6. **读标尺判据**：程度三步（确定特性值 → 与需求比对 → 认定满足程度）；接收准则让质量从"感觉"变"认定"。
7. **分值判据**：关键特性不能被摊平——安全/可靠这类一票否决特性要么设"一票否决"，要么用加权不用平均，否则那个分数是"一个精确的错误"。
8. **冲突解法判据**：判真伪 → 用需求谈判不用质量谈判（走正式变更 8.2.4 / 8.3.6）→ 分清可妥协与不可妥协 → 度量可缩不可砍。
9. **变更判据**：单方面砍需求叫偷换，和顾客一起剪裁才叫变更——排序、留痕、挂账；剪裁是暂存，不是销毁。
10. **基座判据**：定标尺 → 造标尺 → 读标尺；需求与质量是元概念，设计开发是架在中间的桥；"每一个为什么都能从三角推出来"是基座的终极检验。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"需求"（明示的、通常隐含的或必须履行的需要或期望），并给三种形态各举一个 M3 例子。
2. 能辨析 需要（内容·硬性）/ 期望（内容·软性）/ 需求（需要或期望 × 呈现方式）。
3. 能辨析 需求 ≠ 目标（目标回答"为什么做"，需求回答"做成什么样"；目标激励人，需求必须可判定）。
4. 能定义"设计开发"（将客体的需求转换为对其更详细的需求的一组过程）并拆出四构件（客体 / 需求 / 转换为 / 更详细）。
5. 能辨析 设计（阶段）/ 开发（阶段）/ 设计开发（完整过程，3.4.8 不拆两件事）。
6. 能辨析 需求开发（8.2）/ 设计开发（8.3）——边界判据"特性是否被规定"。
7. 能定义"质量"（客体的一组固有特性满足需求的程度）并拆出三关键词（固有 / 满足 / 程度）。
8. 能辨析 符合性（二元）/ 质量（程度）/ 等级（分级）——三个词回答三个问题。
9. 能说出"设计开发止于可实现"的判定话术（还有哪个环节反问"这到底怎么做"）。

### 原理层（应能解释为什么）

1. 能解释为什么需求三种形态并列、无主次（隐含需求漏了是缺陷，不是"没写文档所以不算"）。
2. 能解释为什么需要/期望是内容、三形态是呈现方式、两维交叉才是完整图景（糊成一个 = 扔出视野一半）。
3. 能解释为什么设计开发输入必须是需求不是点子（需求"通常是研究的结果"；起点没收好，终点越完美偏离越远）。
4. 能解释为什么"更详细"是唯一判定标准（不是更正确更优化；方案优劣由评审和验证把关）。
5. 能解释为什么设计开发是递归的（一个项目可有多个设计开发阶段，每级执行同一个 3.4.8）。
6. 能解释为什么"可验证"不能当设计开发终点（循环倒置：验证的参照是规定需求 = 设计开发的输出）。
7. 能解释为什么终点由"最后一个配齐的方案"决定（八方案是一个东西的八个面向，只到技术方案 = 连环空转）。
8. 能解释为什么设计开发交付的是声明不是事实（诚实边界：把"我们觉得能做"和"我们做完了"分开）。
9. 能解释为什么等级高 ≠ 质量好（等级 = 按哪套需求分类，质量 = 满足各自需求的程度）。
10. 能解释为什么特性超出需求范围是过度设计（只加成本不加质量；砍过度设计是唯一既省时间又不伤质量的操作）。
11. 能解释为什么质量被认定、不被计算（程度是形容词不是数字；客观证据可复核可裁决）。
12. 能解释为什么标准层面不给质量打单点分值（特性多维不同质 / 隐含需求无法完整数值化 / 注 1 用形容词修饰）。
13. 能解释为什么关键特性不能被摊平（加权平均掩盖一票否决特性 = "一个精确的错误"）。
14. 能解释为什么质量 vs 进度是需求集合内部打架（进度本身就是一种需求，ISO 9001 §8.2.2）。
15. 能解释为什么口头改需求最危险（需求被偷换，验证确认打一个没被承认的靶子）。
16. 能解释为什么单方面砍需求叫偷换、一起剪裁才叫变更（需求所有权在相关方；剪裁=排序/留痕/挂账）。
17. 能解释为什么剪下来的需求是"挂账"不是"消失"（本轮进度解了，下轮迭代是现成输入）。
18. 能解释为什么进度冲突是隐含需求的显影剂。
19. 能解释为什么三兄弟互为定义拆不掉（定标尺 → 造标尺 → 读标尺；需求/质量是元概念、设计开发是桥）。
20. 能解释为什么"每一个为什么都能从三角推出来"是基座的终极检验。

### 判据层（应会用）

1. **起点判据**：需求"可转化"四闸门——完整 / 无歧义 / 不冲突 / 隐含需求已识别；起点没收好，转化的是错误需求。
2. **需求开发/设计开发边界判据**：特性是否被规定——特性还没开始规定是需求开发（8.2），特性开始被规定是设计开发（8.3）。
3. **终点判据**：设计开发止于"可实现"——"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束"；终点由最后一个配齐的方案决定。
4. **质量判据**：质量 = 特性满足需求的程度，可检验；特性超出需求范围 = 过度设计，只加成本不加质量。
5. **等级≠质量≠符合性判据**：三个词回答三个问题（按哪套需求分类 / 满足到什么程度 / 满足了吗）。
6. **读标尺判据**：程度三步（确定特性值 → 与需求比对 → 认定满足程度）；接收准则让质量从"感觉"变"认定"。
7. **分值判据**：关键特性不能被摊平——一票否决或加权不平均，否则 85 分是"一个精确的错误"。
8. **冲突解法判据**：判真伪 → 用需求谈判（走正式变更 8.2.4 / 8.3.6）→ 分清可妥协不可妥协 → 度量可缩不可砍。
9. **变更判据**：单方面砍需求叫偷换，和顾客一起剪裁才叫变更——排序、留痕、挂账。
10. **基座判据**：定标尺 → 造标尺 → 读标尺；能推出全部现有方法 = 基座。

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 质量 = 特性满足需求的程度（判据主义，可检验） | 1 / 8 / 15 / 16 | 脱口报出定义 + "超出需求区 = 过度设计" |
| ★2 | 设计开发止于"可实现"（终点判据 + 八方案） | 2 / 11 / 17 / 19 | 脱口报出判定话术 + 八个方案名 |
| ★3 | 等级 ≠ 质量 ≠ 符合性（三词回答三个问题） | 1 / 8 / 15 / 16 | "高档车可以是差质量"随口举例 + 三问各答 |
| ★4 | 质量 vs 进度 = 需求集合内部打架（进度是需求） | 12 / 13 | "进度本身是需求"成为口头禅 |
| ★5 | 三形态并列 + 两维交叉（需要/期望/需求） | 3 / 9 / 10 | 脱口报出三形态 + 内容 × 呈现方式 |
| ★6 | 与相关方一起剪裁（排序 / 留痕 / 挂账） | 15 / 17 / 20 | "单方面砍 = 偷换，一起剪 = 变更" |
| ★7 | 特性是否被规定（需求开发/设计开发边界） | 7 / 18 | "特性开始被规定，才是设计开发" |
| ★8 | 关键特性不可摊平（85 分陷阱） | 6 | "一票否决 vs 平均"当场能算 |
| ★9 | 可验证是循环倒置 + 声明 ≠ 事实 | 2 / 11 / 17 | "验证的参照是设计开发的输出" |

### 纠错红线十条

1. **先表态后翻案**：先让学员说出"质量绝对没问题，这还用讨论吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："等级 ≠ 质量"别翻成"等级不重要"；"验证可缩不可砍"别翻成"验证永不缩"；"更详细是唯一判据"别翻成"方案好坏不用评审"。
3. **判据配机制**：每条反转都有"为什么"（机制）和"怎么当场验证"（判据）。
4. **归责到可对照动作**："设计没做完"落到"采购问不出型号准则 / 小赵要不到测试判据"这种可对照动作，不归咎"团队不行"。
5. **教机制不教断言**：教"为什么超出需求区不加质量"，不教"参数越高越不好"。
6. **先立尺子再翻案**：先给判据主义三问（是什么 / 失效边界 / 反例），再翻章首"质量绝对没问题"。
7. **拉开强度层次**：★★★ 常识（参数高 = 质量好 / 技术方案完 = 设计完 / 砍测试赶进度 / 口头改需求）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（如给测试方案补接收准则、列八方案对照表）。
9. **单一权威不另立标准**：判据引用书（本章判据十条）+ ISO 9000/9001 条款，不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是我一个人说的"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给一次"三基座体检"（定标尺 → 造标尺 → 读标尺走一遍）

> 目标：用本章三把尺子，给自己手头一个进行中的产品/项目做一次"三基座体检"，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **定标尺（起点判据）**：把当前项目"要什么"的需求规格拿出来，过"可转化"四闸门——完整？无歧义？不冲突？隐含需求已识别？**最弱的一条记下来**。
2. **画边界（特性是否被规定）**：判断手头这份工作是需求开发还是设计开发——特性开始被规定了吗？没被规定，说明还在 8.2，没到设计开发。
3. **造标尺（终点判据）**：把八个方案（技术 / 物料采购 / 制造·工艺 / 测试 / 交付 / 部署 / 操作 / 运维）列一张表，逐项打勾；**问一句"还有哪个环节会在执行时反问'这到底怎么做'？"** 有，设计开发就没结束。
4. **读标尺（程度三步）**：找出测试方案里有没有接收准则——用什么设备测、测多久、抽多少样本、判定结论写在哪份记录。**没有 = 质量只能"感觉"，不能"认定"。**
5. **查关键特性（85 分陷阱）**：把 8.3.5 d 说的"对预期目的至关重要的特性"列出来，确认它们没被加权平均摊平——该一票否决的一票否决。
6. **解冲突（与相关方一起剪裁）**：如果进度亮红灯，用需求谈判不用质量谈判——找相关方排优先级：命根子（不可动）/ 可降的 / 可砍的；走正式变更，砍下来的**挂账留痕**。

**卡住怎么判断**：找不到接收准则 = 从第 4 步补起；答不上"到底怎么做" = 从第 3 步补起；说不清隐含需求 = 从第 1 步补起。不用全做完——找到第一个"没有"就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 需求规格过了"可转化"四闸门？ | □ | 起点没收好——转化的是错误需求，终点越完美偏离越远 |
| 隐含需求有主动识别记录？ | □ | 隐含需求漏了是缺陷，不是"没写文档所以不算" |
| 特性开始被规定 = 已进入设计开发？ | □ | 8.2 vs 8.3 边界不清——需求规格就是那道闸门 |
| 八方案逐项可执行（执行时不反问"怎么做的"）？ | □ | 设计开发还没结束——还有环节在等判据 |
| 技术方案是唯一完成的方案吗？ | □ | 连环空转的前兆——采购/制造/测试/交付都在空转 |
| 测试方案里有接收准则？ | □ | 质量只能"感觉"，不能"认定" |
| 关键特性没被加权平均摊平？ | □ | 那个分数是"一个精确的错误" |
| 进度冲突走的是正式变更（书面/评审/留痕）？ | □ | 口头"差不多就行"在偷换需求 |
| 砍需求是和相关方一起剪裁（排序/挂账）？ | □ | 单方面砍 = 偷换，不是变更 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（见树见林① · 概念本身 · 章首误解现场破题）**
"冰链的评审会上，小林指着参数表说：'我们 M3 温度精度 ±0.3℃、竞品 ±0.5℃；保温 72 小时、竞品 48 小时；重量还轻 2 公斤。质量绝对没问题。'——质量是什么？按 ISO 9000 的定义拆开讲。他说的是'质量'吗？"
追问：① 质量定义的三个关键词（固有 / 满足 / 程度）各管什么？② ±0.3℃ 超出需求 ±0.5℃ 的那 0.2℃，在质量上是什么（过度设计）？③ 反身：你最近一次说"质量没问题"，依据的是什么——需求，还是参数？

**Q2（见树见林② · 概念关系）**
"请画一张三角图，标出 需求、设计开发、质量 三个词和它们之间的三条边（起点 / 终点 / 参照），并说明：为什么这三个词互为定义、拆不掉？"
追问：① 三条边各是什么判据（可转化 / 可实现 / 程度三步）？② 哪个词是元概念、哪个是桥（需求/质量是元概念，设计开发是架在中间的桥）？③ 反身：你们部门的"设计完成"怎么判定？是技术方案做完，还是八方案齐备？

**Q3（真悖论 · 等级 vs 质量）**
"'高档车可以是差质量，低档车可以是好质量'——这句话是不是自相矛盾？好车怎么质量差？"
追问：① 等级和符合性各回答什么问题（按哪套需求分类 / 满足了吗）？② 把精度做到行业第一，对 M3 的质量贡献了什么（超出需求区 = 只加成本不加质量）？③ 反身：你们把"指标比竞品高"当绩效，还是当过度设计？

**Q4（真悖论 · 终点在验证之前）**
"有人主张设计开发结束于'可验证'——需求写清楚了就能验证了，不就完了吗？但书里说这是'循环倒置'。为什么？那设计开发到底到什么时候算完？"
追问：① 验证的参照是什么（规定需求 = 设计开发的输出）？② 如果"可验证"当终点，怎么区分完成与未完成（几乎所有写清楚的需求都可验证）？③ 八个方案里，为什么是测试方案最难补齐——它把"感觉"变成"认定"？

**Q5（真悖论 · 质量 vs 进度）**
"'质量 vs 进度'是一场冲突吗？保质量就要砍进度，保进度就要降质量——真的是二选一吗？"
追问：① 为什么说进度本身就是一种需求（ISO 9001 §8.2.2 交付时间也是顾客要求）？② 那"冲突"到底是什么在打（同一份需求集合内部打架）？③ 解法为什么不砍质量、而用需求谈判（砍过度设计 = 既省时间又不伤质量）？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 需求开发 vs 设计开发边界）**
"你们公司一个正在进行的工作：市场调研在整理需求、研发在出方案。用'特性是否被规定'这条判据，各自属于需求开发（8.2）还是设计开发（8.3）？边界画在哪？"
追问：① 需求规格就是那道闸门——它的位置在哪？② 把调研文档排除在受控范围外，会出什么事（不能不受控、不可追溯；M3 立项调研无存档，七周返工连"当时为什么这么做"的记录都没有）？③ 反身：你们最近一次"设计得辛苦、产品没人要"，是终点没管好还是起点没收好？

**Q7（判据运用 · 方法时刻题 · 规则 15 · 判据主义）**
"这一章的方法底座时刻是判据主义——不给没有判据的定义。请亲手给'设计开发终点'和'质量好不好'各立一条可检验判据，再用它当场裁一个你们最近的项目。"
追问：① 你的判据符合判据主义三问吗（是什么 / 失效边界 / 反例）？② 终点判据：还有哪个环节会在执行时反问"这到底怎么做"？③ 反身：把这条判据量到你自己头上——你上次宣布"设计完成"，是依据判据，还是依据感觉？

**Q8（判据运用 · 程度三步 + 85 分陷阱）**
"小赵给 M3 打了 85 分——温度控制 92、保温 88、外壳做工 90、重量 70，平均。老周说这是'一个精确的错误'。为什么平均就是错误？那'程度'到底怎么认定？"
追问：① 程度三步（确定特性值 → 与需求比对 → 认定满足程度）哪一步被跳过了？② 关键特性（断电告警）为什么不能摊进平均数（8.3.5 d 一票否决）？③ 反身：你们最近一次质量评审，结论是"程度"还是"分数"？判据是什么？

**Q9（判据运用 · 与相关方一起剪裁）**
"M3 进度亮红灯，小林找疾控中心刘主任砍需求。刘主任三十分钟排完序：断电告警和箱门单手开不能砍、实时推送可降级、重量减 2 公斤是销售吹的可以砍。为什么'砍需求'和'单方面砍需求'是两件完全不同的事？"
追问：① 需求的所有权在谁手里（相关方——需求是顾客的资产，组织只是受托转化）？② 剪下来的需求为什么是"挂账"不是"消失"？③ 反身：你们最近一次砍需求，是"和顾客一起剪裁"还是"单方面砍掉"？走了正式变更吗？

**Q10（落地生根 · 回部门三基座体检）**
"结合你们部门现状，挑一个进行中的项目，用三把尺子（定标尺 / 造标尺 / 读标尺）做一次体检——给出最该做的三件事，每件落到一个动作。"
追问：先查哪把尺子？为什么？两周后回来报告什么（哪把尺子补上了、哪把还虚着）？
