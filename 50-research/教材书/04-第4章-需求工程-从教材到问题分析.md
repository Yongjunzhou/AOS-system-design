## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：标尺从哪来？需求工程把模糊的诉求变成可靠的依据——需求开发负责"生"（造血）、需求管理负责"养"（防腐），两者并列构成需求工程；先立问题域（ConOps），再写条款（SRS）。"需求是开发出来的，不是管出来的。"

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：1.1 一个定义两大过程 → 1.2 为什么并列不是包含 → 1.3 术语不混用 → 1.4 需求开发（造血，四活动循环）→ 1.5 规格与规定需求（SRS 六章、验证与确认）→ 1.6 需求管理（防腐，四活动、变更控制闭环、基线、RMP）→ 案例进展①②—— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：2.1 需求 ≠ 规定需求（说了不等于规定）→ 2.2 验证 ≠ 确认 → 2.3 需求变了 ≠ 当初没说清（欠账二分）→ 2.4 改名留档 ≠ 版本管理（"另存为 v2"）→ 案例进展③—— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：3.1 为什么需要 ConOps → 3.2 ConOps 的位置（分析之后、规格之前）→ 3.3 ConOps 六部分（IEEE 1362）→ 3.4 需求质量六性 → 3.5 骨架五份与文档体系 → 案例进展④—— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **需求工程**（requirements engineering）：需求开发 + 需求管理（总称，两大子过程**并列**）——开发管"生"（创造性·造血），管理管"养"（控制性·防腐）。判据：能说清"生/养"分工吗？两者并列而非包含吗？需求是开发出来的，不是管出来的。
2. **需求开发**（requirements development）：把需要与期望**转化**为规定需求——获取、分析、规格、确认（四活动**循环**），管"生"。
3. **需求管理**（requirements management）：对规定需求进行**基线化受控**——基线、变更、追溯、状态度量，管"养"。变更控制是核心战场。
4. **规定需求**（specified requirement）：被明示的、以成文信息记录的需求（ISO 9000:2015 §3.6.4 注 2）——**验证的参照**。判据：能设计测试证明 → 是规定需求；只能"感觉" → 还不是。
5. **运行概念 ConOps**（concept of operations）：需求工程里**唯一一份"叙事性"的正式输出**——回答"系统怎么被用"（IEEE 1362）。判据：让一个不熟悉系统的人读完，能画出流程图。
6. **需求管理计划 RMP**（requirements management plan）：项目级"怎么管需求"的执行计划（程序文件的项目版），六模块。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 需求工程 | 需求管理 | 需求工程 ⊃ 需求开发、需求管理；需求工程 ≠ 需求管理（并列不是包含） |
| 需求开发 | 需求管理 | 创造（造血） vs 控制（防腐）；"生" vs "养" |
| 规定需求 | 口头明示 | 说了不等于规定；验证需要能对账的靶子 |
| 验证 | 确认 | 对照规定需求（表述对不对） vs 对照预期用途（是不是要的） |
| ConOps | SRS | 讲"故事"（怎么被用） vs 讲"条款"（必须做什么）；问题域 vs 解空间 |
| 版本管理 | 改名留档 | 有基线/变更控制/追溯 vs 只做到留档（"另存为 v2"） |
| 需求工程 | 写需求文档 | 开发+管理是活动，文档是载体 |

### 关联概念（近界 · 辨析）

- **需求工程 ⊃ 需求开发 + 需求管理（并列关系结构）**——这是全书又一个"词汇病"现场（第1章补充区的诊断在这里复发）；流行说法"广义的需求管理包含需求开发"把两类本质不同的活动（创造 vs 控制）揉成一团。
- **明示 ⊃ 规定**：所有规定需求都明示过，但口头明示 ≠ 规定（成文+具体+可验证）——"页面要快一点"无法验证。
- **验证 vs 确认**（近界最像但不同）：验证对照规定需求、确认对照预期用途；隐含需求是"必须分开"最深的原因。
- **ConOps 辨析**：不是运营手册（不含运维操作细节）、不是需求清单（是运行叙事）、不是系统设计（不落入解空间）。
- **SRS 六章 ↔ 第3章 §2.1**：第3章说"特性开始被规定，才是设计开发（8.3）"；本章 SRS 是需求侧把需要写成可验证条文（规定需求）——两道闸门不是同一道，SRS 是需求开发与设计开发的边界文档。
- **需求质量六性 ↔ 第3章起点判据四闸门**：四闸门（完整/无歧义/不冲突/隐含需求已识别）是六性在"设计输入"场景的收缩——不冲突≈一致、隐含⊂完整，六性另补可验证/可追溯/有优先级。
- **需求侧"分解"（第6章同构）↔ 设计侧"分解"**：把父需求拆成子需求是第6章"分解"在需求侧的同构动作——注意与设计侧"分解"区分。
- **基线（第12章配置管理展开）**：基线 = 被批准冻结、作为全生命周期参照的配置信息；"另存为 v2"第12章以 final_2.zip 回声。
- **隐含需求（第7章全展开）**：挖出来显性化写进规格、变成规定需求，否则验证够不着它。
- **与相关方剪裁需求（第3章）↔ 排序（MoSCoW/Kano）**：需求不够时砍哪条保哪条靠排序结果。
- **口头改需求（第3章已讲最危险）↔ 没有凭证的变更**：落到文档层面就是"变更日志只追加不修改"。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 需求工程配得上"工程"二字，因为它占全了工程化的六个方面——有结构、有方法、可重复、全覆盖、受控、可验证（1.1）。
2. 需求开发与需求管理是并列不是包含——把创造（收集/分析/建模/写规格）包进控制（冻结/变更/追溯/跟踪），模糊"需求是开发出来的，不是管出来的"（1.2）。
3. 开发欠账是"源头脏"，管理欠账是"过程乱"——先清源（开发）再修渠（管理），顺序不能反；管理再严，来源没摸清、分析没做透，一样出烂需求（1.2）。
4. 需求开发四活动是循环不是直线——"模糊的诉求"不会一次被看清，每一步都可能推翻前一步的假设；需求天然是渐进的（1.4）。
5. 获取的判据只有一条：每条需求有没有来源——"无来源需求不得入需求池"（1.4）。
6. 分析是"第一道加工"，四件具体的事：澄清 / 需求分解 / 排序 / 协商冲突——每项都有可检验的产出（1.4）。
7. 需求缺陷成本：同一缺陷需求阶段修复为 1，发布后修复为 30~70 倍——每分投入给下游省十倍百倍返工钱（1.4）。
8. 规定需求是验证的参照——没有它，验证（verification）无从谈起；"说了"不等于"规定"（成文+具体+可验证）（1.5）。
9. 验证对照规定需求、确认对照预期用途，必须分开——把需求写得很正确、但完全不是用户要的，是需求开发最常见的失败（1.5/2.2）。
10. 只验证不确认 = 写得很漂亮但没人要；只确认不验证 = 用户要的但没法执行——两道关，缺一不可（1.5/2.2）。
11. 隐含需求不会自己开口——要主动去挖；挖出来显性化写进规格变成规定需求，否则验证够不着它，只有确认（真实场景）兜得住（案例进展②）。
12. 需求管理四活动不是均分——变更控制是核心战场，基线是它的前提，追溯是它的地图，状态度量是它的仪表盘（1.6）。
13. 变更控制三铁律：无 CR 不得变更；不分析不得上会；验证通过方可关闭——每一步都要"可判定"，否则流程就是摆设（1.6）。
14. 基线是分界线——线左是需求开发的产物（还在流动），线右进入需求管理（一切改动走变更控制）；基线是"变更的出发原点"（1.6）。
15. 基线和追溯是一体两面——没有基线，追溯无从谈起；没有追溯，基线一建立就失效（1.6）。
16. 需求开发与需求管理的接口咬合在"批准 → 基线"处——铰链不咬合，开发和管理各管一段，需求就会在中间断层（1.6）。
17. 口头改需求是最危险的变更形式（第3章已讲）——落到文档层面就是"没有凭证的变更"；变更日志只追加不修改（1.6）。

**第二幕 · 磨边弧的机制（不是什么）**
18. 验证需要一个能对账的靶子，口头表述对不了账——"快一点"是几秒？"好用"怎么证明？（2.1）。
19. 隐含需求是"必须分开验证与确认"最深的原因——验证（对照规定需求）照不到没显性化的隐含需求，只有确认（真实场景）兜得住（2.2）。
20. 欠账二分判据：需求"总在变"时先分清是"需求变了"（管理漏洞）还是"当初没说清"（开发欠账）——答错了病，药就开错了（2.3）。
21. 改名留档 ≠ 版本管理——版本管理要有基线（批准的参照）、变更控制（怎么变、谁批）、追溯（从哪变起、波及谁）三样；"另存为 v2"只做到留档（2.4）。

**第三幕 · 往哪去的机制（运用）**
22. 条款需要上下文——ConOps 是 SRS 的上下文；没有它，SRS 的每一条都像悬空条款（3.1）。
23. ConOps 在分析之后、规格之前——ConOps 的完整定稿必须建立在已经摸清需要的基础上；跳过 ConOps 直接写 SRS，等于从"问题域"直接跳到"解空间"（3.2）。
24. ConOps 是问题域的枢纽骨架，SRS 条款是挂上去的细节——先扎进条款、不立骨架，条款越多越悬空（LeafToHub）（3.2/案例进展④）。
25. ConOps 六部分（引言/系统概述/运行环境/运行场景/干系人与角色/运行支持），运行场景是核心——正常/异常/应急三种（3.3）。
26. ConOps 判据：让一个不熟悉系统的人读完，能画出审批流程图——画得出来合格，画不出来故事没讲清楚（3.3）。
27. 需求质量六性互相支撑——无歧义是可验证的前提，可验证是规定需求的门槛，可追溯是变更影响分析的地图，有优先级是"与相关方剪裁需求"的操作基础（3.4）。
28. 六性里最常被牺牲的往往是"可追溯"——它不立刻显形，直到需求变更时才答不上"这条为什么加、影响谁"（3.4）。
29. 骨架五份不可省——没有文档的环节，就是不可追溯的环节；裁掉文档不是省事，是把追溯链砍断（3.5）。
30. RTM 的终极检验：任取一条需求，能不能双向走通——往上游知道从哪来，往下游知道影响谁（3.5）。
31. 编号不是目的，可引用才是——"这条需求在哪个文档、哪一条"要能指到具体位置，否则追溯就是空谈（3.5）。
32. 需求规格的问题，往往要到 ConOps 里才看得出来——恒信三百条 SRS 悬空，一半需要改写，因为先写条款后补故事，顺序反了（案例进展④）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "需求管理包含需求开发，管好需求自然就开发好了。"（附录 C 第4行）
2. "需求乱 = 管理没跟上；加强需求管理 = 往流程上加东西。"
3. "需求工程 = 写需求文档。"
4. "客户说了'页面要快一点'，这就是需求。"（明示但未规定）
5. "验证和确认是一回事，都是确认需求没问题。"
6. "需求变更多，说明需求管理没做好。"
7. "版本文件名改一改（另存为 v2），就是需求管理/版本管理。"
8. "ConOps 是给运营部门看的故事，跟开发没关系。"
9. "需求分析就是开会讨论一下需求。"
10. "写需求文档就是抄用户的话。"
11. "隐含需求会自己冒出来，客户没提就是没有。"
12. "需求开发四活动一次跑完就完。"
13. "口头改需求没关系，大家心里有数。"
14. "小项目不需要 SRS/RTM/基线这些文档。"
15. "有需求文档、有版本号 = 需求工程做得好。"
16. "先写 SRS 条款，上下文后面再补，顺序无妨。"

### 本章判据（八把尺子）

1. **需求工程 = 需求开发 + 需求管理**（并列）——开发管"生"（创造·造血），管理管"养"（控制·防腐）；需求是开发出来的，不是管出来的。
2. **规定需求 = 验证的参照**——被明示的、成文的需求；不能设计测试证明的，还不是规定需求（说了 ≠ 规定）。
3. **验证对照规定需求，确认对照预期用途**——"写对了吗" vs "是要的吗"，必须分开；两道关缺一不可。
4. **欠账二分**——需求"总在变"时，先分清是"需求变了"（管理漏洞）还是"当初没说清"（开发欠账）；先清源（开发）再修渠（管理），顺序不能反。
5. **ConOps 在分析之后、规格之前**——先讲清系统怎么被用（问题域），才谈得上必须做什么（解空间条款）。
6. **无 CR 不得变更，不分析不得上会，验证通过方可关闭**——变更控制三铁律。
7. **改名留档 ≠ 版本管理**——版本管理要有基线、变更控制、追溯；没有基线，变更就不可言说。
8. **骨架五份不可省**：SRS、需求池、RTM、评审报告、基线。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"需求工程"（= 需求开发 + 需求管理，总称，两大子过程**并列**），并说出开发管"生"（创造·造血）、管理管"养"（控制·防腐）。

3. 能定义"需求管理"（对规定需求进行**基线化受控**——基线/变更/追溯/状态度量），并说出四活动各解决什么问题。
4. 能辨析 需求工程 ⊃ 需求开发、需求管理 vs 需求工程 ≠ 需求管理（并列不是包含；"广义需求管理包含需求开发"错在哪）。
5. 能定义"规定需求"（被明示的、以成文信息记录的需求——验证的参照），并辨析 明示 ⊃ 规定（口头明示 ≠ 规定；成文+具体+可验证）。
6. 能定义"运行概念 ConOps"（需求工程里唯一一份"叙事性"的正式输出——回答"系统怎么被用"，IEEE 1362），并辨析 ConOps vs SRS（故事 vs 条款）、ConOps ≠ 运营手册/需求清单/系统设计。
7. 能定义"需求管理计划 RMP"（项目级"怎么管需求"的执行计划，程序文件的项目版），并说出六模块（目的范围/角色职责/需求组织规则/基线策略/变更控制流程/追溯与度量安排）。
8. 能说出 SRS 六章骨架（引言/总体描述/功能需求/非功能需求/外部接口/验证方法），并说明"验证方法"一章为什么最容易被砍却正是"可验证"的落点。
9. 能辨析 requirement/need/expectation/specified requirement 四词（需求/需要/期望/规定需求）。
10. 能说出需求质量六性（完整/一致/无歧义/可验证/可追溯/有优先级）。
11. 能说出骨架五份文档（SRS/需求池/RTM/评审报告/基线）及各司其职。
12. 能说出变更控制闭环（CR→影响分析→CCB 评审→实施→再验证→关闭），并说出三铁律。
13. 能辨析 需求侧"分解"（第6章在需求侧的同构动作）vs 设计侧"分解"。

### 原理层（应能解释为什么）

1. 能解释为什么需求工程配得上"工程"二字（工程化六方面：有结构/有方法/可重复/全覆盖/受控/可验证）。
2. 能解释为什么开发与管理是并列不是包含（把创造包进控制，模糊"需求是开发出来的，不是管出来的"）。
3. 能解释为什么"先清源（开发）再修渠（管理）"顺序不能反（源头脏 vs 过程乱；给脏水修渠没用）。
4. 能解释为什么需求开发四活动是循环不是直线（"模糊的诉求"不会一次被看清；每一步都可能推翻前一步；需求天然渐进）。
5. 能解释为什么"无来源需求不得入需求池"（获取判据 = 每条需求有来源）。
6. 能解释为什么规定需求是验证的参照、口头表述对不了账（验证需要能对账的靶子；"快一点"是几秒没法证明）。
7. 能解释为什么验证与确认必须分开（写得对 ≠ 是要的；隐含需求是分开的最深原因）。
8. 能解释为什么需求缺陷早期修复成本最低（需求阶段 1 vs 发布后 30~70 倍）。
9. 能解释为什么变更控制是需求管理核心战场、三铁律为什么成立（每一步可判定；无 CR = 查无实据的暗改）。
10. 能解释为什么基线是分界线、基线与追溯是一体两面（基线给"变"参照原点，追溯给"变"影响地图）。
11. 能解释为什么"批准→基线"是需求工程铰链（开发与管理接口咬合；铰链断需求断层）。
12. 能解释为什么 ConOps 在分析之后、规格之前（先摸清需要再综合运行概念；跳过 = 从问题域跳解空间）。
13. 能解释为什么需求质量六性互相支撑、可追溯最常被牺牲（不立刻显形，变更时才答不上）。
14. 能解释为什么"没有文档的环节就是不可追溯的环节"（骨架五份不可省；裁文档 = 砍追溯链）。
15. 能解释为什么先写条款后补故事顺序反了（需求规格的问题要到 ConOps 里才看得出来——恒信三百条 SRS 一半需改写）。

### 判据层（应会用）

1. **需求工程判据**：能说清"生/养"分工吗？两者并列而非包含吗？——需求是开发出来的，不是管出来的。
2. **规定需求判据**：一条需求可验证吗？能设计测试证明 → 是规定需求；只能"感觉" → 还不是。
3. **验证/确认判据**：对照规定需求（表述对不对）还是预期用途（是不是要的）？两道关缺一不可。
4. **欠账二分判据**：最近这次需求混乱，是"当初没说清"（开发欠账）还是"定了之后没人管"（管理欠账）？先清源再修渠。
5. **ConOps 位置判据**：ConOps 在分析之后、规格之前——先讲清系统怎么被用，才谈得上必须做什么。
6. **变更控制三铁律**：无 CR 不得变更；不分析不得上会；验证通过方可关闭——每一步可判定。
7. **版本管理判据**：能回答"哪一版是基线、这次为什么改、从什么变到什么"吗？答不上来，就只是改名。
8. **骨架五份判据**：SRS/需求池/RTM/评审报告/基线——缺一份，需求工程链就有断点。

**网搜印证性质区分（事实 vs 观点）**：N1（CMMI 官方模型与微软 CMMI 指南、评审师对标准的解释=事实；博客行文=观点）｜N2（SEBoK/IEEE 610.12 标准与百科=事实；厂商博客=观点）｜N3（ISACA 期刊/IEEE 会议/Springer 案例研究=学术事实；行业博客=观点）｜N4（Fairley & Thayer 论文、INCOSE 分会导引=事实；GovLoop/正义部生命周期指南=标准实践）｜N5（PMI/PMP 培训与 51CTO/ASPICE 规程指南=规程共识；论坛讨论=观点）｜N6（Fraunhofer IESE 官方博客与 adesso 博客=行业共识/观点，RemNote 学习指南=观点；但"RE 持续非一次性"有学术支撑）｜N7（DEV/Visual Paradigm/quackback=实践共识/观点；"可测=阈值+条件+测量法"为需求工程通则）。全部仅作"这不是书里一个人的说法"的佐证——**网搜当弹药，不当铁证**；药与判据均在书内，无超出书处。

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 并列不是包含（需求工程=开发+管理；开发管生、管理管养） | 1 / 2 / 3 / 15 | 脱口报出并列一句 + "需求是开发出来的不是管出来的"成为口头禅 |
| ★2 | 规定需求三要素（成文+具体+可验证；能设计测试证明） | 4 / 10 / 17 / 20(误解库) | "能设计测试证明吗"成为反问句；随手把"要快一点"改写可验证 |
| ★3 | 验证 vs 确认（对照规定需求 vs 对照预期用途；两道关缺一不可） | 5 / 11 | "写对了吗 vs 是要的吗"脱口；隐含需求=分开的最深原因 |
| ★4 | 欠账二分（需求总在变 → 先分清需求变了 vs 当初没说清；先清源再修渠） | 2 / 6 / 19(误解库) | "这条是需求变了还是当初没说清"成为诊断首问 |
| ★5 | 先立问题域再写条款（ConOps 在分析之后、规格之前；LeafToHub） | 8 / 16 / 20(误解库) | "跳过 ConOps 直接写 SRS=条款悬空"脱口；方法操作类，练到亲手写一段 ConOps 场景 |
| ★6 | 变更控制三铁律（无 CR 不得变更；不分析不得上会；验证通过方可关闭） | 13 / 18(误解库) / 19(误解库) | 三铁律脱口；"口头变更=暗改"脱口 |
| ★7 | 改名留档 ≠ 版本管理（基线/变更控制/追溯三样） | 7 / 18(误解库) | "另存为 v2 只是留档"成为查版本管理的口头禅 |
| ★8 | 骨架五份不可省（没有文档的环节=不可追溯的环节） | 14 / 15 | "缺一份，链就有断点"脱口；检查单逐份打勾 |

### 纠错红线十条

1. **先表态后翻案**：先让学员说"需求管理包含需求开发，管好需求自然就开发好了，这还用讨论吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："并列不是包含"别翻成"需求管理没用"；"先立问题域"别翻成"流程越多越好"；"验证≠确认"别翻成"确认不重要"；"口头变更最危险"别翻成"一切变更都是坏变更"。
3. **判据配机制**：每条反转都有"为什么"（机制）和"怎么当场验证"（判据）——并列有 CMMI/IEEE 并列过程域机制，验证确认有"对照物不同"机制。
4. **归责到可对照动作**："你们需求乱"落到"欠账二分两张单子 / 无来源需求 / 写了不可验证的条文"，不归咎"人不行"。
5. **教机制不教断言**：教"为什么隐含需求不会自己开口"（它通常隐含，行业惯例默认），不教"多问几句就安全"。
6. **先立尺子再翻案**：先给判据1/2/3/4，再翻恒信"加强需求管理"的处方。
7. **拉开强度层次**：★★★ 常识（包含=开发好 / 说了就是需求 / 需求变更多=管理没做好 / 口头改需求没关系 / ConOps 与开发无关）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（如用"能设计测试证明吗"改写一条需求）。
9. **单一权威不另立标准**：判据引用书（八把尺子 + 三铁律 + 六性），不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"的佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给团队最近一次"需求混乱"做"需求欠账体检 + ConOps 补桥"

> 目标：用欠账二分 + 规定需求 + ConOps 三个判据，对团队最近一次"需求变来变去 / 改一版崩一版 / 验收扯皮"做一次诊断，产出三件可执行改进（一件补开发、一件补管理、一件立 ConOps）。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑一次需求混乱（先立枢纽）**：选一次"最近需求变来变去 / 改一版崩一版 / 验收扯皮"的事件——症状最像"管理问题"的，往往是"开发欠账"潜伏最深的。**话术**："我们拿最近一次'又改了'来拆。"
2. **诊断一 · 欠账二分（先清源再修渠）**：翻最近的变更记录 / 验收记录——每条"变更"是"需求变了"（管理欠账：没基线、变更失控、查无实据）还是"当初没说清"（开发欠账：没调研、没分析、没写可验证规格）？**话术**："这条是需求真的变了，还是当初就没说清？"答错了病，药就开错了。
3. **诊断二 · 无来源需求排查**：把需求池 / 需求清单过一遍——每条需求答得出"从哪来"吗（访谈？业务规则？竞品？）？**判据**："无来源需求不得入需求池"。**话术**："这条需求是谁、在什么场景下提的？"
4. **改写一条"明示但未规定"的需求**：挑一条"说了但不可验证"的（如"要快一点""要严谨""重要合同要审批"），用规定需求三要素改写（成文 + 具体 + 可验证），并设计一条测试证明它。**话术**："能设计测试证明吗？能，才是规定需求；只能'感觉'，还不是。"
5. **诊断三 · ConOps 补桥（先立问题域再写条款）**：这个系统"怎么被用"写成故事了吗？没有 → 用"先立问题域再写条款"补一段运行场景（正常 / 异常 / 应急各一个）；有 → 让一个不熟悉系统的人读，能画出流程图吗？**话术**："法务怎么审、财务怎么对账、业务怎么发起——这段叙事写出来了吗？"ConOps 写不出来的场景，就是将来要出事故的场景。
6. **检查需求管理四活动**：基线在哪？变更走 CR 吗？RTM 建了吗？**判据**：无 CR 不得变更；改名留档 ≠ 版本管理。**话术**："最近一次变更，'从什么变到什么'说得清吗？"
7. **出报告**：三件事（一件补开发、一件补管理、一件立 ConOps），每个落到可检查动作；两周后回来报告——哪把尺子测出不合格、补了哪个动作。

**卡住怎么判断**：答不上来的那一项就是最该补的——"这条需求从哪来"答不上 = 获取欠账；"能设计测试证明吗"答不上 = 还不是规定需求；"系统怎么被用写出来了吗"答不上 = ConOps 缺桥。不用七步全做完，找到第一个答不出的步骤就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 最近这次需求混乱，分清是"需求变了"还是"当初没说清"了吗？（欠账二分） | □ | 答不上来 = 病没分清，药会开错（把开发欠账当管理漏洞补） |
| 每条需求有来源吗？ | □ | 无来源需求 = 获取欠账——"无来源需求不得入需求池" |
| 每条需求可验证吗（能设计测试证明）？ | □ | 只能"感觉" = 还不是规定需求——说了 ≠ 规定 |
| 验证对照规定需求、确认对照预期用途分开了吗？ | □ | 只验证不确认 = 写得很对但没人要；隐含需求只有确认兜得住 |
| "系统怎么被用"写成叙事了吗？（ConOps） | □ | 没有 = 条款悬空；先立问题域（ConOps）再写条款（SRS） |
| 变更走 CR 吗？（无 CR 不得变更） | □ | 口头变更 = 暗改；没有凭证的变更 = 查无实据 |
| 基线建了吗？ | □ | 改名留档 ≠ 版本管理；没有基线，变更不可言说 |
| 骨架五份缺哪份？（SRS / 需求池 / RTM / 评审报告 / 基线） | □ | 缺一份，需求工程链就有断点——没有文档的环节就是不可追溯的环节 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"章首那场会：恒信 IT 总监拍板『需求最近总是变来变去，我们要加强需求管理。Ada，你来。』Ada 没接话，先问了三句：需求为什么会变？变之前，需求开发做到位了吗？每条需求写得可验证吗？IT 总监反问：这些不都是『需求管理』的一部分吗？管好需求，自然就都做了。这句话错在哪？需求工程、需求开发、需求管理到底是什么关系？"
追问：① 需求开发（生·创造·造血）和需求管理（养·控制·防腐）各管什么？为什么是并列不是包含？② 需求管理四活动（基线/变更/追溯/状态度量）里，变更控制为什么是核心战场？『无 CR 不得变更』堵住的是哪个口子？『改名留档（另存为 v2）』为什么不是版本管理？③ 反身：你们部门说"要加强需求管理"的时候，说的是哪一半——补开发还是补管理？

**Q2（见树见林② · 概念关系）**
"请给出这条链的关系结构：需求工程 ⊃ 需求开发 + 需求管理（并列）；需求开发：获取 → 分析 → ConOps → 规格（SRS·规定需求）→ 确认；需求管理：基线 → 变更 → 追溯 → 状态度量。规定需求在链的什么位置？验证、确认各自对照什么？ConOps 为什么在分析之后、规格之前？"
追问：① 需求开发四活动为什么是循环不是直线？② 验证对照规定需求（表述对不对）、确认对照预期用途（是不是要的）——它们在链上各踩在哪一步？③ 骨架五份（SRS / 需求池 / RTM / 评审报告 / 基线）缺一份会怎样？『批准 → 基线』为什么是需求工程的铰链？

**Q3（真悖论 · 说了 ≠ 规定）**
"客户在评审会上说：『页面要快一点』『系统要好用』『审批要严谨』——客户说了、领导也说了，这算需求吗？有人说算——客户的话不就是需求吗？这一章说：只算一半，它们还不是规定需求。两个都对吗？什么判据分清『说了』和『规定』？"
追问：① 规定需求 = 成文 + 具体 + 可验证——口头表述为什么对不了账（"快一点"是几秒？）？② 恒信『重要合同要审批』——『重要』是期望还是需求？不澄清会怎样（把期望当需求 = 过度设计；把需要漏成期望 = 漏命根子需求）？③ 反身：你们最近一次验收扯皮，是不是卡在一条"说了但没规定"的需求上？

**Q4（真悖论 · 验证 ≠ 确认）**
"恒信把『合同审批在 5 分钟内完成』写得无可挑剔、测试全过——但用户真正要的是『法务在移动端先审』。这是『写得很对但没人要』。可另一边，有人抱怨：需求是要的，但没法执行。两个失败哪个更常见？验证（verification）和确认（validation）为什么要分开？"
追问：① 验证对照什么、确认对照什么（规定需求 vs 预期用途）？各问什么（表述对不对 vs 是不是用户要的）？② 只验证不确认、只确认不验证各是什么后果？③ 隐含需求为什么是『必须分开验证与确认』最深的原因（验证对照规定需求照不到没显性化的隐含需求，只有确认——真实场景——兜得住）？

**Q5（真悖论 · 需求变了 ≠ 当初没说清）**
"IT 总监的直觉：需求变来变去 = 需求管理没做好。Ada 翻了三个月变更记录，发现一大半『变更』根本不是需求变了，而是当初就没说清楚——合同评审的触发条件是『重要合同』要审批，但『重要』从没定义过；财务要的『对账报表』从没说清统计口径。所以：需求『总在变』，到底是需求管理的漏洞，还是需求开发的欠账？什么判据分清哪个病、开哪味药？"
追问：① 开发欠账（源头脏：没调研/没分析/没写可验证规格）和管理欠账（过程乱：没基线/变更失控/查无实据）各是什么症状？为什么『先清源（开发）再修渠（管理）』顺序不能反？② 答错了病，药就开错了——章首 IT 总监开的是什么错药（只加强管理 = 给脏水修渠）？③ 反身：你们团队最近一次"需求又变了"，变的是需求，还是当初没说清？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 规定需求）**
"恒信有一条需求：『重要合同要审批』。法务觉得『重要』很清楚，财务觉得该按金额，业务觉得该按期限。把这条改写成可验证的规定需求——用什么判据判断改写成功了？『页面要快一点』呢？"
追问：① 规定需求三要素（成文 + 具体 + 可验证）——『重要』怎么具体化（金额 ≥ 500 万或三年期以上）？② 改写后的需求，怎么设计测试证明它？——能设计测试证明 → 规定需求；只能"感觉" → 还不是。③ 反身：你们部门找一条"明示但未规定"的需求，现场改写。

**Q7（判据运用 · 欠账二分 + 变更控制三铁律）**
"恒信『改一版崩一版』。Ada 补了需求基线、建了 CR 流程，六周后变更失控率降了七成——不是需求变少了，是每次变更都留下了痕迹。用欠账二分（开发欠账/管理欠账）诊断恒信：崩的是哪张单子？『无 CR 不得变更，不分析不得上会，验证通过方可关闭』——三铁律各堵住哪个暗改口子？"
追问：① 变更控制闭环（CR → 影响分析 → CCB 评审 → 实施 → 再验证 → 关闭）哪一环最常被跳？跳的代价是什么（查无实据的暗改）？② 基线是分界线——线左（需求开发·流动）线右（需求管理·变更控制）各归谁管？『另存为 v2』为什么只做到留档（缺基线/变更控制/追溯三样中的哪样）？③ 反身：你们最近一次需求变更，"从什么变到什么"说得清吗？

**Q8（判据运用 · ConOps + 真悖论）**
"恒信第一版 SRS 三个月写了三百条。评审会上法务翻了两页问：『你们写"合同审批通过后自动通知相关方"——哪个相关方？审批链上有几个人？通知不到会怎样？』没人答得上，因为没人写过 ConOps——三百条条款悬在半空。为什么需求规格的问题，往往要到 ConOps 里才看得出来？『先写条款后补故事』为什么顺序反了？"
追问：① ConOps 六部分哪部分是核心（运行场景：正常/异常/应急）？为什么？② ConOps 判据——让一个不熟悉系统的人读完，能画出流程图吗？③ 跳过 ConOps 直接写 SRS，等于从什么跳到什么（问题域 → 解空间）？三百条 SRS 里为什么有一半需要改写？④ 反身：你们最近一个系统，能写出一段"系统怎么被用"的叙事吗？

**Q9（方法时刻 · 规则 15 · 先立枢纽 vs 陷细节 + 跨域变体）**
"这一章从头到尾演示的是同一只手——先立枢纽，再进细节（第1章：先立枢纽 vs 陷细节 LeafToHub）。开篇立『需求工程 = 开发 + 管理』的并列枢纽，ConOps 立『问题域』的枢纽。请亲手做一遍：给恒信合同审批系统写一段 ConOps 运行场景的开头（正常流程：一份 200 万的采购合同从发起、法务初审、财务校验、业务终审、签章、归档，标注每个环节的角色）——再反过来判断：为什么先扎进三百条 SRS 条款、不立这个骨架，条款越多越悬空？"
追问（跨域变体）：① 你把这段 ConOps 换到冰链 M3 温控箱——『疫苗从出库到接种全程温度不断链』，运行场景里写『疫苗运输车在高速上抛锚 2 小时』这种应急，直接决定了『断电保温时长』这条硬需求。判据变没变——先立问题域（ConOps）再写条款（SRS）在硬件世界还成立吗？这说明了什么（概念不挑行业）？② 反身：你们上次写需求/写方案，是先立了问题域骨架，还是直接陷进了细节条款？

**Q10（落地生根 · 回部门需求欠账体检）**
"结合你们部门现状，用欠账二分、规定需求、ConOps 三个判据，给你们最近一次需求/交付做一次体检——给出最该改进的三件事，每个落到一个动作。"
追问：① 三把尺子（能分清"需求变了/当初没说清"吗 / 每条需求能设计测试证明吗 / "系统怎么被用"写出来了吗）先查哪两把？② "加强需求管理"这种话你们部门说过吗——当时补的是开发还是管理？③ 两周后回来报告：哪把尺子测出不合格、补了哪个动作？
