## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：架构到底是什么？为什么"画一张框图"不算做架构？系统、架构、架构描述这三个词，为什么混着说会让一个团队三个月都答不出三个问题？

**三幕对齐（省一步推导）**：

- **第三幕 往哪去（运用）**：3.1 为什么需要架构描述 → 3.2 相关方与关注点（天然冲突）→ 3.3 视点与视图（相机）→ 3.4 4+1 视图模型（场景是胶水）→ 3.5 架构是压缩 → 3.6 决策/变更/组织三回报 → 3.7 约束即解放 → 3.8 架构师的理论 → 3.9 架构师首先是一个工程师 —— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **架构**（architecture）：系统在其环境中的基本概念或属性，体现在其元素、关系以及设计演进原则之中（ISO/IEC/IEEE 42010:2011）。= 系统不可还原的涵义。判据：三问（去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗）。
2. **架构描述**（architecture description）：对架构的表达——按"相关方 → 关注点 → 视点 → 视图"组织起来的制品集合。判据：链条完整吗？每个视图能说出"在回答谁的什么问题"吗？
3. **系统**（system）：实际存在的那个东西（M3 实物）——弗雷格的"指称"。
4. **相关方 / 关注点**（stakeholder / concern）：对系统有利益关系的任何个人/团队/组织 / 对系统的任何兴趣；关注点天然冲突、只能权衡。
5. **视点 / 视图**（viewpoint / view）：怎么看的规则（镜头设置）/ 按规则画出来的产物（照片）。
6. **设计准则 / 演进准则**（design principle / evolution principle）：怎么造 / 怎么变——合起来是架构的免疫系统。
7. **架构框架**（architecture framework）：预定义的视点集合——4+1、C4、TOGAF、Zachman。
8. **框架**（framework）：对某一类事物/活动预制的"骨架 + 位置 + 组织规则"，内容后填——用框架 ≠ 有架构。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 架构 | 详细设计 | 不可还原（去掉不是这个系统）vs 可还原（改了还是它） |
| 架构 | 架构描述 | 涵义（不可视见）vs 符号（可读可看可存档） |
| 架构 | 图 / 框图 | 逻辑范畴的存在（不长什么样）vs 视觉范畴的存在（纸上的、会过时） |
| 架构 | 框架 | "这一个"的组织本质（属于系统）vs "这一类"的组织方式（属于领域） |
| 架构 | 架构风格 / 模式 | 这个系统的本质属性 vs 抽象的决策套路 |
| 架构 | 技术选型 | 不可还原涵义 vs 选型只是"概念或属性"的一种体现 |
| 约束 | 无约束（消极自由） | 约束即解放：管得最准 vs 管得最多 |

### 关联概念（近界 · 辨析）

- **系统 ≠ 架构 ≠ 架构描述 = 弗雷格模型（第1章补充）**：指称（系统）≠ 涵义（架构）≠ 符号（架构描述）——"晨星 / 暮星"都是金星，两个词不同、呈现方式不同、指向同一个东西；架构领域翻版成 M3 的箱子 / 那组决定 / 老周的图。
- **架构 ↔ 概要定义（第6章）**：第6章那棵树的树干树枝是概要定义，管结构、管承接；架构是那棵树里不可还原的部分——"概要定义是架构的一种描述；架构是概要定义背后那些'去掉就不是它'的决定"。
- **三判据 ↔ 第1章反事实检验**：第1章用"去掉它，这个领域还成立吗"识别领域枢纽；本章用同一动作识别系统架构——同一个动作，换个对象。
- **架构 ↔ 涌现属性（第2章）**：第2章讲飞机"部件全对未必能飞"；本章落到架构层面——可靠性瓶颈通常在组件交互模式，不在单个组件。
- **架构 ↔ 压缩学习（第1章）**：压缩学习的对象是知识（人脑是压缩机器），架构压缩的对象是系统——同一个原理：用结构消化复杂度。
- **架构 ↔ 评审对目标（第7章）**：架构评审审的是架构描述是否对得起系统的不可还原涵义（第7章"评审对目标"的延伸）。
- **架构 ↔ 不可逆（第11章种子）**：一个决定"去掉就不是这个系统"，是因为改它的代价几乎不可逆——架构=对不可逆决策的提前投资（第11章展开）。
- **架构师 ↔ 工程师（第8章）**：架构师首先是一个工程师——第8章六项底座一项不能少；在底座上再长四项系统级能力 → 十项清单第15章收全。
- **架构框架 ↔ 架构描述（严口径）**：4+1、TOGAF 等是"预定义的视点集合"——同一种"骨架+规则"，填进去的是架构描述，不是架构本身。

### 核心原理

**第一幕 · 是什么的底层机制**
1. 架构是系统不可还原的涵义——"断链即报废的疫苗，能从出库一路撑到接入冷库、全程可追溯"那组决定；概要定义是架构的一种描述，架构是概要定义背后那些"去掉就不是它"的决定。
2. 三个词三层 = 弗雷格模型（指称 ≠ 涵义 ≠ 符号）：系统（指称）/ 架构（涵义）/ 架构描述（符号）。
3. 推论一：同一个架构可以有无数种描述；反过来同一张图可能根本没描述对架构（老周的图只画了元素，没画关系，更没画原则）。
4. 推论二：系统不等于架构——系统有生命周期（会报废、会换代），架构（那组不可还原的决定）活得比系统长（作为经验、教训、下一代设计前提继续存在）。
5. "基本"（fundamental ← fundus 地基）是整句定义的核心——地基一动，整栋楼都动；从本义推出三判据（不可再分 / 不可缺失 / 不可替代）。
6. 定义里是"概念**或**属性"（or）不是"概念和属性"（and）——中文翻译常写成"和"；"或"更宽松：从概念切入或从属性切入，两条路都能到架构，不必同时具备。
7. "在它的环境中"——环境决定哪些属性才算"基本"：同一个温控设备，实验室台架上可以是"温度控制单元"，冷链运输里必须包括"断链检测与补传"；环境变了，什么算"基本"就变了。
8. 关系比元素更要紧——系统的涌现属性来自关系，不来自单个元素；可靠性的瓶颈，通常不在单个组件，而在组件之间的交互模式。
9. 三判据 = 第1章三步识别法里最狠的一步（反事实检验）用在系统上——同一个动作，换个对象；架构决策和普通实现决策的分界 = 改它花多大代价、影响多大范围、几乎不可逆。

**第二幕 · 磨边弧的机制（不是什么）**
10. 架构和图不在同一个世界——图是纸上的、可见的、会过时的；架构是系统里那组不可还原的决定，真实存在但不因你没更新图就消失；"架构不长什么样"（视觉范畴 vs 逻辑范畴——宪法 / DNA / 组织架构类比：你能画出来的永远是描述，只有投影，没有"原图"）。
11. 一个系统只有一个架构——所有"XX 架构"都是对同一个架构的描述（视图），来自两套独立分类维度：关注域（业务/数据/应用/技术）× 抽象层次（概念/逻辑/物理）交叉出每一个具体视图。
12. 架构风格 / 模式 = 架构决策的套路（微服务/事件驱动/分层——结构体系的选择，不是建筑本身）；框架 = 把套路"物化"成的可复用制品（骨架 + 位置 + 组织规则，内容后填）——用框架 ≠ 有架构（骨架 ≠ 决策），试金石一句"删掉它，系统还在吗"。
13. 架构不是静态快照——它自带"怎么造"和"怎么变"两套规则：设计准则（约束从无到有的创建过程）+ 演进准则（约束随时间变化的过程）= 免疫系统；缺一个：只有设计准则→系统一改就坏（微服务退化成分布式单体）；只有演进准则→系统建出来就不对。
14. 架构是活的学习系统——免疫系统两点（定义什么是"自我" + 主动防御变化）；每次架构层面的变更失误，沉淀为一条架构原则的更新。

**第三幕 · 往哪去的机制（运用）**
15. 涵义锁在脑子里，没有用——架构必须被表达出来，才能被共享、被讨论、被检查、被传承；架构描述就是这个"表达"。
16. 关注点天然冲突（*The concerns of stakeholders are frequently broad, varied, and conflicting*）——冲突不可消除，只能权衡；权衡有一个前提：你得先能看到每个方面（看不见安全就不会为安全取舍）。
17. 视点（怎么看的规则）× 视图（产物）= 相机比喻（角度/镜头/滤镜 vs 照片）；每个视图是刻意的"不完整"——把不关心的部分剥离掉、只保留本质，视图就是架构的概念化切片。
18. 视图的完备性由相关方及其关注点决定，不由方法论决定——三步白板推导（识别重要相关方 → 明确核心关注点 → 按语言聚类 → 查有没有漏）；"我们需要几个视图"是方法论之争，"我们的相关方是谁"是项目分析。
19. 4+1 视图模型的场景（+1）不是第五个视图，是胶水——拿一条真实使用场景横穿四个视图，检验它们是否互相矛盾；走不通，说明四个视图是四个系统。
20. 架构是保真压缩（不是丢信息）——把两三百个服务、上千张表压成"12 个业务域 × 每域 5-8 个构件"的骨架；共享心智模型让新成员入门、跨团队协作、决策讨论有共同语言。
21. 架构在三个时间维度上起作用——决策层面（划定解空间，削减的不是工作量而是决策量）/ 变更层面（事前预判影响、事中吸收不崩溃、事后从变更中学习）/ 组织层面（康威定律：组织设计出来的系统结构是其沟通结构的副本；构件边界就是团队边界）。
22. 约束即解放——消极自由（freedom from，没人拦）vs 积极自由（freedom to，知道怎么做对）；架构只约束"不改就会造成灾难"的东西，把团队从无穷的重复决策里解放出来；"管得最准"好过"管得最多"。
23. 架构师的核心能力，不是"做出正确的决策"，而是"识别哪些决策如果不正确，后果会很严重"——对不重要的事情不决策，本身就是一种好的架构决策；前提是架构师首先是一个工程师（第8章六项底座一项不能少）。
24. "什么是重要的"，本身需要判断——架构师对系统的理论（靠什么成功 / 最大压力在哪 / 什么做错了最致命）决定"什么重要"（Ralph Johnson：*Architecture is about the important stuff. Whatever that is.*）；而"不可还原"指向不可逆——架构，是对不可逆决策的提前投资（第11章展开）。

### 对立误解（喂给第 3 步误解库 / 第 4 步陷阱清单）

1. "架构 = 一张框图，画完没人维护就完事。"
2. "图过时了 = 架构过时了。"
3. "我们有业务架构、数据架构、应用架构、技术架构——四个架构。"
4. "用了 Spring Cloud，所以我们系统是微服务架构。"
5. "架构就是技术选型。"
6. "架构就是那张总图 / 系统拓扑图。"
7. "约束是给团队上枷锁，约束越少越灵活。"
8. "架构定了'怎么造'的设计准则就够了，'怎么变'的演进准则可有可无。"
9. "架构是架构师一个人的事，开发照着做就行。"
10. "好的架构 = 找一个让所有相关方都满意的方案。"
11. "架构 = 微服务架构（架构风格就是架构）。"
12. "视图画得越完整越好，一张图覆盖所有关注点。"
13. "架构评审 = 对着框图走个过场。"
14. "架构只要数出几个模块（元素）就够了，关系不重要。"
15. "架构是静态快照，画完就锁定了。"
16. "'架构' = 组织架构 / 产品形态 / 技术栈。"
17. "架构 = 系统的功能集合 / 模块清单。"

### 本章判据（八条）

1. **架构三问**：这个决定"去掉还是这个系统吗 / 缺少系统垮吗 / 换掉性质变吗"——三问都答"是"，才是架构；答"否"的，是详细设计，不是架构。
2. **三个词三层**：系统（指称，实际存在的那个东西）≠ 架构（涵义，不可还原的本质）≠ 架构描述（对涵义的表达）。图过时了 ≠ 架构过时了——决策可以一直有效。
3. **一个系统一个架构**："业务/数据/应用/技术"是关注域视角，"概念/逻辑/物理"是描述层次，"微服务/事件驱动"是架构风格——都不是多个架构。
4. **架构描述组织链**：相关方 → 关注点 → 视点（怎么看的规则）→ 视图（产出的切片）→ 组合成完整架构描述。每个视图要能说出"它在回答谁的什么问题"。
5. **关注点天然冲突**：相关方的关注点是宽泛、多样、且相互冲突的——冲突不可消除，只能权衡；权衡的前提是看到每个方面。
6. **约束即解放**：架构只约束"不改会灾难"的决定，把团队从重复决策里解放出来，回收积极自由。"管得最准"好过"管得最多"。
7. **设计准则 + 演进准则 = 免疫系统**：设计准则管"怎么造"，演进准则管"怎么变"；缺一个，系统要么一改就坏，要么建出来就不对。
8. **框架 ≠ 架构**：框架是"这一类"的组织方式（骨架+位置+组织规则，内容后填），架构是"这一个"的组织本质。用框架 ≠ 有架构——框架给骨架，决策得自己做。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"架构"（ISO/IEC/IEEE 42010：系统在其环境中的基本概念或属性，体现在其元素、关系以及设计演进原则之中），并说出"不可还原的涵义"是什么意思（"断链即报废还能撑到接入冷库、全程可追溯"那组决定）。
2. 能辨析 系统 ≠ 架构 ≠ 架构描述（弗雷格：指称 ≠ 涵义 ≠ 符号），各给一个 M3 的例子（产线上的箱子 / 那组决定 / 老周的图）。
3. 能定义"架构描述"（按"相关方 → 关注点 → 视点 → 视图"组织的制品集合），并辨析 架构描述 ≠ 某一张视图（视图是组成部分）≠ 一张总图（一组按视点组织的视图）。
4. 能辨析 架构 × 详细设计（不可还原"去掉不是它" vs 可还原"改了还是它"）。
5. 能辨析 架构 × 图（架构不长什么样——逻辑范畴；图是描述、会过时——视觉范畴）。
6. 能辨析 架构 × 框架（"这一个"的组织本质 vs "这一类"的组织方式；用框架 ≠ 有架构）、架构 × 架构风格/模式（决策套路 vs 系统的本质属性）、架构 × 技术选型（选型只是体现）。
7. 能定义 相关方 / 关注点 / 视点 / 视图（链条四环：谁想看 → 关心什么 → 按什么规则看 → 看到什么），各配一句话。
8. 能定义 设计准则 / 演进准则（怎么造 / 怎么变），并说出两类缺一个的后果。
9. 能说出"一个系统只有一个架构"，及"XX 架构"的两套分类维度（关注域 × 抽象层次）+ 架构风格 + 框架四类各是什么。
10. 能说出 4+1 视图模型的五个视图及"+1 场景"为什么是胶水不是第五个视图。

### 原理层（应能解释为什么）

1. 能解释为什么"基本"（fundamental ← 地基）是定义的核心（地基一动整栋楼都动）。
2. 能解释定义里"概念或属性"为什么是 or 不是 and（两条路都能到架构，不必同时具备）。
3. 能解释为什么"在它的环境中"决定什么算"基本"（实验室台架 vs 冷链——环境变了基本就变了）。
4. 能解释为什么关系比元素更要紧（涌现属性来自关系；可靠性瓶颈在交互模式）。
5. 能解释三判据 = 第1章反事实检验用在系统上（同一个动作，换个对象）。
6. 能解释为什么架构"不长什么样"（视觉范畴 vs 逻辑范畴；宪法 / DNA / 组织架构类比）。
7. 能解释为什么一个系统只有一个架构（日常用语把"架构描述/架构视图"简称成"架构"；一副骨骼多张影像）。
8. 能解释为什么用框架 ≠ 有架构（框架给骨架不给决策；试金石"删掉它，系统还在吗"）。
9. 能解释为什么设计准则 + 演进准则缺一不可（只有设计准则→一改就坏 / 分布式单体；只有演进准则→建出来就不对）。
10. 能解释为什么架构是免疫系统（定义什么是"自我" + 主动防御变化）和活的学习系统（变更失误沉淀为原则更新）。
11. 能解释为什么涵义锁在脑子里没有用（必须被表达才能共享/讨论/检查/传承）。
12. 能解释为什么关注点天然冲突且只能权衡（快便宜安全全功能不能同时到顶；权衡前提是看到每个方面）。
13. 能解释为什么每个视图是刻意的"不完整"（完整=把一切糊在一张图上=对谁都没用；视图是架构的概念化切片）。
14. 能解释为什么视图完备性由相关方决定不由方法论决定（方法论之争 vs 项目分析）。
15. 能解释为什么 4+1 的场景是胶水不是第五个视图（真实场景横穿验证一致性）。
16. 能解释为什么架构是保真压缩（不需要一次记住全部、需要时能定位到；共享心智模型）。
17. 能解释架构在三个时间维度的回报（决策划解空间 / 变更免疫 / 组织康威定律）。
18. 能解释为什么约束即解放（消极 vs 积极自由；只约束要命的地方、回收积极自由）。
19. 能解释为什么架构师的核心能力是识别后果严重的决策（对不重要的事不决策是好的架构决策；架构师首先是一个工程师）。
20. 能解释"什么是重要的需要判断"（架构师的理论；*Whatever that is.*）与"架构 = 对不可逆决策的提前投资"。

### 判据层（应会用）

1. **架构三问**：去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗——三问皆"是"才是架构；答"否"的是详细设计。对任何一条"重要的事"当场打勾。
2. **三个词三层**：系统（指称）/ 架构（涵义）/ 架构描述（符号）分得开；图过时 ≠ 架构过时（决策可以一直有效）。
3. **一个系统一个架构**：业务/数据/应用/技术 = 关注域视角；概念/逻辑/物理 = 描述层次；微服务/事件驱动 = 架构风格；框架 = 可复用制品——用一条真实场景横穿，走不完 = 多个架构的病根。
4. **架构描述组织链**：相关方 → 关注点 → 视点 → 视图 → 完整描述——链条完整吗？每个视图能说出"在回答谁的什么问题"吗？
5. **关注点天然冲突**：冲突不可消除只能权衡；权衡前提是看到每个方面（相关方清单 + 核心关注点表摆出来）。
6. **约束即解放**：架构只约束"不改会灾难"的决定；每条约束能说出它解放了什么重复决策——写不出解放的是"管得最多"。
7. **免疫系统**：设计准则（怎么造）+ 演进准则（怎么变）两栏齐吗？缺一个，系统要么一改就坏要么建出来就不对。
8. **框架 ≠ 架构**：用框架 ≠ 有架构——框架给骨架，决策得自己做；试金石"删掉它，系统还在吗"。

| 21 N5 | "约束是枷锁，约束越少越自由。" | "使能约束"（enabling constraints）在框架内给即兴（爵士乐）；Revolut"通过限制提速"——限制技术栈不是瓶颈而是催化剂，"约束催生真正的自主" | 约束即解放（消极 vs 积极自由） | InfoQ 2025《How Sociotechnical Design Can Improve Architectural Decisions》（enabling constraints，爵士比喻）；Devoxx UK（Revolut《Velocity via Limitation》：enforced constraints accelerate velocity / "constraints fuel true radical autonomy"）；ThoughtWorks/O'Reilly《Lightweight Architecture Governance》（"paved roads and the pit of success"） |

| 23 N7 | "架构是架构师（象牙塔）一个人的事，开发照着做就行。" | 象牙塔架构 = 架构师脱离日常开发、理论与现实脱节；架构决策应分散、寻求建议而非许可——架构是共享的，架构师要"先是一个工程师" | 组织层面（康威定律）；架构师首先是一个工程师 | InfoQ 2023《Avoid Being an "Ivory Tower" Architect》；（Scott Ambler 定义"developed … in relative isolation to the day-to-day development activities"）；ThoughtWorks《Software architecture decisions: who should be involved?》；DevOpsDays《Torching Architecture Ivory Towers》 |

## 第 5 步 · 正误有方：纠错策略

### 强化点优先级（一个知识点反制多个误解）

| 优先级 | 强化点 | 反制误解 | 练到何种程度 |
|---|---|---|---|
| ★1 | 三个词三层（系统 ≠ 架构 ≠ 架构描述 = 弗雷格） | 1 / 2 / 6 / 16 / 19 | 脱口"图可以烂掉，决策可以活着"；随手把一句"架构"用词分类成三层 |
| ★2 | 架构三问（不可再分 / 不可缺失 / 不可替代） | 1 / 5 / 11 / 17 | 三问脱口；对任何一条"重要的事"当场打勾 |
| ★3 | 一个系统一个架构（关注域 × 抽象层次 + 场景横穿） | 3 / 11 / 12 / 18 | 脱口"XX 架构都是同一架构的视角"；拿一条真实场景横穿 |
| ★4 | 框架 ≠ 架构（骨架 ≠ 决策） | 4 / 5 / 11 | 试金石"删掉它，系统还在吗"脱口 |
| ★5 | 约束即解放（消极 vs 积极自由） | 7 | "管得最准好过管得最多"脱口；每条约束能说出解放了什么 |
| ★6 | 免疫系统（设计准则 + 演进准则） | 8 / 15 | "只有设计准则→一改就坏（分布式单体）"脱口 |
| ★7 | 关注点天然冲突（只能权衡） | 10 / 13 | "冲突不可消除只能权衡；权衡前提是看到每个方面"脱口 |
| ★8 | 关系比元素要紧（涌现属性） | 14 | "可靠性瓶颈在交互模式"脱口 |

### 纠错红线十条

1. **先表态后翻案**：先让学员说"架构就是那张图啊，画完就完事"，再翻，不让结论先入。
2. **反转精确不造新误解**："架构≠框图"别翻成"架构描述 / 画图没用"（描述仍是必须的，只是不是架构本身）；"约束即解放"别翻成"约束越多越好"（管得最准，不是管得最多）；"架构不是一张图"别翻成"不要画架构图"。
3. **判据配机制**：每条反转带"为什么"（弗雷格模型 / 免疫系统机制 / 涌现属性）+ "怎么当场验证"（三问 / 链条 / 场景横穿）。
4. **归责到可对照动作**："你们没在做架构"落到"图没画关系、没画原则、说不清每个视图回答谁的什么问题 / 三问一测就倒"，不归咎"人不行"。
5. **教机制不教断言**：教"为什么关系承载架构最硬部分"（涌现属性：可靠性瓶颈在交互模式），不教"多画箭头"。
6. **先立尺子再翻案**：先给三问 / 三个词三层 / 免疫系统判据，再翻老周"图就是架构"。
7. **拉开强度层次**：★★★ 常识（架构=框图 / 四个架构 / 框架=架构 / 约束=枷锁）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（用三问筛一条决定 / 拿一条真实场景横穿一次视图 / 把老规矩写下来）。
9. **单一权威不另立标准**：判据引用书（八条判据）+ ISO 42010，不发明新尺子；术语统一「设计准则 / 演进准则」，不另立"设计原则 / 演进原则"。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"佐证，药与判据全在书内。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给你们的系统写一份"老规矩"清单

> 目标：用本章判据（架构三问 / 三个词三层 / 免疫系统 / 约束即解放 / 场景是胶水），把团队"从没写下来但大家都在守"的决定，写成 M3 式的老规矩清单，区分"不可还原（架构）"与"只是习惯（非架构）"。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑系统（先立枢纽）**：选一个"最近做、你心里最有底"的系统——最有底的，往往是那张图最老、老规矩最没人写下来的。**话术**："你最熟的那个系统，把它的架构说给我们听——三分钟，不许画图。"
2. **项目一 · 三问筛决定（架构三问）**：把团队所有"重要的事"列出来（数据归属 / 接口契约 / 告警策略 / 部署方式 / 技术选型……），逐条用三问筛："去掉它还是这个系统吗？缺了它系统垮吗？换掉它性质变吗？"三问都答"是"的，才是架构。**话术**："少了这条规矩，M3 还是 M3 吗？"
3. **项目二 · 图和决定分开（三个词三层）**：把那张"架构图"翻出来，和筛出的决定对比——图里画了什么、没画什么？"图过时了"和"决定过时了"是不是两回事？**话术**："图可以烂掉，决策可以活着。"
4. **项目三 · 分两栏（免疫系统）**：把筛出的决定分成两栏——设计准则（怎么造：数据归属、断链刚性）+ 演进准则（怎么变：新增传感器不得破坏追溯链、固件升级向后兼容）。缺演进准则的那栏，就是"一改就坏"的高危区。
5. **项目四 · 一条场景横穿（场景是胶水）**：拿一条真实使用场景（如"一批疫苗从出库到接入冷库"），横穿你所有叫"XX 架构"的图/文档——走不通的地方，就是"多个架构"的病根，也是视图没对齐的缝。
6. **项目五 · 相关方补漏（关注点冲突）**：列出至少五个相关方及各自核心关注点（司机可用 / 客户可追溯 / 维修可维修 / 监管合规 / 老板成本）——有没有哪个关注点从没考虑过？冲突不可消除，只能权衡；权衡的前提是看到每个方面。
7. **项目六 · 约束即解放复核**：对每条筛出的约束，写下它把团队从什么重复决策里解放了出来——写不出来的约束，多半是"管得最多"不是"管得最准"。
8. **出清单**：哪些是"少了它就不是它"（架构，写进老规矩），哪些只是习惯（非架构，标注即可）；最后一条建议照书抄——把"架构评审"的标的，从"那张图"换成"那组不可还原的决定"。

**卡住怎么判断**：三问答不上来的那条，就是最该补的；一条真实场景横穿不动的地方，就是最该修的缝；约束写不出"解放了什么"的，就是最该砍的。不用全做完，找到第一个卡住的地方就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 三问筛出的决定"去掉不是它"吗？ | □ | 把"重要的事"当"不可还原的决定"了——可调参数不是架构 |
| 图和决定分开了吗（图过时 ≠ 架构过时）？ | □ | 团队把"图旧"当"架构旧"——过时的只是描述 |
| 所有"XX 架构"对齐到同一个架构了吗？ | □ | 一条真实场景走不完 = "多个架构"的病根 |
| 每个视图能说出"回答谁的什么问题"吗？ | □ | 视图是刻意的"不完整"，不是任意残缺 |
| 相关方关注点摆出来权衡了吗？ | □ | 看不见安全就不会为安全取舍；冲突不可消除只能权衡 |
| 设计准则 + 演进准则两栏齐了吗？ | □ | 只有设计准则，系统一改就坏（分布式单体） |
| 每条约束对应解放了什么重复决策？ | □ | 写不出解放的约束，是"管得最多"不是"管得最准" |
| 一条真实场景横穿所有视图了吗？ | □ | 走不通 = 视图之间藏着矛盾 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"冰链的架构评审会上，老周把那张四层方块图投上投影——硬件层、固件层、云端层、App 层，一根箭头标着'温度数据'——说：'这就是我们 M3 的架构。'三个月后三个问题找上门：改采集间隔（1 分钟改 5 分钟）影响什么，会议室没人能答；加断电补传，云端和固件互相推'重连逻辑在谁那边'；客户问'M3 到底是什么系统'，三个人三个答案。老周翻出图想维护，忽然意识到：这张图从来没有描述过真正的 M3。为什么说那张图不是 M3 的架构？架构到底是什么？用'架构三问'把 M3 不可还原的涵义筛出来。"
追问：① 三个问题各证明那张图缺了什么（采集间隔→关系/定在哪一环、断电补传→关系与原则、三个人三个答案→视角没对齐）——为什么'可靠性瓶颈在交互模式'？② 三判据对'断链即报废还能撑到接入冷库、全程可追溯'逐条打勾——为什么它是架构，而采集间隔不是？定义里'概念或属性'为什么是 or 不是 and？③ 为什么'在它的环境中'决定什么算基本（同一台温控设备，实验室台架 vs 冷链运输）？M3 相关方关注点为什么天然冲突、只能权衡（司机可用/客户可追溯/维修可维修/监管合规/老板成本）？④ 反身：你们最近一次'架构评审'，审的是一张图，还是把关注点摆出来权衡？

**Q2（见树见林② · 概念关系）**
"请给出 系统、架构、架构描述 三个词的关系，并说明：为什么说它们是弗雷格模型的翻版（指称 ≠ 涵义 ≠ 符号）？为什么'图过时了'不等于'架构过时了'？"
追问：① 各给一个 M3 的例子（产线上的箱子 / 那组决定 / 老周的图）？② 推论一：同一个架构可以有无数种描述（四层框图/数据流图/时序图/合规视图都在描述同一个 M3 架构）；反过来同一张图可能根本没描述对架构——老周的图为什么属于后者？推论二：系统有生命周期，架构为什么活得比系统长？③ 架构描述按'相关方 → 关注点 → 视点 → 视图'链条组织——这和'三个词三层'什么关系？④ 反身：你们平时说'架构'，说的是系统、架构还是架构描述？三个层面混着说会怎样？

**Q3（真悖论 · 架构是一张图 vs 架构是不可还原的涵义）**
"有人觉得：架构就是那张图——画出来了、评审了、存档了，架构工作就完成了。这一章说：架构不是一张图，是系统不可还原的涵义；图会过时，决定活着。哪个对？什么判据分清'图'和'架构'？"
追问：① 如果图就是架构，图过时了系统应该怎样？——可 M3 温控箱一直在正常工作，温度一直在采集、断链依然会告警，这说明什么？② 架构是静态快照吗？如果不是，它怎么'活'？（设计准则 + 演进准则 = 免疫系统；每次变更失误沉淀为原则更新）③ 为什么架构'不长什么样'？（宪法 / DNA / 组织架构类比——你看到的永远是文本/双螺旋/组织图，只有投影，没有'原图'）④ 反身：你们有没有'图早就烂了、规矩一直活着'的时刻？

**Q4（真悖论 · 一个架构还是四个架构）**
"恒信的李工把合同审批系统的架构画成四张图：业务架构、数据架构、应用架构、技术架构，挂满一面墙。他说这是四个架构。软件圈还有'微服务架构''事件驱动架构'，老周团队有人张嘴就是'用了 Spring Cloud'。这些到底是不是多个架构？什么判据能把它们分清楚？"
追问：① 两套分类维度（关注域 × 抽象层次）+ 架构风格 + 框架，四类各是什么（一栋楼的平面图+结构图+管线图+立面图 vs 概念草图→施工图 vs 框架结构/剪力墙结构 vs 预制构件+装配手册）？② Ada 用一条真实场景横穿四张图（法务老张在 App 上审批一份 500 万的合同）——为什么走不完四张图，就是四个系统？③ 反身：你们团队叫'XX 架构'的图/文档，用一条真实场景横穿过吗？

**Q5（真悖论 · 约束是枷锁还是解放）**
"有人抱怨：架构是给团队上枷锁——定了数据所有权、定了断链刚性、定了兼容规则，这不是绑住手脚吗？约束越少越灵活。这一章说：约束即解放——约束把团队从无穷的重复决策里解放出来。两个都对吗？什么判据分清'束缚'和'解放'？"
追问：① 消极自由（freedom from）和积极自由（freedom to）差在哪？没有架构时你拥有哪种自由、丧失哪种自由？② 老周的约束（数据所有权/断链刚性/追溯完整性）各自把团队从什么重复决策里解放了出来（改采集间隔不用开会、加新传感器不用重新吵架构）？③ '管得最准'和'管得最多'怎么区分？④ 反身：你们系统里有没有'管得最准'的约束？有没有'管得最多'的约束？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 框架 ≠ 架构）**
"软件圈几乎每天都能听见一句话：'用了 Spring Cloud，所以我们系统是微服务架构。'老周团队也有人张嘴就是'M3 用的某某嵌入式框架'。这句话错在哪？框架和架构差在哪？用'删掉它，系统还在吗'测一测。"
追问：① 框架的三特征（骨架性/留白性/复用性）各是什么意思？② 为什么'骨架搭起来不等于架构有了'——服务边界、数据归属、接口契约，Spring Cloud 一个都没替你决定，为什么？③ 架构风格、框架、架构、架构描述怎么排成一条链（套路 → 物化 → 实例化 → 表达）？④ 反身：你们用过的框架，替你们定了什么、没替你们定什么？没替你们定的那些，是不是正好是架构决策？

**Q7（判据运用 · 免疫系统：设计准则 + 演进准则）**
"老周那天晚上把'老规矩'写了下来：温度数据归属追溯域，传感器只管采、云端只管传、追溯平台管存管管看；断链必须实时告警并记录，不得吞掉、不得延迟；固件升级必须向后兼容已出厂的设备。前两条是设计准则，第三条是演进准则。为什么两类准则缺一不可？只有设计准则、没有演进准则的微服务，会退化成什么？"
追问：① 设计准则（怎么造）和演进准则（怎么变）各管什么？② 为什么说架构是免疫系统（定义什么是'自我' + 主动防御变化）？③ 分布式单体是怎么形成的？④ 反身：你们系统的演进准则写下来了吗？缺演进准则的那次变更，后来怎样了？

**Q8（判据运用 · 相关方 → 关注点 → 视点 → 视图 + 场景是胶水）**
"恒信的李工把合同审批系统的架构画成四张图，挂满一面墙。Ada 问他：'一份合同，在这四张图里分别是什么？'——业务架构里是一条审批流程，数据架构里是'合同主表 + 审批记录 + 附件'三个实体，应用架构里是审批引擎的一个流程实例，技术架构里没画合同。'就凭这最后一句，'Ada 说，'你的四张图是四个系统。'为什么？什么判据能让四张图对得上？"
追问：① 相关方 → 关注点 → 视点 → 视图这条链，四环各是什么（谁想看 → 关心什么 → 按什么规则看 → 看到什么）？② 为什么每个视图是刻意的'不完整'？把一切糊在一张图上会怎样？③ 4+1 的场景为什么是胶水不是第五个视图？④ 反身：你们每个视图能说出'在回答谁的什么问题'吗？

**Q9（方法时刻 · 规则 15 · 勤校准 + 跨域变体）**
"老周把'架构'从'一张框图'修正为'不可还原的涵义'——第1章说，勤校准是正常纠偏，不是失败；概念是活的、可修正的。这一章的方法底座时刻，就是勤校准：完成一次枢纽修正。请亲手把'架构 = 一张框图'这个旧枢纽，修正成'架构 = 系统不可还原的涵义'——你靠什么动作完成这次修正？修正之后，'图过时了'意味着什么？"
追问（跨域变体）：① 冰链的老规矩（数据所有权/断链刚性/追溯完整性）和恒信的四张图（业务/数据/应用/技术），是同一个修正的两面吗？把'架构=框图'的修正用到恒信——判据变没变？② 架构师的核心能力不是'做出正确的决策'，而是'识别哪些决策不正确后果很严重'——老周这次修正，识别出了什么后果严重的错误？为什么说架构师首先是一个工程师（第8章六项底座）？③ 反身：你上次把某个概念从'见过的框图'推到'拥有的涵义'，是什么时候？

**Q10（落地生根 · 回部门）**
"结合你们部门现状，给你们的系统写一份'老规矩'清单（参照老周那天晚上把老规矩写下来）：先用架构三问筛出'少了它就不是这个系统'的决定，再分设计准则/演进准则两栏，再用一条真实场景横穿检验，最后用'约束即解放'复核每条约束解放了什么重复决策——给出最该补的三件事，每个落到一个动作。"
追问：① 三问筛的时候，最容易把哪一类'重要的事'误当架构？（可调参数 / 团队习惯 / 技术选型）② 架构是保真压缩（共享心智模型）——新成员入门、跨团队协作、决策讨论时，你们的'架构'提供共同语言吗？康威定律：构件边界 = 团队边界——你们的构件边界和团队边界对齐吗？③ 恒信四张图对不上——你们团队有没有类似的对不上？④ 两周后回来报告：哪条决定用三问筛出是/不是架构？
