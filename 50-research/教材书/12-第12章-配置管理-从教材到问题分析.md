## 第 1 步 · 剖章立骨：核心内容地图

**这一章回答的问题**：让一直在变的东西说得清——配置管理到底是干什么的？为什么"版本号有了"不等于"配置管理做好了"？它守护的又是什么（第11章那些不可逆决策）？

**三幕对齐（省一步推导）**：
- **第一幕 是什么（定界）**：1.1 配置三词解耦（配置项/配置/配置信息，锚定实体）→ 1.2 三个隐形过滤器（配置三问）→ 1.3 版本（时间轴上的演进刻度 + 版本判据一问）→ 1.4 基线（被批准冻结的参照 + 三特征）→ 1.5 三种正式基线（功能/分配/产品 + 运行部署配置）—— 喂第一组·概念题（见树见林）；
- **第二幕 不是什么（磨边弧）**：2.1 配置不是参数文件（变与不变的分离）→ 2.2 版本不是基线（一横一竖：里程桩 vs 收费站）→ 2.3 变体不是版本（空间与时间正交）→ 2.4 没有基线，变化就不可言说 —— 喂真悖论·辨边界题；
- **第三幕 往哪去（运用）**：3.1 变更控制（冻结→变更→再冻结）→ 3.2 四大活动（标识/控制/状态记录/审计）→ 3.3 核心目的三问（配置管理三问）→ 3.4 配置管理=架构决策的守护者 → 3.5 契约链 → 3.7 三条铁律 + 可剪裁 → 3.9 经济价值 —— 喂第二组·落地 / 方法时刻题（规则 15）。

### 核心概念

1. **配置**（configuration）：实体被记录在配置信息里、相互关联的功能特性与物理特性——实体"被记录下来的样子"（ISO 10007）。判据：配置三问（记录了吗 / 功能物理特性吗 / 关联成整体了吗——三问全"是"才是配置）。它提供"内容"。
2. **版本**（version）：配置项的初始发布或其后基于完整构建的重新发布（ISO/IEC/IEEE 24765）——时间轴上的演进刻度，回答"走到第几步"。判据：版本判据一问（这一个编号能精确对应到"哪一次完整构建"吗？能——是版本；不能——还不算版本）。它提供"位置"。
3. **基线**（baseline）：经批准、确立了产品在某一时点的特性、作为全生命周期各项活动参照的配置信息（ISO 10007:2017）——被批准冻结的参照。判据：基线三问（被批准了吗 / 被冻结了吗 / 全生命周期拿它作参照吗——三问全"是"才是基线）。它提供"资格"。

### 关联概念（近界 · 辨析）

- **配置项 / 配置 / 配置信息 三分离**：三者都锚定"实体"，不再互引——配置项=被纳入管理的实体（对象·管哪些）、配置=实体被记录的关联功能+物理特性（属性·它是什么样）、配置信息=记录特性的资料（记录·拿什么核对）。体检比方：人是配置项、身高体重是配置、体检档案是配置信息。最大坑：文档既是"配置信息"（它描述谁）又可以是"配置项"（它自己要不要被管）——两个层面不冲突。
- **版本 / 修订 / 变体 / 基线 四词**：版本=时间先后（走到第几步，对外整体编号）、修订=内部变更次数（Rev A/B/C，更细）、变体=空间并存（有几种形态，与版本正交）、基线=被批准冻结的参照（哪一版被盖章）。基线 = 变体 × 版本的交叉点被盖章。
- **配置 × 版本 × 基线 三分工**：配置提供"内容"、版本提供"位置"、批准提供"资格"——三者齐备，才成一个基线。
- **配置三问 vs 配置管理三问（防撞名）**：配置三问验"一个东西算不算配置"（记录了吗？功能物理特性吗？关联成整体了吗？）；配置管理三问验"整个产品的配置管理做到位没有"（应该是什么 / 实际是什么 / 怎么变成这样的）。一把管单个概念，一把管整体目的。
- **变与不变的分离 ↔ 第11章推迟决策**：可变的部分（参数/开关/选项）外置、不变的核心（代码/逻辑/功能）只写一遍——正是第11章"显式推迟"的工程形态（让还可能变的东西保持可替换）。
- **配置管理 ↔ 第11章架构决策**：决策记录六问↔配置信息、不可逆决策识别↔基线冻结、推迟决策↔变与不变的分离、变更影响分析↔变更控制——第11章的尺子，第12章给它们配了流程。
- **契约链 ↔ 第6章设计链**：需求→方案→实现，每一对相邻环节都是一组局部"甲方-乙方"——基线是每一级契约的冻结端、版本是交付端（ISO/IEC/IEEE 15288 需方-供方协议）。
- **基线 ↔ 第4章需求基线**：第4章讲"基线是变更的出发原点"（需求管理视角）；本章把原点推广到所有配置项（固件/硬件/代码/图纸/数据）。
- **配置管理 ↔ 第13章治理**：谁有资格批准基线、谁有资格裁决变更——超出配置管理本身，是治理的领地（本章结尾抛给第13章）。

### 对立概念（远界）

| 概念 | 对立面 | 问什么 |
|---|---|---|
| 配置 | 参数文件 | 装好的整机 vs 零件清单——参数是零件，配置是装好的整机 |
| 配置 | 实体的全部客观特性 | 被管理起来的那部分特性 vs 全部特性（三个隐形过滤器切出子集） |
| 版本 | 基线 | 刻度（流动） vs 参照（冻结）——把版本当基线 = 把里程桩当收费站 |
| 版本 | 变体 | 时间（先后因果） vs 空间（并存差异）——二者正交 |
| 版本 | 修订 | 对外整体编号（较粗） vs 内部变更次数（更细） |
| 基线 | 流动状态 | 受控（线右变化必须走变更控制） vs 自由（线左版本自由流动） |
| 基线 | 快照 | 批准+冻结+参照三合一 vs 纯记录（快照是记录，基线是"三合一"） |
| 基线 | 发布 | 参照 vs 交付给用户的动作——发布的东西通常取自基线，但两者不是一个概念 |
| 配置管理 | 版本管理 | 四大活动循环 vs 一个时间刻度——版本管理做好了 ≠ 配置管理做好了 |
| 配置管理 | 文档管理 / 资产管理 | 守护产品全部历史与未来的可答性 vs 归档文件 / 登记财务价值 |
| 配置管理 | 治理 | 守门的工具 vs 掌舵的头脑——治理回答"谁掌舵、谁划桨"（第13章） |

### 核心原理

**第一幕 · 是什么的底层机制**
1. 配置项/配置/配置信息三词互相引用、首尾相连形成循环定义——解耦的方法：往环里引入不依赖任何配置术语的锚点"实体"，让三个概念全部锚定实体、彼此不再互引（1.1）。
2. 配置是实体的全部特性里被三个隐形过滤器切出来的子集：类别边界（只认功能+物理特性）/ 记录边界（只有被配置信息记录/规定下来的才算）/ 关联边界（相互关联的特性整体，不是零散清单）（1.2）。
3. 配置的本质是"组合成形"——configuration ← con-（共同）+ figurare（塑造成形）；中文"配+置"＝配合+安置。它天然是"多体"概念，单个孤立的东西没有配置可言；"从多到一"是 configuration 的全部旅程（即时结果=形 / 正式结果=基线 / 交付结果=实例）（1.1）。
4. 变化是连续的，沟通必须是离散的——版本是把连续的时间切成"可指认的格子"的那把刀（1.3）。
5. 版本解决四个问题：追踪演进（走到哪一步）/ 回溯（回到旧版本）/ 并行（多代共存）/ 复现（版本号是沟通的最小公约数）（1.3）。
6. 基线不是自动生成——从"流动状态"升级为"受控状态"需要一个有权威的动作（被批准）；三特征一个都不能少：被批准（资格）/ 被冻结（状态）/ 作参照（用途）（1.4）。
7. 三种正式基线层层递进：功能基线冻结"目标"（要做什么）/ 分配基线冻结"方案"（由谁实现）/ 产品基线冻结"实物"（实际是什么）；再往下有运行/部署配置——部署的本质就是给某个版本配上某个环境，塑成一个可复现的形态（1.5）。

**第二幕 · 磨边弧的机制（不是什么）**
8. 变与不变的分离：可变的部分（参数）被外置、不变的核心（固件逻辑）只写一遍——所以客户改参数不用重编译；"改一个参数就要改代码、重编译、重发布"是变与不变没分离的信号（2.1）。
9. 版本与时间轴同向（横·流动·刻度），基线与时间轴垂直（竖·切断·闸门）——"横"与"竖"不是上下方向，而是与时间轴的关系：里程桩顺着路排、收费站横在路中间挡住路（2.2）。
10. 变体与版本正交：变体管空间（有几种形态·并存差异）、版本管时间（走到第几步·先后因果）；基线 = 变体 × 版本的交叉点被批准冻结（2.3）。
11. 没有基线，变化就不可言说——描述一个变化必须有一个"从哪变起"的原点；没有原点，'变了'就像在茫茫大海上说"我在动"却没有岸标（2.4）。

**第三幕 · 往哪去的机制（运用）**
12. 变更控制 = 冻结 → 变更 → 再冻结的循环；基线建立之后，任何变化都是"对基线的偏离"，必须走一条正式的路：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线。基线是变更控制的前提，变更控制是基线的守护者（3.1）。
13. 四大活动循环咬合：配置标识管"是什么"（选配置项、立基线）、配置控制管"怎么变"（变更申请→评估→批准→实施）、状态记录管"现在什么样"（记录并报告配置与变更状态）、配置审计管"实物和记录对不对得上"（对照基线核验）——发现不一致，回到标识去修正（3.2）。
14. 核心目的三问：它应该是什么（as-designed，靠需求/设计配置和基线回答）/ 它实际是什么（as-built，靠实物配置和状态记录回答）/ 它是怎么变成这样的（变更历史，靠变更控制和审计回答）——配置管理的全部工作就是让这三个问题在任何时刻都有答案（3.3）。
15. 配置管理 = 架构决策的守护者：决策记录六问↔配置信息（把决定写下来）、不可逆决策识别↔基线冻结（识别出不可逆所以冻结成参照）、推迟决策↔变与不变的分离（保持可变部分可替换）、变更影响分析↔变更控制（个人尺子流程化）——第11章的尺子，第12章给它们配了流程（3.4）。
16. 契约链：链上每一对相邻环节都是一组局部"甲方-乙方"；基线是每一级契约的"冻结端"、版本是"交付端"——这是每一级都重复出现的通用机制，不是某一级专属（3.5）。
17. 三条铁律：产品开发是协作，协作需要共同事实（配置基线）；是长周期，长周期需要组织记忆（配置信息是组织唯一带不走的资产）；要担责，担责需要可答的账（精确召回 vs 全量召回差一个数量级的钱）。配置管理可剪裁——复杂度与产品责任等级匹配，但"版本可指认、变更可追溯"这条底线谁也不能省（3.7）。
18. 经济价值：省钱（返工约 1:10:100:1000 / 报废 / 精确召回）、赚钱（多变体多收入 / 资质=订单 / 交付速度=赢单）、保钱（责任清晰 / 知识资产不流失）（3.9）。

### 本章判据（十三把尺子）

1. **配置三问**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？三问全"是"，才是配置。
2. **变与不变的分离**：核心资产只写一遍，变化的部分外置——"改一个参数就要改代码、重编译、重发布"是变与不变没分离的信号。
3. **配置项/配置/配置信息三分离**：配置项=被管的那个东西（对象）、配置=它被记录下来的该有的样子（属性）、配置信息=记录它的那些资料（记录）——都锚定"实体"。
4. **版本是刻度**：版本回答"走到第几步"；一个版本号必须能精确对应到"哪一次完整构建"（文件名不算）。
5. **基线三特征**：被批准（有权威的盖章）+ 被冻结（任何人不能随意改）+ 作参照（全生命周期拿它对照）——三问全"是"才是基线。
6. **版本顺着流、基线垂直切**：版本沿时间轴排开（流动），基线垂直插入切断时间（受控）；把版本当基线，等于把里程桩当收费站。
7. **没有基线，变化就不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。
8. **变更控制循环**：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线——基线建立后，任何变化必须走这条线。
9. **配置管理四大活动**：配置标识（是什么）→ 配置控制（怎么变）→ 状态记录（现在什么样）→ 配置审计（实物与记录一致吗）——一个都不能少。
10. **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
11. **配置管理守护架构决策**：决策记录↔配置信息、不可逆决策识别↔基线冻结、推迟决策↔变与不变的分离、变更影响分析↔变更控制。
12. **契约链**：需求对方案、方案对实现，每一对相邻环节都是局部甲乙方——基线是每一级契约的冻结端，版本是交付端。
13. **配置 × 版本 × 基线三分工**：变体管空间（有几种形态）、版本管时间（走到第几步）、基线管资格（哪一版被盖章）——配置提供"内容"，版本提供"位置"，批准提供"资格"；三者齐备，才成一个基线。

## 第 2 步 · 量学立标：掌握清单

### 概念层（应能定义与辨析）

1. 能定义"配置"=实体被记录在配置信息里、相互关联的功能+物理特性（"被记录下来的样子"，ISO 10007），并辨析 配置 ≠ 参数文件（参数是零件，配置是装好的整机）。
2. 能辨析 配置项/配置/配置信息 三词各回答的问题（管哪些 / 它是什么样 / 拿什么核对），说明三者都锚定"实体"、为什么文档既是"配置信息"又是"配置项"。
3. 能定义"版本"=时间轴上的演进刻度（初始发布或基于完整构建的重新发布，ISO/IEC/IEEE 24765），说出版本四用（追踪演进/回溯/并行/复现），并说出版本号三段规则（SemVer 主.次.补丁）。
4. 能辨析 版本/修订/变体/发布（时间先后 / 内部次数 / 空间并存 / 交付动作），说明变体与版本正交。
5. 能定义"基线"=被批准冻结的参照（被批准+被冻结+作参照三特征），说出基线 ≠ 版本 / 发布 / 快照。
6. 能说出三种正式基线（功能=要做什么 / 分配=由谁实现 / 产品=实际是什么）及建立时机（需求批准/功能分配定案/产品定型交付），并说明运行/部署配置与三大基线同内核。
7. 能定义"配置管理"四大活动（标识/控制/状态记录/审计）及各自回答的问题，说出完整 CM = 规划 + 四活动循环。
8. 能说出配置管理三问（应该是什么/实际是什么/怎么变成这样的）并区分配置三问（单概念 vs 整体目的）。
9. 能定义"契约链"（基线=冻结端、版本=交付端；每一级重复的通用机制）。
10. 能说出配置管理与第11章架构决策的四组同构（决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟↔变与不变分离 / 影响分析↔变更控制）。

### 原理层（应能解释为什么）

1. 能解释为什么三个配置术语互相引用会形成循环定义，解耦为什么锚定"实体"。
2. 能解释为什么配置是"被管理起来的那部分特性"（三个隐形过滤器：类别/记录/关联边界）。
3. 能解释为什么"configuration"的本质是"组合成形"（con-+figurare / 配+置），为什么它天然是"多体"概念。
4. 能解释为什么变化连续、沟通必须离散（版本是把时间切成可指认格子的刀）。
5. 能解释为什么基线必须"被批准"（流动→受控需要一个有权威的动作）、"被冻结"（随意改基线=拆参照系）、"作参照"（全生命周期拿它对照）。
6. 能解释为什么版本横着流、基线竖着切（与时间轴的关系：刻度 vs 闸门；里程桩 vs 收费站）。
7. 能解释为什么变体与版本正交（空间并存 vs 时间先后），为什么基线 = 变体 × 版本的交叉点被盖章。
8. 能解释为什么没有基线，变化就不可言说（描述变化需要一个"从哪变起"的原点，没有岸标）。
9. 能解释为什么"改一个参数就要改代码、重编译、重发布"是变与不变没分离的信号（可变部分被焊死在不变核心里）。
10. 能解释变更控制循环为什么是"冻结→变更→再冻结"、基线为什么是循环支点（基线是变更控制的前提，变更控制是基线的守护者）。
11. 能解释为什么四大活动一个都不能少（用冰链固件事故四个洞：标识没立基线/控制没影响评估/记录只有一句/审计从没做）。
12. 能解释配置管理为什么是架构决策的守护者（四组同构的机制；个人尺子靠自觉，流程靠结构）。
13. 能解释契约链为什么"基线对谁、版本对谁"经常绕晕团队（每一级都重复出现的通用机制，只因视角不同看起来"属于"不同的人）；技术契约 vs 商务契约勿混。
14. 能解释三条铁律（协作要共同事实 / 长周期要组织记忆 / 担责要可答的账）与可剪裁原则（复杂度与产品责任等级匹配，"版本可指认、变更可追溯"底线不省）。

### 判据层（应会用）

1. **配置三问**：记录了吗（记录边界）/ 功能物理特性吗（类别边界）/ 关联成整体了吗（关联边界）——三问全"是"才是配置。
2. **版本判据一问**：这一个编号能精确对应到"哪一次完整构建"吗？能——是版本；不能（如只有文件名）——还不算版本。
3. **基线三问**：被批准了吗？被冻结了吗（任何人不能随意改）？全生命周期拿它作参照吗？——三问全"是"才是基线。
4. **一横一竖判据**：它顺着流（版本）还是竖着切（基线）？问一句"这一版有没有被批准、被冻结、拿它作参照"。
5. **变体/版本/基线判断口诀**：问"有几种形态"→变体；问"改到第几版"→版本；问"这个版本的这个形态"→基线。
6. **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
7. **变更控制五步**：变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线——哪一步跳过了、代价是什么。
8. **四大活动**：标识（是什么）/ 控制（怎么变）/ 记录（现在什么样）/ 审计（实物与记录一致吗）——逐活动打勾"有/缺/半吊子"。
9. **变与不变的分离判据**："改一个参数就要改代码、重编译、重发布" = 没分离的信号。
10. **契约链判据**：每一级契约都有冻结端（基线）和交付端（版本）；开发链内部是技术契约，完整外部甲乙方多一层商务契约。

### 纠错红线十条

1. **先表态后翻案**：先让学员说"版本号不是有吗？配置管理不就做好了吗"，再翻，不让结论先入。
2. **反转精确不造新误解**："基线不能改"别翻成"基线可以随便改"——要分清"冻结"与"死锁"（改必须走变更控制、改完建新基线）；"配置≠参数文件"别翻成"参数不重要"；"没有基线变化不可言说"别翻成"版本没用"。
3. **判据配机制**：每条反转都有"为什么"（机制）和"怎么当场验证"（判据）——如基线三问的"为什么"是"从流动升格受控需要一个权威动作"。
4. **归责到可对照动作**："你没在做配置管理"落到"四大活动缺哪几个 / 基线三问哪一问答不上 / 版本号能不能对应完整构建"，不归咎"人不上心"。
5. **教机制不教断言**：教"为什么没有基线变化就不可言说"（描述变化需要"从哪变起"的原点、没有岸标），不教"要有基线"。
6. **先立尺子再翻案**：先给基线三问/版本判据/配置三问，再翻老周"我们有版本号啊"、小王"我有日期文件夹"。
7. **拉开强度层次**：★★★ 常识（配置=参数 / 版本管理=配置管理 / 有版本号=有基线 / git 历史=基线）重点翻。
8. **每个纠正落到可操作动作**：讨论完给"回去做一件事"（如给最大配置项过一遍基线三问、四活动打勾）。
9. **单一权威不另立标准**：判据引用书（本章判据 13 条 + ISO 10007 / ISO/IEC/IEEE 24765 / ISO/IEC/IEEE 15288 / SemVer），不发明新尺子。
10. **网搜当佐证**：N1~N7 只作"这不是书里一个人的说法"佐证，药与判据全在书内；有超出书处须标注由作者裁决。

## 第 6 步 · 化尺为用：落地工具

### 作业指南（主产出）：给团队最大的配置项做一次"配置管理体检"

> 目标：用本章的配置三问、版本判据、基线三问、四大活动、配置管理三问，对团队最大的一个配置项做一次完整配置管理体检，产出三件可执行改进。
> 场景：回部门落地。时长：一次 60 分钟；两周后复查。

1. **挑配置项（先立枢纽）**：选一个"你心里最有底、天天在用"的配置项——产品的主程序 / 固件 / 核心服务 / 数据表定义。最自信的，往往是基线三问最没打勾的。
2. **过配置三问（这算不算配置）**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——确认它是配置，不是零散参数。**话术**："你说的'配置'，是那页参数，还是那整套关联成形的形态？"
3. **查版本判据（有版本吗）**：当前的版本号能精确对应到"哪一次完整构建"吗（哪个代码提交、哪次构建、包含哪几条变更）？答不出——它连版本都不算，更遑论基线。
4. **过基线三问（有基线吗）**：有没有一版被批准（谁批的、有没有记录）？被冻结（改它不能随手改、必须走变更控制）？全生命周期拿它作参照？——三问缺一，只是刻度不是基线。
5. **四活动打勾（标识/控制/记录/审计）**：配置标识——它在配置项清单里吗、有基线定义吗？配置控制——最近一次变更走 CR → 影响评估 → CCB 批准 → 实施 → 新基线了吗？状态记录——现在跑的是哪一版、升级历史有台账吗？配置审计——线上/实物 vs 记录对得上吗、抽查过吗？
6. **答配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——三问任一答不出，就是最该补的活动。
7. **出体检报告**：四活动各下结论（有 / 缺 / 半吊子），**最该先补的是"答不出三问"对应的那个活动**；最后一条建议照书抄——先给最大的配置项补一版"被批准、被冻结、作参照"的基线，把"这一版"从刻度升级成参照。

**卡住怎么判断**：答不上来的那一问就是最该补的；基线三问一问答不出 = 只是版本不是基线；"没有记录"的地方就是配置审计失守可能潜伏的地方。不用四活动全查完，找到第一个答不出的项目就能开工。

### 工作检查单（配套素材）

| 检查项 | 是/否 | 否 → 可讨论发现 |
|---|---|---|
| 配置三问：被记录了吗 / 功能物理特性吗 / 关联成整体了吗 | □ | 答不出 = 它只是参数，不是配置 |
| 版本判据：版本号能精确对应哪一次完整构建吗 | □ | 只有文件名/日期文件夹 = 还不算版本 |
| 基线三问：被批准了吗 / 被冻结了吗 / 全生命周期作参照吗 | □ | 缺一问 = 只是刻度不是基线；"有版本号≠有基线" |
| 配置标识：在配置项清单里吗 / 有基线定义吗 | □ | "我们管哪些东西"说不清 = 标识缺位 |
| 配置控制：最近变更走 CR→影响评估→CCB→实施→新基线吗 | □ | 哪步跳过了、代价是什么（影响评估一查就拦住随手改） |
| 状态记录：现在跑哪一版 / 升级历史有台账吗 | □ | 只有一句"已推送 v2.3" = 追溯时查不清 |
| 配置审计：实物/线上 vs 记录一致吗 / 抽查过吗 | □ | 账实不符 = 审计没做，追溯即"查不清" |
| 配置管理三问：应该是什么 / 实际是什么 / 怎么变成这样的 | □ | 任一答不出 = 最该补的活动 |
| 变更控制分级：高不可逆走 CCB、低可逆快速走吗 | □ | 一刀切多开会 = 拖慢交付；不控制 = 事故回滚 |

## 第 7 步 · 淬问成题：题卡（10 题 2×5）

### 第一组 · 概念与原理（5 题）

**Q1（破题 · 见树见林① · 概念本身）**
"疾控审计员问老周：这批疫苗四月运输、全程温度记录正常——你们要证明，这批记录是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？老周说：这简单，查版本号，v2.1、v2.2、v2.3 都标着呢。可结果查不清。为什么'版本号是有了'，'这批记录是哪一版采的'还是答不上来？这一章要钉的三个词——配置、版本、基线——各管什么？"
追问：① 配置提供"内容"、版本提供"位置"、批准提供"资格"——三者为什么谁也不能替谁？② 老周的 v2.3 是版本还是基线？基线三问一答就穿帮，穿在哪一问？③ 老周缺的是配置管理四大活动（标识/控制/状态记录/审计）里的哪几个？④ 反身：你们产品里"被批准、被冻结、全生命周期拿它对照"的那一版，能一指就指出来吗？

**Q2（见树见林② · 概念关系）**
"请给出 配置、配置项、配置信息 三词的关系；再给出 版本、修订、变体、基线 四词的关系——说明为什么'版本顺着流、基线垂直切'，为什么变体与版本正交，为什么基线是变体 × 版本的交叉点被盖章？"
追问：① 三个配置术语互相引用、首尾相连，为什么锚定'实体'后就不循环了？② 一份文档为什么既是'配置信息'又是'配置项'——两个层面怎么不冲突？③ 契约链：需求对方案、方案对实现，为什么说基线是每一级契约的'冻结端'、版本是'交付端'？④ 反身：你平时说的'版本'，到底指的是四词里的哪一个？

**Q3（真悖论 · 参数文件是配置吗）**
"小赵指着 App 设置页说：这就是咱们的配置，客户能改的都在这页——温度上报间隔、超温告警阈值、断电告警开关、蜂鸣器音量。小林却说：配置不是这个参数，是那整套关联在一起塑成的'M3 的行为形态'。参数文件到底是不是配置？什么判据分清'配置'和'配置信息里的一个条目'？"
追问：① 变与不变的分离——为什么客户改上报间隔不用动固件、不用重编译（可变部分被外置），反过来改一个参数就要改代码、重编译、重发布是什么信号？② 三个隐形过滤器（类别/记录/关联边界）怎么从'实体的全部特性'切出'配置'子集？③ 反身：你们产品里'客户能改的那几个开关'，到底是配置，还是配置信息里的条目？

**Q4（真悖论 · 版本有了就有基线吗）**
"老周觉得冤：我们有 v2.1、v2.2、v2.3，版本号都标着呢，升级也走流程了、小赵也验证过了，怎么就不算配置管理了？这一章说：版本只是刻度，基线才是参照；版本顺着流、基线垂直切。既然版本和基线都跟时间有关，为什么说它们方向完全不同？什么判据一眼分清'它是版本还是基线'？"
追问：① 里程桩 vs 收费站——为什么版本'顺着路'、基线'挡住路'？② 基线三问（被批准/被冻结/作参照）一问答不出会怎样？③ 变体与版本为什么正交（有几种形态 vs 走到第几步）？④ 第11章说不可逆决策要提前投资——这一章给'投资之后'配了什么守护（基线冻结 / 变更控制）？

**Q5（原理 · 没有基线变化就不可言说）**
"『从基线出发，一切变更都可描述；离开基线，一切变化都不可言说。』这句话凭什么成立？为什么'有 git 历史'替代不了基线？"
追问：① 描述一个变化必须有一个'从哪变起'的原点——没有原点像什么（在茫茫大海上说'我在动'，却没有岸标）？② git 历史是记录，基线是批准+冻结+作参照——两者差在哪一个动作（批准）？③ 基线建立之后，变化怎么走（变更控制五步在守什么）？配置管理的全部工作为什么是让'三问'任何时刻都有答案？

### 第二组 · 落地与实践（5 题）

**Q6（判据运用 · 配置三问 · 案例进展①）**
"老周抱着一台已出厂的 M3，翻来覆去想小林的话：App 设置页上客户能改'上报间隔'、'告警阈值'——这到底是不是配置？小林反问：你改那个'告警阈值'，改的是什么？请用配置三问给'告警阈值'做一次裁决：它是配置，还是配置信息里的一个条目？"
追问：① '告警阈值'单独过三问，和'上报间隔 + 告警阈值 + 断链判定逻辑 + 采集算法'合起来过三问，结论差在哪——为什么是'关联成整体'那一问在起作用？② 为什么审计员问'这批记录是哪一版固件采的'，问的不是参数、是形态（哪套采集逻辑+判定逻辑组合成的行为）？③ 反身：你们最常改的那个参数，改了之后'这台产品当时是什么样'还能说得清吗？

**Q7（判据运用 · 版本判据 + 基线三问 · 案例进展②）**
"恒信运维小王每次发布把构建产物扔进日期文件夹：'2026-05-12''2026-05-18'。两个月后合同状态流转 bug 暴露，李工要'回滚到上上个版本'，打开'2026-05-18'文件夹——里面 final.zip 和 final_2.zip 分不清哪个是哪个。Ada 说：'final_2 连版本都算不上，遑论基线。'请把这句话的量尺摆出来——用版本判据和基线三问，final_2 到底差在哪？"
追问：① 版本判据一问：final_2 能精确对应到'哪一次完整构建'吗（哪个代码提交、包含哪几条变更）？② 基线三问：它被批准了吗 / 被冻结了吗 / 作参照了吗？③ 为什么说'版本是回滚的地址，基线是变更的参照'——恒信补了发布基线后，'上上个版本'从猜测变成了什么（一句可执行的指令）？④ 反身：你们上次回滚，'回滚到哪'能一指就指出来吗？

**Q8（判据运用 · 四大活动 + 配置管理三问 · 案例进展③）**
"冰链补了配置管理，做了一次'合规的固件升级'：老周先写变更申请、做影响评估（'固件行为变化，历史温度记录的采集与判定逻辑随之变化，需知悉在役设备批次分布'）；小林把升级提到变更控制会（老周汇报、小赵评估、阿凯确认云端兼容、小林拍板），固件 v2.4 升为新固件基线；每台设备从哪一版升到哪一版、升级时间、结果进版本台账；三个月后小赵抽查二十台，一台台账写 v2.4、实物还是 v2.3（升级失败未重试），记录修正、补推送。请用四大活动（标识/控制/状态记录/审计）复盘这次升级——哪一步在防'批次追溯查不清'？哪一步在防'实物与记录对不上'？"
追问：① 四大活动各回答什么问题（是什么/怎么变/现在什么样/实物与记录一致吗）？② 冰链旧事故四个洞（固件没立基线/升级没影响评估/只有一句已推送/从没审计），这次升级补了哪几个？③ 配置管理三问——这次升级让'它是怎么变成这样的'答得上来了吗？④ 配置管理守护的是第11章那些不可逆决策——冰链固件升级、恒信编号规则，各对应四组同构（决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟↔变与不变分离 / 影响分析↔变更控制）里的哪一组？⑤ 反身：你们团队四大活动哪一个是'半吊子'？

**Q9（方法时刻 · 规则 15 · 判据主义 = 判据运用题）**
"这一章的方法底座时刻是判据主义：不给没有判据的定义——版本和基线都不靠感觉认，靠可检验判据验。请亲手给'版本'立一条判据，再给'基线'立一条判据——按判据主义三问自检：它是什么（版本能精确对应'哪一次完整构建'吗 / 基线被批准+被冻结+作参照吗）？它的失效边界在哪（什么样的编号够不上版本 / 什么样的版本够不上基线）？能不能举出一个反例（文件名不是版本 / 没被批准的版本不是基线）？"
追问：① 你把'配置提供内容、版本提供位置、批准提供资格'的哪半句编进了判据？三者为什么缺一不可才成一个基线？② 一横一竖：你立的版本判据测'顺着流'、基线判据测'竖着切'——各自指向哪个特征？③ 反身：你刚给'基线'立的判据，拿到你们部门最大的配置项上量一下——合格吗？——只有版本号只是见过，有判据才算拥有。

**Q10（落地生根 · 回部门配置管理体检）**
"结合你们部门现状，用配置三问、版本判据、基线三问、四大活动四个判据，给你们最大的一个配置项做一次'配置管理体检'——给出最该改进的三件事，每个落到一个动作。"
追问：① 四活动（标识/控制/状态记录/审计）先查哪两个？② 你们最近一次'追溯'或'回滚'查不清的地方，缺的是版本、基线、还是状态记录？③ 画出你们开发链三层（需求→设计→实现），每层'基线（冻结端）'和'版本（交付端）'分别是什么？④ 两周后回来报告：哪个判据测出不合格、补了哪个动作。
