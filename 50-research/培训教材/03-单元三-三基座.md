## 一、单元导读

### 主题

这一章发的不是词，是**三把尺子**——需求（定标尺）、设计开发（造标尺）、质量（读标尺），以及把它们咬成一个拆不掉的基座的那条链：**定标尺 → 造标尺 → 读标尺**。它回答三个更根本的问题：这三个词各是什么？设计开发从哪开始、到哪结束？"等级高"为什么不等于"质量好"、"质量 vs 进度"为什么不是二选一？本章的骨架是：**三兄弟**（需求/设计开发/质量，各带定义、溯源、判据）→ **三条边**（起点边界·可转化、终点边界·止于可实现、参照边界·等级≠质量）→ **运用**（程度三步、质量vs进度、基座三角）。

### 开场破题（对应章首误解现场）

念出冰链科技周五下午那场评审会：产品经理文正把一页参数对比表拍到桌上——"我们 M3 温度精度做到 ±0.3℃，竞品只有 ±0.5℃；保温时长 72 小时，竞品 48 小时；重量还轻了 2 公斤。**质量绝对没问题。** 现在唯一的悬念是宣传口径。"会议室一片点头，有人轻轻鼓掌。坐在上首的产品开发经理永兵也点了头，在评审结论栏签下"**通过**"："三个参数全线领先，**质量这一关，我看不出问题在哪**。"只有坐在角落的测试李旭弱弱举起手："那……测试判据是什么？"文正摆摆手："技术方案都定了，测试判据后面自然会有。先定宣传口径。"

让各组表态：文正说的是"质量"吗？产品开发经理永兵都签"通过"了，质量这一关就真的过了吗？李旭那句被淹没的"测试判据是什么"，宣告了什么？"技术方案做完了"，设计开发结束了吗？

### 本单元要反转的直觉

- **参数比竞品高 = 质量没问题**（× 那是等级，不是质量；质量 = 特性满足需求的程度）
- **技术方案做完了 = 设计开发结束**（× 止于"可实现"，八个方案齐备才算）
- **客户没写进合同 = 不用做**（× 隐含需求是需求，漏了是缺陷）
- **质量 vs 进度 = 二选一**（× 同一份需求集合内部打架；进度本身是需求）
- **质量 85 分 = 客观精确**（× 程度是认定不是计算；关键特性不能被摊平）
- **需求 = 用户说出来的话**（× 明示/隐含/必须履行三形态并列）
- **口头改需求最方便**（× 口头"差不多就行"是偷换需求）
- **和客户一起砍需求 = 降质量**（× 单方面砍 = 偷换，一起剪 = 变更）
- **质量 = 档次高、用料好**（× quality 从"档次、用料"漂移到"符合需求的程度"——本章最大反转）
- **构思、定义、设计开发 = 三个并列流程**（× 构思/定义是设计开发内部的发散/收敛段——容器-子段非并列；先想（构思）再选（定义）才是"转化"）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 质量是什么 + 章首破题 + 质量溯源（概念本身）→ Q2 三角关系 + 三条边 + 需求/设计开发溯源（概念关系）→ Q3 等级 vs 质量（真悖论）→ Q4 终点在验证之前（真悖论）→ Q5 质量 vs 进度（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 需求开发/设计开发边界（判据运用）→ **Q7 方法时刻·判据主义·立质量判据 + 转述**（规则 15：亲手立判据 + 三五句话讲给外行）→ Q8 程度三步 + 85 分陷阱（判据运用）→ Q9 与相关方一起剪裁（判据运用）→ Q10 回部门三基座体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"质量"是温度精度，IT 组的"质量"是查询响应时间——**同一个概念、两个世界、判据不变**；"八方案"在硬件是物料/制造/工艺，在软件是数据/接口/部署/安全。这正是"这套概念不挑行业"的现场证明。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜文正说的"质量没问题"，是质量吗？**
"冰链的评审会上，文正指着参数表说：'我们 M3 温度精度 ±0.3℃、竞品 ±0.5℃；保温 72 小时、竞品 48 小时；重量还轻 2 公斤。质量绝对没问题。'坐在上首的产品开发经理永兵也点了头，在评审结论栏签下"通过"：'三个参数全线领先，质量这一关，我看不出问题在哪。'——质量是什么？按 ISO 9000 的定义拆开讲。文正说的是'质量'吗？永兵这个"通过"签得对吗？"

追问：① 质量定义三关键词（固有 / 满足 / 程度）各管什么——"固有"把什么排除在外（赋予特性：价格/品牌/交付时间）？"满足"是判定还是除法？"程度"是形容词还是数字？② ±0.3℃ 超出需求 ±0.5℃ 的那 0.2℃，在质量上是什么（过度设计，只加成本不加质量）？这给"砍需求"提供了什么抓手（砍过度设计是唯一既省时间又不伤质量的操作）？③ 质量这个词从哪来（quality ← 拉丁 qualitas"如何"；原指"档次、用料"，ISO 9000 纠正为"特性满足需求的程度"——这一漂为什么是本章最大反转）？④ 永兵签"通过"的依据是什么——"三个参数全线领先"比的是等级还是质量？质量判据缺席时，签字是什么（决策者跟着看走眼、比参数不问题本质——这是第5/7章他会回头认的账）？⑤ 你最近一次说"质量没问题"或签"通过"，依据的是什么——需求，还是参数？

**Q2｜三个词什么关系？三兄弟各从哪来？**
"请画一张三角图，标出 需求、设计开发、质量 三个词和它们之间的三条边（起点 / 终点 / 参照），并说明：为什么这三个词互为定义、拆不掉？"

追问：① 三条边各是什么判据（起点=可转化四闸门 / 终点=止于可实现·八方案 / 参照=程度三步·等级≠质量）？哪个词是"元概念"、哪个是"桥"（需求/质量=元概念·地基，设计开发=领域机制·桥）？② 三兄弟各从哪来——需求（requirement ← 拉丁 requirere"要求、寻求"；原指"要的东西"，后漂移出明示/隐含/必须履行三形态，ISO 9000 固化——这正是第1章说的术语会漂移）、设计开发（design ← 拉丁 designare"标注、指明"；"设计开发"是 ISO 9000 用 design and development 完整表述的"需求转化"这一件事，别拆成"设计+开发"两件事）、质量（quality ← 拉丁 qualitas"如何"；从"档次用料"漂移到"符合需求的程度"）——三兄弟的词源为什么都藏着一次"漂移"？③ 检验一个词是不是基座，用什么判据（"每一个为什么都能从三角推出来"——V 模型为什么是 V、IPD 为什么有 TR、为什么需求要追溯矩阵、为什么变更要控制）？④ 你们部门的"设计完成"怎么判定——技术方案做完，还是八方案齐备？⑤ **设计开发内部怎么运转**——构思/定义/设计开发是三个并列流程还是包含关系？构思（conceiving·打开可能性·发散）和定义（defining·终结漂浮·收敛）为什么都在设计开发（3.4.8 转化容器）**里面**？转化为什么"先想（构思）再选（定义）"？这落到第6章结对六步是哪两步（③出方案/⑤做裁决）、落到第11章三动词链是什么（分形递归的内芯）？"三动词"为什么刻意不叫"三兄弟"（"三兄弟"已指需求/设计开发/质量）？

**Q3｜"高档车可以是差质量"自相矛盾吗？**
"'高档车可以是差质量，低档车可以是好质量'——这句话是不是自相矛盾？好车怎么质量差？"

追问：① 符合性 / 质量 / 等级三词各回答什么问题（满足了吗 / 满足到什么程度 / 按哪套需求分类）？它们都以什么为参照（需求 = 设计开发定出的标尺）？② 把精度做到行业第一，对 M3 的质量贡献了什么（超出需求区 = 只加成本不加质量 = 过度设计）？③ 你们把"指标比竞品高"当绩效，还是当过度设计？砍过度设计是唯一"既省时间又不伤质量"的操作——你们敢砍吗？

**Q4｜设计开发结束于"可验证"吗？**
"有人主张设计开发结束于'可验证'——需求写清楚了就能验证了，不就完了吗？但书里说这是'循环倒置'。为什么？那设计开发到底到什么时候算完？"

追问：① 验证的参照是什么（规定需求 = 设计开发的输出）？为什么"验证能发生"就证明"设计开发已经结束"（循环倒置）？② 如果"可验证"当终点，怎么区分完成与未完成（验证的客观证据可以是文件评审，那几乎所有写清楚的需求都可验证）？③ 终点落在哪（止于"可实现"——八方案齐备：技术/物料采购/制造/测试/交付/部署/操作/运维）？为什么终点由"最后一个配齐的方案"决定，不由"第一个完成的技术方案"决定？④ 层1原理可实现 / 层2方案可实现 / 层3事实可实现——设计开发交付的是哪一层？把"纸面可行"当"真能跑"错在哪？

**Q5｜质量 vs 进度是二选一吗？**
"'质量 vs 进度'是一场冲突吗？保质量就要砍进度，保进度就要降质量——真的是二选一吗？"

追问：① 为什么说进度本身就是一种需求（ISO 9001 §8.2.2 交付时间和交付条件也是顾客要求的一部分）？那"冲突"到底是什么在打（同一份需求集合内部打架）？② 解法为什么不砍质量、而用需求谈判（判真伪 → 走正式变更 → 分清可妥协不可妥协 → 度量可缩不可砍）？③ M3"八周做不完"里有多少是七周返工的起点债（假冲突——改计划不动质量）？你们最近一次"赶进度"，砍的是测试（度量）还是过度设计？

### 第二组 · 落地与实践

**Q6｜你们的工作是需求开发还是设计开发？**
"你们公司一个正在进行的工作：市场调研在整理需求、研发在出方案。用'特性是否被规定'这条判据，各自属于需求开发（8.2）还是设计开发（8.3）？边界画在哪？"

追问：① 设计开发不始于什么（点子）？为什么起点必须是"被研究确认过的需求"（需求"通常是研究的结果"；起点没收好，转化的是错误需求，终点越完美偏离越远）？四闸门哪一道最容易被跳过（隐含需求已识别——最贵的一条）？② 需求规格就是那道闸门——需求开发文档（市场调研/可行性研究/URS）算不算设计开发（概念上算、同构；标准上可合可分；实用判据看特性是否被规定）？③ 把调研文档排除在受控范围外会出什么事（不能不受控、不可追溯——文正立项调研无存档，七周返工连"当时为什么这么做"的记录都没有）？④ 你们最近一次"设计得辛苦、产品没人要"，是终点没管好还是起点没收好？

**Q7｜亲手给"设计开发终点"和"质量"立一条判据，再转述给外行（方法时刻）**
"这一章的方法底座时刻是判据主义——不给没有判据的定义。请亲手给'设计开发终点'和'质量好不好'各立一条可检验判据，再用它当场裁一个你们最近的项目；然后把'质量'用三五句话讲给一个完全外行的人。"

追问：① 你的判据符合判据主义三问吗（是什么 / 失效边界 / 反例）？终点判据——还有哪个环节会在执行时反问"这到底怎么做"？质量判据——特性满足需求的程度，用接收准则比对？② （转述·压缩测试）用三五句话把"质量"讲给完全外行——讲到哪卡住，缺口就在哪？四问与转述测的是同一件事（结构没成型 / 边界没划清）？③ 把这条判据量到你自己头上——你上次宣布"设计完成"，是依据判据，还是依据感觉？

**Q8｜85 分为什么是"一个精确的错误"？**
"李旭给 M3 打了 85 分——温度控制 92、保温 88、外壳做工 90、重量 70，平均。水忠说这是'一个精确的错误'。为什么平均就是错误？那'程度'到底怎么认定？"

追问：① 程度三步（确定特性值 3.11.1 → 与需求比对 3.6.11 用接收准则 → 认定满足程度 3.6.2）——李旭哪一步被跳过了（接收准则：用什么设备测、测多久、抽多少样本、结论写在哪份记录）？② 关键特性（断电告警，8.3.5 d 对预期目的至关重要的特性）为什么不能摊进平均数（安全项失 2 分被"温度控制 92"补回来 = 用假象掩盖致命缺陷）？要么怎样（一票否决或加权不平均）？③ 你们最近一次质量评审，结论是"程度"还是"分数"？判据是什么？

**Q9｜为什么"砍需求"和"单方面砍需求"是两件事？**
"M3 进度亮红灯，文正找疾控中心刘主任砍需求。刘主任三十分钟排完序：断电告警和箱门单手开不能砍、实时推送可降级、重量减 2 公斤是销售吹的可以砍。为什么'砍需求'和'单方面砍需求'是两件完全不同的事？"

追问：① 需求的所有权在谁手里（相关方——需求是顾客的资产，组织只是受托转化；单方面剪掉的那块可能恰是顾客最在乎的隐含需求，他没说但你剪了，事后必炸）？② 剪下来的需求为什么是"挂账"不是"消失"（剪裁 = 排序不是删减；留痕：剪了什么、为什么剪、谁决定的、哪天恢复；下轮迭代是现成输入）？③ 为什么"进度冲突"是隐含需求的显影剂（平时问"你还有什么要求"他答不出，你说"进度不够必须砍一样"他立刻知道答案——刘主任十分钟说出真正在意的）？④ 你们最近一次砍需求，是"和顾客一起剪裁"还是"单方面砍掉"？走了正式变更（8.2.4 / 8.3.6 书面、评审、通知相关方）吗？

**Q10｜给你们的部门做一次三基座体检**
"结合你们部门现状，挑一个进行中的项目，用三把尺子（定标尺 / 造标尺 / 读标尺）做一次'三基座体检'——给出最该做的三件事，每件落到一个动作。"

追问：① 先查哪把尺子？为什么（找不到接收准则 = 从读标尺补起；答不上"到底怎么做" = 从造标尺补起；说不清隐含需求 = 从定标尺补起）？② 体检表里哪一项是你们部门最可能"否"的（四闸门过了吗 / 八方案齐吗 / 有接收准则吗 / 关键特性没被摊平吧 / 变更走正式手续吗）？③ 两周后回来报告：哪把尺子补上了、哪把还虚着、卡在哪个判据上？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 文正说的"质量没问题"，是质量吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "对，参数比竞品强就是质量好。" | 正是要翻的——把等级当质量 |
| 中 | 能背出"质量 = 特性满足需求的程度"，但说不清三个关键词各管什么 | 定义是背的，没拆开"固有/满足/程度" |
| 好 | "±0.3℃ 是固有特性、比的是需求区间内的满足、程度靠认定不靠比参数；超出需求 ±0.5℃ 的 0.2℃ 是过度设计，只加成本不加质量；永兵的'通过'签错了——'三个参数全线领先'比的是等级不是质量；'质量'这个词从拉丁 qualitas（如何）来，原指'档次、用料'，ISO 9000 把它纠正成'符合需求的程度'——这一漂是本章最大反转。" | 定义 + 三关键词 + 过度设计 + 溯源全到位，能当场裁文正与永兵 |

**产品侧 vs IT侧**：产品组举"精度比竞品高 = 质量好"；IT 组换"响应时间比同业快 = 质量好"或"平台名气大 = 质量好"。两边同一个病：**比的是等级，不是质量**。

**反转话术**（对应 §3.2.4 质量定义 + §3.3.3 过度设计 + 章末认知反转）：文正说错了一个字——他想说的不是"质量高"，是"**等级高**"。连坐在上首的产品开发经理永兵也签了"通过"——"三个参数全线领先"比的是等级不是质量，**质量判据缺席时，签字就是盖章**：决策者跟着看走眼、比参数不问题本质，这一笔账永兵会在第5/7章回头认（量产翻车认账 / "第3章那张参数表是我签的'通过'"）。质量 = 客体固有特性满足需求的程度：**固有**（价格、品牌、交付时间是赋予特性，设计开发管不着）、**满足**（符合性判定，不是数量比，两边不同质除不了）、**程度**（差/好/优秀，形容词不是数字）。M3 精度远超需求（±0.3 vs ±0.5），那 0.2℃ 对质量没有贡献，只贡献了成本和复杂度——**那部分不是质量，是过度设计**；砍过度设计是唯一"既省时间又不伤质量"的操作。溯源的钥匙：quality ← 拉丁 qualitas（"如何"），原指"档次、用料"——好东西=好质量；ISO 9000 把它纠正为"符合需求的程度"——**这一漂，是本章要立的最大一个反转**，也是"术语会漂移"（第1章 §1.7.4）在质量上的现场。质量被认定，不被计算——正因为程度可用客观证据认定，它才第一次成为工程上的一把尺子。

**参考答案要点**：质量定义与三关键词见 §3.2.4；过度设计硬判据见 §3.3.3；词源漂移（档次/用料 → 符合需求的程度）见 §3.2.4；章末认知反转见"章末·认知反转"。

### Q2 三个词什么关系？三兄弟各从哪来？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把三个词排成一条线，说不清边 | 关系结构错误——是三角，不是并列清单 |
| 中 | 能画三角（定/造/读标尺），但三条边的判据、元概念/桥、溯源没接上 | 骨架对，判据与溯源缺 |
| 好 | "起点边界 = 可转化四闸门；终点边界 = 止于可实现（八方案）；参照边界 = 程度三步·等级≠质量；三定义互相引用，拆不掉；需求/质量是元概念、设计开发是桥；三词源：requirement ← requirere（要求寻求）、design ← designare（标注指明）、quality ← qualitas（如何）——三兄弟都经历过术语漂移；设计开发内部：构思（发散·打开可能性）与定义（收敛·终结漂浮）是容器-子段，不是并列流程。" | 三角 + 三判据 + 元概念/桥 + 溯源 + **三动词容器-子段**全到位 |

**产品侧 vs IT侧**：产品组画 M3 的三角（定标尺 = -20℃~8℃ 宽范围硬需求、造标尺 = 八方案、读标尺 = 温度精度符合性）；IT 组画恒信的三角（定标尺 = 合同三部门审批流转、造标尺 = 接口/数据/部署方案、读标尺 = 查询响应/审批时效）。两边画的是同一张图——**硬件、软件，基座三角纹丝不动**。

**反转话术**（对应 §3.4.4 咬合 + §3.2.1~3.2.4 溯源）：三兄弟不是三个并列概念，是**互为定义、拆不掉**的一个基座：设计开发（3.4.8）引用需求（3.6.4）；质量（3.6.2）引用需求和特性（3.10.1）；设计开发注一说需求"以特性来规定"。抽掉任何一个，另外两个悬空。层级不完全平级——**需求和质量是"元概念"（横跨一切领域），设计开发是"领域机制"（架在中间的桥）**。溯源给三个词补上"从哪来"：需求 requirement ← 拉丁 requirere（要求、寻求），原指"要的东西"，后来漂移出"明示/隐含/必须履行"三形态，ISO 9000 把这场漂移固化成了标准定义；设计开发 design ← 拉丁 designare（标注、指明），ISO 9000 用 design and development 完整表述"需求转化"这一件事，别拆成"设计+开发"两件事；质量 quality ← 拉丁 qualitas（如何），从"档次用料"漂移到"符合需求的程度"。**三个词源都藏着一次漂移——这正是第1章 §1.7.4 说的术语会漂移。** 再往设计开发内部看一眼（§3.2.3 三动词辨析栏）：**构思（conceiving）、定义（defining）、设计（design）不是三个并列流程，是包含关系**——构思是"打开可能性"（发散：生成 ≥2 个候选"怎么做"）、定义是"终结漂浮"（收敛：画边界、挑定一个），两个都发生在设计开发（3.4.8"把需求转换为更详细的需求"）这个容器**里面**；转化不是一步到位，**先想（构思）再选（定义），发散在前、收敛在后，合起来才是"转化"**。落到第6章结对六步 = **③出方案（构思）与⑤做裁决（定义）**；落到第11章三动词链 = **分形递归的内芯**（每一层设计开发内部都重复这一轮构思-定义-设计）；"三动词"刻意不叫"三兄弟"——"三兄弟"已指需求/设计开发/质量，再叫就撞名。检验一个词是不是基座：**"每一个为什么都能从三角推出来"**——V 模型为什么是 V、IPD 为什么有 TR、为什么需求要追溯矩阵、为什么变更要控制，答案全在三角里。

**参考答案要点**：基座三角见 §3.4.4；三条边判据见 §3.3.1 / §3.3.2 / §3.3.3；元概念与桥见 §3.4.4；三词溯源见 §3.2.1 / §3.2.3 / §3.2.4；终极检验见 §3.4.4。

### Q3 "高档车可以是差质量"自相矛盾吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "自相矛盾——高档车用料好，质量当然好。" | 正是要翻的——把等级当质量 |
| 中 | "等级和质量的参照不同。" 结论对，机制浅 | 三个词各回答什么问题没讲清 |
| 好 | "等级答'按哪套需求分类'（高档/低档），质量答'满足各自需求的程度'；符合性答'满足了吗'（二元）；高档车功能设计有缺陷 → 差质量，低档车按它的需求做到极致 → 好质量；三者都以需求为参照——需求是设计开发定出来的标尺。" | 等级/质量/符合性三词分立 + 参照全到位 |

**产品侧 vs IT侧**：产品组举"M3 精度行业第一还是过度设计"；IT 组举"平台名气大 ≠ 审批系统好用"。两边都要翻"越高越高级 = 越好"——**等级定得高 ≠ 质量好**。

**反转话术**（对应 §3.3.3 参照边界）：三个近亲不是同一个词的不同说法，回答三个不同的问题——**符合性**答"满足了吗"（二元）、**质量**答"满足到什么程度"（程度）、**等级**答"按哪套需求分类"（分级）。高档车可以是差质量：它按"高档"那套需求设计，但功能设计有缺陷，没满足它自己那套需求；低档车可以是好质量：它按"经济型"那套需求做到极致。M3 把精度做到行业第一——只是**等级**定得高，如果需求只要 ±0.5℃，超出部分对"质量"没有贡献。**特性超出需求范围的，不是质量加分，是过度设计——只加成本，不加质量。** 这也给"砍需求"一个干净抓手：砍过度设计，是唯一"既省时间又不伤质量"的操作。三兄弟都以"需求"为参照，而需求（标尺）是设计开发定出来的——这条边收口，判据主义的手法也亮了相：概念靠正例活、靠反例定型。

**参考答案要点**：等级/质量/符合性三栏见 §3.3.3；高档车可以是差质量见 §3.3.3；过度设计硬判据见 §3.3.3；概念靠正例活靠反例定型见 §3.3.3。

### Q4 设计开发结束于"可验证"吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "可验证，需求写清楚能验了就完了。" | 正是要翻的——没看到循环倒置 |
| 中 | "设计开发止于可实现。" 结论对，机制缺 | 为什么"可验证"不行没讲透 |
| 好 | "验证的参照是规定需求 = 设计开发的输出，拿可验证当终点是循环倒置；且几乎所有写清楚的需求都可验证，区分不了完成与未完成；终点是'可实现'——八方案齐备（技术/物料采购/制造/测试/交付/部署/操作/运维），还有环节反问'这到底怎么做'就没结束；交付的是层2方案可实现，不是层3事实可实现——纸面可行≠真能跑。" | 循环倒置 + 判据失效 + 终点话术 + 层1~3 全到位 |

**产品侧 vs IT侧**：产品组答 M3 只做技术方案就宣布完成（采购/制造/测试/交付七个方案没有）；IT 组答恒信只做架构/技术选型（数据/接口/部署/安全方案没有）。两边同一个病：**只到技术方案 = 连环空转**。

**场景复盘**（对应书 案例进展②）：文正宣布"设计完成"、产品进入"等待量产"，量产准备会上采购问"压缩机按什么型号采、合格准则是什么"——没有；逸人三连追问"装配工艺文件呢？""低温密封测试怎么做、用哪套工装？""这套方案产线上到底可不可实现？"——都没接上；李旭问"测试判据是什么、验收标准是什么"——没有；交付团队问"怎么装、怎么部署、怎么培训"——没有；董勐问"追溯平台数据谁备份、App 断连谁发现"——没有。五轮追问下来，七个方案，七个"没有"。水忠一句话点破："**我们以为设计开发结束了。其实它连一半都没走完。**"

**反转话术**（对应 §3.3.2 终点边界，全书最重要的推理）：把候选终点一个一删——"确认通过"错位（确认锚定产品，且发生在形式结束之后很久）；"责任移交点"只是制度动作；**"可验证"是逻辑倒置**：验证（3.8.12）的定义是"对规定需求已得到满足的认定"，而规定需求正是设计开发的**输出**——**验证能发生，前提是设计开发已经结束**。拿"可验证"当终点，等于让设计开发结束在验证的起跑线上。更致命的是：验证的客观证据可以是"文件评审"，那几乎所有写清楚的需求都可验证——这个判据区分不了完成与未完成。所以终点只能落在"可实现"：**需求被细化到足以支撑实现、生产和服务提供可直接执行**。实物上具体化为**八方案**（技术/物料采购/制造/测试/交付/部署/操作/运维），它是"规定需求"按下游环节的分配，**终点由最后一个配齐的方案决定，不由第一个完成的技术方案决定**。三个层次分清：层1原理可实现（技术方案，纸上可行）、层2方案可实现（八方案齐备=设计开发终点）、层3事实可实现（验证确认，终点之后）。设计开发交付的不是事实，是**声明**——一份"可信的可实现声明"，最终裁决权在终点之后的验证与确认。

**参考答案要点**：候选终点一删见 §3.3.2；可验证循环倒置见 §3.3.2；八方案与条款落点见 §3.3.2；层1原理/层2方案/层3事实见 §3.3.2；声明≠事实见 §3.3.2；场景复盘见案例进展②。

### Q5 质量 vs 进度是二选一吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "只能二选一，保质量就砍进度，保进度就降质量。" | 正是要翻的——把内讧当拔河 |
| 中 | "进度也是需求。" 结论对，解法缺 | 冲突本质接上了，怎么解没到 |
| 好 | "进度本身是需求（§8.2.2），'质量 vs 进度'是同一份需求集合内部打架；解法 = 判真伪 → 用需求谈判（走正式变更）→ 分清可妥协不可妥协 → 度量可缩不可砍；砍过度设计是唯一既省时间又不伤质量的操作。" | 本质 + 四步解法全到位 |

**产品侧 vs IT侧**：产品组答 M3"八周做不完"里有多少是七周返工的起点债；IT 组答恒信"上线日期定了，验收标准没法改"。两边都容易先信"二选一"——**真正该谈的是需求集合，不是质量原则**。

**反转话术**（对应 §3.4.3 冲突）：先拆两个伪前提——**质量不是时间的函数**（多给三个月，质量不会自动变好）；**进度本身就是一种需求**（ISO 9001 §8.2.2 交付时间和交付条件也是顾客要求的一部分）。所以"质量 vs 进度"本质是**同一份需求集合内部打架**：性能/功能需求 vs 交付时间需求，不是两个系统拔河，是一份需求清单自己起内讧。解法不是二选一，是重新平衡需求集合：**第一步判真伪**（一半以上是估算失真、计划虚报的假冲突——M3"八周做不完"里，有多少是七周返工浪费的？那一部分不是质量的问题，是起点的债——改计划，不动质量）；**第二步用需求谈判不用质量谈判**（走正式变更，口头"差不多就行"是最危险的变更形式）；**第三步分清可妥协与不可妥协**（必须履行的需求/关键特性不可动，非关键、性能裕量、**过度设计**可动——砍过度设计是唯一既省时间又不伤质量的操作）；**第四步度量环节可缩不可砍**（把验证范围缩到关键特性，别全验；但不验不行）。正道是**与相关方一起剪裁需求**：排序、留痕、挂账。

**参考答案要点**：两个伪前提见 §3.4.3；四步解法见 §3.4.3；三条禁忌见 §3.4.3；与相关方一起剪裁四理由见 §3.4.3；进度冲突是隐含需求显影剂见案例进展④。

### Q6 你们的工作是需求开发还是设计开发？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "市场调研是需求，研发是设计，两回事。" | 边界判据没进来——只凭直觉切 |
| 中 | 能说"需求开发也在转化需求，同构"，但判据说不清 | 同构对，判据缺 |
| 好 | "看特性是否被规定——市场调研还没规定特性 = 需求开发（8.2）；研发开始把需求落到特性上 = 设计开发（8.3）；需求规格就是那道闸门；设计开发不始于点子，始于被研究确认过的需求（四闸门，隐含需求已识别最贵）；调研文档也要受控可追溯。" | 判据 + 闸门 + 四闸门 + 受控提醒全到位 |

**产品侧 vs IT侧**：产品组判断"M3 立项调研 vs 制冷子系统设计"；IT 组判断"恒信 ConOps/URS vs 审批流设计"。两边用同一条判据——**8.2 管'要什么'，8.3 管'怎么实现'，边界看特性**。

**反转话术**（对应 §3.3.1 起点边界 + 案例进展①）：设计开发不始于点子，而始于"被研究确认过的需求"——需求（3.6.4 注 1）"通常是研究的结果"。起点这道闸门怎么过？**需求规格必须满足"可转化"判据——四道闸门**：完整、无歧义、不冲突、隐含需求已识别（隐含需求已识别是其中最贵的一条——它没写进规格，却决定规格对不对）。管理评审时的划界问题：需求开发的文档（市场调研/可行性研究/URS）算不算设计开发？**概念上算、而且同构**——需求开发也是需求转化，同样具备 3.4.8 的特征，只是发生在更靠前、更粗的层级；标准上可合可分（8.2/8.3 只是职责组织方式不同）。**实用判据只有一条：特性是否被规定。** 特性还没开始规定，是需求开发（8.2）；特性开始被规定，才是设计开发（8.3）。必须补的提醒：调研文档不属设计开发，但**不能不受控、不可追溯**——文正"M3 立项调研"如果能受控存档，案例进展①那七周返工至少不会连个"当时为什么这么做"的记录都没有。

**参考答案要点**：研究先于需求见 §3.3.1；四闸门见 §3.3.1；需求开发/设计开发同构见 §3.3.1；特性是否被规定见 §3.3.1；受控提醒见 §3.3.1 + 案例进展①。

|---|---|---|
| 弱 | "设计开发做完就是交付；质量好就是大家都说好。" | 没立判据——还在举例、在说感觉；转述也做不成 |
| 中 | 立了判据，但不可检验（如"质量 = 客户满意"），或判据主义三问没走全；转述讲到一半卡住没追问缺口 | 有判据了，但失效边界/反例没给；卡壳处没落到缺口 |
| 好 | "设计开发终点 = 八方案齐备且执行时不反问'这到底怎么做'（可检验、有失效边界）；质量 = 特性满足需求的程度，用接收准则比对（可复核）；用它当场裁了项目：X 环节还在反问，所以设计开发没结束；把'质量'转述给外行讲到'什么时候不该用'卡住——同一个缺口。" | 两条判据 + 三问 + 当场运用 + 转述互证全到位 |

**产品侧 vs IT侧**：产品组立"M3 质量 = 温度波动是否符合 ±0.5℃ 接收准则"；IT 组立"恒信质量 = 查询响应是否符合多大数据量/并发下的接收准则"。两边立的判据结构一样——**判据不挑行业**。

**反转话术**（对应方法底座时刻 = 判据主义 + v2.1 规则 15 转述形态）：这是本单元的**方法时刻**——前面六题在用判据，这一题让你们亲手把判据立出来。判据主义三问：**是什么（可检验的定义）、失效边界（什么时候不适用）、反例（能不能被推翻）**。两条标准答案——设计开发终点：**"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束"**（可检验、有失效边界、有反例：技术方案完成但采购问不出型号准则）；质量：**"特性满足需求的程度，用测试方案里的接收准则比对"**（可复核、可争论、可裁决）。注意：本章是判据主义章，方法时刻题就是判据运用题——判据不是背出来的，是当场立、当场用的；**同方法区分：本章立的是质量判据**（第8章立三把尺子、第13章立版本/基线判据，各章各立各的）。**v2.1 新增转述形态——转述是压缩测试**：用三五句话把"质量"讲给一个完全外行的人——讲不清 = 结构没成型（织关系没到位），卡壳处 = 边界缺口（辨边界没到位）。**你答不齐的那一问，和你转述卡住的那一处，是同一个缺口。**

**参考答案要点**：判据主义三问见第1章方法论 + §3.2.4 方法时刻；终点判据见 §3.3.2；质量判据见 §3.2.4 / §3.3.3；接收准则见 §3.4.1；转述=压缩测试见第1章 §1.4.3。

### Q8 85 分为什么是"一个精确的错误"？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "平均挺公平，85 分就是客观结论。" | 正是要翻的——没看到关键特性被摊平 |
| 中 | "安全项不该平均。" 结论对，机制浅 | 程度三步、一票否决没接上 |
| 好 | "程度是认定不是计算；单项二元、整体程度；程度三步（确定特性值 → 比对 → 认定）第一步没走全（没按接收准则量）；关键特性（断电告警，8.3.5 d）不能被加权平均摊平——安全项失 2 分被'温度控制 92'补回来，就是'一个精确的错误'；要么一票否决，要么加权不平均。" | 程度三步 + 一票否决 + 判据全到位 |

**产品侧 vs IT侧**：产品组举"断电告警被平均"；IT 组举"合同正确性/审批时效被响应速度补回来"。两边同一个坑——**加权平均把一票否决的特性摊平，等于替致命缺陷打掩护**。

**反转话术**（对应 §3.4.1 + §3.4.2）：先立"程度"怎么得出——**三步**：确定特性值（3.11.1，测量/检验/试验/评审/计算）→ 与需求比对（3.6.11，用接收准则）→ 认定满足程度（3.6.2，差/好/优秀）。**单项是二元（符合/不符合），整体是程度（差/好/优秀）**——整体程度按特性重要度综合评价，**关键特性优先（8.3.5 d 对预期目的至关重要的特性）**。那能不能打分？标准层面：**没有**——特性多维不同质、加不成一个数；隐含需求无法完整数值化；注 1 明确用形容词。组织层面可以造分，但三个前提缺一个分就是假的（需求完整/特性规定完整/证据可靠），最要命的是：**关键特性不能被摊平**——安全、可靠这种一票否决的特性摊进平均数，安全项失分被"精度超强"补回来，还是 85 分——**这个 85 分，就是用假象掩盖致命问题**。分值的最大陷阱：**它给了你一个精确的错误**。要么设"一票否决"，要么用加权不用平均。

**参考答案要点**：程度三步见 §3.4.1；单项二元/整体程度见 §3.4.1；接收准则见 §3.4.1 + 测试方案（八方案之一）；85 分陷阱见 §3.4.2 + 案例进展③；关键特性优先见 8.3.5 d。

### Q9 为什么"砍需求"和"单方面砍需求"是两件事？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "都是砍需求，一个找客户聊了，一个没聊。" | 差的不只是"聊"——所有权和变更手续 |
| 中 | "要和客户一起决定。" 结论对，机制浅 | 为什么"一起"是硬要求没讲透 |
| 好 | "需求所有权在相关方手里，组织只是受托转化；单方面砍 = 拿别人的东西替别人做主（偷换），一起剪 = 变更（排序/留痕/挂账）；剪下来的需求是'挂账'不是消失，下轮迭代是现成输入；进度冲突是隐含需求的显影剂——刘主任十分钟说出真正在意的。" | 所有权 + 变更 + 挂账 + 显影剂全到位 |

**产品侧 vs IT侧**：产品组答 M3 刘主任剪裁（命根子/可降/可砍三十分钟排序）；IT 组答恒信"实时推送降级成两小时同步"这类变更必须走正式流程。两边同一个原则——**口头改需求 = 偷换靶子**。

**反转话术**（对应 §3.4.3 正道）：为什么"和顾客一起剪裁"是硬要求？四个理由层层递进——**需求的所有权在相关方手里**（需求是"需要或期望"的表述，是顾客的资产，组织只是受托转化；单方面剪掉的那块可能恰是顾客最在乎的隐含需求，他没说，但你剪了，事后必炸）；**剪裁改变的是验证的靶子**（验证对照规定需求，需求一剪靶子就变了，不一起剪就是在打一个自己偷偷移动的靶子）；**剪裁的正确动作是"排序"不是"删减"**（命根子不可动 / 可降 / 可砍，让相关方排优先级）；**剪裁要留痕、剪下来的要存档**（走 8.2.4 / 8.3.6 正式变更，剪了什么、为什么剪、谁决定的、哪天恢复）。**剪掉的需求不是消失了，是"挂账"**——本轮进度解了，下一轮迭代（持续改进、改型）时就是现成输入。**剪裁是暂存，不是销毁。** 而"进度冲突"是隐含需求的显影剂——平时问"你还有什么要求"他答不出，你说"进度不够，必须砍一样，砍哪个"——他立刻知道答案（刘主任十分钟就把真正在意的全说出来了）。

**参考答案要点**：与相关方一起剪裁四理由见 §3.4.3；排序/留痕/挂账见 §3.4.3；剪裁是暂存不是销毁见 §3.4.3；进度冲突是显影剂见案例进展④。

### Q10 给你们的部门做一次三基座体检

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强需求管理、要提高质量意识。" | 没落到三把尺子任何一把，不可检查 |
| 中 | 用一把尺子查出缺口（如"测试方案没有接收准则"） | 有判据，但只照了一面 |
| 好 | "先查定标尺（四闸门最弱一条）→ 再查造标尺（八方案哪项还反问'怎么做'）→ 读标尺（接收准则有没有）→ 落到一个动作（如'两周内给测试方案补接收准则'），说出先查哪把、两周后报告什么。" | 三把尺子按序 + 一个可检查动作 + 复查机制全到位 |

**产品侧 vs IT侧**：两组各给自己部门体检——体检表本身是同一份（定标尺 → 造标尺 → 读标尺），这正是"概念领域中立"的现场证明。

**反转话术**（对应本章综合应用 + 章末见过→拥有）：这一章的判据不是彼此孤立的——起点判据测"要什么"，终点判据测"造完没"，质量判据测"读出来是程度还是感觉"。**找到第一个"没有"就能开工**：没有接收准则 = 从读标尺补起；答不上"到底怎么做" = 从造标尺补起；说不清隐含需求 = 从定标尺补起。三兄弟从此咬合成一个基座——**能答全四问才算拥有，这把尺子现在装进你手里了**。

**参考答案要点**：三基座体检方法见作业指南（本章分析文档第 6 步）；判据见"本章判据"七条；定标尺→造标尺→读标尺见"本章概念总图"；见过→拥有见"章末·认知反转"。

### 金句（书"本章判据"提炼）

- **需求（定标尺）**：明示的、通常隐含的或必须履行的需要或期望——三种形态并列，隐含需求漏了是缺陷。目标可以激励人，**需求必须可判定**。
- **设计开发（造标尺）**：把需求转换为更详细的需求——**止于"可实现"**："还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束。" 终点由最后一个配齐的方案决定。
- **质量（读标尺）**：客体固有特性满足需求的程度——**等级高 ≠ 质量好**（高档车可以是差质量）；特性超出需求范围 = 过度设计，**只加成本，不加质量**。
- **质量被认定，不被计算**——程度三步：确定特性值 → 与需求比对（接收准则）→ 认定满足程度；关键特性不能被摊平（那个 85 分是"一个精确的错误"）。
- **质量 vs 进度 = 同一份需求集合内部打架**——进度本身是需求（ISO 9001 §8.2.2）；解法是用需求谈判不用质量谈判。
- **单方面砍需求叫偷换，和顾客一起剪裁才叫变更**——排序、留痕、挂账；剪裁是暂存，不是销毁。
- 一个产品开发流程，无非是：**定标尺 → 造标尺 → 读标尺**；"每一个为什么都能从三角推出来" = 基座的终极检验。
- 方法底座时刻：**判据主义**——质量 = 特性满足需求的程度，可检验；设计开发止于可实现，可检验。

1. **书练习（与题卡同源）**：设计开发什么时候算结束？"技术方案做完了"够吗？列出至少三个还缺的方案，并说明为什么终点由"最后一个配齐的方案"决定。（书练习 2）
2. **书练习**：等级、质量、符合性三者各自回答什么问题？"高档车可以是差质量"这句话为什么成立？（书练习 6）
3. **书练习**：用四问法的"它从哪来"量一遍三兄弟——需求、设计开发、质量各自为什么被造出来、如何演化成今天的定义？哪个词曾从"档次/用料"漂移成"符合需求的程度"？（书练习 9）

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次三基座体检：
>
> 1. **定标尺（起点判据）**：把当前项目"要什么"的需求规格拿出来，过"可转化"四闸门——完整？无歧义？不冲突？隐含需求已识别？**最弱的一条记下来**。
> 2. **画边界（特性是否被规定）**：判断手头这份工作是需求开发还是设计开发——特性开始被规定了吗？没被规定，说明还在 8.2，没到设计开发。
> 3. **造标尺（终点判据）**：把八个方案（技术 / 物料采购 / 制造·工艺 / 测试 / 交付 / 部署 / 操作 / 运维）列一张表，逐项打勾；**问一句"还有哪个环节会在执行时反问'这到底怎么做'？"** 有，设计开发就没结束。
> 4. **读标尺（程度三步）**：找出测试方案里有没有接收准则——用什么设备测、测多久、抽多少样本、判定结论写在哪份记录。**没有 = 质量只能"感觉"，不能"认定"。**
> 5. **查关键特性（85 分陷阱）**：把 8.3.5 d 说的"对预期目的至关重要的特性"列出来，确认它们没被加权平均摊平——该一票否决的一票否决。
> 6. **解冲突（与相关方一起剪裁）**：如果进度亮红灯，用需求谈判不用质量谈判——找相关方排优先级：命根子（不可动）/ 可降的 / 可砍的；走正式变更，砍下来的**挂账留痕**。
>
> 卡住时：找到第一个"没有"就能开工——没有接收准则 = 从第 4 步补起；答不上"到底怎么做" = 从第 3 步补起；说不清隐含需求 = 从第 1 步补起。产出三件最该做的事（每条 = 一个可检查动作）。
