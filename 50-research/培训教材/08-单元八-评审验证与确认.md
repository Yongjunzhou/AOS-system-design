## 一、单元导读

### 主题

这一章发的不是词，是**三把尺子**——评审、验证、确认，三个看门人，三把完全不同的尺子。它们不是"检查一下"的三种说法，而是三件不同的事：**评审对目标（方向对不对）、验证对需求（做对了吗）、确认对用途（做对的东西了吗）**。它回答三个更根本的问题：这三个词为什么在中文里看起来像近亲？三个看门人各守哪道门？为什么只做验证不做确认，会"测试全过、没人用"？

本章的骨架是：**三把尺子**（评审对目标·验证对需求·确认对用途，各带可检验判据——判据主义）→ **五维表并排钉死**（定义/参照/动作/证据/时机）+ **六概念闭环**（目的→目标→需求→规定需求→客体，预期用途旁挂场景层；**两系统目的锚：冰链 M3=让疫苗在冷链运输中一路不失活、安全送达、恒信合同系统=让合同审批合规、月底账目清楚对得上——恒信"月底对账不再靠手工"、M3"断链即报废时还能撑到接入冷库"，分别是这两个目的的操作展开**；两条旁路通道〔环境/法规、干系人隐含需要〕不经目标直接进需求；三形态分叉口〔明示→规定需求→验证 / 隐含→场景→确认〕）→ **磨边弧四道"不是 X"**（评审≠核对需求 / 测试通过≠验证通过 / 业务方点了≠确认过了 / 验证的尺子在文档、确认的尺子在场景）+ **方向把关两道闸**（评审早拦·纸面·预测 / 确认终审·真实·实证，验证不沾方向）→ **接力链三关**（评审·开工前→验证·交付时→确认·交给用户）→ **因果链**（只做验证不做确认→测试全过、没人用）→ **三套手法 + 架构评审特化**（目标具体化·目标=供需约定的成功判据 / V 模型右半边 / 仿真·灰度·试运行 / 评审四看·对质三问）。

本章档案的**承重柱（根概念）= 验证**——确认与验证共享同一套三要素、唯一区别在参照（文档 vs 场景），确认从验证的机制生成；评审是"判"族（确定），与"证"族（认定）分家。承重柱是"谁生成谁"的结构问题，不是"只做验证就够"——恰恰相反，正因为确认换了参照，它的射程（场景）才和验证不同，谁也不能替代谁。

### 开场破题（对应章首误解现场）

念出恒信集团合同审批系统上线前那场评审会：万辉在投影上打开了 UAT 报告，语气笃定——"UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。**我们验收合格，可以上线。**"产品开发经理满海已经把报告翻到了最后一页的签字栏，笔尖悬在上面："UAT 全绿，业务方也点了测试环境——**验收合格，这个字我签了。**"会议室里有人开始收东西了。财务的人却没动："你们让我们点的那个测试环境，我们月底对账的场景——25 号之后签的合同算哪个月——测了吗？"万辉愣了一下："测试用例是照着需求清单写的，需求清单里……没有这条。"徐漾坐在角落，轻声说："万辉，你把三件事当成一件事办了。"——"哪三件事？""评审、验证、确认。"

让各组表态：万辉说错在哪？满海这一笔签下去，签的是哪把尺子？"测试通过率 96%"和"业务方点了测试环境"各自是哪件事的（伪）证据？"月底对账的场景没测"说明哪件事缺位？大多数人一开始都站在万辉和满海这边——这正是这一章要推翻的直觉。

### 本单元要反转的直觉

- **UAT 跑了 = 确认过了**（× 让业务方点测试环境是当测试员；确认要真实用户 + 真实任务 + 真实场景）
- **测试全绿 = 验证过了**（× 测试只是提供客观证据的手段之一；验证要对全部规定需求做认定）
- **评审 = 开会过一遍需求**（× 评审对目标，不是核对需求；没结论、没记录，最多算聊天）
- **验证和确认差不多，都是证明没问题**（× 翻译伪朋友：验证对需求，确认对用途——参照不同，射程不同）
- **满足所有需求 = 达成目标**（× 需求本身可能错；评审是唯一在纸面阶段抬头看目标的环节）
- **确认是验证的加强版，范围更大而已**（× 不是范围不同，是参照不同：文档 vs 场景；验证够不着隐含、确认兜得住隐含）
- **复盘也是评审，都带"评"字**（× 评审管把关，复盘管改进；复盘是检测器，裁决才是治理）
- **测试全过、没人用是运气问题**（× 只做验证不做确认 → 隐含需求系统性漏失 → 测试全过没人用，是因果问题）
- **确认可以上线后补**（× 上线后补确认，就叫"上线事故"）
- **架构评审就是过一遍图，图没问题就通过**（× 审的是理由不是图：四看 + 对质三问，没有背书只是个人意见）
- **需求都是从目标推导出来的，目标定了需求就齐了**（× 需求来源不只目标——环境/法规、干系人隐含需要两条旁路通道不经目标直接进需求，靠需求工程兜底）
- **目标是我们（供方）定的成功标准**（× 目标=需方与供方就"成功判据"达成的约定——业务方提方向→供方翻译成操作目标→业务方确认过才成为评审的尺子）
- **操作目标全绿 = 确认通过**（× 操作目标只是预期用途要求的显性子集（MOE），达标是必要非充分）
- **评审和确认都管方向，有一道就够了**（× 方向把关是两道闸：评审早拦·纸面·预测，确认终审·真实·实证——缺一不可）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 三件事被当成一件事（概念本身 · 章首破题 + 溯源：词源/ISO 分家）→ Q2 三个词什么关系（五维表 + 接力链 + 规定需求一词 + 六概念闭环·旁路通道·分叉口·上溯目的，概念关系）→ Q3 评审对目标 vs 核对需求（真悖论）→ Q4 测试通过 vs 验证通过（真悖论）→ Q5 业务方点了 vs 确认过了（真悖论 + 方向两道闸·MOE 显性子集）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 三关走一遍月底对账事故（判据运用 · 因果链 · 复盘 · 案例⑤）→ Q7 目标具体化 + 目标=供需约定 + 通过标准 + 架构评审特化（判据运用 · 评审手法 · 案例①）→ Q8 用三要素拆两场测试（判据运用 · 验证/确认 · 案例③④）→ **Q9 方法时刻·判据主义**（规则 15：亲手给"评审/验证/确认"各立可检验判据 + 转述压缩测试——判据运用形态）→ Q10 回部门三个看门人体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"验证"是零部件试验、整机低温试验，"确认"是真实运输车跑全程——"用例全过，说明不了上路能过"（断档 30 秒）；IT 组的"验证"是单元/集成/系统测试，"确认"是 UAT、灰度、试运行——"测试全绿，月底对账对不上"（合同编号）。**同一个概念、两个世界、判据不变**，这正是本章"三个看门人，两扇世界的门"的现场证明——三把尺子不挑行业。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜万辉把哪三件事当成一件事办了？**
"章首那场评审会上，万辉举着 UAT 报告说：'UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。我们验收合格，可以上线。'产品开发经理满海已经把报告翻到签字栏、笔尖悬在上面：'UAT 全绿，业务方也点了测试环境——验收合格，这个字我签了。'徐漾只问了一句：'月底对账的场景测了吗？'万辉答：'测试用例是照着需求清单写的，需求清单里没有这条。'徐漾说：'你把三件事当成一件事办了。'——是哪三件事？满海这一笔下去，签的是哪把尺子？评审、验证、确认各自是什么、各看什么？为什么三个词在中文里看起来像近亲？"

追问：① 三把尺子各带什么可检验判据（评审三问 / 验证三要素 / 确认三要素）？评审为什么不要求客观证据、却必须记录（系统性三属性：团队参与 + 结果文档化 + 过程文档化——没记录=聊天）？② 三个英文词的词源各自是什么（review←re+view 再看 / verification←verus 求真 / validation←validus 立得住），ISO 9000 为什么把评审分进 3.11"确定"组、验证/确认分进 3.8"规范"组（判 vs 证）？③ 万辉话里"测试通过率 96%"是哪件事的证据？满海那两句——"UAT 全绿"和"业务方也点了测试环境"——各自是哪件事的（伪）证据？它们证明不了另外两件事的什么？④ 满海签字的那一刻，是把三件事糊成一句话——你们最近一次说"验收通过了"，是三个看门人依次签字的，还是也糊成一句话？

**Q2｜评审、验证、确认什么关系？**
"请给出 评审、验证、确认 三个词的关系——用一张五维表（定义 / 参照 / 动作 / 证据 / 时机）把三把尺子并排钉死，再说出三个看门人怎么接力（评审站在哪、验证站在哪、确认站在哪）。为什么三个参照物（目标 / 规定需求 / 预期用途）不是同一个？"

追问：① 参照不同为什么是决定性的（决定射程和命运）？验证和确认的判据为什么长得一样（同一套三要素）——它们真正的区别在哪？② 规定需求一个词为什么三个看门人都绕不开（评审审它 / 验证对它 / 确认兜它）？③ 把三个参照放回六概念闭环：目的在哪一层？目标 / 需求 / 规定需求 / 客体 / 预期用途怎么排？为什么需求来源不只目标（环境 / 法规、干系人隐含需要两条旁路通道不经目标直接进需求，靠需求工程兜底）？需求层三形态在哪分叉（明示→规定需求→验证 / 隐含→场景→确认）？评审 / 确认为什么沿链上溯到目的——上溯的是哪两个系统的什么目的（冰链 M3=让疫苗在冷链运输中一路不失活、安全送达 / 恒信合同系统=让合同审批合规、月底账目清楚对得上）？恒信"月底对账不再靠手工"、M3"断链即报废时还能撑到接入冷库"分别是哪个目的的操作展开？④ 你们平时把"验证"和"确认"糊着用吗？哪次糊出过事？你们的需求，除了目标还有哪些来源漏在外头？

**Q3｜"逐条核对需求"和"评审对目标"，哪个是评审？**
"冰链的需求评审会开了一下午：文正拿着需求清单逐条念、逐条打勾——'有编号 ✓、有来源 ✓、可测吗 ✓、验收标准有 ✓'，三十条念完，宣布评审通过。这不是更省事、更客观吗？可书里说评审以'目标'为参照。'逐条核对需求'和'评审对目标'，哪个对？什么判据能分清？"

追问：① 评审不是核对需求的四个理由（需求本身可能错 / 否则与验证重复 / 满足所有需求≠达成目标 / 目标（目的）会漂移——目标=系统目的在操作层的展开，评审以系统目的为参照=捕捉目的漂移的传感装置）？② "需求满足得越彻底，目标的偏离走得越远"——为什么把评审做成了"最后一小时核对"，就是最失败的评审？③ 你们最近一次评审，问过"这套需求还朝那个目标吗"吗？

**Q4｜测试全绿，算验证通过吗？**
"'测试全绿'不就是'验证通过'吗？测试都跑了，证据还不够吗？可书里说'测试通过≠验证通过'。那什么才算验证通过？测试在验证里到底算什么？"

追问：① 验证三要素（对照规定需求 + 客观证据 + 认定）——测试满足了哪个？② 96% 通过率剩下的 4% 说明什么（那 4% 对应的需求没有证据）？③ "规定需求可验证"是从哪推出来的（验证要求客观证据 + 以规定需求为参照——可验证是入场券，不是标准原话）？④ 你上次说"测试全绿"，验证三要素齐了吗？

**Q5｜让业务方点了测试环境，算确认过了吗？**
"万辉让法务、财务、业务在测试环境点了一圈，'业务方都验收了，这还不是确认？'可书里说这是'让业务方当测试员'。让业务方参与，怎么反而不是确认？"

### Q1 万辉把哪三件事当成一件事办了？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "万辉和满海说得对，UAT 全绿、业务方也点了，就是验收合格，可以签。" | 正是要翻的——把三件事当成一件事，签字人也要拦 |
| 中 | 能背出"评审/验证/确认"三个词，但说不清各看什么、从哪来 | 定义是背的，参照没分清、溯源没抓到——"评/验/认"形近字把分界线糊上了 |
| 好 | "评审对目标、验证对需求、确认对用途——万辉把'测试通过率 96%'（验证的证据）当成了确认（真实场景能用）；满海把'业务方也点了测试环境'也当成了确认的依据（其实是让业务方当测试员，对照的还是需求清单）；三个词是翻译伪朋友：review/verification/validation 词源完全不同（再看/求真/立得住），ISO 9000 把评审分进 3.11'确定'组（判）、验证/确认分进 3.8'规范'组（证），中文形近字糊了四十年；月底对账场景没人测，正是确认缺位的证据——满海这一笔，就是'混到验收签字那一刻就是合同纠纷'的落点。" | 三把尺子 + 参照 + 溯源（词源/ISO 分家）+ 案例全咬合，能当场拦下万辉和满海 |

**产品侧 vs IT侧**：产品组答"冰链 M3——零部件试验/整机低温试验=验证，真实运输车跑全程=确认，设计评审对目标"；IT 组答"恒信——单元/集成/系统测试=验证，UAT/灰度=确认，上线评审对目标"。两边都容易把"测试全绿"当"验证过了"，再顺手当"确认过了"——**三个词，三把尺子，谁都替不了谁**。

**反转话术**（对应 §8.2.1/§8.2.2/§8.2.3 + 章首）：万辉说错的不止一处——他混了三个词。**评审对目标（方向对不对，判断）、验证对需求（做对了吗，证明）、确认对用途（做对的东西了吗）。** 三个词不是"检查一下"的三种说法，而是三件不同的事。中文把它们糊成近亲，是第1章第三种词汇病**"翻译伪朋友"**：review（re+view 再看）/ verification（verus 求真）/ validation（validus 立得住）三个英文词词源、构词、归属完全不同，翻译成中文恰好都带一个"评/验/认"字。

ISO 9000 把评审放在 3.11"有关确定的术语"组（与确定、监视、测量、检验一家），把验证/确认放在 3.8"有关规范的术语"组——**"确定"和"认定"是两种动作：评审的动作是"确定"（主动调查，不要求客观证据），验证/确认的动作是"认定"（结果已经在那儿了，去证实，必须有客观证据）。一个是判，一个是证。** 万辉那句"UAT 全绿"是验证的证据（还只是一部分），它证明不了"真实对账场景能用"（确认），也证明不了"方向对"（评审）。**满海已经把这句话放到了签字栏上——他签"验收合格"，依据是两句：一句"UAT 全绿"（验证的证据），一句"业务方也点了测试环境"（他当成了确认，其实是让业务方当测试员、对照的还是需求清单）——三个看门人只到了验证一个，这一笔下去，就是把三个词糊成一个的代价的合同化。平时混，没事；混到验收签字那一刻，就是合同纠纷。**

**参考答案要点**：三定义见 §8.2.5/§8.2.6/§8.2.7 + 概念卡；翻译伪朋友与词源见 §8.2.1；ISO 分家见 §8.2.2；三参照见 §8.2.3；章首误解现场。

### Q2 评审、验证、确认什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把三个词排成并列的"把关"，说不清分界 | 关系结构错误——是五维分界 + 接力链，不是并列同义 |
| 中 | 能背出"评审对目标、验证对需求、确认对用途"，但五维表/接力链没接上 | 一句口诀会背，五维分家、三个看门人站位没钉死 |
| 好 | "五维表：定义/参照/动作/证据/时机——验证和确认在动作（认定）与证据（必须客观证据）上一致、只在参照上不同（同一套三要素、参照换成预期用途），评审与前两者分族（确定/不要求证据）；接力链：评审站在开工前抬头看方向、验证站在交付时低头对规格、确认站在交给用户时走进真实场景；三个参照物——目标/规定需求/预期用途——参照不同是决定性差异；六概念闭环：目的在最顶层、目标是其在操作层的展开、需求来源不只目标（两条旁路通道不经目标直接进需求）、三形态分叉口、评审/确认沿链上溯到目的。" | 五维表 + 同一套三要素的区别 + 接力链 + 参照三物 + 六概念闭环全到位 |

**产品侧 vs IT侧**：产品组画"M3 的三关——设计评审对'断链即报废时撑到冷库'、整机试验对规格、真实运输车对'疫苗安全送到'"；IT 组画"恒信的三关——上线评审对'月底对账不再靠手工'、系统测试对需求、UAT 对真实对账"。两边画的是一张图——**三个看门人、两扇世界的门，接力链纹丝不动**。

**反转话术**（对应 §8.2.3/§8.2.4/§8.2.7/§8.4.1）：把三个词摆成**五维表**：定义、参照、动作、证据、时机——五个维度一起把三个词分开。验证和确认在"动作"（认定/证明）与"证据"（必须有客观证据）上一致，只在"参照"上不同——**确认和验证共享同一套三要素，唯一区别在第一个要素：验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）**。评审与前两者分族：动作是"确定"（判断）、不要求客观证据。

**参照是决定性的差异**——评审对目标（要实现的结果，3.7.1）、验证对规定需求（明示成文，3.6.4 注2）、确认对预期用途（真实使用情境）。三个看门人守着三道门：**评审站在"开工前"抬头看方向、验证站在"做完了"低头对规格、确认站在"交给用户"走进真实场景。** 目标转化出需求（但不只一个来源），用途要在真实场景里才现形。注意一个词：**规定需求**——评审审它（对象）、验证对它（参照）、确认兜它（验收依据），三个看门人都绕不开它；它没成文，三个看门人就全闭门。这正是章首那条"口头补的需求"的下场。

再把三个参照放回**六概念闭环**，接缝才看清：**目的**（系统存在的理由）在最顶层，**目标**（objective 3.7.1，战略/战术/操作）是它在操作层的展开——操作目标=运行层可判定层；**这一章把两个系统的目的钉死在 §8.2.3：冰链 M3="让疫苗在冷链运输中一路不失活、安全送达"、恒信合同系统="让合同审批合规、月底账目清楚对得上"——恒信"月底对账不再靠手工"、M3"断链即报废时还能撑到接入冷库"，分别是这两个目的的操作展开，评审/确认上溯目的，上溯的就是这两个具体的系统目的**；**需求**（明示/隐含/必须履行三形态）由目标转化而来（跨类导出≠分解），但**需求来源不只目标**——环境/法规（通道②）、干系人隐含需要（通道③）不经目标直接进需求，靠需求工程兜底；需求层三形态分叉：明示成文化=**规定需求**（验证的尺子在文档里够得着）、隐含写不出来只能靠**场景**兜（确认）；**评审/确认沿链上溯到目的**——评审以目标为参照、根子上看的是系统目的。三种参照落在三个世界里：目标=意图世界（方向错）、需求=转写世界（转写错）、预期用途=真实世界（匹配错），用途不能推导只能发现。

**参考答案要点**：五维表见 §8.2.4；三参照·六概念闭环见 §8.2.3；确认=同一套三要素换参照见 §8.2.7；接力链见 §8.4.1 + 开篇枢纽；规定需求一词见 §8.3.1。

### Q3 "逐条核对需求"和"评审对目标"，哪个是评审？

| 答案分级 | 形态 | 讲师判读 |

| 弱 | "逐条核对挺客观，评审不就这样吗。" | 正是要翻的——把核对当评审 |
| 中 | "评审对目标，不对需求。" 结论对，三理由缺 | 结论对，为什么必须对目标没讲透 |
| 好 | "三理由：需求本身可能错（谁审需求本身）；否则评审和验证重复（ISO 分家塌了）；满足所有需求≠达成目标（评审是唯一在纸面阶段抬头看目标的环节，方向还有一道实证终审——确认）。文正的逐条核对是验证的姿势，对的是需求清单；评审对的是'断链即报废时还能撑到接入冷库'这个目标——应急场景（运输车抛锚 2 小时）没写进需求，逐条核对永远发现不了。" | 三理由 + 冰链目标 + 应急场景 + 纸面阶段抬头全到位，能当场裁文正 |

**产品侧 vs IT侧**：产品组举"M3 逐条核对清单，漏了运输车抛锚 2 小时"；IT 组举"恒信核对需求清单，漏了电子签章变更连需求都不是"。两边同一个病——**只认识中间那个看门人（验证），把评审做成了验证**。

**反转话术**（对应 §8.3.1 + 案例进展②）：文正的病，和万辉是**同一个病的镜像**——万辉把"确认"做成"验证"（让业务方当测试员），文正把"评审"做成"验证"（逐条核对需求清单）。病根一模一样：**三个看门人，只认识中间那个。** 评审为什么不能以需求为参照？四个理由，每一条都足以让"以需求为参照"破产：**第一，需求本身可能是错的**——需求是人写的，理解错、互相矛盾、不完整都是常态；如果评审拿"需求"当尺子，就等于默认"需求一定对"，那谁来审需求本身？需求评审的本质，恰恰是审"需求"对"业务目标"是否适宜、充分、有效。

**第二，否则评审和验证就重复了**——验证本来就是"以规定需求为参照、确认符合性"，如果评审也以需求为参照，两个术语就是同一件事，ISO 9000 把评审放在 3.11、把验证放在 3.8，这套体系就塌了。**第三，满足所有需求 ≠ 达成目标**——目标错了，需求再对也是白做；评审是整条链上唯一在纸面阶段"抬头看目标"的环节（方向还有一道实证终审——确认）。**第四，目标（目的）本身会漂移**——目标（objective）是系统目的（purpose）在操作层的展开，真正会漂移、漂了最危险的正是系统目的：产品定位悄悄滑向、业务方一点一点改口径，没有任何一个环节宣告过"目的变了"，需求却还钉在旧目的上——**需求满足得越彻底，目标的偏离走得越远**。这是第14章说的**目的漂移**（无症状、事后才发现），只能靠定期评审以系统目的为参照把它检出来，评审因此是捕捉缓慢漂移的**传感装置**；系统目的显式变更（战略调整、产品定位改变）则是**目的变更**（显式发生的强制扳机，靠变更流程强制挂钩）。**要求是"路"，目标是"目的地"——评审的价值，就是在低头检查路况之外，抬头看看目的地对不对。** 最失败的评审不是没查出问题，而是把评审做成了验证：只核对"满足需求没有"，从不问"这需求本身对吗"。

**参考答案要点**：三理由见 §8.3.1；案例进展②（冰链逐条核对）见"案例进展②"；"路 vs 目的地"见 §8.3.1。

### Q4 测试全绿，算验证通过吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "测试全绿就是验证通过。" | 正是要翻的——把手段当目的 |
| 中 | "测试只是证据之一。" 结论对，三要素/4% 没接上 | 结论对，验证三要素、96% 那 4% 没讲透 |
| 好 | "验证三要素：对照规定需求+客观证据+认定——测试提供了证据，但没覆盖全部规定需求（96% 意味着 4% 的用例没过或没写，那 4% 对应的需求没有证据）；'规定需求可验证'不是标准原话，是从'验证要求客观证据 + 以规定需求为参照'推出来的——可验证是入场券；测试报告是验证的输入，不是验证本身；验证是拿着全部证据（测试、审查、计算、文档评审）对全部规定需求做出认定。" | 三要素 + 4% 无证据 + 可验证推导 + 输入/本身全到位 |

**产品侧 vs IT侧**：产品组举"整机试验全过，但某个分系统需求（振动下连续）没测"；IT 组举"UAT 通过率 96%，剩 4% 的需求没有证据"。两边同一个病——**把"跑测试"升级成"验证过了"**；符合性分析（第6章）在设计层也是验证，不跑测试也能验证。

**反转话术**（对应 §8.3.2 + §8.2.6）：测试只是提供客观证据的**手段之一**——ISO 9000 注1 明确说，验证的证据可以是试验结果、变换方法计算、文件评审等。把"测试过了"等同于"验证过了"，是把手段当成了目的。UAT 报告写"测试用例通过率 96%"——这是一份测试结果，是证据的一种；但验证要回答的是"规定需求是否得到满足"，证据要覆盖全部规定需求——**96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足，测试没有给出证据**。

验证三要素缺一不可：**对照规定需求（有白纸黑字的尺子吗）、客观证据（有可复核的证据吗）、认定（有明确结论吗）**——"我认为满足"不算验证，"差不多吧"不是验证。还有一条推论值得记住：**"规定需求可验证"不是标准直接写的**，是从"验证要求客观证据 + 验证以规定需求为参照"推出来的——可验证，是规定需求当验证参照的资格证；这是第4章"需求质量六性"里"可验证"一性的真正出处。测试报告是验证的输入，不是验证本身；验证是拿着全部证据对全部规定需求做出认定。第6章的符合性分析也在这里归位——它和测试一样满足验证三要素，只是证据形式是文档评审：**符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）。** 别把验证窄化成"跑测试"，也别把"跑测试"升级成"验证过了"。

**参考答案要点**：验证三要素见 §8.2.6 + 概念卡；测试只是证据之一见 §8.3.2；符合性分析归位见 §8.3.2；"规定需求可验证是推导"见 §8.2.6。

### Q5 让业务方点了测试环境，算确认过了吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "业务方都点了，还不算确认？" | 正是要翻的——把参与当确认 |
| 中 | "确认要真实场景。" 结论对，机制浅 | 结论对，为什么"参与≠确认"没讲透 |
| 好 | "确认三要素：真实用户+真实任务+真实场景——万辉让业务方在测试环境点一圈，是让业务方当测试员，替测试团队跑用例，对照的还是需求清单；预期用途三构成（目标用户/使用场景·任务/环境与条件）里，真实对账数据、真实月底时间点、真实并发是测试环境替不了的；真正的 UAT 是财务用真实的对账数据、在真实的月底时间点、跑真实的月底对账任务——对照的是'月底对账能用'这个预期用途；方向把关是两道闸——评审第一道·早拦·纸面·预测、确认第二道·终审·真实·实证，验证不沾方向；操作目标（MOE）只是预期用途要求的显性子集，全绿≠确认通过。" | 真实三件套 + 预期用途三构成 + 对照预期用途 + 方向两道闸 + MOE 显性子集全到位 |

**产品侧 vs IT侧**：产品组举"请疾控中心在恒温台架上点一遍，不是确认——要上真实运输车"；IT 组举"让法务/财务/业务点测试环境，不是确认——要真实数据、真实时间点、真实任务"。两边同一个病——**让业务方点环境，是把确认做成了验证：业务方替你打勾的，还是需求清单上的格子**。

**反转话术**（对应 §8.2.7/§8.3.3 + 案例进展③）：UAT 不是"让业务方点一遍测试环境"，而是"**真实用户 + 真实任务 + 真实场景**"的确认。确认和验证共享同一套三要素——对照、证据、认定——**唯一的区别在第一个要素**：验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）。"预期用途"不是一句空话，由三样东西构成：**目标用户**（给谁用——法务/财务/业务三方审批人，不是 IT 测试员）、**使用场景/任务**（用来干什么——月底对账、电子签章合同审批、出差手机处理）、**环境与条件**（什么情况下用——月末高峰并发、弱网、休假交接）。

章首万辉的 UAT 错在哪？他让业务方在测试环境点了一圈——那是**让业务方当测试员，替测试团队跑用例**，对照的还是需求清单。真正的 UAT 是：财务用真实的对账数据、在真实的月底时间点、跑真实的月底对账任务——对照的是"月底对账能用"这个预期用途。**让业务方点测试环境，是把确认做成了验证。** 只做验证不做确认，隐含需求就系统性漏失——**测试全过、没人用，不是运气问题，是因果问题**。玉杰（运维）把话说死："测试环境那三台机器是我部署的。周二下午三个人轮流点，是人在点；月底几十号人同时冲进去对账那种并发，测试环境扛不住、也测不出来——真实场景，它给不了。"

顺带把方向把关的分工钉清楚——它是**两道闸**，不是一道：**评审=第一道·早拦·预测性把关**（纸面制品·显性部分，判断与论证推演"方向应该对"），**确认=第二道·终审·实证性把关**（系统本身·连隐含兜，真实/仿真使用证实"方向确实对"）。评审通过只代表"基于当时信息的最佳判断"、可被确认推翻；只靠评审=隐含无法论证覆盖、只靠确认=纠偏成本爆炸。**验证在这条线上完全不沾方向。** 再补一句要紧话：**操作目标（MOE）全绿，不等于确认通过**——操作目标只是预期用途要求的显性子集，它达标是确认的必要条件不是充分条件：指标全绿、真实场景却用着别扭，确认照样失败。

**参考答案要点**：确认三要素见 §8.2.7 + 概念卡；预期用途三构成见 §8.2.7；UAT 真实三件套见 §8.3.3；方向两道闸见 §8.3.6；MOE 显性子集见 §8.2.7/§8.3.5；案例进展③（徐漾三问 + 玉杰）。

### Q6 "验证做了，其余没做"——月底对账为什么对不上？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "对账对不上是需求没写全，补条需求就行。" | 把因果问题当缺条需求——三个看门人没进来 |
| 中 | "缺了确认。" 结论对，三关/复盘没接上 | 结论对，三关缺哪两关、复盘与裁决的分别没讲透 |
| 好 | "'验证做了'：UAT 全绿，测试证明按需求做对了；'评审没做'：这条变更从没评审过，目标（月底对账口径）没人对照过；'确认没做'：真实对账场景从没测过，25 号后的合同编号是真实对账时第一次出现；玉杰'系统没坏'恰恰证明技术（验证）过了≠规则/用途（确认）缺失——坏的从来不是机器；缺评审=需求错了没人发现白做、缺确认=做对了也没人用白做；复盘显影了偏差（两条行动项），但裁决（归属规则归谁定）是第14章治理的棒——复盘是检测器不是裁决者。" | 三关逐关拆 + 玉杰证人 + 缺一关代价 + 复盘/裁决全到位 |

**产品侧 vs IT侧**：产品组举"M3 断链事故——验证（试验）做了、确认（真实车）没做"；IT 组举"恒信对账事故——验证（UAT 全绿）做了、评审与确认没做"。两边都是同一句因果——**只验证不确认，隐含需求系统性漏失，测试全过、没人用**。

**反转话术**（对应 §8.4.1/§8.4.3/§8.4.4 + 案例进展⑤）：三个看门人不是三座孤立的门，它们串起来，是一条需求到上线的**三关**：评审站在开工前抬头看方向、验证站在交付时低头对规格、确认站在交给用户时走进真实场景。**缺任何一关，故事都不一样**：缺评审=需求错了没人发现，白做；缺验证=做错了没人知道，返工；缺确认=做对了也没人用，白做。

恒信这次对账事故，徐漾写了六个字：**"验证做了，其余没做。"** 玉杰查完一圈补了一句：**"系统本身没坏——月底并发我盯着，没崩、没卡、日志干净。坏的从来不是机器，是'25 号后算哪个月'这条规则，从没被写进系统。"** 技术（验证）过了 ≠ 规则/用途（确认）到位——运维证人把"验证过了、确认缺失"照得清清楚楚。最要紧的那句因果，值得贴在墙上：**只做验证不做确认，隐含需求系统性漏失——测试全过、没人用，不是运气问题，是因果问题。**

而这场复盘本身——徐漾让万辉把两条行动项记下来（"变更必须先过评审对目标一关"+"UAT 改真实场景跑"，各配负责人和期限）——**复盘是检测器**：它像传感装置一样例行运行，把偏差显影出来（对不上账、漏了场景、口头变更没记录）。但**复盘发现偏差，不等于治理裁决**：对偏差做裁决（合同编号归属规则要不要定、归谁定）才是治理，那是第14章的事。**只诊断不闭环的复盘，是把同样的错再复一遍。**

**参考答案要点**：三关见 §8.4.1；缺一关代价表见 §8.4.1；因果链见 §8.4.4；复盘=检测器见 §8.4.3；案例进展⑤（黄程 + 玉杰证人）。

### Q7 为什么"能上线"评不了？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "评审就是定个上线时间。" | 正是要翻的——目标没具体化，评审没有尺子 |
| 中 | "目标要具体。" 结论对，配方/通过标准没接上 | 目标具体化配方、通过标准会前定没落到动作 |
| 好 | "目标具体化配方=对象+时限+可衡量结果：月底对账（上线后第一个月底，对账单与台账逐笔核对一致率 100%、对账时间 ≤2 小时）/法务合规（电子签章合同审批链完整、可追溯）/业务可用（3 个工作日内完成一次合同发起到归档）；通过标准会前定、会后逐条打勾——'能上线'没有可衡量结果，评不了；徐漾摆出目标，立刻发现电子签章变更连需求都不是，是口头承诺；目标不是供方自定、是需方与供方就成功判据达成的约定——业务方确认过才成为评审的尺子；每个把关节点都是一次转写，评审点卡在转写后对照上一层源；架构评审是评审的特化——四看（概念陈述/选定+ADR/视图·基线/回炉痕迹）缺一材料就是半成品、对质三问（关注点/理由/备选死因）防评审变汇报，架构没有'跑起来给你看'，只能被审明白（ISO 42030:2019 评估目的=架构对预期目的是否适宜）。" | 配方 + 三个具体目标 + 通过标准 + 目标=供需约定 + 转写点 + 案例① + 架构评审特化（含 42030）全到位 |

**产品侧 vs IT侧**：产品组举"M3 的评审目标——'断链即报废时还能撑到接入冷库'要具体成'断电保温 ≥72 小时、真实运输车跑全程'";IT 组举"恒信的评审目标——'能上线'要具体成'月底对账 ≤2 小时、审批链可追溯'"。两边同一个动作——**把抽象目标具体化成可打勾的尺子，再评审**。

**反转话术**（对应 §8.4.5/§8.4.2/§8.4.3/§8.4.9 + 案例进展①）：评审对目标有个操作性难题：**目标是抽象的，怎么评？答案是先把目标具体化，再评审。** 但要防一条读浅的路：**"目标"（ISO 9000 3.7.1）与"目的"（深层判据＝系统目的，系统在其环境中的目的）是两个词——目标具体化是操作性，评审的深层参照是"目的"**；定期评审以目的为参照，正是捕捉"目的漂移"（无症状的缓慢漂移）的传感装置——呼应第14章两类扳机（目的变更=显式发生的强制扳机，靠变更流程强制挂钩；目的漂移=无声漂移，靠以目的为参照的定期检视）。目标 = **对象（谁/什么）＋ 时限（何时）＋ 可衡量结果（多少）**。"做出高质量的产品"评不了，"上线后 3 个月内月底对账时间从 3 小时降到 2 小时以内"评得了。评审会开场前先做**会前三检**：通过的标准是什么？达标有没有可观察/可测量的判定？两个人理解不一致看什么裁决？三个都答得上，这个评审有尺子；答不上来，会开了也是白开。**通过标准的正确用法，是随评审邀请一起发出，会前定好、会后逐条打勾。**

还要看清目标的来历：**它不是供方自定的，是需方与供方就"成功判据"达成的约定**——业务方提方向（要达成什么可度量结果）→ 供方把它翻译成可评审的操作目标 → 回来请业务方确认 → 确认过，它才成为评审的尺子。第4章链头说"立得对不对要业务方点头"，说的就是这一笔。操作目标还有**第二身份**：它是确认参照里明示的那一半——进评审全身进入、进确认只是显性子集，所以**操作目标全绿不等于确认通过**（§8.2.7/§8.3.5）。

而评审不是只做上线前一次——它是洒在整个流程上的门禁：需求评审、设计评审、代码评审、测试评审、发布评审、复盘，**五个把关节点 + 一个复盘节点**。为什么洒到全程？问题越早发现修复成本越低——需求阶段的缺陷修复成本是 1，发布后是 30~70 倍。把"把关"从终点挪到全程，把返工成本高的那段堵在源头。为什么偏是这些节点？**因为每个节点都是一次转写**——需求译成设计、设计译成代码、代码译成测试、测试译成发布，每译一次，"想要的"就可能被带偏一层；评审点卡在每次转写之后对照上一层的源——**评审点的密度就是转写层的密度**。顺带磨一个最易混的边界：复盘是第六个节点，但**复盘不是评审**——评审管把关、复盘管改进；复盘是检测器，裁决是治理（第14章）。

还有一层特化值得单独说——**架构评审**。架构没有"跑起来给你看"这回事，只能被想清楚、被说明白、被审明白，所以**架构靠评审验证、不靠测试**——标准家族还专立了一部 ISO/IEC/IEEE 42030:2019（架构评估框架：42010 管描述 / 42020 管过程 / 42030 管评估），它的评估目的落在"架构对预期目的是否适宜、是否回应了预期目的"，和本章"评审对目标"是同一句话的两个出处。评审材料先过**四看**：概念陈述（不可还原涵义说清了吗）/ 选定 + ADR（为什么是它、被否备选死因）/ 视图·基线（AD 冻结受控了吗）/ 回炉痕迹（上一轮异常闭环了吗）——**四看缺一，材料就是半成品**。评审会再对**质三问**：回应了谁的关注点？决策的理由是什么（ADR）？被否掉的备选死因是什么？——死因说不出的决策，等于从没权衡过。**没有背书的架构，只是架构师的个人意见**（TR2/TR3 通过才放行）。

**参考答案要点**：目标具体化配方见 §8.4.5；目标=供需约定见 §8.4.5；会前三检见 §8.4.5；通过标准会前定见 §8.4.2；五个把关节点 + 一个复盘节点·转写点见 §8.4.2；评审≠复盘见 §8.4.3；架构评审四看·对质三问 + 42030 见 §8.4.9；案例进展①。

| 中 | "测试环境和真实环境不一样。" 结论对，三要素/冰山没接上 | 结论对，验证 vs 确认的判据拆解、冰山没讲透 |
| 好 | "验证三要素：万辉的 UAT 对照了需求清单、证据是测试通过率——但没覆盖全部规定需求，且让业务方当测试员；确认三要素：真实用户+真实任务+真实场景——万辉全缺（造数据/周二下午三个人轮流点/电子签章变更没排进 UAT）；断档 30 秒证明用例全过说明不了上路能过——测试台架稳得像桌面，真实车厢会颠，用例的参照是需求文档，真实场景的参照是'疫苗能不能安全送到'；隐含需求（振动下连续）只有确认兜得住——验证的尺子在文档、确认的尺子在场景。" | 两场各拆 + 三要素 + 参照差异 + 冰山全到位 |

**产品侧 vs IT侧**：产品组拆"M3——零部件试验/整机低温试验=验证（对规格），真实运输车跑全程=确认（对'疫苗安全送到'）；断档 30 秒台架复现不了"；IT 组拆"恒信——系统测试/UAT=验证（对需求清单），真实对账=确认（对'月底对账能用'）；25 号后合同编号真实对账才第一次出现"。两边同一个结论——**验证在文档的尺子上跑，确认在真实世界的尺子上跑**。

**反转话术**（对应 §8.3.2/§8.3.4/§8.3.5 + 案例进展③④）：两场测试放一起，把验证和确认的差别照得最清楚。恒信：徐漾三问——**月底对账的数据，用的是真实数据还是造的数据？真实月底时间点、真实并发下做的吗？法务的电子签章审批链，业务方验证过"谁审谁签"吗？** 三问全答不上。那次不是确认，是让业务方当测试员，把确认做成了验证。冰链：真实运输车跑全程，**断档 30 秒，台架复现不了**——因为测试环境里没有路；用例的参照是需求文档，真实场景的参照是"疫苗能不能安全送到"。这就是验证和确认的差别：**验证在文档的尺子上跑，确认在真实世界的尺子上跑。**

为什么场景兜得住、文档够不着？因为**真实场景自带答案**——月底对账、运输车颠簸、审批人休假，这些场景不会因为你没写文档就不存在。隐含需求像冰山，水面下占了大半；**验证是量吃水线的尺子（只管浮在水面上的部分），确认是把船开进那片水域的试航（水下撞没撞到，试航时才知道）。** 确认为什么兜得住验证够不着的东西？因为**确认的存在价值恰恰建立在非明示需求上**——如果所有需求都能写下来被验证，确认就不需要存在了。那些写不下来的（顺手、直觉、动效、节奏、惯例）和体验类的（手感要高级、用起来要顺），只有真实使用能裁决。**冰链那次真实运输连跑三天抓出的四个问题——颠簸断电、低温掉电、振动漏温、断网重连——翻回需求清单，一条都对不上：没有一条被写进过需求文档。它们是典型的隐含需求，真实存在、没人写过、验证够不着。确认的价值，正在这里：它把"没写下来的需求"显影成"看得见的缺陷"——那次颠簸断档 30 秒，就是需求文档里缺"振动下温度记录连续"这一条的证据。** 隐性缺失看不见，显影出来的缺陷看得见。

**参考答案要点**：徐漾三问见案例进展③；断档 30 秒见案例进展④；验证射程 vs 确认射程见 §8.3.4/§8.3.5；冰山比喻见 §8.3.5；确认的存在价值见 §8.4.4。

### Q9 亲手给"评审/验证/确认"各立一条判据（方法时刻 · 规则 15）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 背书上的判据："评审对目标、验证对需求、确认对用途。" | 只答了"是什么"，没做"立判据"这个动作——方法没上手；转述没做 |
| 中 | 自己立了一条判据（如"确认 = 用户用起来没问题"），但不可检验 / 判据主义三问没走全；转述讲到一半卡住但没追问缺口 | 有判据了，但失效边界/反例没给，量不了；转述卡壳处没暴露 |

**产品侧 vs IT侧**：产品组立"M3 确认判据——真实运输车跑'出库→运输→到达'全程、温度连续不断链"；IT 组立"恒信确认判据——财务在真实月底、用真实数据、跑真实对账任务、口径一致"。两边立出的判据结构相同；转述对象换个行业，卡壳处往往是同一个词（"验证"和"确认"）——**三把尺子的判据不挑行业，这正是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"**。

**反转话术**（对应方法底座时刻 = 判据主义 + 章末见过→拥有）：这是本单元的**方法时刻**——前面八题在讲三把尺子，这一题让你们亲手给三把尺子各立判据。判据主义三问：**是什么（可检验的定义）、失效边界（什么时候不适用）、反例（能不能被推翻）**。三把尺子各立的可检验判据——**评审**：参照是目标（对象+时限+可衡量结果）、不要求客观证据但结论必须记录（没记录=聊天）；**验证**：参照是规定需求（成文）、必须有客观证据、结论是"已验证/未验证"；**确认**：参照是预期用途（真实用户+真实任务+真实场景）、证据来自真实或模拟场景。

注意：**本章是判据主义章，方法时刻题就是判据运用题——判据不是背出来的，是当场立、当场用的。** 立完判据，再做**转述压缩测试**（v2.1 规则 15 新增形态）：用三五句话把三把尺子的区别讲给一个完全外行的人——三句话里若把"验证"和"确认"讲糊了，说明那把尺子还没真正分开，卡壳处正是翻译伪朋友那层糊纸最厚的地方。跨域：你把三把尺子的判据换到冰链 M3（零部件试验=验证、整机低温试验=验证、真实运输车跑全程=确认）还成立吗？判据不变——同一个概念、两个世界，这正是"概念不挑行业"的现场证明。

章首满海把笔悬在签字栏上的那一刻，正是三个看门人没到齐就要落笔——评审没签、确认没签，只有验证的一纸证据在。章末徐漾那句警告——"混到验收签字那一刻，就是合同纠纷"——现在你能说出全部含义：**验收不是一句话，是三个看门人依次签字：评审签'方向对'，验证签'做对了'，确认签'能用'——三个字都签齐，才轮到'验收通过'四个字。** 能答全四问才算拥有，这三把尺子现在装进你手里了。

```
    · 三要素：对照规定需求 + 客观证据 + 做出认定
    · 测试只是证据之一；逐级回收（V 模型右半边）；射程够不着隐含
  确认 validation 3.8.13 —— 对预期用途 · 认定 · 必须客观证据
    · 参照在场景里：真实用户 + 真实任务 + 真实场景（UAT/Beta/灰度/试运行）
    · 与验证共享同一套三要素、唯一区别在参照（文档 vs 场景）；兜隐含需求（冰山水下）：只做验证不做确认 → 测试全过没人用

ISO 9000 分家：评审在 3.11"确定"组（判），验证/确认在 3.8"规范"组（证）——中文糊了四十年
接力链：评审（开工前·方向）→ 验证（交付时·需求）→ 确认（交给用户·用途）
六概念闭环：目的 → 目标 → 需求 → 规定需求 → 客体（预期用途旁挂场景层）；两系统目的锚：冰链 M3=让疫苗在冷链运输中一路不失活、安全送达 / 恒信合同系统=让合同审批合规、月底账目清楚对得上（恒信"月底对账不再靠手工"、M3"断链即报废时还能撑到接入冷库"=这两个目的的操作展开）；两条旁路通道（环境/法规、干系人隐含需要）不经目标直接进需求；三形态分叉口：明示 → 规定需求 → 验证 / 隐含 → 场景 → 确认
五个把关节点 + 一个复盘节点洒全程：需求 → 设计 → 代码 → 测试 → 发布 → 复盘（每节点=一次转写）
辨析：评审 ≠ 核对需求｜验证 ≠ 测试（证据 vs 手段）｜确认 ≠ 让业务方点环境｜评审 ≠ 复盘
方向把关是两道闸：评审（早拦·纸面·预测·显性）→ 确认（终审·真实·实证·连隐含兜）——验证不沾方向
目标=需方与供方就"成功判据"达成的约定（业务方确认过才成为评审的尺子）；操作目标（MOE）全绿 ≠ 确认通过
架构评审特化（第11章六步⑥）：评审四看（概念陈述 / 选定+ADR 备选死因 / 视图·基线受控 / 回炉痕迹闭环）+ 对质三问（谁关注点 / 理由 ADR / 备选死因）——没有背书的架构只是架构师的个人意见（TR2/TR3 放行）
复盘 = 检测器（例行显影偏差），复盘触发的裁决才是治理（第14章）
合同编号对不上（月底对账）：三个看门人只来了一个，剩下两个在等一场事故
```

### 金句（书"本章判据"提炼）

- **评审对目标，验证对需求，确认对用途**——方向对不对、做对了吗、做对的东西了吗，三把不同的尺子，谁也替不了谁。
- **三连问句**：**产品的方向对不对？（评审）→ 在真实场景里立不立得住？（确认）→ 是不是满足规定需求？（验证）**——按"哪个错最贵"排：方向错白做、用途错没人用、实现错可返工；按站岗先后则是评审→验证→确认。
- 评审三问：**适宜性（对症）→ 充分性（够全）→ 有效性（管用）**——方向不对，做得再全也是白费；目标 = 对象 + 时限 + 可衡量结果；通过标准会前定、会后逐条打勾。
- **没记录的评审不算评审，最多算聊天**——团队参与、结果文档化、过程文档化，缺一个就是非系统性评审。
- 验证三要素：**对照规定需求 + 客观证据 + 认定**——测试只是提供证据的手段之一；测试报告是验证的输入，不是验证本身。
- 确认三要素：**真实用户 + 真实任务 + 真实场景**——让业务方点测试环境，是把确认做成了验证。
- **只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用**——不是运气问题，是因果问题。
- 隐含需求像冰山，水面下占了大半；**验证是量吃水线的尺子，确认是把船开进真实水域的试航**——水下撞没撞到，试航时才知道。
- **确认把"没写下来的需求"显影成"看得见的缺陷"**——案例进展④：颠簸断电、低温掉电、振动漏温、断网重连翻回需求清单一条都对不上，全是没写进需求文档的隐含需求；断档 30 秒，就是需求文档缺"振动下温度记录连续"的证据。
- 评审管把关，复盘管改进——**复盘是检测器，复盘触发的裁决才是治理**（第14章）。
- **架构评审审的不是图，是理由**——四看缺一材料就是半成品，对质三问防评审变汇报；没有背书的架构，只是架构师的个人意见。
- 确认是"同一套三要素、参照换成预期用途"——**承重柱（验证）是"谁生成谁"的结构，三把尺子各就各位才是正解**。
- **六概念闭环**：目的在最顶层、目标是其在操作层的展开；**需求来源不只目标**——环境/法规、干系人隐含需要不经目标直接进需求，靠需求工程兜底；明示→规定需求→验证，隐含→场景→确认。
- **两系统目的锚**：冰链 M3=**让疫苗在冷链运输中一路不失活、安全送达**；恒信合同系统=**让合同审批合规、月底账目清楚对得上**——恒信"月底对账不再靠手工"、M3"断链即报废时还能撑到接入冷库"，分别是这两个目的的操作展开。
- **目标不是供方自定，是需方与供方就"成功判据"达成的约定**——业务方提方向、供方翻译成操作目标、业务方确认过，才成为评审的尺子（第4章链头业务方点头）。
- **方向把关是两道闸**：评审早拦（纸面·预测·显性），确认终审（真实·实证·连隐含兜）——验证不沾方向。
- **操作目标（MOE）全绿 ≠ 确认通过**——操作目标只是预期用途要求的显性子集，达标是必要非充分。
- 运维的场景表里添上"月底对账"一格——**场景不写下来，确认就够不着它**。

## 五、课后作业

1. **书练习（与题卡同源）**：用一张表列出评审、验证、确认的参照、动作、证据、时机四个维度，再用你自己最近一个项目的具体例子各填一行。（书练习 1）
2. **书练习**：设计一次真正的确认——选一个你们系统的核心场景，列出真实用户、真实任务、真实场景、真实数据，写一份确认方案。（书练习 7）
3. **回部门落地**：结合现状，用评审三问、验证三要素、确认三要素三把尺子，给你们最近一次上线/交付做一次"三个看门人体检"——给出最该改进的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪个看门人补上了、哪个还虚着、卡在哪个判据上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次"三个看门人体检"：
>
> 1. **挑对象（先立枢纽）**：选一次最近"验收合格、可以上线"的交付——最自信的，往往是三关缺得最狠的（对照章首万辉那句"验收合格，可以上线"、满海那句"这个字我签了"）。
> 2. **第一关 · 评审对目标**：那次评审的通过标准，是会后现想的还是会前定的？评审前有没有先把目标摆出来（对象 + 时限 + 可衡量结果）？评的是目标，还是核对需求清单？那个目标，业务方确认过吗——目标不是供方自定、是需方与供方就"成功判据"达成的约定（业务方提方向→供方翻译成可评审的操作目标→回来请业务方确认→确认过才成为评审的尺子）？**话术**："如果只核对需求清单，你会说'全部覆盖，通过'——你的尺子是目标吗？业务方点头了吗？" 没结论、没记录，最多算聊天。
> 3. **第二关 · 验证对需求**：验证三要素齐吗——对照（规定需求成文了吗？口头补的算不算？）／证据（客观证据可复核吗？测试通过率是全量还是抽验？）／认定（有结论吗？"已验证/未验证"，不是"跑完了"）。验证是逐级回收的吗（V 模型：需求从哪一级分解、验证从哪一级回收）？
> 4. **第三关 · 确认对用途**：上线前有没有把产品放进真实场景（真实用户 + 真实任务 + 真实场景 + 真实数据）？UAT 是让业务方当测试员跑用例，还是跑真实业务任务？灰度/仿真算确认，但只算"初步通过"。对照玉杰那句"月底几十号人同时冲进去对账，测试环境替不了"——你们的真实并发，谁在真实条件下测过？
> 5. **因果链查漏**：有没有"没写进文档的需求"（口头补的 / 隐含的 / 强制的）？它验证够不着——它有没有被放进确认的场景里？**话术**："25 号之后签的合同算哪个月——这条在你们系统里，谁测过？" 对照小白那句"清单里没有的，用例里就没有"——你们口头补的需求，进过任何一份用例吗？
> 6. **架构评审特查（如做架构工作）**：最近一次架构评审，材料过了四看吗（概念陈述 / 选定+ADR / 视图·基线 / 回炉痕迹）？评审会是对质还是汇报（对质三问有人答得上吗）？有背书吗（TR2/TR3 谁放的行）？
> 7. **复盘闭环**：上线后复盘产出的行动项，有负责人 + 截止日期吗？上轮行动项关闭率 ≥ 80% 吗？复盘显影的偏差，由谁做了裁决（裁决是治理，第14章的棒）？
> 8. **转述压缩测试（收尾）**：用三句话，把"评审/验证/确认"三把尺子的区别讲给一个完全外行的人——讲到哪卡住，缺口就在哪。把卡壳处和体检里最不过的那一关对一对，往往同一个地方。
> 9. **出体检报告**：三关各下结论（通过 / 有条件通过 / 不通过），**最该先补最不过的一关**；最后一条建议照书抄——把"验收"从一句话改回"三个看门人依次签字"。
>
> 卡住时：答不上来的那一关就是最该补的——评审没判据就查第一关；测试全绿但没人用就查第三关（因果链）；口头需求一堆就查第二、三关；架构评审过图就通过就查第六步。不用三关全做完，找到第一个答不出的关卡就能开工。
