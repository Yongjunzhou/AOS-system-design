## 一、单元导读

### 主题

这一章回答全书最重的一个问题：**架构到底是什么？** 水忠在架构评审会上投出那张四层方块图，说"这就是我们 M3 的架构"——画了、评审了、存档了，还要怎样？可三个月后，改采集间隔影响什么没人能答、断电补传归谁没人认领、客户问" M3 是什么系统"三个人三个答案。这一章要推翻的正是那个直觉：**架构不是一张框图，是系统不可还原的涵义；系统 ≠ 架构 ≠ 架构描述；而好的架构，是约束，也是解放。**

### 开场破题（对应章首误解现场）

念出冰链架构评审会那场戏：水忠把 U 盘插上投影，屏幕上出现一张图——四层方块，从下到上硬件层、固件层、云端层、App 层，箭头从传感器一路画到 App，旁边标着"温度数据"。"这就是我们 M3 的架构。"水忠讲了十分钟，散会。图被存进共享盘，文件名"M3-架构v1.0"，再没人打开过它。三个月后三个问题先后找上门：产品经理文正要改采集间隔——影响什么，没人能答；水忠要加断电补传——重连逻辑在哪一端，云端说固件的事、固件是水忠自己写的根本没有；客户问"M3 到底是什么系统"——温控箱、追溯平台、冷链管理 App，三个团队三个答案。水忠翻出图想维护，忽然意识到一个让他后背发凉的事实：**这张图，从来没有描述过真正的 M3。**

让各组表态：水忠他们冤不冤——架构画了、评审开了，还要怎样？大多数人一开始都站在"冤"这一边——这正是这一章要推翻的直觉。

### 本单元要反转的直觉

- **架构 = 一张框图，画完没人维护就完事**（× 框图只是架构描述里粗糙的一小块；架构是那组不可还原的决定）
- **图过时了 = 架构过时了**（× 过时的只是描述；决策可以一直有效——图可以烂掉，决策可以活着）
- **我们有业务/数据/应用/技术——四个架构**（× 一个系统只有一个架构，那四个是关注域视角）
- **用了 Spring Cloud = 微服务架构**（× 框架给骨架不给决策；用框架 ≠ 有架构）
- **架构 = 技术选型**（× 选型只是"概念或属性"的一种体现）
- **约束是给团队上枷锁，约束越少越灵活**（× 约束即解放——只约束要命的地方，回收积极自由）
- **架构定了"怎么造"的设计准则就够了**（× 缺演进准则，系统一改就坏——分布式单体）
- **架构是架构师一个人的事**（× 架构是团队共享心智模型和组织原则——康威定律）
- **视图越完整越好，一张图覆盖所有关注点**（× 每个视图是刻意的"不完整"）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 架构是什么 + 三问筛 M3 不可还原的涵义（破题·概念本身）→ Q2 三个词关系（系统/架构/架构描述，概念关系）→ Q3 图 vs 不可还原的涵义（真悖论）→ Q4 一个架构 vs 四个架构 + 风格/框架（真悖论）→ Q5 约束是枷锁 vs 约束是解放（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 框架 ≠ 架构，用"删掉它系统还在吗"测 Spring Cloud（判据运用）→ Q7 设计准则 + 演进准则 = 免疫系统，量水忠的老规矩（判据运用）→ Q8 相关方→关注点→视点→视图 + 场景是胶水，断恒信四张图（判据运用）→ **Q9 方法时刻·勤校准**（规则 15：亲手把"架构=框图"修正成"架构=不可还原的涵义"，含跨域变体）→ Q10 回部门写"老规矩"清单（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"系统"是冰链 M3 温控箱（硬件+固件+云端+App）——"架构 = 一张框图"是硬件世界的词病；IT 组的"系统"是恒信合同审批系统——"架构 = 四张图"是软件世界的词病。两边都容易把"那张图 / 那些图"当成架构本身，而把真正"少了它就不是它"的决定（数据所有权、断链刚性、追溯完整性 / 合同审批链、数据模型、流程实例）当成隐形的背景。**同一个修正（框图 → 不可还原的涵义）、两个世界、判据不变**，这正是本章"概念不挑行业"的现场证明。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"这就是我们 M3 的架构"——架构到底是什么？**
"冰链的架构评审会上，水忠把那张四层方块图投上投影——硬件层、固件层、云端层、App 层，一根箭头标着'温度数据'——说：'这就是我们 M3 的架构。'三个月后三个问题找上门：改采集间隔（1 分钟改 5 分钟）影响什么，会议室没人能答；加断电补传，云端和固件互相推'重连逻辑在谁那边'；客户问'M3 到底是什么系统'，三个人三个答案。水忠翻出图想维护，忽然意识到：这张图从来没有描述过真正的 M3。为什么说那张图不是 M3 的架构？架构到底是什么？用'架构三问'把 M3 不可还原的涵义筛出来。"

追问：① 三个问题各证明那张图缺了什么（采集间隔→关系/定在哪一环、断电补传→关系与原则、三个人三个答案→视角没对齐）——为什么'可靠性瓶颈在交互模式'？② 三判据对'断链即报废还能撑到接入冷库、全程可追溯'逐条打勾——为什么它是架构，而采集间隔不是？定义里'概念或属性'为什么是 or 不是 and？③ 为什么'在它的环境中'决定什么算基本（同一台温控设备，实验室台架 vs 冷链运输）？M3 相关方关注点为什么天然冲突、只能权衡（司机可用/客户可追溯/维修可维修/监管合规/老板成本）？④ 你们最近一次'架构评审'，审的是一张图，还是把关注点摆出来权衡？

**Q2｜系统、架构、架构描述，三个词什么关系？**
"请给出 系统、架构、架构描述 三个词的关系，并说明：为什么说它们是弗雷格模型的翻版（指称 ≠ 涵义 ≠ 符号）？为什么'图过时了'不等于'架构过时了'？"

追问：① 各给一个 M3 的例子（产线上的箱子 / 那组决定 / 水忠的图）？② 推论一：同一个架构可以有无数种描述（四层框图/数据流图/时序图/合规视图都在描述同一个 M3 架构）；反过来同一张图可能根本没描述对架构——水忠的图为什么属于后者？推论二：系统有生命周期，架构为什么活得比系统长？③ 架构描述按'相关方 → 关注点 → 视点 → 视图'链条组织——这和'三个词三层'什么关系？④ 你们平时说'架构'，说的是系统、架构还是架构描述？三个层面混着说会怎样？

**Q3｜架构是一张图，还是不可还原的涵义？**
"有人觉得：架构就是那张图——画出来了、评审了、存档了，架构工作就完成了。这一章说：架构不是一张图，是系统不可还原的涵义；图会过时，决定活着。哪个对？什么判据分清'图'和'架构'？"

追问：① 如果图就是架构，图过时了系统应该怎样？——可 M3 温控箱一直在正常工作，温度一直在采集、断链依然会告警，这说明什么？② 架构是静态快照吗？如果不是，它怎么'活'？（设计准则 + 演进准则 = 免疫系统；每次变更失误沉淀为原则更新）③ 为什么架构'不长什么样'？（宪法 / DNA / 组织架构类比——你看到的永远是文本/双螺旋/组织图，只有投影，没有'原图'）④ 你们有没有'图早就烂了、规矩一直活着'的时刻？

**Q4｜一个架构，还是四个架构？**
"恒信的万晖把合同审批系统的架构画成四张图：业务架构、数据架构、应用架构、技术架构，挂满一面墙。他说这是四个架构。软件圈还有'微服务架构''事件驱动架构'，水忠团队有人张嘴就是'用了 Spring Cloud'。这些到底是不是多个架构？什么判据能把它们分清楚？"

追问：① 两套分类维度（关注域 × 抽象层次）+ 架构风格 + 框架，四类各是什么（一栋楼的平面图+结构图+管线图+立面图 vs 概念草图→施工图 vs 框架结构/剪力墙结构 vs 预制构件+装配手册）？② 徐颺用一条真实场景横穿四张图（法务老张在 App 上审批一份 500 万的合同）——为什么走不完四张图，就是四个系统？③ 你们团队叫'XX 架构'的图/文档，用一条真实场景横穿过吗？

**Q5｜约束是枷锁，还是解放？**
"有人抱怨：架构是给团队上枷锁——定了数据所有权、定了断链刚性、定了兼容规则，这不是绑住手脚吗？约束越少越灵活。这一章说：约束即解放——约束把团队从无穷的重复决策里解放出来。两个都对吗？什么判据分清'束缚'和'解放'？"

追问：① 消极自由（freedom from）和积极自由（freedom to）差在哪？没有架构时你拥有哪种自由、丧失哪种自由？② 水忠的约束（数据所有权/断链刚性/追溯完整性）各自把团队从什么重复决策里解放了出来（改采集间隔不用开会、加新传感器不用重新吵架构）？③ '管得最准'和'管得最多'怎么区分？④ 你们系统里有没有'管得最准'的约束？有没有'管得最多'的约束？

### 第二组 · 落地与实践

**Q6｜用了 Spring Cloud，就是微服务架构吗？**
"软件圈几乎每天都能听见一句话：'用了 Spring Cloud，所以我们系统是微服务架构。'水忠团队也有人张嘴就是'M3 用的某某嵌入式框架'。这句话错在哪？框架和架构差在哪？用'删掉它，系统还在吗'测一测。"

追问：① 框架的三特征（骨架性/留白性/复用性）各是什么意思？② 为什么'骨架搭起来不等于架构有了'——服务边界、数据归属、接口契约，Spring Cloud 一个都没替你决定，为什么？③ 架构风格、框架、架构、架构描述怎么排成一条链（套路 → 物化 → 实例化 → 表达）？④ 你们用过的框架，替你们定了什么、没替你们定什么？没替你们定的那些，是不是正好是架构决策？

**Q7｜水忠的老规矩里，两类准则缺哪个会怎样？**
"水忠那天晚上把'老规矩'写了下来：温度数据归属追溯域，传感器只管采、云端只管传、追溯平台管存管管看；断链必须实时告警并记录，不得吞掉、不得延迟；固件升级必须向后兼容已出厂的设备。前两条是设计准则，第三条是演进准则。为什么两类准则缺一不可？只有设计准则、没有演进准则的微服务，会退化成什么？"

追问：① 设计准则（怎么造）和演进准则（怎么变）各管什么？② 为什么说架构是免疫系统（定义什么是'自我' + 主动防御变化）？③ 分布式单体是怎么形成的？④ 你们系统的演进准则写下来了吗？缺演进准则的那次变更，后来怎样了？

**Q8｜四张图为什么是四个系统？什么判据能让它们对得上？**
"恒信的万晖把合同审批系统的架构画成四张图，挂满一面墙。徐颺问他：'一份合同，在这四张图里分别是什么？'——业务架构里是一条审批流程，数据架构里是'合同主表 + 审批记录 + 附件'三个实体，应用架构里是审批引擎的一个流程实例，技术架构里没画合同。'就凭这最后一句，'徐颺说，'你的四张图是四个系统。'为什么？什么判据能让四张图对得上？"

追问：① 相关方 → 关注点 → 视点 → 视图这条链，四环各是什么（谁想看 → 关心什么 → 按什么规则看 → 看到什么）？② 为什么每个视图是刻意的'不完整'？把一切糊在一张图上会怎样？③ 4+1 的场景为什么是胶水不是第五个视图？④ 你们每个视图能说出'在回答谁的什么问题'吗？

**Q9｜亲手把"架构 = 框图"修正掉（方法时刻）**
"水忠把'架构'从'一张框图'修正为'不可还原的涵义'——第1章说，勤校准是正常纠偏，不是失败；概念是活的、可修正的。这一章的方法底座时刻，就是勤校准：完成一次枢纽修正。请亲手把'架构 = 一张框图'这个旧枢纽，修正成'架构 = 系统不可还原的涵义'——你靠什么动作完成这次修正？修正之后，'图过时了'意味着什么？"

追问（跨域变体）：① 冰链的老规矩（数据所有权/断链刚性/追溯完整性）和恒信的四张图（业务/数据/应用/技术），是同一个修正的两面吗？把'架构=框图'的修正用到恒信——判据变没变？② 架构师的核心能力不是'做出正确的决策'，而是'识别哪些决策不正确后果很严重'——水忠这次修正，识别出了什么后果严重的错误？为什么说架构师首先是一个工程师（第9章六项底座）？③ 你上次把某个概念从'见过的框图'推到'拥有的涵义'，是什么时候？

**Q10｜给你们的系统写一份"老规矩"清单**
"结合你们部门现状，给你们的系统写一份'老规矩'清单（参照水忠那天晚上把老规矩写下来）：先用架构三问筛出'少了它就不是这个系统'的决定，再分设计准则/演进准则两栏，再用一条真实场景横穿检验，最后用'约束即解放'复核每条约束解放了什么重复决策——给出最该补的三件事，每个落到一个动作。"

追问：① 三问筛的时候，最容易把哪一类'重要的事'误当架构？（可调参数 / 团队习惯 / 技术选型）② 架构是保真压缩（共享心智模型）——新成员入门、跨团队协作、决策讨论时，你们的'架构'提供共同语言吗？康威定律：构件边界 = 团队边界——你们的构件边界和团队边界对齐吗？③ 恒信四张图对不上——你们团队有没有类似的对不上？④ 两周后回来报告：哪条决定用三问筛出是/不是架构？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 "这就是我们 M3 的架构"——架构到底是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "水忠挺冤，画了图、评审了、存档了，还要怎样？三个问题是图没画细。" | 正是要翻的——把"画了图"当"做了架构" |
| 中 | 能说出"架构 = 系统不可还原的涵义"，但说不清用三问怎么筛 | 定义是背的，判据没用起来——没落到打勾 |
| 好 | "三问逐条打勾：去掉'断链即报废还能撑到接入冷库、全程可追溯'，M3 就退化成一只能调温的箱子；缺它监管意义上垮掉；换成'只要温度对就行'性质就变——这是架构。采集间隔三问答'否'，是详细设计。那张图只画了元素没画关系没画原则，所以它从没描述过真正的 M3。" | 定义 + 三判据 + 案例全咬合，能当场给 M3 下结论 |

**产品侧 vs IT侧**：产品组筛"M3——数据所有权、断链刚性、追溯完整性"；IT 组筛"合同审批——审批链、数据模型、流程实例"。两边都容易把"改采集间隔 / 改个字段"这种可调参数误当架构——**三问是筛选器，不是"重要的事"的排行榜**。

**反转话术**（对应 1.3 + 章首）：水忠那句"这就是我们 M3 的架构"错在把**那张图**当成了架构。图叫**架构描述**，而且是架构描述里极其粗糙的一小块——它画了元素，没画关系，更没画原则。架构是另一件事：**系统在其环境中的基本概念或属性，体现在其元素、关系以及设计演进原则之中**（ISO/IEC/IEEE 42010）。怎么辨认？用架构三问：**去掉它还是这个系统吗？缺少它系统垮吗？换掉它性质变吗？** 三问都答"是"，才是架构。"断链即报废还能撑到接入冷库、全程可追溯"三问皆"是"；采集间隔改 5 分钟，M3 还是 M3——那是详细设计。水忠那张图没画关系，而 M3 架构里最硬的秘密恰恰全在关系里：数据从传感器到追溯平台，每一跳断了谁补、谁告警——**可靠性瓶颈在交互模式，不在单个组件**。所以那张图三个月没更新不可怕，可怕的是团队从来没把"少了它 M3 就不是 M3"的那组决定写下来过。

**参考答案要点**：架构定义见 §9.2.2；三判据见 §9.2.3；元素与关系见 §9.2.4；案例进展①（"M3 到底是什么系统"）。

### Q2 系统、架构、架构描述，三个词什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把三个词排成一条线（系统 ⊂ 架构 ⊂ 架构描述） | 关系结构错误——它们是三种存在，不是包含 |
| 中 | 能说"系统≠架构≠架构描述"，但弗雷格模型和推论没接上 | 结论对了，机制缺——为什么"图过时≠架构过时"讲不出 |
| 好 | "系统=指称（产线上的 M3），架构=涵义（那组不可还原的决定），架构描述=符号（水忠的图）；涵义≠指称（弗雷格）；同一个架构可以有无数种描述，同一张图也可能没描述对架构；系统会报废，架构作为经验继续活。" | 三层 + 弗雷格 + 两推论全到位 |

**产品侧 vs IT侧**：产品组举"温控箱 / 数据所有权那组决定 / 四层方块图"；IT 组举"合同审批系统 / 审批链+数据模型+流程实例 / 四张图"。两边都要翻"图过时了=架构过时了"——**图是纸上的，会过时；架构是系统里那组不可还原的决定，真实存在，不会因为你没更新图就消失**。

**反转话术**（对应 1.1 + 2.1）：三个词对应第1章补充里的弗雷格模型：**指称（系统）≠ 涵义（架构）≠ 符号（架构描述）**。还记得"晨星"和"暮星"——两个词不同、呈现方式不同、指向同一个金星；弗雷格最重要的一句话是"涵义不等于指称"。架构领域就是翻版：M3 这台真实的箱子（系统）、M3 不可还原的涵义（架构）、水忠画的那张图（架构描述）。三个词之间藏着两个推论：**推论一，同一个架构可以有无数种描述**——四层框图、数据流图、时序图、合规视图，长得完全不同，都在描述同一个 M3 架构；反过来，同一张图可能根本没描述对架构。**推论二，系统不等于架构**——M3 会报废、会换代，但那组不可还原的决定，在系统消失之后还能作为经验、教训、下一代产品的设计前提继续活着。**架构和图，不在同一个世界**：图是纸上的、会过时的；架构是系统里那组不可还原的决定——图可以烂掉，决策可以活着。

**参考答案要点**：三个词三层见 §9.2.1；推论一/二见 §9.2.1；架构和图不在同一个世界见 §9.3.1；案例进展②（图过时了，决策还活着）。

### Q3 架构是一张图，还是不可还原的涵义？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "架构就是那张图，画完评审完就完事。" | 正是要翻的——把描述当本质 |
| 中 | "架构不是图。" 结论对，机制缺 | "图过时了系统却没坏"这条证据没用上 |
| 好 | "如果图就是架构，图三个月没更新，M3 应该和系统脱节——可 M3 一直在正常工作、断链依然会告警。变的只是细节（上传间隔），没变的是那组更底层的决定。所以图是投影，决定才是实体；架构不长什么样（宪法/DNA/组织架构类比）。" | 反事实检验 + 类比 + 判据全到位 |

**产品侧 vs IT侧**：产品组举"图旧的箱子一直在产线上跑"；IT 组举"架构文档过时但系统正常"。两边都要翻"图过时了=架构过时了"——**过时的只是描述；架构决策本身可以持续有效**。

**反转话术**（对应 2.1）：水忠的病不是"没画好图"，是**把图当成了架构**。如果一个系统的架构"过时了"，系统本身会怎样？水忠团队：图三个月没更新，可 M3 温控箱一直在正常工作，温度一直在采集、一直在上传、冷链一直在被追溯——图是旧的，系统是新的，两者早已分道扬镳。如果图就是架构，架构早就该和系统脱节了——可实际上 M3 的"根本逻辑"没变。这指向一个反直觉的结论：**架构和图不在同一个世界。** 顺着再走一步：架构"长什么样"？答案同样是反直觉的——**架构不长什么样**。"长什么样"是视觉范畴的问题，架构是逻辑范畴的存在。宪法长什么样？你看到的永远是宪法文本，宪法本身是一套治理规则；DNA 长什么样？你看到的是双螺旋结构图，DNA 本身是碱基序列里编码的生命信息；一个公司的组织架构长什么样？你看到的永远是组织架构图。架构是同一类存在：**你能画出来的永远是架构描述——从某个视角、回答某组关注点的一份投影。只有投影，没有"原图"。** 架构也不是静态快照——它自带"怎么造"和"怎么变"两套规则（设计准则 + 演进准则），是活的学习系统，见 Q7。

**参考答案要点**：不是一张图·先看病见 §9.3.1；架构不长什么样见 §9.3.1（宪法/DNA/组织架构类比）；案例进展②（图过时了，决策还活着）。

### Q4 一个架构，还是四个架构？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "我们确实有四个架构，业务、数据、应用、技术各管一摊。" | 正是要翻的——把视角当多个架构 |
| 中 | "一个系统只有一个架构。" 结论对，判据缺 | 两套维度 + 场景横穿没接上 |
| 好 | "业务/数据/应用/技术是关注域视角，概念/逻辑/物理是抽象层次，微服务/事件驱动是架构风格，Spring Cloud 是框架——都不是多个架构。判据一条真实场景横穿：一份合同走不完四张图，就是四个系统（技术架构没画合同就是证据）。" | 四类全分清 + 场景判据全到位 |

**产品侧 vs IT侧**：产品组举"M3 的硬件视图/软件视图/客户视图三个视角对不上"；IT 组举"四张图用同一个词'合同'指四种东西"。两边都是同一件事——**不是架构有多个，是描述没有统一**。

**反转话术**（对应 2.2）：市面上"业务架构""数据架构""应用架构""技术架构"满街都是，先钉死结论：**一个系统只有一个架构**。所有"XX 架构"都是对同一个架构从不同角度、不同抽象层次上的描述——它们是架构的视图，不是多个独立的架构。日常用语把"架构描述"简称成"架构"、"架构视图"也简称成"架构"，简称来简称去，听起来就像系统有多个架构了。**就像一个只有一副骨骼的人，医生可以正面拍 X 光、侧面拍 X 光、横切面拍 CT 切片——这些是同一副骨骼的影像，不是多副骨骼。** 这些"XX 架构"来自两套独立的分类维度：**关注域**（业务/数据/应用/技术——按"看什么"切分）和**抽象层次**（概念/逻辑/物理——按"多详细"切分），交叉出每个具体视图。还有第三类——**架构风格/模式**（微服务/事件驱动/分层）：那不是架构的视图，是**架构决策的套路**，相当于框架结构/剪力墙结构——结构体系的选择，不是建筑本身。第四类——**框架**：把套路"物化"成的可复用制品（Spring Cloud、4+1、TOGAF）——见 Q6。怎么证明四张图对得上？**拿一条真实场景横着穿过去**："法务老张在 App 上审批一份 500 万的合同"——业务架构走哪条流程、数据架构动哪些表、应用架构调哪个服务、技术架构跑在哪台机器？一条场景走不完四张图，四张图就是四个系统。

**参考答案要点**：一个系统一个架构见 §9.3.2；两套维度见 §9.3.2；架构风格见 §9.3.2；框架见 §9.3.2 第四类；案例进展③（恒信四张图，场景是胶水）。

### Q5 约束是枷锁，还是解放？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "约束当然是枷锁，约束越少越灵活。" | 正是要翻的——把解放当限制 |
| 中 | "约束即解放。" 结论对，机制浅 | 消极/积极自由没接上 |
| 好 | "没有架构时你拥有消极自由（没人拦你），但失去积极自由（每个决策都要重新推演上下文）；架构只约束'不改会灾难'的决定（数据所有权/断链刚性/追溯完整性），把团队从'要不要拆服务、数据放哪、接口怎么定'的重复决策里解放出来——管得最准，好过管得最多。" | 两种自由 + 约束边界 + 判据全到位 |

**产品侧 vs IT侧**：产品组抱怨"成本红线、法规要求是枷锁"；IT 组抱怨"数据归属、接口契约是枷锁"。两边都要翻"约束越少越灵活"——**约束换来的是把注意力从重复决策里解放出来，投到真正不可逆的决定上**。

**反转话术**（对应 3.7）：这是全章第三个反直觉命题，也是最容易被误解的一条。直觉上，架构是约束——规定数据放哪、接口怎么定、哪里不能越界，听着像上枷锁。这一节说的恰恰相反：**架构约束不是限制，而是回收积极自由。** 先区分两种自由：**消极自由**（freedom from）——不受约束，"我想怎么做都行"；**积极自由**（freedom to）——有能力高效做成，"我知道怎么做是对的"。没有架构的时候，你拥有消极自由（没人拦着你），但你同时丧失了积极自由——**每个决策都需要重新推演上下文**：数据放哪个库，要评估 7 个数据库 × 3 种访问模式；要不要拆服务、接口怎么定义，每次重新吵。有架构后（"订单域数据归属订单服务自有数据库"）——"这个功能的数据放哪个库？"→ 订单服务自有库。下一个问题。**所以好的架构不是"管得最多"，而是"管得最准"**——只约束那些不改就会造成灾难的东西，剩下的交给执行者自由发挥。水忠们怕"加架构就是加约束"，是因为他们把"约束"理解成了"限制所有事"；实际上 M3 的架构约束的只有那几条要命的规矩，而这几条约束恰恰是解放：采集间隔调成 5 分钟不用开会讨论、新传感器加不加不用重新吵架构。

**参考答案要点**：约束即解放见 §9.4.7；消极/积极自由见 §9.4.7；案例进展④（把 M3 的架构说清楚）；本章判据 6。

### Q6 用了 Spring Cloud，就是微服务架构吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "用了 Spring Cloud，所以我们是微服务架构。" | 正是要翻的——把框架当架构 |
| 中 | "框架 ≠ 架构。" 结论对，机制缺 | "骨架搭起来不等于决策有了"没接上 |
| 好 | "Spring Cloud 是框架——骨架+位置+组织规则，内容后填；服务边界划在哪、数据归哪个域、接口契约怎么定，它一个都没替你决定；删掉 Spring Cloud，系统还在吗？在——它只是被借来的。改动服务边界，系统就不是那个系统了。" | 三特征 + 试金石 + 边界全到位 |

**产品侧 vs IT侧**：产品组举"M3 用的嵌入式框架是骨架，不是 M3 的架构"；IT 组举"Spring 全家桶是工具，不是架构"。两边都要翻"用框架 = 有架构"——**框架给你的是骨架，不是决策**。

**反转话术**（对应 2.2 第四类）：软件圈几乎每天都能听见"用了 Spring Cloud，所以我们系统是微服务架构"。Spring Cloud 是一套开源**框架**——服务注册、配置中心、熔断降级，现成的轮子一堆；你下载、引入、按它的规则填业务代码，微服务项目的骨架就搭起来了。**但骨架搭起来，不等于架构有了。** 服务边界划在哪、数据归哪个域、接口契约怎么定——这三样，Spring Cloud 一个都没替你决定。框架可以给一个跨领域的定义：**对某一类事物或活动，预先提供的"骨架 + 位置 + 组织规则"——它规定内容的结构、边界和相互关系，但本身不填充具体内容，留待使用者填入。** 三个特征：骨架性（结构先行）、留白性（扩展点留给你填）、复用性（面向一类场景，不面向一个实例）。框架和架构最根本的分界：**架构是"这一个"的组织本质，框架是"这一类"的组织方式；架构属于系统，框架属于领域。** 一个系统有且只有一个架构；框架是系统**借来**的——可以换，甚至可以完全不用、自己发明。**试金石一句话：删掉它，系统还在吗？** 换掉 Spring Cloud，你的系统还是那个系统；改动服务边界，你的系统就不是那个系统了。把这条链排出来：架构风格（套路）→ 固化成框架（套路的具体化）→ 应用到具体系统 + 叠加独特决策 → 架构（这个系统的本质属性）。**框架给你的是骨架，不是决策；"这一个"是什么，框架永远回答不了。**

**参考答案要点**：第四类——框架见 §9.3.2；框架三特征见 §9.3.2；试金石见 §9.3.2 末段；本章判据 8。

### Q7 水忠的老规矩里，两类准则缺哪个会怎样？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "规矩都写下来了，架构就稳了。" | 分不清"怎么造"和"怎么变"是两套规则 |
| 中 | "设计准则管造，演进准则管变。" 结论对，后果缺 | 缺一个会怎样（分布式单体）没接上 |
| 好 | "只有设计准则没有演进准则：系统建出来是对的，但一改就坏——第二个月有人直接改同事服务的内部实现，架构还标着'独立部署'，实际已耦合，退化成分布式单体；只有演进准则没有设计准则：知道怎么变，但最初服务边界就划错了，怎么变都在错的框架里打转。两类合起来，才构成'既定义正确，又维护正确'的闭环。" | 两类准则 + 缺一后果 + 免疫系统全到位 |

**产品侧 vs IT侧**：产品组举"M3 固件升级向后兼容已出厂的设备是演进准则"；IT 组举"新增服务不能耦合已有服务内部实现是演进准则"。两边都要翻"定了怎么造就够了"——**架构是免疫系统：设计准则定义什么是'自我'，演进准则主动防御变化**。

**反转话术**（对应 2.3）：架构不是一张静态的快照，它自带"怎么造"和"怎么变"两套规则。**设计准则**管怎么造——约束从无到有的创建过程（每个服务独立部署、服务间通过 API 通信不共享数据库）；**演进准则**管怎么变——约束随时间变化的过程（新增服务不能耦合已有服务内部实现、服务拆分保持向后兼容）。为什么两类缺一不可？**只有设计准则，没有演进准则**：系统建出来是对的，但一改就坏——微服务建好了，第二个月有人为了省事直接改同事服务的内部实现，架构还标着"服务独立部署"，实际已经耦合了，最终退化成架构圈著名的病名——**分布式单体**（distributed monolith）：服务越来越多、耦合越来越紧、本质已经塌了，名字还叫微服务。**只有演进准则，没有设计准则**：系统知道怎么变，但建出来就不对——规则写了一大堆"变更保持向后兼容"，可最初的服务边界就划错了，怎么变都在错的框架里打转。两类原则合在一起，构成一个完整闭环——**既定义正确，又维护正确**。这个闭环有个名字：**架构是系统的免疫系统**——其一，它定义什么是"自我"（设计准则说清哪些决定构成了本质，偏离就是"病变"）；其二，它主动防御变化（演进准则说清变化可以怎么来、不能怎么来）。而且架构是**活的学习系统**：每次架构层面的变更失误，都应该沉淀为一条架构原则的更新。

**参考答案要点**：设计准则/演进准则见 §9.3.3；免疫系统见 §9.3.3；分布式单体见 §9.3.3；案例进展④（老规矩两栏）；本章判据 7。

### Q8 四张图为什么是四个系统？什么判据能让它们对得上？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "模板没错，四张图各画各的，对不上是行业常态。" | 正是要翻的——把视角当多个架构 |
| 中 | "要对上。" 结论对，链条缺 | 相关方→关注点→视点→视图没接上 |
| 好 | "同一个架构的四个关注域视角必须对得上：业务里那份合同走到'法务初审'，数据里'审批记录'这个实体就得有'法务初审'这条记录；判据=一条真实场景横穿四张图（4+1 的场景是胶水），走不完就是四个系统；每个视图是刻意的'不完整'，但所有视图合起来说的是同一个 M3/合同审批系统。" | 链条 + 场景判据 + 刻意不完整全到位 |

**产品侧 vs IT侧**：产品组举"给疾控看追溯链路视图、给司机看状态视图、给维修看结构视图、给监管看合规视图——四样没有一样是那张四层方块图"；IT 组举"四张图用同一个词'合同'指四种东西"。两边都是同一件事——**每个相关方看到自己该看的那一面，而它们合起来说的是同一个系统**。

**反转话术**（对应 3.1~9.4.4）：架构必须被**表达**出来，才能被共享、被讨论、被检查、被传承——**涵义锁在脑子里，没有用**。但"表达"立刻撞上一个难题：不同的人关心不同的东西。于是 ISO 42010 用一条链解决"一个涵义，多种表达"：**相关方（谁想看）→ 关注点（关心什么）→ 视点（怎么看的规则）→ 视图（看到的产物）→ 组合成完整架构描述 → 表达架构 → 属于系统**。为什么恒信四张图是四个系统？因为每个相关方都有自己关心的东西，而"一份合同"在四个视图里被画成了四种东西——业务里一条流程、数据里三个实体、应用里一个流程实例、技术里没画。徐颺说：**"你用的是同一个词'合同'，却在四个图里指了四种东西。"** 判据是什么？**拿一条真实场景横着穿过去**：法务老张在 App 上审批一份 500 万的合同——业务架构走哪条流程？数据架构动哪些表？应用架构调哪个服务？技术架构跑在哪台机器？**一条场景走不完四张图，四张图就是四个系统。** 这正对应 4+1 视图模型的"+1"——场景不是第五个视图，是**胶水**：拿一条真实使用场景横穿前四个视图，检验它们是否互相矛盾。还有一个关键细节：**每个视图都是刻意的"不完整"**——逻辑视图不展示部署、物理视图不展示类关系，这不是缺陷，是设计目的；把一切都糊在一张图上，对任何人都没用。视图的完备性由相关方及其关注点决定，不由方法论决定。

**参考答案要点**：为什么需要架构描述见 §9.4.1；相关方与关注点见 §9.4.2（关注点天然冲突）；视点与视图见 §9.4.3（相机比喻 + 刻意不完整）；4+1 见 §9.4.4（场景是胶水）；案例进展③（恒信四张图）；案例进展④（冰链四个视图）；本章判据 4·5。

| 中 | 自己做了修正（"把'图'从'架构'降到'架构描述'"），但说不清靠什么动作 | 修正做出来了，枢纽修正的机制（勤校准=正常纠偏）没讲 |

**产品侧 vs IT侧**：产品组做修正时自然把"那张四层方块图"降格为"架构描述"；IT 组把"四张图"降格为"架构描述"。两边立出的判据相同（三问）——**这就是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"；概念不挑行业**。

**反转话术**（对应方法底座时刻 = 勤校准 + 1.3 末枢纽修正段）：这是本单元的**方法时刻**——前面九题在讲"架构是什么"，这一题让你们亲手做一遍方法底座时刻：**勤校准（枢纽修正）**。第1章说过，概念是活的、可修正的——**勤校准是正常纠偏，不是失败**；1.2 那段行业史，本身就是"架构"被一路校准的轨迹：早期"架构=图纸"→1970s 结构化设计→1990s 软件架构热→2011 ISO 42010 定稿。水忠要做的不是背一条新定义，而是完成一次校准：**把"架构"从"见过的框图"推到"拥有的涵义"**。怎么完成？靠三问当尺子：把框图上每个元素、每根箭头，用"去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗"一测——图上的元素筛掉后 M3 还是 M3，于是"图"从"架构"的位置降格为"架构描述"。修正之后，"图过时了"不再意味着"架构过时了"，而是"描述过时了，决定还活着"。跨域变体：**冰链的老规矩（数据所有权/断链刚性/追溯完整性）和恒信的四张图（业务/数据/应用/技术），是同一个修正的两面**——把"架构=框图"的修正用到恒信，判据变没变？没变：三问一测，四张图降格为架构描述，真正属于合同审批系统架构的是审批链、数据模型、流程实例那组决定。**同一个概念、两个世界、判据不变。** 反身：你们脑子里还有没有别的"框图式"概念——把描述当本质、把载体当判据？

**参考答案要点**：方法底座时刻（勤校准·枢纽修正）见 00-案例设定 §三 第10章行 + 教材书 §9.2.3 末；三判据见 §9.2.3；架构师核心能力见 §9.4.7；架构师首先是一个工程师见 §9.4.9（第9章六项底座）。

**参考答案要点**：架构是压缩见 §9.4.5；三回报见 §9.4.6（含康威定律）；约束即解放见 §9.4.7；案例进展④（冰链把 M3 的架构说清楚）；作业指南见本章分析文档第 6 步；判据见"本章判据"。

```

  系统     —— 实际存在的那个东西（M3 实物）

架构描述：相关方 → 关注点（天然冲突，只能权衡）→ 视点（怎么看的规则）→ 视图（刻意的"不完整"）
          4+1：逻辑 · 过程 · 开发 · 物理 + 场景（胶水，验证四视图一致性）
约束即解放：消极自由（没人拦）vs 积极自由（知道怎么做对）——架构回收积极自由
架构的回报：认知（压缩/心智模型）· 决策（划定解空间）· 变更（免疫系统）· 组织（康威定律）
架构师的理论：什么是"重要的"需要判断——"Architecture is about the important stuff. Whatever that is."
```

### 金句（书"本章判据"提炼）

- **架构三问**：去掉它还是这个系统吗 / 缺少它系统垮吗 / 换掉它性质变吗——三问都答"是"，才是架构；答"否"的，是详细设计。
- 系统（指称）≠ 架构（涵义）≠ 架构描述（符号）——**图可以烂掉，决策可以活着。**
- 一个系统只有一个架构："XX 架构"都是它的视角；**一条真实场景走不完四张图，就是四个系统。**
- 每个视图是刻意的"不完整"——把一切糊在一张图上，对任何人都没用。
- 相关方的关注点**天然冲突，不可消除，只能权衡**；权衡的前提是先看到每个方面。
- 设计准则 + 演进准则 = **免疫系统**——缺一个，系统要么一改就坏（分布式单体），要么建出来就不对。
- 用框架 ≠ 有架构——**框架给你骨架，决策得自己做**；删掉它，系统还在吗？
- **约束即解放**：架构只约束"不改会灾难"的决定，把团队从重复决策里解放出来——管得最准，好过管得最多。

## 五、课后作业

1. **书练习（与题卡同源）**：挑一个你正在做的系统，回答"架构三问"：有哪些决定是"去掉就不再是它"的？写下至少三条。（书练习 1）
2. **书练习**：你们团队现在有没有一份"从没写下来、但大家都在守"的规矩？把它们写下来，标出哪些是不可还原的（架构），哪些只是习惯（非架构）。（书练习 10）
3. **回部门落地**：结合现状，给你们的系统写一份"老规矩"清单——先用架构三问筛出"少了它就不是这个系统"的决定，再分设计准则/演进准则两栏，再用一条真实场景横穿检验。给出最该补的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪条决定用三问筛出是/不是架构。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次"老规矩"清单：
>
> 1. **挑系统（先立枢纽）**：选一个"最近做、你心里最有底"的系统——最有底的，往往是那张图最老、老规矩最没人写下来的。**话术**："你最熟的那个系统，把它的架构说给我们听——三分钟，不许画图。"
> 2. **项目一 · 三问筛决定（架构三问）**：把团队所有"重要的事"列出来（数据归属/接口契约/告警策略/部署方式/技术选型……），逐条用三问筛："去掉它还是这个系统吗？缺了它系统垮吗？换掉它性质变吗？"三问都答"是"的，才是架构。**话术**："少了这条规矩，M3 还是 M3 吗？"
> 3. **项目二 · 图和决定分开（三个词三层）**：把那张"架构图"翻出来，和筛出的决定对比——图里画了什么、没画什么？"图过时了"和"决定过时了"是两回事。**话术**："图可以烂掉，决策可以活着。"
> 4. **项目三 · 分两栏（免疫系统）**：把筛出的决定分成两栏——设计准则（怎么造：数据归属、断链刚性）+ 演进准则（怎么变：新增传感器不得破坏追溯链、固件升级向后兼容）。缺演进准则的那栏，就是"一改就坏"的高危区。
> 5. **项目四 · 一条场景横穿（场景是胶水）**：拿一条真实使用场景（如"一批疫苗从出库到接入冷库"），横穿你所有叫"XX 架构"的图/文档——走不通的地方，就是"多个架构"的病根。
> 6. **项目五 · 相关方补漏（关注点冲突）**：列出至少五个相关方及各自核心关注点（司机可用/客户可追溯/维修可维修/监管合规/老板成本）——有没有哪个关注点从没考虑过？冲突不可消除，只能权衡。
> 7. **项目六 · 约束即解放复核**：对每条筛出的约束，写下它把团队从什么重复决策里解放了出来——写不出来的约束，多半是"管得最多"不是"管得最准"。
> 8. **出清单**：哪些是"少了它就不是它"（架构，写进老规矩），哪些只是习惯（非架构，标注即可）；最后一条建议照书抄——把"架构评审"的标的，从"那张图"换成"那组不可还原的决定"。
>
> 卡住时：三问答不上来的那条就是最该补的；一条真实场景横穿不动的地方就是最该修的缝；约束写不出"解放了什么"的就是最该砍的。不必全做完，找到第一个卡住的地方就能开工。
