## 一、单元导读

### 主题

这一章回答一个绕不开的问题：**让一直在变的东西说得清**——配置管理到底是干什么的？疾控审计问老周："这批疫苗记录是哪一版固件采的？"老周觉得冤："我们版本号不是有吗？v2.1、v2.2、v2.3 都标着呢。"结果查不清。大多数人对此的直觉正是：**版本管理做好了，就等于配置管理做好了。** 这一章要推翻的，正是这个直觉——版本只是时间轴上的刻度，基线才是把"已经批准的决定"冻结下来、让一切变化得以言说的参照；而"配置"——那个被"参数文件""个性化设置"遮蔽的概念——是这一切的地基。

### 开场破题（对应章首误解现场）

念出疾控审计那场问询：冰链的 M3 冷链温控箱在市场跑了一年多，散在约五千台物流车上。一个冬天，传感器偶发丢读数，老周修好、发新固件 v2.3，三个月分批升级约三千八百台。然后疾控中心来审计一批疫苗运输记录，问了一个以前从没人问过的问题："这批记录，是在哪一版固件下采集的？你们从这批之后，采集逻辑、断链判定升级过没有？"老周觉得这问题简单："查一下这批设备当时跑的固件版本。"结果查不清——升级记录只有一句"已推送 v2.3"，没有"哪台设备、哪个时间、从哪一版升到哪一版"的明细。

让各组表态：老周那句"我们有版本号啊，怎么就不算配置管理了"冤不冤？大多数人一开始都站在老周这边——这正是这一章要推翻的直觉。

### 本单元要反转的直觉

- **配置 = 系统设置里那页参数 / 个性化设置**（× 参数是零件，配置是装好的整机——配置是"被记录的形态"）
- **版本管理做好了 = 配置管理做好了**（× 版本只是刻度；配置管理是标识+控制+状态记录+审计四活动，缺基线和变更控制版本也管不住）
- **有版本号 = 有基线**（× 版本是刻度，基线是资格——被批准+被冻结+作参照，三特征全有才是基线）
- **基线一旦建立就永远不能改**（× 基线可以变更，但必须走变更控制，改完建立新基线。"冻结"不是"死锁"）
- **没有基线，变化也说得清——反正有 git 历史**（× git 历史是记录，基线是被批准、被冻结、被全项目认可的参照）
- **配置管理是文档的事，跟代码、硬件没关系**（× 任何配置项——代码、固件、硬件板卡、数据、图纸——都可立基线、走变更控制）
- **小团队、小产品，配置管理是大公司的负担**（× 配置管理可剪裁——至少"版本可指认、变更可追溯"；负担大头来自"查不清"的返工和事故）
- **变体就是版本，改个名字而已**（× 变体管空间、版本管时间，二者正交）
- **改一个参数就要改代码、重编译、重发布——这是正常的**（× 这是"变与不变没分离"的信号）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 配置/版本/基线各管什么（破题·概念本身）→ Q2 两族概念关系（配置三词 + 版本族四词，概念关系）→ Q3 参数文件是配置吗（真悖论）→ Q4 版本有了就有基线吗（真悖论·一横一竖）→ Q5 没有基线变化就不可言说（原理）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 客户能改的"告警阈值"到底是不是配置（判据运用·配置三问）→ Q7 final_2 连版本都算不上？（判据运用·版本判据+基线三问）→ Q8 一次"合规的固件升级"四活动复盘（判据运用·四大活动）→ **Q9 方法时刻·判据主义**（规则 15：判据主义 = 判据运用，亲手给"版本/基线"各立可检验判据，含判据主义三问——不重复出独立方法操作题）→ Q10 回部门配置管理体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"配置管理"是 M3 温控箱——固件、硬件板卡、云端追溯平台、App 都是配置项，追溯温度记录必须知道固件版本；IT 组的"配置管理"是合同审批系统——构建产物、需求文档、部署包都是配置项，回滚必须知道"回滚到哪一版"。产品组出问题靠"批次追溯查得清"、IT 组靠"回滚有地址"——**同一个概念、两个世界、判据不变**（配置提供内容 / 版本提供位置 / 批准提供资格），这正是本章"概念不挑行业"的现场证明。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"版本号不是有吗？"为什么还是查不清？**
"疾控审计员问老周：这批疫苗四月运输、全程温度记录正常——你们要证明，这批记录是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？老周说：这简单，查版本号，v2.1、v2.2、v2.3 都标着呢。可结果查不清。为什么'版本号是有了'，'这批记录是哪一版采的'还是答不上来？这一章要钉的三个词——配置、版本、基线——各管什么？"

追问：① 配置提供"内容"、版本提供"位置"、批准提供"资格"——三者为什么谁也不能替谁？② 老周的 v2.3 是版本还是基线？基线三问一答就穿帮，穿在哪一问？③ 老周缺的是配置管理四大活动（标识/控制/状态记录/审计）里的哪几个？④ 你们产品里"被批准、被冻结、全生命周期拿它对照"的那一版，能一指就指出来吗？

**Q2｜配置、版本、基线两族概念什么关系？**
"请给出 配置、配置项、配置信息 三词的关系；再给出 版本、修订、变体、基线 四词的关系——说明为什么'版本顺着流、基线垂直切'，为什么变体与版本正交，为什么基线是变体 × 版本的交叉点被盖章？"

追问：① 三个配置术语互相引用、首尾相连，为什么锚定'实体'后就不循环了？② 一份文档为什么既是'配置信息'又是'配置项'——两个层面怎么不冲突？③ 契约链：需求对方案、方案对实现，为什么说基线是每一级契约的'冻结端'、版本是'交付端'？④ 你平时说的"版本"，到底指的是四词里的哪一个？

**Q3｜参数文件到底是不是配置？**
"小赵指着 App 设置页说：这就是咱们的配置，客户能改的都在这页——温度上报间隔、超温告警阈值、断电告警开关、蜂鸣器音量。小林却说：配置不是这个参数，是那整套关联在一起塑成的'M3 的行为形态'。参数文件到底是不是配置？什么判据分清'配置'和'配置信息里的一个条目'？"

追问：① 变与不变的分离——为什么客户改上报间隔不用动固件、不用重编译（可变部分被外置），反过来改一个参数就要改代码、重编译、重发布是什么信号？② 三个隐形过滤器（类别/记录/关联边界）怎么从'实体的全部特性'切出'配置'子集？③ 你们产品里"客户能改的那几个开关"，到底是配置，还是配置信息里的条目？

**Q4｜版本有了，就有基线了吗？**
"老周觉得冤：我们有 v2.1、v2.2、v2.3，版本号都标着呢，升级也走流程了、小赵也验证过了，怎么就不算配置管理了？这一章说：版本只是刻度，基线才是参照；版本顺着流、基线垂直切。既然版本和基线都跟时间有关，为什么说它们方向完全不同？什么判据一眼分清'它是版本还是基线'？"

追问：① 里程桩 vs 收费站——为什么版本'顺着路'、基线'挡住路'？② 基线三问（被批准/被冻结/作参照）一问答不出会怎样？③ 变体与版本为什么正交（有几种形态 vs 走到第几步）？④ 第11章说不可逆决策要提前投资——这一章给'投资之后'配了什么守护（基线冻结 / 变更控制）？

**Q5｜没有基线，变化就不可言说——凭什么？**
"『从基线出发，一切变更都可描述；离开基线，一切变化都不可言说。』这句话凭什么成立？为什么'有 git 历史'替代不了基线？"

追问：① 描述一个变化必须有一个'从哪变起'的原点——没有原点像什么（在茫茫大海上说'我在动'，却没有岸标）？② git 历史是记录，基线是批准+冻结+作参照——两者差在哪一个动作（批准）？③ 基线建立之后，变化怎么走（变更控制五步在守什么）？配置管理的全部工作为什么是让'三问'任何时刻都有答案？

### 第二组 · 落地与实践

**Q6｜客户能改的"告警阈值"，到底是不是配置？**
"老周抱着一台已出厂的 M3，翻来覆去想小林的话：App 设置页上客户能改'上报间隔'、'告警阈值'——这到底是不是配置？小林反问：你改那个'告警阈值'，改的是什么？请用配置三问给'告警阈值'做一次裁决：它是配置，还是配置信息里的一个条目？"

追问：① '告警阈值'单独过三问，和'上报间隔 + 告警阈值 + 断链判定逻辑 + 采集算法'合起来过三问，结论差在哪——为什么是'关联成整体'那一问在起作用？② 为什么审计员问'这批记录是哪一版固件采的'，问的不是参数、是形态（哪套采集逻辑+判定逻辑组合成的行为）？③ 你们最常改的那个参数，改了之后"这台产品当时是什么样"还能说得清吗？

**Q7｜final_2 连版本都算不上？**
"恒信运维小王每次发布把构建产物扔进日期文件夹：'2026-05-12''2026-05-18'。两个月后合同状态流转 bug 暴露，李工要'回滚到上上个版本'，打开'2026-05-18'文件夹——里面 final.zip 和 final_2.zip 分不清哪个是哪个。Ada 说：'final_2 连版本都算不上，遑论基线。'请把这句话的量尺摆出来——用版本判据和基线三问，final_2 到底差在哪？"

追问：① 版本判据一问：final_2 能精确对应到'哪一次完整构建'吗（哪个代码提交、包含哪几条变更）？② 基线三问：它被批准了吗 / 被冻结了吗 / 作参照了吗？③ 为什么说'版本是回滚的地址，基线是变更的参照'——恒信补了发布基线后，'上上个版本'从猜测变成了什么（一句可执行的指令）？④ 你们上次回滚，"回滚到哪"能一指就指出来吗？

**Q8｜一次"合规的固件升级"——四大活动各守哪扇门？**
"冰链补了配置管理，做了一次'合规的固件升级'：老周先写变更申请、做影响评估（'固件行为变化，历史温度记录的采集与判定逻辑随之变化，需知悉在役设备批次分布'）；小林把升级提到变更控制会（老周汇报、小赵评估、阿凯确认云端兼容、小林拍板），固件 v2.4 升为新固件基线；每台设备从哪一版升到哪一版、升级时间、结果进版本台账；三个月后小赵抽查二十台，一台台账写 v2.4、实物还是 v2.3（升级失败未重试），记录修正、补推送。请用四大活动（标识/控制/状态记录/审计）复盘这次升级——哪一步在防'批次追溯查不清'？哪一步在防'实物与记录对不上'？"

追问：① 四大活动各回答什么问题（是什么/怎么变/现在什么样/实物与记录一致吗）？② 冰链旧事故四个洞（固件没立基线/升级没影响评估/只有一句已推送/从没审计），这次升级补了哪几个？③ 配置管理三问——这次升级让'它是怎么变成这样的'答得上来了吗？④ 配置管理守护的是第11章那些不可逆决策——冰链固件升级、恒信编号规则，各对应四组同构（决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟↔变与不变分离 / 影响分析↔变更控制）里的哪一组？⑤ 你们团队四大活动哪一个是"半吊子"？

**Q9｜亲手给"版本"和"基线"各立一条判据（方法时刻）**
"这一章的方法底座时刻是判据主义：不给没有判据的定义——版本和基线都不靠感觉认，靠可检验判据验。请亲手给'版本'立一条判据，再给'基线'立一条判据——按判据主义三问自检：它是什么（版本能精确对应'哪一次完整构建'吗 / 基线被批准+被冻结+作参照吗）？它的失效边界在哪（什么样的编号够不上版本 / 什么样的版本够不上基线）？能不能举出一个反例（文件名不是版本 / 没被批准的版本不是基线）？"

追问：① 你把'配置提供内容、版本提供位置、批准提供资格'的哪半句编进了判据？三者为什么缺一不可才成一个基线？② 一横一竖：你立的版本判据测'顺着流'、基线判据测'竖着切'——各自指向哪个特征？③ 你刚给'基线'立的判据，拿到你们部门最大的配置项上量一下——合格吗？——只有版本号只是见过，有判据才算拥有。

**Q10｜给你们的部门最大的配置项做一次体检**
"结合你们部门现状，用配置三问、版本判据、基线三问、四大活动四个判据，给你们最大的一个配置项做一次'配置管理体检'——给出最该改进的三件事，每个落到一个动作。"

追问：① 四活动（标识/控制/状态记录/审计）先查哪两个？② 你们最近一次'追溯'或'回滚'查不清的地方，缺的是版本、基线、还是状态记录？③ 画出你们开发链三层（需求→设计→实现），每层'基线（冻结端）'和'版本（交付端）'分别是什么？④ 两周后回来报告：哪个判据测出不合格、补了哪个动作。

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 "版本号不是有吗？"为什么还是查不清？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "老周说得对，版本号有了、流程走了，审计员是没事找事。" | 正是要翻的——把"有版本号"当"配置管理做好了" |
| 中 | 能说"版本不是基线"，但三个词各管什么说不清 | 词背了，判据（基线三问）没用起来 |
| 好 | "版本只答'走到第几步'（v2.3），没答'哪一版被批准、被冻结、作参照'——基线三问一问答不出；追溯温度记录要的是形态（哪套采集+判定逻辑），不是参数；老周缺状态记录（只有一句已推送）和配置审计。" | 三词分工 + 基线三问 + 四大活动 + 追溯机制全咬合 |

**产品侧 vs IT侧**：产品组答"追溯温度记录必须知道固件版本——v2.1 采的和 v2.3 采的断链判定不一样"；IT 组答"回滚/审计要能回答'这个部署是哪次构建'"。两边都容易把"版本号"当"基线"——**版本只是刻度，基线才是资格**。

**反转话术**（对应章首 + 1.3/1.4 + 3.2）：老周那句"我们有版本号啊"错在两处——第一，他把"配置"当成了"参数"：采集算法、断链判定、告警逻辑关联在一起塑成的 M3 的行为形态，才是配置；第二，他把"版本"当成了"基线"：v2.3 只回答"走到第几步"，它没回答"哪一版被批准、被冻结、全生命周期拿它作参照"。**基线三问一问答不出——它只是刻度，不是参照。** 追溯一条温度记录要的是形态："这批记录是'哪套采集逻辑 + 判定逻辑'采出来的"，而形态由配置提供、位置由版本提供、资格由批准提供——三者缺一不可才成基线。老周缺的还不止基线：升级记录只有一句"已推送 v2.3"，是状态记录缺位；从没核对实物与记录，是配置审计缺位。**不是版本号有了，配置管理就好了；是四大活动一个都不能少。**

**参考答案要点**：配置/版本/基线三分工见"开篇·本章枢纽" + 1.1/1.3/1.4；四大活动见 §3.2；案例进展①（形态 vs 参数）。

### Q2 配置、版本、基线两族概念什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "配置、版本、基线是一个东西的三种叫法。" | 正是要翻的——三层关系没立起来 |
| 中 | 能说"配置项/配置/配置信息锚定实体"，但版本/修订/变体/基线四词混 | 配置族对了，版本族关系缺（变体×版本正交没接上） |
| 好 | "配置项=对象（管哪些）、配置=属性（它是什么样）、配置信息=记录（拿什么核对），锚定实体解循环；版本=时间（走到第几步）、修订=内部次数、变体=空间（有几种形态）、基线=资格（被盖章）；基线=变体×版本的交叉点被批准冻结；契约链每级都有冻结端和交付端。" | 两族关系全到位，正交 + 交叉点 + 契约链全接上 |

**产品侧 vs IT侧**：产品组答"医疗加强版 v2.4 = 变体×版本，被批准冻结成基线"；IT 组答"合同系统需求版本 v2.doc 是版本、被 Ada 批准立功能基线"。两边都要注意**契约链"基线对谁、版本对谁"是每级重复的通用机制，不是某一级专属**。

**反转话术**（对应 1.1/1.3/2.3/3.5）：三个配置术语为什么绕？因为它们互相引用、首尾相连，形成循环定义——要懂一个得先懂另外两个。解耦的办法，是往环里引入一个不依赖任何配置术语的锚点——**实体**。配置项=被纳入管理的实体（对象）、配置=实体被记录的关联功能+物理特性（属性）、配置信息=记录特性的资料（记录）——三者都锚定"实体"，彼此不再互引。版本族四词更得分开：**版本**回答"走到第几步"（时间先后）、**修订**回答"内部改了几次"（更细粒度）、**变体**回答"有几种形态"（空间并存）——变体和版本**正交**；而**基线 = 变体 × 版本的交叉点被批准冻结**（"医疗加强版 v2.4"这个形态，被批准、被冻结，就是基线）。契约链把这个机制推广到整条开发链：需求对方案、方案对实现，每一对相邻环节都是局部甲乙方——**基线是每一级契约的冻结端、版本是交付端**，每一级都重复出现，只因视角不同看起来"属于"不同的人。

**参考答案要点**：配置三词解耦见 §1.1；版本/修订/变体/基线见 §1.3/1.4/2.3；契约链见 §3.5。

**参考答案要点**：一横一竖见 §2.2 / 本章判据6；基线三特征见 §1.4 / 本章判据5；变体与版本正交见 §2.3；守护架构决策见 §3.4 / 本章判据11。

### Q5 没有基线，变化就不可言说——凭什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "有 git 历史不就能查了吗？为什么要基线。" | 正是要翻的——把记录当参照 |
| 中 | "没基线查不清。" 结论对，机制缺 | "从哪变起"的原点没讲出来 |
| 好 | "描述变化必须有一个'从哪变起'的原点；git 历史是记录（流水账），基线是批准+冻结+作参照——差在'批准'这个动作；没有原点，'变了'就像在海上说'我在动'却没有岸标。" | 原点机制 + git 差在哪 + 岸标类比全到位 |

**产品侧 vs IT侧**：产品组答"追溯温度记录必须从固件基线出发"；IT 组答"回滚必须知道从哪个基线偏离"。两边都要翻"git 历史=基线"——**没有批准动作，历史只是流水账**。

**反转话术**（对应 2.4 + 自查5）：要描述一个变化，你必须有一个"从哪变起"的原点。"从 v1.0 变到 v1.1"这句话之所以有意义，是因为 v1.0 是一个所有人都认的、被冻结的、不会动的原点。没有这个原点，"变了"就没有参照——像在茫茫大海上说"我在动"，却没有岸标。**git 历史是记录，基线是被批准、被冻结、被全项目认可的参照。** 两者差在哪一个动作？——**批准**。git 的 commit 是"发生了什么事"的流水账，它没有回答"哪一版是所有人认的参照"；没有批准动作，历史只是流水账，不是基线。基线建立之后，变化就不能随手改——它必须走变更控制这条正式的路（变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线）。配置管理的全部工作，就是让三个问题任何时刻都有答案：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——老周答不上"它是怎么变成这样的"，正因状态记录缺位、变更历史散乱。

**参考答案要点**：没有基线不可言说见 §2.4 / 本章判据7；变更控制见 §3.1 / 本章判据8；配置管理三问见 §3.3 / 本章判据10；git 历史 vs 基线段落见自查5。

| 弱 | 背书上的判据："版本是刻度，基线是参照。" | 只答了"是什么"，没做"立判据+失效边界+反例"这个动作——方法没上手 |
| 中 | 立了一条判据（如"版本号能对应哪次构建"），但失效边界、反例没给 | 判据立出来了，"是什么/失效边界/反例"三问只答了一问 |
| 好 | "版本判据：编号能精确对应'哪一次完整构建'——失效边界：只有文件名/日期文件夹不够；反例：final_2 不是版本。基线判据：被批准+被冻结+作参照——失效边界：没被批准的版本只是刻度；反例：老周的 v2.3 不是基线。把'版本提供位置、批准提供资格'编进了判据，三者缺一不可才成基线。" | 立判据 + 失效边界 + 反例 + 三分工全到位 |

**产品侧 vs IT侧**：产品组给"基线"立判据时自然写"固件 v2.4 被 CCB 批准、冻结、作参照"；IT 组写"发布包被批准、回滚有地址"。两边立出的判据结构相同——**这正是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"；判据不挑行业**。

**反转话术**（对应方法底座时刻 = 判据主义；规则 15）：这是本单元的**方法时刻**——前面八题在讲"配置/版本/基线是什么"，这一题让你们亲手做一遍方法底座时刻：**判据主义**。老周记住了"版本号"，却把版本当成了基线——他不缺版本号，缺的是判据：**版本和基线都不靠感觉认，靠可检验判据验。** 你亲手给"版本"立判据，最稳的那条正是本章的版本判据一问：**能精确对应到"哪一次完整构建"吗**——能，是版本；不能（只有文件名），还不算版本。再给"基线"立判据：**被批准 + 被冻结 + 作参照**——三问全"是"才是基线。按判据主义三问自检：它是什么（上面两条就是）？它的失效边界在哪（什么样的编号够不上版本 / 什么样的版本够不上基线）？能不能举反例（final_2 不是版本、没被批准的 v2.3 不是基线）？——能举反例，判据才算立住。你立的判据里，"配置提供内容、版本提供位置、批准提供资格"——版本判据里是"位置"，基线判据里是"资格"，三者缺一不可才成一个基线。反身：你刚给"基线"立的判据，拿到你们部门最大的配置项上量一下——合格吗？——**只有版本号只是见过，有判据才算拥有**。

**参考答案要点**：方法底座时刻（判据主义）见 00-案例设定 §三 第12章行；版本判据一问见 §1.3 / 本章判据4；基线三问见 §1.4 / 本章判据5；三分工见"开篇·本章枢纽" / 本章判据13；规则 15 注：判据主义章的方法时刻题=判据运用题、不重复出独立方法操作题。

### Q10 给你们的部门最大的配置项做一次体检

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强版本管理、要上工具。" | 没落到四把判据任何一把，不可检查 |
| 中 | 用一把尺子查出问题（如"我们的版本号对不上完整构建"） | 有判据，但只照了一面 |
| 好 | 按配置三问/版本判据/基线三问/四大活动逐项过，挑出最不合格的一项 + 一个可检查动作（如"下周给主程序立一版被批准冻结的基线"），说出先查哪两项、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**产品侧 vs IT侧**：两组各给自己部门体检——体检表本身是同一份（配置三问/版本判据/基线三问/四大活动），这正是"配置/版本/基线三分工"领域中立的现场证明。

**反转话术**（对应 3.2/3.3 + 作业指南）：这一章的判据不是彼此孤立的——**配置三问验"算不算配置"，版本判据验"有没有版本"，基线三问验"有没有基线"，四大活动验"配置管理做到位没有"。** 四个判据合起来，才是一份完整的配置管理体检。冰链体检报告四个洞（标识没立基线/控制没影响评估/记录只有一句/审计没做过），最该先补的是最不合格的一项——对老周是"状态记录"（追溯时查不清的根源）；你们部门体检，**答不上来的那一项就是最该补的**——找到第一个答不出的项目就能开工。最后一条建议照书抄：先给最大的配置项补一版"被批准、被冻结、作参照"的基线，把"这一版"从刻度升级成参照。

**参考答案要点**：配置管理体检四判据见本章判据1/4/5/9；作业指南见本章分析文档第 6 步；可剪裁原则见 §3.7。

## 四、知识卡片

### 一页图（书"本章概念总图"）

```
配置 = 实体被记录下来的形态（配+置=组合成形）——提供"内容"
  配置项（对象·管哪些）/ 配置（属性·它是什么样）/ 配置信息（记录·拿什么核对）——锚定"实体"
  三个隐形过滤器：类别边界 / 记录边界 / 关联边界 —— 配置三问
版本 = 时间轴上的演进刻度（横，与时间同向）——提供"位置"——回答"走到第几步"
  修订 Rev A/B/C = 更细的内部次数；变体 = 空间并存（与版本正交）
基线 = 被批准冻结的参照（竖，垂直切断时间）——提供"资格"——回答"哪一版被盖章"
  三特征：被批准 / 被冻结 / 作参照
  三种正式基线：功能（要做什么）→ 分配（由谁实现）→ 产品（实际是什么）
版本顺着流、基线垂直切：里程桩顺着路排，收费站横在路中间
没有基线，变化就不可言说：描述变化必须有一个"从哪变起"的原点
变更控制：冻结 → 变更 → 再冻结（CR → 影响评估 → CCB → 实施 → 新基线）
四大活动：配置标识 → 配置控制 → 状态记录 → 配置审计
核心目的三问：应该是什么 / 实际是什么 / 怎么变成这样的——任何时刻都答得出
配置管理 = 架构决策的守护者：决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟↔变与不变分离 / 影响分析↔变更控制
契约链：基线=每一级契约的冻结端，版本=每一级契约的交付端
三条铁律：协作要共同事实 / 长周期要组织记忆 / 担责要可答的账
价值：省钱（返工/报废/精确召回）· 赚钱（变体/资质/速度）· 保钱（责任/知识）
```

### 金句（书"本章判据"提炼）

- **配置提供"内容"，版本提供"位置"，批准提供"资格"——三者齐备，才成一个基线。**
- **配置三问**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——三问全"是"，才是配置。**参数是零件，配置是装好的整机。**
- **版本判据一问**：这一个编号，能精确对应到"哪一次完整构建"吗？能——是版本；不能（比如只有文件名）——它还不算版本。
- **基线三问**：被批准了吗？被冻结了吗（任何人不能随意改）？全生命周期拿它作参照吗？——三问全"是"，才是基线。
- **版本顺着流、基线垂直切**——把版本当基线，等于把里程桩当成收费站。
- **没有基线，变化就不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。
- **版本是回滚的地址，基线是变更的参照**——"冻结"不是"死锁"，基线可以变更，但必须走变更控制。
- **配置管理四大活动一个都不能少**：标识（是什么）→ 控制（怎么变）→ 状态记录（现在什么样）→ 审计（实物与记录一致吗）。
- **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
- 配置管理守护的正是第11章那些不可逆决策——**决策记录是决策的配置信息，基线冻结是不可逆决策的物理动作**。

## 五、课后作业

1. **书练习（与题卡同源）**：用"配置三问"找出你们产品里"客户/用户能改的参数"，逐个检验：它是配置，还是配置信息里的一个条目？（书练习 1）
2. **书练习**：用"配置管理四大活动"诊断你们团队——标识、控制、状态记录、审计，各打一个"有/缺/半吊子"，看缺的补上要做什么。（书练习 7）
3. **回部门落地**：结合现状，用配置三问、版本判据、基线三问、四大活动四个判据，给你们最大的一个配置项做一次"配置管理体检"——给出最该改进的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪个判据测出不合格、补了哪个动作、效果如何。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次配置管理体检：
>
> 1. **挑配置项（先立枢纽）**：选一个"你心里最有底、天天在用"的配置项——产品的主程序 / 固件 / 核心服务 / 数据表定义。最自信的，往往是基线三问最没打勾的。
> 2. **过配置三问（这算不算配置）**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——确认它是配置，不是零散参数。**话术**："你说的'配置'，是那页参数，还是那整套关联成形的形态？"
> 3. **查版本判据（有版本吗）**：当前的版本号能精确对应到"哪一次完整构建"吗（哪个代码提交、哪次构建、包含哪几条变更）？答不出——它连版本都不算，更遑论基线。
> 4. **过基线三问（有基线吗）**：有没有一版被批准（谁批的、有没有记录）？被冻结（改它必须走变更控制）？全生命周期拿它作参照？——三问缺一，只是刻度不是基线。
> 5. **四活动打勾（标识/控制/记录/审计）**：配置标识——它在配置项清单里吗、有基线定义吗？配置控制——最近一次变更走 CR → 影响评估 → CCB 批准 → 实施 → 新基线了吗？状态记录——现在跑的是哪一版、升级历史有台账吗？配置审计——线上/实物 vs 记录对得上吗、抽查过吗？
> 6. **答配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——三问任一答不出，就是最该补的活动。
> 7. **出体检报告**：四活动各下结论（有/缺/半吊子），最该先补的是"答不出三问"对应的那个活动；最后一条建议照书抄——先给最大的配置项补一版"被批准、被冻结、作参照"的基线。
>
> 卡住时：答不上来的那一问就是最该补的；基线三问一问答不出 = 只是版本不是基线；"没有记录"的地方就是配置审计失守可能潜伏的地方。不必四活动全查完，找到第一个答不出的项目就能开工。
