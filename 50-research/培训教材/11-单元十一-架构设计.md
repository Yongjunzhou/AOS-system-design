## 一、单元导读

### 主题

这一章讲的是"最重要的决定怎么被造出来"——**架构设计**。它承接第10章"架构 = 不可还原的决定"，开启第12章"哪些决定最不能反悔"：第10章说架构是对不可逆决策的提前投资，这一章补上"投资"之前的最后一课——**先想清楚投资什么**。

### 开场破题（对应章首误解现场）

念出章首那场会：水忠要给 M3 二代做架构设计，带进会议室三样东西——一张新的四层方块图（在固件层和云端层之间加了一个框"边缘预判模块"）、一页技术选型（传感器 / 芯片 / 算法位置 / 上报协议）、一页老规矩（温度数据归属追溯域、断链检测是刚性边界、固件升级向后兼容）。水忠说"这就是新一代 M3 的架构""选型都定了，可以直接下单打样""架构的规矩，都在这里了"。李旭憋了很久，问出那句搅动全章的话："这个能力加进来之后，M3 还是 M3 吗？"

让各组表态：这三样凑齐了，架构设计是不是就做完了？哪里不对？图、选型、规矩，各自是什么东西？

### 本单元要反转的直觉

- **画了图 + 做了选型 + 定了规矩 = 做完架构设计**（× 三样是产物 / 候选 / 规则，没有一样是"把需求翻译成结构"这个动作）
- **架构设计就是选技术栈**（× 选型是候选，待检验待权衡，是五块里很小一部分素材）
- **我们做过架构设计 = 我们有架构描述**（× 设计是动词，定义是完成时；没定形等于没设计）
- **功能需求决定架构形态**（× 非功能需求（质量属性）才是主要驱动）
- **架构设计的输入 = 全部需求原文**（× 五类输入 + 规定需求：已验证 / 可追溯 / 未分配）
- **基本概念是架构师发明出来的**（× 90% 选 + 10% 逼；概念是幸存下来的，命名是完成仪式）
- **直接设计可用性，把 99.99% 分配给每个模块**（× 属性是涌现出来的，不能分只能译）
- **原则越多越严谨**（× 少而精 5~15 条；可判定 / 有理由 / 可入评审）
- **关系越多系统越强**（× 关系是成本；关系稀疏、依赖无环、往弱推才可演进）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 架构设计是什么（概念本身 · 章首破题）→ Q2 五块关系（概念关系）→ Q3 定义 vs 设计（真悖论）→ Q4 概念幸存 vs 属性涌现（真悖论）→ Q5 原则自加 vs 约束被迫（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 输入与驱动（判据运用）→ Q7 关注点识别（判据运用 · 恒信镜照）→ Q8 关系强 vs 弱（真悖论）→ **Q9 方法时刻·五块设计**（规则 15：亲手把"画图 / 选型 / 定规矩"升维成五块设计，含跨域变体）→ Q10 回部门五块体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章是**强镜照章**：产品组的"五块"是 M3 温控箱的（概念 = 断链即报废还能撑到接入冷库、全程可追溯；属性 = 预判及时性 + 可用性 + 可追溯性；关系 = 传感器 → 固件 → 云端 → 追溯平台），IT 组的"五块"是合同平台的（概念 = 合同数据所有权归合同域；准则 = 审批链留痕；关系 = 审批引擎通过契约访问合同数据）——**同一个五块、两个世界、判据不变**，这正是本章"概念不挑行业"的现场证明。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜架构设计到底是什么？**
"水忠带三样东西进会议室——一张新的四层方块图、一页技术选型、一页老规矩，以为架构设计做完了。这三样东西各是什么（产物 / 候选 / 规则）？架构设计本身是什么？为什么三样加在一起，仍然不算架构设计？"

追问：① 三问判据（决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？）——水忠三样东西各自答得出哪一问？② "设计是动词，定义是完成时"——水忠拿不出什么？③ 架构设计与详细设计怎么分工（横向切 vs 纵向挖）？为什么先横后纵？④ 你们最近一次"做架构设计"，带的是哪几样？过得了三问吗？

**Q2｜五块什么关系？**
"画出 基本概念、基本属性、设计准则、演进准则、元素关系 的关系图，标出：哪一块直接面对需求？为什么说只有基本概念直面世界，其余四块都是'翻译的翻译'？"

追问：① 内部输入链怎么串（外部原始输入 → 概念 → 属性 → 准则 → 演进；概念 + 属性 → 关系）？② 概念错了为什么后面全错、而且越错越远（失信放大器）？③ "外部原始输入"具体是什么（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产）？为什么概念吃的必须是规定需求？五块里哪一块是"识别出来的不是设计出来的"（关注点）？哪一块说"关系是成本"要克制？④ 你们系统的五块是并列的五份文档，还是按输入链串起来的？

**Q3｜"做过架构设计"和"有架构描述"是一回事吗？**
""我们做过架构设计"和"我们有架构描述"，是同一件事吗？为什么标准里只有'架构定义过程'和'设计定义过程'，没有'架构设计过程'？"

追问：① 定义 = 划界 + 陈述（de-finis，求真），设计 = 怎么做（how，求优）——为什么过程以产出物命名？② 构思为什么无法评审、验证、基线化？③ 你们团队的架构设计，有可以评审的定形产物吗，还是停在某个人的脑子里？

**Q4｜概念是"幸存"的、属性是"涌现"的，那架构师设计的是什么？**
"这一章说：基本概念不是设计出来的，是幸存下来的；基本属性不是设计出来的，是涌现出来的。那架构师设计的到底是什么？五块里到底有没有'设计'？"

追问：① 概念四副面孔（组织范式 / 核心抽象 / 根本机制 / 根隐喻）+ 五条生成路径（选 / 提 / 逼 / 借 / 推）；"候选→检验→幸存"——检验靠什么（原型 spike / ATAM / 架构评审）？② 命名 = 概念化的完成仪式——"边缘预警输入"这个名字意味着什么？③ 属性四步流水线（QAS 场景化 → 战术 → 结构落位 → 验证度量）——为什么不能直接画个"及时性"模块？"99.99% 可用"怎么逼出"冗余 + 故障域"（路径③ = 非功能需求才是主要驱动）？④ 你最近一次"加概念"，是选出来的、逼出来的，还是拍板发明的？

**Q5｜架构师为什么要自己给自己上规矩？规矩越多越好，还是越少越好？**
""约束是外部强加的，原则是自愿的自我限制"——那架构师为什么要自己给自己上规矩？自加束缚怎么反而是解放（第10章'约束即解放'）？规矩越多越严谨，还是越少越好？"

追问：① 约束 / 决策 / 原则三词辨析（被迫接受 / 架构师选择 / 自愿自加）？② 原则四判据（可判定 / 有理由 / 少而精 5~15 条 / 可入评审）——"追求优雅"为什么不是原则？③ 演进准则 = 设计准则 × 时间轴——"主语全是变"怎么判别？④ 你们团队的"老规矩"过得了四关吗？有理由吗？能入评审吗？

### 第二组 · 落地与实践

**Q6｜什么才决定预判逻辑放硬件还是云端？**
"水忠面对'要能提前告警'——功能上就是'算风险、发告警'六个字。为什么这六个字决定不了预判逻辑放硬件还是云端？什么才真正决定？架构设计的输入到底是什么？"

追问：① 输入五类（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产）各是什么？为什么非功能需求排第一位（"做到什么程度"才决定结构形态）？② 为什么输入必须是规定需求（已验证 / 可追溯 / 未分配）？③ 在流沙上画图 = 自损一目——需求一变结构跟着动，代价是指数级的。④ 你们上次架构设计吃的输入，是"文正嘴里那句话"还是规定需求？

**Q7｜万辉的矩阵里为什么有四格是空的？**
""架构设计的第一步不是画，是听——听那些'在乎'的人，到底在乎什么。"恒信万辉第一次做出 stakeholder × concern 矩阵，发现四格是空的。那四个空格告诉他什么？"

追问：① 关注点识别五步（相关方 → 提取 → 划界 → 编排 → 验证）？② 好 concern 五判据（有主 / 有界 / 可权衡 / 可追溯 / 完备 = 矩阵无空行空列）？③ 漏掉一个 stakeholder = 漏掉一整类 concern——万辉漏了谁（监管 / 运维 / 合同相对方 / 未来的维护者）？④ 你们最近一次架构评审，从"谁在乎什么"出发了吗，还是从"我要画什么"出发？

**Q8｜强关系还是弱关系？"关系是成本"在说什么？**
"强关系（同步调用 / 共享状态）直接、直观、容易理解；弱关系（异步 / 事件 / 契约）解耦、可替换、但要绕。哪个更好？'关系是成本'到底在说什么？"

追问：① 关系五类型（结构 / 行为 / 接口 / 部署 / 时序）+ 强度光谱（强 / 中 / 弱）——为什么强关系变更牵动整片？② 关系设计六步（识别 / 分类 / 定方向 / 降耦合 / 契约化 / 检查）——头号决策为什么是依赖方向（DAG 无环）？③ 五判据（有方向 / 够稀疏 / 尽量弱 / 要显式 / 不穿越）——迪米特法则"talk to your friends, not strangers"？④ 画你们系统关键模块依赖图，有环吗？几条不必要？能往弱推吗？

**Q9｜亲手做一遍五块设计：把"见过"升维成"拥有"（方法时刻）**
"水忠第二次带进会议室的不是图、选型和老规矩，而是五样能'定形'的东西。把你们系统正在设计 / 维护的一个系统（或一次要加的架构能力），亲手做一遍五块设计：基本概念（它还是不是它？）、基本属性（要涌现什么、怎么场景化？）、设计准则（自加什么规矩？）、演进准则（变而不破坏对的规矩？）、元素关系（怎么连、往弱推？）——哪一块卡住了？"

追问（跨域变体）：① 冰链 M3 的五块（边缘预警 = 追溯机制的新输入，候选 B 幸存、命名"边缘预警输入"）↔ 恒信合同平台的五块（合同数据所有权归合同域、审批引擎通过契约访问）——同一个五块，换一个世界判据变没变？"这个概念换个世界还成立吗？"② 冰链的"候选 B 幸存"和恒信的"关系降耦合"，是不是同一套判据在起作用（概念跨域 = 概念是刀、系统是大象）？③ 把"画图 / 选型 / 定规矩 = 见过"和"五块设计定形 = 拥有"对到你们自己的变更上——你们到哪一步了？哪一块还停在"见过"？

**Q10｜给你们的系统做一次五块设计体检**
"结合你们部门现状，挑一个正在设计或维护的系统，用五块设计做一次体检：五块各答得出吗？答不出的那一块是不是就是设计缺口？给出最该做的三件事，每个落到一个可检查动作。"

追问：先答哪一块？为什么（只有概念直面世界，先钉基本概念）？这次体检动的是横切（架构）还是纵挖（详细）？两周后回来报告什么？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 架构设计到底是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "凑齐了就是做完了，图选型规矩都有了呀。" | 正是要翻的——把产物 / 候选 / 规则当翻译动作 |
| 中 | "图是描述、选型是选择、规矩是规则，但它们还不是架构设计本身。" | 层次分对了，但"翻译"这个动作和三问判据没给出来 |
| 好 | "三样是表达 / 候选 / 规则；架构设计是把需求翻译成系统结构的动作——决定切分 / 连接 / 规矩；三问都答'是'才是；没定形等于没设计。" | 三问判据 + 设计动词定义完成时全到位，能当场给水忠开方子 |

**产品侧 vs IT侧**：产品组答"方块图是 M3 的描述、传感器选型是候选、老规矩是设计准则"；IT 组答"四张图是描述、技术栈是候选、接口规范是准则"。两边都容易把"画图"当"设计"——图的地位在两边一样：是产物，不是动作。

**反转话术**（对应 1.1 / 1.3 / 1.5）：水忠那天带的三样东西，没有一样回答"架构设计到底在干什么"。图是**架构描述**（第10章讲过，是产物）；选型是**候选**（待检验、待权衡的素材，选型表没回答"为什么选它、不选它的代价是什么"）；老规矩是**设计准则**（五块设计里的一块，只是一块）。而架构设计是另一个更靠前的动作：**把需求翻译成系统结构**。三问判据当场量：它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计。水忠画了图，但没做切分的权衡；列了选型，但没定义部分之间的连接；写了老规矩，但那是从既有系统里"读出来"的，不是"设计出来"的。**设计是动词，定义是完成时——没定形的构思，等于没设计。**

**参考答案要点**：翻译与系统结构见 §10.2.1；设计是转化见 §10.2.2；定义 vs 设计见 §10.2.3；三问判据见"概念卡片·架构设计"；横切 vs 纵挖见 §10.2.5。

### Q2 五块什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "五块是五份并列的设计文档。" | 正是要翻的——把输入链当并列清单 |
| 中 | 能画出五块清单，但说不清哪块直面世界 | 清单对，链方向缺 |
| 好 | "只有基本概念直接面对外部原始输入，其余四块吃内部级联；概念→属性（限幅）→准则（细则）→演进（时间维化）；概念 + 属性→关系（具身化）；概念错了后面全错且越错越远。" | 输入链 + 失信放大器 + 反向校验全到位 |

**产品侧 vs IT侧**：产品组举"M3 的概念（断链即报废还能撑到接入冷库）限幅了属性的验收线"；IT 组举"合同数据所有权归合同域的概念限幅了准则（谁都不许绕开）"。两边都容易把五块当成五张表——**五块是链，不是表**。

**反转话术**（对应 3.1 / 3.2）：五块不是并列的——**只有"基本概念"直接面对外部原始输入**（功能 / 非功能 / 约束 / 环境 / 关注点 / 资产），越往后的块，输入里"内部成分"占比越高。基本属性吃概念（限幅）、设计准则吃概念 + 属性（执行细则）、演进准则吃设计准则（时间维化）、元素关系吃概念 + 属性（具身化）。这条链带来两个推论：**只有概念是"翻译"，其余是"翻译的翻译"**——概念错了，后面四块全部跟着错，而且错得越来越远；**内部链是"失信放大器"**——评审时发现原则跟概念对不上，基本可以断定链断过。**反向校验就是免费的架构体检**：这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念 / 教训提炼？答不出的，就是"无源之水"。

**参考答案要点**：五块清单见 §10.2.4；内部输入链见 §10.4.1；三推论见 §10.4.2；概念卡四问（架构设计 / 基本概念 / 基本属性）。

### Q3 "做过架构设计"和"有架构描述"是一回事吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "一回事，做过就会有描述。" | 正是要翻的——把动词当完成时 |
| 中 | "不完全是，做过可能是心里的构思。" | 方向对，标准命名玄机没接上 |
| 好 | "定义 = 划界 + 陈述（de-finis·求真）；设计 = 怎么做（how·求优）；15288 只有架构定义过程 / 设计定义过程，没有架构设计过程——过程以产出物命名，构思无法评审，描述才能评审、验证、基线化；设计得再好，没定形等于没设计。" | 元概念 + 命名玄机 + 判据全到位 |

**产品侧 vs IT侧**：产品组举"我们做过架构设计（在几个人的脑子里）"；IT 组举"我们有架构文档（能进配置管理）"。两边都要翻——**"做过"是动词，可能只发生在某几个人的脑子里；"有描述"是完成时，是可以被别人检查、可以进入配置管理（第13章）的资产**。

**反转话术**（对应 1.3）："定义"和"设计"是架构领域天天混用的两个词——definition ← 拉丁 de-finis（彻底地 + 界限）= **划界 + 陈述**，语言性质是陈述性的，判据是求真（准确 / 无歧义 / 可验证）；design 回答"怎么做、怎么造"（how），语言性质是规范性的，判据是求优（满足需求 / 权衡取舍 / 可实现）。**关键洞察：设计本质上也是"定义"的一种**——只是定义的对象从"问题 / 术语"换成了"解决方案"。所以 15288 里只有"架构定义过程""设计定义过程"，没有"架构设计过程"——**过程以产出物命名，而产物必须被定义**。构思无法评审，描述才能评审、验证、基线化。一句话：**设计是动词（构思），定义是它的完成时（定形）**。水忠那天在会议室里做的是"构思"——但他拿不出"定形"的东西。

**参考答案要点**：定义 vs 设计见 §10.2.3；ISO 9000:2015 §3.4.8 见 §10.2.2；15288 两过程见 §10.2.2~10.2.3；与第13章配置管理接续见章末。

### Q4 概念是"幸存"的、属性是"涌现"的，那架构师设计的是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "既然都不是设计出来的，那架构设计可能是个伪命题。" | 把反直觉读成了"没有设计"——正是要翻的 |
| 中 | "概念是选的、属性是长的，架构师是搭结构。" | 结论对，幸存者逻辑和四步流水线没给全 |
| 好 | "设计 = 把候选摆上桌 + 定检验（候选→检验→幸存，命名 = 完成仪式）；属性 = 设计结构让涌现（QAS → 战术 → 落位 → 验证）；'99.99% 可用'逼出'冗余 + 故障域'。" | 幸存者逻辑 + 涌现机制 + 质量属性反推全到位 |

**产品侧 vs IT侧**：产品组举"M3 的候选 A（边缘预判 = 新根本机制）vs 候选 B（追溯机制的新输入），检验靠质量属性反推——客户要的是可追溯，候选 B 幸存"。李旭那句"M3 还是 M3 吗"，问的正是这份选择；IT 组举"合同平台的概念是'合同数据所有权归合同域'，这是从组织范式选出来的"。两边都容易把"检验"当"拍板"——**检验不过，候选就死，哪怕它画进了图里**。

**反转话术**（对应 2.6 / 2.7 / 2.4）：这一章最深的两条反直觉——**基本概念是幸存下来的**：90% 情况下架构师做的不是发明概念，而是从已验证的概念库中选择（模式选择 / 领域抽象 / 质量属性反推 / 类比迁移 / 第一原理五条路径）；剩下的 10% 是需求和质量属性逼着生成的。生成出来的只是"候选"，要经过假设-检验循环（原型 spike / ATAM / 架构评审）活下来，才配叫"基本概念"。**命名就是概念化的完成仪式**——一旦结构被命名，它就从想法变成了可共享、可讨论、可传承的概念。**基本属性是涌现出来的**：你设计的是结构，属性是结构运转之后的宏观效果——不能直接设计"强度"，只能设计微观晶格让强度涌现；不能直接设计"可用性"，只能设计冗余机制让可用性涌现。属性的设计，本质是**结构的设计 + 涌现的验证**（QAS 场景化 → 战术 → 结构落位 → 验证度量）。所以架构师设计的是什么？——**设计的是结构、是把候选摆上桌、是定检验**。概念和属性不是"画"出来的。

**参考答案要点**：概念四副面孔 / 五条生成路径 / 幸存者逻辑见 §10.3.6；属性四步流水线 / 生命线属性见 §10.3.7；涌现属性只能译见 §10.3.4；材料科学类比见 §10.3.7；案例进展③（候选 B 幸存）见"案例进展③"。

### Q5 架构师为什么要自己给自己上规矩？规矩越多越好，还是越少越好？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "被限制就是不自由，规矩越少越好。" | 正是要翻的——把自加原则当外部约束 |
| 中 | "原则是自加的，有帮助，但说不清尺度。" | 自加对了，四判据和"少而精"没接上 |
| 好 | "约束被迫、决策自选、原则自加；原则 = 决策的决策（让你不用重新想）；四判据（可判定 / 有理由 / 少而精 5~15 条 / 可入评审）；用原则代替思考 = 教条。" | 三词辨析 + meta-decision + 四判据全到位 |

**产品侧 vs IT侧**：产品组举"温度数据归属追溯域"（有理由、可判定）；IT 组举"审批链每一步必须留痕"。两边都要翻"规矩越多越好"——**原则太多等于没有原则**；同时"老规矩"不是天然合格——要过四关升格（可判定 / 有理由 / 少而精 / 可入评审）。

**反转话术**（对应 2.8 / 2.9）：先把三个天天被混用的词分开——**约束**是外部强加的（不可谈判，接受）；**决策**是架构师的选择（具体结构选择）；**原则**是架构师自愿的自我限制（"状态必须外置""禁止循环依赖"）。关键区别：**约束是被迫的，原则是自愿的自我限制**。为什么自愿给自己上规矩？因为原则是"**决策的决策**"（meta-decision）——不是替你做决策，是**让你不用重新想**。第10章"约束即解放"——少而精的纪律反而让团队把脑力留给真正要权衡的事。但要守住分寸：**用原则代替思考**是原则永远面对的诱惑——原则负责"不需要重新想的事"，权衡负责"必须重新想的事"；如果一条原则让团队不再权衡，它就已经从纪律退化成教条了。四条有效性判据：可判定（"追求优雅"不可判定，不配当原则）/ 有理由（答不出"为什么"，删掉）/ 少而精（5~15 条）/ 可入评审（能变成架构评审的检查项）。还有演进准则——**设计准则 × 时间轴**，主语全是"变"的是演进准则：没有它，架构在无人管束时必然退化（漂移 / 侵蚀 / 技术债）。

**参考答案要点**：约束 / 决策 / 原则见 §10.3.8；原则四判据见 §10.3.8；演进准则见 §10.3.9；老规矩过四关见 §10.3.8 与案例进展④。

### Q6 什么才决定预判逻辑放硬件还是云端？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "功能需求决定——'要能提前告警'就是要放个预判模块。" | 正是要翻的——把功能当架构驱动 |
| 中 | "质量属性影响架构，具体说不清怎么影响。" | 结论对，"做到什么程度"和规定需求没接上 |
| 好 | "非功能需求才是主要驱动——'提前 30 秒还是 5 分钟''误报率压到多少'决定放硬件还是云端；输入 = 五类 + 规定需求（已验证 / 可追溯 / 未分配）；在流沙上画图 = 自损一目。" | 非功能主导 + 规定需求 + 输入五类全到位 |

**产品侧 vs IT侧**：产品组答"提前量 ≥ 5 分钟、误报率 ≤ 5% 决定边缘计算 + 双路冗余"，逸人补了一句："双路就是多一路采样、多一颗传感器，物料、批次、组装全要重排——这条成本约束得算进权衡"；IT 组答"响应时间、可用性决定缓存 / 冗余 / 分片"。两边都要翻"拿需求一句话直接去设计"——**那句话既没定义"提前多久"（属性缺失），也没定义"判错了怎么办"（约束缺失）**。

**反转话术**（对应 2.2 / 2.3 / 2.4）："要能提前告警"功能上就是六个字——算风险、发告警。但这六个字决定不了预判逻辑放硬件还是云端。**功能需求告诉你"做什么"，质量属性告诉你"做到什么程度"，而"做到什么程度"才真正决定结构形态**（Bass 等《Software Architecture in Practice》）：要 99.99% 可用 → 冗余与故障域；要支持 10 倍扩容 → 无状态与分片；要快速上市 → 最少部件数。**功能相同的系统，质量属性不同，架构可以完全不同。** 水忠那句"提前告警"，真正要追问的是：提前 30 秒还是 5 分钟？误报率压到多少？算错了的后果谁来兜？——这些质量属性才决定预判逻辑放硬件还是云端。董勐追问："那预判到底放固件还是放我云端？"水忠摇头："不是我定，是「做到什么程度」定——要快放固件，置信度模型要可更新就放你云端。"而且输入必须是**规定需求**：架构设计是整条设计链里最不可逆的一环，在流沙上画结构图等于开局自损一目——需求一变结构就得跟着动，代价是指数级的。还有：需求分配是架构设计自己的工作，不是输入；质量属性是涌现属性，不能分，只能译。

**参考答案要点**：非功能需求主导见 §10.3.2；规定需求见 §10.3.3；需求层级见 §10.3.3；涌现属性只能译见 §10.3.4。

### Q7 万辉的矩阵里为什么有四格是空的？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "表格没填满，下次补上就行。" | 正是要翻的——把矩阵当文书活 |
| 中 | "有相关方没有被任何视图回答——架构有盲区。" | 空格意义说对了，五步识别和五判据没给 |
| 好 | "空格 = 有相关方、却没有任何视图打算回答他们在乎什么——漏掉一个 stakeholder 就是漏掉一整类 concern；关注点识别五步；好 concern 五判据。" | 空格判读 + 五步 + 五判据全到位 |

**产品侧 vs IT侧**：产品组举"司机在乎别误报、冷链客户在乎留出补救时间、维修在乎别误动作、监管在乎留痕——这些天然冲突，架构设计就是在冲突的关注点之间做权衡"；IT 组举"万辉漏了监管 / 运维 / 合同相对方 / 未来的维护者"。两边都容易把关注点当"设计"——**关注点是识别出来的，不是设计出来的**。

**反转话术**（对应 2.5）：那四格空格告诉他：**有相关方，却没有任何视图打算回答他们在乎什么**——这就是架构设计的起点。老习惯是"我要画什么"出发；万辉这次从"谁在乎什么"出发。**关注点是识别出来的，不是设计出来的**——42010 从头到尾用的动词是 identify，不是 design。concern 是 stakeholder 的**利益**（interest），已存在于其头脑、组织和契约里；架构师的工作是发现、提取、陈述，而不是发明。一个"设计"出来的、没有 stakeholder 真正关心的 concern，不是架构洞察，是自嗨。识别五步：识别利益相关方 → 提取关注点 → 划界与陈述 → 组织编排（矩阵，标记冲突组 = 权衡点 = 架构决策的主战场）→ 验证完备性。好 concern 五判据：有主 / 有界 / 可权衡 / 可追溯 / 完备（矩阵无空行空列）。**漏掉一个 stakeholder，就是漏掉一整类 concern。**

**参考答案要点**：关注点识别见 §10.3.5；concern 定义三要素见 §10.3.5；案例进展②（恒信矩阵四空格）见"案例进展②"。

### Q8 强关系还是弱关系？"关系是成本"在说什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "关系越多系统越强，大家互联互通。" | 正是要翻的——把关系数量当系统强度 |
| 中 | "弱关系更好，解耦。" | 结论对，但"满足需求前提下克制"的分寸没到 |
| 好 | "关系是成本（n²），每一条都是未来变更时的一处牵动；克制、往弱推、契约化；依赖无环（DAG）——方向即权力；五判据。" | 成本机制 + 降耦合 + 五判据全到位 |

**产品侧 vs IT侧**：产品组举"传感器 → 固件（预判引擎）→ 云端（置信度模型）→ 追溯平台，依赖方向单向、接口契约化"；IT 组举"审批引擎直接调合同主表 → 通过合同服务（契约）访问，关系从强降到契约弱"。两边都要翻"强关系直观 = 好关系"——**同一对要素之间，关系强度是设计的自由变量**。

**反转话术**（对应 2.10）："关系是成本"这一章最反直觉的第一原则——n 个要素如果全互联，是 n² 条关系；**每一条关系，都是未来变更时的一处牵动**。所以关系设计的第一原则是"克制"：能没有的关系就不要有。好的架构往往是**关系稀疏**的架构——关系少，独立性才强，可演进性才高。关系设计六步：识别必要关系 → 分类定性（结构 / 行为 / 接口 / 部署 / 时序）→ 定方向（**依赖方向是关系设计的头号决策**，健康的依赖图必须无环 DAG）→ 降耦合（核心动作：同步调用 → 异步消息；直接调用 → 事件发布订阅；共享状态 → 消息传递，每降一级变更的牵动范围就小一圈）→ 契约化（关系必须白纸黑字，否则就是隐式耦合）→ 检查。五判据：有方向 / 够稀疏 / 尽量弱 / 要显式（依赖抽象不依赖实现）/ 不穿越（迪米特法则——talk to your friends, not strangers）。注意分寸：**不是关系越少越好**，是在满足需求的前提下把每条关系往弱的方向推。

**参考答案要点**：关系是成本见 §10.3.10；关系五类型 / 强度光谱见 §10.3.10；六步动作与五判据见 §10.3.10；案例进展④（审批引擎 → 契约）见"案例进展④"。

### Q9 亲手做一遍五块设计（方法时刻 · 规则 15）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 报出五块清单，但只答得出"是什么"，落不到自己的系统 | 背了清单，没把五块当尺子量自己的东西 |
| 中 | 能答出三块左右，卡在基本属性（场景化）或演进准则（时间维化） | 缺口暴露，但没落到"为什么这块最薄" |
| 好 | "五块逐个落到自己系统：基本概念（它还是不是它）→ 基本属性（QAS 场景化）→ 设计准则（过四关）→ 演进准则（变字句式）→ 关系（往弱推）；对照冰链 / 恒信的五块——同一个五块、两个世界、判据不变。" | 方法做到位 + 跨域对照，把"概念不挑行业"当场做出来 |

**产品侧 vs IT侧**：产品组量 M3 二代（概念 = 候选 B 幸存、属性 = 预判及时性 + 可用性 + 可追溯性、准则 = 数据所有权 / 断链刚性、演进 = 新增传感器不得破坏追溯链、关系 = 传感器 → 固件 → 云端 → 追溯平台单向契约）；IT 组量合同平台（概念 = 合同数据所有权归合同域、准则 = 审批链留痕 / 接口变更走版本化、演进 = 编号事故时间维化、关系 = 审批引擎通过契约访问）。两边各做各的五块，摆在一起就是跨域对照表。**这是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"。**

**反转话术**（对应方法底座时刻 = 从见过到拥有）：这是本单元的**方法时刻**——前面八题在讲架构设计，这一题让你们亲手做一遍方法底座时刻：**画图、选型、定规矩，只是见过；五块设计定形，才是拥有**。水忠第一次带图、选型、规矩进会议室——那是"见过"；第二次带五样能"定形"的东西（概念、属性、准则、演进、关系）——那是"拥有"。你们要做的，就是把画图 / 选型 / 定规矩升维成五块设计。跨域变体（强镜照章必启用）：冰链 M3 的五块和恒信合同平台的五块，**同一个五块、换一个世界，判据变没变**？冰链的"候选 B 幸存"和恒信的"关系降耦合"，是不是同一套判据在起作用？——这是本章"概念不挑行业"的现场证明。（讲师对照 00-案例设定 §四 架构设计行：主案例冰链深度演示、镜照恒信升级合同平台。）

**参考答案要点**：五块设计见 §10.2.4 / §10.4.1；案例进展③（候选 B 幸存）与案例进展④（准则与关系）见"案例进展"；案例进展⑤（五块收口）见"案例进展⑤"；章末"见过→拥有"见"章末·认知反转"。

### Q10 给你们的系统做一次五块设计体检

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强架构管理、要画好架构图。" | 没落到五块任何一块，不可检查 |
| 中 | 用一块查出缺口（如"说不出基本概念"） | 有判据，但只照了一面 |
| 好 | 按五块逐项答，挑出最薄的一块 + 一个可检查动作（如"下周评审会前，把这条老规矩过四关"），说出先答哪块（基本概念）、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**产品侧 vs IT侧**：两组各给自己系统体检——体检表本身是同一份（五块 + 反向校验），这正是"架构设计不挑行业"的现场证明。

**反转话术**（对应本章综合应用）：这一章的判据不是彼此孤立的——三问判据测"是不是架构设计"，四判据测"老规矩是不是原则"，五判据测"关系是不是成本"、QAS 测"属性能不能验收"，反向校验测"输入链断没断"。**答不出的那一块，就是你的设计缺口**（书练习 1）——不用等五块答全，找到第一个答不出的就能开工。先答基本概念——**只有概念直面世界，概念错了后面全错**。

**参考答案要点**：五块体检方法见作业指南（本章分析文档第 6 步）；判据见"本章判据"（11 条）；练习 1~11 见书"练习"。

## 四、知识卡片

### 一页图（书"本章概念总图"）

```
架构设计 = 一个动作（把需求翻译成系统结构）+ 一份清单（五块设计）+ 一条链（只有概念直面世界）

第一幕 · 是什么：翻译五块
  翻译必然做选择：同一需求 → 不同结构
  设计是动词，定义是完成时——过程以产出物命名（15288 只有"架构定义过程"）
  五块清单（42010 定义拆开）：基本概念 / 基本属性 / 设计准则 / 演进准则 / 元素关系
  与详细设计：横向切 vs 纵向挖——先横后纵

第二幕 · 不是什么：幸存涌现自加克制磨边弧
  三样东西不是架构设计：图 = 架构描述（产物）/ 选型 = 候选 / 老规矩 = 设计准则（五块之一）
  输入不是全部需求原文：五类输入 · 规定需求 · 架构吃系统级
  质量属性不是"分"下去的：涌现属性只能"译"成部件约束
  关注点不是设计出来的：是识别出来的（五步识别 · 好 concern 五判据）
  基本概念不是设计出来的：是幸存下来的（四副面孔 · 五条生成路径 · 候选→检验→命名）
  基本属性不是设计出来的：是涌现出来的（QAS → 战术 → 落位 → 验证；生命线属性）
  设计准则不是抄来的：原则是自加的（约束被迫 / 决策自选 / 原则自加；必须·禁止·应当 + 理由）
  演进准则不是静态的：设计准则 × 时间轴（防漂移 / 侵蚀 / 技术债）
  元素关系不是越多越好：关系是成本（克制 · 往弱推 · 契约化）

第三幕 · 往哪去：五块落地
  只有基本概念直面世界，其余四块吃内部级联
  推论：只有概念是"翻译"，其余是"翻译的翻译"；链是失信放大器；反向校验免费体检
  见过→拥有：画图 / 选型 / 定规矩 = 见过；五块设计定形 = 拥有
```

### 金句（书"本章判据"提炼）

- **架构设计 = 翻译**——把需求翻译成系统结构（切分、连接、规矩）；画图、选型、定规矩都只是这个翻译的产物 / 素材 / 规则，不是翻译本身。
- **设计是动词，定义是完成时**——没定形，就等于没设计。构思无法评审，描述才能评审、验证、基线化。
- **横切先于纵挖**——架构设计横向切（切成几块、怎么对接），详细设计纵向挖（每块内部挖多深）。
- **非功能需求才是主要驱动**——功能需求告诉"做什么"，质量属性告诉"做到什么程度"，而"做到什么程度"才真正决定结构形态。
- **质量属性不能分，只能译**——涌现属性是整个系统的属性，只能被架构机制满足、再翻译成部件级约束。
- **概念幸存、属性涌现**——基本概念 90% 选 + 10% 逼，候选→检验→幸存，命名是概念化的完成仪式；基本属性只能设计结构让涌现，且必须度量验证。
- **原则是自愿的自我限制**——约束被迫、决策自选、原则自加；演进准则 = 设计准则 × 时间轴。
- **关系是成本**——关系稀疏才可演进；依赖无环、往弱推、契约化。
- **只有概念直面世界**——其余四块都是"翻译的翻译"；概念错了，后面全错，而且错得越来越远。

## 五、课后作业

1. **书练习（与题卡同源）**：挑一个你正在设计或维护的系统，回答五块设计：它的基本概念（组织范式 / 核心抽象 / 根本机制 / 根隐喻）、基本属性（生命线属性）、设计准则、演进准则、元素关系各是什么？——答不出任何一块，那一块就是你的设计缺口。（书练习 1）
2. **书练习**："把需求翻译成系统结构"——挑一个最近的真实需求（比如"要能提前告警"），试两种翻译（A 边缘计算 / B 云端计算），各列一条好处、一条代价。为什么架构设计必然做选择？（书练习 2）
3. **回部门落地**：结合现状，挑一个正在设计或维护的系统，用五块设计做一次体检——五块各答得出吗？答不出的那一块是不是就是设计缺口？给出最该做的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪一块补上了、哪一块还卡着、卡在哪个判据上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次五块设计体检：
>
> 1. **挑系统 / 挑变更（先立尺子）**：挑一个你正在设计或维护的系统，或最近一次架构变更。
> 2. **分三样东西的层次（先看病）**：列出这次架构工作的"图 / 选型 / 规矩"各是什么——它们只是表达 / 候选 / 规则，不是架构设计本身。
> 3. **逐块答五块（五块设计）**：基本概念（它"怎么想"——"去掉就不是它"的是什么？）→ 基本属性（要涌现什么本质特征，目标属性场景化了吗 QAS？）→ 设计准则（自加哪些规矩，用"必须 / 禁止 / 应当 + 理由"句式，过四关）→ 演进准则（每条设计准则做时间维化，用"变"字句式）→ 元素关系（关键模块依赖图，有环吗？几条不必要？能往弱推吗？）。
> 4. **反向校验（免费体检）**：随机挑一条设计准则向上追——它从哪个概念 / 属性提炼来的？答不出 = 无源之水（输入链断过）。
> 5. **产出三件最该做的事**：每条 = 一个可检查动作 + 一条判据（三问 / 四步 / 四关 / 五判据）。
>
> 卡住时：答不出的那一块就是设计缺口，不必五块答全；先钉基本概念——只有概念直面世界，概念错了后面全错。
