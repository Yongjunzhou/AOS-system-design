## 一、单元导读

### 主题

这一章讲的是"最重要的决定怎么被造出来"——**架构设计**。它承接第10章"架构 = 不可还原的决定"，开启第12章"哪些决定最不能反悔"。这一章的骨架是：**一个动作**（把需求翻译成系统结构——设计是动词，定义是完成时，没定形等于没设计）+ **一份清单**（五块设计：基本概念/基本属性/设计准则/演进准则/元素关系）+ **一条链**（只有基本概念直接面对需求，其余四块都是"翻译的翻译"）+ **一条动词链**（构思打开可能性、定义终结漂浮、设计转换到底——工程化成架构生成六步）+ **一个裁决者**（目的判据——fundamental = 对目的必要且充分，以《系统目的或任务理解确认单》锚定进场、以《系统基本概念和基本属性清单》落纸裁决）+ **链尾创新评分席**（新×成，缺一归零）。

### 开场破题（对应章首误解现场）

念出章首那场会：水忠要给 M3 二代做架构设计，带进会议室三样东西——一张新的四层方块图（在固件层和云端层之间加了一个框"边缘预判模块"）、一页技术选型（传感器/芯片/算法位置/上报协议）、一页老规矩（温度数据归属追溯域、断链检测是刚性边界、固件升级向后兼容）。水忠说"这就是新一代 M3 的架构""选型都定了，可以直接下单打样""架构的规矩，都在这里了"。文正连问三个问题：预判逻辑跑在硬件上还是云端？"提前告警"要提前多久（30 秒、5 分钟还是 1 小时）？这个能力加进来之后，M3 还是 M3 吗？——水忠一个都答不上。散会时，产品开发经理永兵问了一句："咱们做了这么多年 M3，怎么被问到'它是什么'，一句话都说不上来？"

让各组表态：这三样凑齐了，架构设计是不是就做完了？哪里不对？图、选型、规矩，各自是什么东西？为什么三样加在一起，连"M3 是什么"都答不上来？

### 本单元要反转的直觉

- **画了图 + 做了选型 + 定了规矩 = 做完架构设计**（× 三样是产物/候选/规则，没有一样是"把需求翻译成结构"这个动作）
- **架构设计就是选技术栈**（× 选型是候选，待检验待权衡，是五块里很小一部分素材）
- **我们做过架构设计 = 我们有架构描述**（× 设计是动词，定义是完成时；没定形等于没设计）
- **功能需求决定架构形态**（× 非功能需求（质量属性）才是主要驱动）
- **架构设计的输入 = 全部需求原文**（× 六类输入 + 规定需求：已验证/可追溯/未分配）
- **架构设计的输入就是需求，目的和任务跟设计没关系**（× 六类里目的与任务居判据侧首位——它是 fundamental 成员资格的裁决者，以《系统目的或任务理解确认单》锚定进入）
- **《系统目的或任务理解确认单》是设计做完后补的文档**（× 它是入场券——签字之前，后续一切产物都没有判据锚点）
- **基本概念是架构师发明出来的**（× 90% 选 + 10% 逼；概念是幸存下来的，命名是完成仪式；检验的最高判据是目的判据）
- **直接设计可用性，把 99.99% 分配给每个模块**（× 属性是涌现出来的，不能分只能译）
- **原则越多越严谨**（× 少而精 5~15 条；可判定/有理由/可入评审）
- **关系越多系统越强**（× 关系是成本；关系稀疏、依赖无环、往弱推才可演进）
- **构思 = 等灵感**（× 构思有方法：模式库/参考架构/第一性原理，产出 ≥2 个候选）
- **创新 = 灵感 = 构思，想到好点子就是创新**（× 创新是结果义，新×成缺一归零，链尾追认）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 架构设计是什么（概念本身 · 章首破题，永兵"M3 是什么"压底）→ Q2 五块关系 + 输入链（概念关系）→ Q3 定义 vs 设计 + 三动词链 + 创新坐链尾（真悖论）→ Q4 概念幸存 vs 属性涌现 + 目的判据（真悖论）→ Q5 原则自加 vs 约束被迫 + 演进准则含目的漂移（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 输入六类与驱动（判据运用 · 目的与任务居判据侧首位）→ Q7 关注点识别（判据运用 · 恒信镜照）→ Q8 关系强 vs 弱（真悖论）→ **Q9 方法时刻·五块设计 + 转述**（规则 15：亲手把"画图/选型/定规矩"升维成五块设计，含转述压缩测试 + 跨域变体 + 清单）→ Q10 回部门五块体检 + 六步体检（落地生根 · 含确认单入场券）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章是**强镜照章**：产品组的"五块"是 M3 温控箱的（概念 = 断链即报废还能撑到接入冷库、全程可追溯；属性 = 预判及时性 + 可用性 + 可追溯性；关系 = 传感器 → 固件 → 云端 → 追溯平台），IT 组的"五块"是合同平台的（概念 = 合同数据所有权归合同域；准则 = 审批链留痕；关系 = 审批引擎通过契约访问合同数据）——**同一个五块、两个世界、判据不变**，这正是本章"概念不挑行业"的现场证明。两边都容易把"输入"当"全部需求原文"、把"目的和任务"当"跟设计无关"——目的确认单与基本概念清单是跨两边同用的判据载体。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜架构设计到底是什么？**
"水忠带三样东西进会议室——一张新的四层方块图（在固件层和云端层之间加了一个框'边缘预判模块'）、一页技术选型、一页老规矩，以为架构设计做完了。文正三个问题——预判跑硬件还是云端？'提前告警'要提前多久？加进来之后 M3 还是 M3 吗？——水忠一个都答不上。散会时，产品开发经理永兵问了一句：'咱们做了这么多年 M3，怎么被问到它是什么，一句话都说不上来？'这三样东西各是什么（产物/候选/规则）？架构设计本身是什么？为什么三样加在一起，仍然不算架构设计，连'M3 是什么'都答不上来？"

追问：① 三问判据（决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？）——水忠三样东西各自答得出哪一问？② "设计是动词，定义是完成时"——水忠拿不出什么？③ 架构设计与详细设计怎么分工（横向切 vs 纵向挖）？架构设计和第6章概要定义什么关系（架构是那棵树上不可还原的部分）？为什么先横后纵？系统有架构、模块也有架构——模块的详细设计之前先有什么？④ 你们最近一次"做架构设计"，带的是哪几样？过得了三问吗？答得出"它是什么"吗？

**Q2｜五块什么关系？**
"画出 基本概念、基本属性、设计准则、演进准则、元素关系 的关系图，标出：哪一块直接面对需求？为什么说只有基本概念直面世界，其余四块都是'翻译的翻译'？"

追问：① 内部输入链怎么串（外部原始输入 → 概念 → 属性 → 准则 → 演进；概念 + 属性 → 关系）？② 概念错了为什么后面全错、而且越错越远（失信放大器）？反向校验怎么当场用（答不出的就是无源之水）？③ "外部原始输入"具体是什么（目的与任务/功能/非功能/约束/环境/关注点/资产）？为什么概念吃的必须是规定需求？目的与任务为什么居判据侧首位？④ 你们系统的五块是并列的五份文档，还是按输入链串起来的？

**Q3｜"做过架构设计"和"有架构描述"是一回事吗？构思、定义、设计是一条什么链？创新坐哪？**
""我们做过架构设计"和"我们有架构描述"，是同一件事吗？为什么标准里只有'架构定义过程'和'设计定义过程'，没有'架构设计过程'？构思、定义、设计是一条什么链？创新在这条链的什么位置？"

追问：① 定义 = 划界 + 陈述（de-finis，求真），构思 = 打开可能性（con-capere，发散），设计 = 怎么做（how，求优）——为什么过程以产出物命名？② 设计一词两义：广义（ABET 容器）vs 狭义（15288 §6.4.5 基线生效后的下游）——为什么说"设计"前必须声明取哪一义？③ 创新为什么不在动词链上——"我们去创新吧"和"我们去成功吧"为什么是同一类语病？新×成缺一归零——架构式创新的主导动作为什么恰是"定义"（电动车滑板底盘）？④ 你们团队的架构设计，有可以评审的定形产物吗，还是停在某个人的脑子里？最近一次被叫"创新"的事，够新吗？成了吗？

**Q4｜概念是"幸存"的、属性是"涌现"的，那架构师设计的是什么？**
"这一章说：基本概念不是设计出来的，是幸存下来的；基本属性不是设计出来的，是涌现出来的。那架构师设计的到底是什么？五块里到底有没有'设计'？"

追问：① 概念四副面孔（组织范式/核心抽象/根本机制/根隐喻）+ 五条生成路径（选/提/逼/借/推）；"候选→检验→幸存"——检验靠什么（原型 spike/ATAM/架构评审）？② 检验的最高判据是目的判据——fundamental = 对目的必要且充分（IEV 831-01-01），操作化为不变量判别问句"这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统"？李旭问"M3 还是 M3 吗"问的其实是"M3 的目的还在吗"（同一性·忒修斯之船）？③ 目的判据是成员资格判据、代价判据是从属判据——为什么顺序不可颠倒（先过目的关、再过代价关；用代价判据越过目的判据 = 把难改但无关紧要的误当架构）？④ 命名 = 概念化的完成仪式——"边缘预警输入"这个名字意味着什么？⑤ 属性四步流水线（QAS 场景化→战术→结构落位→验证度量）——为什么不能直接画个"及时性"模块？"99.99% 可用"怎么逼出"冗余 + 故障域"（路径③ = 非功能需求才是主要驱动）？⑥ 你最近一次"加概念"，是选出来的、逼出来的，还是拍板发明的？过目的判据了吗？

**Q5｜架构师为什么要自己给自己上规矩？规矩越多越好，还是越少越好？设计准则和演进准则怎么分？**
""约束是外部强加的，原则是自愿的自我限制"——那架构师为什么要自己给自己上规矩？自加束缚怎么反而是解放（第10章'约束即解放'）？规矩越多越严谨，还是越少越好？设计准则和演进准则怎么分？"

追问：① 约束/决策/原则三词辨析（被迫接受/架构师选择/自愿自加）？② 原则四判据（可判定/有理由/少而精 5~15 条/可入评审）——"追求优雅"为什么不是原则？"用原则代替思考"为什么是教条？③ 演进准则 = 设计准则 × 时间轴——"主语全是变"怎么判别？架构熵增（漂移/侵蚀/技术债）怎么防？目的漂移为什么比架构漂移更危险（执行对、判据过期、无症状），防法各是什么（合规评审 vs 以目的为参照的定期检视）？④ 你们团队的"老规矩"过得了四关吗？有理由吗？能入评审吗？最近一次架构变更，目的变了吗？

### 第二组 · 落地与实践

**Q6｜什么才决定预判逻辑放硬件还是云端？**
"水忠面对'要能提前告警'——功能上就是'算风险、发告警'六个字。为什么这六个字决定不了预判逻辑放硬件还是云端？什么才真正决定？架构设计的输入到底是什么？"

追问：① 输入六类（目的与任务/需求[功能+非功能]/约束/环境/关注点/资产）各是什么？为什么目的与任务居判据侧首位（fundamental 成员资格的裁决者，以《系统目的或任务理解确认单》锚定进入）？为什么非功能需求才是第一驱动（"做到什么程度"才决定结构形态——功能决定长相、质量属性决定能不能站起来）？② 为什么输入必须是规定需求（已验证/可追溯/未分配）？在流沙上画图 = 自损一目——代价为什么是指数级？③ 质量属性为什么不能"分"，只能"译"（涌现属性，没有哪个模块负责可用性）？④ 你们上次架构设计吃的输入，是"文正嘴里那句话"还是规定需求？目的确认单签了吗？

**Q7｜万辉的矩阵里为什么有四格是空的？**
""架构设计的第一步不是画，是听——听那些'在乎'的人，到底在乎什么。"恒信万辉第一次做出 stakeholder × concern 矩阵，发现四格是空的。那四个空格告诉他什么？"

追问：① 关注点识别五步（相关方→提取→划界→编排→验证）？② 好 concern 四判据（有主/有界/可权衡/可追溯）+ 清单级完备（矩阵无空行空列）？③ 漏掉一个 stakeholder = 漏掉一整类 concern——万辉漏了谁（监管/运维/合同相对方/未来的维护者）？④ 你们最近一次架构评审，从"谁在乎什么"出发了吗，还是从"我要画什么"出发？

**Q8｜强关系还是弱关系？"关系是成本"在说什么？**
"强关系（同步调用/共享状态）直接、直观、容易理解；弱关系（异步/事件/契约）解耦、可替换、但要绕。哪个更好？'关系是成本'到底在说什么？"

追问：① 关系五类型（结构/行为/接口/部署/时序）+ 强度光谱（强/中/弱）——为什么强关系变更牵动整片？② 关系设计六步（识别/分类/定方向/降耦合/契约化/检查）——头号决策为什么是依赖方向（DAG 无环）？③ 五判据（有方向/够稀疏/尽量弱/要显式/不穿越）——迪米特法则"talk to your friends, not strangers"？④ 画你们系统关键模块依赖图，有环吗？几条不必要？能往弱推吗？

**Q9｜亲手做一遍五块设计：把"见过"升维成"拥有"（方法时刻 · 含转述）**
"水忠第二次带进会议室的不是图、选型和老规矩，而是五样能'定形'的东西。把你们系统正在设计 / 维护的一个系统（或一次要加的架构能力），亲手做一遍五块设计：基本概念（它还是不是它？过目的判据了吗？）、基本属性（要涌现什么、怎么场景化？）、设计准则（自加什么规矩？过四关？）、演进准则（变而不破坏对的规矩？）、元素关系（怎么连、往弱推？）——哪一块卡住了？"

追问（转述 + 跨域变体）：① 转述（压缩测试）：把"架构设计到底是什么"用三五句话讲给一个完全外行的人——讲到哪卡住，缺口就在哪（五块里的哪一块还没定形）？② 冰链 M3 的五块（边缘预警 = 追溯机制的新输入，候选 B 幸存、命名"边缘预警输入"）↔ 恒信合同平台的五块（合同数据所有权归合同域、审批引擎通过契约访问）——同一个五块，换一个世界判据变没变？"这个概念换个世界还成立吗？"③ 五块定形后，目的判据把"什么配得上基本"裁出来，落成《系统基本概念和基本属性清单》——为什么它是评审的第一张核对单（评审先问"这条概念配得上基本吗"）？④ 把"画图/选型/定规矩 = 见过"和"五块设计定形 = 拥有"对到你们自己的变更上——你们到哪一步了？哪一块还停在"见过"？

**Q10｜给你们的系统做一次五块设计体检（含六步体检）**

### Q1 架构设计到底是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "凑齐了就是做完了，图选型规矩都有了呀。" | 正是要翻的——把产物 / 候选 / 规则当翻译动作 |
| 中 | "图是描述、选型是选择、规矩是规则，但它们还不是架构设计本身。" | 层次分对了，但"翻译"这个动作和三问判据没给出来 |
| 好 | "三样是表达 / 候选 / 规则；架构设计是把需求翻译成系统结构的动作——决定切分 / 连接 / 规矩；三问都答'是'才是；没定形等于没设计；永兵那句'M3 是什么'戳中的正是基本概念缺失——三样东西没有一样定义了'M3 在概念层面是什么'。" | 三问判据 + 设计动词定义完成时 + 永兵追问全部接到，能当场给水忠开方子 |

**产品侧 vs IT侧**：产品组答"方块图是 M3 的描述、传感器选型是候选、老规矩是设计准则"；IT 组答"四张图是描述、技术栈是候选、接口规范是准则"。两边都容易把"画图"当"设计"——图的地位在两边一样：是产物，不是动作。两边也都答不出"系统是什么"——产品组答不出 M3 的概念本质，IT 组答不出合同平台的本质。

**反转话术**（对应 11.3.1 / 11.2.3 / 11.2.5 / 11.1 章首）：水忠那天带的三样东西，没有一样回答"架构设计到底在干什么"。图是**架构描述**（第10章讲过，是产物）；选型是**候选**（待检验、待权衡的素材，选型表没回答"为什么选它、不选它的代价是什么"）；老规矩是**设计准则**（五块设计里的一块，且只是候选/雏形，过四关才升格）。而架构设计是另一个更靠前的动作：**把需求翻译成系统结构**。三问判据当场量：它决定"怎么切分"吗？决定"怎么连接"吗？决定"守什么规矩"吗？三问都答"是"，才是架构设计。**永兵那句"M3 是什么"是最狠的一问**——三样东西加在一起，连"基本概念"这一块都没回答：预判是 M3 长出新本质，还是只是追溯机制的一个新输入？（这就是李旭问的"M3 还是 M3 吗"——答案要等目的判据来裁。）**设计是动词，定义是完成时——没定形的构思，等于没设计。** 另外，架构设计是横向切（系统/子系统级），详细设计是纵向挖（部件内部）——**先横后纵，横切错了纵挖白挖**；架构设计比第6章概要定义更深、更不可逆；**系统有架构、模块也有架构**——模块的详细设计（纵挖）之前，模块自己先有一个"概要定义"（内部结构/依赖方向/实现策略，归模块工程师自己），每一层都先定义"它是什么"再实现。

**参考答案要点**：翻译与系统结构见 §11.2.1；设计是转化见 §11.2.2；定义 vs 设计见 §11.2.3；三问判据见"概念卡片·架构设计"；横切 vs 纵挖含模块级见 §11.2.5；三样东西分层见 §11.3.1；永兵"它是什么"见 11.1 章首。

### Q2 五块什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "五块是五份并列的设计文档。" | 正是要翻的——把输入链当并列清单 |
| 中 | 能画出五块清单，但说不清哪块直面世界 | 清单对，链方向缺 |
| 好 | "只有基本概念直接面对外部原始输入，其余四块吃内部级联；概念→属性（限幅）→准则（细则）→演进（时间维化）；概念 + 属性→关系（具身化）；概念错了后面全错且越错越远；反向校验答不出的就是无源之水；外部原始输入是六类——目的与任务居判据侧首位、是 fundamental 成员资格的裁决者。" | 输入链 + 失信放大器 + 反向校验 + 六类全到位 |

**产品侧 vs IT侧**：产品组举"M3 的概念（断链即报废还能撑到接入冷库）限幅了属性的验收线"；IT 组举"合同数据所有权归合同域的概念限幅了准则（谁都不许绕开）"。两边都容易把五块当成五张表——**五块是链，不是表**；也都容易把"目的与任务"漏出输入——它不是第五类需求，是判据侧首位。

**反转话术**（对应 11.4.1 / 11.4.2 / 11.3.2）：五块不是并列的——**只有"基本概念"直接面对外部原始输入**，越往后的块，输入里"内部成分"占比越高。基本属性吃概念（限幅）、设计准则吃概念 + 属性（执行细则）、演进准则吃设计准则（时间维化）、元素关系吃概念 + 属性（具身化）。外部原始输入是**六类**——目的与任务 / 需求（功能+非功能）/ 约束 / 环境 / 关注点 / 资产；其中**目的与任务居判据侧首位**（fundamental 成员资格的裁决者），需求吃系统级规定需求。这条链带来两个推论：**只有概念是"翻译"，其余是"翻译的翻译"**——概念错了，后面四块全部跟着错，而且错得越来越远；**内部链是"失信放大器"**——评审时发现原则跟概念对不上，基本可以断定链断过。**反向校验就是免费的架构体检**：这条关系服务哪个属性？这个属性被哪个概念限幅？这个原则从哪个概念/教训提炼？答不出的，就是"无源之水"。

**参考答案要点**：五块清单见 §11.2.4；内部输入链见 §11.4.1；三推论见 §11.4.2；六类输入见 §11.3.2；概念卡四问（架构设计/基本概念/基本属性）。

### Q3 "做过架构设计"和"有架构描述"是一回事吗？构思、定义、设计是一条什么链？创新坐哪？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "一回事，做过就会有描述；创新就是想到好点子。" | 正是要翻的——把动词当完成时、把结果当过程 |
| 中 | "不完全是，做过可能是心里的构思。" | 方向对，标准命名玄机 + 三动词链 + 创新没接上 |
| 好 | "定义 = 划界 + 陈述（de-finis·求真）；构思 = 打开可能性（con-capere·发散）；设计 = 怎么做（how·求优）；15288 只有架构定义过程/设计定义过程——过程以产出物命名；设计一词两义（广义 ABET 容器 vs 狭义 15288 §6.4.5 下游）必须声明；构思打开可能性、定义终结漂浮、设计转换到底；创新不在链上，是链尾追认——新×成缺一归零，架构式创新主导动作是定义。" | 元概念 + 命名玄机 + 三动词链 + 创新评分席全到位 |

**产品侧 vs IT侧**：产品组举"我们做过架构设计（在几个人的脑子里）"；IT 组举"我们有架构文档（能进配置管理）"。两边都要翻——**"做过"是动词，可能只发生在某几个人的脑子里；"有描述"是完成时，是可以被别人检查、可以进入配置管理（第13章）的资产**。产品组举"M3 二代加了预判 = 创新"；IT 组举"合同平台升级 = 创新"——两边都要翻"创新 = 点子"。

**反转话术**（对应 11.2.3 / 11.2.2 / 11.4.5）："定义"和"设计"是架构领域天天混用的两个词——definition ← 拉丁 de-finis（彻底地 + 界限）= **划界 + 陈述**，判据是求真（准确/无歧义/可验证）；构思（conceiving）← con-capere（收进来 + 握取），"怀在脑中"，判据是**发散**——从一个关注点生成多个候选，**构思打开可能性**；design 回答"怎么做、怎么造"（how），判据是求优——**设计转换到底**。**关键洞察：设计本质上也是"定义"的一种**——只是定义的对象从"问题/术语"换成了"解决方案"。所以 15288 里只有"架构定义过程""设计定义过程"，没有"架构设计过程"——**过程以产出物命名，而产物必须被定义**。构思无法评审，描述才能评审、验证、基线化。而"设计"还有一词两义——**广义**（ABET 容器：构思、定义、表达都被它装在里面）vs **狭义**（15288 §6.4.5 以已生效架构基线为输入的下游流程）；说"设计"前不声明取哪一义，词就在容器与下游之间漂移。一句话：**设计是动词（构思），定义是它的完成时（定形）**——没定形等于没设计。**创新不在动词链上**——ISO 56000 给创新下的定义是"创造或重新分配价值的新对象或变更对象"，它是**名词**，是动作的结果；"我们去创新吧"和"我们去成功吧"是同一类语病。判据只有一条：**新 × 成，缺一归零**；链上的活干完了，够新又成了，才被追认为创新。**架构式创新主导动作恰是"定义"**——电动车滑板底盘：电池、电机都成熟，重新分块，元件不动、连接重排。

**参考答案要点**：定义 vs 设计 vs 构思见 §11.2.3；ISO 9000:2015 §3.4.8 见 §11.2.2；15288 两过程见 §11.2.2~11.2.3；一词两义（ABET/15288 §6.4.5）见 §11.2.3；创新评分席见 §11.4.5。

### Q4 概念是"幸存"的、属性是"涌现"的，那架构师设计的是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "既然都不是设计出来的，那架构设计可能是个伪命题。" | 把反直觉读成了"没有设计"——正是要翻的 |
| 中 | "概念是选的、属性是长的，架构师是搭结构。" | 结论对，幸存者逻辑、目的判据和四步流水线没给全 |
| 好 | "设计 = 把候选摆上桌 + 定检验（候选→检验→幸存，检验的最高判据是目的判据——fundamental = 对目的必要且充分，操作化为不变量判别问句；先过目的关、再过代价关；命名 = 完成仪式）；属性 = 设计结构让涌现（QAS → 战术 → 落位 → 验证）；'99.99% 可用'逼出'冗余 + 故障域'。" | 幸存者逻辑 + 目的判据 + 涌现机制 + 质量属性反推全到位 |

**产品侧 vs IT侧**：产品组举"M3 的候选 A（边缘预判 = 新根本机制）vs 候选 B（追溯机制的新输入），检验靠目的判据——客户要的是可追溯（目的），候选 B 幸存"。李旭那句"M3 还是 M3 吗"，问的正是这份选择（同一性：M3 的目的还在吗）；IT 组举"合同平台的概念是'合同数据所有权归合同域'，这是从组织范式选出来的"。两边都容易把"检验"当"拍板"——**检验不过，候选就死，哪怕它画进了图里**。

**反转话术**（对应 11.3.6 / 11.3.7 / 11.3.4）：这一章最深的两条反直觉——**基本概念是幸存下来的**：90% 情况下架构师做的不是发明概念，而是从已验证的概念库中选择（模式选择/领域抽象/质量属性反推/类比迁移/第一原理五条路径）；剩下的 10% 是需求和质量属性逼着生成的。生成出来的只是"候选"，要经过假设-检验循环（原型 spike/ATAM/架构评审）活下来，才配叫"基本概念"。候选概念幸存的第一问是**目的判据**：fundamental = 对系统在其环境中的目的而言必要且充分（IEV 831-01-01 Note 2），操作化为不变量判别问句——**「这个东西变了，系统还能不能达成它的目的——它还是不是为那个目的的这个系统？」**。问句的后半问的是**同一性**：人造系统的同一性是目的论的（第10章 §10.3.4 忒修斯之船）——李旭问"M3 还是 M3 吗"，问的其实是"M3 的目的还在吗"。**目的判据是成员资格判据**（裁决谁是 fundamental），它之下还有**从属判据**（改动代价，Ralph Johnson）——代价判据只在根本集合之内排优先级/时机、不产生新成员；顺序不可颠倒：**先过目的关，再过代价关**（用代价判据越过目的判据，会把难改但无关紧要的东西误当架构）。**命名就是概念化的完成仪式**——"事件溯源""六边形架构"一旦被命名，就从想法变成可共享、可讨论、可传承的概念（呼应第1章：概念是共同体酿出来的）。**基本属性是涌现出来的**：你设计的是结构，属性是结构运转之后的宏观效果——不能直接设计"强度"，只能设计微观晶格让强度涌现；不能直接设计"可用性"，只能设计冗余机制让可用性涌现。属性的设计，本质是**结构的设计 + 涌现的验证**（QAS 场景化 → 战术选择 → 结构落位 → 验证度量）。所以架构师设计的是什么？——**设计的是结构、是把候选摆上桌、是定检验**。概念和属性不是"画"出来的。

**参考答案要点**：概念四副面孔/五条生成路径/幸存者逻辑/目的判据（成员资格 vs 代价从属）/同一性见 §11.3.6；属性四步流水线/生命线属性见 §11.3.7；涌现属性只能译见 §11.3.4；材料科学类比见 §11.3.7；案例进展③（候选 B 幸存）见"案例进展③"。

### Q5 架构师为什么要自己给自己上规矩？规矩越多越好，还是越少越好？设计准则和演进准则怎么分？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "被限制就是不自由，规矩越少越好。" | 正是要翻的——把自加原则当外部约束 |
| 中 | "原则是自加的，有帮助，但说不清尺度。" | 自加对了，四判据和"少而精"没接上 |
| 好 | "约束被迫、决策自选、原则自加；原则 = 决策的决策（让你不用重新想）；四判据（可判定/有理由/少而精 5~15 条/可入评审）；演进准则 = 设计准则 × 时间轴——主语全是'变'的是演进准则；目的漂移比架构漂移更危险（执行对、判据过期、无症状），防法分别是合规评审与以目的为参照的定期检视。" | 三词辨析 + meta-decision + 四判据 + 演进判别 + 目的漂移全到位 |

**产品侧 vs IT侧**：产品组举"温度数据归属追溯域"（有理由、可判定）；IT 组举"审批链每一步必须留痕"。两边都要翻"规矩越多越好"——**原则太多等于没有原则**；同时"老规矩"不是天然合格——要过四关升格（可判定/有理由/少而精/可入评审）。恒信万辉列的五条里，③"接口变更必须向后兼容或走版本化"、⑤"走捷径必须记债、定还期"主语是"变"，划去演进准则；剩下的①②④才是设计准则。

**反转话术**（对应 11.3.8 / 11.3.9）：先把三个天天被混用的词分开——**约束**是外部强加的（不可谈判，接受）；**决策**是架构师的选择（具体结构选择）；**原则**是架构师自愿的自我限制（"状态必须外置""禁止循环依赖"）。关键区别：**约束是被迫的，原则是自愿的自我限制**。为什么自愿给自己上规矩？因为原则是"**决策的决策**"（meta-decision）——不是替你做决策，是**让你不用重新想**。第10章"约束即解放"——少而精的纪律反而让团队把脑力留给真正要权衡的事。但要守住分寸：**用原则代替思考**是原则永远面对的诱惑——原则负责"不需要重新想的事"，权衡负责"必须重新想的事"；如果一条原则让团队不再权衡，它就已经从纪律退化成教条了。四条有效性判据：可判定（"追求优雅"不可判定，不配当原则）/有理由（答不出"为什么"，删掉）/少而精（5~15 条）/可入评审（能变成架构评审的检查项）。还有演进准则——**设计准则 × 时间轴**，判别法一句话：**主语全是"变"的是演进准则**；没有它，架构在无人管束时必然退化（漂移/侵蚀/技术债）。这里的"漂移"要消一个歧：常见的**架构漂移**——实现偏离了架构，执行歪了，靠演进准则 + 合规评审防；另有一种更危险、且无症状的漂移——**目的漂移**：目的偏离了架构，执行对、判据整体过期，图却还挂得整整齐齐，它靠的是**以目的为参照的定期检视**（第11章 §11.3.9）；目的变更 = 架构重审的强制触发器。

**参考答案要点**：约束/决策/原则见 §11.3.8；原则四判据见 §11.3.8；演进准则八类 + 判别法 + 目的漂移见 §11.3.9；老规矩过四关见 §11.3.8 与案例进展④。

### Q6 什么才决定预判逻辑放硬件还是云端？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "功能需求决定——'要能提前告警'就是要放个预判模块。" | 正是要翻的——把功能当架构驱动 |
| 中 | "质量属性影响架构，具体说不清怎么影响。" | 结论对，"做到什么程度"、规定需求和六类输入没接上 |
| 好 | "非功能需求才是主要驱动——'提前 30 秒还是 5 分钟''误报率压到多少'决定放硬件还是云端；输入 = 六类（目的与任务居判据侧首位）+ 规定需求（已验证/可追溯/未分配）；目的以《系统目的或任务理解确认单》锚定进入；在流沙上画图 = 自损一目。" | 非功能主导 + 六类 + 目的居首 + 确认单全到位 |

**产品侧 vs IT侧**：产品组答"提前量 ≥ 5 分钟、误报率 ≤ 5% 决定边缘计算 + 双路冗余"，逸人翻了翻选型页算账："双路冗余，就是多一路采样、多一颗传感器——物料、批次、组装工序，全要跟着走：BOM 多一行、备件库多一行、组装工序多一步，起订量、交期都得重谈——不是多一颗料的钱，是整条供应链重排的账，这条制造约束得算进权衡"；IT 组答"响应时间、可用性决定缓存/冗余/分片"。两边都要翻"拿需求一句话直接去设计"——**那句话既没定义"提前多久"（属性缺失），也没定义"判错了怎么办"（约束缺失）**；也都要翻"目的任务跟设计无关"——M3 二代的目的（客户要可追溯）正是裁决"预判是不是新本质"的那把尺。

**反转话术**（对应 11.3.2 / 11.3.3 / 11.3.4 / 11.4.3）："要能提前告警"功能上就是六个字——算风险、发告警。但这六个字决定不了预判逻辑放硬件还是云端。**功能需求告诉你"做什么"，质量属性告诉你"做到什么程度"，而"做到什么程度"才真正决定结构形态**（Bass 等《Software Architecture in Practice》）：要 99.99% 可用 → 冗余与故障域；要支持 10 倍扩容 → 无状态与分片；要快速上市 → 最少部件数。**功能相同的系统，质量属性不同，架构可以完全不同。** 水忠那句"提前告警"，真正要追问的是：提前 30 秒还是 5 分钟？误报率压到多少？算错了的后果谁来兜？——这些质量属性才决定预判逻辑放硬件还是云端。而**输入不是"全部需求原文"**，是六类——目的与任务（判据侧首位）/ 需求（功能+非功能）/ 约束 / 环境 / 关注点 / 资产；**目的与任务居判据侧首位**，以《系统目的或任务理解确认单》锚定进入设计——它是 fundamental 成员资格的裁决者。而且输入必须是**规定需求**：架构设计是整条设计链里最不可逆的一环，在流沙上画结构图等于开局自损一目——需求一变结构就得跟着动，代价是指数级的。还有：需求分配是架构设计自己的工作，不是输入；质量属性是涌现属性，不能分，只能译。

**参考答案要点**：非功能需求主导 + 六类输入见 §11.3.2；目的与任务居判据侧首位见 §11.3.2 / §11.4.3；规定需求见 §11.3.3；需求层级见 §11.3.3；涌现属性只能译见 §11.3.4；案例进展①（水忠先搞清楚吃什么）见"案例进展①"。

### Q7 万辉的矩阵里为什么有四格是空的？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "表格没填满，下次补上就行。" | 正是要翻的——把矩阵当文书活 |
| 中 | "有相关方没有被任何视图回答——架构有盲区。" | 空格意义说对了，五步识别和四判据没给 |
| 好 | "空格 = 有相关方、却没有任何视图打算回答他们在乎什么——漏掉一个 stakeholder 就是漏掉一整类 concern；关注点识别五步；好 concern 四判据（有主/有界/可权衡/可追溯）+ 清单级完备（矩阵无空行空列）。" | 空格判读 + 五步 + 四判据 + 清单级完备全到位 |

**产品侧 vs IT侧**：产品组举"司机在乎别误报、冷链客户在乎留出补救时间、维修在乎别误动作、监管在乎留痕——这些天然冲突，架构设计就是在冲突的关注点之间做权衡"；IT 组举"万辉漏了监管/运维/合同相对方/未来的维护者"。两边都容易把关注点当"设计"——**关注点是识别出来的，不是设计出来的**。

**反转话术**（对应 11.3.5）：那四格空格告诉他：**有相关方，却没有任何视图打算回答他们在乎什么**——这就是架构设计的起点。老习惯是"我要画什么"出发；万辉这次从"谁在乎什么"出发。**关注点是识别出来的，不是设计出来的**——42010 从头到尾用的动词是 identify，不是 design。concern 是 stakeholder 的**利益**（interest），已存在于其头脑、组织和契约里；架构师的工作是发现、提取、陈述，而不是发明。一个"设计"出来的、没有 stakeholder 真正关心的 concern，不是架构洞察，是自嗨。识别五步：识别利益相关方 → 提取关注点 → 划界与陈述 → 组织编排（矩阵，标记冲突组 = 权衡点 = 架构决策的主战场）→ 验证完备性。好 concern 四判据：有主/有界/可权衡/可追溯；还有一条清单级判据——**完备**（矩阵无空行空列）。**漏掉一个 stakeholder，就是漏掉一整类 concern。**

**参考答案要点**：关注点识别见 §11.3.5；concern 定义三要素见 §11.3.5；案例进展②（恒信矩阵四空格）见"案例进展②"。

### Q8 强关系还是弱关系？"关系是成本"在说什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "关系越多系统越强，大家互联互通。" | 正是要翻的——把关系数量当系统强度 |
| 中 | "弱关系更好，解耦。" | 结论对，但"满足需求前提下克制"的分寸没到 |
| 好 | "关系是成本（n²），每一条都是未来变更时的一处牵动；克制、往弱推、契约化；依赖无环（DAG）——方向即权力；五判据。" | 成本机制 + 降耦合 + 五判据全到位 |

**产品侧 vs IT侧**：产品组举"传感器 → 固件（预判引擎）→ 云端（置信度模型）→ 追溯平台，依赖方向单向、接口契约化"；IT 组举"审批引擎直接调合同主表 → 通过合同服务（契约）访问，关系从强降到契约弱"。两边都要翻"强关系直观 = 好关系"——**同一对要素之间，关系强度是设计的自由变量**。逸人把元素关系对着产线看："方向要是绕了，我的批次台账第一个乱。"

**反转话术**（对应 11.3.10）："关系是成本"这一章最反直觉的第一原则——n 个要素如果全互联，是 n² 条关系；**每一条关系，都是未来变更时的一处牵动**。所以关系设计的第一原则是"克制"：能没有的关系就不要有。好的架构往往是**关系稀疏**的架构——关系少，独立性才强，可演进性才高。关系设计六步：识别必要关系 → 分类定性（结构/行为/接口/部署/时序）→ 定方向（**依赖方向是关系设计的头号决策**，健康的依赖图必须无环 DAG）→ 降耦合（核心动作：同步调用 → 异步消息；直接调用 → 事件发布订阅；共享状态 → 消息传递，每降一级变更的牵动范围就小一圈）→ 契约化（关系必须白纸黑字，否则就是隐式耦合）→ 检查。五判据：有方向/够稀疏/尽量弱/要显式（依赖抽象不依赖实现）/不穿越（迪米特法则——talk to your friends, not strangers）。注意分寸：**不是关系越少越好**，是在满足需求的前提下把每条关系往弱的方向推。

**参考答案要点**：关系是成本见 §11.3.10；关系五类型/强度光谱见 §11.3.10；六步动作与五判据见 §11.3.10；案例进展④（审批引擎 → 契约）见"案例进展④"。

### Q10 给你们的系统做一次五块设计体检（含六步体检）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强架构管理、要画好架构图。" | 没落到五块任何一块，不可检查 |
| 中 | 用一块查出缺口（如"说不出基本概念"），但没查六步/确认单/创新 | 有判据，但只照了一面 |
| 好 | 按五块逐项答，挑出最薄的一块 + 一个可检查动作（如"下周评审会前，把这条老规矩过四关"），说出先答哪块（基本概念）、确认单签没签（复述有无架构语言）、六步里哪步被跳过（最易②⑥）、评审先过清单（"这条概念配得上基本吗"）、创新够新吗成了吗、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**产品侧 vs IT侧**：两组各给自己系统体检——体检表本身是同一份（五块 + 反向校验 + 三动词链/六步 + 确认单/清单 + 创新判定），这正是"架构设计不挑行业"的现场证明。

**反转话术**（对应本章综合应用）：这一章的判据不是彼此孤立的——三问判据测"是不是架构设计"，四判据测"老规矩是不是原则"，五判据测"关系是不是成本"、QAS 测"属性能不能验收"，目的判据测"概念配不配得上基本"，反向校验测"输入链断没断"，六步测"闭环缺没缺"，创新评分席测"够新吗成了吗"。**答不出的那一块，就是你的设计缺口**（书练习 1）——不用等五块答全，找到第一个答不出的就能开工。先答基本概念——**只有概念直面世界，概念错了后面全错**；开工前先过《系统目的或任务理解确认单》——**签字之前，后续一切产物都没有判据锚点**；评审先从《系统基本概念和基本属性清单》问起——答不出必要性论证的就是"无源之水"。六步里最容易被跳过的是**②生成备选**（直接从需求跳到唯一解画图，架构层的 Cowboy Coding）和**⑥评审背书**（只评审不背书，评审变汇报）——**没有背书的架构，只是架构师的个人意见**。最近一次被叫"创新"的事，用评分席量：够新吗？成了吗？主导动作是构思/定义/设计？元件不动、连接重排的是架构式创新，主导动作是定义。

**参考答案要点**：五块体检方法见作业指南（本章分析文档第 6 步）；判据见"本章判据"（14 条）；目的确认单与清单见 §11.4.3 / §11.4.4；架构生成六步见 §11.4.3；创新评分席见 §11.4.5；练习 1~15 见书"练习"。

## 四、知识卡片

### 一页图（书"本章概念总图"）

```
架构设计 = 一个动作（把需求翻译成系统结构）+ 一份清单（五块设计）+ 一条链（只有概念直面世界）+ 一条动词链（构思→定义→设计）+ 一个裁决者（目的判据）+ 链尾创新评分席

第一幕 · 是什么：翻译五块
  翻译必然做选择：同一需求 → 不同结构
  设计是动词，定义是完成时——过程以产出物命名（15288 只有"架构定义过程"）
  三动词链：构思打开可能性 → 定义终结漂浮 → 设计转换到底（一词两义必须声明）
  五块清单（42010 定义拆开）：基本概念 / 基本属性 / 设计准则 / 演进准则 / 元素关系
  "基本"由目的判据裁决：fundamental = 对目的必要且充分（IEV 831-01-01）
  与详细设计：横向切 vs 纵向挖——先横后纵；系统有架构、模块也有架构

第二幕 · 不是什么：幸存涌现自加克制磨边弧
  三样东西不是架构设计：图 = 架构描述（产物）/ 选型 = 候选 / 老规矩 = 设计准则候选
  输入不是全部需求原文：六类（目的与任务·需求·约束·环境·关注点·资产；判据侧/选项空间，目的居首位） · 规定需求 · 架构吃系统级
  质量属性不是"分"下去的：涌现属性只能"译"成部件约束
  关注点不是设计出来的：是识别出来的（五步识别 · 好 concern 四判据 + 清单级完备）
  基本概念不是设计出来的：是幸存下来的（四副面孔 · 五条生成路径 · 候选→检验→命名；检验最高判据=目的判据）
  基本属性不是设计出来的：是涌现出来的（QAS → 战术 → 落位 → 验证；生命线属性）
  设计准则不是抄来的：原则是自加的（约束被迫 / 决策自选 / 原则自加；必须·禁止·应当 + 理由）
  演进准则不是静态的：设计准则 × 时间轴（防漂移 / 侵蚀 / 技术债 / 目的漂移）
  元素关系不是越多越好：关系是成本（克制 · 往弱推 · 契约化）

第三幕 · 往哪去：五块落地
  只有基本概念直面世界，其余四块吃内部级联
  推论：只有概念是"翻译"，其余是"翻译的翻译"；链是失信放大器；反向校验免费体检
  架构生成六步（前置入场券·目的确认单）：定驱动 → 生成备选 ≥2 → 权衡 → 分配接口 → 表达基线 → 评审背书（没有背书 = 个人意见）
  系统基本概念和基本属性清单：目的判据的裁决产物——五块总纲 · 评审第一核对单 · 受控枚举（确认单是锚、清单是纲）
  创新坐链尾评分席：新 × 成，缺一归零；架构式创新主导动作是定义
  见过→拥有：画图 / 选型 / 定规矩 = 见过；五块设计定形 = 拥有
```

### 金句（书"本章判据"提炼）

- **架构设计 = 翻译**——把需求翻译成系统结构（切分、连接、规矩）；画图、选型、定规矩都只是这个翻译的产物/候选/规则，不是翻译本身。
- **设计是动词，定义是完成时**——没定形，就等于没设计。构思无法评审，描述才能评审、验证、基线化。
- **横切先于纵挖**——墙砌错了要拆楼，装修错了刷一遍就行；系统有架构、模块也有架构。
- **非功能需求才是主要驱动**——功能决定长相，质量属性决定能不能站起来。
- **输入是六类、且必须是规定需求**——目的与任务居判据侧首位，以《系统目的或任务理解确认单》锚定进入。
- **质量属性不能分，只能译**——涌现属性没有哪个模块"负责可用性"。
- **关注点是识别出来的，不是设计出来的**——漏掉一个 stakeholder，就是漏掉一整类 concern。
- **概念幸存、属性涌现**——90% 选 + 10% 逼；不能设计强度，只能设计晶格；检验的最高判据是目的判据（它还是不是为那个目的的这个系统）。
- **原则是自愿的自我限制**——约束被迫、决策自选、原则自加；演进准则 = 设计准则 × 时间轴。
- **关系是成本**——关系稀疏才可演进；依赖无环、往弱推、契约化。
- **只有概念直面世界**——其余四块都是"翻译的翻译"；概念错了，后面全错，而且错得越来越远。
- **构思打开可能性，定义终结漂浮，设计转换到底**——没有背书的架构，只是架构师的个人意见。
- **确认单是锚、清单是纲**——目的进场先签确认单，什么配得上基本由清单裁决；评审先过清单这一关。
- **创新 = 新 × 成，坐链尾评分席**——够新又成了，才被追认为创新；架构式创新主导动作是定义。

## 五、课后作业

1. **书练习（与题卡同源）**：挑一个你正在设计或维护的系统，回答五块设计：它的基本概念（组织范式/核心抽象/根本机制/根隐喻）、基本属性（生命线属性）、设计准则、演进准则、元素关系各是什么？——答不出任何一块，那一块就是你的设计缺口。（书练习 1）
2. **书练习（三动词链拆解）**：把一个架构决策拆成三动词链：构思阶段你生成过几个候选？定义阶段被否掉的备选"死因"记录了吗（ADR）？设计（狭义）阶段是等基线生效才动的吗？（书练习 12）
3. **回部门落地**：结合现状，挑一个正在设计或维护的系统，用五块设计做一次体检——五块各答得出吗？答不出的那一块是不是就是设计缺口？再顺着六步查：六步里哪一步被跳过了？给出最该做的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪一块补上了、哪一块还卡着、卡在哪个判据上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次五块设计体检（含六步体检 + 入场券）：
>
> 1. **挑系统 / 挑变更（先立尺子）**：挑一个你正在设计或维护的系统，或最近一次架构变更。
> 2. **写目的确认单（先锚目的，入场券）**：写一份《系统目的或任务理解确认单》——业务方原话（只引不改）+ 你的复述理解 + 确认记录；检查复述里有没有出现架构语言（元素/方案/需求，出现 = 越界）。**签字之前，后续一切产物都没有判据锚点**；目的模糊或关注点冲突时，先向上游回溯澄清。
> 3. **分三样东西的层次（先看病）**：列出这次架构工作的"图 / 选型 / 规矩"各是什么——它们只是表达 / 候选 / 规则候选，不是架构设计本身。
> 4. **逐块答五块（五块设计）**：基本概念（它"怎么想"——"去掉就不是它"的是什么？走哪条生成路径？**过目的判据了吗**（不变量判别问句"它还是不是它"）？先过目的关、再过代价关？它有名字吗？）→ 基本属性（要涌现什么本质特征，目标属性场景化了吗 QAS？）→ 设计准则（自加哪些规矩，用"必须 / 禁止 / 应当 + 理由"句式，过四关）→ 演进准则（每条设计准则做时间维化，用"变"字句式；顺带查一次目的漂移）→ 元素关系（关键模块依赖图，有环吗？几条不必要？能往弱推吗？）。
> 5. **反向校验（免费体检）**：随机挑一条设计准则向上追——它从哪个概念/属性提炼来的？答不出 = 无源之水（输入链断过）。
> 6. **三动词链 + 六步体检**：构思生成过几个候选（≥2 吗）？被否备选死因记录了吗（ADR）？六步里哪一步被跳过？（最易②生成备选——架构层 Cowboy Coding、⑥评审背书。）
> 7. **落清单（目的判据的裁决产物）**：把"什么配得上基本"落成《系统基本概念和基本属性清单》——每条注明 定义 / 对目的的必要性论证 / 到目的·需求的追溯链；答不出必要性论证的就是"无源之水"。它是评审的第一张核对单。
> 8. **创新判定（链尾评分席）**：最近一次被叫"创新"的事——够新吗？成了吗？主导动作是构思/定义/设计？
> 9. **产出三件最该做的事**：每条 = 一个可检查动作 + 一条判据（三问 / 四步 / 四关 / 五判据 / 六步 / 目的判据）。
>
> 卡住时：答不出的那一块就是设计缺口，不必五块答全；先钉基本概念——只有概念直面世界，概念错了后面全错；开工前先问"确认单签了吗、目的是不是已经确认可判定"。
