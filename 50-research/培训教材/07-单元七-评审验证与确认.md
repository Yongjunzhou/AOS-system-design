## 一、单元导读

### 主题

这一章发的不是词，是**三把尺子**——评审、验证、确认，三个看门人，三把完全不同的尺子。它们不是"检查一下"的三种说法，而是三件不同的事：**评审对目标（方向对不对）、验证对需求（做对了吗）、确认对用途（做对的东西了吗）**。它回答三个更根本的问题：这三个词为什么在中文里看起来像近亲？三个看门人各守哪道门？为什么只做验证不做确认，会"测试全过、没人用"？

### 开场破题（对应章首误解现场）

念出恒信集团合同审批系统上线前那场评审会：李工在投影上打开了 UAT 报告，语气笃定——"UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。**我们验收合格，可以上线。**"会议室里有人开始收东西了。财务的老王却没动："你们让我们点的那个测试环境，我们月底对账的场景——25 号之后签的合同算哪个月——测了吗？"李工愣了一下："测试用例是照着需求清单写的，需求清单里……没有这条。"Ada 坐在角落，轻声说："李工，你把三件事当成一件事办了。"——"哪三件事？""评审、验证、确认。"

让各组表态：李工说错在哪？"测试通过率 96%"是哪件事的证据？"月底对账的场景没测"说明哪件事缺位？大多数人一开始都站在李工这边——这正是这一章要推翻的直觉。

### 本单元要反转的直觉

- **UAT 跑了 = 确认过了**（× 让业务方点测试环境是当测试员；确认要真实用户 + 真实任务 + 真实场景）
- **测试全绿 = 验证过了**（× 测试只是提供客观证据的手段之一；验证要对全部规定需求做认定）
- **评审 = 开会过一遍需求**（× 评审对目标，不是核对需求；没结论、没记录，最多算聊天）
- **验证和确认差不多，都是证明没问题**（× 翻译伪朋友：验证对需求，确认对用途——参照不同，射程不同）
- **满足所有需求 = 达成目标**（× 需求本身可能错；评审是唯一抬头看目标的环节）
- **确认是验证的加强版，范围更大而已**（× 不是范围不同，是参照不同：文档 vs 场景；验证够不着隐含、确认兜得住隐含）
- **复盘也是评审，都带"评"字**（× 评审管把关，复盘管改进；复盘是检测器，裁决才是治理）
- **测试全过、没人用是运气问题**（× 只做验证不做确认 → 隐含需求系统性漏失 → 测试全过没人用，是因果问题）
- **确认可以上线后补**（× 上线后补确认，就叫"上线事故"）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 三件事被当成一件事（概念本身 · 章首破题）→ Q2 三个词什么关系（五维表 + 接力链，概念关系）→ Q3 评审对目标 vs 核对需求（真悖论）→ Q4 测试通过 vs 验证通过（真悖论）→ Q5 业务方点了 vs 确认过了（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 三关走一遍月底对账事故（判据运用 · 因果链 · 复盘）→ Q7 目标具体化 + 通过标准（判据运用 · 评审手法）→ Q8 用三要素拆两场测试（判据运用 · 验证/确认）→ **Q9 方法时刻·判据主义**（规则 15：亲手给"评审/验证/确认"各立可检验判据——判据运用形态）→ Q10 回部门三个看门人体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"验证"是零部件试验、整机低温试验，"确认"是真实运输车跑全程——"用例全过，说明不了上路能过"（断档 30 秒）；IT 组的"验证"是单元/集成/系统测试，"确认"是 UAT、灰度、试运行——"测试全绿，月底对账对不上"（合同编号）。**同一个概念、两个世界、判据不变**，这正是本章"三个看门人，两扇世界的门"的现场证明——三把尺子不挑行业。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜李工把哪三件事当成一件事办了？**
"章首那场评审会上，李工举着 UAT 报告说：'UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。我们验收合格，可以上线。'Ada 只问了一句：'月底对账的场景测了吗？'李工答：'测试用例是照着需求清单写的，需求清单里没有这条。'Ada 说：'你把三件事当成一件事办了。'——是哪三件事？评审、验证、确认各自是什么、各看什么？为什么三个词在中文里看起来像近亲？"

追问：① 三把尺子各带什么可检验判据（评审三问 / 验证三要素 / 确认三要素）？评审为什么不要求客观证据、却必须记录（系统性三属性：团队参与 + 结果文档化 + 过程文档化——没记录=聊天）？② 李工话里"测试通过率 96%"是哪件事的证据？它证明不了另外两件事的什么？③ 你们最近一次说"验收通过了"，是三个看门人依次签字的，还是把三件事当成一件事办了？

**Q2｜评审、验证、确认什么关系？**
"请给出 评审、验证、确认 三个词的关系——用一张五维表（定义 / 参照 / 动作 / 证据 / 时机）把三把尺子并排钉死，再说出三个看门人怎么接力（评审站在哪、验证站在哪、确认站在哪）。为什么三个参照物（目标 / 规定需求 / 预期用途）不是同一个？"

追问：① 参照不同为什么是决定性的（决定射程和命运）？② 规定需求一个词为什么三个看门人都绕不开（评审审它 / 验证对它 / 确认兜它）？③ 你们平时把"验证"和"确认"糊着用吗？哪次糊出过事？

**Q3｜"逐条核对需求"和"评审对目标"，哪个是评审？**
"冰链的需求评审会开了一下午：小林拿着需求清单逐条念、逐条打勾——'有编号 ✓、有来源 ✓、可测吗 ✓、验收标准有 ✓'，三十条念完，宣布评审通过。这不是更省事、更客观吗？可书里说评审以'目标'为参照。'逐条核对需求'和'评审对目标'，哪个对？什么判据能分清？"

追问：① 评审不是核对需求的三个理由（需求本身可能错 / 否则与验证重复 / 满足所有需求≠达成目标）？② "需求满足得越彻底，目标的偏离走得越远"——为什么把评审做成了"最后一小时核对"，就是最失败的评审？③ 你们最近一次评审，问过"这套需求还朝那个目标吗"吗？

**Q4｜测试全绿，算验证通过吗？**
"'测试全绿'不就是'验证通过'吗？测试都跑了，证据还不够吗？可书里说'测试通过≠验证通过'。那什么才算验证通过？测试在验证里到底算什么？"

追问：① 验证三要素（对照规定需求 + 客观证据 + 认定）——测试满足了哪个？② 96% 通过率剩下的 4% 说明什么（那 4% 对应的需求没有证据）？③ 你上次说"测试全绿"，验证三要素齐了吗？

**Q5｜让业务方点了测试环境，算确认过了吗？**
"李工让法务、财务、业务在测试环境点了一圈，'业务方都验收了，这还不是确认？'可书里说这是'让业务方当测试员'。让业务方参与，怎么反而不是确认？"

追问：① 确认三要素（真实用户 + 真实任务 + 真实场景）——李工的 UAT 缺了什么？② 为什么"让业务方点测试环境"是把确认做成了验证？③ 只做验证不做确认，那些没进文档的隐含需求会怎样（因果链：系统性漏失 → 测试全过、没人用）？④ 你们上次的 UAT，业务方是在跑用例，还是在跑真实任务？

### 第二组 · 落地与实践

**Q6｜"验证做了，其余没做"——月底对账为什么对不上？**
"恒信上线两周后第一个月底，财务老王对账对不上了——25 号之后签的合同，合同编号全落在当月。Ada 在白板上写了六个字：'验证做了，其余没做。'——这句话怎么拆？为什么说'三个看门人只来了一个，剩下两个在等一场事故'？"

追问：① 三关接力（评审开工前 / 验证交付时 / 确认交给用户）——这次事故缺了哪两关？② 缺每一关的代价是什么（缺评审白做 / 缺验证返工 / 缺确认没人用白做）？③ 复盘显影了偏差（两条行动项："变更必须先过评审对目标一关"+"UAT 改真实场景跑"），但裁决（合同编号归属规则要不要定、归谁定）为什么不是复盘能给的？④ 用三关走一遍你们最近一次上线，缺的那关代价是什么？

**Q7｜为什么"能上线"评不了？**
"Ada 重开上线评审会，李工说'上线前评审，目标就是系统能上线'。Ada 说：'能上线评不了。目标要有对象、有时限、有可衡量结果。'——为什么'能上线'评不了？目标具体化配方是什么？通过标准为什么要会前定、会后逐条打勾？"

追问：① 目标具体化配方（对象 + 时限 + 可衡量结果）+ 检验三问（通过标准是什么 / 有没有可观察可测量的判定 / 两个人理解不一致看什么裁决）？② 评审是洒在全程的六个把关节点（需求 / 设计 / 代码 / 测试 / 发布 / 复盘），为什么不是只在上线前做一次（问题越早发现修复成本越低：需求 1 → 发布后 30~70 倍）？③ 评审和复盘有什么区别（把关 vs 改进；复盘是检测器）？④ 你们最近一次评审的通过标准是会后现想的吗？

**Q8｜用验证三要素和确认三要素，拆开这两场测试**
"恒信的李工说'业务方点了测试环境，通过了'；冰链的小赵组织了一场真实运输测试——用例全过，但车厢一颠簸，温度记录仪断档 30 秒，测试台架复现不了。用验证三要素和确认三要素拆开这两场：各满足验证吗？各满足确认吗？为什么'用例全过，说明不了上路能过'？"

追问：① Ada 三问（月底对账的数据真实还是造？真实月底时间点真实并发下做的吗？法务电子签章审批链业务方验证过"谁审谁签"吗？）——李工的 UAT 全答不上 ② 断档 30 秒为什么测试台架复现不了（测试环境里没有路；用例的参照是需求文档，真实场景的参照是"疫苗能不能安全送到"）？③ 隐含需求（振动下温度记录连续 / 月底对账口径）为什么只有确认兜得住（验证的尺子在文档、确认的尺子在场景；冰山比喻）？④ 你们最近一次"全绿"，放进真实场景会现出什么形？

**Q9｜亲手给"评审/验证/确认"各立一条判据（方法时刻）**
"这一章的方法底座时刻是判据主义——不给没有判据的尺子。李工混了三个词，因为他从没给每把尺子立过可检验判据。请亲手给'评审 / 验证 / 确认'各立一条可检验判据：参照是什么、证据要不要、结论记不记录？再用你立的判据，当场拆一张你们自己的 UAT 报告或一场评审会。"

追问：① 你的判据符合判据主义三问吗（是什么 / 失效边界 / 反例）？② 你给三把尺子立的判据，换到冰链 M3（硬件侧：零部件试验 / 整机低温试验 / 真实运输车跑全程）还成立吗？判据变没变——这说明了什么（概念不挑行业）？③ 你们最近一次"验收通过"，是三条可检验判据都打勾，还是靠"报告绿了"？——有判据才算拥有，有标签只是见过。

**Q10｜给你们的部门做一次"三个看门人体检"**
"结合你们部门现状，用评审三问、验证三要素、确认三要素三把尺子，给你们最近一次上线/交付做一次'三个看门人体检'——给出最该改进的三件事，每个落到一个动作。"

追问：① 先查哪一关（评审对目标 / 验证对需求 / 确认对用途）？为什么？② 你们最近一次"验收通过"，三个看门人谁没站到门口（对照因果链：只验证不确认 → 测试全过没人用）？③ 两周后回来报告：哪个看门人补上了、哪个还虚着、卡在哪个判据上？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 李工把哪三件事当成一件事办了？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "李工说得对，UAT 全绿就是验收合格，可以上线。" | 正是要翻的——把三件事当成一件事 |
| 中 | 能背出"评审/验证/确认"三个词，但说不清各看什么 | 定义是背的，参照没分清——"评/验/认"形近字把分界线糊上了 |
| 好 | "评审对目标、验证对需求、确认对用途——李工把'测试通过率 96%'（验证的证据）当成了确认（真实场景能用）；三个词是翻译伪朋友，中文形近字糊了四十年；月底对账场景没人测，正是确认缺位的证据。" | 三把尺子 + 参照 + 翻译伪朋友 + 案例全咬合，能当场给李工下结论 |

**产品侧 vs IT侧**：产品组答"冰链 M3——零部件试验/整机低温试验=验证，真实运输车跑全程=确认，设计评审对目标"；IT 组答"恒信——单元/集成/系统测试=验证，UAT/灰度=确认，上线评审对目标"。两边都容易把"测试全绿"当"验证过了"，再顺手当"确认过了"——**三个词，三把尺子，谁都替不了谁**。

**反转话术**（对应 1.1/1.2/1.3 + 章首）：李工说错的不止一处——他混了三个词。**评审对目标（方向对不对，判断）、验证对需求（做对了吗，证明）、确认对用途（做对的东西了吗）。** 三个词不是"检查一下"的三种说法，而是三件不同的事。中文把它们糊成近亲，是第1章第三种词汇病**"翻译伪朋友"**：review / verification / validation 三个英文词词源、构词、归属完全不同，翻译成中文恰好都带一个"评/验/认"字。ISO 9000 把评审放在 3.11"有关确定的术语"组（与确定、监视、测量、检验一家），把验证/确认放在 3.8"有关规范的术语"组——**"确定"和"认定"是两种动作：评审的动作是"确定"（主动调查，不要求客观证据），验证/确认的动作是"认定"（结果已经在那儿了，去证实，必须有客观证据）。一个是判，一个是证。** 李工那句"UAT 全绿"是验证的证据（还只是一部分），它证明不了"真实对账场景能用"（确认），也证明不了"方向对"（评审）。**把三件事当成一件事办，混到验收签字那一刻，就是合同纠纷。**

**参考答案要点**：三定义见 §1.5/§1.6/§1.7 + 概念卡；翻译伪朋友见 §1.1；ISO 分家见 §1.2；三参照见 §1.3；章首误解现场。

### Q2 评审、验证、确认什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把三个词排成并列的"把关"，说不清分界 | 关系结构错误——是五维分界 + 接力链，不是并列同义 |
| 中 | 能背出"评审对目标、验证对需求、确认对用途"，但五维表/接力链没接上 | 一句口诀会背，五维分家、三个看门人站位没钉死 |
| 好 | "五维表：定义/参照/动作/证据/时机——验证和确认在动作（认定）与证据（必须客观证据）上一致、只在参照上不同，评审与前两者分族（确定/不要求证据）；接力链：评审站在开工前抬头看方向、验证站在交付时低头对规格、确认站在交给用户时走进真实场景；三个参照物——目标/规定需求/预期用途——参照不同是决定性差异。" | 五维表 + 接力链 + 参照三物全到位 |

**产品侧 vs IT侧**：产品组画"M3 的三关——设计评审对'断链即报废时撑到冷库'、整机试验对规格、真实运输车对'疫苗安全送到'"；IT 组画"恒信的三关——上线评审对'月底对账不再靠手工'、系统测试对需求、UAT 对真实对账"。两边画的是一张图——**三个看门人、两扇世界的门，接力链纹丝不动**。

**反转话术**（对应 1.3/1.4/3.1）：把三个词摆成**五维表**：定义、参照、动作、证据、时机——五个维度一起把三个词分开。验证和确认在"动作"（认定/证明）与"证据"（必须有客观证据）上一致，只在"参照"上不同；评审与前两者分族：动作是"确定"（判断）、不要求客观证据。**参照是决定性的差异**——评审对目标（要实现的结果，3.7.1）、验证对规定需求（明示成文，3.6.4 注2）、确认对预期用途（真实使用情境）。三个看门人守着三道门：**评审站在"开工前"抬头看方向、验证站在"做完了"低头对规格、确认站在"交给用户"走进真实场景。** 目标驱动需求的推导，用途要在真实场景里才现形。注意一个词：**规定需求**——评审审它（对象）、验证对它（参照）、确认兜它（验收依据），三个看门人都绕不开它；它没成文，三个看门人就全闭门。这正是章首那条"口头补的需求"的下场。

**参考答案要点**：五维表见 §1.4；三参照见 §1.3；接力链见 §3.1 + 开篇枢纽；规定需求一词见 §2.1。

### Q3 "逐条核对需求"和"评审对目标"，哪个是评审？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "逐条核对挺客观，评审不就这样吗。" | 正是要翻的——把核对当评审 |
| 中 | "评审对目标，不对需求。" 结论对，三理由缺 | 结论对，为什么必须对目标没讲透 |
| 好 | "三理由：需求本身可能错（谁审需求本身）；否则评审和验证重复（ISO 分家塌了）；满足所有需求≠达成目标（评审是唯一抬头看目标的环节）。小林的逐条核对是验证的姿势，对的是需求清单；评审对的是'断链即报废时还能撑到接入冷库'这个目标——应急场景（运输车抛锚 2 小时）没写进需求，逐条核对永远发现不了。" | 三理由 + 冰链目标 + 应急场景全到位，能当场裁小林 |

**产品侧 vs IT侧**：产品组举"M3 逐条核对清单，漏了运输车抛锚 2 小时"；IT 组举"恒信核对需求清单，漏了电子签章变更连需求都不是"。两边同一个病——**只认识中间那个看门人（验证），把评审做成了验证**。

**反转话术**（对应 2.1 + 案例②）：小林的病，和李工是**同一个病的镜像**——李工把"确认"做成"验证"（让业务方当测试员），小林把"评审"做成"验证"（逐条核对需求清单）。病根一模一样：**三个看门人，只认识中间那个。** 评审为什么不能以需求为参照？三个理由，每一条都足以让"以需求为参照"破产：**第一，需求本身可能是错的**——需求是人写的，理解错、互相矛盾、不完整都是常态；如果评审拿"需求"当尺子，就等于默认"需求一定对"，那谁来审需求本身？需求评审的本质，恰恰是审"需求"对"业务目标"是否适宜、充分、有效。**第二，否则评审和验证就重复了**——验证本来就是"以规定需求为参照、确认符合性"，如果评审也以需求为参照，两个术语就是同一件事，ISO 9000 把评审放在 3.11、把验证放在 3.8，这套体系就塌了。**第三，满足所有需求 ≠ 达成目标**——目标错了，需求再对也是白做；评审是整条链上唯一"抬头看目标"的环节。**要求是"路"，目标是"目的地"——评审的价值，就是在低头检查路况之外，抬头看看目的地对不对。** 最失败的评审不是没查出问题，而是把评审做成了验证：只核对"满足需求没有"，从不问"这需求本身对吗"。

**参考答案要点**：三理由见 §2.1；案例②（冰链逐条核对）见"案例进展②"；"路 vs 目的地"见 §2.1。

### Q4 测试全绿，算验证通过吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "测试全绿就是验证通过。" | 正是要翻的——把手段当目的 |
| 中 | "测试只是证据之一。" 结论对，三要素/4% 没接上 | 结论对，验证三要素、96% 那 4% 没讲透 |
| 好 | "验证三要素：对照规定需求+客观证据+认定——测试提供了证据，但没覆盖全部规定需求（96% 意味着 4% 的用例没过或没写，那 4% 对应的需求没有证据）；测试报告是验证的输入，不是验证本身；验证是拿着全部证据（测试、审查、计算、文档评审）对全部规定需求做出认定。" | 三要素 + 4% 无证据 + 输入/本身全到位 |

**产品侧 vs IT侧**：产品组举"整机试验全过，但某个分系统需求（振动下连续）没测"；IT 组举"UAT 通过率 96%，剩 4% 的需求没有证据"。两边同一个病——**把"跑测试"升级成"验证过了"**；符合性分析（第6章）在设计层也是验证，不跑测试也能验证。

**反转话术**（对应 2.2 + 1.6）：测试只是提供客观证据的**手段之一**——ISO 9000 注1 明确说，验证的证据可以是试验结果、变换方法计算、文件评审等。把"测试过了"等同于"验证过了"，是把手段当成了目的。UAT 报告写"测试用例通过率 96%"——这是一份测试结果，是证据的一种；但验证要回答的是"规定需求是否得到满足"，证据要覆盖全部规定需求——**96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足，测试没有给出证据**。验证三要素缺一不可：**对照规定需求（有白纸黑字的尺子吗）、客观证据（有可复核的证据吗）、认定（有明确结论吗）**——"我认为满足"不算验证，"差不多吧"不是验证。测试报告是验证的输入，不是验证本身；验证是拿着全部证据对全部规定需求做出认定。第6章的符合性分析也在这里归位——它和测试一样满足验证三要素，只是证据形式是文档评审：**符合性分析 = 设计层的验证（文档评审式）；测试 = 实现层的验证（试验式）。** 别把验证窄化成"跑测试"，也别把"跑测试"升级成"验证过了"。

**参考答案要点**：验证三要素见 §1.6 + 概念卡；测试只是证据之一见 §2.2；符合性分析归位见 §2.2；"规定需求可验证是推导"见 §1.6。

| 弱 | "业务方都点了，还不算确认？" | 正是要翻的——把参与当确认 |
| 中 | "确认要真实场景。" 结论对，机制浅 | 结论对，为什么"参与≠确认"没讲透 |
| 好 | "确认三要素：真实用户+真实任务+真实场景——李工让业务方在测试环境点一圈，是让业务方当测试员，替测试团队跑用例，对照的还是需求清单；真正的 UAT 是财务用真实对账数据、在真实月底时间点、跑真实月底对账任务——对照的是'月底对账能用'这个预期用途。前一种测的还是需求，后一种测的是场景。" | 真实三件套 + 对照预期用途全到位 |

**反转话术**（对应 2.3 + 1.7）：UAT 不是"让业务方点一遍测试环境"，而是"**真实用户 + 真实任务 + 真实场景**"的确认。确认和验证共享同一套三要素——对照、证据、认定——**唯一的区别在第一个要素**：验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）。"预期用途"不是一句空话，由三样东西构成：**目标用户**（给谁用——法务/财务/业务三方审批人，不是 IT 测试员）、**使用场景/任务**（用来干什么——月底对账、电子签章合同审批、出差手机处理）、**环境与条件**（什么情况下用——月末高峰并发、弱网、休假交接）。章首李工的 UAT 错在哪？他让业务方在测试环境点了一圈——那是**让业务方当测试员，替测试团队跑用例**，对照的还是需求清单。真正的 UAT 是：财务用真实的对账数据、在真实的月底时间点、跑真实的月底对账任务——对照的是"月底对账能用"这个预期用途。**让业务方点测试环境，是把确认做成了验证。**

**参考答案要点**：确认三要素见 §1.7 + 概念卡；预期用途三构成见 §1.7；UAT 真实三件套见 §2.3；案例③（Ada 三问）。

**反转话术**（对应 3.4 + 3.1 + 3.3 + 案例⑤）：三个看门人不是三座孤立的门，它们串起来，是一条需求到上线的**三关**：评审站在开工前抬头看方向、验证站在交付时低头对规格、确认站在交给用户时走进真实场景。**缺任何一关，故事都不一样**：缺评审=需求错了没人发现，白做；缺验证=做错了没人知道，返工；缺确认=做对了也没人用，白做。恒信这次对账事故，Ada 写了六个字：**"验证做了，其余没做。"** 最要紧的那句因果，值得贴在墙上：**只做验证不做确认，隐含需求系统性漏失——测试全过、没人用，不是运气问题，是因果问题。** 而这场复盘本身——Ada 让李工把两条行动项记下来（"变更必须先过评审对目标一关"+"UAT 改真实场景跑"，各配负责人和期限）——**复盘是检测器**：它像传感装置一样例行运行，把偏差显影出来（对不上账、漏了场景、口头变更没记录）。但**复盘发现偏差，不等于治理裁决**：对偏差做裁决（合同编号归属规则要不要定、归谁定）才是治理，那是第13章的事。**只诊断不闭环的复盘，是把同样的错再复一遍。**

**参考答案要点**：三关见 §3.1；缺一关代价表见 §3.1；因果链见 §3.4；复盘=检测器见 §3.3；案例⑤见"案例进展⑤"。

| 好 | "目标具体化配方=对象+时限+可衡量结果：月底对账（上线后第一个月底，对账单与台账逐笔核对一致率 100%、对账时间 ≤2 小时）/法务合规（电子签章合同审批链完整、可追溯）/业务可用（3 个工作日内完成一次合同发起到归档）；通过标准会前定、会后逐条打勾——'能上线'没有可衡量结果，评不了；Ada 摆出目标，立刻发现电子签章变更连需求都不是，是口头承诺。" | 配方 + 三个具体目标 + 通过标准 + 案例①全到位 |

**反转话术**（对应 3.5 + 3.2 + 3.6 + 案例①）：评审对目标有个操作性难题：**目标是抽象的，怎么评？答案是先把目标具体化，再评审。** 目标 = **对象（谁/什么）＋ 时限（何时）＋ 可衡量结果（多少）**。"做出高质量的产品"评不了，"上线后 3 个月内月底对账时间从 3 小时降到 2 小时以内"评得了。评审会开场前先做**检验三问**：通过的标准是什么？达标有没有可观察/可测量的判定？两个人理解不一致看什么裁决？三个都答得上，这个评审有尺子；答不上来，会开了也是白开。**通过标准的正确用法，是随评审邀请一起发出，会前定好、会后逐条打勾。** 而评审不是只做上线前一次——它是洒在整个流程上的门禁：需求评审、设计评审、代码评审、测试评审、发布评审、复盘，**六个把关节点**。为什么洒到全程？问题越早发现修复成本越低——需求阶段的缺陷修复成本是 1，发布后是 30~70 倍。把"把关"从终点挪到全程，把返工成本高的那段堵在源头。顺带磨一个最易混的边界：复盘是第六个节点，但**复盘不是评审**——评审管把关、复盘管改进；复盘是检测器，裁决是治理（第13章）。

**参考答案要点**：目标具体化配方见 §3.5；检验三问见 §3.5；通过标准会前定见 §3.2；六个把关节点见 §3.2；系统性三属性见 §3.6；评审≠复盘见 §3.3；案例①见"案例进展①"。

| 中 | "测试环境和真实环境不一样。" 结论对，三要素/冰山没接上 | 结论对，验证 vs 确认的判据拆解、冰山没讲透 |
| 好 | "验证三要素：李工的 UAT 对照了需求清单、证据是测试通过率——但没覆盖全部规定需求，且让业务方当测试员；确认三要素：真实用户+真实任务+真实场景——李工全缺（造数据/周二下午三个人轮流点/电子签章变更没排进 UAT）；断档 30 秒证明用例全过说明不了上路能过——测试台架稳得像桌面，真实车厢会颠，用例的参照是需求文档，真实场景的参照是'疫苗能不能安全送到'；隐含需求（振动下连续）只有确认兜得住。" | 两场各拆 + 三要素 + 参照差异 + 冰山全到位 |

**产品侧 vs IT侧**：产品组拆"M3——零部件试验/整机低温试验=验证（对规格），真实运输车跑全程=确认（对'疫苗安全送到'）；断档 30 秒台架复现不了"；IT 组拆"恒信——系统测试/UAT=验证（对需求清单），真实对账=确认（对'月底对账能用'）；25 号后合同编号真实对账才第一次出现"。两边同一个结论——**验证在文档的尺子上跑，确认在真实世界的尺子上跑**。

**反转话术**（对应 2.4/2.5 + 案例③④）：两场测试放一起，把验证和确认的差别照得最清楚。恒信：Ada 三问——**月底对账的数据，用的是真实数据还是造的数据？真实月底时间点、真实并发下做的吗？法务的电子签章审批链，业务方验证过"谁审谁签"吗？** 三问全答不上。那次不是确认，是让业务方当测试员，把确认做成了验证。冰链：真实运输车跑全程，**断档 30 秒，台架复现不了**——因为测试环境里没有路；用例的参照是需求文档，真实场景的参照是"疫苗能不能安全送到"。这就是验证和确认的差别：**验证在文档的尺子上跑，确认在真实世界的尺子上跑。** 为什么场景兜得住、文档够不着？因为**真实场景自带答案**——月底对账、运输车颠簸、审批人休假，这些场景不会因为你没写文档就不存在。隐含需求像冰山，水面下占了大半；**验证是量吃水线的尺子（只管浮在水面上的部分），确认是把船开进那片水域的试航（水下撞没撞到，试航时才知道）。** 确认为什么兜得住验证够不着的东西？因为**确认的存在价值恰恰建立在非明示需求上**——如果所有需求都能写下来被验证，确认就不需要存在了。那些写不下来的（顺手、直觉、动效、节奏、惯例）和体验类的（手感要高级、用起来要顺），只有真实使用能裁决。

**参考答案要点**：Ada 三问见案例③；断档 30 秒见案例④；验证射程 vs 确认射程见 §2.4/§2.5；冰山比喻见 §2.5；确认的存在价值见 §3.4。

### Q9 亲手给"评审/验证/确认"各立一条判据（方法时刻 · 规则 15）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 背书上的判据："评审对目标、验证对需求、确认对用途。" | 只答了"是什么"，没做"立判据"这个动作——方法没上手 |
| 中 | 自己立了一条判据（如"确认 = 用户用起来没问题"），但不可检验 / 判据主义三问没走全 | 有判据了，但失效边界/反例没给，量不了 |
| 好 | "给评审立判据：参照是目标（对象+时限+可衡量结果），证据不要求但结论必须记录——团队/结论/记录三属性齐；给验证立判据：参照是规定需求（成文），证据必须是客观证据，结论是'已验证/未验证'；给确认立判据：参照是预期用途（真实用户+真实任务+真实场景），证据来自真实或模拟场景；用它拆了我们的 UAT：只满足验证的证据，不满足确认的三件套——确认没过。" | 三条判据 + 三问 + 当场运用全到位 |

**产品侧 vs IT侧**：产品组立"M3 确认判据——真实运输车跑'出库→运输→到达'全程、温度连续不断链"；IT 组立"恒信确认判据——财务在真实月底、用真实数据、跑真实对账任务、口径一致"。两边立出的判据结构相同——**三把尺子的判据不挑行业，这正是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"**。

**反转话术**（对应方法底座时刻 = 判据主义 + 章末见过→拥有）：这是本单元的**方法时刻**——前面八题在讲三把尺子，这一题让你们亲手给三把尺子各立判据。判据主义三问：**是什么（可检验的定义）、失效边界（什么时候不适用）、反例（能不能被推翻）**。三把尺子各立的可检验判据——**评审**：参照是目标（对象+时限+可衡量结果）、不要求客观证据但结论必须记录（没记录=聊天）；**验证**：参照是规定需求（成文）、必须有客观证据、结论是"已验证/未验证"；**确认**：参照是预期用途（真实用户+真实任务+真实场景）、证据来自真实或模拟场景。注意：**本章是判据主义章，方法时刻题就是判据运用题——判据不是背出来的，是当场立、当场用的。** 跨域：你把三把尺子的判据换到冰链 M3（零部件试验=验证、整机低温试验=验证、真实运输车跑全程=确认）还成立吗？判据不变——同一个概念、两个世界，这正是"概念不挑行业"的现场证明。章末 Ada 那句警告——"混到验收签字那一刻，就是合同纠纷"——现在你能说出全部含义：**验收不是一句话，是三个看门人依次签字：评审签'方向对'，验证签'做对了'，确认签'能用'——三个字都签齐，才轮到'验收通过'四个字。** 能答全四问才算拥有，这三把尺子现在装进你手里了。

**参考答案要点**：判据主义三问见第1章方法论 + §1.4；三把尺子判据见"本章判据"1~5；方法底座时刻（判据主义）见 00-案例设定 §三 第7章行；跨域对照见 00-案例设定 §四 评审/验证/确认行（恒信 UAT ↔ 冰链试验/真实车）；见过→拥有见"章末·认知反转"。

### Q10 给你们的部门做一次"三个看门人体检"

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"要加强评审、要多做测试。" | 没落到三把尺子任何一把，不可检查 |
| 中 | 用一把尺子查出缺口（如"我们 UAT 是让业务方点环境"） | 有判据，但只照了一关 |
| 好 | "按三关逐关过：评审关——通过标准会后现想（不通过，改为会前定+目标具体化）；验证关——口头需求没文档（不通过，先补文档再验证）；确认关——真实对账场景从没测过（不通过，用真实数据/真实时间点/真实任务排一轮 UAT）；最该先补确认关，落到一个动作：两周内用确认三要素设计一次真实确认。" | 三关逐关过 + 最该补的一关 + 一个可检查动作 + 复查机制全到位 |

**反转话术**（对应本章综合应用 + 章末）：这一章的判据不是彼此孤立的——**评审三问测"方向对不对"，验证三要素测"做对了吗"，确认三要素测"做对的东西了吗"，三关串起来是一条需求到上线的接力链。** 找到第一个答不出的关卡就能开工：评审没判据 = 从评审关补起（目标具体化 + 通过标准会前定）；口头需求一堆 = 从验证关补起（先成文再验证）；测试全绿没人用 = 从确认关补起（真实三件套）。**最该先补最不过的一关。** 恒信的李工后来在变更流程里加了一道：任何需求变更，必须先过"评审对目标"这一关，再谈开发；UAT 改成真实场景跑。三个月后，第二个月底，对账在一个小时内对完——不是系统变聪明了，是三个看门人都站在了门口。**能答全四问才算拥有，这三把尺子现在装进你手里了。**

### 金句（书"本章判据"提炼）

- **评审对目标，验证对需求，确认对用途**——方向对不对、做对了吗、做对的东西了吗，三把不同的尺子，谁也替不了谁。
- 评审三问：**适宜性（对症）→ 充分性（够全）→ 有效性（管用）**——方向不对，做得再全也是白费；目标 = 对象 + 时限 + 可衡量结果；通过标准会前定、会后逐条打勾。
- **没记录的评审不算评审，最多算聊天**——团队参与、结果文档化、过程文档化，缺一个就是非系统性评审。
- 验证三要素：**对照规定需求 + 客观证据 + 认定**——测试只是提供证据的手段之一；测试报告是验证的输入，不是验证本身。
- 确认三要素：**真实用户 + 真实任务 + 真实场景**——让业务方点测试环境，是把确认做成了验证。
- **只做验证不做确认 → 隐含需求系统性漏失 → 测试全过、没人用**——不是运气问题，是因果问题。
- 隐含需求像冰山，水面下占了大半；**验证是量吃水线的尺子，确认是把船开进真实水域的试航**——水下撞没撞到，试航时才知道。
- 评审管把关，复盘管改进——**复盘是检测器，复盘触发的裁决才是治理**（第13章）。

## 五、课后作业

1. **书练习（与题卡同源）**：用一张表列出评审、验证、确认的参照、动作、证据、时机四个维度，再用你自己最近一个项目的具体例子各填一行。（书练习 1）

3. **回部门落地**：结合现状，用评审三问、验证三要素、确认三要素三把尺子，给你们最近一次上线/交付做一次"三个看门人体检"——给出最该改进的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪个看门人补上了、哪个还虚着、卡在哪个判据上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次"三个看门人体检"：
>
> 1. **挑对象（先立枢纽）**：选一次最近"验收合格、可以上线"的交付——最自信的，往往是三关缺得最狠的（对照章首李工那句"验收合格，可以上线"）。
> 2. **第一关 · 评审对目标**：那次评审的通过标准，是会后现想的还是会前定的？评审前有没有先把目标摆出来（对象 + 时限 + 可衡量结果）？评的是目标，还是核对需求清单？**话术**："如果只核对需求清单，你会说'全部覆盖，通过'——你的尺子是目标吗？" 没结论、没记录，最多算聊天。
> 3. **第二关 · 验证对需求**：验证三要素齐吗——对照（规定需求成文了吗？口头补的算不算？）／证据（客观证据可复核吗？测试通过率是全量还是抽验？）／认定（有结论吗？"已验证/未验证"，不是"跑完了"）。验证是逐级回收的吗（V 模型：需求从哪一级分解、验证从哪一级回收）？
> 4. **第三关 · 确认对用途**：上线前有没有把产品放进真实场景（真实用户 + 真实任务 + 真实场景 + 真实数据）？UAT 是让业务方当测试员跑用例，还是跑真实业务任务？灰度/仿真算确认，但只算"初步通过"。
> 5. **因果链查漏**：有没有"没写进文档的需求"（口头补的 / 隐含的 / 强制的）？它验证够不着——它有没有被放进确认的场景里？**话术**："25 号之后签的合同算哪个月——这条在你们系统里，谁测过？"
> 6. **复盘闭环**：上线后复盘产出的行动项，有负责人 + 截止日期吗？上轮行动项关闭率 ≥ 80% 吗？复盘显影的偏差，由谁做了裁决（裁决是治理，第13章的棒）？
> 7. **出体检报告**：三关各下结论（通过 / 有条件通过 / 不通过），**最该先补最不过的一关**；最后一条建议照书抄——把"验收"从一句话改回"三个看门人依次签字"。
>
> 卡住时：答不上来的那一关就是最该补的——评审没判据就查第一关；测试全绿但没人用就查第三关（因果链）；口头需求一堆就查第二、三关。不用三关全做完，找到第一个答不出的关卡就能开工。
