## 一、单元导读

### 主题

这一章回答"标尺从哪来"：**需求工程把模糊的诉求变成可靠的依据**。IT 总监说"我们要加强需求管理"——需求乱，是管理没跟上吗？这一章要推翻的正是这个直觉：**"需求管理"不包含"需求开发"**。需求不是被"管"出来的，是被"开发"出来的。管理做得再严，来源没摸清、分析没做透，一样出烂需求。需求开发管"生"（造血）、需求管理管"养"（防腐），两者并列构成需求工程；先立问题域（ConOps），再写条款（SRS）。本章的骨架是：**一个并列**（需求工程 = 需求开发 + 需求管理）→ **一条链**（开发四活动循环 + 管理四活动 + 铰链"批准 → 基线"）→ **三条铁律**（无 CR 不得变更；不分析不得上会；验证通过方可关闭）；**承重柱 = 规定需求**——开发以它为产物、管理以它为对象、验证以它为参照。

### 开场破题（对应章首误解现场）

念出恒信集团合同审批系统项目启动后第三周那场会：IT 总监拍板——"需求最近总是变来变去，合同评审、财务对账、法务条款，改一版崩一版。**我们要加强需求管理。** 谁负责？徐漾，你来。"徐漾是需求分析师，他没接话，先问了三个问题："需求为什么会变？变之前，我们的需求**开发**做到位了吗？——需求调研做了吗？需求分析做了吗？每条需求写得可验证吗？"会议室安静了几秒。IT 总监皱眉："这些不都是'需求管理'的一部分吗？管好需求，自然就都做了。"

让各组表态：如果你坐在这间会议室里，你会不会也点头？大多数人一开始都和 IT 总监一个直觉——**需求乱，是因为管理没跟上；把需求管理做好，需求就稳了。** 这正是这一章要推翻的。

### 本单元要反转的直觉

- **需求管理包含需求开发，管好需求自然就开发好了**（× 并列不是包含；需求是开发出来的，不是管出来的）
- **需求乱 = 管理没跟上；加强需求管理 = 往流程上加东西**（× 恒信一半要补开发的课；先问源头清了吗）
- **客户说了"页面要快一点"，这就是需求**（× 那是明示的需求，还不是规定需求——没成文、不可验证；说了 ≠ 规定）
- **验证和确认是一回事**（× 验证对照规定需求"表述对不对"，确认对照预期用途"是不是用户要的"）
- **需求变更多 = 需求管理没做好**（× 先分清是"需求变了"还是"当初没说清"——一大半是开发欠账）
- **版本文件名改一改（另存为 v2），就是需求管理**（× 版本管理要有基线、变更控制、追溯；改名只做到留档）
- **ConOps 是给运营部门看的故事，跟开发没关系**（× 它是问题域到解空间的桥；跳过直接写 SRS，条款悬空）
- **口头改需求没关系，大家心里有数**（× 口头改需求是最危险的变更形式；没有凭证的变更 = 查无实据的暗改）
- **先写 SRS 条款，上下文后面再补，顺序无妨**（× 先立问题域再写条款；需求规格的问题要到 ConOps 里才看得出来）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 需求工程是什么 + "包含"错在哪（破题·概念本身 + 溯源）→ Q2 整链关系结构（需求工程/需求开发/需求管理/规定需求/验证确认/ConOps/骨架五份，概念关系）→ Q3 说了 vs 规定（真悖论）→ Q4 验证 vs 确认（真悖论）→ Q5 需求变了 vs 当初没说清（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 把"重要合同要审批"改写成规定需求（判据运用·含溯源）→ Q7 欠账二分 + 变更控制三铁律（判据运用·事故）→ Q8 300 条 SRS 悬空——先立问题域还是先写条款（判据运用·真悖论）→ **Q9 方法时刻·先立枢纽 + 转述**（规则 15：亲手写一段 ConOps 场景 + 三五句话把"需求工程"讲给外行，先立问题域再写条款，含跨域变体）→ Q10 回部门需求欠账体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"规定需求/ConOps"是 M3 温控箱——"疫苗从出库到接种全程温度不断链"，运行场景里写"疫苗运输车在高速上抛锚 2 小时"这种应急，直接决定了"断电保温时长"这条硬需求；IT 组的"规定需求/ConOps"是合同审批系统——"法务怎么审、财务怎么对账、业务怎么发起"这段叙事不写，三百条 SRS 条款就悬空。**同一个概念、两个世界、判据不变**，这正是本章"先立问题域，再写条款"不挑行业的现场证明。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"加强需求管理"能解决需求乱吗？——需求工程到底是什么？**
"章首那场会：恒信 IT 总监拍板『需求最近总是变来变去，我们要加强需求管理。徐漾，你来。』徐漾没接话，先问了三句：需求为什么会变？变之前，需求开发做到位了吗？每条需求写得可验证吗？IT 总监反问：这些不都是『需求管理』的一部分吗？管好需求，自然就都做了。这句话错在哪？需求工程、需求开发、需求管理到底是什么关系？"

追问：① 需求开发（生·创造·造血）和需求管理（养·控制·防腐）各管什么？为什么是并列不是包含？② 需求管理四活动（基线/变更/追溯/状态度量）里，变更控制为什么是核心战场？『无 CR 不得变更』堵住的是哪个口子？『改名留档（另存为 v2）』为什么不是版本管理？③ 你们部门说"要加强需求管理"的时候，说的是哪一半——补开发还是补管理？④ 溯源："需求工程"这个词从哪来——标准为什么把需求管理与需求开发分列为**并列**过程域（CMMI：REQM 成熟度 2 级、RD 3 级；IEEE 29148 承袭"开发+管理"二分）？

**Q2｜需求工程这条链什么结构？**
"请给出这条链的关系结构：需求工程 ⊃ 需求开发 + 需求管理（并列）；需求开发：获取 → 分析 → 规格（SRS·规定需求）→ 需求确认（Validation）——循环；需求管理：基线 → 变更 → 追溯 → 状态度量。规定需求在链的什么位置？验证、确认各自对照什么？ConOps 为什么在分析之后、规格之前？"

追问：① 需求开发四活动为什么是循环不是直线？② 验证对照规定需求（表述对不对）、确认对照预期用途（是不是要的）——它们在链上各踩在哪一步？③ 骨架五份（SRS / 需求池 / RTM / 评审报告 / 基线）缺一份会怎样？『批准 → 基线』为什么是需求工程的铰链？

**Q3｜客户说了，就是需求吗？**
"客户在评审会上说：『页面要快一点』『系统要好用』『审批要严谨』——客户说了、领导也说了，这算需求吗？有人说算——客户的话不就是需求吗？这一章说：只算一半，它们还不是规定需求。两个都对吗？什么判据分清『说了』和『规定』？"

追问：① 规定需求 = 成文 + 具体 + 可验证——口头表述为什么对不了账（"快一点"是几秒？"好用"怎么证明？）？② 恒信『重要合同要审批』——『重要』是期望还是需求？不澄清会怎样（把期望当需求 = 只加成本不加质量；把需要漏成期望 = 漏掉命根子需求）？③ 你们最近一次验收扯皮，是不是卡在一条"说了但没规定"的需求上？

**Q4｜验证和确认，为什么要分开？**
"恒信把『合同审批在 5 分钟内完成』写得无可挑剔、测试全过——但用户真正要的是『法务在移动端先审』。这是『写得很对但没人要』。可另一边，有人抱怨：需求是要的，但没法执行。两个失败哪个更常见？验证（verification）和确认（validation）为什么要分开？"

追问：① 验证对照什么、确认对照什么（规定需求 vs 预期用途）？各问什么（表述对不对 vs 是不是用户要的）？② 只验证不确认、只确认不验证各是什么后果？③ 隐含需求为什么是『必须分开验证与确认』最深的原因？

**Q5｜需求总在变，是需求变了还是当初没说清？**
"IT 总监的直觉：需求变来变去 = 需求管理没做好。徐漾翻了三个月变更记录，发现一大半『变更』根本不是需求变了，而是当初就没说清楚——合同评审的触发条件是『重要合同』要审批，但『重要』从没定义过；财务要的『对账报表』从没说清统计口径。所以：需求『总在变』，到底是需求管理的漏洞，还是需求开发的欠账？什么判据分清哪个病、开哪味药？"

追问：① 开发欠账（源头脏）和管理欠账（过程乱）各是什么症状？为什么『先清源（开发）再修渠（管理）』顺序不能反？② 答错了病，药就开错了——章首 IT 总监开的是什么错药？③ 你们团队最近一次"需求又变了"，变的是需求，还是当初没说清？

### 第二组 · 落地与实践

**Q6｜把"重要合同要审批"改写成可验证的规定需求**
"恒信有一条需求：『重要合同要审批』。法务觉得『重要』很清楚，财务觉得该按金额，业务觉得该按期限。把这条改写成可验证的规定需求——用什么判据判断改写成功了？『页面要快一点』呢？"

追问：① 规定需求三要素（成文 + 具体 + 可验证）——『重要』怎么具体化？② 改写后的需求，怎么设计测试证明它？——能设计测试证明 → 规定需求；只能"感觉" → 还不是。③ 你们部门找一条"明示但未规定"的需求，现场改写。④ 溯源："规定需求"从哪来——ISO 9000 为什么把"明示并成文"的那一条从需求三态里单列出来（验证需要一个能对账的稳定参照，口头表述对不了账）？specified ← 拉丁 specificare（明确指明）？

**Q7｜恒信"改一版崩一版"，崩的是哪张单子？**
"恒信『改一版崩一版』。徐漾补了需求基线、建了 CR 流程，六周后变更失控率降了七成——不是需求变少了，是每次变更都留下了痕迹。用欠账二分（开发欠账/管理欠账）诊断恒信：崩的是哪张单子？『无 CR 不得变更，不分析不得上会，验证通过方可关闭』——三铁律各堵住哪个暗改口子？"

追问：① 变更控制闭环（CR → 影响分析 → CCB 评审 → 实施 → 再验证 → 关闭）哪一环最常被跳？跳的代价是什么（任何一环断了，这条变更就成了"查无实据"的暗改）？② 基线是分界线——线左线右各归谁管？『另存为 v2』为什么只做到留档（缺基线/变更控制/追溯三样中的哪样）？③ 你们最近一次需求变更，"从什么变到什么"说得清吗？

**Q8｜三百条 SRS 条款，为什么悬空？**
"恒信第一版 SRS 三个月写了三百条。评审会上法务翻了两页问：『你们写"合同审批通过后自动通知相关方"——哪个相关方？审批链上有几个人？通知不到会怎样？』没人答得上，因为没人写过 ConOps——三百条条款悬在半空。为什么需求规格的问题，往往要到 ConOps 里才看得出来？『先写条款后补故事』为什么顺序反了？"

追问：① ConOps 六部分哪部分是核心（运行场景：正常/异常/应急）？为什么？② ConOps 判据——让一个不熟悉系统的人读完，能画出流程图吗？画不出来，故事没讲清楚。③ 跳过 ConOps 直接写 SRS，等于从什么跳到什么（问题域 → 解空间）？三百条 SRS 里为什么有一半需要改写？④ 徐漾补 ConOps 时，应急这一栏是谁问出来的（业务方黄程："审批人要是离职了，谁接得上？"）、运行支持那一栏是谁点破的（运维玉杰："ConOps 要讲清'系统怎么被用'——运维也是用它的人"）？你们最近一个系统，能写出一段"系统怎么被用"的叙事吗？

**Q9｜亲手写一段 ConOps + 三五句话讲给外行（方法时刻）**
"这一章从头到尾演示的是同一只手——先立枢纽，再填细节（第1章：先立枢纽再填细节）。开篇立『需求工程 = 开发 + 管理』的并列枢纽，ConOps 立『问题域』的枢纽。请亲手做两件事：① 给恒信合同审批系统写一段 ConOps 运行场景的开头（正常流程：一份 200 万的采购合同从发起、法务初审、财务校验、业务终审、签章、归档，标注每个环节的角色）——再反过来判断：为什么先扎进三百条 SRS 条款、不立这个骨架，条款越多越悬空？② 用三五句话把『需求工程』讲给一个完全外行的人——讲到哪卡住，缺口就在哪（转述 = 压缩测试）。"

追问（跨域变体）：① 你把这段 ConOps 换到冰链 M3 温控箱——『疫苗从出库到接种全程温度不断链』，运行场景里写『疫苗运输车在高速上抛锚 2 小时』这种应急，直接决定了『断电保温时长』这条硬需求。判据变没变——先立问题域（ConOps）再写条款（SRS）在硬件世界还成立吗？这说明了什么（概念不挑行业）？② 你转述『需求工程』给外行卡住的那一处，和你写 ConOps 时不确定的那一段，是不是同一个缺口（先立枢纽没立住，条款和讲述都会悬空）？——四问与转述，测的是同一件事。③ 你们上次写需求/写方案，是先立了问题域骨架，还是直接陷进了细节条款？

**Q10｜给你们的部门做一次"需求欠账体检"**
"结合你们部门现状，用欠账二分、规定需求、ConOps 三个判据，给你们最近一次需求/交付做一次体检——给出最该改进的三件事，每个落到一个动作。"

追问：① 三把尺子（能分清"需求变了/当初没说清"吗 / 每条需求能设计测试证明吗 / "系统怎么被用"写出来了吗）先查哪两把？② "加强需求管理"这种话你们部门说过吗——当时补的是开发还是管理？③ 两周后回来报告：哪把尺子测出不合格、补了哪个动作。

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 "加强需求管理"能解决需求乱吗？——需求工程到底是什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "需求乱就是管理没跟上，加强管理就稳了；IT 总监没错。" | 正是要翻的——把"需求管理包含需求开发"当当然 |
| 中 | 能说出"需求工程=开发+管理"，但说不清"并列不是包含"的后果 | 定义是背的，机制没接上——没说清"需求是开发出来的" |
| 好 | "并列不是包含：开发管生（创造·造血）、管理管养（控制·防腐）；把开发包进管理，模糊了'需求是开发出来的，不是管出来的'——恒信一半是开发欠账，加强管理等于给脏水修渠；溯源：CMMI 把 REQM（成熟度 2 级）与 RD（3 级）分列并列过程域、IEEE 29148 承袭二分。" | 定义 + 机制 + 案例 + 溯源全咬合，能当场给 IT 总监处方开反的结论 |

**产品侧 vs IT侧**：产品组举"冰链口头改需求'精度差不多就行'——管理再严也管不住没开发好的需求"；IT 组举"恒信三个月变更记录一大半是当初没说清"。两边都容易把"加强管理"当万能药——**先问源头清了吗**。

**反转话术**（对应 §4.2.1 / §4.2.2 + 章首）：IT 总监那句话错在一个词上——**"需求管理"不包含"需求开发"**。需求工程（Requirements Engineering）是一个总称下的两个子过程，标准里两者是**并列**的（CMMI：需求管理 REQM 与需求开发 RD 分列并列过程域，REQM 成熟度 2 级、RD 3 级；IEEE 29148 同样并列）：**需求开发管"生"**——把需要与期望转化为规定需求（获取、分析、规格、确认），是创造性活动，比喻是"造血"；**需求管理管"养"**——对规定需求进行基线化受控（基线、变更、追溯、状态度量），是控制性活动，比喻是"防腐"。流行说法"广义的需求管理包含需求开发"错在，它把两类本质不同的活动揉成一团——**需求是开发出来的，不是管出来的**。管理再严，来源没摸清、分析没做透，一样出烂需求。章首恒信"改一版崩一版"，如果只加强管理，等于给没有清源的水流修水渠——水还是脏的。**先清源（开发），再修渠（管理），顺序不能反。** 反身一问：你们说"要加强需求管理"的时候，一半说的是"补需求开发的课"。

**参考答案要点**：需求工程定义见 §4.2.1；并列不是包含见 §4.2.2；变更控制核心战场见 §4.2.6；溯源（CMMI/IEEE 并列演化）见 §4.2.2 卡 ②③格。

### Q2 需求工程这条链什么结构？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 把需求开发、需求管理排成一条线（开发 ⊂ 管理） | 关系结构错误——并列被画成包含 |
| 中 | 能说"开发+管理并列"，但规定需求/验证确认/ConOps 位置没接上 | 并列对了，整链锚点缺 |
| 好 | "需求工程 ⊃ 需求开发 + 需求管理（并列）；规定需求在规格（SRS）这一步成为验证的参照；验证对照规定需求、确认对照预期用途；ConOps 在分析之后、规格之前——先立问题域再写条款；批准→基线是铰链；骨架五份任何规模不可省。" | 整链结构 + 每个锚点全到位 |

**产品侧 vs IT侧**：产品组答"M3 的 ConOps=冷链断链叙事，先于温控规格"；IT 组答"合同审批的 ConOps=三方怎么用，先于三百条 SRS"。两边都容易把 ConOps 漏掉——**这条链缺了 ConOps，条款就悬空**。

**反转话术**（对应 §4.2.1/§4.2.4/§4.2.5/§4.2.6/§4.4.2）：需求工程是一棵树不是一条线——**一个并列**：需求开发（生）+ 需求管理（养），两者并列不是包含；**一条链**：需求开发走"获取 → 分析 → 规格 → 需求确认"四活动循环（不是直线——分析中发现缺信息回获取，规格中发现问题回分析；需求天然渐进）；**一个枢纽**：规定需求（本章承重柱）在规格这一步成为"验证的参照"——没有它，验证无从谈起；验证对照规定需求（表述对不对）、确认对照预期用途（是不是要的）；**一个位置判断**：ConOps 在分析之后、规格之前——先讲清系统怎么被用（问题域），才谈得上必须做什么（解空间条款）。需求开发与需求管理的接口咬合在"批准 → 基线"处——**这是整条需求工程的铰链**：批准前需求流动（开发负责），批准后一切变更走 CR（管理负责）。骨架五份（SRS / 需求池 / RTM / 评审报告 / 基线）任何规模项目不可省——没有文档的环节就是不可追溯的环节。

**参考答案要点**：四活动循环见 §4.2.4；规定需求见 §4.2.5、验证确认见 §4.3.2；铰链见 §4.2.6；ConOps 位置见 §4.4.2；骨架五份见 §4.4.5。

### Q3 客户说了，就是需求吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "客户说了就是需求，客户是上帝。" | 正是要翻的——把明示当规定 |
| 中 | "说了不等于规定，但说不清差在哪。" | 结论对，判据缺——没落到"成文+具体+可验证" |
| 好 | "那是明示的需求，还不是规定需求——没成文、没具体、不可验证；验证需要一个能对账的靶子，'快一点'是几秒没法证明；恒信'重要合同要审批'，'重要'不澄清就永远是悬案；把期望当需求=只加成本不加质量，把需要漏成期望=漏命根子需求。" | 三要素 + 对账靶子 + 混用代价全到位 |

**产品侧 vs IT侧**：产品组举"温度'保持稳定'"；IT 组举"页面'要快一点'"。两边都是同一件事——**"说了"只算一半；能设计测试证明才算规定需求**。

**反转话术**（对应 §4.3.1 + §4.2.5 + §4.2.3）："页面要快一点""系统要好用""审批要严谨"——这些话，客户说了、领导也说了，它们算需求吗？**算，但只算一半。** 它们是明示的需求，却还不是**规定需求**（specified requirement）——没成文、没具体、不可验证。验证（verification）需要一个能对账的靶子，口头表述对不了账："快一点"是几秒？"好用"怎么证明？**说了不等于规定：规定需求 = 成文 + 具体 + 可验证。** 这条走廊的判据问句：**一条需求，能设计测试证明吗？能，才是规定需求；只能"感觉"，还不是。** 这也呼应了 §4.2.3 那句"恒信的'重要合同要审批'永远是悬案"——"重要"是期望还是需求？不把它规定成"金额 ≥ 500 万或三年期以上"，它就永远停留在"说了"那一层。混用它们的代价，是需求工程里最贵的一种模糊：把"期望"当"需求"，会造出过度设计（只加成本、不加质量）；把"需要"漏成"期望"，会漏掉命根子需求。

**参考答案要点**：走廊一"需求≠规定需求"见 §4.3.1；规定需求卡见 §4.2.5；术语不混用见 §4.2.3。

### Q4 验证和确认，为什么要分开？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "验证和确认是一回事，都是确认需求没问题。" | 正是要翻的——两把尺子当一把 |
| 中 | "验证看对不对、确认看要不要。" 结论对，机制浅 | "隐含需求是分开的最深原因"没接上 |
| 好 | "验证对照规定需求（表述对不对）、确认对照预期用途（是不是要的）；把需求写得很正确、但完全不是用户要的，是需求开发最常见的失败——隐含需求没显性化，验证照不到它，只有确认（真实场景）兜得住。" | 对照 + 失败模式 + 隐含需求机制全到位 |

**产品侧 vs IT侧**：产品组举"温控精度写得很对，但用户要的是断链告警"；IT 组举"5 分钟内审批写得很对，但用户要的是移动端先审"。两边都是同一件事——**写得对，不等于写的是要的**。

**反转话术**（对应 §4.2.5 / §4.3.2 + 案例进展②）：需求开发里最容易混的一对词：**验证（verification）**对照**规定需求**，问"表述对不对"；**确认（validation）**对照**预期用途**，问"是不是用户要的"。两者必须分开，因为**把需求写得很正确、但完全不是用户要的东西，是需求开发最常见的失败**——你把"合同审批在 5 分钟内完成"写得无可挑剔，但用户真正要的是"法务在移动端先审"：写得对，不等于写的是要的。**只验证不确认，需求可能写得很漂亮、但根本没人要；只确认不验证，需求可能是用户要的、但没法执行。两道关，缺一不可。** 为什么这是"必须分开"的最深原因？——**隐含需求**。恒信财务那句"合同如果 25 号之后才签，能不能算到下个月"，是一条隐含需求，没人把它写进任何需求文档——它"通常隐含"，是行业惯例默认。隐含需求不会自己开口；没显性化，验证（对照规定需求）就照不到它——规定需求里根本没这一条；只有确认（真实场景）兜得住它。第8章会全展开，这里先立住这条边。

**参考答案要点**：验证/确认对照见 §4.3.2；隐含需求见案例进展②。

### Q5 需求总在变，是需求变了还是当初没说清？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "需求变更多就是管理没做好，赶紧上管理工具。" | 正是要翻的——把开发欠账当管理漏洞 |
| 中 | "一大半是当初没说清。" 结论对，判据缺 | "先清源再修渠"的顺序机制没出来 |
| 好 | "欠账二分：开发欠账（源头脏：没调研/没分析/没写可验证规格）和管理欠账（过程乱：没基线/变更失控/查无实据）是两种病；需求总在变先分清病——一大半'变更'是当初没说清（开发欠账）；先清源（开发）再修渠（管理），顺序不能反；IT 总监只修渠=给脏水修渠。" | 二分 + 顺序 + 错药定性全到位 |

**产品侧 vs IT侧**：产品组举"冰链'精度差不多就行'口头变更——偷换验证靶子"；IT 组举"恒信'重要合同'从没定义过"。两边都要翻"需求变更多=管理没做好"——**答错了病，药就开错了**。

**反转话术**（对应 §4.3.3 + 案例进展①）：恒信"改一版崩一版"，IT 总监的直觉是"需求管理没做好"。徐漾翻了三个月变更记录，发现一大半根本不是"需求变了"，而是**当初就没说清楚**——合同评审的触发条件是"重要合同"要审批，但"重要"从没定义过；财务要的"对账报表"从没说清统计口径。这条走廊钉死的是一条诊断判据：**当需求"总在变"，先别急着上管理手段——先分清它是哪个病。** 开发欠账是"源头脏"，再好的管理只是把脏水存进干净的罐子；管理欠账是"过程乱"，再好的开发也会被无序变更慢慢腐蚀。**先清源（开发），再修渠（管理），顺序不能反。** 判据问句：**最近这次需求混乱，是"当初没说清"（开发欠账）还是"定了之后没人管"（管理欠账）？** 答错了病，药就开错了——这正是章首 IT 总监的错误处方：只加强管理，等于给没有清源的水流修水渠，水还是脏的。

**参考答案要点**：欠账二分见 §4.3.3；两张单子见案例进展①；先清源再修渠见 §4.2.2。

### Q6 把"重要合同要审批"改写成可验证的规定需求

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "重要合同要审批——已经说得很清楚了，直接进规格。" | 正是要翻的——"重要"没定义，无歧义/可验证都不过 |
| 中 | "改成'金额≥500 万或三年期以上须审批'。" 改写对了，判据没说 | 动作对了，判据（能设计测试证明吗）没点出 |
| 好 | "用规定需求三要素改写：成文（写进 SRS）+ 具体（金额 ≥ 500 万或三年期以上）+ 可验证（设计测试：任取一条金额 600 万合同，必须走审批流）；判据——能设计测试证明 → 规定需求，只能'感觉' → 还不是；溯源——ISO 9000 把'明示并成文'单列，因为验证需要能对账的稳定参照（specified ← specificare 明确指明）。" | 三要素 + 测试设计 + 判据 + 溯源全到位 |

**产品侧 vs IT侧**：产品组改写"M3 温度'保持稳定'"→"'2℃~8℃ 全链路，超温 1 分钟内告警'"；IT 组改写"页面要快一点"。两边都是同一把尺子——**改写不是换词，是让验证有靶子**。

**反转话术**（对应 §4.3.1 / §4.2.5 + 练习 2）："重要合同要审批"——"重要"是期望还是需求？法务觉得清楚、财务觉得按金额、业务觉得按期限，这正是**无歧义**的反面。用规定需求三要素改写：**成文**（写进 SRS，不是停在口头）、**具体**（"重要"规定成"金额 ≥ 500 万或三年期以上"）、**可验证**（能设计测试证明：任取一条金额 600 万的合同，它必须走审批流——这叫能设计测试证明）。**判据问句：一条需求能设计测试证明吗？能，才是规定需求；只能"感觉"，还不是。** "页面要快一点"同理——改写成"首页在 4G 网络下 2 秒内加载完成，在负载均衡器测 p95 时延"。SRS 里禁止"快速/大约/友好"这类不可验证表述，正是"无歧义 + 可验证"的检查项。恒信的"重要合同要审批"为什么烂？因为它违反"无歧义"（"重要"有两种以上理解）和"可验证"（没法设计测试证明）。规定需求这条承重柱的**溯源**：ISO 9000 把需求按"明示的、通常隐含的、必须履行的"三态并立，"明示并成文"的一条被单列——因为验证需要一个能对账的稳定参照，口头表述对不了账；specified ← 拉丁 specificare（明确指明）。

**参考答案要点**：规定需求三要素见 §4.2.5/§4.3.1；质量六性"无歧义+可验证"见 §4.4.4；练习 2（明示但未规定→可验证改写）。

### Q7 恒信"改一版崩一版"，崩的是哪张单子？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "崩在版本文件名——把 v2、v3、真最终版理清楚就好了。" | 正是要翻的——改名留档 ≠ 版本管理 |
| 中 | "补基线、走 CR。" 动作对，二分和三铁律没接上 | 单子分不清，三铁律各堵哪个口没说 |
| 好 | "崩的既有开发欠账（'重要'没说清）也有管理欠账（没基线、变更失控）；徐漾补基线=补管理欠账；三铁律各堵一口：无 CR 不得变更=堵口头暗改、不分析不得上会=堵拍脑袋上会、验证通过方可关闭=堵改完不验收；'另存为 v2'只做到留档，缺基线/变更控制/追溯三样。" | 二分 + 三铁律 + 版本管理判据全到位 |

**产品侧 vs IT侧**：产品组举"冰链'精度差不多就行'口头变更——验证靶子当场偷换"；IT 组举"恒信需求散落六个文件、RTM 没法建"。两边都是同一件事——**没有凭证的变更 = 查无实据的暗改**。

**反转话术**（对应 §4.2.6 / §4.3.4 + 案例进展③）：恒信"改一版崩一版"——崩的是哪张单子？**两张都崩**：开发欠账（"重要"没说清——这是"当初没说清"，管理管不了）＋管理欠账（没基线、变更失控、查无实据——这是"定了之后没人管"）。小白是开发，她接口写到一半，对着六个文件名发愁："照着哪个版本写？"玉杰是运维，他抽出发布记录抖了抖："文件名记不下谁批的、为什么改，我们发布认的是可复现——哪个包配哪套环境参数，能复现出上线时的运行形态。你们这六个文件，连哪一版是基线都对不上。"万辉终于承认："我们不是需求变太多，是这几份需求文件从来没立过基线。"徐漾给这份需求立了第一版基线、之后每个变更走 CR 流程，六周后变更失控率降了七成——**不是需求变少了，是每次变更都留下了痕迹**。变更控制三铁律各堵一个口子：**无 CR 不得变更**——堵口头暗改（没有凭证的变更）；**不分析不得上会**——堵拍脑袋上会（不分析影响就评审）；**验证通过方可关闭**——堵改完不验收（不回到新的规定需求）。闭环是 CR → 影响分析（经 RTM 反查）→ CCB 评审 → 实施变更 → 再验证 → 关闭——**任何一环断了，这条变更就成了"查无实据"的暗改**。而"另存为 v2"只做到了"留档"——留下了每一版快照，却没回答三件事：哪一版是权威基线？这次改为什么、谁批的？这条需求从哪来、影响谁？**没有基线，每一次变更都说不清"从什么变到什么"。** 判据问句：**这次"版本管理"，能回答"哪一版是基线、这次为什么改、从什么变到什么"吗？答不上来，就只是改名。**

**参考答案要点**：变更控制闭环与三铁律见 §4.2.6；基线是分界线见 §4.2.6；走廊四"改名留档≠版本管理"见 §4.3.4；案例进展③（六周降七成）。

| 答案分级 | 形态 | 讲师判读 |

| 弱 | "三百条写得多，规格肯定全。" | 正是要翻的——条款越多越悬空，缺上下文 |
| 中 | "该写 ConOps。" 结论对，机制缺 | "问题域→解空间""条款要挂上骨架"没接上 |
| 好 | "ConOps 回答'系统怎么被用'，是 SRS 的上下文；法务/财务/业务怎么用这套系统审批一份合同，这段叙事从没写成文档，三百条条款每一条都缺上下文；跳过 ConOps 直接写 SRS=从问题域跳到解空间；写完 ConOps，三百条有一半需要改写——先写条款后补故事，顺序反了；应急栏是黄程问出来的、运行支持栏是玉杰点破的（运维也是用它的人）。" | 上下文 + 问题域解空间 + 顺序反转 + 全员戏份全到位 |

**产品侧 vs IT侧**：产品组举"冰链 ConOps='疫苗全程温度不断链'，抛锚 2 小时的应急直接决定断电保温时长"；IT 组举"恒信 ConOps=三方怎么用，缺了就悬空"。两边都是同一件事——**ConOps 写不出来的场景，就是将来要出事故的场景**。

**反转话术**（对应 §4.4.1 / §4.4.2 + 案例进展④）：SRS 回答"系统必须做什么"，但在这之前，还有一个更根本的问题：**系统怎么被用？** 法务怎么审合同、财务怎么对账、业务怎么发起审批——这些"怎么被用"的叙事，是 SRS 的上下文。没有它，SRS 的每一条都像悬空条款——你知道要做什么，但不知道为什么、为谁、在什么场景下。**运行概念（ConOps）就是回答"系统怎么被用"的那份文档**（IEEE 1362）——需求工程里唯一一份"叙事性"的正式输出。它的位置在**分析之后、规格之前**：ConOps 的完整定稿必须建立在已经摸清需要的基础上。**跳过 ConOps 直接写 SRS，等于从"问题域"直接跳到"解空间"，中间的桥没了。** 恒信的三百条 SRS 为什么悬空？因为没人写过 ConOps——"法务、财务、业务三方怎么用这套系统审批一份合同"这个叙事，从没被写成过文档。徐漾花了三周补 ConOps：审批链的细节，业务方的黄程陪着一段段对——"审批人要是离职了，谁接得上？"应急这一栏就是他问出来的；写到"运行支持"那一栏去问运维玉杰——"ConOps 要讲清'系统怎么被用'——运维也是用它的人"，运行支持栏就是他点破的。写完，三百条 SRS 里有一半需要改写——**因为先写条款后补故事，顺序反了。需求规格的问题，往往要到 ConOps 里才看得出来。** ConOps 六部分里运行场景是核心（正常/异常/应急）；判据：让一个不熟悉系统的人读完，能画出流程图吗？画得出来，ConOps 合格；画不出来，故事没讲清楚。这正是第1章"先立枢纽再填细节"的反面——**陷细节而不立枢纽（LeafToHub）**：ConOps 是问题域的枢纽骨架，SRS 条款是挂上去的细节；先扎进条款、不立骨架，条款越多越悬空。

**参考答案要点**：ConOps 定义见 §4.4.1；位置见 §4.4.2；六部分与运行场景见 §4.4.3；案例进展④（三百条 SRS / 一半需改写 / 黄程应急 / 玉杰运行支持）。

**反转话术**（对应方法底座时刻 = 先立枢纽 vs 陷细节 + §4.4.2/§4.4.3 + 案例进展④）：这是本单元的**方法时刻**——前面八题在讲"需求工程是什么"，这一题让你们亲手做本章的方法底座时刻：**先立枢纽 vs 陷细节（LeafToHub）**，外加 v2.1 规则 15 的**转述（压缩测试）**形态。这一章从头到尾演示的是同一只手——开篇立"需求工程=开发+管理"的并列枢纽，ConOps 立"问题域"的枢纽，四条走廊一条条磨边——都在对"陷细节而不立枢纽"说不。第一件事，你亲手给恒信写一段 ConOps 运行场景：**一份 200 万的采购合同从发起、法务初审、财务校验、业务终审、签章、归档**——标注每个环节的角色（法务审条款、财务校金额账期、业务审审批流）、异常（法务驳回怎么办、财务校验不过怎么办）、应急（审批人离职怎么办）。当初徐漾补 ConOps 时，应急栏是黄程那句"审批人要是离职了，谁接得上？"问出来的、运行支持栏是玉杰"运维也是用它的人"点破的。写完反过来判断：为什么先扎进三百条 SRS 条款、不立这个骨架，条款越多越悬空？——**因为 ConOps 是问题域的枢纽骨架，SRS 条款是挂上去的细节；先扎进条款、不立骨架，条款越多越悬空**（恒信三百条 SRS 有一半需要改写，就是顺序反了的代价）。第二件事，**转述压缩测试**：用三五句话把"需求工程"讲给一个完全外行的人——讲不清 = 结构没成型（"开发+管理并列"这一层没压出来），卡壳处 = 边界缺口。**四问与转述，测的是同一件事**——你转述卡住的那一处，和你写 ConOps 时不确定的那一段，是同一个缺口（先立枢纽没立住）。**跨域变体**：你写的这段 ConOps 换到冰链 M3——"疫苗从出库到接种全程温度不断链"，运行场景里写"疫苗运输车在高速上抛锚 2 小时"这种应急，直接决定了"断电保温时长"这条硬需求。**判据变没变？——没变。先立问题域（ConOps）再写条款（SRS）在硬件世界一样成立。同一个概念、两个世界，这正是"概念不挑行业"的现场证明。** 反身：你们上次写需求/写方案，是先立了问题域骨架，还是直接陷进了细节条款？——**先立枢纽是见过，会亲手立 + 会转述讲清，才是拥有。**

**参考答案要点**：方法底座时刻（先立枢纽 vs 陷细节）见 00-案例设定 §三 第4章行 / §十 素材包；ConOps 位置与判据见 §4.4.2/§4.4.3；案例进展④（黄程应急 / 玉杰运行支持）；转述=压缩测试见第1章 §1.4.3；跨域对照见 00-案例设定 §四 规定需求/需求工程行（恒信 ConOps 缺失 ↔ 冰链口头改需求）。

## 四、知识卡片

### 一页图（书"本章概念总图"）

```
需求工程 = 需求开发（生·造血）+ 需求管理（养·防腐）—— 并列，不是包含
需求开发：获取 → 分析 → 规格（SRS·规定需求）→ 需求确认（Validation）——循环
需求管理：基线 → 变更控制（CR→影响分析→CCB→再验证→关闭）→ 追溯 → 状态度量；无 CR 不得变更
ConOps：分析之后、规格之前 —— 先立问题域，再写条款（LeafToHub：先立枢纽 vs 陷细节）
规定需求 = 验证的参照；验证对照规定需求，确认对照预期用途
需求质量六性 = 完整·一致·无歧义·可验证·可追溯·有优先级
骨架五份：SRS · 需求池 · RTM · 评审报告 · 基线
四条边界走廊：需求≠规定需求 / 验证≠确认 / 需求变了≠当初没说清 / 改名留档≠版本管理
```

### 金句（书"本章判据"提炼）

- **需求工程 = 需求开发 + 需求管理，并列，不是包含**——开发管"生"（创造·造血），管理管"养"（控制·防腐）；**需求是开发出来的，不是管出来的。**
- **规定需求 = 验证的参照**（本章承重柱）——被明示的、成文的需求；**能设计测试证明 → 是规定需求；只能"感觉" → 还不是**（说了 ≠ 规定）。
- **验证对照规定需求，确认对照预期用途**——"写对了吗" vs "是要的吗"，必须分开；**两道关缺一不可**。
- **欠账二分**——需求"总在变"时，先分清是"需求变了"还是"当初没说清"；**先清源（开发）再修渠（管理），顺序不能反。**
- **ConOps 在分析之后、规格之前**——**先讲清系统怎么被用（问题域），才谈得上必须做什么（解空间条款）**；ConOps 讲"故事"，SRS 讲"条款"。
- **无 CR 不得变更，不分析不得上会，验证通过方可关闭**——变更控制三铁律。
- **改名留档 ≠ 版本管理**——版本管理要有基线、变更控制、追溯；**没有基线，变更就不可言说。**
- **骨架五份不可省**：SRS、需求池、RTM、评审报告、基线——**没有文档的环节，就是不可追溯的环节。**
- 方法底座时刻：**先立枢纽，再填细节**——ConOps 立问题域、SRS 挂条款；**三五句话讲给外行讲不清 = 枢纽没立住**（转述 = 压缩测试）。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次"需求欠账体检 + ConOps 补桥 + 转述压缩测试"：
>
> 1. **挑一次需求混乱（先立枢纽）**：选一次"最近需求变来变去 / 改一版崩一版 / 验收扯皮"的事件——症状最像"管理问题"的，往往是"开发欠账"潜伏最深的。**话术**："我们拿最近一次'又改了'来拆。"
> 2. **诊断一 · 欠账二分（先清源再修渠）**：翻最近的变更记录 / 验收记录——每条"变更"是"需求变了"（管理欠账：没基线、变更失控、查无实据）还是"当初没说清"（开发欠账：没调研、没分析、没写可验证规格）？**话术**："这条是需求真的变了，还是当初就没说清？"答错了病，药就开错了。
> 3. **诊断二 · 无来源需求排查**：把需求池 / 需求清单过一遍——每条需求答得出"从哪来"吗？**判据**："无来源需求不得入需求池"。**话术**："这条需求是谁、在什么场景下提的？"
> 4. **改写一条"明示但未规定"的需求**：挑一条"说了但不可验证"的（如"要快一点""要严谨""重要合同要审批"），用规定需求三要素改写（成文 + 具体 + 可验证），并设计一条测试证明它。**话术**："能设计测试证明吗？能，才是规定需求；只能'感觉'，还不是。"
> 5. **诊断三 · ConOps 补桥（先立问题域再写条款）**：这个系统"怎么被用"写成故事了吗？没有 → 补一段运行场景（正常 / 异常 / 应急各一个）；有 → 让一个不熟悉系统的人读，能画出流程图吗？**话术**："法务怎么审、财务怎么对账、业务怎么发起——这段叙事写出来了吗？让业务方像恒信黄程那样陪你一段段对——'审批人要是离职了，谁接得上？'应急这一栏就是问出来的；再问运维，像玉杰点破的那样——'ConOps 要讲清系统怎么被用，运维也是用它的人。'"ConOps 写不出来的场景，就是将来要出事故的场景。
> 6. **转述压缩测试**：把"需求工程"或你们最常用的那个需求词，用三五句话讲给一个完全外行的人——讲到哪卡住，缺口在哪。**话术**："用三句话讲给我这个外行听：'需求工程是干嘛的？'"讲不清 = 先立枢纽没立住（"开发+管理并列"这一层压不出来）。四问与转述，测的是同一件事。
> 7. **检查需求管理四活动**：基线在哪？变更走 CR 吗？RTM 建了吗？**判据**：无 CR 不得变更；改名留档 ≠ 版本管理。**话术**："最近一次变更，'从什么变到什么'说得清吗？"
> 8. **出报告**：三件事（一件补开发、一件补管理、一件立 ConOps），每个落到可检查动作；两周后回来报告。
>
> 卡住时：答不上来的那一项就是最该补的——"这条需求从哪来"答不上 = 获取欠账；"能设计测试证明吗"答不上 = 还不是规定需求；"系统怎么被用写出来了吗"答不上 = ConOps 缺桥；转述卡壳处 = 枢纽没立住。不必八步全做完，找到第一个答不出的步骤就能开工。
