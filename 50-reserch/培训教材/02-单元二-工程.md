## 1. 单元导读

**主题**：工程是什么、不是什么；工程与手艺/科学/艺术的区别；系统化 ≠ 机械化；系统工程与工程系统；工程师需要什么能力。这一单元回答全书最基础的问题：**我们到底在做什么。**

**开场破题（请对此发表意见）**：念恒信季度会那场：架构师李工站在投影前，"各位，我们敏捷转型成功了。双周迭代、CI/CD 全绿、自动化测试覆盖 80%。**我们已经是工程化团队了。**"会议室鼓掌。只有需求分析师 Ada 低声问了一句："那……上个月上线那次事故，是为什么？"李工说："那是人手不够，临时赶工。跟工程化没关系。"**先让两组表态：李工的团队，是工程，还是不是？给出你们的判据。**

**本单元要反转的三个直觉**：

1. 「用了敏捷 + CI/CD + 测试 = 在做软件工程」——**错**。敏捷和 CI/CD 只覆盖工程四层里的两层。
2. 「系统化 = 有算法、机械化执行」——**错**。系统化是"有章法的判断"；自动化不是减少判断，是把判断提纯。
3. 「系统上线了 = 工程成功 / 工程师头衔 = 在做工程」——**错**。技术系统 ≠ 工程系统；头衔不定义工程师，能力才定义。

**本轮 7 题的内在逻辑**（**三轮打磨：每题靶心从"书的假断言"升级为"真悖论"——两个都对的东西打架，必须靠判据自己和解；追问链每一问自己就是陷阱**）：Q1 破题（判工程——**"流程完备=工程"这个判据站不住**；"人手不够"与"悄悄牺牲"怎么区分；判断"是不是工程"这个动作本身要工程化）→ Q2 试金石（**"可复现=工程极致"错**——纯可复现是算法；可复现与判断的价值打架，只有一种和解）→ Q3 价值层（**三大事故原因题面自证**——泰坦尼克/挑战者/737 MAX 一句话原因给全；共性=做的时候没守住、发生在价值层、该层无现成检查点；四层齐了也出错→工程目标=错误可见）→ Q4 系统化（**自动化不是减少判断，是把判断提纯**；自动化消灭的不是事故，是人阻止事故的能力——单向门）→ Q5 元工程（**恒信三模块集成失败**——每个部件都对、系统为什么对不上？缝=部件与部件之间，是第1章词汇病在系统级重演；系统工程不造部件、产出隐形；价值靠机制证明、不靠结果）→ Q6 工程系统（**"被用起来"验收的是组织变革，不是产品**；"没人用"=产品问题还是变革问题，工程系统自己答不了）→ Q7 工程师（**能力不是中性的——④定义能力的方向**；招聘从不考的那项最致命）。

## 2. 题卡（打印分发）

> **答题要求**：组内讨论 25 分钟，把答案写在便签/白板上。每题答案不超过 5 行。每组选派一人上台讲解（4–5 分钟）。允许观点不同，但必须给出理由。

**Q1（破题·先表态 + 追问链）** 恒信 IT 部上了敏捷、CI/CD 全绿、自动化测试覆盖 80%，季度会上李工宣布"我们已经是工程化团队了"。上个月合同审批系统月末高峰宕机 40 分钟——容量评估被砍了，没有评审、没有风险登记、没有签字。李工说："那是人手不够，临时赶工，跟工程化没关系。"有人主张："判断一个团队是不是工程，就看流程——流程完备、工具齐全、测试覆盖高，就是工程；出了事故也不能说它不是。"**请先表态："流程完备 = 工程"，这个判据站得住吗？**然后：①"人手不够"这个理由，在什么意义上是真相、在什么意义上是价值层失守的遮羞布？——怎么区分"客观原因"和"悄悄牺牲"？（提示不够用：想三条可检验的标准）②反直觉：恒信的 CI/CD 靠张三三条隐藏命令、李四的环境变量——这算"流程完备"还是"手艺换了载体"？用试金石测：换三个人来运维，能一样跑吗？③连"我们已经是工程化团队了"这个宣告本身，是不是工程行为？——它有没有判据、记录、评审？"判断工程"这个动作，本身要不要工程化？

**Q2（先表态 + 追问链）** 老周做了十五年温控产品，车间里没有一份完整的测试方案，但他"心里有数"——哪个批次容易出问题、哪种工况要降额、哪家供应商的电容不可靠，全在脑子里。有人推论："试金石说'换个人也能同等交付'才是工程。那就把一切流程都写成文档、做成算法，完全可复现、不靠任何人——这才是工程的极致。"**请先表态：这个推论对还是错？**然后：①一个完全确定性的流程（同输入同输出）是工程吗？——不是，它是算法。追问：如果"可复现"就够了，工程四要素里的"判断创造"为什么不能删掉？②悖论：工程追求"换个人也能交付"，可如果换个人也能交付，那个人的价值是什么？——"追求可复现"和"保留不可复现的判断"，这两个方向打架吗？怎么和解？③老周判断顶配、缺可复现（缺⑥）；李工方法在、判断是坏的（先上再说）。追问：如果 AI 把所有判断都写成规则——那时还需要工程师吗？不需要了，那说明什么？

**Q3（先表态 + 追问链）** 三起著名事故，先看原因——**泰坦尼克**号称"不沉之船"，救生艇数量按"不会沉"的假设配置，为了豪华和成本牺牲安全裕量；**挑战者号**，O 形环在低温下失效，工程师反对发射，管理者为了发射窗口把风险"合理化"；**737 MAX**，MCAS 自动防失速系统有设计缺陷，在认证压力下被轻描淡写，为了市场让安全需求让位。三支团队流程都相当完备。有人说："这三起事故证明流程没有用——流程再完备，该出事还是出事。"**请先表态：这个结论对还是错？**然后：①三起事故的共性，是"不会做"，还是"做的时候没守住"？——它们缺的是"技术"，还是"关键时候不让步"？追问：如果只是"不会做"，为什么三起事故都是同一类原因？②"做的时候没守住"发生在哪一层？——工程科学、方法论、工具实践有现成的检查点（CI、测试、评审），价值与伦理有吗？追问：流程完备会不会让失守更隐蔽——大家都以为"流程这么全，不会有问题"？③反直觉：四层都齐了，还会出事吗？——也会。那四层齐了降低的是"出错概率"，还是"错误被掩盖的概率"？追问：工程的目标是"零错误"还是"错误可见"？怎么检验——事后能不能回答四个问题（改了什么 / 为什么 / 影响谁 / 怎么验证）？

**Q4（先表态 + 追问链）** 有人建议把发布流程完全自动化、固化成算法，"机器不会犯错，也不用靠人了"。有人说："自动化程度越高，系统越安全。"**请先表态：这句话对还是错？**然后：①算法不需要判断，工程方法每一步都留判断——把"阈值设多少、异常怎么处置"也交给机器，机器知道"为什么这个阈值"吗？换场景会怎样？这缺了四层里的哪一层？②反直觉：自动化不是减少判断，是把判断提纯——机器接走执行，人接住的全是最难的判断。追问：一个全自动发布系统，人还剩下什么活？——剩下的是"不用判断"，还是"判断密度最高"？③悖论：737 MAX 的 MCAS 把失速判断交给系统——自动化消灭的是事故，还是**人阻止事故的能力**？追问：自动化是不是单向门——出问题时，还有没有"手动接管"的退路？全自动的终点是什么？

**Q5（先表态 + 追问链）** 恒信合同审批系统：法务模块、财务模块、业务模块，各自都做得很好——每个模块都有测试、都通过验收、都符合各自的需求文档。集成上线那天，出事了：法务说"合同状态"是"审批到哪一步"，财务说"合同状态"是"钱到没到账"——同一份合同，同一个词，两套定义；审批流跨部门还有断点没人管。有人说："每个部件都做对了，系统凭什么出问题？一定是某个部件没做好。"**请先表态：这句话对还是错？**然后：①每个模块都对，系统为什么对不上？——问题出在哪个"部件"身上，还是"部件与部件之间"？"合同状态"一个词、两套定义，这个现象在第1章叫什么？②系统工程"造部件"吗？——不造。那它管什么？它的"产品"是什么（接口契约 / 集成方案 / 系统级验证方案）？追问：为什么这些看不见摸不着的东西，决定系统能不能转？③有人说："系统工程不造部件、看不到成果，它到底做了什么？"——追问：系统工程的价值靠什么被证明？"没出事"够不够？（结果分不清运气和工程）——不靠结果，靠什么（接口契约写没写、集成方案测没测、追溯记录有没有）？

**Q6（先表态 + 追问链）** 恒信合同审批系统上线了：服务器跑起来了、模块全部上线。李工说："我们成功了。"有人说："判断成不成功，就看系统有没有被用起来——被用起来就是成功。"也有人说："按这个标准，那些'没人用但技术上完美'的系统就全盘失败了——可没人用，未必是系统的错，可能是人的问题、变革的问题。"**请先表态：'被用起来'作为工程系统的验收标准，公不公平？**然后：①按"技术系统"看，它上线了；按"工程系统"看——法务还在线下签、财务还是手工台账、业务还走邮件——缺的是"设备"还是"人/流程/组织"？"被用起来"怎么设可检验的验收条款（电子签比例≥X% / 台账迁移 / 业务走线上）？②反直觉：一个"上线了没人用"的系统，和"根本不该建"的系统，怎么区分？——是产品问题（不好用），还是变革问题（没推动）？追问：这个区分，工程系统能不能独立回答？它还需要什么？③"上线"是终点还是起点？——INCOSE 说工程系统要被实现、**使用、退役**。追问：恒信十年前的纸质台账怎么迁入？退役时数据怎么归档？——这些"技术系统"不会问、"工程系统"必须答的问题，说明了什么？

**Q7（先表态 + 选边 + 追问链）** 老周（手艺顶配、判断全在脑子里、请两周假产线就停）和李工（流程齐全、却为进度砍了容量评估、出事归咎人手不够）——**直觉上谁更配得上"工程师"？先表态，不许犹豫。**然后：①老周缺哪两项能力？李工缺哪两项？追问："经验丰富"是能力，"可复现"是什么？②反直觉：一个①③⑤顶配、④为零的工程师，是"更强"还是"更危险"？——**能力是中性的吗？** 追问：④（职业伦理）和①（科学素养）是独立的，还是能力的意义由④定义？737 MAX 里缺的是"会算的工程师"，还是"守住底线的工程师"？③六项能力里，招聘几乎从不考哪一项？——为什么偏偏是最致命的那项不被测？工程化的目标是什么？怎么让老周和李工"合体"（具体第一步）？

## 3. 点评要点·讲师版

### Q1　给恒信做工程体检（破题）

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"流程完备 = 工程" | 把判据停在最表面——正踩章首李工的病 |
| 中：说"不算，因为出了事故" | 方向对，但判据是"事故"不是"缺层/可检验" |
| 好："人手不够"要用三条可检验标准区分客观原因与悄悄牺牲；CI/CD 靠隐藏命令 = 手艺换载体；判断"是不是工程"本身要工程化（可检验+记录+评审） | 反直觉三层全中 |

**产品侧 vs IT侧**：产品组可能说"那不就是样机过了就宣布成功吗"（提前用了第5章的话），IT 组说"系统上线了当然算工程"。两边其实都缺"工程系统"的验收参照——Q6 会收。

**反转话术**：
> "'流程完备 = 工程'——这个判据最诱人，也最不可靠。**恒信的 CI/CD 靠张三三条隐藏命令、李四的环境变量，流程清单上写满了'已自动化'，可换三个人来运维就趴窝——这是工程还是手艺换了载体？试金石一测就倒。** 而'人手不够'是最精致的遮羞布：人手不够可以是真的，也可以是把容量评估悄悄砍掉的理由。**怎么区分客观原因和悄悄牺牲？看三条：相关方知不知情、有没有评审、有没有记录。** 没有人会为'人手不够'留记录，但价值层失守恰恰发生在'没有记录'的地方。最后是递归那一刀：连'我们已经是工程化团队了'这个宣告，都没有判据、没有记录、没有评审——**判断一个团队是不是工程，这个动作本身也要工程化。**"

**参考答案要点**（书 §3.3~3.4、案例进展①②）：四层缺层后果表；价值层一票否决；"悄悄牺牲"=没有让任何相关方知情（案例进展②）；"工具不会自动把人从手艺变成工程，可复现才会"（案例进展①）；工程化六方面判据（§4.3）。

**追问链答案**：①区分"客观原因"与"悄悄牺牲"三条：相关方知不知情 / 有没有评审 / 有没有记录——"悄悄牺牲"的定义就是"没有让任何相关方知情"（案例进展②）；②不是工程，是"手艺换了载体"——试金石：换三个人运维能一样跑吗？不能 = 手艺（案例进展①）；③宣告不工程化——"工程化"要用六方面判据测（有结构/有方法/可重复/全覆盖/受控/可验证），且要有记录；判断工程的动作本身要工程化（可检验 + 记录 + 评审）。

### Q2　试金石：可复现 ≠ 工程

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"可复现 = 工程极致" | 正中陷阱——把"试金石"当成了充分条件 |
| 中：说"纯可复现是算法" | 方向对，但没说清"判断的价值"在哪 |
| 好：可复现是必要非充分；可复现与判断的价值打架、唯一和解 = 方法复现（⑥）+ 判断留在人（⑤）+ 错误可见；AI 写全规则 = 约束被消灭 = 不是工程 | 悖论化解到位 |

**产品侧 vs IT侧**：产品侧容易答"工程 = 有方法论的流程"，IT 侧容易答"工程 = 可测试可复现"。两边的完整版是同一个：**可复现的方法 × 不可复现的判断**——缺判断的一侧掉进"算法化"，缺复现的一侧掉进"手艺"。

**反转话术**：
> "'把流程写成算法、完全可复现'——这恰恰是工程的反面。**排序算法完全可复现，它是工程吗？不是，它是算法。可复现是工程的必要条件，不是充分条件。** 于是出现一个真悖论：工程追求'换个人也能交付'（试金石），可如果换个人也能交付，那个人的价值是什么？**这是两个方向在打架：既要事情不依赖人，又要判断在人身上。** 和解只有一种：把方法复现（⑥可复现意识），把判断留在人身上（⑤工程判断），但让判断的错误可见（可检查）。老周是判断在、方法不在（缺⑥）；李工是方法在、判断是坏的（先上再说 = 坏判断）。**判断不能被完全写下来——能写下来的规则是方法，不是判断。判断 = 在约束下做取舍，约束一变，规则就失效。** 如果 AI 把所有判断都写成规则，那时不需要工程师了——不是工程进步了，是约束被消灭了，工程的定义本身失效了。"

**参考答案要点**（书 §1.1、§3.5⑤⑥、§4.1、§4.3）：工程四要素"判断创造"是料；⑤工程判断横切四层（在约束下做对的取舍）；⑥可复现意识把个人能力变组织能力；algorithmic = 确定性执行；ABET "applied with judgment"。

**追问链答案**：①可复现是**必要**条件不是**充分**条件；"判断创造"不能删——工程的定义就是"在约束下做取舍"，没有约束、没有取舍，就没有工程；②打架的和解：方法复现（⑥）+ 判断留在人（⑤）+ 错误可见（可检查）——老周李工各缺一半；③AI 写全规则 → 不需要工程师 → 约束被消灭 → 不是工程；判断是工程不可算法化的内核。

### Q3　敏捷 ≠ 软件工程（四层结构）

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"流程没有用" | 把事故归罪于流程——正中陷阱 |
| 中：说"是价值层失守" | 对，但没到"为什么流程完备还失守"这一层 |
| 好：三起事故共性=没守住不是不会做（安全让位）；发生在价值层（该层无现成检查点）；四层齐了也出错→错误可见 | 反直觉三层全中 |

**产品侧 vs IT侧**：产品侧容易补"还缺需求管理、评审"，IT 侧容易补"还缺架构、容量评估"。讲师要点出"工程科学"才是一般人漏的那层，而"价值层的检查点要主动设"是所有人漏的那层。

**反转话术**：
> "看完三起事故的原因，先回答'流程没有用'——这个结论是错的，但错得很有启发。**泰坦尼克按'不会沉'配救生艇、挑战者把低温 O 形环的风险'合理化'、737 MAX 在认证压力下轻描淡写 MCAS 缺陷——三起事故没有一个是'技术做不到'，全是'关键时候安全让了位'。是'不会做'还是'做的时候没守住'？——是后者，而且发生在价值与伦理这一层。** 挑战者号的 O 形环有技术检查，可'这个决定是否违背安全承诺'没人检查。更阴险的是：流程越完备，失守越隐蔽——**大家都以为'流程这么全，不会有问题'，于是没人再去看价值层。** 这就是为什么'四层齐了'降低的不是出错概率，是错误被掩盖的概率：**工程的目标不是零错误，是错误可见。** 怎么检验？事后能否回答四问：改了什么、为什么、影响谁、怎么验证。"

> 讲师补充（若讨论时间允许）：给价值层设了检查点（评审+签字）之后，它还会退化成"走流程"——签字的人不再判断、觉得走了流程就免责。检查点不失效，靠的是背后站着有判断力的人（工程师④），不是流程本身。

**参考答案要点**（书 §3.1~3.4、4.4、案例进展②）：方法 < 方法论 < 工程；四层缺层后果表；价值层事故（不是不会做，是做的时候没守住，§3.4 三起事故原因）；系统化 = 可检查（4.4）；补价值层 = 评审 + 风险登记 + 签字。

**追问链答案**：①三起事故共性 = "做的时候没守住"不是"不会做"——救生艇按"不会沉"配 / O 形环低温被"合理化" / MCAS 缺陷被轻描淡写，全是安全让位（价值层失守），没有一起是技术做不到；如果只是不会做，不会三起都是同一类原因；②发生在价值与伦理层——前三层有现成检查点（CI/测试/评审），价值层没有；流程完备让失守更隐蔽（"流程这么全，不会有问题"）；③四层齐了也出错；降低的是"错误被掩盖的概率"；工程目标 = 错误可见；检验 = 事后四问（改了什么 / 为什么 / 影响谁 / 怎么验证）。

### Q4　系统化 ≠ 机械化

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"自动化程度越高越安全" | 正中陷阱——把"机器不会犯错"当"系统安全" |
| 中：说"算法不需要判断" | 对，但没到"单向门" |
| 好：自动化提纯判断；把判断交给机器 = 机器不知道为什么 = 缺工程科学；自动化消灭的不是事故是人阻止事故的能力（单向门） | 反直觉核心全中 |

**产品侧 vs IT侧**：产品侧用"流程/模板"举例，IT 侧用"自动化/流水线"举例。可点出：连自动化流水线本身，"要不要自动、阈值设多少"仍是人的判断——且这是自动化之后**剩下**的判断，判断密度更高。

**反转话术**：
> "'机器不会犯错'——对，机器确实不会犯错，**但机器会犯的错是：它不知道自己在干什么。** 排序算法同输入同输出，不需要判断；工程方法每一步留判断。把'阈值设多少、异常怎么处置'交给机器，机器不知道'为什么这个阈值'，换场景就抓瞎——缺的是工程科学（第一层）。所以自动化不是减少判断，**是把判断提纯**：机器接走执行，人接住的全是最难的判断（异常/边界/目标）。再往前推一步，是最疼的反直觉：**737 MAX 的 MCAS 把失速判断交给系统——自动化消灭的不是事故，是人阻止事故的能力。它是个单向门。** 系统接管的那一刻，飞行员不再能手动接管。自动化程度越高的系统，出问题时越没有'手动接管'的退路。**全自动的终点是消灭判断，消灭判断 = 消灭工程——工程的定义里，判断是料。**"

**参考答案要点**（书 §4.1、§4.3、判据#3、§1.1、§3.4）：三词辨析（systematic / systemic / algorithmic）；"有方法（含判断）"对应 ABET "applied with judgment"；三问验证系统化；737 MAX / MCAS 属价值层事故。

**追问链答案**：①算法无需判断；工程方法留判断——把"阈值/异常"交给机器 = 机器不知道"为什么" = 缺工程科学第一层（换场景抓瞎）；②自动化提纯判断——机器接执行、人接最难判断；全自动系统人剩下的是"判断密度最高"不是"不用判断"；③MCAS：自动化消灭的不是事故，是人阻止事故的能力（单向门——出问题无手动接管退路）；全自动终点 = 消灭判断 = 消灭工程。

### Q5　系统工程 = 元工程

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"一定是某个部件没做好" | 正中陷阱——把系统问题归到部件身上 |
| 中：说"问题在集成、在接口" | 对，没到"缝"和"隐形产出"这一层 |
| 好：问题在部件与部件之间（缝=跨部件无人拥有）；系统工程不造部件、产出隐形；价值靠机制证明不是结果 | 反直觉核心全中 |

**产品侧 vs IT侧**：产品侧"硬件+软件+云端+App 各做好"；IT 侧"微服务每个健康"。都是"部件加总"的直觉。可追问两边：你团队的"接口契约"写在哪？——写不出来的，就是没有系统工程。

**反转话术**：
> "恒信三个模块各自都好，集成那天为什么对不上？——**问题不出在任何一个部件上，出在'部件与部件之间'：那个看不见的'缝'。** '合同状态'一个词两套定义——这个现象第1章讲过：同词异义（词汇病），在系统级的重演。**而'缝'恰恰是系统工程的地盘：系统工程不造任何部件，它管的是整合——定义接口、对齐数据口径、理清时序依赖。它的产品是接口契约、集成方案、系统级验证方案——看不见摸不着，但决定系统能不能转。** 于是问题来了：系统工程不造部件、成果看不见，怎么证明它有用？——**'没出事'不够，因为结果分不清运气和工程：一个运气好的团队和一个工程好的团队，结果可能一模一样。** 能区分它们的只有机制：接口契约写没写、集成方案测没测、追溯记录有没有。**工程的质量靠机制证明，不靠结果证明。**"

**参考答案要点**（书 §5.1~5.2）：系统工程 = 元工程（整合部件、不造部件）；产品 = 接口契约 / 集成方案 / 系统级验证方案；涌现属性（部件全对 ≠ 系统对）；恒信数据口径 = 词汇病系统级重演。

**追问链答案**：①问题不在部件身上，在"部件与部件之间"（缝）——跨部件、无人拥有，所以平时看不见；"合同状态"一个词两套定义 = 同词异义（词汇病）在系统级重演；②不造部件；管整合（接口/数据口径/时序依赖）；产品 = 接口契约 / 集成方案 / 系统级验证方案（隐形产出，决定系统能不能转）；③"没出事"不够——结果分不清运气和工程（涌现双向不可推导：部件对≠系统对，系统对≠部件对）；靠机制：接口契约写没写、集成方案测没测、追溯记录有没有。

### Q6　技术系统 vs 工程系统

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：认同"被用起来 = 成功"或"技术完美就是成功"任一边 | 各抓一半，没看到"验收的是变革" |
| 中：说"两个都算，要看情况" | 对，没说清区分需要工程之外的东西 |
| 好："被用起来"验收的是组织变革不是产品；"没人用"=产品问题还是变革问题，工程系统自己答不了，需要治理视角（预告第11章）；上线是起点不是终点（生命周期） | 反直觉核心全中 |

**产品侧 vs IT侧**：这题对 IT 侧冲击最大（ERP 经典翻车：软件部署好了、服务器跑起来了、模块上线了 = "系统成功"；采购流程没改、财务不会用、数据没清洗 = "系统失败"）。产品侧则容易想到"智能硬件交付后没人持续用"——硬件"上线"和软件"上线"是一个陷阱的两面。

**反转话术**：
> "'被用起来'作为验收标准——它既对又不够。**对，是因为'有用的人造物'是工程的目的，没人用的系统技术上再完美也是失败；不够，是因为'被用起来'验收的其实是组织变革，不是产品。** 于是出现一个工程系统自己答不了的难题：一个'上线了没人用'的系统，是产品问题（不好用）还是变革问题（没推动）？——**工程系统能回答'设备跑没跑起来'，回答不了'人为什么不用'。后者要的是第11章治理的视角：谁在推动流程改造、谁有权力让业务走线上。** 所以工程系统的验收，天然延伸到工程之外。而'上线'从来不是终点：INCOSE 说工程系统要被实现、使用、退役——纸质台账怎么迁入、退役数据怎么归档，这些'技术系统'不会问、'工程系统'必须答的问题，才暴露你是不是只当技术系统在管。"

**参考答案要点**（书 §5.3、案例进展④、判据#5）：技术系统 ⊂ 工程系统（工程系统含人/流程/组织/信息，INCOSE 2019）；工程系统生命周期（实现/使用/退役）；机场例子——工程系统的边界画在"整个运行环境"上；20 世纪 70-80 年代最贵的教训：把工程系统当技术系统管。

**追问链答案**：①缺的是"人/流程/组织"——法务线下签、财务手工台账、业务走邮件，都是工程系统的一部分；"被用起来"可设可检验的验收条款（电子签比例≥X% / 台账迁移 / 业务走线上）；②"没人用"要区分产品问题 vs 变革问题——工程系统自己答不了，需要治理视角（谁推动流程改造、谁有权让业务走线上——第11章预告）；③上线是起点不是终点（生命周期：实现/使用/退役）；纸质台账迁入 + 退役数据归档 = 工程系统必须答、技术系统不会问——暴露你是不是只当技术系统在管。

### Q7　工程师：选边 + 六能力

| 各组答案的常见形态 | 讲师判读 |
|---|---|
| 弱：选老周——手艺好、经验足 | 正中直觉——把"个人能力"当"工程能力" |
| 中：选老周但犹豫（李工有流程） | 有判断，没到"能力不是中性的" |
| 好：能力不是中性的——④定义能力的方向，①③⑤顶配+④为零 = 更危险；老周缺②⑥、李工缺①④（⑥也站不住）；合体 = 老周的判断 + 李工的流程 + 价值层守住 | 反直觉核心全中 |

**产品侧 vs IT侧**：产品组容易站老周（手艺）、IT 组容易站李工（流程）——两边都只看到四层的一半。这正是"头衔不定义工程师"的现场证据。

**反转话术**：
> "直觉选老周——但先回答一个更狠的问题：**能力是中性的吗？** 一个①③⑤顶配、④为零的工程师，是更强还是更危险？——**更强，也更危险。能力不是中性的，能力放大的是选择的规模，而选择的方向由④定义。** 有能力的坏工程师，破坏比无能的坏工程师大得多。737 MAX 里不缺'会算的工程师'，缺的是'守住底线的工程师'。可招聘偏偏只看①学历、③项目、②方法，**从不考④——六项能力里，唯一'关键时刻决定生死'的那项，恰恰是招聘最不测的那项。** 回到选边：老周缺②⑥（判断在、人走判断走）、李工缺①④（方法在、底线守不住）——两个都不是工程师画像。工程化的目标不是二选一，**是让老周和李工合体：老周的判断 + 李工的流程 + 价值层守住。**"

**参考答案要点**（书 §3.5、§3.6）：工程师六能力（科学素养/方法论素养/实践能力/职业伦理/工程判断横切/可复现元能力）；老周缺②⑥、李工缺①④（⑥也站不住——CI/CD 依赖隐藏命令）；头衔不定义工程师。

**追问链答案**：①老周缺②方法论素养 + ⑥可复现意识；李工缺①科学素养 + ④职业伦理（⑥也站不住）；"经验丰富"是个人能力、"可复现"是组织能力；②能力不是中性的——④定义能力方向，①③⑤顶配 + ④为零 = 更危险（有能力 + 不守底线，破坏更大）；737 MAX 缺守住底线的工程师；③招聘从不考④ = 最致命项不被测；合体第一步 = 把老周判断写成可检验规则（⑥）+ 给李工设价值层检查点（评审 + 签字，④）。

## 4. 知识卡片

### 一页图

```
工程 = 科学原理 × 判断创造 ——在约束下—— 用系统方法 → 有用且安全的人造物

工程的三维对立面
  认识论 → 科学（创造 vs 发现）
  方法论 → 手艺（可复现 vs 依赖个人）  ← 试金石：换团队能否同等交付
  目标   → 艺术（满足需求 vs 自我表达）

工程的四层结构（只讲方法论 ≠ 在做工程）
  价值与伦理 ← 重大事故的根源层；流程管不到它；检查点必须主动设、且会退化成走流程
  工具与实践
  方法论     ← 敏捷在这里
  工程科学

三词辨析
  systematic 系统化  = 做事有章法（有步骤/检查点/判断）
  systemic   系统性  = 看问题有全局（部分关系/涌现/环境）
  algorithmic 算法化 = 确定性执行（同输入同输出）——纯可复现是算法，不是工程

系统工程 = 元工程（整合部件，不造部件）→ 产出隐形 → 价值用"没发生什么"衡量
  涌现属性：部件全对 ≠ 系统对（双向不可推导）→ 结果证明不了工程，机制才证明
技术系统 ⊂ 工程系统（人/流程/组织/信息也是工程系统的一部分）——验收的是行为不是设备

工程师：四层各一项能力 + 工程判断（横切）+ 可复现意识（元能力）——头衔不定义工程师
  能力不是中性的：④定义能力的方向——①③⑤顶配 + ④为零 = 更危险
```

### 金句

- **试金石**：换个团队、换个人，用同样的需求文档和约束，能交付质量相当的成果——能，是工程；不能，那是手艺。
- **约束即定义**：约束不是工程的对立面，约束是工程的全部舞台——约束越多，判断的价值越大。
- **工程 = 可复现的方法 × 不可复现的判断。**（纯可复现是机器，纯不可复现是手艺。）
- **系统化 ≠ 机械化**：系统化是"有章法的判断"，不是"确定性的执行"；工程靠方法，不靠算法。
- **自动化不是减少判断，是把判断提纯。**（自动化消灭的不是事故，是人阻止事故的能力——单向门。）
- **工程的目标不是零错误，是错误可见。**（系统化=可检查。）
- **最贵的工程成果，是"没发生的事"。**（系统工程产出隐形，结果证明不了工程，机制才证明。）
- **工程系统的验收，延伸在工程之外。**（"被用起来"验收的是组织变革，不是产品。）
- **能力不是中性的，④定义能力的方向。**（头衔不定义工程师，能力才定义——而能力的意义由伦理定义。）
