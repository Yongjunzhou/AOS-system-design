## 一、单元导读

### 主题

验收把关怎么把？——三个看门人，三把不同的尺子：**评审对目标**（方向对不对，判断）、**验证对需求**（做对了吗，证明）、**确认对用途**（做对的东西了吗，证明）。三个词在中文里像近亲，其实是三种完全不同的活动——唯一共同点是翻译形近字。

### 开场破题（对应章首误解现场）

念出恒信上线前评审会里李工的话："UAT 全部通过。测试用例通过率 96%，P0/P1 缺陷清零，三条业务主流程全部走通。我们验收合格，可以上线。"

会议室里有人开始收东西了。财务老王却问："你们让我们点的那个测试环境，我们月底对账的场景——25 号之后签的合同算哪个月——测了吗？"李工愣了一下："测试用例是照着需求清单写的，需求清单里……没有这条。"

Ada 把 UAT 报告合上，竖起三根手指："李工，你把三件事当成一件事办了——评审、验证、确认。你说业务方点了测试环境，所以确认过了——不是。那是让业务方当测试员，替你们跑用例。你说测试全绿，所以验证过了——是过了，但你验证的是'按需求做对了'，不是'真实场景能用'。你说上线前评审过了——评审对的是目标，你们只对了需求清单。"

让各组表态：如果你坐在那间会议室里，你会站在李工那边吗？"评审""验证""确认"——不都是"检查一下""把关"吗？带"评/验/认"字，听起来像近亲。三个词真的差这么多？

### 本单元要反转的直觉

- **评审、验证、确认差不多，都是把关**（× 三把尺子、三个参照、三种动作；唯一共同点是翻译形近字）
- **评审就是开会过一遍需求 / 逐条核对需求清单**（× 核对需求是验证的姿势；评审对目标——适宜/充分/有效）
- **测试全绿 = 验证过了**（× 测试是证据手段之一；96% 意味着 4% 没证据；测试报告是验证的输入不是验证本身）
- **UAT 跑了 = 确认过了 / 让业务方点测试环境就是 UAT**（× 让业务方当测试员是把确认做成验证；确认 = 真实用户 + 真实任务 + 真实场景）
- **测试全过、没人用是运气问题**（× 因果链：只做验证不做确认 → 隐含需求系统性漏失 → 测试全过没人用）
- **隐含需求写进文档后就能被验证**（× 很多隐含需求写不出来，只有真实场景能裁决；验证量吃水线、确认开船试航）
- **确认是验证的加强版，范围更大而已**（× 参照不同——文档 vs 场景；射程不同——够不着隐含 vs 兜得住隐含）
- **复盘也是评审，都带"评"字**（× 评审管把关，复盘管改进；复盘不在 IEEE 1028 五类里）

### 本轮题卡的内在逻辑（10 题 2×5）

**第一组 · 概念与原理（先立概念）**：Q1 三把尺子（概念本身·破题）→ Q2 三者关系 + 三个参照（概念关系·真悖论）→ Q3 评审对目标不是核对需求（真悖论）→ Q4 验证三要素·测试≠验证（真悖论）→ Q5 确认三要素·UAT 本质（真悖论）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 恒信重开上线评审会（评审对目标·目标具体化）→ Q7 月底对账复盘（评审≠复盘）→ Q8 恒信 UAT 教训（确认三要素·预期用途三构成）→ Q9 冰链断档 30 秒（确认射程·因果链）→ Q10 回部门"三关体检"（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。恒信合同审批系统（流程软件）与冰链 M3 温控箱（硬件 × 软件）是同一个概念的两面——三个看门人在两边都各站其位：恒信把"月底对账"当目标评审、把"25 号后归属"当规定需求验证、把"真实对账场景"当用途确认；冰链把"断链即报废时还能撑到接入冷库"当目标、把"断电保温 ≥72 小时"当规定需求验证、把"真实运输车跑全程"当用途确认。这正是"评审验证确认"领域中立的证据。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜三个词到底差在哪？**
"Ada 对李工竖起三根手指：'你把三件事当成一件事办了——评审、验证、确认。'三个词在中文里看起来像近亲，它们到底差在哪？"

追问：① 翻译伪朋友：review / verification / validation 三个英文词源、构词、归属完全不同，ISO 9000 里还不在同一组词（评审在 3.11"有关确定的术语"，验证确认在 3.8"有关规范的术语"）——"确定"和"认定"是两种动作，判断和证明是两回事，为什么中文形近字把这个分家糊了四十年？② 三把尺子：评审对目标、验证对规定需求、确认对预期用途——三个参照各回答什么问题（方向对不对 / 做对了吗 / 做对的东西了吗）？③ 你们最近一次"验收签字"，是三个看门人依次签字，还是三个词糊成一个签了？

**Q2｜三者什么关系？三个参照各在哪层？**
"请给出 评审、验证、确认 的关系（一句话）。再把'参照'放进去——三个参照（目标 / 规定需求 / 预期用途）各在哪一层？为什么说'参照不同'是决定性差异？"

追问：① 五维对比（定义 / 参照 / 动作 / 证据 / 时机）——哪一维全不同？② 动作分家：评审动作是"确定"（主动调查）、验证确认是"认定"（证实）——为什么"判靠判断力、证靠客观证据"直接决定了评审不要求证据、验证确认必须证据？③ "评审、验证、确认都是把关（它们都叫把关）" vs "三个词是三把完全不同的尺子（翻译伪朋友）"——两个都对，靠什么判据分清？④ 目标 vs 预期用途：目标驱动需求推导、用途在真实场景里才现形——这两个参照为什么不是一回事？

**Q3｜评审为什么不以需求为参照？**
"小林的评审会开了一下午：逐条念需求、逐条打勾——'有编号✓、有来源✓、可测吗✓'，三十条划满对勾，宣布'评审通过'。小赵：'你只核对清单有没有写——那是验证的姿势。评审要对目标。'——评审为什么不以需求为参照？"

追问：① 三理由——需求本身可能错（谁来审需求本身）/ 否则评审和验证就重复（标准不会为同一件事分两组）/ 满足所有需求 ≠ 达成目标（要求是路、目标是目的地）？② "评审就是逐条核对需求（我们天天这么干，现成的文档一条条对最省事）" vs "评审对目标（核对需求是验证的姿势，需求满足得越彻底目标偏离得越远）"——两个都对，靠什么判据分清？③ 目标具体化：目标 = 对象 + 时限 + 可衡量结果——为什么"月底对账时间 ≤ 2 小时"评得了、"系统能上线"评不了？④ 你们最近一次评审，通过标准是会后现想的吗？评审问的是"这需求对吗"还是"这些需求还朝那个目标吗"？

**Q4｜测试和验证差在哪？**
"李工亮出 UAT 报告：'测试用例通过率 96%，P0/P1 清零，验收合格，可以上线。'Ada：'你验证的是按需求做对了——可测试全绿不等于验证过了。'——测试和验证差在哪？"

追问：① 验证三要素：对照规定需求 + 客观证据 + 认定——缺一个都不算验证；"口头大概要快一点"缺对照、"我认为满足"缺证据、"差不多吧"缺认定？② 测试只是证据手段之一（ISO 9000 注 1：试验结果 / 变换方法计算 / 文件评审），测试报告是验证的输入不是验证本身——96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足，测试没有给出证据？③ "测试全绿 = 验证过了（测试不就是验证吗）" vs "测试只是证据之一、验证要对全部规定需求做认定（96% 是缺口不是 100%）"——两个都对，靠什么判据分清？④ 你们说"测试全绿"的时候，验证三要素齐了吗？缺的是哪一条？

**Q5｜UAT 跑了为什么不算确认过了？**
"章首李工让法务、财务、业务'在测试环境点了一圈'，说'业务方点了，确认过了'。Ada：'那是让业务方当测试员。'——确认到底是什么？为什么 UAT 跑了不等于确认过了？"

追问：① 确认 = 对照预期用途 + 客观证据 + 认定；UAT = 真实用户 + 真实任务 + 真实场景——前一种 UAT 测的还是需求、后一种 UAT 测的是场景，差别在哪？② 参照在场景里：验证的参照在文档里（明示成文可复制）、确认的参照在场景里（真实使用情境）——为什么真实场景自带答案（对不上账、断档 30 秒、卡在离职审批人手里全是看得见的缺陷）？③ "让业务方点测试环境 = 确认（用户都参与验收了）" vs "让业务方当测试员 = 把确认做成验证（对照的还是需求清单）"——两个都像，靠什么判据分清？④ 隐含需求像冰山：验证是量吃水线的尺子只管浮面、确认是把船开进真实水域试航——为什么很多隐含需求写不下来（顺手/直觉/动效/节奏/惯例），只有真实场景能裁决？

### 第二组 · 落地与实践

**Q6｜Ada 为什么先定目标再评审？**
"重开上线评审会前，Ada 没讲方案，先写了三条目标：月底对账一致率 100% + 对账时间 ≤ 2 小时；法务合规：电子签章审批链完整可追溯；业务可用：3 个工作日完成一次发起归档。李工对着'法务合规'忽然卡住：'这条变更当初是口头定的，需求清单里没有，方案里也没有。'——Ada 为什么先定目标再评审？"

追问：① 如果只核对需求清单，李工会说"全部覆盖，通过"——可尺子不是需求清单是"法务合规"这个目标，目标一摆出来就发现"这条变更连需求都不是"——评审对目标的实操威力在哪？② 目标具体化三成分（对象 + 时限 + 可衡量结果）+ 检验三问（通过标准 / 可观察判定 / 看什么裁决）——三条目标各满足吗？③ 通过标准会前定、会后逐条打勾——为什么"会前定"让评审有尺子、"会上现想"等于没有尺子？④ 你们最近一次上线评审，通过标准是"系统能上线"这种评不了的，还是三条可打勾的目标？

**Q7｜复盘和评审是一回事吗？**
"恒信月底对账对不上，复盘会产出了两条行动项：'变更必须先过评审对目标一关'和'UAT 改真实场景跑'，各配负责人和期限。Ada：'复盘的价值，一半在诊断，一半在闭环。'——复盘和评审是一回事吗？"

追问：① 评审管把关（干活之前/之中，判断适宜/充分/有效）、复盘管改进（干完了，事后总结，绕回起点驱动下一轮）——复盘不在 IEEE 1028 五类里、也不是 ISO 9000 的"评审"，为什么？② 复盘的通过标准同样要会前定：负责人 + 截止日期、关闭率 ≥ 80%、按根因归类（而非甩锅）、记录归档——"只诊断不闭环"的复盘是把同样的错再复一遍，你们团队怎么防？③ 复盘绕回起点，把上一轮教训变成下一轮评审的目标——这条"改进→把关"的回路在第11章治理里叫"事件触发"，为什么复盘是那个事件源？④ 你们最近一次复盘，产出的是"我们很努力"还是"下一轮改什么、谁改、何时改完"？

**Q8｜UAT 三问——考的是确认的什么？**
"Ada 复盘那次 UAT，连问三问：月底对账用的是真实数据还是造的 20 条（没有一条是 25 号之后的）？在真实月底时间点、真实并发下做的吗（不是周二下午三个人轮流点）？电子签章审批链'谁审谁签'验证过吗（没排进 UAT）？三问都是'否'。Ada 合上文件夹：'你把确认做成了验证。'——这三问各在考确认的什么？"

追问：① 三问对应预期用途三构成——目标用户（法务/财务/业务，不是 IT 测试员）、使用场景/任务（月底对账、电子签章、审批人休假交接）、环境与条件（月末高峰并发、弱网、休假交接）——哪一问最容易被"造不出缺陷的测试环境"带过？② 确认不能后补到上线后——"上线后补确认，就叫上线事故"；把三个真实场景排进下一轮 UAT，用真实数据、真实任务、真实时间点——为什么？③ "UAT 是确认（用户验收测试嘛）" vs "那次 UAT 是验证（对照的还是需求清单）"——两个都像，靠什么判据分清？④ 你们一次"UAT 通过"，数据是真的吗？时间点是真实的吗？真实场景里会现形的隐含需求，有几个是测试用例提前发现的？

**Q9｜"用例全过，说明不了上路能过"——在说什么？**
"M3 交付前跑真实运输：疫苗装箱、上真实的疫苗运输车、跑出库→运输→到达全程。第一天晚上，车厢过减速带时温度记录仪振动断电重启，断档 30 秒。测试台架复现不了——台架没有颠簸；测试用例里只有'温度记录连续'，没有'振动下温度记录连续'。老周：'用例全过，说明不了上路能过。'——这句话在说什么？"

追问：① 断档 30 秒是验证的错还是确认的错（测试用例没写好 = 执行问题）？——验证的参照是需求文档（没写"振动下连续"=不在射程内）、确认的参照是真实场景（"疫苗能不能安全送到"=场景里现形），断档 30 秒是场景里显影出来的隐含需求？② "这是测试用例没写好（执行问题，改用例就行）" vs "这是测试环境里没有路（场景问题，台架替代不了那辆会颠的车）"——两个都像，靠什么判据分清？③ 因果链三段：隐含需求没进文档 → 只做验证的团队让它在体系外漏着 → 上线后处处别扭（功能全对、测试全绿、没人用/对不上）——为什么这是因果不是运气？④ 你们有没有"用例全过、一上路就露馅"的经历？那个露馅，是缺了哪一关？

**Q10｜给你们的部门做一次"三关体检"**
"结合你们部门现状，用七把尺子（三把尺子 / 评审三问 / 评审三属性 / 验证三要素 / 确认三要素 / 因果链 / 评审≠复盘）给最近一次上线 / 验收做一次'三关体检'——给出最该改进的三个事项，每个落到一个动作。"

追问：先做哪把尺子？为什么？两周后回来报告什么？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 三个词到底差在哪？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "差不多，都是检查一下、都是把关。" | 正是要翻的——没看见三个词是三把不同的尺子 |
| 中 | "评审对目标、验证对需求、确认对用途。" 三句口诀背出来了，翻译伪朋友/五维说不清 | 结论对，机制缺 |
| 好 | 三把尺子（目标/规定需求/预期用途）+ 翻译伪朋友（英文词源不同 + ISO 9000 分组不同 + 中文形近字糊分家四十年）+ 五维全不同（定义/参照/动作/证据/时机）+ 判证有别（判靠判断力、证靠客观证据） | 机制 + 判据 + 必然性全到位 |

**产品侧 vs IT侧**：产品组答"M3 三个看门人各对什么——断链即报废（目标）/断电保温 ≥72 小时（规定需求）/疫苗安全送到（用途）"；IT 组答"恒信三个看门人各对什么——月底对账不再靠手工（目标）/25 号后归属（规定需求）/月底对账能用（用途）"。同一个"三把尺子"。

**反转话术**（对应 §1.1~1.3 + 章末反转）：李工的病不是笨，是中文给了他一个陷阱。**review、verification、validation**——三个词源、构词、归属完全不同的英文词，翻译成中文恰好都带一个"评/验/认"字，看起来像三个近亲。ISO 9000 里它们根本不在同一组词：评审在 3.11"有关确定的术语"（和确定、监视、测量、检验是一家人），验证确认在 3.8"有关规范的术语"（和规范、要求、符合性是一家人）。**"确定"和"认定"是两种动作，判断和证明是两回事。** 三把尺子一句话定案：**评审对目标，验证对需求，确认对用途。** 评审站在开工前抬头看方向、验证站在做完了低头对规格、确认站在交给用户走进真实场景。五维对比（定义/参照/动作/证据/时机）全部不同——没有一维是"差不多"。这三个词不是"差不多"的三个说法，是三个看门人各守一道门；混到验收签字那一刻，就是第1章那场四个月扯皮的预演。

**参考答案要点**：翻译伪朋友见 §1.1；三把尺子见 §1.1 表；三层参照图见 §1.2；五维对比见 §1.3；概念总图。

### Q2 三者什么关系？三个参照各在哪层？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "评审是看方案，验证是测试，确认是验收。" | 把三种活动当三个流程阶段，参照/动作没分清 |
| 中 | "评审对目标、验证对需求、确认对用途。" 三句对，参照层级/判证机制说不清 | 关系对，机制缺 |
| 好 | 三者共享"把关"之名但参照/动作/证据/时机全不同 + 目标最上层、规定需求中间、客体最下、预期用途场景层 + 判证有别（确定=判断可无证据、认定=证明必须有证据）+ 目标 vs 用途的区别（驱动推导 vs 场景现形） | 关系 + 层级 + 判证机制全到位 |

**产品侧 vs IT侧**：两组都套同一句关系——冰链的"目标（断链撑到冷库）/需求（断电保温）/用途（疫苗安全送到）"与恒信的"目标（月底对账不再手工）/需求（25 号归属）/用途（对账能用）"。三把尺子不挑角色。

**反转话术**（对应 §1.2 + §1.3）：把产品开发的世界画成三层：**目标层**（所规定目标，要实现的结果）最上面、**要求层**（规定需求，明示成文）中间、**客体层**（方案/产品/代码）最下面，而**预期用途在旁边的场景层**。向下是建造（目标推导需求、需求规定客体），向上是三个看门人从客体出发分别向三个参照看去。为什么"参照不同"是决定性差异？因为**三种参照不是一回事**——尤其目标（要实现的结果）和预期用途（真实使用的场景）：目标驱动需求推导，用途要在真实场景里才现形。动作分家是关键：评审动作是**确定**（主动调查，从没有结论到有结论），验证确认是**认定**（结果已经在那儿了，去证实）。**一个判、一个证——判靠判断力、证靠客观证据。** 这就是评审不要求证据、验证确认必须证据的原因：判断可以不依赖证据，证明不行。

**参考答案要点**：三层参照图见 §1.2；五维对比表见 §1.3；判证之别见 §1.3 第一段。

### Q3 评审为什么不以需求为参照？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "逐条核对需求清单、划对勾，不就是评审吗？很标准。" | 正是要翻的——把"验证的姿势"当"评审" |
| 中 | "评审对目标。" 结论对，三理由/目标具体化说不全 | 结论对，机制缺 |
| 好 | 三理由（需求可能错/否则与验证重复/满足所有需求≠达成目标）+ 目标具体化（对象+时限+可衡量结果）+ 需求满足越彻底目标偏离越远 + 通过标准会前定 | 理由 + 判据 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"冰链需求评审逐条打勾'有编号/有来源/可测/有验收'——小赵问'运输车抛锚 2 小时'在哪"；IT 组答"恒信评审核对需求清单——'电子签章变更'连需求都不是"。同一个"核对需求是验证的姿势"。

**反转话术**（对应 §2.1~2.4 + 案例进展②）：如果评审以"需求"为参照，不是更省事吗？——**三个理由，每一条都足以让它破产。** 一、**需求本身可能是错的**：需求是人写的，如果拿需求当尺子就等于默认"需求一定对"，那谁来审需求本身？需求评审的本质，恰恰是审"需求"对"业务目标"是否适宜、充分、有效。二、**否则评审和验证就重复了**：验证本来就是"以规定需求为参照、确认符合性"，两个词必须两件事，否则 ISO 9000 不会把评审放 3.11、验证放 3.8。三、**满足所有需求 ≠ 达成目标**：需求全做完可能还是没人要的东西——要求是"路"，目标是"目的地"，评审的价值就是在低头检查路况之外，抬头看看目的地对不对。恒信的目标是"月底对账不再靠手工"，需求清单里全是"审批提速、流程优化"——**需求满足得越彻底，目标的偏离走得越远。** 评审三问：适宜性（对症吗）、充分性（够全吗）、有效性（管用吗）层层递进。目标具体化配方：**对象 + 时限 + 可衡量结果**——"月底对账时间 ≤ 2 小时"评得了、"系统能上线"评不了；通过标准会前定、会后逐条打勾，检验三问答得上才开会。

**参考答案要点**：评审三问见 §2.1；三理由见 §2.2；目标具体化见 §2.4；案例进展②。

### Q4 测试和验证差在哪？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "测试全绿了不就是验证过了吗？" | 正是要翻的——把"测试结果"当"验证结论" |
| 中 | "测试只是验证的手段之一。" 结论对，三要素/96% 缺口说不清 | 结论对，机制缺 |
| 好 | 验证三要素（对照/证据/认定）+ 测试只是证据手段之一（注 1）+ 96% 意味着 4% 没证据 + 测试报告是验证的输入不是验证本身 + 逐级回收（V 模型左右镜像） | 三要素 + 案例 + 必然性全到位 |

**产品侧 vs IT侧**：产品组答"M3 台架试验全过≠整机验证过——缺了真实运输这一层"；IT 组答"恒信 UAT 通过率 96%——4% 的用例没过或没写，需求没证据"。同一个"测试≠验证"。

**反转话术**（对应 §3.1~3.3）：测试只是**提供客观证据的手段之一**——ISO 9000 注 1 明确说，验证的证据可以是试验结果、变换方法计算、文件评审等；验证还包括审查、替代计算、文档评审。**验证 = 对照规定需求 + 客观证据 + 做出认定，缺一个都不算。** UAT 报告写"测试通过率 96%"——这是一份**测试结果**，是证据的一种；但 96% 意味着 4% 的用例没过或没写，这 4% 对应的需求是否满足，测试没有给出证据。**测试报告是验证的输入，不是验证本身；验证是拿着全部证据对全部规定需求做出认定。** 还有一条推论：规定需求"可验证"不是标准直接写的，是从"验证要求客观证据 + 验证以规定需求为参照"推出来的——可验证是规定需求当验证参照的**资格证**（呼应第4章需求质量六性）。验证还**逐级回收**：需求从哪一级分解下去，验证就从哪一级收回来（V 模型左右镜像）——只做最后一次性验证，等于让所有分解白做，中间断掉的层级恰是缺陷藏身的地方。

**参考答案要点**：验证三要素见 §3.1；可验证推论见 §3.1；测试≠验证见 §3.2；V 模型见 §3.3。

### Q5 UAT 跑了为什么不算确认过了？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "业务方都点了测试环境，还不算确认？" | 正是要翻的——把"让业务方当测试员"当"确认" |
| 中 | "确认要对用途，UAT 要真实场景。" 结论对，参照在场景/冰山说不清 | 结论对，机制缺 |
| 好 | 确认=对照预期用途+客观证据+认定 + UAT=真实用户+真实任务+真实场景 + 参照在场景里（真实场景自带答案）+ 冰山比喻（验证量吃水线、确认开船试航）+ 很多隐含需求写不下来 | 三要素 + 场景机制 + 冰山全到位 |

**产品侧 vs IT侧**：产品组答"M3 真实运输车跑全程（疫苗安全送到）vs 恒温台架模拟"；IT 组答"恒信财务用真实对账数据、真实月底时间点跑月底对账任务"。同一个"放进场景里看结果"。

**反转话术**（对应 §4.1~4.3 + 案例进展③）：确认和验证**共享同一套三要素**（对照、证据、认定），唯一区别在第一个要素——验证对照"规定需求"（文档），确认对照"特定的预期用途"（场景）。就这一个词的区别，决定两个看门人完全不同的射程和命运。**验证的参照在文档里，确认的参照在场景里**——预期用途不是一份文档，是一种真实使用情境，真实场景自带答案：对不上账、断档 30 秒、待办卡在离职审批人手里，全是看得见的缺陷。章首李工的 UAT 错在哪？他让法务、财务、业务"在测试环境点了一圈"——那是**让业务方当测试员，替测试团队跑用例**，对照的还是需求清单。真正的 UAT 是：财务用真实的对账数据、在真实的月底时间点、跑真实的月底对账任务——对照的是"月底对账能用"这个预期用途。**前一种 UAT 测的还是需求；后一种 UAT 测的是场景。** 隐含需求像冰山：验证是量吃水线的尺子（只管浮在水面上），确认是把船开进那片水域的试航（水下撞没撞到，试航时才知道）——很多隐含需求写不下来（顺手、直觉、动效、节奏、惯例），只有真实场景能裁决。

**参考答案要点**：确认定义与三构成见 §4.1；参照在场景见 §4.2；冰山比喻见 §4.2；UAT 本质见 §4.4；案例进展③。

### Q6 Ada 为什么先定目标再评审？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "评审先讲方案、列需求，最后大家表个态。" | 正是要翻的——目标不具体，评审没有尺子 |
| 中 | "目标具体化才好评审。" 结论对，三成分/检验三问/会前定说不全 | 结论对，机制缺 |
| 好 | 评审对目标（目标一摆出来发现"变更连需求都不是"）+ 目标具体化三成分（对象+时限+可衡量结果）+ 检验三问（通过标准/可观察判定/看什么裁决）+ 通过标准会前定、会后逐条打勾 | 判据 + 案例 + 机制全到位 |

**产品侧 vs IT侧**：产品组答"M3 评审目标——断链即报废时还能撑到接入冷库，拿它照需求清单问'运输车抛锚 2 小时在哪'"；IT 组答"恒信三条目标（对账/合规/可用）——法务合规一摆出来，电子签章变更就现形"。同一个"先立尺子再翻案"。

**反转话术**（对应案例进展① + §2.4）：如果只核对需求清单，李工会说"全部覆盖，通过"。可尺子不是需求清单，是"法务合规"这个目标——目标一摆出来，立刻发现这条变更连需求都不是，是口头的一句承诺。**评审对目标的意义，就是先把目标摆出来，再拿目标照需求。** 目标具体化的配方，三个成分缺一不可：**对象（谁/什么）＋ 时限（何时）＋ 可衡量结果（多少）**。评审会开场前先做检验三问：①通过的标准是什么？②这个"达标"有没有可观察/可测量的判定？③如果两个人理解不一致，看什么能裁决？三个都答得上，这个评审有尺子；答不上来，会开了也是白开。而"通过标准"的正确用法，是**随评审邀请一起发出**——"本评审通过标准：……全部打勾 = 通过；任一不满足 = 打回修改"，不是开会时现想，是会前定好、会后逐条打勾。目标还分层级：战略目标负责让大家相信值得做，操作目标负责让评审开得下去——评审要挂的是可判定那一层的目标，拿战略目标当尺子等于没有尺子。

**参考答案要点**：案例进展①；目标具体化配方见 §2.4；检验三问见 §2.4；目标分层级见 §2.4。

### Q7 复盘和评审是一回事吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "复盘也是评审，都带'评'字。" | 正是要翻的——用词形判同类 |
| 中 | "评审是事前把关，复盘是事后总结。" 结论对，闭环/事件触发说不清 | 结论对，机制缺 |

**产品侧 vs IT侧**：产品组答"冰链断链事故复盘——修了固件 bug 是执行、追到数据所有权是治理"；IT 组答"恒信对账事故复盘——两条行动项各配负责人期限"。同一个"复盘管改进"。

**反转话术**（对应 §5.2 + 案例进展⑤）：复盘（retrospective）容易被顺手划进"评审"——反正都带"评"字。但它是两件事：**评审管"把关"**（干活之前/之中，判断适宜/充分/有效，在流程链条上），**复盘管"改进"**（干完了，事后总结，绕回起点）。复盘不在 IEEE 1028 的五类里，也不是 ISO 9000 的"评审"。复盘的通过标准同样要会前定：**每个行动项有负责人 + 截止日期、上轮行动项关闭率 ≥ 80%、问题按根因归类（而非甩锅）、记录归档可追溯**。复盘不产出"我们很努力"，产出"下一轮改什么、谁改、何时改完"。恒信对账事故复盘产出两条行动项——"变更必须先过评审对目标一关"和"UAT 改真实场景跑"，各配负责人和期限。**复盘的价值，一半在诊断，一半在闭环；只诊断不闭环的复盘，是把同样的错再复一遍。** 它还绕回起点，把上一轮教训变成下一轮评审的目标——这条"改进→把关"回路，第11章治理里叫"事件触发"，复盘就是那个事件源。

**参考答案要点**：§5.2 对比表；复盘通过标准见 §5.2；案例进展⑤；治理事件触发见第11章。

### Q8 UAT 三问——考的是确认的什么？

| 答案分级 | 形态 | 讲师判读 |

| 弱 | "业务方都点了，三问都过关不是更好？" | 正是要翻的——三问全"否"，确认根本没发生 |

| 好 | 三问对应预期用途三构成（目标用户/使用场景任务/环境与条件）+ 让业务方当测试员=把确认做成验证（对照需求清单打勾）+ 确认不能后补到上线后（上线后补确认=上线事故）+ 验证证明做对了、确认证明能用，缺一个另一个是自我安慰 | 三构成 + 案例 + 因果全到位 |

**产品侧 vs IT侧**：产品组答"M3 真实运输的三问——真实疫苗/真实路线/真实天气"；IT 组答"恒信月底对账三问——真实对账数据/真实月底时间点/真实并发"。同一个"放进真实场景"。

**反转话术**（对应案例进展③ + §4.1 + §4.4）：Ada 的三问，考的是预期用途的**三构成**：目标用户（给谁用——法务、财务、业务三方审批人，不是 IT 测试员）、使用场景/任务（用来干什么——月底对账、电子签章审批、审批人出差时手机处理）、环境与条件（什么情况下用——月末高峰并发、弱网、审批人休假交接）。三问全"否"，说明那次 UAT 没让真实场景当裁判——**前一种 UAT 测的还是需求；后一种 UAT 测的是场景。** 让业务方对着需求清单替你打勾，是把确认做成了验证。**确认不能后补到上线后——上线后补确认，就叫"上线事故"。** 把月底对账、电子签章、审批人休假交接三个真实场景排进下一轮 UAT，用真实数据、真实任务、真实时间点。验证证明"做对了"，确认证明"能用"——两个都要，缺一个，另一个就是自我安慰。

**参考答案要点**：案例进展③；预期用途三构成见 §4.1；UAT 本质见 §4.4；确认时机见 §4.4 末。

### Q9 "用例全过，说明不了上路能过"——在说什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "改用例，把'振动下温度记录连续'加进去就好了。" | 正是要翻的——把"场景问题"当"用例没写好"，没看见验证射程 |
| 中 | "确认在真实场景，测试用例管不到振动。" 结论对，因果链/射程说不清 | 判据用了一层，机制缺 |
| 好 | 验证射程在文档（没写"振动下连续"=不在射程内）vs 确认射程在场景（断档 30 秒是场景里显影的隐含需求）+ 因果链三段（隐含没进文档→只做验证→漏在体系外→测试全过没人用）+ 因果不是运气 | 射程 + 因果 + 案例全到位 |

**产品侧 vs IT侧**：产品组答"M3 台架稳得像桌面、真实车厢会颠——断档 30 秒"；IT 组答"恒信月底对账场景没人测——25 号后的合同真实对账时第一次出现"。同一个"测试环境里没有路"。

**反转话术**（对应案例进展④ + §3.4 + §4.2~4.3）：这不是"测试用例没写好"——改用例也白搭，因为**验证的尺子在文档里**：用例的参照是需求文档，需求文档里没有"振动下温度记录连续"，验证就够不着它（没文档 = 没参照）。断档 30 秒是**确认的射程**里现形的：确认的参照是真实场景（"疫苗能不能安全送到"），把产品放进场景，隐含需求漏没漏当场现形。**测试台架做得再好，也替代不了那辆会颠的车。** 老周那句话的深意是因果链：隐含需求没进文档 → 只做验证的团队让它漏在体系外（连被检验的机会都没有）→ 上线后功能全对、测试全绿，但用户处处别扭（没人用/对不上/卡死）。**"测试全过、没人用"不是运气问题，是因果问题。** 冰链三天真实运输抓出四个问题（断档 30 秒、低温掉电、箱门漏温、断网重连 40 秒），没有一个是测试用例能提前发现的——因为用例的参照是需求文档，真实场景的参照是"疫苗能不能安全送到"。

**参考答案要点**：案例进展④；验证射程见 §3.4；参照在场景见 §4.2；因果链见 §4.3；显影见 §4.3。

### Q10 给你们的部门做一次"三关体检"

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 泛泛"验收要认真、测试要全面"。 | 没落到七把尺子任何一把，不可检查 |
| 中 | 用一把尺子查出缺口（如"我们的 UAT 用的是造的数据""评审通过标准会后现想"） | 有判据，但只照了一面 |
| 好 | 七把尺子逐项打勾，挑出三个缺口各配一个可检查动作，说出先做哪把、两周后报告什么 | 体检完整，动作可执行，有复查机制 |

**产品侧 vs IT侧**：两组各给自己部门体检——体检表本身是同一份（七把尺子），这正是"三个看门人"概念领域中立的现场证明。

**反转话术**：这一章的判据不是彼此孤立的——三把尺子判据管"这个把关对什么参照"（说不出参照，三个词就糊成一个）、评审三问判据管"目标具体化了吗、三问答得上吗"（通过标准会前定、会后打勾）、评审三属性判据管"有团队、有结论、有记录吗"（没记录=聊天）、验证三要素判据管"对照+证据+认定齐吗"（证据覆盖全部规定需求）、确认三要素判据管"真实用户+任务+场景齐吗"（让业务方当测试员=把确认做成验证）、因果链判据管"只验证不确认→没人用"（是因果不是运气）、评审≠复盘判据管"这个活动是把关还是改进"（复盘要有行动项闭环）。**七把尺子合起来，才是一次完整的"三关体检"。** 不用等全打完——找到第一个"否"，就能开工。

**参考答案要点**：七把尺子见"本章判据"；作业指南见课后作业。

## 四、知识卡片

### 一页图（三个看门人 · 三把尺子 · 一条接力链）

```
三个看门人，三把尺子：
  评审 review 3.11.2 —— 对目标 · 确定（判断）· 不要求客观证据
    三问：适宜性（对症）→ 充分性（够全）→ 有效性（管用）
    目标具体化：对象 + 时限 + 可衡量结果；通过标准会前定
    系统性三属性：团队参与 · 结果文档化 · 过程文档化（没记录 = 聊天）
  验证 verification 3.8.12 —— 对规定需求 · 认定（证明）· 必须客观证据
    三要素：对照规定需求 + 客观证据 + 做出认定
    测试只是证据之一；逐级回收（V 模型右半边）；射程够不着隐含
  确认 validation 3.8.13 —— 对预期用途 · 认定 · 必须客观证据
    参照在场景里：真实用户 + 真实任务 + 真实场景（UAT/Beta/灰度/试运行）
    兜隐含需求（冰山水下）：只做验证不做确认 → 测试全过没人用

接力：评审（开工前·方向）→ 验证（交付时·需求）→ 确认（交给用户·用途）
六类评审洒全程：需求 → 设计 → 代码 → 测试 → 发布 → 复盘
辨析：评审 ≠ 复盘（把关 vs 改进）｜ 验证 ≠ 测试（证据 vs 手段）
```

### 金句（书"本章判据"提炼）

- **评审对目标，验证对需求，确认对用途。方向对不对、做对了吗、真实场景好用吗——三个看门人，三把不同的尺子，谁也替不了谁。**
- **这三个词不是"差不多"的三个说法——唯一共同点是中文翻译恰好都带一个"评/验/认"字，这是翻译伪朋友。**
- **要求是"路"，目标是"目的地"。评审的价值，就是在低头检查路况之外，抬头看看目的地对不对。**
- **没记录的评审不算评审，最多算聊天。**
- **测试报告是验证的输入，不是验证本身——别把验证窄化成"跑测试"，也别把"跑测试"升级成"验证过了"。**
- **验证的参照在文档里，确认的参照在场景里——真实场景自带答案。**
- **隐含需求像冰山，水面下的部分占了大半——验证是量吃水线的尺子，确认是把船开进那片水域的试航。**
- **只做验证不做确认，隐含需求系统性漏失——测试全过、没人用，不是运气问题，是因果问题。**
- **验收不是一句话，是三个看门人依次签字。评审签"方向对"，验证签"做对了"，确认签"能用"。**
- **评审管"把关"，复盘管"改进"——复盘的价值，一半在诊断，一半在闭环。**

## 五、课后作业

1. **书练习（与题卡同源）**：找出你们团队最近一次把"评审"做成"逐条核对需求"的例子——把这次评审重做一遍：先写出目标（对象 + 时限 + 可衡量结果），再问三问。（书练习 2）
2. **书练习**：用"三关"走一遍你们最近一次上线——评审（对目标）过了吗？验证（对需求）过了吗？确认（对用途）过了吗？缺的那一关，代价是什么？（书练习 11）
3. **回部门落地**：结合现状，用七把尺子（三把尺子 / 评审三问 / 评审三属性 / 验证三要素 / 确认三要素 / 因果链 / 评审≠复盘）给部门最近一次上线/验收做一次"三关体检"——给出最该改进的三个事项，每个落到一个可检查动作。**两周后回来报告**：哪一项做成了、哪一项卡住了、卡在哪把尺子上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，2 小时内完成一次体检：
>
> 1. **查三把尺子（尺1）**：这次上线/验收，"把关"动作各对什么参照——评审对目标了吗？验证对规定需求了吗？确认对预期用途了吗？有没有三个词糊成一个的地方？
> 2. **查评审（尺2 + 尺3）**：评审通过标准是**会前定**的还是会上现想的？目标具体化了吗（对象+时限+可衡量结果）？有结论、有记录、有下一步谁负责吗？
> 3. **查验证（尺4）**：验证三要素齐吗——对照（需求成文了吗）、证据（有客观证据吗）、认定（有结论吗）？证据覆盖**全部**规定需求吗？测试是不是被当成了验证本身？
> 4. **查确认（尺5）**：确认是"真实用户 + 真实任务 + 真实场景"吗？用的是真实数据、真实时间点、真实并发吗？隐含需求在真实场景里显现并处理了吗？
> 5. **查因果链（尺6）**：有没有"只做验证没做确认"的迹象——功能全对、测试全绿，但用户用起来别扭、对不上账、没人用？
> 6. **查复盘（尺7）**：最近一次复盘是"把关"还是"改进"？有行动项、负责人、截止日期、闭环吗？
>
> 卡住时：找到第一个"否"就能开工，不必打完全部。产出三件最该改进事项（每条 = 一个可检查动作）。
