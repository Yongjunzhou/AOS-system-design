## 一、单元导读

### 主题

设计开发怎么落地？——方案不是写出来的，是种出来的：**一棵树**（枝干=概要定义、叶子=详细定义）、**三个动作**（分解、分配、分析）、**一条链**（五层链上四遍"长叶子、搬叶子、查叶子"接力）。

### 开场破题（对应章首误解现场）

念出恒信评审会里 Ada 的话："李工，这不是一篇方案。**这是一本小说。**"李工那六十页《合同审批系统总体设计方案》写了两个月、覆盖了需求调研的全部三百条需求。Ada 合上打印稿："方案不该是一篇文章，应该是一棵树。一篇文章是线性的，读者只能从头读到尾。可是你的方案有五种读者——法务要看审批规则、财务要看校验和台账、业务要看怎么发起、开发要知道模块边界、运维要知道怎么部署。**五个人的问题分散在六十页里，谁也找不到自己那一枝。**"

李工不服："树？树能装下三百条需求吗？"Ada："正因为有三百条需求，才必须是树。文章装不下三百条需求——**文章没有叶子。**"

让各组表态：如果你坐在评审会里，你会觉得 Ada 在故弄玄虚吗？方案不是写出来的吗？写得越详细、越全面，不是越好吗？**六十页的方案，难道不比一页的树更负责任吗？**

### 本单元要反转的直觉

- **设计方案写得越详细越好，六十页比一页树强**（× 散文不可定位/承接/追溯；没有结构的详细只是堆砌）
- **概要定义就是架构定义，换个名字而已**（× 概要定义是结构骨架文档，架构是系统不可还原的涵义）
- **一条需求分给两个模块做，双保险**（× 违反 1:1：重复实现、验证无对象、变更难定位）
- **分解就是多列几条**（× 语义四查 + 指标三场景 + 七种反模式）
- **符合性分析写"本节点满足上述需求"就够了**（× 空话；要对每片叶子说清"怎么满足、指标多少"）
- **先把需求全部写完，再开始设计**（× 结对设计骨架先行、填充并行；悬空叶子最后才暴露）
- **指标拆不动的就先不管**（× 标注"向下一层传递"，让指标不消失）
- **第4章的"分析"和第6章的"分析"是一回事**（× 需求分析是加工（往前看），符合性分析是检查（往后看））
- **三个动作是同一棵树的三个步骤**（× 分解在树内、分配分析在树间）

### 本轮题卡的内在逻辑（10 题 2×5）

**第一组 · 概念与原理（先立概念）**：Q1 设计文档是树（概念本身·破题）→ Q2 五概念关系 + 需求/方案相对（概念关系）→ Q3 概要定义≠架构（改名真悖论）→ Q4 1:1 约束（一片叶子一个归宿）→ Q5 三个动作各自的自检（原理清单）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 李工第一次分解漏多两查（分解四查）→ Q7 冰链可靠度 0.989（指标三场景）→ Q8 悬空叶子该拆片还是该加枝（分配 + 骨架先行）→ Q9 符合性分析"重要合同"（符合性三问 + 逐层清账）→ Q10 回部门"设计方案体检"（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。恒信合同审批系统（流程软件）与冰链 M3 温控箱（硬件 × 软件）是同一个概念的两面——一棵树、三个动作在两边都能验：恒信把"审批流程"长成 SYS 叶子、把 SYS 叶子搬到"审批引擎"；冰链把"全程可靠度"拆成硬件 × 固件 × 云端、把"温度控制"叶子搬给温控模块。这正是"设计开发落地"领域中立的证据。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜设计文档为什么必须是树？**
"Ada 说李工那六十页《总体设计方案》'是一本小说'。设计文档为什么必须是树、不能是散文？树的'叶子'指的是什么？"

追问：① 散文的三宗罪——不可定位、不可承接、不可追溯，各自用树的一个构件回答（可查询/可承接/可追溯）？② 树为什么是唯一让"导航路径"与"承接路径"合一的形态——列表、表格、网状各自差在哪（列表没有层次 / 表格是映射表不是内容组织形态 / 网状没有唯一根，回答不了"这条需求归谁"）？③ 你们部门最近一份"总体设计"，五类读者各能几秒定位到自己的枝，还是一篇文章从头读到尾？

**Q2｜五者什么关系？中间层为什么是双面人？**
"请给出 概要定义、详细定义、分解、分配、符合性分析 的关系（一句话）。再把'需求/方案相对'放进去——中间层为什么是双面人？"

追问：① 一棵树 = 枝干（概要定义·组织承接）+ 叶子（详细定义·定义验证）——两个部分各回答什么问题？② 三个动作里，为什么只有"分解"在树内、分配和分析都在树间（"一旦到分配，你已经站在两棵树之间了"）？③ "相关方需求是需求（它是需求文档）" vs "相关方需求是方案（它承接原始需求）"——两个都对，靠什么判据分清？④ 五层链是几遍"长叶子、搬叶子、查叶子"（四遍）——为什么叫"动作"不叫"步骤"？

**Q3｜为什么叫"概要"，不叫"架构"？**
"'概要定义'和'架构定义'只差一个词。这一章为什么偏要叫'概要'，不叫'架构'？"

追问：① 三个理由——与"架构"撞车（承载重量级含义的词命名轻量级文档）/ 不对称（孪生兄弟叫"详细定义"、"详概分离"原则自己叫概）/ 名实相符？② "概要定义是目录，详细定义是正文，架构是这本书真正要表达的思想"——目录和思想什么关系？③ "设计树的形状就是架构（日常语境'架构'就指系统结构）" vs "架构是系统不可还原的涵义（第8章定义）"——两个都对，靠什么判据分清？④ 你们管叫"架构文档"的那份东西，里面有没有不可还原的涵义，还是一张结构图？

**Q4｜"双保险"错在哪？**
"李工想给'金额校验'在审批引擎和前端各放一份：'两个模块都做，双保险，一个坏了还有一个。'——错在哪？"

追问：① 1:1 的三个理由——避免重复实现、保证验证唯一对象、让变更可定位，哪个对你们团队最致命？② 枝梢挂叶子是 N:1、叶子归宿枝梢是 1:1——聚合与定位两个方向为什么不能搞反？③ 一片叶子需要两个枝梢才能承接，这个信号说明什么（该拆片了——1:1 逼你拆得足够细）？④ 你们系统里有没有"同一逻辑两处实现"？当初为什么分给了两个模块？

**Q5｜三个动作各自拿什么尺子自检？**
"'分解让枝梢长出叶子，分配让叶子搬到下一棵树，分析检查每一片叶子都挂得对。'——三个动作各自拿什么尺子自检？为什么说它们是互相把门的？"

追问：① 分解四查（覆盖完整/不超出/逻辑一致/约束继承）——为什么"覆盖完整"和"不超出"是姊妹对（一个防漏、一个防多，方向相反都让树偏离）？② 指标分解三场景（可拆分/下放/暂不分解）——最忌讳的是什么？③ 分配三自检（全覆盖/1:1/N:1 合理）——哪个最容易被"觉得没问题"带过（全覆盖）？④ "分配检出来的问题，一半是分配自己的错，一半是上游的错"——三个动作怎么互相把门？

### 第二组 · 落地与实践

**Q6｜漏了一片，多了一片——违反哪一查？**
"李工把'合同校验'拆成金额校验、条款校验、资格校验三片叶子，又顺手加了一片'合同打印'。Ada：'漏了一片，多了一片。'——漏的是哪片、多的是哪片？各自违反哪一查？"

追问：① 覆盖完整性（漏：期限校验）vs 不超出性（多：合同打印 = 影子需求）——一漏一多方向相反，都让树偏离该承接的需求；你们更常犯哪个？② 影子需求为什么危险（多出来的内容没经上游确认 = 范围蔓延）？③ 过分解：把"怎么做"混进"做什么"——为什么分解只切 What、不写 How（下游失去实现自由）？④ 你们最近一次拆需求，漏了什么、多加了什么？哪一查没做？

**Q7｜可靠度 0.989——这个数字拆错了吗？**
"M3 '全程可靠度 ≥ 0.99'，老周拆成硬件 0.995 × 固件 0.995 × 云端 0.999，乘积约 0.989——不够 0.99。老周：'这个数字是不是拆错了？'——他拆对了吗？这个'不够'说明了什么？"

追问：① 0.99 属于指标三场景哪一类（可拆分：串联乘积函数关系）？② "数字一旦落纸，立刻发现预算不够，就得回炉"——为什么说这是"可拆分"的价值（把账算清楚，不是靠感觉）？③ 最忌讳的是把第三种（算不清）当第二种（下放）硬塞给一片叶子——为什么那片叶子怎么都满足不了？④ 你们一条带指标的需求（响应时间/可用性/成本）落到子需求时，真算了账，还是"差不多就行"？

**Q8｜该拆片，还是该加枝？**
"SYS-004.01 合同全文检索，在审批业务域、平台服务、数据与接口三个枝干上哪个都不像。硬塞给'合同台账'？台账只管存储不做检索。Ada：'一片叶子没有归宿，只有两种可能。'——哪两种？怎么区分？"

追问：① "该拆片（欠分解，这片太粗）" vs "该加枝（方案树没种全，确实缺一根'检索服务'）"——两个都像，靠什么判据分清？② 李工怎么判断的（拆得开吗——再拆就把"建索引/查索引"的接口也写进去 = 设计不是需求）？③ 为什么说"分配检出来的问题，一半是分配自己的错、一半是上游的错"——欠分解找分解、缺枝找方案？④ 你们有没有"悬空"的需求/功能？当时硬塞给谁了，还是补了枝？

**Q9｜"重要合同要审批"，为什么没人认领？**
"符合性分析评审上，李工卡在'审批引擎'：'重要合同要审批'——金额 ≥ 500 万或三年期以上——这条需求哪去了？'我把它归到合同校验去了，校验过了就触发重点审……'Ada 摇头：'那审批引擎的定义里，有没有写承接重点审触发？'——没有。问题出在哪？"

追问：① 语义符合性三问（覆盖度/映射正确性/分析具体性）——这个案例违反的是哪一问（覆盖度：需求写着"重要合同要审批"，方案里"进入重点审批流程"这个动作没枝梢承接）？② "本节点满足上述需求"为什么是空话——合格句式长什么样（针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失）？③ 指标符合性：满足/降级/丢失——降级为什么必须说明理由并经评审确认（不能默默降）？④ 为什么符合性分析要每层分配完立刻做（逐层清账，不是最后算总账）？⑤ 你们最近一次评审，有没有"本节点满足上述需求"这句空话？

**Q10｜给你们的部门做一次"设计方案体检"**
"结合你们部门现状，用六把尺子（散文还是树 / 概详分离 / 分解四查+指标三场景 / 分配三自检 / 符合性分析 / 结对骨架先行）给最近一份设计文档做一次体检——给出最该改进的三个事项，每个落到一个动作。"

追问：先做哪把尺子？为什么？两周后回来报告什么？

## 三、点评要点·讲师版

> 点评纪律：先表态后翻案 / 反转精确不造新误解 / 判据配机制 / 归责到可对照动作 / 教机制不教断言 / 先立尺子再翻案 / 拉开强度层次 / 每个纠正落到可操作动作 / 单一权威不另立标准 / 网搜当佐证。

### Q1 设计文档为什么必须是树？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "方案写详细点、全面点，当然是负责。" | 正是要翻的——把"长度"当"质量"，没看见散文三宗罪 |
| 中 | "文档要有结构，用树/目录组织。" 结论对，说不出树的必然性 | 概念对，机制缺 |
| 好 | 散文不可定位/不可承接/不可追溯 + 树三构件（根层级/分类节点/末级节点）+ 树是唯一让"导航路径"与"承接路径"合一的形态 + 叶子=能 1:1 搬走的原子条目 | 机制 + 判据 + 必然性全到位 |

**产品侧 vs IT侧**：产品组答"M3 的设计文档是树还是散文——五个子系统各能找到自己的枝吗"；IT 组答"恒信合同系统五类读者（法务/财务/业务/开发/运维）各查各的"。同一个"树 vs 散文"。

**反转话术**（对应 §1.1 + 章末第一反转）：李工的病不是写得不好——他写得太像文章了。散文有三宗罪：**不可定位**（"审批驳回"在第几页？五类人只能从头找起，找不到就开始猜）、**不可承接**（没有模块边界，开发只能全文通读自己揣摩）、**不可追溯**（需求变了，只能人肉找相关性，找不全就漏改）。而一棵树恰好是三件事：根与层级给"层层细化、同层同级"，分类节点当文件夹，**末级节点（枝梢）是需求挂靠的钩子、也是开发认领的任务单**。为什么必须是树？因为设计开发的内涵要求可验证、可落实——内容必须条目化；条目化带来数量爆炸——必须组织；而**树是唯一能让"导航路径"与"承接路径"合一的形态**：顺着树走一遍，就是一次完整的承接验证。**"设计方案"的"设计"，不是"写"，是"种"。**

**参考答案要点**：散文三宗罪见 §1.1；树三构件见 §1.1 表；"为什么必须是树"三步推导见 §1.1 末。

### Q2 五者什么关系？中间层为什么是双面人？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "概要定义是结构、详细定义是内容，分解分配分析是过程。" | 名词背出来了，关系结构/树间树内/双面人说不出 |
| 中 | "一棵树=枝干+叶子；三个动作在每层重复。" 结构对，需求/方案相对缺 | 关系对，机制缺 |
| 好 | 一棵树=枝干（概要·组织承接）+叶子（详细·定义验证）+ 分解树内、分配分析树间 + 中间层是双面人（对上层方案/对下层需求，靠相对角色判据）+ 五层链=四遍"长叶子、搬叶子、查叶子"（动作非步骤） | 关系 + 分界 + 相对角色全到位 |

**产品侧 vs IT侧**：两组都套同一句关系——冰链的"温控需求→硬件/固件/云端组件"与恒信的"SYS 叶子→审批引擎/前端/台账"。树不挑角色：需求是树，方案也是树。

**反转话术**（对应 §2.0 + §3.1）：一棵树只有两种东西：**枝干（概要定义）管组织与承接**——"结构是什么、承接了谁"；**叶子（详细定义）管定义与验证**——"每个模块具体做什么"。三个动作里，**只有"分解"在树内**（枝干 ↔ 叶子）；**分配、分析都在树间**——"一旦到分配，你已经站在两棵树之间了"。新手最容易把三个动作当同一棵树的三个步骤，其实一棵树内部只能发生分解。中间层为什么是双面人？**需求不是文档的固有标签，而是它相对于相邻文档扮演的角色**——相关方需求对上层（原始需求）是方案、对下层（业务流程）是需求；接力棒是同一份文档，只是换了角色。所以五层链不是四个大步骤，是**四遍"长叶子、搬叶子、查叶子"**——动作是每层重复的固定功课，步骤是串行的一次性流程。

**参考答案要点**：三个动作发生地见 §2.0 表；需求/方案相对见 §3.1 表；文档结对与两阶段见 §3.1；动作非步骤见 §3.1 末。

### Q3 为什么叫"概要"，不叫"架构"？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "架构定义听起来更专业，叫架构多好。" | 正是要翻的——没看见"架构=文档"词汇病的坑 |
| 中 | "架构是更大的概念，概要定义是它的结构骨架。" 结论对，三理由说不全 | 结论对，机制缺 |
| 好 | 三理由（与架构撞车/不对称/名实相符）+ "概要定义是目录、详细定义是正文、架构是这本书要表达的思想" + 目录不是思想但定位思想 | 理由 + 比喻 + 判据全到位 |

**产品侧 vs IT侧**：产品组答"冰链'架构=一张框图画完就没人维护'的病"；IT 组答"恒信'总体设计方案'六十页文章叫不叫架构"。同一个"文档是文档、架构是架构"。

**反转话术**（对应 §1.3 + 概念卡片·概要定义）：不是换个名字。"架构"在全书是极其重量级的词——第8章定义：**系统不可还原的涵义**（ISO/IEC/IEEE 42010），那是关于系统根本性质的决定：几个要素、怎么连接、哪个决定不可推倒重来。三个理由：**一、撞车**——用一个已经承担重量级含义的词去命名轻量级文档，读者十有八九以为"架构就是这份文档，画出来就是架构了"（这是冰链团队的病）；**二、不对称**——孪生兄弟叫"详细定义"，按对称该叫"概要"，而且那个原则本来就叫"详概分离"；**三、名实相符**——它比架构轻得多，是初步的、概要的、用来组织与承接的。"概要定义是目录，详细定义是正文，架构是这本书真正要表达的思想。目录不是思想，但好的目录帮你定位思想。"李工问 Ada："为什么不叫架构定义？"Ada 反问："你写的那六十页文章，叫不叫架构？""当然不是。""所以别把文档叫成架构——**文档是文档，架构是架构，名字上就要分开。**"

**参考答案要点**：三理由见 §1.3；概要定义概念卡片（定义/对立/辨析/误区/判据）。

### Q4 "双保险"错在哪？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "两个模块都做，一个坏了还有一个，更保险。" | 正是要翻的——没看见 1:1 是硬约束 |
| 中 | "违反 1:1，一片叶子只能一个归宿。" 结论对，三理由说不全 | 结论对，机制缺 |
| 好 | 1:1 三理由（避免重复实现/验证唯一对象/变更可定位）+ N:1 聚合 vs 1:1 定位方向别搞反 + 一片叶子需要两个枝梢=该拆片 | 机制 + 判据 + 信号全到位 |

**产品侧 vs IT侧**：产品组答"M3 温度采集逻辑同时放主控板和云端，同一逻辑两处实现"；IT 组答"金额校验同时放审批引擎和前端，改一处漏一处"。同一个"违反 1:1"。

**反转话术**（对应 §2.2 + 概念卡片·分配）：不是"双保险"，是**双倍的风险**。一片叶子只能搬到下一棵树的唯一一根枝梢上——三个理由：**避免重复实现**（同一逻辑两处实现，改一处漏一处，这是重复代码的根源）、**保证验证有唯一对象**（"金额校验"做得对不对，该测哪个模块？1:1 让验证有唯一目标）、**让变更可定位**（需求改变对金额校验的要求，只改一个模块）。注意一个对称：**枝梢挂叶子是 N:1（聚合），叶子归宿枝梢是 1:1（定位）**——很多团队把方向搞反：让叶子挂多个枝梢（违反 1:1），却让一个枝梢只挂一片叶子（浪费聚合）。反过来，**一片叶子需要两个枝梢才能承接，本身就是一个信号——该拆片了**。1:1 约束真正的作用，是逼你拆得足够细。

**参考答案要点**：1:1 约束三理由见 §2.2；N:1 对称见 §2.2；悬空叶子两因见 §2.2 末 + 案例进展③。

### Q5 三个动作各自拿什么尺子自检？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "分解就是把需求拆细，分配就是分给模块，分析就是检查一下。" | 名词有了，四查/三自检/空话/把门关系全缺 |
| 中 | "分解四查、分配三自检、符合性分析两维。" 清单背出了，姊妹对/全覆盖陷阱/把门说不清 | 清单对，机制缺 |
| 好 | 分解四查（覆盖完整/不超出/逻辑一致/约束继承）+ 指标三场景 + 分配三自检（全覆盖/1:1/N:1 合理）+ 符合性分析（语义+指标，空话不行）+ 三个动作互相把门（欠分解找分解、缺枝找方案） | 清单 + 机制 + 把门全到位 |

**产品侧 vs IT侧**：两组都背同一套尺子——冰链拆"温控功能"、恒信拆"合同校验"，四查三自检纹丝不动。尺子是领域无关的。

**反转话术**（对应 §2.1~2.3 + 本章判据 3/4/5）：三个动作各有一把尺子。**分解**：语义四查——覆盖完整（防漏）、不超出（防多）、逻辑一致（防矛盾）、约束继承（防丢）——"覆盖完整"和"不超出"是姊妹对，**一个防漏、一个防多，方向相反但都让树偏离**；加指标三场景（能拆就拆/拆不动下放/算不清传递）。**分配**：三自检——全覆盖（都搬了）、1:1（一片一个归宿）、N:1 合理（每枝梢 2~5 片较优，以语义为准）——最容易被"觉得没问题"带过的正是全覆盖。**分析**：符合性分析，语义 + 指标两维，"本节点满足上述需求"是空话。为什么互相把门？**分配检出来的问题，一半是分配自己的错、一半是上游的错**——悬空叶子，欠分解要找分解、方案缺枝要找方案。三个动作是一道流水线，每一道都替下一道把门。

**参考答案要点**：语义四查见 §2.1 表；指标三场景见 §2.1；七反模式见 §2.1；分配三自检见 §2.2 表；符合性分析见 §2.3。

### Q6 漏了一片，多了一片——违反哪一查？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "拆得不够细，再拆几条就好了。" | 正是要翻的——没看见"漏"和"多"是两个方向的病 |
| 中 | "漏了期限校验，多了合同打印。" 结论对，违反哪一查/影子需求说不清 | 判据用了一层，机制缺 |
| 好 | 漏期限校验=覆盖完整性失败、多合同打印=不超出性失败（影子需求）+ 一漏一多方向相反都让树偏离 + 过分解把 What/How 混起来压缩设计空间 | 判据 + 机制 + 反模式全到位 |

**产品侧 vs IT侧**：产品组答"M3 拆'温控功能'漏了'低温保护'、多加了'语音播报'"；IT 组答"恒信拆'合同校验'漏期限、多加了打印"。同一个"漏多两查"。

**反转话术**（对应案例进展② + §2.1）：李工漏的是**期限校验**——父需求"金额 ≥ 500 万或三年期以上要重点审"里，期限校验在他拆的叶子里没有对应，这是**覆盖完整性失败**；多的是**合同打印**——"校验"枝梢上不该长"打印"这片叶子，这是**不超出性失败**，多出来的内容没经上游确认，就是**影子需求（范围蔓延）**。Ada 说："分解是精确切分，不是顺手多列。"补期限、删打印、再复查约束继承——四查齐了才算过。还要防七种反模式里的**过分解**：把"怎么做"混进"做什么"——"支持温度控制"是需求，"先加热再保温"是设计；后者一旦写进需求，下游就失去了选择"怎么实现"的自由。**分解是需求侧的动作，只切 What，不写 How。**

**参考答案要点**：案例进展②；语义四查表见 §2.1；七反模式表见 §2.1；过分解 What/How 见 §2.1。

### Q7 可靠度 0.989——这个数字拆错了吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "拆错了，三个数乘起来不够 0.99，应该把数调大。" | 正是要翻的——把"发现不够"当"拆错"，没看见算账的价值 |
| 中 | "0.99 可拆分，串联乘积函数关系。" 场景判断对了，回炉价值说不全 | 场景对，价值缺 |
| 好 | 可拆分（串联乘积）+ 数字落纸发现预算不够就得回炉（把账算清楚不是靠感觉）+ 最忌讳第三种当第二种硬塞（那片叶子怎么都满足不了）+ 拆分可以重算（硬件降到更低/加冗余/改架构） | 场景 + 价值 + 禁忌全到位 |

**产品侧 vs IT侧**：产品组答"M3 可靠度 0.995×0.995×0.999≈0.989"；IT 组答"恒信整笔审批 48 小时 → 发起+各级审批+签章+归档各段加起来 ≤48h（串联可加）"。同一个"能拆就拆、把账算清"。

**反转话术**（对应 §2.1 指标三场景 + 案例进展②镜照）：老周拆对了——0.99 属于**可拆分**：子指标之间存在函数关系，可靠度是串联乘积（任何一个环节断链，整条链就断），三个数乘积约 0.989。**这个"不够"不是拆错，正是"可拆分"的价值**：数字一旦落纸，立刻发现预算不够，就得回炉——硬件降要求、加冗余、改拓扑，把账算出来，而不是靠感觉"应该差不多"。指标三场景的顺序：**能拆就拆**（函数关系）、**拆不动就下放**（同值继承，如工作温度 -20℃~60℃ 每个部件都要满足）、**算不清就传递**（系统级耦合如整机噪声，标注"向下一层传递"）。**最忌讳的是假装能拆**——第三种当第二种，硬塞给一片叶子，结果那片叶子怎么都满足不了。

**参考答案要点**：指标分解三场景见 §2.1；串联可加/串联乘积例见 §2.1 场景一；"最忌讳假装能拆"见 §2.1 场景三。

### Q8 该拆片，还是该加枝？

### Q9 "重要合同要审批"，为什么没人认领？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "归到合同校验了呀，校验过了就触发重点审，没问题。" | 正是要翻的——"归宿了"不等于"接住了" |
| 中 | "审批引擎没写承接重点审触发，语义覆盖失败。" 结论对，三问/空话/时机说不全 | 判据用了一层，机制缺 |
| 好 | 语义符合性三问（覆盖度/映射正确性/分析具体性）违反覆盖度 + "本节点满足上述需求"是空话/合格句式 + 指标满足/降级/丢失（降级要理由经评审）+ 每层分配完立刻做（逐层清账不是最后算总账） | 三问 + 句式 + 时机全到位 |

**产品侧 vs IT侧**：产品组答"M3 '低温保护'需求在'固件'定义里没写承接，温度数据照样丢"；IT 组答"恒信重点审触发没枝梢认领，三年期合同漏重点审=合规事故"。同一个"归宿≠接住"。

**反转话术**（对应案例进展④ + §2.3）：分配只保证"每片叶子都有归宿"，不保证"每个枝梢都接住了叶子"。李工把"重要合同要审批"归到合同校验，但**"进入重点审批流程"这个动作本身，没有枝梢承接**——需求写着"重要合同要审批"，方案里"审批"这一环没人认领，语义覆盖失败。这不是小事：没有这个承接，三年期合同会和其他合同一样走普通流程，是合规事故。符合性分析的三问：**覆盖度**（方案定义提到每条承接需求了吗）、**映射正确性**（需求"安全审计"对方案"操作日志"——范围不同）、**分析具体性**（"通过实现 X 机制满足 Y 需求，具体体现在 Z"，不是"本节点满足上述需求"）。合格句式：**"针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"**——写不出的，等于没分析。指标符合性还要守住：方案承诺的指标不能低于需求要求的指标，**降级必须说明理由、经评审确认，不能默默降**。时机上，**每层分配完立刻做**——分析越晚，缺陷离源头越远、返工越贵；逐层清账，不是最后算总账。

**参考答案要点**：案例进展④；语义符合性三问见 §2.3；空话与合格句式见 §2.3；指标符合性三档见 §2.3；时机见 §2.3 末。

## 四、知识卡片

### 一页图（一棵树 + 三个动作 + 一条链）

```
一棵树：枝干（概要定义·结构·组织承接）  +  叶子（详细定义·内容·定义验证）
       任取一条需求 → 说出挂在哪根枝梢（末级节点）；叶子 = 能 1:1 搬走的原子条目
       结构不轻易变，内容随时长（分开维护）

三个动作：分解（树内·枝梢长叶子）→ 分配（树间·叶子 1:1 搬走）→ 分析（树间·检查挂得对）
       分解四查：覆盖完整/不超出/逻辑一致/约束继承 + 指标三场景：可拆分/下放/暂不分解
       分配三自检：全覆盖/1:1/N:1 合理
       符合性分析：语义 + 指标（满足/降级/丢失）；"本节点满足上述需求"= 空话

一条链：五层链 OR→STR→BP→SR→PA = 四遍"长叶子、搬叶子、查叶子"
       中间层是双面人：对上层是方案、对下层是需求；骨架先行、填充并行
       概要定义 ≠ 架构：目录是文档、架构是不可还原的涵义
```

### 金句（书"本章判据"提炼）

- **方案不是写出来的，是种出来的——一棵树、三个动作，在整条链上接力。**
- **一棵树：枝干是概要定义（管结构），叶子是详细定义（管内容）——结构不轻易变，内容随时长。**
- **概要定义是目录，详细定义是正文，架构是这本书真正要表达的思想。目录不是思想，但好的目录帮你定位思想。**
- **一片叶子，只能被搬到下一棵树的唯一一根枝梢上——1:1，避免重复实现、保证验证唯一对象、让变更可定位。**
- **分解让枝梢长出叶子，分配让叶子搬到下一棵树，分析检查每一片叶子都挂得对。**
- **"本节点满足上述需求"是空话——要写"针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"。**
- **分析是每层都要做的动作，不是最后的仪式——逐层清账，不是最后算总账。**
- **一棵树内部只能发生分解；一旦到了分配，你已经站在两棵树之间了。**
- **一片叶子没有归宿，只有两种可能：欠分解，或方案树没种全——先判断是哪种，再动。**

## 五、课后作业

1. **书练习（与题卡同源）**：找一份你们团队最近的设计文档，判断它是树还是散文。如果是散文，找出它"不可定位""不可承接""不可追溯"各一个具体例子。（书练习 1）
2. **书练习**：把你们系统的一个功能域画成一棵概要树（根→末级），标出分类节点和末级节点（枝梢），再取一根枝梢分解成 3~5 片叶子；用语义分解四查检验（覆盖完整吗？不超出吗？一致吗？约束继承吗？）。（书练习 2/3）
3. **回部门落地**：结合现状，用六把尺子（散文还是树 / 概详分离 / 分解四查+指标三场景 / 分配三自检 / 符合性分析 / 结对骨架先行）给部门最近一份设计文档做一次"树"体检——给出最该改进的三个事项，每个落到一个可检查动作。**两周后回来报告**：哪一项做成了、哪一项卡住了、卡在哪把尺子上。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，2 小时内完成一次体检：
>
> 1. **查树形（尺1）**：这份文档是树还是散文？任取一条需求，能说出它挂在哪根枝梢上吗？五类读者各能几秒定位到自己的枝？
> 2. **查概详分离（尺2）**：枝干和叶子分开维护吗？修剪枝条能不动叶子吗？长新叶能不动枝干吗？每片叶子有编号/描述/指标/验收/映射吗？
> 3. **查分解（尺3）**：任取一根枝梢，语义四查过吗？带指标的需求走了三场景判定吗？
> 4. **查分配（尺4）**：全覆盖（叶子数对账）？1:1（一片一个归宿）？N:1 合理？有悬空叶子吗——是欠分解还是缺枝？
> 5. **查符合性（尺5）**：每个枝梢都有合格句（针对需求 A、通过 X 满足 Y、指标 Z 满足/降级/丢失）吗？降级有理由经评审吗？有"本节点满足上述需求"空话吗？
> 6. **查结对（尺6）**：每个文档结对走"分解→分配→分析"吗？骨架先行、并行填充吗？
>
> 卡住时：找到第一个"否"就能开工，不必打完全部。产出三件最该改进事项（每条 = 一个可检查动作）。
