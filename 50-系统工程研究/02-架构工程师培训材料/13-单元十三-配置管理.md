## 一、单元导读

### 主题

这一章回答一个绕不开的问题：**让一直在变的东西说得清**——配置管理到底是干什么的？疾控审计问水忠："这批疫苗记录是哪一版固件采的？"水忠觉得冤："我们版本号不是有吗？v2.1、v2.2、v2.3 都标着呢。"结果查不清。产品开发经理永兵也在场，补了一句："咱们把箱子卖出去的时候，跟客户讲的是'全程可追溯、断链必告警'。今天连自己都追溯不清，这四个字还怎么站得住？"大多数人对此的直觉正是：**版本管理做好了，就等于配置管理做好了。** 这一章要推翻的，正是这个直觉——版本只是时间轴上的刻度，基线才是把"已经批准的决定"冻结下来、让一切变化得以言说的参照；而"配置"——那个被"参数文件""个性化设置"遮蔽的概念——是这一切的地基。本章的骨架是：**三个词**（配置/版本/基线，各管内容/位置/资格）→ **一横一竖**（版本顺着流、基线垂直切）→ **变更控制**（冻结→变更→再冻结）→ **四大活动**（标识/控制/状态记录/审计）→ **配置管理三问**（应该是什么/实际是什么/怎么变成这样的）。还有一个新增的边界：**受控分级**——目的、目标也要受控，但走的是与功能/分配/产品"成熟度轴"正交的**变更权威轴**（谁批准、谁变更、变了意味什么）：目的/原则/红线入治理基线、目标/成功判据入协议级、需求及以下入产品 CM 基线。

### 开场破题（对应章首误解现场）

念出疾控审计那场问询：冰链的 M3 冷链温控箱在市场跑了一年多，散在约五千台物流车上。这年春天，一个 bug 冒了出来——箱温降到 -20℃ 以下时，传感器偶发丢读数，一秒的数据偶尔缺一格。水忠修好、发新固件 v2.3，三个月分批升级约三千八百台。然后疾控中心来审计一批疫苗运输记录，问了一个以前从没人问过的问题："这批记录，是在哪一版固件下采集的？你们从这批之后，采集逻辑、断链判定升级过没有？"水忠觉得这问题简单："查一下这批设备当时跑的固件版本。"结果查不清——升级记录只有一句"已推送 v2.3"，没有"哪台设备、哪个时间、从哪一版升到哪一版"的明细。逸人翻出产线台账，补上制造侧那半截底细："出厂时每批设备烧的哪版固件、各批多少台，账上有；可它们出了厂，App 推送升过几回级、哪批升了哪批没升——这边没账。中间那根线，两头没接上。"产品开发经理永兵也在场，低声补了一句："咱们把箱子卖出去的时候，跟客户讲的是'全程可追溯、断链必告警'。今天连自己都追溯不清，这四个字还怎么站得住？"水忠愣住了。——追溯断的，正是这根两头没接上的线，也是冰链卖给客户的产品承诺。

让各组表态：水忠那句"我们有版本号啊，怎么就不算配置管理了"冤不冤？永兵那句"这四个字还怎么站得住"扎不扎心？大多数人一开始都站在水忠这边——这正是这一章要推翻的直觉。

### 本单元要反转的直觉

- **配置 = 系统设置里那页参数 / 个性化设置**（× 参数是零件，配置是装好的整机——配置是"被记录的形态"，是这一切的地基）
- **版本管理做好了 = 配置管理做好了**（× 版本只是刻度；配置管理是标识+控制+状态记录+审计四活动，缺基线和变更控制版本也管不住）
- **有版本号 = 有基线**（× 版本是刻度，基线是资格——被批准+被冻结+作参照，三特征全有才是基线）
- **基线一旦建立就永远不能改**（× 基线可以变更，但必须走变更控制，改完建立新基线。"冻结"不是"死锁"）
- **没有基线，变化也说得清——反正有 git 历史**（× git 历史是记录，基线是被批准、被冻结、被全项目认可的参照）
- **配置管理是文档的事，跟代码、硬件没关系**（× 任何配置项——代码、固件、硬件板卡、数据、图纸——都可立基线、走变更控制）
- **小团队、小产品，配置管理是大公司的负担**（× 配置管理可剪裁——至少"版本可指认、变更可追溯"；负担大头来自"查不清"的返工和事故）
- **变体就是版本，改个名字而已**（× 变体管空间、版本管时间，二者正交）
- **改一个参数就要改代码、重编译、重发布——这是正常的**（× 这是"变与不变没分离"的信号）
- **同一设计号的板卡，装这块还是那块无所谓**（× 场景二判据：选 A 选 B 特性/形态变了吗——类型级=分配、实例级=配置）
- **目的、目标也要纳入配置管理——那就跟需求一样走 CCB 管着就行**（× 要受控但走另一条变更权威轴：目的/原则/红线入治理基线、目标/成功判据入协议级、需求及以下才入产品 CM 基线——"谁批准、谁变更、变了意味什么"不同，不能全挤进 CCB）

### 本轮题卡的内在逻辑（10 题 2×5 + 方法时刻）

**第一组 · 概念与原理（先立概念）**：Q1 配置/版本/基线各管什么 + 配置溯源（破题·概念本身，永兵"四个字还怎么站得住"把产品承诺的代价摆上桌）→ Q2 两族概念关系 + 契约链（概念关系）→ Q3 参数文件是配置吗（真悖论）→ Q4 版本有了就有基线吗（真悖论·一横一竖 + 版本/基线溯源 + 受控分级）→ Q5 没有基线变化就不可言说（原理）。由"是什么"走到"为什么"。

**第二组 · 落地与实践（用尺量）**：Q6 客户能改的"告警阈值"到底是不是配置（判据运用·配置三问）→ Q7 final_2 连版本都算不上？（判据运用·版本判据+基线三问）→ Q8 一次"合规的固件升级"四活动复盘 + 编号事故（判据运用·四大活动）→ **Q9 方法时刻·判据主义**（规则 15：判据主义 = 判据运用，亲手给"版本/基线"各立可检验判据，含判据主义三问 + **三五句转述给完全外行**——不重复出独立方法操作题）→ Q10 回部门配置管理体检（落地生根）。判据运用 + 落地动作。

### 同类分组说明

产品组与 IT 组答同一组题，答案互为镜像。这一章的题尤其适合镜像对照：产品组的"配置管理"是 M3 温控箱——固件、硬件板卡、云端追溯平台、App 都是配置项，追溯温度记录必须知道固件版本；IT 组的"配置管理"是合同审批系统——构建产物、需求文档、部署包都是配置项，回滚必须知道"回滚到哪一版"。产品组出问题靠"批次追溯查得清"、IT 组靠"回滚有地址"——**同一个概念、两个世界、判据不变**（配置提供内容 / 版本提供位置 / 批准提供资格），这正是本章"概念不挑行业"的现场证明。永兵那句"四个字还怎么站得住"：产品组读作对客户的追溯承诺，IT 组读作对回滚/审计的可答账——承诺与账，是同一个判据（三问任何时刻答得出）的两面。本章的承重柱是"配置"（版本/基线都从它派生），两组都能拿"配置=被记录的形态"核自己的产品。

## 二、题卡（打印分发）

**答题要求**：组内讨论 25 分钟 / 答案 ≤5 行 / 上台讲解 4–5 分钟 / 观点不同必须给理由。

### 第一组 · 概念与原理

**Q1｜"版本号不是有吗？"为什么还是查不清？**
"疾控审计员问水忠：这批疫苗四月运输、全程温度记录正常——你们要证明，这批记录是在哪一版固件下采集的？采集逻辑、断链判定升级过没有？水忠说：这简单，查版本号，v2.1、v2.2、v2.3 都标着呢。可结果查不清。产品开发经理永兵也在场，听完低声说了一句："咱们把箱子卖出去的时候，跟客户讲的是'全程可追溯、断链必告警'。今天连自己都追溯不清，这四个字还怎么站得住？"水忠愣住了。为什么'版本号是有了'，'这批记录是哪一版采的'还是答不上来？'全程可追溯、断链必告警'这个卖给客户的承诺，断在哪一环？这一章要钉的三个词——配置、版本、基线——各管什么？各自从哪来、往哪去？"

追问：① 配置提供"内容"、版本提供"位置"、批准提供"资格"——三者为什么谁也不能替谁？② 水忠的 v2.3 是版本还是基线？基线三问一答就穿帮，穿在哪一问？③ 永兵那句"这四个字还怎么站得住"——'全程可追溯、断链必告警'靠配置管理哪条判据/哪个活动兜底（状态记录答'它是怎么变成这样的'、配置审计对'实物与记录一致'）？④ 配置这个词从哪来（硬件工业组件选配 + con-/figurare 组合成形）？为什么说配置是"这一切的地基"？⑤ 你们产品里"被批准、被冻结、全生命周期拿它对照"的那一版，能一指就指出来吗？你们对客户承诺过的"可追溯/可回滚"，靠哪一条判据兜底？

**Q2｜配置、版本、基线两族概念什么关系？**
"请给出 配置、配置项、配置信息 三词的关系；再给出 版本、修订、变体、基线 四词的关系——说明为什么'版本顺着流、基线垂直切'，为什么变体与版本正交，为什么基线是变体 × 版本的交叉点被盖章？"

追问：① 三个配置术语互相引用、首尾相连，为什么锚定'实体'后就不循环了？② 一份文档为什么既是'配置信息'又是'配置项'——两个层面怎么不冲突？③ 契约链：需求对方案、方案对实现，为什么说基线是每一级契约的'冻结端'、版本是'交付端'？它在第6章的结对处怎么长（候选声明 + 骨架先行）？④ 你平时说的"版本"，到底指的是四词里的哪一个？

**Q3｜参数文件到底是不是配置？**
"李旭指着 App 设置页说：这就是咱们的配置，客户能改的都在这页——温度上报间隔、超温告警阈值、断电告警开关、蜂鸣器音量。文正却说：配置不是这个参数，是那整套关联在一起塑成的'M3 的行为形态'。参数文件到底是不是配置？什么判据分清'配置'和'配置信息里的一个条目'？"

追问：① 变与不变的分离——为什么客户改上报间隔不用动固件、不用重编译（可变部分被外置），反过来改一个参数就要改代码、重编译、重发布是什么信号？② 三个隐形过滤器（类别/记录/关联边界）怎么从'实体的全部特性'切出'配置'子集？③ 配置这个术语为什么会被当成参数文件（硬件'组件选配'→软件'参数文件'→数据'元数据治理'的漂移，ISO 10007 把它钉回）？④ 你们产品里"客户能改的那几个开关"，到底是配置，还是配置信息里的条目？

**Q4｜版本有了，就有基线了吗？**
"水忠觉得冤：我们有 v2.1、v2.2、v2.3，版本号都标着呢，升级也走流程了、李旭也验证过了，怎么就不算配置管理了？这一章说：版本只是刻度，基线才是参照；版本顺着流、基线垂直切。既然版本和基线都跟时间有关，为什么说它们方向完全不同？什么判据一眼分清'它是版本还是基线'？"

追问：① 里程桩 vs 收费站——为什么版本'顺着路'、基线'挡住路'？版本为什么诞生（变化连续、沟通必须离散——报障时说不出口'改过17次的固件'）？② 基线三问（被批准/被冻结/作参照）一问答不出会怎样？基线这个词从哪来（军品工程'版本失控、改坏了找不回来'的教训→受控快照→ISO 10007 凝结）？③ 变体与版本为什么正交（有几种形态 vs 走到第几步）？④ 第12章说不可逆决策要提前投资——这一章给'投资之后'配了什么守护（基线冻结 / 变更控制）？⑤ 目的、目标要不要也纳入配置管理？这一章说'要受控，但走的是另一条分级'——为什么目的/原则/红线入治理基线、目标/成功判据入协议级、需求及以下入产品 CM 基线？这条'变更权威轴'和功能/分配/产品的'成熟度轴'怎么正交？

**Q5｜没有基线，变化就不可言说——凭什么？**
"『从基线出发，一切变更都可描述；离开基线，一切变化都不可言说。』这句话凭什么成立？为什么'有 git 历史'替代不了基线？"

追问：① 描述一个变化必须有一个'从哪变起'的原点——没有原点像什么（在茫茫大海上说'我在动'，却没有岸标）？② git 历史是记录，基线是批准+冻结+作参照——两者差在哪一个动作（批准）？③ 基线建立之后，变化怎么走（变更控制五步在守什么）？配置管理的全部工作为什么是让'三问'任何时刻都有答案？

### 第二组 · 落地与实践

**Q6｜客户能改的"告警阈值"，到底是不是配置？**
"水忠抱着一台已出厂的 M3，翻来覆去想文正的话：App 设置页上客户能改'上报间隔'、'告警阈值'——这到底是不是配置？文正反问：你改那个'告警阈值'，改的是什么？请用配置三问给'告警阈值'做一次裁决：它是配置，还是配置信息里的一个条目？"

追问：① '告警阈值'单独过三问，和'上报间隔 + 告警阈值 + 断链判定逻辑 + 采集算法'合起来过三问，结论差在哪——为什么是'关联成整体'那一问在起作用？② 客户改'上报间隔'不用动固件、不用重编译——这是'变与不变的分离'；反过来改一个参数就要改代码、重编译、重发布，是什么信号？③ 为什么审计员问'这批记录是哪一版固件采的'，问的不是参数、是形态（哪套采集逻辑+判定逻辑组合成的行为）？④ 你们最常改的那个参数，改了之后"这台产品当时是什么样"还能说得清吗？

**Q7｜final_2 连版本都算不上？**
"恒信运维玉杰每次发布把构建产物扔进日期文件夹：'2026-05-12''2026-05-18'。两个月后合同状态流转 bug 暴露，万辉要'回滚到上上个版本'，打开'2026-05-18'文件夹——里面 final.zip 和 final_2.zip 分不清哪个是哪个。徐漾说：'final_2 连版本都算不上，遑论基线。'请把这句话的量尺摆出来——用版本判据和基线三问，final_2 到底差在哪？"

追问：① 版本判据一问：final_2 能精确对应到'哪一次完整构建'吗（哪个代码提交、包含哪几条变更）？② 基线三问：它被批准了吗 / 被冻结了吗 / 作参照了吗？③ 为什么说'版本是回滚的地址，基线是变更的参照'——恒信补了发布基线后，'上上个版本'从猜测变成了什么（一句可执行的指令）？④ 你们上次回滚，"回滚到哪"能一指就指出来吗？

**Q8｜一次"合规的固件升级"——四大活动各守哪扇门？**
"冰链补了配置管理，做了一次'合规的固件升级'：水忠先写变更申请、做影响评估（'固件行为变化，历史温度记录的采集与判定逻辑随之变化，需知悉在役设备批次分布'）；文正把升级提到变更控制会（水忠汇报、李旭评估、董勐确认云端兼容、逸人报批次分布、文正拍板），固件 v2.4 升为新固件基线；每台设备从哪一版升到哪一版、升级时间、结果进版本台账；三个月后李旭抽查二十台，一台台账写 v2.4、实物还是 v2.3（升级失败未重试），记录修正、补推送。请用四大活动（标识/控制/状态记录/审计）复盘这次升级——哪一步在防'批次追溯查不清'？哪一步在防'实物与记录对不上'？"

### Q1 "版本号不是有吗？"为什么还是查不清？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "水忠说得对，版本号有了、流程走了，审计员是没事找事。" | 正是要翻的——把"有版本号"当"配置管理做好了" |
| 中 | 能说"版本不是基线"，但三个词各管什么说不清 | 词背了，判据（基线三问）没用起来 |
| 好 | "版本只答'走到第几步'（v2.3），没答'哪一版被批准、被冻结、作参照'——基线三问一问答不出；追溯温度记录要的是形态（哪套采集+判定逻辑），不是参数；配置是这一切的地基——从硬件组件选配凝结成'被记录的形态'；永兵点破'全程可追溯、断链必告警'=卖给客户的产品承诺，断在固件这一环：出厂台账有、App 推送没账，两头没接上；水忠缺状态记录（只有一句已推送）和配置审计。" | 三词分工 + 基线三问 + 四大活动 + 配置溯源 + 追溯机制 + 产品承诺代价全咬合 |

**产品侧 vs IT侧**：产品组答"追溯温度记录必须知道固件版本——v2.1 采的和 v2.3 采的断链判定不一样"；IT 组答"回滚/审计要能回答'这个部署是哪次构建'"。两边都容易把"版本号"当"基线"——**版本只是刻度，基线才是资格**。永兵那句"四个字还怎么站得住"：产品组读作对客户的追溯承诺，IT 组读作对回滚/审计的可答账——承诺与账，是同一个判据（三问任何时刻答得出）的两面。

**反转话术**（对应章首 + 13.2.1/13.2.3/13.2.4 + 13.4.2）：水忠那句"我们有版本号啊"错在两处——第一，他把"配置"当成了"参数"：采集算法、断链判定、告警逻辑关联在一起塑成的 M3 的行为形态，才是配置；第二，他把"版本"当成了"基线"：v2.3 只回答"走到第几步"，它没回答"哪一版被批准、被冻结、全生命周期拿它作参照"。**基线三问一问答不出——它只是刻度，不是参照。** 永兵那句"这四个字还怎么站得住"，点的是这场审计失败的真正代价——**"全程可追溯、断链必告警"是冰链卖给客户的产品承诺**：追溯一条温度记录要的是形态（"这批记录是'哪套采集逻辑 + 判定逻辑'采出来的"），形态由配置提供、位置由版本提供、资格由批准提供——三者缺一不可才成基线，四个字才站得住。追溯链断在哪一环？出厂时每批设备烧的哪版固件、各批多少台，产线台账上有；可它们出了厂，App 推送升过几回级、哪批升了哪批没升——这边没账。中间那根线，两头没接上。水忠缺的还不止基线：升级记录只有一句"已推送 v2.3"，是状态记录缺位；从没核对实物与记录，是配置审计缺位。**不是版本号有了，配置管理就好了；是四大活动一个都不能少。**

**参考答案要点**：配置/版本/基线三分工见"开篇·本章枢纽" + 13.2.1/13.2.3/13.2.4；永兵"全程可追溯、断链必告警"=产品承诺见 §13.1；配置溯源（组件选配/词源）见 13.2.1；四大活动见 §13.4.2；案例进展①（形态 vs 参数）。

### Q2 配置、版本、基线两族概念什么关系？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "配置、版本、基线是一个东西的三种叫法。" | 正是要翻的——三层关系没立起来 |
| 中 | 能说"配置项/配置/配置信息锚定实体"，但版本/修订/变体/基线四词混 | 配置族对了，版本族关系缺（变体×版本正交没接上） |
| 好 | "配置项=对象（管哪些）、配置=属性（它是什么样）、配置信息=记录（拿什么核对），锚定实体解循环；版本=时间（走到第几步）、修订=内部次数、变体=空间（有几种形态）、基线=资格（被盖章）；基线=变体×版本的交叉点被批准冻结；契约链每级都有冻结端和交付端，在结对处长成候选声明+骨架先行。" | 两族关系全到位，正交 + 交叉点 + 契约链 + 第6章咬合全接上 |

**产品侧 vs IT侧**：产品组答"医疗加强版 v2.4 = 变体×版本，被批准冻结成基线"；IT 组答"合同系统需求版本 v2.doc 是版本、被徐漾批准立功能基线"。两边都要注意**契约链"基线对谁、版本对谁"是每级重复的通用机制，不是某一级专属**。

**反转话术**（对应 13.2.1/13.2.3/13.3.3/13.4.5）：三个配置术语为什么绕？因为它们互相引用、首尾相连，形成循环定义——要懂一个得先懂另外两个。解耦的办法，是往环里引入一个不依赖任何配置术语的锚点——**实体**。配置项=被纳入管理的实体（对象）、配置=实体被记录的关联功能+物理特性（属性）、配置信息=记录特性的资料（记录）——三者都锚定"实体"，彼此不再互引。版本族四词更得分开：**版本**回答"走到第几步"（时间先后）、**修订**回答"内部改了几次"（更细粒度）、**变体**回答"有几种形态"（空间并存）——变体和版本**正交**；而**基线 = 变体 × 版本的交叉点被批准冻结**（"医疗加强版 v2.4"这个形态，被批准、被冻结，就是基线）。契约链把这个机制推广到整条开发链：需求对方案、方案对实现，每一对相邻环节都是局部甲乙方——**基线是每一级契约的冻结端、版本是交付端**，每一级都重复出现，只因视角不同看起来"属于"不同的人。它不抽象：在第6章结对处，就长在"候选声明 + 骨架先行"里——叶子"声明我归谁"是向方案方提要求、方案方"验证对不对"是验收，先约好的枝梢清单就是这一环先谈好的接口。

**参考答案要点**：配置三词解耦见 §13.2.1；版本/修订/变体/基线见 §13.2.3/13.2.4/13.3.3；契约链 + 第6章咬合见 §13.4.5。

### Q3 参数文件到底是不是配置？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "那页设置就是配置，客户能改的就是配置。" | 正是要翻的——把配置当参数文件 |
| 中 | "配置不是参数。" 结论对，判据缺 | 配置三问、变与不变的分离没接上 |
| 好 | "配置三问一过：'告警阈值'被记录了（记录边界✓）、是功能特性（类别边界✓），但单独一个不关联成整体（关联边界✗）——它是配置信息里的一个条目，不是配置；合起来的整套行为形态才是配置；客户改参数不用重编译=变的部分被外置，改参数要改代码重编译=变与不变没分离的信号；配置被当参数文件是术语漂移（组件选配→参数文件→元数据治理）。" | 三问打勾 + 三过滤器 + 变与不变的分离 + 术语漂移溯源全到位 |

**产品侧 vs IT侧**：产品组举"App 设置页告警阈值"；IT 组举"application.yml / 环境变量"。两边都是同一把尺子——**参数是零件，配置是装好的整机；参数文件只是记录"形态"的图纸，形态本身才是配置**。

**反转话术**（对应 13.2.2/13.3.1 + 案例进展①）：李旭那页设置确实"是配置信息的一部分"——那些参数被记录下来了。但**参数文件只是记录"形态"的图纸，形态本身才是配置**。要分清"配置"和"配置信息里的一个条目"，用配置三问：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——"告警阈值"单独过三问，前两问✓、第三问✗：它是配置信息里的一个条目，不是配置；"上报间隔+告警阈值+断链判定+采集算法"关联成整体塑成的行为形态，才是配置。这背后是**变与不变的分离**：客户改上报间隔不用动固件、不用重编译，正因为可变的部分（参数）被外置了、不变的核心（固件逻辑）只写一遍；反过来改一个参数就要改代码、重编译、重发布——那是变与不变没分离的信号。它为什么会被当参数文件？术语漂移：硬件"组件选配"→软件"参数文件"→数据"元数据治理"，ISO 10007 把它钉回"实体被记录下来的关联功能与物理特性"。

**参考答案要点**：配置三问见 §13.2.2 / 本章判据1；变与不变的分离见 §13.3.1 / 本章判据2；术语漂移溯源见 13.2.2 概念卡②③格；案例进展①（参数是零件、配置是整机）。

### Q4 版本有了，就有基线了吗？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "版本号有了、升级走流程了，就是配置管理了。" | 正是要翻的——把版本当基线 |
| 中 | "版本不是基线。" 结论对，一横一竖没画出来 | "顺着流/竖着切"的机制没接上 |
| 好 | "版本与时间同向（横·刻度·里程桩·流动），基线垂直插入切断时间（竖·闸门·收费站·冻结）；版本因变化连续、沟通离散而生（切时间的刀）；基线三问（被批准/被冻结/作参照）一问答不出就只是刻度；基线源于军品版本失控教训凝结成 ISO 10007；变体与版本正交，基线=变体×版本交叉点被盖章。" | 一横一竖 + 版本/基线溯源 + 基线三问 + 正交 + 交叉点全到位 |

**产品侧 vs IT侧**：产品组画"M3 固件版本链 v1.0→v2.3，基线竖切在批准点"；IT 组画"合同系统版本 v2.doc→v3.doc，功能基线在徐漾批准时竖切"。两边都要翻"有版本号=有基线"——**把版本当基线，等于把里程桩当成收费站：你确实知道路走了多远，但没人拦着检查，任何车都能随意改道**。

**反转话术**（对应 13.3.2/13.3.3/13.2.4 + 章末）：版本和基线都跟时间有关，但方向完全不同——**"横"与"竖"不是上下方向，而是与时间轴的关系**。版本与时间同向，像尺子上的刻度沿时间轴排开，只描述位置、不改变时间轴性质，它是**流动**的；基线垂直插入时间轴，像横在路中间的闸门把时间**切断**——线左是自由区（版本随便流动）、线右是受控区（任何变化必须停下接受批准）。版本为什么诞生？变化是连续的，沟通必须是离散的——报障时说不出口"改过 17 次的固件"，需要一把把时间切成可指认格子的刀。生活类比：版本是高速路上的里程桩（顺着路、告诉你走了多远），基线是收费站（横在路中间、过站要检查）。判据一句话：**它顺着流（版本），还是竖着切（基线）？** 再问基线三问——被批准了吗？被冻结了吗？全生命周期作参照吗？一问答不出，它只是刻度。基线这个词从哪来？军品工程"版本失控、改坏了找不回来"的惨痛教训，共同体摸出"受控快照"的做法，由 ISO 10007 凝结成定义。水忠有 v2.1/v2.2/v2.3，那是里程桩；他没有的是收费站。补一层：变体与版本正交（空间并存 vs 时间先后），基线 = 变体 × 版本的交叉点被批准冻结。再点一句：第12章说不可逆决策要提前投资——这一章给的守护正是**基线冻结**（识别出不可逆，把它冻住）和**变更控制**（改它必须走正式的路）。最后补一条新划的边界（§13.2.5）：**目的、目标要不要也纳入配置管理？** 要受控，但走的是另一条分级——功能/分配/产品基线（连同运行/部署配置）按**生命周期成熟度**切（"要做什么、由谁实现、实际是什么"），另有一条**正交的变更权威轴**按"谁批准、谁变更、变了意味什么"切：目的/原则/红线入**治理基线**（治理层批准·一变就是"系统该不该存在"的危机）、目标/成功判据入**协议级**（需供双方约定·变更要重谈承诺）、需求及以下入产品 CM 基线（CCB 批准·正常工程动作）。别把这三档全塞进 CCB——**谁批准、变了意味什么不同，管控的权威就不一样**（第14章 §14.3.3 专讲这条轴）。

**参考答案要点**：版本溯源（连续/离散）见 §13.2.3；一横一竖见 §13.3.2 / 本章判据6；基线三特征见 §13.2.4 / 本章判据5；基线溯源（军品凝结）见 13.2.4 概念卡②③格 + §1.2.1；变体与版本正交见 §13.3.3；守护架构决策见 §13.4.4 / 本章判据11。

### Q5 没有基线，变化就不可言说——凭什么？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "有 git 历史不就能查了吗？为什么要基线。" | 正是要翻的——把记录当参照 |
| 中 | "没基线查不清。" 结论对，机制缺 | "从哪变起"的原点没讲出来 |
| 好 | "描述变化必须有一个'从哪变起'的原点；git 历史是记录（流水账），基线是批准+冻结+作参照——差在'批准'这个动作；没有原点，'变了'就像在海上说'我在动'却没有岸标。" | 原点机制 + git 差在哪 + 岸标类比全到位 |

**产品侧 vs IT侧**：产品组答"追溯温度记录必须从固件基线出发"；IT 组答"回滚必须知道从哪个基线偏离"。两边都要翻"git 历史=基线"——**没有批准动作，历史只是流水账**。

**反转话术**（对应 13.3.4 + 自查5）：要描述一个变化，你必须有一个"从哪变起"的原点。"从 v1.0 变到 v1.1"这句话之所以有意义，是因为 v1.0 是一个所有人都认的、被冻结的、不会动的原点。没有这个原点，"变了"就没有参照——像在茫茫大海上说"我在动"，却没有岸标。**git 历史是记录，基线是被批准、被冻结、被全项目认可的参照。** 两者差在哪一个动作？——**批准**。git 的 commit 是"发生了什么事"的流水账，它没有回答"哪一版是所有人认的参照"；没有批准动作，历史只是流水账，不是基线。基线建立之后，变化就不能随手改——它必须走变更控制这条正式的路（变更申请 → 影响评估 → CCB 批准 → 实施 → 建立新基线）。配置管理的全部工作，就是让三个问题任何时刻都有答案：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——水忠答不上"它是怎么变成这样的"，正因状态记录缺位、变更历史散乱。

**参考答案要点**：没有基线不可言说见 §13.3.4 / 本章判据7；变更控制见 §13.4.1 / 本章判据8；配置管理三问见 §13.4.3 / 本章判据10；git 历史 vs 基线段落见自查5。

### Q6 客户能改的"告警阈值"，到底是不是配置？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "客户能改的，当然是配置。" | 正是要翻的——用"客户能改"判"是不是配置" |
| 中 | "不是配置，是配置信息里的条目。" 结论对，判据没摆 | 配置三问单独过 vs 合起来过没演示 |
| 好 | "三问一过：'告警阈值'被记录✓、功能物理特性✓、但单独一个不关联成整体✗——它是配置信息里的条目；'上报间隔+告警阈值+断链判定+采集算法'关联成整体塑成行为形态，才是配置；改参数让形态变了，温度记录的含义都跟着变。" | 三问打勾 + 三过滤器 + 形态机制全到位 |

**产品侧 vs IT侧**：产品组举"告警阈值"；IT 组举"审批链上的一个配置开关"。两边都要翻"客户能改的那几个开关就是配置"——**改的是参数，形态才是配置；你永远要知道它当时是哪副样子**。

**反转话术**（对应 13.2.2/13.3.1 + 案例进展①）：文正没有直接答，反问"你改那个'告警阈值'，改的是什么"。水忠说"固件里的一个参数"——这一句话里藏了三样东西：客户改的"上报间隔"这个**参数**是配置信息里的一个条目，被记录在案，没错；但"配置"不是这个参数，是这一整套东西——上报间隔、告警阈值、断链判定逻辑、采集算法关联在一起塑成的"M3 的行为形态"。用配置三问当场裁决：**它被记录了吗（记录边界✓）？它是功能/物理特性吗（类别边界✓）？它和其他特性关联成整体了吗（关联边界✗）？** ——"告警阈值"单独过三问，是配置信息里的一个条目；合起来过三问，才是配置。这背后是**变与不变的分离**：可变的部分（参数）被外置、核心（固件逻辑）只写一遍——所以客户改上报间隔不用重编译；反过来改一个参数就要改代码、重编译、重发布，就是没分离的信号。为什么审计员问"这批记录是哪一版固件采的"，问的不是参数、是形态？因为你改的任何一个参数，都可能改变"这台设备当时是什么样"——**参数是变了就变了的开关；配置是'这台设备被记录下来的样子'**。

**参考答案要点**：配置三问见 §13.2.2 / 本章判据1；三个隐形过滤器见 §13.2.2；案例进展①（形态 vs 参数）。

### Q7 final_2 连版本都算不上？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "有 final.zip 和 final_2.zip，文件名区分了不就行了吗。" | 正是要翻的——把文件名当版本 |
| 中 | "final_2 不是版本。" 结论对，判据没摆 | 版本判据一问、基线三问没接上 |
| 好 | "版本判据一问：final_2 不能精确对应'哪一次完整构建'（哪个代码提交、包含哪几条变更）——它连版本都不算；基线三问：没被批准/没被冻结/没作参照——遑论基线；版本是回滚的地址、基线是变更的参照；补发布基线后'上上个版本'从猜测变成可执行指令。" | 版本判据 + 基线三问 + 地址/参照 + 恒信闭环全到位 |

**产品侧 vs IT侧**：产品组举"固件升级记录只有一句已推送 v2.3"；IT 组举"日期文件夹 final_2"。两边是同一个病换文件后缀——**同一套概念：版本是回滚的地址，基线是变更的参照**。

**反转话术**（对应 13.2.3/13.3.2 + 案例进展② + 自查14）：玉杰的日期文件夹里，两个包一个新一个旧，文件名"final""final_2"，分不清哪个是哪个。徐漾说："你把'文件名的版本'当成了'版本'，把'版本'当成了'基线'——三层都差一点。"用尺子摆开：**版本判据一问**——final_2 能精确对应到"哪一次完整构建"吗（这份产物是哪个代码提交编译出来的、包含哪几条变更）？答不出——它连"版本"都算不上。**基线三问**——它被批准了吗？被冻结了吗？作参照了吗？——都没有。真正的版本号要能精确对应"哪一次完整构建"；没有它，"回滚到哪"都指不出来。**版本是回滚的地址，基线是变更的参照。** 你只有日期文件夹，既没地址、也没参照——两个月前还能说的"变了"，两个月后就"不可言说"了。恒信后来补了发布基线：一个包 = 一个版本号 + 对应代码提交号 + 对应需求基线 + 变更记录，一次一张发布记录。从此"上上个版本"从一句猜测，变成了一句可执行的指令。

**参考答案要点**：版本判据一问见 §13.2.3 / 本章判据4；版本是回滚的地址见 案例进展②；基线三问见 §13.2.4 / 本章判据5；恒信补发布基线见 案例进展②。

### Q8 一次"合规的固件升级"——四大活动各守哪扇门？

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | "有流程、有台账，这次升级很规范。" | 只看到"做了什么"，没看到"各防什么" |
| 中 | 能说出四大活动名字，但对应不上这次升级的每一步 | 活动名背了，判据（各答哪一问）没用起来 |
| 好 | "配置标识立固件基线（管'是什么'）；配置控制走 CR→影响评估→CCB→新基线（管'怎么变'，影响评估把采集逻辑变没变问住）；状态记录每台设备进台账（管'现在什么样'，防'批次追溯查不清'）；配置审计抽查二十台、修正记录补推送（管'实物与记录一致吗'，防'账实不符'）。旧事故四个洞补了三缺一——审计是这次才补的；编号事故若当时有 CR，评估单会写'编号规则被财务/台账/审计/电子签章四个下游引用、影响全部历史合同数据、不可逆性高'。" | 四活动对应 + 旧洞对照 + 防什么 + 编号事故跨章全到位 |

**产品侧 vs IT侧**：产品组答"固件升级批次追溯"；IT 组答"发布回滚与审计"。两边都要点破——**四大活动循环咬合，一个都不能少；配置管理的全部工作，是让三问任何时刻都有答案**。

**反转话术**（对应 13.4.2/13.4.3/13.4.4 + 案例进展③④）：四大活动各守一扇门：**配置标识**管"是什么"——固件是配置项、立过固件基线；**配置控制**管"怎么变"——固件升级走 CR → 影响评估 → CCB 批准 → 新基线；**状态记录**管"现在什么样"——哪台设备、哪个时间、升到哪一版，进版本台账；**配置审计**管"实物和记录一致吗"——抽查实物、核实记录与实物一致。这次升级每一步都对着一个洞补：影响评估单上那行"固件行为变化，历史温度记录的采集与判定逻辑随之变化"——正把"采集逻辑变没变"这个当年没问的问题问住了（补配置控制的洞）；影响评估还要再上溯一步——**这条变更仍在服务系统目的吗？** 高层级变更不止评估波及哪些配置项，还要确认它仍在服务系统目的（=守住第14章不变量链的目的环）；逸人把产线批次台账翻出来、把批次分布补进评估单，哪批出厂烧的哪版固件、各批多少台摊在纸面——"哪些批次的历史温度记录会改判定"，这次有据可查；每台设备进台账——当年只有一句"已推送 v2.3"，现在"它是怎么变成这样的"答得上了（补状态记录的洞）；三个月后抽查二十台、一台台账 v2.4 实物 v2.3、记录修正补推送——**配置审计**把"实物与记录对不上"逮住了，这个洞旧事故里从没补过。水忠说"版本号管好就行"是错觉——**不是做了版本号就等于做了配置管理，四大活动一个都不能少**；而四大活动围着同一个核心转：它应该是什么 / 它实际是什么 / 它是怎么变成这样的——**任何时刻都答得出，就是配置管理的全部工作**。跨章接线：第12章万辉改编号——如果当时有 CR + 影响评估，评估单上会写"编号规则这个配置项，被财务、台账、审计、电子签章四个下游引用；影响全部历史合同数据，不可逆性高"——这一行字写出来，他当天就不敢"今天就能上"。**个人尺子靠自觉，流程靠结构**；配置管理守护的正是第12章那些不可逆决策。

**参考答案要点**：四大活动见 §13.4.2 / 本章判据9；配置管理三问见 §13.4.3 / 本章判据10；案例进展③（合规固件升级）；守护架构决策 + 编号事故见 §13.4.4 / 本章判据11。

### Q9 亲手给"版本"和"基线"各立一条判据 + 讲给外行（方法时刻 · 规则 15）

| 答案分级 | 形态 | 讲师判读 |
|---|---|---|
| 弱 | 背书上的判据："版本是刻度，基线是参照。" | 只答了"是什么"，没做"立判据+失效边界+反例+转述"这个动作——方法没上手 |
| 中 | 立了一条判据（如"版本号能对应哪次构建"），但失效边界、反例、转述没给 | 判据立出来了，"是什么/失效边界/反例"三问只答了一问，转述没做 |
| 好 | "版本判据：编号能精确对应'哪一次完整构建'——失效边界：只有文件名/日期文件夹不够；反例：final_2 不是版本。基线判据：被批准+被冻结+作参照——失效边界：没被批准的版本只是刻度；反例：水忠的 v2.3 不是基线、同型号板卡选 3 号是分配不是配置。把'版本提供位置、批准提供资格'编进了判据。三五句转述'版本不是基线'给外行，讲到'没被盖章'卡住——缺口在'批准'这个动作。" | 立判据 + 失效边界 + 反例 + 三分工 + 转述压缩测试全到位 |

**产品侧 vs IT侧**：产品组给"基线"立判据时自然写"固件 v2.4 被 CCB 批准、冻结、作参照"；IT 组写"发布包被批准、回滚有地址"。两边立出的判据结构相同——**这正是本章方法时刻的核心：不考"方法名能不能背"，考"方法会不会用"；判据不挑行业**。

**反转话术**（对应方法底座时刻 = 判据主义；规则 15）：这是本单元的**方法时刻**——前面八题在讲"配置/版本/基线是什么"，这一题让你们亲手做一遍方法底座时刻：**判据主义**。水忠记住了"版本号"，却把版本当成了基线——他不缺版本号，缺的是判据：**版本和基线都不靠感觉认，靠可检验判据验。** 你亲手给"版本"立判据，最稳的那条正是本章的版本判据一问：**能精确对应到"哪一次完整构建"吗**——能，是版本；不能（只有文件名），还不算版本。再给"基线"立判据：**被批准 + 被冻结 + 作参照**——三问全"是"才是基线。按判据主义三问自检：它是什么（上面两条就是）？它的失效边界在哪（什么样的编号够不上版本 / 什么样的版本够不上基线）？能不能举反例（final_2 不是版本、没被批准的 v2.3 不是基线、同型号板卡选 3 号是分配不是配置）？——能举反例，判据才算立住。**转述 = 压缩测试**（v2.1 规则 15 形态）：判据立完，用三五句话把"版本不是基线"讲给一个完全外行的人——讲到哪卡住，缺口就在哪；讲得清=判据结构成型，卡壳处=边界缺口。绝大多数人讲到"没被盖章"会卡——那正是"批准"这个动作。你立的判据里，"配置提供内容、版本提供位置、批准提供资格"——版本判据里是"位置"，基线判据里是"资格"，三者缺一不可才成一个基线。反身：你刚给"基线"立的判据，拿到你们部门最大的配置项上量一下——合格吗？——**只有版本号只是见过，有判据才算拥有**。

**参考答案要点**：方法底座时刻（判据主义）见 00-案例设定 §三 第13章行；版本判据一问见 §13.2.3 / 本章判据4；基线三问见 §13.2.4 / 本章判据5；三分工见"开篇·本章枢纽" / 本章判据13；场景二判据见 §13.4.6；转述=压缩测试见第1章 §1.4.3；规则 15 注：判据主义章的方法时刻题=判据运用题、不重复出独立方法操作题。

### 一页图（书"本章概念总图"）

```

  三特征：被批准 / 被冻结 / 作参照
  三种正式基线：功能（要做什么）→ 分配（由谁实现）→ 产品（实际是什么）——按成熟度切
  受控分级（正交·变更权威轴）：目的/原则/红线→治理基线 / 目标→协议级 / 需求及以下→产品 CM 基线
版本顺着流、基线垂直切：里程桩顺着路排，收费站横在路中间
没有基线，变化就不可言说：描述变化必须有一个"从哪变起"的原点
变更控制：冻结 → 变更 → 再冻结（CR → 影响评估 → CCB → 实施 → 新基线）
四大活动：配置标识 → 配置控制 → 状态记录 → 配置审计（一个都不能少）
核心目的三问：应该是什么 / 实际是什么 / 怎么变成这样的——任何时刻都答得出
配置管理 = 架构决策的守护者：决策记录↔配置信息 / 不可逆识别↔基线冻结 / 推迟↔变与不变分离 / 影响分析↔变更控制（AD+ADR 纳管）
契约链：基线=每一级契约的冻结端，版本=每一级契约的交付端（结对处=候选声明+骨架先行）
两个易混场景：需求子集=需求配置=功能基线；同设计号选实体=类型级分配 / 实例级配置（选 A 选 B 形态变了吗）
三条铁律：协作要共同事实 / 长周期要组织记忆 / 担责要可答的账——可剪裁，底线"版本可指认、变更可追溯"
价值：省钱（返工/报废/精确召回）· 赚钱（变体/资质/速度）· 保钱（责任/知识）
```

### 金句（书"本章判据"提炼）

- **配置提供"内容"，版本提供"位置"，批准提供"资格"——三者齐备，才成一个基线。** 配置是这一切的地基——版本是配置项的演进刻度，基线是被批准冻结的配置信息。
- **配置三问**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——三问全"是"，才是配置。**参数是零件，配置是装好的整机。**
- **版本判据一问**：这一个编号，能精确对应到"哪一次完整构建"吗？能——是版本；不能（比如只有文件名）——它还不算版本。
- **基线三问**：被批准了吗？被冻结了吗（任何人不能随意改）？全生命周期拿它作参照吗？——三问全"是"，才是基线。
- **基线把目的冻成参照，原则库把目的冻成规则，评审定期把目的请回现场**——治理=目的的远程存续机制：所有者不在场，但目的必须在场（第14章 §14.3.3）。
- **版本顺着流、基线垂直切**——把版本当基线，等于把里程桩当成收费站。
- **没有基线，变化就不可言说**：任何变更必须能回答"从什么基线变到什么基线"；答不出，就还没有基线。git 历史是流水账，批准动作才让它成基线。
- **版本是回滚的地址，基线是变更的参照**——"冻结"不是"死锁"，基线可以变更，但必须走变更控制。
- **配置管理四大活动一个都不能少**：标识（是什么）→ 控制（怎么变）→ 状态记录（现在什么样）→ 审计（实物与记录一致吗）。
- **配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——任何时刻都答得出。
- 配置管理守护的正是第12章那些不可逆决策——**决策记录是决策的配置信息，基线冻结是不可逆决策的物理动作**；不受变更控制的 AD 不是架构，是草图堆。
- 场景二判据：选 A 选 B，特性/形态变了吗？**变了=配置（实例级），没变=分配（类型级）。**

## 五、课后作业

1. **书练习（与题卡同源）**：用"配置三问"找出你们产品里"客户/用户能改的参数"，逐个检验：它是配置，还是配置信息里的一个条目？（书练习 1）
2. **书练习**：用"配置管理四大活动"诊断你们团队——标识、控制、状态记录、审计，各打一个"有/缺/半吊子"，看缺的补上要做什么。（书练习 7）
3. **书练习（四问补薄）**：用第1章的四问法量"配置"或"基线"——它是什么、不是什么、从哪来、往哪去——哪一问你现在答得最薄？回本章概念卡片或 §1.2.1（基线的"凝结"故事）把它补上。（书练习 12）
4. **回部门落地**：结合现状，用配置三问、版本判据、基线三问、四大活动四个判据，给你们最大的一个配置项做一次"配置管理体检"——给出最该改进的三件事，每个落到一个可检查的动作。**两周后回来报告**：哪个判据测出不合格、补了哪个动作、效果如何。

### 作业指南（回部门落地的步骤 + 话术）

> 照着做，60 分钟完成一次配置管理体检：
>
> 1. **挑配置项（先立枢纽）**：选一个"你心里最有底、天天在用"的配置项——产品的主程序 / 固件 / 核心服务 / 数据表定义。最自信的，往往是基线三问最没打勾的。
> 2. **过配置三问（这算不算配置）**：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——确认它是配置，不是零散参数。**话术**："你说的'配置'，是那页参数，还是那整套关联成形的形态？"
> 3. **查版本判据（有版本吗）**：当前的版本号能精确对应到"哪一次完整构建"吗（哪个代码提交、哪次构建、包含哪几条变更）？答不出——它连版本都不算，更遑论基线。
> 4. **过基线三问（有基线吗）**：有没有一版被批准（谁批的、有没有记录）？被冻结（改它必须走变更控制）？全生命周期拿它作参照？——三问缺一，只是刻度不是基线。
> 5. **四活动打勾（标识/控制/记录/审计）**：配置标识——它在配置项清单里吗、有基线定义吗？配置控制——最近一次变更走 CR → 影响评估 → CCB 批准 → 实施 → 新基线了吗？状态记录——现在跑的是哪一版、升级历史有台账吗？配置审计——线上/实物 vs 记录对得上吗、抽查过吗？
> 6. **答配置管理三问**：它应该是什么（as-designed）？它实际是什么（as-built）？它是怎么变成这样的（变更历史）？——三问任一答不出，就是最该补的活动。
> 7. **出体检报告**：四活动各下结论（有/缺/半吊子），最该先补的是"答不出三问"对应的那个活动；最后一条建议照书抄——先给最大的配置项补一版"被批准、被冻结、作参照"的基线。小团队按剪裁原则做"够用的那一档"：版本可指认、变更可追溯，底线不省。
>
> 卡住时：答不上来的那一问就是最该补的；基线三问一问答不出 = 只是版本不是基线；"没有记录"的地方就是配置审计失守可能潜伏的地方。不必四活动全查完，找到第一个答不出的项目就能开工。
