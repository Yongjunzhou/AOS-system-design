## 一、类比：产品生产流水线

### 核心类比

用产品生产流水线来理解 EOS 平台的执行者场景。流水线上流动着物料或半成品，每个工位使用工艺对接收的半成品进行加工、装配、调试、测试等工作，生成加工后的半成品给下一个工位。

在 EOS 中，文档就是产品的半成品。文档的开发者接收前序文档，按照作业指南，利用各种资源对输入文档进行加工生成输出文档，再流转给后续的文档开发者。

```
生产线类比              →  EOS 平台对应
─────────────────────────────────────────────
半成品（物料）          →  输入文档（前序输出文档 PL5）
工位                    →  文档开发任务（场景业务 SL5 中的某个 PL6-A 活动节点）
工艺/作业指南            →  待定义（这是讨论的核心）
加工动作                →  文档开发工作（填写/审查/修订/审批）
资源（工具/量具/辅料）    →  参考文档/模板/检查清单/数据标准/引擎工具
加工后的半成品           →  输出文档（新的 PL5）
下道工序                →  后续活动节点（文档流转到下一个执行者）
```

### 执行者的真实处境

执行者打开平台时，面对的不是"一个系统"，而是一件事：

> "我接到一个任务——把文档 X 做出来。我需要知道：做成什么样、拿什么来做、按什么规矩做、做到什么程度算完、做完交给谁。"

这五个问号，就是作业指南要回答的全部。

## 二、文档开发工位的七维框架

参照制造业的"人机料法环测信息"七维工位设计框架，映射到文档开发工位：

### 人 —— 谁在做、和谁配合

| 子维度 | 工位上的体现 |
|--------|------------|
| **我自己** | 我是谁、我的角色权限、我能做什么操作 |
| **上游人** | 输入文档是谁写的——有问题可以追溯询问 |
| **下游人** | 做完交给谁——提前对齐期望、理解他的验收标准 |
| **同行人** | 和我在同一场景业务中并行干活的人——他们的进度影响我 |
| **裁决人** | 遇到问题找谁拍板——评审人、审批人、技术负责人 |

人在工位上不是"目录树里的一个名字"，而是**附着在资源和流转关系上的可达对象**——点击"用户需求 v2.1 张三"，可以发起询问；看到"李四等待接收"，可以提前沟通。

### 机 —— 用什么工具做

| 子维度 | 工位上的体现 |
|--------|------------|
| **编辑工具** | 文档正文的增删改、字段填写、格式化 |
| **导入/导出** | 从外部拿数据进来、把文档送出去 |
| **校验工具** | 字段合法性自动检查——"这个值不能为空""这个编码格式不对" |
| **计算工具** | 指标自动计算、数值自动汇总 |
| **对比工具** | 版本 diff——"上一次和这次改了什么" |
| **批注/讨论** | 在文档特定位置和上下游的人讨论 |
| **流程操作** | 提交审批、退回、签字、流转 |

机的设计原则：**工具不离开工位**。执行者不需要为了"对比两个版本"而跳转到另一个页面——对比功能就在编辑区的 TAB 里。

### 料 —— 拿什么来加工

料的两个层次：

```
料
├── 文档料（被动接收）—— 上游传过来的文档，我拿它们当原料用
│    例：需求文档、接口定义、合规要求
│    动作：接收 → 阅读 → 摘取关键数据 → 写入正文
│
└── 内容料（主动选用）—— 我在设计方案中要引用或选定的实体对象
     例：物料、零部件、供应商、标准件、软件模块、复用构件
     动作：查找 → 比对 → 选定 → 写入正文 → 若没有则触发寻源
```

| 子维度 | 工位上的体现 |
|--------|------------|
| **原料（输入文档）** | 上游工位传过来的文档——是我加工的直接对象 |
| **辅料（参考素材）** | 历史同类文档、填写示例、模板——辅助我写，但不进入产品结构 |
| **标准件（引用规范）** | 设计规范、数据标准、法规——我需要遵循但不需重写，直接引用即可 |
| **外购件（外部输入）** | 平台外工具生成的附件、外部系统提供的数据——来料但非平台内生产 |

料的三个关键属性：**来源**（谁给的）、**状态**（能不能用）、**版本**（用的是哪一版）。一样料来源清楚、状态就绪、版本明确——执行者才能放心用。一样料来源不明或状态未完成——系统应该在工位上标出来，让执行者知道"这里还缺料"。

### 法 —— 按什么规矩做

| 子维度 | 工位上的体现 |
|--------|------------|
| **标准/规范** | 必须遵循的设计方法、格式要求、术语约定 |
| **操作步骤** | 当前这一步的具体操作指引——做什么、怎么做 |
| **检查清单** | 自检项——交出去之前必须确认的条目 |
| **模板** | 预置结构的空白文档——"照着填就行" |
| **判定标准** | 什么算合格、什么算不合格——通过/不通过的硬标准 |
| **异常处理** | 遇到问题怎么处理——退回到哪一步、找谁裁决 |

法的层次：

```
标准（管全局）  →  通用设计规范、行业标准
  │
操作步骤（管流程） →  第3步：需求分析——逐项检查输入需求的完整性和一致性
  │
检查清单（管出口） →  交出去之前：
  │                    ☐ 所有必填字段已完成
  │                    ☐ 引用的规范版本已确认
  │                    ☐ 与上游矛盾点已标记并说明
  │                    ☐ 指标口径与输入文档一致
  │
判定标准（管合格） →  全部 ☐ 勾选 + 评审人签字 = 合格
```

### 环 —— 在什么条件下做

环在制造业指温度、湿度、洁净度。在文档开发工位中，它是**执行者所处的任务上下文和协作氛围**：

| 子维度 | 工位上的体现 |
|--------|------------|
| **任务上下文** | 我在整个端到端流程中的位置——前序完成了没、后续在等吗 |
| **时间上下文** | 这个任务有截止日期吗、我花了多少时间、还剩多少 |
| **并行上下文** | 和我同在一个场景业务下的其他文档在什么状态 |
| **变更上下文** | 上游的料变了，影响到我了吗 |
| **注意力保护** | 默认只展示和当前任务有关的信息，不相关的自动收起来 |

环的设计原则：**不制造噪音**。执行者进入工位，默认看到的就是"与当前这一步直接相关的全部信息，且仅此而已"。跨场景业务的状态、平台通知、无关文档的变更——收在可折叠的通知区里，不抢占主空间。

### 测 —— 做到什么程度算合格

测在制造业是检验。在文档开发中，它既是出口闸门，也是过程纠偏：

| 子维度 | 工位上的体现 |
|--------|------------|
| **字段级校验** | 实时——"编码格式不对""这个值超出范围"（红色边框） |
| **完整性检查** | 提交时——"还有 3 个必填字段为空" |
| **一致性检查** | 提交时——"§3.1 引用的指标值与输入文档 v2.1 §2.3 不一致" |
| **合规性检查** | 提交时——"引用的规范已经过期，最新版本是 v2.0" |
| **评审判定** | 人工——评审人在对应字段上批注/打回 |
| **签字确认** | 人工——评审通过、签署通过意见 |

测的两层：

```
运行时测（在执行者工位上自动发生）：
  → 字段级校验 / 完整性检查 / 一致性检查 / 合规性检查
  → 即时反馈，不让问题流到下一道工序

门禁测（在流转节点上由人执行）：
  → 评审 / 审批 / 签字
  → 人是最终的判定者，但系统把能自动检查的都先查了
```

### 信息 —— 把六要素串联起来的那根线

信息不是第七个独立的要素，而是**渗透在所有六个要素中的连接组织**：

```
      人 ──────────────── 料
      │                  │
      │    信息层          │
      │   （状态、版本、    │
      │    进度、变更、    │
      │    追溯、依赖）    │
      │                  │
      法 ──────────────── 环
      │                  │
      └──────── 测 ──────┘
```

信息回答的是**跨要素的连接问题**：

| 连接关系 | 信息回答 |
|---------|---------|
| 料 × 测 | "输入文档 v2.1 中的指标值，在你正文 §3.1 中是否被正确引用？" |
| 人 × 环 | "张三的任务完成了，你的输入文档已就绪，可以开始了" |
| 料 × 法 | "你引用的通用设计规范 v1.0 已经过期，新版 v2.0 已生效" |
| 机 × 法 | "检查清单 10 条中还有 4 条未通过，确认后才可以提交流转" |
| 人 × 料 | "用户需求 v2.1 的作者张三在线，点击即可询问" |
| 环 × 人 | "同一场景业务的李四刚提交了接口定义 v1.1，你的 §3.2 可能需要更新" |

信息层的核心形态是**自动关联和主动推送**——它不是让执行者去查询，而是在工位上实时呈现。

**关键设计问题**：哪些关联变化需要"推"给执行者（主动通知），哪些只需要"拉"的时候有（点击可查）？

推送边界取决于：这个变化是否影响执行者**当下能做决策或能动手做事**。上游文档版本变了影响我正文内容 → 推；同场景业务中无关文档的进度更新 → 不推，收在可展开的通知列表里。

### 制造业工位 vs 文档开发工位：一张对照表

| 维度 | 制造业工位 | 文档开发工位 | 在页面上的位置 |
|------|-----------|-------------|--------------|
| **人** | 操作工、班组长、质检员 | 执行者本人、上下游协作者、评审人、审批人 | 右侧·协作面板 + 正文中的协作痕迹 |
| **机** | 设备、工具、量具 | 编辑/校验/对比/批注/流程按钮 | 底部·操作栏 + 正文 TAB 里的工具 |
| **料** | 原料、半成品、辅料、标准件 | 输入文档、参考素材、规范标准、外部附件 | 右侧·输入文档面板 + 正文中的内联引用 |
| **法** | 工艺文件、作业指导书、检验标准 | 操作步骤指引、检查清单、模板、判定标准 | 右侧·操作步骤面板 + 检查清单面板 |
| **环** | 温度、湿度、洁净度、照明 | 任务上下文、时间约束、并行进度、变更感知 | 顶部·进度条 + 右侧·变更通知 |
| **测** | 量具、检具、试验设备 | 实时字段校验、完整性/一致性/合规性自动检查、人工评审 | 正文中的红色边框 + 提交前阻塞提示 |
| **信息** | 工单、报工、物料追溯 | 跨维度关联：料→正文引用追踪、法→测勾连、人→料归属、料→环状态 | **不单独占位，渗透在所有区域中** |

## 三、内容料与文档正文的双向纠缠

### 内容料的特殊性

以一份采购技术规范为例：

```
正文 §3 技术要求
  │
  ├── §3.1 主控芯片
  │     型号：STM32F407VGT6
  │     参数：Cortex-M4, 168MHz, 1MB Flash
  │     来源：物料库 ✓ 已有（料号 MAT-IC-00342）
  │
  ├── §3.2 电源模块
  │     型号：[待选定]
  │     要求：输入 12V，输出 3.3V/5V，纹波 < 50mV
  │     来源：物料库 ⏳ 检索中——现有料号均不满足"纹波 < 50mV"
  │     ↓
  │     [发起新物料寻源] ← 从这里启动一个新的工作项
  │
  └── §3.3 连接器
        型号：[待选定]
        要求：2.54mm 间距，16Pin，带锁扣
        来源：物料库 ✗ 未检索到匹配项
        ↓
        [发起新物料调研] ← 或者是调研任务
```

文档正文**不是内容的容器**，而是**内容决策的记录**。内容料的状态反过来决定了文档本身能不能写完——物料没选定时，§3.2 就是一片空白或一个待定的占位符。

### 内容料的三种来源状态决定了三种交互模式

```
内容料的状态              在文档正文中的呈现          执行者可做的操作

┌─ 已有 ──────────┐
│ 物料库中找到       │  "型号：STM32F407VGT6"      [查看详情] [更换]
│ 料号已确认        │  显示关键参数摘要              [对比同类物料]
│ 可被直接引用       │  链接到物料详情页
└─────────────────┘

┌─ 待比对 ────────┐
│ 物料库中检索到     │  "候选物料 (3):           [并排比对]
│ 多个符合要求的     │   A. STM32F407 (¥52)       [选定A/B/C]
│ 需要执行者做选择   │   B. ATSAM4E8  (¥48)       [查看各物料详情]
│                  │   C. LPC1788   (¥55)"       [扩大搜索条件]
└─────────────────┘

┌─ 缺失 ──────────┐
│ 物料库中未找到     │  "§3.2 电源模块              [发起寻源任务]
│ 或现有物料不满足   │   要求：12V→3.3V/5V,       [发起调研任务]
│ 需要启动新的工作项  │   纹波<50mV                 [放宽要求重新检索]
│                  │   状态：物料缺失 ⚠"          [标记此处为"待定"]
└─────────────────┘
```

**关键：文档正文中的一段内容，可以是一个新工作项的起点。** 这打破了"场景业务 = 文档序列"的线性模型——文档开发过程中会**横向分叉**出寻源、调研、试制、验证等子任务，这些子任务不在原场景业务的文档序列中，但它们的产出（新物料、新的复用构件）会回流到当前文档中。

### 内容料的七维图层

内容料自身也涉及全部七个维度：

```
内容料 × 人：   谁负责选定这个物料？（执行者）选完后谁来审？（技术负责人）
内容料 × 机：   用什么工具检索物料库？（物料搜索引擎）用什么工具比对候选物料？（参数对比面板）
内容料 × 料：   物料本身的数据（型号、参数、供应商、价格、交期、认证状态）
内容料 × 法：   选用规则——"优先复用已有物料""关键器件需要三家比价""新物料需要试制验证"
内容料 × 环：   物料的生命周期状态——研发中 / 已认证 / 已停供 / EOL
内容料 × 测：   选用后是否通过——满足参数要求吗？供应商在合格名录中吗？有 RoHS 认证吗？
内容料 × 信息： 这个物料被哪些其他设计文档引用过？（变更影响追溯）这个文档引用了哪些物料？（BOM 视图）
```

这七维的聚合点，就是正文中的**那一段物料描述**。它不是一段静态文字——它周围环绕着检索入口、比对面板、选用规则提示、关联人员、生命周期警告、合规检查、引用链追溯。

### 与制造业的类比：BOM 编制

设计方案中包括要选用哪些物料——在制造业中对应的是 **BOM 编制**。BOM 工程师不是凭空创造一个物料清单，而是在**已有物料库中选型**——能复用的就复用，找不到的就启动新物料流程。

这本质上是把内容料的**全生命周期**（检索→候选→比对→选定→写入→审验→追溯）压缩在文档正文的一段描述周围。

| **操作栏** | 底部 | 保存 / 预览 / 提交流转 | 固定位置，不随正文滚动 |

### 几个关键交互

**1. 正文中的内联引用与右侧面板联动**

执行者在正文 §3.1 中看到 `[参考用户需求 §2.3]`，点击后右侧面板展开用户需求文档的 §2.3，而不是跳转到一个新页面——执行者不需要离开编辑现场。

**2. 资源就绪状态可视化**

输入文档未完成时（合规要求 ⏳），正文对应区域灰化并标注原因。执行者不需要自己去查"为什么这里填不了"——原因就在眼前。

**3. 检查清单嵌入右侧**

不单独一个"自检"页面。检查清单就在资源面板中，与编辑区同时可见。执行者可以边写边打勾，"交出去之前要确认的 10 条"始终在视线范围内。

**4. 辅助栏的角色升级**

在当前的 91 规范中，辅助栏定义为"显示选中行详情（字段名|字段值）"。在执行者工作台中，辅助栏成为**作业指南的动态聚合面板**——它按作业指南的声明自动装配资源，且随当前步骤/输入状态实时变化。文档工作区与辅助栏联动：执行者在工作区编辑某节时，辅助栏自动切换到该节相关的资源。

### 关键设计点

1. **内容料的选择发生在正文编辑的现场**：不是"打开物料库→找到物料→记下料号→回到文档粘贴"——而是在文档正文中写需求描述时，右侧面板实时变成物料检索面板，选定结果直接写回正文。

2. **"缺失"是工作项的起点**：当物料库中找不到时，系统不是报一个"未找到"就完了——它在同一个面板里给出默认的下一步操作。执行者点一下，新工作项就创建了。

3. **子任务与父文档保持双向可见**：寻源任务创建后，执行者不用追到另一个菜单看进度——在当前文档段落旁边，物料状态会从"物料缺失 ⚠"变成"寻源中 ⏳ #SRC-2026-0089"，再到"物料已选定 ✓"。反过来，寻源负责人也能看到这个任务是为哪份文档的哪一节服务的。

4. **内容料的约束来自"法"**：不是所有物料都可以随便选用。法里定义的规则在执行者做选定时，系统应该主动提示和校验。

## 六、作业指南的结构

### 本质变化

加入内容料之后，作业指南从"资源清单 + 操作步骤"变成了**决策引导手册**：

```
之前的认知：                      扩展后的认知：

作业指南 = 需要什么 + 怎么操作    作业指南 = 需要什么 + 怎么操作 + 怎么判断 + 判断不了怎么办

       输入文档清单                  输入文档清单
       规范/标准                     规范/标准
       操作步骤                      操作步骤
       检查清单                      检查清单
                              ────  实体库声明 ← 新增
                                     选用规则   ← 新增
                                     异常路径   ← 新增
```

### 作业指南的完整结构

```
作业指南
│
├── ① 任务标识
│     文档类型、所属场景业务、在文档序列中的位置
│
├── ② 输入检查
│     需要哪些输入文档、每份的角色标签、就绪判定标准
│
├── ③ 操作步骤（1..N）
│   │
│   │  【理解型步骤】
│   │  【选用型步骤】← 内容料在此展开
│   │  【编写型步骤】
│   │
│   └── 每个步骤统一结构：
│       ├── 步骤序位（第几步/共几步、前序是谁、后续是谁）
│       ├── 资源声明
│       ├── 规则声明
│       ├── 操作路径（正常路径 + 异常路径）
│       └── 完成标准
│
├── ④ 自检
│     检查清单、门禁条件
│
└── ⑤ 完成与流转
      验收标准、提交动作、下一站
```

### 三种步骤类型的模板对比

| 块 | 理解型步骤 | 选用型步骤 | 编写型步骤 |
|----|-----------|-----------|-----------|
| ① 序位 | ✓ | ✓ | ✓ |
| ② 资源声明 | 输入文档清单 | 输入文档 + **实体库清单** | 模板 + 规范引用 |
| ③ 规则声明 | 完整性检查规则、矛盾点标记规则 | **选用约束规则**（R1~RN） | 格式规范、术语约定 |
| ④ 正常路径 | 逐文档阅读→标记矛盾→汇总 | **检索→比对→验证→写入** | 按模板填写→规范校验 |
| ⑤ 异常路径 | 输入缺失→退回上游、输入矛盾→标记裁决 | **候选不足→扩大检索→标记裁决、无匹配→发起寻源/调研、供应商不在册→发起准入** | 规范冲突→标记裁决 |
| ⑥ 完成标准 | 所有输入已检查、矛盾已标记 | 所有对象已选定或异常已触发 | 所有章节已填写、已自检 |

### 选用型步骤的七块展开

以下以"步骤 2：选定内容对象"为例，展示作业指南中选用型步骤的完整声明结构：

```
步骤 2 · 选定内容对象
──────────────────────────────────────────────────

┌─ 资源声明：这一步需要查阅哪些实体库 ─────────────────┐

│  ─────────────────────────────────────────────────  │
│  物料库 (MAT)                 候选来源     必须       │

│  外购件目录 (BOUGHT)          候选来源     按需       │
│  合格供应商名录 (AVL)         约束来源     必须       │
│  历史设计文档库                参考来源     可选       │
│                                                      │
│  对每个待选内容对象，依次检索以上实体库。                │
│  物料库的权威字段：型号/参数/供应商/认证/生命周期。       │
└──────────────────────────────────────────────────────┘

┌─ 约束规则：选用时必须遵守什么 ─────────────────────────┐
│                                                      │
│  R1  优先复用已有物料或复用构件                         │
│      判定：物料库中存在满足全部参数要求的物料 → 直接选用   │
│                                                      │

│      须在候选物料中至少比对三家供应商后方可选定             │

│                                                      │
│  R3  新物料选用须经试制验证                             │
│      判定对象：物料库中不存在、须新增入物料库的物料         │

│                                                      │
│  R4  供应商须在合格供应商名录中                           │
│      选定物料后，校验其供应商是否在 AVL 中                │
│      不在 → 触发异常路径 E2                             │
│                                                      │
│  R5  物料生命周期状态检查                               │
│      已停供/EOL 的物料不得选用                           │
│      即将EOL的物料标记"⚠ 需确认替代方案"                  │
└──────────────────────────────────────────────────────┘

┌─ 正常路径：检索→比对→选定→写入 ────────────────────────┐
│                                                      │
│  对于文档中每一个"待选定"的内容对象：                     │
│                                                      │
│  ① 检索                                               │
│     从正文中的需求描述提取关键参数 → 在实体库中检索       │

│                                                      │
│  ③ 验证约束                                           │
│     用 R1~R5 逐条校验选定的物料                         │

┌─ 异常路径：找不到或不符合规则时 ─────────────────────────┐

│      → 扩大检索范围（允许相近参数 / 海外供应商）          │

│      → 准入完成后通知执行者更新物料状态                    │
│                                                      │
│  E3  物料库中无满足要求的物料（R3 的前置条件）             │
│      → [发起新物料寻源] → 创建寻源任务，描述需求参数        │
│      → 或 [发起新物料调研] → 创建调研任务                  │
│      → 文档中该段标记"待物料就绪"，关联任务编号             │

│                                                      │
│  E4  物料已 EOL 或即将 EOL（触发 R5）                    │

│      → 即将EOL：允许选用但标记"⚠ EOL预警，建议确认替代方案" │
│      → [查找替代物料] → 返回检索步骤                      │
└──────────────────────────────────────────────────────┘

┌─ 完成标准：这一步怎样算做完 ────────────────────────────┐
│                                                      │
│  ☐ 文档中所有"待选定"的内容对象均已处理                    │
│  ☐ 已选定的物料全部通过 R1~R5 约束检查                    │
│  ☐ 所有异常路径（E1~E4）已触发对应动作或获得裁决            │
│  ☐ 无"待物料就绪"的段处于阻断状态（寻源/准入进行中 = 不阻断）│
│      ⚠ 注意："进行中"不阻断文档流转，但文档中该段为"待定"    │
└──────────────────────────────────────────────────────┘
```

### 作业指南与平台的装配关系

作业指南定义好之后，平台在运行时按以下流程使用它：

```
执行者打开工位
      │
      ▼
平台读取 ① 任务标识  →  定位当前文档类型、场景业务、序位
      │
      ▼
平台执行 ② 输入检查  →  在场景业务中查找已完成的输入文档
      │                  标记就绪状态（✓ / ⏳ / ⚠ 版本变更）
      │
      ▼
┌─ 对于每个步骤 ──────────────────────────────────────┐
│                                                      │
│  平台读取 ① 步骤序位  →  展示进度条                    │
│                                                      │
│  平台读取 ② 资源声明  →  装配资源到右侧面板              │
│    理解型：列出输入文档及其状态                          │
│    选用型：列出输入文档 + 激活实体库检索入口              │
│    编写型：加载模板 + 规范文档                          │
│                                                      │
│  平台读取 ③ 规则声明  →  激活校验引擎                    │
│    执行者在正文中操作时，逐条校验规则                      │
│    校验结果实时反馈到正文（红色边框 / 警告标记）           │
│                                                      │
│  平台读取 ④+⑤ 路径  →  激活操作按钮                    │
│    正常路径：展示当前步骤的"下一步"操作按钮                │
│    异常路径：当对应条件触发时，展示异常处理入口             │
│                                                      │
│  平台读取 ⑥ 完成标准 →  激活自检面板                    │
│    逐条显示完成项的打勾状态                              │
│    全部通过前，提交流转按钮灰化                           │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**作业指南是执行者工位的"配置文件"**——不是一份执行者阅读的文档，而是平台读取后驱动工位页面装配的指令集。换了文档类型，作业指南不同，执行者看到的工位就不同——资源面板里的东西、校验规则、异常处理入口、自检清单，跟着作业指南走。

## 七、参照：制造业工艺卡的结构与 ERP/MES 解析

### 工艺卡的三层数据结构

制造业的工艺卡不是一张纸，而是**三层数据结构的投影**：

```
第一层 · 工艺路线（Routing）
─────────────────────────────
定义"这个产品怎么做出来"——从毛坯到成品的完整工序序列。
全局视图，不涉及单道工序的细节。

第二层 · 工序卡片（Operation Sheet）
─────────────────────────────────────
定义"这一道工序怎么做"——针对单道工序的详细描述。
包含：工位/工作中心、工步序列、投入物料（BOM行）、工装/刀具/量具、检验要求、异常处理

第三层 · 工艺流转卡（Traveler / Route Card）
────────────────────────────────────────────
工艺路线 × 具体生产批次 = 工艺流转卡。
MES 按工单生成，跟随实物在车间流转，逐工序记录实际执行结果。
```

三层的关系：**工艺路线是模板、工序卡片是细则、流转卡是实例**。

### 工艺卡的数据结构（机器可解析版）

现代 MES 中，工艺卡不是 PDF 文件，而是一组**结构化数据表**。数据结构包含：

- **工艺路线头**：routing_id / product_id / version / status / effective_from / bom_id / batch_qty
- **工序序列**：op_seq / op_name / work_center_id / resource_type / setup_time / run_time / queue_time / move_time
- **关联物料（Materials at Operation）**：component_id / component_name / qty_per_assembly / auto_consumed
- **作业指导（Work Instructions）**：wi_id / wi_type / wi_content / required / log_viewing
- **检验要求（Inspection）**：characteristic / spec_nominal / spec_upper / spec_lower / gauge_id / sample_freq
- **异常处理（Exception Paths）**：exception_id / trigger / action
- **审批与签核（Sign-offs）**：designed_by / reviewed_by / approved_by
- **版本历史（Change Log）**

### ERP 和 MES 如何解析和使用这套数据

数据在三个系统间流转：

```
PLM/CAPP                          ERP                             MES
───────                          ─────                           ─────
工艺设计阶段                      计划阶段                         执行阶段

定义：                            读取：                           读取：
· 工艺路线头                       · routing_id                    · 工单 → 关联 routing
· 工序序列 + 工时                  · batch_qty                    · 按工序序列拆分流转卡
· 物料关联（BOM）                  · 每道工序的工时                  · 每道工序绑定：工位/设备/操作者/物料/WI/检验
· 作业指导（WI）                  · 每道工序的工作中心
· 检验要求                                                        → 工位终端（触摸屏/平板）
· 异常处理                        生成：                            渲染：当前工序的作业指导 +
                                 · 生产工单（WO）                       待投入的物料清单 +
                                 · 派工 → 工作中心                     待使用的工装/量具 +
                                 · 物料需求计划（MRP）                  需记录的检验项 +
                                 · 成本核算（工时×费率）                异常情况下的触发路径
                                 ↓
                                 下发工单到 MES
```

**工位终端的渲染是"工序数据 + 工位上下文"的选择性投影**。MES 工位终端不是把整个 routing 的全部数据都展示出来——它只取**当前工序的数据**，再按工位的角色和权限做二次过滤。操作者看到的信息是：当前工序的作业指导 + 本工序需投入的物料 + 本工序需记录的检验项 + 本工序可触发的异常路径。前后工序的信息在进度条上缩略显示但不是主体。

## 八、从工艺卡到作业指南的映射

### 三层对应

```
制造业                                 EOS 文档开发
──────                                 ────────────

工艺路线（Routing）                     作业指南·文档类型级（静态声明）
  ├── routing_id                         ├── 文档类型ID
  ├── product_id（产出什么）              ├── 产出文档的结构定义
  ├── bom_id（用料清单）                  ├── 输入文档声明 + 实体库声明 + 规范引用
  ├── 工序序列 + 工时                     ├── 操作步骤序列 + 每个步骤的完成标准
  ├── version + status                   ├── 版本 + 状态
  └── 审批签核                           └── 设计者/审核者/批准者

工序卡片（Operation Sheet）            操作步骤·选用型步骤（作业指南中的单步展开）
  ├── 工位/工作中心                       ├── 这一步在哪个角色类型的工作台
  ├── 投入物料（BOM行）                   ├── 输入文档 + 实体库检索声明
  ├── 工步序列 + 参数                     ├── 正常路径（检索→比对→验证→写入）
  ├── 工装/刀具/量具                     ├── 引擎工具 + 模板 + 检查清单
  ├── 检验要求 + 量具                     ├── 约束规则 + 校验引擎
  └── 异常处理                            └── 异常路径（寻源/准入/裁决）

工艺流转卡（Traveler）                  任务实例·工位视图
  ├── 工单号 + 批次                       ├── 任务ID + 所属场景业务
  ├── 前序完成状态                         ├── 上游文档就绪状态
  ├── 本工序作业指导（工位终端渲染）         ├── 当前步骤操作指引
  ├── 物料扫码消耗                         ├── 输入文档确认 / 实体库检索即用
  ├── 检验值录入                           ├── 约束校验结果 + 自检清单打勾
  ├── 工时记录                             ├── 步骤完成时间记录
  └── 异常触发（NCR）                     ├── 异常路径触发（寻源/准入/裁决）
```

### 四个关键启示

**启示 1：工艺卡是数据，不是文档**

MES 不"读"一份 PDF 工艺卡——它从结构化工艺数据库中查询工序的所有关联数据，用这些数据**动态渲染**工位界面。EOS 的作业指南也应如此——不是执行者打开一份"作业指南文档"来读，而是平台读取作业指南的声明数据，**装配成工位页面**。

**启示 2：工艺卡的组织轴心是"工序"，不是"产品"**

同一份工艺卡中，不同工序的物料不同、WI 不同、检验要求不同、异常处理不同——这些数据全部**挂在工序上**，而不是挂在产品头上。因为**工位看到的就是一道工序**，不是整个产品。

对应到作业指南：每种资源、每条规则、每条异常路径，都要明确声明**它属于哪个步骤**。执行者在工位上看到的永远只是**当前步骤**的资源装配，不是整个作业指南的全文。

**启示 3：工艺卡 ÷ 工单 = 流转卡**

工艺路线是模板，乘以具体工单后才生成流转卡——流转卡上有了具体的批次号、数量、实际日期、责任人。**模板和实例是两个对象**。

对应到作业指南：文档类型级的声明是模板，每次任务实例化时乘上具体上下文（场景业务中的文档序列、上下游实际的人和文档版本）才生成工位视图。模板定义"需要什么"，实例回答"具体有什么"。

**启示 4：工位终端的渲染是"工序数据 + 工位上下文"的选择性投影**

MES 工位终端不是把整个 routing 的全部数据都展示出来——它只取**当前工序的数据**。对应到作业指南：工位上默认展示的永远是**当前步骤的资源**，其他步骤折叠在进度条中。执行者不需要看到整个作业指南的全貌。

## 十、工艺路线的作用对象：一份文档还是一个文档序列

### 制造业中的区分

```
工艺路线（Routing）
  作用对象：一个物料号（一个零件/一个组件）
  回答："把这个东西做出来，需要哪几道工序"

生产订单（Production Order）
  作用对象：一个最终产品 + 它的 BOM 展开
  回答："做这批货，要按什么顺序生产哪些零件、装配哪些组件"

BOM（Bill of Materials）
  定义：最终产品由哪些零件和组件构成、它们的层次和数量关系
  作用：生产订单按 BOM 展开为多个子订单 → 每个子订单有自己的工艺路线 → 各子订单间有先后依赖
```

**工艺路线只管一个零件怎么做出来。** 它不关心这个零件什么时候装配、和谁装配、装到哪个最终产品上——那是生产订单的排程逻辑。

### 对应到 EOS

```
作业指南（= 工艺路线）
  作用对象：一个文档类型（如"采购技术规范"）
  回答："把这份文档开发出来，需要哪几步"

场景业务（= 生产订单 + BOM）
  作用对象：一组有先后依赖的文档序列
  回答："完成这条端到端业务，要按什么顺序产出哪些文档"

输出文档序列
  定义：场景业务中，哪些文档类型按什么先后顺序产出
  作用：场景业务实例化时，按文档序列逐个分派任务 →
        每个任务对应一个文档类型 →
        每个文档类型有自己的作业指南 →
        各任务之间有先后依赖
```

### 为什么必须是一份文档

**原因 1：不同文档类型的"做法"根本不同**

| | 用户需求整理 | 采购技术规范 | 供应商评审报告 |
|------|-----------|------------|--------------|
| **步骤类型构成** | 理解型 + 编写型 | 理解型 + **选用型** + 编写型 | 理解型 + **选用型** + 编写型 |
| **实体库声明** | 无 | 物料库 / 复用构件库 / AVL | 供应商库 / AVL |
| **约束规则** | 完整性检查 | 优先复用 / 三家比价 / 新物料试制 | 供应商资质 / 供应业绩 |
| **异常路径** | 输入缺失→退回 | 物料缺失→寻源 | 供应商不足→扩大寻源 |

如果把这些写进同一份作业指南，这份指南会变成一个无法维护的巨型文档。

**原因 2：复用。** "采购技术规范"可能出现在多个不同的场景业务中——设备采购、软件采购、外协采购。不管在哪，做法是一样的。作业指南应该定义一次，被所有包含它的场景业务复用。

**原因 3：维护边界。** 物料库的检索规则变化了，受影响的是所有涉及内容料选用的文档类型。按文档类型分，变更范围清晰：三种文档类型的作业指南各改一处。按场景业务分，变更范围模糊。

### 场景业务的角色

场景业务定义了"哪几份文档、按什么顺序"，但它不定义"每份文档怎么做"。后者是每份文档自己的作业指南的职责。

```
场景业务 × 文档序列 = 生产订单 × BOM
     ↓                        ↓
  "产出这些文档"            "按这个顺序做"

一份文档 × 作业指南 = 一个零件 × 工艺路线
     ↓                    ↓
  "做这份文档"            "按这些步骤做"
```

## 十一、生产订单在 EOS 中的对应：业务启动指令

### 生产订单在制造业中的位置

```
设计层（PLM）                   计划层（ERP）                   执行层（MES）
───────────                    ───────────                    ──────────

产品设计（图纸/3D模型）           生产订单（Production Order）      工序流转卡（Traveler）
BOM（用什么料）       ──┬──→     工单号/产品/数量/交期         →  工位终端
工艺路线（怎么加工）    ──┘       绑定 BOM + 工艺路线              逐工序报工

                                    ↑
                                    │
                              生产订单是"做一批货"的指令：
                              - 做什么？ → 产品 × BOM
                              - 怎么做？ → 工艺路线
                              - 做多少？ → 数量
                              - 什么时候要？ → 交期
                              - 谁来做？ → 工作中心
                              - 为什么做？ → 销售订单/库存补货/项目需求
```

**生产订单不是设计数据，也不是执行记录——它是一份"指令"。** 它把设计层定义的模板数据（BOM + 工艺路线）实例化为一次具体的生产任务，然后交给 MES 去执行。

### EOS 中的对应：业务启动指令

```
设计层（91规范定义的）              计划/指令层                     执行层
──────────────────              ────────────                   ────────

场景业务（SL5）   ──┬──→        业务启动指令                      工位
  文档序列定义        │          ├── 启动哪个场景业务？                逐文档执行

  作业指南            │          ├── 为什么启动？                    报工/流转
                     │          ├── 什么时候要？
                     │          ├── 谁来负责？

```

```
      管理视图                       工位视图                        步骤视图
   "整批活到哪了"                  "我这摊活怎么干"                 "这一步具体怎么干"
```

### 场景业务的正确定位

场景业务不是工作台，它是**任务编排单元**：

| 场景业务负责 | 文档工位负责 |
|------------|------------|
| 定义文档序列的先后依赖 | 定义单份文档的开发步骤 |
| 文档 A 完成后才能启动文档 B | 步骤 1 完成后才能进入步骤 2 |
| 文档间流转：A 的输出 → B 的输入 | 步骤内操作：检索 → 比对 → 验证 → 写入 |
| 谁负责哪份文档 | 当前步骤需要什么资源 |
| 整体什么时候要 | 这一步做到什么程度算完 |

**场景业务不定义"怎么做"，它只定义"先做什么后做什么、谁来做"。** "怎么做"是每份文档自己的作业指南定义的。

### 执行者和管理者看到的是不同的东西

两个视图，同一组底层数据。场景业务是底层的数据组织方式，但它投影到不同角色时，呈现出完全不同的视图——管理者的场景业务看板，执行者的文档工位。

## 十三、PCA 模型分析

### 当前 91 规范的问题

当前规范把 PCA 定义为一类场景业务，一个场景业务包揽了 P、C、A 三个阶段。但三个阶段的**工作性质根本不同**。

### P（策划）——是文档开发

策划工作产出的是**文档**：计划清单、指标清单、看板清单、风险清单。这些是正式/轻量文档，由执行者按作业指南开发。**P 天然适合场景业务 + 文档工位模型。**

### C（监控）——不是文档开发

监控不产出文档。监控是**消费已有指标定义，看指标结果**。管理者打开看板，看到趋势和偏差——不需要写文档，只需要看懂、判断。

**C 不是场景业务——它是指标引擎和看板引擎的运行时使用场景。** 没有"文档序列"，没有"输入文档→加工→输出文档"的流转，没有作业指南。

### A（改进）——是被 C 触发的新 P

发现问题后启动改进，改进的形式又是文档开发。**A 不是 PCA 场景业务的"第三阶段"——它是由 C 的发现触发的一个新的场景业务。**

### 三者是不同的东西

```
P（策划）
  类型：场景业务
  产出：计划清单 + 指标清单 + 看板清单 + 风险清单 + ...
  文档序列：有先后依赖
  每个文档：有作业指南
  触发方式：按周期（每季度/每年），或上一轮 A 完成后触发新一轮 P

C（监控）
  类型：不是场景业务
  行为：管理者消费指标引擎和看板引擎的产出
  工具：指标目录/看板清单/图示模式/看板图示
  周期：持续进行

A（改进）
  类型：场景业务（由 C 触发）
  产出：改进方案文档 / 问题处理工单
  触发方式：事件驱动——C 发现偏差/超标/趋势恶化 → 启动
```

### P 和 A 之间靠什么连接

不是"生产订单的工序序列"关系，而是**"触发来源"的追溯关系**：

```
P 生产订单 #BI-2026-0089（Q3 策划）
  ├── 产出：指标清单（定义了 12 个 Q3 指标）
  ├── 产出：看板清单（定义了 3 个看板）
  └── 产出：计划清单（定义了 Q3 的工作节奏）
        │
        │  C 阶段：管理者按看板清单上的看板，日常监控指标
        │
        ├── 7 月 20 日：采购订单处理周期超标 → 创建 A 生产订单 #BI-2026-0091
        │      来源：P 生产订单 #BI-2026-0089 的指标清单 · 指标 #IND-004
        │
        ├── 8 月 05 日：供应商交付准时率恶化 → 创建 A 生产订单 #BI-2026-0095
        │      来源：P 生产订单 #BI-2026-0089 的指标清单 · 指标 #IND-007
        │
        └── 8 月 30 日：无异常 → 不创建 A
```

P 和 A 之间的关系不是"工序 10 → 工序 20"，而是**"定义了什么算异常 → 监测到异常 → 触发纠正"**。

如果把 P、C、A 硬塞进一个场景业务会出现三个问题：

1. C 没有"文档序列"——场景业务的核心模型"输出文档序列→流转"对 C 不适用
2. P 和 A 的时间跨度完全不同——P 在季度初做 2 周 → C 持续 3 个月 → A 随时可能发生，作为管理单元失去意义
3. A 可能触发多次——一个季度内可能触发 3 次改进，如果 A 是"第三阶段"则只能发生一次

拆开后的对照：

| | D（执行类） | P（策划） | C（监控） | A（改进） |
|------|----------|---------|---------|---------|
| **本质** | 场景业务 | 场景业务 | 信息消费 | 场景业务 |
| **产出** | 产品数据文档 | 管理数据文档 | 不产出文档 | 管理数据文档 |
| **触发** | 项目驱动/需求驱动 | 周期驱动 | 持续 | 事件驱动（C 触发） |
| **文档序列** | ✓ | ✓ | — | ✓ |
| **作业指南** | 每份文档有 | 每份文档有 | — | 每份文档有 |

**P 和 A 在"处理逻辑"上与 D 类确实同构——都是场景业务，都是文档开发。C 则完全不同。**

## 十四、管理者的三个工作视图

对应 P、C、A 的分离，管理者需要的是不同的视图：

### 策划视图（P 阶段使用）

管理者启动 P 场景业务 → 看到一个管理视图，和之前讨论的**场景业务管理视图**完全同构——P 就是一个普通的场景业务，管理者看的是它的文档序列进度：

```
P 生产订单 #BI-2026-0089（Q3 策划）进度
  ├── 计划清单（总调度表）
  │     条目1 ✓ 已发布
  │     条目2 ⏳ "制定指标清单" → 采购工程师 · 李四 正在进行
  │     条目3 ⏳ "识别风险清单" → 质量工程师 · 王五 正在进行
  │     条目4 □ "设计看板清单" → 待启动（依赖条目2完成）
  ├── 指标清单：编制中
  ├── 看板清单：待开始
  └── 风险清单：编制中
```

### 监控视图（C 阶段使用）

管理者日常打开看板清单 → 选择"部门 KPI 看板"。这不是一个"场景业务的工位"——它是指标引擎和看板引擎的运行时产出。管理者在这里**消费信息、做判断、决定要不要启动改进**：

```
管理者看板视图：
  ├── 当前值 vs 目标值（Stat 面板阵列）
  ├── 趋势折线图（叠加阈值线）
  ├── 异常标记：⚠ 供应商交付准时率 连续 3 个月低于警戒线
  └── [深入分析] [启动改进]
```

### 改进视图（A 阶段使用）

管理者在监控视图中发现偏差 → 点击"启动改进" → 系统创建一条 A 场景业务。A 场景业务启动后，管理者的视图和 P 场景业务一样——是普通的场景业务管理视图：

```
A 生产订单 #BI-2026-0091（供应商交付改进）进度
  ├── 问题分析报告：已完成 ✓
  ├── 改进方案：编制中 ⏳
  ├── 改进措施追踪表：待开始
  └── 改进效果验证报告：待开始
```

## 十五、Q3 不是生产订单，是管理节拍

### 制造业对照

制造业中有严格区分：

```
生产计划（Production Plan）
  → "Q3 计划产出 10,000 根轴"
  → 它汇总数字，不是可以派到工位上的指令

生产订单（Production Order）
  → "WO-2026-0715：轴 200 根，7 月 20 日前交付，工作中心 B"
  → 它是一张具体指令，可以派到工位

两者的关系：
  Q3 生产计划说要做 10,000 根
    → 拆成 50 张生产订单（每张 200 根）
    → 分布在 7/8/9 三个月
    → 每张订单有自己的交期、工作中心、负责人
```

**Q3 生产计划是"要做多少"，生产订单是"这批怎么做"。**

### Q3 在 EOS 中的正确位置

```
管理日历（Q3 管理周期）
  作用：定义节奏——什么时候该做 P、什么时候该做 C、什么时候出季度报告
  它不是生产订单

  Q3 管理日历包含：
    │
    ├── 7 月初：P 生产订单启动
    │     "做 Q3 的管理工具——指标清单、看板清单、计划清单"
    │     这是一张生产订单，有负责人、截止日、交付物
    │
    ├── 7 月中 ~ 9 月底：C 持续运行
    │     管理者日常看指标看板，这不是生产订单
    │
    └── 7~9 月期间：A 生产订单（0~N个，事件触发）
         每次发现偏差 → 判断 → 创建一张 A 生产订单
```

### 为什么 Q3 不能是生产订单

试想如果 Q3 是一张生产订单，它的 BOM 和工艺路线是什么？

| 生产订单应有 | Q3 的状况 |
|-----------|---------|
| 产出：确定的交付物 | Q3 不产出任何一份确定的文档——P 和 A 各自产出具体文档，Q3 本身不产出任何东西 |
| BOM：确定的来料清单 | P 的产出是 P 做出来的，不是 Q3 的"来料" |
| 工艺路线：确定的工序序列 | P→C→A 不是工序序列——C 不是加工动作，A 可能不发生 0~N 次 |
| 数量：确定的批次量 | A 发生几次事先不知道 |

三个硬伤：**没有固定的产出**（P 和 A 各自产出文档，Q3 本身不产出）；**中间有一大段不是"加工"**（C 是管理者看指标，不产生文档，不消耗工时定额）；**下游依赖不确定**（A 可能 0 次或多次，序列不固定）。

### Q3 的正确定义

**Q3 是管理节拍（Management Cadence）**——一个时间框架，定义了管理活动的节奏：

```
生产计划（Production Plan）
  → "Q3 我们要把供应商交付准时率从 82% 提升到 90%"
  → 它是一个管理目标声明，不是一张工单

管理节拍（Management Cadence）
  → 每个季度初做 P，每月看一次 C 总结，有偏差随时启动 A，季度末做回顾
  → 它是节奏定义，不是工单

P 生产订单（Production Order）
  → "创建 Q3 指标清单 + 看板清单 + 计划清单，负责人 XXX，7 月 14 日前完成"
  → 这是一张具体的工单，可派到工位
```

**管理节拍告诉管理者"什么时候该做什么"，生产订单告诉执行者"这批活怎么做"。**

最接近的制造业概念是**工作中心的能力基线和周期性校准**：

```
制造业中：
  工作中心 B 的车床需要定期校准
    → 校准计划：每季度校准一次（这是管理节拍）
    → 校准活动本身是一张维护工单，有标准操作流程、有检查清单、有签字
    → 校准后投入生产
    → 生产过程中用检具测量，发现偏差 → 触发纠正（维修工单）

对应到 EOS：
  Q3 管理周期
    → 管理节拍：每个季度做一次 P
    → P 是一张生产订单
    → P 完成后投入 C：管理者用这些工具持续监控
    → C 过程中发现偏差 → 触发 A 生产订单（纠正工单）
```

## 十六、总结：全概念关系图

```
管理节拍（Q3）
  └── 定义了 P、C、A 的节奏和时间框架
       │
       ├── 触发 ──→ P 生产订单（= 业务启动指令，按周期）
       │               └── 绑定场景业务（= BOM：定义文档序列）
       │                    └── 每份文档有自己的作业指南（= 工艺路线）
       │                         └── 每个步骤展开为工位视图（= 流转卡）
       │
       ├── 持续 ──→ C 信息消费（不是生产订单）
       │               └── 消费 P 产出的指标引擎和看板引擎
       │
       └── 触发 ──→ A 生产订单（0~N个，事件驱动）
                       └── 绑定场景业务
                            └── 每份文档有自己的作业指南

概念对应表：

  制造业                          EOS 文档开发
  ──────                          ────────────
  产品设计 + BOM                   场景业务（文档序列定义 + 依赖关系）
  工艺路线                         作业指南（单份文档的开发步骤定义）
  生产计划                         管理节拍（Q3 节奏定义）
  生产订单                         业务启动指令（一次具体业务启动）
  工序流转卡                       工位视图（任务实例 × 当前步骤）
  维护/校准工单                    P 生产订单 / A 生产订单
  Andon 看板                       C 信息消费视图
```

### 核心认知

1. **执行者是文档开发者，管理者的工作是 PCA。**

2. **作业指南的作用对象是一份文档，不是一个文档序列。** 它是数据，不是文档——平台在运行时解析作业指南的声明，动态装配出当前步骤所需的全部资源。

3. **场景业务是任务编排单元，不是工作台。** 它定义了"先做什么后做什么、谁来做"，但"怎么做"是每份文档自己的作业指南定义的。

4. **生产订单是"设计模板 × 具体实例"的连接层。** 在 EOS 中对应的是业务启动指令——把场景业务和作业指南实例化为具体的任务，有负责人、截止日、优先级。

5. **PCA 不是一个场景业务。** P 和 A 各是场景业务（触发方式不同：周期 vs 事件），C 不是场景业务——它是指标引擎和看板引擎面向管理者的信息消费视图。

6. **Q3 不是生产订单，是管理节拍。** 它定义"什么时候该做什么事"，不产出任何文档，没有 BOM 和工艺路线。

## 十七、可复用资产：工艺路线还是工艺卡片

### 区分依据

制造业中：

- **工艺路线（Routing）**：可复用的主数据对象，绑定到一个物料号。包含完整的工序序列 + 每道工序的关联数据。一次定义，所有引用它的生产订单都生效。
- **工序卡片（Operation Sheet）**：工艺路线内部某道工序的详细展开，绑定到工艺路线上的一道工序。不是独立的可复用资产——它是工艺路线的组成部分。

### 对应到 EOS

- **作业指南（= 工艺路线）**：可复用的主数据对象，绑定到一个文档类型。包含完整的步骤序列 + 每个步骤的关联数据。一次定义，所有业务启动指令引用它时都生效。
- **步骤声明（= 工序详述，内嵌于工艺路线）**：作业指南内部某个步骤的详细展开。不是独立的可复用资产——它是作业指南的组成部分。

### 为什么在 EOS 中应合为一个

制造业中工艺路线和工序卡片分离是因为媒介限制（纸质）、受众不同（计划员 vs 操作工）、变更频率不同。EOS 从一开始就是数字化的——作业指南是一个完整的结构化数据对象，步骤详述内嵌其中，系统按需投影当前步骤即可。

**可复用资产是作业指南，对应制造业的工艺路线（内嵌工序详述）。**

## 十八、EOS 平台如何依据作业指南为用户提供工作台

### 整体机制：四步流水线

平台做的事情不是"打开一份文档给执行者看"，而是**读取作业指南的声明，在运行时上下文中逐条解析每项声明对应的具体实例，把它们装配到工位页面的对应区域**。

```
第一步·定位：
  任务ID → 业务启动指令 → 场景业务 → 文档实例 → 文档类型 → 作业指南 → 当前步骤

第二步·解析声明：
  读取当前步骤的全部声明块 → 按五类逐条分类：
    - 查找式声明（"需要输入文档，类型=用户需求文档"）
    - 引用式声明（"需要参考：通用设计规范 v1.0"）
    - 推导式声明（"步骤序位：第 2/4 步"）
    - 激活式声明（"E3：检索结果为空 → 激活[发起新物料寻源]"）
    - 校验式声明（"R2.4：物料.供应商 IN AVL，阻断"）

第三步·上下文解析：
  查找式 → 在场景业务文档序列中按类型匹配实例
  引用式 → 直接加载指定资源
  推导式 → 基于处理配置和执行历史计算当前进度
  激活式 → 注册事件监听器（暂不渲染入口）
  校验式 → 注册到校验引擎（等待执行者操作时触发）

第四步·装配渲染：
  工位布局模板（固定） × 解析结果（动态） → 执行者看到的工位页面
```

### 五类声明的解析方式

| 声明类型 | 作业指南中写什么 | 平台解析引擎做什么 | 输出 |
|---------|---------------|-----------------|------|
| **查找式** | 资源角色 + 类型条件 | 在运行时上下文中按类型匹配实例 | 具体实例引用 + 状态 |
| **引用式** | 精确资源标识符 | 直接加载指定资源 | 资源链接 + 版本状态 |
| **推导式** | 当前状态 + 判定规则 | 基于上下文和规则计算 | 当前进度/完成度 |
| **激活式** | 触发条件 + 动作 | 注册事件监听器 | 条件满足时渲染操作入口 |
| **校验式** | 约束条件 + 阻断级别 + 异常路径 | 实时校验正文内容 | 通过/警告/阻断 + 异常路径激活 |

### 完整的运行时例子

执行者李四打开任务"采购技术规范 #DOC-0715-003"的完整交互序列——从定位作业指南、解析声明、上下文装配，到执行者在 §3.1/§3.2/§3.3 中逐个检索物料、比对候选、选定、校验约束、触发异常路径（E3: 物料缺失→发起寻源→回流）的全过程。

## 十九、作业指南的自动推导：五层数据

### 已有四层结构化数据

作业指南的大部分内容可以从已有的资产定义中自动推导：

| 层级 | 数据 | 能推导什么 |
|------|------|-----------|
| **PL2 所属项目** | 业务域 / E2E 项目类型 | 步骤构成模式 / 默认规范引用 / 业务域上下文 |
| **PL3 所属构件** | 构件类型（自研/外购/复用/项目） | 选用型步骤有无 / 实体库集合 / 约束规则集 / 异常路径集 |
| **PL5 前序文档** | 输入文档清单 + 角色标签 + 是否必须 | 输入检查的具体内容 / 就绪条件 / 异常路径（输入未就绪） |
| **文档类型定义** | 结构 / 字段类型 / 引擎 / 处理配置 | 编写型步骤的模板 / 字段约束 / 完成标准 / 流转路径 |

### 第五层：同类文档资产

"同类文档"由四个维度定义：同一构件类型 × 同一业务域 × 同一任务类型 × 同一转化引擎。四维相似度排序 → 取最相似的 1~3 份文档类型。

同类文档有两层可用数据：

- **资产定义（26号资产）**：永远存在，冷启动可用。用结构同构判定 + 差异映射来复用推导结果。
- **作业指南**：有先例后才可用。复用人工写过的业务策略规则、异常路径、编写指引、业务检查清单。

### 五层推导的覆盖度

```
第一层（PL2 项目）：     ~5%
第二层（PL3 构件）：    ~25%    ← 构件类型是最强推导信号
第三层（PL5 前序）：    ~15%
第四层（文档定义）：    ~40%
第五层（同类文档资产）：  ~5%（冷启动·资产定义模式）/~15%（热运行·作业指南模式）
─────────────────────────────
总计：                 ~90%
```

**前四层是创成式推导（从模型推导），第五层是变异式推导（从先例推导）。** 两者互补——前四层搭骨架保证完整性，第五层补血肉保证实用性。

## 二十、作业指南不需要独立编制

### 编制文档类型就是编制作业指南

26 号资产的文档类型定义和作业指南是**同一套数据的两种投影**——文档类型定义是"设计者视角"，作业指南是"执行者视角"。系统自动完成投影，不需要人手写。

```
26号资产的文档类型定义        作业指南
─────────────────────       ──────
封面字段定义                  →  编写型步骤的模板声明
正文字段·实体引用(→物料库)     →  选用型步骤的实体库声明
正文字段·是否必填              →  完成标准的检查项
支持信息引用(输入,必须)        →  输入检查 + 就绪条件
支持信息引用(规范,必须)        →  参考资源面板中的规范
转化引擎                      →  工位工具激活
任务类型                      →  流转路径
处理配置(节点+角色+动作)       →  步骤数 + 流转动作
```

### 从创建到成熟作业指南的完整路径

```
T0  定义文档类型（26号资产）
T1  系统自动推导作业指南 v0.1 → ~80% 自动填充，标记缺失项
T2  人工打开补全界面 → 审阅推导结果 → 补充策略性内容 → 发布 v1.0
T3  执行者使用 v1.0 → 在工位上提交反馈
T4  收集反馈 → 持续改进 → v1.1 → v1.2 → ...
T5  后续同类文档 → 变异复用已有作业指南 → 覆盖度 ~90%
```

### 谁负责根据反馈修改

**文档类型的设计者。** 和制造业工艺路线由工艺工程师负责完全对应。执行者在工位上发现问题 → 点击反馈按钮 → 反馈自动关联到作业指南的具体步骤和声明项 → 汇总到设计者 → 设计者评估 → 采纳/拒绝 → 修改 → 发布新版 → 新版自动推送到受影响的任务。

## 二十二、系统如何知道执行到哪一步

### 自动判定，不需要人工填报

系统通过**作业指南声明的完成标准 + 对文档正文实际状态的实时扫描**自动判定当前处于哪一步。

执行者选定一个物料、填完一个字段、通过一条校验——系统立刻知道。完成标准全部自动打勾时，系统就知道这一步做完了。`[下一步]` 按钮只是确认动作，不是"上报进度"。

### 三种判定机制

| 触发时机 | 判定内容 |
|---------|---------|
| **执行者操作即时触发** | 选定物料 → 重跑校验 → 更新打勾 |
| **保存时触发** | 扫描必填字段完整性 |
| **上下文变更时触发** | 前序文档完成 → 通知执行者 → 输入就绪状态更新 |

### 步骤状态机

```
未开始 → 前置步骤未完成，步骤灰显
进行中 → 前置已完成 + 本步完成标准未全部满足
已完成 → 完成标准全部满足 → 正文只读 → 自动推进到下一步
```

极少数完成标准无法自动判定（如"已与上游确认矛盾点"），在作业指南中标记 `[需人工确认]`，执行者手动勾选。这是例外，不是常态。

### 退回机制

上游输入文档发布新版本 → 系统检测变更 → 受影响步骤的完成标准重新判定 → 如果不再满足，该步骤自动退回"进行中"。这是变更传播协议的自动执行，不是人操作的。

## 二十三、作业指南的核心结构：做→查→过

### 每一步都以检查结束

作业指南的本质是一张工序表——每一步的结构都是同一个模式：**做→查→过**。

| 列 | 内容 | 谁负责 |
|----|------|--------|
| **做** | 操作路径 + 需要的资源 + 约束规则 + 异常路径 | 设计者声明，执行者操作 |
| **查** | 完成标准——这一步怎样算做完 | 设计者声明，系统自动判定 |
| **过** | 全部通过后去哪 | 设计者声明，系统自动流转 |

### 选用型步骤的"做→查→过"示例

**做**：在正文字段中描述需求参数 → 检索声明的实体库 → 候选比对 → 验证约束规则 → 选定写入

**查**：
- ☐ 所有实体引用字段均已选定（系统扫描正文中字段类型="实体引用"的字段）
- ☐ 已选定全部通过约束规则（系统逐条重跑校验）
- ☐ 阻断型异常全部已触发（系统检查异常路径触发状态）

**过**：全部 ✓ → 可进入 Step 3。待就绪不阻断流转。

### 对设计者而言

编制作业指南就是填这张"做→查→过"的表。不需要长篇操作手册——声明每个步骤的做（操作路径 + 资源 + 规则 + 异常）、查（完成标准 + 判定逻辑）、过（流转去向）。平台读取后把"做"装配到辅助栏，把"查"注册为实时校验，把"过"变成步骤状态机的流转规则。

### "做"和"查"的数据来源

```
"做"来自                       "查"来自
───────                       ───────
文档类型定义·正文字段类型       →   实体库列表
文档类型定义·正文结构           →   操作步骤类型
PL2 所属项目                    →   步骤模式
PL3 所属构件                    →   实体库集合 + 约束规则集 + 异常路径集
PL5 前序文档                    →   输入检查清单
同类文档资产（变异复用）          →   已有人工补全的规则/指引/检查项
人工补充                        →   特定业务策略规则 + 编写指引
```

两者共用同一组数据源。"做"和"查"都是从同一套资产定义中推导出来的——正文字段的类型定义了"查什么"（实体引用完整性），约束规则定义了"怎么查"（校验逻辑），完成标准定义了"查到什么程度算过"。

### 每个步骤以检查结束的多层价值

- **对执行者**：不用记规则、不用判断"做完了没有"、不用怕遗漏
- **对管理者**：进度不是人报上来的——系统自动判定，阻塞可视
- **对设计者**：质量门禁前置到每一步，作业指南在使用中持续改进

这与丰田生产方式的"工序内自检"完全对应——每一步以检查结束，不合格当场改，不让问题流到下一步。

## 二十四、资源的获取方式

### 三种方式，不需要独立的"资源申请流程"

| 资源类型 | 获取方式 | 需要启动流程？ |
|---------|---------|-------------|
| **已就绪的资源** | 系统自动装配——打开工位时已在那里 | 不需要 |
| **待就绪的资源** | 系统自动监听——就绪后自动通知 | 不需要 |
| **不存在的资源** | 执行者触发异常路径——创建子任务 | 需要（辅助栏中一键触发） |

### 已就绪：系统自动装配

作业指南声明了什么，系统就去查有没有——有的就直接放上去。输入文档已完成 → 辅助栏·输入文档区自动列出。规范文档已定位 → 辅助栏·参考资料区自动显示。实体库服务可用 → 辅助栏·实体库检索面板自动激活。

### 待就绪：系统自动监听

上游文档仍在编制中 → 辅助栏标记 ⏳，正文引用段落灰化。系统在后台持续监听上游状态 → 就绪后自动通知执行者 → 辅助栏状态更新 → 灰化解除。不需要人催、不需要刷新页面。

### 不存在：异常路径触发子任务

这是唯一需要"启动流程"的情况——但不是在别处发起，而是在辅助栏中一键触发。执行者检索物料库返回 0 条 → 辅助栏底部自动出现异常路径入口 → 点击 [发起新物料寻源] → 系统按作业指南的异常路径声明自动创建子任务、从当前段落提取需求描述填充任务描述、关联锚点、标记正文段落"待就绪"、不阻断步骤流转。子任务完成后系统自动通知，候选物料就绪，执行者回到段落选定即可。

**作业指南的异常路径声明决定了每种"不存在"情况下的具体处理方式——是发起寻源、发起供应商准入、还是标记裁决。执行者只需点击，系统按声明执行。**

## 二十五、指标和看板作为内容料

### 实体库体系：管理数据类与产品数据类同构

指标和看板在平台中的位置和物料完全同构——它们同属实体库体系：

```
实体库体系
├── 产品数据类实体库
│   ├── 物料库(MAT)          候选来源
│   ├── 复用构件库(REUSE)     候选来源
│   ├── 外购件目录(BOUGHT)    候选来源
│   └── 合格供应商名录(AVL)   约束来源
│
├── 管理数据类实体库
│   ├── 指标定义库(IND)       候选来源 / 约束来源
│   ├── 看板定义库(KANBAN)    候选来源
│   ├── 计划清单库(PLAN)      候选来源
│   ├── 风险清单库(RISK)      候选来源
│   └── 问题清单库(ISSUE)     候选来源
│
└── 参考类实体库
    ├── 标准库(STD)           约束来源
    ├── 法规库(REG)           约束来源
    └── 历史文档库            参考来源
```

### 与物料选用的完整同构

| 操作 | 物料库(MAT) | 指标定义库(IND) | 看板定义库(KANBAN) |
|------|-----------|---------------|------------------|
| **检索已有** | 搜索物料库，按参数检索 | 搜索指标定义库，按业务域/组织/维度检索 | 搜索看板定义库，按业务域/组织/受众检索 |
| **候选比对** | 并排比对参数/价格/交期/认证 | 并排比对口径/维度/目标值 | 并排比对受众/指标集/布局 |
| **选定写入** | 选定→校验约束→写入正文 | 选定→校验约束→写入正文 | 选定→校验约束→写入正文 |
| **定义新的** | 发起新物料寻源→入库后回流 | 定义新指标→指标引擎CU表单→入库即用 | 创建新看板→看板引擎CU编排→入库即用 |

**差异不在机制，只在约束规则和异常路径的具体内容。** 平台为每种实体库类型提供对应的检索面板、比对面板、校验规则、异常路径入口——但它们的运行机制完全相同。

### 指标/看板作为内容料 vs 作为参考资源

- **作为内容料**：文档正文中有字段引用了指标或看板。正文字段类型="实体引用"，引用实体库=指标定义库(IND)或看板定义库(KANBAN)。执行者在辅助栏中检索→选定→写入——和选物料完全一样。找不到时触发异常路径 [定义新指标]/[创建新看板]。
- **作为参考资源**：作业指南中声明了"需要参考：公司级指标清单"。辅助栏·参考资料区自动显示，点击即查，不写入正文。

## 二十六、辅助栏作为作业指南资源的装配载体

### 辅助栏的角色扩展

辅助栏在 91 规范中的当前定义是"显示选中行详情（字段名|字段值）"——被动的数据展示。在执行者工作台中，辅助栏扩展为**按作业指南声明动态装配的资源面板**——内容随当前步骤和光标位置而变化。

三态（关闭/展开/关闭操作）保持不变——扩展的只是展开时的**内容装配逻辑和渲染格式**。

### 页级区块 vs 段级区块

- **页级区块**（始终显示，不随光标位置变化）：当前步骤、输入文档、参考资料、完成标准、输出流转、协作。来自作业指南的**步骤级声明**。
- **段级区块**（随光标在正文中的位置变化）：实体库检索。来自作业指南中与**正文字段实体引用类型**关联的实体库声明。光标移到实体引用字段时激活，移到非实体引用字段时自动折叠。

### 默认展开/折叠策略

| 区块 | 理解型步骤 | 选用型步骤 | 编写型步骤 | 最后一步(自检与提交) |
|------|----------|----------|----------|------------------|
| 当前步骤 | 展开 | 展开 | 展开 | 展开 |
| 输入文档 | **展开** | 展开 | 折叠 | 折叠 |
| 实体库检索 | —（无） | **展开** | 折叠 | —（无） |
| 参考资料 | 展开 | 折叠 | **展开** | 折叠 |
| 完成标准 | 折叠 | **展开** | 展开 | **展开（重点突出）** |
| 输出流转 | 折叠 | 折叠 | 折叠 | **展开** |
| 协作 | 折叠 | 折叠 | 折叠 | 折叠 |

默认状态由作业指南声明驱动，执行者可手动展开/折叠任意区块。

### 正文与辅助栏的实时联动

执行者光标移动 → 辅助栏·实体库检索面板实时切换。光标在 §3.1 → 检索面板显示 §3.1 的上下文。光标在 §3.2 → 检索面板切换为 §3.2 的上下文。光标在已选定的物料段落 → 检索面板切换为"已选定"模式（显示详情而非检索入口）。光标在非实体引用字段 → 检索面板自动折叠
