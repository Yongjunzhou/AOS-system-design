# 流程引擎 — 业务流程 (BP)

> 术语以 `08-背景知识/07-generalspec-architecture-fundamentals.pdf` 为准。
> **BP = Business Process = 业务流程**（不是"业务架构"——后者是 PDF §8 的能力地图视角）。
> 本文档是流程引擎的**唯一业务需求文档、自闭环**（无前置 STR 文档，不依赖 06）。倒置开发：从 [06-EOS平台-流程管理需求.md](../05-原系统需求文档/06-EOS平台-流程管理需求.md) 反推，06 退役后本文档成为唯一权威。数据模型（表结构）在 PA 层，另行成文。

**配置单元**：本文档的末级节点，一个可独立交付、独立验证的原子需求单元。一个页面/Tab/弹窗/操作/接口对应一个配置单元；页面含多个 Tab 时每个 Tab 为独立配置单元（如 BP-1.3~1.6 是流程定义单据页的 4 个 Tab），页面无 Tab 或单 Tab 时整个页面为一个配置单元；一组语义紧密相关的操作可合并为一个逻辑型配置单元（如 BP-4.8 取回/加签/跳转三接口合并）。每个配置单元自包含「需求描述 + 字段清单 + 处理逻辑 + 异常边界 + 验收标准」。

**文档约定**：字段清单 `✅` = 必填；「数据列」= 字段↔表列映射锚点（完整表结构在 PA 层）；优先级 P0（核心闭环）/P1（重要）/P2（增强）/P3（远期，V2 版本以后）。

## 一、业务术语

本章定义流程引擎的核心业务术语。术语总表如下，后续子章节逐个展开说明。

### 术语总表

| 术语 | 英文 | 定义 | 例句 |
|------|------|------|------|
| 流程定义 | Flow Definition | 流程的"壳"——名称、编码、绑定实体、主管。一个定义有多个版本 | 配置人员在流程定义清单新建"合同审批流程"，绑定合同实体 |
| 流程版本 | Flow Version | 定义的一个具体发行版——版本号、BPMN图、节点配置、全局变量。同一时间仅一个使用中 | V2 发布后 V1 自动停用，在途实例继续走 V1，新实例用 V2 |
| 流程实例 | Flow Instance | 一次具体的流程运行——只记录抽象流程信息（标题/所属流程/发起人/发起部门/当前节点/时间/状态），**不含具体业务字段**；业务数据在绑定实体的实例（业务实例）中，通过引用关联 | 合同 SC-001 发起审批，生成一条流程实例，记录"当前在部门审批节点" |
| 业务实例 | Biz Instance | 流程绑定实体的一个具体数据实例——含具体业务字段（如设备借用流程的"被借用设备编号、归还时间"），存在实体自己的表里，与流程实例通过业务实例ID关联 | 设备借用流程的"被借用设备编号、归还时间"在设备借用单实例里 |
| 流程任务 | Flow Task | 待办/待阅——办理人待处理的审批或知会 | 李四的待办出现"合同SC-001 部门审批"任务 |
| 节点事件 | Node Event | 节点配置里绑定的事件，事件类型=新增数据/更新数据/新增流程/普通事件，通过服务绑定关联具体服务 | 节点配置面板里配一个"发送通知"事件，绑定服务管理里注册的通知服务 |
| 事件触发时机 | Event Trigger Timing | 节点事件在节点生命周期中的执行时机，分三阶段：PRE(前置·进入节点时)/VALIDATE(校验·提交前)/POST(后置·办理完成后) | POST时机的事件在节点办理完成后执行——审批通过后自动发通知 |
| 服务绑定 | Service Binding | 节点事件绑定服务/脚本。绑定后，事件在对应触发时机自动执行——事件引擎按配置参数+运行时上下文调用服务并返回结果，失败行为可按配置。所有可绑定服务统一注册在服务管理模块 | 节点POST事件绑定"发送通知"服务→配参数→审批通过后自动发送通知 |

> **补充**：**节点**（任务节点/网关/开始/结束）、**网关**（排他/相容/并行）、**连接线**为 BPMN 标准概念——节点是流程图上的执行单元，网关控制分支路由，连接线是节点间的流转路径，详见 BP-2.3~2.8 的详细规格。

### 1.1 流程定义（Flow Definition）

**定义**：流程的"壳"——名称、流程编码、流程标识、绑定实体、主管。流程定义只存封皮信息，不存 BPMN 图和节点配置。

**关键字段**：流程名称（全系统唯一）、流程标识 flow_key（全局唯一，最大 30 字符）、绑定实体（流程关联的业务数据实体）、主管（最多 3 人）。

**状态**：未发布 → 使用中 → 已停用，由版本状态自动联动，无手动切换。

**例子**：配置人员新建"合同审批流程"这个流程定义，绑定"合同"实体，指定张三为流程主管。此时它只是个空壳，还没有任何可运行的版本——真正的配置在版本里做。

### 1.2 流程版本（Flow Version）

**定义**：流程定义的一个具体发行版——版本号、BPMN 图（节点拓扑/连线/网关）、节点配置、全局变量。真正的流程配置都在版本里。

**关键规则**：同一流程定义同时仅一个版本"使用中"；发布新版本时旧使用中版本自动停用；版本号升级自增 1。

**例子**：给"合同审批流程"新建 V1，画 BPMN（提交→部门审批→结束）并配置节点，发布后 V1 使用中。后续改流程，升级生成 V2（版本号=2），发布 V2 后 V1 自动停用。

### 1.3 流程实例（Flow Instance）

**定义**：一次具体的流程运行——只记录抽象流程信息（标题/所属流程/发起人/发起部门/当前节点/时间/状态），**不含具体业务字段**。由"发起流程"产生，是配置产物（定义/版本）的运行态。

**状态**：草稿 → 审批中 → 已挂起 / 已终止 / 已结束。

**例子**：业务员把合同 SC-001 提交审批，系统生成一条流程实例，记录"当前在部门审批节点、办理人李四"；合同金额、供应商等业务字段在合同实体实例（业务实例）里，通过 biz_inst_id 关联。

### 1.4 业务实例（Biz Instance）

**定义**：流程绑定实体的一个具体数据实例——含具体业务字段（如设备借用流程的"被借用设备编号、归还时间"），存在实体自己的表里。

**关系**：流程实例通过 `biz_inst_id` 引用业务实例；流程实例只记录抽象流转信息，业务数据在业务实例中。

**例子**：设备借用流程实例的"被借用设备编号、归还时间"存在设备借用单实例里，流程实例只记录"这条借用正在审批中"。

### 1.5 流程任务（Flow Task）

**定义**：办理人的待办/待阅。任务由流程实例流转到某节点时生成，办理完成移入已办/已阅表。

**类型**：审批（需办理人通过/驳回等操作）/ 阅知（仅需知悉，无需审批操作）。

**例子**：流程实例流转到"部门审批"节点，给李四生成一条审批任务，出现在李四的待办清单里。

### 1.6 节点事件（Node Event）

**定义**：节点配置里绑定的事件，事件类型 = 新增数据/更新数据/新增流程/普通事件，通过服务绑定关联具体服务。

**例子**：节点配置面板里配一个"发送通知"事件，绑定服务管理里注册的通知服务。

### 1.7 事件触发时机（Event Trigger Timing）

**定义**：节点事件在节点生命周期中的执行时机，分三个阶段——PRE(前置，进入节点时)、VALIDATE(校验，提交前)、POST(后置，办理完成后)。

**关键区别**：三阶段将"进入节点的准备操作"和"提交时的校验操作"分离，避免混在一起误触发；三阶段失败行为不同（PRE 阻断流转、VALIDATE 阻断提交、POST 可配置）。

**例子**：节点配 PRE 事件"资源上锁"，VALIDATE 事件"跨实体状态校验"，POST 事件"发送通知"——分别在不同时机执行。

### 1.8 服务绑定（Service Binding）

**定义**：节点事件绑定服务/脚本。所有可绑定的服务统一注册在服务管理模块，节点事件通过"服务绑定"引用它们并配置参数。

**执行机制**：绑定后，事件在对应触发时机自动执行——事件引擎按配置参数 + 运行时上下文（流程实例ID/操作人/流程变量）调用服务并返回结果，失败行为可按配置（跳过/仅提示/回滚）。

**例子**：节点 POST 事件绑定"发送通知"服务，配置参数（接收人/标题/内容）——审批通过后自动发送站内通知。

## 二、基本原理

本章说明流程引擎的核心原理。2.1~2.5 为业务原理，2.6 为技术原理（技术选型）。

### 2.1 四层结构：定义 → 版本 → 实例 → 任务

流程引擎的业务对象分四层，粒度由粗到细：**流程定义**（壳，一次配置长期有效）→ **流程版本**（发行版，定义的某个具体 BPMN 配置）→ **流程实例**（一次具体审批的运行）→ **流程任务**（某个办理人在某个节点的一次待办）。

### 2.2 壳与内容分离：定义是壳，版本是内容

流程定义只存封皮（名称/标识/绑定实体/主管），真正的 BPMN 图、节点配置都在版本里。因此"复制流程定义"无意义（只复制空壳），"复制版本"才有意义（复制配置）。

### 2.3 版本升级：在途实例走老版本到底

发布新版本后，已发起的在途实例继续用发起时的版本走到底，新建实例自动用最新版本，不提供手动迁移。

### 2.4 状态流转：定义/版本/实例/任务四套状态机

流程引擎有四个业务对象，各自有独立的状态机：

**① 流程定义状态**（由版本状态自动联动，无手动切换）：
```
未发布 →[某版本发布]→ 使用中 →[所有版本停用]→ 已停用 →[某版本重新发布]→ 使用中
```

**② 流程版本状态**：
```
未发布 →[发布]→ 使用中 →[停用]→ 已停用 →[发布]→ 使用中
未发布 →[删除]；使用中 →[升级]→ 生成新版本(未发布)
```
规则：同一流程定义同时仅一个版本"使用中"，发布新版本时旧使用中版本自动停用。

**③ 流程实例状态**：
```
草稿 →[提交]→ 审批中 →[挂起]→ 已挂起 →[恢复]→ 审批中
审批中 →[终止]→ 已终止（不可恢复）；审批中 →[审批结束]→ 已结束
```

**④ 流程任务状态**：
```
待办 →[通过/驳回/移交/终止/超时/多人取消…]→ 已办
待阅 →[阅知]→ 已阅
```
规则：审批类任务办理完成移入已办表（task_result 记录处理结果），阅知类任务移入已阅表。

### 2.5 节点事件三阶段

节点事件按触发时机分三阶段：PRE(进入时) → VALIDATE(提交前) → POST(办理后)。三者时机不同、失败行为不同，配合 1.7 节的事件触发时机。

### 2.6 技术原理：Camunda 只管骨架，平台自管配置

底层 Camunda 引擎只管理流程骨架——节点拓扑、连线、网关条件；视觉样式和节点运营配置（办理人/审批按钮/超时/事件）由平台自管。骨架变更需升版，运营配置变更不升版（见 5.10 BP-2.3 BPMN 画布）。

### 5.2 BP-1.2 流程定义新建/编辑

> 类型：页面型·配置实现（走实体页面模型渲染）　|　来源：06§4.2/§6.1

**需求描述**：配置相关方新建/编辑流程定义封皮——名称、流程标识、绑定实体、主管，必填校验、标识全局唯一。

**页面原型**：配置实现界面，不手绘 ASCII，布局规则——基本信息折叠区（流程名称/流程标识/绑定实体，主管/主管部门/当前版本名称，当前版本号/状态/实例编码规则，1/3 行布局）+ 标题规则折叠区 + 绩效指标折叠区 + 系统信息折叠区（默认折叠）。

**字段清单**：

| # | 字段 | 数据列 | 类型 | 必填 | 默认值 | 交互 | 校验规则 |
|---|------|--------|------|:--:|--------|------|---------|
| 1 | 流程名称 | object_name | 单行文本(100) | ✅ | — | 空值标红 | 全系统唯一 |
| 2 | 流程编码 | code | 单行文本(36) | — | 自动生成 | 系统缺省 | 全局唯一 |
| 3 | 流程标识 | flow_key | 单行文本(36) | ✅ | — | 发布后置灰 | ≤30字符，全局唯一，仅未发布可改 |
| 4 | 绑定实体 | bind_entity_id | 引用字段 | ✅ | — | 联想搜索+弹窗+反显+超链接 | 候选=实体类型"普通流程"使用中实体，仅未发布可改 |
| 5 | 主管 | owner | 用户 | ✅ | — | 多选 | 最多3个 |
| 6 | 主管部门 | owner_dept | 部门 | ✅ | 当前用户顶级部门 | — | 单选 |
| 7 | 实例标题规则 | inst_title_rule | 文本 | — | `{flow_name}-{biz_inst_title}` | — | — |
| 8 | 实例编码规则 | inst_code_rule | 引用编码规则 | — | 与绑定实体一致 | — | — |
| 9 | 备注 | description | 多行文本(500) | — | — | — | — |
| 10 | 当前版本名称/号 | cur_version_name/no | 反向字段 | — | 系统聚合 | — | 只读 |
| 11 | 状态 | life_cycle_status | 单选 | — | 由版本联动 | — | 只读，无手动切换 |

**字段业务含义说明**：

| 序号 | 字段 | 业务含义 | 设置不同值的应用效果 |
|------|---------|---------------------|---------------------|
| 1 | 流程名称/编码/标识（三者区别） | 名称=显示名（用户看到、清单展示）；编码=系统内部唯一标识（自动生成）；标识 flow_key=对外调用 key（系统集成用） | 名称用于清单和实例标题；编码用于系统内部引用；标识用于系统间集成、实例编码 |
| 2 | 绑定实体 | 流程审批时操作的业务实体（数据表） | 绑定"合同"实体→审批时操作合同数据；变更会清空已有关联配置 |
| 3 | 主管 | 谁能管理这个流程 | 设张三→张三成为该流程主管，能在清单看到并管理该流程 |
| 4 | 实例标题规则 | 流程实例的标题生成模板 | 默认 `{flow_name}-{biz_inst_title}`；改模板→影响所有新实例标题 |
| 5 | 实例编码规则 | 流程实例的编码生成规则 | 默认与绑定实体一致；改规则→影响新实例编码 |

**处理逻辑**：

| 场景 | 规则 |
|------|------|
| 加载 | 单据页默认详情态（只读）；点"编辑"进入编辑态 |
| 编辑权限 | 仅流程管理员，或主管字段含本人的主管可见 |
| 必填校验 | 名称/标识/绑定实体/主管/主管部门必填 |
| 唯一校验 | 名称全系统唯一、标识全局唯一，重复拦截 |
| 绑定实体变更 | 弹"将清空已有关联配置"确认，确认后清空 |
| 字段可改约束 | 绑定实体、流程标识仅未发布可改，发布后置灰 |
| 状态联动 | 由版本状态联动：有使用中版本→使用中；全停用→已停用 |
| 保存 | 校验通过后保存回详情态；取消放弃修改 |

**异常与边界**：绑定实体已有配置时变更需确认清空；发布后改标识/实体拦截；名称/标识重复拦截；主管超3人拦截。

**验收标准**：
- [ ] Given 流程名称留空 → When 点"保存" → Then 拦截标红、不落库、焦点回名称框
- [ ] Given 名称/标识重复 → When 点"保存" → Then 提示重复、不落库
- [ ] Given 流程已发布 → When 打开编辑 → Then 绑定实体、流程标识置灰
- [ ] Given 发布某版本 → When 刷新详情 → Then 状态自动变"使用中"

### 5.25 BP-4.1 审批办理-通过/驳回

> 类型：逻辑型　|　来源：06§5.8/§5.13/§8.3/§8.5

**需求描述**：审批人对当前待办执行通过或驳回，驱动实例流转至下一节点（通过）或前序节点/发起人（驳回），记录办理意见与处理结果。

**输入/输出**：

| 项 | 内容 |
|----|------|
| 输入 | 任务ID、办理意见（可空）、下一步办理人（办理人可选时）、节点表单数据 |
| 输出 | 流转结果（下一节点待办 / 驳回目标节点）；办理记录写 sys_flow_task_rec（task_result=approved/rejected） |
| 格式 | 意见文本 ≤1000 字符；下一步办理人 = 用户ID 列表 |

**处理逻辑**（统一处理流程，06§5.13.2）：

```
1. 子业务校验（必填+字段合法性）→ 2. eventEngine.execute(VALIDATE)
3. 调 Camunda completeTask/moveTo → 4. eventEngine.execute(POST)
5. 处理 doneList（当前任务移已办）→ 6. 处理 todoList（生成下一节点待办）
7. eventEngine.execute(PRE) → 8. 刷新实例 → 9. 事务提交 → 10. 异步发通知
```

**状态流转**：

```
状态图：待办 →[通过]→ 已办(approved) →[流转]→ 下一节点待办
       待办 →[驳回]→ 已办(rejected) →[流转]→ 驳回目标节点待办
转移表：
| 当前状态 | 事件 | 目标状态 | 动作 |
| 待办 | 通过 | 已办(approved) | 流转至下一节点，生成新待办 |
| 待办 | 驳回 | 已办(rejected) | 按重提策略流转至目标节点 |
```

**驳回后重提策略**（驳回按钮所在节点配置，06§8.3）：全部失效(默认)/仅驳回节点重审/指定重审起点。

**异常与边界**：校验事件失败阻断提交、数据保留；非办理人拦截（管理员/主管可代办）；意见必填留空拦截；下一步办理人空且不可自动选→弹窗选人；并行分支多人取消。

**验收标准**：
- [ ] Given 办理人点"通过" → When 提交 → Then 当前任务移已办(approved)，下一节点生成待办
- [ ] Given 办理人点"驳回" → When 提交 → Then 当前任务移已办(rejected)，按重提策略流转
- [ ] Given 校验事件失败 → When 提交 → Then 阻断弹提示、数据保留
- [ ] Given 意见必填留空 → When 提交 → Then 拦截不流转
