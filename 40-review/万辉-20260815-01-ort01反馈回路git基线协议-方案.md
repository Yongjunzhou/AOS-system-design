## 一、背景与动机

**现状问题**：ort01 反馈回路叠了三层状态载体——表A/表B（外部权威源）+ 管理区状态摘要（内嵌给人看）+ 反馈区/方案块（方案与反馈载体），再叠加对话口令层与同步契约。光反馈回路就要七步（对话→写触发词→执行→表A→表B→管理区→清理反馈区），且双轨（反馈区 ∥ 表A）靠同步契约对齐，任何一边漏写即漂移。

**根因**：91 §A.5 对话模式（人类说话→AI 直接执行）与「文档即状态」模式（反馈写进文档→下次运行检测）叠床架屋。

**目标**：反馈**单源化**——人类编辑文档 = 反馈；git diff 检测；表A 汇总；交互只记录不处理。

---

## 二、新机制总览（git 基线协议）

**一句话**：反馈的唯一持久载体 = **文档变更**；AI 用 `git diff <基线>` 检出变更、判读意图、**记录**到表A；**处理**由 Step 2 基于表A 记录执行，不由对话触发；AI 每轮交接 commit 形成基线。

```
① AI 交接：更新表A/表B → ai-commit（[AI] 标识 = 新基线）→ Step End 摘要
② 人类反馈：直接编辑文档（或对话告知，AI 代为记录）
     · 改方案块行号/标签          → 调整
     · 反馈区写 [同意执行]        → 同意（照当前文档执行）
     · 反馈区写 [确认不拆分]/[废弃] → 对应动作
     · 已切分后改切分文件/写 [重新切分] → 重切
     · 人类提交与否均可（git diff <基线> 全覆盖）
③ AI 下次运行：
     Step 1: git diff <基线> 找变更文件 → 读变更 hunk → 判读意图 → 记录到表A
     Step 2: 读表A 已记录未处理反馈 → 处理（同意→切分 / 调整→重生成 / 废弃→终止 / 重切→重切）
     Step 3: 读表A 选入材料 → 生成方案块
     Step End: ai-commit 新基线 → 输出摘要 → 保持对话（对话反馈只记录）
```

**角色表**：

| 对象 | 定位 | 谁写 |
|------|------|------|
| 文档（方案块/反馈区/切分文件） | 反馈的输入源（人类编辑处） | 人类 |
| git（基线 + diff） | 变更检测通道 | AI 管提交（带标识）；人类随意 |
| 表A/表B | 流程路由权威源 + **反馈记录载体** | 生命周期/AI建议/记录：AI；人类决策：人类 |
| 管理区记录 | 给人看的决策/迭代摘要 | AI 推导 |

**单源原则**：反馈内容只存在于表A 的记录字段（内容摘要/反馈意见），从文档 diff 聚合导出、由对话记录写入——不做平行维护。表A 可随时从基线重导出 → **不会不同步（自愈）**。

## 三、四条修正（已锁定）

1. **编号从 1 开始**：步骤为 Start / 1 / 2 / 3 / End，无 Step 0。
2. **先反馈后新增**：Step 2（反馈处理）在 Step 3（新增处理）之前，同一次运行内按此顺序执行。
3. **交互之前先提交变更**：Step End 第一个动作 = `ai-commit`（形成新基线），再输出摘要。
4. **交互只记录，不处理**：记录与处理分离——Step 1 + Step End 对话只把反馈记入表A；Step 2 才基于表A 记录执行处理，不由对话触发。

## 四、新 Step 布局

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查目录/状态文档/**基线就绪** | 统一 | 就绪/结束 | — |
| **1** | **变更检测与反馈汇总** | git diff 检变更 → 判读意图 → **记录**表A | 统一 | 反馈记录/变更清单 | 表A（内容摘要/反馈意见） |
| **2** | **反馈处理** | 读表A 已记录反馈 → 执行/调整/废弃/重切 | 统一 | 切分文件/新版方案/废弃记录 | 表A、表B、切分文件、文本化文档 |
| **3** | **新增处理** | 读表A 选入材料 → 生成方案块 | 统一 | 方案块+反馈区 | 表A、文本化文档 |
| End | 输出交互 | **先 ai-commit** → 输出三区摘要 → 保持对话（反馈只记录） | 人类 | Step End 输出 | git（基线） |

**编号映射**：检测 = 新 Step 1；反馈 = 原 Step 2（编号不变，输入改「读表A 记录」）；新增 = 原 Step 1（编号 1→3）。

### Step 1 · 变更检测与反馈汇总（新增，详述）

1. **取基线**：`HEAD @上次AI运行` 字段（校验：最近 AI 提交 `git log --author="EOS-AI" -1`）
2. **找变更**：`git diff --name-status <基线>` → 变更文件清单（含表A 变更）
3. **按状态筛范围**：`切分方案待确认` → 只看文本化文档；`已切分` → 看切分文件/文本化文档
4. **读变更**：逐文件 `git diff <基线> -- <文件>` 只取变更 hunk
5. **判读意图**：

   | diff 内容 | 意图 |
   |-----------|------|
   | 方案块行号/标签被改 | 调整 |
   | 反馈区写 `[同意执行]` | 同意 |
   | 反馈区写 `[确认不拆分]`/`[废弃]` | 对应动作 |
   | 切分文件被改 / 写 `[重新切分]` | 重切 |
   | 表A 人类决策被改 | 选材/终止 |

6. **记录写表A**：内容摘要/反馈意见；人类对表A 的直接修改标记 `[需确认]` 不覆盖
7. **路由**：有反馈 → Step 2；有新增选入 → Step 3；全无 → 「无待处理对象」结束

**红利**：人类的一切输入（选材、反馈、终止）都以「文档/表A 变更」落在 git 里，Step 1 统一检测分类——单一检测源，不再有「读正文区反馈」「读表A 人类决策」两套入口。

### 记录 vs 处理（修正 4 落实）

| 动作 | 触发 | 落点 | 内容 |
|------|------|------|------|
| **记录** | Step 1（离线 diff 检出）+ Step End 对话（在线反馈） | 表A 内容摘要/反馈意见 | 反馈内容与要点 |
| **处理** | Step 2 反馈处理（读表A 已记录未处理反馈） | 表A/表B/切分文件/文档 | 执行动作 |

**反馈生命周期两轮**：
```
记录轮: Step 1 diff 检编辑 → 记入表A → End：提交 + 摘要「已记录：调整002范围」
        对话中人类补充反馈 → AI 记入表A → 提交 → 摘要「已记录：…」（不处理）
处理轮: Step 2 读表A 已记录反馈 → 执行 → End：提交 + 摘要「已处理：…」
```
