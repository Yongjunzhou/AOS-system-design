# 《流程引擎-业务流程》评审意见

> 评审对象：`万辉-20260814-01-流程引擎-业务流程.md`
> 评审日期：2026-08-14
> 评审范围：全文——业务术语（一）、基本原理（二）、BP 树（三）、配置单元清单（四）、详细规格（五）
> 评审结论：**结构合格，方法论扎实，可继续推进；但存在 5 处内部矛盾（高优先级），建议在展开其余 30 个配置单元之前先消项，否则矛盾会被后续单元放大。**

## 一、总体评价

**优点（值得保持）：**

1. **自闭环设计清晰**：明确 BP 文档为唯一权威、从 06 反推后不再依赖源文档；「来源」列定位为历史溯源而非依赖引用，思路正确。
2. **配置单元原子化 + 自包含模板**：一个页面/Tab/弹窗/操作/接口对应一个单元，且固定「需求描述→字段清单→处理逻辑→异常边界→验收标准」结构，可独立交付、独立验证——是需求文档里少见的"可验收单元"粒度。
3. **术语有例句支撑**：术语总表每条配"定义+例句"，业务含义展开表（如 5.2 字段业务含义）能有效消除歧义。
4. **边界意识好**：数据表结构划到 PA 层、业务实例与流程实例分离、Camunda 只管骨架平台自管配置——职责边界交代清楚。
5. **验收标准用 Given-When-Then**，与"独立可验证"的单元定义自洽。

**主要风险：** 文档主体仍是"清单级"（32 个单元中仅 2 个展开详细规格），当前可验证性集中在 5.2/5.25 两处。而 5.2/5.25 本身又暴露了若干内部矛盾——这些矛盾若不先解决，会直接影响后续 30 个单元的展开口径。

## 二、必须修正（高优先级）

> A1~A5 为文档内部矛盾；**A6 为定义地基缺失（评审中补充）**——概念引入顺序问题，影响全文理解。

### A1. BP-2.5 的 Tab 拆分与「每 Tab 独立成单元」规则冲突
- **位置**：引言「配置单元」定义（§ 文档约定，第 7 行） ↔ BP-2.5（第 239 行）
- **问题**：引言明确「页面含多个 Tab 时每个 Tab 为独立配置单元（如 BP-1.3~1.6）」。而 BP-2.5「任务节点配置面板」把**基础 + 高级两个 Tab 合并成一个单元**，优先级还分裂为 P0（基础）/P1（高级）。一个单元内两种优先级，与「原子、独立交付」的定义矛盾。
- **建议**：二选一——
  - 按规则拆分为两个单元：BP-2.5 任务节点配置-基础（P0）+ BP-2.5a 任务节点配置-高级（P1），并同步更新 BP 树与清单、依赖表；
  - 或修改引言规则，补充例外：「同一页面内强耦合的 Tab（如节点基础/高级配置）可合并为一个单元」，并注明优先级取高者。

### A2. 办理意见「可空」与「必填」矛盾
- **位置**：5.25 输入/输出表（第 396 行「办理意见（可空）」） ↔ 异常与边界（第 423 行「意见必填留空拦截」） ↔ 验收标准（第 429 行「意见必填留空→拦截不流转」）
- **问题**：三处口径不一致。结合 BP-2.4「全局配置面板」含「办理意见设置」，实际语义应是**意见是否必填由流程级配置决定**，但正文未这样表述。
- **建议**：统一表述为——「办理意见是否必填由流程全局配置的『办理意见设置』决定（可空/必填/默认文案在 BP-2.4 定义）」；验收标准相应改为「Given 流程配置意见必填 且 意见留空 → Then 拦截不流转」与「Given 流程配置意见可空 → Then 允许空提交」两条。

### A3. 「复制流程定义无意义」与 BP-1.7 提供复制功能冲突
- **位置**：2.2（第 117 行「复制流程定义无意义」） ↔ BP-1.7（第 227 行，P0，「复制仅复制封皮」）
- **问题**：基本原理断言"复制定义无意义、复制版本才有意义"，但功能清单却把「复制定义」作为 P0 交付。要么是原理表述错误，要么是复制定义有 2.2 未承认的业务价值（如：以现有流程为模板快速新建相似流程）。
- **建议**：二选一——删除 2.2 的"无意义"论断，改为「复制定义仅复制封皮，用于以现有流程为起点新建相似流程」；或删除 BP-1.7 的定义复制功能（仅保留导入/导出/删除）。

### A4. flow_key 长度口径不一致
- **位置**：1.1（第 45 行「流程标识 flow_key…最大 30 字符」） ↔ 5.2 字段清单 #3（第 344 行「单行文本(36)」+ 校验「≤30字符」）
- **问题**：同一字段两处长度冲突；且 5.2 字段清单内部"列类型(36)"与"校验(≤30)"本身就自相矛盾。另注意 #2 流程编码为「单行文本(36)」，疑似把 flow_key 误抄为 36。
- **建议**：统一为 30——字段清单 #3 改为「单行文本(30)」，校验「≤30 字符、全局唯一、仅未发布可改」；并与 PA 层表结构对齐。

### A5. BP-1.2 与 BP-1.3 内容重叠，单元边界不清
- **位置**：BP-1.3（第 223 行「基本信息+标题规则+绩效指标+系统信息折叠区」） ↔ 5.2 页面原型（第 336 行，同样四个折叠区）
- **问题**：BP-1.2（新建/编辑）与 BP-1.3（单据页基本信息 Tab）字段集几乎完全相同。按「一个 Tab 一个单元」规则，两者边界难以判定，后续展开时极易重复铺开。
- **建议**：明确分工——**BP-1.2 = 新建入口 + 表单校验/唯一性/绑定实体变更清理**（写"动作"），**BP-1.3 = 详情页基本信息 Tab 的展示与再编辑**（写"页面"）。字段清单只维护一份（建议放 5.3），5.2 引用之，避免双份维护漂移。

### A6. 缺根概念「流程」定义，「壳」比喻无地基
- **位置**：术语表第一章 1.1（第 41~49 行）——全文未见"流程"本身的定义；头部注释仅将 BP 锚定为"业务流程"（第 4 行），未定义其内涵
- **问题**：文档直接从「流程定义是流程的壳」切入，但从未先回答"流程是什么"。壳/内容这对比喻是全文的**承重结构**——2.2 壳与内容分离、BP-1.7「复制仅复制封皮」、1.1/1.2 定义、2.1 四层结构都建立在它之上——却从半路引入。读者不知道流程的边界、与审批流/工作流/子流程的关系，就无法判断"壳"对应什么、为什么存在。这是概念引入顺序问题，影响整篇可理解性。
- **建议**：
  1. 术语表最前新增根概念「流程（业务流程）」词条：先定义业务过程的本质（如"为达成特定业务目标，由节点与流转规则组成的业务活动集合"），再界定它与审批流/工作流/子流程的关系；
  2. 重构 1.1/1.2 引入顺序为——**先定义"流程"→ 再说明平台如何承载一个流程（四层结构：定义=壳/静态封皮，版本=内容/具体配置，实例=运行态，任务=办理态）→ 壳/内容比喻自然落地**，与 2.1/2.2 呼应；
  3. 术语总表同步补「流程」条目，置于 1.1 之前。

**草案 A｜术语表新增「1.0 流程」根概念（可整段贴入术语表）：**

```
### 1.0 流程（业务流程，Business Process）

**定义**：为达成特定业务目标，由若干**节点**（任务节点/网关/开始/结束）按既定**流转规则**
（顺序、条件分支、并行汇聚）串接而成的业务活动集合。一次完整的流程包含
"发起 → 逐节点办理 → 结束"的过程。

**关键区别（与相关概念）**：
| 概念 | 与"流程"的关系 |
|------|----------------|
| 审批流 | 流程的特化形态：以"通过/驳回"驱动流转，用于审批类场景 |
| 工作流 | 流程的特化形态：以"任务推进"为主，覆盖审批以外的协同场景 |
| 子流程 | 流程的一种节点类型（BP-2.5）：被主流程嵌入调用，本质是另一个可复用流程 |

**在信息平台中的体现（流程引擎如何承载一个流程）**：一个业务"流程"在平台中不是单一
对象，而是按"静态配置 → 运行态 → 办理态"分四层承载：

| 层 | 对象 | 承载内容 | 回答的问题 |
|----|------|---------|-----------|
| 静态配置·壳 | 流程定义 | 名称/编码/标识/绑定实体/主管 | 系统里有哪些流程 |
| 静态配置·内容 | 流程版本 | BPMN 图/节点配置/全局变量 | 这个流程具体怎么跑 |
| 运行态 | 流程实例 | 标题/当前节点/办理人/状态 | 这一次跑得怎么样 |
| 办理态 | 流程任务 | 待办/待阅（办理人×节点） | 现在轮到谁办 |

四层关系：定义下有多个版本；版本发布后发起流程产生实例；实例流转到节点生成任务；
版本升级后在途实例走老版本到底（见 2.3）。

**例子**：采购流程在平台中的体现——流程定义"采购审批"（壳）+ 版本 V1（内容）→
业务员提交采购单生成一条流程实例（运行态）→ 流转到"部门审批"节点给李四生成一条
审批任务（办理态）。
```

（内容）→ 1.3 流程实例（运行态）→ 1.4 业务实例 → 1.5 流程任务 → …（后续编号不变）。

1.1 开篇建议（把"壳"放到四层上下文之后）：
**定义**：流程的静态封皮（壳）——承载流程的名称、流程编码、流程标识、绑定实体、

### B3. 挂起/终止的操作对象层级不清

## 六、方法与结构建议

- **E1. 展开排期建议（按依赖 + P0 主线）**：30 个待展开单元建议按链路推进——`BP-1.1/1.2/1.3/1.7 → BP-2.3/2.5/2.9 → BP-3.2 → BP-4.1`（与文档端到端场景"配置流程→发起审批→办理审批"一致），其余单元（P1/P2/P3）随后补齐。
- **E2. 逻辑型单元补充「Camunda 映射」**：5.25 提到「调 Camunda completeTask/moveTo」——`moveTo` 非 Camunda 标准 API（标准为 complete / createModification / jump），需确认是平台封装。建议每个逻辑型单元固定一节「与 Camunda/平台接口的映射」，避免开发期口径反复。
- **E3. 页面型单元补充边界**：建议在模板中增加「权限矩阵」「空态/加载态/无权态」两项（验收标准已有 Given-When-Then，可并入）。
- **E4. 文档维护机制**：建议在版本记录前固定「待展开清单」节，评审意见消项后回填到版本记录，保持"清单级 → 详细级"的演进可追踪。

### 中优先级

#### M1. 角色视角表与「管理员/主管可代办」冲突
- **位置**：角色视角表（§四末） ↔ 5.25 异常与边界
- **问题**：角色表只给「业务用户」开放 BP-4 全部办理；「流程管理员」「流程主管」仅列 BP-1/2/3，无 BP-4。但 5.25 异常与边界写明"非办理人拦截（管理员/主管可代办）"——代办即执行审批，属 BP-4.1 能力。两处口径矛盾，直接影响 BP-4 各单元展开时的权限建模。
- **建议**：二选一——① 角色表为管理员/主管补 BP-4（标注"代办"权限）；② 5.25 改为"非办理人拦截（管理员/主管可代办，须有 BP-4 办理权限）"，并同步角色表。另 BP-3.4 数据修正归管理员/主管，宜一并明确其与 BP-4 的权限边界。

#### M5. 首个版本（V1）的创建途径未定义
- **位置**：端到端使用场景「BP-2.1 新建版本」 ↔ BP-2.1/BP-2.9
- **问题**：端到端场景以「BP-2.1 新建版本」作为链路第二步，但 BP-2.1 是版本清单页（仅发布/停用/升级/复制按钮），BP-2.9 只定义"升级自增 1"（前提是已有使用中版本）。全新定义、零版本状态如何生成 V1 进入"未发布"态，全文无单元定义——首个版本是"升级"之外的另一条创建路径，却无归属单元。
- **建议**：二选一——① BP-2.1 补"新建版本"动作（生成空白 BPMN 的未发布版本）；② BP-2.9 明确"新建首个版本"分支。端到端场景改用实际单元名。

### 低优先级

#### M3. BP-3.4 数据修正的范围未定义
- **位置**：BP-3.4（§四）
- **问题**：仅定义"数据修正页面模型，无审批按钮"，但可修正哪些字段、由谁修正、修正是否重触发节点事件/重发通知均未交代（复用页面模型关系 C4 已述）。
- **建议**：补一句修正边界，如"仅修正业务数据、不重走审批、记变更日志"。

#### M4. 任务状态机把「移交/终止/超时」一律归"已办"
- **位置**：2.4 ④ 任务状态机
- **问题**：状态图将 通过/驳回/移交/终止/超时/多人取消 全部指向"已办"——被移交任务在转办人视角应为"已移交"（受让人另生成新待办），被终止任务应为"已终止"；正文"task_result 记录处理结果"可部分弥补，但状态图口径丢失了区分。
- **建议**：按 task_result 拆分目标态（已办/已移交/已终止），或加注"终点统一为已办，具体结果见 task_result"。

#### M6/M7. 外部概念引用未定义出处
- **位置**：变更记录 Tab 复用 `sys_change_log`（§四注）；BP-2.5 绑定"作业指南"
- **问题**：`sys_change_log` 组件与"作业指南"概念被引用但无出处，与 C1（服务管理模块）、B2（术语缺失）同类。
- **建议**："作业指南"并入 B2 待补术语清单；`sys_change_log` 注明归属组件或改写为可追溯引用。

## 九、附录：配置单元定义示例（A1 CU 口径基准）

> 本节为 **2026-08-14 讨论定稿**的 @engine-flow 配置单元完整示例，作为「万辉」文档 32 个配置单元按 A1 CU 口径重表达的参照基准（口径定义见 91 规范 v5.13 §3.3 + wft02-eng v8.6 §2.2.1）。
>
> **口径要点**：CU → 配置信息组二级结构；配置信息组 = 某组配置字段，这组字段能够提供相对独立的业务能力；每组按「配置操作（配置人员操作过程）→ 系统处理（保存时 + 生效后编号式，生成载件）→ 运行期能力（业务人员操作过程）」说明。

### 示例一：@flow-cu-node-config 流程节点配置（操作型）

> 类型：A1 CU｜目标引擎：@engine-flow｜对应系统实体：FlowNodeConfig
> A2 上下文：业务配置人员 → 流程引擎场景；业务运行对象=流程版本下的任务节点；触发=画完 BPMN 后需配节点才可发布。
> A1 产品路径：流程与IT域 → @engine-flow → 流程节点配置（CU）｜配置入口：流程设计器·节点配置面板

**5.1 节点基本信息/类型组** —— 提供：节点办理形态能力
- 字段：节点名称、节点类型（审批/征集/子流程）
- 配置操作：1. 选中画布上的节点；2. 填节点名称、选节点类型；3. 提交保存
- 系统处理：保存时——校验类型合法、名称不冲突 → 落库；生效后——该组保存后系统应：① 将节点类型写入 FlowNodeConfig 并随版本装载；② 运行期按类型决定该节点的办理形态
- 运行期能力：1. 实例流转到该节点，业务人员打开办理单据页；2. 看到该节点的办理形态（审批/征集/子流程）

**5.2 关联表单组** —— 提供：节点办理界面能力
- 字段：关联表单
- 配置操作：1. 打开配置面板的"关联表单"；2. 从已发布表单中选择该节点办理时打开的功能表单；3. 提交保存
- 系统处理：保存时——校验表单已发布 → 记录绑定；生效后——该组保存后系统应：① 记录绑定关系；② 运行期将该表单生成为该节点的界面载件
- 运行期能力：1. 业务人员打开该节点的办理功能表单；2. 在此页面上办理该节点

**5.3 办理人/传阅人组** —— 提供：任务分派能力
- 字段：办理人、传阅人
- 配置操作：1. 在配置面板配置办理人（选角色/人员）；2. 配置传阅人；3. 提交保存
- 系统处理：保存时——校验角色/人员存在 → 记录分派；生效后——该组保存后系统应：① 记录办理人/传阅人配置；② 实例流转到该节点时按配置生成流程任务并分派
- 运行期能力：1. 实例流转到该节点，系统按配置生成待办/待阅任务；2. 业务人员在待办/待阅清单看到该节点任务；3. 进入办理

**5.4 操作项/办理意见组** —— 提供：节点办理操作能力
- 字段：操作项（通过/驳回/转办/加签）、办理意见设置（必填/可空/默认文案）
- 配置操作：1. 在配置面板勾选该节点的操作项按钮集；2. 配置办理意见设置（必填/可空/默认文案）；3. 提交保存
- 系统处理：保存时——校验操作项引用的事件/服务已注册 → 记录按钮集与意见设置；生效后——该组保存后系统应：① 记录按钮集与意见设置；② 运行期在办理单据页上按配置渲染按钮构件载件；③ 点击后按配置驱动该节点办理结果
- 运行期能力：1. 业务人员打开办理单据页，看到通过/驳回/转办/加签按钮与意见输入；2. 点"通过"→该节点办理完成并流转 / 点"驳回"→按重提策略流转至目标节点；3. 提交办理意见→记录为 task_result

**5.5 子业务校验规则组** —— 提供：提交校验能力（以系统处理为主）
- 字段：校验规则（条件表达式、错误提示）
- 配置操作：1. 在配置面板配置子业务校验规则（条件表达式、错误提示文案）；2. 提交保存
- 系统处理：保存时——校验规则可解析 → 存储规则；生效后——该组保存后系统应：① 装载校验规则；② 业务人员提交时按规则执行校验，失败阻断提交并提示
- 运行期能力（以系统处理为主）：业务人员提交时如校验失败，看到阻断提示、数据保留

**5.6 节点事件组** —— 提供：事件触发能力（以系统处理为主）
- 字段：事件绑定（关联服务）、触发时机（PRE/VALIDATE/POST）、失败行为（阻断/仅提示/回滚）
- 配置操作：1. 在配置面板配置节点事件；2. 选触发时机（PRE/VALIDATE/POST）；3. 绑定到已注册服务；4. 配失败行为；5. 提交保存
- 系统处理：保存时——校验服务已注册、时机合法 → 存储事件绑定；生效后——该组保存后系统应：① 装载事件绑定；② 运行期在对应时机触发绑定服务；③ 按失败行为处理
- 运行期能力（以系统处理为主）：POST 事件如发通知，业务人员事后收到消息

**5.7 超时流转规则组** —— 提供：超时处理能力（以系统处理为主）
- 字段：超时时长、超时动作（自动审批/流转目标）
- 配置操作：1. 在配置面板配置超时流转规则（超时时长、超时动作）；2. 提交保存
- 系统处理：保存时——校验时长/目标合法 → 存储超时规则；生效后——该组保存后系统应：① 装载超时规则；② 到点自动按规则审批/流转；③ 通知相关角色
- 运行期能力（以系统处理为主）：超时未办时业务人员收到催办/超时通知

### 示例二：@flow-cu-version 流程版本配置（生命周期型）

> 类型：A1 CU｜目标引擎：@engine-flow｜对应系统实体：FlowVersion
> A2 上下文：业务配置人员 → 流程引擎场景；业务运行对象=流程定义下的流程版本；触发=定义建好后需建版本、画 BPMN、发布。
> A1 产品路径：流程与IT域 → @engine-flow → 流程版本配置（CU）｜配置入口：流程设计器·版本管理页

**4.1 版本基本信息组** —— 提供：版本创建/登记能力
- 字段：版本号、版本说明
- 配置操作：1. 在版本管理页新建版本；2. 填版本号、版本说明；3. 保存生成"未发布"版本（未发布可删除）
- 系统处理：保存时——校验版本号不重复/自增合法、说明非空 → 落库 FlowVersion（状态=未发布）；删除时校验无在途引用；生效后——该组保存后系统应：① 生成未发布版本记录；② 在版本清单中呈现该版本及状态指示灯
- 运行期能力（以系统处理为主）：未发布版本对业务无影响，发布后才影响新实例

**4.2 生效策略组** —— 提供：版本生效能力（以系统处理为主）
- 字段：生效策略（发布即生效/定时生效）、生效时间（定时时）
- 配置操作：1. 选生效策略（发布即生效/定时生效）；2. 若定时生效则指定生效时间；3. 提交保存
- 系统处理：保存时——校验策略合法、定时时间合法 → 存储生效策略；生效后——该组保存后系统应：① 发布时按策略生效（发布即生效→置"使用中"并自动停用其他使用中版本；定时生效→登记定时任务到点生效）；② 生效后新流程实例自动用该版本
- 运行期能力（以系统处理为主）：业务人员发起新流程时系统自动选"使用中"版本，无感

**4.3 升版规则组** —— 提供：升版管理能力（以系统处理为主）
- 字段：版本号自增规则、在途实例处理方式
- 配置操作：1. 配置升版规则（版本号自增方式、在途实例处理方式）；2. 提交保存
- 系统处理：保存时——校验升版规则合法 → 存储规则；生效后——该组保存后系统应：① 升级时按规则生成新版本（自增 1，状态=未发布）；② 发布新版本后在途实例继续走发起时版本、新实例用新版本；③ 在途实例不提供手动迁移
- 运行期能力（以系统处理为主）：业务人员在途流程继续按老版本办理，不受升版影响
