```
概念档案 · 核心概念
① 定义  概念网络中处于枢纽地位的概念——解释领域内其他概念都要用到它，理解它自己只需很少前置知识

② 背景  压缩学习实验发现无标度网（少数枢纽占据大量连接）最易学——识别枢纽成为学习的第一步

判据  反事实检验（去掉它领域还成立吗？）+ 词频（领域文本里被反复提到）+ 被引用度（其他概念定义引用它最多）+ 前置数（理解它所需前置最少）；后三条为代理判据
```

```
概念档案 · 根概念
① 定义  概念网络的"承重柱"——领域中不可再向下归约的源头概念，其余概念（含核心概念）都由它导出；根概念 ⊂ 核心概念（承重柱 ⊂ 骨架），通常 1~3 个
⑥ 对立  派生概念——可由根概念导出（如流程 = 产品数据在时间上的投影）；根概念不可由任何域内概念导出（维度：归约方向）
⑦ 辨析  核心概念（骨架，管"连接多"，3~5 个）vs 根概念（承重柱，管"是源头"，1~3 个）；枢纽 hub（认知层，压缩学习术语）vs 根概念（知识层，源头术语）——同一结构原理的两层表现
⑨ 英文  root concept；root 本义"植物的根"——营养从根流向枝叶；图论有向图的根（root）= 无入边的源节点，恰对应"被全部依赖、不依赖别人"
② 背景  早期用"被引用度=出度、前置数=入度"测核心概念，实际测的是 root（有向源）属性而非 hub（无向中心）属性——名称与判据错位，逼出"根概念"这一层
③ 历史  图论 root（有向源）→ 存在物的不可归约者→ 本方法论四条判据（原子/生成/不可替代/递归）→ 判定矩阵 + 演绎链（§1.7.3）
④ 问题  没有根概念之前，"核心概念清单"只是凭感觉的枢纽列表，不知道哪根柱子最承重——这个领域，什么存在物是不可再归约的源头？
⑤ 场景  确定学习与治理的第一对象、解释"为什么是这个概念"；只需"学得快"时用核心概念就够，不必每次都挖到根
⑧ 误区  ✗ "根概念=最重要的概念"——是最"源头"的，未必最"重要"（质量很重要，但它是需求/系统的派生）；✗ "根概念与核心概念矛盾"——分层不冲突（承重柱 ⊂ 骨架）；✗ "根概念凭直觉找"——必须过判定矩阵+演绎链；✗ "根概念永恒"——随范式更替
判据  原子性（不可由域内概念定义）+ 生成性（其余概念从它派生）+ 不可替代性（去掉它领域崩塌）+ 递归性（多个抽象层级反复生效）
```

```
概念档案 · 基本原理
① 定义  原理侧的"源头"——领域中不可再被推导的法则（命题），是根概念（母体）的语义内蕴被展开成的显式命题；基本原理 ⊂ 核心原理（公理 ⊂ 骨架规则），与根概念同处源头层
⑥ 对立  派生命题——可由基本原理推导（如测试用例设计规则由"验证以规定需求为参照"推出）；基本原理不可由域内任何命题推导（维度：推导方向）
⑦ 辨析  核心原理（枢纽命题，骨架规则）vs 基本原理（源头命题，公理）；原理 principle（一般规律）vs 命题 proposition（可判真假的陈述，弗雷格）；"原理"日常还指"原则/准则"，本方法论取"源头法则"义
⑨ 英文  root principle / axiom；root 与根概念同源（图论有向源：无入边）；axiom 希腊语 axiōma"被认为值得的东西"——自明、无需证明的起点
② 背景  诞生于"原理也有根"的追问：概念侧分出根层后，原理侧是否同样有源头？2×2 层级矩阵（节点/边 × 核心/根）落位后，发现原理侧的源头恰是根概念定义的语义内蕴
③ 历史  欧氏几何公设法 → 弗雷格"概念无真假、命题才有真假" → 本方法论 2×2 层级矩阵 → 母体—展开修正（基本原理 = 根概念的展开运算，演绎链即展开器）
④ 问题  没有基本原理之前，领域推理没有公理层——规则从哪来、凭什么站得住，全凭经验与权威：这个领域，什么法则是不容再推导的源头？
⑤ 场景  建立领域公理层、把概念内蕴显式化为工程规则（评审准则/测试用例/追溯矩阵）、用原理作探针检验对根概念的理解；只需"学得快"时用核心原理即可
⑧ 误区  ✗ "基本原理=最重要的原理"——是最"源头"的，未必最"重要"；✗ "搞懂根概念就自动搞懂基本原理"——跨概念原理在接缝里，且内蕴≠显式、须展开成命题才可检验；✗ "基本原理凭直觉找"——须过四判据；✗ "基本原理永恒"——随范式更替
判据  不被推导（域内无更基本命题推它）+ 生成规则（派生命题与工程规则从它导出）+ 去之崩塌（去掉它领域推理失去依据）+ 多层生效（多个抽象层级反复适用）
```

```
概念档案 · 概念体系能力
① 定义  以概念为单位的压缩与组织能力（简称"概念能力"）——识别枢纽 × 织关系 × 迁移 × 辨边界
```

```
⑤ 场景  团队交接/招聘/复盘时用试金石；"在不在做工程"用四层检验
⑧ 误区  ✗ "有流程有工具 = 在做工程"——四层缺一不可
         ✗ "工程 = 写代码 / 画图纸"——载体不是判据
判据  试金石：换个人、换团队，用同样的需求和约束，能交付质量相当的成果——能，是工程；不能，那是手艺
```

```
概念档案 · 需求
① 定义  明示的、通常隐含的或必须履行的需求或期望（ISO 9000:2026 §3.5.1）
⑥ 对立  点子 / 创意——点子不表述为需求，就进不了设计开发的流程
⑦ 辨析  需要（内容·硬性）→ 期望（内容·软性）→ 需求（需要或期望 × 呈现方式）；需求 ≠ 目标
⑨ 英文  requirement ← 拉丁 requirere（要求、寻求）
② 背景  需要或期望的表述——"往往是研究的成果"
③ 历史  从"要的东西"漂移出"明示/隐含/必须履行"三形态——ISO 9000:2026 把这场漂移固化为标准定义（ISO 9000:2026 §3.5.1）
④ 问题  需求与目标、点子混用 → 设计开发转化了错误需求
⑤ 场景  设计开发的输入；三种形态都要识别，隐含需求要主动去挖
⑧ 误区  ✗ "需求 = 用户说出来的"——隐含需求、必须履行的需求漏掉是缺陷
         ✗ "需求 = 目标"——目标回答"达成什么可度量的结果"，需求回答"做成什么样"（答"为什么做"的是目的）
判据  起点判据"可转化"：完整、无歧义、不冲突、隐含需求已识别
```

```
概念档案 · 设计开发
① 定义  将某一客体的需求转换为该客体更详细需求的一组过程（ISO 9000:2026 §3.3.11）
⑥ 对立  走流程——输入输出同样详细，没发生设计开发
⑦ 辨析  设计、开发、设计开发三个词的关系（§3.3.11 注 2）；需求开发（ISO 9001:2015 §8.2，**该标准库内无正本、属库外来源**）与设计开发（§8.3）的边界——看"特性有没有被规定"（第3章 §3.3.3 立此边界；第4章 §4.2.5 承接句改挂该节，不引 ISO 9001 条款号）
⑨ 英文  design and development；design ← 拉丁 designare（标注、指明）
② 背景  起点是研究的结果——需求往往是研究的成果，设计开发天然带不确定性
③ 历史  输入比输出更宽泛、更概括；一个项目可有多个设计开发阶段（递归）——输出是更详细的需求，且逐级更细
④ 问题  何时开始、何时结束说不清 → 只做技术方案就宣布完成 → 下游环节停摆
⑤ 场景  从需求到可实现的转化；"这算不算设计开发"用"更详细"判据
⑧ 误区  ✗ "设计开发 = 画图 / 创意活动"——是需求转化
         ✗ "技术方案做完 = 设计开发完成"——下游方案配齐才算
判据  止于"可实现"；"还有哪个环节会在执行时反问'这到底怎么做'？有，设计开发就没结束"
```

```
概念档案 · 质量
① 定义  客体的一组固有特性满足需求的程度（ISO 9000:2026 §3.5.2）
⑥ 对立  等级 grade——高档车可以是差质量，低档车可以是好质量
⑦ 辨析  符合性（满足了吗，二元）→ 质量（满足到什么程度，评价）→ 等级（按哪套需求分类）
⑨ 英文  quality ← 拉丁 qualitas（"如何"）
② 背景  程度是被"认定"出来的，不是被"计算"出来的——靠验证/确认用客观证据判定
③ 历史  （薄）从制造业"规格档位"来；标准通篇没有给质量一个单点分值
④ 问题  等级高 ≠ 质量好；"质量 vs 进度"被误判成打架
⑤ 场景  判定满足程度时用；特性超出需求范围的不是加分，是过度设计
⑧ 误区  ✗ "特性越多/越高，质量越好"——出了需求区间，只加成本、不加质量
         ✗ "质量能算分（85 分）"——关键特性不能被加权平均摊平
判据  特性超出需求范围的不是质量加分，是过度设计——只加成本，不加质量
```

```
概念档案 · 规定需求
① 定义  被明示的需求——验证的参照；**成文与基线是它的可采条件，不是它的构成条件**（ISO 9000:2026 §3.5.1 注 2 的 e.g. 是举例）
⑥ 对立  不可采的明示——口头说了，但没判定方法、不可复现、无版本，够不上"依据"
⑦ 辨析  明示 ＝ 规定（一个等号）；成文 ⊂ 明示（最常用的一种明示方式）
⑨ 英文  specified requirement；specified ← 拉丁 specificare（明确指明）
② 背景  需求开发四活动的输出——需求被"生"出来的成品
③ 历史  （薄）"可验证"是从验证定义（§3.11.12）推出来的，不是定义原话
④ 问题  没有规定需求，验证无从谈起（验证三要素的第一要素）
⑤ 场景  验证的参照；需求评审的对象；验收与责任的依据——评审、验证、确认都绕不开它
⑧ 误区  ✗ "客户说了就是规定需求"——那是资格，不是可采；✗ "没写成文档就不算规定需求"——不算的是可采，不是资格；✗ "口头说了就能当依据"——缺的是可采
判据  一条需求能提供客观证据吗（测试只是其一）？能，就可采、可当依据；只能"感觉"，就还得写下来、定下来
```

```
概念档案 · 评审
① 定义  为达成既定目标，对客体的适宜性、充分性或有效性所作的确定（ISO 9000:2026 §3.11.2）
⑥ 对立  验证——评审对目标（方向对不对，判断），验证对需求（做对了吗，证明）
⑦ 辨析  评审 ≠ 核对需求——核对需求是验证的姿势；评审是唯一在纸面阶段抬头看目标的环节（确认是建成后的实证终审，方向上的把关是前后两处，见 §8.3.6）
⑨ 英文  review ← re-（再）+ view（看）——再看一遍；第一遍是做，第二遍是看
② 背景  2026 版与验证/确认同属 §3.11"有关确定的术语"组——分野在动作词：评审用"确定"（determination，§3.11.1）定义，验证/确认用"证实"（confirmation）定义
③ 历史  IEEE 1028 把评审做法分成五类：管理/技术/检查/走查/审计
④ 问题  把评审做成核对需求 → 需求错了没人发现；目标偏了没人看
⑤ 场景  五个把关节点处的评审洒全程（需求/设计/代码/测试/发布）；复盘是单独的节点、不是评审（评审对目标，复盘查偏差）；目标具体化才评得起来
⑧ 误区  ✗ "评审就是开会过一遍"——没结论、没记录，最多算聊天
         ✗ "评审目标太抽象，评不了"——目标具体化配方：对象 + 时限 + 可衡量结果
判据  三问过了吗（适宜/充分/有效）？通过标准会前定了吗？团队、结论、记录三属性齐吗？
```

```
概念档案 · 验证
① 定义  通过提供客观证据，证实规定需求已得到满足（ISO 9000:2026 §3.11.12）
⑥ 对立  评审——验证对需求（做对了吗，证明），评审对目标（方向对不对，判断）
⑦ 辨析  验证 ≠ 测试——测试是提供证据的手段之一；验证 = 对照规定需求 + 客观证据 + 证实
⑨ 英文  verification ← verus（真）——求真：对照规定需求，证明为真
② 背景  2026 版与评审同属 §3.11"有关确定的术语"组——分野在动作词：验证用"证实"（confirmation）配客观证据定义
③ 历史  V 模型的右半边——需求在哪一级分解，验证在哪一级回收（左右镜像）
④ 问题  只验证不确认 → 隐含需求系统性漏失 → 测试全过、没人用
⑤ 场景  对照规定需求提供客观证据；测试/检验/审查/计算/文档评审都是证据（符合性分析=设计层的验证）
⑧ 误区  ✗ "测试全绿 = 验证过了"——测试只是证据之一，验证要对全部规定需求做证实
         ✗ "隐含需求靠验证兜住"——验证的尺子在文档里，够不着没写下来的需求
判据  三要素齐吗（对照 / 证据 / 证实）？逐级回收（单元 → 集成 → 系统）了吗？
```

```
概念档案 · 确认
① 定义  通过提供客观证据，证实针对特定预期用途或应用的需求已得到满足（ISO 9000:2026 §3.11.14）
⑥ 对立  验证——确认对用途（做对的东西了吗），验证对需求（做对了吗）
⑦ 辨析  确认 ≠ UAT 走流程——UAT 必须是真实用户 + 真实任务 + 真实场景；让业务方点测试环境是把确认做成了验证
⑨ 英文  validation ← validus（强壮、有效）——放进真实场景，看它"立得住"吗
② 背景  参照在场景里不在文档里——预期用途三构成：目标用户 / 使用场景任务 / 环境条件
③ 历史  （薄）"使用条件可以是真实的或模拟的"给了灰度发布、仿真测试的合法性
④ 问题  确认的存在价值建立在非明示需求上——写不下来的需求，只有真实场景能裁决
⑤ 场景  UAT / Beta / 灰度 / 试运行 / 仿真测试；兜住隐含需求，也兜住体验类需求
⑧ 误区  ✗ "测试全过 = 能用"——测试证明做对，不证明能用
         ✗ "隐含需求先写文档再验证"——很多隐含需求写不出来，只有真实场景能裁决
判据  真实用户 + 真实任务 + 真实场景齐了吗？隐含需求在真实场景里显现并处理了吗？
```

```
概念档案 · 架构
① 定义  一个实体（如系统）在其环境中的基本概念或属性，以及用于该实体及其相关生存周期过程的实现和演化的管控原则（governing principles；ISO/IEC/IEEE 42010:2022；本书读作系统不可还原的涵义）——这些基本概念与属性构成演化中必须守住的**不变量集合**，是第14章不变量链（目的→不变量→根本决策→遵从与演化）的第二环
⑥ 对立  详细设计——架构是"去掉就不是这个系统"的那组**基本概念或属性与管控原则**（不可还原）；详细设计是"改了系统还是它"的细节（可还原）
⑦ 辨析  架构 ≠ 一张图——图是架构描述；架构是那份内容、**不是交付物**（能交付、能评审、能版本化的是架构描述）；**元素与关系不是定义要素**（2022 版已从定义句删去，降为 42020:2019 §3.3 注 1；见 T-63 行）；框架 ≠ 架构——框架是"这一类"的组织方式（骨架+位置+组织规则，内容后填），架构是"这一个"实体在其环境中的基本概念或属性与管控原则，用框架 ≠ 有架构
⑨ 英文  architecture ← 希腊语 arkhitekton（首席工匠）；fundamental ← fundus（底部、地基）
② 背景  系统太复杂，一个人装不下 → 靠"**哪些才是基本的**"这一问把复杂度压成可管理
③ 历史  早期"架构=图纸" → 1970s 结构化设计 → 1990s 软件架构热 → 后由 ISO/IEC/IEEE 42010（现行 2022）定稿
④ 问题  架构 = 一张框图 → 图过时了架构也"过时"了（其实那组基本概念或属性一直活着）；架构 = 那组改起来贵的决定 → 漏判"不贵但承重"的，误纳"很贵却与目的无关"的
⑤ 场景  在不可逆决策做出来之前；变更影响评估时；团队边界定义时
⑧ 误区  ✗ "架构就是那张架构图"——图会过时，**那组基本概念或属性与管住它的管控原则（架构）**可以一直有效
         ✗ "架构等于技术选型"——技术选型是"概念或属性"的一种体现，不是全部
判据  **必要性**（去掉它，目的落空吗；"不可再分／不可缺失／不可替代"三问是它的顺口问法）＋**充分性**（齐备之后，剩余问题是否都不影响目的的可达）——**不可逆性一类只是代理，管排序与时机，不管准入**
```

```
概念档案 · 架构描述
① 定义  用来表达一个架构的**工作产品**（work product；42010:2022 §3.3）——架构是那份内容，不是交付物；能交付、能评审、能版本化的是它
⑥ 对立  架构——架构是抽象的、不可交割；架构描述是有形的、可交付、可版本化的
⑦ 辨析  ≠ 架构本身；≠ 一张图（图只是它的**视图**之一）；≠ 交付物清单——它按"利益相关方 → 关注点 → 架构视角 → 架构视图"组织，含 11 类架构描述元素（§3.4 Note 1）
⑨ 英文  architecture description（AD）；description ← de-（彻底）+ scribere（写）
② 背景  架构无形，要被人使用、评审、冻结基线，必须落成有形的信息载体
③ 历史  2011 版定义句曾把架构"体现于元素与关系"，易被读成"结构即架构"；2022 版删去该分句，并把 AD 明写为 work product（§3.3）
④ 问题  把架构描述当架构 → 图过时就说"架构过时了"；把描述当交付物 → 以为交付了描述就等于交付了架构
⑤ 场景  评审、入库、基线冻结、交付与沟通的**唯一有形标的**；架构符合性检查的输入
⑧ 误区  ✗ "我们的架构在这台服务器上"——说的是描述；✗ "画完图架构就有了"——图只是视图，架构要靠两样内容立住
判据  能不能被**单独识别**、**存储**、**交付**给别人用（§3.14 信息部件的三个动词）；**受控状态**（进配置管理、可冻结基线）是它成为"参照"的条件
```

```
概念档案 · 架构定义
① 定义  把一组**输入**变换成架构**两样内容**的那次动作（兼 15288:2023 §6.4.4 的**过程名** *System architecture definition process*）——输入五组（相关架构／组织与项目的方针与指令／生存周期概念与约束／利益相关方关切与需求／系统需求与约束），产出两样（**基本概念或属性**＋**管控原则**），落成的是**清单**不是描述；**不是"给架构下定义"**（那是第10章已完成的事）
⑥ 对立  给架构下定义（一个语义动作：把词说准）——**定义是动作，不是语义动作**；也对立于"设计"（另一样工作，在换手点的另一侧，归第14章）和"表达成件"（把内容按视角落成视图、写成描述，归第13章）
⑦ 辨析  架构定义 ≠ 汇总需求（需求只占输入里两样，且只有 *key architecturally-relevant* 的那部分留下）；≠ 整理（整理不产生内容，变换必然做选择）；≠ 发明（动词是综合与识别：偏好解类／既有解／模式战术与启发式）；≠ 画图选型定规矩（三样分别是描述、候选、原则的雏形，没有一样是变换本身）
⑨ 英文  architecture definition；15288:2023 §6.4.4 *System architecture definition process*；动词 *transforms*（**不是** collect／summarize）；42020:2019 §8 概念化是它内部第一件事
② 背景  第10章立了"架构是什么"（两样内容），却留下一个空：**这些内容不会自己长出来**——"这几份清单怎么长出来，是第11章的事"；15288 只有"架构定义过程"没有"架构设计过程"，**过程以产出物命名**
③ 历史  42010:2022 §3.2 定义句（两半）→ 15288:2023 §6.4.4 过程化（目的句／成果八条／四活动）→ 42020:2019 §8~§10 三核心过程（概念化／评估／细化）＋§6／§7 两并行过程；**本书读法**：四环（判断→立成内容→选定并背书→下游必须依据它）＋需求进架构三条去向＋资产·知识·经验各占一位
④ 问题  没有这个动作之前，"开始做架构设计"一句话罩着好几件事（定义／选定／表达），责任与交接都无处落；把入口说小成"一份需求"、把产出说成"一份文档"，都会让后面的人无从依据
⑤ 场景  章首现场（带图／选型／老规矩三样东西开会，三问都答不上）→ 吃进什么、吐出什么（入口五样＋一条例外；三条去向；产出只有两样；清单≠描述）→ 一句判断怎么变成依据（四环，**本章只走到第二环**）→ 素材从哪来（资产／知识／经验各占一位；都没有时怎么办）
⑧ 误区  ✗ "架构定义 = 给架构下定义"——那是第10章做完的事，本章讲的是一个动作；✗ "我是从需求出发的，所以输入就是需求"——输入五组，需求只占两样；✗ "送进来的需求最后都会变成架构内容"——只有关键架构相关的那部分会，其余各有去向但**不许消失**；✗ "清单写完，架构描述就有了"——清单属内容侧、描述属描述侧；✗ "手上没资产就没法做"——缺资产改变取材方式与细化深浅，不改变有无
判据  入口那一句问法（**这条需求是不是只有在"这个实体是什么"定下来之后才判得了**）＋四道准入（有类可归·有物可依·有径可循·有辨可评；四项全过＝候选，任何一项不过＝"想法"）＋三条红线（不许拿"没资产"当不写架构的理由／不许把参考架构当答案／不许把"不熟"写成"不该"）
概念档案 · 基本概念
① 定义  系统在其环境中"怎么想"的根源——组织范式 / 核心抽象 / 根本机制 / 根隐喻（42010 定义里的 concepts——本质·怎么想）；**来历一句话：概念是幸存下来的**——一个实体身上可以说的概念很多，能进架构的只是极少数，它们经历一轮又一轮取舍，最后活下来；活下来的理由只有一个：**去掉它，这个实体就不再是它自己**（第11章 §11.3.6）
⑥ 对立  详细实现——基本概念是"去掉就不是它"的层，改它等于换一个系统；详细实现是"改了系统还是它"的层
⑦ 辨析  基本概念 ≠ 技术选型——选型是候选，概念是幸存下来的承诺；命名是概念化的完成仪式
⑨ 英文  fundamental concepts；concept ← 拉丁 concipere（一起抓住、成孕）——把分散的东西"抓住"成一个整体
② 背景  概念不会自己长出来，也不靠灵感——**它从一轮又一轮的取舍里幸存**；可参的来路是既有解、参考架构、模式战术与启发式（第11章），过不了承重测试的就被筛掉
③ 历史  "基本概念"来自 42010 定义中的 fundamental concepts；生成路径五条（模式选择/领域抽象/质量反推/类比迁移/第一原理）
④ 问题  把概念当发明 → 每代系统从零开始；概念没命名 → 无法共享、讨论、传承
⑤ 场景  组织范式定形态、核心抽象定实体、根本机制定机理、根隐喻定眼光；质量属性反推是"驱动"机制
⑧ 误区  ✗ "概念是架构师发明出来的"——候选要过准入检验才配叫"基本"，概念是**幸存**下来的（去了它这个实体就不是它自己）
         ✗ "画了架构图 = 定义了概念"——概念长在决策里，不长在图上
判据  四问：它是组织范式还是核心抽象？走哪条生成路径来的？过了检验吗？它有名字吗？
```

```
概念档案 · 基本属性
① 定义  系统具备的本质特征——可观察、可度量的表现；涌现属性，由结构决定
⑥ 对立  基本概念——概念定"系统是什么"（可切可选）；属性定"系统具备什么"（涌现，只能让结构去催生）
⑦ 辨析  属性 ≠ 需求指标——需求指标是目标，属性是结构运转后涌现的结果；场景化（QAS）是两者的桥
⑨ 英文  fundamental properties；property ← 拉丁 proprius（自身的、固有的）——系统固有的东西
② 背景  你设计的是结构，属性是结构运转之后的宏观效果——不能直接设计属性，只能设计结构让属性涌现
③ 历史  SEI 属性驱动设计（ADD）把属性设计拆成四步：QAS 场景化 → 战术选择 → 结构落位 → 验证度量
④ 问题  直接设计属性 → 画不出"可用性模块"；属性不场景化 → 无法进入设计、无法验收
⑤ 场景  质量属性是架构的主要驱动；属性之间天然冲突，设计实质是排优先级（ATAM）；生命线属性 = 关键性分析
⑧ 误区  ✗ "直接设计可用性"——不能设计强度，只能设计晶格；不能设计可用性，只能设计冗余
         ✗ "属性可以分配给某个模块"——质量属性是涌现的，不能"分"，只能"译"成部件约束
判据  四问：目标属性场景化了吗（QAS）？选了哪个战术？战术落在哪个结构位置？度量过、涌现达标了吗？
```

```
概念档案 · 架构决策
① 定义  在架构总体语境中所做选择的一个集合（42010:2022 §5.2.12）——不是一个动作，不是拍板那一下；
        它的理据与它并排，同为架构描述元素（§5.2.9）
⑥ 对立  实现决策——架构决策要按架构待遇办（识别→判断→选定→记录）；实现决策改得动、改得起。
        另两个常见对立：不是"架构风格"（微服务/事件驱动是套路），不是"画图时做的决定"
⑦ 辨析  与"权衡"分家：权衡管能不能把东西分开，决策管谁把它定下来；与"一组决定"分家——
        架构定义句里没有"决定"，决策是抓手不是架构本身（T-63）
⑨ 英文  architecture decision；decision ← 拉丁 decidere（切断、裁断）；rationale ＝ 解释、论证或推理
② 背景  42010:2022 §5.2.12 给定义句与示例（含"所要考虑的选项集的选择"）；§6.10 管记录与理据；
        Nygard 2011 提出 ADR 的实践惯例
③ 历史  从模糊说法变成可记录、可管理、可审查的工程对象
④ 问题  架构决策不可避免——不是做不做，是早晚（"我们没做架构决策"是伪选项）；
        拍板通常在架构过程之外——评估出"最佳"是判断，处置是决定
⑤ 场景  恒信编号事故（把四条选择打包成"改个字段"）；把谁列为候选本身是一条决策；
        量不可逆性用三样（影响半径/信息成本/修改风险）；记录用六问（十一项的本书压法）
⑧ 误区  ✗ "改字段是小事"——数据模型可能正是最难反悔的那一类
         ✗ "架构决策是评审会上才有的"——没被识别出来的架构决策依然承担全部代价
         ✗ "贵的东西就算架构"——"改起来贵"只出现在"要不要记"那张单子上，不构成准入判据
         ✗ "记下来就算拍板了"——记录不产生授权，决策权属方要单独写
         ✗ "写了就一次定死"——三个时间戳里有一个专记修改
         ✗ "记不记随我"——标准分 shall 与 should 两档（决策与理由必须记）
判据  ① 准入：它对目的是必要的吗（承第10章"承重测试"）；
      ② 识别：它是不是一组选择、而不是一个动作；
      ③ 排序与时机：三样（影响半径/信息成本/修改风险）各看几个来路指高——**只定先后，不发身份证**
```

```
概念档案 · 配置
① 定义  实体被记录在配置信息里、相互关联的功能特性与物理特性——实体"被记录下来的样子"
⑥ 对立  实体的全部客观特性——特性客观存在，配置是"被管理起来的那部分特性"（三个隐形过滤器切出来的子集）
⑦ 辨析  配置 ≠ 配置项（对象 vs 属性：配置项是"人"，配置是"人的身高体重"）；配置 ≠ 配置信息（属性 vs 记录：配置是"体检结果"，配置信息是"体检档案"）；配置 ≠ 参数文件（参数是零件，配置是装好的整机）
⑨ 英文  configuration——con-（共同）+ figurare（塑造成形）＝共同塑成的形态；中文"配+置"＝配合+安置＝搭配并安置成形，两语同源
② 背景  变与不变的分离——核心只写一遍，变化的部分外置；"改一个参数就要改代码、重编译、重发布"是没分离的信号
③ 历史  从"多"到"一"的旅程——多个组件经"配"与"置"塑成一个整体形态（as-designed / as-built）；选配有 requires / excludes / mandatory 约束
④ 问题  把配置当参数文件 → 拿零件清单当整机图纸，追溯时"这台箱子当时是什么样"答不上来
⑤ 场景  配置项清单（管哪些）；类别/记录/关联三个隐形过滤器（哪些特性算配置）；追溯温度记录必须知道固件版本
⑧ 误区  ✗ "配置 = 参数文件 / 个性化设置"——参数只是记录形态的图纸，形态才是配置
         ✗ "配置只跟软件有关"——硬件、图纸、文档、数据都要配
         ✗ "配置就是客户能改的那几个开关"——选配、约束、组合都是配置
判据  问三句：它被记录了吗（记录边界）？它是功能/物理特性吗（类别边界）？它和其他特性关联成整体了吗（关联边界）？——三句全"是"，才是配置
```

```
概念档案 · 基线
① 定义  经批准、确立了产品或服务某一时点特性、作为生存周期参照的配置信息（ISO 9000:2026 §3.10.12）——被批准冻结的参照
⑥ 对立  流动状态——基线把"流动"升格为"受控"：线左版本自由流动，线右任何变化必须走变更控制
⑦ 辨析  基线 ≠ 版本（版本是刻度，基线是有"资格"的那一版——把里程桩当收费站）；基线 ≠ 发布；基线 ≠ 快照
⑨ 英文  baseline——base（基础）+ line（线）＝"底线/基线"；本指测绘基准线，转义为"作为基准的那一条"
② 背景  让一直在变的东西说得清——变化需要一个"从什么变起"的原点
③ 历史  功能 → 分配 → 产品三种正式基线；"版本顺着流、基线垂直切"（里程桩 vs 收费站）
④ 问题  没有基线，变化就不可言说——每一次变更都查无实据
⑤ 场景  功能基线/分配基线/产品基线；变更控制循环（冻结→变更→再冻结）的支点
⑧ 误区  ✗ "版本号就是基线"——版本是刻度，基线是资格
         ✗ "基线建立了就不能改"——基线可以变更，但必须走变更控制，改完建立新基线
判据  三特征问全：被批准了吗？被冻结了吗？生存周期拿它作参照吗？——三问全"是"，才是基线
```

```
概念档案 · 治理
① 定义  一种以人为基础的系统——组织为实现其宗旨，通过该系统受到指导、接受监督，并被要求就其宗旨的实现作出说明、承担后果（ISO 37000:2021 §3.1.1；ISO/IEC 38500:2024 §3.3 同口径作"指导、监督和担责"）；由被治理对象之外的人或机构，依据规则与担责，对"方向与框架"持续纠偏——掌舵，不是统治
⑥ 对立  统治（rule）——统治预设"主权者-臣属"关系（主体单一、强制命令、自上而下）；治理预设"领域+规则+角色+担责"（主体多元、协商为主、多向互动）
⑦ 辨析  治理 ≠ 管理（掌舵 vs 划桨：决策系统 vs 执行系统；判据——"定参数是治理，在参数内选最优是管理"）；治理 ≠ 例行工作（治理是持续系统，定期评审只是传感装置）；治理 ≠ 清洗工具（定规则裁例外是治理，清洗是执行层的活）；治理 ≠ 文件堆或 IT 系统（以人为基础说的是**构成**）
⑨ 英文  governance ← govern ← 拉丁 gubernare ← 希腊 kybernân（掌舵、领航）——同根词 cybernetics（控制论）保留"反馈纠偏"本义
② 背景  委托必有治理——责任可委托、担责不可委托（ISO 37000 §4.2.2／§6.5.2、ISO/IEC 38500 §6.1）；委托不是治理的前提，无委托时治理同样是组织常态（§3.3）
③ 历史  1989 世界银行"治理危机" → 1995"治道" → 2000 俞可平定译 → 2013 国家治理现代化；"治"=治水疏导、"理"=治玉顺纹
④ 问题  治理与管理混淆 → 买了"治理平台"干管理的活（术语膨胀）；判据与门槛混用 → 把"跨部门"当判据
⑤ 场景  三条件（分离/静默积累/框架级）同时满足、需要正式治理机构时；治理机构持续行使四活动（利益相关方参与/评估/指导/监督）；委员会定规则、裁例外、设传感
⑧ 误区  ✗ "治理 = 领导发号施令"——治理是引导不是命令，舵手不是船主
         ✗ "治理 = 买一套治理平台"——平台是工具，治理是人做的一套安排
         ✗ "治理 = 管理制度健全"——制度是管理；谁定制度、制度偏了谁来纠，才是治理
         ✗ "跨部门才算治理"——跨部门是升级门槛，不是判据
判据  问四句：谁来治（角色）？依何治（规则）？如何治（机制）？治得怎样（担责）？——四问有答，才谈得上治理
```

```
概念档案 · 三类需求
① 定义  产品需求要全 = 功能需求 + 环境适应性需求 + 可实现性需求，每类"及其指标"（功能以 IPO 定义行为；环境对气候/法规/文化的适应；可实现为生存周期八方面）
⑥ 对立  功能清单——只写"要做什么"，把产品需求当成功能需求，缺了环境适应性与可实现性
⑦ 辨析  功能/非功能二分 ⊂ 三类需求："非功能需求"是个大筐，装着环境适应性和可实现性两类主人、来源、验证载体都不同的需求；分类的判据不是特性本身，是"谁在问"
⑨ 英文  functional / environmental adaptability / realizability requirement；realizability ← realize（实现）
② 背景  产品的终点是"可实现"——只有功能需求，交付物停在原理样机；补上环境适应性需求，停在环境样机；补上可实现性需求，才是产品。分类判据是"谁在问"（客户、环境、承制方），不是特性的名字（第5章 §5.2.2）
③ 历史  以"产品 vs 样机"为界：功能/环境/可实现三对三对应原理样机/环境样机/产品（需求类别 → 验证条件 → 交付物）
④ 问题  需求"全不全"说不清 → 靠"功能写得多"自欺 → 量产翻车
⑤ 场景  相关方需求捕获、需求评审、SRS 编写；每一类都要答出来源、相关方、指标、验证载体
⑧ 误区  ✗ "需求写全了 = 功能写全了"
         ✗ "可实现性需求是后续工艺的事"——它是产品的固有特性，必须写进相关方需求
判据  每一类都能答出"谁在问"（客户/环境/承制方）+ "用什么交付物验证它"（原理样机/环境样机/产品）
```

```
概念档案 · 验证载体
① 定义  每类需求的专属验证交付物：功能→原理样机、环境适应性→环境样机、可实现性→真正的产品
⑥ 对立  用一个载体验证全部需求——用原理样机的通过宣布产品成功
⑦ 辨析  验证载体 vs 评审/验证/确认（第8章）：载体回答"每种需求用什么证明"，判定回答"验证时对照什么"；载体验证的是需求，不是"做对了吗"的动作
⑨ 英文  prototype（原型、样机）——先造的、用于检验的实物；validation vehicle（沿用译名；按第8章严格口径，环境样机入真实环境更近确认，见⑥⑦）
② 背景  三类需求需要三种互不相容的验证条件：原理要脱离环境/成本单独验，环境要在真实环境验，可实现要在量产经济性约束下验
③ 历史  "样机→环境样机→产品"逐级完备，让"样机通过"被误读为"产品成功"——但每类需求只有一个专属载体
④ 问题  原理样机通过就宣布产品成功 → 环境适应性未验、可实现性根本没进需求清单 → 量产翻车
⑤ 场景  验收、里程碑决策、需求评审；判定"交付物是什么"用三类载体的验证完成度
⑧ 误区  ✗ "样机验证通过了 = 产品成功了"——只验证了功能需求
判据  每一类需求都答出"用什么交付物验证它"——答不上来的那类，就是需求没写全的证据
```

```
概念档案 · 承制方主导
① 定义  产品需求开发由承制方主导（捕获、分析、建模、引导范围、形成条目），利益相关方只保留确认终审权
⑥ 对立  客户主导——把需求开发当成"客户说、承制方记"；承制方对产品更专业，是主导方而非转述方
⑦ 辨析  承制方（主导·加工）vs 来源方（客户/环境/资产·原料）vs 确认方（相关方·终审）——三分工；引导可以激进，确认不能缺席
⑨ 英文  承制方 = 产品的实现方（realizing party / developer）；主导 ≈ lead / drive，区别于 guide（引导）
② 背景  客户知道"要什么"但不知道"什么可能/什么成熟/什么惯例"——专业不对称让承制方必须引导
③ 历史  需求捕获的"隐含性"（客户的需要连他自己都没意识到）→ 需要专业需求分析师（承制方团队）去挖——"承制方引导"在需求分析师角色上显形
④ 问题  承制方被动接单 → 需求不全 → 责任甩给客户（"没提清楚"）
⑤ 场景  需求访谈、范围沟通、需求评审；"需求全不全"的问责对象永远是承制方
⑧ 误区  ✗ "承制方就是听客户要什么就做什么"
         ✗ "需求不够全是客户没提清楚"——需求全不全是承制方的责任
判据  需求全不全、明不明确、可不可度量——问责承制方；引导可以激进，利益相关方确认一次不能省
```

```
概念档案 · 产品数据
① 定义  关于产品的信息的、形式化的表示，适合由人或计算机处理（ISO 10303-1:2021 §3.1.29〔库内无正本〕）；产品的信息存在、开发工作的全部对象（六类：需求/设计/制造/质量/服务/管理）
⑥ 对立  产品本身（物理存在）——描述与被描述者；数据管不到实物那一半
⑦ 辨析  不是文档（数据是内容、文档是容器）；不是配置项（受控的才是）；不是产品（验证要求两者一致）；不是架构本身（可交付与可冻结的是架构描述 AD）
⑨ 英文  product data ← product（产品）+ data（数据）；ISO 10303（STEP）为数据交换而定义
② 背景  产品数据交换困难催生 STEP 标准；开发全程在数据上工作，实物只是数据的复制品
③ 历史  ISO 10303（STEP）1980s 起规范产品数据表达；与 ISO 10007"配置信息"同族
④ 问题  没有它，开发="把实物做出来"、数据="开发完再补的文档"——追溯、验证、交接全断
⑤ 场景  六类数据的定义、组织、交接；评价锚点、问责落点、协作的对象
⑧ 误区  ✗ "数据是文档，开发完再补"——数据是开发工作的全部对象
         ✗ "产品=实物"——设计态里产品=纯数据
判据  六类数据覆盖产品全程、可验证可追溯；设计态里开发产品 ≡ 开发产品数据
```
```

概念档案 · 两域三态
① 定义  产品在两个域（信息域/物理域）、三种状态（设计态/制造态/使用态）中存在；设计态产品=纯数据
⑥ 对立  物理存在（实物）——数据管不着的那一半（制造偏差、使用体验）
⑦ 辨析  三态是同一产品的三种存在方式，不是三个产品；设计态同一性 ≠ 产品就是数据
⑨ 英文  as-designed（设计态）/as-built（制造态）/as-maintained（使用态）；数字孪生=信息域对物理域的实时映射
② 背景  开发/制造/使用三个阶段，产品的存在形态不同；PLM 用三态组织数据
③ 历史  PLM/STEP 数据管理实践；EBOM（工程 BOM）→ MBOM（制造 BOM）→ 维护记录
④ 问题  把三态混为一谈，就会问错"产品是什么"——设计态里没有实物可看
⑤ 场景  判断"开发产品=开发产品数据"的成立范围；组织产品数据的分态管理
⑧ 误区  ✗ "质量在车间里"——开发环节的质量就是数据质量（数据质量决定上限）
判据  设计态产品=纯数据（开发≡开发数据）；制造态=数据+实物；使用态=实物+实况
```
```

概念档案 · 价值三层
① 定义  利益相关方对产品贡献价值的沉淀层（物化/决策/过程三层）；产品数据是价值的投影与锚
⑥ 对立  价值本体（人的判断与协作）——数据管不到的源头
⑦ 辨析  三层 ≠ 全部价值：决策层（ADR）部分沉淀、过程层只留结果
⑨ 英文  ADR = architecture decision record（决策层沉淀）；Polanyi"我们知道的多于我们能说出的"
② 背景  工件是判断的投影：完美工件可能是错误决策的产物（验证全绿、确认全红）
③ 历史  源自"决策要记录"（决策记录六问）与知识管理实践
④ 问题  以为"数据全=价值全"——决策与过程层的价值流失，产品数据装不下
⑤ 场景  评价角色价值（工件质量×判断质量×下游影响）；职责挂在工件上
⑧ 误区  ✗ "产品数据装下了全部价值"——物化层全在，决策/过程层只部分沉淀
判据  物化层完全在产品数据中、决策层部分沉淀（ADR）、过程层结果记入；数据是锚，判断与协作是本
```

```
概念档案 · 构思
① 定义  从关注点出发生成多个候选架构概念的发散性概念活动——"打开可能性"；产物是"可能是什么"，不是"决定是什么"
⑥ 对立  定义——构思发散、定义收敛；构思停在候选，定义画定边界
⑦ 辨析  构思 ≠ 灵感（构思有方法：模式库/参考架构/第一性原理）；≠ 设计本身（构思是广义设计的发散半场，设计还负责收敛与转换到底）
⑨ 英文  conceiving ← 拉丁 con（收进来）+ capere（握取）——"怀在脑中"；基因是孕育可能性，不是做决定
② 背景  ISO/IEC/IEEE 42010 architecting 动词链第一词；标准用了它却未单独立词条，操作化在 15288 §6.4.4"生成候选架构"任务
③ 历史  构思作为工程概念长期被"设计"吞并——42010 把 architecting 拆成七动词后，构思才从设计的影子里走出来
④ 问题  直接把第一个想法当唯一解——"唯一解 = 未审视的解"，没有候选就没有权衡
⑤ 场景  架构生成六步的①②步（定驱动因素→生成备选）；纪律：备选 ≥2 个；陷阱：稻草人备选（造注定输的陪跑，让预定方案"胜出"）
⑧ 误区  ✗ "构思=等灵感"——构思有方法，方法正是创新可工程化的核心证据
判据  这一个动作产出了 ≥2 个候选概念吗？每个候选都能说清它回应谁的什么关注点吗？——是，才是构思；只有一个解的"构思"，等于没构思（本书凝练）
```

```
概念档案 · 定义
① 定义  在候选之间画边界、做选择，使方案从多义变单义、从漂浮变确定——"终结漂浮"
⑥ 对立  构思——定义终结构思打开的漂浮；一个是发散、一个是收敛
⑦ 辨析  定义 ≠ 陈述一句话（陈述是定义的产出，定义是画边界的过程）；≠ 设计狭义（定义收敛出被承诺的架构，设计把它转换到底）
⑨ 英文  defining ← 拉丁 de（往下）+ finis（边界/终点）——"划到边界为止"；同根：finish、final；ISO 1087-1：definition = 把概念与相关概念区分开来的表述
② 背景  ISO/IEC/IEEE 42010 architecting 动词链第二词；15288 §6.4.4"架构定义过程"内部第一件事就是构思——流程义的"定义"包住了动作义的"定义"的上游
③ 历史  定义是"口径事故"高发词：三重身份共存（动作义=画边界 / 流程义=15288 §6.4.4 技术流程 / 概念框架义=ISO 1087-1 界定表述）——同一句"架构定义"可能指三种东西
④ 问题  候选停留在多义、漂浮——没有边界就没有"被承诺的架构"，下游无法接棒
⑤ 场景  架构生成六步的③④步（权衡选定→分配与接口）；效用树+ADR 落定选择；partition/align/allocate 把边界落到元素与契约
⑧ 误区  ✗ "架构定义 = 给架构写一句描述"——动作义与概念框架义混用，把"画边界"读成"写词条"
判据  选定方案有边界吗？被否掉的备选"死因"说得清吗（ADR）？——边界画定、漂浮终结，才是定义（本书凝练）
```

```
概念档案 · 设计（一词两义）
① 定义  一词两义：广义 = ABET 容器（迭代决策与创造的容器过程，⊃ 构思+定义+表达）；狭义 = 以生效架构基线为输入的下游细化流程（15288 §6.4.5）——"转换到底"
⑥ 对立  广义设计 vs 狭义设计——容器（包含构思定义）vs 下游（基线生效后才接棒）；并列使用时"设计"必须降为狭义义
⑦ 辨析  设计 ≠ 画图/选型/定规矩（那些是产物与候选，见架构设计卡）；≠ 构思（构思是设计的发散半场）；≠ 定义（定义收敛，设计转换）
⑨ 英文  design ← 拉丁 de（出来）+ signare（做记号）——"做记号标出来"，把意图标记成可传递的形式；ISO 24765：design 兼指过程与结果
② 背景  ABET engineering design = devising a system/component/process to meet desired needs（iterative/creative/open-ended）——"容器"出处；ISO 9000 §3.4.8：设计开发 = 把需求转换为更详细需求（可递归）
③ 历史  广义/狭义两义长期并存：工程教育（ABET）取容器义，系统生命周期（15288）取流程义——"设计是动词（构思）"是广义的通俗说法，"设计定义过程"是狭义的正式名称
④ 问题  不声明取哪一义，"设计"就在容器与下游之间漂移——说"我们在设计"，可能是构思阶段，也可能是基线后的细化
⑤ 场景  广义：设计全过程的统称（构思→定义→表达→…）；狭义：架构基线生效后 15288 §6.4.5 接手，把架构逐层细化为可实现元素与契约
⑧ 误区  ✗ "设计 = 把想法画出来"——忽略广义容器（构思定义在内）；✗ "设计 = 架构基线前的一切"——忽略狭义下游（基线生效后设计还在继续）
判据  说"设计"时声明了取广义还是狭义吗？狭义设计的输入是生效的架构基线吗？——一词两义分得清，才是设计（本书凝练）
```

```
概念档案 · 架构活动
① 定义  architecting——在系统整个生存周期内构思、定义、表达、记录、沟通、认证恰当实现、维护与改进架构的过程（ISO/IEC/IEEE 42010 §3.1）；架构师能力增量的母词
⑥ 对立  架构设计（本书用语；15288 的规范过程名是 **System architecture definition process**〔§6.4.4〕，正本无 `architectural design` 一词，见 ch11 §11.2.2）——架构活动覆盖整个生存周期，架构设计只是其中一段
⑦ 辨析  架构活动 ≠ 架构师头衔——42010 只认活动不认头衔；本书讨论"从事架构活动的人"（架构师），标准讨论"架构活动"本身
⑨ 英文  architecting = 42010 给 architecture 造的过程词（architecture 当动词用会硌牙，才造出 architecting）
② 背景  六块能力增量（架构决策/关注点管理/质量权衡/抽象建模/技术领导/演化对齐）收敛到同一个母词——动词链的投影
③ 历史  ISO/IEC/IEEE 42010 立"architecting"（架构活动）词条，把原本混在"架构设计"里的活动拆成七动词；中文定译"架构活动"（封面译法源同步 42020）
④ 问题  没有母词，架构师的能力只能罗列成碎片清单——有了动词链，每一项能力都能在链上找到位置
⑤ 场景  贯穿系统生存周期反复发生（不是串行阶段）；ch14 治理取链尾两项（认证=符合性监控、维护改进=演化治理），ch18 架构师取全链
⑧ 误区  ✗ "架构活动 = 架构设计"——设计只是七动词之一；✗ "架构师 = 42010 头衔"——标准只认活动，不认职位
判据  一个动作能在七动词链上找到位置吗？在生存周期里反复发生吗？——能，才是架构活动（本书凝练：动词链为母词映射，非标准原文）
```

```
概念档案 · 创新
① 定义  创造或重新分配价值的新对象或变更对象（ISO 56000:2020）——结果义：新 × 成，缺一归零；只有新没成=点子/发明，只有成没新=优化/复现
⑥ 对立  发明——发明是新想法的诞生，创新是新组合的兑现（熊彼特）；发明在链上（构思），创新在链尾（评分席）
⑦ 辨析  创新 ≠ 构思（构思供给"新"的因子，"成"的因子大头在定义与设计）；≠ 创意/点子（没落地的改进不叫创新，奥斯陆手册）
⑨ 英文  innovation ← 拉丁 innovare（更新）；ISO 56000 取名词义（new or changed entity），熊彼特取活动义——本书统一取结果义
② 背景  创新管理是经济学/管理学话题（熊彼特、ISO 56000 家族），工程动作（构思/定义/设计）是它的生产现场
③ 历史  熊彼特 1912《经济发展理论》把创新从发明中剥出；Henderson & Clark 1990 四分型（突破式/架构式/模块式/渐进式）指出主导动作随类型在构思/定义/设计间滑动
④ 问题  把"创新"当动词用（"我们去创新吧"= 语病）——你能做的是构思/定义/设计/开发，创新是对动作结果的追认
⑤ 场景  链上的活干完了，够新又成了，才被追认为创新；工程化对象是流程/方法/组织/组合（ISO 56001 可认证），单点命中不可承诺
⑧ 误区  ✗ "创新 = 灵感 = 构思"——架构式创新的主导动作恰是定义（元件不动、连接重排、重新画边界）；✗ "创新可被保证"——工程化管漏斗的形状与流量，不管哪一滴水通过
判据  够新吗（新颖性）× 成了吗（价值兑现）？缺一归零——两个都答"是"，才追认创新（本书凝练）
```

## 附录 E 练习答案

> 各章"自查 · 这些说法对吗"的答案与理由已随章给出，下表只给**对/错**速查；"练习"的**答案要点**在下。要点给的是"往哪个方向想、用哪把尺子"，不是唯一答案——它们与训练教材题卡同源，考的是你有没有把话说准。

### 第1章 概念体系能力：学习能力的杠杆

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗ ⑯ ✗（背熟定义≠懂，懂=能答四问；概念能力=组织得好非渊博；根概念能力是概念体系能力的子能力非全集；乘号里有两个归零项（方向与表征），力臂长≠产出大；先学细节越学越累；转述=压缩测试；四问答出"是什么"不够；概念是共识不是真理；掌握=结构不是记忆；识别枢纽有可操作的三步法（收集候选→硬判据→往上挂）；多数概念是凝结不是发明；枢纽是骨架还有根概念/原理层；根概念是最源头非最重要；概念是节点、原理是边，核心原理之上还有基本原理；表征是 1、上面三级是 0——先建图式不能替代表征；答全四问只是**入场**——四问是第一级（表征）的作业工具，上面还有心智模型与解释框架）

**练习答案要点**（**10 题**，与正文 §附录 D 逐条对位）：
1. 用**承重测试**筛：**把这一条内容拿掉，这个实体还能达成它的目的吗**——写下至少三条"拿掉就不再是它"的。
2. 逐条跑**两遍**：兑现侧（实现目的需要它吗）＋演化侧（目的变了它守不守得住）。
3. 判一条"改起来贵"的决定：它是不是因为"贵"才被叫架构？拿掉它，目的还达得成吗（**不可逆性只是代理**，会漏判也会误纳）。
4. 按五类归位：**关注域**（业务／数据／应用／技术）／**描述层次**（概念／逻辑／物理）／**架构种类与范围**（企业／系统／参考／总体（战略）／SoS；基线／目标）／**架构风格**（微服务等）／**框架**（Spring 等）；五类叠在一起才是"一堆架构"的病根。
5. 一条规矩的**根据在内容侧、不在人**：说得出"不合它就不叫这个系统了"＝架构在起作用；只说得出"有人这么定"＝命令。
6. 评审的标的是**工作产品**：图会过时，能签收与冻结的是**架构描述**（不是"那张图"，也不只是那组基本概念或属性）。
7. 框架替你定的是"这一类"的组织方式；它**没替你定**服务边界、数据归属、接口契约——那些正是**架构内容**。
8. **被默认的架构**也是一份架构：它只是没被评审、没被记录、没人对它负责（这正是最贵的一种状态）。
9. 四问量"来路"：建筑图纸 → 最高层构想 → fundamental organization → 概念或属性（含 embodied-in）→ **2022 的 entity＋两样内容**。
10. 只问两件事：**那句"它是什么"说清了没有；它排掉了什么**——答不上第二个，就还没有架构，只有主张。

### 第2章 工程：我们到底在做什么

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ◐（显性化是第一步，还要可检验）⑧ ✗

**练习答案要点**：
1. 试金石检验 → 换三个人做，能否同等交付；不能 → 缺的是可复制性，对照四层定位（多是方法论层或价值与伦理层）。
2. 敏捷+CI/CD+测试覆盖方法论、工具与实践两层；缺工程科学（"为什么能行"）与价值与伦理（压力下守不守）。
3. systematic 答"怎么做事有章法"、systemic 答"怎么看问题有全局"、algorithmic 答"能否自动执行"；例：敏捷迭代是有章法的判断，不是算法执行。
4. 系统工程 = 元工程（整合部件、不造部件）；"部件全对、整体出事" = 涌现属性，去查没人管的接口/数据口径。
5. 技术系统看：上线 = 成功；工程系统看：人会用、流程顺、组织撑得住 = 成功；答案不一致 → 缺的是人/流程/组织/数据。机场就是现成例子：物理、技术、人、流程、信息协同起来，才产生"顺利运行"的涌现行为，工程系统的边界画在整个运行环境上。
6. 验收记录：对上"规定需求"的是验证，对上"预期用途"的是确认。最常见的病是"验证全过、确认没做"——测试全绿只说明"做对了"，没人用仍然可能失败（§2.4.4）。
7. 三大事故共同点 = 价值与伦理这一层先松手（不是不会做，是没守住）；找"为进度牺牲可靠性"的真实例子。
8. 水忠 = 手艺（依赖个人）；工程化改造第一步 = 把"心里有数"的判断显性化成可检验的规则/文档。
9. 六方面打分：恒信有结构/有方法/可重复**沾了边**；全覆盖/受控/可验证不合格（缺三个）。
10. 最值钱的手艺 → 显性化：把"心法"写成可检验的规则，再验证换个人能按它交付。
11. 四要素打分：科学原理、约束、系统方法、有用且安全的人造物；缺"有用且安全"（价值与伦理层失守）最致命。
12. "工程 ≠ 手艺"转述测试 → 量的是"工程"的"不是什么"（对立：手艺），用第1章转述测试检验——讲不清"换个人也能同等交付"就卡在"试金石"上；溯源：engineering ← 拉丁 ingenium（天生的才智、巧思），ECPD 1941 首次把"造东西"提炼成可检验的要素。

### 第3章 需求、设计开发、质量：产品开发的图式

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✓ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗

**练习答案要点**：
1. 点子不算输入 → 要经研究确认成需求；分界线 = 是否表述为"明示 / 通常隐含 / 必须履行"的需求或期望（ISO 9000:2026 §3.5.1）。
2. 技术方案做完不够 → 缺采购/制造/测试/交付/部署/操作/运维等方案；终点由"最后一个配齐的方案"决定。
3. 特性超出需求范围 = 过度设计，只加成本、不加质量（质量 = 固有特性满足需求的程度，超出需求范围的特性对质量没有贡献）。
4. 本质 = 需求集合内部打架（交付时间也是需求）；砍验证 = 不度量就宣布合格，风险后移成现场返工；口头改需求 = 偷换靶子。
5. 一起剪裁 = 需求所有权在利益相关方 + 走正式变更（排序/留痕/挂账）；单方面砍 = 偷换。
6. 等级答"按哪套需求分类"、质量答"满足到什么程度"、符合性答"满足了吗"；高档车可以是差质量，因为等级高 ≠ 质量好。
7. 特性还没开始规定 = 需求开发（ISO 9001:2015 §8.2）；特性开始被规定 = 设计开发（§8.3）——需求规格就是那道分界。
8. 起点判据"可转化"的四条前提：完整、无歧义、不冲突、隐含需求已识别；最弱那条的后果 = 错误需求被完整转化。
9. 用四问的"它从哪来"量三个词 → 需求 ← 拉丁 requirere（要求、寻求），原指"要的东西"，后漂移出"明示/隐含/必须履行"三形态；设计开发 ← designare（标注、指明），ISO 9000:2026 以 design and development 完整表述"需求转化"一件事，不拆两半；质量 ← 拉丁 qualitas（"如何"），从"档次、用料"漂移成"符合需求的程度"——漂移的那个词是"质量"，正是本章最大反转。
10. "定需求 → 出规格 → 判满足"走项目 → 定需求=需求（"可转化"的四条前提，隐含需求最易漏）；出规格=设计开发（方案配齐才到"可实现"，只到技术方案=没走完）；判满足=质量（靠测试方案里的接收准则认定，没有准则只能"感觉"）；三处边界易混处——起点看"特性有没有被规定"、终点看"还有哪个环节反问这到底怎么做"、参照看"超出需求范围的特性是过度设计"。

### 第4章 需求工程：从诉求到依据

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗

**练习答案要点**：
1. 开发欠账 = 没调研、没分析、没写可验证的规格；管理欠账 = 没基线、没变更流程、没追溯——两张单子按"源头／过程"归类，"加强需求管理"只治得着后一张。
2. "明示但不可采" → 补上判定方法与版本：例"重要合同要审批"→"金额 ≥ 500 万或三年期以上须审批"（注意它本来就是规定需求，缺的是可采，不是资格）。
3. 跳过分析直接进规格的代价：澄清不足（"重要"没定义）、分解没做、排序没做、建模没做 → 验证没有可对照的靶子。
4. 改口叫评审的差别：评审对的是**工作产品**（判适宜、充分、有效），签的是"这份需求立得住"；叫成"确认"等于给还没实现的东西签了确认的字，验收时那句"确认通过"就成了扯皮的证据。
5. ConOps 讲一段过程（系统怎么被用）、SRS 讲一条条条款（必须做什么）；ConOps 还兼着确认判据的载体（隐含需求的正文写在运行场景里）；先条款后故事，条款就悬空。
6. 用六条判据打分 → 最弱一条及其后果：如"可追溯"最常被牺牲——它不立刻显形，变更时答不上"从哪来、影响谁"。
7. 需求基线在哪；没有基线，最近一次变更"从什么变到什么"说不清。
8. 最常被跳的一环是影响分析（口头改需求）；代价 = 查无实据的暗改，出事时拿不出凭证。
9. "25 号之后签的合同算下个月"：访谈随口一句 → 挖出来 → 显性化进需求池 → 写成规定需求（隐含需求不会自己开口）。
10. "合同数据留档十年" = MoSCoW 的 Must / Kano 的基本型——走的是环境与法规那条来路，不经组织目标，所以不在被砍清单里。
11. 三条来路 = 目标转化（主流，明示）、法规与环境约束（**法规强制**那一支属"必须履行"、不经目标；"环境"那一支另立一类，第5章承接）、利益相关方的隐含需要（通常隐含，未必被目标覆盖）；最容易被漏的是第三条——它不开口，也不在目标的覆盖范围里，只能靠需求工程自己补齐。

### 第5章 需求的完整性：谁在问，谁在验

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗

**练习答案要点**：
1. 冰链八条 → 八条可实现性需求一一对应：定制芯片＝物料可采购性、注塑做不出来＝可制造性、手工校准＝可测试性、无认证＝可交付性、无远程升级＝可部署性、无备件模块＝可运维性、电池回收＝可回收性、成本超四成＝经济可承受性。重做需求时这八条都该在需求阶段写出来，尤其经济可承受性——它是前七条共同堆出来的总账。
2. 三类各三条 → 最少的那一块通常是可实现性；原因从四个错位里找（相关方、时间、话语权、认知），多半是承制方的代表没在需求阶段发声。
3. 逐块问验证载体那条判据：功能需求用什么验（原理样机）、环境适应性需求用什么验（环境样机）、可实现性需求用什么验（真正的产品）——答不上来的那一块，就是欠账。
4. 症状反推：每一个"不方便"对应一条可实现性需求；当时评审没人提，多半因为提它的那些人（承制方各业务代表）不在需求阶段的桌上。
5. 测试性与可测试性：同一个特性两个主人——使用环境问"在役测得出吗"，归环境适应性需求；承制方问"产线上测得方便吗"，归可实现性需求；判据是谁在问，叫法跟着主人走。
6. 访谈对象清单：采购、制造、测试、交付、部署、运维、回收的业务代表，加市场代表，有没有在需求阶段发过声？没有，可实现性需求就会系统性漏失。
7. 回路诊断（问题、转化、入库、复用）：卡点最常见在"转化"（问题停在口头，没提炼成带指标的需求条目）与"入库"（没人维护资产库）。
8. 经济可承受性：提出者应是市场代表（依据对竞品与替代产品的价格成本研究），要设目标成本一类的指标，并经相关方确认；若没有，"降本大会"反复开就是证据。
9. 恒信镜照：原型＝原理样机、试点＝环境样机、正式产品＝真正的产品；"上线成功"只走到功能那一块，部署、运维、成本这些属可实现性需求，要等真正的产品跑起来才验得了。
10. 四问量"验证载体"或"承制方主导"：答全四问才算拥有。最薄的那一问通常就是最容易出错的地方——答不出"往哪去"，验收时会拿错交付物；答不出"从哪来"，就说不清为什么每一块内容要各配一个载体。

### 第6章 设计开发落地：需求与方案结对

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗

**练习答案要点**：
1. 树 vs 散文判断：查"不可定位/不可承接/不可追溯"三罪各一个具体例子。
2. 画框架树：标分类节点（文件夹）与枝梢节点；给一个枝梢节点写承接判据（可承接哪类需求）＋分解源判据（分解产出哪类叶节点）——双向可用。
3. 语义四查给证据：覆盖完整（父要求都有对应）、不超出（无影子需求）、逻辑一致（不打架）、约束继承（约束有叶子承接）。
4. 指标三情形：判断"可拆分（函数关系）/ 下放（同值继承）/ 暂不分解（标注向下一层传递）"，写出判断过程。
5. 分配三自检：全覆盖（叶节点数对账）、单承接（一个叶节点一个归宿）、N:1 合理（每个节点 2~5 条较优，以语义为准）。
6. 悬空叶节点判断：叶节点切粗了（迭代重切／拆条）vs 方案树缺节点（生成新节点）——用"拆得开吗"区分。
7. 覆盖检查＋符合性分析：先核"该节点承接的所有需求的语义 ⊆ 其叶节点语义之并"，再按"针对需求 A，本节点通过 X 机制满足 Y，指标 Z 满足/降级/丢失"落句——写不出就是没分析。
8. 框架定义 vs 架构：一个是结构骨架（一份文档），一个是系统不可还原的涵义；"架构 = 一份文档"是词汇病。
9. 干枝叶子独立演进：修剪枝条只动框架、长新叶只动详细 → 变更成本下降，可分别纳入基线（第13章）。
10. 结对走一遍：上层叶节点落到下层节点（复用／改进／新增各试一次）+ 覆盖检查/符合性分析，记录每步自检结果。
11. 四问量"分配生成"（或"分解分析"）→ 分配生成是什么（叶节点落到能负责它的节点上＋自下而上调树：复用→改进→新增）、不是什么（不是简单分派——单承接是硬约束、资产优先有序）、从哪来（从分配实践与资产复用原则凝结）、往哪去（阶段一长骨架，是分解分析的前提）；最薄的一问通常是"不是什么"——把"分配=简单分派"当成它，正是最容易混用的地方。
13. 判步型：两侧的叶节点不是同一批 → **分配步**（做承接，Y=F(X) 在此求值）；两侧叶节点是同一批 → **整段搬入步**（不做映射，活是长干枝并逐级判定落位）；同一份产品数据在两个形态之间 → **形态轴步**（不是承接）。
12. 六步走一遍：①接需求（需求就位：链首自原始材料结构化/链上验收上一对移交）、②验就位（三把尺子：可转化/可分配/边界不越位 + 两把数值尺子：指标闭合/分配预判）、③出方案（两个以上候选骨架）、④对需求（复用→改进→新增）、⑤做裁决（写下理由）、⑥签定稿（分解分析：节点→方案叶节点＋覆盖检查／符合性分析 → 利益相关方确认 → 冻结基线）——六步 = 三动作的展开：①②=需求就位（做+验）、③④⑤=分配生成（目标+做+裁决）、⑥=分解分析（做+核+封存）。

### 第7章 产品数据：开发产品就是开发产品数据

**自查速查**：① ✗ ② ✓ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✓ ⑧ ✗ ⑨ ✗ ⑩ ✓ ⑪ ✓ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗ ⑯ ✗

**练习答案要点**：
1. 六类数据各两个工件：需求（需求规格/验收准则）、设计（图纸/架构描述）、制造（工艺文件/BOM）、质量（测试报告/验证证据）、服务（维护手册/故障数据）、管理（变更记录/基线标识）。
2. 把数据当文档的例子：如"需求在共享盘里三个版本分不清"——数据是内容、文档是容器；开发全程在数据上工作，实物只是数据的复制品。
3. 两域三态图：信息域（开发/验证）↔物理域（制造/使用），靠数字孪生映射；设计态（EBOM·纯数据）、制造态（MBOM·数据+实物）、使用态（维护记录·实物+实况）。
4. 多环相乘分析：最终质量=需求正确性×数据质量×制造质量×使用质量；找出断掉的那一环，数据质量在其中起"上限"作用。
5. ISO 25012 的五把尺子逐项给证据：准确性（数据反映真实对象）/完整性（无遗漏）/一致性（不矛盾）/现时性（跟上现实）/可信度（经得起验证）。
6. 出题人=客户（需求源头）、判卷人=用户（验收裁判）；四条路径：需要（源头）/使用（新数据）/反馈（修正）/验收（把关）。
7. 价值三层：物化层（需求/架构描述 AD/实现工件，完全在数据里）、决策层（选型判断，ADR 部分沉淀）、过程层（沟通/评审，只留记录）；漏掉的那层怎么补（如决策补 ADR、过程补复盘）。
8. 职责三步：识别工件（配置项清单）→ 指定 owner（一件只一人）→ 挂机制（权限/签字/审批/指标挂到 owner）。
9. 数据资产四类：需求资产（该做什么）/设计架构资产（怎么做得好）/验证资产（怎么证明对）/管理资产（为什么这么做）；判断能否跨产品复用。
10. 实现方案八方案：技术/物料采购/制造/测试/交付/部署/操作/运维；最易漏的通常是交付/部署/操作/运维——只到技术方案就宣布终点，下游空转。
11. 流水线工位/工件：需求定义（需求数据）→设计（设计数据）→实现（实现产物）→验证（验证证据）→移交（基线）；缺陷放大例：需求错→设计跟着错→验证测错→量产全错，修复成本从 1 涨到 30~70 倍。
12. 增值判据分格：完善需求（内容增值）/加顾客不要的特性（过度加工）/审批草稿转受控、合规打标注满足规则（状态增值）/走过场、数据没变（必要非增值）/重复造轮子（纯浪费）。

### 第8章 评审、验证与确认：目标、需求、用途

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗

**练习答案要点**：
1. 四维表：参照（目标/规定需求/预期用途）、动作（确定/证实/证实）、证据（不要求/必须/必须）、时机（事前事中/对结果/真实场景）各填一行。
2. 评审重做：先写目标（对象 + 时限 + 可衡量结果），再问适宜/充分/有效三问。
3. "测试全绿"缺哪一要素：多为"证实"缺（只有结果没结论），或"对照"缺（需求没成文，尺子没有）。
4. 评审对目标：写出这条需求对应的目标，拿目标照需求——需求够吗？
5. "测试全过、没人用"病根 = 隐含需求系统性漏失；验证射程在文档、确认射程在场景。
6. 口头改的需求：定位它漏在哪一步（没进文档 → 验证够不着 → 确认没场景）。
7. 设计一次确认：真实用户 + 真实任务 + 真实场景 + 真实数据，写一份确认方案。
8. V 模型：需求在哪一级分解，验证在哪一级回收（左右镜像）；只做最后一次性验证 = 中间层级缺陷藏身。
9. 评审管把关（事前/事中），复盘管改进（事后、绕回起点）；复盘驱动下一轮评审的目标。
10. 通过标准会后现想 = 没有尺子；改成会前发出去、会后逐条打勾。
11. 三关走查：评审（对目标）过了吗、验证（对需求）过了吗、确认（对用途）过了吗；缺每一关的代价不同（白做/返工/没人用）。
12. 架构评审四看（概念陈述 / 选定 + ADR / 视图·基线 / 回炉痕迹）缺哪样 = 材料半成品；对质三问答不上 = 没权衡；没背书 = 只是架构师个人意见（评审变汇报、异常不闭环 = 放行半成品）。

### 第9章 工程师：一份能力清单

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ◐（显性化只是第一步，还要可检验）⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗ ⑯ ✗ ⑰ ✗

**练习答案要点**：
1. 体检：逐项打勾，指出缺项，并说出缺这一项会走岔成哪一种（只会做不会说／只会说不会做／守不住底线／能力失控）。判据只有一条：换个人接得住——缺哪一项，就问哪一项。
2. 粒度定位：按谱系（模块工程师／系统工程师／系统架构师）定位——背的是专责还是终责；有没有"名片一个粒度、实际另一个粒度"的人（如水忠＝模块岗位、干系统级的事）。
3. 起点：最近一次亲手把东西做出来是什么时候？答不上来，先做这一件事。
4. 第一道关口：把最近一次做对的事写成可交接的记录（步骤、依据、坑），交给没参与过的同事照做一次——他卡在哪一步，就是你还没显性化到位的地方。
5. 第二道关口：写下最近一次重要取舍（当时哪些约束在打架、选了哪个、依据是什么、后果如何、重来会怎么选）。
6. 第三道关口：写下不可越线清单（安全、合规、隐私、数据真实性各一条），再找出最近一次"为进度让路"的现场——利益相关方知情吗？有记录吗？
7. 证据：拿你负责的那套产品数据问一句"换个人拿着它，能不能做出来、继续演进"——答不出的部分，就是你的缺口。
8. 拓宽自测：现在的视角是模块视角还是系统视角？最近一次"为系统牺牲自己的模块"是什么时候？
9. 清单对表：把你手上这摊活按"需求 → 设计开发 → 产品数据 → 判定"摆一遍——摆不出来的那一段，就是你的缺口；断在哪一段，回头读哪一章（需求→第3、4、5章／设计开发→第3、6章／产品数据→第6、7章／判定→第8章）。

### 第10章 架构：定义、价值与误解

**自查速查**（**14 题**，与正文 §附录 C 逐条对位）：① ✗ ② ✗ ③ ✗ ④ ◐（不准确：微服务是**架构风格**——决策的套路，不是"架构"） ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗（清单是"表达"，不是架构；能签收的是那份描述） ⑩ ✗（需求可判，但判定宾语不是做法） ⑪ ✗（指派是授权，不是能力） ⑫ ✗ ⑬ ✗ ⑭ ✗（不补这一层会落空判据／责任／留痕三组）〔**2026-10-12 校**：旧速查 15 条对应旧题序；三块版后正文为 14 条，已重排〕

**练习答案要点**（**10 题**，与正文 §附录 D 逐条对位）：
1. 用**承重测试**筛：去掉它，这个实体还能达成它的目的吗——写下至少三条"去掉就不再是它"的。
2. 逐条跑**两遍**：兑现侧（实现目的需要它吗）＋演化侧（目的变了它守不守得住）。
3. 判一条"改起来贵"的决定：它是不是因为"贵"才被叫架构；去掉它，目的还达得成吗（**不可逆性只是代理**，会漏判也会误纳）。
4. 按五类归位：**关注域**（业务／数据／应用／技术）／**描述层次**（概念／逻辑／物理）／**架构种类与范围**（企业／系统／参考／总体（战略）／SoS；基线／目标）／**架构风格**（微服务等）／**框架**（Spring 等）。被当成"四个架构"的，正是把第一类当成了四个实体。
5. 一条规矩的**根据在内容侧、不在人**：说得出"不合它就不叫这个系统了"＝架构在起作用；只说得出"有人这么定"＝命令。
6. 评审的标的是**工作产品**：图会过时，能签收与冻结的是**架构描述**（不是"那张图"，也不只是那组基本概念或属性）。
7. 框架替你定的是"这一类"的组织方式；它**没替你定**服务边界、数据归属、接口契约——那些正是**架构内容**。
8. **被默认的架构**也是一份架构：它只是没被评审、没被记录、没人对它负责（这正是最贵的一种状态）。
9. 四问量"来路"：建筑图纸 → 1996 最高层级的构想 → IEEE 1471 根本组织 → 42010:2011 基本概念或属性（体现于元素与关系）→ 42010:2022 实体＋删去该层。
10. 只问两件事：**那句"它是什么"说清了没有；它排掉了什么**——答不上第二个，就还没有架构，只有主张。
### 第11章 架构定义：什么算输入，什么算产出

**自查速查**：① ✗ ② ◐（不准确） ③ ✗ ④ ✗ ⑤ ✗ ⑥ ◐（不准确） ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗（"不成立"） ⑬ ◐（不准确） ⑭ ✗ ⑮ ✗ ⑯ ✗
（⑤ 动词是变换、不是整理：整理不产生内容；⑨ 清单属内容侧、描述属描述侧；⑩ 架构可以关乎结构，那是外延不是产出，且架构实体≠系统元素；⑪ 往里加的是四样；⑫ 判断要成为依据，中间四个环节缺一不可；⑮ 经验只帮着找、不帮着选）

**练习答案要点**：
1. 逐项归位：相关架构／方针与指令／生存周期概念／利益相关方关切与需求／系统需求。**目的与目标不在清单里**——它们是**准绳**；而**架构目标与关键成功准则**才是这一步的**产物**（别把准绳当输入、也别把产物当输入）。
2. 三条去向：**落成架构内容**（变成某一则基本概念／基本属性／管控原则）／**被既有架构覆盖**（上一轮已把它管住）／**不在架构层承接**（归设计定义或实现）。判据只有一句：**这条需求是不是只有在"这个实体是什么"定下来之后才判得了**。去向不许是"消失"，要能倒查回去（42010:2022 §6.2 未处理项声明即此意在标准里的着落）。
3. 归到"不在架构层承接"的，各写它该去的那一层（设计层／流程配置／实现）。写不出来，说明它可能没人管——这正是"不许消失"要防的。
4. 四环体检：判断"这个实体是什么"／把它立成内容／**选定并背书**／**下游必须依据它**。冰链那间会议室四环全空（没有可划的界／没有可引用的内容／没有可背书的定案／没有可立得住的依据）；绕过去的方式通常是**从第四环倒着补**（先定了再说）。
5. 三条"必须遵守"的规矩各问一句：它是从哪条需求或目的读出来的？读不出来 → 它可能是**该立的管控原则**（自加），也可能只是一句习惯。分辨点：原则管的是**演化**（将来新增什么功能都不许破坏它），习惯只管这一次。
6. 四项检查逐条过。过不了"有物可依"＝用了哪件既有解答不出、**适配理由没写**（＝把没验证过的做法直接搬进来）；过不了"有辨可评"＝它跟别的候选在权衡空间上分辨不出差别（42020 §9.4.8 NOTE 1：权衡完全相同的两条不予考察）。
7. "现状照旧"要写成正式候选并配一句目的陈述（42020 §9.4.7 NOTE 2：*the status quo is sometimes one of the alternatives*）。写不出来，说明你还没认清**现状在保什么**。
8. 三句话：它是什么（**概念**）／它必须守什么（**原则**）／它为什么适用（**适配理由**）。最难写的通常是第三句——前两句靠标准与经验，第三句只能靠你对**这个局面**的判断。
9. 经验（启发式）在**生成那一环**最有用（想不出候选时它是起头的本事）；在**选定那一环**则是把偏好偷渡成理由。给一个具体例子，并指出它出错时**位置**错在哪一步。
10. 先分流：全新开发（*no prior system*）／产品线启动（一次为多次服务）／遗产革新（有资产但不打算沿用，重点在**重判资产可用性**）／增量启动（不确定性大，产出**后续步骤的选项**）。五处适配：走法从"资产优先"改"前向为主"／取材换来源／输出加两件／迭代策略换／**收窄的口径也要调**（去掉明显走不通的，不是去掉不熟的）。
11. 每划一条界写一句理由：**是因为它威胁目的，还是因为我们不熟**？说不出理由的界，就不该划——三条红线即由此来。
12. 四个问题：它说清"这个实体是什么"了吗？它是一条概念、一条属性还是一条原则？去掉它这个实体还能达成目的吗（**承重测试**）？它凭什么管住下游？——四问都答不出，它多半只是一句口号（"我们是微服务架构"就属这一类）。

### 第12章 架构决策：在承重处做选择

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ◐（不准确） ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ◐（半对） ⑨ ✗ ⑩ ✗（①②③⑧⑨ 的错因见附录 C 第12行；④"越早定越好"错在一刀切——按不可逆性定节奏；⑧"记录写全六问就够了"错在漏了标准分 shall／should 两档与"决策理由要单独记"）

**练习答案要点**：
1. 把一次改动拆成"一组选择"：这次改动里其实含几条独立的选择？各有几个选项？（拆不开，多半是还没认出它是一条架构决策）
2. 数据模型级决定的联动清单：主键／状态枚举／字段口径这类，列出重做时要动到的下游（结构上的、时间上的、组织上的）。
3. 三样各打高／中／低：影响半径（结构／时间／组织耦合）、信息成本（知识深度／隐含上下文）、修改风险（关键路径交叉／是否动已存在的数据）——**只用来定先后，不用来定资格**。
4. 找"不知为何这么定、不敢改"的决定 → 大概率信息成本极高 → 先补写"背景"。
5. 用六问写一份记录（名称／缘由／候选／定者与时间／影响／反悔难度）——它的骨是 §6.10.1 的十一项内容；找不到"背景／候选" = 这个决策从没被认真记录过，这本身就是发现。
6. 五个决策按不可逆性排序；对照你们投入的审查资源是否跟着排序走。
7. 显式推迟三句：现在为什么不做？等什么信息？什么时候再评估？（记成未决议题，不是记成决策）
8. 高不可逆的决策：先过目的关（它守住的是对目的必要的不变量吗），再按三样定节奏与审查深度。
9. 高不可逆的决策，先问"谁有权定"——评估给出判断，处置要有权的人作出。
10. "把谁列为候选"也是一条决策：你们这一轮的候选是怎么定的？范围定窄了没有？现状照旧上桌了吗？
11. 复盘一次被测序压住的决策：那一次是"威胁目的"，还是"我们不熟"？两个理由要分开写。
12. 你写下的那条记录，别人（没参与的人）读完能不能接着往下做决定？读不懂，缺的多半是理据与决策权属方。
13. 恒信"六问写不全的不进评审"这条规矩，管的是记录写没写全，还是这条规则谁有权改？（答案：只管前者。前者是团队自己立的关，自己也能撤；后者要有人有权，归第16章。）

### 第13章 架构描述：交得出去的工作产品

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗（① 图只是视图组件的一种形态，描述才是信息部件；② 能签收、能入库、能版本化的是描述，不是架构；③ 立场是利益相关方角度，视角是一组惯例；④ 内容与读法是两件事——读法不写下来，五个人读出五个意思；⑤ 规格缺项，产出的东西不成其为视图；⑥ 关切没有视角框定，它在这份描述里就没有位置；⑦ 生成顺序不可颠倒：先订视角、后造视图；⑧ 非模型式组件带一份图例即可，标准不规定形式化程度；⑨ 功能视图不是规范性要求，但几乎总会被包含；⑩ 决策权属方那一格补不回来——补上去的名字不是当时拍板的人。）

**练习答案要点**：
1. 三问落点都在"能不能上账"：不在描述里、不受某视角治理、组件没标模型种类也没有图例——任一问过不去，它是目录页或草图，不是视图。
2. 逐项数 §8.1 a)~g) 七项（外加第二段一句"宜"）；最容易缺的是**对应方法**与**视图方法**——缺了它，换个人复现不出同一张图。
3. 判视图看"受不受某视角治理"；组件可以同时进另一张视图（§3.19）——同一张数据流图既能在功能视图里，也能进信息安全视图。
4. 按附录 B.2 模板的次序走；自查一句＝"换个人拿着它，能不能产出同一张图"。
5. 两堆的分法看有没有管控模型种类；不基于模型的那一堆必须配图例（§3.19 注 1），否则读法没写下来。
6. 对照十一条自检逐条过；过不去的条目按出处回补——多半落在 §6.6／§6.7／§6.9 三处。
7. 由关切反推：每条关切至少一个视角框定、每个视角至少一张视图、每张视图应对它那个视角框定的全部关切；用不上的那一类，往往是没有对应关切（或关切没写下来）。
8. 那一格问的是"谁拍的板"；空着就写清为什么空——它是治理在描述里落款的地方，事后补名字等于把记录做假。

### 第14章 从架构到设计：三道关与四条边界

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗ ⑯ ✗ ⑰ ✗ ⑱ ✗（① 两类工作不是粗细两版，design 宽义句推不出粗细论；③ 有效的架构尽可能不依赖于设计（**15288:2023 §5.9 标准正文**）；④ 交接第一步是"检查"不是"接收"；⑥ 分配须同时满足系统需求**和架构目标**；⑦ 新增元素是正常的，要管的是认领；⑨ 〈待定〉不是留白是欠账；⑩ 设计定义只可**评审**，确认要落在实现出的客体上；⑪ 一致永远落在跨视图对应关系上；⑬ 换手点是**信息充分性**判据；⑮ 7±2 是可管理性规则不是停止规则；⑯ 切视角的维度是"看什么"不是"谁在看"；⑰ 受理口是义务、视角是手段；⑱ 自建视角有成本，先穷尽复用）

**练习答案要点**：
1. 交接体检："收到文档就开工"的标志是——设计描述里说不出"本次从架构取到了哪几条约束"；正确形态是列得出"基本属性与概念／指导设计及其演化的原则"两栏。
2. 两条转化：转不动的两种病因要对症——架构侧没立住（特性本身不可判定）／设计侧没转（有元素无特性落点）；先判在哪一侧，再决定回架构还是补设计。
3. 分配对两个量：找不到承担者的多半是**架构目标**（系统需求通常有人认领）；原因写在"这条目标该由哪一层承担"，往往发现它根本没往下分。
4. 无主的接口：判据是"架构有没有识别过它"；选"回架构补识别"还是"进需求基线"，看它是**架构漏了**（既有职责没交代）还是**需求变了**（新出现的功能）。
5. 描述符对账：对不上的两格＝两种病——元素自设指标（无据）与系统级指标无人接（缺项）；〈待定〉逐格写责任人。
6. 九查：加戏查在"实体转化"（多出架构未授权的元素或依赖），滥项查在"查滥"（技术选型当概念／交付关切升格／把自由度当架构资产）；三档结论中"条件性合规"必须带补项、责任方、期限。
7. 可实现性归位：四步依次试——并入既有视角、扩既有视角规格、新建视角、改用别的标准手段；判据只看"是否需要独立模型种类且能独立判定"。
8. 换手点验证：两个条件各自问一句——"它的需求能不能只用黑盒描述"（能不能）＋"我能不能自信而明确地说出它在现实世界中的解决方案"（敢不敢）；两条都过，买／造／重用才是决策而不是赌博。

### 第15章 配置管理：让一直在变的东西说得清

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗

**练习答案要点**：
1. 配置三问检验客户可改参数：被记录了吗（记录边界）/功能物理特性吗（类别边界）/关联成整体了吗（关联边界）——参数是零件，配置是整机。
2. 五个配置项（代码/固件/文档/数据/硬件）+ 该不该纳入管理的判断（组织选定纳入的实体才是配置项）。
3. 最大配置项三查：有版本号吗 / 版本号对应哪次完整构建吗 / 有基线吗（批准+冻结+参照）。
4. 回滚/追溯复盘：查不到的地方，缺的是版本、基线、还是状态记录。
5. 版本链画基线点：在里程碑（需求批准→功能基线、分配定案→分配基线、产品定型→产品基线）竖切。
6. 变更控制循环五步（CR→影响评估→CCB→实施→新基线）：哪步跳过了、代价是什么。
7. 四大活动诊断：标识（是什么）/控制（怎么变）/状态记录（现在什么样）/审计（实物与记录一致吗）各打有/缺/半吊子。
8. 决策记录六问对照同构表：对应的配置信息、基线（冻结）、变更控制各在哪里。
9. 契约链三层：每层"基线（冻结端）"与"版本（交付端）"分别是什么。
10. 编号事故用配置管理复盘：CR + 影响评估会写"影响全部历史合同数据，不可逆性高"——这一行字就拦住"今天就能上"。
11. 精确召回 vs 全量召回案例：算一下批次追溯能省下"精确召回受影响批次 vs 召回全部在役五千台"的差量。
12. 四问量"配置"（或"基线"）→ 基线是什么（被批准、被冻结、作全生命周期参照的配置信息）、不是什么（不是版本：版本是刻度、基线是资格）、从哪来（"凝结"型概念：从测绘"基准线"转义，工程实践中被共同体固化，见§1.2.1）、往哪去（变更控制循环的支点：冻结→变更→再冻结）；最薄的一问往往是从哪来——答不出"凝结"故事，就会把"版本号=基线"当真。

### 第16章 治理：谁掌舵，谁划桨

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗（⑪ 治理的对象不是"文档"，是「目的→不变量→根本决策→遵从与演化」链——架构资产只是四层之一，目的漂移了、决策偏离了目的，文档再整齐也白搭；⑫ 目的变更是架构重审的强制触发器——fundamental 判据本身换了、不变量集合整体过期，目的漂移只能靠以目的为参照的定期检视抓）

**练习答案要点**：
1. 治理四问检验挂"治理"名头的事：谁来治（角色）/依何治（规则）/如何治（机制）/治得怎样（担责）——四问答得上才谈治理；再用标准定义句对成分——以人为基础（人说了算还是文件说了算）/三职能（指导·监督·担责）/为宗旨/"被"字（须交账的地位是制度给的还是靠自觉）。
2. 五个大决策分类：掌舵（定方向/定规则/裁例外）vs 划桨（执行/优化/交付）；再按三条判据（层级/对象/不可自裁）逐段定性，用介入门槛（跨出单管理层权限）说明该不该升级——判据管分类、门槛管升级，别把"跨部门"当判据。
3. 三条件核对：分离/静默积累/框架级——符合几个？还差哪个？差的往往就是"管理足够"的原因。
4. 委员会诊断：治理机构是否持续行使四活动（利益相关方参与/评估/指导/监督）、评估发现偏差后是否调整指导？只开会看报告、从不处置 = 橡皮图章。
5. "坏了"（内部失效，红旗评估抓）vs"不适合了"（外部过时，定期检视抓）各一例；后者往往要等爆雷。
6. 权力链画出来：所有权→治理→管理→执行，每层是谁；哪层空了（有管理没治理最典型）。
7. 过滤器改造：定哪几条规则让 90% 的争议自动处理、不再上会。
8. 三活动循环诊断：感知/定规/裁例外，哪环最弱；缺感知则盲、缺定规则乱、缺裁例外则僵。
9. 术语膨胀五问：有分离吗/治理在持续运转吗/委员会在定规则裁例外吗/有传感装置吗/治理层碰桨吗——任一"没有"就要警惕（五问是体检表，判"转不转得动"，不判"算不算治理"）。
10. 伞结构写出：XX管理 = XX治理 + XX开发与运营，三个加数对应谁；伞名有没有和子流重名（自包含）；分域模子三条不变（原则不另立/治理机构不另设/最终担责不转移）。
11. 编号事故治理视角：有"编号标准由法务归口"这条规则时，改编号必须走跨部门裁决——规则从根上拦下"今天就能上"。
12. 挑一个系统架构决策，沿"目的→不变量→根本决策→遵从与演化"四层各问一遍：这层谁在守护、被什么侵蚀；再按 §14.4.4 判例（目的漂移事件链）的拆法走一遍：目的漂移后，哪个动作算治理（侦测/裁决/重审判据）、哪个算管理（调整架构/实施迁移）。

### 第17章 整合：从一条需求到上线运维

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗

**练习答案要点**：
1. 画完整闭环时间线：七站（需求/设计/把关/运维 + 架构[含架构设计与架构决策]/配置/治理贯穿）+ 每站之间标接缝；圈出最弱一环。
2. 顺次/横切分类：第3~8 章顺次（需求3/4/5·设计6/7·把关8；运维对应第2章工程系统回归）、第10~14 章横切（架构10·架构设计11·架构决策12·配置13·治理14）；组织里横切线各自谁在贯穿，有没有没人贯穿的线。
3. "切片都做了但系统失败"复盘：接缝断在哪两个切片之间、断在四条接缝（承接/参照/记录/问责）的哪一条。
4. 配置管理三问复盘模块：应该是什么（需求）/实际是什么（验证）/怎么变成这样（变更记录）——三答对得上吗。
5. 先用**目的关**裁它够不够格进架构（它守的是目的之下的不变量吗），再用三层判断框架量代价与时机（影响半径/信息成本/修改风险——它只是**代理**，管排序不管准入）：被提前投资了，还是等爆雷才做。
6. 起点判据检查真实需求：完整/无歧义/不冲突/隐含需求已识别，哪条最弱；有没有"编号进台账"式藏在场景里的隐含需求。
7. 模块拆树 + 语义四查 + 分配三自检：找两片叶子之间缺的"接缝叶"。
8. 评审、验证、确认复盘上线：各自站住了吗（目标、规定需求、预期用途各对上了吗）；"确认"是不是真在场景里做的。
9. 治理四问（谁来治〔角色〕/依何治〔规则〕/如何治〔机制〕/治得怎样〔问责〕，第14章原词）诊断跨部门变更：落到这次变更就是——谁裁决/依什么规则/机制是什么/谁担责——答不上来的那一问，就是接缝。
10. 概念跨域实例：把基线/确认/治理/不可逆性搬到一个陌生行业，还能成立吗——成立在哪个位置。
11. 接缝人角色扮演：至少 5 处接缝 + 每条靠四条接缝里的哪条缝合 + 责任人是谁——写得出来才缝得上。

### 第18章 架构师：把整条链背在身上的人

**自查速查**：① ✗ ② ✗ ③ ✗ ④ ✗ ⑤ ✗ ⑥ ✗ ⑦ ✗ ⑧ ✗ ⑨ ✗ ⑩ ✗ ⑪ ✗ ⑫ ✗ ⑬ ✗ ⑭ ✗ ⑮ ✗ ⑯ ✗ ⑰ ✗ ⑱ ✗ ⑲ ✗ ⑳ ✗（⑭ 架构师再往上≠升任 CTO；⑮ 专责≠终责；⑯ 拍板权在系统工程师、理由权在架构师；⑰ 架构符合性把关是职责的一部分；⑱ 42010 只给架构活动立词条、不给头衔立词条——标准认活不认职位；⑲ 十项清单是体检切法（六项底座+四项增量）、七动词链是工序切法，两套并行不互吞；⑳ 目的定义权和问责在业务方——架构师对"架构忠于目的"负责（理解/澄清/质疑/守护），越界改写目的是 Cowboy Coding 式架构的病因）

**练习答案要点**：
1. 十项能力体检：逐项打勾，指出缺项，判断对方在补底座（六项）还是补增量（四项）。
2. 专责终责盘点：系统成败的账（终责）在谁手里、架构正确性的账（专责）在谁手里——同一个人是兼任还是失职（把专责当终责 = 什么都管）。
3. 角色边界归属：这个决定本该归谁——按"管决定/管结构/懂系统"划分，说出它为什么被相邻角色抢走了。
4. 失败模式对号入座：画图匠（没判断）/ 什么都管（管太多·把专责当终责）/ 不决策（不管）/ 远离代码（看不见），对应十项清单里缺的那一项。
5. 产品数据体检：翻出架构描述+接口契约，逐项问"换个人拿着能不能继续做下去"——答不上来的那部分就是⑥的缺口。
6. 工作检查单落地：下一次不可逆决策前过七条（是不是严重决策 / 理论是什么 / 利益相关方视图跟上没 / 记录写了没 / 我是在做决定还是在画图 / 接口契约改了没·下游叶子跟着变没 / 我在背专责还是终责）。
7. 晋升阶梯盘点 → 四条路径（深度/宽度/组织/权威）各对应一条核心关切；标出你们"架构线"与"管理线"的分叉点在哪——对照你现在的棋盘在哪一格（工具不变，棋盘变大）。
8. 目的权责盘点：你们系统"目的/任务"的定义权在谁手里？架构师是在理解/澄清/质疑/守护目的，还是悄悄改写它？写一份《系统目的或任务理解确认单》试试：业务方原话 + 你的复述——复述里有没有冒出架构语言（冒出，就是越界了）。
