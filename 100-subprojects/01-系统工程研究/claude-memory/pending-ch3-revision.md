- **定需求**——需求定义"要什么"（确立那份宽泛的需求规格），是设计开发的输入、也是质量判定的参照；
- **出规格**——设计开发把需求转化为**更详细的需求**，形成规定需求（**规格＝规定需求的集合**）；
- **判满足**——质量认定客体固有特性满足要求的程度（单项二元／整体程度）。

**★ "这里的规格＝规定的需求"要写进正文首现处，且要点在两处**：① ISO 9000:2026 **§3.5.1 注 2**「规定的要求是**明示的要求**，例如写在成文信息中的要求」；底本 §0「**验证的参照 = 规定需求（specified requirement，即被明示的需求）**」；底本 §2.4「**设计输出 = 新的规定需求**……设计输出文件（规格书、图纸、工艺文件）本质是**规定需求集合**」——**"规格"就是规定需求的集合，用户的理解成立**；② 但**输入那份也叫规格**（底本 §5.5：「需求规格 = what……**需求规格不止一份**——系统级规格 → 子系统级规格 → 部件级规格，**每一级设计开发阶段的输入都是一份规格**」），输出那份才是规定需求；**差别不在名字，在 §3.3.11 注 1 的"宽泛 vs 更详细"**。故正文要写一句"**这里说的规格，是更详细的那一份，即规定需求**"，否则读者会与输入那份混——这也正是"出规格"区别于"定需求"的地方。

### 7.6 教训（本会话新增两条，入册）

1. **`git add` 是原子的**：一条 `git add` 里若含一个不存在的路径，**整条命令中止、什么都不暂存**——本会话因此产生过一个只记改名、不含内容的空提交（`570a2ef1`，随即以 `85cd549b` 补上）。**做法：`git add` 只列存在的路径；暂存后必须 `git diff --cached --name-only` 复核"要提交的都进去了"。**
2. **PowerShell 会把单元素数组拆成字符**：用 `@(@(a,b))` 这类嵌套数组批量做字符串替换时，`$pr` 迭代到的是**字符串的每个字符**，于是 `Replace('下','一')`、`Replace('第','3')` 这类**灾难性误替换**在四个文件上发生（ch2／ch6／ch8／ch17）。**做法：批量替换一律用"函数＋逐条显式调用"，不用嵌套数组；落盘后立刻 `git diff` **看内容**，不只 `--numstat`**（等量增删恰是行尾统一或误替换的信号）。
