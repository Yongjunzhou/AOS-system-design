# EOS 规范化的相关方需求预处理状态文档

**用途**：规范化的相关方需求预处理链（`ort00-textualize` / `ort01-chunk` / `ort02-clarify` / `ort03-norm`）的状态追踪共享接口。AI 通过此表感知原始材料、文本化文档、切分子文件和 规范化的相关方需求基线条目的处理状态；人类通过此表做预处理阶段的批量决策。

**HEAD @上次AI运行**：`{commit-hash}`（AI 每轮 `scripts/ai-commit.sh` 提交基线后更新；各步 Step 1 以 `git diff <该 hash>` 检出人类变更，`git log --author="EOS-AI" -1` 校验兜底）

**权威源契约**：

1. 本表只管理 规范化的相关方需求预处理阶段的状态：表 A（原始材料）、表 B（切分子文件）、表 C（规范化的相关方需求基线条目）。
2. `wft01/02/03/04/05` 不以本表管理 业务概要 / 业务方案 / 系统需求概要 / 产品概要 状态；这些状态以对应产品文档管理区为权威源。
3. `wft01/02/03/04/05` 若生成补充原始需求材料，只登记到表 A，生命周期为 `已登记`，后续仍由 `ort00~ort03` 进入预处理链。

**同步契约**：

1. 规范化的相关方需求预处理链写入顺序：先更新本表 A/B/C，再更新对应原料、文本化、切分或规范化文件。
2. 设计链写入顺序：直接更新对应产品文档管理区；本表不派生、不同步 业务概要 / 业务方案 / 系统需求概要 / 产品概要 状态。
3. 本表不承载设计正文，只承载 规范化的相关方需求预处理状态、选材和批量决策信息。
4. AI 每次运行结束更新表头 `**HEAD @上次AI运行**` 为本次 ai-commit 基线 hash（供 Step 1 以 `git diff` 检出人类变更）；人类无需维护该字段。

### 表B — 切分文件处理进度

| 源文件 | 子文件 | 内容摘要 | 生命周期 | AI建议 | 人类决策 | last_size | iteration_count | unresolved_count | 操作指引 | 最后更新 |
|--------|--------|---------|---------|-------|---------|----------|----------------|-----------------|---------|---------|

**粒度**：一行/切分子文件（`.chunk-{seq}.md`），追踪从切分创建到规范化完成的子文件预处理全生命周期。

**生命周期取值**：

```
已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃
```

| 阶段 | 说明 | 管理步骤 |
|------|------|---------|
| 已切分 | 切分执行完成 | ort01 完成 |
| 澄清中 | AI 已做首轮标注或正在迭代，等待人类反馈 | ort02 迭代中 |
| 已澄清 | 三项条件全满足，澄清完成 | ort02 完成 |
| 待确认规范方案 | AI 已给出规范化方案，等待人类确认 | ort03 等待反馈 |
| 已规范化 | 规范化完成，规范化的相关方需求条目已写入基线 | ort03 完成 |
| 已废弃 | 子文件不再处理 | 任何步骤 |

**AI建议取值**：可以澄清 / 需继续澄清 / 可以规范化 / 建议执行 / 已完成 / 建议终止

**控制流**：
- 人类设 `人类决策=同意澄清` → ort02 选材入澄清
- 人类设 `人类决策=同意规范化` → ort03 选材入规范化
- 人类设 `人类决策=已终止` → 废弃处理

**单对字段覆盖机制**：生命周期转迁时，AI 更新 `AI建议` 为针对新阶段的前视建议，同时 `人类决策` **自动清空**，等待人类针对新建议重新决策。

**字段说明**：

| 字段 | 写入者 | 说明 |
|------|--------|------|
| 源文件 | ort01 | 所属原始材料文件名 |
| 子文件 | ort01 | 切分子文件路径（`.chunk-{seq}.md`） |
| 内容摘要 | 各步更新 | 该子文件核心内容一句话摘要 |
| 生命周期 | 各步转迁 | 见上方生命周期取值 |
| AI建议 | 各步更新 | 对当前阶段的前视建议（如"可以澄清""可以规范化"） |
| 人类决策 | 人类 | 空（未处理）/ 同意澄清 / 同意规范化 / 已终止 |
| last_size | ort02/ort03 | 最近处理时的正文区字节数，用于增量检测（各步存各步处理对象：ort02 存切分文件正文区，ort03 存 规范化的相关方需求基线 `#body-{seq}`） |
| iteration_count | ort02 | 澄清迭代轮次计数 |
| unresolved_count | ort02 | 当前未解决的模糊项数量 |
| 操作指引 | 各步更新 | 人类下一步应执行的操作 |
| 最后更新 | 各步更新 | 格式 YYYY-MM-DD |

### 表C — 规范化的相关方需求基线条目处理进度

| 源文件 | 节点ID | 规范化的相关方需求编号 | 内容摘要 | 标题 | 类型 | 优先级 | 当前状态 | 人类决策 | AI建议 | 操作指引 | 最后更新 |
|--------|--------|--------|---------|------|------|--------|---------|---------|--------|---------|---------|

**粒度**：一行/规范化的相关方需求条目，追踪规范化产出的每条 规范化的相关方需求基线条目从生成、进入 wft01 分配，到完成初始 STR 分配的全过程。进入 wft 链后的设计产物状态不在本表管理。

**状态取值**：待处理 → 待确认方案 → 已分配 → 验证中 → 已验证冻结 → 已废弃

| 状态 | 含义 | 管理步骤 |
|------|------|---------|
| 待处理 | 初写入（ort03 设定初始值） | ort03 写入 → wft01-* 启动时自动扫描 |
| 待确认方案 | wft01-* 已给出 规范化的相关方需求→STR 分配方案，等人类确认 | wft01-*（人类审阅） |
| 已分配 | 规范化的相关方需求→STR 分配方案已通过，等待或进入下游承接 | wft01-*（STR 审阅通过时同步回写） |
| 验证中 | 该 规范化的相关方需求 的承接链已进入全链追溯验证；本表仅保留只读同步状态 | 追溯验证 |
| 已验证冻结 | 全链验证通过；本表仅保留只读同步状态 | 追溯验证 |
| 已废弃 | 规范化的相关方需求条目被废弃 | 本步/下游均可触发 |

**人类决策取值**：**同意分配**→选入当前批次进入 wft01-* 分解分配 | **—**→暂不处理

**控制流**：人类设 `人类决策=同意分配` → ort03 将符合条件的 规范化的相关方需求 按类型加入对应 wft01 的 `AI可以处理节点` 分节；AI 在下一轮 wft01-* 中读取处理；wft01-* 首次生成方案后写为 `待确认方案`；相关 STR 节点审阅通过并进入 `可以分解分配` 时，对应 规范化的相关方需求 同步更新为 `已分配`；追溯验证选入时推进到 `验证中`，验证通过后更新为 `已验证冻结`。
