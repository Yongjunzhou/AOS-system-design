# EOS 输出产品架构

**文档版本**：v3.1
**修订日期**：2026-08-10
**HEAD @上次 AI 运行**：3af7de3

> **概述**：EOS 输出产品架构的权威资产文件。按 业务域→项目类型→构件 组织（六级层级模型中已填充的层级），以统一 13 字段横表表单记录各节点。[24 可复用业务资产](24-eos-business-assets.md) 和 [25 引擎资产](25-eos-engine-models.md) 并列，共同构成完整的输出产品架构资产体系。通过 ID 引用关联 [26 文档资产](26-eos-document-definitions.md) 和 [28 看板指标资产](28-eos-dashboard-indicator-assets.md)。
>
> **统一节点字段（全层级通用，13 字段）**：`节点ID / 节点名称 / 节点层级 / 层级名称 / 父节点ID / 复用方式 / 复用节点ID / 输入 / 输出 / 节点说明 / 生命周期状态 / AI建议 / 人类反馈`。任何层级节点均为横表中的一行；不适用字段填 "—"。
>
> **六级层级模型**：业务域(L1) → 项目类型(L2) → 端到端业务(L3) → WBS(L4) → 输出文档(L5) → 构件(L6)。本文档当前填充 L1/L2/L6；L3/L4/L5 随 BP 设计演化渐进填充，插入时往统一表加行即可，schema 不变。（L5=输出文档；旧版 IPO 层级已弃用。）
>
> **字段口径**：
> - `复用方式`：原创 / 复用 / 改进（对应资产优先原则 Reuse > Improve > Add）。原"实现策略"已并入：平台配置→复用、自研→原创。
> - `复用节点ID`：仅当复用方式∈{复用, 改进}时填写，可指向 @engine-*/@bp-*/@node-*/@doc-*（前缀区分被复用对象类型），原创时填 "—"。
> - `生命周期状态` / `AI建议` / `人类反馈`：三字段正交状态模型。`人类反馈` 为覆盖式当前反馈（[同意]/[修改]/[驳回]/[需裁决]），历史轨迹由 git 承载，不在文档建表。
> - 业务域(L1)节点为组织容器，其 复用方式/复用节点ID/输入/输出/生命周期状态/AI建议/人类反馈 默认 "—"。
>
> **产品类型说明**：项目类型(L2) 分为两类——**输出产品**（流水线视角，如采购管理、生产管理）和**角色场景**（工作台视角，如业务架构管理员、数据治理员）。两者都是 EOS 运行输出的产品。
>
> **追溯关系**：向上需求追溯（相关方需求→输出产品资产）由 [08 追溯矩阵](08-eos-sysdev-traceability-matrix.md) 统一承载，本文档不重复持有（依赖单向：产品数据→资产）。详见附录B。

## 附录A：识别规则与口径（参考附录）

> 本附录保留 23 号资产特有的识别方法论。通用读写规则见 91 规范 §十一。

### A.1 基本生成路径

对每个被选入设计的 STR 架构末级节点，按以下路径识别输出产品架构资产：

1. **理解角色场景**——明确该 STR 末级节点描述的角色、业务目标、触发条件、期望结果和边界
2. **补齐文档序列**——基于该角色场景，识别完成该场景所需的输入文档、过程文档、输出文档和状态记录
3. **逐文档识别归属**——对文档序列中的每个文档或信息载体，识别其所属业务域、产品类型、构件类型和产品数据类型
4. **匹配既有 23 资产**——优先复用已确认条目；若语义接近但边界不足，标记为扩展或改进；若无合适承接对象，生成候选新条目
5. **人类反馈与确认**——AI 只能提出识别建议和候选归属。业务边界、产品类型命名、构件类型归并和废弃判断必须经过人类反馈或确认
6. **沉淀为资产**——人类确认后，将产品类型、构件类型、产品数据关系写入本文件节点行，并维护生命周期状态与人类反馈

### A.2 三维业务域规则

| 维度 | 主要目的 | 典型业务域 |
|------|---------|-----------|
| 管理维 | 满足监管相关方要求 | 规划与经营、质量管理、合规管理、企业党建、部门运行 |
| 价值维 | 满足产品相关方需求 | 市场销售、产品研发、生产制造、售后服务 |
| 支持维 | 满足资源申请方需要 | 采供管理、人力资源管理、财经业务管理、能力建设管理、流程与IT、行政服务 |

子域判断：
- 每个业务域可包含管理子域和运行子域
- 管理维业务域以管理子域为主；价值维、支持维通常同时具有管理子域和运行子域
- 规划与经营业务域代表企业全部业务，其他业务域默认只负责本业务域
- 各业务域的管理子域通常复用通用管理类产品类型业务
- 各业务域的运行子域产品类型业务按业务域特性分别识别，不强制统一模板

### A.3 资产确认原则

1. **需求驱动**：新增或修订产品类型、构件类型时，应能追溯到一个或多个 STR 架构末级节点、BP 分析或人类确认的业务流程规则（向上追溯关系记入 08 追溯矩阵，见附录B）
2. **资产优先**：识别时优先复用已确认资产（Reuse > Improve > Add），再考虑扩展、归并或新增
3. **人类裁定**：全企业级/本域级边界、产品类型命名、构件归并、废弃判断由人类最终确认
4. **候选隔离**：AI 推断但未确认的条目标记为 `生命周期状态：疑似` + `AI建议`，不得直接作为已确认资产供下游强依赖
5. **规则沉淀**：反复出现的识别判断、边界口径和归并原则，应沉淀到本附录或相关权威规范中
6. **项目管理构件标配**：每个已确认的 E2E 项目下均应包含项目管理构件，作为该产品管理/绩效/指标的管理控制承载节点（wft01-biz 设计意图）
