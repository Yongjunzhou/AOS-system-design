## 一、目的与目标

### 1.1 本任务在设计链上的位置

设计开发 = 由需求到方案的逐对生成。业务路径的首对，是由相关方需求设计出业务流程：

```
相关方需求 → 业务流程：  X = 相关方需求，不分形态，最深一级＝用例场景
        │  本任务一次产出 Y 的概要态与完整态
        ▼
       Y = 业务流程方案，一份文档含两个形态，即「业务流程概要 + 业务流程方案」
```

- 本任务是业务路径的首对。**它的概要态与完整态合并在一份文档里、一次产出**——这是本链上的特例，其余各对分两个任务、各出一份。
- **本任务不造末三级**：相关方需求里的业务文档、任务节点、用例场景，就是 R／P 两棵树里的同名三级——**同名同批、整段搬入**。不做映射、不做分配、不做承接；本任务只把它们按属性归位，并补 Y 侧内容。
- **本任务做三件事**：其一，按业务文档自带的三个属性——所属主责角色、所属产品构件、所属E2E职责——把它归拢成 **R 树**，即谁做什么、按什么序；其二，把它归拢成 **P 树**，即作为产品数据从属谁、依赖谁；其三，覆盖检查检出缺口，分业务类与引擎类补原始需求。三件事各占一步。
- **概要的位置**：概要是业务流程的**浅态**，即根→枝梢（任务节点）；完整态是它的**深态**，即根→叶（用例场景）。两态同在一份文档里、同出一次，故本任务既要写概要级的结构判定，也要写完整态的叶与方案内容。概要不自成一段交付，也不占需求-方案对的一端。
- **人类门禁位置**：两处——本任务产出方案后人类「整体确认」；覆盖检查检出缺口后，候选去留由人类裁决。
- 下游退回：系统需求概要设计任务检出缺陷 → 标 `需biz01修订`，这是**反向迭代**，也就是方案迭代需求。

### 1.2 主要目的

> 取信于相关方——「你听懂了我的需求和意图」。把 X 已给的这批业务文档按它们自带的属性组装成业务流程方案：文档、任务、用例场景照原样进入 Y，本任务长出它们之上的干枝、写出两棵树的秩序；并以覆盖检查检出缺口，把业务链与平台引擎接不住的部分补成原始需求交回预处理链。

### 1.3 目标

1. **组装 R 树 · 归拢到场景**：按「所属E2E职责」把业务文档归到同一个业务对象闭环，判定该 E2E职责，也就是枝干，已有还是新长——有则**复用**；否则**新建**。
2. **组装 R 树 · 长干枝**：业务域、相关方角色取自 X 的属性，角色职责属目标组织级；E2E职责本任务产出——判执行类或管理类、命名、边界定义，边界即主责角色的业务对象闭环。
3. **组装 R 树 · 写秩序**：场景职责边界陈述；该角色按什么序处理这些文档；加需求明示的任务触发关系，用业务语言表达。
4. **组装 P 树 · 长干枝**：产品类型、产品构件类型、构件开发WBS（包），逐文档判定它在这一级的位置，走三档——引用／扩展／新建。
5. **组装 P 树 · 写秩序**：WBS 归组，判据是数据依赖链；再做 P 树一致性三类检查，产出 P 组装结论。
6. **归位与 Y 侧内容**：X 已给的业务文档、任务节点、用例场景按属性落进两棵树；为每张业务文档补封面模式，即正式或轻量；并写**分解源判据**。
7. **属性齐备保证**：每张业务文档的三个属性齐备且唯一——归拢对不对全由它决定。
8. **覆盖检查与缺口补足**：端到端闭环核对「需求条目有没有全部被业务链覆盖」；检出缺口分两条通道补足原始需求——**业务类**由 P 树对照给出，**引擎类**由用例场景对照平台引擎给出。

### 1.4 本任务负责 / 不负责

**负责**：把 X 已给的业务文档、任务节点、用例场景按属性组装成 R 树与 P 树——长两棵树的干枝、定边界与秩序、归位业务文档、任务节点、用例场景并补齐其 Y 侧内容与传出承诺；覆盖检查检出缺口后，**以 P 树补业务类原始需求、以用例场景对照平台引擎补引擎类原始需求**；人类确认后落账并推进状态；处理下游退回，即反向迭代修订。

**不负责，均指向其实际归属**：

- 引擎能力功能需求 → 引擎能力设计任务；非功能需求 → 非功能需求设计任务。二者在输入校验检出后退出
- **X 的切分与建树**，含业务文档、任务节点、用例场景三级的落位与三个属性 → 需求预处理链。本任务只受理或退回，不自行重切、不重定属性
- **补充原始需求材料的加工与路由** → 需求预处理链。本任务只出材料；加工成条目、按类型路由由它办
- **引擎能力本身的设计** → 引擎能力设计任务。本任务只出引擎类原始需求材料，不代引擎设计
- **下游各对的展开**，即业务流程 → 系统需求 → 平台构成 → 配置方案 → 前后端组件方案 → 系统需求概要设计任务及其后继
- 页面层级/菜单设计 → 系统需求概要设计任务
- 业务人员确认 → 人类线下活动
- **治理业务流程方案**中无需求输入者 → 无需求锚点，由人类按平台治理业务渐进增补、经预处理链补需求，本任务不主动展开

### 1.5 与上下游的衔接

| 方向 | 任务 | 交接内容 |
|------|------|---------|
| 上游，X 的来源 | 需求预处理链的规范化任务 | 产出 X：功能需求树——业务文档 → 任务节点 → 用例场景，业务文档上落三个属性；业务功能需求条目置状态 `待处理`。X 的结构与切分、建树规则由预处理链与相关方需求数据文件单源 |

## 二、输入文档结构及规则（X = 相关方需求 · 需求侧）

### 2.1 主输入文档定位

本任务的 X = **相关方需求**，现行文件 `01-eos-specified-requirements.md`，是产品数据。它与其他产品数据不同，**不分概要态与完整态**——一产出即是完整态，最深一级为用例场景。它由**需求预处理链**的四个任务生成，不在 SKILL 指南之列。

相关方需求含两棵树——功能需求树与非功能需求树。**本任务消费功能需求树**；非功能需求树归非功能需求设计任务。

本任务运行时的**主输入对象** = X 中处于 `待处理` 的**业务功能需求条目**，即功能需求树的叶，按业务文档聚集、同一张业务文档下的条目优先成批，每批 ≤10 条。读 X 时按树定位、按属性归拢。文档的完整结构、字段与读写约定以 91 号规范 §11 与相关方需求数据文件自身为准。

### 2.2 相关方需求的树形结构与各级语义（X 树）

X 是本次映射的自变量。下图是该树在本任务视图下的展开，树形与各级语义以 94 号文档 §2.1.1 为准。

```
相关方功能需求
└── 业务文档 ──────── ① 根　带三个属性：所属主责角色 × 所属产品构件 × 所属E2E职责
    └── 任务节点 ──────── ② 开发文档所对应任务的子节点，原则上，一个节点对应一个表单标签页
        └── 用例场景 ─ ③ 任务节点上包括的用例场景操作，原则上对应着标签页上的一个功能按钮、右键操作项，或一个快捷键所提供的功能
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务文档 | 业务运行结束后应输出的产品数据文档，一般对应一个流程、一个工单、一个计划，或一个看板业务 | **预处理链产出** | **到 Y 侧就是 ⑤，即业务文档**：归位、P 认亲；三个属性是归拢的依据，「所属主责角色」定 R 树的域与角色，「所属E2E职责」定它落在 R 树的哪个场景，「所属产品构件」定它在 P 侧落到哪个构件 |
| ② | 任务节点 | 开发文档所对应任务的子节点，原则上，一个节点对应一个表单标签页 | **预处理链产出** | **到 Y 侧就是 ⑥，即枝梢节点**：对于同一个业务文档下的任务节点，应从语义和业务逻辑上进行整理，成为规范的任务节点 |
| ③ | 用例场景 | 任务节点上包括的用例场景操作，原则上对应着标签页上的一个功能按钮、右键操作项，或一个快捷键所提供的功能 | **预处理链产出** | **到 Y 侧就是 ⑦，即叶节点**：对于整理后任务节点，对其下的多个用例场景从语义和业务逻辑上进行整理，成为规范的用例场景 |

> **文档的三个属性，不占级位**：所属主责角色／所属产品构件／所属E2E职责随业务文档携带——角色与场景是本份数据的**索引／分片轴**，不是归集级。
>
> **同一个文档可对应多个相关方需求**：需求捕获时，不同的相关方，其业务对象可能是同一个文档；亦或，同一个相关方对同一个文档的业务，后续可能有改进的需求。
>
> **X 的三级就是 Y 的同名三级**：同一批节点，在 X 里按文档平铺，在 R／P 两棵树里按角色与产品归拢。故本任务的文档清单以 X 的业务文档为准。
>
> **落位现状**：相关方需求的现行物理文件以角色分片直接挂条目，尚未含业务文档与任务节点两级；本任务读时按条目正文语义归拢，标 `[待复核]`。

### 2.3 X 侧规则（复核与退回）

- **切分与建树权在预处理链**：业务对象闭环的切分、业务文档的三个属性、任务节点与条目的落位，都由预处理链制定并执行——**本任务不重切 X、不重定属性**。
- **复核两项**：业务文档的三个属性是否齐备且唯一；条目的语义是否与它所属业务文档同指一个业务对象——判归属，不判内容。二者通不过 → 标 `需退回重切` → 回预处理链处置后重新进入。
- **承载量超限**，一批吞不下 → 分批进入；≤10 条/批是软限制，人类可确认放宽。
- **Y 侧的节点拆分与改 X 不是一回事**：Y 侧装不下时的拆分或横切出口动的是 Y 的节点，不回头改 X。

### 2.4 受理门槛（输入校验）

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 条目状态 = `需退回重切` | 不可处理 | 输出退回记录 → 退出 |
| 条目状态 ≠ `待处理` | 不可处理 | 输出当前状态 → 退出 |
| 同一批业务文档的主责角色不唯一 | 不可处理 | 输出角色分布 → 退出 |
| 条目类型含引擎能力功能需求 / 非功能需求 | 路由错误 | 输出类型分布 + 路由指引 → 退出 |
| 同一业务文档下条目 > 10 条 | 软限制 | 输出超限提示 → 人类确认 |
| 无待处理条目 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

### 2.5 依赖与校验（读 X 时）

- 业务文档的三个属性齐备、条目正文语义自洽：预处理链已归一化。缺标或矛盾 → 标 `[需确认]`，不自动推进。
- **同一业务文档内的一致性**：该文档下的条目必须归到同一个业务对象——归不到 → 输出退回重切提示，不自动拆。**判的是归属，不是内容**：不同相关方、不同时期提的需求各说各事，都落在这一张文档上即成立。
- 读 X 遵循 91 号规范 §A.3.3 读取协议：AI 可以处理节点优先、逐节点加载、按需扩大，不默认加载全文。

## 三、输出文档结构及规则（Y = 业务流程方案 · 方案侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程方案**——**一份文档，内含两个形态**：概要，即根→枝梢（任务节点），到结构判定级；完整态，即到叶（用例场景），含叶定义与方案内容。两态同出一次，不各自交付。

### 3.2 输出空间的两棵树（Y 树）

本任务的 Y 即业务流程，不在一条树上——**同一批业务文档在两条独立的树里各得其位**：**R 角色履职树**回答「某角色在哪个场景、按什么序、处理哪些业务文档完成闭环」，讲的是履职与工作序；**P 输出产品树**回答「这批文档作为构件产品数据，属于哪个产品/构件/WBS 包、怎么生成与流转」，讲的是产品数据与依赖。两树在**业务文档及其下两级**处对位互连、经**认亲**互指；不是一棵树的共享节点。

**树一 · R 角色履职树（业务运行角色履职视角）**

```
角色履职业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的一类职责范围
            └── E2E职责 ─ ④ 一个业务对象闭环，分执行类与管理类
                └── 业务文档 ─ ⑤ 业务运行输出的"产品"数据文档，对应本文档开发任务
                    └── 任务节点 ─ ⑥ 文档开发任务的多个步骤，枝梢节点
                        └── 用例场景 ─ ⑦ 是叶
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务域 | 归属域 | **本任务产出**；R／P 两棵树各有一份，同值、不共享节点 | 作定位与对账域 |
| ② | 相关方角色 | 主责角色，即业务对象生命周期的主推动者 | **本任务产出**，取自 X 的「所属主责角色」 | 作分片与复用宿主范围 |
| ③ | 角色职责 | 角色承担的一类职责范围 | **目标组织级**，随业务流程方案演进 | 本任务不产该节点 |
| ④ | E2E职责 | 一个业务对象闭环，分执行类或管理类 | **本任务产出**（复用 → 新建） | 本任务新建/修订单位 + 人类确认挂点：归拢条目、职责边界、收敛自查 |
| ⑤ | 业务文档 | 业务运行输出的"产品"数据文档，对应本文档开发任务 | **承 X**（X 的 ①） | 归位；补 Y 侧内容：封面模式、**分解源判据**、P 认亲 |
| ⑥ | 任务节点 | 文档开发任务的多个步骤，枝梢节点 | **承 X**（X 的 ②） | 归位到 ⑤ 之下；概要到本级为止 |
| ⑦ | 用例场景 | 是叶 | **承 X**（X 的 ③） | 归位到 ⑥ 之下；完整态到本级为止 |

> **平台侧的 R 树**：本任务的主体走**各业务域的 R 树**；平台自身的治理业务走**平台侧的 R 树**——同一棵 R 树在「平台本身」这一侧**少「角色职责」一级**：业务域 → 相关方角色 → E2E职责 → 业务文档 → 任务节点 → 用例场景，因为业务配置角色不按角色类型再归纳。层级差非遗漏。业务流程方案里预置的治理节点 bpd-biz-GOV-* 即平台侧场景，本任务对其只作渐进增补，不主动展开。

**树二 · P 输出产品树（产品开发视角）**

```
输出产品业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 产品类型 ─────── ② 部门级的端到端业务输出
        └── 产品构件类型 ─ ③ 科室级的端到端业务输出
            └── 构件开发WBS（包）─ ④ 文档序列
                └── 业务文档 ─ ⑤ 业务运行输出的"产品"数据文档，对应本文档开发任务
                    └── 任务节点 ─ ⑥ 文档开发任务的多个步骤，枝梢节点
                        └── 用例场景 ─ ⑦ 是叶
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务域 | 归属域 | **本任务产出**；R／P 两棵树各有一份，同值、不共享节点 | 认亲检索与完备对账的域边界 |
| ② | 产品类型 | 产品类别，如采购产品、实物产品 | **本任务产出**（复用 → 改进 → 新增） | 本任务按需建立或确认 |
| ③ | 产品构件类型 | 构件分类，如自研、外购、复用、项目 | **本任务产出**，同上 | 同上 |
| ④ | 构件开发WBS（包） | 一批数据依赖闭合的产品数据单元 | **本任务产出**，同上 | 同上 |
| ⑤ | 业务文档 | 业务运行输出的"产品"数据文档，对应本文档开发任务 | **承 X**（X 的 ①） | 认亲归位：R 树的文档逐一标定 P 侧归属；本体唯一——可被多场景引用、只占一个产品数据位 |
| ⑥ | 任务节点 | 文档开发任务的多个步骤，枝梢节点 | **承 X**（X 的 ②） | 归位 |
| ⑦ | 用例场景 | 是叶 | **承 X**（X 的 ③） | 归位 |

> **认亲 = 两树对位**：R 场景链里的每张业务文档，逐一识别其 P 归属，即产品类型×构件×WBS 包，归位 P 树；两树靠这层互指联通。业务流程方案是双视角，以场景为单位把 R 链序与 P 位置并成一份。
>
> **两棵树的末三级就是 X 的三级**：同一批节点，认亲依据由 X 给出——业务文档上带「所属产品构件」属性，本任务据此定位 P 侧构件归属。同一张文档因此有三个视图：X 侧的需求承载级、R 侧的文档开发任务、P 侧的产品数据位。
>
> **方案边界**：概要级到结构判定——文档是否存在、封面模式、候选引擎、任务节点；完整态补到叶定义、封面映射、正文实体结构、数据权限、引擎权威值。下游各对的展开不在本任务。
>
> **树权威**：R／P 两棵树的拓扑与各级语义以《EOS 系统设计产品数据分解结构》（94 号文档）为准；X 与 Y 两份产品数据的树画像以各自数据文件的树画像区为准。

### 3.3 节点类型与结构要点

> 方法读法：**E2E职责及其以上的各级，即枝干**，是聚合层；**任务节点 = 枝梢**，即概要的最深一级；**用例场景 = 叶**，即完整态的末级。两棵树的末三级由 X 直接给出，本任务不另造它们，只按属性归位并补 Y 侧内容——**任务节点与用例场景另按语义与业务逻辑整理成规范节点**。**本对两侧的叶是同一批**，故**不涉及映射与分配**。业务流程方案的输出文档转译到功能表单，走的是**页面视角**、不是承接，见 91 号规范 §7.3。

- **E2E职责，即枝干**：一个主责角色——业务对象生命周期的主推动者——的一个业务对象闭环，由一组有流转依赖的业务文档序列构成。类型二分类：**执行类**，从需求提出到需求满足；**管理类**，计划→监控→分析→纠正，须含计划清单文档 + 承载监控与分析环节的业务文档。
- **业务文档，即 X 的根**——业务运行结束后应输出的产品数据文档，对应本文档的开发任务，即一份要开发的业务文档；一般对应一个流程、一个工单、一个计划，或一个看板业务。**它的 Y 侧内容** = 封面模式 + 分解源判据 + P 认亲。
- **分解源判据**：任务节点声明它可分解出哪些用例场景，到名称级，各项带内联稳定标签——标签既是概要到完整态的追溯键，也是本任务到系统需求概要设计任务的追溯键。
- **两树对位，即认亲**：R 树与 P 树是两条独立树——同一份业务文档在 R 侧是场景履职链的一环，即该角色按什么序处理它；在 P 侧是某 产品类型×构件×WBS 包 的产品数据，即属哪个域的产品、怎么生成、与哪些前序文档有数据依赖。两树经**认亲**互指：本任务逐文档识别其 P 归属并归位，依据由 X 的业务文档给出；一张文档可被多个场景引用，但 P 侧产品数据位唯一。
- 业务文档按封面模式分**正式**与**轻量**：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。判据见 91 号规范 §2。
- **任务类型的启动规则**：E2E职责中第一个有任务类型的文档必然为**计划**，这是闭环启动机制。

### 3.4 Y 侧规则（组装与收敛）

- **方案边界**：概要级只做结构判定——文档是否存在、封面模式、候选引擎、任务节点的步骤；完整态补到定义要素、封面映射、正文实体结构、数据权限、引擎权威值。**Y 侧不重写 X 给的条目前三层**，只在其上长干枝、补方案内容。
- **E2E职责构建规则**，用于新建：识别触发 → 追踪自然终点，不得在终点之后扩展 → 闭合验证 → 边界四标准，即完整性、一致性、紧凑性、粒度匹配，产出场景职责边界陈述。
- **文档序列构建规则**：执行类按输入-输出传递链排列；管理类按计划→监控→分析循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有枝干，才上溯建更高层。

### 3.5 要素清单（本任务写入方案节点必须带齐）

写入业务流程方案节点，字段对齐业务流程方案数据文件 §4.1 的模板、逐字同名：

- **块头字段**：块ID / 节点类型 bpd-biz / 类型 执行类或管理类 / 主责角色 / 当前状态。
- **正文要素行**，依次为：
  - 业务域 / 产品路径；用户角色；场景职责边界陈述；
  - **承接的条目引用**——X 的用例场景条目引用，N:1 汇聚，**跨批追加不覆盖**，作覆盖与追溯锚点；治理预置节点按治理覆盖口径；
  - **R 场景装配**——R 树干枝，含业务域、相关方角色、角色职责、E2E职责；加文档序列，即该角色按什么序处理哪张文档；
  - **业务文档方案**，每张业务文档一段：封面映射、即正式或轻量；正文实体结构；支撑引擎**校验权威值**；数据权限；**P 认亲**，即所属 产品类型×构件×WBS 包 + 层级判定档位；
  - **任务与叶**，每张业务文档之下：任务节点的步骤，含处理角色、动作、状态变迁；用例场景；均到名称级并带内联稳定标签；
  - **P 组装结论**——WBS 归组 + P 树一致性结论 + 缺口推断与候选节点建议；
  - 推理依据与补全说明；完备性检查结果；补充材料引用；变更影响声明 / 版本号。

### 3.6 传出承诺（给系统需求概要设计任务）

本任务把方案节点交给下游时，承诺节点达到：

1. 状态 = `可以srh设计`，在人类「整体确认」之后；
2. 要素清单齐备；
3. **每张业务文档带任务节点的步骤与用例场景**，到名称级并带内联稳定标签；并带 **P 认亲**，即所属 产品类型×构件×WBS 包 + 层级判定档位；
4. 覆盖检查结果已落账于节点——**节点累计承接的**全部需求语义 ⊆ 其业务链所能实现的范围；缺口已走补充材料回路，不是隐藏遗漏。

> **接口契约，与系统需求概要设计任务的受理前提互为对侧**：下游受理本任务传出的业务流程方案节点，状态为 `可以srh设计` 或 `待补充srh设计`；它以要素清单与传出承诺为对照——要素缺失、冲突 → 退回 `需biz01修订` + 缺失说明。契约的对侧成文于[系统需求概要设计任务的指南](eos-biz03-bpd2srh.md) 第二章；核对方法 = 93 号规范 §4.2 的逐条映射。

## 四、输出与输入转换规则

### 4.1 归拢与长枝规则（X 已给末三级，本任务长干枝）

- **归拢由属性定**：每张业务文档落进哪一支，由它身上带的属性决定——「所属主责角色」定它走哪条 R 树分片，「所属E2E职责」定它落在 R 树的哪个场景，「所属产品构件」定它的 P 侧构件归属。三个属性齐备且唯一，是本任务唯一的归拢依据。
- **文档整体分流**：它对应的 E2E职责与 WBS 包已在 Y 中存在 → **复用**，走修订转换；尚无 → **新建**。优先级始终 复用 → 改进 → 新增。
- **语义跨界**：同一张业务文档下的条目指向不同业务对象 → 属 X 的缺陷，标 `需退回重切` 回预处理链，不在 Y 侧就地分。
- **Y 侧装不下时**：节点拆分，或横切式承接走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有枝干做扩展/拆分/合并后，须复查其下已归位的文档是否失配 → 批量重归位或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则与判据出处 |
|--------|--------------------|
| 业务域与角色 | 读业务文档的「所属主责角色」→ 定 R 树的域与角色 |
| E2E职责类型 | 需求动作词偏向执行类/管理类；存疑标 `[推断]` |
| 产品类型路径 | 读业务文档的「所属产品构件」→ 定它在 P 树里的产品类型／构件类型／WBS 包路径；缺则 `[推断]` |
| 文档清单 | **以 X 的业务文档为准**——本任务不另立清单；覆盖检查发现应有而未列者 → 走补充材料回路 |
| P 认亲 | 读业务文档的「所属产品构件」属性 → 定位 P 侧构件归属；层级不全时走三档判定 |
| 封面模式 | 是否需审批/发布/版本追溯等生效动作 |
| 任务类型 | 读任务节点直接捕获；只给出管理模式→判定+`[推断]`；任务节点缺失→推断+`[推断]`；首个有任务类型的文档必为计划 |
| 支撑引擎 | 按正文数据类型匹配平台引擎，**全量 `[推断]`** |
| 引擎能力对照 | 用例场景逐一对照**平台引擎**的能力清单；接不住的操作 → 记 `[引擎缺口]`，走引擎类补充原始需求 |
| 用例场景 | 取 X 的条目原文，不另拟名 |
| 文档间关系 | 流转顺序，执行类走传递链、管理类走循环；加需求明示的任务触发关系 |

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回需求侧／宿主误匹配 → 业务链关系检测，分 确认／无新增／引擎判定变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查 → P 组装重跑。

### 4.4 层级构建与缺口规则

**P 树三级，即产品类型／产品构件类型／构件开发WBS 的建立**：逐文档判定它在 P 树里的位置，分三档——**已有、直接引用**，**需扩展**，**无、给新建建议**；再执行 WBS 归组，判据是数据依赖链；加 P 树自身一致性检查，查 归属冲突／误新建／误引用；再加按 P 树已有的产品数据类型做名称级缺口推断，不依赖任务类型或引擎。

**缺口的两条通道，都通向补充原始需求**：

- **业务类**——本批涉及的 WBS 包对照闭合模型检查，应有而缺失的产品数据 → 以**候选节点**挂 P 树、标疑似态；候选只是建议，不直成正式文档。
- **引擎类**——用例场景逐一对照**平台引擎**的能力清单，接不住的那些操作 → 记 `[引擎缺口]`；它指向的是引擎能力，不是业务数据，故不走 P 树。

两条通道都生成**补充原始需求材料**，回需求预处理链——业务类经它加工成业务功能需求条目、归业务路径，引擎类加工成引擎能力功能需求条目、归引擎路径。人类裁决「需要」→ 落地；「不要」→ 候选废弃。**本任务不脑补节点，也不代引擎设计**。

判据之家 = 91 号规范 §5.3.1。

#### 5.1.1 Step 1 · 设计材料加载

读 `待处理` 业务功能需求条目 + 同一业务文档／同域候选存量方案节点；加载按读取协议。

#### 5.1.2 Step 2 · 反馈处理

人类对话修改／整体确认／线下修订；反馈双轨按 91 号规范 §A.5 记录。

#### 5.1.3 Step 3 · 组装 R 树

针对一批属性相近的业务文档：

- 归拢 → 复用，归已有E2E职责；或新建，进待聚合池；
- 长 R 树干枝：业务域、相关方角色、角色职责 承袭或不产；**E2E职责本任务产出**——判执行类或管理类、命名、定边界，边界即主责角色的业务对象闭环，产出场景职责边界陈述；
- 归位业务文档、任务节点、用例场景，补业务文档的 Y 侧内容——封面模式，并写**分解源判据**；
- 写履职序：该角色按什么序处理这些文档，加需求明示的任务触发关系；
- 有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.4 Step 4 · 组装 P 树

对同一批业务文档：

- 长 P 树干枝：产品类型、产品构件类型、构件开发WBS（包），走三档判定——已有直接引用／需扩展／无则给新建建议；
- **P 认亲**：逐文档按「所属产品构件」标定 P 侧归属并归位，本体唯一；
- **WBS 归组**，判据是数据依赖链；再做 P 树一致性三类检查——归属冲突／误新建／误引用；
- 产出 **P 组装结论**；
- **影响面复查**：对已有干枝做扩展/拆分/合并后，复查其下已归位的文档是否失配；有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.5 Step 5 · 补充业务类原始需求

执行关口检查，其中 **端到端闭合** 是本需求-方案对的关口——执行类从需求提出贯通到需求满足；管理类按计划→监控→分析→纠正核对。再以 P 树做缺口推断：本批涉及的 WBS 包对照闭合模型，应有而缺失的产品数据以**候选节点**挂 P 树、标疑似态。

缺口生成**业务类补充原始需求材料**交需求预处理链，加工成业务功能需求条目归业务路径。候选去留由**人类裁决**：「需要」转正式条目落地，「不要」废弃。**不脑补节点。**

#### 5.1.6 Step 6 · 补充引擎类原始需求

用例场景逐一对照平台引擎的能力清单，接不住的操作记 `[引擎缺口]`——它指向的是引擎能力、不是业务数据，故不走 P 树。

缺口生成**引擎类补充原始需求材料**交需求预处理链，加工成引擎能力功能需求条目归引擎路径。候选去留同样由**人类裁决**。

#### 5.1.7 Step 7 · 写回与落账

业务流程方案落账 + 状态推进 + 基线，引 91 号规范 §A.3.3 与 §A.6。

### 5.2 检验规则（关口）

- **属性齐备检查**：每张业务文档的三个属性齐备且唯一——这是本任务唯一的归拢依据，缺一个就落不了位。
- **覆盖检查**，这是本需求-方案对的关口：**节点累计承接的**全部需求语义 ⊆ 其业务链即枝梢之并能实现的范围。同一张业务文档的需求分多批到来，故检查范围累计——每批检新增部分；本批改动了已有枝干，另按影响面复查其下已归位部分。EOS 实例化 = **端到端闭合检查**——执行类从需求提出贯通到需求满足；管理类按计划→监控→分析→纠正核对，须含计划清单文档 + 承载监控与分析环节的业务文档，这两环节的运行时推进结果不作需求缺口。缺口 → 分业务类与引擎类两条通道生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐文档要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待下游推断]`。
- **治理覆盖检查**：预置治理业务流程方案业务链按角色预定文档集核对；无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以srh设计 ──下游锁定──→ 在srh设计 ──下游完成──→ 已srh设计
     ↑                       ↑                      │
     │                       │          下游退回     │
     └── 本任务修订 ──── 需biz01修订 ←───────────────┘
```

上游变更，即新需求汇入，按状态分流：`可以srh设计`→版本递增，未消费；`在srh设计`→版本递增，增量处理；`已srh设计`→`待补充srh设计`→下游补全。四态模型与写回范围引 91 号规范 §A.6，此处为本任务特化。

### 5.4 运行时特化参数

- **锚点需求** = 节点累计承接的全部业务功能需求条目，跨批追加
- **操作条目** = 场景职责边界 + 干枝 + 业务文档方案段 + 分解源判据展开项 + P 组装结论 + 补充原始需求材料候选
- **推进目标** = `可以srh设计`
- **退回节点状态值** = `需biz01修订`，退回修订走修订转换
- **清除与级联条件**由状态机与上游分流定
- 其余运行时机制——Step Start／Step End、入口条件与优先级、反馈双轨状态机、git 基线、Step End 三区模板——按 91 号规范 附录A 执行；本任务的受理门槛已就地成文

## 六、关联产品数据及规则（接口）

**R 树与 P 树本身就是资产**——本任务不另读资产文档，除 X 之外没有外部输入。本节记本任务读什么、写什么。

### 6.1 读

| 产品数据 | 读什么 | 用途 |
|---------|--------|------|
| 相关方需求（X） | 业务文档 → 任务节点 → 用例场景，及业务文档上的三个属性 | 本任务的唯一外部输入 |
| 平台引擎 | 引擎能力清单 | 引擎能力对照 |

> 治理节点的预定文档集不由外部给出，由人类按平台治理业务增补。

### 6.2 写

本任务只写 **Y = 业务流程方案**——两棵树即资产，写在 Y 里，不另立一册。写回动作与状态推进引 91 号规范 §A.6。

### 6.3 判定动作

层级三档判定，即引用／扩展／新建；WBS 归组硬判据，即数据依赖链 + 完成耦合；P 树一致性三类，即归属冲突／误新建／误引用；缺口推断，即按 P 树已有的产品数据类型做名称级比对。动作规则已就地成文。

## 七、收尾

### 7.1 AI 标记约定

`[新增]`/`[变更]`/`[确认]`/`[需裁决]` + `[推断]`/`[待下游推断]`/`供人类确认`——标记的定义与使用、三区输出格式见 91 号规范 §A.3.1／§A.3.2；本任务增量清单对操作条目逐条标注；并附 P 组装段与覆盖检查结果行。

### 7.2 自检清单

本任务自检——一次运行收尾前，按本任务流程分组逐项核对：

- **入口/受理**：受理门槛已校验通过；退回优先，`需biz01修订` 时读缺失说明走修订转换；无待处理已退出。
- **载入与校验**：待处理业务功能需求 + 同一业务文档／域存量方案节点已按 91 号规范 §A.3.3 加载、不全载全文；条目正文与业务文档的三个属性自洽。
- **组装**：R 树与 P 树分步组装，归拢走复用还是新建判定正确；修订转换的边界匹配／关系检测／变更影响声明已执行；业务文档、任务节点、用例场景已按属性归位；两棵树各自收敛，判据是覆盖完整 + 兄弟互斥。
- **Y 侧要素**：每张业务文档齐封面模式；加分解源判据展开项，带内联稳定标签；加支撑引擎候选 `[推断]`、任务关系；要素非空或合理空置。
- **关口**：属性齐备检查与覆盖检查已执行，后者检的是节点累计承接的全部需求语义；缺口分业务类与引擎类两条通道产出补充原始需求材料交预处理链，候选去留有人类裁决，**不脑补节点**；治理覆盖已核对。
- **写回**：两棵树写进业务流程方案，`[归属冲突]` 项暂不落定、待人类裁决；加状态推进 `可以srh设计`、AI 最近变更/可处理节点分节维护、基线提交。
