### 2.1 配置页面 SR-F

**一句话**：本节讲配置页面 SR-F 的概念——定义与分类（2.1.1）、架构与属性（2.1.2）；完备性判据见 §三 3.4。

#### 2.1.1 定义与分类

配置页面是配置、治理或运行支撑人员直接使用的页面单元，用来维护 CU 配置、触发引擎处理、查看发布/运行结果或处理异常。它**不同于** biz 路径面向业务角色的功能表单和窗口标签页。

配置页面按职责分为五类（由 AI 根据 CU 配置能力要素判定）：

| 页面类别 | 用途 | 典型来源 |
|----------|------|----------|
| 配置维护页 | 维护 CU 配置要素 | 配置入口、配置过程说明 |
| 配置管理页 | 管理配置版本、状态、引用关系 | 系统处理、治理依赖 |
| 发布生效页 | 校验、发布、装载、回滚、停用 | 系统处理 |
| 运行支撑页 | 查看运行期能力、刷新、重试、处理异常 | 业务人员操作过程 |
| 治理追溯页 | 审计、影响范围、引用关系、操作日志 | 横切治理依赖 |

> 布局组件与构件的详细定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)，eng 路径分工见 [91 规范 §8.3](91-eos-biz-eng-spec.md#83-系统需求开发wft03-eng)。

#### 2.1.2 架构与属性

配置页面设计涉及三个**相互独立**的维度，不能互相替代：

| 维度 | 来源 | 回答的问题 | 进入 SR-F 的字段 |
|------|------|------------|------------------|
| 页面类型 | 91 规范 §1.2 | 是否属于硬代码开发的配置页面？ | `页面类型=配置页面` |
| 页面类别 | 91 规范 §8.3 | 承担哪种配置职责？ | `页面类别` |
| 布局组件 | 91 规范 §四 | 内部由哪些布局组件承载内容和交互？ | `布局组件清单` |

> 页面类别和布局组件的判定规则见 §3.2，页面功能架构见 §2.3.1，操作活动定义见 §2.3.2。

**SR-F 节点完整要素**（写入 `05-*.md` SR-F 节点块）：

- 页面 ID / 名称 / 页面类型（固定为配置页面）/ 页面类别 / 使用角色（来源 BP A2 上下文）
- 来源 BP / 来源 CU / 配置信息组业务过程引用
- 页面职责 · 布局组件与构件线索 · 页面字段或配置对象摘要
- 页面操作活动清单 · 权限、状态、版本、发布约束
- PA 层收敛项 · 确认状态

### 2.2 页面类型、页面类别与布局组件

#### 2.2.1 定义与正交关系

**页面类型**：本 Skill 的末级节点固定为**配置页面**。配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页是**页面类别**（职责分类），不是新的页面类型。

**布局组件**：多级横版、列表、树表、单据、辅助栏、弹窗、指标页面、看板页面通过布局组件组合表达，替代旧"六种页面形态"。

每个 SR-F 必须同时写明：**`页面类型=配置页面`** + **页面类别** + **布局组件清单**。

**布局组件可选范围**：

| 布局组件 | 典型用途 |
|----------|----------|
| 多级横版 | 多层级配置对象、主从配置、流程/规则设计器 |
| 列表页面 | 配置对象集合、发布记录、版本记录、执行记录 |
| 单据页 | 单个配置对象编辑、参数维护、规则详情 |
| 辅助栏 | 详情预览、上下文摘要、引用关系、校验结果 |
| 弹窗页 | 选择、确认、局部参数编辑、冲突处理 |
| 指标页面 | 运行状态、质量指标、发布影响、异常趋势 |
| 看板页面 | 运行看板、任务看板、发布状态、异常汇总 |

**构件完整性分类**（四类须分别检查；无需求时写明"不适用"，不得只列按钮类构件）：

| 类别 | 典型构件 |
|------|----------|
| 展示类 | 列定义、字段布局、图表类型、卡片、树节点、阶段/里程碑 |
| 交互类 | 功能按钮、右键菜单、快捷键、下钻、行选中、TAB 切换 |
| 数据类 | 筛选器、排序器、分页器、导入、导出 |
| 反馈类 | 通知提示、进度条、状态标签、校验提示 |

### 2.3 页面功能架构与操作活动

#### 2.3.1 页面功能架构

页面功能架构回答：一个 CU 或一组强依赖 CU 的配置页面如何组合使用。**它组织的正是 CU 的业务过程——CU 业务过程是其所有配置信息组业务过程的集成，页面功能架构把该集成业务过程编排为页面层的组合方式**。

**要素**：
- 配置页面清单与布局组件
- TAB 顺序或导航关系 · 主子页面关系
- 页面间跳转和上下文传递
- 权限、状态、版本和发布依赖
- 与来源 CU、配置信息组业务过程的对应关系

#### 2.3.2 操作活动定义

操作活动是用户在配置页面上执行的可验证动作，**承接自配置信息组业务过程**。每个操作活动的规范必填项为：**触发方式、操作对象、结果反馈**。以下字段用于补充业务语义，不得写成 PA 实现设计：

| 字段 | 说明 |
|------|------|
| 活动名称 | 如新建配置、校验配置、发布配置 |
| 操作入口 | 按钮、右键、快捷键、双击、自动触发 |
| 所属页面 / 构件 | 页面 ID 和入口构件 |
| 前置条件 | 状态、权限、版本、依赖 |
| 用户动作 | 用户做什么（点击、填写、选择等） |
| 系统处理摘要 | 系统校验、保存、发布、装载、记录等——**承接 wft02-eng 定义的配置信息组系统处理，标注承接引用，不重新描述业务过程** |
| 结果状态 | 页面状态、配置状态或运行期状态 |
| 校验规则 | 必填、唯一、依赖、权限、冲突等 |
| 异常处理 | 失败提示、回滚、重试、人工处理 |
| PA 层待处理线索 | 仅记录待 wft05-eng 判断的问题，不给组件/接口/存储实现结论 |

操作活动承接配置信息组业务过程（三类对应）：

| 操作活动类型 | 承接的组业务过程 | 典型动作 | 适用页面类别 |
|----------|------------------|----------|-------------|
| 配置维护 | 配置过程说明 | 新建、编辑、复制、删除、导入、导出 | 配置维护页 |
| 校验处理 | 系统处理（校验） | 校验、预览、冲突检查、依赖检查 | 配置维护/管理页 |
| 发布生效 | 系统处理（发布/装载） | 保存、提交、发布、装载、回滚、停用 | 发布生效页 |
| 运行支撑 | 业务人员操作过程 | 查看生效结果、刷新缓存、重试、异常处理 | 运行支撑页 |
| 治理追溯 | 系统处理（审计） | 查看版本、审计、引用关系、影响范围 | 治理追溯页 |

#### 2.3.3 PA 层收敛项

**PA 层收敛项是本 Skill 在 SR-F 中标注的「待 PA 设计判断的问题线索」——PA 本身（前后端组件）由 wft05-eng 设计**。本 Skill **不设计组件**，只把需要 wft05 判断的问题传递过去；不得预选同步/异步、存储归属或实现机制。

| 收敛项 | 示例 | 标注 |
|--------|------|------|
| 组件边界 | 发布按钮构件是否复用公共构件 | `PA层收敛-组件边界` |
| 接口问题 | 发布动作是否存在跨组件交互待判定 | `PA层待处理-接口` |
| 数据问题 | 配置版本、发布记录、审计记录需要持久化能力 | `PA层待处理-数据` |
| 运行问题 | 装载、缓存刷新、回滚、重试等需要下游确定机制 | `PA层待处理-运行` |
| NFR 问题 | 关联的 NFR 约束由 wft05-eng 消费约束包后决策 | `PA层待处理-NFR` |

> **载件是 PA 收敛项的主要来源**：wft02-eng 详设的配置信息组"系统处理·生效后响应"生成的载件（数据/配置/界面/构件/实例/支撑载件），由 wft05-eng 判断如何由前后端组件承接——前端组件承接配置展示/交互，后端组件承接配置处理与业务逻辑。本 Skill 只标注问题线索，不设计载件的实现。

## 三、设计原理与判据：为什么这样设计、怎么判定

**一句话**：本章讲页面设计的逻辑——为什么用配置页面承接 CU 配置能力（3.1 转换原理）、怎么提取页面要素（3.2）、怎么承接操作活动（3.3）、怎么判完备（3.4）；概念见 §二，节点演进见 §四，操作步骤见 §五。

### 3.1 转换原理：为什么用配置页面承接 CU 配置能力

**CU 配置能力描述"这个配置单元配置什么、系统怎么处理、运行期产出什么"，SR-F 回答"为支撑这些，需要哪些配置页面、每页用什么布局组件/构件承载、页面上有哪些可执行活动"**。wft02-eng 详设的配置信息组业务过程是页面内容的承接锚——本 Skill 承接该业务过程，组织为页面形态的系统需求（配置页面 SR-F），供 wft05-eng 设计 PA（前后端组件）。承接单位 = 配置页面（末级节点），布局组件与构件是其细分节点。

**配置信息组是 eng 链的末级节点，三级设计分工各司其职**。wft01-eng 概要设计锚定配置信息组结构并给出概要性说明（配置什么、运行期提供什么）；wft02-eng 承接后展开三段式业务过程定义（配置过程说明 / 系统处理及生成的载件 / 业务人员在业务实例上的操作过程）；本 Skill 承接 wft02 详设后的组业务过程映射为配置页面内容。**CU 业务过程 = 其所有配置信息组业务过程的集成**——页面以 CU 为边界，页面功能架构组织的正是该集成业务过程（若按组分页，集成关系就碎了）。

**操作活动是承接，不是再定义业务**。本 Skill 把配置信息组业务过程挂载为页面操作活动——配置过程说明 → 配置维护活动、系统处理及载件 → 校验/发布生效活动、业务人员操作过程 → 运行支撑活动。操作活动的「系统处理摘要」承接 wft02 定义的组系统处理，标注承接引用，不重新描述业务过程。**发现组业务过程不足（三段式缺段）→ 退回 `需wft02修订`；发现组结构/概要缺陷 → 经 wft02 退回 `需wft01修订`**，不脑补。

**PA 是 wft05-eng 的设计产出，本 Skill 只标注问题线索**。PA = wft05-eng 设计的前后端组件（前端承接配置展示/交互，后端承接配置处理与业务逻辑）。本 Skill 在 SR-F 中标注 PA 层收敛项（组件边界/接口/数据/运行机制/NFR 的待判断问题），作为 wft05 设计 PA 的输入，不设计任何组件。

**推断不是转录，也不越权设计**。本 Skill 不只复述配置信息组业务过程，还要在页面上下文推断页面形态（页面类别/布局组件组合）、识别构件；但页面推断必须有配置能力依据——CU 未承载但页面必需的，标注依据不足退回上游，不静默补判。页面组件类型及组合属页面需求本身（对齐 91 规范 §4.4），仅布局组件/构件无法承载才走缺口。

**这套原理方法为什么可行**：它以**可验证性**为锚——页面以 CU 为边界（页面单位）承接集成业务过程，每个页面可被 wft05-eng 承接为组件、追溯链（页面→配置信息组→CU→BP→STR-E→OR）完整、变更可传播；权威归信息最全的一方且只归其信息全的部分（业务过程定义在 wft02、页面设计在本 Skill、组件设计在 wft05）；判据全部可机械判定，操作全部有明确输入输出与执行模式（§5 Step 布局表），原理→判据→操作三层一一咬合，且与 91 规范、biz 路径同一套协议运转。

### 3.2 要素提取规则

**一句话**：本节讲从 BP 提取页面要素的规则——页面候选生成（3.2.1）、页面类别与布局组合判定（3.2.2）、布局组件判定（3.2.3）、宿主匹配检查（3.2.4）。Phase B（修订已有 SR-F）与 Phase C（新建 SR-F）共用以下规则——先看 3.2.5 的 B/C 分工差异表，再读细节更顺。

#### 3.2.1 页面候选生成

对每个非占位 CU，按配置能力要素生成页面候选（页面以 CU 为边界，内容以配置信息组业务过程为线索）：

| CU 配置能力要素 | 页面/活动映射 |
|----------------|---------------|
| 配置入口 | 配置维护页、配置列表、配置详情、选择弹窗 |
| 配置过程说明（组级） | 字段/规则编辑区、关系维护区、辅助栏详情、选择器 |
| 系统处理（组级） | 校验、保存、发布、装载、回滚、停用、异常处理活动，以及执行记录页 |
| 运行期能力（组级） | 能力预览页、运行支撑页、结果查看页、异常处理页；业务运行页面本体仍由 biz 路径承接 |

候选覆盖五类：配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页。

#### 3.2.2 页面类别与布局组合判定

**页面类型**固定为`配置页面`。先按配置职责确定页面类别，再按内容与交互选择布局组件组合：

| 判定条件 | 页面类别 | 候选布局组件组合 |
|----------|----------|------------------|
| 多条配置对象或版本记录维护 | 配置维护/管理页 | 多级横版 + 列表页面 + 辅助栏（可选） |
| 层级对象维护 | 配置维护页 | 多级横版 + 列表页面（树表）+ 辅助栏（可选） |
| 单个配置对象编辑 | 配置维护页 | 多级横版 + 单据页 + 辅助栏（可选） |
| 主配置与子规则强相关 | 配置维护/管理页 | 多级横版（双窗）+ 列表页面/单据页 + 辅助栏（可选） |
| 发布、装载、回滚或运行状态处理 | 发布生效/运行支撑页 | 列表/指标/看板页面 + 单据页/弹窗页（按需） |
| 审计、引用关系或影响范围追溯 | 治理追溯页 | 列表/指标页面 + 辅助栏（可选） |
| 临时选择、确认、局部参数或冲突处理 | 从属父页面类别 | 弹窗页 |

#### 3.2.3 布局组件判定

在页面类别判定之后，独立判断页面内部需要哪些布局组件：

| 判定条件 | 布局组件 |
|----------|----------|
| 需要展示对象集合、版本记录或执行记录 | 列表页面 |
| 需要编辑单个配置对象或参数组 | 单据页 |
| 需要并列展示多层主从对象 | 多级横版 |
| 需要上下文、详情、校验结果或引用关系 | 辅助栏 |
| 需要临时选择、确认、局部参数或冲突处理 | 弹窗页 |
| 需要展示运行指标、发布影响或异常趋势 | 指标页面 |
| 需要展示运行状态概览、任务分布或发布汇总 | 看板页面 |

#### 3.2.4 宿主匹配检查

按 `引擎 + CU + 页面类别 + 页面职责` 匹配已有配置页面：

| 结果 | 判定 | 动作 |
|------|------|------|
| 复用 | 页面类别、布局组合和页面职责匹配 | 追加 BP/CU 来源，标记 `[确认]` |
| 扩展 | 页面类别和职责一致，但布局组合、操作活动或 PA 收敛项扩展 | 全量重写该页面 SR-F，保留历史引用，输出变更声明 |
| 新建 | 无可匹配的配置页面 | 新建配置页面 SR-F |
| 冲突 | 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

#### 3.2.5 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B（修订） | Phase C（新建） |
|------|----------------|-----------------|
| 判定范围 | SR-F 已承接全部 BP/CU + 本轮新 BP/CU | 待聚合池本组 BP/CU |
| 页面清单基线 | 已有清单为基线，仅扫描新 CU 是否引入新页面 | 从零构建 |
| 页面候选 | 增量生成（仅新 CU 触发） | 全量生成（§3.2.1） |
| 宿主匹配 | 执行匹配检查（§3.2.4），可能检出复用/扩展/新建/冲突 | 无需匹配，直接新建 |
| 操作活动 | 基线基础上增量合并（关系检测见 §3.3.3） | 全量承接 |
| 变更传播 | 输出变更影响声明（§4.2） | 写"首版，无变更" |

### 3.3 操作活动承接与推断规则

**一句话**：本节讲操作活动承接的规则——操作活动类型与字段（3.3.1）、PA 层收敛项标注（3.3.2）、Phase B 配置页面关系检测（3.3.3）。Phase B（修订已有 SR-F）与 Phase C（新建 SR-F）共用以下规则。

#### 3.3.1 操作活动类型与字段

对每个配置页面的操作活动，按 §2.3.2 的五类活动类型和十个字段逐项填写。活动类型由页面类别和 CU 配置能力要素共同决定，操作活动承接配置信息组业务过程（承接映射见 §2.4.2）：

| 页面类别 | 主导活动类型 | 辅助活动类型 |
|----------|-------------|-------------|
| 配置维护页 | 配置维护 | 校验处理 |
| 配置管理页 | 配置维护 | 治理追溯 |
| 发布生效页 | 发布生效 | 校验处理、运行支撑 |
| 运行支撑页 | 运行支撑 | 治理追溯 |
| 治理追溯页 | 治理追溯 | — |

每个操作活动写入：活动名称、入口构件、所属页面、前置条件、用户动作、系统处理摘要（承接组系统处理，标注承接引用）、结果状态、校验规则、异常处理、PA 层收敛项（§2.3.3）。

#### 3.3.2 PA 层收敛项标注

为每个活动检查是否存在待下游裁决的事项，存在则写入 `PA层收敛-*` 标记（五类定义见 §2.3.3）。载件（wft02 详设的配置信息组系统处理产物）是 PA 收敛项的主要来源——供 wft05 判断由前后端组件承接，本 Skill 只标注不设计。

#### 3.3.3 Phase B 配置页面关系检测

宿主匹配通过后，将本轮生成的页面与 SR-F 已有清单比对。比对锚点为**页面类别 + 布局组件组合 + 页面职责匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 页面匹配 + 类别/布局一致 + 来源升级（新 CU→已有页面） | 追加 BP/CU 来源 |
| 无新增 | 页面匹配 + 类别/布局一致 + 所有来源已确认 | 增量合并新 CU 的细节（如有） |
| 页面职责扩展 | 页面匹配 + 类别一致 + 操作活动/PA 收敛项边界扩展 | 全量重写，保留历史引用 |
| 布局组合变更 | 页面匹配 + **布局组件组合不同**（CU 配置能力变化导致） | 更新布局组合 + 重判构件 |
| 补充 | 页面不匹配 | 新增配置页面 SR-F |
| 过时 | 基线已有页面**未被**本轮 CU 覆盖 | 保留在清单中，标注`过时`，由人类裁决移除 |

> 关系检测前先基于**全部 CU** 重新判定页面类别与布局组件组合——新 CU 可能改变页面职责或布局需求（如 `布局组合变更`）。`[调整]` 是与关系类型正交的叠加标记，用于页面职责/操作活动/PA 收敛项有变化时。

## 四、SR-F 节点演进：生命周期与变更传播

**一句话**：本章讲 SR-F 节点设计与确认后的演进机制——生命周期（4.1，节点状态四态主线 + 上游变更分流 + 本 Skill 写回范围）与变更传播（4.2，修订后写变更影响声明告诉下游 wft05-eng）。

### 4.1 SR-F 节点生命周期

SR-F 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转。状态名映射按 §A.6 通用六态自声明（见下方主线流转与写回范围）。并行推进规则（SR 线与 PA 线互不阻塞）同 §A.6。

**主线流转**（wft03-eng ↔ wft05-eng）：

```
待确认方案 ──人类确认──→ 待产品架构 ──wft05锁定──→ 在PA设计 ──wft05完成──→ 已产品架构
     ↑                        ↑                         │
     │                        │               wft05退回  │
     │                        │                         ↓
     └─── wft03修订 ────── 需wft03修订 ←───────────────┘
```

**上游变更**（新 BP/CU 汇入触发 SR-F 修订）：

```
待产品架构 ──新BP/CU修订──→ 待产品架构（版本递增，wft05 未消费）
在PA设计   ──新BP/CU修订──→ 在PA设计（版本递增，wft05 增量处理）
已产品架构 ──新BP/CU修订──→ 待补充PA设计 ──wft05补全──→ 已产品架构
```

**本 Skill 写回范围**：`待确认方案` / `待产品架构` / `待补充PA设计` / `需wft03修订`。`在PA设计` 和 `已产品架构` 由 wft05-eng 推进。

**下游退回处理**：读取 wft05-eng 缺失说明 → 按人类改进方案修订（走 Phase B）→ 人类确认 → SR-F → `待产品架构`。根因在 BP 时退回 wft02-eng。

## 五、操作流程

**一句话**：一次运行 = Step Start 入口路由 → Step 1 材料加载 → Step 2 反馈处理 → Step 3 配置页面设计 → Step 4 功能架构与操作活动 → Step 5 覆盖自查与变更声明 → Step 6 资产写回 → Step End 输出与对话反馈。反馈走自然语言对话（§5.3），跨轮余留由 AI 标记持久化。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、输入校验、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |
| 1 | 设计材料加载 | 安全复查 + 读 AI 可以处理节点 + 加载 BP/SR-F/资产 | 无（AI 自动） | 统一 | BP / SR-F / 资产全景 | — |
| 2 | 方案反馈处理 | 读"待反馈处理"分节 + 对话处理人类修改意见 | **有**——对话反馈修改意见 / 整体确认 | 对话 | 调整后的 SR-F | `05` |
| 3 | 配置页面设计 | Phase A 路由 / B 修订 / C 新建 + 页面类别/布局组件判定 | **有**——设计决策审核（页面类别/布局组件/页面职责），对话反馈 | 统一（AI 产出带判据理由）+ 对话 | 页面清单 + 类别 + 布局组件 + 页面职责 | `05` |
| 4 | 功能架构与操作活动 | 页面功能架构 + 操作活动承接 + PA 收敛项 | **有**——设计决策审核（功能架构/操作活动承接/PA 收敛项），对话反馈 | 统一（AI 产出带判据理由）+ 对话 | 页面功能架构 + 操作活动 + PA 收敛项 | `05` |

| Step End | 运行结束输出 | 三区摘要输出 + 等待人类反馈 | **有**——查看摘要、对话反馈 | 对话 | 人类下一步操作提示 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 输出后需要你说句话（反馈或确认）才继续。Step 1/5/6 为运行内自动步骤——其中 **Step 3/4 是设计步骤（人机协同交互密度最高处）**：AI 承接配置信息组业务过程，基于对配置需求与已有资产的语义理解产出页面方案并附判据理由，人类在 Step End/Step 2 对页面设计决策（页面类别/布局组件/操作活动承接/PA 收敛项）审核、思考、决策、反馈，AI 落实；Step 2 / Step End 为人机交互步骤（对话反馈，见 §5.3）。

**反馈机制一句话**：反馈走**自然语言对话**（AI 产出方案后不结束对话，§5.3）；跨轮余留反馈由 AI 标 `[修改]`/`[驳回]` 入"待反馈处理"分节（§5.3 状态机）；人类线下修订经 Step Start 变更感知（git diff，§5.1 变更感知）检出后纳入"待反馈处理"分节；AI 每轮写回提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

### 5.1 Step Start · 前置校验与路由

> 入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。

**变更感知（检出人类线下修订，先于入口判定）**

读取目标文件前先检测自上次 AI 运行以来人类是否修改过文件（[§11.10](91-eos-biz-eng-spec.md#1110-ai-反馈检测规则)）：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入入口判定
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 纳入待反馈；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

> 变更感知必须先于入口判定——人类纯线下修订（不选新 BP）时，只有 git diff 能发现该反馈并将其纳入"待反馈处理"分节，入口判定②才命中。若入口判定先于变更感知，纯线下修订会被误判"无待处理对象"退出。

#### 5.1.1 入口检测

读取产品数据中的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口：

| # | 条件 | 检测方式 |
|---|------|---------|
| ① | **有新输入** | 「待 wft03-eng 处理」分节非空 |
| ② | **有待处理反馈** | 「待反馈处理」分节含本 Skill 产出节点 |
| ③ | **有下游退回** | 「待下游退回处理」分节含 `需wft03修订` 的节点 |

三类均不满足 → 输出"无待处理对象" → **退出**。

**退回门禁**（条件③时）：退回节点缺失说明中是否含人类改进方案（`[修改]`/`[同意]` 或下游 Skill 的具体指引）。已提供 → 通过。未提供 → 输出缺失说明，提示提供改进方案 → **退出**。

#### 5.1.2 输入校验

入口检测通过后进行校验。逻辑上不可能的条件为**硬退出**，数量/归属模糊条件为**软提示**：

> **消费前提（出口闸门再验证）**：BP 推进为 `可以SR设计` 前已通过 wft02-eng 出口闸门（[wft02-eng §3.4](eos-wft02-eng-str2bp.md#34-完备性判据)——运行期制品/构件/功能、指标和配置入口足以推断配置页面）。此处输入校验对该判据做再验证，配置信息组业务过程定义须含配置入口、配置过程说明、系统处理及载件、业务人员操作过程与 FR-ENG 指标。

| 校验条件 | 判定 | 类型 |
|---------|------|------|
| BP 不是 A1 类型 | 输出类型分布，提示走 `wft03-biz` → **退出** | 硬退出 |
| BP 状态不是 `可以SR设计`/`待补充SR设计` | 输出不合格节点及当前状态 → **退出** | 硬退出 |
| 配置信息组业务过程缺少任一项（配置入口/配置过程/系统处理及载件/业务人员操作/FR-ENG 指标） | BP → `需wft02修订`，输出缺失说明 → **退出** | 硬退出 |
| CU 依赖不闭合且 AI 无法阶段性说明 | BP → `需wft02修订`，输出依赖断点 → **退出** | 硬退出 |
| SR-F 为 `需wft03修订` 且人类未提供改进方案 | 输出 wft05-eng 缺失说明，提示提供改进方案 → **退出** | 硬退出 |
| 选中 BP >5 个 | 输出超限提示 → 人类确认后继续或退出 | 软提示 |

#### 5.1.3 分流处理

按优先级顺序执行（源于 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序)）：

**① 退回优先**：存在 `需wft03修订` 且门禁通过 → 读取缺失说明，按人类方案走 Phase B（§5.4.2），确认后推进为 `待产品架构`

**② 反馈处理**：存在 `待确认方案` + 未处理反馈 → 进入 Step 2（§5.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 BP，Step End 时提示

**③ 新 BP 路由**：有未处理 BP → 进入 Step 1 → Step 3，逐节点执行 Phase A 宿主匹配（§5.4.1）

> **顺序约束**：Step 2（反馈）必须早于 Step 3（新增设计），因为反馈可能改变 SR-F 的页面清单/类别/布局/操作活动/PA 收敛项。Phase A 匹配须基于 Step 2 修改后的最新 SR-F 内容。

### 5.3 Step 2 · 方案反馈处理

**一句话**：处理人类反馈——对话内即时处理（修改 / 整体确认，§5.3.1），跨轮余留按 `[修改]`/`[驳回]` 标记处理（§5.3 状态机）。

人类反馈的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)（反馈通道双轨：对话 + 线下修订）。以下为本 Skill 的特化规则。

**反馈双轨**——人类可任选两种方式反馈，本 Skill 均支持：

- **AI 对话反馈**：Step End 后不结束对话，直接在对话中提出修改意见（自然语言）——AI 按 §5.3.1 即时处理（主通道）
- **线下文档修订**：直接打开 `05-*.md` 修订——在确认状态字段标注 `[同意]`/`[修改]`/`[驳回]`，或直接编辑方案内容（自由文本）——经 Step Start 变更感知（git diff，§5.1 变更感知）检出后按 §A.5 处理

两轨等价：对话反馈由 AI 即时落账（追 `[已处理]`），线下修订经 git diff 检出后同样落账；AI 每轮写回提交基线（§5.7），保证下一轮 diff 只含人类变更。

**本 Skill 的操作条目**：配置页面 + 页面功能架构 + 操作活动 + PA 收敛项。各条目的 `确认状态` 字段写入 `05-*.md` SR-F 节点块中。

**确认状态标记状态机**（本 Skill 反馈落账标记，定义单源；对话反馈写入者=AI，线下标注写入者=人类——经 git diff 检出后按 §A.5 处理）：

| 标记 | 含义 | 写入时机 | 转迁 |
|------|------|---------|------|
| `(空)` | 条目待人类反馈 | Step 3/4 产出时初始化 | 人类反馈后按情况转下 |
| `[修改]` | 人类提出修改意见、当轮未落地 | AI 在运行结束仍有余留修改意见时写入（跨轮持久化） | 下轮 Step 2 处理完追 `[已处理]` |
| `[驳回]` | 人类否决该条目方案、当轮未落地 | 同上 | 同上 |
| `[同意]` | 人类确认该条目 | "整体确认"时 | 随 `[已处理]` 一并追加 |
| `[已处理]` | 反馈已处理完毕（git 可追溯） | 处理完成后 | 默认跳过；满足清除条件（§5.3.1）时回到待处理 |

> 当轮对话内的反馈由 AI 即时处理（§5.3.1），不经 `[修改]`/`[驳回]` 态；`[修改]`/`[驳回]` 只在运行结束仍有余留反馈时出现，供下一轮 Step Start 检出（§5.1.1 入口②）。

**跨轮反馈持久化**：人类反馈（对话为主，§5.3.1）由 AI 当轮处理并追 `[已处理]`；若当轮对话结束仍有未落地的修改/驳回意见，AI 将对应条目标记 `[修改]`/`[驳回]` 并加入"待反馈处理"分节 → 下一轮 Step Start 检出（§5.1 变更感知）、Step 2 处理。AI 每轮写回后提交基线（§5.7），保证下一轮 Step Start 的 `git diff <HEAD @上次 AI 运行>..HEAD` 只含人类变更。

#### 5.3.1 AI 处理流程

按统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以配置信息组业务过程为锚点的方案修订。先理解人类反馈在 CU 配置能力语境中的含义，执行修订后检查 SR-F 是否仍满足配置信息组业务过程的需求。

按 [91 规范 §A.5.3](91-eos-biz-eng-spec.md#a53-ai-处理流程) 的流程处理人类自然语言反馈：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → 理解修改意图 → 执行修改 → 检查是否仍满足配置信息组业务过程 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改，继续等待决策 |
| 整体确认（"整体确认"/"可以"） | 全部条目追加 `[同意] [已处理]` → 总结反馈要点写入 `## AI最近变更` → 推进 SR-F 至 `待产品架构` → **提交基线并更新 HEAD（机制见 §5.7，防下轮把 AI 自写当人类变更）** |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |
| 线下修订检出（git diff 发现确认状态标注/自由文本编辑） | 定位条目 → Edit 修订 → 追加 `[已处理]` → 输出修改摘要 → 继续等待 |

**特化参数**：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 配置信息组业务过程——不脱离配置信息组业务过程自行修订 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → `待产品架构`。存在 `[修改]`/`[驳回]` 无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需重做 Step 3~5 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过。仅在新输入满足以下任一时，清除 `[已处理]`（保留 `[同意]`）回到待处理：<br>• 新输入是条目的直接上游节点（如新 BP 是 SR-F 来源）<br>• 新输入与条目同属一个架构层级且边界重叠（如新页面改变已有页面的类别或布局）<br>• 新输入导致条目被修订（变更影响声明标注修订型或结构型） |
| **级联触发条件** | 页面清单、类别或布局组件组合变更；操作活动新增/删除/类型变更；PA 收敛项边界变化 → 触发需求级联检查 → 通过后触发资产对齐级联 |
| **资产对齐级联** | 方案变更影响 25 资产时更新对齐结论——配置页面变更 → 更新 25 配置页面能力引用（由 Step 6 维护） |

### 5.4 Step 3 · 配置页面设计

#### 5.4.1 Phase A：页面候选生成与宿主匹配

对每个非占位 CU，按配置能力要素生成五类页面候选（规则见 §3.2.1），然后逐页面做宿主匹配：

| 条件 | 路由 |
|------|------|
| 页面类别 + 页面职责落入已有 SR-F 配置页面，且布局需求可兼容 | 归入该 SR-F → **Phase B** |
| 不满足 | 进入待聚合池 → **Phase C** |
| 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

待聚合池按 `{引擎, CU, 页面类别, 页面候选列表}` 分组。此阶段仅粗略分组，布局组件判定和完整要素提取在 Phase C 执行。

#### 5.4.2 Phase B：修订已有 SR-F

1. **要素提取**：从本轮配置信息组业务过程提取页面职责、布局组件线索和操作活动候选（§3.2.1、§3.3.1）。已有页面职责仅追加不重建
2. **宿主匹配检查**：确认配置信息组业务过程仍在 SR-F 职责范围内（§3.2.4）。复用 → 追加来源；扩展 → 全量重写保留历史；冲突 → `[需裁决]`。Phase A 是候选筛选，Phase B 是精确匹配——职责扩展时不得回退 Phase A 重选宿主
3. **重判定与关系检测**：基于全部 CU 重判页面类别与布局组合（§3.2.2、§3.2.3），比对基线判定六种关系（§3.3.3）。新增/变更操作活动 → 定义十字段；PA 收敛项 → 写入标记
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 SR-F 节点末尾（§4.2）

#### 5.4.3 Phase C：新建 SR-F

1. **确定页面类型与类别** → 页面类型固定为配置页面；按职责判定五类页面类别之一（§3.2.2）
2. **判定布局组件** → 独立判断页面需要的布局组件组合（§3.2.3）。三者互不替代
3. **定义页面职责** → 页面类别 + 页面用途 + 配置对象 + 使用角色（使用角色承接自 BP 的 A2 上下文，配置或支撑角色）
4. **承接操作活动** → 逐活动承接配置信息组业务过程定义十字段（§3.3.1）
5. **标注 PA 层收敛项** → 组件边界/接口/存储/运行机制/NFR 均标注 `PA层收敛-*`（§2.3.3）
6. **组装 SR-F** → 写入 `05-*.md`：页面 ID/名称/类型/类别/布局组合 + 使用角色 + 来源 BP/CU + 页面职责 + 构件线索 + 操作活动清单 + PA 收敛项（完整要素见 §2.1.2）

### 5.5 Step 4 · 功能架构与操作活动

> 按每个 CU 或强依赖 CU 组独立执行。新建 → 全量设计；修订 → 仅当配置信息组业务过程变更或页面拓扑变化时重验架构。

**1. 页面功能架构设计**

基于 Step 3 确定的配置页面清单、类别和布局组件组合，组织功能架构（其本质是 CU 集成业务过程的页面编排，§2.3.1）：

- **TAB / 导航顺序**：基于 CU 配置入口的页面级定位
- **主子页面关系**：配置维护主页面 → 配置要素子页面
- **页面间跳转与上下文传递**：跳转路径 + CU ID、配置版本、引擎实例等上下文
- **权限、状态、版本、发布依赖**：页面受哪些引擎治理能力约束
- **追溯矩阵**：每个页面 TAB/区块 → 配置信息组 → CU → 配置能力 → 运行期制品/构件/功能

**2. 操作活动承接**

对每个配置页面，先承接配置信息组业务过程挂载操作活动（§2.4.2：配置过程→配置维护、系统处理及载件→校验/发布生效、业务人员操作过程→运行支撑），再按四类构件检查覆盖（§2.2.1），为相关构件定义操作活动。活动类型按 §2.3.2 五类归组。每个操作活动写入十字符段（§3.3.1），系统处理摘要承接 wft02 定义的组系统处理并标注引用。所有活动标注 `[推断]`，人类确认后方可落账。

**3. PA 层收敛项标注**

逐活动检查（五类见 §2.3.3），存在则写入 `PA层收敛-*` 标记（载件是主要来源——供 wft05 判断由前后端组件承接）：

- 组件边界待定 · 接口契约待定 · 数据存储待定 · 运行机制待定 · NFR 承接待定

**4. 要素机械检查**（逐页面，发现即标注 `[覆盖缺口]`，留待下一轮补全）

- [ ] TAB/导航/主子/跳转路径 **已定义**
- [ ] 权限、状态、版本、发布依赖 **已标注**
- [ ] 页面→配置信息组→CU→配置能力→运行期能力追溯矩阵 **完整**
- [ ] 操作活动 **已承接**，十字段要素齐全，系统处理摘要标注承接引用
- [ ] PA 收敛项 **已标注**
- [ ] 所有非占位 CU 的配置能力均被页面承接

### 5.6 Step 5 · 覆盖自查与变更声明

> 按每个 SR-F 节点独立执行。新建 → 全量自查；修订 → 仅当页面清单或操作活动变更时重验。

**1. 覆盖自查**

按十项逐条检查（判据见 §3.4），发现遗漏标注 `[覆盖缺口]`，不回退：

- [ ] CU 覆盖 · 配置入口覆盖 · 配置过程覆盖 · 系统处理覆盖
- [ ] 运行期能力覆盖 · 构件线索覆盖 · 追溯覆盖 · 共享不重复
- [ ] PA 收敛项覆盖 · 推断依据标注 · 25 关系清晰

**2. 缺口处理**

| 缺口类型 | 处理方式 |
|----------|----------|
| 配置入口或配置过程未覆盖 | 补充页面或退回 wft02-eng |
| 系统处理未覆盖 | 补充操作活动或标注 PA 收敛 |
| 运行期能力未覆盖 | 补充运行支撑页面或说明由 biz 承接 |
| 构件线索缺失 | 补充按钮/右键/快捷键/图表/钻取等线索 |
| PA 必收敛项缺失 | 补充收敛项，不推进到可消费 |
| — | 不因缺口脑补节点——缺口就是缺口 |

**3. 要素机械检查**

- [ ] 十项覆盖自查已执行，遗漏项已标注
- [ ] 缺口已分流，处理方式明确
- [ ] SR-F 版本号已递增（修订时），首版为 v1

**4. 变更影响声明**

新建或修订后写入声明（§4.2）。首版写"首版，无变更"。修订时判定变更类型，列出受影响页面、操作活动和下游建议。
