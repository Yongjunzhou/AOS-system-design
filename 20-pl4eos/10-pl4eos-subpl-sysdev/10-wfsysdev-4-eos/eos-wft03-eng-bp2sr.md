# BP(A1) → SR-F · 配置页面设计
**人类方案ID**: wft03-eng-bp2sr

> **概述**：接收 A1 配置单元 BP（含 CU 配置入口、配置要素、系统处理、运行期能力和指标），经前置校验、材料加载和反馈处理后，推断配置、发布、运行支撑和治理所需的配置页面；再为每个页面识别布局组件与构件，组织页面功能架构和操作活动。该 SR-F 以配置页面为末级节点、构件为细分节点，并将组件、接口、存储和运行机制标注为 PA 层收敛项。
>
> **输入 → 输出**：A1 BP 节点（`可以SR设计` / `待补充SR设计`）/ 有反馈的 SR-F 节点 → 配置页面 SR-F（页面清单 + 布局组件/构件 + 页面功能架构 + 操作活动 + PA 层收敛项）+ BP 推进为 `已SR设计` + SR-F 推进为 `待产品架构`
>
> **适用场景**：瀑布式系统设计第3步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v7.3 | **修订**：2026-07-14 | **说明**：向应 91 规范 v5.6——布局组件可选范围、页面类别判定条件和布局组件判定规则中补充看板页面

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台开发人员——「为了配置、发布和支撑这个 CU，需要哪些配置页面，每个页面需要哪些可复用构件和操作活动」。把 wft02-eng 产出的 CU 配置能力转化为可进入 PA 的配置页面 SR-F，为下游三类组件设计（wft05-eng）提供可展开的系统需求输入。

**目标**：

1. **推断配置页面** —— 基于 CU 的配置入口、配置要素、系统处理、运行期能力（含 FR-ENG 指标），确定五类页面类别之一
2. **组织页面功能架构** —— 将同一 CU 或强依赖 CU 组的配置页面按 TAB、主子关系、跳转、依赖、上下文传递组织成页面功能架构
3. **推断操作活动** —— 逐活动定义入口构件线索、前置条件、用户动作、系统处理摘要、结果状态、校验规则、异常处理和 PA 层收敛项
4. **保留完整追溯** —— 配置页面 → 来源 CU → CU IPO → 运行期能力的追溯链完整可验证
5. **执行覆盖自查** —— 检查每个 CU 的配置入口、配置要素、系统处理和运行期能力均被页面承接

**本 Skill 负责**：

| # | 职责 | 动作 |
|---|------|------|
| 1 | **接收** | 人类选中的 ≤5 个 A1 BP 节点 → 校验状态 `可以SR设计`/`待补充SR设计`，检查 CU IPO、指标和入口线索完整；缺失时退回 wft02-eng |
| 2 | **匹配** | 按 `引擎 + CU + 配置页面职责` 匹配已有 SR-F，再匹配布局组件与构件 → 职责一致则复用，职责扩展则全量重写，无可匹配则新建，冲突标记 `[需裁决]` |
| 3 | **构件识别**（§8.3 任务 1"选用布局组件"的细化，四分类体系见 91 规范 §四） | 按展示/交互/数据/反馈四类逐页面识别构件，标注类型和跨页面复用范围 |
| 4 | **功能架构生成** | 为同一 CU 的配置页面按构件组织 TAB、主子、跳转、上下文和权限依赖 |
| 5 | **操作活动设计** | 为每个构件定义操作活动（配置维护/校验处理/发布生效/运行支撑/治理追溯五类），写入十字符段并标注 PA 层收敛项 |
| 6 | **覆盖自查** | 检查 CU IPO → 配置页面 → 构件的承接链完整，PA 收敛项不缺失 |
| 7 | **推进** | 人类确认后：SR-F → `待产品架构`，BP → `已SR设计`，记录消费版本 |
| 8 | **回修** | 接收 wft05-eng 退回的 `需wft03修订` SR-F，读取缺失说明，按人类方案修订；根因在 BP 时退回 wft02-eng |

**本 Skill 不负责**：

| 职责 | 归属 |
|------|------|
| CU IPO 定义、CU 拆分/合并 | → `wft02-eng` |
| 功能表单和窗口标签页设计 | → `wft03-biz` |
| 前端/后端组件划分、接口详细规格、数据存储结构和实现机制 | → `wft05-eng` |
| NFR 量化 | 本 Skill 只保留需要 wft05-eng 消费的 NFR 约束引用 |

### 1.2 与上下游的衔接

**上游 wft02-eng**：产出 A1 BP，包含 CU 配置入口、配置要素、系统处理、运行期能力、FR-ENG 指标和依赖。本 Skill 据此推断配置页面并识别布局组件与构件，不重新定义 CU。

**下游 wft05-eng**：消费 `待产品架构` 的配置页面 SR-F，结合 FR-BIZ 指标约束包和 NFR 约束包推断三类组件。若发现页面、构件、操作活动或 PA 收敛项缺失，将 SR-F 退回为 `需wft03修订`。

## 二、配置页面 SR-F 设计基础

### 2.1 配置页面 SR-F

#### 2.1.1 定义与分类

配置页面是配置、治理或运行支撑人员直接使用的页面单元，用来维护 CU 配置、触发引擎处理、查看发布/运行结果或处理异常。它**不同于** biz 路径面向业务角色的功能表单和窗口标签页。

配置页面按职责分为五类（由 AI 根据 CU 配置能力要素判定）：

| 页面类别 | 用途 | 典型来源 |
|----------|------|----------|
| 配置维护页 | 维护 CU 配置要素 | 配置入口、配置要素 |
| 配置管理页 | 管理配置版本、状态、引用关系 | 系统处理、治理依赖 |
| 发布生效页 | 校验、发布、装载、回滚、停用 | 系统处理 |
| 运行支撑页 | 查看运行期能力、刷新、重试、处理异常 | 运行期能力 |
| 治理追溯页 | 审计、影响范围、引用关系、操作日志 | 横切治理依赖 |

> 布局组件与构件的详细定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)，eng 路径分工见 [91 规范 §8.3](91-eos-biz-eng-spec.md#83-系统需求开发wft03-eng)。

#### 2.1.2 架构与属性

配置页面设计涉及三个**相互独立**的维度，不能互相替代：

| 维度 | 来源 | 回答的问题 | 进入 SR-F 的字段 |
|------|------|------------|------------------|
| 页面类型 | 91 规范 §1.2 | 是否属于硬代码开发的配置页面？ | `页面类型=配置页面` |
| 页面类别 | 91 规范 §8.3 | 承担哪种配置职责？ | `页面类别` |
| 布局组件 | 91 规范 §四 | 内部由哪些布局组件承载内容和交互？ | `布局组件清单` |

> 页面类别和布局组件的判定规则见 §2.2，页面功能架构见 §2.3.1，操作活动定义见 §2.3.2。

**SR-F 节点完整要素**（写入 `05-*.md` SR-F 节点块）：

- 页面 ID / 名称 / 页面类型（固定为配置页面）/ 页面类别 / 使用角色
- 来源 BP / 来源 CU / CU 配置能力引用
- 页面职责 · 布局组件与构件线索 · 页面字段或配置对象摘要
- 页面操作活动清单 · 权限、状态、版本、发布约束
- PA 层收敛项 · 确认状态

#### 2.1.3 完备性判据（覆盖自查检查项）

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| CU 覆盖 | 每个非占位 CU 均有配置页面承接 | 补充页面或退回 wft02-eng |
| 配置入口覆盖 | 每类配置入口都有页面承接 | 补充页面或退回 wft02-eng |
| 配置要素覆盖 | 关键配置要素有录入、维护或选择方式 | 补充页面字段或标注 PA 收敛 |
| 系统处理覆盖 | 校验、保存、发布、装载、回滚等处理有操作活动，或写明不适用理由 | 补充操作活动或标注 PA 收敛 |
| 运行期能力覆盖 | 运行期制品、构件或功能有查看/预览/触发/支撑说明，或说明由 biz 页面承接 | 补充运行支撑页面或说明承接方 |
| 构件线索覆盖 | 页面操作入口能映射到按钮、右键、快捷键、图表、钻取等构件线索 | 补充构件线索 |
| 追溯覆盖 | 页面 → CU → BP → STR-E 追溯完整 | 补充追溯引用 |
| 共享不重复 | 共享 CU 的配置页面只在主责链下定义；消费场景仅保留入口或依赖引用 | 删除重复页面，补共享依赖 |
| PA 收敛 | 组件、接口、存储、运行机制、NFR 待定项均标注 | 补充收敛项，不推进到可消费 |

### 2.2 配置页面类型、页面类别与布局组件

#### 2.2.1 定义与正交关系

**页面类型**：本 Skill 的末级节点固定为**配置页面**。配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页是**页面类别**（职责分类），不是新的页面类型。

**布局组件**：多级横版、列表、树表、单据、辅助栏、弹窗、指标页面、看板页面通过布局组件组合表达，替代旧"六种页面形态"。

每个 SR-F 必须同时写明：**`页面类型=配置页面`** + **页面类别** + **布局组件清单**。

**布局组件可选范围**：

| 布局组件 | 典型用途 |
|----------|----------|
| 多级横版 | 多层级配置对象、主从配置、流程/规则设计器 |
| 列表页面 | 配置对象集合、发布记录、版本记录、执行记录 |
| 单据页 | 单个配置对象编辑、参数维护、规则详情 |
| 辅助栏 | 详情预览、上下文摘要、引用关系、校验结果 |
| 弹窗页 | 选择、确认、局部参数编辑、冲突处理 |
| 指标页面 | 运行状态、质量指标、发布影响、异常趋势 |
| 看板页面 | 运行看板、任务看板、发布状态、异常汇总 |

**构件完整性分类**（四类须分别检查；无需求时写明"不适用"，不得只列按钮类构件）：

| 类别 | 典型构件 |
|------|----------|
| 展示类 | 列定义、字段布局、图表类型、卡片、树节点、阶段/里程碑 |
| 交互类 | 功能按钮、右键菜单、快捷键、下钻、行选中、TAB 切换 |
| 数据类 | 筛选器、排序器、分页器、导入、导出 |
| 反馈类 | 通知提示、进度条、状态标签、校验提示 |

### 2.3 页面功能架构与操作活动

#### 2.3.1 页面功能架构

页面功能架构回答：一个 CU 或一组强依赖 CU 的配置页面如何组合使用。

**要素**：
- 配置页面清单与布局组件
- TAB 顺序或导航关系 · 主子页面关系
- 页面间跳转和上下文传递
- 权限、状态、版本和发布依赖
- 与来源 CU、配置能力要素的对应关系

#### 2.3.2 操作活动定义

操作活动是用户在配置页面上执行的可验证动作。每个操作活动的规范必填项为：**触发方式、操作对象、结果反馈**。以下字段用于补充业务语义，不得写成 PA 实现设计：

| 字段 | 说明 |
|------|------|
| 活动名称 | 如新建配置、校验配置、发布配置 |
| 操作入口 | 按钮、右键、快捷键、双击、自动触发 |
| 所属页面 / 构件 | 页面 ID 和入口构件 |
| 前置条件 | 状态、权限、版本、依赖 |
| 用户动作 | 用户做什么（点击、填写、选择等） |
| 系统处理摘要 | 系统校验、保存、发布、装载、记录等 |
| 结果状态 | 页面状态、配置状态或运行期状态 |
| 校验规则 | 必填、唯一、依赖、权限、冲突等 |
| 异常处理 | 失败提示、回滚、重试、人工处理 |
| PA 层待处理线索 | 仅记录待 wft05-eng 判断的问题，不给组件/接口/存储实现结论 |

操作活动按类型分为五类：

| 活动类型 | 典型动作 | 适用页面类别 |
|----------|----------|-------------|
| 配置维护 | 新建、编辑、复制、删除、导入、导出 | 配置维护页 |
| 校验处理 | 校验、预览、冲突检查、依赖检查 | 配置维护/管理页 |
| 发布生效 | 保存、提交、发布、装载、回滚、停用 | 发布生效页 |
| 运行支撑 | 查看生效结果、刷新缓存、重试、异常处理 | 运行支撑页 |
| 治理追溯 | 查看版本、审计、引用关系、影响范围 | 治理追溯页 |

#### 2.3.3 PA 层收敛项

本 Skill **不设计组件**。PA 层内容只能作为"待处理问题"传递，不得预选同步/异步、存储归属或实现机制。

| 收敛项 | 示例 | 标注 |
|--------|------|------|
| 组件边界 | 发布按钮构件是否复用公共构件 | `PA层收敛-组件边界` |
| 接口问题 | 发布动作是否存在跨组件交互待判定 | `PA层待处理-接口` |
| 数据问题 | 配置版本、发布记录、审计记录需要持久化能力 | `PA层待处理-数据` |
| 运行问题 | 装载、缓存刷新、回滚、重试等需要下游确定机制 | `PA层待处理-运行` |
| NFR 问题 | 关联的 NFR 约束由 wft05-eng 消费约束包后决策 | `PA层待处理-NFR` |

### 2.4 SR-F 要素提取规则

Phase B（修订已有 SR-F）与 Phase C（新建 SR-F）共用以下规则。

#### 2.4.1 页面候选生成

对每个非占位 CU，按配置能力要素生成页面候选：

| CU 配置能力要素 | 页面/活动映射 |
|----------------|---------------|
| 配置入口 | 配置维护页、配置列表、配置详情、选择弹窗 |
| 配置要素 | 字段/规则编辑区、关系维护区、辅助栏详情、选择器 |
| 系统处理 | 校验、保存、发布、装载、回滚、停用、异常处理活动，以及执行记录页 |
| 运行期能力 | 能力预览页、运行支撑页、结果查看页、异常处理页；业务运行页面本体仍由 biz 路径承接 |

候选覆盖五类：配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页。

#### 2.4.2 页面类别与布局组合判定

**页面类型**固定为`配置页面`。先按配置职责确定页面类别，再按内容与交互选择布局组件组合：

| 判定条件 | 页面类别 | 候选布局组件组合 |
|----------|----------|------------------|
| 多条配置对象或版本记录维护 | 配置维护/管理页 | 多级横版 + 列表页面 + 辅助栏（可选） |
| 层级对象维护 | 配置维护页 | 多级横版 + 列表页面（树表）+ 辅助栏（可选） |
| 单个配置对象编辑 | 配置维护页 | 多级横版 + 单据页 + 辅助栏（可选） |
| 主配置与子规则强相关 | 配置维护/管理页 | 多级横版（双窗）+ 列表页面/单据页 + 辅助栏（可选） |
| 发布、装载、回滚或运行状态处理 | 发布生效/运行支撑页 | 列表/指标/看板页面 + 单据页/弹窗页（按需） |
| 审计、引用关系或影响范围追溯 | 治理追溯页 | 列表/指标页面 + 辅助栏（可选） |
| 临时选择、确认、局部参数或冲突处理 | 从属父页面类别 | 弹窗页 |

#### 2.4.3 布局组件判定

在页面类别判定之后，独立判断页面内部需要哪些布局组件：

| 判定条件 | 布局组件 |
|----------|----------|
| 需要展示对象集合、版本记录或执行记录 | 列表页面 |
| 需要编辑单个配置对象或参数组 | 单据页 |
| 需要并列展示多层主从对象 | 多级横版 |
| 需要上下文、详情、校验结果或引用关系 | 辅助栏 |
| 需要临时选择、确认、局部参数或冲突处理 | 弹窗页 |
| 需要展示运行指标、发布影响或异常趋势 | 指标页面 |
| 需要展示运行状态概览、任务分布或发布汇总 | 看板页面 |

#### 2.4.4 Phase B 宿主匹配检查

按 `引擎 + CU + 页面类别 + 页面职责` 匹配已有配置页面：

| 结果 | 判定 | 动作 |
|------|------|------|
| 复用 | 页面类别、布局组合和页面职责匹配 | 追加 BP/CU 来源，标记 `[确认]` |
| 扩展 | 页面类别和职责一致，但布局组合、操作活动或 PA 收敛项扩展 | 全量重写该页面 SR-F，保留历史引用，输出变更声明 |
| 新建 | 无可匹配的配置页面 | 新建配置页面 SR-F |
| 冲突 | 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

#### 2.4.5 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B（修订） | Phase C（新建） |
|------|----------------|-----------------|
| 判定范围 | SR-F 已承接全部 BP/CU + 本轮新 BP/CU | 待聚合池本组 BP/CU |
| 页面清单基线 | 已有清单为基线，仅扫描新 CU 是否引入新页面 | 从零构建 |
| 页面候选 | 增量生成（仅新 CU 触发） | 全量生成（§2.4.1） |
| 宿主匹配 | 执行匹配检查（§2.4.4），可能检出复用/扩展/新建/冲突 | 无需匹配，直接新建 |
| 操作活动 | 基线基础上增量合并（关系检测见 §2.5.3） | 全量设计 |
| 变更传播 | 输出变更影响声明（§2.7） | 写"首版，无变更" |

### 2.5 操作活动推断规则

Phase B 与 Phase C 共用以下规则。

#### 2.5.1 操作活动类型与字段

对每个配置页面的操作活动，按 §2.3.2 的五类活动类型和十个字段逐项填写。活动类型由页面类别和 CU 配置能力要素共同决定：

| 页面类别 | 主导活动类型 | 辅助活动类型 |
|----------|-------------|-------------|
| 配置维护页 | 配置维护 | 校验处理 |
| 配置管理页 | 配置维护 | 治理追溯 |
| 发布生效页 | 发布生效 | 校验处理、运行支撑 |
| 运行支撑页 | 运行支撑 | 治理追溯 |
| 治理追溯页 | 治理追溯 | — |

每个操作活动写入：活动名称、入口构件、所属页面、前置条件、用户动作、系统处理摘要、结果状态、校验规则、异常处理、PA 层收敛项（§2.3.3）。

#### 2.5.2 PA 层收敛项标注

为每个活动检查是否存在待下游裁决的事项，存在则写入 `PA层收敛-*` 标记（五类定义见 §2.3.3）。

#### 2.5.3 Phase B 配置页面关系检测

宿主匹配通过后，将本轮生成的页面与 SR-F 已有清单比对。比对锚点为**页面类别 + 布局组件组合 + 页面职责匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 页面匹配 + 类别/布局一致 + 来源升级（新 CU→已有页面） | 追加 BP/CU 来源 |
| 无新增 | 页面匹配 + 类别/布局一致 + 所有来源已确认 | 增量合并新 CU 的细节（如有） |
| 页面职责扩展 | 页面匹配 + 类别一致 + 操作活动/PA 收敛项边界扩展 | 全量重写，保留历史引用 |
| 布局组合变更 | 页面匹配 + **布局组件组合不同**（CU 配置能力变化导致） | 更新布局组合 + 重判构件 |
| 补充 | 页面不匹配 | 新增配置页面 SR-F |
| 过时 | 基线已有页面**未被**本轮 CU 覆盖 | 保留在清单中，标注`过时`，由人类裁决移除 |

> 关系检测前先基于**全部 CU** 重新判定页面类别与布局组件组合——新 CU 可能改变页面职责或布局需求（如 `布局组合变更`）。`[调整]` 是与关系类型正交的叠加标记，用于页面职责/操作活动/PA 收敛项有变化时。

### 2.6 SR-F 节点生命周期

SR-F 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转。状态名映射见 §A.6 表（wft03-eng 列）。并行推进规则（SR 线与 PA 线互不阻塞）同 §A.6。

**主线流转**（wft03-eng ↔ wft05-eng）：

```
待确认方案 ──人类确认──→ 待产品架构 ──wft05锁定──→ 在PA设计 ──wft05完成──→ 已产品架构
     ↑                        ↑                         │
     │                        │               wft05退回  │
     │                        │                         ↓
     └─── wft03修订 ────── 需wft03修订 ←───────────────┘
```

**上游变更**（新 BP/CU 汇入触发 SR-F 修订）：

```
待产品架构 ──新BP/CU修订──→ 待产品架构（版本递增，wft05 未消费）
在PA设计   ──新BP/CU修订──→ 在PA设计（版本递增，wft05 增量处理）
已产品架构 ──新BP/CU修订──→ 待补充PA设计 ──wft05补全──→ 已产品架构
```

**本 Skill 写回范围**：`待确认方案` / `待产品架构` / `待补充PA设计` / `需wft03修订`。`在PA设计` 和 `已产品架构` 由 wft05-eng 推进。

**下游退回处理**：读取 wft05-eng 缺失说明 → 按人类改进方案修订（走 Phase B）→ 人类确认 → SR-F → `待产品架构`。根因在 BP 时退回 wft02-eng。

### 3.1 Step Start · 前置校验与路由

> 入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。

#### 3.1.1 入口检测

读取产品数据中的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口：

| # | 条件 | 检测方式 |
|---|------|---------|
| ① | **有新输入** | 「待 wft03-eng 处理」分节非空 |
| ② | **有待处理反馈** | 「待反馈处理」分节含本 Skill 产出节点 |
| ③ | **有下游退回** | 「待下游退回处理」分节含 `需wft03修订` 的节点 |

三类均不满足 → 输出"无待处理对象" → **退出**。

**退回门禁**（条件③时）：退回节点缺失说明中是否含人类改进方案（`[修改]`/`[同意]` 或下游 Skill 的具体指引）。已提供 → 通过。未提供 → 输出缺失说明，提示提供改进方案 → **退出**。

#### 3.1.2 输入校验

入口检测通过后进行校验。逻辑上不可能的条件为**硬退出**，数量/归属模糊条件为**软提示**：

| 校验条件 | 判定 | 类型 |
|---------|------|------|
| BP 不是 A1 类型 | 输出类型分布，提示走 `wft03-biz` → **退出** | 硬退出 |
| BP 状态不是 `可以SR设计`/`待补充SR设计` | 输出不合格节点及当前状态 → **退出** | 硬退出 |
| CU 配置能力定义缺少任一项（配置入口/要素/系统处理/运行期能力） | BP → `需wft02修订`，输出缺失说明 → **退出** | 硬退出 |
| CU 依赖不闭合且 AI 无法阶段性说明 | BP → `需wft02修订`，输出依赖断点 → **退出** | 硬退出 |
| SR-F 为 `需wft03修订` 且人类未提供改进方案 | 输出 wft05-eng 缺失说明，提示提供改进方案 → **退出** | 硬退出 |
| 选中 BP >5 个 | 输出超限提示 → 人类确认后继续或退出 | 软提示 |

#### 3.1.3 分流处理

按优先级顺序执行（源于 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序)）：

**① 退回优先**：存在 `需wft03修订` 且门禁通过 → 读取缺失说明，按人类方案走 Phase B（§3.4.2），确认后推进为 `待产品架构`

**② 反馈处理**：存在 `待确认方案` + 未处理反馈 → 进入 Step 2（§3.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 BP，Step End 时提示

**③ 新 BP 路由**：有未处理 BP → 进入 Step 1 → Step 3，逐节点执行 Phase A 宿主匹配（§3.4.1）

> **顺序约束**：Step 2（反馈）必须早于 Step 3（新增设计），因为反馈可能改变 SR-F 的页面清单/类别/布局/操作活动/PA 收敛项。Phase A 匹配须基于 Step 2 修改后的最新 SR-F 内容。

### 3.3 Step 2 · 方案反馈处理

> 人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 特化规则。

**本 Skill 的操作条目**：配置页面 + 页面功能架构 + 操作活动 + PA 收敛项。各条目的 `确认状态` 字段写入 `05-*.md` SR-F 节点块中。

#### 3.3.1 AI 处理流程

按统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 BP/CU 配置能力定义为锚点的方案修订。先理解人类反馈在 CU 配置能力语境中的含义，执行修订后检查 SR-F 是否仍满足 CU 需求。

**特化参数**：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | BP/CU 配置能力定义——不脱离 CU 内容自行修订 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → `待产品架构`。存在 `[修改]`/`[驳回]` 无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需重做 Step 3~5 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过。仅在新输入满足以下任一时，清除 `[已处理]`（保留 `[同意]`）回到待处理：<br>• 新输入是条目的直接上游节点（如新 BP 是 SR-F 来源）<br>• 新输入与条目同属一个架构层级且边界重叠（如新页面改变已有页面的类别或布局）<br>• 新输入导致条目被修订（变更影响声明标注修订型或结构型） |
| **级联触发条件** | 页面清单、类别或布局组件组合变更；操作活动新增/删除/类型变更；PA 收敛项边界变化 → 触发需求级联检查 → 通过后触发资产对齐级联 |
| **资产对齐级联** | 方案变更影响 25 资产时更新对齐结论——配置页面变更 → 更新 25 配置页面能力引用（由 Step 6 维护） |

#### 3.3.2 确认状态格式示例

**AI 写入（Step 3~5 完成时）**——为每个条目初始化，状态为空：

```text
- 配置页面：流程节点配置页（类型=配置页面；类别=配置维护页；布局=多级横版+列表页面（树表）+辅助栏） | 确认状态: (空)
- 配置页面：流程发布管理页（类型=配置页面；类别=发布生效页；布局=多级横版+列表页面+辅助栏） | 确认状态: (空)
- 页面功能架构：节点配置页 → 发布管理页（TAB切换） | 确认状态: (空)
- 操作活动：新建流程节点（配置维护，节点配置页，按钮入口） | 确认状态: (空)
- PA 层收敛项：节点元数据存储归属 [PA层收敛-存储] | 确认状态: (空)
```

**人类标注**——三种形式：

```text
- 配置页面：流程节点配置页（...） | 确认状态: [同意]
- 配置页面：流程发布管理页（...） | 确认状态: [修改]：应补充"回滚"操作活动

- 配置页面：流程发布管理页（...） | 确认状态: [修改]：应补充"回滚"操作活动 [已处理]

### 3.4 Step 3 · 配置页面设计

#### 3.4.1 Phase A：页面候选生成与宿主匹配

对每个非占位 CU，按配置能力要素生成五类页面候选（规则见 §2.4.1），然后逐页面做宿主匹配：

| 条件 | 路由 |
|------|------|
| 页面类别 + 页面职责落入已有 SR-F 配置页面，且布局需求可兼容 | 归入该 SR-F → **Phase B** |
| 不满足 | 进入待聚合池 → **Phase C** |
| 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

待聚合池按 `{引擎, CU, 页面类别, 页面候选列表}` 分组。此阶段仅粗略分组，布局组件判定和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 SR-F

1. **要素提取**：从本轮 CU 配置能力定义提取页面职责、布局组件线索和操作活动候选（§2.4.1、§2.5.1）。已有页面职责仅追加不重建
2. **宿主匹配检查**：确认 CU 配置能力仍在 SR-F 职责范围内（§2.4.4）。复用 → 追加来源；扩展 → 全量重写保留历史；冲突 → `[需裁决]`。Phase A 是候选筛选，Phase B 是精确匹配——职责扩展时不得回退 Phase A 重选宿主
3. **重判定与关系检测**：基于全部 CU 重判页面类别与布局组合（§2.4.2、§2.4.3），比对基线判定六种关系（§2.5.3）。新增/变更操作活动 → 定义十字段；PA 收敛项 → 写入标记
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 SR-F 节点末尾（§2.7）

#### 3.4.3 Phase C：新建 SR-F

1. **确定页面类型与类别** → 页面类型固定为配置页面；按职责判定五类页面类别之一（§2.4.2）
2. **判定布局组件** → 独立判断页面需要的布局组件组合（§2.4.3）。三者互不替代
3. **定义页面职责** → 页面类别 + 页面用途 + 配置对象 + 使用角色（§2.1.1）
4. **设计操作活动** → 逐活动定义十字段（§2.5.1）
5. **标注 PA 层收敛项** → 组件边界/接口/存储/运行机制/NFR 均标注 `PA层收敛-*`（§2.3.3）
6. **组装 SR-F** → 写入 `05-*.md`：页面 ID/名称/类型/类别/布局组合 + 使用角色 + 来源 BP/CU + 页面职责 + 构件线索 + 操作活动清单 + PA 收敛项（完整要素见 §2.1.2）

### 3.5 Step 4 · 功能架构与操作活动

> 按每个 CU 或强依赖 CU 组独立执行。新建 → 全量设计；修订 → 仅当 CU 配置能力变更或页面拓扑变化时重验架构。

**1. 页面功能架构设计**

基于 Step 3 确定的配置页面清单、类别和布局组件组合，组织功能架构：

- **TAB / 导航顺序**：基于 CU 配置入口的页面级定位
- **主子页面关系**：配置维护主页面 → 配置要素子页面
- **页面间跳转与上下文传递**：跳转路径 + CU ID、配置版本、引擎实例等上下文
- **权限、状态、版本、发布依赖**：页面受哪些引擎治理能力约束
- **追溯矩阵**：每个页面 TAB/区块 → CU → 配置能力 → 运行期制品/构件/功能

**2. 操作活动设计**

对每个配置页面，先按四类构件检查覆盖（§2.2.1），再为相关构件定义操作活动。活动类型按 §2.3.2 五类归组。每个操作活动写入十字符段（§2.5.1）。所有活动标注 `[推断]`，人类确认后方可落账。

**3. PA 层收敛项标注**

逐活动检查（五类见 §2.3.3），存在则写入 `PA层收敛-*` 标记：

- 组件边界待定 · 接口契约待定 · 数据存储待定 · 运行机制待定 · NFR 承接待定

**4. 要素机械检查**（逐页面，发现即标注 `[覆盖缺口]`，留待下一轮补全）

- [ ] TAB/导航/主子/跳转路径 **已定义**
- [ ] 权限、状态、版本、发布依赖 **已标注**
- [ ] 页面→CU→配置能力→运行期能力追溯矩阵 **完整**
- [ ] 操作活动 **已定义**，十字段要素齐全
- [ ] PA 收敛项 **已标注**
- [ ] 所有非占位 CU 的配置能力均被页面承接

### 3.6 Step 5 · 覆盖自查与变更声明

> 按每个 SR-F 节点独立执行。新建 → 全量自查；修订 → 仅当页面清单或操作活动变更时重验。

**1. 覆盖自查**

按八项逐条检查（判据见 §2.1.3），发现遗漏标注 `[覆盖缺口]`，不回退：

- [ ] CU 覆盖 · 配置入口覆盖 · 配置要素覆盖 · 系统处理覆盖
- [ ] 运行期能力覆盖 · 构件线索覆盖 · 追溯覆盖 · PA 收敛项覆盖

**2. 缺口处理**

| 缺口类型 | 处理方式 |
|----------|----------|
| 配置入口或要素未覆盖 | 补充页面或退回 wft02-eng |
| 系统处理未覆盖 | 补充操作活动或标注 PA 收敛 |
| 运行期能力未覆盖 | 补充运行支撑页面或说明由 biz 承接 |
| 构件线索缺失 | 补充按钮/右键/快捷键/图表/钻取等线索 |
| PA 必收敛项缺失 | 补充收敛项，不推进到可消费 |
| — | 不因缺口脑补节点——缺口就是缺口 |

**3. 要素机械检查**

- [ ] 八项覆盖自查已执行，遗漏项已标注
- [ ] 缺口已分流，处理方式明确
- [ ] SR-F 版本号已递增（修订时），首版为 v1

**4. 变更影响声明**

新建或修订后写入声明（§2.7）。首版写"首版，无变更"。修订时判定变更类型，列出受影响页面、操作活动和下游建议。

### 3.7 Step 6 · 资产写回与落账

> 遵循 [91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 的统一写回协议。仅写回人类已在 Step 2 确认的 SR-F 条目。不设二次确认。

**写回操作**：

1. `05` 写入或更新 SR-F 架构节点、状态队列、追溯引用
2. `25` 写入配置页面能力引用或待办，不固化组件设计
3. `04` BP 节点写入 `BP 消费版本：v{N}`，状态推进为 `已SR设计`
4. SR-F → `待产品架构`
5. 写入资产写回记录（日期/来源 BP/目标 SR-F/动作/消费版本/下游状态）

**同步维护**：

| 操作 | 同步更新 |
|------|---------|
| 新增/修改节点 | 更新域产品索引 `节点数`；更新 `## AI可以处理节点` 对应分节 |
| 修改节点状态 | 更新 AI可以处理节点分节——状态符合消费条件时加入，不符合时移出 |
| 新增/删除子条目 | 更新父节点 `**子条目状态**` 汇总值 |
| 人类标注处理 | 更新父节点 `**子条目状态**` 和 `**确认状态**`；AI可以处理节点同步 |

**提交规范**（每次写回后必须执行）：

1. 在 `## AI最近变更` 表追加记录（[91 规范 §11.6](91-eos-biz-eng-spec.md#116-ai最近变更)），含时间/操作 Skill/操作类型/节点ID/变更摘要，操作类型列含 `[→](#节点ID)` 超链接
2. 更新文件头 `**文档版本**`（递增次版本号）、`**修订日期**`、`**HEAD @上次 AI 运行**`（=当前提交 hash）
3. 保留 AI最近变更最近 30 条，超出时从最旧行滚动删除
4. git add + git commit（带 `Co-Authored-By: Claude`）

> **写回要求**：幂等去重、局部写回、全貌同步。所有操作在 Step 内完成，不允许"本次写节点、下次更新索引"。资产写回是独立收尾，不构成 wft05-eng 前置条件。

配置页面
  [新增] "流程节点配置页"（类型=配置页面；类别=配置维护页；布局=多级横版+列表页面（树表）+辅助栏）

完备性检查
  CU 覆盖 ✓ / 配置入口覆盖 ✓ / 系统处理覆盖 ✓ / PA 收敛 ⚠
  → [需裁决] 发布记录页是否与版本记录页合并（操作对象相近，但审计职责可能独立）
```
