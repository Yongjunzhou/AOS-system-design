## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：产出可交付构件开发的业务侧页面组件——证明 BA 已被功能表单和窗口标签页完整承接，并将其 IPO 性能指标分配到支撑引擎能力。两类对象从 EOS 视角是业务配置需求，从配置业务系统视角是 PA 末级节点。
>
> **目标**（对齐 [91 规范 §7.3](91-eos-biz-eng-spec.md#73-业务配置需求与配置产品架构开发wft03-biz) 八项任务）：
> 1. **菜单树方案**——菜单层级结构、末级节点与场景业务映射
> 2. **场景业务方案**——功能表单/主子表单序列编排、显示顺序与依赖关系
> 3. **输出文档实体需求**——正式文档 DocumentCover 封面字段+正文实体字段；轻量文档正文实体字段
> 4. **正文功能表单**——将正文实体转化为功能表单形态，定义字段布局、交互行为、展示方式和 FR-BIZ 指标
> 5. **窗口标签页序列**——消费 wft02 的 PL6-A 活动节点需求定义，编排为窗口标签页序列，定义页面间流转规则、页面交互和 FR-BIZ 指标
> 6. **任务关系需求**——消费 wft02 的任务关系，定义任务间触发规则（触发条件/启动参数）
> 7. **支持信息引用需求**——文档间多对多引用的引用规则及引用角色标签
> 8. **引擎能力使用与指标分配**——逐业务页面形成引擎能力使用需求，将 FR-BIZ 指标分配到既有引擎/CU并判定覆盖关系；能力或指标不足时生成 FR-ENG 候选线索

本 Skill 负责：

1. **接收**——接收人类选中的 ≥1 个 BA 节点（`可以SR设计`/`待补充SR设计`）或有反馈的 SR-F，校验状态/类型/数量
2. **匹配**——按来源 BA、需求对象和主职责匹配已有需求节点，判定复用/扩展/新建
3. **定义菜单和场景编排需求**——明确场景入口、功能表单/主子表单序列、显示顺序、依赖和下钻关系
4. **定义实体与正文功能表单需求**——明确封面/正文字段、布局、交互、展示、校验和权限
5. **定义流程类窗口标签页序列需求**——将 PL6-A 转化为窗口标签页序列、流转规则和节点级交互差异
6. **定义任务关系与支持信息引用需求**——明确触发条件、启动参数和引用规则
7. **引擎能力使用与指标分配**——形成业务页面→引擎/CU的能力使用需求，将 FR-BIZ 指标分配到相应能力；现有能力或指标上限不能承接时生成 FR-ENG 候选线索，不在 biz 路径设计 CU
8. **覆盖自查与写回**——校验 BA 覆盖、追溯和下游可消费性，确认后推进到 `可构件开发`
9. **回修**——接收构件开发流水线退回的 `需wft03修订` 需求节点；根因在 BA 则退回 `需wft02修订`

本 Skill 不负责：

1. A1 平台引擎产品的 SR-F 设计（→ `wft03-eng-ba2sr`）
2. 非功能需求（→ `wft04-nfr-str2sr`）
3. PA 组件设计、CU 设计或实例配置、技术实现参数（→ 构件开发流水线）
4. 25 引擎资产写回（→ 仅只读参照，不写回 25）
5. 28 看板指标资产写回（→ 仅只读参照，看板指标方案从 BA 节点直接读取，不独立写回 28）
6. 引擎能力缺口的技术实现（→ 本 Skill 只输出线索，由 eng 路径判断并承接）
7. 主子表单的运行期实现；但本 Skill 必须定义所需主子关系、1:1 封面正文组装、1+N 下钻关系及其交互需求

## 二、功能表单与窗口标签页设计基础

> **本章定义**：功能表单、窗口标签页、三层页面编排（菜单标签页→场景标签页→页面组件）、布局组件、主子组装关系、引擎能力使用需求和 FR-BIZ 指标约束包——即本 Skill 的操作对象及其关系。权威定义见 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型)、[§2.2~§2.5](91-eos-biz-eng-spec.md#22-正式文档的组成)、[§3.2~§3.4](91-eos-biz-eng-spec.md#32-引擎及层级)、[§4](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)。操作流程见第三章。

> 本章只定义操作对象"是什么"，不定义"怎么做"（§A.2.3）。领域规则、覆盖自查清单、生命周期和变更传播协议放在章末。

### 2.1 功能表单定义

**功能表单**是功能引擎将物理表转换后的用户可操作界面单元（[91-eos-biz-eng-spec] §2.2）。其命名已揭示双重构成：

- **表单**——用户看到的界面载体：字段、表格、布局、TAB（引擎能力①：表单能力）
- **功能**——用户在表单上执行的操作：按钮、右键操作项、双击下钻（引擎能力②：功能能力）

功能引擎将物理表的数据结构**转换为表单**，再为表单**注入业务功能**，两者合称为**功能表单**。功能表单是运行时形态的抽象定义，由窗口标签页、全屏单据页、辅助栏标签页或弹窗页面等页面组件承载；配置页面不属于功能表单的页面组件。

> **从输出文档到功能表单需求**：每个 PL5 输出文档形成正文功能表单需求；正式文档还形成封面表单需求以及封面—正文 1:1 主子关系需求。若正文与其他文档存在层级引用，再形成 1+N 下钻需求。指标、看板等仍按相同文档模型处理。

功能表单按 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型) 选择页面组件承载：窗口标签页（列表模式/单据模式）、全屏单据页、辅助栏标签页（列表模式/单据模式）或弹窗页面。菜单引擎内置的场景编排能力（91 规范中简称“场景引擎”，不是独立引擎资产）把窗口标签页编排为场景标签页（初始态单窗/分屏态双窗），菜单树能力再把场景标签页编排进菜单标签页。列表页面、单据页、辅助栏、弹窗页和指标页面属于页面组件内部的布局组件，不是与页面组件并列的页面类型。

在引擎生成链中的位置（§2.3）：

```
物理表（实体引擎） → 功能表单及页面组件（功能引擎） → 场景标签页（@engine-menu 场景编排能力） → 菜单标签页（@engine-menu 菜单树能力）
```

- 物理表是用户看不到的底层数据
- **功能表单/主子表单**是同一概念——有子表单的功能表单即为主子表单（N≥1），无子表单的为简单功能表单（N=0），1+N 组装是功能引擎的运行期能力（§2.2 能力③）
- 场景业务通过菜单引擎内置的场景编排能力组织窗口标签页，并由菜单树能力发布为菜单标签页中的端到端工作台

### 2.2 三层页面编排

页面层级自顶向下为菜单标签页→场景标签页→页面组件，生成过程则自底向上执行：

- **窗口标签页**：单个实体数据在场景标签页中的展示载体，以列表页面或单据页面承载内容。本 Skill 描述业务角色需要哪些窗口标签页、标签页如何流转，以及每个标签页的字段可见性、操作按钮、校验、结果反馈和 FR-BIZ 性能指标。
- **场景标签页**：菜单引擎内置的场景编排能力将窗口标签页编排而成的页面集合，必须说明初始态单窗、双击下钻后的分屏态双窗、辅助栏和面包屑行为。
- **菜单标签页**：末级菜单 M4 打开的浏览器标签页，是一个场景业务的端到端工作台，由若干场景标签页组成；菜单引擎负责菜单树、M4 映射和场景标签页编排。

三层编排至少包含：

- **TAB 序列**：同层功能表单/主子表单按输出文档流转顺序呈现
- **表单依赖**：表单间生成、提交、引用和触发依赖
- **流程类页面序列**：由 PL6-A 活动节点形成的审批、派发、处理、验收等页面序列
- **主子与下钻关系**：正式文档封面—正文 1:1，以及关联文档的 1+N 下钻关系

主子组装由功能引擎在运行期实现；本 Skill 不设计实现机制，但必须给出所需组装关系和交互需求。

### 2.3 支撑引擎与 CU 能力参照

wft02-biz 已为每个 BA 末级对象标注支撑引擎。本 Skill 读取 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 的引擎/CU 能力结构，仅用于判断现有能力能否承接需求及定位缺口，不生成 CU 设计或配置参数。

**CU**：每个引擎包含若干可独立选配的配置单元，能力边界定义见 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md)。本 Skill 只读取其运行期能力作为参照，形成引擎能力使用需求，不修改 CU。页面组件、布局组件与构件体系见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)。

支撑引擎信息分三层，仅只读参照，不写回 25。支撑状态为"能力不足"的对象标注 `分解依据不足`，不补写引擎方案。

每个业务页面同时形成引擎能力使用需求：`业务页面 / 业务动作 / 引擎 / CU能力引用 / 输入 / 期望输出 / FR-BIZ指标 / 覆盖结论`。全部已确认的使用需求装配为 `FR-BIZ 指标约束包`，由 wft05-eng 消费。指标仍归属于原 FR-BIZ，不转为 NFR。

覆盖判定：Q1=能力和指标均已覆盖，直接引用；Q2=能力存在但指标上限不足，生成 FR-ENG 增强候选；Q3=IPO能力缺失，生成 FR-ENG 新增候选；Q4=引擎/CU边界不清，标记 `[需裁决]`。

### 2.4 需求定义要素

#### 2.4.1 公共要素

每条 SR-F 末级条目包含以下要素：

| 要素 | 说明 |
|------|------|
| **来源 BA** | BA 节点 ID、BA 消费版本、来源 BA 对象 ID |
| **输入线** | A2 / Bn / 横切 |
| **支撑引擎** | 来自 wft02-biz 引擎支撑信息 |
| **能力参照** | 可能承接该需求的引擎/CU（来自 25 号资产，仅作参照） |
| **页面组件与布局** | 页面组件：窗口标签页（列表/单据）、全屏单据页、辅助栏标签页（列表/单据）或弹窗页面；布局组件组合：多级横版、列表页面、单据页、辅助栏、弹窗页、指标页面的适用组合。完整定义见 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型) 和 [§4.1](91-eos-biz-eng-spec.md#41-布局组件) |
| **辅助栏** | 是否启用右侧辅助栏（是/否） |
| **功能描述** | 一句话说明系统在表单上提供什么功能 |
| **主表单字段** | 主表单的主要字段定义（字段名、数据类型、必填、唯一、默认值） |
| **功能按钮/操作项** | 主表单上的功能按钮和右键操作项（新建、保存、提交、删除等） |
| **主表单权限规则** | 主表单的行/列/按钮对角色或状态的可见可操作规则 |
| **子表单** | 子表单列表（字段定义、显示规则、触发条件）；无子表单时 N=0 |
| **功能流程** | 用户从触发到结果的操作步骤 |
| **功能规则** | 约束、校验、权限、状态、异常、指标口径 |
| **生命周期** | 存在任务类型或独立状态变迁时定义表单状态机（如草稿→已提交→审批中→已完成） |
| **校验规则** | 字段/行级/表单级校验 |
| **确认状态** | `[同意]` / `[修改]` / `[驳回]` + `[已处理]` |
| **验收口径** | 可独立验证该末级条目是否被系统承接 |
| **FR-BIZ性能指标** | 指标名称、目标值/判定值、适用条件、统计口径、测量方法和来源 OR/STR-F/BA |
| **引擎能力使用** | 引擎/CU引用、输入、期望输出、指标分配和覆盖结论 |

### 2.5 设计规则与匹配判定

#### 2.5.1 设计规则

**规则1：功能视角转换**。BA 的"业务怎么做"转成 SR-F 的"用户在表单上按什么按钮、走什么流程完成业务"。

**规则2：单主职责粒度**。每条 SR-F 末级只表达一个主系统职责（结构定义/录入提交/流程流转/指标计算等）。

**规则3：不替代引擎设计**。引擎能力不足不得写成业务功能 SR-F。

**规则4：不做 PA 配置规格**。SR-F 描述"系统必须提供什么功能"，不写入 CU 配置参数或构件方案。

#### 2.5.2 Q1/Q2/Q3 匹配判定

| 判定 | 条件 | 动作 |
|------|------|------|
| SR-Q1 | 已有 SR-F 对应同一 BA 对象、同一输入线、同一支撑引擎，且功能职责一致 | 复用已有 SR-F，追加 BA 引用 |
| SR-Q2 | 已有 SR-F 主体一致但功能规则、按钮操作、流程或验收口径需扩展 | 扩展已有 SR-F，全量重写该条功能定义 |
| SR-Q3 | 无可用已有 SR-F | 新建 SR-F 末级条目 |

#### 2.5.3 覆盖自查清单

覆盖自查在 Step 7 统一执行，先检查业务需求覆盖，再检查引擎能力参照和缺口路由。

**业务覆盖自查**：

1. A2 线：每个 SL5 场景业务均有用户可操作 SR-F 承接
2. A2 线：每个被编排的功能表单/主子表单均有需求定义承接
3. Bn 线：每个 PL5 输出文档/产品数据均有生成、维护或查询类 SR-F 承接
4. Bn 线：每个 PL5 输出文档的实体定义、实体关系、状态事件和业务规则均已被对应 SR-F 承接
5. 横切线：菜单可达、权限推导、上层指标方案均已转成必要 SR-F 或明确"不生成 SR-F"的理由
6. 追溯：每条 SR-F 均记录 BA 节点 ID、BA 对象 ID（即来源 BA 子对象在 23/24/26/28 中的资产 ID，wft02 资产写回未完成时可后补）、BA 消费版本
7. 页面模型：每条需求均区分页面组件与其内部布局组件，并说明其所在菜单标签页→场景标签页→窗口标签页编排链，组合与功能特征匹配

**引擎覆盖自查**：

8. 25 参照：每条需求记录支撑引擎及能力参照；能力不足项已形成 FR-ENG 线索或退回 wft02，不写 CU 配置参数

### 2.6 SR-F 节点生命周期

SR-F 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §A.6.2 通用六态定义表（wft03-biz 列）。

#### 2.6.1 推进态

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `待确认方案` | SR-F 方案已生成或修订，等待人类反馈 | §3 设计完成 |
| `可构件开发` | 方案已确认，可进入构件开发流水线 | 全部条目 `[同意]` + `[已处理]` |
| `在构件需求定义` | 构件开发流水线首 skill 已锁定此 SR-F，正在展开构件需求定义 | 下游写入活动锁 |
| `已构件需求定义` | 构件需求定义完成，SR-F 消费版本与当前版本一致 | 下游处理完成且未检测到上游新版本 |

本 Skill 写入 `待确认方案` / `可构件开发` / `需wft03修订`；下游流水线负责其自身的锁定态和完成态。

#### 2.6.2 BA 消费状态

| BA 状态 | 含义 | 本 Skill 动作 |
|---------|------|--------------|
| `可以SR设计` | BA 已确认，首次进入本 Skill | 生成或修订 SR-F |
| `待补充SR设计` | BA 已被旧版 SR-F 消费，上游新增/修订 | 按 BA 变更影响声明增量补全 SR-F |
| `在SR设计` | 本 Skill 正在处理 | 写入活动说明，避免并发重入 |
| `已SR设计` | SR-F 展开完成且 BA 消费版本一致 | 处理完成后写入 |

本 Skill 首次消费 BA 时在 SR-F 节点中记录 `BA 消费版本：v{N}`。重入时若 BA 当前版本 > SR-F 记录的消费版本，按 BA 变更影响声明判断增量型/修订型/结构型影响。

#### 2.6.3 下游退回态

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `需wft03修订` | SR-F 方案存在缺陷，需本 Skill 修订后重新交付 | 下游构件开发流水线写入，附带缺失说明 |

本 Skill 重入 `需wft03修订` 的需求节点时：读取缺失说明 → 按人类改进方案修订 → 人类确认 → `可构件开发`。若缺失根因在 BA（如 PL6-A/PL6-B 定义或支撑引擎信息缺失），将 BA 标为 `需wft02修订`，附带缺失说明。

### 2.7 BA → SR-F 变更传播协议

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。以下为本 Skill 特有的 BA→SR-F 影响判定与声明格式。

#### 2.7.1 变更类型判定（BA → SR-F 特化）

| 类型 | 判定条件 | SR-F 处理 |
|------|----------|-----------|
| **增量型** | BA 新增 SL5/PL5/权限/指标对象，既有对象未变 | 仅为新增对象生成 SR-F，既有 SR-F 不动 |
| **修订型** | BA 既有 IPO、编排、权限、指标口径或产品数据边界被修改 | 修订受影响 SR-F，全量重写受影响条目 |
| **结构型** | BA 场景边界、产品路径、场景部件结构或菜单结构重塑 | 输出影响范围，等待人类裁决后重组 SR-F |
| **缺失型** | BA 缺少必要 IPO、引擎支撑信息或变更声明 | 将 BA 标为 `需wft02修订` 候选，附缺失说明 |

#### 2.7.2 受影响范围判断

| BA 变化 | 可能影响 |
|---------|----------|
| SL5 场景业务变更 | A2 场景入口、场景流、场景指标 SR-F |
| PL5 场景部件变更 | A2 部件操作、Bn 文档处理、权限、指标 SR-F；若涉及实体结构或业务规则变更，同步影响对应实体定义和规则 SR-F |
| 文档主子关系变更 | 功能表单的主子组装关系（由引擎运行时处理，本 Skill 只记录变更通知） |
| 菜单路径变更 | 菜单可达性、权限级联 SR-F |
| 权限推导变更 | 菜单权限、字段权限、行级权限、按钮权限 SR-F |
| 指标口径变更 | 指标定义、计算、展示、聚合 SR-F |
| 引擎支撑信息变更 | 对应 CU、25 参照、分解依据 |

#### 2.7.3 变更影响声明格式

每次生成或修订 SR-F 后写入：

```text
SR-F 变更影响声明
来源 BA：BA-XXX vN
SR-F 当前版本：vM
变更类型：增量型 / 修订型 / 结构型
影响的功能表单：<受影响条目列表>
影响的组装关系：<TAB序列/流程节点序列等变化>
受影响构件：<如已知则列出；未知写"待下游检查">
建议动作：新增构件 / 修订构件 / 重做构件 / 人类裁决
```

### 3.1 Step Start

运行时 AI 按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策流程执行。先读取 `05-*.md`/`06-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表（"待 wft03-biz 处理"/"待反馈处理"/"待下游退回处理"），再按以下顺序处理。

#### 3.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| BA 状态不是 `可以SR设计`/`待补充SR设计` | 状态不符 | 列出不合格节点及状态 → **退出** |
| BA 含 A1 平台引擎产品 | 类型不匹配 | 提示分路径（→ `wft03-eng`）→ **退出** |
| BA 状态为 `需wft02修订` | 上游待修 | 输出缺失说明，提示回到 wft02-biz → **退出** |
| SR-F 状态为 `需wft03修订` 且人类未提供改进方案 | 退回方案缺失 | 输出下游缺失说明，提示提供改进方案 → **退出** |
| 无 BA 选中 + 无"待反馈处理"节点 + 无"待下游退回处理"节点 | 无待处理对象 | 输出"无待处理对象"→ **退出** |
| 选中 BA >5 个 | 超建议阈值（软提示） | 输出建议分批 → 人类确认后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出。逻辑上不可能的条件（状态不符、类型不匹配）为硬退出（§A.4.5）。

#### 3.1.2 退回优先（§A.4.3 门禁）

存在 `需wft03修订` 的 SR-F 节点（来自"待下游退回处理"分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注或下游 Skill 的具体改进指引）
- 已提供 → 通过门禁，读取下游缺失说明，按人类方案修订，人类确认后推进为 `可构件开发`
- 未提供 → 输出下游缺失说明 + 提示提供改进方案 → **退出**

#### 3.1.3 反馈处理

存在"待反馈处理"分节中的 SR-F 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理。全部已 `[同意]`+`[已处理]` 的条目跳过，不阻塞新 BA。

#### 3.1.4 新 BA 路由

有未处理的 BA 节点（来自"待 wft03-biz 处理"分节）→ 反馈处理完成后，逐 BA 节点进入 Step 1→Step 3 新设计流程。

**执行顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计）。反馈可能改变 SR-F 的功能定义或追溯关系，Step 3 必须基于 Step 2 修改后的内容，不得使用 Step 1 缓存的状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：Step 3~7 生成的菜单树与菜单标签页映射、场景标签页编排、功能表单、窗口标签页、引擎能力使用需求、FR-BIZ指标、任务关系和支持信息引用。各条目的 `确认状态` 字段位于 `05/06` 产品数据文档节点正文中。

**AI 处理流程**（对存在 `待确认方案` 的 SR-F 节点）：

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 BA 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3~6 同为设计者——先理解人类反馈在 BA 需求语境中的含义，再执行修订，最后检查修订后的 SR-F 是否仍满足 BA 需求。

本 Skill 特化参数（锚点需求 / 操作条目 / 推进目标 / 级联触发条件 / 资产对齐级联）见下表（按 [§A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 实例化）：

| 特化维度 | wft03-biz 值 |
|---------|-------------|
| **锚点需求** | 当前 SR-F 所承接的全部 BA 方案——人类反馈理解和修订均以 BA 角色的场景职责及其输出文档需求为最终锚点 |
| **操作条目** | Step 3~7 生成的菜单树与菜单标签页映射、场景标签页编排、功能表单、窗口标签页、引擎能力使用需求、FR-BIZ指标、任务关系和支持信息引用，确认状态位于 `05/06` 节点正文中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → 需求节点推进至 `可构件开发` |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过扫描。仅当本轮新输入满足以下任一条件时，清除 `[已处理]`（保留 `[同意]`）使其回到待处理：（1）新输入为该条目的直接上游节点（如新 BA 节点是 SR-F 条目的来源）；（2）新输入与条目同属一个架构层级且边界重叠（如同属 SR-F 功能表单，新表单改变了已有表单的范围或归属）；（3）新输入导致条目定义被修订（变更影响声明标注为修订型或结构型，§A.5.3 Step 1） |
| **级联触发条件** | `[修改]`/`[驳回]` 导致菜单映射、场景标签页边界、页面组件组合、功能表单结构、流程节点顺序或指标定义变化 → 标记受影响条目为 `[需重设计]` |
| **资产对齐级联** | 方案变更影响 05/06 资产引用 → 更新受影响 SR-F 的 BA 追溯引用 |

### 3.4 Step 3 · 菜单树与场景编排推导

> 本 Step 在窗口标签页详细设计（Step 4~5）之前，先从 BA 的结构信息推导菜单层级骨架、场景标签页划分和窗口标签页占位序列。产出为**骨架层**——窗口标签页此处仅以占位符存在（含页面 ID、来源 PL5、页面组件类型候选、显示顺序），字段/布局/交互/权限/校验的详细定义由 Step 4~5 填充，Step 4~5 不得更改占位符的页面 ID 和 TAB 顺序。菜单树和场景编排的权威定义见 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型)、[§1.4](91-eos-biz-eng-spec.md#14-平台菜单)、[§1.5](91-eos-biz-eng-spec.md#15-业务场景)、[§3.4](91-eos-biz-eng-spec.md#34-业务组装)。

**3.4.1 菜单树骨架推导**

从 BA 中提取业务域（PL1/SL1）、角色类型（SL3）、角色职责（SL4）、场景业务（SL5）四层信息，按以下规则映射到 ML 菜单层级 [91 §1.4]：

| 菜单层级 | 推导规则 | 来源 |
|---------|---------|------|
| **M1** | 业务域名称（如"采购管理"）。多个场景业务同属一个业务域时共用同一 M1 | BA 的 PL1/SL1 业务域归属 |
| **M2** | 按 SL3 角色类型分组——同一角色类型下的多个场景业务归入同一 M2。若 M1 下辖场景业务 ≤3 个，可省略 M2 直接将场景业务挂到 M1 下的 M3 | BA 的 SL3 角色类型 |
| **M3** | 按 SL4 角色职责分组——同一角色职责下的场景业务归入同一 M3。若 M2 下辖场景业务 ≤2 个，可省略 M3 直接将场景业务挂到 M2 下的 M4 | BA 的 SL4 角色职责 |
| **M4** | 末级菜单 = SL5 场景业务，1:1 映射。M4 名称取场景业务名称 | BA 的 SL5 场景业务 |

逐 M4 定义：
- M4 名称 + 映射的场景业务 ID
- M4 可见性候选（继承场景业务的角色范围，标注 `[推断]`）
- M4 单击后打开的菜单标签页所含场景标签页列表（见 3.4.2）

逐非末级节点（M1~M3）定义：
- 父节点归属、显示顺序（按 BA 中场景业务的首次出现顺序）、可见角色候选（下辖节点的角色并集，标注 `[推断]`）

> 若 wft02 的 BA 节点已标注菜单归属提示，优先采用；否则按上表规则全量标注 `[推断]` 供确认。菜单引擎（`@engine-menu`）对每条场景业务无条件支撑 [91 §1.4]，本 Step 不判定"能否支撑"。

**3.4.2 场景标签页骨架推导**

场景标签页是菜单引擎内置场景编排能力将窗口标签页组织而成的页面集合 [91 §1.2]。本子步骤在窗口标签页存在之前，从 BA 的输出文档序列和业务上下文中推导场景标签页的划分和编排骨架。

**输入**：BA 的 PL5 输出文档序列 + 文档流转顺序 + 下钻关系（来自 wft02 的文档间引用）+ PL6-A 活动节点归属。

**场景标签页划分规则**：

| 判定条件 | 动作 | 依据 |
|---------|------|------|
| 输出文档序列中发生**角色切换**（如从申请人→审批人），且切换后的角色需要独立的初始态入口 | 拆分为新场景标签页（新角色的首个页面为新场景的初始态单窗） | BA 的 PL6-A 活动节点的处理角色 |
| 文档间存在**下钻关系**（双击 A 文档行 → 打开 B 文档的子业务） | B 文档作为分屏态双窗目标，与 A 文档**同属一个场景标签页** | wft02 的文档间引用关系 + [91 §1.2 分屏态规则] |
| 连续输出文档无角色切换、无下钻关系 | 归入同一场景标签页，按流转顺序排列 TAB | 默认 |

逐场景标签页定义：
- **初始态单窗**：用户首次进入该场景时全宽显示的窗口标签页占位符。通常为输出文档序列中该场景的第一个列表页；若场景首个文档为单据页（如直接创建表单），则以单据页为初始态
- **分屏态双窗**：逐下钻关系定义——触发条件（双击哪个占位符的哪类行数据）、右窗目标占位符、上下文传递字段映射（左窗选中行→右窗的过滤/关联字段，来自 BA 的文档引用字段）
- **辅助栏**：逐窗口标签页占位符判定——该页面是否需要不下钻即可查看/编辑行详情？是→启用辅助栏（标注辅助栏显示模式：列表/单据）；否→不启用。默认规则：列表页启用辅助栏，单据页和弹窗页不启用。交互行为见 [91 §1.3]
- **面包屑**：层级路径 = M4 名称 → 初始态占位符名称 →（分屏态目标占位符名称，递归）。初始态单窗无面包屑 [91 §1.2]

**场景标签页的数量判定**：
- 仅一个角色 + 无下钻 → 1 个初始态单窗场景标签页（特殊情形：无 TAB）
- 有下钻无角色切换 → 1 个初始态单窗 + N 个分屏态目标（N = 下钻层级数，受系统层级限制）
- 有角色切换 → 每个角色 1 个场景标签页（各自含初始态单窗 + 各自下钻链）

**3.4.3 窗口标签页占位符定义**

为每个 PL5 输出文档生成一个**窗口标签页占位符**，按输出文档流转顺序排列为 TAB 序列：

逐占位符定义（仅骨架，不含字段和交互）：
- **页面 ID**：分配稳定页面 ID，格式 `@srf-tab-{场景业务简称}-{序号}`，使页面 NFR 可绑定到具体页面 [91 §1.2 七种页面类型]
- **来源**：PL5 输出文档 ID + BA 节点 ID + BA 消费版本
- **页面组件类型候选**：列表模式 / 单据模式。判定依据——台账/指标/看板/WBS/风险清单等集合型正文 → 列表模式；流程/工单的活动节点页 → 单据模式。全量标注 `[推断]`，Step 4 可修正类型但不得更改页面 ID
- **显示顺序**：在 TAB 序列中的位置（按输出文档流转顺序 [91 §1.5]）
- **所属场景标签页**：标注归属的场景标签页 ID（见 3.4.2 划分结果）
- **组装关系注解**：正式文档标注"需 1:1 封面—正文主子组装"；存在下钻关系标注"需 1+N 下钻组装→目标占位符 ID"；轻量文档标注"无封面组装"。组装由功能引擎运行期完成 [91 §3.4]，本 Skill 只声明需求

> 占位符的字段定义、布局、交互行为、功能按钮、权限、校验规则和 FR-BIZ 指标由 Step 4（正文功能表单需求）填充；PL6-A 活动节点的窗口标签页序列由 Step 5 消费占位符后编排。Step 4~5 不得更改占位符的页面 ID、TAB 顺序和场景归属；如需调整页面组件类型或组装关系，须回写到占位符并标注 `[变更]`，同步更新受影响场景标签页的编排。

**3.4.4 页面 ID 分配与标注**

| 对象 | ID 格式 | 示例 |
|------|--------|------|
| 菜单标签页 | `@srf-menu-{M4简称}` | `@srf-menu-purchase-apply` |
| 场景标签页 | `@srf-scene-{场景业务简称}-{序号}` | `@srf-scene-purchase-apply-1` |
| 窗口标签页占位符 | `@srf-tab-{场景业务简称}-{序号}` | `@srf-tab-purchase-apply-01` |

全量标注：每条产出记录所属菜单标签页、场景标签页、场景业务、来源 BA 节点和 BA 消费版本。AI 推断的菜单层级、场景划分、TAB 顺序、页面组件类型候选均标注 `[推断]` 供确认。`[推断]` 项在 Step 2（反馈处理）中由人类确认或修正。

### 3.5 Step 4 · PL5 输出文档：实体与功能表单定义

> 逐 PL5 输出文档，先消费 BA 的文档方案（wft02 Step 5）提取实体结构、定义实体字段（§7.3 Task 3），再将正文实体转化为功能表单需求（§7.3 Task 4），最后为功能表单选择页面组件与布局组件组合。Step 3 产出的窗口标签页占位符在此被填充字段/布局/交互/权限/校验的详细定义，但不得更改占位符的页面 ID、TAB 顺序和场景归属。实体与文档模型的权威定义见 [91 规范 §二](91-eos-biz-eng-spec.md#二输出文档模型)，引擎能力见 [§3.2](91-eos-biz-eng-spec.md#32-引擎及层级)。

**3.5.1 输出文档定义消费**

逐 PL5 输出文档，从 BA 节点中提取以下信息（wft02 已产出，本步骤只读消费）：

| 提取项 | 来源（BA 节点字段） | 用途 |
|--------|-------------------|------|
| 文档类型 | wft02 Step 5 判定结果——正式 / 轻量 | 决定是否生成封面实体 |
| 封面字段（正式文档） | wft02 Step 5”封面字段”列表——单据号/标题/状态/版本/创建人/部门/日期等 [91 §2.2] | → Task 3 实体字段定义 |
| 正文实体结构 | wft02 Step 5”正文实体结构”——实体名称、核心字段及类型线索 | → Task 3 实体字段定义 |
| 正文转化引擎 | wft02 Step 5”正文转化引擎”——如 @engine-ledger / @engine-flow / @engine-indicator 等 | → Task 4 功能表单类型判定 |
| 任务类型 | 计划 / 流程 / 工单 / 无（wft02 Step 6 PL6-A 需求） | → Task 4 功能按钮集合、Step 5 窗口标签页序列 |
| PL6-B 条目类型 | wft02 Step 7 三独立判定通过的条目类型清单 | → §3.5.5 PL6-B 条目需求转化 |
| 支持信息引用 | wft02 Step 5 文档间引用关系及角色标签 | → Step 6 引用需求 |
| 角色范围 | BA 的 SL3/SL4 角色归属 + PL6-A 活动节点的处理角色 | → 权限推导 |

> 若 BA 缺少某项信息（如正文转化引擎未标注、封面字段列表为空），将该 PL5 文档标记为 `分解依据不足`，在 Step End 输出缺失说明并建议退回 `需wft02修订`。不得自行补做 BA 设计。

**3.5.2 实体需求定义**

根据文档类型，分两路定义实体：

**正式文档**：

| 实体 | 字段来源 | 定义规则 |
|------|---------|---------|
| **封面实体**（DocumentCover 表） | BA 的”封面字段”列表 | 逐字段：名称（取 BA 字段名）、数据类型（单据号→VARCHAR、日期→DATE、状态→枚举等，按字段语义推断，标注 `[推断]`）、必填/唯一/默认值（ID 类字段必填+唯一，日期字段默认当前日期，状态字段默认”草稿”） |
| **正文实体**（1:1 绑定封面行） | BA 的”正文实体结构” | 逐字段：名称、数据类型（按字段语义推断——金额→DECIMAL、数量→INT、文本→VARCHAR/TEXT）、必填/唯一/默认值、校验（按业务规则推断——金额>0、日期不晚于当前等） |

封面行与正文行关系：`derived_from` 追溯链 + 严格 1:1 [91 §2.5 R3]。

**轻量文档**：

仅定义正文实体字段（无封面实体），规则同上。正文实体即为文档本身，1 行 = 1 文档内容条目实例。

**字段定义要素**（逐字段）：

| 要素 | 说明 |
|------|------|
| 字段名 | 中文名 + 英文字段名（蛇形命名） |
| 数据类型 | VARCHAR(n) / INT / DECIMAL(m,n) / DATE / DATETIME / TEXT / 枚举 |
| 必填 | 是 / 否 |
| 唯一 | 是 / 否 |
| 默认值 | 有则写明，无则留空 |
| 校验规则 | 字段级约束（范围/格式/引用完整性） |
| CRUD | 新建时可见/可编辑、更新时可见/可编辑、删除规则、查询可见 |
| 追溯关系 | 来源字段映射——该字段对应 BA 输出文档定义中的哪个字段或哪个业务规则 |

**26 资产对齐**：逐字段检查 [26 号资产](../../80-pl4eos-2-eosdata/26-eos-document-definitions.md) 是否有同名同语义的已有字段定义。Q1→引用已有字段名和类型；Q2→引用+扩展约束；Q3→新建字段。资产对齐结论写入字段定义，不入增量清单。

**实体关系**：
- 正式文档：DocumentCover 实体 ← 1:1 → 正文实体（通过 DocumentCover 行的 `derived_from` 字段追溯）
- 轻量文档：正文实体独立存在，无关联实体
- 存在支持信息引用时：记录引用目标（正式文档→DocumentCover 行，轻量文档→正文实体行），引用字段定义由 Step 6 完成

**3.5.3 正文功能表单需求定义**

在实体字段定义完成之后，将正文实体转化为功能表单需求。功能表单 = 表单（字段布局/展示）+ 功能（按钮/操作），由对应引擎转化 [91 §3.2]。

**引擎→功能表单类型映射**：

| 正文转化引擎（来自 BA） | 功能表单类型 | 默认展示方式 | 典型按钮/操作集 |
|------------------------|------------|------------|---------------|
| @engine-ledger | 台账功能表单 | 列表（表格/树表） | 新建/编辑/删除/导入/导出/批量操作 |
| @engine-flow | 流程功能表单 | 单据（单据布局） | 提交审批/通过/驳回/撤回/催办 |
| @engine-workorder | 工单功能表单 | 单据（单据布局） | 派发/处理/验收/关闭/转派 |
| @engine-indicator | 指标功能表单 | 列表 + 图示 2×3 网格 | 新建/编辑/删除/切换视图 |
| @engine-kanban | 看板功能表单 | 视图/卡片/泳道 | 新建卡片/拖拽/筛选/切换视图 |
| @engine-task | 计划功能表单 | 甘特/任务列表 | 新建任务/编辑/标记完成/调整依赖 |
| @engine-project | 项目功能表单 | 阶段/里程碑列表 | 新建阶段/编辑里程碑/更新进度 |
| @engine-wbs | WBS 功能表单 | 树形分解列表 | 新建节点/拆分/合并/更新进度 |
| @engine-progress | 进展功能表单 | 列表 | 填报进展/更新状态/查看历史 |
| @engine-scheduler | 定时任务功能表单 | 列表 | 新建任务/编辑触发规则/启用/停用 |

**功能表单定义**（逐 PL5 输出文档）：

1. **字段布局**：正文实体字段 → 表单布局区排列。列表模式——字段映射到表格列（前 5~8 个核心字段为默认列，其余可配置）；单据模式——字段分组排列（基础信息/业务详情/附件 等字段组），每行 1~2 列
2. **功能按钮**：默认按钮集（上表”典型按钮/操作集”）+ 任务类型加项（流程→提交审批/通过/驳回、工单→派发/验收、计划→策划→发布）。按钮状态随文档生命周期联动（草稿→提交审批可见、审批中→通过/驳回可见、已完成→全部操作按钮禁用）
3. **筛选/排序/分页**：列表模式默认启用——列头筛选（核心字段）、多列排序、分页器（默认 20 条/页）。单据模式不启用分页
4. **导入/导出**：台账功能表单默认启用导入（含模板下载）和导出（Excel）；其余类型按需启用
5. **权限**：行/列/按钮对角色或状态的可见可编辑规则——从 BA 的 SL3/SL4 角色归属和 PL6-A 活动节点的处理角色推导，标注 `[推断]`
6. **校验**：字段级校验（来自实体字段定义）+ 表单级校验（提交时的业务规则——如流程提交时必须填写审批意见）+ 状态前置校验（按钮仅在对应状态下可用）
7. **状态反馈**：操作结果 Toast（成功/失败/警告）+ 数据状态标签（审批中/已通过/已驳回/草稿，颜色见 [91 §4.2 反馈类·状态标签]）
8. **FR-BIZ 性能指标**：记录该功能表单承接的 FR-BIZ 指标（来自 BA 的 IPO 性能指标），含指标名称/目标值/适用条件/统计口径/测量方法，留待 Step 7 分配到引擎/CU

**3.5.4 页面组件与布局组件选择**

为功能表单选择承载的页面组件 [91 §1.2] 和内部布局组件组合 [91 §4.1]：

| 功能表单类型 | 页面组件 | 布局组件组合 |
|------------|---------|------------|
| 台账功能表单 | 窗口标签页（列表模式）| 多级横版 + 列表页面 |
| 流程/工单功能表单 | 窗口标签页（单据模式）| 多级横版 + 单据页 |
| 指标功能表单 | 窗口标签页（列表模式）| 多级横版 + 指标页面（含列表页面模式切换） |
| 看板功能表单 | 窗口标签页（列表模式）| 多级横版 + 列表页面（含卡片/泳道布局） |
| 计划/WBS/项目功能表单 | 窗口标签页（列表模式）| 多级横版 + 列表页面（含甘特条/树节点/里程碑） |
| 查看详情 | 全屏单据页 | 单据页（无 TAB 栏） |
| 行详情不下钻 | 辅助栏标签页（单据模式）| 辅助栏 + 单据页 |
| 字段值引用选择 | 弹窗页面 | 弹窗页 + 列表页面 |

判定优先级：正文功能表单类型（§3.5.3 映射表） > 用户操作上下文（列表浏览 / 单据详情 / 弹窗选择）> 默认规则。辅助栏启用判定见 §3.4.2。选择结果填充到 Step 3 产出的窗口标签页占位符，不得更改占位符的页面 ID。

**3.5.5 PL6-B 正文条目需求转化**

仅当 PL5 输出文档的正文条目经 wft02 Step 7 三独立判定通过后，才进入本子步骤：

1. **消费**：读取 BA 的 PL6-B 条目类型清单——每类条目含名称、定义要素、生命周期和正文支撑引擎（均来自 wft02）
2. **转化**：逐 PL6-B 条目类型定义：
   - **条目字段**：将条目的定义要素展开为字段——指标条目→名称/口径/目标/维度/图示类型、看板条目→名称/布局/指标集/视图类型、风险条目→描述/概率/影响/缓解措施/状态、问题条目→描述/根因/纠正措施/状态、计划条目→名称/起止日期/依赖/交付物/状态
   - **条目表单**：条目字段的展示方式（列表模式展示条目集合、单据模式展示单条目详情）
   - **条目生命周期**：将 wft02 定义的条目生命周期转化为条目的状态机（如指标条目：草稿→已发布→已修订→已废弃）+ 状态变迁规则 + 各状态下可执行的操作
   - **条目约束**：条目间的引用关系（如看板条目引用指标条目）、唯一性约束（条目名称在容器内唯一）
3. **去重**：轻量文档的原子正文行（1 行 = 1 文档实例）不得展开为 PL6-B；PCA 定义型/管理型条目须逐类判定，不得整包作为 PL6-B 展开
4. **不独立生成页面**：PL6-B 条目是正文功能表单的内容展开——指标条目在指标功能表单中逐条展示、看板条目在看板功能表单中逐条展示。PL6-B 不生成独立的页面组件或窗口标签页

### 3.6 Step 5 · 窗口标签页序列编排

> 对有任务类型（计划/流程/工单）的 PL5 输出文档，消费 wft02 的 PL6-A 活动节点需求定义 [91 §7.2 Task 6]，将活动节点序列编排为窗口标签页序列，定义页面间流转规则和逐标签页的交互差异（§7.3 Task 5）。无任务类型的文档跳过本 Step，仅保留 Step 4 的正文功能表单需求。

**3.6.1 前置判定**

逐 PL5 输出文档检查 BA 的 PL6-A 活动节点清单：

| BA 信息 | 判定 | 动作 |
|---------|------|------|
| 有任务类型（计划/流程/工单）+ 有 PL6-A 活动节点 | 进入本 Step | 按 §3.6.2~§3.6.6 处理 |
| 有任务类型但 PL6-A 活动节点清单为空 | BA 信息不完整 | 标记 `分解依据不足`，退回 `需wft02修订` |

活动节点清单来自 wft02 Step 6——wft01 在业务语言层捕获主要节点（"部门经理审批，通过后到财务"），wft02 在架构语言层补全为完整的活动节点序列（含系统自动节点、异常路径、超时处理），全量标注 `[推断]` [91 §7.2]。

**3.6.2 PL6-A 活动节点消费**

逐 PL6-A 活动节点，从 BA 中提取以下要素（wft02 已产出，本步骤只读消费）：

| 要素 | 来源 | 说明 |

| 活动节点名称 | wft02 Step 6 节点定义 | 如"部门经理审批""财务审核""采购员创建" |
| 处理角色 | wft02 Step 6 定义的处理角色 | 该节点由哪个角色操作 |
| 可执行动作 | wft02 Step 6 定义的动作列表 | 如通过/驳回/退回修改/转派/催办 |
| 状态变迁 | wft02 Step 6 定义的状态迁移 | 执行动作后文档状态的变化——如"通过→状态=审批中→已通过" |
| 前置状态 | 状态变迁的起点 | 文档进入该节点时必须处于什么状态 |
| 系统自动节点 | wft02 Step 6 定义 | 无人类操作的自动处理节点——如"超时自动驳回""数据校验通过后自动流转" |
| 异常路径 | wft02 Step 6 定义 | 异常情况的处理——如"审批人不存在→转派上级""数据校验失败→退回提交人" |

**3.6.3 活动节点 → 窗口标签页映射**

| 节点类型 | 映射规则 | 页面组件类型 |
|---------|---------|------------|
| 人类操作节点 | **1 节点 = 1 窗口标签页**（单据模式）。该标签页展示文档单据 + 操作按钮，处理角色在此页面上执行动作 | 窗口标签页（单据模式）|
| 系统自动节点 | **不生成独立窗口标签页**。将自动节点的触发条件、处理逻辑和状态变迁合并到前一或后一人类操作节点的标签页定义中，标注"含系统自动处理：{逻辑描述}" | — |
| 异常路径 | 两种情况——（a）异常处理后回到原流程→不生成独立标签页，作为前一节点的异常分支定义；（b）异常需要人工介入（如异常审批、管理员修正）→生成独立窗口标签页 | 窗口标签页（单据模式）或不生成 |

**标签页序列编排**：按活动节点的执行顺序排列窗口标签页——提交→审批→（下一个审批→）归档/完成。系统自动节点不占位，其逻辑附着到前序人类操作节点。

**3.6.4 标签页逐项定义**

逐窗口标签页（即逐人类操作节点）定义：

1. **标签页标识**：分配页面 ID（格式 `@srf-tab-{场景业务简称}-act-{序号}`），标注来源 PL6-A 节点 ID、来源 BA 节点 ID 和 BA 消费版本
2. **页面组件与布局**：页面组件 = 窗口标签页（单据模式）；布局组件 = 多级横版 + 单据页。活动节点标签页固定为单据模式——处理人员需要在单据布局下查看完整文档并执行操作
3. **字段可见/可编辑差异**：逐实体字段，按处理角色判定——
   - 处理角色可查看的字段 → **可见**
   - 处理角色可编辑的字段 → **可编辑**（如审批人可填写审批意见、但不可修改申请人填写的业务数据）
   - 与该节点无关的字段 → **隐藏**
   - 判定依据：字段的 CRUD 属性（§3.5.2）+ 处理角色对该字段的权限。角色在 BA 中无对应权限定义时，默认规则——申请人可编辑申请字段、审批人只读申请字段+可编辑审批意见字段
4. **可执行动作 → 功能按钮**：将活动节点的可执行动作映射为单据页上的功能按钮 [91 §4.2 交互类·功能按钮]——
   - 通过 → `[通过]` 按钮（主按钮样式）
   - 驳回 → `[驳回]` 按钮（次按钮样式，需强制填写驳回理由）
   - 退回修改 → `[退回修改]` 按钮（次按钮样式）
   - 转派 → `[转派]` 按钮（次按钮样式，弹出人员选择弹窗）
   - 催办 → `[催办]` 按钮（链接样式）
   - 提交 → `[提交]` 按钮（主按钮样式）
   - 保存草稿 → `[保存]` 按钮（次按钮样式）
5. **校验规则**：节点操作的前置校验——
   - 必填字段完整性（审批意见、驳回理由等强制填写字段不得为空）
   - 状态前置条件（仅当前置状态匹配时按钮才可用）
   - 权限校验（仅处理角色可见操作按钮）
6. **状态变迁**：逐可执行动作定义——
   - 前提状态：文档进入该节点时的状态
   - 动作：审批人点击 `[通过]`
   - 后置状态：文档状态变为下一活动节点的前置状态
   - 记录方式：`{前提状态} --[{动作}]--> {后置状态}`
7. **异常路径处理**：
   - 异常条件（如审批人不存在、数据校验失败）
   - 异常动作（自动转派/退回提交人/通知管理员）
   - 异常后的状态和下一节点
   - 异常反馈（页面提示内容）
8. **超时处理**：
   - 超时时限和计时起点（从文档进入该节点开始计时）
   - 超时动作（自动通过/自动驳回/催办通知/升级到上级）
   - 超时后的状态变迁和下一节点
9. **结果反馈**：操作完成后的反馈方式 [91 §4.2 反馈类]——
   - 成功：Toast 提示（如"审批通过"）
   - 失败：Toast 提示 + 错误原因（如"审批意见不能为空"）
   - 状态标签更新：文档状态标签同步更新（如从"审批中"→"已通过"）
10. **FR-BIZ 性能指标**：该窗口标签页承接的 FR-BIZ 指标（来自 BA 的 IPO 性能指标），如审批时限、处理量等，留待 Step 7 分配到引擎/CU

**3.6.5 页面间流转规则定义**

基于状态变迁链，定义窗口标签页之间的流转规则：

| 流转类型 | 定义规则 | 示例 |
|---------|---------|------|
| **顺序流转** | 前一节点的后置状态 = 后一节点的前置状态 → 前一标签页操作完成后自动打开下一标签页 | 提交→审批：提交后状态变为"待审批"，审批标签页的前置状态="待审批" |
| **条件分支** | 同一节点有多个可执行动作，不同动作导向不同后置状态 | 审批通过→下一审批节点；审批驳回→退回提交节点 |
| **回退流转** | 后置状态指向已有标签页的前置状态 → 回到已有标签页（不新建） | 驳回→回到提交人的标签页，状态变为"待修改" |
| **异常流转** | 异常路径触发→异常标签页或异常状态 | 超时自动驳回→回到提交人标签页 |
| **终止流转** | 后置状态为终态（已通过/已驳回/已完成/已关闭）→不打开新标签页，当前标签页显示终态 | 最终审批通过→状态"已通过"，无下一标签页 |

流转上下文传递：标签页间的数据传递——前一标签页的处理意见、时间戳、操作人信息自动带入下一标签页。传递字段来自状态变迁的定义。

**3.6.6 任务状态附着位置判定**

| 文档类型 | 任务状态附着 | 说明 |
|---------|------------|------|
| 正式文档 | DocumentCover 封面行 | 封面行的状态字段承载任务生命周期——审批中/已通过/已驳回/已完成。封面单据页展示任务状态标签 [91 §2.5 R6] |
| 轻量文档 | 正文实体行 | 正文实体的状态字段承载任务生命周期。因无封面，任务状态由对应引擎（流程/工单/计划）在正文实体上直接管理 [91 §2.4] |

> 任务状态的读写由功能引擎在运行时按 CU 定义执行；本 Step 只声明"该文档的任务状态附着在哪个实体上"，不设计引擎实现机制。

### 3.7 Step 6 · 任务关系与文档引用定义

**3.7.1 wft02 任务关系与引用信息消费**

从 BA 中提取两类信息（wft02 已产出，本步骤只读消费）：

**任务关系**（来自 wft02 Step 8"任务关系引擎化"）：

| 引用角色标签 | 输入文档 / 规范文档 / 指南文档 / 合规文档 / 资源文档 [91 §2.2] | → Task 7 角色标签 |

**3.7.2 任务间触发规则定义**

逐条任务关系（来源任务→目标任务），定义触发规则：

1. **触发条件**：
   - 触发事件类型——`任务完成` / `任务到达指定节点` / `任务状态变更`
   - 条件表达式——仅当来源任务的结果满足条件时才触发（如 `来源任务.审批结果 = '通过'`、`来源任务.最终状态 = '已完成'`）。条件字段来自来源任务的状态变迁定义（§3.6.4 第 6 项）
   - 不触发情形——明确列出不触发的情形（如驳回→不触发下游、终止→不触发下游）

2. **启动参数**——目标任务被触发启动时需传入的数据：

| 参数 | 来源 | 说明 |
|------|------|------|
| 来源文档 ID | 来源任务的 PL5 输出文档实例 ID | 建立任务间追溯链 |
| 来源任务实例 ID | 来源任务的任务实例 ID | 追溯具体触发来源 |
| 传递字段 | 来源文档的关键字段→目标文档的对应字段 | 如"采购申请单号→采购订单的申请单号引用" |

3. **任务类型兼容性**：计划/流程/工单可任意触发任意类型（含同类型）[91 §2.5 R5]。不因类型不同而禁止触发，只记录类型组合供 Step 7 分配引擎能力时参考。

4. **首个有任务类型的文档**：场景业务中第一个有任务类型的输出文档，其任务类型必为**计划** [91 §2.5 R4]。该文档本体的任务类型是计划（策划→发布），不是其他文档的触发源。此约束由 wft01/wft02 判定，本 Step 只校验不重新判定——若发现首个有任务类型的文档不是计划，标记 `[需裁决]`。

**3.7.3 文档间引用需求定义**

逐条文档间引用关系，定义引用规则：

1. **引用目标定位**：
   - 引用目标为正式文档 → 指向该文档的 **DocumentCover 行**（通过 DocumentCover 的唯一 ID 引用）
   - 引用目标为轻量文档 → 指向该文档的**正文实体行**（通过正文实体的唯一 ID 引用）
   - 依据：[91 §2.2 支持信息]

2. **引用角色标签**：逐引用关系标注角色标签——`输入文档`（前序流程产出、作为本流程输入）/ `规范文档`（定义本流程需遵守的标准/规范）/ `指南文档`（提供操作指引）/ `合规文档`（证明合规性的证据文档）/ `资源文档`（提供参考信息的数据/模板）。角色标签来自 wft02 Step 5 的定义

3. **引用基数约束**：
   - 一对一：引用源只能关联一个引用目标（如一个采购订单只能关联一个采购申请）
   - 一对多：引用源可关联多个引用目标（如一个检验报告可引用多个检验标准）
   - 多对多：多个引用源可关联多个引用目标（如多个看板可引用多个指标）
   - 基数来自 BA 的文档间关系定义

4. **引用完整性约束**：
   - 引用目标必须存在（不得悬空引用）
   - 引用目标的状态必须允许被引用（如已废弃的文档不可作为规范文档被引用）
   - 删除引用源时，被引用的目标不受影响（引用是单向依赖）

5. **引用展示需求**：
   - 列表模式：引用在正文功能表单中以"关联文档"TAB 或侧边栏展示
   - 单据模式：引用在正文单据页中以"引用文档"字段组展示，含目标文档超链接

**3.7.4 一致性校验**

逐场景业务校验以下三项无矛盾：

| 校验维度 | 检查内容 | 矛盾示例 | 处理 |
|---------|---------|---------|------|
| **任务触发 vs 文档流转** | 任务触发链的顺序是否与输出文档流转顺序一致 | 文档流转为 A→B→C，但任务触发为 C→A（循环触发与文档顺序矛盾） | 标记 `[需裁决]`，说明矛盾点 |
| **任务触发 vs TAB 顺序** | 任务触发的目标文档 TAB 是否在来源文档 TAB 之后 | 来源文档 TAB=3，目标任务触发打开了 TAB=1 的文档（回退不通过面包屑） | 判定触发类型的合理性——驳回/退回修改类触发允许回退，新建类触发不允许回退 |
| **引用依赖 vs 文档流转** | 文档 A 引用了文档 B，文档 A 是否在 B 之后（或同时）生成 | A 引用了 B 但 A 的流转顺序在 B 之前（B 还不存在时 A 已生成） | 标记 `[需裁决]`——可能为模板引用（B 是静态规范文档，可提前存在）或顺序错误 |

校验通过后，任务触发规则和引用需求写入 `05/06`，标注 `[推断]` 供确认。

### 3.8 Step 7 · 引擎能力使用、指标分配与缺口路由

> 汇集 Step 3~6 产出的全部业务页面，逐页面对照 [91 §3.2](91-eos-biz-eng-spec.md#32-引擎及层级) 的引擎职责和 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 的引擎/CU 能力范围，判定能力覆盖关系（Q1~Q4）、分配 FR-BIZ 指标到对应引擎/CU、生成能力缺口候选线索，最后装配 FR-BIZ 指标约束包（§7.3 Task 8）。biz 路径不设计 CU——本 Step 只引用既有能力并判定覆盖，能力不足时生成候选线索而非自行设计。

**3.8.1 引擎能力需求汇集**

从 Step 3~6 的产出中，逐业务页面提取引擎依赖和 FR-BIZ 指标：

| 来源 Step | 业务页面类型 | 涉及的引擎 | 携带的 FR-BIZ 指标 |
|----------|------------|----------|------------------|
| Step 3 | 菜单树、场景标签页（编排层） | @engine-menu | 菜单可达性、场景切换响应时间 |
| Step 4 | 正文功能表单（PL5 输出文档） | @engine-entity（实体字段）+ 正文转化引擎（§3.5.3 映射表——如 @engine-ledger / @engine-flow 等） | 正文功能表单的 FR-BIZ 指标（§3.5.3 第 8 项） |
| Step 5 | 窗口标签页序列（PL6-A 活动节点） | @engine-flow / @engine-task / @engine-workorder（取决于任务类型） | 窗口标签页的 FR-BIZ 指标（§3.6.4 第 10 项） |
| Step 6 | 任务触发关系、文档引用 | @engine-task / @engine-flow / @engine-workorder（任务触发）+ @engine-entity（引用外键） | —（任务关系和引用无独立指标，指标附着在来源页面） |

汇集后形成 `{业务页面 → 引擎 → 业务动作 → 期望输出 → FR-BIZ指标}` 的需求行清单。每个需求行 = 一个业务页面的一次引擎能力使用。

> 覆盖判定以**引擎/CU**为单位（非以业务页面为单位）——同一引擎被多个业务页面依赖时合并判定，不逐页重复评估。

**3.8.2 25 号资产对照与能力覆盖判定**

逐引擎，按以下步骤执行覆盖判定：

**步骤一：读取 25 号资产的能力范围**

逐需求行涉及的引擎，读取 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 中该引擎的 CU 清单和能力定义：
- 该引擎有哪些 CU（配置单元）
- 每个 CU 的运行期能力（输入/输出/功能边界/性能指标上限）
- 只读参照，不写回 25

**步骤二：逐需求行判定覆盖关系**

| 判定 | 条件 | 动作 | 输出 |
|------|------|------|------|
| **Q1** | 25 资产中已有 CU 的能力范围覆盖该需求行的业务动作+期望输出，且 FR-BIZ 指标在 CU 的性能上限之内 | 记录引擎/CU 引用、资产版本、覆盖证据；不生成 CU 配置参数 | `引擎能力使用需求` 行，覆盖结论=Q1 |
| **Q2** | 已有 CU 的能力范围覆盖业务动作+期望输出，但 FR-BIZ 指标**超出**CU 的性能上限 | 记录指标差距（当前上限 vs 需求目标）；生成 FR-ENG 增强候选 | `引擎能力使用需求` 行（覆盖结论=Q2）+ FR-ENG 候选线索 |
| **Q3** | 25 资产中**不存在**可承接该业务动作的 CU，或缺少构件/布局组件/引擎能力 | 按 [91 §4.4](91-eos-biz-eng-spec.md#44-扩展规则) 标注缺口层级（构件级 / 布局组件级 / CU 级）；生成 FR-ENG 新增候选 | `引擎能力使用需求` 行（覆盖结论=Q3）+ FR-ENG 候选线索 |
| **Q4** | 引擎/CU 的能力边界在 25 资产中定义不清，无法判定是否覆盖 | 标记 `[需裁决]`，说明边界不清的具体问题；**不得自行设计 CU** | `引擎能力使用需求` 行（覆盖结论=Q4）+ 裁决项 |
| **无法判定** | wft02 未标注支撑引擎，或 BA 的引擎支撑信息缺失 | 退回 `需wft02修订`，附缺失说明；**不得由本 Skill 自行补做 BA 或引擎设计** | 退回记录 |

**步骤三：判定方法**

- 匹配粒度：业务动作 vs CU 运行期能力——“业务页面上的'提交审批'按钮”匹配 @engine-flow 的”审批流转能力”，不是匹配”流程引擎”这个整体
- 指标比较：FR-BIZ 指标的目标值与 CU 性能上限的数值比较——如需求”审批响应 ≤ 2h”、CU 上限”审批响应 ≤ 30min” → Q1 覆盖；需求”审批响应 ≤ 2h”、CU 上限”审批响应 ≤ 4h” → Q2 不足
- 语义匹配：业务动作的描述与 CU 能力描述的语义一致性——“派发”匹配 @engine-workorder 的”工单派发能力”，”看板布局”匹配 @engine-kanban 的”看板视图配置能力”

**3.8.3 FR-BIZ 指标分配**

逐需求行的 FR-BIZ 指标，分配到对应引擎/CU：

| 指标来源 | 分配目标 | 分配方式 |
|---------|---------|---------|
| 正文功能表单的 FR-BIZ 指标（§3.5.3） | 正文转化引擎 | 指标名称、目标值、适用条件、统计口径、测量方法→写入该引擎的 `引擎能力使用需求` 行 |
| 窗口标签页的 FR-BIZ 指标（§3.6.4） | 任务引擎（@engine-flow / @engine-task / @engine-workorder） | 同上 |
| 菜单可达性/场景切换指标（§3.4） | @engine-menu | 同上 |

指标仍归属于原 FR-BIZ，不转为 NFR。指标分配不改变指标的定义和数值——只决定”这个指标由哪个引擎的能力来承载”。

**3.8.4 FR-ENG 候选线索生成**

对 Q2/Q3/Q4 判定，生成 FR-ENG 候选线索。每条线索包含：

| 字段 | 说明 |
|------|------|
| 线索 ID | `FR-ENG-CAND-{YYYYMMDD}-{序号}` |
| 来源业务页面 | 产生该缺口的业务页面 ID + 业务动作 |
| 缺口层级 | 构件级 / 布局组件级 / CU 级 / 引擎级（按 [91 §4.4] 判定） |
| 已有能力 | 25 资产中与该需求最接近的已有 CU 及其能力描述（Q2 时填写，Q3 写”无”） |
| 缺失能力 | 具体缺少什么能力——不能承接的业务动作或未达到的指标要求 |
| 触发场景 | 什么业务场景下该缺口暴露——用户操作→期望的系统行为→实际无法实现 |
| 不补充时的业务影响 | 该缺口不解决时，业务页面的哪部分功能不可用、影响哪个角色的什么职责 |
| FR-BIZ 指标差距 | Q2 时填写数值差距（当前上限 vs 需求目标），Q3/Q4 写”能力缺失，无法量化” |
| 建议归属引擎 | 按能力缺口类型推断归属引擎（标记 `[推断]`） |

> **门禁**：FR-ENG 候选线索**不是正式 OR**。本 Step 只把候选材料登记到 OR 原料状态表 A，不得直接写入 `01-eos-original-requirements.md` 的正式 OR 节点，也不得加入”待 wft01-eng 处理”分节。人类确认纳入需求后，该材料必须完整经过 ort00→ort01→ort02→ort03，形成正式 FR-ENG OR 后，才可由 wft01-eng 消费 [91 §4.4]。

**3.8.5 FR-BIZ 指标约束包装配**

将全部 Q1~Q4 需求行（含覆盖结论）装配为 `FR-BIZ 指标约束包`：

逐行格式：

```text
包 ID：FR-BIZ-PKG-{YYYYMMDD}-{序号}
版本：v{N}
来源业务页面：{页面ID / 页面名称 / 来源 BA 节点ID}
来源 FR-BIZ：{指标名称 / 目标值 / 适用条件 / 统计口径 / 测量方法 / 来源 OR或STR-F}
目标引擎/CU：{引擎ID / CU名称 / 25 资产版本}
覆盖结论：Q1 / Q2 / Q3 / Q4
  Q1：覆盖证据——{CU 能力的哪部分承接了该指标}
  Q2/Q3/Q4：→ 关联 FR-ENG 候选线索 ID
变更声明：{本版本与上一版本的差异——新增/修订/删除}
```

约束包由 wft05-eng 逐行消费——每个 Q1 行说明”这个指标由哪个引擎/CU 承载”，wft05-eng 据此将指标落实到软件组件的运行机制中。构件开发流水线和 wft06 使用同一包验证业务页面配置与软件能力是否联合满足指标。

**3.8.6 门禁检查**

方案生成完成前，逐项检查以下门禁全部通过：

| # | 门禁项 | 判定 |
|---|--------|------|
| 1 | 八类任务（Step Start + Step 1~7）均有产出或明确不适用理由 | 逐 Step 检查产出非空或有”不适用”标注 |
| 2 | 每个 PL5 输出文档有实体需求和正文功能表单需求（Step 4） | 逐 PL5 匹配 Step 4 产出 |
| 3 | 每个有任务类型的文档的 PL6-A 活动节点有窗口标签页承接（Step 5） | 逐 PL6-A 节点匹配 Step 5 产出 |
| 4 | 每个经 wft02 确认的 PL6-B 条目类型有条目需求转化（§3.5.5） | 逐 PL6-B 条目检查 §3.5.5 产出 |
| 5 | 轻量文档的原子正文行未被重复展开为 PL6-B | 逐轻量文档检查”正文行数=1”的文档无 PL6-B 产出 |

全部门禁通过后，方案状态进入 `待确认方案`。任一门禁不通过 → 补充对应产出后重新执行门禁检查，通过后再进入 `待确认方案`。
