# STR-NFR → SysReq-NFR · 非功能需求架构与操作页面约束设计
**Skill ID**: wft04-nfr

> **概述**：接收已确认的 STR-NFR 角色非功能需求分类，经前置校验、材料加载和反馈处理后，生成系统侧非功能需求架构（SysReq-NFR）和操作页面非功能需求。该方案将 wft01-nfr 的定性分类需求清单转化为可验证的量化约束、分层约束表、操作页面约束包、22 具体需求资产和 06 系统需求详细定义。
>
> **输入 → 输出**：STR-NFR 节点（`可以NFR设计` / `待补充NFR设计`）/ 有反馈的 SysReq-NFR 节点 → SysReq-NFR 架构节点 + 量化指标 + 分层约束表 + 操作页面 NFR 约束 + 22 具体需求写回 + 06 系统需求详细定义 + STR-NFR 推进为 `已NFR设计`
>
> **适用场景**：瀑布式系统设计第4步 · 非功能需求路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v3.6 | **修订**：2026-07-09

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于架构师和验证者——「指标可验证，约束分层正确，操作页面知道怎么消费」。把 STR-NFR 的角色非功能诉求转化为系统侧 SysReq-NFR 架构和操作页面非功能需求——不仅将定性期望量化为可验证的指标体系和分层约束表，更将 NFR 约束落到操作页面、CU/PA 组件和 06 详细定义等具体消费对象，为下游 biz/eng 路径和追溯验证提供可消费的 NFR 约束包。

**目标**：

1. **生成非功能需求架构**——按 22 分类维度和系统约束边界生成或复用 SysReq-NFR 节点，保证每条 STR-NFR 分类需求项有唯一系统侧宿主
2. **生成量化约束**——将定性期望转为可验证的指标、目标值、单位、统计口径、测量方法和验收条件；信息不足时标记待确认，不伪造确定值
3. **生成操作页面非功能需求**——把 NFR 约束落到全局、业务域、SR-F、CU、PA 组件和操作页面对象，形成 wft03-biz / wft05-eng 可消费的约束包
4. **写回 22 具体需求资产**——复用、升级或新增 22 具体需求条目及指标集，保留 STR-NFR / SysReq-NFR 追溯
5. **展开 06 详细定义**——将确认后的 SysReq-NFR 量化约束写为可验证系统需求详细定义，供后续验证与实现使用

本 Skill 负责：

1. **接收**——接收人类选中的一批 STR-NFR 节点（≤5 个），校验状态为 `可以NFR设计` / `待补充NFR设计`；状态/类型不符时退出并提示
2. **量化**——消费 STR-NFR 分类需求清单，逐项生成系统级量化指标（指标名称/目标值/单位/统计口径/测量方法/验收条件）；信息不足时标记待确认，不伪造确定值
3. **归架构**——按 22 分类维度、约束对象和语义内聚度匹配或新建 SysReq-NFR 节点，保证每条分类需求项有唯一系统侧宿主
4. **分层**——生成分层约束表，明确约束范围、适用链路、约束对象、消费目标、影响级别和影响点
5. **落页面**——对影响业务操作体验、界面行为、页面性能、安全、可访问性、审计提示等诉求，生成操作页面非功能需求
6. **落账**——写回 22 具体需求资产、06 系统需求详细定义、05 SysReq-NFR 节点和 STR-NFR 消费版本
7. **推进**——人类确认后 STR-NFR → `已NFR设计`，SysReq-NFR → `已验证冻结`
8. **退回**——当 STR-NFR 分类边界、角色语境或适用范围线索不足时，将节点退回为 `需wft01修订` 并附缺失说明

本 Skill 不负责：

1. 修改 wft01-nfr 已确认的角色语境、NFR 分类边界或 OR 分组；发现问题时退回 wft01-nfr
2. 设计业务场景、输出文档或功能表单（→ biz 路径）
3. 设计引擎场景、CU 详细定义或前后端组件结构（→ eng 路径）
4. 修改 22 已确认分类维度本身；本 Skill 写入的是具体需求、指标集、引用和候选升级
5. 替代人类确认无法从 STR-NFR 或资产推断出的目标值

### 1.2 与上下游的衔接

**上游 wft01-nfr**：提供已确认 STR-NFR，包含角色语境、22 分类路径、NFR 分类需求清单、适用对象线索、待量化线索和变更影响声明。本 Skill 重入时读取 STR-NFR 版本号和变更声明，按无变更/增量型/修订型/结构型处理。

**下游消费方**：wft03-biz 消费业务链和操作页面相关 NFR 约束，wft05-eng 消费 CU/PA 组件/运行机制相关 NFR 约束，06 系统需求详细定义供验证与追溯使用。SysReq-NFR 的分层约束表是这些下游对象消费 NFR 的唯一入口。

**时序说明**：瀑布流程中 wft03-biz 先生成 SR-F，wft04-nfr 后生成 NFR 约束包。因此 wft04-nfr 对 wft03-biz 的“消费”不是前置输入，而是回补/重入输入：wft03-biz 已产出的 SR-F 或操作页面在收到 NFR 约束包后，按约束行 ID 增量补记验收标准、页面约束或退回修订项；新一轮 wft03-biz 运行则直接读取最新 NFR 约束包。

## 二、非功能需求架构与操作页面约束基础

### 2.1 非功能需求架构（SysReq-NFR）

#### 2.1.1 定义与分类

SysReq-NFR 是 STR-NFR 在系统需求层的结构化表达，末级节点为**非功能需求分类**。它回答"系统需要满足哪类非功能质量、以什么指标验证、约束哪些业务/平台对象、由哪些下游设计对象消费"。NFR 路径分工见 [91 规范 §8.4](91-eos-biz-eng-spec.md#84-nfr-路径-skill)。

SysReq-NFR 的宿主匹配锚点为四元组：

| 锚点 | 说明 |
|------|------|
| 22 分类维度 | 一级类目 + 分类维度，决定主要质量属性 |
| 约束对象 | 全局、业务域、SR-F、CU、PA 组件、操作页面 |
| 指标口径 | 目标值、单位、统计口径、测量方法 |
| 适用链路 | `biz` / `eng` / `共享` |

#### 2.1.2 架构与属性

SysReq-NFR 的内部条目为量化指标（§2.2），约束结构为分层约束表与操作页面 NFR（§2.3），资产对齐为 22 具体需求（§2.3.3）。

SysReq-NFR 节点完整要素（写入 `05-*.md` SysReq-NFR 节点块）：

- SysReq-NFR ID / 名称 / 22 分类路径
- 来源 STR-NFR 清单与消费版本
- 量化指标清单
- 分层约束表
- 操作页面 NFR 清单
- 22 具体需求写回项
- 06 详细定义引用
- 闭环检查结果
- 版本号 / 确认状态

#### 2.1.3 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 量化完整 | 全部 STR-NFR 需求项已生成量化指标，或明确标注待确认缺口 | 标记缺口，不进入写回 |
| 宿主唯一 | 每条 STR-NFR 需求项有唯一 SysReq-NFR 宿主 | 标记宿主冲突 |
| 分层正确 | 全局/业务域/SR-F/CU/PA组件/操作页面未错层 | 修正分层 |
| 页面可消费 | 影响页面体验的 NFR 已生成操作页面约束 | 补充操作页面 NFR |
| biz/eng 一致 | 共享指标在两侧保持同一指标 ID、目标值和测量方法 | 对齐指标 |
| 22 可落账 | 具体需求写回项指标集完整、分类路径明确 | 标记缺口 |
| 06 可验证 | 详细定义包含来源、指标、测量、验收和追溯 | 补充 06 条目 |

### 2.2 量化指标

#### 2.2.1 定义与记录字段

量化指标是 SysReq-NFR 的核心条目，将 STR-NFR 的定性期望转化为可验证的指标定义。每条指标至少记录：

| 字段 | 说明 |
|------|------|
| 指标名称 | 可验证的非功能指标 |
| 目标值 / 单位 | 明确阈值、范围或布尔要求；无法确定则标记 `待确认` |
| 统计口径 | 时间窗口、样本范围、百分位、业务条件或环境条件 |
| 测量方法 | 压测、审计检查、日志统计、模拟、外部认证、人工检查等 |
| 验收条件 | 满足/不满足的判断标准 |
| 来源 STR-NFR | 需求项 ID 与消费版本 |
| 22 具体需求引用 | 复用或新增的 `@nfr-xxx-REQ-yy` |
| 确认状态 | 人类反馈字段 |

模糊诉求处理原则：可依据 22 具体需求模板、同类场景和行业常识推断时标记 `[需裁决]` 并给出依据；无法推断时保留 `待确认`，不得推进到写回。

### 2.3 分层约束与操作页面 NFR

#### 2.3.1 分层约束表定义

每个 SysReq-NFR 节点必须带分层约束表，供 wft03-biz / wft05-eng 消费：

| 约束范围 | 适用链路 | 约束对象 | 消费目标 | 影响级别 | 影响点 | 说明 |
|----------|----------|----------|----------|----------|--------|------|

字段取值：

| 字段 | 取值 |
|------|------|
| 约束范围 | `全局` / `业务域` / `SR-F` / `CU` / `PA组件` / `操作页面` |
| 适用链路 | `biz` / `eng` / `共享` |
| 约束对象 | EOS、业务域名、SR-F ID、目标引擎+CU 类型、组件类型、操作页面/页面类型 |
| 消费目标 | `wft03-biz:SR-F/操作页面约束` / `wft05-eng:CU或组件约束` / `wft03-biz+eng` |
| 影响级别 | `阻断型` / `非阻断型` / `待判定` |
| 影响点 | 配置项、配置规则、配置可达性、验收标准、页面交互、页面性能、权限/审计、组件边界、接口机制、运行约束机制等 |

填写约束：

1. 一行只表达一个约束对象和一个消费目标的关系。
2. 阻断型约束必须填写影响点。
3. 待判定约束必须说明待判原因。
4. 影响面大时优先使用全局或业务域，不强制枚举所有 SR-F。
5. 明确影响引擎实现时，至少补一行 `适用链路=eng` 的 CU 或 PA 组件约束。
6. 明确影响业务使用方式或页面体验时，至少补一行 `适用链路=biz` 的 SR-F 或操作页面约束。

#### 2.3.2 操作页面非功能需求

操作页面 NFR 是分层约束表中 `约束范围=操作页面` 的特化条目，覆盖页面类型、交互行为和用户可感知质量。

典型类型：

| 类型 | 示例 |
|------|------|
| 页面性能 | 首屏加载、列表查询、下钻切换、弹窗响应、批量操作反馈 |
| 页面安全 | 字段脱敏、按钮权限、行列权限、敏感操作二次确认 |
| 易用性/工效 | 操作步数、错误提示、批量处理、键盘可达性、认知负荷 |
| 可访问性 | 对比度、焦点顺序、读屏标签、无鼠标操作 |
| 可恢复性 | 草稿保存、异常重试、重复提交防护 |
| 可观测性 | 操作日志、审计轨迹、错误定位信息 |

操作页面约束应引用 91 规范定义的页面类型、辅助栏、分屏、下钻、菜单和引擎生成模型。能落到具体 SR-F 或操作页面时写具体 ID；暂不能定位时写页面类型或业务域，并标记 `[需裁决]`。

#### 2.3.3 22 具体需求资产

wft04-nfr 写回 22 的对象是**具体需求及其指标集**，不是分类维度本身。

| 判定 | 条件 | 动作 |
|------|------|------|
| 复用 | 22 已有同义具体需求，指标口径兼容 | 引用已有 `@nfr-xxx-REQ-yy` |
| 升级候选 | 候选区存在同义候选，且本轮指标集完整 | 状态→已确认，补充指标集和来源 |
| 新增 | 无同义具体需求或候选 | 新建具体需求条目，挂到已有分类维度 |
| 回退 | 指标集不完整或口径无法确认 | 回退 Step 3，不写入 22 |

### 2.4 NFR 架构要素提取规则

Phase B（修订已有 SysReq-NFR）与 Phase C（新建 SysReq-NFR）共用以下规则。

#### 2.4.1 量化指标生成

逐 STR-NFR 分类需求项生成量化指标：

| 输入线索 | 处理 |
|----------|------|
| OR 明示数值或布尔约束 | 直接采信，记录来源 |
| OR 有比较词或质量方向 | 基于 22 具体需求模板和同类场景推断，标记 `[需裁决]` |
| OR 有验证语义但无目标值 | 生成测量方法和待确认目标值 |
| 无可验证线索 | 标记缺口，回退补充 NFR，不推进写回 |

量化输出必须包含指标名称、目标值/单位、统计口径、测量方法、验收条件、来源 STR-NFR、22 具体需求判定和确认状态。

#### 2.4.2 分层约束判定

对每条量化指标判定约束范围：

| 约束范围 | 判定线索 | 典型消费 |
|----------|----------|----------|
| 全局 | 影响 EOS 整体运行质量 | wft03-biz + wft05-eng |
| 业务域 | 只影响某业务域或产品类型 | wft03-biz |
| SR-F | 指向具体功能性系统需求 | wft03-biz |
| CU | 指向配置单元、配置规则或配置可达性 | wft05-eng |
| PA组件 | 指向前后端组件类型、接口或运行机制 | wft05-eng |
| 操作页面 | 指向页面类型、交互行为或页面体验 | wft03-biz，必要时 wft05-eng |

#### 2.4.3 Phase B SysReq-NFR 宿主匹配检查

Phase B 修订已有 SysReq-NFR 时，按 `22 分类维度 + 约束对象 + 指标口径` 匹配已有宿主：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 复用宿主 | 已有 SysReq-NFR 分类、约束对象和指标口径兼容 | 追加指标和追溯，标记 `[确认]` |
| Q2 扩展宿主 | 已有宿主可承载但边界需扩展 | 修订宿主，标记 `[变更]` |
| Q3 新建宿主 | 无合适宿主 | 新建 SysReq-NFR |
| 宿主冲突 | 多个宿主均可承载或语义不内聚 | 标记 `[需裁决]` |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 SysReq-NFR | Phase C 新建 SysReq-NFR |
|------|---------------------------|------------------------|
| 判定范围 | SysReq-NFR 已承接的全部 STR-NFR + 本轮新 STR-NFR | 待聚合池本组 STR-NFR |
| 量化指标基线 | 以已有量化指标清单为基线，仅扫描本轮新需求项 | 从零构建 |
| 宿主匹配 | 执行宿主匹配检查（§2.4.3），可能检出 Q1/Q2/Q3/宿主冲突 | 无需匹配，直接新建 |
| 分层约束 | 增量合并新指标 → 更新分层约束表行 | 全量判定（§2.4.2） |
| 22 重识别 | 合并重识别可能导致已有指标的 22 判定变更——标记 `[22判定变更]` 并附变更原因 | 全量判定，无此问题 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写"首版，无变更" |

### 2.5 NFR 量化推断规则

Phase B（修订已有 SysReq-NFR）与 Phase C（新建 SysReq-NFR）共用以下规则。

#### 2.5.1 量化指标推断

对每个 STR-NFR 分类需求项：

1. 提取待量化线索（数值、比较词、验证条件、约束对象线索）。
2. 匹配 22 具体需求模板和同类场景的指标口径。
3. 生成目标值/单位/统计口径/测量方法/验收条件。
4. 信息不足时标注 `待确认`，不得伪造确定值；能推断时标注 `[需裁决]` 并给出依据。
5. 判定 22 具体需求归属：复用/升级候选/新增/回退（§2.3.3）。

#### 2.5.2 操作页面 NFR 推断

当指标影响用户可感知页面行为时，必须生成操作页面 NFR：

| 页面线索 | 输出 |
|----------|------|
| 页面类型明确 | 绑定六类页面类型之一，说明约束行为 |
| SR-F 明确 | 引用具体 SR-F 或功能表单 |
| 只知道业务域 | 写业务域级页面约束，标记 `[需裁决]` |
| 影响辅助栏/分屏/下钻/面包屑 | 明确关联 91 的交互模型要素 |
| 影响权限/审计/安全提示 | 同时生成 biz 页面约束和 eng 权限/审计约束 |

操作页面 NFR 条目至少包含：页面对象 / 约束内容 / 量化目标 / 测量方法 / 影响点 / 消费目标 / 确认状态。

#### 2.5.3 Phase B 量化指标关系检测

Phase B 修订已有 SysReq-NFR 时，宿主匹配通过后，将本轮生成的量化指标与 SysReq-NFR 已有量化指标清单比对。比对锚点为**指标名称+22分类维度匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 指标匹配 + 22 分类一致 + 来源升级 | 追加 STR-NFR 引用，内部细分结论=`确认` |
| 无新增 | 指标匹配 + 22 分类一致 + 所有来源已确认 | 增量合并新需求项中的口径/测量细节（如有新内容），内部细分结论=`改进` |
| 指标口径变更 | 指标匹配 + **目标值/统计口径/测量方法变化**（STR-NFR 修订导致） | 更新指标定义 + 内部细分结论=`指标口径变更` + 变更原因。不新增指标 |
| 22 判定变更 | 指标匹配 + **22 具体需求判定不同**（合并重识别导致） | 更新 22 判定 + 内部细分结论=`22判定变更` + 变更原因 |
| 补充 | 指标不匹配 | 新增量化指标，内部细分结论=`新增` |
| 过时 | 基线已有指标 **未被**本轮需求项覆盖（需求项移除导致指标不再被需要） | 内部细分结论=`过时` + 追加说明"对应需求项已不再覆盖此指标，请确认是否移除"。保留该指标在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 STR-NFR 重新判定 22 归属**——新需求项可能改变指标特征导致 22 判定变更（表中 `22判定变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有指标的目标值/统计口径/测量方法变化，在关系标记之外叠加 `[调整]`。

### 2.6 SysReq-NFR 节点生命周期

wft04-nfr 同时管理两条生命周期线：STR-NFR（上游节点，本 Skill 消费并推进）和 SysReq-NFR（本 Skill 产出节点）。通用模型见 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型)。

**STR-NFR 侧**（wft01-nfr ←→ wft04-nfr）：

```
可以NFR设计 ──wft04锁定──→ 在NFR设计 ──wft04完成──→ 已NFR设计
     ↑                         │                         │
     │                         │               wft04退回  │
     │                         │                         ↓
     └─── wft01修订 ───── 需wft01修订 ←───────────────┘
```

**SysReq-NFR 侧**（wft04-nfr 产出 → 验证与 biz/eng 消费）：

```
待确认方案 ──人类确认+落账──→ 已验证冻结
     ↑                             │
     │               验证/消费退回   │
     │                             ↓
     └───── wft04修订 ────── 需wft04修订
```

**上游变更**（新 STR-NFR 汇入触发 SysReq-NFR 修订）：

```
已验证冻结 ──新STR-NFR修订──→ 待补充NFR验证 ──wft04补全──→ 已验证冻结
```

**本 Skill 的写回范围**：SysReq-NFR `待确认方案` / `待补充NFR验证` / `需wft04修订`。`在NFR设计` 由本 Skill 锁定期间设置，`已验证冻结` 由本 Skill 完成落账后写入。

本 Skill 在首次消费 STR-NFR 时记录 `STR-NFR 消费版本：v{N}`；重入时若 STR-NFR 当前版本大于消费版本，则读取变更影响声明并增量处理。

下游退回 `需wft04修订` 时：读取验证或消费方的缺陷说明 → 按人类改进方案修订 SysReq-NFR（走 Phase B 修订流程）→ 人类确认 → 重新推进。根因在 STR-NFR 时退回 wft01-nfr。

### 3.1 Step Start

运行时 AI 按以下顺序执行：

1. **输入校验**：
   - SysReq-NFR 状态为 `需wft04修订` 且人类未提供改进方案 → 输出验证或消费方的缺失说明，提示提供改进方案 → **退出**
   - STR-NFR 状态不是 `可以NFR设计` / `待补充NFR设计` → 输出不合格节点及当前状态 → **退出**
   - STR-NFR 分类边界或角色语境明显缺失 → STR-NFR → `需wft01修订`，输出缺失说明 → **退出**
   - 选中 STR-NFR >5 个 → 输出超限提示 → 人类确认后继续或退出
   - 无 STR-NFR 选中 + 无待处理反馈的 SysReq-NFR 节点 + 无 `需wft04修订` 的 SysReq-NFR 节点 → 输出”无待处理对象”→ **退出**
2. **退回优先**：存在 `需wft04修订` 的 SysReq-NFR 节点（且人类已提供改进方案）→ 定位受影响 SysReq-NFR，进入 Step 2 按人类方案修订，人类确认后重新推进
3. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 SysReq-NFR 节点 → 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 STR-NFR，Step End 时提示
4. **新 STR-NFR 路由**：有未处理的 STR-NFR 节点 → 进入 Step 1→Step 3，逐节点执行 Phase A 消费与变更感知，匹配已有 SysReq-NFR 宿主或进入待聚合池新建

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 SysReq-NFR 的量化指标/分层约束/操作页面 NFR。Step 3 的 Phase C 宿主匹配必须基于 Step 2 修改后的最新 SysReq-NFR 内容，不得使用缓存旧状态。

### 3.2 Step 1 · 设计材料加载

1. `02-*.md` STR 树画像 / 状态队列 / 节点索引 — 定位本轮 STR-NFR 正文块（含角色语境、分类需求清单、适用对象线索）
2. `05-*.md` SysReq 树画像 / 状态队列 / 节点索引 — 定位已有 SysReq-NFR 节点块，同时读取 SR-F 节点 ID 清单和页面/功能线索

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：量化指标 + 分层约束表行 + 操作页面 NFR + 22 写回项 + 06 详细定义。各条目的 `确认状态` 字段位于 `05-*.md` SysReq-NFR 节点块各条目正文中。

#### 3.3.1 AI 处理流程

本 Skill 特化参数见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 实例化参数表（wft04-nfr 列）。

### 3.4 Step 3 · 非功能需求架构设计

#### 3.4.1 Phase A：STR-NFR 消费感知与宿主匹配

逐 STR-NFR 检查消费版本——首次消费→全量设计，版本递增→按变更声明执行增量/修订/结构型分流；分类边界或角色语境不足→退回 wft01-nfr。版本确认后，按 22 分类维度 + 约束对象 + 指标口径匹配已有宿主（详见 §2.4.3）：

| 条件 | 路由 |
|------|------|
| 已有 SysReq-NFR 分类维度 + 约束对象 + 指标口径兼容 | 归入该宿主 → Phase B |
| 不满足 | 进入待聚合池 → Phase C |
| 多个宿主均可承载或语义不内聚 | 标记 `[需裁决]` |

待聚合池按**同一 22 分类维度 + 同一约束对象类型**分组（`{22分类维度, 约束对象类型, STR-NFR列表}`）。此阶段仅粗略分组，量化指标生成和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 SysReq-NFR

1. **要素提取**：从本轮 STR-NFR 分类需求清单提取待量化线索、适用对象线索和 22 分类路径（详见 §2.4.1、§2.4.2）。已有指标口径仅追加不重定
2. **宿主匹配检查**：确认 STR-NFR 需求仍在 SysReq-NFR 宿主范围内（详见 §2.4.3）。Q1 复用宿主→追加指标和追溯；Q2 扩展宿主→修订宿主 + 变更声明；宿主冲突→标记 `[需裁决]`。Phase A 匹配是候选筛选、Phase B 是精确匹配——宿主扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决
3. **量化指标/分层约束/操作页面 NFR 重判定与关系检测**：基于全部 STR-NFR 重新量化指标（详见 §2.5.1），比对已有基线判定六种关系（详见 §2.5.3）。新增/变更指标→更新分层约束表行（详见 §2.4.2）；影响页面体验→生成操作页面 NFR（详见 §2.5.2）；22 判定变更→更新具体需求归属（详见 §2.3.3）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 SysReq-NFR 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 SysReq-NFR

1. **确定 22 分类路径** → 一级类目 → 分类维度 → 具体需求归属判定（详见 §2.4.2）
2. **生成量化指标** → 逐需求项提取待量化线索 → 匹配 22 模板和同类场景 → 目标值/单位/统计口径/测量方法/验收条件（详见 §2.5.1）。信息不足时标注 `待确认`，不伪造确定值
3. **判定分层约束** → 全局/业务域/SR-F/CU/PA组件/操作页面六类约束范围 → 适用链路 → 约束对象 → 消费目标 → 影响级别 → 影响点（详见 §2.4.2）
4. **生成操作页面 NFR** → 影响用户可感知页面行为时绑定页面类型/SR-F/业务域 → 约束内容 → 量化目标 → 测量方法 → 消费目标（详见 §2.5.2）
5. **装配分层约束包** → 按消费目标组织 biz/eng 约束包视图，引用分层约束表行
6. **组装 SysReq-NFR** → 22 分类路径 + 量化指标清单 + 分层约束表 + 操作页面 NFR + 22 写回项 + 06 引用，写入 `05-*.md`（完整要素见 §2.1.2）

### 3.5 Step 4 · 操作页面与分层约束设计

Step 4 按每个 SysReq-NFR 实例独立执行。新建 SysReq-NFR → 全量设计；修订已有 SysReq-NFR → 仅当量化指标或约束范围变更时重验分层，要素机械检查始终针对变更节点执行。

**1. 分层约束表生成**

基于 Step 3 产出的量化指标，对每条指标判定约束范围和消费目标（详见 §2.3）：

| 约束范围 | 判定线索 | 典型消费 |
|----------|----------|----------|
| 全局 | 影响 EOS 整体运行质量 | wft03-biz + wft05-eng |
| 业务域 | 只影响某业务域或产品类型 | wft03-biz |
| SR-F | 指向具体功能性系统需求 | wft03-biz |
| CU | 指向配置单元、配置规则或配置可达性 | wft05-eng |
| PA组件 | 指向前后端组件类型、接口或运行机制 | wft05-eng |
| 操作页面 | 指向页面类型、交互行为或页面体验 | wft03-biz，必要时 wft05-eng |

每条分层约束记录约束行 ID、约束范围、约束对象、量化指标引用、影响级别和消费目标。无法确定约束范围时标注 `[推断]`。

**2. 操作页面 NFR 生成**

当指标影响用户可感知页面行为时，按页面线索逐条生成操作页面 NFR（详见 §2.3）：

| 页面线索 | 输出 |
|----------|------|
| 页面类型明确 | 绑定六类页面类型之一，说明约束行为 |
| SR-F 明确 | 引用具体 SR-F 或功能表单 |
| 只知道业务域 | 写业务域级页面约束，标记 `[需裁决]` |
| 影响辅助栏/分屏/下钻/面包屑 | 明确关联 91 的交互模型要素 |
| 影响权限/审计/安全提示 | 同时生成 biz 页面约束和 eng 权限/审计约束 |

每个操作页面 NFR 写入：指标 ID / 页面对象（页面类型 / SR-F ID / 操作页面线索）/ 约束内容 / 量化目标 / 测量方法 / 影响点 / 消费目标 / 确认状态。所有操作页面 NFR 标注 `[推断]`，经由人类确认后方可落账。

**3. 下游约束包装配**

Step 4 末尾按消费目标生成装配视图，只引用分层约束表行 ID 和操作页面 NFR 条目，不复制正文：

- wft03-biz NFR 约束包：全局约束 / 业务域与 SR-F 约束 / 操作页面约束（页面对象 + 指标 ID + 约束行 ID）
- wft05-eng NFR 约束包：CU 约束（目标引擎 / CU 类型 / 指标 ID / 约束行 ID）/ PA 组件约束（组件类型 / 指标 ID / 约束行 ID）/ 共享约束（需与 wft03-biz 保持一致的指标 ID）

**4. 要素机械检查**（逐 SysReq-NFR，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 每条量化指标的约束范围 **已判定**，约束行 ID/约束对象/影响级别/消费目标 **已记录**
- [ ] 影响用户可感知页面行为的指标 **已生成**操作页面 NFR
- [ ] 每个操作页面 NFR 的九项要素 **齐全**
- [ ] 下游约束包装配视图 **已生成**，只引用行 ID 不复制正文
- [ ] wft03-biz 和 wft05-eng 消费包各自覆盖的约束范围 **无遗漏**

### 3.6 Step 5 · 闭环检查与变更声明

Step 5 按每个 SysReq-NFR 实例独立执行。新建 SysReq-NFR → 全量检查；修订已有 SysReq-NFR → 仅当量化指标、约束范围或操作页面 NFR 变更时重验闭环，要素机械检查始终针对变更节点执行。

**1. 闭环检查**

对每个 SysReq-NFR 节点，按七项逐条检查，发现遗漏优先当场补齐，无法补齐时标记 `[需裁决]` 或退回 wft01-nfr——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全：

- [ ] 量化完整：全部 STR-NFR 分类需求项已生成量化指标，或明确标注待确认缺口
- [ ] 宿主唯一：每条 STR-NFR 分类需求项有唯一 SysReq-NFR 宿主
- [ ] 分层正确：全局/业务域/SR-F/CU/PA组件/操作页面未错层
- [ ] 页面可消费：影响页面体验的 NFR 已生成操作页面约束
- [ ] biz/eng 一致：共享指标在两侧保持同一指标 ID、目标值和测量方法
- [ ] 22 可落账：具体需求写回项指标集完整、分类路径明确
- [ ] 06 可验证：详细定义包含来源、指标、测量、验收和追溯

**2. 缺口处理**

发现缺口时按严重程度分流：

- 可当场补齐（指标定义不全/约束范围未判定/操作页面 NFR 缺失）→ 在本 Skill 内补齐，补齐后重验
- 无法补齐且根因在上游（STR-NFR 分类边界不清/角色语境缺失/适用范围线索不足）→ 退回 wft01-nfr 为 `需wft01修订`，携带缺失说明
- 需人类裁决（目标值无法从 STR-NFR 推断/约束层级归属有争议）→ 标记 `[需裁决]`，不进入 Step 6 写回
- 不因缺口脑补节点——缺口就是缺口

**3. 要素机械检查**（逐 SysReq-NFR，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 七项闭环检查 **已执行**，遗漏项已标注 `[覆盖缺口]`
- [ ] 缺口处理 **已分流**，无未裁决的边界情况
- [ ] SysReq-NFR 版本号 **已递增**（修订时），首版为 v1

**4. 变更影响声明**

每次新建或修订 SysReq-NFR 后写入变更影响声明；首版写"首版，无变更"。修订时按 §2.7 判定变更类型（无变更/增量型/修订型/结构型），列出受影变量化指标、操作页面 NFR 和下游 wft03-biz/wft05-eng 建议动作。格式见 §2.7。

### 3.7 Step 6 · 资产落账与状态推进

仅写回人类已在 Step 2 确认的 SysReq-NFR 条目。不设二次确认。

1. 遍历已确认 SysReq-NFR，按分类路径写回 22 资产：
   - 复用 → 定位已有条目，追加反向引用（去重）
   - 升级 → 扩展已有条目，追加引用 + 扩展指标集
   - 新增 → 新建条目，写入具体需求与指标集
2. `06` 写入 NFR 系统需求详细定义（来源 STR-NFR / SysReq-NFR 宿主 / 指标 / 测量方法 / 验收条件 / 分层约束表引用 / 22 资产引用）
3. `05` SysReq-NFR → `已验证冻结`，记录 22/06 引用和 STR-NFR 消费版本
4. `02` 对应 STR-NFR 节点写入 `STR-NFR 消费版本：v{N}`，状态推进为 `已NFR设计`；若仅部分增量完成，保留待补充说明
5. 写入资产写回记录（日期/来源 STR-NFR/目标 SysReq-NFR/动作/消费版本/下游状态）

写回要求：幂等去重、局部写回、全貌同步。资产写回失败时不得推进状态。

说明：资产落账是独立收尾，不构成 wft03-biz 或 wft05-eng 消费的前置条件。

### 3.8 Step End · 运行结束输出

遵循 [91 规范 §8.8](91-eos-biz-eng-spec.md#88-skill-通用约定) 的三区模板。

```text
当前状态：<待确认方案 / 已NFR设计 / 需wft01修订>
  SysReq-NFR：新增/修订 <N> 个；量化指标 <N> 条；操作页面 NFR <N> 条；22 写回 <N> 条；06 详细定义 <N> 条；待裁决 <N> 项。

一、方案反馈
  A. 整体确认 -> 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 -> 在确认状态中标注 [修改]：...
  C. 驳回重做 -> 在确认状态中标注 [驳回]：...

二、下一步
  本Skill -> 存在未处理反馈 / 需wft04修订 / 新 STR-NFR 时重入
  后续    -> SysReq-NFR 已验证冻结后，wft03-biz / wft05-eng 按约束包消费
```
