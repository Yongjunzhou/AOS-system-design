# NFR OR → STR-NFR · 角色非功能需求分类设计
**Skill ID**: wft01-nfr-or2str

> **概述**：接收正式 NFR OR，经前置校验、材料加载和反馈处理后，将非结构化非功能诉求转化为 STR-NFR 角色非功能需求分类方案。该方案以“哪个角色在什么业务/平台语境下关注哪类非功能质量”为锚，完成角色 NFR 分类、需求清单和 22 分类资产对齐，并识别非功能诉求缺口形成补充 NFR OR 材料。
>
> **输入 → 输出**：NFR OR 条目（≤10 条）/ 有反馈的 STR-NFR 节点 → STR-NFR 角色 NFR 分类方案（角色语境 + NFR 分类路径 + NFR 分类需求清单 + 22 分类对齐 + 补充 NFR 缺口）+ OR 推进为 `已分配` + STR-NFR 推进为 `可以NFR设计`
>
> **适用场景**：瀑布式系统设计第1步 · 非功能需求路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v5.0 | **修订**：2026-07-13 | **说明**：对齐 91 七种页面类型与页面 NFR 术语

---

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于非功能需求相关方——「你听懂了我关心的质量属性、适用语境和约束对象」。把非结构化的 NFR OR 转化为结构化的 STR-NFR 角色非功能需求分类方案——不仅将分散的质量诉求按角色+语境+分类维度归组为分类需求清单，更识别同一角色语境下的非功能诉求缺口和 22 分类资产对齐关系，为下游 NFR 量化设计（wft04-nfr）提供可展开的输入。

**目标**：

1. **推断生成角色 NFR 分类节点**——以角色非功能需求分类为锚点，识别 OR 背后的用户角色、业务域/平台能力语境、NFR 一级类目与分类维度，形成 STR-NFR 末级节点
2. **推断 NFR 分类需求清单**——把 OR 中的质量诉求归纳为可供 wft04-nfr 量化的分类需求项，保留定性期望、适用范围线索、来源 OR 和判定依据
3. **基于需求清单补充 NFR 需求**——检查同一角色语境下的非功能诉求是否存在分类缺口、适用范围缺口或验证语义缺口，将不完整的质量意图还原为可确认的需求条目
4. **对齐 22 分类资产**——逐分类需求项判定其与 22 NFR 分类维度的 Q1/Q2/Q3/Q3+ 关系，新增或扩展分类只提出分类建议，不生成系统级指标
5. **保持路径边界**——将业务功能诉求和平台能力诉求及时路由到 biz/eng 路径，避免 NFR 路径替代功能设计

本 Skill 负责：

1. **接收**——接收人类选中的一批 NFR OR 条目（≤10 条），校验输入为正式 NFR OR、状态为 `待处理`；状态/类型不符时退出并提示路由
2. **定语境**——识别 NFR 所属用户角色、业务域、产品类型、链身份（业务链/平台链/共享）和适用对象线索，无法确定语境时标记 `需澄清`
3. **分类**——按 22 资产的一级类目/分类维度归组 OR，无法稳定匹配时提出分类扩展建议
4. **归组**——按“用户角色 + 业务/平台语境 + NFR 分类维度 + 适用对象线索”四元组匹配已有 STR-NFR：边界一致则归入，边界扩展则修订并输出变更声明，边界冲突则标记 `[需裁决]`
5. **列清单**——生成 NFR 分类需求清单，逐项记录定性期望、适用范围线索、来源类型、22 分类候选对齐和确认状态；22 判定全量标注 `[推断]`，由 wft04 校验
6. **补需**——检出分类缺口、适用范围缺口或验证语义缺口，生成补充 NFR OR 材料，登记到 OR 原料状态表，进入 OR 预处理链
7. **推进**——人类确认后 STR-NFR → `可以NFR设计`，对应 OR → `已分配`
8. **回修**——接收 wft04-nfr 退回的 `需wft01修订` STR-NFR，读取缺失说明，按人类改进方案修订 STR-NFR，人类确认后重新推进为 `可以NFR设计`

本 Skill 不负责：

1. FR-BIZ 业务场景和输出文档设计（→ `wft01-biz`）
2. FR-ENG 平台能力场景和 CU 候选设计（→ `wft01-eng`）
3. 将 NFR 定性诉求直接转成系统量化指标、阈值或测试方法（→ `wft04-nfr`）
4. 生成 SysReq-NFR、页面 NFR、CU/PA 组件约束或 06 系统需求详细定义（→ `wft04-nfr`）
5. 修改 22 已确认分类维度的权威定义；本 Skill 只写入引用、候选分类建议或分类扩展建议

### 1.2 与上下游的衔接

**上游 OR 预处理**：只消费已进入 `01-*.md` 的正式 NFR OR。本 Skill 在 Step Start 中通过 `01-*.md` 的 `## AI可以处理节点` 分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)）检测待处理 OR 条目，定位并读取 OR 正文块（按 [§A.3.3](91-eos-biz-eng-spec.md#a33-产品数据文档与资产文档读取与写回约定) 读取协议执行）。若 OR 实际描述业务流程、输出文档、引擎能力或配置数据，应退回对应路径重新处理。

**下游 wft04-nfr**：消费状态为 `可以NFR设计` / `待补充NFR设计` 的 STR-NFR，将分类需求清单量化为 SysReq-NFR 与页面 NFR。若 wft04-nfr 发现 STR-NFR 分类边界不清、适用对象缺失、角色语境错误或需求清单不足，将 STR-NFR 退回为 `需wft01修订`。本 Skill 重入时（[§A.4.3](91-eos-biz-eng-spec.md#a43-规则二退回节点的门禁) 退回门禁）读取缺失说明，按人类改进方案走 Phase B 修订流程。

## 二、角色非功能需求分类基础

### 2.1 角色非功能需求分类（STR-NFR）

#### 2.1.1 定义与分类

STR-NFR 是 NFR OR 在相关方需求层的结构化表达，末级节点为**角色非功能需求分类**。它回答"哪个角色在什么业务/平台语境下关注哪类非功能质量属性"。NFR 路径分工见 [91 规范 §10.5](91-eos-biz-eng-spec.md#105-nfr-路径-skill)。

STR-NFR 的归组锚点为四元组：

| 锚点 | 说明 |
|------|------|
| 用户角色 | 提出或承受该非功能诉求的角色、外部系统或保障者 |
| 业务/平台语境 | 业务域、产品类型、STR-F/STR-E 线索或横切平台能力 |
| NFR 分类维度 | 22 资产中的一级类目 + 分类维度 |
| 适用对象线索 | 可能约束的 STR-F、STR-E、业务域、平台能力、91 规范七种页面类型之一、具体页面 ID 或全局对象 |

#### 2.1.2 架构与属性

STR-NFR 的内部条目为 NFR 分类需求项（§2.2），分类锚定为 22 分类资产对齐（§2.3）。

STR-NFR 节点完整要素（写入 `02-*.md` STR-NFR 节点块）：

- STR-NFR ID / 名称 / 角色 / 业务域或平台语境 / 链身份
- 来源 OR 清单
- 22 分类路径与对齐判定
- NFR 分类需求清单
- 适用对象线索汇总
- 完备性检查结果
- 补充 NFR 材料引用
- 变更影响声明
- 版本号 / 确认状态

#### 2.1.3 完备性判据

| 检查项 | 通过标准 | 不通过处理 |
|--------|----------|------------|
| 角色语境清楚 | 能定位提出者或承受者 | 生成澄清型补充 NFR |
| 分类维度单一 | 一个 STR-NFR 只表达同一角色语境下的一类 NFR 分类维度 | 拆分 STR-NFR 或退回 OR 重切 |
| 适用对象有线索 | 至少能标注全局/业务域/STR-F/STR-E/平台能力中的一种线索 | 标记适用范围缺口 |
| 待量化线索保留 | OR 中的数值、比较词、验证条件未丢失 | 补齐记录，不自行量化 |
| 分类资产对齐明确 | 22 判定已完成，Q3/Q3+ 有建议 | 标记 `[需裁决]` |

---

### 2.2 NFR 分类需求项

#### 2.2.1 定义与记录字段

NFR 分类需求项是 STR-NFR 的内部条目。wft01-nfr 只把 OR 转为可被 wft04-nfr 消费的分类化诉求，不生成系统级阈值。

每个需求项至少记录：

| 字段 | 说明 |
|------|------|
| 需求项名称 | 定性质量诉求的短名称 |
| 定性期望 | OR 中表达的性能、安全、可用性、易用性等期望 |
| 适用范围线索 | OR 明示或 AI 推断的角色、业务域、STR-F/STR-E、平台能力或全局范围 |
| 22 分类路径 | 一级类目 / 分类维度 / 资产 ID |
| 22 判定 | `22-Q1` / `22-Q2` / `22-Q3` / `22-Q3+` |
| 来源 OR | 承接的 OR ID 列表 |
| 来源类型 | `OR明示` / `OR隐含` / `同类语境推断` / `资产线索推断` |
| 待量化线索 | OR 中出现的数值、比较词、验证语义或约束条件；仅作为 wft04 输入 |
| 确认状态 | 人类反馈字段 |

---

### 2.3 22 分类资产对齐

#### 2.3.1 定义与判定规则

22 资产是 NFR 分类与具体需求资产的权威来源。wft01-nfr 只对齐**分类维度**，不写具体需求指标集。

| 判定 | 条件 | 动作 |
|------|------|------|
| `22-Q1` | OR 语义明确落入已有已确认分类维度 | 引用已有分类维度 |
| `22-Q2` | OR 是已有分类维度的子类、扩展场景或边界细化 | 引用已有分类维度 + 提出候选扩展说明，等待 wft04 校验 |
| `22-Q3` | 现有一级类目可承载，但缺少分类维度 | 提出候选新增分类维度建议，标记 `[需裁决]`，不作为资产事实 |
| `22-Q3+` | 现有一级类目也无法承载 | 提出候选新增一级类目 + 分类维度建议，标记 `[需裁决]`，不作为资产事实 |

状态敏感规则：`已确认` 可稳定引用；`候选` / `疑似` 只能作为线索，引用时标记 `[需裁决]`；`废弃` 不得作为归属。

### 2.4 NFR 要素提取规则

Phase B（修订已有 STR-NFR）与 Phase C（新建 STR-NFR）共用以下规则。

#### 2.4.1 角色语境确定

逐条 OR 提取以下要素：

| 提取项 | 说明 |
|--------|------|
| 关注角色 | 操作用户、外部系统、运维保障者、管理者等 |
| 业务/平台语境 | 业务域、产品类型、STR-F/STR-E 线索、平台能力或全局 |
| 非功能诉求 | 性能、安全、可用性、易用性、可靠性、可部署性等 |
| 待量化线索 | 数值、比较词、验证词、约束条件；只记录不定指标 |
| 适用对象线索 | 全局/业务域/STR-F/STR-E/页面类型/具体页面ID/平台能力 |

路由规则：

| 情况 | 处理 |
|------|------|
| OR 实际要求业务流程、输出文档或业务规则 | 退回 `wft01-biz` |
| OR 实际要求引擎能力、CU、组件或平台治理功能 | 退回 `wft01-eng` |
| OR 只给出具体配置数据 | 标记为业务配置实例，不进入 NFR 设计 |
| OR 描述质量属性、运行约束或可验证非功能期望 | 进入 wft01-nfr |

#### 2.4.2 22 分类路径判定

Phase C 新建 STR-NFR 时，从 22 资产动态读取一级类目和分类维度清单（每次运行时读取、不缓存），按 OR 的非功能诉求语义匹配分类维度。wft01 仅有 OR 文本信息，22 分类维度归属**标注 `[推断]` 或 `[22确认]`**，最终判定在 wft04 的量化设计中校验。

判定流程：

1. 匹配一级类目：性能/安全/可用性/易用性/可靠性/可部署性/...
2. 在一级类目下匹配分类维度：OR 语义与分类维度定义的语义相似度。
3. 无法匹配已有分类维度 → 22-Q3（新增分类维度建议）。
4. 一级类目也无法承载 → 22-Q3+（新增一级类目 + 分类维度建议）。

#### 2.4.3 Phase B 边界匹配检查

Phase B 修订已有 STR-NFR 时，检查本轮 OR 是否在 STR-NFR 节点边界内。边界 = 同一角色 + 同一业务/平台语境 + 同一 22 分类维度。

按以下顺序匹配：

1. 同一用户角色或同类承受者。
2. 同一业务/平台语境。
3. 同一 22 分类维度。
4. 适用对象线索不冲突。

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 直接归入 | 新 OR 只补强已有需求项 | 追加来源，标记 `[确认]` |
| 新增需求项 | 角色语境和分类不变，但新增分类需求 | 加入清单，标记 `[新增]` |
| 边界扩展 | 适用范围线索扩展但仍属同一分类 | 修订 STR-NFR，输出变更声明 |
| 分类冲突 | 分类维度需改变或跨维度 | 标记 `[需裁决]`，必要时拆分 |
| 宿主误匹配 | 不属于同一角色语境或分类维度 | 退回待聚合池或新建 |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 STR-NFR | Phase C 新建 STR-NFR |
|------|------------------------|---------------------|
| 判定范围 | STR-NFR 已承接的全部 OR + 本轮新 OR | 待聚合池本组 OR |
| 分类需求清单基线 | 以已有需求清单为基线，仅扫描本轮新 OR | 从零构建 |
| 边界定义 | 执行边界匹配检查（§2.4.3），可能检出直接归入/新增需求项/边界扩展/分类冲突/宿主误匹配 | 执行角色语境确定+22分类路径判定（§2.4.1+§2.4.2） |
| 要素提取 | 在基线基础上增量合并（关系检测见 §2.5.3） | 全量提取 |
| 22 重识别 | 合并重识别可能导致已有需求项的 22 判定变更——标记 `[22判定变更]` 并附变更原因 | 全量判定，无此问题 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写"首版，无变更" |

### 2.5 NFR 分类需求项推断规则

Phase B（修订已有 STR-NFR）与 Phase C（新建 STR-NFR）共用以下规则。

#### 2.5.1 分类需求清单提取

**识别 NFR 分类需求清单**：从当前操作范围内的全部 OR 中识别非功能质量诉求。去重/收敛后形成分类需求清单，每个需求项 → STR-NFR 中一个分类条目。多条 OR 指向同一需求项时归入同一项（要素收敛）。

**逐需求项判定 22 分类路径**：从 22 资产动态读取一级类目和分类维度（每次运行时读取、不缓存），根据需求项的定性期望语义匹配。wft01 仅有 OR 文本信息，22 判定**全量标注 `[推断]`**（Q3/Q3+ 标注 `[需裁决]`），定位为供下游 wft04 校验的**候选建议**而非最终判定。

> **待量化线索的处理**：wft01-nfr 只记录 OR 中出现的数值、比较词和验证条件，**不将其转为系统量化指标**。该职责在 wft04-nfr。例如 OR 说"页面查询要在2秒内响应"，wft01 记录 `待量化线索：OR提到"2秒内"和"页面查询响应"`，量化指标（如 P95 响应时间 ≤ 2000ms）由 wft04 产出。

#### 2.5.2 需求项标注与来源类型

对每个分类需求项逐项判定要素并标注。标注字段见 §2.2.1。

**来源类型定义**（NFR 分类需求项）：

| 来源类型 | 含义（含示例） |
|----------|---------------|
| `OR明示` | OR 文本中直接说出该非功能质量诉求。如"采购单列表查询要在2秒内响应" → "页面查询响应时间"需求项 |
| `OR隐含` | OR 未直接说出，但不补充则质量期望存在逻辑缺口。如"支持高峰期使用"→隐含并发性能需求 |
| `同类语境推断` | 同角色同业务域已有 STR-NFR 的类似 NFR 分类模式，当前 OR 语境与之高度相似时推断。如已有"采购订单管理"含"操作审计追溯"需求项 → 新建"采购合同管理"时推断也需要 |
| `资产线索推断` | 22 资产中已有与当前角色语境匹配的分类维度，但 OR 未提及。如 22 资产已有"数据安全"分类维度位于当前角色语境下 → 推断应存在 |

#### 2.5.3 Phase B 需求项关系检测

Phase B 修订已有 STR-NFR 时，边界检查通过后，将本轮提取的需求项与 STR-NFR 已有分类需求清单比对。比对锚点为**需求项名称+22分类维度匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 需求项匹配 + 22 分类一致 + 至少一个来源非 `OR明示` | 来源升级（`OR隐含`→`OR明示`、`同类语境推断`→`OR明示`、`资产线索推断`→`OR明示`），内部细分结论=`确认` |
| 无新增 | 需求项匹配 + 22 分类一致 + 所有来源已为 `OR明示` | 追加 OR 引用 + 增量合并新 OR 中的定性期望/待量化线索（如有新内容），内部细分结论=`改进` |
| 22 判定变更 | 需求项匹配 + **22 判定不同**（合并重识别导致） | 更新 22 判定 + 内部细分结论=`22判定变更` + 变更原因。不新增需求项 |
| 补充 | 需求项不匹配 | 新增到分类需求清单，来源=`OR明示`，内部细分结论=`新增` |
| 过时 | 基线已有需求项 **未被**本轮 OR 覆盖（边界扩展触发语境重追踪后，基线中某些需求项不再落入新的 NFR 范围） | 内部细分结论=`过时` + 追加说明"边界扩展后未落入新的 NFR 分类范围，请确认是否移除"。保留该需求项在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 OR 重新判定 22 分类路径**——新 OR 可能改变需求项特征导致 22 判定变更（表中 `22判定变更` 行）。来源证据强度只升不降：`OR隐含`/`同类语境推断`/`资产线索推断` → `OR明示`，在 `确认` 行触发。

`[调整]` 是与关系类型正交的叠加标记：已有需求项的定性期望/适用范围线索/待量化线索变化，在关系标记之外叠加 `[调整]`。

### 2.6 STR-NFR 节点生命周期

STR-NFR 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §A.6 状态名映射表（wft01-nfr 列）。并行推进规则（资产线与 BA 线互不阻塞）见 91 规范 §A.6。

**主线流转**（wft01-nfr ←→ wft04-nfr）：

```
待确认方案 ──人类确认──→ 可以NFR设计 ──wft04锁定──→ 在NFR设计 ──wft04完成──→ 已NFR设计
     ↑                        ↑                         │
     │                        │               wft04退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

**上游变更**（新 OR 汇入触发 STR-NFR 修订）：

```
可以NFR设计 ──新OR修订──→ 可以NFR设计（版本递增，wft04 未消费）
在NFR设计   ──新OR修订──→ 在NFR设计（版本递增，wft04 增量处理）
已NFR设计   ──新OR修订──→ 待补充NFR设计 ──wft04补全──→ 已NFR设计
```

**本 Skill 的写回范围**：`待确认方案` / `可以NFR设计` / `待补充NFR设计` / `需wft01修订`。`在NFR设计` 和 `已NFR设计` 由 wft04-nfr 写入和推进。

下游退回 `需wft01修订` 时：读取 wft04-nfr 的缺失说明 → 按人类改进方案修订 STR-NFR（走 Phase B 修订流程）→ 人类确认 → STR-NFR → `可以NFR设计`。

### 3.1 Step Start

运行时 AI 按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策流程执行。先读取 `01-*.md`/`02-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表，再按以下顺序处理：

#### 3.1.1 输入校验

| 校验条件 | 判定 | 类型 |
|---------|------|------|
| STR-NFR 状态为 `需wft01修订` 且人类未提供改进方案 | 输出 wft04-nfr 的缺失说明，提示提供改进方案 → **退出** | 硬退出 |
| OR 状态不是 `待处理` | 输出不合格条目及当前状态 → **退出** | 硬退出 |
| OR 类型不是 NFR（含 FR-BIZ） | 输出类型分布，提示走 `wft01-biz` → **退出** | 硬退出 |
| OR 类型不是 NFR（含 FR-ENG） | 输出类型分布，提示走 `wft01-eng` → **退出** | 硬退出 |
| OR 为业务配置实例 | 标记并提示不进入 NFR 设计 → **退出** | 硬退出 |
| OR >10 条 | 输出超限提示 → 人类确认后继续或退出 | 软提示 |
| OR 混入多个无关角色语境 | 输出边界混杂提示 → 人类确认拆分后继续或退出 | 软提示 |
| 无任何入口条件满足 | 输出”无待处理对象”→ **退出** | — |

> 软提示不强制退出，由人类选择继续或退出。逻辑上不可能的条件（状态不符、类型不匹配）为硬退出（§A.4.5）。

#### 3.1.2 退回优先（§A.4.3 门禁）

存在 `需wft01修订` 的 STR-NFR 节点（来自”待下游退回处理”分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注或下游 Skill 的具体改进指引）
- 已提供 → 通过门禁，读取 wft04-nfr 的缺失说明，按人类方案走 Phase B 修订流程
- 未提供 → 输出 wft04-nfr 的缺失说明 + 提示提供改进方案 → **退出**

#### 3.1.3 反馈处理

存在”待反馈处理”分节中的 STR-NFR 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理（§3.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 OR，Step End 时提示。

#### 3.1.4 新 STR-NFR 路由

有未处理的 OR 条目（来自”待 wft01-nfr 处理”分节）→ 进入 Step 1→Step 3，逐条执行 Phase A 语境提取与路由（§3.4.1），归入已有 STR-NFR（→Phase B）或待聚合池（→Phase C）。

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 STR-NFR 的角色语境/分类维度/需求清单。Step 3 的 Phase B 宿主匹配必须基于 Step 2 修改后的最新 STR-NFR 内容，不得使用缓存旧状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

### 3.2 Step 1 · 设计材料加载

加载产品数据与资产文档遵循 [91 规范 §A.3.3](91-eos-biz-eng-spec.md#a33-产品数据文档与资产文档读取与写回约定) 的统一读取协议：变更感知 → AI可以处理节点优先 → 索引导航。

**步骤零：变更感知（检测人类反馈）**

读取文件前先检测自上次 AI 运行以来人类是否修改过文件：

1. 读取文件头 `**HEAD @上次 AI 运行**` 字段，获取上次提交 hash H
2. Bash("git diff H..HEAD -- 目标文件") → 返回 H 到当前 HEAD 之间的全部变更
3. 无变更 → 进入优先读取
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）
   → 判定变更类型：结构化标注（`[同意]`/`[修改]`/`[驳回]`）→ 按 §A.5 协议处理；非标自由文本 → 标记 `[需确认]`；无关修改（格式/排版）→ 忽略
   → 将存在反馈的节点加入AI可以处理节点"待反馈处理"分节

**优先读取**（通过 `## AI可以处理节点` 定位本轮入口）：

入口判定通过后（§3.1.1），从 `## AI可以处理节点` 对应分节获取待处理节点 ID 列表：
- 有新输入 → 读「待 wft01-nfr 处理」分节
- 有待处理反馈 → 读「待反馈处理」分节
- 有下游退回 → 读「待下游退回处理」分节

逐节点：Bash("grep -n '@{节点ID}' 目标文件") 定位行号 → Read 节点块。

**索引导航**（AI可以处理节点无待处理时，或按域浏览时）：

1. Bash("grep -n '索引行数：' 目标文件") → 定位索引行号 L
2. 从 L 提取 N → Read 业务域索引
3. 按锚点 Read 域内索引 → 获取节点 ID 列表
4. 按需：Bash("grep -n '@{节点ID}' 目标文件") → 定位行号 → Read 节点

**加载清单**（按需扩大 - 仅在索引缺失、候选冲突、资产全貌不足以判断边界或追溯关系断裂时）：

1. `01-*.md` 树画像 / 状态队列 / 节点索引 — 定位本轮 NFR OR 条目正文块及追溯线索
2. `02-*.md` STR 树画像 / 状态队列 / 节点索引 — 定位本轮 STR-NFR 节点块，同时读取相关 STR-F/STR-E 索引用于适用范围线索
3. `21-eos-stakeholder-roles.md` — 角色定义、业务域和角色类型线索
4. `22-eos-nfr-taxonomy.md` — NFR 一级类目/分类维度清单（运行时动态读取，不缓存）
5. `91-eos-biz-eng-spec.md` — nfr 路径分工、反馈、生命周期和变更协议

**按需扩大规则**（[91 规范 §11.12](91-eos-biz-eng-spec.md#1112-按需读取规则)）：

- OR / STR-NFR 正文块 — 按 ID 从索引定位
- 候选 STR-NFR 块 — 按同角色/同语境/同分类维度筛选，用于宿主匹配
- 反馈重入 — 仅读取条目的确认状态字段及反馈指向块，不做全量重读
- 扩大触发：索引缺失 / 候选冲突 / 资产全貌不足以判断边界 / 追溯关系断裂时

> 禁止行为：不得在常规 Step 运行中默认加载完整文件正文；不得将 `疑似` 或 `待确认` 节点的 ID 作为下游强依赖（§A.3.3 R3）。

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：角色语境 + 每个 NFR 分类需求项 + 每条 22 分类建议 + 每条补充 NFR 缺口。各条目的 `确认状态` 字段位于 `02-*.md` STR-NFR 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 NFR OR 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解人类反馈在 NFR OR 需求语境中的含义，再执行修订，最后检查修订后的 STR-NFR 是否仍满足 OR 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 NFR OR——反馈处理以 NFR OR 需求理解为锚，不脱离 OR 文本内容自行修订 |
| **操作条目** | 角色语境 + 每个 NFR 分类需求项 + 每条 22 分类建议 + 每条补充 NFR 缺口。各条目的 `确认状态` 字段写入 `02-*.md` STR-NFR 节点的对应条目中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → STR-NFR → `可以NFR设计`。存在 `[修改]`/`[驳回]` 且无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需进入 Step 3 重做 |
| **级联触发条件** | 角色语境或被驳回/修改导致 NFR 分类维度变更、22 分类拓扑变化或需求清单重组 → 触发需求级联检查（重验修改后 STR-NFR 是否仍满足 NFR OR 需求）→ 通过后触发资产对齐级联 |
| **资产对齐级联** | 方案变更影响 22 资产时，更新对齐结论——分类维度变更 → 更新 22 引用；Q 级别变更 → 更新 22 判定。资产映射由 Step 5 维护 |

### 3.4 Step 3 · 角色 NFR 分类设计

#### 3.4.1 Phase A：OR 语境提取与路由

对每条新 OR 执行语境提取（关注角色 + 业务/平台语境 + 非功能诉求 + 适用对象线索，详见 §2.4.1）。先判定路径归属——实际为业务流程/输出文档→退回 `wft01-biz`，实际为引擎能力/CU/组件→退回 `wft01-eng`，仅为业务配置数据→标记不进入 NFR 设计。路径确认后，逐条做宿主匹配：

| 条件 | 路由 |
|------|------|
| OR 的角色 + 业务/平台语境 + 22 分类维度落入已有 STR-NFR 的分类边界 | 归入该 STR-NFR → Phase B |
| 不满足 | 进入待聚合池 → Phase C |

待聚合池按**同一角色 + 同一语境 + 同一 22 分类维度**分组（`{角色, 语境, 22分类维度, OR列表}`）。此阶段仅粗略分组，需求项去重和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 STR-NFR

1. **要素提取**：从本轮 OR 提取关注角色、业务/平台语境、非功能诉求、待量化线索和适用对象线索（详见 §2.4.1）。先提取后检查——分类维度冲突时需输出分类裁决项，依赖提取结果中的 22 分类信息
2. **边界匹配检查**：确认 OR 仍在 STR-NFR 分类边界内（详见 §2.4.3）。直接归入→追加来源；新增需求项→加入清单；边界扩展→更新适用范围线索 + 变更声明；分类冲突→标记 `[需裁决]`；宿主误匹配→退回待聚合池。Phase A 匹配是候选筛选、Phase B 是精确匹配——边界扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决；宿主误匹配时退回待聚合池留待下一轮
3. **需求项关系检测**：比对已有基线，判定确认/无新增/22判定变更/补充/过时（详见 §2.5.3）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 STR-NFR 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 STR-NFR

1. **确定角色语境** → 从 OR 语义提取关注角色、业务/平台语境、链身份（详见 §2.4.1）
2. **判定 22 分类路径** → 一级类目 → 分类维度 → Q1/Q2/Q3/Q3+ 判定（详见 §2.4.2）
3. **生成分类需求清单** → 识别需求项 + 去重收敛 + 逐项判定来源类型与待量化线索 + 标注字段（详见 §2.5.1、§2.5.2）
4. **执行完备性检查** → 角色语境清楚/分类维度单一/适用对象有线索/待量化线索保留/分类资产对齐明确（详见 §2.1.3）
5. **组装 STR-NFR** → 角色语境 + 22 分类路径 + 分类需求清单 + 适用对象线索汇总 + 完备性检查结果，写入 `02-*.md`（完整要素见 §2.1.2）

### 3.5 Step 4 · 补充 NFR 与变更声明

Step 4 按每个 STR-NFR 实例独立执行。新建 STR-NFR → 全量检查；修订已有 STR-NFR → 仅当分类维度拓扑变化（新增/过时/维度归属变更）时重验闭合，要素机械检查始终针对变更节点执行。

**1. NFR 闭合检查**

- 逐 STR-NFR 检查 NFR 分类需求清单的三类闭合
- 关注角色缺失（不知道谁提出/承受该非功能约束）→ 标记 `[需澄清]`，不生成补充材料（无法确定角色语境）
- 适用对象缺失（不知道约束全局、业务域、STR-F、STR-E 还是平台能力）→ 缺口类型 = `补充OR`
- 可验证语义缺失（不知道通过什么现象证明该质量已满足）→ 缺口类型 = `澄清项`
- 分类维度冲突（同一 OR 无法稳定归入已有 22 分类维度）→ 输出分类裁决项，不自行并入
- 一个 OR 混合多个 NFR 维度 → 输出拆分建议，退回 OR 预处理
- 缺口 → 进入「补充 NFR 材料生成」。不因缺口脑补节点——缺口就是缺口

**2. 要素机械检查**（逐 STR-NFR，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 用户角色 / 业务域或平台能力语境 / NFR 一级类目 **非空**
- [ ] NFR 分类需求清单 **非空**，逐项标注定性期望、适用范围线索、来源类型（`OR明示` / `OR隐含` / `同类语境推断` / `资产线索推断`）
- [ ] 22 分类资产对齐（Q1/Q2/Q3/Q3+）**到位** / `[推断]` 标记已写入推理依据
- [ ] 变更影响声明 **已写入**（首版写”首版，无变更”；格式见 §2.7）

**3. 补充 NFR 材料生成**

闭合缺口时生成。写入 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<STR-NFR名称>补充原始需求材料.md`，包含：材料编号 / 来源 STR-NFR / 来源 OR / 缺口类型 / 补充需求文本 / 推断依据 / 建议类型（`补充OR` / `澄清项` / `拆分建议` / `分类裁决`）/ 确认状态。同时登记到 `01-eos-sysdev-status.md` 表 A（生命周期=`已登记`）。文件引用写入 STR-NFR 节点的完备性检查结果。

**4. 22 分类资产触发检查**

从 22 资产比对当前 STR-NFR 的分类维度引用，判定当前批次 STR-NFR 是否触发了 22 分类资产增补需求（当前批 STR-NFR 使用了 22 中不存在的分类维度，或 Q3+ 候选分类建议指向新的维度定义）。缺分类定义且触发时 → 形成 22 分类建议（不直接固化），在 Step End 中提示人类审查后录入 22 资产。不生成补充 OR 材料、不登记 OR 状态表、不自动补。

### 3.6 Step 5 · 资产写回与落账

遵循 [91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 的统一写回协议。仅写回状态=`可以NFR设计` 的 STR-NFR 节点。人类已在 Step 2 确认方案（含 22 分类对齐结果），Step 5 不设二次确认。Step 3 新产出留待下一轮。

**写回资产操作**：

1. 遍历已确认 STR-NFR，按 22 分类对齐结果写回 22 资产：
   - Q1 → 定位已有分类维度，追加 STR-NFR 引用（去重）
   - Q2 → 引用已有分类维度，写入候选扩展说明并标注 `[推断]`，等待 wft04-nfr 量化校验，不改写 22 分类资产
   - Q3/Q3+ → 写入候选分类建议并标注 `[推断]`、`[需裁决]`，等待 wft04-nfr 校验，不固化为资产事实
   不写系统量化指标（量化指标由 wft04-nfr 负责）
2. 记录资产写回记录到 `02`（日期/路径/动作/判定）
3. 对应 OR 条目 → `已分配`；补充 NFR 材料登记到 `01` 原料状态表
4. 记录 OR→STR-NFR→22 引用链

**写回时的同步维护**（[91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 要求每次写回同时维护以下内容）：

| 操作 | 同步更新 |
|------|---------|
| 新增/修改节点 | 更新域产品索引的 `节点数`；更新 `## AI可以处理节点` 对应分节——节点状态变更时移入或移出 |
| 修改节点状态 | 更新AI可以处理节点对应分节：状态符合消费条件时加入，不符合时移出 |
| 新增/删除子条目 | 更新父节点 `**子条目状态**` 汇总值 |
| 人类标注处理 | 同步更新父节点 `**子条目状态**`（子条目标注时）和 `**确认状态**`（父节点标注时）；AI可以处理节点"待反馈处理"同步 |

**提交规范**（每次写回后必须执行）：

1. 在 `## AI最近变更` 表追加一条记录（[91 规范 §11.6](91-eos-biz-eng-spec.md#116-ai最近变更)），含时间/操作 Skill/操作类型/节点ID/变更摘要，操作类型列含 `[→](#节点ID)` 超链接
2. 更新文件头 `**文档版本**`（递增次版本号）、`**修订日期**`、`**HEAD @上次 AI 运行**`（=当前提交 hash）
3. 保留 AI最近变更最近 30 条，超出时从最旧行滚动删除
4. git add + git commit（带 Co-Authored-By: Claude）

**写回要求**：幂等去重、局部写回、全貌同步。所有操作在本 Step 内完成，不允许"本次写节点、下次更新索引"。

说明：Step 5 不改变 STR-NFR 状态。资产写回是独立收尾，不构成 wft04-nfr 前置条件。

### 3.7 Step End · 运行结束输出
