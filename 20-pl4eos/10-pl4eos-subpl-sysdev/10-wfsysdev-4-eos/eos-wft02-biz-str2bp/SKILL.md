## 一、职责定位

| 接收 wft03 退回的 `需wft02修订` BP 节点，按人类方案修订 | — |

## 二、操作流程

### Step Start · 前置校验与路由

**入口检测**（按 [91 规范 §A.4](../91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)）：

```bash
# 1. 读取待处理节点（三个分节）
bash ../scripts/read-section.sh ../../80-pl4eos-2-eosdata/04-eos-business-architecture.md "AI可以处理节点"
```

三类入口节点：
- **待 wft02-biz 处理** → 新 STR-F 节点
- **待反馈处理** → 人类退回的 BP 条目
- **待下游退回处理** → `需wft02修订` 的 BP 节点

**输入校验**（按顺序，命中即退出）：

| 条件 | 判定 | 动作 |
|------|------|------|
| BP 状态=`需wft02修订` 且人类未提供改进方案 | 退回方案缺失 | 输出 wft03 缺失说明 → **退出** |
| 无任何待处理节点 | 无待处理对象 | 输出"无待处理对象"→ **退出** |
| STR-F 状态≠`可以分解分配`/`待补充分解分配` | 状态不符 | 输出状态分布 → **退出** |
| 选中节点含 STR-E/STR-NFR 类型 | 类型不匹配 | 输出类型分布 + 路由指引 → **退出** |
| 选中 STR-F >5 个 | 超建议阈值（软提示） | 输出建议分批 + 节点列表 → 人类确认 |

**退回优先**：存在 `需wft02修订` BP 节点 → 检查人类是否提供改进方案。已提供 → 读取缺失说明，走 Step 3~5 修订。未提供 → 输出缺失说明 → **退出**。

**反馈处理**：存在"待反馈处理"分节中 BP 节点（确认状态=`[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2。

**新 STR-F 路由**：有未处理 STR-F → 进入 Step 1→Step 3，按产品路径+用户角色匹配已有 BP（Q1/Q2 归入 / Q3 新建）。

> **执行顺序**：Step 2（反馈处理）必须先于 Step 3（新增设计）——反馈可能改变 BP 的产品路径、业务清单或权限结论。

**触发条件**：Step Start 检出"待反馈处理"分节中有未处理的 BP 条目，或上一轮 Step End 的反馈等待中人类提出修改意见。

**本 Skill 的条目**：A2 方案 / Bn 方案 / 输出文档设计（含 PL6-A 活动节点 + PL6-B 正文条目需求）/ 数据权限 / 23/24/26/27/28 资产对齐结论。条目 `确认状态` 字段位于 `04-*.md` BP 节点块各条目正文中。

#### 特化参数

| 特化维度 | wft02-biz 值 |
|---------|-------------|
| **锚点需求** | 当前 BP 所承接的全部 STR-F 节点——人类反馈理解和修订均以 STR-F 场景业务需求为最终锚点 |
| **操作条目** | A2 方案 / Bn 方案 / 输出文档设计（含 PL6-A + PL6-B）/ 数据权限 / 23/24/26/27/28 资产对齐结论 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → BP 推进至 `可以SR设计` |
| **清除条件** | 已有 `[同意]`+`[已处理]` 默认跳过。仅当本轮新输入满足**任一**条件时清除 `[已处理]`（保留 `[同意]`）：<br>1. 新输入是该条目的直接上游节点（如新 STR-F 是 BP 来源）<br>2. 新输入与条目同属一个架构层级且边界重叠<br>3. 新输入导致条目定义被修订（变更影响声明标注为修订型/结构型） |
| **级联触发条件** | `[修改]`/`[驳回]` 导致方案结构性变更（产品路径变更/文档增删/引擎变更/PL6-B 条目增删）→ 标记受影响条目为 `[需重设计]` |
| **资产对齐级联** | 方案变更影响 23/24/26/27/28 资产引用 → 更新受影响资产的 Q 判定和引用路径 |

#### 确认状态格式示例

**AI 写入（Step 3~5 完成时）** —— 为每个条目初始化 `确认状态` 字段，初始为空：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: (空)
- 采购申请单（输出文档，@engine-flow + @engine-entity） [23B-Q2] | 确认状态: (空)
```

**人类在条目 `确认状态` 字段标注**：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: [同意]
- 采购申请单（输出文档，@engine-flow + @engine-entity） [23B-Q2] | 确认状态: [修改]：引擎应改为 @engine-workorder + @engine-entity
```

**AI 处理完成后** —— 在人类标注末尾追加 `[已处理]`：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: [同意] [已处理]

```

人类改写 `确认状态` 即覆盖旧内容，`[已处理]` 自然消失，条目回到待处理状态。

### Step 3 · 角色场景视角 BP 设计

以 STR-F 场景职责边界为锚，落成 A2 角色场景视角 BP。核心工作：给每个 STR-F 的 SL5 场景业务确定 SL4 角色职责归宿。

#### 3.1 推断 SL4 角色职责

| 判定 | 条件 | 动作 |
|------|------|------|
| **Q1 复用** | 已有同名/同义 SL4 且职责范围一致 | 直接引用，STR-F 归入该 SL4 |
| **Q2 扩展** | 已有相近 SL4 但需扩展其职责边界 | 扩展已有 SL4 + 归纳新 STR-F |
| **Q3 新建** | 无匹配的已有 SL4 | 新建 SL4 角色职责节点，写入 `04-*.md` |

SL3 角色类型从 STR-F 用户角色直接映射，不重复判定。SL4 占级规则：角色仅一个 SL5 时 SL4 不独立占级，已有 SL4 可扩展边界容纳新 L5 节点（Q2），无法归入时新建（Q3）。

Q1/Q2 归入已有 SL4 时，将本轮新 STR-F 的输出文档清单与该 SL4 下已有内容逐项比对——确认则升级来源、补充则全量重新展开（非增量追加）、无新增则仅加引用、矛盾则记录待人类裁决。

#### 3.2 输出文档需求定义

场景业务的需求由 STR-F 定义，Step 3 将其分解分配到各输出文档——每个输出文档承接一部分场景职责。对 STR-F 业务链中的每个输出文档，确定：

- **文档职责**：该文档在场景中承担什么角色（如"承载申请数据""记录审批结果""汇总指标"）
- **信息来源**：数据从哪个前序文档流入，或由用户直接录入
- **输出去向**：产出物被哪个后续文档消费，或直接交付给用户

SL5 与 STR-F 1:1 映射，场景职责复用 STR-F 的场景职责边界。将上述分配结果连同触发动作和上下文传递点按 STR-F 的业务链顺序写入 BP 节点。

完成写入后执行 23A/24 对齐判定（规则见附录 A.1），写入 `04-*.md`。

### Step 4 · 输出产品视角 BP 设计

将 STR-F 的输出文档清单落成 Bn 输出产品视角 BP。分五个 Phase 执行。

#### Phase A — 引擎校验与 PL4 节点生成

**① 引擎候选建议校验**：对每个输出文档，基于 BP 上下文逐文档校验 wft01 的引擎候选建议：

| 校验结果 | 判定条件 | 动作 |
|---------|---------|------|
| **确认** | 候选引擎与 BP 展开后的文档职责和处理模式完全匹配 | 去掉 `[推断]` 标记 |
| **修正** | 候选引擎部分匹配但需调整 | 写入修正后引擎 + 修正原因 + 去掉 `[推断]` |
| **推翻** | 候选引擎与 BP 展开后不兼容，且 25 资产中无可替代引擎 | 标注 `[引擎待确认]` + 不兼容原因 → Step End 提示人类裁决 |

**② PL4 节点生成**：对每个输出文档，PL1（业务域）从 STR-F 读取，PL2/PL3 从 STR-F 23B 判定读取。若 wft01 尚未产出 23B 判定，AI 基于输出文档性质和校验后引擎类型推断，标注 `[推断]`。

PL4 WBS 将同一构件类型下的输出文档按业务模块归纳分组。取输出文档名称/用途/支撑引擎的共性特征命名 WBS。已有 WBS 可扩展边界容纳新文档（Q2），无法归入时新建（Q3）。WBS 归组规则（含完成耦合）详见 [人类方案 §2.6.2](../eos-wft02-biz-str2bp.md#262-sl4pl4-归纳分组)。

**③ 23 资产一致性检查**：PL 路径确定后，逐文档比对 wft01 的 23B 判定与 BP PL 路径推导结论：

| 不一致类型 | 判定条件 | 动作 |
|-----------|---------|------|
| **归属冲突** | wft01 23B 建议的 PL2/PL3 与 BP PL 路径推导不一致 | 标注 `[23归属冲突]` + 两者路径对比 + 提示人类裁决 |
| **误新建** | wft01 23B-Q3 建议新建，BP 上下文发现已有条目可承接 | 降为 Q2 + 记录降级原因 |
| **误引用** | wft01 23B-Q1 引用已有条目，BP 展开后发现职责边界不能覆盖 | 升为 Q2 或 Q3 + 记录升级原因 |

矛盾项在 Step 6 写回时**暂不写回 23**（待人类裁决后下一轮处理），其余无矛盾项正常写回。

#### Phase B — 输出文档方案定义

对每个输出文档，PL 路径和支撑引擎确定后，定义文档的完整结构方案。

**正式文档方案**：

| 要素 | 定义内容 |
|------|---------|
| **封面字段** | DocumentCover 表映射——单据号/标题/状态/版本/创建人/部门/日期等。按文档类型裁剪（流程文档添加审批字段、计划文档添加计划周期字段） |
| **正文实体结构** | 内容实体的字段集——字段名/字段类型/约束/CRUD。从 STR-F 输出文档的 `业务链文档序列` 提取 |
| **正文转化引擎** | 由 Phase A ① 校验后的引擎结论直接引用，不再重新判定 |
| **支持信息引用** | 引用关系——引用文档名称/引用方式（只读/更新）/引用用途。去重 |

**轻量文档方案**：无封面，正文实体结构定义同正式文档；正文转化引擎由校验后结论直接引用。全部方案内容标注 `[推断]`，经人类确认后方可落账。

#### Phase C — 流程工单活动设计 + 看板指标设计

**流程工单活动设计**（仅针对 STR-F 已确认的流程/工单类输出文档）：

按 §2.5 定义活动节点序列——逐节点定义处理角色、可执行动作、状态变迁、系统自动节点/异常路径/超时处理。推断依据（按优先级逐层驱动）：
1. **主驱动**：对 STR-F 场景需求的理解——该文档在业务链中承担什么职责、需要哪些处理步骤
2. **约束**：支撑引擎的能力边界——是否在 `@engine-flow`/`@engine-workorder` 能力范围内
3. **参考**：同类文档模式 + AI 经验
4. **门禁**：全部标注 `[推断]`，经人类确认后方可落账

非流程/非工单类输出文档跳过。

**看板指标设计**（仅针对 STR-F 已确认的看板类输出文档）：

逐指标标注指标名称、度量口径、度量目标、聚合维度、显示图示和刷新频率。推断依据同活动设计（主驱动→约束→参考→门禁）。非看板类输出文档跳过。

#### Phase D — 文档缺口推断 + 权限设计

**文档缺口推断**：逐文档检查 26 资产是否已有对应文档定义。有则引用（26-Q1），需扩展则标注（26-Q2），无则形成新建建议（26-Q3）。按 WBS 推断应有文档清单，与 STR-F 已有文档比对：

| 推断来源 | 说明 | 处理 |
|---------|------|------|
| 26 资产已定义 | 23 WBS 行引用的文档定义清单 | 正式依据，直接比对 |
| AI 经验推断 | 基于同类 WBS 模式、行业知识 | 标注 `[推断-待OR确认]`，由 Step 5 生成 OR 材料 |
| STR-F 已确认 | wft01-biz 已确认的输出文档 | 视为已覆盖 |

比对后，STR-F 未覆盖的为缺口——写入 BP 节点缺口说明。

**文档权限设计**（仅针对 STR-F 已确认的输出文档）：

基于 STR-F 的 `用户角色` 和角色在业务链中的位置，按四维度推导：

| 维度 | 推导来源 |
|------|---------|
| 字段可见性 | 角色职责范围、风险合规约束 |
| 字段可编辑性 | 角色在业务链中的位置：录入者/审批者/查询者 |
| 行级数据范围 | 角色组织归属 |

### A.5 变更类型判定

| 变更类型 | 判定标准 | 对下游影响 |
|---------|---------|----------|
