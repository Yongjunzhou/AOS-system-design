## 二、功能表单与窗口标签页设计基础

> **本章定义**：功能表单、窗口标签页、三层页面编排（菜单标签页→场景标签页→页面组件）、布局组件、主子组装关系、引擎能力使用需求和 FR-BIZ 指标约束包——即本 Skill 的操作对象及其关系。权威定义见 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型)、[§2.2~§2.5](91-eos-biz-eng-spec.md#22-正式文档的组成)、[§3.2~§3.4](91-eos-biz-eng-spec.md#32-引擎及层级)、[§4](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)。操作流程见第三章。

> 本章只定义操作对象"是什么"，不定义"怎么做"（§A.2.3）。领域规则、覆盖自查清单、生命周期和变更传播协议放在章末。

### 2.1 功能表单定义

**功能表单**是功能引擎将物理表转换后的用户可操作界面单元（[91-eos-biz-eng-spec.md] §2.2）。其命名已揭示双重构成：

- **表单**——用户看到的界面载体：字段、表格、布局、TAB（引擎能力①：表单能力）
- **功能**——用户在表单上执行的操作：按钮、右键操作项、双击下钻（引擎能力②：功能能力）

功能引擎将物理表的数据结构**转换为表单**，再为表单**注入业务功能**，两者合称为**功能表单**。功能表单是运行时形态的抽象定义，由窗口标签页、全屏单据页、辅助栏标签页或弹窗页面等页面组件承载；配置页面不属于功能表单的页面组件。

> **从输出文档到功能表单需求**：每个 PL5 输出文档形成正文功能表单需求；正式文档还形成封面表单需求以及封面—正文 1:1 主子关系需求。若正文与其他文档存在层级引用，再形成 1+N 下钻需求。指标、看板等仍按相同文档模型处理。

功能表单按 [91 规范 §1.2](91-eos-biz-eng-spec.md#12-平台页面层级与类型) 选择页面组件承载：窗口标签页（列表模式/单据模式/图示模式：含指标模式、看板模式）、全屏单据页、辅助栏标签页（列表模式/单据模式）或弹窗页面。菜单引擎内置的场景编排能力（91 规范中简称“场景引擎”，不是独立引擎资产）把窗口标签页编排为场景标签页（初始态单窗/分屏态双窗），菜单树能力再把场景标签页编排进菜单标签页。列表页面、单据页、指标页面、看板页面、辅助栏、弹窗页属于页面组件内部的布局组件，不是与页面组件并列的页面类型。

在引擎生成链中的位置（§2.3）：

```
物理表（实体引擎） → 功能表单及页面组件（功能引擎） → 场景标签页（@engine-menu 场景编排能力） → 菜单标签页（@engine-menu 菜单树能力）
```

- 物理表是用户看不到的底层数据
- **功能表单/主子表单**是同一概念——有子表单的功能表单即为主子表单（N≥1），无子表单的为简单功能表单（N=0），1+N 组装是功能引擎的运行期能力（§2.2 能力③）
- 场景业务通过菜单引擎内置的场景编排能力组织窗口标签页，并由菜单树能力发布为菜单标签页中的端到端工作台

### 2.2 三层页面编排

页面层级自顶向下为菜单标签页→场景标签页→页面组件，生成过程则自底向上执行：

- **窗口标签页**：单个实体数据在场景标签页中的展示载体，以列表页面（列表模式）、单据页面（单据模式）承载数据内容，或以指标页面（指标模式）、看板页面（看板模式）承载图示化内容。本 Skill 描述业务角色需要哪些窗口标签页、标签页如何流转，以及每个标签页的字段可见性、操作按钮、校验、结果反馈和 FR-BIZ 性能指标。
- **场景标签页**：菜单引擎内置的场景编排能力将窗口标签页编排而成的页面集合，必须说明初始态单窗、双击下钻后的分屏态双窗、辅助栏和面包屑行为。
- **菜单标签页**：末级菜单 M4 打开的浏览器标签页，是一个场景业务的端到端工作台，由若干场景标签页组成；菜单引擎负责菜单树、M4 映射和场景标签页编排。

三层编排至少包含：

- **TAB 序列**：同层功能表单/主子表单按输出文档流转顺序呈现
- **表单依赖**：表单间生成、提交、引用和触发依赖
- **流程类页面序列**：由 PL6-A 活动节点形成的审批、派发、处理、验收等页面序列
- **主子与下钻关系**：正式文档封面—正文 1:1，以及关联文档的 1+N 下钻关系

主子组装由功能引擎在运行期实现；本 Skill 不设计实现机制，但必须给出所需组装关系和交互需求。

### 2.3 支撑引擎与 CU 能力参照

wft02-biz 已为每个 BP 末级对象标注支撑引擎。本 Skill 读取 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 的引擎/CU 能力结构，仅用于判断现有能力能否承接需求及定位缺口，不生成 CU 设计或配置参数。

**CU**：每个引擎包含若干可独立选配的配置单元，能力边界定义见 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md)。本 Skill 只读取其运行期能力作为参照，形成引擎能力使用需求，不修改 CU。页面组件、布局组件与构件体系见 [91 规范 §四](91-eos-biz-eng-spec.md#四布局组件构件与路径边界)。

支撑引擎信息分三层，仅只读参照，不写回 25。支撑状态为"能力不足"的对象标注 `分解依据不足`，不补写引擎方案。

每个业务页面同时形成引擎能力使用需求：`业务页面 / 业务动作 / 引擎 / CU能力引用 / 输入 / 期望输出 / FR-BIZ指标 / 覆盖结论`。全部已确认的使用需求装配为 `FR-BIZ 指标约束包`，由 wft05-eng 消费。指标仍归属于原 FR-BIZ，不转为 NFR。

覆盖判定：Q1=能力和指标均已覆盖，直接引用；Q2=能力存在但指标上限不足，生成 FR-ENG 增强候选；Q3=IPO能力缺失，生成 FR-ENG 新增候选；Q4=引擎/CU边界不清，标记 `[需裁决]`。

### 2.5 设计规则与匹配判定

#### 2.5.1 设计规则

**规则1：功能视角转换**。BP 的"业务怎么做"转成 SR-F 的"用户在表单上按什么按钮、走什么流程完成业务"。

**规则2：单主职责粒度**。每条 SR-F 末级只表达一个主系统职责（结构定义/录入提交/流程流转/指标计算等）。

**规则3：不替代引擎设计**。引擎能力不足不得写成业务功能 SR-F。

**规则4：不做 PA 配置规格**。SR-F 描述"系统必须提供什么功能"，不写入 CU 配置参数或构件方案。

#### 2.5.2 Q1/Q2/Q3 匹配判定

| 判定 | 条件 | 动作 |
|------|------|------|
| SR-Q1 | 已有 SR-F 对应同一 BP 对象、同一输入线、同一支撑引擎，且功能职责一致 | 复用已有 SR-F，追加 BP 引用 |
| SR-Q2 | 已有 SR-F 主体一致但功能规则、按钮操作、流程或验收口径需扩展 | 扩展已有 SR-F，全量重写该条功能定义 |
| SR-Q3 | 无可用已有 SR-F | 新建 SR-F 末级条目 |

#### 2.5.3 覆盖自查清单

覆盖自查在 Step 7 统一执行，先检查业务需求覆盖，再检查引擎能力参照和缺口路由。

**业务覆盖自查**：

1. A2 线：每个 SL5 场景业务均有用户可操作 SR-F 承接
2. A2 线：每个被编排的功能表单/主子表单均有需求定义承接
3. Bn 线：每个 PL5 输出文档/产品数据均有生成、维护或查询类 SR-F 承接
4. Bn 线：每个 PL5 输出文档的实体定义、实体关系、状态事件和业务规则均已被对应 SR-F 承接
5. 横切线：菜单可达、权限推导、上层指标方案均已转成必要 SR-F 或明确"不生成 SR-F"的理由
6. 追溯：每条 SR-F 均记录 BP 节点 ID、BP 对象 ID（即来源 BP 子对象在 23/24/26/28 中的资产 ID，wft02 资产写回未完成时可后补）、BP 消费版本
7. 页面模型：每条需求均区分页面组件与其内部布局组件，并说明其所在菜单标签页→场景标签页→窗口标签页编排链，组合与功能特征匹配

**引擎覆盖自查**：

8. 25 参照：每条需求记录支撑引擎及能力参照；能力不足项已形成 FR-ENG 线索或退回 wft02，不写 CU 配置参数

### 2.6 SR-F 节点生命周期

SR-F 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §A.6.2 通用六态定义表（wft03-biz 列）。

#### 2.6.1 推进态

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `待确认方案` | SR-F 方案已生成或修订，等待人类反馈 | §3 设计完成 |
| `可构件开发` | 方案已确认，可进入构件开发流水线 | 全部条目 `[同意]` + `[已处理]` |
| `在构件需求定义` | 构件开发流水线首 skill 已锁定此 SR-F，正在展开构件需求定义 | 下游写入活动锁 |
| `已构件需求定义` | 构件需求定义完成，SR-F 消费版本与当前版本一致 | 下游处理完成且未检测到上游新版本 |

本 Skill 写入 `待确认方案` / `可构件开发` / `需wft03修订`；下游流水线负责其自身的锁定态和完成态。

#### 2.6.2 BP 消费状态

| BP 状态 | 含义 | 本 Skill 动作 |
|---------|------|--------------|
| `可以SR设计` | BP 已确认，首次进入本 Skill | 生成或修订 SR-F |
| `待补充SR设计` | BP 已被旧版 SR-F 消费，上游新增/修订 | 按 BP 变更影响声明增量补全 SR-F |
| `在SR设计` | 本 Skill 正在处理 | 写入活动说明，避免并发重入 |
| `已SR设计` | SR-F 展开完成且 BP 消费版本一致 | 处理完成后写入 |

本 Skill 首次消费 BP 时在 SR-F 节点中记录 `BP 消费版本：v{N}`。重入时若 BP 当前版本 > SR-F 记录的消费版本，按 BP 变更影响声明判断增量型/修订型/结构型影响。

#### 2.6.3 下游退回态

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `需wft03修订` | SR-F 方案存在缺陷，需本 Skill 修订后重新交付 | 下游构件开发流水线写入，附带缺失说明 |

本 Skill 重入 `需wft03修订` 的需求节点时：读取缺失说明 → 按人类改进方案修订 → 人类确认 → `可构件开发`。若缺失根因在 BP（如 PL6-A/PL6-B 定义或支撑引擎信息缺失），将 BP 标为 `需wft02修订`，附带缺失说明。

### 2.7 BP → SR-F 变更传播协议

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。以下为本 Skill 特有的 BP→SR-F 影响判定与声明格式。

#### 2.7.1 变更类型判定（BP → SR-F 特化）

| 类型 | 判定条件 | SR-F 处理 |
|------|----------|-----------|
| **增量型** | BP 新增 SL5/PL5/权限/指标对象，既有对象未变 | 仅为新增对象生成 SR-F，既有 SR-F 不动 |
| **修订型** | BP 既有 IPO、编排、权限、指标口径或产品数据边界被修改 | 修订受影响 SR-F，全量重写受影响条目 |
| **结构型** | BP 场景边界、产品路径、场景部件结构或菜单结构重塑 | 输出影响范围，等待人类裁决后重组 SR-F |
| **缺失型** | BP 缺少必要 IPO、引擎支撑信息或变更声明 | 将 BP 标为 `需wft02修订` 候选，附缺失说明 |

#### 2.7.2 受影响范围判断

| BP 变化 | 可能影响 |
|---------|----------|
| SL5 场景业务变更 | A2 场景入口、场景流、场景指标 SR-F |
| PL5 场景部件变更 | A2 部件操作、Bn 文档处理、权限、指标 SR-F；若涉及实体结构或业务规则变更，同步影响对应实体定义和规则 SR-F |
| 文档主子关系变更 | 功能表单的主子组装关系（由引擎运行时处理，本 Skill 只记录变更通知） |
| 菜单路径变更 | 菜单可达性、权限级联 SR-F |
| 权限推导变更 | 菜单权限、字段权限、行级权限、按钮权限 SR-F |
| 指标口径变更 | 指标定义、计算、展示、聚合 SR-F |
| 引擎支撑信息变更 | 对应 CU、25 参照、分解依据 |

#### 2.7.3 变更影响声明格式

每次生成或修订 SR-F 后写入：

```text
SR-F 变更影响声明
来源 BP：BP-XXX vN
SR-F 当前版本：vM
变更类型：增量型 / 修订型 / 结构型
影响的功能表单：<受影响条目列表>
影响的组装关系：<TAB序列/流程节点序列等变化>
受影响构件：<如已知则列出；未知写"待下游检查">
建议动作：新增构件 / 修订构件 / 重做构件 / 人类裁决
```

### 3.1 Step Start

运行时 AI 按 [§A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start) 入口决策流程执行。先读取 `05-*.md`/`06-*.md` 的 `## AI可以处理节点` 分节（[§11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），获取三类入口的节点列表（"待 wft03-biz 处理"/"待反馈处理"/"待下游退回处理"），再按以下顺序处理。

#### 3.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| BP 状态不是 `可以SR设计`/`待补充SR设计` | 状态不符 | 列出不合格节点及状态 → **退出** |
| BP 含 A1 平台引擎产品 | 类型不匹配 | 提示分路径（→ `wft03-eng`）→ **退出** |
| BP 状态为 `需wft02修订` | 上游待修 | 输出缺失说明，提示回到 wft02-biz → **退出** |
| SR-F 状态为 `需wft03修订` 且人类未提供改进方案 | 退回方案缺失 | 输出下游缺失说明，提示提供改进方案 → **退出** |
| 无 BP 选中 + 无"待反馈处理"节点 + 无"待下游退回处理"节点 | 无待处理对象 | 输出"无待处理对象"→ **退出** |
| 选中 BP >5 个 | 超建议阈值（软提示） | 输出建议分批 → 人类确认后继续或退出 |

> 软提示不强制退出，由人类选择继续或退出。逻辑上不可能的条件（状态不符、类型不匹配）为硬退出（§A.4.5）。

#### 3.1.2 退回优先（§A.4.3 门禁）

存在 `需wft03修订` 的 SR-F 节点（来自"待下游退回处理"分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注或下游 Skill 的具体改进指引）
- 已提供 → 通过门禁，读取下游缺失说明，按人类方案修订，人类确认后推进为 `可构件开发`
- 未提供 → 输出下游缺失说明 + 提示提供改进方案 → **退出**

#### 3.1.3 反馈处理

存在"待反馈处理"分节中的 SR-F 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理。全部已 `[同意]`+`[已处理]` 的条目跳过，不阻塞新 BP。

#### 3.1.4 新 BP 路由

有未处理的 BP 节点（来自"待 wft03-biz 处理"分节）→ 反馈处理完成后，逐 BP 节点进入 Step 1→Step 3 新设计流程。

**执行顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计）。反馈可能改变 SR-F 的功能定义或追溯关系，Step 3 必须基于 Step 2 修改后的内容，不得使用 Step 1 缓存的状态。此顺序与 §A.4.4 规则三一致（退回优先 → 反馈处理 → 新输入路由）。

| 特化维度 | wft03-biz 值 |

| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过扫描。仅当本轮新输入满足以下任一条件时，清除 `[已处理]`（保留 `[同意]`）使其回到待处理：（1）新输入为该条目的直接上游节点（如新 BP 节点是 SR-F 条目的来源）；（2）新输入与条目同属一个架构层级且边界重叠（如同属 SR-F 功能表单，新表单改变了已有表单的范围或归属）；（3）新输入导致条目定义被修订（变更影响声明标注为修订型或结构型，§A.5.3 Step 1） |

| **资产对齐级联** | 方案变更影响 05/06 资产引用 → 更新受影响 SR-F 的 BP 追溯引用 |

### 3.4 Step 3 · 菜单树与场景编排推导

**3.4.1 菜单树推导**

菜单树推导分两步：先将新增场景业务匹配到平台已有菜单树，匹配不上的层级才按规则新建。

**步骤一：读取已有菜单树**

从 `05-*.md` / `06-*.md` 中读取平台当前已定义的菜单节点（M1~M4），提取以下信息作为匹配基准：

| 提取项 | 用途 |
|--------|------|
| 已有 M1 及其业务域归属 | 判定新场景业务的业务域是否已被已有 M1 覆盖 |
| 已有 M2 及其角色类型分组 | 判定新场景业务的 SL3 角色类型是否已被已有 M2 覆盖 |
| 已有 M3 及其角色职责分组 | 判定新场景业务的 SL4 角色职责是否已被已有 M3 覆盖 |
| 已有 M4 及其映射的场景业务 ID | 去重——新场景业务 ID 与已有 M4 映射重复时，不再新建 M4 |

**步骤二：逐新增场景业务匹配与推导**

从 BP 中提取每个新增场景业务的四层归属信息（PL1/SL1 业务域、SL3 角色类型、SL4 角色职责、SL5 场景业务），按以下顺序逐层匹配：

| 层级 | 匹配规则 | 匹配成功 | 匹配失败 |
|------|---------|---------|---------|
| **M1** | 新场景业务的 PL1 业务域名称与已有 M1 的域名称语义一致（同域或同义词） | 复用已有 M1，M4 挂入其下 | **新建 M1**，名称取 PL1 业务域名称（如"采购管理"） |
| **M2** | 在已确定 M1 下，新场景业务的 SL3 角色类型与已有 M2 的角色分组语义一致 | 复用已有 M2，M4 挂入其下；若 M1 下辖场景业务 ≤3 个且无已有 M2，可**省略 M2** | **新建 M2**，名称取 SL3 角色类型名称；排序在已有同级 M2 之后 |
| **M3** | 在已确定 M2 下（或省略 M2 时在 M1 下），新场景业务的 SL4 角色职责与已有 M3 的职责分组语义一致 | 复用已有 M3，M4 挂入其下；若上级下辖场景业务 ≤2 个且无已有 M3，可**省略 M3** | **新建 M3**，名称取 SL4 角色职责名称；排序在已有同级 M3 之后 |
| **M4** | 新场景业务的 SL5 场景业务 ID 与已有 M4 映射的场景业务 ID 是否重复 | **去重**——已有 M4 已映射此场景业务 → 不新建，仅更新 M4 属性（如新增场景标签页） | **新建 M4**，名称取 SL5 场景业务名称，映射该场景业务 ID |

**新建非末级节点的规则**：

| 规则 | 说明 |
|------|------|
| **命名** | M1 = 业务域名称（取 BP 的 PL1/SL1 域名称）；M2 = SL3 角色类型名称；M3 = SL4 角色职责名称。不得自行编造与 BP 不一致的名称 |
| **显示顺序** | 新增节点排在同级已有节点之后；同级多个新增节点按场景业务在 BP 中的首次出现顺序排列 |
| **可见角色** | 非末级节点的可见角色 = 下辖所有节点的角色并集（即只要有任意一个子节点对某角色可见，父节点即对该角色可见） |
| **省略条件** | M2 省略条件：M1 下辖场景业务 ≤3 个；M3 省略条件：上级节点下辖场景业务 ≤2 个。省略时 M4 直接挂到上一级节点下，被省略层级的语义在 M4 名称中体现 |

**步骤三：逐节点定义**

逐 M4（含新建和复用的）：
- M4 名称 + 映射的场景业务 ID
- M4 可见性候选（继承场景业务的角色范围，标注 `[推断]`）
- M4 权限需求（见 §3.4.5）
- M4 单击后打开的菜单标签页所含场景标签页列表（见 §3.4.2）

逐非末级节点（仅新建或属性变更的已有节点）：
- 父节点归属、显示顺序、可见角色候选（下辖节点的角色并集，标注 `[推断]`）

> 若 wft02 的 BP 节点已标注菜单归属提示，优先采用，跳过匹配流程。AI 推断的匹配结论、新建节点和省略判定均标注 `[推断]` 供确认。菜单引擎（`@engine-menu`）对每条场景业务无条件支撑 [91 §1.3]，本 Step 不判定"能否支撑"。

**3.4.2 场景标签页编排**

一个场景业务（SL5）= 一个角色的一条端到端业务闭环 [91 §1.4]。场景标签页是菜单引擎将该场景业务的输出文档序列编排而成的页面集合 [91 §1.1.1]——**一个场景业务对应一个场景标签页**，不存在场景业务内部跨角色拆分。场景标签页此时尚未详细设计，以占位符（§3.4.3）参与编排。

**输入**：从 BP 中提取场景业务的 PL5 输出文档序列——按 wft02 Step 8 定义的文档流转顺序排列。序列中每条输出文档携带：文档类型（正式/轻量，决定是否生成封面占位符）、下钻子文档列表（来自 wft02 文档间引用关系 1+N）、任务类型（计划/流程/工单/无）。

**编排规则**：从序列首文档开始，逐文档生成 TAB：

```text
首文档 D1 的正文占位符 = 初始态单窗

遍历 D2, D3, ..., DN（k = 2, 3, ..., N）：
  │
  ├── D_k 有下钻子文档 D_sub？
  │     → D_sub 不占 TAB。平台在 D_k 行双击时自动分屏展示 D_sub [91 §1.2]
  │     → 继续处理 D_{k+1}
  │
  └── 否则
        → D_k 追加到 TAB 序列末位
```

- **初始态单窗**：序列首文档的正文占位符。列表模式优先——集合型正文（台账/指标/看板等）→ 列表页；单据型正文（流程/工单的活动节点）→ 单据页
- **TAB 序列**：除下钻子文档外，其余占位符按流转顺序依次排列。每个 TAB 对应一个 PL5 输出文档的正文占位符；正式文档封面占位符与正文占位符 1:1 主子组装（由功能引擎运行期完成），封面不单独占 TAB

场景标签页的**分屏态双窗**、**辅助栏**和**面包屑**均为平台级交互能力 [91 §1.1.1 / §1.2]，由菜单引擎和功能引擎在运行期自动提供，本 Step 无需定义。

**3.4.3 窗口标签页占位符定义**

为每个 PL5 输出文档生成一个**窗口标签页占位符**，按输出文档流转顺序排列为 TAB 序列：

逐占位符定义（仅骨架，不含字段和交互）：
- **页面 ID**：分配稳定页面 ID，格式 `@srf-tab-{场景业务简称}-{序号}`，使页面 NFR 可绑定到具体页面 [91 §1.1.1 页面类型定义]
- **来源**：PL5 输出文档 ID + BP 节点 ID + BP 消费版本
- **页面组件类型候选**：列表模式 / 单据模式 / 图示模式（含指标模式、看板模式）。判定依据详见 §3.5.3 步骤一。全量标注 `[推断]`
- **显示顺序**：在 TAB 序列中的位置（按输出文档流转顺序 [91 §1.4]）
- **所属场景标签页**：标注归属的场景标签页 ID（见 §3.4.2 划分结果）
- **组装关系注解**：正式文档标注"需 1:1 封面—正文主子组装"；存在下钻关系标注"需 1+N 下钻组装→目标占位符 ID"；轻量文档标注"无封面组装"。组装由功能引擎运行期完成 [91 §3.4]，本 Skill 只声明需求

> 占位符的字段定义、布局、交互行为、功能按钮、权限、校验规则和 FR-BIZ 指标由 Step 4（正文功能表单需求）填充；PL6-A 活动节点的窗口标签页序列由 Step 5 消费占位符后编排。Step 4~5 不得更改占位符的页面 ID、TAB 顺序和场景归属；如需调整页面组件类型或组装关系，须回写到占位符并标注 `[变更]`，同步更新受影响场景标签页的编排。

**3.4.4 页面 ID 分配与标注**

| 对象 | ID 格式 | 示例 |
|------|--------|------|
| 菜单标签页 | `@srf-menu-{M4简称}` | `@srf-menu-purchase-apply` |
| 场景标签页 | `@srf-scene-{场景业务简称}-{序号}` | `@srf-scene-purchase-apply-1` |
| 窗口标签页占位符（PL5 文档） | `@srf-tab-{场景业务简称}-{序号}` | `@srf-tab-purchase-apply-01` |
| 窗口标签页（PL6-A 活动节点） | `@srf-tab-{场景业务简称}-act-{序号}` | `@srf-tab-purchase-apply-act-01` |

全量标注：每条产出记录所属菜单标签页、场景标签页、场景业务、来源 BP 节点和 BP 消费版本。AI 推断的菜单层级、场景划分、TAB 顺序、页面组件类型候选均标注 `[推断]` 供确认。`[推断]` 项在 Step 2（反馈处理）中由人类确认或修正。

**3.4.5 菜单权限需求定义**

> 以上 §3.4.1~§3.4.4 为菜单结构方案和场景编排方案。菜单权限是**需求**——定义每个菜单节点对角色/人员的可见或不可见规则，由菜单引擎承载 [91 §1.3]。

1. **可见角色**：逐 M4，从 BP 中提取该场景业务涉及的角色范围——SL3 角色类型 + PL6-A 活动节点的处理角色（如审批人、派发对象）。取两者**并集**作为 M4 的可见角色候选。场景业务的直接角色（SL3）和任务流转中需要进入该菜单的角色（PL6-A 处理角色）均应能看到菜单入口
2. **可达性**：可见角色默认具有可达性（可点击进入）。若业务规则要求某角色可见但不可进入，单独标注可达性例外
3. **权限继承**：M1~M3 的可见角色 = 下辖所有 M4 可见角色的并集
4. 全量标注 `[推断]` 供确认。权限的运行期执行由菜单引擎负责，本 Step 只声明需求

### 3.5 Step 4 · PL5 输出文档：实体与功能表单定义

> 逐 PL5 输出文档，先消费 BP 的文档方案（wft02 Step 5）提取实体结构、定义实体字段（§7.3 Task 3），再将正文实体转化为功能表单需求（§7.3 Task 4），最后为功能表单选择页面组件与布局组件组合。Step 3 产出的窗口标签页占位符在此被填充字段/布局/交互/权限/校验的详细定义（占位符约束见 §3.4.3）。实体与文档模型的权威定义见 [91 规范 §二](91-eos-biz-eng-spec.md#二输出文档模型)，引擎能力见 [§3.2](91-eos-biz-eng-spec.md#32-引擎及层级)。

**3.5.1 输出文档定义消费**

逐 PL5 输出文档，从 BP 节点中提取以下信息（wft02 已产出，本步骤只读消费）：

| 提取项 | 来源（BP 节点字段） | 用途 |
|--------|-------------------|------|
| 文档类型 | wft02 Step 5 判定结果——正式 / 轻量 | 决定是否生成封面实体 |
| 封面字段（正式文档） | wft02 Step 5”封面字段”列表——单据号/标题/状态/版本/创建人/部门/日期等 [91 §2.2] | → Task 3 实体字段定义 |
| 正文实体结构 | wft02 Step 5”正文实体结构”——实体名称、核心字段及类型线索 | → Task 3 实体字段定义 |
| 正文转化引擎 | wft02 Step 5”正文转化引擎”——如 @engine-ledger / @engine-flow / @engine-indicator 等 | → Task 4 功能表单类型判定 |
| 任务类型 | 计划 / 流程 / 工单 / 无（wft02 Step 6 PL6-A 需求） | → Task 4 功能按钮集合、Step 5 窗口标签页序列 |
| PL6-B 条目类型 | wft02 Step 7 三独立判定通过的条目类型清单 | → §3.5.4 PL6-B 条目需求转化 |
| 支持信息引用 | wft02 Step 5 文档间引用关系及角色标签 | → Step 6 引用需求 |
| 角色范围 | BP 的 SL3/SL4 角色归属 + PL6-A 活动节点的处理角色 | → 权限推导 |

> 若 BP 缺少某项信息（如正文转化引擎未标注、封面字段列表为空），将该 PL5 文档标记为 `分解依据不足`，在 Step End 输出缺失说明并建议退回 `需wft02修订`。不得自行补做 BP 设计。

**3.5.2 实体需求定义**

根据文档类型，分两路定义实体：

**正式文档**：

| 实体 | 字段来源 | 定义规则 |
|------|---------|---------|
| **封面实体**（DocumentCover 表） | BP 的”封面字段”列表 | 逐字段：名称（取 BP 字段名）、数据类型（单据号→VARCHAR、日期→DATE、状态→枚举等，按字段语义推断，标注 `[推断]`）、必填/唯一/默认值（ID 类字段必填+唯一，日期字段默认当前日期，状态字段默认”草稿”） |
| **正文实体**（1:1 绑定封面行） | BP 的”正文实体结构” | 逐字段：名称、数据类型（按字段语义推断——金额→DECIMAL、数量→INT、文本→VARCHAR/TEXT）、必填/唯一/默认值、校验（按业务规则推断——金额>0、日期不晚于当前等） |

封面行与正文行关系：`derived_from` 追溯链 + 严格 1:1 [91 §2.5 R3]。

**轻量文档**：

仅定义正文实体字段（无封面实体），规则同上。正文实体即为文档本身，1 行 = 1 文档内容条目实例。

**字段定义要素**（逐字段）：

| 要素 | 说明 |
|------|------|
| 字段名 | 中文名 + 英文字段名（蛇形命名） |
| 数据类型 | VARCHAR(n) / INT / DECIMAL(m,n) / DATE / DATETIME / TEXT / 枚举 |
| 必填 | 是 / 否 |
| 唯一 | 是 / 否 |
| 默认值 | 有则写明，无则留空 |
| 校验规则 | 字段级约束（范围/格式/引用完整性） |
| CRUD | 新建时可见/可编辑、更新时可见/可编辑、删除规则、查询可见 |
| 追溯关系 | 来源字段映射——该字段对应 BP 输出文档定义中的哪个字段或哪个业务规则 |

**26 资产对齐**：逐字段检查 [26 号资产](../../80-pl4eos-2-eosdata/26-eos-document-definitions.md) 是否有同名同语义的已有字段定义。Q1→引用已有字段名和类型；Q2→引用+扩展约束；Q3→新建字段。资产对齐结论写入字段定义，不入增量清单。

**实体关系**：
- 正式文档：DocumentCover 实体 ← 1:1 → 正文实体（通过 DocumentCover 行的 `derived_from` 字段追溯）
- 轻量文档：正文实体独立存在，无关联实体
- 存在支持信息引用时：记录引用目标（统一指向被引用文档的 DocumentCover 行），引用字段定义由 Step 6 完成

**3.5.3 正文功能表单需求定义**

在实体字段定义完成之后，将正文实体转化为功能表单需求。功能表单 = 表单（字段布局/展示）+ 功能（按钮/操作），由对应引擎转化 [91 §3.2]。

**步骤一：从 25 号资产读取引擎的功能表单能力**

BP 中的”正文转化引擎”字段（wft02 Step 5 产出）给出了每个正文实体由哪个引擎转化。逐正文实体，读取 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 中该引擎的 CU 定义，提取以下功能表单相关属性：

| 属性 | 说明 | 用途 |
|------|------|------|
| 功能表单类型 | 该引擎生成的功能表单类别——台账/流程/工单/指标/看板/计划/项目/WBS/进展/定时任务 | → 字段布局模式、展示方式 |
| 默认展示方式 | 列表（表格/树表）/ 单据（单据布局）/ 列表+图示 / 视图卡片泳道 / 甘特任务列表 / 阶段里程碑 / 树形分解 | → 字段布局模式判定（§3.5.3 步骤二）|
| 默认操作集 | 该引擎 CU 运行期提供的标准按钮/操作清单 | → 功能按钮定义 |
| 性能指标上限 | CU 运行期可承载的 FR-BIZ 指标上限（响应时间/吞吐量等） | → Step 7 覆盖判定 |

> 引擎资产随平台演进，本 Skill 不硬编码映射表——每次运行时动态读取 25 号资产获取当前能力。若 BP 指定的引擎在 25 号资产中不存在，标记该文档为 `分解依据不足`，退回 `需wft02修订`。

**步骤二：定义功能表单**（逐 PL5 输出文档）

**① 展示层——字段与数据操作**

1. **字段布局**：正文实体字段 → 表单布局区排列。布局模式按 25 号资产的”默认展示方式”判定——列表型（表格/树表/甘特/卡片/泳道/阶段/里程碑）→ 字段映射到表格列，前 5~8 个核心字段为默认列，其余可配置；单据型（单据布局）→ 字段分组排列（基础信息/业务详情/附件等字段组），每行 1~2 列
2. **筛选/排序/分页**：列表型展示默认启用——列头筛选（核心字段）、多列排序、分页器（默认 20 条/页）。单据型展示不启用分页
3. **导入/导出**：列表型展示默认启用导入（含模板下载）和导出（Excel）；单据型按需启用

**② 交互层——按钮、权限、校验与反馈**

4. **功能按钮**：取 25 号资产的”默认操作集”作为基础按钮集；叠加任务类型——计划→策划/发布、流程→提交审批/通过/驳回、工单→派发/验收。按钮状态随文档生命周期联动（草稿→提交审批可见、审批中→通过/驳回可见、已完成→全部操作按钮禁用）
5. **权限**：行/列/按钮对角色或状态的可见可编辑规则——从 BP 的 SL3/SL4 角色归属和 PL6-A 活动节点的处理角色推导，标注 `[推断]`
6. **校验**：字段级校验（来自实体字段定义）+ 表单级校验（提交时的业务规则——如流程提交时必须填写审批意见）+ 状态前置校验（按钮仅在对应状态下可用）
7. **状态反馈**：操作结果 Toast（成功/失败/警告）+ 数据状态标签（审批中/已通过/已驳回/草稿，颜色见 [91 §4.2 反馈类·状态标签]）

**③ 性能层——指标与分配**

8. **FR-BIZ 性能指标**：记录该页面承接的 FR-BIZ 指标（名称/目标值/适用条件/统计口径/测量方法/来源 BP），由 Step 7 分配到引擎/CU

> 展示方式决定了表单的数据呈现模式（集合型→列表展示、单据型→单据布局、图表型→图示展示）。平台据此自动匹配页面组件（窗口标签页）和布局组件 [91 §1.1 / §4.1]，本 Step 无需选择。全屏单据页、辅助栏和弹窗页面均为平台级交互能力 [91 §1.1.1 / §1.2]，同样无需定义。

**3.5.4 PL6-B 正文条目需求转化**

仅当 PL5 输出文档的正文条目经 wft02 Step 7 三独立判定通过后，才进入本子步骤。

**步骤一：从资产读取条目类型定义**

逐 PL6-B 条目类型，按条目类型读取对应资产中的字段结构定义：

| 条目类型 | 读取资产 | 说明 |
|---------|---------|------|
| 指标条目 | [28 号资产](../../80-pl4eos-2-eosdata/28-eos-dashboard-indicator-assets.md) | 指标的定义要素（名称/口径/目标/维度/图示类型等）由 28 号资产定义 |
| 看板条目 | [28 号资产](../../80-pl4eos-2-eosdata/28-eos-dashboard-indicator-assets.md) | 看板的定义要素（名称/布局/指标集/视图类型等）由 28 号资产定义 |
| 风险条目 / 问题条目 / 行动项条目 / 改进措施条目等 | [26 号资产](../../80-pl4eos-2-eosdata/26-eos-document-definitions.md) | 通用清单类条目的字段结构由 26 号资产定义 |
| 计划条目 | 26 号资产 | 计划条目的字段结构（名称/起止日期/依赖/交付物/状态等）由 26 号资产定义 |

> 条目类型在对应资产中不存在时，标记 `分解依据不足`——说明"该条目类型在 26/28 资产中未定义"，在 Step End 输出缺失说明。不得在 Skill 文档中硬编码条目字段模板。

**步骤二：转化条目需求**

逐 PL6-B 条目类型，基于资产定义转化：

1. **条目字段**：取资产中该条目类型的字段定义（字段名/数据类型/必填/唯一/默认值/校验），作为该条目的实体字段。字段结构以资产为权威源，BP 的 wft02 定义要素作为补充校验
2. **条目表单**：条目字段的展示方式——集合型条目（指标清单/看板清单/风险清单/问题清单/计划清单）→ 列表模式展示条目集合；单据模式展示单条目详情。展示方式按数据呈现模式（集合型→列表 / 单据型→单据 / 图表型→指标页面）判定
3. **条目生命周期**：将 wft02 定义的条目生命周期转化为条目的状态机 + 状态变迁规则 + 各状态下可执行的操作。生命周期模式（如草稿→已发布→已修订→已废弃）来自 wft02 Step 7 的定义，本子步骤只做结构化转化，不自行定义
4. **条目约束**：条目间的引用关系（如看板条目引用指标条目）、唯一性约束（条目名称在容器内唯一）——来自 BP 的条目间关系定义

**步骤三：去重与边界**

- 轻量文档的原子正文行（1 行 = 1 文档实例）不得展开为 PL6-B
- PCA 定义型/管理型条目须逐类判定，不得整包作为 PL6-B 展开
- PL6-B 条目是正文功能表单的内容展开，不生成独立的页面组件或窗口标签页

### 3.6 Step 5 · 流程类业务需求定义

> 对有任务类型（计划/流程/工单）的 PL5 输出文档，通过 [26 号资产](../../80-pl4eos-2-eosdata/26-eos-document-definitions.md) 找到该输出文档类型关联的流程/工单/计划定义，再到 [24 号资产](../../80-pl4eos-2-eosdata/24-eos-business-assets.md) 读取该定义的完整内容——活动节点序列、各节点的功能表单、状态集和动作清单。对照 BP 的 PL6-A 活动节点需求（wft02 Step 6）判定 Q1 复用 / Q2 改进 / Q3 新建，然后基于该定义生成窗口标签页序列（§7.3 Task 5）。无任务类型的文档跳过本 Step。

**3.6.1 通过输出文档定位流程定义**

流程类业务的锚点是**输出文档**——同一个输出文档类型对应同一个流程定义，不同输出文档类型也可能共用同一个流程定义。

**步骤一：从 26 号资产查找流程定义引用**

逐有任务类型的 PL5 输出文档，读取 [26 号资产](../../80-pl4eos-2-eosdata/26-eos-document-definitions.md) 中该输出文档类型的定义。26 号资产定义了该输出文档的实体结构、转化引擎，以及——对有任务类型的文档——**关联的流程/工单/计划定义 ID**（指向 24 号资产）。

| 查找路径 | 说明 |
|---------|------|
| PL5 输出文档 ID → 26 号资产 → 输出文档类型定义 → 关联流程定义 ID | 一对一：每个输出文档类型有一个关联流程定义 |
| 关联流程定义 ID → 24 号资产 → 流程/工单/计划定义 | 多对一：多个输出文档类型可能关联同一个流程定义 |

> 若 26 号资产中该输出文档类型未标注关联流程定义 ID，标记 `分解依据不足`——说明"26 号资产中该输出文档类型缺少流程定义关联"，退回 `需wft02修订`。

**步骤二：从 24 号资产读取流程定义**

通过 26 号资产的关联 ID 定位到 [24 号资产](../../80-pl4eos-2-eosdata/24-eos-business-assets.md) 中的流程/工单/计划定义。该定义包含该流程类型的**完整业务内容**：

| 要素 | 说明 |
|------|------|
| **活动节点序列** | 该流程类型的标准活动节点及其顺序——如 提交→部门审批→财务审核→归档。每个节点定义了关联的功能表单（单据页） |
| **各节点的功能表单** | 每个活动节点对应的功能表单定义——字段布局、可执行动作、校验规则 |
| **状态集与状态变迁** | 文档生命周期状态及状态间迁移规则 |
| **动作清单** | 各节点/状态下可执行的动作——名称/前置条件/后置状态/需填字段/显示样式 |
| **流转规则** | 节点间的流转路径——顺序流转/条件分支/回退/终止 |
| **超时与异常规则** | 默认超时时限/动作/异常处理策略 |
| **角色分配** | 各节点的默认处理角色 |

**3.6.2 匹配 BP 节点与资产定义**

将 BP 的 PL6-A 活动节点序列（wft02 Step 6）与 24 号资产的流程定义的活动节点序列对照，判定匹配关系：

| 判定 | 条件 | 动作 |
|------|------|------|
| **Q1 复用** | BP 的 PL6-A 节点序列与 24 定义的活动节点序列**一致**（节点数量/类型/顺序均匹配），BP 的动作均在 24 定义的各节点动作清单中存在 | 直接以 24 定义为主体。BP 的 PL6-A 只提供场景特定的处理角色分配（覆盖 24 定义的默认角色） |
| **Q2 改进** | BP 的 PL6-A 节点序列与 24 定义**部分一致**——24 定义缺少某些节点（BP 有而 24 无）、或 24 定义的某些节点缺少 BP 需要的动作 | 以 24 定义为**基础**，BP 的额外节点/动作标记 `[推断]` 作为**改进建议**写入 24 号资产的变更影响声明 |
| **Q3 新建** | 24 号资产中**不存在**该关联流程定义 ID 指向的定义 | 标记 `[需裁决]`——基于 BP 的 PL6-A 节点推断活动节点序列/各节点功能表单/状态集/动作清单/流转规则，全量标注 `[推断]` 作为**新建建议**。人类确认后写入 24 号资产和 26 号资产的关联引用 |
| **无法匹配** | BP 未标注任务类型、或 26 号资产未关联流程定义、或 BP 的节点序列与 24 定义的结构性差异无法归入 Q2 | 退回 `需wft02修订` |

> Q2 情形下，仅 BP 的额外节点/动作标注 `[推断]`，与 24 定义一致的部分不做标记。Q3 情形下，AI 可推断流程定义的全部要素，但全量标注 `[推断]` 且须人类确认后写入资产。

**步骤三：输出流程类业务需求定义**

基于匹配结果，定义该输出文档的流程类业务需求。每项需求以 24 定义为**主体**，BP 的 PL6-A 做场景补充：

**节点层——序列、表单与角色**

| 需求项 | 主体（来自 24 定义） | 场景补充（来自 BP 的 PL6-A） |
|--------|-------------------|--------------------------|
| **活动节点序列** | 24 定义的标准节点及顺序——如 提交→审批→归档 | BP 额外节点（Q2）/ 全量推断节点（Q3） |
| **各节点功能表单** | 24 定义各节点的功能表单——字段布局/可执行动作/校验规则 | — |
| **各节点处理角色** | 24 定义的默认处理角色 | BP 的处理角色（覆盖默认） |

**动作层——动作、状态与变迁**

| 需求项 | 主体（来自 24 定义） | 场景补充（来自 BP 的 PL6-A） |
|--------|-------------------|--------------------------|
| **各节点可执行动作** | 24 定义的动作清单——动作名称/前置条件/后置状态/需填字段/显示样式 | BP 额外动作（Q2/Q3） |
| **状态集与状态变迁** | 24 定义的状态集和状态迁移 | BP 特有的状态分支 |

**规则层——流转、超时与附着**

| 需求项 | 主体（来自 24 定义） | 场景补充（来自 BP 的 PL6-A） |
|--------|-------------------|--------------------------|
| **流转规则** | 24 定义的标准流转路径——顺序流转/条件分支/回退/终止 | BP 特有的异常流转 |
| **超时与异常规则** | 24 定义的默认规则 | BP 特有的超时时限/异常条件 |
| **任务状态附着** | 正式文档→DocumentCover 封面行 [91 §2.5 R6]；轻量文档→正文实体行 [91 §2.4] | — |

> 上述需求定义即为 §3.6 的**产出**——每个活动节点即为一个窗口标签页（单据模式，页面 ID 格式 `@srf-tab-{场景业务简称}-act-{序号}`），系统自动节点不生成独立标签页。24 定义的状态集即为封面行/正文行状态字段的可选值域。

### 3.7 Step 6 · 任务关系与文档引用定义

> 消费 wft02 的任务关系（wft02 Step 8）和文档间引用信息（wft02 Step 5），定义任务间触发规则需求和文档间引用需求（§7.3 Task 6+7），最后校验两者与 TAB 顺序的一致性。任务触发和文档引用的权威定义见 [91 §2.2 支持信息](91-eos-biz-eng-spec.md#22-正式文档的组成)、[§2.5 R5](91-eos-biz-eng-spec.md#25-设计规则)、[§2.6](91-eos-biz-eng-spec.md#26-任务间触发关系)。

**3.7.1 wft02 任务关系与引用信息消费**

从 BP 中提取两类信息（wft02 已产出，本步骤只读消费）：

**任务关系**（来自 wft02 Step 8"任务关系引擎化"）：

| 要素 | 说明 | 用途 |
|------|------|------|
| 来源任务 | 发起触发的任务——哪个 PL5 输出文档的任务完成时触发 | → Task 6 触发条件定义 |
| 目标任务 | 被触发的任务——触发后启动哪个 PL5 输出文档的任务 | → Task 6 启动参数定义 |
| 触发时机 | 来源任务的哪个事件触发——任务完成/任务到达某节点/任务状态变更 | → Task 6 触发条件的事件类型 |
| 触发条件 | 触发需满足的附加条件（如审批通过才触发、驳回不触发） | → Task 6 条件表达式 |
| 启动参数 | 目标任务启动时需传入的上下文数据——来源文档 ID、来源任务实例 ID、传递字段映射 | → Task 6 参数定义 |

**文档间引用**（来自 wft02 Step 5"支持信息引用"）：

| 要素 | 说明 | 用途 |
|------|------|------|
| 引用源 | 发起引用的 PL5 输出文档 | → Task 7 引用规则 |
| 引用目标 | 被引用的 PL5 输出文档（正式 / 轻量） | → Task 7 目标定位规则 |
| 引用角色标签 | 输入文档 / 规范文档 / 指南文档 / 合规文档 / 资源文档 [91 §2.2] | → Task 7 角色标签 |

> 若 BP 缺少任务关系或引用信息（wft02 Step 5 或 Step 8 产出不完整），标记对应文档为 `分解依据不足`，在 Step End 输出缺失说明并建议退回 `需wft02修订`。

**3.7.2 任务间触发规则需求定义**

逐任务关系（来源任务→目标任务），定义触发规则：

1. **触发条件**：
   - 触发事件类型——`任务完成` / `任务到达指定节点` / `任务状态变更`
   - 条件表达式——仅当来源任务的结果满足条件时才触发（如 `来源任务.审批结果 = '通过'`、`来源任务.最终状态 = '已完成'`）。条件字段来自来源任务的状态变迁定义（§3.6.2）
   - 不触发情形——明确列出不触发的情形（如驳回→不触发下游、终止→不触发下游）

2. **启动参数**——目标任务被触发启动时需传入的数据：

| 参数 | 来源 | 说明 |
|------|------|------|
| 来源文档 ID | 来源任务的 PL5 输出文档实例 ID | 建立任务间追溯链 |
| 来源任务实例 ID | 来源任务的任务实例 ID | 追溯具体触发来源 |
| 传递字段 | 来源文档的关键字段→目标文档的对应字段 | 如"采购申请单号→采购订单的申请单号引用" |

3. **任务类型兼容性**：计划/流程/工单可任意触发任意类型（含同类型）[91 §2.5 R5]。不因类型不同而禁止触发，只记录类型组合供 Step 7 分配引擎能力时参考。

4. **首个有任务类型的文档**：场景业务中第一个有任务类型的输出文档，其任务类型必为**计划** [91 §2.5 R4]。该文档本体的任务类型是计划（策划→发布），不是其他文档的触发源。此约束由 wft01/wft02 判定，本 Step 只校验不重新判定——若发现首个有任务类型的文档不是计划，标记 `[需裁决]`。

**3.7.3 文档间引用需求定义**

逐引用关系（文档 A 引用文档 B），定义以下规则：

1. **引用目标定位**：文档引用目标均为正式文档（轻量文档不作引用目标），统一指向被引用文档的 **DocumentCover 行**（通过 DocumentCover 的唯一 ID 引用）。依据：[91 §2.2 支持信息]

2. **引用角色标签**：逐引用关系标注角色标签——`输入文档`（前序流程产出、作为本流程输入）/ `规范文档`（定义本流程需遵守的标准/规范）/ `指南文档`（提供操作指引）/ `合规文档`（证明合规性的证据文档）/ `资源文档`（提供参考信息的数据/模板）。角色标签来自 wft02 Step 5 的定义

**3.7.4 一致性校验**

逐场景业务校验以下三项无矛盾：

| 校验维度 | 检查内容 | 矛盾示例 | 处理 |
|---------|---------|---------|------|
| **任务触发 vs 文档流转** | 任务触发链的顺序是否与输出文档流转顺序一致 | 文档流转为 A→B→C，但任务触发为 C→A（循环触发与文档顺序矛盾） | 标记 `[需裁决]`，说明矛盾点 |
| **任务触发 vs TAB 顺序** | 任务触发的目标文档 TAB 是否在来源文档 TAB 之后 | 来源文档 TAB=3，目标任务触发打开了 TAB=1 的文档（回退不通过面包屑） | 判定触发类型的合理性——驳回/退回修改类触发允许回退，新建类触发不允许回退 |
| **引用依赖 vs 文档流转** | 文档 A 引用了文档 B，文档 A 是否在 B 之后（或同时）生成 | A 引用了 B 但 A 的流转顺序在 B 之前（B 还不存在时 A 已生成） | 标记 `[需裁决]`——可能为模板引用（B 是静态规范文档，可提前存在）或顺序错误 |

校验通过后，任务触发规则和引用需求写入 `05/06`，标注 `[推断]` 供确认。

### 3.8 Step 7 · 引擎能力需求增补

**3.8.1 汇集业务侧引擎依赖**

从 Step 3~6 的产出中，逐业务页面提取对引擎能力的依赖：

| 来源 Step | 业务页面类型 | 依赖的引擎 | 业务动作 | FR-BIZ 指标 |
|----------|------------|----------|---------|-----------|
| Step 3 | 菜单树、场景标签页 | @engine-menu | 菜单树生成、场景编排 | 菜单可达性、场景切换响应时间 |
| Step 4 | 正文功能表单 | @engine-entity + 正文转化引擎（来自 §3.5.3 步骤一） | 实体 CRUD、表单转化 | 正文功能表单的 FR-BIZ 指标（§3.5.3） |
| Step 5 | 流程类业务标签页 | 任务引擎（@engine-flow / @engine-task / @engine-workorder） | 流程流转、工单派发/验收、计划发布 | 窗口标签页的 FR-BIZ 指标（§3.6.2） |

**3.8.2 对照 25 号资产识别缺口**

逐需求行，读取 [25 号资产](../../80-pl4eos-2-eosdata/25-eos-engine-models.md) 中对应引擎的 CU 清单和能力定义（只读），与业务动作和 FR-BIZ 指标对照，识别缺口：

| 判定 | 条件 | 缺口描述 |
|------|------|---------|
| **Q1 已覆盖** | 已有 CU 的能力范围覆盖业务动作+期望输出，且 FR-BIZ 指标在 CU 性能上限之内 | 无缺口 |
| **Q2 性能不足** | 已有 CU 可承接该业务动作，但 FR-BIZ 指标超出 CU 性能上限 | 性能缺口——当前上限 {X}，需求目标 {Y}，差距 {Y-X} |
| **Q3 能力缺失** | 25 资产中不存在可承接该业务动作的 CU | 能力缺口——缺 {业务动作} 对应的 CU，缺口层级按 [91 §4.4] 判定（构件级/布局组件级/CU级） |
| **Q4 边界不清** | CU 能力边界在 25 资产中定义不清，无法判定 | 定义缺口——需明确该 CU 的能力边界 |
| **无法判定** | wft02 未标注支撑引擎 | 信息缺口——退回 `需wft02修订` |

判定方法：业务动作与 CU 运行期能力按**语义+指标**双维度对照。语义维度——业务动作”提交审批”匹配 CU 的”审批流转能力”（非匹配整个引擎）；指标维度——FR-BIZ 目标值与 CU 性能上限做数值比较。

**3.8.3 缺口转化为引擎需求**

Q2/Q3/Q4 缺口不是需求——缺口描述的是”差了什么”（业务视角），引擎需求描述的是”需要引擎提供什么”（引擎视角）。逐缺口转化：

| 缺口类型 | 转化后的引擎需求 |
|---------|---------------|
| **Q2 性能不足** | 对已有 CU **增强性能**——将 {CU名称} 的 {指标名称} 上限从 {当前值} 提升至 {目标值}，以满足 {业务页面} 的 {业务动作} 场景 |
| **Q3 能力缺失** | **新增 CU 或扩展 CU 能力**——在 {引擎名称} 中新增/扩展 CU，使其能够承接 {业务动作}，输出 {期望输出}，满足 {FR-BIZ指标} |
| **Q4 边界不清** | **明确 CU 能力边界**——{引擎名称} 的 {CU名称} 需明确其能力范围定义，以判定能否承接 {业务动作} |

每条引擎需求包含以下要素，按用途分三组：

**标识**

| 要素 | 说明 |
|------|------|
| 需求 ID | `FR-ENG-REQ-{YYYYMMDD}-{序号}` |
| 来源 | 产生该需求的业务页面 ID + 来源 BP 节点 ID（如 `@srf-tab-purchase-apply-01 / @bp-proc-apply-001`） |
| 目标引擎 | 该需求归属的引擎 |
| 需求类型 | 增强性能 / 新增能力 / 明确边界 |

**能力描述**

| 要素 | 说明 |
|------|------|
| 缺口层级 | 构件级 / 布局组件级 / CU 级（Q3 时填写，按 [91 §4.4] 判定） |
| 当前能力 | 25 资产中与该需求最接近的已有 CU 及其能力描述（Q2 时填写，Q3/Q4 写“无”） |
| 需求能力 | 需要引擎提供什么能力——能承接什么业务动作、达到什么期望输出 |
| 指标要求 | FR-BIZ 指标的目标值/适用条件/统计口径/测量方法（Q2 时填写差距，Q3/Q4 按需） |

**业务影响**

| 要素 | 说明 |
|------|------|
| 业务场景 | 什么场景下需要该能力——用户操作→期望的系统行为→当前无法实现 |
| 业务影响 | 该需求不满足时，哪个角色的什么职责受影响 |

> **门禁**：引擎需求**不是正式 OR**，作为 FR-ENG 候选线索登记到 OR 原料状态表 A。人类确认纳入后，须完整通过 ort00→ort01→ort02→ort03 形成正式 FR-ENG OR，才可由 wft01-eng 消费 [91 §4.4]。不得直接写入 `01-eos-original-requirements.md` 或”待 wft01-eng 处理”分节。

**3.8.4 FR-BIZ 指标分配与约束包装配**

两件事合并执行：

**一、指标分配**——逐 Q1 需求行，将 FR-BIZ 指标分配到对应引擎/CU：记录指标名称/目标值/适用条件/统计口径/测量方法→写入该引擎的 `引擎能力使用需求` 行。指标仍归属 FR-BIZ，不转为 NFR。Q2/Q3/Q4 的指标随引擎需求（§3.8.3）进入 eng 路径。

**二、约束包装配**——将全部 Q1~Q4 行装配为 `FR-BIZ 指标约束包`，逐行格式：

```text
包 ID：FR-BIZ-PKG-{YYYYMMDD}-{序号} / 版本：v{N}
来源业务页面：{页面ID / 名称 / 来源 BP 节点ID}
来源 FR-BIZ：{指标名称 / 目标值 / 适用条件 / 统计口径 / 测量方法 / 来源 OR或STR-F}
目标引擎/CU：{引擎ID / CU名称 / 25 资产版本}
覆盖结论：Q1（覆盖证据：{CU能力的哪部分承接了该指标}）/ Q2/Q3/Q4（→ 关联 FR-ENG-REQ-{ID}）
变更声明：{新增/修订/删除}
```

约束包由 wft05-eng 逐行消费。构件开发流水线和 wft06 使用同一包验证业务页面配置与软件能力是否联合满足指标。完成后检查：FR-ENG 引擎需求已登记 OR 原料状态表 A、约束包逐行字段完整。

### 3.9 Step 8 · 资产写回与落账
