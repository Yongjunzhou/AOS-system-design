# 设计与开发 SKILL 指南编制规范—93 号规范
**EOS Design-Development SKILL Guide Authoring Spec**

> **本规范是什么**：统一 EOS 设计线上"设计与开发落地"各任务 SKILL 指南的**编制**，此类方案亦称操作规程——总骨架、各章编制规则、跨文档引用与对接，使全链 SKILL 指南读成同一个方法在不同链位的实例化；该方法是 20 号报告的由需求到方案的逐对生成、Y=F(X)。SKILL 指南是权威源；其 SKILL 是可执行提取，派生关系见 §五.3。
>
> **版本**：v0.34 | **修订**：2026-09-15

## 一、总则

### 1.1 目的与定位

设计与开发落地 = 把产品数据链切成相邻的"需求-方案结对"，由需求开发出方案、并由方案迭代需求，正反交替逐个需求-方案对收敛。每一个需求-方案对即一次 Y=F(X) 求值：X 为需求，Y 为方案，F 为规则，即 X 侧/Y 侧树形与节点规则 ＋ Y 承接 X 的承接规则。推进分两步：预处理定义规则、结构化存量、初步承接；正式设计由需求叶节点驱动，走承接设计 → 分解 → 覆盖检查。方法完整定义见 [20 号报告](../../../50-系统工程研究/00-系统工程相关研究报告/20-设计与开发落地方法研究报告—需求与方案结对开发.md)。

**一份 SKILL 指南**就是落地方法在**一个任务位**上的操作规程：**先交代这个任务位在链上的位置——属于哪个"需求-方案对"、哪一阶段**；再规定它消费的输入文档、产出的输出文档、两者转换的规则、转换流程与检验规则，及其与资产文档的接口。

**本规范规定此类 SKILL 指南怎么编**：章序、各章该写什么、不该写什么、跨文档如何保持一致。它不重述 EOS 领域设计模式与运行时协议，也不重述方法论证——前者引 91 规范，后者引 20 号报告。

### 1.2 适用范围

- 适用于 **EOS 设计线 SKILL 指南**：biz/eng/nfr 三路径 01→07 链上的承接/分解任务，即 `spr2bph`、`bph2bpd`、`bpd2srh`、`srh2srd`、`srd2pa` 及 nfr 链对应任务。本规范按**方法级**编制、不绑定 biz/eng/nfr 具体名词，各任务以自己的输入/输出产品数据填充。
- 同一需求-方案对内的"阶段一·承接设计出概要"与"阶段二·分解出完整态或链尾移交"两类任务均适用——骨架一致，只内容随其在链上的位置而不同。
- **暂不适用 ort00~ort03 需求预处理链**，即原始需求的文本化、切分、澄清、规范化。ort 属 20 号方法的"预处理过程"，但 EOS 已将其独立成链、现行 SKILL 模板不同，维持 [91 规范](91-eos-biz-eng-spec.md) 附录A 既有模板。如需同构再行扩展。

## 二、SKILL 指南总骨架

### 2.1 骨架总览

每份系统或构件设计类 SKILL 指南按六主章 + 收尾章组织：

| 章 | 章名 | 定位 | 对应 20 号方法 |
|----|------|------|----------------|
| 一 | 目的与目标 | 说明本任务在链上的位置与职责边界——属哪个"需求-方案对"、哪一阶段 | 需求-方案对与链定位 |
| 二 | 输入文档结构及规则 | X 的**消费侧**视图 | X 侧规则之使用面 |
| 三 | 输出文档结构及规则 | Y 的**生产侧**视图 | Y 侧规则 + 分解源判据 |
| 四 | 输出与输入转换规则 | X→Y 的映射与判定 | 承接规则，即 F 的第三块 |
| 五 | 转换流程及检验规则 | 设计动作序列 + 关口 | 正式设计过程 + 两道关口 |
| 六 | 资产文档结构及规则 | 旁支参照接口，读写资产 | — 旁支 |
| 收尾 | AI 标记约定 / 自检清单 / 变更记录 | 执行收尾 | — |

> 章序逻辑：先文档后转换再流程——二、三章先立两端，即 X 是什么、Y 是什么；四章给**映射规则 F**；五章给"执行与验收"；六章给"映射时查阅/回写的旁支词典"。

### 2.2 组织原理

- **一份 SKILL 指南 = 一次 Y=F(X) 的完整说明**：输入文档是**自变量 X**、输出文档是**函数值 Y**、转换规则是**映射规则 F**，流程及检验是执行与验收。
- **概念跟文档走、原理跟规则走**：描述 X 的概念进第二章，描述 Y 的概念进第三章；解释"规则为何如此"的原理与其规则同章同节，不另设独立的"概念/原理"章。理由：在逐对生成里，所谓"概念"，如节点类型、概要/完整态判据，本身就是某侧文档的结构或规则，没有脱离文档而独立存在的概念层。
- **不设孤立的知识层三章、以设计动作序列为纲**：旧版 SKILL 指南的第三章即操作流程，按会话 Step 组织（Start／1／2／End／反馈／写回），每节讲一个 Step 里 AI 与人怎么交互；本骨架改按**设计动作序列**组织——**即本任务的 Step 1…N**，见 §三.5。会话**协议**本身——反馈双轨状态机、git 基线、写回脚本、Start 与 End 两端的固定机制——属 91 附录A 运行时协议，SKILL 指南只引不重述；但 **Step 的划分与每步动作属本任务特有，要写**。
- **只引用、不搬运**：schema、资产内容、运行时协议、方法论证各有单源，见 §四.1、§1.3；SKILL 指南写"本任务怎么用"，不复制权威正文。

### 2.3 输入/输出文档的树形结构图

每一份 SKILL 指南的**第二章**与**第三章**，都必须给出所涉产品数据的**树形结构图 + 逐级节点语义**——第二章管输入，给 **X 的树**；第三章管输出，给 **Y 的树**。

**为什么必须给**：二、三两章先立两端，即 X 树、Y 树；而第四、五两章的规则全都要指着这两棵树说话——承接规则要说"X 的叶落到 Y 的哪一级"，分解源判据要说"这个枝梢能分解出哪些叶"。**树不给出来，这些规则就没有可指的对象。**

**图怎么画**：

- 图内只写**节点名称 + 节点意义**：纵向嵌套、逐级列出；级位编号 ①…，按该文档的实际级数。
- 只画**本任务的任务视图**——本任务不涉及的层级不必展开；并注明树权威 = [94](94-eos-sys-dev-dbs.md)，不得另立一套树口径，见 §4.1。
- 输出横跨多条产品树，如 biz 链的 **R／P 两棵**，各给一图。

**图外紧跟一张级语义表**：每个节点"**怎么得到**"与"本任务如何处置"都写进表里，**不占树位**。怎么得到有四种来源——承袭、本任务产出、AI 建议+人类确认、目标组织级。

全链 SKILL 指南 biz/eng/nfr 均须遵守并回填。

## 三、各章编制规则

> 每章统一给：应含 / 禁含 / 规则来源。逐章规则随链上落地继续回填，带【待回填】处未定案。

### 3.1 第一章 目的与目标

**应含**：

- **链上坐标**：本任务 = 哪个"需求-方案对"的哪一阶段——阶段一即承接设计·出概要，阶段二即分解·出完整态，或是链尾移交；X、Y 各为哪份产品数据的哪个形态，是概要态还是完整态。
- **主要目的**：一段话说明本任务要达成什么，写成引用块。
- **目标**：逐条列出本任务这次运行要产出的结果，写成编号列表。
- **负责 / 不负责**：本任务做什么、不做什么；**不做的要写明它归谁**——指向承担它的那个任务，不留悬空。
- **与上下游的衔接**：X 从哪里来；下游由谁接，是阶段二执行者还是链尾接手方；检出缺陷时退回给谁、按什么条件退。
- **概要的位置**：说明"概要 = 同一份逻辑产品数据的骨架形态，**只是一个需求-方案对的中间形态、不算它的一端**——一个需求-方案对的两端是需求与方案两份产品数据，各取完整态；完整态由阶段二产出"。

**禁含**：schema、规则、流程细节——这些属后章。

### 3.2 第二章 输入文档结构及规则

**定位**：X 的**消费侧**视图。每份 SKILL 指南只描述**一份**主输入文档；它是哪一份，由下面的"输入文档两类语义"决定。

**输入文档两类语义**：按本任务在对中的角色，X 属两类之一：
- **承接型**：X = **上一份产品数据的最深可用原子，即它的叶**——它即本需求-方案对的需求。此处不用形态词概括：94 §1.1 明示「**`01` 相关方需求不分形态**」，其叶＝需求条目；其余上游为完整态。[94 §1.4](94-eos-sys-dev-dbs.md) 的承接规则一律以"叶"表述。本任务是新"需求-方案对"的阶段一，任务是**承接**；
- **落叶型**：X = **本需求-方案对的概要**，即同一需求-方案对阶段一产出的 Y 概要、对内中间形态。本任务是同一需求-方案对的阶段二，任务不是承接而是**落叶/实现化**——把已承接语义从骨架落到叶定义。

两类在第二章标题下内容不同：承接型写"X 里哪些是可承接对象 + 单承接/映射"；落叶型写"本需求-方案对概要的枝梢与分解源判据如何落叶、叶如何定义"。**更上游文档不作第二章文档**——只作覆盖检查锚点，经承接记录/追溯引用。

**应含**：

- **受理门槛**：什么样的 X 才归本任务处理——什么状态、哪个范围、一次多少；不满足就退出，写成一张受理门槛表。
- **读法**：本任务从 X 里读什么——哪些结构是**可承接对象**、要接过来，哪些字段本任务**消费**、要直接用。
- **X 的树形结构图**：画出 X 的树，逐级写节点名称与意义；图外跟一张级语义表，说明每个节点怎么得到、本任务怎么处置；并注明树权威。规格同 §2.3。
- **X 侧规则**：X 的分解决定权归谁、切得不对退回给谁重切；以及本任务使用 X 时必须守的规矩。
- **依赖与校验**：读到上游的承诺缺失或冲突时怎么办——与对侧核对、退回，还是反向迭代。
- **schema 引用**：只引 X 的文档结构的出处——91 §11 加该产品数据文件自身——**不复述结构本身**。

**禁含**：X schema 全量；本任务旧 Y 的存量，归第三章和第五章的修订流程；资产内容，归第六章。

### 3.3 第三章 输出文档结构及规则

**定位**：Y 的**生产侧**视图。

**应含**：
- **Y 的树形结构图**：画出 Y 的树，逐级写节点名称与意义；图外跟一张级语义表，说明每个节点怎么得到、本任务怎么处置；并注明树权威。输出横跨多条产品树，如 **R／P 两棵**，各给一图。规格同 §2.3。
- **节点类型与结构要点**：引用 schema 出处，并给出本任务产出的节点类型判据，如正式/轻量、正文条目三独立、D/PCA。这些"概念"即 Y 的节点类型规则，在此定义或引用。
- **Y 侧规则**：构建规则——父节点归组、收敛自查要"覆盖完整 + 兄弟互斥"；概要态边界——本任务写到哪一层，即枝梢 + 分解源判据。
- **枝梢节点的双向物理意义**：承接判据，即该枝梢承接哪类需求；分解源判据，即它能分解出哪些叶节点。后者是移交阶段二／下游的规则接口。
- **要素清单**：本任务产出节点必须带齐的要素。
- **传出承诺**：交到下游前节点须达到的状态与完备程度，供 B 的第二章消费。

**禁含**：阶段二的执行内容，即叶节点与字段级详设；schema 全量，只引单源。

> **概要—完整态边界**：**叶节点只在完整态**；**枝梢 = 叶的上一级，即概要的最深节点**，树级语义取自 94 §1.3。概要不含叶，但**枝梢内容可含"分解源判据的展开声明"**——叶清单 + 活动行为锚点，各项带内联稳定标签作 02→04 追溯键；展开项**不是 02 的树节点**，其身份在阶段二产出完整态时转为叶。若本任务概要已含名称级子项，一律按此归入枝梢分解源判据。
>
> 落到 EOS 业务流程树：枝梢即 ⑤ 业务输出文档；叶即 ⑥ 活动节点/正文条目，在业务流程方案 04 定义成叶，三独立为其"可独立成叶"的判据。业务流程概要以 02 为单一文件，不另设"概要详细定义"档。
>
> **承接源只取上游叶**：跨需求-方案对承接的**定义域只取上游叶**。94 §1.2 依据三写的是：**定义域取需求侧的原子，即叶**——粗粒度节点**不能被 1:1 分配**，它内部含着多条性质不同的需求，交出去后无法判定谁负责哪一部分；94 §1.4 的承接规则同此。**故枝梢不参与承接。**
>
> **05 的枝梢＝⑤ 用例场景功能**：94 §1.4 的承接表把它写作 04→05 的下游落点，94 §2.3.1 的 SR-F 树里它正是枝梢。**功能表单不属于系统需求树**——它是「**用户操作页面视角**」的载体，见 91 §7.3。

### 3.4 第四章 输出与输入转换规则

**定位**：X→Y 的映射与判定，即承接规则在本需求-方案对上的实例化。

**应含**：
- 承接/分配规则：X 的叶与节点如何落到 Y 的各级枝干/枝梢；**单承接**，可 N:1、不可 1:N；承载量超限则拆分节点；切不动则走横切式承接或独立分支，本需求-方案对适用时。
- 类型与要素生成判定：从 X 内容推出 Y 节点类型/要素的判定规则。
- 修订转换规则：已有 Y 时，新 X 如何并入——复用 → 改进 → 新增 的分流与关系检测。
- 对齐规则：Y → 资产侧的判定动作，如 Q 判定——判定动作在此定义，资产概念引资产文件。
- 影响面复查：对 Y 枝梢做 Extend/Split/Merge 改进时，对既有承接的复查规则。

**禁含**：流程步骤顺序，属第五章；资产自身结构，属资产文件。

### 3.5 第五章 转换流程及检验规则

**定位**：设计动作序列 + 关口。

**应含**：
- **设计过程，即本任务的 Step 序列**：第五章的动作序列**就是**本任务的 Step 1…N——一节一个 Step，标题写「Step N · 动作名」。序列形如 预处理〔载规则 F、结构化存量、初步承接——只做复用〕→ 承接设计循环〔选相关联 X 组 → 复用→改进→新增 → 单承接检查 → 有改则自下而上调树至收敛〕→ 完备性/覆盖检查 → 状态推进。**Step 数随任务而异，属本任务特有**；Start 与 End 两端由 91 附录A 承载，本任务不重述。不另起一套与 Step 平行的动作编号。
- **关口**，即检验规则：
  - 单承接检查——出口有二：程序违规回炉，或切不动的整体；
  - **承接覆盖检查**——承接的 X 语义 ⊆ 其分解产出之并；EOS 实例 = 闭合检查，缺口不脑补，走补充需求材料回路；
  - 人类门禁——整体确认后推进；退回——下游检出缺陷则反向迭代／修订。
- 状态推进与退回机制在本任务的特化。

**禁含**：EOS 会话运行时**协议**的复述——反馈双轨状态机、git 基线、写回脚本、Start 与 End 两端的固定机制。这些由 91 附录A 统一规定，本任务只引不重述；**本任务自己的 Step 划分不在此列**。

### 3.6 第六章 资产文档结构及规则（接口）

**定位**：本任务与资产文档 21~28 的**接口**；资产自身的结构与概念是其文件自己的内容，不搬入。

**应含**：本任务**读**哪些资产，写明引用分节；**写**哪些资产，写明写回动作与规则，如 Q1/Q2/Q3 引用、WBS 归组结论写回、一致性矛盾暂不写回。

**禁含**：资产文档自身的结构／概念／规则的复述——引资产文件。

### 3.7 收尾章与运行时

- AI 标记约定 / 自检清单 / 变更记录：引 91 附录A 格式约定 + 本任务增量清单示例。
- 运行时协议，含 Step Start→End、反馈交互、生命周期、变更传播、读写与写回约定——属 [91 规范](91-eos-biz-eng-spec.md) 附录A，SKILL 指南只引不重述。

### 4.2 同一份文档的生产侧与消费侧

链上相邻任务共享**边界文档**：任务 A 输出它、任务 B 输入它。该文档被且只被描述两次，且两次天然不同：

- **A 的第三章，生产侧**：怎么产出合规文档 + **传出承诺**，即交到下游前达到的状态与完备程度，含枝梢分解源判据。
- **B 的第二章，消费侧**：怎么把它当 X 用 + **受理前提**，即受理门槛、可承接对象、依赖与校验。

**A 的第三章的传出承诺与 B 的第二章的受理前提互为对侧——并排核对即本需求-方案对的接口契约校验**；不吻合即对侧缺陷 → 退回 / 修订。这一对侧关系就是防止"A 以为交全了、B 发现接不上"的机制，也就是 20 号方法反向迭代在文档体系上的落点。

```
┌─ A 的第三章生产侧 ─┐        ┌─ B 的第二章消费侧 ─┐
│ schema 引用     │        │ schema 引用      │
│ 构建/分解源判据  │ ──接口──▶ │ 受理门槛/可承接对象│
│ 要素清单        │  契约   │ 依赖与校验·退回  │
│ 传出承诺 ====== │ =======│ ====== 受理前提  │
└───────────────┘  对侧核对  └────────────────┘
```

> **核对方法 = 逐条映射**，核对项为状态门槛、要素齐备、分解源判据、引擎权威、覆盖落账——两处边界各按此表逐条比对：**对内概要移交**，即需求-方案对① 内的 02，A 的第三章传出承诺 ↔ B 的第二章受理前提；**跨需求-方案对完整态移交**，即需求-方案对①→② 边界上的 04，A 的第三章传出承诺 ↔ B 的第二章受理前提。
>
> **首条边界例外**：链首那份产品数据即相关方需求，其生产侧在 ort 预处理链、并非 SKILL 指南，故其下游任务的第二章只有消费侧一栏。

### 4.3 输入文档的来源

本任务的需求树没有独立构建规则——它就是上一需求-方案对／上一任务的方案树，这正是 20 号报告 §2.4「需求树的来历」所说的。因此 B 的第二章不重述 X 的结构与构建，那是 A 的第三章的职责；只写"B 把 X 当 X 用"的受理与使用规则 + schema 引用。

> **覆盖逐对下传**："承接了的一定被实现"沿需求-方案对逐层演化为每个需求-方案对各自的检查内容——需求-方案对① 内：阶段一在 02 落承接承诺 → 阶段二在 04 实现到叶 → 需求-方案对② 的覆盖自查证明 04 已被 05 完整承接。每个需求-方案对的覆盖检查落在该任务第五章的关口。
>
> **链尾移交**：**设计线的链尾需求-方案对 = 需求-方案对③**，即 06→07——这是 20 号 §5.4 的形态。承接链末份产品数据是 **07 平台构成概要**，见 [94 §1.1](94-eos-sys-dev-dbs.md) 与 20 号 §5.4。需求-方案对③ 只产出 Y **概要**，末级＝枝梢，枝梢带**分解源判据**；**Y 完整态叶由开发线阶段二执行**——20 号 §5.4 说，开发线按分解源判据把枝梢节点分解为组件规格，设计线的产品数据链止于概要。该任务第三章传出承诺的对象 = **开发线首 skill**，设计线内无第三个消费侧；契约对侧在开发线规范——不需再造一份"开发需求"。**需求-方案对③ 的下游落点在 [94 §1.4](94-eos-sys-dev-dbs.md) 标【待裁】**，即 06 的系统功能需求树叶 ⑥ IPO功能 落到平台构成树哪一级；本处随之待 94 收口。
>
> **两条"尾"要分清**：**路径止点**——biz 路径在 **05 系统需求概要**止，biz 不入 07，见 91 §7.3，其后交构件开发流水线；**设计线链尾**——需求-方案对③，即 06→07。二者不是一回事，勿以路径止点代链尾。
