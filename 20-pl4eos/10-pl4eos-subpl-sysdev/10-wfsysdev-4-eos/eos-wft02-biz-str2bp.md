## 二、BP 设计基础

> 本章定义 wft02-biz 操作的领域对象——业务流程（BP）、A2/Bn 两类产品及其末级节点、功能引擎与输出文档的关系、任务节点引擎化与任务关系引擎化。操作流程见 §三。层级体系的权威定义见 [91 规范 §3.1](91-eos-biz-eng-spec.md#31-业务及层级)。

### 2.1 业务流程（BP）

#### 2.1.1 定义

BP 是五层设计链的第三层（OR→STR→**BP**→SR→PA），将 STR-F 的场景业务展开为可被系统需求（SR-F）承接的业务方案。BP 的权威定义见 [通用设计规范 §7.4](../../../00-generalspec/01-generalspec-sysdev.md)。

#### 2.1.2 双视角模型

EOS 的 BP 包含两个并存互补的视角：

- **A2 角色场景视角**（§2.2）：回答“谁在什么场景、按什么顺序使用哪些功能表单、完成端到端的职责闭环”；菜单入口和页面类型不在 BP 层确定
- **Bn 输出产品视角**（§2.3）：回答"某类输出文档属于哪个业务域/构件类型、需要哪些前序文档和业务规则才能生成"

两个视角互相校验完备性：A2 侧覆盖场景已提到的业务，Bn 侧完备性检查暴露输出文档缺失。A2/Bn 的定义见 [91 规范 §5.2~§5.3](91-eos-biz-eng-spec.md#52-a2产品)。

#### 2.1.3 A2与Bn的交汇点

两个视角通过“输出文档→功能表单/主子表单”的转化关系交汇——PL5 输出文档是 Bn 侧的产品数据节点，经实体引擎和对应功能引擎转化、组装后，形成 A2 侧 SL6 使用的功能表单/主子表单。两者存在稳定映射，但不是同一层级对象。

对于流程类和工单类输出文档，BP 还需定义其**文档状态**（详见 §2.5.1）。

### 2.2 A2产品：角色场景视角

#### 2.2.1 定义

A2 是**各业务域的角色场景**。定义见 [91 规范 §5.2](91-eos-biz-eng-spec.md#52-a2产品)。构件为角色（如采购员、库存管理员），末级节点为场景业务（SL5）。

#### 2.2.2 SL层级

沿角色场景视角（SL）展开：

| 层级 | 名称 | 说明 |
|------|------|------|
| SL0 | 平台 | EOS 平台 |
| SL1 | 业务域 | 如采购管理、生产管理 |
| SL2 | A2产品 | 角色场景产品 |
| SL3 | 角色类型 | 如采购员、库存管理员 |
| SL4 | 角色职责 | 归纳层，可选占级 |
| SL5 | 场景业务 | **末级节点**，与 STR-F 1:1 映射 |
| SL6 | 功能表单/主子表单 | 由 PL5 输出文档经引擎转化和组装的抽象表单定义。窗口标签页及页面编排由 wft03-biz 设计（交汇关系见 §2.1.3） |

**场景业务（SL5）**：STR-F 末级节点，定义端到端职责闭环。

场景业务定义以下内容：
- **用户角色**：谁在执行
- **入口条件**：何时进入
- **可用功能表单**：用哪些表单完成工作
- **跨部件上下文传递**：数据如何在表单间流转

BP 只定义**场景边界**和**表单使用顺序**。wft03-biz 负责配置页面组件、将窗口标签页编排为场景标签页、将场景标签页编排进菜单标签页。

场景业务分为**执行类（D）**和**管理类（PCA）**，分类定义见 [91 规范 §1.4](91-eos-biz-eng-spec.md#14-业务场景)。

#### 2.2.3 本Skill在A2侧的职责

**装配 A2 产品业务流程**——将 STR-F 的场景业务展开为 SL3~SL5 角色场景 BP，将需求分解分配到各输出文档。指标文档、看板文档等均为独立 PL5 输出文档，与执行类文档同等处理——按 A2 侧分配到场景业务、按 Bn 侧定位 PL 路径和文档定义，不设独立的处理流程。流程/工单/计划的任务节点引擎化分工见 §2.5。

### 2.3 Bn产品：输出产品视角

#### 2.3.1 定义

Bn 是**各业务域的输出产品**。定义见 [91 规范 §5.3](91-eos-biz-eng-spec.md#53-bn产品)。构件为产品构件，末级节点为构件的产品数据——即**输出文档**（PL5）。这也是 wft02-biz 的末级节点（[91 规范 §7.2](91-eos-biz-eng-spec.md#72-业务流程开发wft02-biz)）。

#### 2.3.2 PL层级

沿产出视角（PL）展开：

| 层级 | 名称 | 说明 |
|------|------|------|
| PL0 | 平台 | EOS 平台 |
| PL1 | 业务域 | 如采购管理、生产管理 |
| PL2 | E2E 项目业务 | 如采购申请管理 |
| PL3 | 构件类型 | 产品的分解分类节点。按开发方式分三类，产生不同的输出文档集合。完整定义见 [91 规范 §5.3](91-eos-biz-eng-spec.md#53-bn产品) |
| | | **示例**：设备产品 → 系统/电子模块/电路板/软件模块/复用构件/外购构件/项目 |
| | | **开发方式后缀**：`自研` / `外购` / `复用` |
| | | **文档差异**：自研→全套研发文档；外购→采购规格/验收标准；复用→适配说明 |
| PL4 | WBS | 归纳层，可选占级 |
| PL5 | 业务输出文档 | **末级节点**；按条件细分 PL6-A 活动节点和 PL6-B 正文条目 |
| PL6-A | 活动节点 | 有任务类型时存在；定义处理角色、动作和状态变迁 |
| PL6-B | 正文条目 | 正文条目满足三独立时存在 |

#### 2.3.3 输出文档分类


输出文档按生成方式分为内置 CAX 和外置 CAX 两类，定义及引擎推导路径详见 §2.4.2。

正式输出文档在引擎层形成封面—正文 1:1 主子表单；轻量文档以正文功能表单直接呈现。存在关联文档下钻时，再在此基础上扩展 1+N 子表单。wft01-biz 在名称级识别输出文档及其候选支撑引擎链，wft02-biz 在 BP 层展开输出文档设计。

#### 2.3.4 本Skill在Bn侧的职责

**装配 Bn 产品业务流程** + **推断 Bn 构件输出文档**——定位输出文档的 PL1~PL5 路径，展开每个输出文档的设计。正式文档：封面字段（DocumentCover 表映射）+ 正文实体结构 + 支撑引擎 + 支持信息引用；轻量文档：正文实体结构 + 支撑引擎 + 支持信息引用。推断文档缺口，定义权限。任务节点引擎化见 §2.5。

### 2.4 功能引擎与输出文档的关系

#### 2.4.1 三层引擎生成链

EOS 平台通过三层引擎（EL1~EL3）逐级生成业务（[91 规范 §3.2~§3.4](91-eos-biz-eng-spec.md#32-引擎及层级)）。权威资产定义见 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景)。

```
实体引擎（EL3）──生成──→ 物理表
                           ↓ 被消费
功能引擎（EL2）  ──生成──→ 功能表单 / 主子表单
                           ↓ 被消费
菜单引擎（EL1）  ──生成──→ 菜单树 + 场景业务
```

**功能引擎**是 EL2 层级，将物理表转换为功能表单并按主子关系组装。具体引擎清单见 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景)，wft02-biz 不重复枚举。

#### 2.4.2 输出文档推导路径

自顶向下推导（[91 规范 §3.4](91-eos-biz-eng-spec.md#34-业务组装)）：

- **内置 CAX**：输出文档条目化内容 → 实体引擎（`@engine-entity`）生成物理表 → 功能引擎转换为功能表单 → 按主子关系（1+N）组装为主子表单 → 菜单引擎（`@engine-menu`）编排为场景业务
- **外置 CAX**：输出文档 → 计划引擎（`@engine-task`）管理任务/状态/附件/评审/归档，附件能力由实体引擎提供，N=0

wft01-biz 已在名称级产出每个输出文档的**候选支撑引擎建议**（全量 `[推断]`）。本 Skill 在 BP 层展开输出文档设计时，基于 BP 上下文校验候选建议，确认/修正/推翻。wft03-biz 仅对照引擎/CU 能力判断需求能否被承接并生成缺口线索，不承担 CU 设计（91 规范 §7.3）。

**引擎候选建议校验规则**：

本 Skill 在 Step 4（Bn 侧）设计中对 wft01 的引擎候选建议执行校验。校验依据 BP 展开后的完整上下文——输出文档在业务链中的职责、需执行的处理动作、文档状态变迁路径——而非 wft01 阶段仅有的 OR 文本。

| 校验结果 | 判定条件 | 动作 |
|---------|---------|------|
| **确认** | 候选引擎与 BP 展开后的文档职责和处理模式完全匹配 | 去掉 `[推断]` 标记，升级为已确认的支撑引擎 |
| **修正** | 候选引擎部分匹配但需调整（如 @engine-flow → @engine-workorder） | 写入修正后的引擎 + 修正原因（如"BP 设计发现需派发/验收能力，@engine-flow 不覆盖"）+ 去掉 `[推断]` |
| **推翻** | 候选引擎与 BP 展开后的文档处理模式不兼容，且 25 资产中无可替代引擎 | 标注 `[引擎待确认]` + 不兼容原因说明 → Step End 提示人类裁决 → 不阻塞其余文档的设计 |

修正时记录变更原因（写入文档的引擎判定依据字段），供 wft01 回查。wft03 消费的引擎信息以本 Skill 校验后的结论为准。

### 2.5 任务节点引擎化与任务关系引擎化

适用于所有有任务类型的正式或轻量文档。正式文档的活动节点附着于封面实体，轻量文档的活动节点附着于正文实体。

#### 2.5.1 任务节点引擎化

消费 wft01-biz 的任务类型与主要节点（业务语言），转化为引擎 CU 候选映射（引擎语言）：

**类型→引擎映射**：
- 计划 → @engine-task（计划引擎）
- 流程 → @engine-flow（流程引擎）
- 工单 → @engine-workorder（工单引擎）

**节点转化规则**：
- wft01 已捕获的节点 → 映射到引擎 CU——角色→引擎角色配置（如 `审批人=部门经理`）、动作→引擎动作配置（如 `[通过→财务审批, 驳回→申请人]`）、状态变迁→引擎状态配置（如 `部门已通过/已驳回`）
- wft01 标注 `[待wft02推断]` 的节点 → 设计完整节点序列（含系统自动节点、异常路径、超时处理）
- 全部节点标注 `[推断]`，未经人类确认不得落账

**业务语言→引擎语言示例**：

```yaml
# wft01 产出（业务语言）
任务类型：流程
节点：部门经理审批，通过后到财务

# wft02 转化（引擎语言）
引擎：@engine-flow
CU候选：@flow-cu-node-config
  角色=部门经理
  动作=[通过→财务审批, 驳回→申请人]
  状态变迁=部门已通过/已驳回
```

#### 2.5.2 任务关系引擎化

消费 wft01-biz 的任务关系（文档间流转顺序 + OR 明示的触发关系），转化为引擎可执行的触发规则：

- **文档间流转顺序** → 输出文档序列编排
- **OR 明示的触发关系** → 触发条件（如"审批通过后生成合同"→文档A(流程)节点"审批"=通过→创建文档B）
- **任意任务触发**（91 规范 §2.5 R5）→ 计划/流程/工单可触发任意任务类型，包括同类型；仅依据业务需要生成具体关系，不套固定拓扑

每个关系定义：源文档、触发条件（状态/节点）、目标文档、启动参数。

#### 2.5.3 PCA 策划阶段的任务判定

PCA 场景与 D 场景遵循同一任务规则：每个正式或轻量文档可配置零个或一个任务类型；场景业务中第一个有任务类型的输出文档必然为计划，但文档本体仍是开发/记录类业务文档，不因此变成“计划清单”。其余文档是否配置任务及任务类型，必须由业务需要、上游节点和任务触发关系决定，不得推定为全量计划，也不得自动生成无 OR 或 E2E 缺口依据的自指任务条目。

#### 2.5.4 PL6-B 正文条目需求定义

> wft01-biz 在业务语言层先判定正文集合性，再按三独立捕获 PL6-B 条目类型；PCA 定义型/管理型条目通常满足但仍逐类判定。本 Skill 在 BP 层将其展开为结构化需求定义。

**适用范围**：先判定 PL5 正文是否为集合容器，再对其中的条目类型执行三独立判定。PCA 场景的看板、指标、计划、风险、问题、行动项等定义型/管理型条目通常满足三独立，但仍须逐类判定。轻量文档若正文是一行一个原子文档实例，该正文行停留在 PL5 实例层，不得重复展开为 PL6-B；事务性物料行和普通议题记录等运行实例同样不展开。

**定义要素**：

| 维度 | 说明 | 示例（指标"订单及时率"） |
|------|------|------------------------|
| **条目名称** | 确认/精炼 wft01 捕获的名称（业务语言→标准化名称） | 订单及时率 |
| **定义要素** | 条目的核心定义内容——度量口径/维度/目标值（指标）、数据源/图表类型/刷新频率（看板卡片）、清单类型/优先级规则（计划项）、分类/等级（风险/问题）、状态集（行动项） | 口径=按约定交期准时交付的订单数/订单总数；维度=供应商/月份；目标值≥95% |
| **生命周期** | 独立于父文档的状态变迁路径 | 草稿→已发布→已废弃（审批后发布） |
| **支撑引擎** | 继承自文档支撑引擎，不单独判定 | 继承自父文档 @engine-kanban |

> wft01 已确认或标注 `[待wft02推断]` 的 PL6-B 条目，本 Skill 按以下优先级定义：OR 明示/隐含的条目名称→原样确认并展开定义要素；OR 仅提管理模式的条目→基于 BP 上下文推断定义要素，标注 `[推断]`；wft01 未捕获但对闭环必要的条目→先行推断 + `[推断-待OR确认]`，由 Step 5 生成 OR 材料。

**Phase B 关系检测**（PL6-B 条目级）：

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 条目名称匹配 + 定义范围一致 | 来源升级，追加 BP 引用，定义要素可细化 |
| 补充 | 条目名称不匹配 | 新增 PL6-B 条目，全面定义三要素 |
| 过时 | 基线条目未被本轮覆盖 | `[过时]` + 说明，保留不删除 |

**与封面模式及 PL6-A 的关系**：正式/轻量是 PL5 封面模式，PL6-A 是任务活动分解，PL6-B 是正文集合内的条目类型分解，三者相互正交。同一文档可兼有 PL6-A 和 PL6-B，但不得把轻量文档正文实例同时作为 PL5 文档实例和 PL6-B 条目重复建模。

**BP 节点完整要素**：

**资产对齐范围**：

|------|------|--------------|
| **23** 产品架构 | A2产品/Bn产品产品路径（含 A2 菜单可达性路径）。A2产品侧对齐记为 `23A`，Bn产品侧对齐记为 `23B` | Q1=直接引用已有路径 / Q2=扩展已有 / Q3=新建 |

| **26** 文档定义 | 输出文档对应功能表单的定义与归属 | Q1=同名同义文档已存在 / Q2=相似文档需扩展 / Q3=无匹配需新建 |

#### 2.6.1 Q1/Q2/Q3 对齐判定

对每个设计对象，按资产对齐范围执行对齐判定。Q1/Q2/Q3 描述当前设计对象与已有资产的匹配程度——**Q1（复用）**：已有资产完全匹配，直接引用；**Q2（扩展）**：已有资产部分匹配，需扩展边界；**Q3（新建）**：无匹配资产，需新建。

| 资产 | Q1 复用 | Q2 扩展 | Q3 新建 |
|------|---------|---------|---------|
| **23** 产品架构 | A2/Bn 产品路径存在且职责边界一致，直接引用已有路径 | 路径存在但需扩展构件类型、子节点或菜单可达性边界，引用路径并写扩展建议 | 路径不存在，写新建路径建议（名称/归属/边界） |
| **24** 业务资产 | 已有同名/同义业务块且职责范围一致，直接引用 | 存在相似业务块但职责需扩展，引用并写扩展建议 | 无匹配业务块，写新建业务块建议（名称/职责/归属路径） |
| **26** 文档定义 | 已有同名/同义文档定义且业务域、构件类型一致，直接引用 | 存在相似文档定义但名称、归属或范围需扩展，引用并写扩展建议 | 无匹配文档定义，写新建文档定义建议（名称/职责/归属业务域） |
| **28** 看板指标资产 | 已有同名/同义看板且指标方案一致，直接引用 | 存在相似看板但指标方案需扩展（新增/修改指标），引用并写扩展建议 | 无匹配看板，写新建看板建议（名称/职责/归属路径） |

**27 资源资产对齐判定**：27 不使用 Q1/Q2/Q3。已有资源直接追加 BP 引用（去重）；缺失资源形成资源资产建议（名称/类型/用途，建议状态=`待确认`）。

**28 看板指标资产对齐判定**：28 的 Q1/Q2/Q3 聚焦看板级别——已有看板匹配则 Q1，需扩展看板则 Q2，无看板则 Q3。看板内的单个指标不独立走 Q 判定，随看板方案整体对齐。

#### 2.6.2 SL4/PL4 归纳分组

SL4 角色职责从 SL5 场景业务的职责边界归纳分组，PL4 WBS 从 PL5 输出文档的业务模块归属归纳分组；命名取共性特征。归入同一 WBS 的输出文档满足**完成耦合**——WBS 中最后一个文档未确认完成时，其内容变化将迭代要求前序文档相应调整；仅当 WBS 内全部文档均确认完成，该 WBS 的产出才稳定。角色仅一个 SL5 时 SL4 不独立占级（菜单深度降为 3 级），PL4 同理。已有 SL4/PL4 可扩展边界容纳新 L5 节点（Q2），无法归入时新建（Q3）。

#### 2.6.3 覆盖自查清单

Step 5 末尾使用，机械检查，逐项打勾，发现遗漏**仅标注、不回退**——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全：

1. SL3~SL5 角色场景 BP 方案（含需求分配到输出文档）
2. PL3~PL5 产出产品 BP 方案（含输出文档路径 / 数据权限 / 文档缺口推断）
3. Step 4 执行完整性——逐 STR-F 输出文档核对 Step 4 已生成 PL4 WBS、任务节点引擎化（流程/工单/计划）、缺口推断、权限（无遗漏）
4. 23 对齐判定（A2/Bn 产品路径 / 菜单可达性路径）
5. 24 对齐判定（角色职责 / 场景业务）
6. 26 对齐判定（文档定义）
7. 27 对齐判定（资源资产引用）
8. 28 对齐判定（看板指标资产）
9. 变更影响声明
10. BP 版本号

#### 2.6.4 23 资产一致性检查

wft01-biz Step 5 已按 STR-F 的 23B 判定（Q1/Q2/Q3）写回 23 资产的 Bn 侧引用——即输出文档→E2E 项目业务/构件类型的对齐关系。本 Skill 在 BP 展开后拥有更完整的上下文（文档职责/处理动作/状态变迁路径），需对 wft01 已写回的 23 引用执行一致性检查，检出矛盾而非静默覆盖。

**检查时机**：Step 4 PL 路径确定后（§3.5.1 ② PL4 节点生成完成后），逐文档比对 wft01 的 23B 判定与 BP PL 路径推导结论。

| 不一致类型 | 判定条件 | 动作 |
|-----------|---------|------|
| **归属冲突** | wft01 23B-Q2/Q3 建议的 E2E 项目业务或构件类型归属，与 BP PL 路径推导的 PL2/PL3 不一致 | 标注 `[23归属冲突]` + 两者路径对比（wft01 建议 vs BP 推导）+ 冲突原因说明，提示人类裁决 |
| **误新建** | wft01 23B-Q3 建议新建 23 条目，BP 上下文发现已有 23 条目（同名/同义且职责范围覆盖）可承接 | 降为 Q2（扩展已有），记录降级原因和已有条目路径；不写入两条并行路径 |
| **误引用** | wft01 23B-Q1 引用已有条目，BP 展开后发现该条目职责边界不能覆盖当前文档 | 升为 Q2（扩展）或 Q3（新建），记录升级原因和 BP 上下文中发现的覆盖缺口 |

**与 Step 6 资产写回的关系**：一致性检查聚焦**检出矛盾**——产出矛盾标注和裁决提示，不自行修正 23 资产中的已有内容。矛盾项在 Step 6 写回时**暂不写回 23**（待人类裁决后下一轮处理），其余无矛盾项正常写回。

**与并行推进的关系**：wft01 资产写回（Step 5）与 wft02 BP 设计可并行推进。若 wft02 运行时 wft01 尚未完成 23 写回：

- STR-F 23B 判定仅有 Q 级别和路径建议（无实际 23 资产块 ID）
- → 一致性检查降级为校验 Q 判定与 PL 路径的语义一致性
- → 仅检出归属冲突，不执行误新建/误引用判断（因无可比对的实际资产块）
- → Step End 时提示"wft01 23 写回未完成，一致性检查不完整"

### 2.7 BP 节点生命周期

BP 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §A.6.2 通用六态定义表（wft02-biz 列）。并行推进规则（资产写回与 SR-F 展开互不阻塞）见 91 规范 §A.6.3。

**主线流转**（wft02-biz ←→ wft03-biz）：

```
待确认方案 ──人类确认──→ 可以SR设计 ──wft03锁定──→ 在SR设计 ──wft03完成──→ 已SR设计
     ↑                      ↑                       │
     │                      │              wft03退回 │
     │                      │                       ↓
     └──── wft02修订 ──── 需wft02修订 ←─────────────┘
```

**上游变更**（STR-F 修订触发 BP 重入）：

```
可以SR设计 ──上游修订──→ 可以SR设计（版本递增，wft03 未消费）
在SR设计   ──上游修订──→ 在SR设计（版本递增，wft03 增量处理）
已SR设计   ──上游修订──→ 待补充SR设计 ──wft03补全──→ 已SR设计
```

> **分工**：wft02-biz 写入 `待确认方案` / `可以SR设计` / `待补充SR设计` / `需wft02修订`；wft03 写入 `在SR设计` / `已SR设计`。

#### 2.7.1 推进态（按顺序）

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `待确认方案` | 方案已生成或修订，等待人类反馈 | Step 3~5 方案与缺口出口生成完成后 |
| `可以SR设计` | 方案已确认，wft03 可启动 SR 架构设计 | 全部条目 `[同意]` + `[已处理]` |
| `在SR设计` | wft03 已锁定此 BP，正在展开 SR-F | wft03 写入活动锁 |
| `已SR设计` | SR-F 展开完成，BP 消费版本与当前版本一致 | wft03 处理完成且未检测到上游新版本 |

人类确认方案后，BP 节点推进为 `可以SR设计`，此时 wft03 即可启动 SR-F 展开——wft03 直接从 BP 节点（`04-*.md`）读取设计内容，不依赖 23/24/26/27/28 资产文件的写回结果。资产写回（Step 6）与 SR-F 展开（wft03）并行推进、互不阻塞。

#### 2.7.2 上游变更态（STR-F 汇入触发 BP 修订）

当新 STR-F 汇入已有 BP 触发修订时，BP 内容变更、版本号递增——但下游 wft03 可能已基于旧版本生成了 SR-F。修订后 BP 状态按 wft03 的消费进度分流：

| 修订前状态 | 修订后 | 说明 |
|-----------|--------|------|
| `可以SR设计` | 保持，版本递增 | wft03 尚未消费，不受影响 |
| `在SR设计` | 保持，版本递增 | wft03 正在处理中，重入时检测版本差异，按变更影响声明增量处理 |
| `已SR设计` | 降为 **`待补充SR设计`** | wft03 之前生成的 SR-F 基于旧版本 BP，需 wft03 重新介入补全 |

- **`待补充SR设计`**：wft03 之前已消费的 SR-F 节点不动（它们仍然有效），但 BP 新增了业务或功能表单需要生成新的 SR-F。wft03 进入后按 BP 的变更影响声明确定增量映射范围，处理完成后若消费版本追上 BP 当前版本 → 推进回 `已SR设计`

#### 2.7.3 下游退回态（wft03 发现缺陷退回修订）

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| **`需wft02修订`** | BP 方案存在缺陷，需本 Skill 修订后重新交付 | wft03 写入，附带缺失说明 |

本 Skill 重入 `需wft02修订` 的 BP 时：读取 wft03 的缺失说明 → 按人类改进方案修订 BP（走 Step 3 修订流程）→ 人类确认 → BP → `可以SR设计`

#### 2.7.4 版本标记与消费追溯

- BP 节点初次生成时版本 = `v1`，变更影响声明写"首版，无变更"
- 每次因新 STR-F 触发 Step 3 修订，版本号递增
- 版本号写入 BP 节点头部（与节点 ID 同级）
- wft03 首次消费 BP 时，在对应 SR-F 节点中记录 `BP 消费版本：v{N}`
- wft03 重入同一 BP 时比对版本：若 BP 当前版本 > 已消费版本 → 触发变更感知

### 2.8 BP 变更传播协议

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板、增量清单与变更影响声明的分工）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。

#### 2.8.1 变更类型分类（BP → SR-F 特化）

| 变更类型 | 判定标准 | 对下游影响 |
|---------|---------|----------|
| **增量型** | 仅新增业务/场景要素，已有业务/产品路径/功能表单结构均未改动 | 已有 SR-F 节点不受影响，仅需映射新业务 |
| **修订型** | 已有业务/场景要素被修改；产品路径与功能表单结构未变 | 对应 SR-F 节点需局部调整 |
| **结构型** | 产品路径需新增 SL2/PL2 节点或跨业务域重组、菜单新增/合并/拆分、BP 结构需重塑 | SR-F 结构可能重塑，需人类裁决后方可处理 |

> 注：Q2 在已有路径下扩展子节点属「修订型」，不触发「结构型」。判定优先级：结构型 > 修订型 > 增量型。

#### 2.8.2 变更影响声明格式

每次修订已有 BP 后，在 BP 节点末尾写入（`04-*.md` 中 BP 节点块内）：

```text
### 变更影响声明

BP 版本：v{N}（本次修订前为 v{N-1}）
本轮变更类型：增量型 / 修订型 / 结构型

变更项：
- [新增] / [变更] / [确认] / [需裁决] ...

下游已消费此 BP 的 SR-F 节点：
  <SR-F节点ID列表>（如无则写"尚未被下游消费"）

对已消费 SR-F 节点的影响：
  受影响节点：<SR-F节点ID + 受影响原因>
  不受影响节点：<SR-F节点ID>
  待新增 SR-F 映射：<新业务/新功能表单/权限需求对应的待映射说明>

建议 wft03 动作：
  - 增量型：增量映射新增 PL5/权限需求即可，已有 SR-F 节点不动
  - 修订型：修订受影响的 SR-F 节点 → 标记 [来自上游变更]
  - 结构型：输出影响范围，等人类裁决后再处理
```

分工见 [91 规范 §A.7.4](91-eos-biz-eng-spec.md#a74-增量清单与变更影响声明的分工) 对照表。

#### 3.1.1 输入校验

| 校验条件 | 判定 | 动作 |
|---------|------|------|

> 软提示不强制退出，由人类选择继续或退出。逻辑上不可能的条件（状态不符、类型不匹配）为硬退出（§A.4.5）。

#### 3.1.2 退回优先（§A.4.3 门禁）

存在 `需wft02修订` 的 BP 节点（来自"待下游退回处理"分节）：
- 检查人类是否已提供改进方案（读取退回节点的缺失说明中是否含人类标注或下游 Skill 的具体改进指引）
- 已提供 → 通过门禁，读取 wft03 的缺失说明，按人类方案修订 BP
- 未提供 → 输出 wft03 的缺失说明 + 提示提供改进方案 → **退出**

#### 3.1.3 反馈处理

存在"待反馈处理"分节中的 BP 节点（确认状态 = `[修改]`/`[驳回]` 且无 `[已处理]`）→ 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 STR-F，Step End 时提示。

#### 3.1.4 新 STR-F 路由

有未处理的 STR-F 节点（来自"待 wft02-biz 处理"分节）→ 进入 Step 1→Step 3，按产品路径+用户角色匹配已有 BP（Q1 归入/Q2 扩展归入/Q3 新建），逐节点展开设计。

**执行顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计）。

| 原因 | 规则 |
|------|------|
| 反馈可能改变 BP 的产品路径、业务清单或权限结论 | Step 3 必须基于 Step 2 修改后的最新 BP 内容，不得使用缓存旧状态 |
| 与 §A.4.4 规则三一致 | 退回优先 → 反馈处理 → 新输入路由 |

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：BP 节点的 A2 方案 / Bn 方案 / 输出文档设计 / PL6-B 正文条目需求 / 数据权限 / 资产对齐结论。各条目的 `确认状态` 字段位于 `04-*.md` BP 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 STR-F 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3~5 同为设计者——先理解人类反馈在 STR-F 需求语境中的含义，再执行修订，最后检查修订后的方案是否仍满足 STR-F 需求。

本 Skill 特化参数（锚点需求 / 操作条目 / 推进目标 / 级联触发条件 / 资产对齐级联）见下表（按 [§A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 实例化）：

| 特化维度 | wft02-biz 值 |
|---------|-------------|
| **锚点需求** | 当前 BP 所承接的全部 STR-F 节点——人类反馈理解和修订均以 STR-F 场景业务需求为最终锚点 |
| **操作条目** | A2 方案 / Bn 方案 / 输出文档设计（含 PL6-A 活动节点 + PL6-B 正文条目需求）/ 数据权限 / 23/24/26/27/28 资产对齐结论。条目 `确认状态` 字段位于 `04-*.md` BP 节点块各条目正文中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → BP 推进至 `可以SR设计` |
| **清除条件** | 已有 `[同意]`+`[已处理]` 默认跳过。仅当本轮新输入满足**任一**条件时，清除 `[已处理]`（保留 `[同意]`）：<br>1. 新输入是该条目的直接上游节点（如新 STR-F 是 BP 来源）<br>2. 新输入与条目同属一个架构层级且边界重叠（如同属 PL5，新文档改变了已有文档的范围/归属）<br>3. 新输入导致条目定义被修订（变更影响声明标注为修订型/结构型，§A.5.3 Step 1） |
| **级联触发条件** | `[修改]`/`[驳回]` 导致方案结构性变更（产品路径变更/文档增删/引擎变更/PL6-B 条目增删）→ 标记受影响条目为 `[需重设计]` |
| **资产对齐级联** | 方案变更影响 23/24/26/27/28 资产引用 → 更新受影响资产的 Q 判定和引用路径 |

#### 3.3.2 确认状态格式示例

**AI 写入（Step 3~5 完成时）** —— 为每个条目初始化 `确认状态` 字段，初始为空：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: (空)
- 采购申请单（输出文档，@engine-flow + @engine-entity） [23B-Q2] | 确认状态: (空)
- 采购申请合格率（看板，@engine-kanban） | 确认状态: (空)
```

**人类在条目 `确认状态` 字段标注** —— 三种标注形式：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: [同意]
- 采购申请单（输出文档，@engine-flow + @engine-entity） [23B-Q2] | 确认状态: [修改]：引擎应改为 @engine-flow + @engine-entity
- 采购申请合格率（看板，@engine-kanban） | 确认状态: [驳回]：该指标已有 BP-YYY 覆盖，不重复
```

**AI 处理完成后** —— 在人类标注末尾追加 `[已处理]`：

```text
- A2-场景业务-采购员执行采购申请 | 确认状态: [同意] [已处理]
- 采购申请单（输出文档，@engine-flow + @engine-entity） [23B-Q2] | 确认状态: [修改]：引擎应改为 @engine-flow + @engine-entity [已处理]
- 采购申请合格率（看板，@engine-kanban） | 确认状态: [驳回]：该指标已有 BP-YYY 覆盖，不重复 [已处理]
```

人类改写 `确认状态` 即覆盖旧内容，`[已处理]` 自然消失，条目回到待处理状态。完整历史追溯通过 BP 版本号 + 变更记录实现。

### 3.4 Step 3 · 角色场景视角 BP 设计

以 STR-F 场景职责边界为锚，落成 A2 角色场景视角 BP。核心工作是给每个 STR-F 的 SL5 场景业务确定一个 SL4 角色职责归宿。

#### 3.4.1 推断 SL4 角色职责

SL4 角色职责是 Step 3 的核心产出——从 STR-F 的场景职责归纳，取名取共性特征。按已有资产情况分流：

| 判定 | 条件 | 动作 |
|------|------|------|
| **Q1 复用** | 已有同名/同义 SL4 且职责范围一致 | 直接引用，STR-F 归入该 SL4 |
| **Q2 扩展** | 已有相近 SL4 但需扩展其职责边界 | 扩展已有 SL4，归纳规则见 §2.6.2 |
| **Q3 新建** | 无匹配的已有 SL4 | 新建 SL4 角色职责节点，写入 `04-*.md` |

SL4 占级规则见 §2.6.2。SL3 角色类型从 STR-F 用户角色直接映射，不重复判定。

Q1/Q2 归入已有 SL4 时，将本轮新 STR-F 的输出文档清单与该 SL4 下已有内容逐项比对，按 §1.1 收敛规则（确认/补充/无新增/矛盾）执行对应动作：确认→升级来源，补充→全量重新展开（非增量追加），无新增→仅加引用，矛盾→记录待人类裁决。

#### 3.4.2 输出文档需求定义

场景业务的需求由 STR-F 定义，Step 3 将其分解分配到各输出文档——每个输出文档承接一部分场景职责。对 STR-F 业务链中的每个输出文档，确定：

- **文档职责**：该文档在场景中承担什么角色（如"承载申请数据""记录审批结果""汇总指标"）
- **信息来源**：数据从哪个前序文档流入，或由用户直接录入
- **输出去向**：产出物被哪个后续文档消费，或直接交付给用户

这是将 STR-F 的"场景业务"分解为 BP 的"文档级需求"的第一步。输出文档的完整设计（PL 路径、生命周期、权限）在 Step 4 完成。

SL5 与 STR-F 1:1 映射，场景职责复用 STR-F 的场景职责边界。将上述分配结果连同触发动作和上下文传递点按 STR-F 的业务链顺序写入 BP 节点。流程/工单类输出文档的活动节点引用规则见 §2.5.2。

完成写入后执行 23/24 对齐判定（规则见 §2.6.1）。

### 3.5 Step 4 · 输出产品视角 BP 设计

将 STR-F 的输出文档清单落成 Bn 输出产品视角 BP——生成 PL4 WBS 节点，定义输出文档方案（正式文档：封面字段+正文实体结构+支撑引擎+支持信息引用；轻量文档准用），设计流程/工单的活动节点与任务关系，定义 PL6-B 正文条目需求，推断文档缺口，推导权限。设计过程中识别的业务缺口不在此步生成 OR 材料，交由 Step 5 统一处理。

#### 3.5.1 引擎校验与 PL4 节点生成

**① 引擎候选建议校验**：对每个输出文档，按 §2.4.2 校验规则，基于 BP 上下文逐文档校验 wft01 的引擎候选建议——确认则去掉 `[推断]`、修正则写入修正后引擎+修正原因、推翻则标注 `[引擎待确认]`。校验后的引擎结论（确认/修正/推翻）写入输出文档的引擎标注字段。PL3 构件类型的判定来源见 ②。

**② PL4 节点生成**：对每个输出文档，PL1（业务域）从 STR-F 读取，PL2（E2E 项目业务）和 PL3（构件类型）从 STR-F 23B 判定读取。若 wft01-biz 尚未产出 23B 判定，AI 基于输出文档性质和校验后的支撑引擎类型推断，标注 `[推断]`。

PL4 WBS 是 Step 4 的核心结构产出——将同一构件类型下的输出文档按业务模块归纳分组，形成 PL3 到 PL5 之间的中间节点。取输出文档名称/用途/支撑引擎的共性特征命名 WBS 包（如"采购申请创建与维护""供应商评估与准入"）。已有 WBS 可扩展边界容纳新文档（Q2），无法归入时新建（Q3）。WBS 归组规则（含完成耦合）见 §2.6.2。

**③ 23 资产一致性检查**：PL 路径确定后，按 §2.6.4 规则逐文档比对 wft01 的 23B 判定与 BP PL 路径推导结论。检出归属冲突→标注 `[23归属冲突]` + 提示人类裁决；检出误新建→降为 Q2 + 记录降级原因；检出误引用→升为 Q2/Q3 + 记录升级原因。矛盾项在 Step 6 写回时暂不写回 23，待人类裁决后下一轮处理。

#### 3.5.2 输出文档方案定义

对每个输出文档，在 PL 路径和支撑引擎确定后，定义文档的完整结构方案。正式文档与轻量文档的方案要素不同。

**正式文档方案**：

| 要素 | 定义内容 | 示例（采购申请单） |
|------|---------|------------------|
| **封面字段** | DocumentCover 表映射——单据号/标题/状态/版本/创建人/部门/日期等文档级元数据字段 | 单据号（自动生成）、标题（手动录入）、状态（草稿/已提交/审批中/已通过/已驳回）、版本（v1.0） |
| **正文实体结构** | 内容实体的字段集——字段名/字段类型/约束/CRUD。从 STR-F 输出文档的 `业务链文档序列` 提取，确保字段覆盖场景需求 | 物资编码（FK→物资主数据）、物资名称、规格型号、申请数量、预算科目、期望到货日期 |
| **支撑引擎** | 由 §3.5.1 ① 校验后的引擎结论直接引用，不再重新判定 | @engine-entity + @engine-flow |
| **支持信息引用** | 引用关系——引用文档名称/引用方式（只读/更新）/引用用途。去重，同一文档被多次引用只记录一次 | 引用「采购策略表」（只读，用于匹配审批路径） |

**轻量文档方案**：

轻量文档无封面，正文实体结构定义同正式文档的正文实体结构；支撑引擎由校验后的引擎结论直接引用；支持信息引用处理规则同正式文档。

**执行规则**：
- 封面字段以 DocumentCover 表模板（[91 规范 §2.2](91-eos-biz-eng-spec.md#22-正式文档的组成)）为基，按文档类型裁剪——正式流程文档添加审批相关字段、正式计划文档添加计划周期字段
- 正文实体字段集从 STR-F 输出文档的业务链文档序列提取
- 支持信息引用去重处理
- 全部方案内容标注 `[推断]`，经人类确认后方可落账

#### 3.5.3 流程工单活动设计

仅针对 STR-F 已确认的输出文档。对流程类和工单类输出文档，按 §2.5 定义活动节点序列——逐节点定义处理角色、可执行动作、状态变迁、系统自动节点/异常路径/超时处理，画出状态变迁路径（如草稿→已提交→审批中→已通过/已驳回）。

推断依据（按优先级逐层驱动，非平铺并列）：
  - **主驱动——对 STR-F 场景需求的理解**：该输出文档在业务链中承担什么职责、需要哪些处理步骤方能完成端到端闭环、每个步骤由哪个角色执行并产出什么文档状态。活动节点本质是对 STR-F 需求的方案响应（需求/方案相对原则），而非对 OR 词汇的机械映射
  - **约束——支撑引擎的能力边界**：设计的活动节点是否在 `@engine-flow` / `@engine-workorder` 的能力范围内（如流转模板定义的可用节点类型和合法状态迁移）。超出引擎能力的节点不修改方案迁就，标注为引擎需求缺口
  - **参考——同类文档模式 + AI 经验**：同域/同引擎类型的已有活动节点序列作为参考模板，行业通用流程模式作为补充材料，不替代对 STR-F 需求的分析
  - **门禁——人类反馈与确认**：全部活动节点标注 `[推断]`，经由人类在确认状态字段标注 `[同意]` / `[修改]` / `[驳回]` 后方可落账，不得未经确认直接写入资产

非流程/非工单类输出文档无需此项，跳过。

#### 3.5.4 看板指标设计

仅针对 STR-F 已确认的看板类输出文档。对看板类输出文档，按 §2.5.2 定义指标序列——逐指标标注指标名称、度量口径、度量目标、聚合维度、显示图示和刷新频率。

推断依据（按优先级逐层驱动，非平铺并列）：
  - **主驱动——对 STR-F 场景需求的理解**：该看板在业务链中承担什么度量职责、需要哪些指标方能完整反映业务健康状况、每个指标如何度量与展示。指标本质是对 STR-F 需求的方案响应，而非对 OR 词汇的机械映射
  - **约束——支撑引擎的能力边界**：设计的指标及其显示图示是否在 `@engine-kanban` 的能力范围内（如支持的图表类型、聚合规则、刷新机制）。超出引擎能力的指标不修改方案迁就，标注为引擎需求缺口
  - **参考——同类看板模式 + AI 经验**：同域/同引擎类型的已有指标方案作为参考模板，行业通用指标设计模式作为补充材料，不替代对 STR-F 需求的分析
  - **门禁——人类反馈与确认**：全部指标标注 `[推断]`，经由人类在确认状态字段标注 `[同意]` / `[修改]` / `[驳回]` 后方可落账，不得未经确认直接写入资产

非看板类输出文档无需此项，跳过。

#### 3.5.5 文档缺口推断

**逐文档检查**：对每个输出文档，检查 26 资产中是否已有对应的文档定义。有则引用（26-Q1），需扩展则标注（26-Q2），无则形成新建建议（26-Q3）。

**按 WBS 推断缺口**：对每个 PL4 WBS，推断该 WBS 下应有的输出文档清单，与 STR-F 已有文档比对：

| 推断来源 | 说明 | 处理 |
|---------|------|------|
| 26 资产已定义 | 23 WBS 行引用的文档定义清单 | 正式依据，直接比对 |
| AI 经验推断 | 基于同类 WBS 模式、行业知识推断的应有文档 | 标注 `[推断-待OR确认]`，由 Step 5 生成 OR 材料 |
| STR-F 已确认 | wft01-biz 已确认的输出文档 | 正式产品数据，视为已覆盖 |

比对后，STR-F 未覆盖的为缺口——写入 BP 节点缺口说明，不直接写入 24/26 资产。

#### 3.5.6 文档权限设计

仅针对 STR-F 已确认的输出文档。基于 STR-F 的 `用户角色` 和角色在业务链中的位置，按四维度推导：

| 维度 | 推导来源 | 示例（采购申请单 / 采购员） |
|------|---------|--------------------------|
| 字段可见性 | 角色职责范围、风险合规约束 | 审批意见字段对采购员只读 |
| 字段可编辑性 | 角色在业务链中的位置：录入者/审批者/查询者 | 草稿态字段全部可编辑 |
| 行级数据范围 | 角色组织归属 | 仅可见本人创建的申请单 |
| 按钮操作权限 | 角色可执行动作 | 提交/撤回可操作，审批不可操作 |

#### 3.5.7 PL6-B 正文条目需求定义

逐输出文档先执行“正文是否为集合容器”判定，再按三独立执行。PCA 场景的定义型/管理型条目逐类判定；轻量文档原子正文行、事务性物料行和普通议题记录跳过。

消费 wft01-biz 在名称级捕获的 PL6-B 条目清单，按 §2.5.4 的定义要素逐条展开：

| 维度 | 说明 |
|------|------|
| **确认条目名称** | wft01 已捕获 → 确认并标准化名称；wft01 标注 `[待wft02推断]` → 基于 BP 上下文推断命名 |
| **定义要素** | 指标：口径/维度/目标值；看板卡片：数据源/图表类型/刷新频率；计划项：清单类型/优先级规则；风险/问题：分类/等级；行动项：状态集 |
| **定义生命周期** | 独立于父文档的状态变迁路径（如指标：草稿→已发布→已废弃） |
| **支撑引擎** | 继承自文档支撑引擎（§3.5.1 ① 校验后的结论），不单独判定 |

全部 PL6-B 条目标注 `[推断]`（名称+定义要素+生命周期均标注 `[推断]`），经由人类确认后方可落账。发现对闭环必要的但 wft01 未捕获的条目 → 先行推断 + `[推断-待OR确认]`，由 Step 5 生成 OR 材料。

PL6-B 与 PL6-A 的关系见 §2.5.4 末段。

#### 3.5.8 任务关系引擎化

在全部输出文档方案及活动节点设计完成后，对 Step 4 涉及的输出文档之间及文档内部的任务间关系进行引擎化配置定义。

**执行时机**：PL4 WBS 确立、输出文档方案定义、活动节点设计完成后——此时文档结构和节点序列已明确，可导出完整触发关系网。

**定义内容**：

| 关系类型 | 来源 | 转化规则 | 示例 |
|---------|------|---------|------|
| **文档间流转顺序** | wft01 `业务链文档序列` 的先后顺序 | → 输出文档序列编排，定义文档间的依赖先后关系 | 采购申请单(创建)→审批记录(审批)→采购订单(生成) |
| **OR 明示的触发关系** | wft01 在 OR 中捕获的任务间触发关系 | → 引擎任务间触发规则配置——源文档、触发条件（状态/节点）、目标文档、启动参数 | 审批记录.节点"审批"=通过 → 创建采购订单 |
| **任意任务触发** | 91 规范 §2.5 R5 | 计划/流程/工单可触发任意类型，包括同类型；仅基于需要生成具体关系，不套固定拓扑 | 采购计划(计划)发布 → 触发采购申请单(流程) |

**每个关系的定义要素**：

```yaml
源文档：<PL5 输出文档ID>
源状态/节点：<触发条件>
目标文档：<PL5 输出文档ID>
启动参数：<选项。需传递到目标文档的初始化字段值>
关系来源：<OR 明示 / wft01 业务链序列 / AI 推断>
```

**门禁**：全部关系定义标注 `[推断]`（来源为业务链序列的直接映射除外——继承 wft01 的业务语言确认，无需 `[推断]`）。经由人类在确认状态字段标注后方可落账。
