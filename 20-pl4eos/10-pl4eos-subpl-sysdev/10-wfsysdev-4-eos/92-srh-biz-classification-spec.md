## 一、分类层级结构与作用域

### 1.1 树源

系统功能需求树的形态以 94 §3.1 为准，本规范不另设树口径。为执行分类，复述该树并标注本规范作用域：

```
SR 系统功能需求树（树权威 = 94 §3.1）
└── 信息系统 ────── ① 承接（部分）业务流程的信息系统（可多个）
    └── 系统用例功能簇 ─ ② 对系统用例功能类的再聚类           ← 本规范管辖（最粗簇）
        └── 系统用例功能类 ─ ③ 按系统职责维度对系统用例功能的聚类  ← 本规范管辖（核心类）
            └── 系统用例功能 ─ ④ 同一功能的不同实现方式的归并层（分类的最小处理单元）
                └── 用例场景功能 ─ ⑤ 将用例场景（用户视角）转换为系统视角的功能
                    └── IPO功能 ─ ⑥ 系统对输入的响应
```

### 1.2 层级判定

- **叶（末级）＝ ⑥ IPO功能**；**枝梢＝ ⑤ 用例场景功能**（叶的上一级，概要的最深节点）。
- **概要＝ ①~⑤**（除叶之外的全部节点）；**⑥ 的叶定义只在完整态**（详设阶段落叶）。
- ⑤ 由业务侧用例场景（= 94 二章业务树 ⑦ 用例场景类操作）转换而来，与 bpd-biz 末级承接分配**不变**；⑥ 是 ⑤ 之下对每次输入给出响应的最小需求单元，分配关系同样不变。

### 1.3 本规范作用域

只规 **② 簇、③ 类** 两层非叶聚类——**④ 系统用例功能**（同功能不同实现的归并层）是分类对象与最小处理单元；**不规**：

- ① 信息系统分群——属"哪套系统承接业务"的归属，不是职责分类；
- ⑤⑥——业务→系统的转换产物，不做职责聚合。

**对象边界（重要）**：本树只含上述功能节点。旧 srh 曾以"流程定义 / 表单结构定义 / 指标定义 / 功能表单 / 窗口标签页"等**平台可落地对象**充当末级——这些对象不是 94 §3.1 树的节点，属 94 §五 配置方案 / §六 组件方案 承载（待定义）。wft03 承接落点仍在 **⑤ 枝梢**，分配关系不变。分类中遇到这些词，只当"③ 类将由哪些引擎/对象类型承接"的**检索线索**，不作树层、不作桶名。

### 1.4 分类与 [91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md) 的关系

| 91 规范映射 | 本规范补充 |
|-------------|-----------|
| `wft03`：bpd-biz 末级（用例场景/操作）→ srh ⑤ 用例场景功能（枝梢） | 明确 ⑤/④ 之上的非叶聚类结构：④ → ③ 类 → ② 簇 |
| 分类宿主匹配与写回 | 明确聚类依据是**系统职责**（非业务域、非业务对象） |

## 二、系统职责的定义

### 2.1 定义

**系统职责**是形成 **③ 系统用例功能类** 的聚类维度，指：

> 对已就位的 **④ 系统用例功能**（同一业务功能的不同实现方式的归并单元）按其**系统需求职责、实现机制与承接边界**聚合后形成的 ③ 类。

它回答的问题是：

> "这个系统用例功能在系统里主要负责什么、由哪类机制承接？"

而不是：

> "它属于哪个业务域？"

### 2.2 与 bpd-biz 分类的区分

| 维度 | bpd-biz 分类（业务视角） | srh-biz 分类（系统职责视角） |
|------|-------------------|------------------------|
| 分类对象 | 业务侧末级（用例场景/操作，04） | ④ 系统用例功能（③ 类的对象） |
| 分类依据 | 业务域、业务对象、角色场景 | 系统需求职责、实现机制、pa-eng 承接边界 |
| 聚合方式 | 按"做什么业务"聚合 | 按"系统怎么处理"聚合 |
| 分类稳定性 | 随业务组织方式变动 | 相对稳定，跨业务域复用 |
| 对 pa-eng 的意义 | 间接 | 直接——为 pa-eng 组件划分边界 |

### 2.3 系统职责的判断句式

可用以下句式判断一个 ④ 系统用例功能应归入哪个 ③ 类：

> "这个功能在系统里主要负责什么？"

典型答案（候选 ③ 类名）包括：采集/录入、校验/计算、计划/调度、执行/驱动、监控/预警、分析/评价、规则/配置、协同/通知 等。详见 §四。

## 三、分类原则

### 原则 1：先有具体功能（⑤/⑥），再做聚类

分类只能建立在已完成视角转换的具体功能之上（概要内以 ⑤ 枝梢为对象边界），由下而上聚合 ④ → ③ → ②。不能先假设上层 ③/②，再倒推具体功能去适配。⑥ 叶虽在完整态才定义，但 ⑤ 及其实现方式是聚类的前提。

### 原则 2：按系统职责聚合，不按业务对象

两个 ④ 系统用例功能能否归入同一 ③ 类，首先看它们是否承担同一种系统职责。判断句式见 §2.3。

✅ 按系统职责分：
```
④ 采购审批流转功能        ─┐
④ 生产审批流转功能        ─┴→ ③ 规则判定/流程编排（同一系统职责，跨业务域）
```

❌ 不按业务域分：
```
④ 采购审批流转功能 ─→ ③ 采购域功能类       ← 这不是系统职责
④ 采购状态跟踪功能 ─→ ③ 采购域功能类       ← 职责不同，不该硬聚在同一类
```

### 原则 3：一节点只归一个主职责

一个 ④ 系统用例功能可能兼有执行、校验、通知等多重特征。分类时只按其**主职责**归入一个 ③ 类，不做一节点多父类。次要职责写入节点定义或设计指导，不用于主导分类。

### 原则 4：非叶节点（③/②）必须能写出一句统一定义

如果一个候选 ③ 类（或 ② 簇）无法写出一句覆盖其全部子节点的统一定义，说明这个类不成立。

判断模板：

> "本类功能用于支持系统完成 **\_\_\_** 类职责，为下层系统用例功能提供统一的能力边界。"

写不顺，通常就是聚合错了。

### 原则 5：粒度适中

一个 ③ 类下的 ④ 系统用例功能数量应适中：
- **太少**：只有 1 个 ④，通常说明这层分类没有价值
- **太多**：超过 7~9 个 ④，通常说明职责混杂，需要再拆
- **合理**：2~5 个最稳，6~8 个可接受

### 原则 6：信息系统只做上层分群，不替代系统职责

功能树顶层 ① 信息系统 是按"谁承接业务"分群；**每个 ① 之下仍须按系统职责聚 ③/②**，不能直接用 ① 信息系统（或业务域）代替 ③ 类。

```
✅ 正确（信息系统之下再按职责聚类）：
信息系统 A
├── ③ 规则/配置类
├── ③ 执行/流转类
├── ③ 监控/预警类
└── ③ 统计/分析类

❌ 错误：
信息系统 A
└── ③ A 系统功能类（非系统职责）
```

### 原则 7：允许跨域复用同一职责类

不同业务域（乃至不同 ① 信息系统）下可以出现相同的 ③ 类名。例如采购域、生产域都可有：

- `规则/配置`
- `执行/流转`
- `监控/预警`
- `统计/分析`

跨域保持系统需求架构一致；跨 ① 信息系统时同类名各自独立成节点、路径不同，不算冲突（§5.3）。

### 原则 8：引擎能力类功能少设中间层

引擎能力类功能（由引擎/CU 能力直接表达的 ④）默认 **④ → ③** 即可，多数不设 ② 簇中间层；仅当 ③ 类过多（>7 类）或 pa-eng 承接边界混杂时，才用 ② 簇再聚。

## 四、标准职责桶清单（候选 ③ 类名）

> 桶清单是**组织索引**：按"业务定义类型 / 引擎能力域"（如 流程/表单/指标/工单/计划……）分节组织候选的 **③ 系统用例功能类** 名称。业务定义类型与引擎域**不进树**，只用于按场景检索应优先选用的 ③ 类名。

### 4.0 ② 簇（最粗层）粗分建议

跨类型的 ② 系统用例功能簇，建议按下述粗簇归组（每簇含若干 ③ 类）：

| ② 簇（粗分） | 含义 | 含的典型 ③ 类 |
|-------------|------|--------------|
| 定义配置簇 | 各类业务定义/能力结构的配置与管理 | 定义配置、结构定义、字段校验 |
| 规则判定簇 | 条件判断、审批路由、自动决策 | 规则判定、授权审批 |
| 执行流转簇 | 业务数据的产生、流转与提交 | 录入提交、流程编排、任务分派 |
| 监控协同簇 | 状态、通知、协同与预警 | 状态跟踪、通知触发、协同交互 |
| 统计展示簇 | 查询、计算与分析展示 | 展示查询、指标计算、分析预警、进度追踪 |

### 4.1 跨类型通用职责桶（候选 ③ 类）

以下 ③ 类名在多个业务定义类型下可复用：

| ③ 类名 | 系统职责描述 | 典型适用类型 |
|--------|-------------|-------------|
| 定义配置 | 业务定义的结构、属性、规则的配置与管理 | 流程定义、表单定义、指标定义、工单定义、计划定义 |
| 规则判定 | 条件判断、审批路由、自动决策 | 流程定义 |
| 流程编排 | 多步骤流程定义、条件分支、并行/串行编排 | 流程定义 |
| 状态跟踪 | 状态推进、进度查看、历史记录 | 流程定义、工单定义、计划定义 |
| 通知触发 | 消息生成、待办推送、通知分发 | 流程定义、工单定义 |
| 结构定义 | 数据字段、表格结构、关系定义 | 表单定义、台账定义 |
| 字段校验 | 数据格式验证、必填检查、业务规则校验 | 表单定义 |
| 录入提交 | 数据创建、编辑、保存、提交 | 表单定义、工单定义 |
| 展示查询 | 列表展示、筛选、排序、详情查看 | 表单定义、台账定义 |
| 数据采集 | 外部数据接入、批量导入、接口同步 | 指标定义、台账定义 |
| 指标计算 | 公式计算、聚合运算、周期计算 | 指标定义 |
| 分析预警 | 阈值判断、异常检测、预警生成 | 指标定义 |
| 计划编制 | 计划创建、任务分解、资源分配 | 计划定义 |
| 进度追踪 | 执行反馈、进度汇总、偏差分析 | 计划定义 |
| 授权审批 | 权限控制、审批节点、签名确认 | 定义通用 |
| 协同交互 | 跨角色通知、待办转办、共享协作 | 定义通用 |

### 4.2 按业务定义类型/引擎域的推荐 ③ 类

#### 流程定义（索引）

```
④ 采购审批流转功能 ─→ ③ 定义配置 / 规则判定 / 流程编排 / 状态跟踪 / 通知触发
```

- ③ 定义配置：流程定义的结构配置（节点、流向、角色）
- ③ 规则判定：审批条件、自动路由、决策规则
- ③ 流程编排：多步骤编排、条件分支、并行处理
- ③ 状态跟踪：流程实例状态、当前节点、处理记录
- ③ 通知触发：待办通知、超时提醒、事件通知

#### 表单定义（索引）

- ③ 结构定义：表单字段定义、布局结构、关联关系
- ③ 字段校验：必填检查、数据格式、业务规则
- ③ 录入提交：数据创建、编辑、保存、提交流程
- ③ 展示查询：表单列表、详情查看、搜索筛选

#### 指标定义（索引）

- ③ 指标定义配置：指标名称、口径、维度、周期
- ③ 数据采集：数据源接入、数据加载、接口获取
- ③ 指标计算：公式计算、聚合运算、趋势计算
- ③ 分析预警：阈值判断、异常检测、预警推送

#### 工单定义（索引）

- ③ 定义配置：工单模板、字段配置、流转规则
- ③ 任务分派：自动派工、抢单、指定责任人
- ③ 状态跟踪：工单状态推进、处理记录、回退
- ③ 通知触发：新工单通知、超时催办、完成通知

#### 计划定义（索引）

- ③ 计划编制：计划创建、任务分解、资源分配
- ③ 进度追踪：执行反馈、进度上报、偏差分析
- ③ 监控预警：进度延迟提醒、资源冲突预警
- ③ 指标统计：计划完成率、资源利用率统计

### 4.3 桶清单的使用方式

1. **优先选择**：对要聚类的 ④ 系统用例功能，先按 §4.0 定 ② 簇归属，再按 §4.1 的通用 ③ 类找匹配。
2. **按业务定义类型/引擎域特化**：若通用 ③ 类不够精确，按 §4.2 查找对应索引下的推荐 ③ 类。
3. **可新增 ③ 类**：当通用与推荐均无法覆盖时，允许新增，但必须：
   - 写明类名与系统职责描述（可写成一句统一定义，见原则 4）
   - 确保该类名在同类业务定义类型/引擎域下可复用
   - 经人类审阅确认后再纳入

## 五、冲突裁定规则

### 5.1 多归属冲突

当一个 ④ 系统用例功能同时匹配多个候选 ③ 类时：

| 冲突类型 | 裁定规则 | 示例 |
|---------|---------|------|
| 执行类 vs 管理类 | 取**执行类**为主职责 | "审批流转"既像"授权审批"又像"流程编排"——以执行流程编排为主 |
| 配置类 vs 运行类 | 取**运行类**为主职责 | "表单录入"既涉及"结构定义"又涉及"录入提交"——以录入提交为主 |
| 计算类 vs 展示类 | 取**计算类**为主职责 | "指标计算"同时需要"数据采集"和"结果展示"——以数据采集和计算为主 |
| 业务类 vs 支撑类 | 取**业务类**为主职责 | "通知触发"既像"协同交互"又像流程定义下的"通知触发"——按业务定义类型/引擎域的推荐类为准 |

### 5.2 通用裁定流程

按以下优先级裁定：

1. **看主功能**——该 ④ 在系统中**主要**做什么处理？
2. **看对应业务定义类型/引擎域的推荐 ③ 类**——§4.2 优先于 §4.1
3. **看 pa-eng 承接方向**——该功能未来大概率进入哪个 pa-eng 组件？按 pa-eng 归属裁定
4. **仍不确定时**——以"该类下是否已有一句统一定义"为最终标准：能写通统一节点定义的类才是正确归属

### 5.3 命名冲突

不同 ② 簇/不同业务定义类型下可出现同名 ③ 类（例如"定义配置"出现在流程、表单、指标各处）——允许，路径不同。同一 ③ 类下不得有两个同语义子类；同一 ② 簇下出现两个同名 ③ 类，说明粒度冲突，应合并或换更精确的类名。
