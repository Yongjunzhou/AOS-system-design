# SR-F(A1) → PA · 引擎前后端组件设计
**Skill ID**: wft05-eng-sr2pa

> **概述**：接收引擎操作页面 SR-F，经前置校验、材料加载和反馈处理后，将操作页面、操作活动、操作页面组件/构件、NFR 约束和 CU 追溯展开为 PA 前后端组件方案。该 PA 以“前后端组件”为末级节点，回答“为了支撑这些操作页面、页面组件、构件和操作活动，需要哪些前端组件、后端组件及其架构关系”。
>
> **输入 → 输出**：SR-F 操作页面节点（`待产品架构` / `待补充PA设计`）/ 有反馈或退回的 PA 节点 → PA 前后端组件方案 + SR 详细定义 + SR-F 推进为 `已产品架构` + PA 组件进入 `待追溯验证`
>
> **适用场景**：瀑布式系统设计第5步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v4.6 | **修订**：2026-07-09

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于开发方——「能开工」。把已确认的引擎操作页面 SR-F 翻译为可实现、可追溯、可验证的前后端组件方案——不仅推断前端容器/构件和后端服务/处理组件，更定义组件间的平台架构归属、依赖关系和 NFR 承接方式，为上游追溯验证与下游构件开发提供完整的产品架构输入。

**目标**：

1. **基于操作页面 SR 及 NFR 推断平台架构归属**——判断组件属于引擎专属、页面组件扩展、公共构件、公共平台服务或运行支撑模块，优先复用已有公共能力
2. **基于操作页面及活动推断前端组件**——从页面类型推断容器组件，从操作页面组件和构件线索推断布局、字段、按钮、右键、辅助栏、弹窗、钻取等前端组件
3. **基于操作活动推断后端组件**——从校验、保存、发布、装载、回滚、审计、运行处理等活动推断后端服务和处理组件
4. **推断前端组件架构**——定义前端组件职责、组合关系、状态管理、交互边界和复用范围
5. **推断后端组件架构与 SR 详细定义**——定义后端组件职责、服务边界、依赖关系和运行约束；将已确认的组件需求展开为可验证的 SR 详细定义条目

本 Skill 负责：

1. **接收**——接收人类选中的一批 SR-F 操作页面节点（≤5 个），校验 SR-F 状态为 `待产品架构` / `待补充PA设计`、页面、操作活动、操作页面组件/构件线索、CU 追溯和 PA 层收敛项完整；缺失时退回 wft03-eng
2. **归属**——按引擎专属/页面组件扩展/公共构件/公共平台服务/运行支撑模块五类判定每个组件的平台架构归属和复用层级，优先复用已有公共能力
3. **前端设计**——从操作页面类型、操作页面组件、构件线索和操作活动推断前端容器组件、页面组件、交互构件和状态反馈组件，定义职责边界、组合关系和 NFR 承接
4. **后端设计**——从操作活动和系统处理要求推断后端校验、保存、发布、装载、回滚、审计、运行支撑等服务组件，标注同步/异步、回滚点和任务依赖
5. **架构装配**——组织前后端组件关系、依赖链、接口边界、事件边界、状态流和错误处理，检查循环依赖和无人承接
6. **NFR 装配**——消费适用于 eng 组件的性能、安全、权限、审计、可用性、可观测性等约束，阻断型 NFR 必须改变组件边界、接口或运行机制，只写备注不得进入正式冻结
7. **SR 详细定义**——将已确认的组件需求写入 `06-*.md`，按系统职责/输入触发/系统处理/输出结果/约束与 NFR/验收口径六要素形成可验证需求条目
8. **推进**——人类确认且满足冻结条件后 SR-F → `已产品架构`，PA 组件 → `待追溯验证`
9. **回修**——接收验证或构件开发退回的 `需wft05修订` PA，按缺陷说明判定根因：组件边界/依赖/NFR/SRD 缺陷留在本 Skill 修订，页面/活动/构件线索缺失则退回 wft03-eng

本 Skill 不负责：

1. STR-E 引擎场景业务识别（→ `wft01-eng`）
2. CU 配置能力定义、CU 拆分/合并和依赖重切（→ `wft02-eng`）
3. 操作页面、页面类型、页面功能架构和操作活动设计（→ `wft03-eng`）
4. 业务功能表单或业务应用组件设计（→ biz 路径或构件开发流水线）
5. 代码实现、测试用例、数据库物理表或字段级接口协议

### 1.2 与上下游的衔接

**上游 wft03-eng**：产出操作页面 SR-F，包含页面类型、操作页面组件、构件线索、操作活动、权限/状态约束、PA 层收敛项、CU 追溯和变更声明。本 Skill 消费这些内容推导 PA 组件。若 SR-F 缺少页面、活动、构件线索或 PA 层收敛项，本 Skill 不临时补写，退回 wft03-eng。

**下游验证与构件开发**：PA 组件和 SR 详细定义经确认后进入追溯验证；验证通过后由构件开发流水线消费。若验证或开发发现 SR-F 缺陷，回退到 wft03-eng；若发现组件边界、依赖、NFR 承接或 SR 详细定义缺陷，将 PA 标记为 `需wft05修订` 并回到本 Skill 修订。

## 二、前后端组件设计基础

### 2.1 PA 组件架构

#### 2.1.1 定义与层级

PA 是 A1 平台引擎产品的产品架构，末级节点为**前后端组件**。PA 从 SR-F 操作页面、操作页面组件、构件线索和操作活动推导而来，回答”为了支撑这些操作页面和能力，需要哪些前端组件、后端组件及其架构关系”。操作页面组件与构件定义见 [91 规范 §三](91-eos-biz-eng-spec.md#三-操作页面组件与构件)，eng 路径分工见 [91 规范 §7.4](91-eos-biz-eng-spec.md#74-产品架构开发wft05-eng)。

91 规范 §3 定义了操作页面组件和构件两个上游概念，wft05-eng 的组件设计必须从它们出发，不重新定义页面需求：

- **操作页面组件**：平台 UI 的结构层次，如多级横版、列表、单据、弹窗、指标、辅助栏等。
- **构件**：安装在操作页面组件上的公共功能单元，可跨组件复用，如功能按钮、右键菜单项、快捷键绑定、列定义、字段布局、图表类型、钻取等。

#### 2.1.2 架构与属性

PA 组件的架构由三部分构成：平台架构归属（§2.2）、前后端组件类型（§2.3）、SR 详细定义（§2.5.3）。

每个 PA 组件节点至少包含（写入 `07-*.md` PA 节点块）：

- PA ID / 名称
- 来源 SR-F / 操作页面 / 操作活动 / CU 追溯
- 组件归属与组件类型
- 组件职责边界
- 承接的前端页面组件/构件或后端操作活动
- 前后端依赖关系
- 接口、事件或状态边界摘要
- NFR 承接
- SR 详细定义引用
- 23 / 25 引用
- 确认状态
- 生命周期状态

#### 2.1.3 完备性判据

**覆盖检查**：

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 页面覆盖 | 每个操作页面有前端组件承接 | 补充前端组件 |
| 活动覆盖 | 每个操作活动有前端入口和后端处理承接 | 补充组件或标注 PA 收敛 |
| 构件覆盖 | 每个构件线索有复用/扩展/新建结论 | 补充构件结论 |
| PA 收敛 | 所有 PA 层必收敛项已闭合 | 补充收敛，不推进冻结 |
| NFR 承接 | 阻断型 NFR 已改变组件边界、接口或运行机制 | 重新设计组件边界，只写备注不得冻结 |
| 依赖闭合 | 前后端组件依赖无未裁决断点 | 补充依赖或标记 `[需裁决]` |
| SRD 完整 | 每个 PA 组件有 SR 详细定义或明确无需 SRD 的理由 | 补充 SRD |

**正式冻结条件**（全部满足方可推进 PA 为 `待追溯验证`）：

1. 来源 SR-F 已确认，状态为 `待产品架构` / `待补充PA设计`。
2. 操作页面和操作活动均有唯一组件承接。
3. PA 层必收敛项已闭合。
4. 阻断型 NFR 已影响组件边界、接口或运行机制，而不只是备注。
5. 前后端依赖关系闭合，无未裁决循环依赖。
6. SR 详细定义完整、可验证。
7. 人类已确认全部 PA 条目。

不满足时只能形成阶段性 PA，不推进 SR-F 为 `已产品架构`。

### 2.2 平台架构归属

#### 2.2.1 定义与五类归属

平台架构归属判定组件的复用层级和架构位置。组件若可跨引擎复用，应优先归入公共构件或公共平台服务；若承接特定 CU 语义，则归入引擎专属组件。

| 归属 | 判定 | 典型组件 |
|------|------|----------|
| 引擎专属组件 | 只服务某个引擎或 CU 的配置/运行能力 | 流程发布服务、看板指标聚合服务 |
| 页面组件扩展 | 扩展列表、单据、弹窗、指标、辅助栏等页面组件 | 树表配置容器、配置详情辅助栏 |
| 公共构件 | 功能按钮、右键、快捷键、列定义、字段布局、图表、钻取等可复用构件 | 发布按钮、回滚按钮、引用钻取 |
| 公共平台服务 | 权限、审计、版本、发布、调度、通知等跨引擎能力 | 审计服务、版本服务、任务调度服务 |
| 运行支撑模块 | 监控、回滚、日志、错误恢复、任务执行等运行期支撑 | 运行日志模块、错误恢复模块 |

---

### 2.3 前后端组件与 NFR

#### 2.3.1 前端组件定义

前端组件承载显示、交互、页面状态和用户操作入口。

| 来源 | 前端组件类型 | 设计要点 |
|------|--------------|----------|
| 页面类型 | 列表容器、树表容器、单据容器、弹窗容器、辅助栏、指标容器 | 容器职责、状态、上下文 |
| 操作页面组件 | 筛选区、列定义、字段组、图表区、详情面板、上下文摘要 | 组件组合与复用边界 |
| 构件 | 按钮、右键菜单、快捷键、钻取、导入导出入口 | 入口、可见性、可操作性 |
| 操作活动 | 进度反馈、结果提示、错误提示、二次确认、状态刷新 | 活动体验与状态反馈 |

#### 2.3.2 后端组件定义

后端组件承载页面操作背后的校验、保存、发布、运行处理和治理能力。

| 操作活动 | 后端组件类型 | 设计要点 |
|----------|--------------|----------|
| 校验 | 配置校验、依赖校验、权限校验、冲突检查 | 校验边界、错误返回 |
| 保存 | 配置存储、版本记录、草稿管理 | 幂等、版本、一致性 |
| 发布/装载 | 发布编排、运行态生效、缓存刷新、影响范围计算 | 同步/异步、回滚点 |
| 回滚/停用 | 历史版本恢复、停用控制、回滚审计 | 安全边界、影响范围 |
| 审计/追溯 | 变更记录、操作日志、引用关系、运行日志 | 可追溯、查询性能 |
| 运行支撑 | 状态机、规则执行、调度、指标聚合、错误恢复 | 可靠性、可观测性 |

#### 2.3.3 NFR 装配

NFR 只消费适用于 `eng` 或 `共享` 的约束，并按组件类型落位：

| NFR 影响点 | 承接位置 |
|------------|----------|
| 性能/并发 | 后端发布、装载、运行支撑组件；前端状态反馈 |
| 安全/权限 | 前端可见/可操作规则；后端鉴权与权限校验 |
| 审计/追溯 | 后端审计组件；前端引用关系/日志查询入口 |
| 可用性/可靠性 | 后端重试、补偿、回滚、降级 |
| 可观测性 | 运行日志、指标、告警、追踪 |
| 兼容性/易用性 | 前端容器、构件交互、提示和校验体验 |

阻断型 NFR 必须改变组件边界、接口或运行机制；只写备注不得进入正式冻结。

### 2.4 PA 要素提取规则

Phase B（修订已有 PA）与 Phase C（新建 PA）共用以下规则。

#### 2.4.1 候选组件生成

从 SR-F 提取组件候选：

| 来源 | 生成的候选 |
|------|-----------|
| 页面类型 + 操作页面组件 | 前端容器/页面组件候选 |
| 构件线索 | 公共构件候选 |
| 操作活动 | 前端入口构件 + 后端处理组件候选 |
| PA 层收敛项 | 必须决策的组件边界、接口、存储、运行机制候选 |
| NFR | 可能改变归属或拆分的约束 |

#### 2.4.2 平台架构归属判定

按 §2.2 判断每个候选组件的归属，判定优先级：

1. 已有公共构件/公共平台服务可复用。
2. 页面组件扩展可承载。
3. 引擎专属组件承接。
4. 运行支撑模块承接。
5. 仍不明确则标记 `[需裁决]`。

#### 2.4.3 Phase B 组件匹配检查

Phase B 修订已有 PA 时，按 `组件归属 + 组件职责 + 承接对象` 匹配已有 PA 组件：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 复用 | 已有组件同归属、同职责、同承接对象，NFR 不冲突 | 复用并追加 SR-F 引用，标记 `[确认]` |
| Q2 扩展 | 已有组件主体职责一致，但需新增活动、NFR 或接口边界 | 扩展已有组件，全量重写受影响定义，输出变更声明 |
| Q3 新建 | 无可复用组件 | 新建 PA 组件 |
| 需裁决 | 组件可能公共化、拆分/合并或跨引擎归属不明 | 标记 `[需裁决]` |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 PA | Phase C 新建 PA |
|------|-------------------|-----------------|
| 判定范围 | PA 已承接的全部 SR-F + 本轮新 SR-F | 待聚合池本组 SR-F |
| 组件清单基线 | 以已有组件清单为基线，仅扫描本轮新页面/活动是否引入新组件 | 从零构建 |
| 候选生成 | 增量生成（仅新页面/活动触发） | 全量生成（§2.4.1） |
| 归属判定 | 增量判定 + 已有组件归属重检 | 全量判定（§2.4.2） |
| 组件匹配 | 执行组件匹配检查（§2.4.3），可能检出 Q1/Q2/Q3/需裁决 | 无需匹配，直接新建 |
| NFR 装配 | 增量合并新 NFR + 重检已有 NFR 承接 | 全量装配 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 组件推断规则

Phase B（修订已有 PA）与 Phase C（新建 PA）共用以下规则。

#### 2.5.1 前端组件推断

对每个操作页面：

1. 从页面类型推断容器组件。
2. 从操作页面组件推断布局、字段、辅助栏、弹窗、指标等组件。
3. 从构件线索推断按钮、右键、快捷键、列定义、图表、钻取等公共构件。
4. 从操作活动推断前端状态、进度反馈、结果提示、错误提示和二次确认。
5. 装配前端 NFR：权限可见性、易用性、可访问性、兼容性、响应时间。
6. 写明组件职责边界、复用范围、依赖关系和验收口径。

前端组件输出字段：组件名称 / 归属 / 类型 / 来源页面 / 操作活动 / 构件线索 / 职责边界 / 状态与交互 / 依赖组件 / NFR 承接 / 确认状态。

#### 2.5.2 后端组件推断

对每个操作活动：

1. 推断校验、保存、发布、装载、回滚、审计、运行支撑等后端组件。
2. 识别服务边界、事件边界、状态变化和错误处理。
3. 装配权限、安全、审计、性能、可靠性、可观测性等 NFR。
4. 保留 CU、页面、操作活动追溯。
5. 标注是否同步/异步、是否需要任务、是否需要回滚点。

后端组件输出字段：组件名称 / 归属 / 类型 / 来源活动 / 来源 CU / 页面 / 职责边界 / 服务或事件边界摘要 / 状态变化与异常处理 / 依赖组件 / NFR 承接 / 确认状态。

#### 2.5.3 SR 详细定义要素

将已确认的组件需求展开为 SR 详细定义，写入 `06-*.md`。每条 SR 详细定义至少包含：

| 要素 | 说明 |
|------|------|
| 系统职责 | 系统必须提供什么能力 |
| 输入/触发 | 页面动作、事件、状态或配置 |
| 系统处理 | 校验、保存、发布、查询、回滚等摘要 |
| 输出/结果 | 页面反馈、状态变化、记录、事件 |
| 约束与 NFR | 性能、安全、审计、可靠性等 |
| 验收口径 | 如何验证该需求被承接 |

格式模板：

```text
SRD-XXX：<组件/能力名称>
来源：SR-F-XXX / PA-XXX
系统职责：<系统必须提供什么能力>
输入/触发：<页面动作、事件、状态或配置>
系统处理：<校验、保存、发布、查询、回滚等摘要>
输出/结果：<页面反馈、状态变化、记录、事件>
约束与 NFR：<性能、安全、审计、可靠性等>
验收口径：<如何验证该需求被承接>
```

#### 2.5.4 Phase B 组件关系检测

Phase B 修订已有 PA 时，组件匹配通过后，将本轮生成的组件与 PA 已有组件清单比对。比对锚点为**组件归属+组件职责+承接对象匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 组件匹配 + 归属/职责一致 + 来源升级（SR-F 引用→新活动确认） | 追加 SR-F 引用，内部细分结论=`确认` |
| 无新增 | 组件匹配 + 归属/职责一致 + 所有来源已确认 | 增量合并新 SR-F 中的活动细节/NFR（如有新内容），内部细分结论=`改进` |
| 组件职责扩展 | 组件匹配 + 归属一致 + 新增活动、NFR 或接口边界 | 扩展已有组件，全量重写受影响定义 + 内部细分结论=`组件职责扩展` + 变更原因 |
| 归属变更 | 组件匹配 + **平台架构归属不同**（公共化或专属化） | 更新归属 + 内部细分结论=`归属变更` + 变更原因 |
| 补充 | 组件不匹配 | 新增 PA 组件，内部细分结论=`新增` |
| 过时 | 基线已有组件 **未被**本轮 SR-F 覆盖（页面/活动移除导致组件不再被需要） | 内部细分结论=`过时` + 追加说明”对应页面/活动已不再需要此组件，请确认是否移除”。保留该组件在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 SR-F 重新判定归属**——新 SR-F 可能改变组件特征导致归属变更（表中 `归属变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有组件的职责边界/接口/NFR 承接变化，在关系标记之外叠加 `[调整]`。

### 2.6 PA 节点生命周期

wft05-eng 同时管理两条生命周期线：SR-F（上游节点，本 Skill 消费并推进）和 PA（本 Skill 产出节点，分方案确认态与组件验证态）。通用模型见 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型)。

**SR-F 侧**（wft03-eng ←→ wft05-eng）：

```
待产品架构 ──wft05锁定──→ 在PA设计 ──wft05完成──→ 已产品架构
     ↑                        ↑                         │
     │                        │               wft05退回  │
     │                        │                         ↓
     └─── wft03修订 ───── 需wft03修订 ←───────────────┘
```

**PA 侧**（wft05-eng → 验证 → 构件开发）：

```
待确认方案 ──人类确认──→ 已确认方案 ──冻结──→ 待追溯验证 ──验证──→ 已验证冻结
     ↑                       ↑            │             │
     │                       │            │  验证/开发退回│
     │                       │            ↓             ↓
     └─── wft05修订 ──── 需wft05修订 ←─── 需wft05修订
```

**上游变更**（新 SR-F 汇入触发 PA 修订）：

```
已确认方案 ──新SR-F修订──→ 已确认方案（版本递增）
待追溯验证 ──新SR-F修订──→ 待追溯验证（版本递增，增量验证）
已验证冻结 ──新SR-F修订──→ 待补充方案 ──wft05补全──→ 已确认方案
```

**本 Skill 的写回范围**：PA 方案侧 `待确认方案` / `已确认方案` / `待补充方案`；PA 组件侧 `需wft05修订`。`待追溯验证` / `验证中` / `已验证冻结` / `已废弃` 由验证和构件开发流程写入和推进。

下游退回 `需wft05修订` 时：读取验证或开发的缺陷说明 → 判定根因（组件边界不清、依赖不闭合、NFR 承接不足、SRD 不可验证 → 留在本 Skill 修订；页面/活动/构件线索缺失 → 退回 wft03-eng）→ 按人类改进方案修订 PA → 人类确认 → 重新推进。

### 3.1 Step Start

运行时 AI 按以下顺序执行：

1. **输入校验**：
   - PA 状态为 `需wft05修订` 且人类未提供缺陷说明或改进方案 → 输出缺少的验证证据或开发反馈 → **退出**
   - SR-F 不是 eng 操作页面类型 → 输出类型分布，提示回到对应路径 → **退出**
   - SR-F 状态不是 `待产品架构` / `待补充PA设计` → 输出不合格节点及当前状态 → **退出**
   - SR-F 缺少页面、构件线索、操作活动、CU 追溯或 PA 收敛项中任一项 → SR-F → `需wft03修订`，输出缺失说明 → **退出**
   - 阻断型 NFR 未加载 → 输出"约束不足"提示 → 提示补充 NFR 包，必要时退出
   - 选中 SR-F >5 个 → 输出超限提示 → 人类确认后继续或退出
   - 无 SR-F 选中 + 无待处理反馈的 PA 节点 + 无 `需wft05修订` 的 PA 节点 → 输出"无待处理对象"→ **退出**
2. **退回优先**：存在 `需wft05修订` 的 PA 节点（且人类已提供缺陷说明或改进方案）→ 定位受影响 PA/SRD/SR-F，进入 Step 2 按 §3.3 根因分流表判定处理
3. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 PA 节点 → 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 SR-F，Step End 时提示
4. **新 SR-F 路由**：有未处理的 SR-F 节点 → 进入 Step 1→Step 3，逐节点执行 Phase C 组件匹配，归入已有 PA 或进入待聚合池新建

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 PA 的组件归属/组件职责/依赖关系/NFR 承接。Step 3 的 Phase C 组件匹配必须基于 Step 2 修改后的最新 PA 内容，不得使用缓存旧状态。

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：平台架构归属 + 前端组件 + 后端组件 + 依赖关系 + NFR 承接 + SR 详细定义。各条目的 `确认状态` 字段位于 `07-*.md` PA 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 SR-F 操作页面需求为锚点的方案修订。AI 在 Step 2 中与 Step 3~7 同为设计者——先理解人类反馈在操作页面需求语境中的含义，再执行修订，最后检查修订后的 PA 是否仍满足 SR-F 需求。

本 Skill 特化参数见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 实例化参数表（wft05-eng 列）。

若入口为 `需wft05修订` PA，本 Step 先按缺陷说明判定根因：

| 根因 | 处理 |

| CU 配置能力或依赖来源错误 | 退回 wft02-eng，退出本 Skill |

### 3.4 Step 3 · 平台架构归属

#### Phase A · 候选组件生成

从 SR-F 提取：

1. 页面类型和操作页面组件 → 前端容器/页面组件候选。
2. 构件线索 → 公共构件候选。
3. 操作活动 → 前端入口构件和后端处理组件候选。
4. PA 层收敛项 → 必须决策的组件边界、接口、存储、运行机制候选。
5. NFR → 可能改变归属或拆分的约束。

#### Phase B · 归属判定

按 §2.2 判断组件归属。判定优先级：

1. 已有公共构件/公共平台服务可复用。
2. 页面组件扩展可承载。
3. 引擎专属组件承接。
4. 运行支撑模块承接。
5. 仍不明确则标记 `[需裁决]`。

#### Phase C · 匹配已有 PA

按 §2.5 执行 Q1/Q2/Q3/需裁决判定。

### 3.5 Step 4 · 前端组件设计

对每个操作页面：

1. 从页面类型推断容器组件。
2. 从操作页面组件推断布局、字段、辅助栏、弹窗、指标等组件。
3. 从构件线索推断按钮、右键、快捷键、列定义、图表、钻取等公共构件。
4. 从操作活动推断前端状态、进度反馈、结果提示、错误提示和二次确认。
5. 装配前端 NFR：权限可见性、易用性、可访问性、兼容性、响应时间。
6. 写明组件职责边界、复用范围、依赖关系和验收口径。

前端组件输出字段：

- 组件名称 / 归属 / 类型
- 来源页面 / 操作活动 / 构件线索
- 职责边界
- 状态与交互
- 依赖组件
- NFR 承接
- 确认状态

### 3.6 Step 5 · 后端组件设计

对每个操作活动：

1. 推断校验、保存、发布、装载、回滚、审计、运行支撑等后端组件。
2. 识别服务边界、事件边界、状态变化和错误处理。
3. 装配权限、安全、审计、性能、可靠性、可观测性等 NFR。
4. 保留 CU、页面、操作活动追溯。
5. 标注是否同步/异步、是否需要任务、是否需要回滚点。

后端组件输出字段：

- 组件名称 / 归属 / 类型
- 来源活动 / 来源 CU / 页面
- 职责边界
- 服务或事件边界摘要
- 状态变化与异常处理
- 依赖组件
- NFR 承接
- 确认状态

### 3.7 Step 6 · 组件架构与 SR 详细定义

#### 3.7.1 组件架构

1. 组织前端组件架构：页面容器、公共构件、状态管理、交互依赖。
2. 组织后端组件架构：服务边界、数据/事件流、运行支撑依赖。
3. 建立前后端协作关系：页面动作 → 后端服务 → 状态/结果反馈。
4. 标记共享组件、专属组件和运行支撑组件。
5. 检查循环依赖、重复承接和无人承接。

#### 3.7.2 SR 详细定义

```text
系统处理：<校验、保存、发布、查询、回滚等摘要>
输出/结果：<页面反馈、状态变化、记录、事件>
约束与 NFR：<性能、安全、审计、可靠性等>

```

### 3.8 Step 7 · 闭环检查与冻结判定

检查：

| 检查项 | 判据 |
|--------|------|
| 页面覆盖 | 每个操作页面有前端组件承接 |
| 活动覆盖 | 每个操作活动有前端入口和后端处理承接 |
| 构件覆盖 | 每个构件线索有复用/扩展/新建结论 |
| PA 收敛 | 所有 PA 层必收敛项已闭合 |
| NFR 承接 | 阻断型 NFR 已改变组件边界、接口或运行机制 |
| 依赖闭合 | 前后端组件依赖无未裁决断点 |
| SRD 完整 | 每个 PA 组件有 SR 详细定义或明确无需 SRD 的理由 |

结论：

| 结论 | 条件 | 状态动作 |
|------|------|----------|
| 正式 PA | 全部检查通过 + 人类确认 | SR-F → `已产品架构`，PA → `待追溯验证` |
| 阶段性 PA | 有未确认 25 模型、可延后收敛项或非阻断缺口 | 保持待确认/待补充，不进入冻结 |
| 退回 wft03 | 页面、活动、构件线索或 PA 收敛项缺失 | SR-F → `需wft03修订` |
| 退回本 Skill | 验证或开发发现组件边界、依赖、NFR 或 SRD 缺陷 | PA → `需wft05修订` |
| 待裁决 | 组件公共化、拆分合并、阻断 NFR 承接存在架构判断 | 保持 `待确认方案` |

### 3.9 Step 8 · 资产写回与落账

仅对已确认且满足正式冻结条件的 PA 执行。这里的“已确认”对应 PA 方案确认态，写回后 PA 组件进入验证态：

1. `07`：写入 PA 组件方案，PA 组件 → `待追溯验证`。
2. `06`：写入 SR 详细定义。
3. `05`：SR-F → `已产品架构`，记录消费版本。
4. `23`：更新 A1 产品组件索引。
5. `25`：更新引擎/CU/构件引用，不反向改写未确认模型。

阶段性 PA 只写待办和缺口，不推进 SR-F 为 `已产品架构`。

### 3.10 Step End · 运行结束输出

遵循 [91 规范 §8.8](91-eos-biz-eng-spec.md#88-skill-通用约定) 的三区模板。

```text
当前状态：<待确认方案 / 已产品架构 / 阶段性PA>
  PA：新增/修订前端组件 <N> 个、后端组件 <N> 个；SR 详细定义 <N> 条；待裁决 <N> 项。

一、方案反馈
  A. 整体确认 -> 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 -> 在确认状态中标注 [修改]：...
  C. 驳回重做 -> 在确认状态中标注 [驳回]：...

二、下一步
  本Skill -> 存在未处理反馈 / 新 SR-F / 待补充PA设计 / 需wft05修订 PA 时重入
  后续    -> PA 组件进入追溯验证；验证通过后进入构件开发流水线
```
