# SR-F(A1) + NFR 约束包 → PA · 引擎三类组件设计
**Skill ID**: wft05-eng-sr2pa

> **概述**：接收 SR-F 构件清单和 wft05-eng NFR 约束包，将构件展开为 PA 组件需求定义。PA 末级节点包含前端组件、后端组件、平台服务组件三类；同时消费 NFR 形成部署、通信、数据、安全四类平台架构决策。
>
> **输入 → 输出**：SR-F 构件清单（`待产品架构` / `待补充PA设计`）+ wft05-eng NFR 约束包 / 有反馈或退回的 PA 节点 → 三类 PA 组件需求定义 + 四类平台架构决策 + SR 详细定义 + PA 组件进入 `待追溯验证`
>
> **适用场景**：瀑布式系统设计第5步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v6.0 | **修订**：2026-07-12 | **说明**：依据 91 规范 v4.8 增加平台服务组件、NFR 约束包版本消费和部署/通信/数据/安全架构决策

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于开发方——「能开工」。把已确认的构件 SR-F 和 NFR 约束翻译为可实现、可追溯、可验证的三类 PA 组件需求及平台架构决策，不预设具体技术栈。

**目标**：

1. **加载并映射 NFR 约束包**——首次消费全量加载，版本递增时按变更声明处理增量/修订；逐约束行映射到 CU、PA 组件或平台级决策
2. **基于构件推断前端组件**——从构件类型和操作页面组件推断容器组件、布局、字段、按钮、右键、辅助栏、弹窗、钻取等前端组件
3. **基于操作活动推断后端组件**——从操作活动（校验/保存/发布/装载/回滚/审计）推断后端服务和处理组件
4. **推断前端组件架构**——定义前端组件职责、组合关系、状态管理、交互边界和复用范围
5. **推断后端组件架构与 SR 详细定义**——定义后端组件职责、服务边界、依赖关系和运行约束
6. **制定平台架构并推断平台服务组件**——形成部署、通信、数据、安全架构决策，推断承接全局/共享/业务域约束的平台服务组件
7. **展开 SR 详细定义**——将三类组件需求展开为可验证条目

本 Skill 负责：

1. **接收**——接收 SR-F 构件清单和 wft05-eng NFR 约束包，校验状态、消费版本、构件清单和变更声明
2. **归属**——按引擎专属/公共构件/公共平台服务/运行支撑模块四类判定每个构件的实现组件归属和复用层级，优先复用已有公共能力
3. **前端设计**——从构件类型和操作页面组件推断前端容器组件、页面组件、交互构件和状态反馈组件，定义职责边界、组合关系和 NFR 承接
4. **后端设计**——从操作活动和系统处理要求推断后端校验、保存、发布、装载、回滚、审计、运行支撑等服务组件
5. **NFR 映射与平台架构决策**——逐约束行判定范围和消费对象，形成部署/通信/数据/安全决策
6. **平台服务组件设计**——定义职责、来源约束行、实现策略、依赖和消费方
7. **架构装配与 SR 详细定义**——组织三类组件依赖并形成可验证需求条目
8. **推进**——人类确认且满足冻结条件后 PA 组件 → `待追溯验证`
9. **回修**——组件/NFR/平台架构缺陷留在本 Skill；构件缺失退回 wft03-eng；约束包缺陷退回 wft04-nfr

本 Skill 不负责：

1. STR-E 引擎场景业务识别（→ `wft01-eng`）
2. CU IPO 定义和操作页面设计（→ `wft02-eng`）
3. 构件识别、页面功能架构和操作活动设计（→ `wft03-eng`）
4. 业务功能表单或业务应用组件设计（→ biz 路径或构件开发流水线）
5. 代码实现、测试用例、数据库物理表或字段级接口协议

### 1.2 与上下游的衔接

**上游 wft03-eng**：产出操作页面 SR-F，包含构件清单、操作活动、页面功能架构、PA 层收敛项和 CU 追溯。本 Skill 消费构件清单推导前后端组件。若 SR-F 缺少构件或操作活动，退回 wft03-eng。

**下游验证与构件开发**：PA 组件和 SR 详细定义经确认后进入追溯验证；验证通过后由构件开发流水线消费。若验证或开发发现构件缺陷，回退到 wft03-eng；若发现组件边界、依赖、NFR 承接或 SR 详细定义缺陷，将 PA 标记为 `需wft05修订` 并回到本 Skill 修订。

## 二、三类 PA 组件与平台架构设计基础

### 2.1 PA 组件架构

#### 2.1.1 定义与层级

PA 是 A1 平台引擎产品的产品架构，末级节点为**前端组件、后端组件、平台服务组件**。PA 从 SR-F 构件清单和 NFR 约束包推导，回答各构件由什么组件承接、横切质量约束由什么平台能力保障。操作页面组件与构件定义见 [91 规范 §四](91-eos-biz-eng-spec.md#四操作页面组件与构件)，eng 路径分工见 [91 规范 §8.4](91-eos-biz-eng-spec.md#84-产品架构开发wft05-eng)。

91 规范 §3 定义了操作页面组件和构件两个上游概念，wft05-eng 的组件设计必须从它们出发，不重新定义页面需求：

- **操作页面组件**：平台 UI 的结构层次，如多级横版、列表、单据、弹窗、指标、辅助栏等。
- **构件**：安装在操作页面组件上的公共功能单元，可跨组件复用，如功能按钮、右键菜单项、快捷键绑定、列定义、字段布局、图表类型、钻取等。

#### 2.1.2 架构与属性

PA 组件架构由三类组件、四类平台架构决策、组件依赖和 SR 详细定义构成。

每个 PA 组件节点至少包含（写入 `07-*.md` PA 节点块）：

- PA ID / 名称
- 来源 SR-F / 操作页面 / 操作活动 / CU 追溯
- 组件归属与组件类型
- 组件职责边界
- 组件类型（前端/后端/平台服务）及所承接的构件、活动或 NFR 约束行
- 前后端依赖关系
- 接口、事件或状态边界摘要
- NFR 约束行 ID、实现策略与消费版本
- SR 详细定义引用
- 23 / 25 引用
- 确认状态
- 生命周期状态

#### 2.1.3 完备性判据

**覆盖检查**：

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 页面覆盖 | 每个操作页面有前端组件承接 | 补充前端组件 |
| 活动覆盖 | 每个操作活动有前端入口和后端处理承接 | 补充组件或标注 PA 收敛 |
| 构件覆盖 | 每个构件线索有复用/扩展/新建结论 | 补充构件结论 |
| PA 收敛 | 所有 PA 层必收敛项已闭合 | 补充收敛，不推进冻结 |
| NFR 承接 | 阻断型 NFR 已改变组件边界、接口或运行机制 | 重新设计组件边界，只写备注不得冻结 |
| 依赖闭合 | 三类组件依赖无未裁决断点 | 补充依赖或标记 `[需裁决]` |
| 平台服务覆盖 | 全局/共享/业务域级约束均有平台服务组件或平台架构决策承接 | 补充平台服务组件 |
| SRD 完整 | 每个 PA 组件有 SR 详细定义或明确无需 SRD 的理由 | 补充 SRD |

**正式冻结条件**（全部满足方可推进 PA 为 `待追溯验证`）：

1. 来源 SR-F 已确认，状态为 `待产品架构` / `待补充PA设计`。
2. 操作页面、构件和操作活动均有组件承接。
3. PA 层必收敛项已闭合。
4. 阻断型 NFR 已影响组件边界、接口或运行机制，而不只是备注。
5. 三类组件依赖关系闭合，无未裁决循环依赖。
6. SR 详细定义完整、可验证。
7. 人类已确认全部 PA 条目。

不满足时只能形成阶段性 PA，不推进 SR-F 为 `已产品架构`。

### 2.2 平台架构归属

#### 2.2.1 定义与五类归属

平台架构归属判定组件的复用层级和架构位置。组件若可跨引擎复用，应优先归入公共构件或公共平台服务；若承接特定 CU 语义，则归入引擎专属组件。

| 归属 | 判定 | 典型组件 |
|------|------|----------|
| 引擎专属组件 | 只服务某个引擎或 CU 的配置/运行能力 | 流程发布服务、看板指标聚合服务 |
| 页面组件扩展 | 扩展列表、单据、弹窗、指标、辅助栏等页面组件 | 树表配置容器、配置详情辅助栏 |
| 公共构件 | 功能按钮、右键、快捷键、列定义、字段布局、图表、钻取等可复用构件 | 发布按钮、回滚按钮、引用钻取 |
| 公共平台服务 | 权限、审计、版本、发布、调度、通知等跨引擎能力 | 审计服务、版本服务、任务调度服务 |
| 运行支撑模块 | 监控、回滚、日志、错误恢复、任务执行等运行期支撑 | 运行日志模块、错误恢复模块 |

### 2.3 三类组件与 NFR

#### 2.3.1 前端组件定义

前端组件承载显示、交互、页面状态和用户操作入口。

| 来源 | 前端组件类型 | 设计要点 |
|------|--------------|----------|
| 页面类型 | 列表容器、树表容器、单据容器、弹窗容器、辅助栏、指标容器 | 容器职责、状态、上下文 |
| 操作页面组件 | 筛选区、列定义、字段组、图表区、详情面板、上下文摘要 | 组件组合与复用边界 |
| 构件 | 按钮、右键菜单、快捷键、钻取、导入导出入口 | 入口、可见性、可操作性 |
| 操作活动 | 进度反馈、结果提示、错误提示、二次确认、状态刷新 | 活动体验与状态反馈 |

#### 2.3.2 后端组件定义

后端组件承载页面操作背后的校验、保存、发布、运行处理和治理能力。

| 操作活动 | 后端组件类型 | 设计要点 |
|----------|--------------|----------|
| 校验 | 配置校验、依赖校验、权限校验、冲突检查 | 校验边界、错误返回 |
| 保存 | 配置存储、版本记录、草稿管理 | 幂等、版本、一致性 |
| 发布/装载 | 发布编排、运行态生效、缓存刷新、影响范围计算 | 同步/异步、回滚点 |
| 回滚/停用 | 历史版本恢复、停用控制、回滚审计 | 安全边界、影响范围 |
| 审计/追溯 | 变更记录、操作日志、引用关系、运行日志 | 可追溯、查询性能 |
| 运行支撑 | 状态机、规则执行、调度、指标聚合、错误恢复 | 可靠性、可观测性 |

#### 2.3.3 NFR 装配

NFR 仅从 wft04-nfr 产出的 wft05-eng NFR 约束包消费。首次消费全量加载；包版本递增时按变更影响声明处理增量、修订或结构型变化。每条约束保留约束行 ID、消费版本、范围和目标对象。

| NFR 影响点 | 承接位置 |
|------------|----------|
| 性能/并发 | 后端发布、装载、运行支撑组件；前端状态反馈 |
| 安全/权限 | 前端可见/可操作规则；后端鉴权与权限校验 |
| 审计/追溯 | 后端审计组件；前端引用关系/日志查询入口 |
| 可用性/可靠性 | 后端重试、补偿、回滚、降级 |
| 可观测性 | 运行日志、指标、告警、追踪 |
| 兼容性/易用性 | 前端容器、构件交互、提示和校验体验 |

阻断型 NFR 必须改变组件边界、接口或运行机制；只写备注不得进入正式冻结。

#### 2.3.4 平台服务组件与四类平台架构

平台服务组件承接全局、共享和业务域级 NFR，是与前端组件、后端组件并列的第三类 PA 末级节点。每个组件至少定义：组件名称、职责、来源 NFR 约束行 ID、实现策略（自研/外购/云服务）、依赖组件、消费方、验收口径。

NFR 映射必须形成四类平台架构决策：

| 架构 | 决策内容 |
|------|----------|
| 部署架构 | 节点、集群、扩缩容、容灾与故障域 |
| 通信架构 | 协议、同步/异步、消息、超时、重试与幂等 |
| 数据架构 | 持久化、缓存、一致性、备份恢复、数据生命周期 |
| 安全架构 | 身份、权限、加密、审计、密钥与边界防护 |

### 2.4 PA 要素提取规则

Phase B（修订已有 PA）与 Phase C（新建 PA）共用以下规则。

#### 2.4.1 候选组件生成

从 SR-F 提取组件候选：

| 来源 | 生成的候选 |
|------|-----------|
| 页面类型 + 操作页面组件 | 前端容器/页面组件候选 |
| 构件线索 | 公共构件候选 |
| 操作活动 | 前端入口构件 + 后端处理组件候选 |
| PA 层收敛项 | 必须决策的组件边界、接口、存储、运行机制候选 |
| NFR | 可能改变归属或拆分的约束 |

#### 2.4.2 平台架构归属判定

按 §2.2 判断每个候选组件的归属，判定优先级：

1. 已有公共构件/公共平台服务可复用。
2. 页面组件扩展可承载。
3. 引擎专属组件承接。
4. 运行支撑模块承接。
5. 仍不明确则标记 `[需裁决]`。

#### 2.4.3 Phase B 组件匹配检查

Phase B 修订已有 PA 时，按 `组件归属 + 组件职责 + 承接对象` 匹配已有 PA 组件：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 复用 | 已有组件同归属、同职责、同承接对象，NFR 不冲突 | 复用并追加 SR-F 引用，标记 `[确认]` |
| Q2 扩展 | 已有组件主体职责一致，但需新增活动、NFR 或接口边界 | 扩展已有组件，全量重写受影响定义，输出变更声明 |
| Q3 新建 | 无可复用组件 | 新建 PA 组件 |
| 需裁决 | 组件可能公共化、拆分/合并或跨引擎归属不明 | 标记 `[需裁决]` |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 PA | Phase C 新建 PA |
|------|-------------------|-----------------|
| 判定范围 | PA 已承接的全部 SR-F + 本轮新 SR-F | 待聚合池本组 SR-F |
| 组件清单基线 | 以已有组件清单为基线，仅扫描本轮新页面/活动是否引入新组件 | 从零构建 |
| 候选生成 | 增量生成（仅新页面/活动触发） | 全量生成（§2.4.1） |
| 归属判定 | 增量判定 + 已有组件归属重检 | 全量判定（§2.4.2） |
| 组件匹配 | 执行组件匹配检查（§2.4.3），可能检出 Q1/Q2/Q3/需裁决 | 无需匹配，直接新建 |
| NFR 装配 | 增量合并新 NFR + 重检已有 NFR 承接 | 全量装配 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 组件推断规则

Phase B（修订已有 PA）与 Phase C（新建 PA）共用以下规则。

#### 2.5.1 前端组件推断

对每个操作页面：

1. 从页面类型推断容器组件。
2. 从操作页面组件推断布局、字段、辅助栏、弹窗、指标等组件。
3. 从构件线索推断按钮、右键、快捷键、列定义、图表、钻取等公共构件。
4. 从操作活动推断前端状态、进度反馈、结果提示、错误提示和二次确认。
5. 装配前端 NFR：权限可见性、易用性、可访问性、兼容性、响应时间。
6. 写明组件职责边界、复用范围、依赖关系和验收口径。

前端组件输出字段：组件名称 / 归属 / 类型 / 来源页面 / 操作活动 / 构件线索 / 职责边界 / 状态与交互 / 依赖组件 / NFR 承接 / 确认状态。

#### 2.5.2 后端组件推断

对每个操作活动：

1. 推断校验、保存、发布、装载、回滚、审计、运行支撑等后端组件。
2. 识别服务边界、事件边界、状态变化和错误处理。
3. 装配权限、安全、审计、性能、可靠性、可观测性等 NFR。
4. 保留 CU、页面、操作活动追溯。
5. 标注是否同步/异步、是否需要任务、是否需要回滚点。

后端组件输出字段：组件名称 / 归属 / 类型 / 来源活动 / 来源 CU / 页面 / 职责边界 / 服务或事件边界摘要 / 状态变化与异常处理 / 依赖组件 / NFR 承接 / 确认状态。

#### 2.5.3 SR 详细定义要素

将已确认的组件需求展开为 SR 详细定义，写入 `06-*.md`。每条 SR 详细定义至少包含：

| 要素 | 说明 |
|------|------|
| 系统职责 | 系统必须提供什么能力 |
| 输入/触发 | 页面动作、事件、状态或配置 |
| 系统处理 | 校验、保存、发布、查询、回滚等摘要 |
| 输出/结果 | 页面反馈、状态变化、记录、事件 |
| 约束与 NFR | 性能、安全、审计、可靠性等 |
| 验收口径 | 如何验证该需求被承接 |

格式模板：

```text

```

#### 2.5.4 Phase B 组件关系检测

Phase B 修订已有 PA 时，组件匹配通过后，将本轮生成的组件与 PA 已有组件清单比对。比对锚点为**组件归属+组件职责+承接对象匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 组件匹配 + 归属/职责一致 + 来源升级（SR-F 引用→新活动确认） | 追加 SR-F 引用，内部细分结论=`确认` |
| 无新增 | 组件匹配 + 归属/职责一致 + 所有来源已确认 | 增量合并新 SR-F 中的活动细节/NFR（如有新内容），内部细分结论=`改进` |
| 组件职责扩展 | 组件匹配 + 归属一致 + 新增活动、NFR 或接口边界 | 扩展已有组件，全量重写受影响定义 + 内部细分结论=`组件职责扩展` + 变更原因 |
| 归属变更 | 组件匹配 + **平台架构归属不同**（公共化或专属化） | 更新归属 + 内部细分结论=`归属变更` + 变更原因 |
| 补充 | 组件不匹配 | 新增 PA 组件，内部细分结论=`新增` |
| 过时 | 基线已有组件 **未被**本轮 SR-F 覆盖（页面/活动移除导致组件不再被需要） | 内部细分结论=`过时` + 追加说明”对应页面/活动已不再需要此组件，请确认是否移除”。保留该组件在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 SR-F 重新判定归属**——新 SR-F 可能改变组件特征导致归属变更（表中 `归属变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有组件的职责边界/接口/NFR 承接变化，在关系标记之外叠加 `[调整]`。

### 2.6 PA 节点生命周期

wft05-eng 同时管理两条生命周期线：SR-F（上游节点，本 Skill 消费并推进）和 PA（本 Skill 产出节点，分方案确认态与组件验证态）。通用模型见 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型)。

**SR-F 侧**（wft03-eng ←→ wft05-eng）：

```
待产品架构 ──wft05锁定──→ 在PA设计 ──wft05完成──→ 已产品架构
     ↑                        ↑                         │
     │                        │               wft05退回  │
     │                        │                         ↓
     └─── wft03修订 ───── 需wft03修订 ←───────────────┘
```

**PA 侧**（wft05-eng → 验证 → 构件开发）：

```
待确认方案 ──人类确认──→ 已确认方案 ──冻结──→ 待追溯验证 ──验证──→ 已验证冻结
     ↑                       ↑            │             │
     │                       │            │  验证/开发退回│
     │                       │            ↓             ↓
     └─── wft05修订 ──── 需wft05修订 ←─── 需wft05修订
```

**上游变更**（新 SR-F 汇入触发 PA 修订）：

```
已确认方案 ──新SR-F修订──→ 已确认方案（版本递增）
待追溯验证 ──新SR-F修订──→ 待追溯验证（版本递增，增量验证）
已验证冻结 ──新SR-F修订──→ 待补充方案 ──wft05补全──→ 已确认方案
```

**本 Skill 的写回范围**：PA 方案侧 `待确认方案` / `已确认方案` / `待补充方案`；PA 组件侧 `需wft05修订`。`待追溯验证` / `验证中` / `已验证冻结` / `已废弃` 由验证和构件开发流程写入和推进。

下游退回 `需wft05修订` 时：读取验证或开发的缺陷说明 → 判定根因（组件边界不清、依赖不闭合、NFR 承接不足、SRD 不可验证 → 留在本 Skill 修订；页面/活动/构件线索缺失 → 退回 wft03-eng）→ 按人类改进方案修订 PA → 人类确认 → 重新推进。

### 3.1 Step Start

#### 3.1.1 入口检测

读取产品数据文档中的 `## AI可以处理节点` 对应分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口条件：

| # | 入口条件 | 检测方式 | 对应分节 |
|---|---------|---------|---------|
| ① | **有新输入** | AI可以处理节点「待 wft05-eng 处理」分节非空 | §11.7 |
| ② | **有待处理反馈** | AI可以处理节点「待反馈处理」分节含本 Skill 产出节点 | §11.7 |
| ③ | **有下游退回节点** | AI可以处理节点「待下游退回处理」分节含状态为 `需wft05修订` 的节点 | §11.7 |

**退回门禁**（满足条件③时）：检查退回节点的缺失说明中是否包含人类改进方案（人类标注 `[修改]`/`[同意]` 或下游 Skill/验证流程产出的具体改进指引）。已提供 → 通过门禁。未提供 → 输出缺失说明 + 提示提供改进方案 → **退出**。

#### 3.1.2 输入校验

入口检测通过后进行输入校验。以下校验中逻辑上不可能的条件为硬退出，NFR/数量条件为软提示：

| 校验条件 | 判定 | 类型 |
|---------|------|------|
| SR-F 不是 eng 操作页面类型 | 输出类型分布，提示回到对应路径 → **退出** | 硬退出 |
| SR-F 状态不是 `待产品架构` / `待补充PA设计` | 输出不合格节点及当前状态 → **退出** | 硬退出 |
| SR-F 缺少页面、构件线索、操作活动、CU 追溯或 PA 收敛项中任一项 | SR-F → `需wft03修订`，输出缺失说明 → **退出** | 硬退出 |

| 约束包存在待确认行但不影响当前组件 | 列出待确认行及影响范围 → 人类确认后继续或退出 | 软提示 |
| 选中 SR-F >5 个 | 输出超限提示 → 人类确认后继续或退出 | 软提示 |

#### 3.1.3 分流处理

按 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序) 定义的优先顺序执行（退回优先 → 反馈处理 → 新输入路由）：

1. **退回优先**：存在 `需wft05修订` 的 PA 节点（且门禁通过）→ 定位受影响 PA/SRD/SR-F，进入 Step 2 按 §3.3.1 根因分流表判定处理
2. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 PA 节点 → 进入 Step 2 处理（§3.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 SR-F，Step End 时提示
3. **新 SR-F 路由**：有未处理的 SR-F 节点 → 进入 Step 1→Step 3，逐节点执行 Phase A 宿主匹配（§3.4.1），归入已有 PA 或进入待聚合池新建

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 PA 的组件归属/组件职责/依赖关系/NFR 承接。Step 3 的 Phase A 组件匹配必须基于 Step 2 修改后的最新 PA 内容，不得使用缓存旧状态。

3. 无变更 → 进入优先读取
   有变更 → 解析变更行号，读取变更行附近的节点块（上下 5 行）

- 有待处理反馈 → 读「待反馈处理」分节
- 有下游退回 → 读「待下游退回处理」分节

逐节点：Bash("grep -n '@{节点ID}' 目标文件") 定位行号 → Read 节点块。

**索引导航**（AI可以处理节点无待处理时，或按域浏览时）：

1. Bash("grep -n '索引行数：' 目标文件") → 定位索引行号 L
2. 从 L 提取 N → Read 业务域索引
3. 按锚点 Read 域内索引 → 获取节点 ID 列表
4. 按需：Bash("grep -n '@{节点ID}' 目标文件") → 定位行号 → Read 节点

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：平台架构归属 + 前端组件 + 后端组件 + 依赖关系 + NFR 承接 + SR 详细定义。各条目的 `确认状态` 字段位于 `07-*.md` PA 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 SR-F 操作页面需求为锚点的方案修订。AI 在 Step 2 中与 Step 3~7 同为设计者——先理解人类反馈在操作页面需求语境中的含义，再执行修订，最后检查修订后的 PA 是否仍满足 SR-F 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 SR-F 操作页面构件清单和操作活动——反馈处理以构件→组件映射需求为锚，不脱离 SR-F 内容自行修订 |
| **操作条目** | 平台架构归属 + 前端组件 + 后端组件 + 依赖关系 + NFR 承接 + SR 详细定义。各条目的 `确认状态` 字段写入 `07-*.md` PA 节点的对应条目中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` + 满足正式冻结条件 → PA → `待追溯验证`，SR-F → `已产品架构`。存在未闭合项 → 保持待确认态 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过扫描。仅当本轮新输入满足以下任一条件时，清除 `[已处理]`（保留 `[同意]`）使其回到待处理：（1）新输入为该条目的直接上游节点（如新 SR-F 节点是 PA 组件的来源）；（2）新输入与条目同属一个架构层级且边界重叠（如同属前端组件，新组件改变了已有组件的职责或归属）；（3）新输入导致条目定义被修订（变更影响声明标注为修订型或结构型，§A.5.3 Step 1） |
| **级联触发条件** | 平台架构归属变更、组件新增/删除/职责扩展、依赖关系重组、阻断型 NFR 边界变化 → 触发需求级联检查（重验修改后 PA 是否仍满足 SR-F 操作页面和构件需求）→ 通过后触发资产对齐级联 |
| **资产对齐级联** | 方案变更影响 23/25 资产时，更新对齐结论——组件新增 → 更新 23 组件索引；CU/构件引用变更 → 更新 25 引用。资产映射由 Step 8 维护 |

若入口为 `需wft05修订` PA，本 Step 先按缺陷说明判定根因：

| 根因 | 处理 |

### 3.4 Step 3 · NFR 约束映射与平台架构决策

先加载 wft05-eng NFR 约束包并按消费版本分流：首次消费全量加载；版本递增时读取变更影响声明，仅处理新增、修订或结构型影响行。逐约束行判定约束范围和消费目标：

- 操作页面/SR-F 约束 → 对应前端、后端组件及交互边界。

输出部署、通信、数据、安全四类平台架构决策，并记录每项决策承接的 NFR 约束行 ID。完成约束映射后，再执行组件归属与候选匹配。

#### 3.4.1 Phase A：候选组件生成与宿主匹配

|------|------|
| 组件归属 + 组件职责 + 承接对象落入已有 PA 组件 | 归入该 PA → Phase B |
| 不满足 | 进入待聚合池 → Phase C |
| 组件可能公共化、拆分/合并或跨引擎归属不明 | 标记 `[需裁决]` |

待聚合池按**同一归属 + 同一承接对象类型**分组（`{归属, 承接对象类型, 候选组件列表}`）。此阶段仅粗略分组，归属判定和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 PA

1. **要素提取**：从本轮 SR-F 的页面/操作页面组件/构件线索/操作活动/PA 层收敛项/NFR 提取组件候选（详见 §2.4.1）。已有组件职责仅追加不重建
2. **组件匹配检查**：确认 SR-F 需求仍在 PA 组件职责范围内（详见 §2.4.3）。Q1 复用→追加 SR-F 引用；Q2 扩展→全量重写受影响定义 + 变更声明；需裁决→标记 `[需裁决]`。Phase A 匹配是候选筛选、Phase B 是精确匹配——组件职责扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决
3. **归属/组件/NFR 重判定与关系检测**：基于全部 SR-F 和当前 NFR 约束包重新判定组件归属。新增/变更前端组件、后端组件按构件和活动展开；全局/共享/业务域约束映射到平台服务组件和四类平台架构决策；所有组件保留约束行追溯
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型/返工型），写入 PA 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 PA

1. **判定平台架构归属** → 引擎专属/页面组件扩展/公共构件/公共平台服务/运行支撑模块五类（详见 §2.2、§2.4.2）。优先复用已有公共能力

3. **推断后端组件** → 校验/保存/发布/装载/回滚/审计/运行支撑 → 服务边界/事件边界/状态变化/同步异步/回滚点
4. **制定平台架构决策** → 部署/通信/数据/安全架构，每项引用来源约束行
5. **推断平台服务组件** → 职责/约束行 ID/实现策略/依赖/消费方/验收条件
6. **装配三类组件架构** → 前端组件组合 → 后端服务边界 → 平台服务依赖 → 循环依赖与无人承接检查
7. **展开 SR 详细定义并组装 PA** → 三类组件均写入 `06/07`，保留 NFR 消费版本和约束行追溯

- 待裁决（组件公共化、拆分合并、阻断 NFR 承接存在架构判断，需人类决策）：保持 `待确认方案`

**3. 要素机械检查**（逐 PA，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 七项闭环检查 **已执行**，遗漏项已标注 `[覆盖缺口]`
- [ ] 冻结判定 **已分流**，无未裁决的边界情况
- [ ] PA 版本号 **已递增**（修订时），首版为 v1

**4. 变更影响声明**

每次新建或修订 PA 后写入变更影响声明；首版写"首版，无变更"。修订时按 §2.7 判定变更类型（无变更/增量型/修订型/结构型），列出受影响组件、SRD 条目和下游验证/构件开发建议动作。格式见 §2.7。

### 3.9 Step 8 · 资产写回与落账

遵循 [91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 的统一写回协议。仅写回已确认且满足正式冻结条件的 PA 组件。不设二次确认。

**写回资产操作**：

1. `07` 写入 PA 组件方案，PA 组件 → `待追溯验证`
2. `06` 写入 SR 详细定义
3. `05` SR-F 节点写入 `SR-F 消费版本：v{N}`，状态推进为 `已产品架构`
4. `23` 更新 A1 产品组件索引
5. `25` 更新引擎/CU/构件引用，不反向改写未确认模型
6. 写入资产写回记录（日期/来源 SR-F/目标 PA 组件/动作/消费版本/下游状态）

**写回时的同步维护**（[91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 要求每次写回同时维护以下内容）：

| 操作 | 同步更新 |
|------|---------|
| 新增/修改节点 | 更新域产品索引的 `节点数`；更新 `## AI可以处理节点` 对应分节——节点状态变更时移入或移出 |
| 修改节点状态 | 更新AI可以处理节点对应分节：状态符合消费条件时加入，不符合时移出 |
| 新增/删除子条目 | 更新父节点 `**子条目状态**` 汇总值 |
| 人类标注处理 | 同步更新父节点 `**子条目状态**`（子条目标注时）和 `**确认状态**`（父节点标注时）；AI可以处理节点"待反馈处理"同步 |

**提交规范**（每次写回后必须执行）：

1. 在 `## AI最近变更` 表追加一条记录（[91 规范 §11.6](91-eos-biz-eng-spec.md#116-ai最近变更)），含时间/操作 Skill/操作类型/节点ID/变更摘要，操作类型列含 `[→](#节点ID)` 超链接
2. 更新文件头 `**文档版本**`（递增次版本号）、`**修订日期**`、`**HEAD @上次 AI 运行**`（=当前提交 hash）
3. 保留 AI最近变更最近 30 条，超出时从最旧行滚动删除
4. git add + git commit（带 Co-Authored-By: Claude）

**写回要求**：幂等去重、局部写回、全貌同步。所有操作在本 Step 内完成，不允许"本次写节点、下次更新索引"。

说明：阶段性 PA 只写待办和缺口，不推进 SR-F 为 `已产品架构`。资产写回是独立收尾，不构成下游验证或构件开发的前置条件。

### 3.10 Step End · 运行结束输出

```text
当前状态：<待确认方案 / 已确认方案 / 阶段性PA>
  本轮 PA：<PA-ID / 新建或修订 / 版本变化 / 来源 SR-F>
冻结判定：<正式冻结（SR-F→已产品架构）/ 阶段性冻结（待办 N 项）/ 未冻结>

  A. 整体确认 → 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 → 在确认状态中标注 [修改]：...
  C. 驳回重做 → 在确认状态中标注 [驳回]：...

二、下一步
  本Skill → 选择 SR-F 节点（`待产品架构` / `待补充PA设计`）或 `需wft05修订` 的 PA 节点重新运行
  后续    → PA-XXX（已确认方案）冻结后进入追溯验证 → 构件开发流水线
```
