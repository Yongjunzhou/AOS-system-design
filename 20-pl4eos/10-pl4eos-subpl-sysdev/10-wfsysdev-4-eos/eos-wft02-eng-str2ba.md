# STR-E → BA · A1 配置单元架构设计
**Skill ID**: wft02-eng-str2ba

> **概述**：接收 STR-E 引擎场景业务，经前置校验、材料加载和反馈处理后，将场景业务展开为 A1 平台引擎产品的配置单元 BA。该 BA 以 CU（配置单元）为末级节点，完成 A2 产品业务架构上下文装配、A1 引擎产品架构装配、CU 清单收敛、CU 配置能力定义、CU 依赖关系与能力缺口识别。
>
> **输入 → 输出**：STR-E 节点（`可以分解分配` / `待补充分解分配`）/ 有反馈的 BA 节点 → A1 BA 配置单元方案（A2 上下文 + A1 路径 + CU 清单 + CU 配置能力定义 + CU 依赖 + 触发追溯 + 缺口补需）+ STR-E 推进为 `已分解分配` + BA 推进为 `可以SR设计`
>
> **适用场景**：瀑布式系统设计第2步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v4.6 | **修订**：2026-07-09

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台配置方——「这个平台能力应由哪些配置单元承接，每个配置单元让配置人员配置什么、系统如何处理、运行期生成或渲染什么制品/构件/功能」。把 STR-E 引擎场景业务展开为 A1 配置单元 BA——不仅将 CU 候选收敛为可展开的配置单元清单，更定义每个 CU 的四类配置能力（配置入口/配置要素/系统处理/运行期能力）和依赖关系，为下游操作页面设计（wft03-eng）提供可展开的输入。

**目标**：

1. **装配 A2 产品业务架构**——从 STR-E 读取业务运行对象、业务场景、配置用户、治理对象、构件缺口、页面组件缺口或横切能力阶段，形成 eng 侧可追溯的 A2 上下文，服务 CU 推导且不替代业务链输出文档
2. **装配 A1 产品业务架构**——将 STR-E 归入 A1 平台引擎产品路径（流程与 IT 域 → 引擎 → CU），确定目标引擎、能力域和 A1 产品归属
3. **收敛并定义配置单元**——以 CU 为末级节点，对 STR-E 的 CU 候选执行确认/新增/扩展/拆分/合并/占位收敛判定，为每个需设计 CU 形成四类配置能力定义
4. **校验依赖与闭合性**——识别 CU 间引擎内依赖、跨引擎依赖、页面组件/构件依赖和治理依赖，确保能力链闭合且运行期能力可被 wft03-eng 消费
5. **基于 A1 补充引擎需求**——发现缺少 CU、依赖不闭合、配置能力不自洽或 25 模型不足时，形成补充 FR-ENG、25 模型建议或退回 wft01-eng

本 Skill 负责：

1. **接收**——接收人类选中的一批 STR-E 节点（≤5 个），校验 STR-E 状态为 `可以分解分配` / `待补充分解分配`、场景边界、能力链和 CU 候选完整；缺失场景边界或能力链时退回 wft01-eng
2. **匹配**——按 A1 引擎产品 / 主能力域匹配已有 BA 节点：同引擎同能力域归入，边界冲突标记 `[需裁决]`
3. **装配**——建立 A2 产品业务架构上下文、A1 产品路径与触发追溯（业务运行对象/治理对象/构件缺口/页面组件缺口/横切能力阶段）；A2 上下文只服务 eng 链 CU 推导，不替代业务链输出文档
4. **收敛 CU**——将 STR-E CU 候选与已有 BA CU、25 模型线索逐项比对，按确认既有/扩展既有/新增/拆分/合并/占位/退回上游七种收敛判定，输出 CU 清单（设计 CU / 占位 CU / 待裁决 CU）
5. **定义 CU 配置能力**——为每个需设计 CU 定义四类配置能力：配置入口（页面级定位/配置对象）、配置要素（关键配置项/关系/约束）、系统处理（校验/保存/版本/发布/装载摘要）、运行期能力（制品/构件/功能），达到 wft03-eng 可推断操作页面的粒度
6. **校验依赖**——识别 CU 间引擎内依赖、跨引擎依赖、页面组件/构件依赖和治理依赖（发布/版本/审计/回滚/监控），避免孤立 CU；依赖缺失时生成补充 FR-ENG 或 25 模型建议
7. **补需**——将 CU 缺口、依赖缺口、模型缺口整理为补充 FR-ENG 或 25 模型建议，登记到 OR 原料状态表，进入 OR 预处理链
8. **推进**——人类确认后 BA → `可以SR设计`，STR-E → `已分解分配`，记录消费版本
9. **回修**——接收 wft03-eng 退回的 `需wft02修订` BA，读取缺失说明，按人类改进方案修订 BA，人类确认后重新推进为 `可以SR设计`

本 Skill 不负责：

1. STR-E 场景业务边界、能力链和 CU 候选初识别（→ `wft01-eng`）
2. A2/Bn 业务架构输出文档的完整设计（→ `wft02-biz`）；本 Skill 只装配 eng 链推导 CU 所需的 A2 上下文
3. CU 操作页面、页面功能架构和操作活动设计（→ `wft03-eng`）
4. 前后端组件、接口、数据库、服务边界设计（→ `wft05-eng`）
5. 将业务实例配置写入 25；25 是类型/模型事实源，本 Skill 的 BA 是场景化设计方案

### 1.2 与上下游的衔接

**上游 wft01-eng**：产出 STR-E 场景业务，包含场景边界、能力链、CU 候选和触发追溯。本 Skill 消费这些内容，展开为配置单元 BA。若 STR-E 缺少能力链、场景终点或触发来源，本 Skill不临时补写，退回 wft01-eng。

**下游 wft03-eng**：消费 `可以SR设计` 的 A1 BA，为每个 CU 推断操作页面、页面功能架构和操作活动。若 wft03-eng 发现 CU 配置入口、配置要素、系统处理、运行期制品/构件/功能或依赖关系不清，将 BA 退回为 `需wft02修订`。

## 二、A1 配置单元 BA 设计基础

### 2.1 A1 配置单元架构（BA）

#### 2.1.1 定义与层级

A1 是平台引擎产品，归属流程与 IT 域。构件为引擎，末级节点为 CU（配置单元）。A1 产品定义见 [91 规范 §4.1](91-eos-biz-eng-spec.md#41-a1产品)，CU 功能本质见 [91 规范 §2.2](91-eos-biz-eng-spec.md#22-引擎及层级) 与 [§3.3](91-eos-biz-eng-spec.md#33-cu-与操作页面组件及构件的对应关系)，eng 路径分工见 [91 规范 §7.2](91-eos-biz-eng-spec.md#72-业务架构开发wft02-eng)。

```text
流程与 IT 域
  → A1 平台引擎产品
    → 引擎（@engine-xxx）
      → CU（配置单元）
```

CU 是引擎内可独立选配的配置单元。按 91 规范，CU 的功能本质是在实体页面或操作页面组件上增加一组业务操作能力：配置时，配置人员打开 CU 对应的硬代码配置页面，编辑配置要素并提交；系统校验正确性和完备性后保存配置；运行时，引擎按 CU 定义生成或渲染对应的运行期制品、构件及其功能。

#### 2.1.2 架构与属性

BA 节点的架构（CU 清单 + 配置能力 + 依赖关系）见 §2.2~§2.3 与 §2.5.5。

BA 节点完整要素（写入 `04-*.md` BA 节点块）：

- BA ID / 名称 / A1 产品路径 / 目标引擎 / 能力域
- 来源 STR-E 与消费版本
- A2 产品业务架构上下文
- 触发追溯
- CU 清单（设计 CU / 占位 CU / 待裁决 CU）
- 每个 CU 的配置入口、配置要素、系统处理、运行期能力
- CU 依赖关系
- 25 对齐与模型状态
- 缺口与补充 FR-ENG 材料
- 变更影响声明
- 版本号 / 确认状态

#### 2.1.3 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| CU 覆盖 | STR-E 能力链中的配置/治理/运行能力均有 CU 承接 | 补充 CU 或退回 wft01-eng |
| 配置能力自洽 | 配置入口/配置要素能被系统处理，并形成运行期制品或功能 | 标记 `[需裁决]` 或补充 FR-ENG |
| 依赖闭合 | CU 依赖的实体、表单、权限、发布、构件等能力有来源 | 形成依赖缺口 |
| 运行期能力可消费 | 运行期制品/构件/功能足以让 wft03-eng 推断操作页面 | 不足则保持待确认方案 |
| 25 关系清晰 | 25 中已有、待确认或缺失的模型关系已标注 | 形成 25 建议或阶段性标记 |

### 2.2 CU 配置能力

#### 2.2.1 定义与四类要素

每个 CU 用以下四类要素定义其配置能力：

| 要素 | 回答的问题 | 本 Skill 设计粒度 |
|------|------------|------------------|
| 配置入口 | 配置人员在哪个配置页面/子页面维护该 CU | 页面职责、配置对象、配置类别；不设计具体 UI 布局 |
| 配置要素 | 配置人员需要编辑哪些关键信息 | 关键配置项、关系、约束；不写字段级全量规格 |
| 系统处理 | 系统如何校验、保存、版本化、发布或装载配置 | 处理规则摘要、状态变化、异常处理；不写实现算法 |
| 运行期能力 | 引擎按 CU 定义生成或渲染什么制品/构件/功能 | 物理表、功能表单、菜单入口、按钮构件、流程节点构件、指标构件等 |

### 2.3 A2 上下文与触发追溯

#### 2.3.1 定义与装配规则

wft02-eng 必须同时保留三条视角：

| 视角 | 作用 | 输出 |
|------|------|------|
| A2 产品业务架构上下文 | 说明 CU 服务于哪个业务运行对象、配置用户和业务场景 | A2 产品/场景引用、业务运行对象、配置或支撑角色、触发事件、业务状态影响 |
| 触发追溯 | 说明 CU 为什么需要 | 业务运行对象、治理对象、构件缺口、页面组件缺口、横切能力阶段 |
| A1 产品装配 | 说明 CU 属于哪个平台引擎产品 | A1 产品路径、目标引擎、CU 清单、依赖关系 |

本 Skill 的 A2 装配是”上下文装配”：从业务链或 STR-E 中摘取并结构化与 CU 推导有关的 A2 信息，形成可追溯的 BA 上下文。它不重写业务链 BA 文档，也不把 Bn 业务子产品展开到 eng 链；若 A2 上下文缺失到无法判断 CU 来源，应退回 wft01-eng 或生成补充 FR-ENG。

A2 上下文至少写明：

| 字段 | 输出要求 |
|------|----------|
| A2 产品/场景引用 | 指向业务链已有 A2/场景节点；缺失时标注来源 STR-E |
| 业务运行对象 | 被配置、支撑或治理的业务对象 |
| 配置或支撑角色 | 配置人员、业务管理员、运行支撑人员或外部系统 |
| 触发事件 | 业务配置、发布、运行、异常、治理或构件缺口触发 |
| 状态影响 | CU 生效后影响的业务状态、运行状态或治理状态 |

### 2.4 BA 要素提取规则

Phase B（修订已有 BA）与 Phase C（新建 BA）共用以下规则。

#### 2.4.1 目标引擎与能力域确定

从 STR-E 读取并确认：

| 提取项 | 说明 |
|--------|------|
| 目标引擎 | STR-E 指向的主引擎（如 @engine-flow、@engine-entity 等） |
| 能力域 | STR-E 场景的配置生成/构件扩展/页面组件扩展/横切治理/运行支撑类型 |
| 依赖引擎 | STR-E 能力链中引用的其他引擎 |

路由规则：

| 情况 | 处理 |
|------|------|
| STR-E 目标引擎明确，能力域覆盖范围与 BA 一致 | 进入宿主匹配（Phase B）或新建（Phase C） |
| STR-E 目标引擎不明确或能力域混杂 | 标记 `[推断]`，必要时退回 wft01-eng |
| STR-E 缺少能力链或触发来源 | 退回 wft01-eng，不进入 BA 设计 |

#### 2.4.2 A2 上下文装配

Phase C 新建 BA 时，从 STR-E 和 24 资产装配 A2 上下文：

1. **定位 A2 产品/场景**：从 STR-E 的触发追溯中提取业务运行对象或治理对象，匹配 23/24 资产中的 A2 产品/场景节点。
2. **提取配置/支撑角色**：从 STR-E 的场景边界陈述中提取配置人员或支撑角色。
3. **确定触发事件与状态影响**：从 STR-E 能力链的”触发来源”段和”运行期可用性确认”段分别提取。
4. **装配触发追溯链**：`A2/Bn 业务运行对象/治理对象/构件缺口/页面组件缺口/横切阶段 → STR-E → A1 BA → CU`。

若 A2 上下文信息不足，标注 `[推断]` 并记录缺失项；若缺失到无法判断 CU 来源，退回 wft01-eng。

#### 2.4.3 Phase B 宿主匹配检查

Phase B 修订已有 BA 时，按目标引擎和能力域匹配已有 BA：

按以下顺序匹配：

1. 同一 A1 产品路径（流程与 IT 域 → 同一引擎）。
2. 同一目标引擎（@engine-xxx）。
3. 同一能力域或互补能力域。
4. CU 清单可归入同一 BA。

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| Q1 直接归入 | 同一 A1 路径、同一目标引擎、能力域一致 | 追加 STR-E 来源，标记 `[确认]` |
| Q2 扩展归入 | 同一目标引擎，但新增能力域或 CU 能力扩展 | 扩展 BA，写变更声明 |
| Q3 新建 | 无可用 BA 宿主 | 新建 A1 BA 节点 |
| 冲突 | 同一 CU 被多个主引擎争用或 A1 路径不一致 | 标记 `[需裁决]` |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 BA | Phase C 新建 BA |
|------|-------------------|-----------------|
| 判定范围 | BA 已承接的全部 STR-E + 本轮新 STR-E | 待聚合池本组 STR-E |
| CU 清单基线 | 以已有 CU 清单为基线，仅扫描本轮新 CU 候选 | 从零构建 |
| A2 上下文 | 增量合并新 STR-E 中的 A2 信息，已有上下文仅追加不重建 | 全量装配（§2.4.2） |
| 宿主匹配 | 执行宿主匹配检查（§2.4.3），可能检出 Q1/Q2/Q3/冲突 | 无需匹配，直接新建 |
| CU 收敛 | 在基线基础上增量合并（关系检测见 §2.5.4） | 全量收敛（§2.5.3） |
| 依赖重识别 | 合并重识别可能导致已有依赖关系变更——标记 `[依赖变更]` 并附变更原因 | 全量识别，无此问题 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 CU 收敛与依赖推断规则

Phase B（修订已有 BA）与 Phase C（新建 BA）共用以下规则。

#### 2.5.1 CU 清单提取

**识别 CU 清单**：从当前操作范围内的全部 STR-E 的 CU 候选中提取。去重/收敛后形成 CU 清单，每个 CU → BA 中一个配置单元节点。多个 STR-E 的 CU 候选指向同一 CU 时归入同一节点（要素收敛）。

**逐 CU 判定目标引擎/能力域**：从 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景) 动态读取引擎清单和 CU 类型线索（每次运行时读取、不缓存），根据 CU 的功能特征匹配。wft02 基于 STR-E 场景业务和 25 模型线索做收敛判定，CU 的引擎归属**标注 `[推断]` 或 `[25确认]`**，最终判定在 wft03 的操作页面设计中校验。

#### 2.5.2 CU 来源类型

| 来源类型 | 含义（含示例） |
|----------|---------------|
| `STR-E明示` | STR-E 已明确列出该 CU 候选。如 STR-E 的 CU 候选清单中直接列出”流程节点配置” |
| `STR-E隐含` | 没有该 CU 则 STR-E 能力链无法闭合。如 STR-E 能力链要求”发布后回滚”但未列出回滚配置 CU |
| `构件缺口推断` | 为支撑某类操作页面构件扩展而需要。如 STR-E 描述”单据页需要审批按钮构件”→ 推断需要按钮构件配置 CU |
| `页面组件缺口推断` | 为支撑某类操作页面组件扩展而需要。如 STR-E 描述”需要甘特图页面组件”→ 推断需要甘特图组件配置 CU |
| `同类引擎推断` | 同类引擎已有相似配置能力。如同类 @engine-flow 的已有 BA 含”流转规则配置”→ 当前 BA 推断也需要 |
| `25模型线索` | 25 中已有 CU 类型或待确认模型线索。如 25 资产 §2.x 已有”实体字段配置”CU 类型定义 |
| `引擎内置` | 引擎预定义能力，本轮 STR-E 未触发，仅占位。如 @engine-entity 内置的子业务配置单元 |

#### 2.5.3 CU 收敛判定

对每个 CU 候选执行以下七种判定：

| 判定 | 条件 | 动作 |
|------|------|------|
| 确认既有 | BA 已有 CU 与本轮候选同名同义，配置能力边界一致 | 追加来源，标记 `[确认]` |
| 扩展既有 | BA 已有 CU 主体一致，但新增配置要素、系统处理或运行期能力 | 修订 CU 配置能力，标记 `[变更]` |
| 新增 CU | 无可复用 CU，且候选粒度可展开 | 新建 CU |
| 拆分 CU | 候选同时承接多个配置入口、多个不连续系统处理或多个运行期能力族 | 输出拆分建议，标记 `[需裁决]` |
| 合并 CU | 多个候选必须同页配置、共同校验并共同生成一个运行期能力 | 合并为一个 CU，保留来源映射 |
| 占位 CU | 25 或引擎模型已有预定义能力，但本轮 STR-E 未触发 | 保留名称，占位不进入确认范围 |
| 退回上游 | 候选缺少触发来源或能力链 | BA 不设计，退回 wft01-eng |

收敛时同时判断 CU 粒度：`可展开` / `过粗待拆` / `过细待并` / `边界待确认`。粒度过粗或过细时触发拆分/合并判定。

#### 2.5.4 Phase B CU 关系检测

Phase B 修订已有 BA 时，宿主匹配通过后，将本轮提取的 CU 与 BA 已有 CU 清单比对。比对锚点为**CU 名称+配置能力边界匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU 匹配 + 配置能力边界一致 + 至少一个来源非 `STR-E明示` | 来源升级（`STR-E隐含`→`STR-E明示`、`构件缺口推断`→`STR-E明示`、`页面组件缺口推断`→`STR-E明示`、`同类引擎推断`→`STR-E明示`、`25模型线索`→`STR-E明示`），内部细分结论=`确认` |
| 无新增 | CU 匹配 + 配置能力边界一致 + 所有来源已为 `STR-E明示` | 追加 STR-E 引用 + 增量合并新 STR-E 中的配置要素/系统处理/运行期能力细节（如有新内容），内部细分结论=`改进` |
| 配置能力扩展 | CU 匹配 + 配置入口/配置要素/系统处理/运行期能力任一项边界扩展 | 修订 CU 配置能力定义 + 内部细分结论=`配置能力扩展` + 变更原因。不新增 CU |
| 引擎归属变更 | CU 匹配 + **目标引擎不同**（合并重识别导致） | 更新 CU 的目标引擎 + 内部细分结论=`引擎归属变更` + 变更原因。不新增 CU |
| 补充 | CU 不匹配 | 新增到 CU 清单，来源=`STR-E明示`，内部细分结论=`新增` |
| 过时 | 基线已有 CU **未被**本轮提取覆盖（宿主扩展触发能力域重追踪后，基线中某些 CU 不再落入新的 BA 范围） | 内部细分结论=`过时` + 追加说明”宿主扩展后未落入新的 BA 能力域范围，请确认是否移除”。保留该 CU 在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 STR-E 重新识别目标引擎**——新 STR-E 可能改变 CU 特征导致引擎归属变更（表中 `引擎归属变更` 行）。来源证据强度只升不降：`STR-E隐含`/`构件缺口推断`/`页面组件缺口推断`/`同类引擎推断`/`25模型线索` → `STR-E明示`，在 `确认` 行触发。

`[调整]` 是与关系类型正交的叠加标记：已有 CU 的名称/配置入口/配置要素/系统处理/运行期能力变化，在关系标记之外叠加 `[调整]`。

#### 2.5.5 依赖关系分类与校验

CU 依赖分为四类：

| 依赖类型 | 示例 | 处理 |
|----------|------|------|
| 引擎内依赖 | 流转规则配置依赖流程节点配置 | 在 BA 中写明先后关系 |
| 跨引擎依赖 | 流程配置依赖实体字段、权限规则 | 引用依赖引擎/CU，不改主归属 |
| 页面组件/构件依赖 | 流程 CU 运行期需要按钮构件、节点构件 | 说明被渲染的操作页面组件/构件 |
| 治理依赖 | 发布、版本、审计、回滚、监控 | 若缺失则生成补充 FR-ENG 或 25 模型建议 |

依赖校验流程：

1. **引擎内**：检查 CU 间是否有先后配置关系，缺失前置 CU 时标记依赖断点。
2. **跨引擎**：检查引用引擎/CU 是否在 25 或已有 BA 中存在，不存在时标记 `[推断]` 依赖。
3. **页面组件/构件**：检查运行期能力中的构件/组件是否可追溯到来源 CU 或 25 中的页面组件/构件定义。
4. **治理**：检查发布、版本、审计、权限、回滚等横切依赖是否在 BA 或 25 中有覆盖，缺失时生成补充 FR-ENG。

### 2.6 BA 节点生命周期

BA 节点沿 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §8.6 状态名映射表（wft02-eng 列）。并行推进规则（资产线与 SR 线互不阻塞）见 91 规范 §8.6。

**主线流转**（wft02-eng ←→ wft03-eng）：

```
待确认方案 ──人类确认──→ 可以SR设计 ──wft03锁定──→ 在SR设计 ──wft03完成──→ 已SR设计
     ↑                        ↑                         │
     │                        │               wft03退回  │
     │                        │                         ↓
     └─── wft02修订 ────── 需wft02修订 ←───────────────┘
```

**上游变更**（新 STR-E 汇入触发 BA 修订）：

```
可以SR设计 ──新STR-E修订──→ 可以SR设计（版本递增，wft03 未消费）
在SR设计   ──新STR-E修订──→ 在SR设计（版本递增，wft03 增量处理）
已SR设计   ──新STR-E修订──→ 待补充SR设计 ──wft03补全──→ 已SR设计
```

**本 Skill 的写回范围**：`待确认方案` / `可以SR设计` / `待补充SR设计` / `需wft02修订`。`在SR设计` 和 `已SR设计` 由 wft03-eng 写入和推进。

下游退回 `需wft02修订` 时：读取 wft03-eng 的缺失说明 → 按人类改进方案修订 BA（走 Phase B 修订流程）→ 人类确认 → BA → `可以SR设计`。

### 3.1 Step Start

运行时 AI 按以下顺序执行：

1. **输入校验**：
   - BA 状态为 `需wft02修订` 且人类未提供改进方案 → 输出 wft03-eng 的缺失说明，提示提供改进方案 → **退出**
   - STR 类型不是 STR-E → 输出类型分布，提示走 `wft02-biz` 或 nfr 路径 → **退出**
   - STR-E 状态不是 `可以分解分配` / `待补充分解分配` → 输出不合格节点及当前状态 → **退出**
   - STR-E 缺少场景边界、能力链或触发追溯 → STR-E → `需wft01修订`，输出缺失说明 → **退出**
   - STR-E 无 CU 候选且 AI 无法推断 → 输出"输入不足"提示 → 标记 `[需裁决]`，必要时退回 wft01-eng
   - 选中 STR-E >5 个 → 输出超限提示 → 人类确认后继续或退出
   - 无 STR-E 选中 + 无待处理反馈的 BA 节点 + 无 `需wft02修订` 的 BA 节点 → 输出"无待处理对象"→ **退出**
2. **退回优先**：存在 `需wft02修订` 的 BA 节点（且人类已提供改进方案）→ 读取 wft03-eng 的缺失说明，按人类方案走 Phase B 修订，人类确认后推进为 `可以SR设计`
3. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 BA 节点 → 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 STR-E，Step End 时提示
4. **新 STR-E 路由**：有未处理的 STR-E 节点 → 进入 Step 1→Step 3，逐节点执行 Phase A 宿主匹配，归入已有 BA（→Phase B）或待聚合池（→Phase C）

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 BA 的 A1 路径/CU 清单/配置能力/依赖关系。Step 3 的 Phase A 宿主匹配必须基于 Step 2 修改后的最新 BA 内容，不得使用缓存旧状态。

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议)。以下为本 Skill 的特化规则。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 STR-E 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解人类反馈在 STR-E 需求语境中的含义，再执行修订，最后检查修订后的 BA 是否仍满足 STR-E 需求。

本 Skill 特化参数见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 实例化参数表（wft02-eng 列）。

### 3.4 Step 3 · A1/CU BA 设计

#### Phase A · 确定 BA 宿主

按目标引擎和能力域匹配已有 BA：

| 匹配结果 | 判定 | 动作 |
|----------|------|------|
| Q1 直接归入 | 同一 A1 路径、同一目标引擎、能力域一致 | 追加 STR-E 来源 |
| Q2 扩展归入 | 同一目标引擎，但新增能力域或 CU 能力扩展 | 扩展 BA，写变更声明 |
| Q3 新建 | 无可用 BA 宿主 | 新建 A1 BA 节点 |
| 冲突 | 同一 CU 被多个主引擎争用或 A1 路径不一致 | 标记 `[需裁决]` |

#### Phase B · 装配 A2 上下文、触发追溯与 A1 路径

为 BA 节点建立：

```text
来源 STR-E
  → A2 上下文（产品/场景 / 业务运行对象 / 配置或支撑角色 / 触发事件 / 状态影响）
  → 触发来源（治理对象 / 构件缺口 / 页面组件缺口 / 横切阶段）
  → A1 产品路径（流程与 IT 域 → 目标引擎 → CU）
  → 运行期制品/构件/功能
```

A2 上下文至少写明：

| 字段 | 输出要求 |
|------|----------|
| A2 产品/场景引用 | 指向业务链已有 A2/场景节点；缺失时标注来源 STR-E |
| 业务运行对象 | 被配置、支撑或治理的业务对象 |
| 配置或支撑角色 | 配置人员、业务管理员、运行支撑人员或外部系统 |
| 触发事件 | 业务配置、发布、运行、异常、治理或构件缺口触发 |
| 状态影响 | CU 生效后影响的业务状态、运行状态或治理状态 |

#### Phase C · 收敛 CU 清单

对 STR-E 的每个 CU 候选执行 §2.5 收敛判定：

1. 与已有 BA CU 比对名称和职责。
2. 与 25 CU 类型或模型线索比对。
3. 判断粒度：可展开、过粗、过细、边界待确认。
4. 输出 CU 清单：设计 CU、占位 CU、待裁决 CU、退回上游项。

#### Phase D · 定义 CU 配置能力

对每个需设计 CU，写出四类要素：

| 要素 | 输出要求 |
|------|----------|
| 配置入口 | 配置页面/子页面名称级定位、配置对象、配置人员 |
| 配置要素 | 关键配置项、配置关系、约束和必备校验口径 |
| 系统处理 | 校验、保存、版本、发布、装载、停用、异常处理的摘要 |
| 运行期能力 | 生成/渲染的物理表、功能表单、菜单入口、操作页面构件或功能 |

#### Phase E · 依赖链校验

检查：

1. 引擎内 CU 依赖是否有先后关系。
2. 跨引擎依赖是否明确主从关系。
3. 运行期制品/构件/功能是否能追溯到来源 CU。
4. 发布、版本、审计、权限、回滚等治理依赖是否缺失。
5. 依赖缺失是否应补充 FR-ENG 或形成 25 模型建议。

BA 节点要素：

- BA ID / 名称 / A1 产品路径 / 目标引擎 / 能力域
- 来源 STR-E 与消费版本
- A2 产品业务架构上下文
- 触发追溯
- CU 清单（设计 CU / 占位 CU / 待裁决 CU）
- 每个 CU 的配置入口、配置要素、系统处理、运行期能力
- CU 依赖关系
- 25 对齐与模型状态
- 缺口与补充 FR-ENG 材料
- 变更影响声明
- 版本号 / 确认状态

### 3.5 Step 4 · 缺口补需与变更声明

#### 3.5.1 缺口处理规则

| 缺口 | 处理 |
|------|------|
| STR-E 场景边界/能力链缺口 | 退回 wft01-eng 修订 |
| CU 缺口 | 在 BA 中新增候选 CU，标注 `[推断]`，供人类确认 |
| CU 粒度过粗/过细 | 输出拆分/合并建议，标记 `[需裁决]` |
| 配置入口缺口 | 生成补充 FR-ENG 或 25 模型建议 |
| 配置要素缺口 | 标记 `[需裁决]`，需要人类补充业务配置意图 |
| 系统处理缺口 | 生成补充 FR-ENG，如发布、装载、回滚、审计 |
| 运行期能力缺口 | 生成补充 FR-ENG，说明需生成或渲染的制品/构件/功能 |
| 依赖缺口 | 标记依赖断点并生成补需 |
| 25 模型缺口 | 形成 25 模型建议，不直接固化 |

#### 3.5.2 变更影响声明

每次新建或修订 BA 后写入变更影响声明；首版写“首版，无变更”。修订时按 §2.8 判定无变更、增量型、修订型或结构型，并列出受影响 CU、依赖和下游 wft03-eng 建议动作。

### 3.6 Step 5 · 资产写回与落账

仅对已确认 BA 执行：

1. `04`：BA → `可以SR设计`，写入版本、确认状态、变更影响声明。
2. `02`：对应 STR-E → `已分解分配`，记录消费版本。
3. `23`：更新 A1 产品路径引用。
4. `25`：写入 CU 配置能力引用或模型建议；25-Q3 未确认时仅保留候选建议。

资产写回与 wft03-eng 消费并行推进，写回完成与否不改变 BA 的可消费状态。

### 3.7 Step End · 运行结束输出

遵循 [91 规范 §8.8](91-eos-biz-eng-spec.md#88-skill-通用约定) 的三区模板。

```text
当前状态：<待确认方案 / 可以SR设计>
  BA：新增/修订 <N> 个 A1 BA 节点；设计 CU <N> 个；占位 CU <N> 个；补充 FR-ENG <N> 条；待裁决 <N> 项。

一、方案反馈
  A. 整体确认 -> 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 -> 在确认状态中标注 [修改]：...
  C. 驳回重做 -> 在确认状态中标注 [驳回]：...

二、下一步
  本Skill -> 存在未处理反馈 / 需wft02修订 / 新 STR-E 时重入
  后续    -> BA 状态为 可以SR设计 后进入 wft03-eng
```
