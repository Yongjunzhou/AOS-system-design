## 一、目的与目标

### 1.1 本任务在对/链上的位置

设计开发 = 由需求到方案的逐对生成。biz 链首对即**需求-方案对①**：

```
需求-方案对①：  X = 相关方需求 ── 01，不分形态，叶＝系统用例场景级操作
        │  阶段一 承接设计，本任务 biz01   —— 产出 Y 概要 02，不含叶
        ▼
       Y概要 = 业务流程概要 ── 02，枝干：场景业务 → 枝梢：业务输出文档
        │  阶段二 分解，biz02 —— 产出 Y 完整态叶节点：活动节点／正文条目，落 04
        ▼
       Y完整态 = 业务流程 ── 04，即需求-方案对② 的 X ──▶ 系统需求概要 05，biz03…
```

- 本任务 = 需求-方案对① 的**阶段一**：按规则 F 做**承接设计**，产出 Y 的概要形态，即 02。
- **承接的落点由 X 给出**：X 的叶是 ③ 系统用例场景级操作，它的上级 ① 业务输出文档带「所属E2E场景业务」属性——[94 §1.4](94-eos-sys-dev-dbs.md) 的 01→02 承接即按该属性把叶落到 Y 的 ④ 场景业务，也就是枝干。
- **概要的位置**：概要是同一份逻辑产品数据即业务流程的骨架形态，**只是一个需求-方案对的中间形态、不算它的一端**；一个需求-方案对的两端是需求与方案两份产品数据、各取完整态。需求-方案对① 的收敛以 Y 完整态 04 达成。
- **概要到枝梢为止、不含叶**：枝梢即**业务输出文档**；叶即**活动节点／正文条目**，由阶段二在 04 定义成叶。
- 人类门禁位置：本任务产出概要 → 人类「整体确认」→ 节点推进为 `可以分解分配` → 阶段二可进入。
- 下游退回：biz02 检出概要缺陷 → 标 `需biz01修订`，这是对内**反向迭代**，也就是方案迭代需求。

### 1.2 主要目的

> 取信于相关方——「你听懂了我的需求和意图」。把 X 的相关方需求即 FR-BIZ 转化为 Y 概要即业务流程概要的声明与骨架：不仅承接需求已说出的内容，更识别其指向的端到端完整业务意图，按本需求-方案对的规则 F 落到概要的各级枝干/枝梢，为阶段二——biz02 分解出完整态——提供可展开的输入与分解源判据。

### 1.3 目标

1. **识别可承接对象**：从待处理条目中按 ① 的三坐标归拢出同一业务对象闭环的一组，判定是否已有可承接的场景业务，也就是枝干——有则**复用**；否则**新建**。
2. **生成场景业务枝干**：判定类型 D/PCA、命名、边界定义，边界即主责角色的业务对象闭环。
3. **补齐业务输出文档枝梢**：X 的 ① 已列出文档，本任务为每张补齐 Y 侧内容——封面模式，即正式或轻量；任务类型与主要节点、正文条目，到名称级；并写**承接判据 + 分解源判据**。
4. **写任务关系**：文档间流转顺序 + 需求明示的任务触发关系，用业务语言表达。
5. **单承接保证**：叶的落点由 ① 的场景属性决定，同一 ① 下的叶必落同一个场景业务——单承接由树形保证；本任务检查 ① 的三坐标齐备与分流正确，见 §2.3／§4.1。
6. **承接覆盖检查**：基于端到端闭环核对「承接了的需求有没有被业务链实现」——检出缺口生成补充原始需求材料，不脑补节点。
7. **P 对齐与组装**：逐文档判定与 23 资产 P 侧的对齐，取对齐 Q1~Q3；再做 WBS 归组 + 23 一致性检查 + 按构件产品数据清单名称级推断缺口。

### 1.4 本任务负责 / 不负责

**负责**：承接分配叶到概要枝干/枝梢，走 复用 → 改进 → 新增 的分流；生成概要节点与传出承诺；人类确认后写回 23 资产与推进状态；处理下游退回，即反向迭代修订。

**不负责，均指向其实际归属**：

- FR-ENG 需求 → `wft01-eng`；NFR → `wft01-nfr`。二者在输入校验检出后退出
- Y 完整态分解，含叶节点与字段级详设 → 阶段二 `biz02`
- 页面层级/菜单设计 → `biz03`
- 业务人员确认 → 人类线下活动
- **X 侧的切分与建树** → ort 链。本任务只受理或退回，不自行重切、不重定坐标，见 §2.3
- **治理业务流程概要**中无需求输入者 → 23 资产预置，由人类按平台治理业务渐进增补、经 ort 链补需求，本任务不主动展开

### 2.3 X 侧规则（复核与退回）

- **切分与建树权在 ort**：业务对象闭环的切分、① 的三个坐标、② 与 ③ 的落位，都由 ort 链制定并执行——**本任务不重切 X、不重定坐标**。
- **复核两项**：① 的三个坐标是否齐备且唯一；③ 条目的语义是否与它所属 ① 的三坐标一致。二者通不过 → 标 `需退回重切` → 回 ort 链处置后重新进入。
- **承载量超限**，一批吞不下 → 分批进入；≤10 条/批是软限制，人类可确认放宽。
- **Y 侧的节点拆分与改 X 不是一回事**：Y 侧装不下时的拆分或横切出口见 §4.1，它动的是 Y 的节点，不回头改 X。

### 2.4 受理门槛（输入校验）

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 条目状态 = `需退回重切` | 不可处理 | 输出退回记录 → 退出 |
| 条目状态 ≠ `待处理` | 不可处理 | 输出当前状态 → 退出 |
| 条目分属多个主责角色 | 不可处理 | 输出角色分布 → 退出 |
| 条目类型含 FR-ENG / NFR | 路由错误 | 输出类型分布 + 路由指引 → 退出 |
| 同一 ① 下条目 > 10 条 | 软限制 | 输出超限提示 → 人类确认 |
| 无待处理条目 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

### 2.5 依赖与校验（读 X 时）

- ① 的三坐标齐备、条目正文语义自洽：ort03 已归一化，主责角色的业务域在 21 角色侧。缺标或矛盾 → 标 `[需确认]`，不自动推进。
- **同 ① 内一致性**：同一张业务输出文档下的条目应指向同一业务对象、语义不漂移——漂移 → 输出退回重切提示，不自动拆。
- 读 X 遵循 91 §A.3.3 读取协议：AI 可以处理节点优先、逐节点加载、按需扩大，不默认加载全文。

## 三、输出文档结构及规则（Y = 02 业务流程概要 · 生产侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程** 的**概要态**，即 02，不含叶；Y 的**完整态** 04 由阶段二 biz02 产出。概要 = 同一份逻辑产品数据的骨架形态，只是一个需求-方案对的中间形态、不算它的一端——故本任务写出的节点目标状态是「**可供阶段二展开**」，而非「自成完整的业务流程」。

### 3.2 输出空间的两棵树（Y 树 · 生产视图）

本任务的 Y 即业务流程，不在一条树上——**同一批业务输出文档在两条独立的树里各得其位**：**R 角色履职树**回答「某角色在哪个场景、按什么序、处理哪些业务输出文档完成闭环」，讲的是履职与工作序；**P 输出产品树**回答「这批输出文档作为构件产品数据，属于哪个产品/构件/WBS 包、怎么生成与流转」，讲的是产品数据与依赖。两树在**业务输出文档以及其活动节点**处对位互连、经**认亲**互指；不是一棵树的共享节点。

**树一 · R 角色履职树（业务运行角色履职视角）**

```
角色履职业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的一类职责范围
            └── 场景业务 ─ ④ 一个业务对象闭环，分 D 执行与 PCA 管理
                └── 业务输出文档 ─ ⑤ 该闭环产生与流转的文档，即履职对象，是枝梢
                    └── 活动节点 / 正文条目 ─ ⑥ 活动：处理角色/动作/状态变迁；条目：名称/定义要素/生命周期，是叶
```

| 级 | 节点与意义 | 怎么得到 | 本任务如何处置 |
|----|-----------|---------|--------------|
| ① | 业务域——归属域 | **承袭** 21／23 域根 | 作定位与 P 对账域，不产出 |
| ② | 相关方角色——主责角色，即业务对象生命周期的主推动者 | **承袭** 21 的 `ROLE-*` | 作 02 分片与复用宿主范围，不产出 |
| ③ | 角色职责——角色承担的一类职责范围 | **目标组织级**，随 02／21 演进 | 本任务不产该节点 |
| ④ | 场景业务 bph-biz——一个业务对象闭环，分 D 或 PCA | **本任务产出**（复用 → 新建） | 本任务新建/修订单位 + 人类确认挂点：承接条目、职责边界、收敛自查、推进 `可以分解分配` |
| ⑤ | 业务输出文档——该闭环产生与流转的文档，是枝梢 | **本任务产出**，写到概要说明级；文档本体由 X 的 ① 给出，见 §2.2 | 产出枝梢，也就是最深结构层：概要说明 + 承接判据 + 分解源判据展开项 + P 认亲 |
| ⑥ | 活动节点／正文条目——文档上的活动与条目，是叶 | **阶段二产出** | 非 02 树位，本任务只预告，交 biz02 落叶、04 定义 |

> **「任务」不占树位**：一个业务输出文档有 0 或 1 个任务；任务的主要节点与正文条目一样，是**枝梢的分解源判据展开项**——名称级预告，完整态在 04 定义成叶。
>
> **R0 与 Rn**：本任务的主体走 **Rn 树**。平台自身的治理业务走 **R0 树**——同一棵 R 树在「平台本身」这一侧**少「角色职责」一级**：业务域 → 相关方角色 → 场景业务 → 业务输出文档 → 活动节点／正文条目，因为业务配置角色不按角色类型再归纳。层级差非遗漏。02 里预置的治理节点 bph-biz-GOV-* 即 R0 场景，本任务对其只作渐进增补，不主动展开。

**树二 · P 输出产品树（产品开发视角）**

```
输出产品业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 产品类型 ─────── ② 部门级的端到端业务输出
        └── 产品构件类型 ─ ③ 科室级的端到端业务输出
            └── 构件开发WBS（包）─ ④ 文档序列
                └── 构件产品数据，即业务输出文档 ─ ⑤ 该构件/WBS 包承载的产品数据文档
                    └── 活动节点 / 正文条目 ─ ⑥ 是叶
```

| 级 | 节点与意义 | 怎么得到 | 本任务如何处置 |
|----|-----------|---------|--------------|
| ① | 业务域——归属域 | **承袭** 23 域根 | 认亲检索与完备对账的域边界 |
| ② | 产品类型——产品类别，如采购产品、实物产品 | **AI 建议 + 人类确认**，走对齐 Q1 引用／Q2 扩展／Q3 新建，见 §4.4 | 本任务按需建立或确认 |
| ③ | 产品构件类型——构件分类，如自研、外购、复用、项目 | **AI 建议 + 人类确认**，同上 | 同上 |
| ④ | 构件开发WBS（包）——一批数据依赖闭合的产品数据单元 | **AI 建议 + 人类确认**，同上；打包生成规则挂账 | 同上 |
| ⑤ | 构件产品数据，即业务输出文档 | **本任务认亲归位**：R 树的文档逐一标定 P 坐标 | 本体唯一——可被多场景引用、只占一个产品数据位 |
| ⑥ | 活动节点／正文条目 | **阶段二产出** | 叶：非本任务产出，只预告，交 biz02 落叶、04 定义 |

> **认亲 = 两树对位**：R 场景链里的每张业务输出文档，逐一识别其 P 归属，即产品类型×构件×WBS 包，归位 P 树；两树靠这层互指联通。04 由 biz02 产出，是双视角完整态，以场景为单位把 R 链序与 P 位置并成一份。
>
> **⑤ 与 X 的 ① 同指，认亲坐标由 X 给出**：本树 ⑤ 的业务输出文档即 01 树的 ① 节点——X 的 ① 上带「所属产品构件」属性，本任务据此定位 P 侧构件坐标，见 §4.2；同一张文档因此有三个视图：X 侧的需求承载级、R 侧的履职对象、P 侧的产品数据位。
>
> **概要边界**：本任务把业务输出文档写到**名称/概要 级**——R 侧到「文档枝梢 + 分解源判据」，P 侧到「产品数据归位 + 组装/完备结论」；叶、字段级详设、P 详设都归 biz02/biz03，不在本任务展开。
>
> **树权威**：R／P 两棵树拓扑与级语义的权威 = [94 §二](94-eos-sys-dev-dbs.md)，见 93 §4.1；本图是本任务的视图，不另立口径。23 按其维护产品架构节点数据。01 与 02 两份产品数据的树画像单源 = 各自数据文件的树画像区。

### 3.3 节点类型与结构要点

> 方法读法：02 概要 = 一棵不含叶的树。**场景业务 = 各级枝干**，即聚合层；**业务输出文档 = 枝梢节点**，即架构末级；**活动节点／正文条目 = 叶**，由阶段二在 04 定义成叶——概要不含叶，故其名称在本任务只以枝梢**分解源判据展开项**出现、不占 02 树位。**跨需求-方案对承接，即 04→05，只取 04 的叶**：[94 §1.2](94-eos-sys-dev-dbs.md) 依据三说承接的定义域取需求侧的**原子，即叶**，粗粒度节点不能被 1:1 分配，**故枝梢不参与承接**。「04 输出文档 → 功能表单」是**页面视角的转译**，不是承接。

- **场景业务，即枝干**：一个主责角色——业务对象生命周期的主推动者——的一个业务对象闭环，由一组有流转依赖的业务输出文档序列构成。类型二分类：**执行类 D**，从需求提出到需求满足；**管理类 PCA**，计划→监控→分析→纠正，须含计划清单输出文档 + 承载 C/A 的输出文档。
- **业务输出文档，即枝梢**：场景业务的组成单元。**枝梢双向物理意义**——①**承接判据**：本枝梢承接哪类需求或业务，属承接侧；②**分解源判据**：本枝梢将被阶段二分解出哪些叶节点，含活动、正文条目、表单，即交给 biz02 的规则接口。两条判据共享同一物理意义，避免「承接说能来、分解实现不了」的结构性空洞。
- **两树对位，即认亲**：R 树与 P 树是两条独立树，见 §3.2——同一份业务输出文档在 R 侧是场景履职链的一环，即该角色按什么序处理它；在 P 侧是某 产品类型×构件×WBS 包 的产品数据，即属哪个域的产品、怎么生成、与哪些前序文档有数据依赖。两树经**认亲**互指，见 §4.4：本任务逐枝梢识别其 P 归属并归位，坐标由 X 的 ① 给出，见 §4.2；一张文档可被多个场景引用，但 P 侧产品数据位唯一。
- 业务输出文档按封面模式分**正式**与**轻量**：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。判据见 91 §2。
- **任务类型 R4**：场景业务中第一个有任务类型的文档必然为**计划**，这是闭环启动机制。
- **叶之预告**，即枝梢分解源判据展开项：有任务类型的文档预告其活动节点，即行为锚点——谁审批、通过后到哪，供人类确认；正文为集合容器且条目满足**三独立**，即独立名称、独立定义要素、独立生命周期时，预告其正文条目。叶是 Y 的完整态，04 由阶段二定义成叶；本任务在 02 只写**预告**，各带内联稳定标签作 02→04 追溯键，**不是 02 的树节点**。

### 3.4 Y 侧规则（构建与收敛）

- **概要边界，结构判定级**：本任务只做结构级判定——文档是否存在，到名称级；封面模式、候选引擎、开发方式、任务层、条目层三独立。**字段级详设留阶段二**。
- **场景业务构建规则**，用于新建：识别触发 → 追踪自然终点，不得在终点之后扩展 → 闭合验证 → 边界四标准，即完整性、一致性、紧凑性、粒度匹配，产出场景职责边界陈述。
- **文档序列构建规则**：D 类按输入-输出传递链排列；PCA 类按 P→C→A 管理循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有枝干，才上溯建更高层。

### 3.5 要素清单（本任务写入 02 节点必须带齐）

写入 bph-biz 概要节点，字段对齐 02 §4.1 模板、逐字同名：

- **块头字段**：块ID / 节点类型 bph-biz / 视角类型 / 类型 D 或 PCA / 主责角色 / 当前状态。
- **正文要素行**，依次为：
  - 业务域 / 产品路径；用户角色；场景职责边界陈述；
  - **承接的规范化的相关方需求**——FR-BIZ 条目引用，N:1 汇聚；治理预置节点按治理覆盖口径；
  - **业务链**，每枝梢一段，段内六项：概要说明，即名称/用途/封面模式/开发方式，结构判定级；任务类型；支撑引擎候选 `[推断]`；**分解源判据展开项**，即任务主要节点 + 条目名，各带内联稳定标签，见 §3.3；任务关系；**P 认亲**，即所属 产品类型×构件×WBS 包 + 对齐 Q1~Q3；
  - **P 组装结论**——WBS 归组 + 23 一致性结论 + 缺口推断与候选节点建议；
  - 推理依据与补全说明；完备性检查结果；补充材料引用；变更影响声明 / 版本号。

### 3.6 传出承诺（给阶段二 biz02）

本任务把概要节点交给下游时，承诺节点达到：

## 四、输出与输入转换规则

### 4.1 承接规则（X 叶 → Y 枝干/枝梢）

- **落点由 X 给出**：叶落到哪个 ④ 场景业务，由叶所属 ① 上的「所属E2E场景业务」属性决定，见 [94 §1.4](94-eos-sys-dev-dbs.md)。同一 ① 下的全部叶共用该属性，故**必落同一个场景业务——单承接由树形保证**，不靠逐条检查；本任务的检查落在 ① 的三坐标齐备与分流正确上，见 §2.3。
- **① 整体分流**：① 对应的场景业务已在 Y 中存在 → **复用**，走修订转换；尚无 → **新建**。优先级始终 复用 → 改进 → 新增。
- **落点已定而 ① 内部语义跨界**：属 X 的缺陷，标 `需退回重切` 回 ort 链，不在 Y 侧就地分。
- **Y 侧装不下时**：节点拆分，或横切式承接走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有枝梢做扩展/拆分/合并后，须复查其已承接的既有条目是否失配 → 批量重分配或回退。

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回规范化／宿主误匹配 → 业务链关系检测，分 确认／无新增／引擎判定变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查 → P 组装重跑。

### 4.4 对齐规则（输出 → 资产）

逐枝梢判定与 23 资产 P 侧的对齐：**对齐 Q1** 已有、直接引用，**对齐 Q2** 需扩展，**对齐 Q3** 无、给新建建议；再执行 WBS 归组，判据是数据依赖链；加 23 一致性检查，查 归属冲突／误新建／误引用；再加按构件产品数据清单名称级缺口推断，不依赖任务类型或引擎。
