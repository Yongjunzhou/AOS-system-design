## 一、目的与目标

### 1.1 本任务在对/链上的位置

设计开发 = 由需求到方案的逐对生成。biz 链首对即**需求-方案对①**：

```
需求-方案对①：  X = 相关方需求 ── 01，完整态，需求叶＝相关方需求条目
        │  阶段一 承接设计，本任务 biz01   —— 产出 Y 概要 02，不含叶
        ▼
       Y概要 = 业务流程概要 ── 02，枝干：场景业务 → 枝梢：输出文档 PL5
        │  阶段二 分解，biz02 —— 产出 Y 完整态叶节点：活动/正文条目/表单，落 04
        ▼
       Y完整态 = 业务流程 ── 04，即需求-方案对② 的 X ──▶ 系统需求概要 05，biz03…
```

- 本任务 = 需求-方案对① 的**阶段一**：按规则 F 做**承接设计**，产出 Y 的概要形态，即 02。
- 概要是 Y 的骨架，只是一个需求-方案对的中间形态、不算它的一端；需求-方案对① 的收敛以 Y 完整态 04 达成。
- 人类门禁位置：本任务产出概要 → 人类"整体确认" → 节点推进为 `可以分解分配` → 阶段二可进入。
- 下游退回：biz02 检出概要缺陷 → 标 `需biz01修订`，这是对内**反向迭代**，也就是方案迭代需求。

### 1.2 主要目的

取信于相关方——「你听懂了我的需求和意图」。把 X 的相关方需求即 FR-BIZ 转化为 Y 概要即业务流程概要的声明与骨架：不仅承接需求已说出的内容，更识别其指向的端到端完整业务意图，按本需求-方案对的规则 F 落到概要的各级枝干/枝梢，为阶段二——biz02 分解出完整态——提供可展开的输入与分解源判据。

### 1.3 目标

1. **识别可承接对象**：从待处理需求叶中识别属于同一业务对象闭环的一组，判定是否已有可承接的场景业务，也就是枝干——有则**复用**，标 Reuse；否则进入新建，标 Add。
2. **生成场景业务枝干**：判定类型 D/PCA、命名、边界定义，边界即主责角色的业务对象闭环。
3. **生成输出文档枝梢**：逐文档识别封面模式，即正式或轻量；正文实体类型、任务类型与主要节点、PL6-B 条目，到名称级；每条枝梢写**承接判据 + 分解源判据**。
4. **写任务关系**：文档间流转顺序 + 需求明示的任务触发关系，用业务语言表达。
5. **单承接保证**：一条需求只归一个场景业务，可 N:1、不可 1:N——归属冲突走退回或重切。
6. **承接覆盖检查**：基于端到端闭环核对"承接了的需求有没有被业务链实现"——检出缺口生成补充原始需求材料，不脑补节点。
7. **P 对齐与组装**：逐文档判定与 23 资产 P 侧的对齐，取 Q1/Q2/Q3；再做 PL4 WBS 归组 + 23 一致性检查 + 按构件产品数据清单名称级推断缺口。

### 1.4 本任务负责 / 不负责

**负责**：承接分配需求叶到概要枝干/枝梢，走 Reuse→Add 分流；生成概要节点与传出承诺；人类确认后写回 23 资产与推进状态；处理下游退回，即反向迭代修订。

**不负责，均指向其实际归属**：
- FR-ENG 需求 → `wft01-eng`；NFR → `wft01-nfr`。二者在输入校验检出后退出
- Y 完整态分解，含叶节点与字段级详设 → 阶段二 `biz02`
- 页面层级/菜单设计 → `biz03`
- 业务人员确认 → 人类线下活动
- 无需求输入的治理业务流程概要不主动展开

### 1.5 与上下游的衔接

| 方向 | 任务 | 交接内容 |
|------|------|---------|
| 上游，X 生产侧 | `ort03`，属预处理链 | 产出 X=01：相关方需求 str + 建议簇，FR-BIZ 置状态 `待处理`。01 结构与建簇规则由 ort/数据文件单源 |
| 下游，阶段二执行者 | `biz02` | 消费 `可以分解分配` 的 02 概要节点，按枝梢分解源判据产出 04 完整态；检出缺陷退回 `需biz01修订` + 缺失说明 |
| 同级 | `wft01-eng` / `wft01-nfr` | 各自处理 FR-ENG / NFR |
| 资产 | 21 / 23 / 25 | 读写接口见第六章 |

## 二、输入文档结构及规则（X = 01 相关方需求 · 消费侧）

### 2.1 主输入文档定位

本任务的 X = **01 规范化的相关方需求**，这是产品数据、完整态；本文件按 20 号简称"相关方需求"；现行文件为 `01-eos-specified-requirements.md`。X 的生产侧在 **ort 预处理链**，即 ort00~03，不在任何 wft 人类方案内——因此本任务对 01 只有**消费侧视图**。对照 93 §四.2：本需求-方案对的首个 X 没有"生产它的 A 的第三章"，只剩 B 的第二章一栏。

本任务运行时的**主输入对象** = X 中处于 `待处理` 的 **FR-BIZ 需求叶**，即 str，按角色分批、每批 ≤10 条、同簇需求优先成批——即本任务的"需求叶节点"。读 X 时按 2.2 的四级坐标定位可承接对象。

### 2.2 01 的树形结构与级物理意义（X 树 · 消费视图）

X 即 01，是本次映射的自变量，本任务按**四级坐标**读它。文档完整结构、字段与写读约定单源 = [91 规范 §11](../../91-eos-biz-eng-spec.md) + 01 数据文件自身，不在此重述；此处为本任务消费的树视图：

```
01 规范化的相关方需求
└── 业务域 ──────────── ① 归属域级
    └── 相关方角色 ───── ② 角色级，即 str 的归属对象
        └── 需求簇 ───── ③ 簇级，业务对象闭环的种子
            └── str ──── ④ 需求叶
```

| 级 | 是什么 | 本任务消费的物理意义 |
|----|--------|---------------------|
| ① 业务域 | str 与角色的归属域，角色业务域见 21、域根见 23 | **检索上界**：候选场景业务、候选 P 产品类型都在域内找；与 23 域根对账的口子 |
| ② 相关方角色 | str 的归属角色，见 21 的 `ROLE-*` | **批分片与 Reuse 检索范围**：同角色 ≤10 条/批；候选场景业务只在该角色的业务对象闭环里找 |
| ③ 需求簇 | 同一业务对象闭环上的一组 str；簇由 ort 建议，标 `[建议簇]`，biz01 复核 | **本任务聚簇·升格的直接对象**：整簇判定 Reuse→Add；复核可重切或合并；确认后升格为场景业务 bph-biz，见 §4.1 |
| ④ str 需求叶 | 单条规范化的相关方需求，含类型/优先级/状态/正文/来源映射 | **承接最小对象**：正文→推导文档要素的输入；`类型`→路由，FR-BIZ 归本任务、FR-ENG/NFR 归 eng/nfr；`状态`→受理门槛，见 2.4 |

> **注 1 · 业务域与需求簇是目标组织级**：01 现行物理文件以角色分片挂 str；业务域、需求簇两级是**目标形态**，随 01 模板重建与 ort 建簇动作落位，属批次待办。落位前本任务按 str 的 `所属角色` + 21 角色业务域推定坐标，簇在读时归拢、标 `[待复核]`，不视为已定结构。
>
> **注 2 · 文档不是需求树的一级**：str 正文点名文档/表单的句子是**内容**、不是树位——它驱动本任务为该簇产出哪些文档枝梢，见第三章。文档含其任务节点是需求的**满足位**，属 Y 侧，不在 X 树里占级。

### 2.3 X 侧规则（切分、建簇与重切）

- str 的**切分规则**，即分解规则，由 ort 预处理链按"可单点分配"制定并执行——本任务不重切需求叶，只消费。
- **建簇**：ort 产出 str 时按"可归入同一业务对象闭环"给出建议簇，标 `[建议簇]`；簇边界是本任务的复核对象——复核可拆分、合并或重切簇，见 §4.1；确认后按簇升格场景业务。
- 违规路径：若 str 粒度无法单点归入一个业务对象闭环、混了多关注点 → 标记 `需退回重切` → 回 ort 链按建议拆分后重新进入。
- 承载量超限、一个簇或一批吞不下 → 分批进入；≤10 条/批是软限制，人类可确认放宽。

### 2.4 受理门槛（输入校验）

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 需求状态 = `需退回重切` | 不可处理 | 输出退回记录 → 退出 |
| 需求状态 ≠ `待处理` | 不可处理 | 输出当前状态 → 退出 |
| 需求分属多角色 | 不可处理 | 输出角色分布 → 退出 |
| 需求类型含 FR-ENG / NFR | 路由错误 | 输出类型分布 + 路由指引 → 退出 |
| 同角色需求 > 10 条 | 软限制 | 输出超限提示 → 人类确认 |
| 无待处理需求 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

### 2.5 依赖与校验（读 X 时）

- str 正文语义自洽、`所属角色` 标注齐备：ort03 已归一化，业务域坐标在 21 角色侧。缺标或矛盾 → 标 `[需确认]`，不自动推进。
- **簇内一致性**：同一簇的 str 应指向同一业务对象、语义不漂移——簇内混对象 → 输出重切或拆簇提示，不自动拆。
- 读 X 遵循 91 §A.3.3 读取协议：AI 可以处理节点优先、逐节点加载、按需扩大，不默认加载全文。

## 三、输出文档结构及规则（Y = 02 业务流程概要 · 生产侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程** 的**概要态**，即 02，不含叶；Y 的**完整态** 04 由阶段二 biz02 产出。概要 = 同一份逻辑产品数据的骨架形态，只是一个需求-方案对的中间形态、不算它的一端——故本任务写出的节点目标状态是"**可供阶段二展开**"，而非"自成完整的业务流程"。

### 3.2 输出空间的两棵树（Y 树 · 生产视图）

本任务的 Y 即业务流程，不在一条树上——**同一批业务输出文档在两条独立的树里各得其位**：**R 业务链树**回答"某角色在哪个场景、按什么序、处理哪些业务输出文档完成闭环"，讲的是履职与工作序；**P 输出产品树**回答"这批输出文档作为构件产品数据，属于哪个产品/构件/WBS 包、怎么生成与流转"，讲的是产品数据与依赖。两树在**输出文档以及任务节点**处对位互连、经**认亲**互指；不是一棵树的共享节点。

**树一 · R 角色履职树，写入 02 概要**

```
R 角色履职树
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的一类职责范围
            └── 场景业务 ─ ④ 一个业务对象闭环，分 D 执行与 PCA 管理
                └── 业务输出文档 ─ ⑤ 该闭环产生与流转的文档，即履职对象
                    └── 输出文档任务节点 ─ ⑥ 文档上的活动节点 / 正文条目，是叶
```

| 级 | 节点与意义 | 在本任务的来源 / 处置 |
|----|-----------|----------------------|
| ① | 业务域——归属域 | 承袭 21／23 域根：作定位与 P 对账域，不产出 |
| ② | 相关方角色——主责角色，即业务对象生命周期的主推动者 | 承袭 21 的 `ROLE-*`：作 02 分片与 Reuse 宿主范围，不产出 |
| ③ | 角色职责——角色承担的一类职责范围 | 目标组织级，随 02／21 演进：本任务不产该节点 |
| ④ | 场景业务 bph-biz——一个业务对象闭环，分 D 或 PCA | 本任务新建/修订单位 + 人类确认挂点：承接 str、职责边界、收敛自查、推进 `可以分解分配` |
| ⑤ | 业务输出文档——该闭环产生与流转的文档 | 本任务产出枝梢，也就是最深结构层：概要说明 + 承接判据 + 分解源判据展开项 + P 认亲 |
| ⑥ | 输出文档任务节点——文档上的活动节点 / 正文条目 | 叶：非 02 树位，本任务只预告，交 biz02 落叶，04 定义 |

**树二 · P 输出产品树，组装进 23**

```
P 输出产品树

    └── 产品类型 ─────── ② 产品类别，如 采购产品 / 实物产品
        └── 产品构件类型 ─ ③ 构件分类，如 自研 / 外购 / 复用 / 项目…
            └── 构件WBS 包 ── ④ 一批数据依赖闭合的产品数据单元
                └── 构件产品数据，即业务输出文档 ─ ⑤ 该构件/WBS 包承载的产品数据文档
                    └── 产品数据任务节点 ─ ⑥ 数据文档上的活动节点 / 正文条目，是叶
```

| 级 | 节点与意义 | 在本任务的来源 / 处置 |
|----|-----------|----------------------|
| ① | 业务域——归属域 | 承袭 23 域根：认亲检索与完备对账的域边界 |

> **认亲 = 两树对位**：R 场景链里的每张输出文档，逐一识别其 P 归属，即产品类型×构件×WBS 包，归位 P 树；两树靠这层互指联通。04 由 biz02 产出，是双视角完整态，以场景为单位把 R 链序与 P 位置并成一份。

> **概要边界**：本任务把输出文档写到**名称/概要 级**——R 侧到"文档枝梢 + 分解源判据"，P 侧到"产品数据归位 + 组装/完备结论"；任务节点即叶、字段级详设、P 详设都归 biz02/biz03，不在本任务展开。
>
> **单源**：R／P 两棵树拓扑与级语义的**权威将落 23 树画像区**，见 93 §4.1。本图是 biz01 的**任务视图**，试点先行、作 schema 对齐靶；权威落定后此处只引用不重述。单文档树，即 01 与 02，单源 = 各自数据文件的树画像区。

### 3.3 节点类型与概念（= Y 侧的结构知识）

> 方法读法：02 概要 = 一棵不含叶的树。**场景业务 = 各级枝干**，即聚合层；**输出文档 = 枝梢节点**，即业务输出文档、架构树末级。活动节点 / 正文条目 = **Y 完整态 04 的叶节点**，由阶段二定义成叶——概要不含叶，故其名称在本任务只以枝梢**分解源判据展开项**出现、不占 02 树位。**跨需求-方案对承接，即 04→05，只取 04 的叶**：[94 §1.2](94-eos-sys-dev-dbs.md) 依据三说承接的定义域取需求侧的**原子，即叶**，粗粒度节点不能被 1:1 分配，**故枝梢不参与承接**。"04 输出文档 → 功能表单"是**页面视角的转译**，不是承接。

- **场景业务，即枝干**：一个主责角色——业务对象生命周期的主推动者——的一个业务对象闭环，由一组有流转依赖的输出文档序列构成。类型二分类：**执行类 D**，从需求提出到需求满足；**管理类 PCA**，计划→监控→分析→纠正，须含计划清单输出文档 + 承载 C/A 的输出文档。
- **输出文档，即枝梢 PL5**：场景业务的组成单元。**枝梢双向物理意义**——①**承接判据**：本枝梢承接哪类需求或业务，属承接侧；②**分解源判据**：本枝梢将被阶段二分解出哪些叶节点，含活动、正文条目、表单，即交给 biz02 的规则接口。两条判据共享同一物理意义，避免"承接说能来、分解实现不了"的结构性空洞。
- **两树对位，即认亲**：R 树与 P 树是两条独立树，见 §3.2——同一份业务输出文档在 R 侧是场景履职链的一环，即该角色按什么序处理它；在 P 侧是某 产品类型×构件×WBS 包 的产品数据，即属哪个域的产品、怎么生成、与哪些前序文档有数据依赖。两树经**认亲**互指，见 §4.4：本任务逐枝梢识别其 P 归属并归位；一张文档可被多个场景引用，但 P 侧产品数据位唯一。
- 输出文档按封面模式分**正式**与**轻量**：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。判据见 91 §2。
- **任务类型 R4**：场景业务中第一个有任务类型的文档必然为**计划**，这是闭环启动机制。
- **PL6 叶之预告**，即枝梢分解源判据展开项：有任务类型的文档预告其活动节点，即 PL6-A 行为锚点——谁审批、通过后到哪，供人类确认；正文为集合容器且条目满足**三独立**，即独立名称、独立定义要素、独立生命周期时，预告其正文条目，即 PL6-B 叶清单。PL6 是 Y 的**叶**，完整态 04 由阶段二定义成叶；本任务在 02 只写**预告**，各带内联稳定标签作 02→04 追溯键，**不是 02 的树节点**。

### 3.4 Y 侧规则（构建与收敛）

- **概要边界，结构判定级**：本任务只做结构级判定——文档是否存在，到名称级；封面模式、候选引擎、开发方式、任务层、条目层三独立。**字段级详设留阶段二**。
- **场景业务构建规则**，用于 Phase C 新建：识别触发 → 追踪自然终点，不得在终点之后扩展 → 闭合验证 → 边界四标准，即完整性、一致性、紧凑性、粒度匹配，产出场景职责边界陈述。
- **文档序列构建规则**：D 类按输入-输出传递链排列；PCA 类按 P→C→A 管理循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有枝干，才上溯建更高层。

写入 bph-biz 概要节点，字段对齐 02 §4.1 模板、逐字同名：

## 四、输出与输入转换规则

### 4.1 承接规则（X 叶 → Y 枝干/枝梢）

- **单承接**：一条相关方需求只归入**一个**场景业务——可 N:1，即多条需求或多份文档汇聚一个场景；不可 1:N。违反时先判定类型：程序违规，即切分未按消费方语义范围 → 退回重切；切不动的整体 → 两个出口，节点拆分，或横切式承接走独立分支并作影响面标注。
- **分流**：已有场景业务可直接承接 → **Reuse**，走 Phase B 修订；无宿主 → **Add**，走 Phase C 新建。优先级始终 复用 → 改进 → 新增。
- **改进 = 影响面复查**：对已有枝梢做 Extend/Split/Merge 后，须复查其已承接的既有需求是否失配 → 批量重分配或回退。

## 五、转换流程及检验规则

### 5.1 设计过程（动作序列）

一次运行 = **入口 → 载 X 与存量 Y → 反馈处理 → 承接设计循环 → 覆盖/完备检查 → 人类确认 → 推进 → 写回**：

1. **入口**：按受理门槛判定，见 2.4；退回优先——`需biz01修订` 时读缺失说明、走 Phase B 修订；再处理待反馈；最后路由新需求。
2. **载 X 与存量 Y**：读 `待处理` FR-BIZ 需求条目 + 同角色/同域候选存量 02 概要节点 + 21/23/25 资产，见第六章。
3. **反馈处理**：人类对话修改／整体确认／线下修订；反馈双轨的规则引 91 §A.5。
4. **承接设计循环**——针对一组相关联、落点相近的需求叶：
   - Phase A 路由 → Reuse，归已有场景；或 Add，进待聚合池；
   - Phase B/C 生成概要，见 §三.3／§三.4／§四；
   - **单承接检查** + **影响面复查**；
   - 有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。
5. **覆盖/完备检查**，见 5.2 的关口。
6. **人类确认** → 推进 `可以分解分配`。
7. **写回与落账**：23 资产 + 状态推进 + 基线，引 91 §A.3.3／§A.6；运行时细节不在此重述。

### 5.2 检验规则（关口）

- **单承接检查**：一条需求只归一个场景业务，见 §四.1。
- **承接覆盖检查**，这是本需求-方案对的关口：该场景业务承接的全部需求语义 ⊆ 其业务链即枝梢之并能实现的范围。EOS 实例化 = **端到端闭合检查**——D 从需求提出贯通到需求满足；PCA 按计划→监控→分析→纠正核对，须含计划清单文档 + 承载 C/A 的输出文档，C/A 运行时推进结果不作需求缺口。缺口 → 生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐枝梢要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待阶段二推断]`。
- **治理覆盖检查**：预置治理业务流程概要业务链按角色预定文档集核对；无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以分解分配 ──阶段二锁定──→ 在分解分配 ──阶段二完成──→ 已分解分配
     ↑                       ↑                      │
     │                       │          阶段二退回    │
     └── biz01修订 ──── 需biz01修订 ←───────────────┘
```

上游变更，即新需求汇入，按状态分流：`可以分解分配`→版本递增，未消费；`在分解分配`→版本递增，增量处理；`已分解分配`→`待补充分解分配`→阶段二补全。四态模型与写回范围引 91 §A.6，此处为本任务特化。

### 5.4 运行时外壳（引 91 附录A，不重述）

Step Start / Step 1~5 / Step End 的会话机制、反馈双轨状态机、git 基线、Step End 三区模板 = 91 附录A 统一协议；本任务只保留特化参数——锚点需求 = 本任务承接的全部 FR-BIZ 需求条目；操作条目 = 场景职责边界 + 业务链枝梢 + PL6-B 条目名；推进目标 = `可以分解分配`。清除与级联条件见 §5.3 状态机与上游分流，会话级清除引 91 §A.6。
