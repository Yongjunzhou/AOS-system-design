## 一、目的与目标

### 1.1 本任务在设计链上的位置

设计开发 = 由需求到方案的逐对生成。业务路径的首对，是由相关方需求设计出业务流程：

```
相关方需求 → 业务流程：  X = 相关方需求，不分形态，叶＝系统用例场景级操作
        │  阶段一 承接设计，本任务   —— 产出 Y 概要，不含叶
        ▼
       Y 概要 = 业务流程概要，枝干：场景业务 → 枝梢：文档开发任务之节点
        │  阶段二 分解，阶段二任务 —— 产出 Y 完整态叶节点：系统用例场景级操作
        ▼
       Y 完整态 = 业务流程方案，即「业务流程 → 系统需求」这一步的需求侧 ──▶ 系统需求概要设计任务
```

- 本任务 = 由相关方需求设计出业务流程的**阶段一**：按转换规则做**承接设计**，产出 Y 的概要形态，即业务流程概要。
- **承接的落点由 X 给出**：X 的叶是系统用例场景级操作，它所属的业务输出文档带「所属E2E场景业务」属性，承接即按该属性把叶落到 Y 的场景业务，也就是枝干。
- **概要的位置**：概要是同一份逻辑产品数据即业务流程的骨架形态，**只是一个需求-方案对的中间形态、不算它的一端**；一个需求-方案对的两端是需求与方案两份产品数据、各取完整态。**本次转换**的收敛以 Y 的完整态即业务流程方案达成。
- **概要到枝梢为止、不含叶**：枝梢即**业务输出文档**，本级上它就是**文档开发任务**；叶即**系统用例场景级操作**，挂在活动节点之下，由阶段二在业务流程方案里定义成叶。
- 人类门禁位置：本任务产出概要 → 人类「整体确认」→ 节点推进为 `可以分解分配` → 阶段二可进入。
- 下游退回：阶段二任务检出概要缺陷 → 标 `需biz01修订`，这是对内**反向迭代**，也就是方案迭代需求。

### 1.2 主要目的

> 取信于相关方——「你听懂了我的需求和意图」。把 X 的相关方需求即业务功能需求转化为 Y 概要即业务流程概要的声明与骨架：不仅承接需求已说出的内容，更识别其指向的端到端完整业务意图，按本需求-方案对的转换规则落到概要的各级枝干/枝梢，为阶段二分解出完整态提供可展开的输入与分解源判据。

### 1.3 目标

1. **识别可承接对象**：从待处理条目中按业务输出文档的三个坐标归拢出同一业务对象闭环的一组，判定是否已有可承接的场景业务，也就是枝干——有则**复用**；否则**新建**。
2. **生成场景业务枝干**：判定执行类或管理类、命名、边界定义，边界即主责角色的业务对象闭环。
3. **补齐枝梢**：X 的业务输出文档已列出，本任务为每张补齐 Y 侧内容——封面模式，即正式或轻量；活动节点与系统用例场景级操作，到名称级；并写**承接判据 + 分解源判据**。
4. **写任务关系**：文档间流转顺序 + 需求明示的任务触发关系，用业务语言表达。
5. **单承接保证**：叶的落点由业务输出文档的场景属性决定，同一业务输出文档下的叶必落同一个场景业务——单承接由树形保证；本任务检查该文档的三坐标齐备与分流正确，见 §2.3／§4.1。
6. **承接覆盖检查**：基于端到端闭环核对「承接了的需求有没有被业务链实现」——检出缺口生成补充原始需求材料，不脑补节点。
7. **P 对齐与组装**：逐文档判定与 23 输出产品架构 P 侧的对齐；再做 WBS 归组 + 输出产品架构一致性检查 + 按构件产品数据清单名称级推断缺口。

### 1.4 本任务负责 / 不负责

**负责**：承接分配叶到概要枝干/枝梢，走 复用 → 改进 → 新增 的分流；生成概要节点与传出承诺；人类确认后写回 23 输出产品架构与推进状态；处理下游退回，即反向迭代修订。

**不负责，均指向其实际归属**：

- 引擎能力功能需求 → 引擎能力设计任务；非功能需求 → 非功能需求设计任务。二者在输入校验检出后退出
- Y 完整态分解，含叶节点与字段级详设 → 阶段二任务
- 页面层级/菜单设计 → 系统需求概要设计任务
- 业务人员确认 → 人类线下活动
- **X 侧的切分与建树** → 需求预处理链。本任务只受理或退回，不自行重切、不重定坐标，见 §2.3
- **治理业务流程概要**中无需求输入者 → 由 23 输出产品架构预置，由人类按平台治理业务渐进增补、经预处理链补需求，本任务不主动展开

### 1.5 与上下游的衔接

| 方向 | 任务 | 交接内容 |
|------|------|---------|
| 上游，X 生产侧 | 需求预处理链的规范化任务 | 产出 X：功能需求树——业务输出文档 → 任务节点 → 条目，业务输出文档上落业务对象闭环的场景坐标；业务功能需求条目置状态 `待处理`。X 的结构与切分、建树规则由预处理链与相关方需求数据文件单源 |

## 二、输入文档结构及规则（X = 相关方需求 · 消费侧）

### 2.1 主输入文档定位

本任务的 X = **相关方需求**，现行文件 `01-eos-specified-requirements.md`，是产品数据。它与其他产品数据不同，**不分概要态与完整态**——一产出即是完整态，最深一级为系统用例场景级操作，见 §2.2。它的生产侧是**需求预处理链**的四个任务，不在 SKILL 指南之列——故本任务对它只有**消费侧视图**。

相关方需求含两棵树——功能需求树与非功能需求树。**本任务消费功能需求树**；非功能需求树归非功能需求设计任务。

本任务运行时的**主输入对象** = X 中处于 `待处理` 的**业务功能需求条目**，即功能需求树的叶，按业务输出文档聚集、同一张业务输出文档下的条目优先成批，每批 ≤10 条。读 X 时按 §2.2 的树定位可承接对象。文档的完整结构、字段与读写约定以 91 号规范 §11 与相关方需求数据文件自身为准。

### 2.2 相关方需求的树形结构与级语义（X 树 · 消费视图）

X 是本次映射的自变量。下图是该树在本任务视图下的展开，树形与级语义以《EOS 系统设计产品数据分解结构》（94 号文档）§2.1.1 为准。

```
相关方功能需求
└── 业务输出文档 ──────── ① 根　带三个坐标属性：所属主责角色 × 所属产品构件 × 所属E2E场景业务
    └── 任务节点 ──────── ② 该业务输出文档开发所对应的任务
        └── 系统用例场景级操作 ─ ③ 任务节点中的一个系统用例场景级操作，是叶
```

| 级 | 节点与意义 | 怎么得到 | 本任务如何处置 |
|----|-----------|---------|--------------|
| ① | 业务输出文档——根；三个坐标属性随节点携带 | **预处理链产出**：切分按业务对象闭环定下场景坐标，规范化补满本树三级 | **落点与认亲坐标的来源**：由「所属E2E场景业务」定 Y 的场景业务即承接落点；由「所属产品构件」定 P 侧构件坐标即认亲落点；本级到 Y 侧成为**文档开发任务**，即枝梢，本任务为它补齐概要说明与两条判据 |
| ② | 任务节点——该业务输出文档开发所对应的任务 | **预处理链产出** | **枝梢任务类型的捕获来源**：读任务节点即知该文档有无任务、是哪一类，见 §4.2 |
| ③ | 系统用例场景级操作——条目，是叶 | **预处理链产出**：规范化时归一化并落位 | **承接最小对象**：正文是推导文档要素的输入；`类型`→路由，业务功能需求归本任务、引擎能力功能需求与非功能需求归各自任务；`状态`→受理门槛，见 §2.4 |

> **三个坐标是属性、不占级位**：所属主责角色／所属产品构件／所属E2E场景业务随业务输出文档携带——角色与场景是本份数据的**索引／分片轴**，不是归集级。
>
> **X 的业务输出文档到 Y 侧成为枝梢**：同一张业务输出文档，在 X 里是需求承载级，在 R／P 两棵树里是 ⑤ 文档开发任务。故本任务的文档清单以 X 的业务输出文档为准，见 §4.2。
>
> **落位现状**：相关方需求的现行物理文件以角色分片直接挂条目，尚未含业务输出文档与任务节点两级；本任务读时按条目正文语义归拢，标 `[待复核]`。

### 2.3 X 侧规则（复核与退回）

- **切分与建树权在预处理链**：业务对象闭环的切分、业务输出文档的三个坐标、任务节点与条目的落位，都由预处理链制定并执行——**本任务不重切 X、不重定坐标**。
- **复核两项**：业务输出文档的三个坐标是否齐备且唯一；条目的语义是否与它所属业务输出文档的三坐标一致。二者通不过 → 标 `需退回重切` → 回预处理链处置后重新进入。
- **承载量超限**，一批吞不下 → 分批进入；≤10 条/批是软限制，人类可确认放宽。
- **Y 侧的节点拆分与改 X 不是一回事**：Y 侧装不下时的拆分或横切出口见 §4.1，它动的是 Y 的节点，不回头改 X。

### 2.4 受理门槛（输入校验）

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 条目状态 = `需退回重切` | 不可处理 | 输出退回记录 → 退出 |
| 条目状态 ≠ `待处理` | 不可处理 | 输出当前状态 → 退出 |
| 条目分属多个主责角色 | 不可处理 | 输出角色分布 → 退出 |
| 条目类型含引擎能力功能需求 / 非功能需求 | 路由错误 | 输出类型分布 + 路由指引 → 退出 |
| 同一业务输出文档下条目 > 10 条 | 软限制 | 输出超限提示 → 人类确认 |
| 无待处理条目 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

### 2.5 依赖与校验（读 X 时）

- 业务输出文档的三个坐标齐备、条目正文语义自洽：预处理链已归一化，主责角色的业务域在 21 相关方角色资产侧。缺标或矛盾 → 标 `[需确认]`，不自动推进。
- **同一业务输出文档内的一致性**：该文档下的条目应指向同一业务对象、语义不漂移——漂移 → 输出退回重切提示，不自动拆。
- 读 X 遵循 91 号规范 §A.3.3 读取协议：AI 可以处理节点优先、逐节点加载、按需扩大，不默认加载全文。

## 三、输出文档结构及规则（Y = 业务流程概要 · 生产侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程** 的**概要态**，即业务流程概要，不含叶；Y 的**完整态**即业务流程方案，由阶段二任务产出。概要 = 同一份逻辑产品数据的骨架形态，只是一个需求-方案对的中间形态、不算它的一端——故本任务写出的节点目标状态是「**可供阶段二展开**」，而非「自成完整的业务流程」。

### 3.2 输出空间的两棵树（Y 树 · 生产视图）

本任务的 Y 即业务流程，不在一条树上——**同一批业务输出文档在两条独立的树里各得其位**：**R 角色履职树**回答「某角色在哪个场景、按什么序、处理哪些业务输出文档完成闭环」，讲的是履职与工作序；**P 输出产品树**回答「这批输出文档作为构件产品数据，属于哪个产品/构件/WBS 包、怎么生成与流转」，讲的是产品数据与依赖。两树在**枝梢以及其下的活动节点**处对位互连、经**认亲**互指；不是一棵树的共享节点。

**树一 · R 角色履职树（业务运行角色履职视角）**

```
角色履职业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的一类职责范围
            └── 场景业务 ─ ④ 一个业务对象闭环，分执行类与管理类
                └── 业务输出文档 ─ ⑤ 待开发的那份；本级即文档开发任务，是枝梢
                    └── 活动节点 ─ ⑥ 处理角色/动作/状态变迁
                        └── 系统用例场景级操作 ─ ⑦ 是叶
```

| 级 | 节点与意义 | 怎么得到 | 本任务如何处置 |
|----|-----------|---------|--------------|
| ① | 业务域——归属域 | **承袭** 21 相关方角色资产／23 输出产品架构的域根 | 作定位与 P 对账域，不产出 |
| ② | 相关方角色——主责角色，即业务对象生命周期的主推动者 | **承袭** 21 相关方角色资产的 `ROLE-*` | 作业务流程概要的分片与复用宿主范围，不产出 |
| ③ | 角色职责——角色承担的一类职责范围 | **目标组织级**，随业务流程概要与角色资产演进 | 本任务不产该节点 |
| ④ | 场景业务——一个业务对象闭环，分执行类或管理类 | **本任务产出**（复用 → 新建） | 本任务新建/修订单位 + 人类确认挂点：承接条目、职责边界、收敛自查、推进 `可以分解分配` |
| ⑤ | 业务输出文档——待开发的那份；本级即**文档开发任务**，是枝梢 | **本任务产出**，写到概要说明级；文档本体由 X 的业务输出文档给出，见 §2.2 | 产出枝梢，也就是最深结构层：概要说明 + 承接判据 + 分解源判据展开项 + P 认亲 |
| ⑥ | 活动节点——处理角色/动作/状态变迁 | **阶段二产出** | 非概要树位，本任务只预告；其下还有系统用例场景级操作 |
| ⑦ | 系统用例场景级操作——是叶 | **阶段二产出** | 非概要树位，本任务只预告，交阶段二落叶、在业务流程方案里定义 |

> **⑤ 与「任务」的关系**：⑤ 说的是「要开发哪份文档」这件事，每份业务输出文档对应一个 ⑤ 节点，与它有没有内嵌的计划／流程／工单任务无关——那是 ⑥ 以下的事。
>
> **平台侧的 R 树**：本任务的主体走**各业务域的 R 树**；平台自身的治理业务走**平台侧的 R 树**——同一棵 R 树在「平台本身」这一侧**少「角色职责」一级**：业务域 → 相关方角色 → 场景业务 → 业务输出文档 → 活动节点 → 系统用例场景级操作，因为业务配置角色不按角色类型再归纳。层级差非遗漏。业务流程概要里预置的治理节点 bph-biz-GOV-* 即平台侧场景，本任务对其只作渐进增补，不主动展开。

**树二 · P 输出产品树（产品开发视角）**

```
输出产品业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 产品类型 ─────── ② 部门级的端到端业务输出
        └── 产品构件类型 ─ ③ 科室级的端到端业务输出
            └── 构件开发WBS（包）─ ④ 文档序列
                └── 业务输出文档 ─ ⑤ 待开发的那份；本级即文档开发任务
                    └── 活动节点 ─ ⑥ 处理角色/动作/状态变迁
                        └── 系统用例场景级操作 ─ ⑦ 是叶
```

| 级 | 节点与意义 | 怎么得到 | 本任务如何处置 |
|----|-----------|---------|--------------|
| ① | 业务域——归属域 | **承袭** 23 输出产品架构的域根 | 认亲检索与完备对账的域边界 |
| ② | 产品类型——产品类别，如采购产品、实物产品 | **AI 建议 + 人类确认**，走对齐判据的三档：引用／扩展／新建，见 §4.4 | 本任务按需建立或确认 |
| ③ | 产品构件类型——构件分类，如自研、外购、复用、项目 | **AI 建议 + 人类确认**，同上 | 同上 |
| ④ | 构件开发WBS（包）——一批数据依赖闭合的产品数据单元 | **AI 建议 + 人类确认**，同上 | 同上 |
| ⑤ | 业务输出文档——待开发的那份；本级即**文档开发任务** | **本任务认亲归位**：R 树的文档逐一标定 P 坐标 | 本体唯一——可被多场景引用、只占一个产品数据位 |
| ⑥ | 活动节点——处理角色/动作/状态变迁 | **阶段二产出** | 非本任务产出，只预告 |
| ⑦ | 系统用例场景级操作 | **阶段二产出** | 叶：非本任务产出，只预告，交阶段二落叶、在业务流程方案里定义 |

> **认亲 = 两树对位**：R 场景链里的每张业务输出文档，逐一识别其 P 归属，即产品类型×构件×WBS 包，归位 P 树；两树靠这层互指联通。业务流程方案由阶段二产出，是双视角完整态，以场景为单位把 R 链序与 P 位置并成一份。
>
> **本树的 ⑤ 即 X 的业务输出文档，认亲坐标由 X 给出**：X 的该节点上带「所属产品构件」属性，本任务据此定位 P 侧构件坐标，见 §4.2；同一张文档因此有三个视图：X 侧的需求承载级、R 侧的文档开发任务、P 侧的产品数据位。
>
> **概要边界**：本任务把枝梢写到**名称/概要 级**——R 侧到「枝梢 + 分解源判据」，P 侧到「产品数据归位 + 组装/完备结论」；叶、字段级详设、P 详设都归阶段二与其下游任务，不在本任务展开。
>
> **树权威**：R／P 两棵树的拓扑与级语义以《EOS 系统设计产品数据分解结构》（94 号文档）为准；23 输出产品架构按其维护节点数据，X 与 Y 两份产品数据的树画像以各自数据文件的树画像区为准。

### 3.3 节点类型与结构要点

> 方法读法：**概要态 = 一棵不含叶的树**。**场景业务 = 各级枝干**，即聚合层；**业务输出文档 = 枝梢节点**——本级上它就是**文档开发任务**，即概要的最深一级；**系统用例场景级操作 = 叶**，挂在活动节点之下，由阶段二在业务流程方案里定义成叶——概要不含叶，故其名称在本任务只以枝梢**分解源判据展开项**出现、不占概要的树位。**跨需求-方案对承接只取上游的叶**——承接的定义域是需求侧的**原子**，粗粒度节点不能被 1:1 分配，**故枝梢不参与承接**。业务流程方案的输出文档转译到功能表单，走的是**页面视角**、不是承接，见 91 号规范 §7.3。

- **场景业务，即枝干**：一个主责角色——业务对象生命周期的主推动者——的一个业务对象闭环，由一组有流转依赖的业务输出文档序列构成。类型二分类：**执行类**，从需求提出到需求满足；**管理类**，计划→监控→分析→纠正，须含计划清单输出文档 + 承载监控与分析环节的输出文档。
- **业务输出文档，即枝梢**——本级上它就是**文档开发任务**：一份要开发的业务输出文档。**枝梢双向物理意义**——其一**承接判据**：本枝梢承接哪类需求或业务，属承接侧；其二**分解源判据**：本枝梢将被阶段二分解出哪些叶节点，含活动节点与系统用例场景级操作，即交给阶段二的规则接口。两条判据共享同一物理意义，避免「承接说能来、分解实现不了」的结构性空洞。
- **两树对位，即认亲**：R 树与 P 树是两条独立树，见 §3.2——同一份业务输出文档在 R 侧是场景履职链的一环，即该角色按什么序处理它；在 P 侧是某 产品类型×构件×WBS 包 的产品数据，即属哪个域的产品、怎么生成、与哪些前序文档有数据依赖。两树经**认亲**互指：本任务逐枝梢识别其 P 归属并归位，坐标由 X 的业务输出文档给出；一张文档可被多个场景引用，但 P 侧产品数据位唯一。
- 业务输出文档按封面模式分**正式**与**轻量**：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。判据见 91 号规范 §2。
- **任务类型的启动规则**：场景业务中第一个有任务类型的文档必然为**计划**，这是闭环启动机制。
- **叶之预告**，即枝梢分解源判据展开项：预告其**活动节点**，即行为锚点——谁审批、通过后到哪，供人类确认；再预告活动节点下的**系统用例场景级操作**。叶是 Y 的完整态，在业务流程方案里由阶段二定义；本任务在概要里只写**预告**，各带内联稳定标签作概要到完整态的追溯键，**不是概要的树节点**。

### 3.4 Y 侧规则（构建与收敛）

- **概要边界，结构判定级**：本任务只做结构级判定——文档是否存在，到名称级；封面模式、候选引擎、开发方式、活动节点。**字段级详设留阶段二**。
- **场景业务构建规则**，用于新建：识别触发 → 追踪自然终点，不得在终点之后扩展 → 闭合验证 → 边界四标准，即完整性、一致性、紧凑性、粒度匹配，产出场景职责边界陈述。
- **文档序列构建规则**：执行类按输入-输出传递链排列；管理类按计划→监控→分析循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有枝干，才上溯建更高层。

### 3.5 要素清单（本任务写入概要节点必须带齐）

写入业务流程概要节点，字段对齐业务流程概要数据文件 §4.1 的模板、逐字同名：

- **块头字段**：块ID / 节点类型 bph-biz / 视角类型 / 类型 执行类或管理类 / 主责角色 / 当前状态。
- **正文要素行**，依次为：
  - 业务域 / 产品路径；用户角色；场景职责边界陈述；
  - **承接的规范化的相关方需求**——业务功能需求条目引用，N:1 汇聚；治理预置节点按治理覆盖口径；
  - **业务链**，每枝梢一段，段内六项：概要说明，即名称/用途/封面模式/开发方式，结构判定级；任务类型；支撑引擎候选 `[推断]`；**分解源判据展开项**，即任务主要节点 + 条目名，各带内联稳定标签，见 §3.3；任务关系；**P 认亲**，即所属 产品类型×构件×WBS 包 + 对齐判据档位；
  - **P 组装结论**——WBS 归组 + 输出产品架构一致性结论 + 缺口推断与候选节点建议；
  - 推理依据与补全说明；完备性检查结果；补充材料引用；变更影响声明 / 版本号。

### 3.6 传出承诺（给阶段二任务）

本任务把概要节点交给下游时，承诺节点达到：

1. 状态 = `可以分解分配`，在人类「整体确认」之后；
2. 要素清单见 3.5，齐备；概要说明为结构判定级；
3. **每个枝梢带分解源判据**——声明阶段二可分解出的活动节点与系统用例场景级操作，到名称级；并带 **P 认亲**，即所属 产品类型×构件×WBS 包 + 对齐判据档位；
4. 覆盖检查结果落账，见第五章——本节点承接的全部需求语义 ⊆ 其业务链所能实现的范围；缺口已走补充材料回路，不是隐藏遗漏。

> **接口契约，与阶段二任务的受理前提互为对侧**：阶段二受理本任务传出的业务流程概要节点，状态为 `可以分解分配` 或 `待补充分解分配`；它以 §3.5／§3.6 为对照——要素或分解源判据缺失、冲突 → 退回 `需biz01修订` + 缺失说明。契约两侧分别成文于本任务 §3.6 与[阶段二任务的指南](eos-biz02-bph2bpd.md) §2.3；核对方法 = 93 号规范 §4.2 的逐条映射。

## 四、输出与输入转换规则

### 4.1 承接规则（X 叶 → Y 枝干/枝梢）

- **落点由 X 给出**：叶落到哪个场景业务，由叶所属业务输出文档上的「所属E2E场景业务」属性决定，见 [94 号文档 §1.4](94-eos-sys-dev-dbs.md)。同一业务输出文档下的全部叶共用该属性，故**必落同一个场景业务——单承接由树形保证**，不靠逐条检查；本任务的检查落在该文档的三坐标齐备与分流正确上，见 §2.3。
- **业务输出文档整体分流**：它对应的场景业务已在 Y 中存在 → **复用**，走修订转换；尚无 → **新建**。优先级始终 复用 → 改进 → 新增。
- **落点已定而业务输出文档内部语义跨界**：属 X 的缺陷，标 `需退回重切` 回 ort 链，不在 Y 侧就地分。
- **Y 侧装不下时**：节点拆分，或横切式承接走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有枝梢做扩展/拆分/合并后，须复查其已承接的既有条目是否失配 → 批量重分配或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则与判据出处 |
|--------|--------------------|
| 业务域/路由 | 读业务输出文档的「所属主责角色」→ 21 相关方角色资产的业务域 → 映射 23 输出产品架构的产品类型路径；缺则 `[推断]` |
| 场景业务类型 | 需求动作词偏向执行类/管理类；存疑标 `[推断]` |
| 文档清单与来源 | **以 X 的业务输出文档为准**——本任务不另立清单；覆盖检查发现应有而未列者 → 走补充材料回路，见 §5.2 |
| P 认亲 | 读业务输出文档的「所属产品构件」属性 → 定位 P 侧构件坐标；再走对齐判据，见 §4.4 |
| 封面模式 | 是否需审批/发布/版本追溯等生效动作 |
| 任务类型 | 读任务节点直接捕获；任务节点只给出管理模式→判定+`[待阶段二推断]`；任务节点缺失→推断+`[待阶段二推断]`；首个有任务类型的文档必为计划 |
| 支撑引擎候选 | 按正文数据类型匹配功能引擎，**全量 `[推断]`**；引擎清单读 25 引擎资产，不缓存 |
| 系统用例场景级操作名 | 由活动节点展开，名称级捕获；只提管理模式→`[待阶段二推断]` |
| 文档间关系 | 流转顺序，执行类走传递链、管理类走循环；加需求明示的任务触发关系 |

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回需求侧／宿主误匹配 → 业务链关系检测，分 确认／无新增／引擎判定变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查 → P 组装重跑。

### 4.4 对齐规则（输出 → 资产）

逐枝梢判定与 23 输出产品架构 P 侧的对齐，分三档：**已有、直接引用**，**需扩展**，**无、给新建建议**；再执行 WBS 归组，判据是数据依赖链；加输出产品架构一致性检查，查 归属冲突／误新建／误引用；再加按构件产品数据清单名称级缺口推断，不依赖任务类型或引擎。

**缺口的两条出口**：本批涉及的 WBS 包对照闭合模型检查，应有而缺失者 → 以**候选节点**挂 P 树、标疑似态；候选只是建议、不直成正式文档——人类裁决「需要」→ 转原始需求材料 → 经需求预处理链 → 条目 → 正常设计落地；「不要」→ 候选废弃。

判据动作成文于 §6.3；判据之家 = 91 号规范 §5.3.1，即对齐判据族；引用数据读 23 输出产品架构。

#### 5.1.1 Step 1 · 设计材料加载

读 `待处理` 业务功能需求条目 + 同一业务输出文档／同域候选存量概要节点 + 21 相关方角色资产／23 输出产品架构／25 引擎资产，见第六章；加载按 §2.5 的读取规则。

#### 5.1.2 Step 2 · 反馈处理

人类对话修改／整体确认／线下修订；反馈双轨按 91 号规范 §A.5 记录。

#### 5.1.3 Step 3 · 承接设计循环

针对一组相关联、落点相近的叶：

- 路由 → 复用，归已有场景业务；或新建，进待聚合池；
- 生成概要，见 §3.3／§3.4／§4；
- **单承接检查** + **影响面复查**；
- 有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.4 Step 4 · 覆盖与完备检查

执行 §5.2 的关口检查。检出缺口 → 生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。

#### 5.1.5 Step 5 · 写回与落账

23 输出产品架构 + 状态推进 + 基线，引 91 号规范 §A.3.3 与 §A.6。

### 5.2 检验规则（关口）

- **单承接检查**：单承接由 X 树形保证——同一业务输出文档下的叶共用一个场景坐标；本任务检的是该文档的三坐标齐备与分流正确，见 §2.3／§4.1。
- **承接覆盖检查**，这是本需求-方案对的关口：该场景业务承接的全部需求语义 ⊆ 其业务链即枝梢之并能实现的范围。EOS 实例化 = **端到端闭合检查**——执行类从需求提出贯通到需求满足；管理类按计划→监控→分析→纠正核对，须含计划清单文档 + 承载监控与分析环节的输出文档，这两环节的运行时推进结果不作需求缺口。缺口 → 生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐枝梢要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待阶段二推断]`。
- **治理覆盖检查**：预置治理业务流程概要业务链按角色预定文档集核对；无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以分解分配 ──阶段二锁定──→ 在分解分配 ──阶段二完成──→ 已分解分配
     ↑                       ↑                      │
     │                       │          阶段二退回    │
     └── 本任务修订 ──── 需biz01修订 ←───────────────┘
```

上游变更，即新需求汇入，按状态分流：`可以分解分配`→版本递增，未消费；`在分解分配`→版本递增，增量处理；`已分解分配`→`待补充分解分配`→阶段二补全。四态模型与写回范围引 91 号规范 §A.6，此处为本任务特化。
