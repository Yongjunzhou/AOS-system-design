## 一、目的与目标

### 1.1 本任务在对/链上的位置

设计开发 = 由需求到方案的逐对生成。biz 链首对即**对①**：

```
对①：  X = 相关方需求（01，完整态，需求叶=相关方需求条目）
        │  阶段一 承接设计（本任务 biz01）   —— 产出 Y 概要（02，不含叶）
        ▼
       Y概要 = 业务流程概要（02，枝干：场景业务 → 枝梢：输出文档 PL5）
        │  阶段二 分解（biz02）—— 产出 Y 完整态叶节点（活动/正文条目/表单，04）
        ▼
       Y完整态 = 业务流程（04）──(= 对② 的 X)──▶ 系统需求概要（05，biz03）…
```

- 本任务 = 对① 的**阶段一**：按规则 F 做**承接设计**，产出 Y 的概要形态（02）。
- 概要是 Y 的骨架，不是对端点；对① 的收敛以 Y 完整态（04）达成。
- 人类门禁位置：本任务产出概要 → 人类"整体确认" → 节点推进为 `可以分解分配` → 阶段二可进入。
- 下游退回（biz02 检出概要缺陷 → `需biz01修订`）= 对内**反向迭代**（方案迭代需求）。

### 1.2 主要目的

取信于相关方——「你听懂了我的需求和意图」。把 X 的相关方需求（FR-BIZ）转化为 Y 概要（业务流程概要）的声明与骨架：不仅承接需求已说出的内容，更识别其指向的端到端完整业务意图，按本对规则 F 落到概要的各级枝干/枝梢，为阶段二（biz02 分解出完整态）提供可展开的输入与分解源判据。

### 1.3 目标

1. **识别可承接对象**：从待处理需求叶中识别属于同一业务对象闭环的一组，判定是否已有可承接的场景业务（枝干）——有则**复用（Reuse）**，否则进入新建（Add）。
2. **生成场景业务枝干**：判定类型（D/PCA）、命名、边界定义（主责角色的业务对象闭环）。
3. **生成输出文档枝梢**：逐文档识别——封面模式（正式/轻量）、正文实体类型、任务类型与主要节点、PL6-B 条目（名称级）；每条枝梢写**承接判据 + 分解源判据**。
4. **写任务关系**：文档间流转顺序 + 需求明示的任务触发关系（业务语言）。
5. **单承接保证**：一条需求只归一个场景业务（可 N:1，不可 1:N）——归属冲突走退回/重切。
6. **承接覆盖检查**：基于端到端闭环核对"承接了的需求有没有被业务链实现"——检出缺口生成补充原始需求材料，不脑补节点。
7. **Bn 对齐与组装**：逐文档判定与 23 资产 Bn 侧的对齐（Q1/Q2/Q3）+ PL4 WBS 归组 + 23 一致性检查 + 按构件产品数据清单名称级推断缺口。

### 1.4 本任务负责 / 不负责

**负责**：承接分配需求叶到概要枝干/枝梢（Reuse→Add 分流）；生成概要节点与传出承诺；人类确认后写回 23 资产与推进状态；处理下游退回（反向迭代修订）。

**不负责（路由指向）**：
- FR-ENG 需求 → `wft01-eng`；NFR → `wft01-nfr`（输入校验检出后退出）
- Y 完整态分解（叶节点/字段级详设）→ 阶段二 `biz02`
- 页面层级/菜单设计 → `biz03`
- 业务人员确认 → 人类线下活动
- 无需求输入的治理业务流程概要不主动展开

## 三、输出文档结构及规则（Y = 02 业务流程概要 · 生产侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程** 的**概要态**（02，不含叶）；Y 的**完整态**（04）由阶段二（biz02）产出。概要 = 同一份逻辑产品数据的骨架形态，非对端点——故本任务写出的节点目标状态是"**可供阶段二展开**"，而非"自成完整的业务流程"。

### 3.2 02 的结构要点（schema 引用，不重述）

02 完整结构单源 = [91 规范 §11](../../91-eos-biz-eng-spec.md) + 02 数据文件自身。本任务产出的节点类型 = **业务流程概要节点（bph-biz-XXX，即一个场景业务）**，写入 02 的业务流程概要节点块。

### 3.3 节点类型与概念（= Y 侧的结构知识）

> 方法读法：02 概要 = 一棵不含叶的树。**场景业务 = 各级枝干**（聚合层），**输出文档 = 枝梢节点（PL5，架构树末级）**；PL6 活动节点 / 正文条目 = **Y 完整态（04）的叶节点**，由阶段二定义成叶——概要不含叶，故 PL6 名称在本任务只以枝梢**分解源判据展开项**出现、不占 02 树位。跨对（04→05）承接允许枝梢（文档→功能表单）与叶（PL6→标签页/正文内容）混入——EOS 转译常态。

- **场景业务（枝干）**：一个主责角色（业务对象生命周期主推动者）的一个业务对象闭环，由一组有流转依赖的输出文档序列构成。类型二分类——**执行类（D）**：从需求提出到需求满足；**管理类（PCA）**：计划→监控→分析→纠正（须含计划清单输出文档 + 承载 C/A 的输出文档）。
- **输出文档（枝梢 PL5）**：场景业务的组成单元。**枝梢双向物理意义**——①**承接判据**：本枝梢承接哪类需求/业务（承接侧）；②**分解源判据**：本枝梢将被阶段二分解出哪些叶节点（活动/正文条目/表单），即交给 biz02 的规则接口。两条判据共享同一物理意义，避免"承接说能来、分解实现不了"的结构性空洞。
- 输出文档按封面模式分**正式**（有独立于正文 CRUD 的生命周期）/ **轻量**（无封面，正文即文档）——判据见 91 §2。
- **任务类型（R4）**：场景业务中第一个有任务类型的文档必然为**计划**（闭环启动机制）。
- **PL6 叶之预告（= 枝梢分解源判据展开项）**：有任务类型的文档预告其活动节点（PL6-A 行为锚点：谁审批/通过后到哪，供人类确认）；正文为集合容器且条目满足**三独立**（独立名称/独立定义要素/独立生命周期）时预告其正文条目（PL6-B 叶清单）。PL6 是 Y 的**叶**（完整态 04 由阶段二定义成叶）；本任务在 02 只写**预告**，各带内联稳定标签（作 02→04 追溯键），**不是 02 的树节点**。【定案 2026-09-04】

### 3.4 Y 侧规则（构建与收敛）

- **概要边界（结构判定级）**：本任务只做结构级判定——文档是否存在（名称级）、封面模式、候选引擎、开发方式、任务层、条目层三独立；**字段级详设留阶段二**。
- **场景业务构建规则**（Phase C 新建）：识别触发 → 追踪自然终点（不得在终点之后扩展）→ 闭合验证 → 边界四标准（完整性/一致性/紧凑性/粒度匹配），产出场景职责边界陈述。
- **文档序列构建规则**：D 类按输入-输出传递链排列；PCA 类按 P→C→A 管理循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并（覆盖完整）+ 同层兄弟不重叠（兄弟互斥）；新文档归不进现有枝干才上溯建更高层。

### 3.5 要素清单（本任务写入 02 节点必须带齐）

写入业务流程概要节点块：场景业务名称/业务域/产品类型/用户角色/类型（D/PCA）/场景职责边界陈述/**业务链**（每个 PL5 枝梢的：概要说明（名称/用途/封面模式/开发方式）、任务类型、**分解源判据展开项（任务主要节点 + PL6 条目名，见 3.3）**、支撑引擎候选 `[推断]`、任务关系）/**Bn 组装结论**（WBS 归组 + 23 一致性结论 + 缺口推断）/推理依据与补全说明/完备性检查结果/补充材料引用/变更影响声明/版本号。

### 3.6 传出承诺（给阶段二 biz02）

本任务把概要节点交给下游时，承诺节点达到：

1. 状态 = `可以分解分配`（人类"整体确认"后）；
2. 要素清单（3.5）齐备，概要说明为结构判定级；
3. **每个枝梢（PL5 文档）带分解源判据**——声明阶段二可分解出的活动/正文条目/表单类型（名称级）；

## 四、输出与输入转换规则

### 4.1 承接规则（X 叶 → Y 枝干/枝梢）

- **单承接**：一条相关方需求只归入**一个**场景业务（可 N:1——多条需求/多文档汇聚一个场景；不可 1:N）。违反 → 判定类型：程序违规（切分未按消费方语义范围）→ 退回重切；切不动的整体 → 两个出口（节点拆分 / 横切式承接走独立分支+影响面标注）。
- **分流**：已有场景业务可直接承接 → **Reuse（Phase B 修订）**；无宿主 → **Add（Phase C 新建）**。优先级始终 复用 → 改进 → 新增。
- **改进 = 影响面复查**：对已有枝梢做 Extend/Split/Merge 后，须复查其已承接的既有需求是否失配 → 批量重分配或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则（判据出处） |
|--------|--------------------|
| 业务域/路由 | 读 `#role-list` 角色业务域 → 映射 23 资产 Bn 产品类型路径（缺则 `[推断]`） |
| 场景业务类型 D/PCA | 需求动作词偏向执行类/管理类；存疑标 `[推断]` |
| 文档清单与来源 | 从需求正文识别（明示/隐含/同类场景推断/资产线索推断）；去重收敛 |
| 封面模式 | 是否需审批/发布/版本追溯等生效动作（91 §2） |
| 任务类型 | 需求明示→直接捕获；只提管理模式→判定+`[待阶段二推断]`；缺失→推断+`[待阶段二推断]`；R4 首个必为计划 |
| 支撑引擎候选 | 按正文数据类型匹配功能引擎，**全量 `[推断]`**（引擎清单读 25，不缓存） |
| PL6-B 条目名 | 集合容器 + 三独立 → 名称级捕获；只提管理模式→`[待阶段二推断]` |
| 文档间关系 | 流转顺序（D 传递链 / PCA 循环）+ 需求明示的任务触发关系 |

### 4.3 修订转换（Phase B：新需求并入已有 Y）

## 五、转换流程及检验规则

### 5.1 设计过程（动作序列）

一次运行 = **入口 → 载 X 与存量 Y → 反馈处理 → 承接设计循环 → 覆盖/完备检查 → 人类确认 → 推进 → 写回**：

1. **入口**：按受理门槛（2.4）判定；退回优先（`需biz01修订` → 读缺失说明走 Phase B 修订）；再处理待反馈；最后路由新需求。
2. **载 X 与存量 Y**：读 `待处理` FR-BIZ 需求条目 + 同角色/同域候选存量 02 概要节点 + 21/23/25 资产（§六）。
3. **反馈处理**：人类对话修改/整体确认/线下修订（反馈双轨，规则引 91 §A.5）。
4. **承接设计循环**（对一组相关联需求叶，落点相近）：
   - Phase A 路由 → Reuse（归已有场景）或 Add（待聚合池）；
   - Phase B/C 生成概要（§三.3/§三.4/§四）；
   - **单承接检查** + **影响面复查**；
   - 有新增/改进 → 自下而上调树至收敛（覆盖完整 + 兄弟互斥）。
5. **覆盖/完备检查**（5.2 关口）。
6. **人类确认** → 推进 `可以分解分配`。
7. **写回与落账**（23 资产 + 状态推进 + 基线，引 91 §A.3.3/§A.6；运行时细节不在此重述）。

### 5.2 检验规则（关口）

- **单承接检查**：一条需求只归一个场景业务（§四.1）。
- **承接覆盖检查**（本对关口）：该场景业务承接的全部需求语义 ⊆ 其业务链（枝梢之并）能实现的范围。EOS 实例化 = **端到端闭合检查**：D 从需求提出贯通到需求满足；PCA 按计划→监控→分析→纠正核对（须含计划清单文档 + 承载 C/A 的输出文档；C/A 运行时推进结果不作需求缺口）。缺口 → 生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐枝梢要素非空或合理空置 + 标注齐备（含 `[推断]`/`[待阶段二推断]`）。
- **治理覆盖检查**：预置治理业务流程概要业务链按角色预定文档集核对（无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补）。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以分解分配 ──阶段二锁定──→ 在分解分配 ──阶段二完成──→ 已分解分配
     ↑                       ↑                      │
     │                       │          阶段二退回    │
     └── biz01修订 ──── 需biz01修订 ←───────────────┘
```

上游变更（新需求汇入）分流：`可以分解分配`→版本递增（未消费）；`在分解分配`→版本递增（增量处理）；`已分解分配`→`待补充分解分配`→阶段二补全。（四态模型与写回范围引 91 §A.6，此处为本任务特化。）

### 5.4 运行时外壳（引 91 附录A，不重述）

Step Start/Step 1~5/Step End 的会话机制、反馈双轨状态机、git 基线、Step End 三区模板 = 91 附录A 统一协议；本任务只保留特化参数（锚点需求=本任务承接的全部 FR-BIZ 需求条目；操作条目=场景职责边界+业务链枝梢+PL6-B 条目名；推进目标=`可以分解分配`；清除/级联条件见 §5.3 状态机与上游分流，会话级清除引 91 §A.6）。
