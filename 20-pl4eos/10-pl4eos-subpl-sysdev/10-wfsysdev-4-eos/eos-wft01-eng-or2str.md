# FR-ENG OR → STR-E · 平台能力场景业务设计
**Skill ID**: wft01-eng-or2str

> **概述**：接收正式 FR-ENG OR，经前置校验、材料加载和反馈处理后，将非结构化平台能力需求转化为 STR-E 场景业务方案。STR-E 是流程与IT域中**业务配置人员**围绕一项可独立配置、治理并验收的平台能力场景形成的端到端业务。每个 STR-E 只有一个主责能力域；主责能力域可以是引擎，也可以是平台共享能力域。一个能力域可包含多个 STR-E，多个引擎可消费同一共享 STR-E，但不得重复定义共享 CU。
>
> **输入 → 输出**：FR-ENG OR 条目（≤10 条）/ 有反馈的 STR-E 节点 → STR-E 场景业务方案（能力链 + CU 候选 + 补充 FR-ENG 缺口）+ OR 推进为 `已分配` + STR-E 推进为 `可以分解分配`
>
> **适用场景**：瀑布式系统设计第1步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v8.3 | **修订**：2026-07-13 | **说明**：§8.1 三层定位对齐 + 可读性优化（导览段/实例/本节回答）

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台能力相关方——「你听懂了这项平台能力需要配置或治理什么、完成后能得到什么可验收结果」。把非结构化的 FR-ENG OR 转化为结构化的 STR-E 平台能力场景业务方案，并识别场景所需 CU、共享依赖及能力链缺口。

> **三层定位（按 §8.1）**：本 Skill 属于第1层（流水线设计）活动——在 EOS 流水线设计层将平台能力需求转化为 STR-E 方案；产出物经 wft02-eng→wft05-eng 完整链条后，以设计规范/AI SKILL 形态交付第2层（构件开发），最终由第3层 EOS 开发者（确认者/用户）使用。本 Skill 的执行分工按 §8.3：流水线开发者（主导者/审核者）审核 AI 的 STR-E 方案并决策变更路径，AI（执行者）执行标准操作流程，EOS 开发者（确认者/用户）确认交付物可用性。

**目标**：

1. **推断生成平台能力场景业务节点**——以`主责能力域 + 配置/治理目标 + 可独立验收结果`为归组锚点，匹配已有 STR-E 或新建；主责能力域分为`引擎专属`和`平台共享`两类
2. **推断场景业务配置单元**——在名称级列出该引擎可能触及的 CU 候选，标注来源、支撑对象和判定依据，为 wft02-eng 展开配置单元 BP 提供起点。CU 是 STR-E 的细分节点——与 STR-F 下辖输出文档的层级关系完全对称
3. **基于能力链补充引擎需求**——检查“配置/治理意图→系统处理要求→运行期制品/构件/功能→可用性确认”的能力链闭合性；检出实质能力缺口时生成补充 FR-ENG OR 材料。若仅“配置完成后如何判定能力可用”不明确，则标记澄清项，不生成补充材料
4. **建立追溯链**——保留 `FR-ENG OR → STR-E主责能力域 → CU候选/依赖STR-E` 的追溯链，记录提供能力、消费方和复用范围
5. **判断路径归属**——将 FR-BIZ、NFR、业务配置实例需求及时路由到对应路径，避免 eng 路径替业务链或非功能路径做方案

本 Skill 负责：

1. **接收**——接收流水线开发者选中的一批 FR-ENG OR 条目（≤10 条），校验输入为正式 FR-ENG OR、状态为 `待处理`；状态/类型不符时退出并提示路由
2. **溯源**——识别每条 OR 的主责能力域、配置/治理目标和可独立验收结果，判定为引擎专属或平台共享
3. **归组**——按三元组匹配已有 STR-E；同一能力域中的不同独立场景分别建 STR-E。跨场景共享能力通过`依赖STR-E`引用，不在消费引擎下复制共享 CU
4. **识别 CU 候选**——名称级识别可能触及的配置单元，标注来源类型（`OR明示` / `OR隐含` / `构件缺口推断` / `布局组件缺口推断` / `同类引擎推断` / `模型线索推断`）和粒度判断（`可展开` / `过粗待拆` / `过细待并` / `边界待确认`），不定义配置页面、配置要素或运行期构件
5. **补需**——检出配置/治理意图、系统处理要求或运行期制品等实质缺口时生成补充 FR-ENG OR 材料；仅能力可用判据不明确时输出澄清项
6. **推进**——流水线开发者确认后 STR-E → `可以分解分配`，对应 OR → `已分配`
7. **回修**——接收 wft02-eng 退回的 `需wft01修订` STR-E，读取缺失说明，按流水线开发者的改进方案修订 STR-E，流水线开发者确认后重新推进为 `可以分解分配`

本 Skill 不负责：

1. FR-BIZ 业务需求的场景业务与输出文档设计（→ `wft01-biz`）
2. NFR 分类与量化（→ `wft01-nfr` / `wft04-nfr`）
3. CU 的配置页面、配置要素、校验保存规则和运行期能力定义（→ `wft02-eng`）
4. 配置页面、操作活动和页面功能需求设计（→ `wft03-eng`）
5. 前后端组件、接口和实现边界设计（→ `wft05-eng`）
6. 25 资产中引擎/CU 模型的正式定义；本 Skill 最多形成名称级候选引用或模型建议

### 1.2 与上下游的衔接

**上游 OR 预处理**：只消费已进入 `01-*.md`、类型=`FR-ENG`、状态=`待处理` 的正式 OR。wft03-biz 产生的引擎能力缺口线索只是候选材料，必须先经流水线开发者确认，并完整通过 ort00→ort01→ort02→ort03 转化为正式 FR-ENG OR，才能进入本 Skill；不得从缺口材料或状态表 A 直接启动 wft01-eng。

**下游 wft02-eng**：消费状态为 `可以分解分配` / `待补充分解分配` 的 STR-E，展开配置单元 BP。若 wft02-eng 发现 STR-E 缺少场景边界、业务运行追溯、能力链闭合说明或 CU 候选过粗，将 STR-E 退回为 `需wft01修订`。

**交付链条**（按 §8.1 三层框架）：本 Skill 产出（STR-E 场景业务方案）→ wft02-eng（CU BP 分解分配）→ wft03-eng（配置页面设计）→ wft05-eng（PA 架构）→ **第2层交付**（设计规范/AI SKILL 形态交付至 EOS 设计空间）→ **第3层使用**（EOS 开发者使用交付物对 EOS 进行系统设计）。本 Skill 处于第1层起点——完成平台能力场景定义后，由下游链路逐步转化为可执行的流水线构件。

## 二、引擎场景业务设计基础

本节阅读链条：先理解 STR-E 是什么（§2.1~§2.3 定义层），再掌握怎么做（§2.4~§2.5 提取与推断规则），最后了解节点产出后如何流转（§2.6 生命周期）和修订时如何传播影响（§2.7 变更传播）。

### 2.1 引擎场景业务（STR-E）

#### 2.1.1 定义与分类

STR-E 是 FR-ENG 在相关方需求层的结构化表达，末级节点为**场景业务**。角色为流程与IT域的**业务配置人员**，STR-E 架构树上无需角色层做分组维度。

> **◆ 角色层次注记**：此处的"业务配置人员"是目标系统（EOS）中的第3层用户角色，是 STR-E 场景业务的需求锚点。本 Skill 本身是第1层（流水线设计）活动，其执行者按 §8.3 为流水线开发者（主导者/审核者）、AI（执行者）和 EOS 开发者（确认者/用户）——后者的 EOS 开发者角色与被设计系统中的"业务配置人员"是不同概念，切勿混淆。

**一个独立能力场景 = 一个 STR-E**：归组锚点为`主责能力域 + 配置/治理目标 + 可独立验收结果`。主责能力域可以是业务引擎，也可以是权限、审计、版本、发布、调度、通知等平台共享能力域。一个能力域可包含多个 STR-E；多个引擎可依赖同一共享 STR-E。STR-E 在 A2 视角是业务配置人员的 SL5/PL5 场景业务，在 A1 视角对应主责能力域下的能力场景，CU 是其细分节点。

共享技术能力若没有独立配置/治理活动和可验收结果，不建立 STR-E；其需求由 NFR 约束或平台架构决策进入 wft05-eng，形成公共构件或平台服务组件。

> **与 STR-F 的对称性**：STR-E 与 STR-F 在架构层级上完全同构——同为 SL5 末级节点（场景业务）、同有下辖细分节点（CU vs 输出文档）、同为角色端到端职责闭环。区别仅在于场景业务的产出物不是业务文档，而是**可用的平台能力**。

**FR-ENG OR 的五种类型**（不是 STR-E 的分类——一个 STR-E 可承接多种类型的 OR）：

| 类型 | 触发源 | 场景自然终点 |
|------|--------|--------------|
| 配置生成类 | 配置人员提出或维护引擎配置 | 配置通过系统校验并在运行期制品/构件/功能中生效 |
| 构件扩展类 | 业务页面需要新增按钮、右键、图表、钻取等构件能力 | 目标布局组件可渲染并使用该构件 |
| 布局组件扩展类 | 现有布局组件无法承载业务操作方式 | 新/扩展布局组件能力可被对应引擎或业务页面调用 |
| 横切治理类 | 权限、审计、版本、发布、回滚、监控等治理需要 | 横切规则对目标业务对象或运行期能力稳定生效 |
| 运行支撑类 | 业务运行页需要引擎能力调用、状态处理或异常恢复 | 引擎能力可被业务页面调用并产生可追溯结果 |

AI 根据 OR 语义判定类型，作为 OR 的能力诉求特征标注——不用于划分 STR-E 边界。

#### 2.1.2 架构与属性

场景业务的架构（能力链）见 §2.2。CU 功能本质及其与布局组件、构件的关系见 [91 规范 §3.2](91-eos-biz-eng-spec.md#32-引擎及层级) 与 [§4.3](91-eos-biz-eng-spec.md#43-cu-与布局组件及构件的对应关系)。

每条 STR-E 保留从 OR 到主责能力域、CU及依赖场景的追溯链：

```text
FR-ENG OR（含触发来源标注——A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 布局组件缺口 / 横切能力阶段）
  → STR-E（唯一主责能力域：引擎专属 / 平台共享）
  → CU 候选 + 依赖 STR-E
```

触发来源用于说明“为什么需要该平台能力”，不作为 STR-E 的唯一边界。无法确定唯一主责能力域或独立验收结果的 OR 标记 `需澄清`，不得推进为正式 STR-E。

STR-E 节点完整要素（写入 `02-*.md` STR-E 节点块）：

- STR-E ID / 名称 / 主责类型 / 主责能力域
- 配置或治理目标 / 可独立验收结果
- 提供能力 / 消费方 / 依赖 STR-E / 复用范围
- 来源 OR 清单（各条标注触发来源类型）
- 能力链
- CU 候选清单
- 完备性检查结果
- 补充 FR-ENG 材料引用
- 变更影响声明
- 版本号 / 确认状态

> **STR-E 实例**（写入 `02-*.md` 时的节点片段）：
> ```text
> @STR-E-ENG-FLOW-001 | 流程节点配置场景 | 引擎专属 | @engine-flow
> 配置/治理目标：流程节点及流转规则配置
> 可独立验收结果：配置的流程节点和流转规则可通过业务表单的流程按钮在运行期使用
> 提供能力：流程节点配置、流转规则配置、发布配置
> 消费方：引擎概览场景（STR-E-ENG-FLOW-002）
> 能力链：流程节点配置意图 → 校验保存 → 发布装载 → 业务表单流程按钮可用
> CU 候选：[推断]流程节点配置（@engine-flow）[OR明示]、[推断]流转规则配置（@engine-flow）[OR隐含]
> 来源 OR：OR-ENG-001（配置生成类）、OR-ENG-003（运行支撑类）
> ```

#### 2.1.3 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 能力链闭合 | 配置/治理意图能走到运行期制品/构件/功能可用 | 生成补充 FR-ENG |
| 主责归属明确 | 每个 STR-E 只有一个主责能力域；可为引擎专属或平台共享 | 标记 `需澄清` 或退回 OR 预处理 |
| 场景可独立验收 | 配置/治理目标和完成结果可独立判定 | 与其他场景合并，或降为依赖/NFR/PA 能力 |
| 共享不重复 | 共享能力只在主责共享 STR-E 下定义 CU，消费方仅引用依赖 | 删除重复 CU，补依赖关系 |
| CU 可展开 | CU 候选足以让 wft02-eng 定位配置单元 | 标记 `[需裁决]` 或 `需澄清` |
| 缺口层级正确 | 构件级/布局组件级/CU 级缺口区分清楚 | 改写缺口说明 |

### 2.2 能力链

#### 2.2.1 定义与构成

能力链是 wft01-eng 判断 STR-E 是否闭合的业务链类比物。它不展开业务输出文档，而是描述平台能力从一个引擎的配置意图到运行期生效的最小闭环。

```text
配置/治理意图
  → 系统处理要求
  → 运行期制品/构件/功能
  → 可用性确认
```

各段含义：

| 段 | 说明 | wft01-eng 粒度 |
|----|------|----------------|
| 配置/治理意图 | 需要配置或治理哪类平台能力 | 名称级表达 |
| 系统处理要求 | 系统至少要校验、保存、发布、装载或控制什么 | 只描述能力要求，不写实现 |
| 运行期制品/构件/功能 | 91 规范中的物理表、功能表单、菜单入口、配置页面或页面组件上的构件等 | 名称级，不设计构件 |
| 可用性确认 | 何种结果代表平台能力可用——即业务配置人员完成配置后，运行期业务人员可使用该能力的判定标准 | 作为场景终点 |

> **能力链实例**（以"流程节点配置"场景为例）：
> ```text
> 配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认
>   ↓               ↓               ↓                    ↓
>   配置流程节点    校验节点参数     流程按钮绑定到业务表单   流程按钮可用、节点跳转正常
>   和流转规则      保存规则配置     页面、发布后装载生效
> ```
> 注：能力链在 `02-*.md` STR-E 节点中以一句陈述呈现，不展开为箭头的细分项。此处的展开是为了帮助 AI 理解各段的具体含义。

> **触发来源不在此链中**：触发来源（A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 布局组件缺口 / 横切能力阶段）是 OR 级上下文信息，标注在 OR→引擎的追溯链中（§2.1.2），不属于能力链的闭合段。能力链本身只关注"配置侧→运行期可用"，即业务配置人员从打开配置页面到能力可用的完整闭环。

### 2.3 CU 候选

#### 2.3.1 定义与记录字段

CU 候选是 STR-E 场景业务中的名称级配置单元线索。wft01-eng 只说明”可能需要哪些配置单元”，不定义每个 CU 的配置页面、配置要素、系统处理细节或运行期构件。

每个 CU 候选至少记录：

| 字段 | 说明 |
|------|------|
| CU 候选名称 | 名称级线索，可带 `[推断]` |
| 主责类型 / 主责能力域 | 引擎专属：实体、流程、工单等；平台共享：权限、审计、发布等 |
| 来源 OR | 触发该候选的 OR ID |
| 支撑对象 | 业务运行对象、平台治理对象、构件或布局组件缺口 |
| 候选理由 | 为什么需要这个 CU |
| 来源类型 | `OR明示` / `OR隐含` / `构件缺口推断` / `布局组件缺口推断` / `同类引擎推断` / `模型线索推断` |
| 粒度判断 | `可展开` / `过粗待拆` / `过细待并` / `边界待确认` |
| 确认状态 | 人类反馈字段 |

### 2.4 场景业务要素提取规则

**本节要回答的问题**：每条 FR-ENG OR 应该提取什么信息（§2.4.1）？提取后怎么划定场景边界（§2.4.2）？已有场景怎么匹配（§2.4.3）？修订与新建的做法差异在哪（§2.4.4）？

Phase B（修订已有 STR-E）与 Phase C（新建 STR-E）共用以下规则。

#### 2.4.1 能力域确定

逐条 OR 提取以下要素：

| 提取项 | 说明 |
|--------|------|
| 触发来源 | 业务运行对象 / 平台治理对象 / 构件缺口 / 布局组件缺口 / 横切能力阶段（OR 级上下文信息，标注在 OR→引擎追溯链中，不用于 STR-E 边界划分） |
| 能力诉求 | 需要平台提供什么能力 |
| 运行期结果 | 期望生成或增强什么制品、构件或功能 |
| 主责类型 | `引擎专属` / `平台共享` |
| 主责能力域 | 实体、流程、工单等引擎，或权限、审计、版本、发布、调度、通知等共享能力域 |
| 配置/治理目标 | 本场景要完成的独立配置或治理目标 |
| 可独立验收结果 | 不依附其他场景也能判断完成与否的结果 |
| 依赖能力 | 本场景消费的其他 STR-E 或无需建立 STR-E 的技术能力 |

路由规则：

| 情况 | 处理 |
|------|------|
| OR 实际要求业务输出文档或业务流程 | 退回 `wft01-biz` |
| OR 实际是性能、安全、可用性等约束 | 退回 nfr 路径 |
| OR 只是具体业务配置数据 | 标记为业务配置实例，不进入 eng 设计 |
| OR 描述可独立配置、治理和验收的引擎能力 | 进入相应引擎专属 STR-E |
| OR 描述跨引擎复用且可独立配置、治理和验收的能力 | 进入平台共享 STR-E；消费引擎建立依赖引用 |
| OR 描述无独立配置场景的公共技术能力 | 转为 NFR 约束或 wft05-eng 平台组件线索，不建立 STR-E |
| OR 同时包含多个可独立验收结果 | 按结果拆分为多个 STR-E，并建立依赖；无法拆分时标记 `[需裁决]`

#### 2.4.2 场景边界定义

Phase C 新建 STR-E 时，按`主责能力域 + 配置/治理目标 + 可独立验收结果`定义边界。主责能力域已有其他 STR-E，不妨碍新建不同的独立能力场景。

**判定主责能力域**：先判断能力是否具有独立配置/治理活动和验收结果，再判断主责类型。跨引擎复用不等于拆到各引擎；具有独立场景时归入平台共享能力域，消费引擎仅建立依赖。

**定义能力场景闭环**：STR-E 的边界是一次可独立完成和验收的配置/治理业务。AI 需回答以下问题：

1. 配置人员要配置什么？（配置要素清单——从 OR 中提取）
2. 系统要怎么处理？（校验/保存/发布/装载——从 OR 中提取，不足的进入缺口清单）
3. 配置后产出什么运行期能力？（制品/构件/功能——从 OR 中提取）
4. 怎么算配置完成、能力可用？（可用性确认标准）

**能力场景范围完整性检查**：

| 判据 | 通过标准 | 不通过处理 |
|------|----------|------------|
| 主责能力域唯一 | 一个 STR-E 只有一个主责能力域，依赖方不改变主责 | 拆分场景或标记待裁决 |
| 独立验收 | 配置/治理目标具有独立完成标准 | 合并到其他 STR-E 或降为依赖 |
| 共享复用 | 共享 CU 只在共享 STR-E 定义一次 | 消费方删除重复 CU，建立依赖 |
| 能力链闭合 | 配置意图能走到运行期可用 | 缺口进入补充 OR 材料 |
| 终点明确 | 能说清”何时算配置完成、能力可用” | 标记 `需澄清` |
| 不替代 biz | 不新增业务输出文档、不重做业务场景 | 退回 biz 路径 |

输出**场景边界陈述**：`业务配置人员针对「<主责能力域>」完成<配置/治理目标>，经<系统处理>形成<运行期产出>，达到<独立验收标准>后场景完成；<消费方>通过依赖关系复用该能力。`

边界定义完成后，按 §2.1.2 完整要素组装 STR-E 节点写入 `02-*.md`。

#### 2.4.3 Phase B 场景匹配检查

Phase B 修订已有 STR-E 时，按三元组检查本轮 OR 是否属于该能力场景。

1. 提取主责能力域、配置/治理目标和独立验收结果
2. 三元组一致 → 归入该 STR-E（进入 CU 候选关系检测 §2.5.3）
3. 仅主责能力域一致但目标或验收结果不同 → 匹配该能力域下其他 STR-E 或新建 STR-E
4. 属于共享依赖 → 关联共享 STR-E，不向当前 STR-E 复制共享 CU

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 场景匹配 | 三元组一致 | 进入 CU 候选关系检测（§2.5.3）+ 输出变更影响声明 |
| 同域不同场景 | 主责能力域相同，但目标或验收结果不同 | 匹配其他 STR-E 或触发 Phase C 新建 |
| 共享依赖 | 能力由已有共享 STR-E 提供 | 写入依赖关系和消费方，不复制 CU |
| 主责不匹配 | OR 归属其他能力域 | 退回待聚合池，重新匹配或新建 |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 STR-E | Phase C 新建 STR-E |
|------|----------------------|-------------------|
| 判定范围 | STR-E 已承接的全部 OR + 本轮新 OR | 待聚合池本组 OR |
| 引擎锚点 | 以已有引擎的能力链为基线，仅扫描本轮新 OR 是否引入新链段 | 从零构建引擎的能力链 |
| 归组 | 执行场景匹配检查（§2.4.3）——三元组一致才归入 | 执行能力场景边界定义（§2.4.2）——同域不同独立场景分别新建 |
| 要素提取 | 在基线基础上增量合并（CU 关系检测见 §2.5.3） | 全量提取 |
| CU 重识别 | 合并重识别可能导致已有 CU 候选的归属变更——标记 `[CU归属变更]` 并附变更原因 | 无此问题 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 CU 候选推断规则

**本节要回答的问题**：怎么从 OR 和资产中推断出 CU 候选（§2.5.1）？每个候选标注哪些信息（§2.5.2）？修订已有 STR-E 时怎么检测 CU 关系的变化（§2.5.3）？

Phase B（修订已有 STR-E）与 Phase C（新建 STR-E）共用以下规则。

#### 2.5.1 能力链提取

**识别 CU 候选清单**：从当前操作范围内的全部 OR 中识别可能触及的配置单元。去重/收敛后形成 CU 候选清单，每个候选 → 能力链上一个配置节点。多条 OR 指向同一 CU 时归入同一候选（要素收敛）。

**逐候选判定目标引擎/能力域**：从 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景) 动态读取引擎清单（每次运行时读取、不缓存），根据 CU 候选的功能特征匹配目标引擎。wft01 仅有 OR 文本信息，CU 候选的引擎归属**全量标注 `[推断]`**，定位为供下游 wft02 校验的**候选建议**而非最终判定。

#### 2.5.2 CU 候选标注与来源类型

对每个 CU 候选逐项判定要素并标注。标注字段见 §2.3.1。

**来源类型定义**（CU 候选）：

| 来源类型 | 含义（含示例） |
|----------|---------------|
| `OR明示` | OR 文本中直接说出该 CU。如”需要配置流程节点” → “流程节点配置”CU |
| `OR隐含` | OR 未直接说出，但不推出该 CU 则能力链存在逻辑缺口。如”流程发布后需支持回滚” → 必然需要”回滚配置”CU |
| `构件缺口推断` | OR 描述业务页面需要某构件能力，但现有构件无法满足 → 推断需要新的构件配置 CU |
| `布局组件缺口推断` | OR 描述页面操作方式现有布局组件无法承载 → 推断需要新的布局组件配置 CU |
| `同类引擎推断` | 同引擎类型已有 STR-E 的类似 CU 模式，当前 OR 场景与之高度相似时推断 |
| `模型线索推断` | 25 资产中已有与当前能力域匹配的 CU 定义，但 OR 未提及 |

#### 2.5.3 Phase B CU 候选关系检测

Phase B 修订已有 STR-E 时，边界检查通过后，将本轮提取的 CU 候选与 STR-E 已有 CU 候选清单比对。比对锚点为**CU 候选名称+目标引擎匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU 匹配 + 引擎相同 + 至少一个来源非 `OR明示` | 来源升级（`OR隐含`→`OR明示`、`构件缺口推断`→`OR明示`、`布局组件缺口推断`→`OR明示`、`同类引擎推断`→`OR明示`、`模型线索推断`→`OR明示`），内部细分结论=`确认` |
| 无新增 | CU 匹配 + 引擎相同 + 所有来源已为 `OR明示` | 追加 OR 引用 + 增量合并新 OR 中的候选理由/粒度判断（如有新内容），内部细分结论=`改进` |
| 引擎归属变更 | CU 匹配 + **引擎不同**（合并重识别导致） | 更新已有 CU 的目标引擎 + 内部细分结论=`引擎归属变更` + 变更原因。不新增 CU |
| 补充 | CU 不匹配 | 新增到 CU 候选清单，来源=`OR明示`，内部细分结论=`新增` |
| 过时 | 基线已有 CU **未被**本轮提取覆盖（引擎配置范围变更后，基线中某些 CU 不再落入新的能力链追踪范围） | 内部细分结论=`过时` + 追加说明”引擎配置范围变更后未落入新的能力链追踪范围，请确认是否移除”。保留该 CU 在候选清单中（不删除）——移除是架构决策，由流水线开发者反馈触发 |

关系检测前先基于**全部 OR 重新识别目标引擎**——新 OR 可能改变 CU 特征导致引擎归属变更（表中 `引擎归属变更` 行）。来源证据强度只升不降：`OR隐含`/`构件缺口推断`/`布局组件缺口推断`/`同类引擎推断`/`模型线索推断` → `OR明示`，在 `确认` 行触发。

`[调整]` 是与关系类型正交的叠加标记：已有 CU 的名称/能力域/粒度判断变化，在关系标记之外叠加 `[调整]`。

### 2.6 STR-E 节点生命周期

**本节要回答的问题**：STR-E 节点在 wft01-eng 和 wft02-eng 之间按什么状态流转？上游新 OR 进来时怎么处理？

STR-E 节点沿 [91 规范 §A.6](91-eos-biz-eng-spec.md#a6-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §A.6 状态名映射表（wft01-eng 列）。并行推进规则（资产线与 BP 线互不阻塞）见 91 规范 §A.6。

**主线流转**（wft01-eng ←→ wft02-eng）：

```
待确认方案 ──流水线开发者确认──→ 可以分解分配 ──wft02锁定──→ 在分解分配 ──wft02完成──→ 已分解分配
     ↑                        ↑                         │
     │                        │               wft02退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

**上游变更**（新 OR 汇入触发 STR-E 修订）：

```
可以分解分配 ──新OR修订──→ 可以分解分配（版本递增，wft02 未消费）
在分解分配   ──新OR修订──→ 在分解分配（版本递增，wft02 增量处理）
已分解分配   ──新OR修订──→ 待补充分解分配 ──wft02补全──→ 已分解分配
```

**本 Skill 的写回范围**：`待确认方案` / `可以分解分配` / `待补充分解分配` / `需wft01修订`。`在分解分配` 和 `已分解分配` 由 wft02-eng 写入和推进。

下游退回 `需wft01修订` 时：读取 wft02-eng 的缺失说明 → 按流水线开发者的改进方案修订 STR-E（走 Phase B 修订流程）→ 流水线开发者确认 → STR-E → `可以分解分配`。

### 2.7 STR-E 变更传播协议

**本节要回答的问题**：修订已有 STR-E 后，如何告诉下游 wft02-eng 这是个什么性质的变更？哪些 BP 节点受影响？

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板、增量清单与变更影响声明的分工）见 [91 规范 §A.7](91-eos-biz-eng-spec.md#a7-变更传播协议)。

**本 Skill 的变更影响声明格式**，每次修订已有 STR-E 后写入 STR-E 节点末尾（`02-*.md` 中 STR-E 节点块内）：

```text
### 变更影响声明

STR-E 版本：v{N}（本次修订前为 v{N-1}）
本轮变更类型：无变更 / 增量型 / 修订型 / 结构型

变更项：
- [新增] / [变更] / [确认] / [需裁决] ...
  说明字段中记录细分原因：CU 候选新增 / 引擎归属变更 / 过时等

下游已消费此 STR-E 的 BP 节点：
  <BP节点ID列表>（如无则写”尚未被下游消费”）

对已消费 BP 节点的影响：
  受影响节点：<BP节点ID + 受影响原因>
  不受影响节点：<BP节点ID>
  待新增 BP 节点：<新CU候选对应的待展开 BP 说明>

建议 wft02-eng 动作：
  - 无变更：无需任何动作
  - 增量型：增量展开新增 CU 候选即可，已有 BP 节点不动
  - 修订型：修订受影响的 BP 节点 → 标记 [来自上游变更]
  - 结构型：输出影响范围，等流水线开发者裁决后再处理；含场景合并/拆分时 wft02-eng 需新建或重组 BP 节点
```

### 3.1 Step Start

入口条件与优先级判定遵循 [91 规范 §A.4](91-eos-biz-eng-spec.md#a4-入口条件与优先级step-start)。AI 依次执行入口检测、输入校验和分流处理。

#### 3.1.1 入口检测

读取产品数据文档中的 `## AI可以处理节点` 对应分节（[91 规范 §11.7](91-eos-biz-eng-spec.md#117-ai可以处理节点)），检测三类入口条件：

| # | 入口条件 | 检测方式 | 对应分节 |
|---|---------|---------|---------|
| ① | **有新输入** | AI可以处理节点「待 wft01-eng 处理」分节非空 | §11.7 |
| ② | **有待处理反馈** | AI可以处理节点「待反馈处理」分节含本 Skill 产出节点 | §11.7 |
| ③ | **有下游退回节点** | AI可以处理节点「待下游退回处理」分节含状态为 `需wft01修订` 的节点 | §11.7 |

三类均不满足 → 输出"无待处理对象"→ **退出**。

**退回门禁**（满足条件③时）：检查退回节点的缺失说明中是否包含改进方案（流水线开发者标注 `[修改]`/`[同意]` 或下游 Skill 产出的具体改进指引）。已提供 → 通过门禁。未提供 → 输出缺失说明 + 提示提供改进方案 → **退出**。

#### 3.1.2 输入校验

入口检测通过后进行输入校验。以下校验中逻辑上不可能的条件为硬退出（输出提示后退出），数量/归属模糊条件为软提示（输出提示后由流水线开发者选择继续或退出）：

| 校验条件 | 判定 | 类型 |
|---------|------|------|
| OR 状态不是 `待处理` | 输出不合格条目及当前状态 → **退出** | 硬退出 |
| OR 类型不是 FR-ENG（含 FR-BIZ） | 输出类型分布，提示走 `wft01-biz` → **退出** | 硬退出 |
| OR 类型不是 FR-ENG（含 NFR） | 输出类型分布，提示走 `wft01-nfr` → **退出** | 硬退出 |
| OR 为业务配置实例 | 标记并提示不进入 eng 设计 → **退出** | 硬退出 |
| OR 是 wft03-biz 线索但未转正式 OR | 输出"输入未正式化"，提示先确认并写入 `01-*.md` → **退出** | 硬退出 |
| OR 无法判定唯一主责能力域或独立验收结果 | 输出归属/边界不明条目，标记 `需澄清` → **退出** | 硬退出 |
| OR >10 条 | 输出超限提示 → 流水线开发者确认后继续或退出 | 软提示 |
| OR 跨多个引擎 | 输出引擎混杂提示 → 流水线开发者确认拆分后继续或退出 | 软提示 |

#### 3.1.3 分流处理

按 [91 规范 §A.4.4](91-eos-biz-eng-spec.md#a44-规则三优先执行顺序) 定义的优先顺序执行（退回优先 → 反馈处理 → 新输入路由）：

1. **退回优先**：存在 `需wft01修订` 的 STR-E 节点（且门禁通过）→ 读取 wft02-eng 的缺失说明，按流水线开发者的改进方案走 Phase B 修订（§3.4.2），流水线开发者确认后推进为 `可以分解分配`
2. **反馈处理**：存在 `待确认方案` + 有流水线开发者反馈未处理的 STR-E 节点 → 进入 Step 2 处理（§3.3）。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 OR，Step End 时提示
3. **新 OR 路由**：有未处理的 OR 条目 → 进入 Step 1→Step 3，逐条执行 Phase A 溯源与路由（§3.4.1），归入已有 STR-E（→Phase B）或待聚合池（→Phase C）

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 STR-E 的边界/能力链/CU 候选。Step 3 的 Phase A 宿主匹配必须基于 Step 2 修改后的最新 STR-E 内容，不得使用缓存旧状态。

### 3.3 Step 2 · 方案反馈处理

流水线开发者审阅与 AI 处理的通用协议见 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：场景边界 + 能力链 + 每个 CU 候选 + 每条补充 FR-ENG 缺口。各条目的 `确认状态` 字段位于 `02-*.md` STR-E 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §A.5](91-eos-biz-eng-spec.md#a5-反馈交互协议) 的统一流程处理流水线开发者反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对流水线开发者标注的机械执行，而是以 OR 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解流水线开发者反馈在 OR 需求语境中的含义，再执行修订，最后检查修订后的 STR-E 是否仍满足 OR 需求。

**本 Skill 反馈处理特化参数**（[91 规范 §A.5.4](91-eos-biz-eng-spec.md#a54-其他规则) 要求各 Skill 定义以下参数）：

| 参数 | 本 Skill 值 |
|------|-------------|
| **锚点需求** | 本 Skill 的锚点是 FR-ENG OR——反馈处理以 OR 需求理解为锚，不脱离 OR 文本内容自行修订 |
| **操作条目** | 场景边界 + 能力链 + 每个 CU 候选 + 每条补充 FR-ENG 缺口。各条目的 `确认状态` 字段写入 `02-*.md` STR-E 节点的对应条目中 |
| **推进目标** | 全部条目含 `[同意]`+`[已处理]` → STR-E → `可以分解分配`。存在 `[修改]`/`[驳回]` 且无 `[需重设计]` → 保持 `待确认方案`。存在 `[需重设计]` → 保持 `待确认方案`，需进入 Step 3 重做 |
| **清除条件** | 已有 `[同意]`+`[已处理]` 的条目默认跳过扫描。仅当本轮新输入满足以下任一条件时，清除 `[已处理]`（保留 `[同意]`）使其回到待处理：（1）新输入为该条目的直接上游节点（如新 FR-ENG OR 条目是 STR-E 节点的来源）；（2）新输入与条目同属一个架构层级且边界重叠（如同属 CU 候选，新候选改变了已有候选的范围或归属）；（3）新输入导致条目定义被修订（变更影响声明标注为修订型或结构型，§A.5.3 Step 1） |

| **资产对齐级联** | 方案变更影响 23/25 资产时，更新对齐结论——CU 候选引擎归属变更 → 更新 25 引用；引擎归属变更 → 更新 23 引用。资产映射由 Step 5 维护 |

### 3.4 Step 3 · STR-E 场景业务设计

#### 3.4.1 Phase A：OR 溯源与路由

对每条新 OR 执行溯源提取（触发来源 + 能力诉求 + 运行期结果 + 主能力域，详见 §2.4.1）。先判定路径归属——实际为业务输出文档/流程→退回 `wft01-biz`，实际为性能/安全等约束→退回 nfr 路径，仅为业务配置数据→标记不进入 eng 设计。路径确认后，逐条按主能力域（引擎）做宿主匹配：

| 条件 | 路由 |
|------|------|
| OR 的主责能力域、配置/治理目标和独立验收结果均命中已有 STR-E | 归入该 STR-E → Phase B |
| OR 的主能力域尚无对应 STR-E | 进入待聚合池 → Phase C |

待聚合池按**主能力域（引擎）**分组。此阶段仅粗略分组，CU 候选去重和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 STR-E

1. **要素提取**：从本轮 OR 提取触发来源（OR 级上下文）、能力诉求、运行期结果和主能力域（详见 §2.4.1）。先提取后检查——主引擎不一致时退回待聚合池
2. **场景匹配检查**：确认 OR 与 STR-E 的主责能力域、目标和验收结果一致（详见 §2.4.3）
3. **CU 候选关系检测**：比对已有基线，判定确认/无新增/引擎归属变更/补充/过时（详见 §2.5.3）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 STR-E 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 STR-E

1. **确定引擎** → 从 OR 语义提取主能力域（详见 §2.4.1）
2. **定义能力场景范围** → 判定配置/治理目标→系统处理→运行期产出→独立验收，输出场景边界陈述（详见 §2.4.2）
3. **要素提取** → 识别 CU 候选清单 + 逐候选判定目标引擎 + 标注字段（详见 §2.5，含粒度判断与来源类型）
4. **构建能力链** → 按配置→处理→运行期→可用确认排列，标注依赖关系（详见 §2.2）
5. **标注 OR 类型** → 逐条 OR 判定其 FR-ENG OR 类型（配置生成类 / 构件扩展类 / 布局组件扩展类 / 横切治理类 / 运行支撑类，详见 §2.1.1），作为 OR 级能力诉求特征——不用于划分 STR-E 边界
6. **组装 STR-E** → 引擎名称 + 场景边界陈述 + 能力链 + CU 候选清单 + 推理依据，写入 `02-*.md`（完整要素见 §2.1.2）

### 3.5 Step 4 · 补充 FR-ENG 与变更声明

Step 4 按每个 STR-E 实例独立执行。新建 STR-E → 全量检查；修订已有 STR-E → 仅当能力链拓扑变化（新增/过时/引擎归属变更）时重验闭合，要素机械检查始终针对变更文档执行。

**1. 能力链闭合检查**

- 逐 STR-E 检查能力链三段闭合：配置/治理 → 系统处理 → 运行期可用
- 配置/治理段缺失（缺少配置或治理意图）→ 缺口类型 = `补充OR`
- 系统处理段缺失（缺少校验/保存/发布/装载/控制要求）→ 缺口类型 = `补充OR`
- 运行期可用段缺失 → 细分：缺少运行期制品/构件/功能 → `补充OR`；缺少”何时算配置完成、能力可用”→ `澄清项`
- CU 候选 `过粗待拆` → 缺口类型 = `拆分建议`，交流水线开发者裁决
- 缺口 → 进入「补充 FR-ENG 材料生成」。不因缺口脑补节点——缺口就是缺口

**2. 要素机械检查**（逐 STR-E，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 引擎名称 / 场景边界陈述 **非空**
- [ ] 能力诉求 / 运行期结果 / 主能力域 **有标注**（含合理空置原因）
- [ ] 追溯链（FR-ENG OR → 引擎 → CU 候选）**完整**，各条 OR 已标注触发来源类型
- [ ] CU 候选清单 **非空**，每条 CU 标注来源类型（`OR明示` / `OR隐含` / `构件缺口推断` / `布局组件缺口推断` / `同类引擎推断` / `模型线索推断`）和粒度判断（`可展开` / `过粗待拆` / `过细待并` / `边界待确认`）
- [ ] 变更影响声明 **已写入**（首版写”首版，无变更”；格式见 §2.7）

**3. 补充 FR-ENG 材料生成**

闭合缺口时生成。写入 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<STR-E名称>补充原始需求材料.md`，包含：材料编号 / 来源 STR-E / 来源 OR / 缺口类型 / 补充需求文本 / 推断依据 / 建议类型（`补充OR` / `澄清项` / `拆分建议` / `模型建议`）/ 确认状态。同时登记到 `01-eos-sysdev-status.md` 表 A（生命周期=`已登记`）。文件引用写入 STR-E 节点的完备性检查结果。

**4. 横切治理触发检查**

从 25 资产读取各引擎内置的治理能力（权限归属见菜单引擎+功能引擎、版本/发布/回滚见各引擎 CU、审计/监控见各引擎运行期接口），判定当前批次 STR-E 是否触发了治理能力缺口（当前批 STR-E 涉及引擎的新建/修改/发布或运行期监控能力，但现有引擎的治理配置单元未覆盖）。缺对应 FR-ENG OR 且触发时 → 在 Step End 中提示流水线开发者渐进增补。不生成补充材料、不登记状态表、不自动补。

### 3.6 Step 5 · 资产写回与落账

**写回资产操作**：

1. 遍历已确认 STR-E，按主责类型和主责能力域写回 23 资产：

2. 遍历已确认 STR-E 的 CU 候选，写回 25 资产：
   - 仅写 CU 候选名称级引用或模型建议，不写 CU 详细定义
3. 记录资产写回记录到 `02`（日期/路径/动作/判定）
4. 对应 OR 条目 → `已分配`；补充 FR-ENG 材料登记到 `01` 原料状态表
5. 记录 OR→STR-E→23/25 引用链

**写回时的同步维护**（[91 规范 §11.11](91-eos-biz-eng-spec.md#1111-ai-写回规则) 要求每次写回同时维护以下内容）：

| 新增/删除子条目 | 更新父节点 `**子条目状态**` 汇总值 |
| 流水线开发者标注处理 | 同步更新父节点 `**子条目状态**`（子条目标注时）和 `**确认状态**`（父节点标注时）；AI可以处理节点"待反馈处理"同步 |

4. git add + git commit（带 Co-Authored-By: Claude）
