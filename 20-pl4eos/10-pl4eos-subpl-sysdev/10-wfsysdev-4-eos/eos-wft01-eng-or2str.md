# FR-ENG OR → STR-E · 引擎场景业务设计
**Skill ID**: wft01-eng-or2str

> **概述**：接收正式 FR-ENG OR，经前置校验、材料加载和反馈处理后，将非结构化引擎需求转化为 STR-E 引擎场景业务方案。STR-E 即流程与IT域中**业务配置人员**对一个引擎的端到端配置业务——从打开配置页面、编辑配置要素、系统校验保存、发布装载、到运行期构件/功能可用的完整闭环。一个引擎对应一个 STR-E（~11 引擎 → ~11 STR-E），wft01-eng 负责名称级推断该引擎所需配置单元（CU）候选，并识别能力链缺口形成补充 FR-ENG 材料。
>
> **输入 → 输出**：FR-ENG OR 条目（≤10 条）/ 有反馈的 STR-E 节点 → STR-E 场景业务方案（能力链 + CU 候选 + 补充 FR-ENG 缺口）+ OR 推进为 `已分配` + STR-E 推进为 `可以分解分配`
>
> **适用场景**：瀑布式系统设计第1步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v5.1 | **修订**：2026-07-10 | **说明**：对齐 [91 规范 v4.0](91-eos-biz-eng-spec.md)——引擎体系 11 引擎（-需求/+指标独立）、STR-E 架构不变

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台能力相关方——「你听懂了这个引擎需要配置什么、配置完后能产出什么运行期能力」。把非结构化的 FR-ENG OR 转化为结构化的 STR-E 引擎场景业务方案——不仅复述 OR 已说出的引擎需求，更识别该引擎完整的配置业务闭环与所需 CU，为下游配置单元 BA 设计（wft02-eng）提供可展开的输入。

**目标**：

1. **推断生成引擎场景业务节点**——以引擎为锚点，判定 FR-ENG OR 归属哪个引擎（主能力域），匹配已有 STR-E 或新建。STR-E 的端到端闭环即业务配置人员对该引擎的配置业务：打开配置页→编辑配置要素→系统校验保存→发布装载→运行期能力可用
2. **推断场景业务配置单元**——在名称级列出该引擎可能触及的 CU 候选，标注来源、支撑对象和判定依据，为 wft02-eng 展开配置单元 BA 提供起点。CU 是 STR-E 的细分节点——与 STR-F 下辖输出文档的层级关系完全对称
3. **基于能力链补充引擎需求**——检查”配置/治理意图→系统处理要求→运行期制品/构件/功能→可用性确认”的能力链闭合性，检出缺口时生成补充 FR-ENG OR 材料，将不完整的能力需求意图还原为可确认的需求条目
4. **建立追溯链**——保留 `FR-ENG OR → 引擎 → CU 候选` 的追溯链。每条 OR 按 §2.4.1 提取触发来源（A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段），作为 OR 级上下文信息，不作为 STR-E 的边界划分依据
5. **判断路径归属**——将 FR-BIZ、NFR、业务配置实例需求及时路由到对应路径，避免 eng 路径替业务链或非功能路径做方案

本 Skill 负责：

1. **接收**——接收人类选中的一批 FR-ENG OR 条目（≤10 条），校验输入为正式 FR-ENG OR、状态为 `待处理`；状态/类型不符时退出并提示路由
2. **溯源**——识别每条 OR 的主能力域（目标引擎），提取触发来源、能力诉求、运行期结果；无法判定归属引擎时标记 `需澄清`
3. **归组**——按主能力域（引擎）匹配已有 STR-E——同一引擎则归入，新引擎则新建 STR-E。FR-ENG OR 的五种类型（配置生成类/构件扩展类/页面组件扩展类/横切治理类/运行支撑类）描述的是 OR 的能力诉求特征，不是 STR-E 的分类——一个引擎的 STR-E 可承接多种类型的 OR
4. **识别 CU 候选**——名称级识别可能触及的配置单元，标注来源类型（`OR明示` / `OR隐含` / `构件缺口推断` / `页面组件缺口推断` / `同类引擎推断` / `模型线索推断`）和粒度判断（`可展开` / `过粗待拆` / `过细待并` / `边界待确认`），不定义配置页面、配置要素或运行期构件
5. **补需**——检出能力链缺口（缺少配置/治理意图、系统处理要求、运行期制品或可用性确认），生成补充 FR-ENG OR 材料，登记到 OR 原料状态表，进入 OR 预处理链
6. **推进**——人类确认后 STR-E → `可以分解分配`，对应 OR → `已分配`
7. **回修**——接收 wft02-eng 退回的 `需wft01修订` STR-E，读取缺失说明，按人类改进方案修订 STR-E，人类确认后重新推进为 `可以分解分配`

本 Skill 不负责：

1. FR-BIZ 业务需求的场景业务与输出文档设计（→ `wft01-biz`）
2. NFR 分类与量化（→ `wft01-nfr` / `wft04-nfr`）
3. CU 的配置页面、配置要素、校验保存规则和运行期能力定义（→ `wft02-eng`）
4. 操作页面、操作活动和页面功能需求设计（→ `wft03-eng`）
5. 前后端组件、接口和实现边界设计（→ `wft05-eng`）
6. 25 资产中引擎/CU 模型的正式定义；本 Skill 最多形成名称级候选引用或模型建议

### 1.2 与上下游的衔接

**上游 OR 预处理**：只消费已进入 `01-*.md` 的正式 FR-ENG OR。wft03-biz 产生的引擎能力缺口线索，必须先经人类确认并转化为正式 FR-ENG OR，才能进入本 Skill。

**下游 wft02-eng**：消费状态为 `可以分解分配` / `待补充分解分配` 的 STR-E，展开配置单元 BA。若 wft02-eng 发现 STR-E 缺少场景边界、业务运行追溯、能力链闭合说明或 CU 候选过粗，将 STR-E 退回为 `需wft01修订`。

## 二、引擎场景业务设计基础

### 2.1 引擎场景业务（STR-E）

#### 2.1.1 定义与分类

STR-E 是 FR-ENG 在相关方需求层的结构化表达，末级节点为**场景业务**。角色为流程与IT域的**业务配置人员**——所有引擎配置均由该角色执行，因此 STR-E 架构树上无需角色层做分组维度。

**一个引擎 = 一个 STR-E**：当前约 11 个引擎对应约 11 个 STR-E。每个 STR-E 描述业务配置人员对该引擎的端到端配置业务——从打开配置页面、编辑配置要素、系统校验保存、发布装载、到运行期构件/功能可用的完整闭环。STR-E 的双重身份（A2 PL5 末级节点 ←→ A1 PL3 构件节点）见 [91 规范 §4.1](91-eos-biz-eng-spec.md#41-a1产品)。

> **与 STR-F 的对称性**：STR-E 与 STR-F 在架构层级上完全同构——同为 SL5 末级节点（场景业务）、同有下辖细分节点（CU vs 输出文档）、同为角色端到端职责闭环。区别仅在于场景业务的产出物不是业务文档，而是**可用的平台能力**。

**FR-ENG OR 的五种类型**（不是 STR-E 的分类——一个 STR-E 可承接多种类型的 OR）：

| 类型 | 触发源 | 场景自然终点 |
|------|--------|--------------|
| 配置生成类 | 配置人员提出或维护引擎配置 | 配置通过系统校验并在运行期制品/构件/功能中生效 |
| 构件扩展类 | 业务页面需要新增按钮、右键、图表、钻取等构件能力 | 目标操作页面组件可渲染并使用该构件 |
| 页面组件扩展类 | 现有页面组件无法承载业务操作方式 | 新/扩展页面组件能力可被对应引擎或业务页面调用 |
| 横切治理类 | 权限、审计、版本、发布、回滚、监控等治理需要 | 横切规则对目标业务对象或运行期能力稳定生效 |
| 运行支撑类 | 业务运行页需要引擎能力调用、状态处理或异常恢复 | 引擎能力可被业务页面调用并产生可追溯结果 |

AI 根据 OR 语义判定类型，作为 OR 的能力诉求特征标注——不用于划分 STR-E 边界。

#### 2.1.2 架构与属性

场景业务的架构（能力链）见 §2.2。CU 功能本质和操作页面组件关系见 [91 规范 §2.2](91-eos-biz-eng-spec.md#22-引擎及层级) 与 [§3.3](91-eos-biz-eng-spec.md#33-cu-与操作页面组件及构件的对应关系)。

每条 STR-E 保留从 OR 到引擎到 CU 的追溯链：

```text
FR-ENG OR（含触发来源标注——A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段）
  → 引擎（主能力域）
  → CU 候选
```

触发来源是 OR 级上下文信息——用于说明"业务运行为什么需要这个平台能力"，**不作为 STR-E 的边界划分依据**。STR-E 的边界划分依据是引擎（一个引擎一个 STR-E）。无法判定归属引擎的 OR 标记 `需澄清`，不得推进为正式 STR-E。

STR-E 节点完整要素（写入 `02-*.md` STR-E 节点块）：

- STR-E ID / 名称 / 目标引擎（主能力域）
- 来源 OR 清单（各条标注触发来源类型）
- 能力链
- CU 候选清单
- 完备性检查结果
- 补充 FR-ENG 材料引用
- 变更影响声明
- 版本号 / 确认状态

#### 2.1.3 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 能力链闭合 | 配置/治理意图能走到运行期制品/构件/功能可用 | 生成补充 FR-ENG |
| 引擎归属明确 | 每条 OR 判定到唯一引擎（主能力域）；跨引擎 OR 拆分 | 标记 `需澄清` 或退回 OR 预处理 |
| CU 可展开 | CU 候选足以让 wft02-eng 定位配置单元 | 标记 `[需裁决]` 或 `需澄清` |
| 缺口层级正确 | 构件级/页面组件级/CU 级缺口区分清楚 | 改写缺口说明 |

### 2.2 能力链

#### 2.2.1 定义与构成

能力链是 wft01-eng 判断 STR-E 是否闭合的业务链类比物。它不展开业务输出文档，而是描述平台能力从一个引擎的配置意图到运行期生效的最小闭环。

```text
配置/治理意图
  → 系统处理要求
  → 运行期制品/构件/功能
  → 可用性确认
```

各段含义：

| 段 | 说明 | wft01-eng 粒度 |
|----|------|----------------|
| 配置/治理意图 | 需要配置或治理哪类平台能力 | 名称级表达 |
| 系统处理要求 | 系统至少要校验、保存、发布、装载或控制什么 | 只描述能力要求，不写实现 |
| 运行期制品/构件/功能 | 91 规范中的物理表、功能表单、菜单入口、操作页面构件等 | 名称级，不设计构件 |
| 可用性确认 | 何种结果代表平台能力可用——即业务配置人员完成配置后，运行期业务人员可使用该能力的判定标准 | 作为场景终点 |

> **触发来源不在此链中**：触发来源（A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段）是 OR 级上下文信息，标注在 OR→引擎的追溯链中（§2.1.2），不属于能力链的闭合段。能力链本身只关注"配置侧→运行期可用"，即业务配置人员从打开配置页面到能力可用的完整闭环。

---

### 2.3 CU 候选

#### 2.3.1 定义与记录字段

CU 候选是 STR-E 场景业务中的名称级配置单元线索。wft01-eng 只说明”可能需要哪些配置单元”，不定义每个 CU 的配置页面、配置要素、系统处理细节或运行期构件。

每个 CU 候选至少记录：

| 字段 | 说明 |
|------|------|
| CU 候选名称 | 名称级线索，可带 `[推断]` |
| 目标引擎 / 能力域 | 如实体、流程、工单、看板、菜单、权限、发布等 |
| 来源 OR | 触发该候选的 OR ID |
| 支撑对象 | 业务运行对象、平台治理对象、构件或页面组件缺口 |
| 候选理由 | 为什么需要这个 CU |
| 来源类型 | `OR明示` / `OR隐含` / `构件缺口推断` / `页面组件缺口推断` / `同类引擎推断` / `模型线索推断` |
| 粒度判断 | `可展开` / `过粗待拆` / `过细待并` / `边界待确认` |
| 确认状态 | 人类反馈字段 |

### 2.4 场景业务要素提取规则

Phase B（修订已有 STR-E）与 Phase C（新建 STR-E）共用以下规则。

#### 2.4.1 能力域确定

逐条 OR 提取以下要素：

| 提取项 | 说明 |
|--------|------|
| 触发来源 | 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段（OR 级上下文信息，标注在 OR→引擎追溯链中，不用于 STR-E 边界划分） |
| 能力诉求 | 需要平台提供什么能力 |
| 运行期结果 | 期望生成或增强什么制品、构件或功能 |
| 主能力域 | 归属引擎——实体、流程、工单、看板、菜单、权限、发布、审计等。**这是 STR-E 的分组锚点** |
| 依赖能力 | 被主能力调用或依赖的其他能力域 |

路由规则：

| 情况 | 处理 |
|------|------|
| OR 实际要求业务输出文档或业务流程 | 退回 `wft01-biz` |
| OR 实际是性能、安全、可用性等约束 | 退回 nfr 路径 |
| OR 只是具体业务配置数据 | 标记为业务配置实例，不进入 eng 设计 |
| OR 描述构件/页面组件/CU 缺口，归属明确引擎 | 进入该引擎的 STR-E |
| OR 跨多个引擎 | 输出拆分建议，标记 `需澄清`；无法拆分时标记 `[需裁决]`

#### 2.4.2 场景边界定义

Phase C 新建 STR-E 时的边界定义流程。新建 STR-E 的触发条件：OR 的主能力域指向一个尚无 STR-E 的引擎。

**判定主能力域**：从本组 OR 提取主能力域（引擎）。主能力域一致 → 进入引擎配置范围定义；跨引擎 → 拆分 OR 分组，每组对应一个引擎。

**定义引擎的配置业务闭环**：STR-E 的边界即该引擎完整的配置业务——从打开配置页面开始的端到端闭环。AI 需回答以下问题：

1. 配置人员要配置什么？（配置要素清单——从 OR 中提取）
2. 系统要怎么处理？（校验/保存/发布/装载——从 OR 中提取，不足的进入缺口清单）
3. 配置后产出什么运行期能力？（制品/构件/功能——从 OR 中提取）
4. 怎么算配置完成、能力可用？（可用性确认标准）

**引擎配置范围完整性检查**：

| 判据 | 通过标准 | 不通过处理 |
|------|----------|------------|
| 主引擎单一 | 本组 OR 指向同一引擎；依赖引擎可记录但不改主引擎 | 跨引擎 OR 拆分 |
| 能力链闭合 | 配置意图能走到运行期可用 | 缺口进入补充 OR 材料 |
| 终点明确 | 能说清”何时算配置完成、能力可用” | 标记 `需澄清` |
| 不替代 biz | 不新增业务输出文档、不重做业务场景 | 退回 biz 路径 |

输出**场景边界陈述**：`「<引擎>」的配置业务——业务配置人员打开配置页、编辑<配置要素>、经<系统处理>后<运行期产出>、确认<可用标准>后配置完成。`

边界定义完成后，按 §2.1.2 完整要素组装 STR-E 节点写入 `02-*.md`。

#### 2.4.3 Phase B 引擎匹配检查

Phase B 修订已有 STR-E 时，检查本轮 OR 是否属于该引擎的配置业务范围。引擎匹配是唯一锚点——一个引擎一个 STR-E。

1. 提取本轮 OR 的主能力域 → 与已有 STR-E 的目标引擎比对
2. 引擎一致 → 归入该 STR-E（进入 CU 候选关系检测 §2.5.3）
3. 引擎不一致 → 不属于该 STR-E，退回待聚合池（留待下一轮匹配其他 STR-E 或新建）

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 引擎匹配 | 本轮 OR 归入该引擎的 STR-E | 进入 CU 候选关系检测（§2.5.3）+ 输出变更影响声明 |
| 引擎不匹配 | OR 归属其他引擎或新引擎 | 退回待聚合池，留待下一轮匹配或触发 Phase C 新建 |

#### 2.4.4 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 STR-E | Phase C 新建 STR-E |
|------|----------------------|-------------------|
| 判定范围 | STR-E 已承接的全部 OR + 本轮新 OR | 待聚合池本组 OR |
| 引擎锚点 | 以已有引擎的能力链为基线，仅扫描本轮新 OR 是否引入新链段 | 从零构建引擎的能力链 |
| 归组 | 执行引擎匹配检查（§2.4.3）——引擎一致则归入，不一致则退回待聚合池 | 执行引擎配置范围定义（§2.4.2）——主引擎不一致时拆分 OR 组 |
| 要素提取 | 在基线基础上增量合并（CU 关系检测见 §2.5.3） | 全量提取 |
| CU 重识别 | 合并重识别可能导致已有 CU 候选的归属变更——标记 `[CU归属变更]` 并附变更原因 | 无此问题 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 CU 候选推断规则

Phase B（修订已有 STR-E）与 Phase C（新建 STR-E）共用以下规则。

#### 2.5.1 能力链提取

**识别 CU 候选清单**：从当前操作范围内的全部 OR 中识别可能触及的配置单元。去重/收敛后形成 CU 候选清单，每个候选 → 能力链上一个配置节点。多条 OR 指向同一 CU 时归入同一候选（要素收敛）。

**逐候选判定目标引擎/能力域**：从 [25 资产 §1.1](../../80-pl4eos-2-eosdata/25-eos-engine-models.md#11-引擎全景) 动态读取引擎清单（每次运行时读取、不缓存），根据 CU 候选的功能特征匹配目标引擎。wft01 仅有 OR 文本信息，CU 候选的引擎归属**全量标注 `[推断]`**，定位为供下游 wft02 校验的**候选建议**而非最终判定。

#### 2.5.2 CU 候选标注与来源类型

对每个 CU 候选逐项判定要素并标注。标注字段见 §2.3.1。

**来源类型定义**（CU 候选）：

| 来源类型 | 含义（含示例） |
|----------|---------------|
| `OR明示` | OR 文本中直接说出该 CU。如”需要配置流程节点” → “流程节点配置”CU |
| `OR隐含` | OR 未直接说出，但不推出该 CU 则能力链存在逻辑缺口。如”流程发布后需支持回滚” → 必然需要”回滚配置”CU |
| `构件缺口推断` | OR 描述业务页面需要某构件能力，但现有构件无法满足 → 推断需要新的构件配置 CU |
| `页面组件缺口推断` | OR 描述页面操作方式现有页面组件无法承载 → 推断需要新的页面组件配置 CU |
| `同类引擎推断` | 同引擎类型已有 STR-E 的类似 CU 模式，当前 OR 场景与之高度相似时推断 |
| `模型线索推断` | 25 资产中已有与当前能力域匹配的 CU 定义，但 OR 未提及 |

#### 2.5.3 Phase B CU 候选关系检测

Phase B 修订已有 STR-E 时，边界检查通过后，将本轮提取的 CU 候选与 STR-E 已有 CU 候选清单比对。比对锚点为**CU 候选名称+目标引擎匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | CU 匹配 + 引擎相同 + 至少一个来源非 `OR明示` | 来源升级（`OR隐含`→`OR明示`、`构件缺口推断`→`OR明示`、`页面组件缺口推断`→`OR明示`、`同类引擎推断`→`OR明示`、`模型线索推断`→`OR明示`），内部细分结论=`确认` |
| 无新增 | CU 匹配 + 引擎相同 + 所有来源已为 `OR明示` | 追加 OR 引用 + 增量合并新 OR 中的候选理由/粒度判断（如有新内容），内部细分结论=`改进` |
| 引擎归属变更 | CU 匹配 + **引擎不同**（合并重识别导致） | 更新已有 CU 的目标引擎 + 内部细分结论=`引擎归属变更` + 变更原因。不新增 CU |
| 补充 | CU 不匹配 | 新增到 CU 候选清单，来源=`OR明示`，内部细分结论=`新增` |
| 过时 | 基线已有 CU **未被**本轮提取覆盖（引擎配置范围变更后，基线中某些 CU 不再落入新的能力链追踪范围） | 内部细分结论=`过时` + 追加说明”引擎配置范围变更后未落入新的能力链追踪范围，请确认是否移除”。保留该 CU 在候选清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 OR 重新识别目标引擎**——新 OR 可能改变 CU 特征导致引擎归属变更（表中 `引擎归属变更` 行）。来源证据强度只升不降：`OR隐含`/`构件缺口推断`/`页面组件缺口推断`/`同类引擎推断`/`模型线索推断` → `OR明示`，在 `确认` 行触发。

`[调整]` 是与关系类型正交的叠加标记：已有 CU 的名称/能力域/粒度判断变化，在关系标记之外叠加 `[调整]`。

### 2.6 STR-E 节点生命周期

STR-E 节点沿 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §8.6 状态名映射表（wft01-eng 列）。并行推进规则（资产线与 BA 线互不阻塞）见 91 规范 §8.6。

**主线流转**（wft01-eng ←→ wft02-eng）：

```
待确认方案 ──人类确认──→ 可以分解分配 ──wft02锁定──→ 在分解分配 ──wft02完成──→ 已分解分配
     ↑                        ↑                         │
     │                        │               wft02退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

**上游变更**（新 OR 汇入触发 STR-E 修订）：

```
可以分解分配 ──新OR修订──→ 可以分解分配（版本递增，wft02 未消费）
在分解分配   ──新OR修订──→ 在分解分配（版本递增，wft02 增量处理）
已分解分配   ──新OR修订──→ 待补充分解分配 ──wft02补全──→ 已分解分配
```

**本 Skill 的写回范围**：`待确认方案` / `可以分解分配` / `待补充分解分配` / `需wft01修订`。`在分解分配` 和 `已分解分配` 由 wft02-eng 写入和推进。

下游退回 `需wft01修订` 时：读取 wft02-eng 的缺失说明 → 按人类改进方案修订 STR-E（走 Phase B 修订流程）→ 人类确认 → STR-E → `可以分解分配`。

变更传播协议的通用定义（变更类型分类、判定优先级、声明格式模板、增量清单与变更影响声明的分工）见 [91 规范 §8.7](91-eos-biz-eng-spec.md#87-变更传播协议)。

### 3.1 Step Start

运行时 AI 按以下顺序执行：

1. **输入校验**：
   - STR-E 状态为 `需wft01修订` 且人类未提供改进方案 → 输出 wft02-eng 的缺失说明，提示提供改进方案 → **退出**
   - OR 状态不是 `待处理` → 输出不合格条目及当前状态 → **退出**
   - OR 类型不是 FR-ENG：
     - 含 FR-BIZ → 输出类型分布，提示走 `wft01-biz` → **退出**
     - 含 NFR → 输出类型分布，提示走 `wft01-nfr` → **退出**
     - 为业务配置实例 → 标记并提示不进入 eng 设计 → **退出**
   - OR >10 条 → 输出超限提示 → 人类确认后继续或退出
   - OR 是 wft03-biz 线索但未转正式 OR → 输出"输入未正式化"，提示先确认并写入 `01-*.md` → **退出**
   - OR 无法判定归属引擎（主能力域不明）→ 输出归属不明条目，标记 `需澄清` → **退出**
   - OR 跨多个引擎 → 输出引擎混杂提示 → 人类确认拆分后继续或退出
   - 无 OR 选中 + 无待处理反馈的 STR-E 节点 + 无 `需wft01修订` 的 STR-E 节点 → 输出"无待处理对象"→ **退出**
2. **退回优先**：存在 `需wft01修订` 的 STR-E 节点（且人类已提供改进方案）→ 读取 wft02-eng 的缺失说明，按人类方案走 Phase B 修订，人类确认后推进为 `可以分解分配`
3. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 STR-E 节点 → 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 OR，Step End 时提示
4. **新 OR 路由**：有未处理的 OR 条目 → 进入 Step 1→Step 3，逐条执行 Phase A 溯源与路由，归入已有 STR-E（→Phase B）或待聚合池（→Phase C）

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 STR-E 的边界/能力链/CU 候选。Step 3 的 Phase A 宿主匹配必须基于 Step 2 修改后的最新 STR-E 内容，不得使用缓存旧状态。

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：场景边界 + 能力链 + 每个 CU 候选 + 每条补充 FR-ENG 缺口。各条目的 `确认状态` 字段位于 `02-*.md` STR-E 节点块各条目正文中。

#### 3.3.1 AI 处理流程

> **原则**：反馈处理不是对人类标注的机械执行，而是以 OR 需求理解为锚点的方案修订。AI 在 Step 2 中与 Step 3 同为设计者——先理解人类反馈在 OR 需求语境中的含义，再执行修订，最后检查修订后的 STR-E 是否仍满足 OR 需求。

本 Skill 特化参数见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 实例化参数表（wft01-eng 列）。

### 3.4 Step 3 · STR-E 场景业务设计

#### 3.4.1 Phase A：OR 溯源与路由

对每条新 OR 执行溯源提取（触发来源 + 能力诉求 + 运行期结果 + 主能力域，详见 §2.4.1）。先判定路径归属——实际为业务输出文档/流程→退回 `wft01-biz`，实际为性能/安全等约束→退回 nfr 路径，仅为业务配置数据→标记不进入 eng 设计。路径确认后，逐条按主能力域（引擎）做宿主匹配：

| 条件 | 路由 |
|------|------|
| OR 的主能力域命中已有 STR-E 的目标引擎 | 归入该 STR-E → Phase B |
| OR 的主能力域尚无对应 STR-E | 进入待聚合池 → Phase C |

待聚合池按**主能力域（引擎）**分组。此阶段仅粗略分组，CU 候选去重和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 STR-E

1. **要素提取**：从本轮 OR 提取触发来源（OR 级上下文）、能力诉求、运行期结果和主能力域（详见 §2.4.1）。先提取后检查——主引擎不一致时退回待聚合池
2. **引擎匹配检查**：确认 OR 的主能力域与 STR-E 的目标引擎一致（详见 §2.4.3）
3. **CU 候选关系检测**：比对已有基线，判定确认/无新增/引擎归属变更/补充/过时（详见 §2.5.3）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 STR-E 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 STR-E

1. **确定引擎** → 从 OR 语义提取主能力域（详见 §2.4.1）
2. **定义引擎配置范围** → 判定配置要素→系统处理→运行期产出→可用确认，输出场景边界陈述（详见 §2.4.2）
3. **要素提取** → 识别 CU 候选清单 + 逐候选判定目标引擎 + 标注字段（详见 §2.5，含粒度判断与来源类型）
4. **构建能力链** → 按配置→处理→运行期→可用确认排列，标注依赖关系（详见 §2.2）
5. **标注 OR 类型** → 逐条 OR 判定其 FR-ENG OR 类型（配置生成类 / 构件扩展类 / 页面组件扩展类 / 横切治理类 / 运行支撑类，详见 §2.1.1），作为 OR 级能力诉求特征——不用于划分 STR-E 边界
6. **组装 STR-E** → 引擎名称 + 场景边界陈述 + 能力链 + CU 候选清单 + 推理依据，写入 `02-*.md`（完整要素见 §2.1.2）

### 3.5 Step 4 · 补充 FR-ENG 与变更声明

Step 4 按每个 STR-E 实例独立执行。新建 STR-E → 全量检查；修订已有 STR-E → 仅当能力链拓扑变化（新增/过时/引擎归属变更）时重验闭合，要素机械检查始终针对变更文档执行。

**1. 能力链闭合检查**

- 逐 STR-E 检查能力链三段闭合：配置/治理 → 系统处理 → 运行期可用
- 配置/治理段缺失（缺少配置或治理意图）→ 缺口类型 = `补充OR`
- 系统处理段缺失（缺少校验/保存/发布/装载/控制要求）→ 缺口类型 = `补充OR`
- 运行期可用段缺失 → 细分：缺少运行期制品/构件/功能 → `补充OR`；缺少”何时算配置完成、能力可用”→ `澄清项`
- CU 候选 `过粗待拆` → 缺口类型 = `拆分建议`，交人类裁决
- 缺口 → 进入「补充 FR-ENG 材料生成」。不因缺口脑补节点——缺口就是缺口

**2. 要素机械检查**（逐 STR-E，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 引擎名称 / 场景边界陈述 **非空**
- [ ] 能力诉求 / 运行期结果 / 主能力域 **有标注**（含合理空置原因）
- [ ] 追溯链（FR-ENG OR → 引擎 → CU 候选）**完整**，各条 OR 已标注触发来源类型
- [ ] CU 候选清单 **非空**，每条 CU 标注来源类型（`OR明示` / `OR隐含` / `构件缺口推断` / `页面组件缺口推断` / `同类引擎推断` / `模型线索推断`）和粒度判断（`可展开` / `过粗待拆` / `过细待并` / `边界待确认`）
- [ ] 变更影响声明 **已写入**（首版写”首版，无变更”；格式见 §2.7）

**3. 补充 FR-ENG 材料生成**

闭合缺口时生成。写入 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<STR-E名称>补充原始需求材料.md`，包含：材料编号 / 来源 STR-E / 来源 OR / 缺口类型 / 补充需求文本 / 推断依据 / 建议类型（`补充OR` / `澄清项` / `拆分建议` / `模型建议`）/ 确认状态。同时登记到 `01-eos-sysdev-status.md` 表 A（生命周期=`已登记`）。文件引用写入 STR-E 节点的完备性检查结果。

**4. 横切治理触发检查**

从 25 资产读取横切治理引擎清单（权限/审计/版本/发布/回滚/监控），判定当前批次 STR-E 是否触发了横切治理需求（当前批 STR-E 涉及引擎的新建/修改/发布或运行期监控能力）。缺对应 FR-ENG OR 且触发时 → 在 Step End 中提示人类渐进增补。不生成补充材料、不登记状态表、不自动补。

### 3.6 Step 5 · 资产写回与落账

仅写回状态=`可以分解分配` 的 STR-E 节点。人类已在 Step 2 确认方案（含引擎判定与 CU 候选对齐结果），Step 5 不设二次确认。Step 3 新产出留待下一轮。

1. 遍历已确认 STR-E，按引擎判定结果写回 23 资产：
   - 已有引擎 → 定位已有块，追加场景引用（去重）
   - 新引擎候选 → 新建候选建议，附置信度说明
2. 遍历已确认 STR-E 的 CU 候选，写回 25 资产：
   - 仅写 CU 候选名称级引用或模型建议，不写 CU 详细定义
3. 记录资产写回记录到 `02`（日期/路径/动作/判定）
4. 对应 OR 条目 → `已分配`；补充 FR-ENG 材料登记到 `01` 原料状态表
5. 记录 OR→STR-E→23/25 引用链

写回要求：幂等去重、局部写回、全貌同步。

说明：Step 5 不改变 STR-E 状态。资产写回是独立收尾，不构成 wft02-eng 前置条件。
