# FR-ENG OR → STR-E · 引擎场景业务设计
**Skill ID**: wft01-eng-or2str

> **概述**：接收正式 FR-ENG OR，经前置校验、材料加载和反馈处理后，将非结构化引擎需求转化为 STR-E 引擎场景业务方案。该方案以“业务运行为什么需要平台能力”为锚，定义 A1 平台能力场景业务边界，名称级推断场景业务所需配置单元（CU）候选，并识别能力链缺口形成补充 FR-ENG 材料。
>
> **输入 → 输出**：FR-ENG OR 条目（≤10 条）/ 有反馈的 STR-E 节点 → STR-E 场景业务方案（能力链 + 场景边界 + CU 候选 + 业务运行追溯 + 补充 FR-ENG 缺口）+ OR 推进为 `已分配` + STR-E 推进为 `可以分解分配`
>
> **适用场景**：瀑布式系统设计第1步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v4.1 | **修订**：2026-07-08

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台能力相关方——「你听懂了我需要哪类平台能力、它服务哪条业务运行链」。把 FR-ENG OR 转化为 STR-E 场景业务，不直接设计 CU 的配置页面、配置要素、操作页面或组件。

**目标**：

1. **推断生成引擎场景业务节点**——识别 FR-ENG OR 背后的平台能力场景：谁提出配置/治理意图，为了支撑哪类业务运行，能力从触发到生效的自然边界是什么。
2. **推断场景业务配置单元**——在名称级列出该场景业务可能触及的 CU 候选，标注来源、支撑对象和判定依据，为 wft02-eng 展开配置单元 BA 提供输入。
3. **基于能力链补充引擎需求**——检查“触发来源 → 配置/治理 → 系统处理 → 运行期构件/功能可用”的能力链，发现缺口时形成补充 FR-ENG OR 材料。
4. **建立业务运行追溯**——保留 `A2/Bn 业务运行对象或横切平台能力 → A1 引擎场景业务 → CU 候选` 的追溯。
5. **判断路径归属**——将 FR-BIZ、NFR、业务配置实例需求及时路由到对应路径，避免 eng 路径替业务链或非功能路径做设计。

本 Skill 负责：

1. **接收**——校验输入为正式 FR-ENG OR，状态为 `待处理`，数量 ≤10；状态/类型不符时退出并提示路由。
2. **溯源**——识别需求支撑的业务运行对象、平台治理对象或横切能力阶段；无法说明支撑对象时标记 `需澄清`。
3. **定界**——形成 STR-E 场景业务边界，回答“这个平台能力场景从哪里开始、到哪里算完成”。
4. **归组**——按同一平台能力场景匹配已有 STR-E；边界一致则归入，边界扩展则修订，边界冲突则标记 `[需裁决]`。
5. **识别 CU 候选**——名称级识别可能触及的配置单元，不定义配置页面、配置要素或运行期构件。
6. **补需**——检出能力链缺口，生成补充 FR-ENG OR 材料，进入 OR 预处理链。
7. **推进**——人类确认后 STR-E → `可以分解分配`，对应 OR → `已分配`。
8. **回修**——接收 wft02-eng 退回的 `需wft01修订` STR-E，按缺失说明和人类改进方案修订。

本 Skill 不负责：

1. FR-BIZ 业务需求的场景业务与输出文档设计（→ `wft01-biz`）。
2. NFR 分类与量化（→ `wft01-nfr` / `wft04-nfr`）。
3. CU 的配置页面、配置要素、校验保存规则和运行期能力定义（→ `wft02-eng`）。
4. 操作页面、操作活动和页面功能需求设计（→ `wft03-eng`）。
5. 前后端组件、接口和实现边界设计（→ `wft05-eng`）。
6. 25 资产中引擎/CU 模型的正式定义；本 Skill 最多形成名称级候选引用或模型建议。

### 1.2 与上下游的衔接

**上游 OR 预处理**：只消费已进入 `01-*.md` 的正式 FR-ENG OR。wft03-biz 产生的引擎能力缺口线索，必须先经人类确认并转化为正式 FR-ENG OR，才能进入本 Skill。

**下游 wft02-eng**：消费状态为 `可以分解分配` / `待补充分解分配` 的 STR-E，展开配置单元 BA。若 wft02-eng 发现 STR-E 缺少场景边界、业务运行追溯、能力链闭合说明或 CU 候选过粗，将 STR-E 退回为 `需wft01修订`。

## 二、引擎场景业务设计基础

> 本章定义 wft01-eng 的操作对象：A1 平台能力场景业务、能力链、CU 候选和追溯关系。A1 产品定义见 [91 规范 §4.1](91-eos-biz-eng-spec.md#41-a1产品)，CU 功能本质和操作页面组件关系见 [91 规范 §2.2](91-eos-biz-eng-spec.md#22-引擎及层级) 与 [§3.3](91-eos-biz-eng-spec.md#33-cu-与操作页面组件及构件的对应关系)，eng 路径分工见 [91 规范 §七](91-eos-biz-eng-spec.md#七-平台能力系统设计)。操作流程见 §三。

### 2.1 A1 平台能力场景业务（STR-E）

STR-E 是 FR-ENG 在相关方需求层的结构化表达，末级节点为**场景业务**。这里的场景业务不是业务人员办理采购、生产、售后等业务，而是平台能力从“配置/治理意图”到“运行期构件或功能可用”的端到端场景。

典型场景类型：

| 类型 | 触发源 | 场景自然终点 |
|------|--------|--------------|
| 配置生成类 | 配置人员提出或维护引擎配置 | 配置通过系统校验并在运行期制品/构件/功能中生效 |
| 构件扩展类 | 业务页面需要新增按钮、右键、图表、钻取等构件能力 | 目标操作页面组件可渲染并使用该构件 |
| 页面组件扩展类 | 现有页面组件无法承载业务操作方式 | 新/扩展页面组件能力可被对应引擎或业务页面调用 |
| 横切治理类 | 权限、审计、版本、发布、回滚、监控等治理需要 | 横切规则对目标业务对象或运行期能力稳定生效 |
| 运行支撑类 | 业务运行页需要引擎能力调用、状态处理或异常恢复 | 引擎能力可被业务页面调用并产生可追溯结果 |

### 2.2 能力链

能力链是 wft01-eng 判断 STR-E 是否闭合的业务链类比物。它不展开业务输出文档，而是描述平台能力从触发到生效的最小闭环。

```text
触发来源
  → 配置/治理意图
  → 系统处理要求
  → 运行期制品/构件/功能
  → 业务运行可用性确认
```

各段含义：

| 段 | 说明 | wft01-eng 粒度 |
|----|------|----------------|
| 触发来源 | 来自业务运行对象、平台治理对象、构件缺口或页面组件缺口 | 说明来源，不重做 biz 设计 |
| 配置/治理意图 | 需要配置或治理哪类平台能力 | 名称级场景表达 |
| 系统处理要求 | 系统至少要校验、保存、发布、装载或控制什么 | 只描述能力要求，不写实现 |
| 运行期制品/构件/功能 | 91 规范中的物理表、功能表单、菜单入口、操作页面构件等 | 名称级，不设计构件 |
| 业务运行可用性确认 | 何种结果代表平台能力可用 | 作为场景终点 |

### 2.3 CU 候选

CU 候选是 STR-E 场景业务中的名称级配置单元线索。wft01-eng 只说明“可能需要哪些配置单元”，不定义每个 CU 的配置页面、配置要素、系统处理细节或运行期构件。

每个 CU 候选至少记录：

| 字段 | 说明 |
|------|------|
| CU 候选名称 | 名称级线索，可带 `[推断]` |
| 目标引擎 / 能力域 | 如实体、流程、工单、看板、菜单、权限、发布等 |
| 来源 OR | 触发该候选的 OR ID |
| 支撑对象 | 业务运行对象、平台治理对象、构件或页面组件缺口 |
| 候选理由 | 为什么需要这个 CU |
| 来源类型 | `OR明示` / `OR隐含` / `构件缺口推断` / `页面组件缺口推断` / `同类引擎推断` / `模型线索推断` |
| 粒度判断 | `可展开` / `过粗待拆` / `过细待并` / `边界待确认` |
| 确认状态 | 人类反馈字段 |

### 2.4 业务运行追溯

每条 STR-E 必须保留追溯：

```text
FR-ENG OR
  → 触发来源（A2/Bn 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段）
  → A1 引擎场景业务
  → CU 候选
```

无法说明触发来源的能力，不得推进为正式 STR-E；只能作为需澄清线索或补充 OR 候选。

### 2.5 场景边界判据

| 判据 | 通过标准 | 不通过处理 |
|------|----------|------------|
| 同一触发来源 | 本组 OR 指向同一类业务运行对象、治理对象或构件/页面组件缺口 | 拆分 STR-E 或退回 OR 预处理 |
| 同一能力链 | OR 能连成同一条触发到生效的链 | 分场景处理 |
| 同一主引擎/能力域 | 主能力域一致；依赖引擎可记录但不改主场景 | 主引擎混杂时拆分或裁决 |
| 终点明确 | 能说清“何时算平台能力可用” | 标记 `需澄清` |
| 不替代 biz | 不新增业务输出文档、不重做业务场景 | 退回 biz 路径 |

### 2.6 完备性判据

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| 能力链闭合 | 触发来源能走到运行期制品/构件/功能可用 | 生成补充 FR-ENG |
| 场景边界单一 | 一个 STR-E 只表达一个平台能力场景 | 拆分建议，退回 OR 预处理 |
| CU 可展开 | CU 候选足以让 wft02-eng 定位配置单元 | 标记 `[需裁决]` 或 `需澄清` |
| 追溯清晰 | 能说明支撑对象或横切阶段 | 退回澄清 |
| 缺口层级正确 | 构件级/页面组件级/CU 级缺口区分清楚 | 改写缺口说明 |

### 2.7 节点生命周期与变更传播

生命周期引用 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型)。本 Skill 状态映射：

| 通用态 | STR-E 状态 |
|--------|------------|
| 待确认方案 | `待确认方案` |
| 可推进态 | `可以分解分配` |
| 锁定态 | `在分解分配` |
| 已完成态 | `已分解分配` |
| 待补充态 | `待补充分解分配` |
| 待修订态 | `需wft01修订` |

变更传播引用 [91 规范 §8.7](91-eos-biz-eng-spec.md#87-变更传播协议)。wft01-eng 的变更影响判定：

| 变更 | 类型 | 下游影响 |
|------|------|----------|
| 仅追加 OR 来源或补强证据 | 无变更 | wft02-eng 无需动作 |
| 新增 CU 候选，场景边界不变 | 增量型 | wft02-eng 增量设计 CU |
| 修改 CU 候选名称、主引擎、支撑对象或能力链段 | 修订型 | wft02-eng 修订受影响 CU |
| 场景边界扩展、拆分、合并或主能力域变化 | 结构型 | 等人类裁决后再展开 |

### 3.4 Step 3 · STR-E 场景业务设计

#### Phase A · OR 溯源与路由

逐条 OR 提取：

| 提取项 | 说明 |
|--------|------|
| 触发来源 | 业务运行对象 / 平台治理对象 / 构件缺口 / 页面组件缺口 / 横切能力阶段 |
| 能力诉求 | 需要平台提供什么能力 |
| 运行期结果 | 期望生成或增强什么制品、构件或功能 |
| 主能力域 | 实体、流程、工单、看板、菜单、权限、发布、审计等 |
| 依赖能力 | 被主能力调用或依赖的其他能力域 |

路由规则：

| 情况 | 处理 |
|------|------|
| OR 实际要求业务输出文档或业务流程 | 退回 `wft01-biz` |
| OR 实际是性能、安全、可用性等约束 | 退回 nfr 路径 |
| OR 只是具体业务配置数据 | 标记为业务配置实例，不进入 eng 设计 |
| OR 描述构件/页面组件/CU 缺口 | 进入 wft01-eng |

#### Phase B · 匹配已有 STR-E

按以下顺序匹配：

1. 同一触发来源或同一缺口对象。
2. 同一能力链终点。
3. 同一主能力域/主引擎。
4. CU 候选可归入同一场景。

匹配结果：

| 结果 | 判定 | 动作 |
|------|------|------|
| 直接归入 | 本轮 OR 只补强既有 STR-E | 追加来源，标记 `[确认]` |
| 边界扩展 | 终点延伸但仍属同一能力链 | 修订 STR-E，输出变更声明 |
| 新增 CU | 场景不变但新增 CU 候选 | 增量加入候选清单 |
| 宿主误匹配 | 不属于同一能力链 | 退回待聚合池或新建 |
| 边界冲突 | 主能力域或终点冲突 | 标记 `[需裁决]` |

#### Phase C · 新建 STR-E

无法匹配既有 STR-E 时新建：

1. 定义场景名称：`<主能力域><配置/治理/运行支撑>场景`，与已有命名风格一致。
2. 定义场景边界：起点、终点、参与者、运行期可用标准。
3. 生成能力链：触发来源 → 配置/治理意图 → 系统处理要求 → 运行期制品/构件/功能 → 可用性确认。
4. 识别 CU 候选：名称级、来源类型、粒度判断。
5. 执行完备性检查。

STR-E 节点要素：

- STR-E ID / 名称 / 目标引擎或能力域
- 来源 OR 清单
- 触发来源与业务运行追溯
- 场景边界陈述
- 能力链
- CU 候选清单
- 完备性检查结果
- 补充 FR-ENG 材料引用
- 变更影响声明
- 版本号 / 确认状态

### 3.5 Step 4 · 补充 FR-ENG 与变更声明

#### 3.5.1 补充 FR-ENG 生成规则

| 缺口 | 生成材料 |
|------|----------|
| 缺少配置或治理意图 | 补充“需要配置/治理哪类能力”的 FR-ENG |
| 缺少系统处理要求 | 补充“需要校验/保存/发布/装载/控制什么”的 FR-ENG |
| 缺少运行期制品/构件/功能 | 补充“运行期应生成或增强什么”的 FR-ENG |
| 缺少可用性确认 | 补充“何时算能力可用”的 FR-ENG |
| CU 候选过粗 | 补充“需拆分能力域或候选 CU”的说明，交人类裁决 |
| 主能力域混杂 | 输出拆分建议，不生成单一 STR-E |

补充 FR-ENG 材料至少包含：

- 材料 ID
- 来源 STR-E / 来源 OR
- 缺口类型
- 补充需求文本
- 推断依据
- 建议类型：`补充OR` / `澄清项` / `拆分建议` / `模型建议`
- 确认状态

#### 3.5.2 变更影响声明

每次新建或修订 STR-E 后写入变更影响声明；首版写“首版，无变更”。修订时按 §2.7 判定无变更、增量型、修订型或结构型，并列出受影响 CU 候选和下游 wft02-eng 建议动作。

### 3.6 Step 5 · 资产写回与落账

仅对已确认 STR-E 执行：

1. `02`：STR-E → `可以分解分配`，写入版本、确认状态、变更影响声明。
2. `01`：对应 OR → `已分配`；补充 FR-ENG 材料进入 OR 预处理链。
3. `23`：写入 A1 产品/引擎引用或候选建议。
4. `25`：只写 CU 候选名称级引用或模型建议，不写 CU 详细定义。

资产写回与 wft02-eng 消费并行推进；写回完成与否不改变 STR-E 的可消费状态。

### 3.7 Step End · 运行结束输出

遵循 [91 规范 §8.8](91-eos-biz-eng-spec.md#88-skill-通用约定) 的三区模板。

```text
当前状态：<待确认方案 / 可以分解分配>
  STR-E：新增/修订 <N> 个引擎场景业务；识别 CU 候选 <N> 个；补充 FR-ENG <N> 条；待裁决 <N> 项。

一、方案反馈
  A. 整体确认 -> 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 -> 在确认状态中标注 [修改]：...
  C. 驳回重做 -> 在确认状态中标注 [驳回]：...

二、下一步
  本Skill -> 存在未处理反馈 / 需wft01修订 / 新 FR-ENG OR 时重入
  后续    -> STR-E 状态为 可以分解分配 后进入 wft02-eng
```
