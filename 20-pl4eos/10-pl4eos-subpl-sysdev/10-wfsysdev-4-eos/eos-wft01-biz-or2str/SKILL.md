## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 接收同角色 FR-BIZ OR（≤10条），校验类型/数量/状态 | FR-ENG → `wft01-eng` |
| 按用户角色匹配已有 STR-F → 归入（Phase B）或待聚合池（Phase C） | NFR → `wft01-nfr` |
| 定义场景职责边界（= 主责角色的业务对象闭环）+ 业务链文档序列 + 引擎候选 + Bn 对齐 | 下游详细分解 → `wft02-biz` |
| E2E 闭合检查 + 生成补充 OR 材料 | 无 OR 输入的治理 STR-F 不主动展开 |
| 人类确认后写回 23 资产 + 推进 STR-F→`可以分解分配` + OR→`已分配` | 业务人员确认（人类线下活动） |
| 接收 wft02 退回的 `需wft01修订` STR-F，按人类方案修订 | — |

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `ort03` | FR-BIZ OR 写入 `01-*.md`，状态=`待处理`。通过 `## AI可以处理节点` 的"待 wft01-biz 处理"分节检测 |
| 下游 | `wft02-biz` | 消费 `可以分解分配`/`待补充分解分配` 的 STR-F。缺陷时退回 `需wft01修订`+缺失说明 |
| 同级 | `wft01-eng`、`wft01-nfr` | 各自处理 FR-ENG / NFR，本 Skill 输入校验检出后退出并提示路由 |

## 二、操作流程

### Step Start · 前置校验与路由

**入口检测**（按 [§A.4](../protocols/wft01-runtime-protocols.md#a4-入口条件与优先级step-start)）：

```bash
# 1. 读取待处理节点
bash ../scripts/read-section.sh ../../80-pl4eos-2-eosdata/01-eos-original-requirements.md "AI可以处理节点"
bash ../scripts/read-section.sh ../../80-pl4eos-2-eosdata/02-eos-stakeholder-requirements-architecture.md "AI可以处理节点"
```

**输入校验**（按顺序，命中即退出）：

| 条件 | 判定 | 动作 |
|------|------|------|
| OR 状态=`需退回重切` | 不可处理 | 输出退回记录 → **退出** |
| OR 状态≠`待处理` | 不可处理 | 输出当前状态 → **退出** |
| OR 分属多个角色 | 不可处理 | 输出角色分布 → **退出** |
| OR 类型含 FR-ENG/NFR | 路由错误 | 输出类型分布 + 路由指引 → **退出** |
| 同角色 OR >10 条 | 软提示 | 输出超限提示 → 人类确认 |
| 无任何待处理 | — | 输出"无待处理对象"→ **退出** |

**退回优先**：存在 `需wft01修订` STR-F → 检查人类是否提供改进方案（§A.4 退回门禁）。已提供 → 读取缺失说明，走 Phase B 修订。未提供 → 输出缺失说明 → **退出**。

### Step 2 · 方案反馈处理

**触发条件**：Step Start 检出 `需wft01修订` STR-F，或上一轮 Step End 的反馈等待中人类提出修改意见。

**处理规则**：

1. 从当前轮次对话上下文或退回缺失说明中读取人类反馈意图
2. **逐条处理**（按人类反馈内容）：
   - AI 输出方案后人类直接回复修改意见 → 在当前轮次继续对话处理，不重新走 Step Start
   - wft02 退回的 `需wft01修订` → 下一轮 Skill 调用时走 Step Start 退回优先
3. 修改后检查是否仍满足该 STR-F 所承接的 OR 需求
4. 修改导致结构性变更（边界/引擎/PL6-B 增删）→ 按需重入 Step 3
5. 全部条目获人类认可 → STR-F → `可以分解分配`
6. **元信息维护**：
   ```bash
   bash ../scripts/update-meta.sh <02-file> bump-version
   bash ../scripts/update-meta.sh <02-file> update-head
   ```

### Step 3 · 场景业务设计

#### Phase A — OR 路由

对每条新 OR：
1. 从已加载的 OR 节点块（Step 1 通过 `read-node.sh` 获取）中读取 `**所属角色**` 字段——角色已在 OR 归一化时标注
2. 轻量提取：文档名称 + 触发动作（够路由即可）
3. 宿主匹配——OR 的文档名称 + 描述职责落入已有 STR-F 的场景职责边界 → Phase B；否则 → 待聚合池 → Phase C

待聚合池按**触发动作相似 + 文档名称重叠**分组。

#### Phase B — 修订已有 STR-F

**执行顺序**：
1. **要素提取**——从本轮 OR 提取文档名称和支撑引擎
2. **边界匹配检查**——确认 OR 在 STR-F 边界内（[§2.3.3](../eos-wft01-biz-or2str.md#233-phase-b-边界匹配检查)）（详见 human spec）：
   - 边界内 → 进入关系检测
   - 边界扩展 → 更新边界陈述 + `[推断]`
   - 退回规范化 → 输出拆分建议，OR→`需退回重切`
   - 宿主误匹配 → 退回待聚合池
3. **业务链关系检测**——比对已有基线（[§2.4.5](../eos-wft01-biz-or2str.md#245-phase-b-业务链关系检测)）（详见 human spec）：
   - 确认（文档匹配+引擎相同+来源非OR明示）→ 来源升级
   - 无新增（文档匹配+来源已为OR明示）→ 追加引用+增量合并
   - 引擎变更（文档匹配+引擎不同）→ 更新引擎+变更原因
   - 补充（文档不匹配）→ 新增到业务链
   - 过时（基线文档未被本轮覆盖）→ `[过时]`+保留不删
4. **变更影响声明**——按 [§A.7](../protocols/wft01-runtime-protocols.md#a7-变更传播协议) 判定变更类型，写入 STR-F 节点末尾

#### Phase C — 新建 STR-F

**执行顺序**：

1. **确定业务域**——从已加载的 OR 节点块的 `**所属角色**` 字段获取角色名。若 Step 1 已加载的角色索引中有该角色的业务域信息则直接引用；否则用 `bash ../scripts/read-node.sh ../../80-pl4eos-2-eosdata/21-eos-stakeholder-roles.md ROLE-<ID>` 加载角色定义块查找。若 21 文件中无该角色或角色定义中无业务域字段，标记 `[推断]` 并基于角色职责语义匹配
2. **定义端到端边界**——识别触发→追踪自然终点→闭合验证→边界检查（[§2.3.2](../eos-wft01-biz-or2str.md#232-端到端边界定义)）（详见 human spec）
3. **判定 STR-F 类型**——D 或 PCA（判据见附录 A.1）
4. **逐文档要素提取**：
   - **a. 封面模式**——正文变更是否需要审批/发布/版本追溯？→ 是=正式 / 否=轻量
   - **b. 支撑引擎**——按正文数据类型匹配功能引擎候选，全量 `[推断]`（引擎清单从 25 资产动态读取）
   - **c. 任务类型**——零个或一个（计划/流程/工单）。**R4 约束**：场景业务中第一个有任务类型的文档，任务类型必然是计划
   - **d. PL6-B 正文条目**——先判定正文是否为集合容器，再按三独立（判据见附录 A.3）逐类判定；轻量文档原子正文行不重复展开
   - **e. Bn 对齐**——逐文档 Q1/Q2/Q3 判定（判据见附录 A.4）
5. **确定文档序列**——按业务流转顺序排列
6. **组装 STR-F**——写入 `02-*.md`，完整要素见 [§2.1.2](../eos-wft01-biz-or2str.md#212-str-f-节点要素与职责边界)（详见 human spec）

**写入 STR-F 节点时**，为每个条目初始化空的 `确认状态` 字段。

### Step 4 · 业务需求增补

按每个 STR-F 独立执行。新建 → 全量检查；修订 → 仅当链拓扑变化时重验闭合。

**1. E2E 闭合检查**——D 闭合（需求提出→需求满足）/ PCA 闭合（P→C→A）。缺口不脑补 → 生成补充 OR 材料。

**2. 要素机械检查**——逐文档确认非空或有合理空置原因：文档名称/用途/封面模式/引擎/开发方式/任务类型/任务关系/PL6-B/生命周期/支持信息/Bn 对齐。

**3. 补充 OR 材料生成**——写入 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/<YYYYMMDD>-<场景业务名称>补充原始需求材料.md`，登记到 OR 原料状态表。

**4. 治理业务覆盖检查**——从 Step 1 已加载的 STR树画像（`read-section.sh` 获取）中识别治理角色（业务架构管理员/数据治理员）的 STR-F 节点，判定当前批次是否触发治理需求。触发但缺 OR → Step End 提示人类渐进增补。

## 附录A：判据速查

### A.1 STR-F 类型判定

**概念锚点**：场景业务（STR-F）= 一个主责角色的一个业务对象闭环——业务对象与主责角色一一对应（主推动者：提出需求 / 负责完成 / 确认结果），配合角色是闭环内流程环节、不单独成 STR-F（[91 §1.4](../91-eos-biz-eng-spec.md#14-业务场景)）。D 与 PCA 两种类型：

| 类型 | 典型动作词 | 闭合规则 |
|------|-----------|---------|
| **执行类（D）** | 创建/提交/审批/交付/验收/退货/对账 | D 闭合——从需求提出到需求满足，文档间以输入-输出传递链为主 |
| **管理类（PCA）** | 策划/计划/监控/度量/分析/识别/纠正/改进 | PCA 闭合——P（计划/指标清单）→C（度量/看板）→A（风险/改进） |

D 和 PCA 处理逻辑完全同构，仅影响 wft02-biz 引擎推断偏好。

### A.2 封面模式判定

问：该文档是否有独立于正文 CRUD 的生命周期（需要审批流转/版本追溯/派发验收/独立状态变迁）？
- **是** → 正式文档（有封面，DocumentCover 表一行 + 正文 1:1）
- **否** → 轻量文档（无封面，正文即文档）

### A.3 PL6-B 三独立判定

| 条件 | 判据 | 正例 | 反例 |
|------|------|------|------|
| ① 独立名称 | 在文档内有固有称谓 | ✓ "订单及时率"、"采购预警" | ✗ 物料行（"序号1"不是名称） |
| ② 独立定义要素 | 有独立业务约束/规则/格式 | ✓ 指标有口径/维度/目标值 | ✗ 物料行的编码/数量由文档字段结构定义 |
| ③ 独立生命周期 | 独立于父文档的状态变迁 | ✓ 指标需审批后发布 | ✗ 物料行随申请单创建/删除 |

三项全满足 → 展开 PL6-B。轻量文档原子正文行不重复判定。

### A.4 Bn 对齐 Q1/Q2/Q3

| 判定 | 条件 | 动作 |
|------|------|------|
| **Q1** | E2E 项目业务 + 构件类型均在 23 资产中存在，职责范围未超出 | 直接引用已有路径 |
| **Q2** | E2E 存在但构件需扩展，或构件存在但归属需调整 | 引用+扩展建议 |
| **Q3** | E2E 或构件类型不存在 | 新建建议（名称/归属路径/定义） |

### A.5 Phase B 关系检测

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 文档匹配+引擎相同+来源非OR明示 | 来源升级 |
| 无新增 | 文档匹配+引擎相同+全部已OR明示 | 追加引用+增量合并 |
| 补充 | 文档不匹配 | 新增，来源=OR明示 |
| 过时 | 基线文档未被本轮覆盖 | `[过时]`+保留不删 |
| 引擎变更 | 文档匹配+引擎不同 | 更新引擎+变更原因 |

### A.6 节点生命周期状态流转

```
待确认方案 ──人类确认──→ 可以分解分配 ──wft02锁定──→ 在分解分配 ──wft02完成──→ 已分解分配
     ↑                       ↑                        │
     │                       │              wft02退回   │
     │                       │                        ↓
     └── wft01修订 ──── 需wft01修订 ←────────────────┘

上游变更分流：
  可以分解分配 → 可以分解分配（版本递增）
  在分解分配   → 在分解分配（版本递增）
  已分解分配   → 待补充分解分配
```
