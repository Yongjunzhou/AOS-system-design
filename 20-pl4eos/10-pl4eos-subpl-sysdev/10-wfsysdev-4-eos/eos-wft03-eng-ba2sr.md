# BA(A1) → SR-F · 引擎操作页面设计
**Skill ID**: wft03-eng-ba2sr

> **概述**：接收 A1 配置单元 BA，经前置校验、材料加载和反馈处理后，将 CU 配置能力定义展开为引擎操作页面 SR-F。该 SR-F 以“操作页面”为末级节点，定义配置人员或运行支撑人员在页面上完成哪些操作、页面之间如何组织成功能架构、页面操作活动如何触发引擎处理，并将需要 PA 阶段决定的组件、接口、存储和运行机制标注为 PA 层收敛项。
>
> **输入 → 输出**：A1 BA 节点（`可以SR设计` / `待补充SR设计`）/ 有反馈的 SR-F 节点 → 操作页面 SR-F（页面清单 + 页面类型 + 操作页面组件 + 页面功能架构 + 操作活动 + PA 层收敛项）+ BA 推进为 `已SR设计` + SR-F 推进为 `待产品架构`
>
> **适用场景**：瀑布式系统设计第3步 · 平台能力系统设计路径。
>
> **设计模式参考**：[91-eos-biz-eng-spec.md](91-eos-biz-eng-spec.md)
>
> **版本**：v4.7 | **修订**：2026-07-09

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：取信于平台开发人员——「这个 CU 应该有哪些操作页面，用户在页面上如何配置、发布、查看和触发引擎能力」。把 A1 BA 的 CU 配置能力定义转化为可进入 PA 的操作页面 SR-F——不仅为每个 CU 推断操作页面清单和页面类型，更组织页面的功能架构（TAB/主子/跳转/依赖）和操作活动定义，为下游前后端组件设计（wft05-eng）提供可展开的系统需求输入。

**目标**：

1. **为 CU 推断操作页面**——基于 CU 的配置入口、配置要素、系统处理和运行期能力，确定配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页和必要弹窗，判定页面类型和操作页面组件
2. **组织页面功能架构**——将页面按 TAB、主子关系、跳转、依赖、上下文传递、权限和状态组织成页面功能架构，建立页面与 CU 配置能力要素的追溯矩阵
3. **定义操作活动与 PA 收敛项**——定义每个页面上的操作活动（入口构件/前置条件/系统处理摘要/结果状态/校验规则/异常分支），将组件边界、接口契约、数据存储、运行机制等需要 PA 决策的事项标注为 PA 层收敛项
4. **保留 CU 完整追溯**——每个操作页面必须追溯到来源 BA、来源 CU、CU 配置能力定义和运行期能力，确保页面承接可验证
5. **执行覆盖自查**——检查每个 CU 的配置入口、配置要素、系统处理和运行期能力均被操作页面承接，构件线索和 PA 收敛项不缺失

本 Skill 负责：

1. **接收**——接收人类选中的一批 A1 BA 节点（≤5 个），校验 BA 状态为 `可以SR设计` / `待补充SR设计`、CU 配置能力定义完整（配置入口/配置要素/系统处理/运行期能力四类要素齐全）、依赖链闭合；缺失时退回 wft02-eng
2. **匹配**——按 `引擎 + CU + 页面职责 + 操作活动` 匹配已有 SR-F 操作页面：职责一致则复用并追加 BA/CU 来源，职责扩展则全量重写保留历史引用，无可匹配则新建，页面职责冲突则标记 `[需裁决]`
3. **页面推断**——从每个非占位 CU 的配置能力定义生成五类操作页面候选（配置维护/配置管理/发布生效/运行支撑/治理追溯），判定页面类型（91 规范六类）和操作页面组件清单
4. **功能架构生成**——为每个 CU 或强依赖 CU 组组织页面的 TAB、主子、跳转、上下文、状态依赖和权限依赖，建立页面→CU→配置能力要素的追溯矩阵
5. **操作活动设计**——定义页面操作活动（配置维护/校验处理/发布生效/运行支撑/治理追溯五类），写入活动名称、入口构件、前置条件、系统处理摘要、结果状态、校验规则和异常处理，标注 PA 层收敛项
6. **覆盖自查**——按八项检查（CU 覆盖/配置入口覆盖/配置要素覆盖/系统处理覆盖/运行期能力覆盖/构件线索覆盖/追溯覆盖/PA 收敛项覆盖）逐项验证；缺口时补充页面/活动或退回 wft02-eng
7. **推进**——人类确认后 SR-F → `待产品架构`，BA → `已SR设计`，记录消费版本
8. **回修**——接收 wft05-eng 退回的 `需wft03修订` SR-F，读取缺失说明，按人类改进方案修订 SR-F；根因在 BA 时退回 wft02-eng

本 Skill 不负责：

1. CU 配置能力定义、CU 拆分/合并和依赖链重切（→ `wft02-eng`）
2. 业务功能表单和业务场景页面设计（→ `wft03-biz`）
3. 前端/后端组件划分、接口详细规格、数据存储结构和实现机制（→ `wft05-eng`）
4. NFR 量化；本 Skill 只保留需要 wft05-eng 消费的 NFR 约束引用
5. 运行期业务页面本体编排；本 Skill 只说明 CU 运行期能力在操作页面组件/构件上的支撑关系

### 1.2 与上下游的衔接

**上游 wft02-eng**：产出 A1 BA，包含 CU 配置能力定义、依赖链、触发追溯和变更声明。本 Skill 不重新拆 CU，只把每个 CU 的配置与运行能力翻译成操作页面需求。

**下游 wft05-eng**：消费 `待产品架构` 的操作页面 SR-F，基于操作页面、操作活动、操作页面组件/构件、NFR 和 PA 收敛项推断前端/后端组件。若 wft05-eng 发现页面职责缺失、操作活动不闭合、构件支撑不明或 PA 收敛项缺失，将 SR-F 退回为 `需wft03修订`。

## 二、操作页面 SR-F 设计基础

### 2.1 操作页面 SR-F

#### 2.1.1 定义与分类

操作页面是配置人员或运行支撑人员直接使用的页面单元，用来维护 CU 配置、触发引擎处理、查看发布/运行结果或处理异常。它不同于业务人员使用的业务功能表单；业务运行页面本体由 biz 路径设计，eng 路径只设计引擎能力所需的配置与支撑页面。操作页面组件与构件定义见 [91 规范 §三](91-eos-biz-eng-spec.md#三-操作页面组件与构件)，eng 路径分工见 [91 规范 §7.3](91-eos-biz-eng-spec.md#73-系统需求开发wft03-eng)。

操作页面按职责分为五类，由 AI 根据 CU 配置能力要素判定：

| 页面类别 | 用途 | 典型来源 |
|----------|------|----------|
| 配置维护页 | 维护 CU 配置要素 | 配置入口、配置要素 |
| 配置管理页 | 管理配置版本、状态、引用关系 | 系统处理、治理依赖 |
| 发布生效页 | 校验、发布、装载、回滚、停用 | 系统处理 |
| 运行支撑页 | 查看运行期能力、刷新、重试、处理异常 | 运行期能力 |
| 治理追溯页 | 审计、影响范围、引用关系、操作日志 | 横切治理依赖 |

#### 2.1.2 架构与属性

操作页面涉及两个正交维度，不能互相替代：

| 维度 | 来源 | 回答的问题 | 进入 SR-F 的字段 |
|------|------|------------|------------------|
| 页面类型 | 91 规范 §1.2 | 这个操作页面整体采用什么页面组织形态 | `页面类型` |
| 操作页面组件 | 91 规范 §3.1 | 页面内部由哪些平台页面组件承载内容和交互 | `操作页面组件清单` |

页面类型、操作页面组件的具体分类与判定见 §2.2。页面功能架构见 §2.3.1，操作活动定义见 §2.3.2。

SR-F 节点完整要素（写入 `05-*.md` SR-F 节点块）：

- 页面 ID / 名称 / 页面类别 / 页面类型 / 使用角色
- 来源 BA / 来源 CU / CU 配置能力引用
- 页面职责
- 操作页面组件与构件线索
- 页面字段或配置对象摘要
- 页面操作活动清单
- 权限、状态、版本、发布约束
- PA 层收敛项
- 确认状态

#### 2.1.3 完备性判据（覆盖自查）

| 检查项 | 判据 | 缺口处理 |
|--------|------|----------|
| CU 覆盖 | 每个非占位 CU 均有操作页面承接 | 补充页面或退回 wft02-eng |
| 配置入口覆盖 | 每类配置入口都有页面承接 | 补充页面或退回 wft02-eng |
| 配置要素覆盖 | 关键配置要素有录入、维护或选择方式 | 补充页面字段或标注 PA 收敛 |
| 系统处理覆盖 | 校验、保存、发布、装载、回滚、异常等处理有操作活动或明确不适用理由 | 补充操作活动或标注 PA 收敛 |
| 运行期能力覆盖 | 运行期制品、构件或功能有查看、预览、触发、支撑说明或 biz 页面承接说明 | 补充运行支撑页面或说明由 biz 页面承接 |
| 构件线索覆盖 | 页面操作入口能映射到按钮、右键、快捷键、图表、钻取等构件线索 | 补充构件线索 |
| 追溯覆盖 | 页面 → CU → BA → STR-E 追溯完整 | 补充追溯引用 |
| PA 收敛 | 组件、接口、存储、运行机制、NFR 待定项均标注 | 补充收敛项，不推进到可消费 |

### 2.2 页面类型与操作页面组件

#### 2.2.1 定义与正交关系

页面类型与操作页面组件是两个正交维度，不能互相替代。页面类型决定页面的整体组织形态，操作页面组件决定页面内部用哪些平台组件承载内容和交互。

**页面类型**沿用 91 规范 §1.2 的六种：

| 页面类型 | eng 侧典型用途 | 候选操作页面组件 |
|----------|----------------|------------------|
| 单窗列表+辅助栏 | 配置项列表、发布记录、版本记录 | 列表页面 + 辅助栏 |
| 单窗树表+辅助栏 | 菜单树、流程节点树、权限树 | 列表页面（树表） + 辅助栏 |
| 单窗单据页 | 单个配置对象编辑 | 单据页 |
| 左窗主表+右窗子表+辅助栏 | 主配置 + 子规则/子节点 | 多级横版 + 列表/单据 + 辅助栏 |
| 全屏单据页 | 复杂设计器或大篇幅配置 | 单据页 / 多级横版 |
| 弹窗 | 选择、确认、局部参数编辑 | 弹窗页 |

上表中的”候选操作页面组件”只是提示，不能作为固定映射。每个 SR-F 必须单独给出操作页面组件清单。

**操作页面组件**可选范围：

| 操作页面组件 | 典型用途 |
|--------------|----------|
| 多级横版 | 多层级配置对象、主从配置、流程/规则设计器 |
| 列表页面 | 配置对象集合、发布记录、版本记录、执行记录 |
| 单据页 | 单个配置对象编辑、参数维护、规则详情 |
| 辅助栏 | 详情预览、上下文摘要、引用关系、校验结果 |
| 弹窗页 | 选择、确认、局部参数编辑、冲突处理 |
| 指标页面 | 运行状态、质量指标、发布影响、异常趋势 |

### 2.3 页面功能架构与操作活动

#### 2.3.1 页面功能架构

页面功能架构回答：一个 CU 或一组强依赖 CU 的操作页面如何组合使用。

要素：

- 页面清单与页面类型
- 操作页面组件与构件清单
- TAB 顺序或导航关系
- 主子页面关系
- 页面间跳转和上下文传递
- 权限、状态、版本和发布依赖
- 与来源 CU、配置能力要素的对应关系

#### 2.3.2 操作活动定义

操作活动是用户在操作页面上执行的可验证动作。

每个操作活动至少包含：

| 字段 | 说明 |
|------|------|
| 活动名称 | 如新建配置、校验配置、发布配置 |
| 操作入口 | 按钮、右键、快捷键、双击、自动触发 |
| 所属页面 / 构件 | 页面 ID 和入口构件 |
| 前置条件 | 状态、权限、版本、依赖 |
| 用户动作 | 用户做什么 |
| 系统处理摘要 | 系统校验、保存、发布、装载、记录等 |
| 结果状态 | 页面状态、配置状态或运行期状态 |
| 校验规则 | 必填、唯一、依赖、权限、冲突等 |
| 异常处理 | 失败提示、回滚、重试、人工处理 |
| PA 层收敛项 | 组件/接口/存储/运行机制待 PA 决策项 |

操作活动按类型分为五类：

| 活动类型 | 典型动作 |
|----------|----------|
| 配置维护 | 新建、编辑、复制、删除、导入、导出 |
| 校验处理 | 校验、预览、冲突检查、依赖检查 |
| 发布生效 | 保存、提交、发布、装载、回滚、停用 |
| 运行支撑 | 查看生效结果、刷新缓存、重试、异常处理 |
| 治理追溯 | 查看版本、审计、引用关系、影响范围 |

#### 2.3.3 PA 层收敛项

本 Skill 不设计组件，但必须把 wft05-eng 需要决策的事项显式传递。

| 收敛项 | 示例 | 标注 |
|--------|------|------|
| 组件边界 | 发布按钮构件是否复用公共构件 | `PA层收敛-组件边界` |
| 接口契约 | 发布动作调用同步接口还是异步任务 | `PA层收敛-接口` |
| 数据存储 | 配置版本、发布记录、审计记录的存储归属 | `PA层收敛-存储` |
| 运行机制 | 装载、缓存刷新、回滚、重试、补偿 | `PA层收敛-运行机制` |
| NFR 承接 | 性能、安全、审计、可观测性如何落组件 | `PA层收敛-NFR` |

### 2.4 SR-F 要素提取规则

Phase B（修订已有 SR-F）与 Phase C（新建 SR-F）共用以下规则。

#### 2.4.1 页面候选生成

对每个非占位 CU，按配置能力要素生成页面候选：

| CU 配置能力要素 | 页面/活动映射 |
|----------------|---------------|
| 配置入口 | 配置维护页、配置列表、配置详情、选择弹窗 |
| 配置要素 | 字段/规则编辑区、关系维护区、辅助栏详情、选择器 |
| 系统处理 | 校验、保存、发布、装载、回滚、停用、异常处理活动，以及执行记录页 |
| 运行期能力 | 能力预览页、运行支撑页、结果查看页、异常处理页；业务运行页面本体仍由 biz 路径承接 |

生成的页面候选覆盖五类操作页面：配置维护页、配置管理页、发布生效页、运行支撑页、治理追溯页。

#### 2.4.2 页面类型判定

按页面内容选择 91 规范六类页面类型：

| 判定条件 | 页面类型 |
|----------|----------|
| 多条配置对象维护 | 单窗列表+辅助栏 |
| 层级对象维护 | 单窗树表+辅助栏 |
| 单个配置对象编辑 | 单窗单据页 |
| 主配置与子规则强相关 | 左窗主表+右窗子表+辅助栏 |
| 复杂设计器、大篇幅配置 | 全屏单据页 |
| 临时选择、确认、局部编辑 | 弹窗 |

#### 2.4.3 操作页面组件判定

在页面类型判定之后，独立判断页面内部需要哪些操作页面组件：

| 判定条件 | 操作页面组件 |
|----------|--------------|
| 需要展示对象集合、版本记录或执行记录 | 列表页面 |
| 需要编辑单个配置对象或参数组 | 单据页 |
| 需要并列展示多层主从对象 | 多级横版 |
| 需要上下文、详情、校验结果或引用关系 | 辅助栏 |
| 需要临时选择、确认、局部参数或冲突处理 | 弹窗页 |
| 需要展示运行指标、发布影响或异常趋势 | 指标页面 |

#### 2.4.4 Phase B 宿主匹配检查

Phase B 修订已有 SR-F 时，按 `引擎 + CU + 页面类别 + 页面职责` 匹配已有操作页面：

| 结果 | 判定 | 动作 |
|------|------|------|
| 复用 | 页面类别/类型一致、页面职责匹配 | 追加 BA/CU 来源，标记 `[确认]` |
| 扩展 | 页面类别/类型一致、但操作活动或 PA 收敛项扩展 | 全量重写该页面 SR-F，保留历史引用，输出变更声明 |
| 新建 | 无可匹配的操作页面 | 新建操作页面 SR-F |
| 冲突 | 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

#### 2.4.5 Phase B（修订）与 Phase C（新建）的提取差异

| 维度 | Phase B 修订已有 SR-F | Phase C 新建 SR-F |
|------|---------------------|-------------------|
| 判定范围 | SR-F 已承接的全部 BA/CU + 本轮新 BA/CU | 待聚合池本组 BA/CU |
| 页面清单基线 | 以已有操作页面清单为基线，仅扫描本轮新 CU 是否引入新页面 | 从零构建 |
| 页面候选 | 增量生成（仅新 CU 触发） | 全量生成（§2.4.1） |
| 宿主匹配 | 执行宿主匹配检查（§2.4.4），可能检出复用/扩展/新建/冲突 | 无需匹配，直接新建 |
| 操作活动 | 在基线基础上增量合并（关系检测见 §2.5.3） | 全量设计 |
| 变更传播 | 需输出变更影响声明（§2.7） | 写”首版，无变更” |

### 2.5 操作活动推断规则

Phase B（修订已有 SR-F）与 Phase C（新建 SR-F）共用以下规则。

#### 2.5.1 操作活动类型与字段

对每个操作页面的操作活动，按 §2.3.2 的五类活动类型（配置维护/校验处理/发布生效/运行支撑/治理追溯）和十个字段逐项填写。活动类型由页面类别和 CU 配置能力要素共同决定：

| 页面类别 | 主导活动类型 | 辅助活动类型 |
|----------|-------------|-------------|
| 配置维护页 | 配置维护 | 校验处理 |
| 配置管理页 | 配置维护 | 治理追溯 |
| 发布生效页 | 发布生效 | 校验处理、运行支撑 |
| 运行支撑页 | 运行支撑 | 治理追溯 |
| 治理追溯页 | 治理追溯 | — |

每个操作活动写入：活动名称、入口构件、所属页面、前置条件、用户动作、系统处理摘要、结果状态、校验规则、异常处理、PA 层收敛项（§2.3.3）。

#### 2.5.2 PA 层收敛项标注

为每个活动检查是否存在组件边界、接口契约、数据存储、运行机制、NFR 承接待定项。存在则写入 `PA层收敛-*` 标记，供 wft05-eng 消费。五类收敛项定义见 §2.3.3。

#### 2.5.3 Phase B 操作页面关系检测

Phase B 修订已有 SR-F 时，宿主匹配通过后，将本轮生成的操作页面与 SR-F 已有操作页面清单比对。比对锚点为**页面类别+页面类型+页面职责匹配**。

| 关系 | 判定 | 处理 |
|------|------|------|
| 确认 | 页面匹配 + 页面类别/类型一致 + 来源升级（BA 引用→新 CU 确认） | 追加 BA/CU 来源，内部细分结论=`确认` |
| 无新增 | 页面匹配 + 页面类别/类型一致 + 所有来源已确认 | 增量合并新 CU 中的配置要素/操作活动/PA 收敛项细节（如有新内容），内部细分结论=`改进` |
| 页面职责扩展 | 页面匹配 + 页面类别/类型一致 + 操作活动或 PA 收敛项边界扩展 | 全量重写该页面 SR-F，保留历史引用 + 内部细分结论=`页面职责扩展` + 变更原因 |
| 页面类型变更 | 页面匹配 + **页面类型不同**（CU 配置能力变化导致） | 更新页面类型 + 重判操作页面组件 + 内部细分结论=`页面类型变更` + 变更原因 |
| 补充 | 页面不匹配 | 新增操作页面 SR-F，内部细分结论=`新增` |
| 过时 | 基线已有页面 **未被**本轮 CU 覆盖（CU 被移除或合并导致页面不再被需要） | 内部细分结论=`过时` + 追加说明”对应 CU 已不再覆盖此页面，请确认是否移除”。保留该页面在清单中（不删除）——移除是架构决策，由人类在反馈中触发 |

关系检测前先基于**全部 CU 重新判定页面类型**——新 CU 可能改变页面特征导致页面类型变更（表中 `页面类型变更` 行）。

`[调整]` 是与关系类型正交的叠加标记：已有页面的页面职责/操作活动/PA 收敛项变化，在关系标记之外叠加 `[调整]`。

### 2.6 SR-F 节点生命周期

SR-F 节点沿 [91 规范 §8.6](91-eos-biz-eng-spec.md#86-节点生命周期模型) 的四态主线流转及上游变更三条分流规则运行。本 Skill 的状态名映射见 91 规范 §8.6 状态名映射表（wft03-eng 列）。并行推进规则（SR 线与 PA 线互不阻塞）见 91 规范 §8.6。

**主线流转**（wft03-eng ←→ wft05-eng）：

```
待确认方案 ──人类确认──→ 待产品架构 ──wft05锁定──→ 在PA设计 ──wft05完成──→ 已产品架构
     ↑                        ↑                         │
     │                        │               wft05退回  │
     │                        │                         ↓
     └─── wft03修订 ────── 需wft03修订 ←───────────────┘
```

**上游变更**（新 BA/CU 汇入触发 SR-F 修订）：

```
待产品架构 ──新BA/CU修订──→ 待产品架构（版本递增，wft05 未消费）
在PA设计   ──新BA/CU修订──→ 在PA设计（版本递增，wft05 增量处理）
已产品架构 ──新BA/CU修订──→ 待补充PA设计 ──wft05补全──→ 已产品架构
```

**本 Skill 的写回范围**：`待确认方案` / `待产品架构` / `待补充PA设计` / `需wft03修订`。`在PA设计` 和 `已产品架构` 由 wft05-eng 写入和推进。

下游退回 `需wft03修订` 时：读取 wft05-eng 的缺失说明 → 按人类改进方案修订 SR-F（走 Phase B 修订流程）→ 人类确认 → SR-F → `待产品架构`。根因在 BA 时退回 wft02-eng。

### 3.1 Step Start

运行时 AI 按以下顺序执行：

1. **输入校验**：
   - SR-F 状态为 `需wft03修订` 且人类未提供改进方案 → 输出 wft05-eng 的缺失说明，提示提供改进方案 → **退出**
   - BA 不是 A1 类型 → 输出类型分布，提示走 `wft03-biz` → **退出**
   - BA 状态不是 `可以SR设计` / `待补充SR设计` → 输出不合格节点及当前状态 → **退出**
   - CU 配置能力定义缺少配置入口 / 配置要素 / 系统处理 / 运行期能力中任一项 → BA → `需wft02修订`，输出缺失说明 → **退出**
   - CU 依赖不闭合且 AI 无法阶段性说明 → BA → `需wft02修订`，输出依赖断点 → **退出**
   - 选中 BA >5 个 → 输出超限提示 → 人类确认后继续或退出
   - 无 BA 选中 + 无待处理反馈的 SR-F 节点 + 无 `需wft03修订` 的 SR-F 节点 → 输出"无待处理对象"→ **退出**
2. **退回优先**：存在 `需wft03修订` 的 SR-F 节点（且人类已提供改进方案）→ 读取 wft05-eng 的缺失说明，按人类方案走 Phase B 修订，人类确认后推进为 `待产品架构`
3. **反馈处理**：存在 `待确认方案` + 有人类反馈未处理的 SR-F 节点 → 进入 Step 2 处理。若全部条目已 `[同意]`+`[已处理]`，不阻塞新 BA，Step End 时提示
4. **新 BA 路由**：有未处理的 BA 节点 → 进入 Step 1→Step 3，逐节点执行 Phase D 宿主匹配，归入已有 SR-F 或进入待聚合池新建

**顺序约束**：Step 2（反馈处理）必须先于 Step 3（新增设计），因为反馈可能改变 SR-F 的页面清单/页面类型/操作活动/PA 收敛项。Step 3 的 Phase D 宿主匹配必须基于 Step 2 修改后的最新 SR-F 内容，不得使用缓存旧状态。

2. `05-*.md` SR-F 架构树画像/状态队列/节点索引 — 定位候选操作页面 SR-F 节点
3. `23-eos-output-architecture.md`（按 A1 产品路径筛选）
4. `25-eos-engine-models.md`（按目标引擎/CU 筛选，只读）
5. `22-eos-nfr-taxonomy.md`（按操作页面相关 NFR 约束筛选，只读）

按需扩大：

- 扩大触发：索引缺失 / 候选冲突 / 资产全貌不足 / 关系断裂时

### 3.3 Step 2 · 方案反馈处理

人类审阅与 AI 处理的通用协议见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议)。以下为本 Skill 的特化规则。

**本 Skill 的条目**：操作页面 + 页面功能架构 + 操作活动 + PA 收敛项。各条目的 `确认状态` 字段位于 `05-*.md` SR-F 节点块各条目正文中。

#### 3.3.1 AI 处理流程

按 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 的统一流程处理人类反馈：扫描待处理条目 → 收集整体确认 → 逐条处理 `[同意]`/`[修改]`/`[驳回]` → 级联检查（需求优先、资产对齐随后）→ 判定节点状态 → 确定写回时机 → 落反馈处理记录。

> **原则**：反馈处理不是对人类标注的机械执行，而是以 BA/CU 配置能力定义为锚点的方案修订。AI 在 Step 2 中与 Step 3~5 同为设计者——先理解人类反馈在 CU 配置能力语境中的含义，再执行修订，最后检查修订后的 SR-F 是否仍满足 CU 配置能力需求。

本 Skill 特化参数见 [91 规范 §8.5](91-eos-biz-eng-spec.md#85-skill-反馈交互协议) 实例化参数表（wft03-eng 列）。

### 3.4 Step 3 · 操作页面设计

#### 3.4.1 Phase A：页面候选生成与宿主匹配

对每个非占位 CU，按配置能力要素生成五类页面候选（配置维护/配置管理/发布生效/运行支撑/治理追溯，详见 §2.4.1），然后逐页面做宿主匹配：

| 条件 | 路由 |
|------|------|
| 页面类别 + 页面类型 + 页面职责落入已有 SR-F 操作页面 | 归入该 SR-F → Phase B |
| 不满足 | 进入待聚合池 → Phase C |
| 页面职责冲突或同一 CU 被多个页面争用 | 标记 `[需裁决]` |

待聚合池按**同一引擎 + 同一 CU + 同一页面类别**分组（`{引擎, CU, 页面类别, 页面候选列表}`）。此阶段仅粗略分组，页面类型判定和完整要素提取在 Phase C 执行。

#### 3.4.2 Phase B：修订已有 SR-F

1. **要素提取**：从本轮 CU 的配置能力定义提取页面职责、操作页面组件线索和操作活动候选（详见 §2.4.1、§2.5.1）。已有页面职责仅追加不重建
2. **宿主匹配检查**：确认 CU 配置能力仍在 SR-F 页面职责范围内（详见 §2.4.4）。复用→追加 BA/CU 来源；扩展→全量重写保留历史引用；冲突→标记 `[需裁决]`。Phase A 匹配是候选筛选、Phase B 是精确匹配——页面职责扩展时不得回退 Phase A 重选宿主，继续完成 Phase B 全部处理并标记 `[推断]` 供人类裁决
3. **页面类型/组件/操作活动重判定与关系检测**：基于全部 CU 重新判定页面类型（详见 §2.4.2）和操作页面组件（详见 §2.4.3），比对已有基线判定六种关系（详见 §2.5.3）。新增/变更操作活动→定义十字段（详见 §2.5.1）；PA 层收敛项→写入标记（详见 §2.3.3）
4. **变更影响声明**：判定变更类型（无变更/增量型/修订型/结构型），写入 SR-F 节点末尾（详见 §2.7）

#### 3.4.3 Phase C：新建 SR-F

1. **判定页面类型** → 按页面内容选择 91 规范六类页面类型（详见 §2.4.2）
2. **判定操作页面组件** → 独立判断页面内部需要的平台组件（详见 §2.4.3）。页面类型与操作页面组件是正交维度，不能互相替代
3. **定义页面职责** → 页面类别 + 页面用途 + 配置对象 + 使用角色（详见 §2.1.1）
4. **设计操作活动** → 逐活动定义十字段：活动名称/入口构件/所属页面/前置条件/用户动作/系统处理摘要/结果状态/校验规则/异常处理（详见 §2.5.1）
5. **标注 PA 层收敛项** → 组件边界/接口契约/数据存储/运行机制/NFR 承接待定项均标注 `PA层收敛-*` 标记（详见 §2.3.3）
6. **组装页面 SR-F** → 页面 ID/名称/类别/类型 + 使用角色 + 来源 BA/CU + 页面职责 + 操作页面组件与构件线索 + 操作活动清单 + PA 层收敛项，写入 `05-*.md`（完整要素见 §2.1.2）

### 3.5 Step 4 · 功能架构与操作活动

Step 4 按每个 CU 或强依赖 CU 组实例独立执行。新建页面组 → 全量设计；修订已有页面组 → 仅当 CU 配置能力变更或页面拓扑变化（新增 TAB/主子关系/跳转路径/上下文依赖）时重验架构，要素机械检查始终针对变更页面执行。

**1. 页面功能架构设计**

基于 Step 3 确定的操作页面清单和页面类型，为每个 CU 或强依赖 CU 组组织页面的功能架构（详见 §2.3）：

- 页面 TAB / 导航顺序：基于 CU 配置入口的页面级定位，确定页面内 TAB 结构和导航层级
- 主子页面关系：配置维护主页面 → 配置要素子页面的嵌套结构
- 页面间跳转和上下文传递：页面间跳转路径及传递的 CU ID、配置版本、引擎实例等上下文
- 权限、状态、版本、发布依赖：页面受哪些治理引擎约束（权限校验 / 状态锁定 / 版本比对 / 发布门禁）
- 页面与 CU、配置能力要素、运行期能力的追溯矩阵：每个页面 TAB/区块 → CU → 配置能力定义 → 运行期制品/构件/功能的完整追溯链（详见 §2.3.3）

**2. 操作活动设计**

对每个操作页面，按五类活动逐项定义（详见 §2.5）：

| 活动类型 | 典型动作 | 适用页面类别 |
|----------|----------|-------------|
| 配置维护 | 新建、编辑、复制、删除、导入、导出 | 配置维护页 |
| 校验处理 | 校验、预览、冲突检查、依赖检查 | 配置维护页、配置管理页 |
| 发布生效 | 保存、提交、发布、装载、回滚、停用 | 发布生效页 |
| 运行支撑 | 查看生效结果、刷新缓存、重试、异常处理 | 运行支撑页 |
| 治理追溯 | 查看版本、审计、引用关系、影响范围 | 治理追溯页 |

每个操作活动写入：活动名称 / 入口构件 / 所属页面 / 前置条件 / 用户动作 / 系统处理摘要 / 结果状态 / 校验规则 / 异常处理 / PA 层收敛项（详见 §2.5.1）。所有操作活动标注 `[推断]`，经由人类确认后方可落账。

**3. PA 层收敛项标注**

逐活动检查是否存在需要 wft05-eng 裁决的事项（详见 §2.3.3），存在则写入 `PA层收敛-*` 标记，供 wft05-eng 消费：

- [ ] 组件边界待定 — 前后端组件划分尚不明确
- [ ] 接口契约待定 — API 端点、请求/响应格式、错误码待定义
- [ ] 数据存储待定 — 持久化策略、缓存策略、数据结构待确定
- [ ] 运行机制待定 — 异步处理、定时任务、事件驱动、消息队列待确定
- [ ] NFR 承接待定 — 性能/安全/可用性约束的承接方式待明确

**4. 要素机械检查**（逐页面，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 页面 TAB / 导航顺序 / 主子关系 / 跳转路径 **已定义**
- [ ] 权限、状态、版本、发布依赖 **已标注**（含合理空置原因）
- [ ] 页面→CU→配置能力→运行期能力追溯矩阵 **完整**
- [ ] 每个页面的操作活动 **已定义**，十字段要素齐全
- [ ] PA 层收敛项 **已标注**，必收敛项不遗漏
- [ ] 所有非占位 CU 的配置能力均被页面承接（交叉校验覆盖，缺口留待 §3.6 统一处理）

### 3.6 Step 5 · 覆盖自查与变更声明

Step 5 按每个 SR-F 节点独立执行。新建 SR-F → 全量自查；修订已有 SR-F → 仅当页面清单或操作活动变更时重验覆盖，要素机械检查始终针对变更节点执行。

**1. 覆盖自查**

对每个 SR-F 节点，按八项逐条检查（详见 §2.4），发现遗漏仅标注、不回退——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全：

- [ ] CU 覆盖：每个需设计 CU 的配置能力均被至少一个操作页面承接
- [ ] 配置入口覆盖：每个 CU 的配置入口已映射到操作页面的 TAB/区块
- [ ] 配置要素覆盖：每个 CU 的配置要素可在对应操作页面上完成维护
- [ ] 系统处理覆盖：每个 CU 的系统处理（校验/保存/发布/装载/控制）已由操作活动承接
- [ ] 运行期能力覆盖：每个 CU 的运行期制品/构件/功能已由运行支撑页面或说明承接
- [ ] 构件线索覆盖：按钮/右键/快捷键/图表/钻取等构件线索已标注
- [ ] 追溯覆盖：页面→CU→配置能力→运行期能力追溯链完整
- [ ] PA 收敛项覆盖：组件边界/接口契约/数据存储/运行机制/NFR 承接的待定项均已标注

**2. 缺口处理**

发现缺口时按类型分流：

- 配置入口或配置要素未覆盖 → 补充操作页面或退回 wft02-eng（根因在 CU 配置能力定义不完整）
- 系统处理未覆盖 → 补充操作活动或标注 PA 收敛（系统处理可在 wft05-eng 阶段确定具体机制）
- 运行期能力未覆盖 → 补充运行支撑页面或说明由 biz 页面承接（标注承接方和追溯路径）
- 构件线索缺失 → 补充按钮/右键/快捷键/图表/钻取等构件线索描述
- PA 必收敛项缺失 → 补充收敛项，不推进到可消费
- 不因缺口脑补节点——缺口就是缺口

**3. 要素机械检查**（逐 SR-F，发现即标注——在对应条目中写入 `[覆盖缺口]` 及缺失说明，留待下一轮补全）

- [ ] 八项覆盖自查 **已执行**，遗漏项已标注 `[覆盖缺口]`
- [ ] 缺口处理 **已分流**，每项缺口有明确处理方式（补充 / 退回 / PA 收敛 / 标注承接方）
- [ ] SR-F 版本号 **已递增**（修订时），首版为 v1

**4. 变更影响声明**

每次新建或修订 SR-F 后写入变更影响声明；首版写”首版，无变更”。修订时按 §2.7 判定变更类型（无变更/增量型/修订型/结构型），列出受影响页面、操作活动和下游 wft05-eng 建议动作。格式见 §2.7。

### 3.7 Step 6 · 资产写回与落账

仅写回人类已在 Step 2 确认的 SR-F 条目。不设二次确认。

1. `05` 写入或更新 SR-F 架构节点、状态队列、追溯引用
2. `25` 写入操作页面能力引用或待办，不固化组件设计
3. `04` BA 节点写入 `BA 消费版本：v{N}`，状态推进为 `已SR设计`
4. SR-F → `待产品架构`
5. 写入资产写回记录（日期/来源 BA/目标 SR-F/动作/消费版本/下游状态）

写回要求：幂等去重、局部写回、全貌同步。

说明：资产写回是独立收尾，不构成 wft05-eng 前置条件。

### 3.8 Step End · 运行结束输出

遵循 [91 规范 §8.8](91-eos-biz-eng-spec.md#88-skill-通用约定) 的三区模板。

```text
当前状态：<待确认方案 / 待产品架构>
  SR-F：新增/修订操作页面 <N> 个；操作活动 <N> 条；PA 层收敛项 <N> 条；待裁决 <N> 项。

一、方案反馈
  A. 整体确认 -> 回复「整体确认」，快捷同意全部未标注条目
  B. 局部修改 -> 在确认状态中标注 [修改]：...
  C. 驳回重做 -> 在确认状态中标注 [驳回]：...

二、下一步
  本Skill -> 存在未处理反馈 / 需wft03修订 / 新 BA 时重入
  后续    -> SR-F 状态为 待产品架构 后进入 wft05-eng
```
