## 一、目的与目标

### 1.1 主要目的

> 把 X 已给的这批业务文档按它们自带的 P 侧属性——所属业务域、所属产品类型、所属产品构件——归拢成产品开发视角业务流程概要：文档、任务、用例场景按对位取用；并以覆盖检查检出缺口，把产品数据侧接不住的部分补成原始需求交回预处理链。

### 1.2 在设计链上的位置

设计开发 = 由需求到方案的逐对生成。业务路径首对的阶段一，由两个并列任务分担同一份业务数据的两个视角——**本任务是这个任务位的第二半**，把业务流程从职责视角转到产品开发视角：

```
职责视角业务流程概要 → 产品开发视角业务流程概要：  X = R 树，最深一级＝用例场景
        │  本任务交出 Y 的概要——P 树根→叶，不做详细定义
        ▼
       Y = 产品开发视角业务流程概要（03），装 P 树
```

- **本任务是首步的第二半**：第一半长 R 树的干枝，本任务在同一批业务文档上长 P 树的干枝，末三级同批。**叶由上游直接给出，本任务与第一半一样两级合做**——框架设计定下 WBS 包及其以上的干枝，概要设计把末三级按对位收成同名视图。详细定义的落点是界面，而界面只属于 R 侧，故产品开发视角没有定义形态。
- **形态的位置**：本任务交出**概要**——根→叶。产品开发视角**没有定义形态**，本任务不产出它。框架是概要内部的一层截面，不自成一段交付；框架与概要都不占需求-方案对的一端。
- **人类门禁位置**：两处——本任务产出后人类「整体确认」，节点状态由 `待确认方案` 推进；覆盖检查检出缺口后，候选去留由人类裁决。

### 1.3 主要目标

1. **组装 P 树 · 长干枝**：产品类型、产品构件类型、构件开发WBS（包），逐文档判定它在这一级的位置，走三档——引用／扩展／新建。
2. **组装 P 树 · 写秩序**：WBS 归组，判据是数据依赖链；再做 P 树一致性三类检查，产出 **P 树一致性结论**。
3. **认亲归位**：R 树的每张业务文档逐一标定 P 坐标，即所属 产品类型 × 产品构件类型 × 构件开发WBS（包）；**本体唯一**——一张文档可被多个场景引用，只占一个产品数据位。
4. **归位与 Y 侧视图**：X 已给的业务文档、任务节点、用例场景按对位进入本文件，带同名视图。
5. **属性齐备保证**：每张业务文档的 P 侧三个属性齐备且唯一，且所属产品构件挂在其产品类型之下——归拢对不对全由它们决定。
6. **覆盖检查与缺口补足**：数据依赖闭合核对；检出缺口以 **WBS 包对照闭合模型**补足产品数据类原始需求。
7. **落账与推进**：要素齐备、覆盖结论落账于节点；人类确认后推进状态，并受理上游退回与变更。

## 三、输出文档结构及规则（Y = 产品开发视角业务流程概要 · 方案侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 产品开发视角业务流程概要**——**一份文档，根→叶**：各级节点只到**说明**，末级用例场景即叶，到结构判定级。产品开发视角**没有定义形态**；末三级的**实体仍在职责视角业务流程概要那份文档里**，本文件带同名视图。

### 3.2 输出空间的 P 树（Y 树）

本任务的 Y 是业务流程的 **P 树**——**P 输出产品树**回答「这批文档作为产品数据，属于哪个产品／构件／WBS 包、怎么生成与流转」，讲的是产品数据与依赖。

**P 输出产品树（产品开发视角）**

```
输出产品业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 产品类型 ─────── ② 部门级的端到端业务输出
        └── 产品构件类型 ─ ③ 科室级的端到端业务输出
            └── 构件开发WBS（包）─ ④ 一批数据依赖闭合的产品数据单元
                └── 业务文档 ─ ⑤ 业务运行结束后应输出的产品数据文档
                    └── 任务节点 ─ ⑥ 枝梢节点
                        └── 用例场景 ─ ⑦ 叶
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务域 | 归属域 | **承 X**，取自 X 的「所属业务域」；R／P 两棵树各有一份，同值、不共享节点 | 认亲检索与完备对账的域边界 |
| ② | 产品类型 | 产品类别，如采购产品、实物产品 | **本任务产出**，取自 X 的「所属产品类型」（复用 → 改进 → 新增） | 本任务按需建立或确认 |
| ③ | 产品构件类型 | 构件分类，如自研、外购、复用、项目 | **本任务产出**，取自 X 的「所属产品构件」——后者挂在其所属产品类型之下，同上 | 同上 |
| ④ | 构件开发WBS（包） | 一批数据依赖闭合的产品数据单元 | **本任务产出**，同上 | 本任务新建／修订单位 + 人类确认挂点：归拢文档、包边界、收敛自查 |
| ⑤ | 业务文档 | 业务运行结束后应输出的产品数据文档 | **承 X**，同名同级 | 认亲归位：逐一标定 P 坐标；本体唯一——可被多场景引用、只占一个产品数据位 |
| ⑥ | 任务节点 | 开发文档所对应任务的子节点，原则上，一个节点对应一个表单标签页 | **承 X**，同名同级 | 带同名视图取用 |
| ⑦ | 用例场景 | 任务节点上包括的用例场景操作，原则上对应着标签页上的一个功能按钮、右键操作项，或一个快捷键所提供的功能 | **承 X**，同名同级 | 带同名视图取用 |

> **平台侧的 P 树**：平台自身走 **P0 树**——业务域（IT与信息化）→ 产品类型（EOS平台）→ 构件（引擎）→ 配置单元（CU）→ 配置信息组；单分支，没有 WBS 包一级。平台侧的业务由引擎能力设计任务承担，本任务只对其作渐进增补。
>
> **认亲 = 两树对位**：R 场景链里的每张业务文档，逐一识别其 P 归属，即产品类型 × 产品构件类型 × WBS 包，归位 P 树；两树靠这层互指联通，末三级同名同批。
>
> **树权威**：P 树的拓扑与各级语义以《EOS 系统设计产品数据分解结构》（94 号文档）为准；X 与 Y 两份产品数据的树画像以各自数据文件的树画像区为准。

### 3.3 节点类型与结构要点

> 方法读法：**业务域到任务节点的各级都是干枝**，即非叶节点；其中**任务节点 = 枝梢**，即框架的最深一级；**用例场景 = 叶**，即概要的末级。末三级由 X 直接给出，本任务不另造它们，只按对位收成同名视图并标定 P 坐标。**X 与 Y 两侧的叶是同一批**，故**不涉及映射与分配**。

- **构件开发WBS（包）**：一批数据依赖闭合的产品数据单元，由一组按数据依赖链排定的业务文档构成。包内前一文档的正文数据成为后一文档的输入。
- **产品类型与产品构件类型**：产品类型是部门级的端到端业务输出，产品构件类型是科室级的端到端业务输出；后者的性质决定构件所需的产品数据集合。
- **三档判定**：逐文档判定它在 P 树里的位置——**已有、直接引用**；**需扩展**；**无、给新建建议**。优先级始终 复用 → 改进 → 新增。
- 末三级在**正式**与**轻量**上的分法承上游：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。

### 3.4 Y 侧规则（组装与收敛）

- **方案边界**：只到结构判定——文档是否存在、产品类型／构件类型／WBS 包的位置与包边界、层级判定档位、包内数据依赖与逐文档的 P 坐标。**Y 侧不重写 X 给的角色、场景与文档内容**，只在其上长 P 侧干枝。下游各对的展开不在本任务。
- **WBS 包构建规则**，用于新建：按数据依赖链把文档收进同一个包——前序文档的输出即后续文档的输入；包边界取依赖闭合处。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有包，才上溯建更高层。

### 3.5 要素清单（本任务写入方案节点必须带齐）

写入产品开发视角业务流程概要的节点，字段对齐该数据文件 §4.1 的模板：

## 四、输出与输入转换规则

### 4.1 认亲与长枝规则

- **归拢由属性定**：每张业务文档落进哪一支，由它身上带的 P 侧属性决定——「所属业务域」定域、「所属产品类型」定产品类型、「所属产品构件」定产品构件类型；**WBS 包不由属性给**，由归组判据定。这三个属性齐备且唯一，是本任务唯一的归拢依据。
- **认亲 = 逐文档标定 P 坐标**：本体唯一——一张文档可被多个场景引用，但只占一个产品数据位；同一张文档在两个视角下的两次出现，指的是同一个产品数据。
- **文档整体分流**：它对应的 WBS 包已在 Y 中存在 → **复用**，走修订转换；尚无 → **新建**。优先级始终 复用 → 改进 → 新增。
- **X 侧语义不重判**：文档归属哪个场景、是什么类型，是上游的事；本任务发现 X 的缺陷 → 标 `需biz01修订`，不在 Y 侧就地改。
- **Y 侧装不下时**：WBS 包拆分，或横切式归位走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有干枝做扩展／拆分／合并后，须复查其下已归位的文档是否失配 → 批量重归位或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则与判据出处 |
|--------|--------------------|
| 产品类型路径 | 读业务文档的「所属产品类型」→ 定 P 树的产品类型，读「所属产品构件」→ 定产品构件类型；WBS 包路径由归组判据定；缺则 `[推断]` |
| 层级判定档位 | 三档判定——已有直接引用／需扩展／无则给新建建议；存疑标 `[推断]` |
| WBS 归组 | 数据依赖链：前序文档的输出即后续文档的输入；完成耦合 |
| 认亲 | 读业务文档的「所属产品构件」属性 → 定位 P 侧构件归属；层级不全时走三档判定 |
| 文档视图 | **以 X 的业务文档为准**——同一次序、同一个名称，不另立清单 |
| 用例场景与任务节点 | 从 X 取用同名视图，不另拟名 |
| 缺口推断 | 按 P 树已有的产品数据类型做名称级比对，不依赖任务类型或引擎 |

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回上游／宿主误匹配 → 产品数据链关系检测，分 确认／无新增／依赖变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查。

### 4.4 层级构建与缺口规则

**P 树三级，即产品类型／产品构件类型／构件开发WBS 的建立**：逐文档判定它在 P 树里的位置，分三档——**已有、直接引用**，**需扩展**，**无、给新建建议**；再执行 WBS 归组，判据是数据依赖链；加 P 树自身一致性检查，查 归属冲突／误新建／误引用；再加按 P 树已有的产品数据类型做名称级缺口推断，不依赖任务类型或引擎。

**缺口一条通道——产品数据类**：本批涉及的 WBS 包对照闭合模型检查，应有而缺失的产品数据 → 以**候选节点**挂 P 树、标疑似态；候选只是建议，不直成正式文档。

缺口生成**产品数据类补充原始需求材料**，回需求预处理链，由它加工成业务功能需求条目、归业务路径。人类裁决「需要」→ 转正式条目落地；「不要」→ 候选废弃。**本任务不脑补节点**。

层级构建、WBS 归组、一致性三类与缺口推断的判据引 91 号规范 §5.3.1。

> **另外两类缺口不在本任务**，按锚定归属：**引擎类**——"用例场景逐一对照平台引擎，接不住的操作"，锚在用例场景，归职责视角业务流程定义任务；**业务链类**——"闭合检查核对这条业务对象闭环是否走完，缺了应有的业务文档或任务节点"，锚在业务链，归职责视角业务流程任务。

#### 5.1.1 Step 1 · 设计材料加载

读 `可以srb设计` 节点 + 同一产品类型／同域存量节点；加载按读取协议。

#### 5.1.2 Step 2 · 反馈处理

人类对话修改／整体确认／线下修订；反馈双轨按 91 号规范 §A.5 记录。

#### 5.1.3 Step 3 · 组装 P 树

针对一批同产品类型的业务文档：

- 长 P 树干枝：产品类型、产品构件类型、构件开发WBS（包），走三档判定——已有直接引用／需扩展／无则给新建建议；
- **P 认亲**：逐文档按 P 侧属性标定 P 坐标并归位，本体唯一；
- **WBS 归组**，判据是数据依赖链；再做 P 树一致性三类检查——归属冲突／误新建／误引用；
- 取用末三级的同名视图：业务文档、任务节点、用例场景，与 X 同一次序、同一个名称，不重写实体内容；
- 产出 **P 树一致性结论**；
- **影响面复查**：对已有干枝做扩展／拆分／合并后，复查其下已归位的文档是否失配；有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.4 Step 4 · 补充产品数据类原始需求

执行关口检查，其中 **数据依赖闭合** 是本需求-方案对的关口——包内数据依赖从源头贯通到交付。再以 P 树做缺口推断：本批涉及的 WBS 包对照闭合模型，应有而缺失的产品数据以**候选节点**挂 P 树、标疑似态。

缺口生成**产品数据类补充原始需求材料**交需求预处理链，加工成业务功能需求条目归业务路径。候选去留由**人类裁决**：「需要」转正式条目落地，「不要」废弃。**不脑补节点。**

#### 5.1.5 Step 5 · 写回与落账

产品开发视角业务流程概要落账 + 状态推进 + 基线，引 91 号规范 §A.3.3 与 §A.6。

### 5.2 检验规则（关口）

- **属性齐备检查**：每张业务文档的 P 侧三个属性齐备且唯一，且所属产品构件挂在其产品类型之下——这是本任务唯一的归拢依据，缺一个就落不了位。
- **认亲本体唯一检查**：一张文档只占一个产品数据位；同一产品数据位被两张文档争用 → 输出冲突清单，待人类裁决。
- **覆盖检查**，这是本需求-方案对的关口：**节点累计承接的**全部需求语义 ⊆ 其产品数据链所能实现的范围。同一批业务文档的需求分多批到来，故检查范围累计——每批检新增部分；本批改动了已有干枝，另按影响面复查其下已归位部分。EOS 实例化 = **数据依赖闭合检查**——包内数据依赖从源头贯通到交付。缺口 → 以 WBS 包对照闭合模型生成产品数据类补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐文档要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待下游推断]`。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以srb设计 ──下游锁定──→ 在srb设计 ──下游完成──→ 已srb设计
     ↑                       ↑                      │
     │                       │          下游退回     │
     └── 本任务修订 ──── 需biz01修订 ←───────────────┘
```

上游变更，即新需求汇入，按状态分流：`可以srb设计`→版本递增，未消费；`在srb设计`→版本递增，增量处理；`已srb设计`→`待补充srb设计`→本任务补全。节点生命周期与写回范围引 91 号规范 §A.6，此处为本任务特化。
