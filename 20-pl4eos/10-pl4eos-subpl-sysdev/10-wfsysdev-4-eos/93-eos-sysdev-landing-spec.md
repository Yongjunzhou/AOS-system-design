# 设计与开发落地方案编制规范（93 规范）
**EOS Design-Development Landing Plan Authoring Spec**

> **本规范是什么**：统一 EOS 设计线上"设计与开发落地"各任务人类方案（wft 类操作规程）的**编制**——总骨架、逐章编制规则、跨文档一致规则，使全链人类方案读成同一个方法（20 号报告：由需求到方案的逐对生成，Y=F(X)）在不同链位的实例化。人类方案是权威源；其 SKILL 是可执行提取（派生关系见 §五.3）。
>
> **状态**：v0.1 骨架草案（2026-09-04）。第二章/第四章为已收敛内容；第三章逐章编制规则与第六章工作流、附录 B 实例待 wft01-biz 试写验证后回填校准。带【待回填】【待试写校准】标注处均未定案。

## 一、总则

### 1.1 目的与定位

设计与开发落地 = 把产品数据链切成相邻的"需求-方案结对"，由需求开发出方案、并由方案迭代需求，正反交替逐对收敛。每一对相邻产品数据即一次 Y=F(X) 求值：X 为需求，Y 为方案，F 为规则（X 侧/Y 侧树形与节点规则 + Y 承接 X 的承接规则）；同对经预处理（定义规则、结构化存量、初步承接）与正式设计（需求叶节点驱动：承接设计 → 分解 → 覆盖检查）两步过程推进（方法完整定义见 [20 号报告](../../../50-research/00-系统工程相关研究报告/20-设计与开发落地方法研究报告—需求与方案结对开发.md)）。

**一份人类方案**就是落地方法在**一个任务位**上的操作规程：声明本任务在对/链上的坐标，规定它消费的输入文档、产出的输出文档、两者转换的规则、转换流程与检验规则，及其与资产文档的接口。

**本规范规定此类人类方案怎么编**：章序、各章该写什么、不该写什么、跨文档如何保持一致。它不重述 EOS 领域设计模式与运行时协议（引 91 规范），不重述方法论证（引 20 号报告）。

### 1.2 适用范围

- 适用于 **EOS 设计线 wft 类人类方案**：biz/eng/nfr 三路径 01→07 链上的承接/分解任务（`spr2bph`、`bph2bpd`、`bpd2srh`、`srh2srd`、`srd2pa` 及 nfr 链对应任务）。本规范按**方法级**编制、不绑定 biz/eng/nfr 具体名词，各任务以自己的输入/输出产品数据填充。
- 同对"阶段一（承接设计·出概要）"与"阶段二（分解·出完整态/链尾移交）"的任务均适用——骨架一致，只内容随其在链上的位置而不同。
- **暂不适用 ort00~ort03 需求预处理链**（原始需求文本化/切分/澄清/规范化）。ort 属 20 号方法的"预处理过程"，但 EOS 已将其独立成链、现行 SKILL 模板不同，维持 [91 规范](91-eos-biz-eng-spec.md) 附录A 既有模板。如需同构再行扩展。

### 1.4 术语（简表）

| 术语 | 指代 |
|------|------|
| 人类方案 | EOS 设计线某任务位的操作规程文档（`eos-wftNN-xxx.md`），本规范约束对象 |
| 输入文档 / X | 本任务消费的上一棒产物（= 上游任务输出文档），作为转换的源语言 |
| 输出文档 / Y | 本任务产出的产品数据文档，作为转换的目标语言 |
| 概要态 / 完整态 | 同一份逻辑产品数据的两个形态：概要不含叶节点、完整态含叶节点；概要非"对"的端点 |
| 边界文档 | 相邻两任务的接缝文档——既是任务 A 的输出，又是任务 B 的输入 |
| schema | 某类产品数据文档的结构（节点类型/要素清单/字段/状态），全链单源（§四.1） |
| 生产侧 / 消费侧 | 边界文档在 A.ch3 的视图（生产 + 传出承诺）/ 在 B.ch2 的视图（消费 + 受理前提） |
| 接口契约 | A.ch3 的传出承诺与 B.ch2 的受理前提互为对侧；并排核对即契约校验 |
| 单承接 | 一条需求只能被一个枝梢/枝干承接（可 N:1，不可 1:N） |
| 覆盖检查 | "承接了的一定被实现"：某节点承接的全部需求语义 ⊆ 其叶节点语义之并 |

## 二、人类方案总骨架

### 2.1 骨架总览

每份 wft 类人类方案按六主章 + 收尾章组织：

| 章 | 章名 | 定位 | 对应 20 号方法 |
|----|------|------|----------------|
| 一 | 目的与目标 | 声明本任务在对/链上的坐标与职责边界 | 对与链定位 |
| 二 | 输入文档结构及规则 | X（上一棒产物）的**消费侧**视图 | X 侧规则之使用面 |
| 三 | 输出文档结构及规则 | Y 的**生产侧**视图 | Y 侧规则 + 分解源判据 |
| 四 | 输出与输入转换规则 | X→Y 的映射与判定 | 承接规则（F 第三块） |
| 五 | 转换流程及检验规则 | 设计动作序列 + 关口 | 正式设计过程 + 两道关口 |
| 六 | 资产文档结构及规则 | 旁支参照接口（读/写资产） | —（旁支） |
| 收尾 | AI 标记约定 / 自检清单 / 变更记录 | 执行收尾 | — |

> 章序逻辑：先文档后转换再流程——二、三章先立"源语言/目标语言文法"，四章给"翻译法则"，五章给"执行与验收"，六章给"翻译时查阅/回写的旁支词典"。

### 2.2 组织原理

- **一份人类方案 = 翻译规格书**：输入文档是源语言、输出文档是目标语言、转换规则是翻译法则、流程及检验是执行与验收——这正是 Y=F(X) 的文档化。
- **概念跟文档走、原理跟规则走**：描述 X 的概念进第二章，描述 Y 的概念进第三章；解释"规则为何如此"的原理与其规则同章同节（不进独立"概念/原理"章）。理由：在逐对生成里，所谓"概念"（如节点类型、概要/完整态判据）本身就是某侧文档的结构或规则，没有脱离文档而独立存在的概念层。
- **不设孤立的知识层三章、不以会话 Step 为纲**：第三章（操作流程）里"会话 Step"（Start/1/2/End/反馈/写回）是 EOS 运行外壳，属 91 附录A 运行时协议，人类方案只引不重述；设计动作序列才是人类方案要写的过程（§三.5）。
- **只引用、不搬运**：schema、资产内容、运行时协议、方法论证各有单源（§四.1、§1.3），人类方案写"本任务怎么用"，不复制权威正文。

## 三、逐章编制规则

> 【待 wft01-biz 试写验证后回填校准】以下给收敛的骨架规则，细节标注待校准处。每章统一给：应含 / 禁含 / 规则来源。

### 3.1 第一章 目的与目标

**应含**：
- **链上坐标**：本任务 = 哪个"对"的哪一阶段——阶段一（承接设计·出概要）/ 阶段二（分解·出完整态）/ 链尾移交；X、Y 各为哪份产品数据的哪个形态（概要态 / 完整态）。
- 主要目的（引用块）、目标（编号列表）、本任务负责 / 不负责（含路由指向）、与上下游的衔接（X 来源 / 阶段二执行者 / 退回机制）。
- 明确"概要 = 同一份逻辑产品数据的骨架形态、非对端点；完整态由阶段二产出"。

**禁含**：schema、规则、流程细节（属后章）。

### 3.2 第二章 输入文档结构及规则

**定位**：X（上一棒产物，即上游任务输出文档）的**消费侧**视图。wft01 的 X=01、wft02 的 X=02 概要、wft03 的 X=04……每份人类方案只描述**一份**主输入文档。

**应含**：
- 受理门槛：哪些 X 进入本任务（状态 / 范围 / 数量）。
- 读法：X 作为源语言，哪些结构是本任务的可承接对象、哪些字段本任务消费。
- X 侧规则：X 的切分（分解）规则来源与违规重切路径（退回）；本任务把 X 当 X 用的规则。
- 依赖与校验：读到 A 的承诺缺失/冲突时的处理（对侧校验 → 退回 / 反向迭代）。
- schema 引用（§四.1），不重述。

**禁含**：X schema 全量；本任务旧 Y（存量——归第三章 + 第五章修订流程）；资产内容（归第六章）。

> 【待试写校准】schema 引用粒度、可承接对象的清单写法（拟以 wft01-biz 对 01、wft02-biz 对 02 试写校准）。

### 3.3 第三章 输出文档结构及规则

**定位**：Y 的**生产侧**视图。

**应含**：
- 节点类型与结构要点（schema 引用 + 本任务产出的节点类型判据，如正式/轻量、PL6-B 三独立、D/PCA——这些"概念"即 Y 节点类型规则，在此定义/引用）。
- Y 侧规则：构建规则（父节点归组、收敛自查：覆盖完整 + 兄弟互斥）、概要态边界（本任务写到哪一层：枝梢 + 分解源判据）。
- 枝梢节点的**双向物理意义**：承接判据（承接哪类需求）+ 分解源判据（能分解出哪些叶节点——移交阶段二/下游的规则接口）。
- 要素清单：本任务产出节点必须带齐的要素。
- **传出承诺**：交到下游前节点须达到的状态与完备程度（供 B.ch2 消费）。

**禁含**：阶段二（叶节点/字段级详设）执行内容；schema 全量（引单源）。

> 【待试写校准】"要素清单 vs schema"的分工写法；传出承诺的成文化（拟以 wft01-biz 对 02、与 wft02-biz 对 02 的接口对照校准）。

### 3.4 第四章 输出与输入转换规则

**定位**：X→Y 的映射与判定（承接规则的本对实例化）。

**应含**：
- 承接/分配规则：X 叶/节点如何落到 Y 的各级枝干/枝梢；**单承接**（N:1 不可 1:N）；承载量超限 → 节点拆分；切不动 → 横切式承接/独立分支（本对适用时）。
- 类型与要素生成判定：从 X 内容推出 Y 节点类型/要素的判定规则。
- 修订转换规则：已有 Y 时，新 X 如何并入（复用 → 改进 → 新增 的分流与关系检测）。
- 对齐规则：Y → 资产侧的判定动作（Q 判定等）——判定动作在此定义，资产概念引资产文件。
- 影响面复查：改进（Extend/Split/Merge）Y 枝梢时对既有承接的复查规则。

**禁含**：流程步骤顺序（属第五章）；资产自身结构（属资产文件）。

### 3.5 第五章 转换流程及检验规则

**定位**：设计动作序列 + 关口。

**应含**：
- **设计过程**（以设计动作序列为纲，非会话 Step）：预处理〔载规则（F）/结构化存量/初步承接（只复用）〕→ 承接设计循环〔选相关联 X 组 → 复用→改进→新增 → 单承接检查 → 有改则自下而上调树至收敛〕→ 完备性/覆盖检查 → 状态推进。
- **关口（检验规则）**：
  - 单承接检查（程序违规回炉 vs 切不动的整体两个出口）；
  - **承接覆盖检查**（承接的 X 语义 ⊆ 其分解产出之并；EOS 实例 = 闭合检查，缺口不脑补 → 补充需求材料回路）；
  - 人类门禁（整体确认 → 推进）；退回（下游检出缺陷 → 反向迭代/修订）。
- 状态推进与退回机制在本任务的特化。

**禁含**：EOS 会话运行时细节（Step Start/End、反馈双轨、git 基线、写回脚本）——引 91 附录A。

### 3.6 第六章 资产文档结构及规则（接口）

**定位**：本任务与资产文档（21~28）的**接口**；资产自身结构与概念是其文件自己的内容，不搬入。

**应含**：本任务**读**哪些资产（引用分节）、**写**哪些资产（写回动作与规则，如 Q1/Q2/Q3 引用、WBS 归组结论写回、一致性矛盾暂不写回）。

**禁含**：资产文档自身的结构/概念/规则的复述（引资产文件）。

### 3.7 收尾章与运行时

- AI 标记约定 / 自检清单 / 变更记录：引 91 附录A 格式约定 + 本任务增量清单示例。
- 运行时协议（Step Start→End、反馈交互、生命周期、变更传播、读写与写回约定）：属 [91 规范](91-eos-biz-eng-spec.md) 附录A，人类方案只引不重述。

## 四、跨文档一致规则

### 4.1 schema 全链单源

任何文档类型的**结构**只有一个权威家；人类方案只引用、只写"本任务这一侧的规则"，不重复定义结构。若结构需演进，改单源 + 改受影响的侧规则，不改多份重复。

| 文档类型 | schema 之家 | 人类方案中的写法 |
|---------|------------|-----------------|
| 产品数据文档（01~07） | [91 规范](91-eos-biz-eng-spec.md) §11（文档结构）+ 各数据文件自身 + [00-doc-conventions](../../../00-generalspec/00-doc-conventions.md) | ch2/ch3 引用结构，只写本任务消费/生产侧的规则 |
| 节点类型判据（正式/轻量、PL6-B 三独立、D/PCA 等） | [91 规范](91-eos-biz-eng-spec.md)（§二/§7~§9 相应节）+ 20 号报告（方法级树判据） | ch3 引用并给本任务的判定特化 |
| 资产文档（21~28） | 资产文件自身 | ch6 只写读写接口 |
| 运行时协议 | [91 规范](91-eos-biz-eng-spec.md) 附录A | 只引用 |

### 4.2 边界文档的两侧面与接口契约

链上相邻任务共享**边界文档**：任务 A 输出它、任务 B 输入它。该文档被且只被描述两次，且两次天然不同：

- **A 的第三章（生产侧）**：怎么产出合规文档 + **传出承诺**（交到下游前达到的状态与完备程度，含枝梢分解源判据）。
- **B 的第二章（消费侧）**：怎么把它当 X 用 + **受理前提**（受理门槛、可承接对象、依赖与校验）。

**A.ch3 的传出承诺与 B.ch2 的受理前提互为对侧——并排核对即本对接口契约校验**；不吻合即对侧缺陷 → 退回 / 修订。这一对侧关系就是防止"A 以为交全了、B 发现接不上"的机制（20 号方法反向迭代在文档体系上的落点）。

```
┌─ A.ch3 生产侧 ─┐        ┌─ B.ch2 消费侧 ─┐
│ schema 引用     │        │ schema 引用      │
│ 构建/分解源判据  │ ──接口──▶ │ 受理门槛/可承接对象│
│ 要素清单        │  契约   │ 依赖与校验(退回)  │
│ 传出承诺 ====== │ =======│ ====== 受理前提  │
└───────────────┘  对侧核对  └────────────────┘
```

> 先例实例：`02 业务流程概要` 同时出现在 wft01-biz.ch3（生产）与 wft02-biz.ch2（消费）；wft01 的 X=01 属首条边界——01 的生产侧在 ort 预处理链（不在 wft 人类方案内），故 wft01.ch2 只有消费侧一栏。【待 wft01-biz 试写时落成文】

### 4.3 上一份完整态 = 下一份需求

本任务的需求树没有独立构建规则——它就是上一对/上一任务的方案树（20 号报告 §2.4「需求树的来历」）。因此 B.ch2 不重述 X 的结构与构建（那是 A.ch3 的职责），只写"B 把 X 当 X 用"的受理与使用规则 + schema 引用。

### 4.4 概念/原理归位与引用纪律

- 概念跟文档走、原理跟规则走（§二.2）；资产概念归资产文件自身（§三.6）。
- 引用纪律：不搬运权威正文（schema、资产、运行时、方法论证），一律链接引用；本规范内容与 91/20 号如有口径出入，以各自权威源为准并同步修订。

## 五、与既有文档体系的关系

### 5.1 与 20 号方法的映射

| 人类方案章节 | 20 号方法要素 |
|-------------|--------------|
| 一 目的与目标（链上坐标） | 对与链定位（相对角色、概要态/完整态） |

### 5.2 与 91 规范的分工

- 91 规范 = EOS 领域设计模式 + 产品数据文档结构（§11）+ Skill 运行时协议与格式（附录A 第三部分）+ ort 预处理链 Skill 模板（附录A 第二部，维持现状）。
- 93 = wft 类人类方案的**静态编制**规范。
- 91 附录A 第二部「编写 Skill 文档」中面向 wft 类的静态布局部分，将随本规范落地**迁出/改指 93**（【待改造执行时改指】）；面向 ort 类的模板保留在 91。

### 5.3 与 SKILL 的关系

人类方案是**权威源**；SKILL 是其**可执行提取**——SKILL 头部声明"设计依据 = 人类方案"，运行时细节引 91 附录A，脚本化数据访问/判据速查就地嵌入。本规范只约束人类方案静态编制；SKILL 的派生与同步规则由 [91 规范](91-eos-biz-eng-spec.md) 附录A + 各任务约定管辖（不扩展）。
