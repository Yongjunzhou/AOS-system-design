## §A.4 入口条件与优先级（Step Start）

### 三种合法入口（通过 `## AI可以处理节点` 分节检测）

| # | 入口 | 检测方式 | wft01-biz 示例 |
|---|------|---------|---------------|
| ① | 有新输入 | 「待 <Skill> 处理」分节非空 | OR 状态=`待处理` |
| ② | 有待处理反馈 | 「待反馈处理」分节含本 Skill 产出节点，含 `[修改]`/`[驳回]` 无 `[已处理]` | STR-F 条目有人类标注未处理 |
| ③ | 有下游退回 | 「待下游退回处理」分节含 `需wft01修订` 节点 | wft02 退回的 STR-F |

三种均不满足 → 输出"无待处理对象"→ **退出**。

### 退回门禁（入口③时）

| 情况 | 动作 |
|------|------|
| 人类已提供改进方案（缺失说明中含 `[修改]`/`[同意]` 标注或具体改进指引） | 通过门禁 |
| 仅含概括性退回原因（如"方案不完整，需修订"） | 输出缺失说明 + 提示 → **退出** |

### 优先执行顺序

```
退回优先 → 反馈处理 → 新输入路由
```

原因：退回和反馈都可能改变已有节点（边界/业务链/要素），新输入匹配必须基于最新内容。

### 校验类型

- **硬退出**：状态不符、类型不匹配 → 输出原因后退出
- **软提示**：数量超限（>10条）、跨角色 → 输出提示，人类选择继续或退出

## §A.5 反馈交互协议

反馈全部通过自然语言讨论进行，人类不直接编辑文档标注。

### 交互流程

```
Step 3 AI 产出方案 → Step End AI 输出摘要
                           ↓
              AI 不结束对话，等待人类反馈
                           ↓
              人类自然语言回复修改意见
                           ↓
              AI 理解反馈 → 修改方案 → Edit 写回
                           ↓
              AI 输出修改摘要 → 继续等待确认
```

### AI 处理规则

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位条目 → Edit 修改 → 检查是否仍满足 OR 需求 |
| 质疑/讨论（"为什么选 X？"） | 解释理由，不自动修改 |
| 整体确认（"可以"/"整体确认"） | 推进状态 → Step 5 资产写回 |
| 模糊意见（"粒度太粗"） | 追问具体化，引导可执行指令 |

### 级联检查

修改导致结构性变更（边界/引擎/PL6-B 增删）→ 重验受影响条目是否仍满足 OR 需求 → 必要时重入设计步骤。

### 修改落账

AI 完成修改后在方案条目后追加 `[已处理]`，作为 git 可追溯的处理记录。历史通过节点版本号 + 变更记录追溯。

## §A.6 节点生命周期模型

### 主线流转

```
待确认方案 ──人类确认──→ 可以分解分配 ──wft02锁定──→ 在分解分配 ──wft02完成──→ 已分解分配
     ↑                        ↑                         │
     │                        │               wft02退回  │
     │                        │                         ↓
     └─── wft01修订 ────── 需wft01修订 ←───────────────┘
```

### 上游变更分流（新 OR 汇入时）

| 原状态 | 修订后状态 | 说明 |
|--------|----------|------|
| 可以分解分配 | 可以分解分配（版本递增） | wft02 未消费 |
| 在分解分配 | 在分解分配（版本递增） | wft02 增量处理 |
| 已分解分配 | **待补充分解分配** | wft02 需补全 |

### 并行推进

资产写回（Step 5）与下游消费（wft02）互不阻塞——人类确认后两者并行。

### 版本标记

节点初始 v1，每次上游修订递增。下游首次消费记录 `消费版本：v{N}`，重入时比对版本。

## §A.7 变更传播协议

### 变更类型（优先级排序）

| 类型 | 判定 | 下游动作 |
|------|------|---------|
| **结构型** | 边界扩展/收缩、节点移除/合并/拆分 | 需人类裁决后方可处理 |
| **修订型** | 已有项定义/范围/归属被修改；边界未变 | 修订受影响节点 → 标记 `[来自上游变更]` |
| **增量型** | 仅新增子节点/条目；已有项未改动 | 增量展开新增内容，已有不动 |
| **无变更** | 全部走确认/引用追加；无实质变更 | 无需动作 |

### 变更影响声明模板（wft01-biz 实例化）

```text
### 变更影响声明

STR-F 版本：v{N}（本次修订前为 v{N-1}）
本轮变更类型：无变更 / 增量型 / 修订型 / 结构型

变更项：
- [新增] / [变更] / [确认] / [需裁决] ...
  说明字段中记录细分原因

下游已消费此 STR-F 的 BA 节点：
  <BA节点ID列表>（如无则写"尚未被下游消费"）

对已消费 BA 节点的影响：
  受影响节点：<BA节点ID + 受影响原因>
  不受影响节点：<BA节点ID>
  待新增 BA 节点：<新文档/指标对应的待展开 BA 说明>

建议 wft02-biz 动作：
  - 无变更：无需任何动作
  - 增量型：增量展开新增文档/指标即可
  - 修订型：修订受影响的 BA 节点 → 标记 [来自上游变更]
  - 结构型：输出影响范围，等人类裁决后再处理
```

## §A.3.2 Step End 输出模板（三区结构）

```text
当前状态：<待确认方案 / 可以分解分配>
  修订 STR-F-XXX（+N OR，v{N-1}→v{N}）/ 新建 STR-F-YYY（聚合 K 条 OR，v1）
  退回规范化 OR-ZZZ（建议拆为子 OR 后重新提交预处理链）
资产落账：<23 Bn引用写回 / 未落账>
补充原始需求材料：<无 / YYYYMMDD-场景业务名-补充原始需求材料.md>

一、方案反馈
  直接回复修改意见即可，无需手动标注文档。
  A. 整体确认 → 回复「整体确认」或「可以」
  B. 局部修改 → 直接说"X 应改为 Y"
  C. 驳回重做 → 说"XX 不对"并说明原因

二、下一步
  本Skill → 选择 FR-BIZ OR（含退回重切 OR 拆分后提交）或 需wft01修订 的 STR-F 重新运行
  后续    → STR-F（可以分解分配 / 待补充分解分配）→ wft02-biz
```
