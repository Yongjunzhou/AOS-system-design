## 一、目的与目标

### 1.1 主要目的

> 取信于相关方——「你听懂了我的需求和意图」。把 X 已给的这批业务文档按它们自带的属性组装成角色履职视角业务流程概要：文档、任务、用例场景照原样进入 Y，本任务长出它们之上的干枝、写出这棵树的秩序；并以闭合检查检出缺口，把业务链接不住的部分补成原始需求交回预处理链。

### 1.2 在设计链上的位置

设计开发 = 由需求到方案的逐对生成。业务路径的首对，是由相关方需求设计出业务流程。这一对的首步占一个任务位、分两半——**本任务是第一半**：

```
相关方需求 → 角色履职视角业务流程概要：  X = 相关方需求，不分形态，最深一级＝用例场景
        │  首对的叶由上游直接给出，这一步只组装干枝、做到框架
        ▼
       Y = 角色履职视角业务流程概要（02），装 R 树；P 树由同一任务位的第二半补
```

- **本任务是首步的第一半**：把 X 已给的这批业务文档按它们自带的属性组装成 **R 树**——谁在哪个场景、按什么序、处理哪些业务文档；同一位的第二半在同一批业务文档上长 P 树，末三级同批。
- **框架的位置**：首对的叶由相关方需求直接给出，本步骤因此只组装干枝。框架是业务流程的**浅态**，即根→枝梢（任务节点）；完整态是它的**深态**，即根→叶（用例场景），由下一个任务位产出。本任务写到枝梢为止，不写叶的详细定义。框架不自成一段交付，也不占需求-方案对的一端。
- **人类门禁位置**：两处——本任务产出后人类「整体确认」，节点状态由 `待确认方案` 推进；覆盖检查检出缺口后，候选去留由人类裁决。

### 1.3 主要目标

1. **组装 R 树 · 逐级定位与归拢**：按「所属主责角色」「所属E2E职责」在 R 树上逐级定位，缺哪一级就在哪一级判**合并**还是**新建**；业务文档归到所属 E2E职责之下。
2. **组装 R 树 · 长干枝**：业务域承 X，角色职责属目标组织级；相关方角色与 E2E职责本任务产出——角色按合并或新建落定，E2E职责判执行类或管理类、命名、边界定义，边界即主责角色的业务对象闭环。
3. **组装 R 树 · 写秩序**：场景职责边界陈述；该角色按什么序处理这些文档；加需求明示的任务触发关系，用业务语言表达。
4. **归位与 Y 侧内容**：X 已给的业务文档、任务节点、用例场景按属性落进 R 树，任务节点与用例场景判**新增**还是**改进**；为每张业务文档补封面模式，即正式或轻量；并写**分解源判据**。
5. **属性齐备保证**：每张业务文档的属性齐备且唯一——归拢对不对全由它决定。
6. **覆盖检查与缺口补足**：端到端闭环核对「需求条目有没有全部被业务链覆盖」；检出缺口以**业务链的闭合检查**补足原始需求材料。
7. **落账与推进**：要素齐备、覆盖结论落账于节点；人类确认后推进状态，并受理下游退回与上游变更。

> **P 侧不在本任务**：产品类型、产品构件类型、构件开发WBS（包）的建立，认亲与 P 树一致性结论，以及产品数据类缺口的推断——统归产品开发视角业务流程任务。

## 二、输入文档结构及规则（X = 相关方需求 · 需求侧）

### 2.1 主输入文档定位

本任务的 X = **相关方需求**，现行文件 `01-eos-specified-requirements.md`，是产品数据。它与其他产品数据不同，**不分框架态与完整态**——一产出即是完整态，最深一级为用例场景。它由**需求预处理链**的四个任务生成，不在 SKILL 指南之列。

相关方需求含两棵树——功能需求树与非功能需求树。**本任务消费功能需求树**；非功能需求树归非功能需求设计任务。

本任务运行时的**主输入对象** = X 中处于 `待处理` 的**业务功能需求条目**，即功能需求树的叶，按业务文档聚集、同一张业务文档下的条目优先成批，每批 ≤10 条。读 X 时按树定位、按属性归拢。文档的完整结构、字段与读写约定以 91 号规范 §11 与相关方需求数据文件自身为准。

### 2.2 相关方需求的树形结构与各级语义（X 树）

X 是本次映射的自变量。下图是该树在本任务视图下的展开，树形与各级语义以 94 号文档 §2.1.1 为准。

```
相关方功能需求
└── 业务文档 ──────── ① 根　带五个属性：所属业务域 × 所属主责角色 × 所属E2E职责 × 所属产品类型 × 所属产品构件
    └── 任务节点 ──────── ② 开发文档所对应任务的子节点，原则上，一个节点对应一个表单标签页
        └── 用例场景 ─ ③ 任务节点上包括的用例场景操作，原则上对应着标签页上的一个功能按钮、右键操作项，或一个快捷键所提供的功能
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务文档 | 业务运行结束后应输出的产品数据文档，一般对应一个流程、一个工单、一个计划，或一个看板业务 | **预处理链产出** | **到 Y 侧就是业务文档**：归位；归拢的依据是它自带的属性——「所属业务域」定 R 树的域，「所属主责角色」定 R 树的角色，「所属E2E职责」定它落在 R 树的哪个场景。「所属产品类型」与「所属产品构件」不由本任务消费，供下游那份 P 侧文档用 |
| ② | 任务节点 | 开发文档所对应任务的子节点，原则上，一个节点对应一个表单标签页 | **预处理链产出** | **到 Y 侧就是枝梢节点**：归拢到所属业务文档之下，标 `[待复核]`；首次归位照原样搬入，已归位的文档再来新需求时判**新增**还是**改进**。这两级的规范化归预处理链 |
| ③ | 用例场景 | 任务节点上包括的用例场景操作，原则上对应着标签页上的一个功能按钮、右键操作项，或一个快捷键所提供的功能 | **预处理链产出** | **到 Y 侧就是叶节点**：归拢到所属任务节点之下，标 `[待复核]`；首次归位照原样搬入，已归位的任务节点再来新需求时判**新增**还是**改进** |

> **文档的五个属性，不占级位**：所属业务域／所属主责角色／所属E2E职责／所属产品类型／所属产品构件随业务文档携带——这五个是 R／P 两树的坐标，在本份数据里作**索引／分片轴**，不是归集级。本任务消费其中三个：所属业务域、所属主责角色、所属E2E职责。
>
> **同一个文档可对应多个相关方需求**：需求捕获时，不同的相关方，其业务对象可能是同一个文档；亦或，同一个相关方对同一个文档的业务，后续可能有改进的需求。
>
> **X 的三级就是 Y 的同名三级**：同一批节点，在 X 里按文档平铺，在 R／P 两棵树里按角色与产品归拢。故本任务的文档清单以 X 的业务文档为准。
>
> **落位现状**：相关方需求的现行物理文件以角色分片直接挂条目，尚未含业务文档与任务节点两级；本任务读时按条目正文语义归拢，标 `[待复核]`。这两级的规范化与写归预处理链。

### 2.3 X 侧规则（复核与退回）

- **切分与建树权在预处理链**：业务对象闭环的切分、业务文档的五个属性、任务节点与条目的落位，都由预处理链制定并执行——**本任务不重切 X、不重定属性**。
- **复核两项**：业务文档的五个属性是否齐备且唯一；条目的语义是否与它所属业务文档同指一个业务对象——判归属，不判内容。二者通不过 → 标 `需退回重切` → 回预处理链处置后重新进入。
- **承载量超限**，一批吞不下 → 分批进入；≤10 条/批是软限制，人类可确认放宽。
- **Y 侧的节点拆分与改 X 不是一回事**：Y 侧装不下时的拆分或横切出口动的是 Y 的节点，不回头改 X。

### 2.4 受理门槛（输入校验）

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 条目状态 = `需退回重切` | 不可处理 | 输出退回记录 → 退出 |
| 条目状态 ≠ `待处理` | 不可处理 | 输出当前状态 → 退出 |
| 同一批业务文档的主责角色不唯一 | 不可处理 | 输出角色分布 → 退出 |
| 条目类型含引擎能力功能需求 / 非功能需求 | 路由错误 | 输出类型分布 + 路由指引 → 退出 |
| 同一业务文档下条目 > 10 条 | 软限制 | 输出超限提示 → 人类确认 |
| 无待处理条目 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

### 2.5 依赖与校验（读 X 时）

- 业务文档的五个属性齐备、条目正文语义自洽：预处理链已归一化。缺标或矛盾 → 标 `[需确认]`，不自动推进。
- **同一业务文档内的一致性**：该文档下的条目必须归到同一个业务对象——归不到 → 输出退回重切提示，不自动拆。**判的是归属，不是内容**：不同相关方、不同时期提的需求各说各事，都落在这一张文档上即成立。
- 读 X 遵循 91 号规范 §A.3.3 读取协议：AI 可以处理节点优先、逐节点加载、按需扩大，不默认加载全文。

## 三、输出文档结构及规则（Y = 角色履职视角业务流程概要 · 方案侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 角色履职视角业务流程概要**——**一份文档，写到框架为止**：根→枝梢（任务节点），到结构判定级，不含叶定义。完整态（角色履职视角业务流程定义）由下一个任务位产出，不在本任务；末三级（业务文档、任务节点、用例场景）的**实体由本文件持有**，同一步的第二半与下一任务位都按对位取用。

### 3.2 输出空间的 R 树（Y 树）

本任务的 Y 是业务流程的 **R 树**——**R 角色履职树**回答「某角色在哪个场景、按什么序、处理哪些业务文档完成闭环」，讲的是履职与工作序。同一批业务文档在 P 树里另有一面（属哪个产品/构件/WBS 包、怎么生成与流转），那一面由产品开发视角业务流程任务长；两树经**认亲**互指，末三级同名同批，实体在本任务这份文档里。

**R 角色履职树（业务运行角色履职视角）**

```
角色履职业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的一类职责范围
            └── E2E职责 ─ ④ 一个业务对象闭环，分执行类与管理类
                └── 业务文档 ─ ⑤ 业务运行输出的"产品"数据文档，对应本文档开发任务
                    └── 任务节点 ─ ⑥ 文档开发任务的多个步骤，枝梢节点
                        └── 用例场景 ─ ⑦ 是叶
```

| 级 | 节点 | 意义 | 怎么得到 | 本任务如何处置 |
|----|------|------|---------|--------------|
| ① | 业务域 | 归属域 | **承 X**，取自 X 的「所属业务域」；R／P 两棵树各有一份，同值、不共享节点 | 作定位与对账域 |
| ② | 相关方角色 | 主责角色，即业务对象生命周期的主推动者 | **本任务产出**，取自 X 的「所属主责角色」；节点不存在时与同类角色合并或新建 | 作分片与复用宿主范围 |
| ③ | 角色职责 | 角色承担的一类职责范围 | **目标组织级**，随角色履职视角业务流程概要演进 | 本任务不产该节点 |
| ④ | E2E职责 | 一个业务对象闭环，分执行类或管理类 | **本任务产出**（合并 → 新建，**端到端为判据**） | 本任务新建/修订单位 + 人类确认挂点：归拢条目、职责边界、收敛自查 |
| ⑤ | 业务文档 | 业务运行输出的"产品"数据文档，对应本文档开发任务 | **承 X**，同名同级 | 归位；补 Y 侧内容：封面模式、**分解源判据** |
| ⑥ | 任务节点 | 文档开发任务的多个步骤，枝梢节点 | **承 X**，同名同级 | 归位到业务文档之下；框架到本级为止 |
| ⑦ | 用例场景 | 是叶 | **承 X**，同名同级 | 归位到任务节点之下；完整态到本级为止 |

> **平台侧的 R 树**：本任务的主体走**各业务域的 R 树**；平台自身的治理业务走**平台侧的 R 树**——同一棵 R 树在「平台本身」这一侧**少「角色职责」一级**：业务域 → 相关方角色 → E2E职责 → 业务文档 → 任务节点 → 用例场景，因为业务配置角色不按角色类型再归纳。层级差非遗漏。角色履职视角业务流程概要里预置的治理节点 `bpd-biz-GOV-*` 即平台侧场景，本任务对其只作渐进增补，不主动展开。

> **两树的末三级就是 X 的三级**：同一批节点——X 侧的需求承载级、本树的文档开发任务，到下游那份是产品数据位，三者同指一张文档。**认亲**（逐文档标定 P 坐标）由产品开发视角业务流程任务做，因为只有它两棵树都在场。
>
> **方案边界**：本任务只到结构判定——文档是否存在、封面模式、正文实体类型、候选引擎、任务类型与任务节点；叶定义、封面映射、正文实体结构、数据权限、引擎权威值、处理角色与状态变迁，以及四级页面的写实由下一个任务位补。下游各对的展开不在本任务。
>
> **树权威**：R 树的拓扑与各级语义以《EOS 系统设计产品数据分解结构》（94 号文档）为准；X 与 Y 两份产品数据的树画像以各自数据文件的树画像区为准。

### 3.3 节点类型与结构要点

> 方法读法：**E2E职责及其以上的各级，即枝干**，是聚合层；**任务节点 = 枝梢**，即框架的最深一级；**用例场景 = 叶**，即完整态的末级。末三级由 X 直接给出，本任务不另造它们——**首次归位时照原样搬入**；**已归位的文档再来新需求时**，新增的任务节点与用例场景与树上已有的做语义与业务逻辑分析，判**新增**还是**改进**。**本对两侧的叶是同一批**，故**不涉及映射与分配**。业务流程的文档转译到功能表单，走的是**页面视角**、不是承接，见 91 号规范 §7.3。

- **E2E职责，即枝干**：一个主责角色——业务对象生命周期的主推动者——的一个业务对象闭环，由一组有流转依赖的业务文档序列构成。类型二分类：**执行类**，从需求提出到需求满足；**管理类**，计划→监控→分析→纠正，须含计划清单文档 + 承载监控与分析环节的业务文档。
- **业务文档，即 X 的根**——业务运行结束后应输出的产品数据文档，对应本文档的开发任务，即一份要开发的业务文档；一般对应一个流程、一个工单、一个计划，或一个看板业务。**它的 Y 侧内容** = 封面模式 + 分解源判据。
- **分解源判据**：任务节点声明它可分解出哪些用例场景，到名称级，各项带内联稳定标签——标签既是框架到完整态的追溯键，也是本任务到系统需求框架设计任务的追溯键。
- 业务文档按封面模式分**正式**与**轻量**：正式有独立于正文 CRUD 的生命周期，轻量无封面、正文即文档。判据见 91 号规范 §2。
- **任务类型的启动规则**：E2E职责中第一个有任务类型的文档必然为**计划**，这是闭环启动机制。

### 3.4 Y 侧规则（组装与收敛）

- **方案边界**：只到结构判定——文档是否存在、封面模式、正文实体类型、候选引擎、任务类型与任务节点；叶定义、封面映射、正文实体结构、数据权限、引擎权威值、处理角色与状态变迁，以及四级页面的写实由下一个任务位补。**Y 侧不重写 X 给的条目前三层**，只在其上长干枝、补方案内容。
- **E2E职责构建规则**，用于新建：识别触发 → 追踪自然终点，不得在终点之后扩展 → 闭合验证 → 边界四标准，即完整性、一致性、紧凑性、粒度匹配，产出场景职责边界陈述。
- **文档序列构建规则**：执行类按输入-输出传递链排列；管理类按计划→监控→分析循环排列。
- **收敛自查**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。新文档归不进现有枝干，才上溯建更高层。

### 3.5 要素清单（本任务写入方案节点必须带齐）

写入角色履职视角业务流程概要的节点，字段对齐该数据文件 §4.1 的模板：

- **块头字段**：块ID / 节点类型 bpd-biz / 类型 执行类或管理类 / 主责角色 / 当前状态。
- **正文要素行**，依次为：
  - 业务域 / 相关方角色 / 角色职责；场景职责边界陈述；
  - **承接的条目引用**——X 的用例场景条目引用，N:1 汇聚，**跨批追加不覆盖**，作覆盖与追溯锚点；治理预置节点按治理覆盖口径；
  - **文档序列**——该角色按什么序处理这批业务文档；加需求明示的任务触发关系；
  - **业务文档方案**，每张业务文档一段：封面模式，即正式或轻量；正文实体类型；支撑引擎**候选**，全量标 `[推断]`；
  - **任务与叶**，每张业务文档之下：任务类型与任务节点的名称、用例场景的名称，**均到业务语言名称级**并带内联稳定标签；并写**分解源判据**；
  - 推理依据与补全说明；完备性检查结果；补充材料引用；变更影响声明 / 版本号。

> **P 侧要素不在本清单**：认亲坐标、层级判定档位、WBS 归组、P 树一致性结论、缺口与候选节点建议——那些写在产品开发视角那份文档的节点里。

### 3.6 传出承诺（给两个下游任务）

本任务把方案节点交给下游时，承诺节点达到：

1. 状态 = `可以srb设计`，在人类「整体确认」之后；
2. 要素清单齐备；
3. **每张业务文档带任务节点与用例场景**，到业务语言名称级并带内联稳定标签，并带**分解源判据**；末三级的实体在本任务这份文档里，两个下游都按对位取用；
4. 覆盖检查结果已落账于节点——**节点累计承接的**全部需求语义 ⊆ 其业务链所能实现的范围；缺口已走补充材料回路，不是隐藏遗漏。

> **接口契约，与两个下游任务的受理前提互为对侧**：同一任务位的第二半与下一个任务位各自受理本任务传出的节点，状态为 `可以srb设计` 或 `待补充srb设计`；它们都以要素清单与传出承诺为对照——要素缺失、冲突 → 退回 `需biz01修订` + 缺失说明。核对方法 = 93 号规范 §4.2 的逐条映射。

## 四、输出与输入转换规则

### 4.1 归拢与长枝规则（X 已给末三级，本任务长干枝）

- **归拢由属性定**：每张业务文档落进哪一支，由它身上带的属性决定——「所属业务域」定它走哪个域，「所属主责角色」定它走哪条 R 树分片，「所属E2E职责」定它落在 R 树的哪个场景。这三个属性齐备且唯一，是本任务唯一的归拢依据。
- **逐级分流**：文档按属性在 R 树上查到哪一级、缺哪一级，就在哪一级定 合并还是新建——相关方角色与 E2E职责 两级判**合并／新建**，其中 E2E职责以**端到端**为判据；业务文档一级判**新增文档节点**；任务节点与用例场景两级判**新增／改进**，以**语义与业务逻辑**为判据。优先级始终 复用 → 改进 → 新增。
- **语义跨界**：同一张业务文档下的条目指向不同业务对象 → 属 X 的缺陷，标 `需退回重切` 回预处理链，不在 Y 侧就地分。
- **Y 侧装不下时**：节点拆分，或横切式承接走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有枝干做扩展/拆分/合并后，须复查其下已归位的文档是否失配 → 批量重归位或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则与判据出处 |
|--------|--------------------|
| 业务域与角色 | 读业务文档的「所属业务域」→ 定 R 树的域；读「所属主责角色」→ 定 R 树的角色 |
| E2E职责类型 | 需求动作词偏向执行类/管理类；存疑标 `[推断]` |
| 文档清单 | **以 X 的业务文档为准**——本任务不另立清单；覆盖检查发现应有而未列者 → 走补充材料回路 |
| 封面模式 | 是否需审批/发布/版本追溯等生效动作 |
| 任务类型 | 读任务节点直接捕获；只给出管理模式→判定+`[推断]`；任务节点缺失→推断+`[推断]`；首个有任务类型的文档必为计划 |
| 支撑引擎 | 按正文数据类型匹配平台引擎，**全量 `[推断]`** |
| 用例场景 | 取 X 的条目原文，不另拟名 |
| 文档间关系 | 流转顺序，执行类走传递链、管理类走循环；加需求明示的任务触发关系 |

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回需求侧／宿主误匹配 → 业务链关系检测，分 确认／无新增／引擎判定变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查。

### 4.4 缺口规则

覆盖检查检出缺口，**业务链类**一条通道：闭合检查核对这条业务对象闭环是否走完——执行类从需求提出到需求满足，管理类按计划→监控→分析→纠正；走不完即缺了应有的业务文档或任务节点 → 记 `[业务链缺口]`。它锚在业务链上，是这张业务文档序列自身的缺口，不挂在别处。

缺口生成**补充原始需求材料**，回需求预处理链，由它加工成业务功能需求条目、归业务路径。人类裁决「需要」→ 落地；「不要」→ 废弃。**本任务不脑补节点**。

> **另外两类缺口不在本任务**，按锚定归属：**产品数据类**——"本批涉及的 WBS 包对照闭合模型，应有而缺失的产品数据"，锚在 P 树，归产品开发视角业务流程任务；**引擎类**——"用例场景逐一对照平台引擎，接不住的操作"，锚在用例场景，归角色履职视角业务流程定义任务，那时用例场景已有叶定义，对照才判得准。

## 五、转换流程及检验规则

### 5.1 设计过程（Step 序列）

Step Start 与 Step End 两端由 [91 附录A](91-eos-biz-eng-spec.md) 统一承载，下表一并列出以便看全序列。入口的受理判定按受理门槛表特化；下表列定义引 00-doc-conventions §十三。

|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、受理判定、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |

#### 5.1.1 Step 1 · 设计材料加载

读 `待处理` 业务功能需求条目 + 同一业务文档／同域候选存量方案节点；加载按读取协议。

#### 5.1.2 Step 2 · 反馈处理

人类对话修改／整体确认／线下修订；反馈双轨按 91 号规范 §A.5 记录。

#### 5.1.3 Step 3 · 组装 R 树

逐一对新进的业务文档，按它自带的属性——所属主责角色、所属E2E职责——在 R 树上查找位置；查到哪一级缺节点，就在哪一级定"合并还是新建"：

- **相关方角色节点已在** → 看 **E2E职责**节点：
  - **E2E职责已在** → 看 **业务文档**节点：
    - **业务文档节点已存在** → 对新增业务文档下的任务节点与树上已有的任务节点做**语义分析与业务逻辑分析**，给出**新增任务节点**还是**改进任务节点**的建议方案；再对拟变更任务节点下的用例场景，连同新增的用例场景，做同样的分析，给出**新增用例场景**还是**改进用例场景**的建议方案
    - **业务文档节点不存在** → 把新进的业务文档作为该 E2E职责下的一个**新增文档节点**
  - **E2E职责不存在** → 分析该相关方角色下已有的 E2E职责，判断新进的 E2E职责能否与其中之一**合并**——**端到端是判据**；能合则合，不能则**新增 E2E职责节点**，判执行类或管理类、命名、定边界，边界即主责角色的业务对象闭环，产出场景职责边界陈述
- **相关方角色节点不存在** → 分析该业务域下已有的相关方角色，判断新进的相关方角色能否与其中之一**合并**；能合则合，不能则**新增角色节点**

节点落定之后：

- 写履职序：该角色按什么序处理这批业务文档，加需求明示的任务触发关系；
- 为每张业务文档补封面模式，并写**分解源判据**；
- 有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.4 Step 4 · 覆盖检查与补充原始需求

执行关口检查，其中**端到端闭合**是本需求-方案对的关口——执行类从需求提出贯通到需求满足；管理类按计划→监控→分析→纠正核对，须含计划清单文档与承载监控、分析环节的业务文档。检出缺口即缺了应有的业务文档或任务节点，记 `[业务链缺口]`。

缺口生成**补充原始需求材料**交需求预处理链，加工成业务功能需求条目归业务路径。候选去留由**人类裁决**。

#### 5.1.5 Step 5 · 写回与落账

角色履职视角业务流程概要落账 + 状态推进 + 基线，引 91 号规范 §A.3.3 与 §A.6。

### 5.2 检验规则（关口）

- **属性齐备检查**：每张业务文档的五个属性齐备且唯一；本任务据其中三个——所属业务域、所属主责角色、所属E2E职责——归拢，缺一个就落不了位。
- **覆盖检查**，这是本需求-方案对的关口：**节点累计承接的**全部需求语义 ⊆ 其业务链即枝梢之并能实现的范围。同一张业务文档的需求分多批到来，故检查范围累计——每批检新增部分；本批改动了已有枝干，另按影响面复查其下已归位部分。EOS 实例化 = **端到端闭合检查**——执行类从需求提出贯通到需求满足；管理类按计划→监控→分析→纠正核对，须含计划清单文档 + 承载监控与分析环节的业务文档，这两环节的运行时推进结果不作需求缺口。缺口 → 生成补充原始需求材料 → 经预处理链补回，**不脑补节点**。
- **要素机械检查**：逐文档要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待下游推断]`。
- **治理覆盖检查**：预置治理业务流程的业务链按角色预定文档集核对；无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以srb设计 ──下游锁定──→ 在srb设计 ──下游完成──→ 已srb设计
     ↑                       ↑                      │
     │                       │          下游退回     │
     └── 本任务修订 ──── 需biz01修订 ←───────────────┘
```

上游变更，即新需求汇入，按状态分流：`可以srb设计`→版本递增，未消费；`在srb设计`→版本递增，增量处理；`已srb设计`→`待补充srb设计`→下游补全。节点生命周期与写回范围引 91 号规范 §A.6，此处为本任务特化。

### 5.4 运行时特化参数

- **锚点需求** = 节点累计承接的全部业务功能需求条目，跨批追加
- **操作条目** = 场景职责边界 + 干枝 + 业务文档方案段 + 分解源判据展开项 + 补充原始需求材料候选
- **推进目标** = `可以srb设计`
- **退回节点状态值** = `需biz01修订`，退回修订走修订转换
- **清除与级联条件**由状态机与上游分流定
- 其余运行时机制——Step Start／Step End、入口条件与优先级、反馈双轨状态机、git 基线、Step End 三区模板——按 91 号规范 附录A 执行；本任务的受理门槛已就地成文

## 六、关联产品数据及规则（接口）

**R 树本身就是资产**——本任务不另读资产文档，除 X 之外没有外部输入。本节记本任务读什么、写什么。

### 6.1 读

| 产品数据 | 读什么 | 用途 |
|---------|--------|------|
| 相关方需求（X） | 业务文档 → 任务节点 → 用例场景，及业务文档上的五个属性 | 本任务的唯一外部输入 |
