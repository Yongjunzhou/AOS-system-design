## 一、目的与目标

### 1.1 主要目的

> 把上游交来的概要深化到定义：每个场景成一页场景标签页、每张业务文档成一个窗口标签页、每个任务节点成一张表单标签页、每个用例场景成一个功能操作项；并以用例场景对照平台引擎，把接不住的操作补成原始需求交回原始需求处理。

### 1.2 在设计链上的位置

设计开发 = 由需求到方案的逐对生成。业务路径首对，是由相关方需求设计出业务流程。这一对的首步已由上一个任务位交出概要——职责视角与产品开发视角各一份；**本任务把职责视角那份深化到定义**：

```
职责视角业务流程概要 → 职责视角业务流程定义：  X = R 树概要，最深一级＝用例场景
        │  本任务给各级节点补详细定义——落点是界面四级
        ▼
       Y = 职责视角业务流程定义（04），R 树定义
```

- **本任务是首对的深化步**，占下一个任务位：上一个任务位交出概要，本任务把它的各级节点深化到详细定义。
- **详细定义的落点是界面**：菜单、窗口标签页、表单标签页、功能操作项四级都挂在 R 树上，故定义只做职责视角；**产品开发视角止于概要**，其详细定义不在本树的定义里。
- **形态的位置**：本任务交出**定义**——概要加上各级节点的详细定义。概要是本对方案侧的中间形态，是同一棵 R 树的较浅形态，叶在其中已是说明级树节点；框架只是概要内部的一层截面，不自成一段交付。三形态都是方案的不同详细程度，都不算需求-方案对的一端。
- **人类门禁位置**：两处——本任务产出后人类「整体确认」，节点状态由 `待确认方案` 推进；引擎类缺口候选去留由人类裁决。

### 1.3 主要目标

1. **场景装配写实**：E2E职责 → 场景标签页——单窗／双窗／下钻层级／面包屑；场景职责边界承上游，本任务不重定。
2. **业务文档写实**：逐文档定封面映射、正文实体结构、支撑引擎**校验权威值**、数据权限，并定它的窗口标签页显示模式，即列表／单据／图示。
3. **任务节点写实**：一个任务节点一张表单标签页——处理角色、可执行动作、状态变迁、页面间流转规则；同一文档的若干表单标签页按任务顺序构成序列。
4. **用例场景写实**：一个用例场景一个功能操作项——功能按钮、右键操作项，或快捷键；取 X 的用例场景名，不另拟名。
5. **叶与详细定义对齐**：X 的每个叶节点都拿到详细定义，内联稳定标签逐一对上。
6. **任务关系引擎化**：文档间流转顺序 → 输出文档序列；任务间触发规则 → 引擎触发规则。
7. **引擎类原始需求**：用例场景逐一对照平台引擎的能力清单，接不住的操作记 `[引擎缺口]`，生成引擎类补充原始需求材料交原始需求处理。
8. **覆盖自查**：证明 X 节点承接的需求语义 ⊆ 本任务叶定义之并。
9. **落账与推进**：要素齐备、覆盖结论落账于节点；人类确认后推进状态，并受理下游退回与上游变更。

## 二、输入文档结构及规则

输入文档（X） = 职责视角业务流程概要，为需求-方案对的需求侧文档。

### 2.1 X 的树形结构与各级语义

X 是职责视角业务流程概要，由**职责视角业务流程任务**产出，根到叶，最深一级为用例场景，各级节点到说明为止。**输入语义属深化型**：X 是本需求-方案对阶段一产出的 Y，即该对方案侧的较浅形态；本任务是同一需求-方案对的深化步，任务不是承接而是**深化**——把已承接的语义从说明级写到详细定义。写到多深，由**详细定义的落点**给出：界面四级。下图是该树的展开，树形与各级语义以 94 号文档 §2.2.1 为准；结构、字段与读写约定以 91 号规范 §11 与职责视角业务流程概要数据文件自身为准。

```
职责业务
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的职责清单，是多个E2E职责的聚类。
            └── E2E职责 ─ ④ 一个端到端的职责业务，分执行类（从接收需求到需求被确认得到满足）与管理类（PCA）
                └── 业务文档 ─ ⑤ 业务运行输出的产品数据文档，对应本文档开发任务
                    └── 任务节点 ─ ⑥ 文档开发任务的多个步骤，枝梢节点，内容到步骤级
                        └── 用例场景 ─ ⑦ 是叶
```

| 级 | 节点 | 本任务如何处置 |
|----|------|--------------|
| ① | 业务域 | 只读——本任务不重定域 |
| ② | 相关方角色 | 只读——本任务不重定角色 |
| ③ | 角色职责 | 只读——该级随职责视角业务流程概要演进 |
| ④ | E2E职责 | **写实的起点**：写实为场景标签页——单窗／双窗／下钻／面包屑；场景职责边界承上游 |
| ⑤ | 业务文档 | **写实的二级**：写实为窗口标签页；补封面映射、正文实体结构、支撑引擎权威值、数据权限 |
| ⑥ | 任务节点 | **写实的三级**：写实为表单标签页——处理角色、动作、状态变迁、页面间流转 |
| ⑦ | 用例场景 | **写实的四级**：给它补详细定义——功能操作项，即功能按钮、右键操作项，或快捷键；名称照搬 |

### 2.2 X 的树形结构规则

> **概要里叶已是树节点**：用例场景在 X 里就是说明级树节点，带内联稳定标签，作概要→定义的追溯键。本任务给它补详细定义，不新增、不改名、不重排。
>
> **平台侧的 R 树**：各业务域走各业务域的 R 树；平台自身的治理业务走**平台侧的 R 树**——同一棵 R 树在「平台本身」这一侧**少「角色职责」一级**：业务域 → 相关方角色 → E2E职责 → 业务文档 → 任务节点 → 用例场景，因为业务配置角色不按角色类型再归纳。X 里预置的治理节点 `bpd-biz-GOV-*` 即平台侧场景，本任务对其照常深化，不另立一套写法。
>
> **落位现状**：相关方需求的现行物理文件以角色分片直接挂条目，其业务文档与任务节点两级尚未落位；上游照此读时按正文语义归拢并标 `[待复核]`。

## 三、输出文档结构及规则

输出文档（Y） = 职责视角业务流程定义，为需求-方案对的方案侧文档。

### 3.1 Y 的树形结构与各级语义

本任务的 Y 是同一棵 **R 树**的定义，一份文档，根到叶。**R 树（各业务域 · 业务运行职责视角）**回答「某角色在哪个场景、按什么序、处理哪些业务文档，在页面上怎么操作完成闭环」；概要里只到说明的各级节点，到这里带上详细定义。同一批业务文档在 **P 树**里另有一面，由产品开发视角业务流程概要持有。两树经**认亲**互指，末三级同名同批。

**R 树（各业务域 · 业务运行职责视角）**

```
职责业务 ──────── 根
└── 业务域 ──────────── ① 归属域
    └── 相关方角色 ───── ② 主责角色，即业务对象生命周期的主推动者
        └── 角色职责 ─── ③ 角色承担的职责清单，是多个E2E职责的聚类。
            └── E2E职责 ─ ④ 一个端到端的职责业务，分执行类（从接收需求到需求被确认得到满足）与管理类（PCA）
                └── 业务文档 ─ ⑤ 同 X 树的同名节点
                    └── 任务节点 ─ ⑥ 同 X 树的同名节点
                        └── 用例场景 ─ ⑦ 同 X 树的同名节点
```

| 级 | 节点 | 怎么得到 |
|----|------|---------|
| ① | 业务域 | **承袭**，与 X 同名同级；R／P 两棵树各有一份节点，同值、不共享；照搬，不重定 |
| ② | 相关方角色 | **承袭**，与 X 同名同级；照搬，不重定 |
| ③ | 角色职责 | **承袭**，与 X 同名同级；照搬，不重定 |
| ④ | E2E职责 | **承袭**，与 X 同名同级；场景职责边界照搬，写实为场景标签页 |
| ⑤ | 业务文档 | **承袭**，与 X 同名同级；写实为窗口标签页，补封面映射、正文实体结构、支撑引擎权威值、数据权限 |
| ⑥ | 任务节点 | **承袭**，与 X 同名同级；写实为表单标签页——处理角色、动作、状态变迁、页面间流转 |
| ⑦ | 用例场景 | **承袭**，与 X 同名同级；**叶的详细定义本任务产出**——写实为功能操作项，即功能按钮、右键操作项，或快捷键 |

> **同一棵 R 树的深浅两态**：概要那份与定义这份是同一份产品数据的两个形态——Y 复述 X 的整棵树，再给各级节点补详细定义，节点编号沿用 X 的，不另起一套。
>
> **树权威**：R 树的拓扑与各级语义以 94 号文档 §2.2.1 为准；Y 的树画像以职责视角业务流程定义的数据文件为准。

### 3.2 节点类型与结构要点

**界面四级就是详细定义的落点**——除最外层的菜单标签页只是浏览器标签页级的容器、不占树级外，其余四级各对应 R 树的一级。四级写的是各节点在页面上的形态；页面组件背后的**配置对象**即功能表单，其归属在**配置方案**层，不在本任务：

| 页面层级 | 对应树级 | 本任务的写实内容 |
|---------|---------|----------------|
| 场景标签页 | E2E职责 | 一个场景业务的工作区——初始态单窗、分屏态双窗、持续下钻、面包屑导航 |
| 窗口标签页 | 业务文档 | 单个实体数据的展示载体，三种可切换模式——列表模式、单据模式，以及按数据源类型决定的第三种模式 |
| 表单标签页 | 任务节点 | 一份业务文档在其任务流转中的一页；同一文档的若干表单标签页按任务顺序构成序列 |
| 功能操作项 | 用例场景 | 表单标签页上的一个可点操作——功能按钮、右键操作项，或快捷键 |

- **场景标签页**：由窗口标签页编排而成；场景内的窗口标签页序列即该 E2E职责处理这批业务文档的文档序列。
- **窗口标签页的显示模式**：按数据源类型定——常规数据取列表／单据／指标，指标清单取图示·指标，看板清单取图示·看板。
- **轻量/正式业务文档**：判定看它有没有**独立于正文 CRUD 的生命周期**——需要审批流转、版本追溯、派发验收或独立状态变迁的，是**正式文档**，有封面实体；都不需要的，是**轻量文档**，无封面、正文即文档。
- **表单标签页序列**：由文档的任务节点依序编排，页与页之间有流转规则；一个任务节点对应一张，不并页、不拆页。
- **任务节点这一级的两个形态**：上游写到业务语言名称级，即任务类型与节点名称；本任务写到架构语言，即处理角色、可执行动作、状态变迁与页面间流转规则，并落成一张表单标签页。
- **功能操作项**：表单标签页上的一个可点操作；一个用例场景对应一个，不多不少。
- **支撑引擎权威值**：上游给的候选一律是 `[推断]`；本任务在定义的上下文里校验，确认／修正／推翻，**权威以本任务的落定值为准**，下游据此分配能力与指标。

### 3.3 Y 侧规则

- **形态边界**：写到界面形态与数据定义为止——E2E职责的场景装配、业务文档的封面映射与正文实体结构、任务节点的表单标签页序列、用例场景的功能操作项。**Y 复述 X 的整棵树**，节点编号沿用 X 的。
- **深化不造叶**：叶的名称、次序、内联稳定标签由 X 给出，照搬不改；本任务给每个节点写实其界面形态与数据定义。
- **逐级写实**：写实自 E2E职责 往下推——场景 → 窗口 → 表单 → 操作项；下一级的定义以本级的形态为前提，上一级未定不给下一级下结论。
- **收敛判据**：父节点语义覆盖子节点语义之并，即覆盖完整；同层兄弟不重叠，即兄弟互斥。

### 3.4 要素清单

写入 Y 的节点必须带齐下列要素，字段对齐 Y 的数据文件 §4.1 的模板：

- **块头字段**：块ID / 节点类型 bpd-biz / 类型 执行类或管理类 / 主责角色 / 当前状态。
- **正文要素行**，依次为：
  - 业务域 / 相关方角色 / 角色职责；场景职责边界陈述——承 X；
  - **承接的条目引用**——经 X 的承接记录引用，N:1 汇聚，**跨批追加不覆盖**，作覆盖与追溯锚点；
  - **场景装配**——场景标签页：单窗／双窗／下钻层级／面包屑；
  - **业务文档实现方式**，每张业务文档一段：封面映射，即正式走封面实体字段、轻量无封面；正文实体结构；支撑引擎**校验权威值**；数据权限；窗口标签页显示模式；
  - **表单标签页序列**，每张业务文档之下：每个任务节点一张，含处理角色、可执行动作、状态变迁、页面间流转规则；
  - **叶定义**，每个任务节点之下：每个用例场景一个功能操作项，含形态、触发条件、执行结果，带内联稳定标签，与 X 的叶节点逐一对上；
  - 任务关系引擎化；推理依据与补全说明；完备性检查结果；补充材料引用；变更影响声明 / 版本号。

### 3.5 传出承诺

本任务把方案节点交给下游时，承诺节点达到：

1. 状态 = `可以srb设计`，在人类「整体确认」之后；
2. 要素清单齐备——场景装配、业务文档实现方式、表单标签页序列、叶定义已写实到位；
3. **每个叶带界面形态与数据定义**，内联稳定标签与 X 的叶节点逐一对上，可作下游的承接源；
4. 覆盖检查结果已落账于节点——**节点累计承接的**全部需求语义 ⊆ 其叶定义之并；缺口已走补充材料回路，不是隐藏遗漏。

> **接口契约，与系统需求框架设计任务的受理前提互为对侧**：本任务的方案节点即下一对的需求侧，状态为 `可以srb设计` 或 `待补充srb设计`。下游以要素清单与传出承诺为对照，受理前提分作两处：可承接对象在其第二章的输入文档结构，门槛与检验在其第五章的入口检验。要素缺失、冲突 → 退回 `需biz01cr修订` + 缺失说明。核对方法 = 93 号规范 §4.2 的逐条映射。

## 四、输出与输入转换规则

### 4.1 深化与写实规则（X 已给各级节点与叶名，本任务补详细定义）

- **叶清单由 X 定**：X 的用例场景就是叶清单——名称、次序、内联稳定标签照搬，不新增、不改名、不重排。
- **写实自外向内**：场景标签页定工作区形态，窗口标签页定文档的展示载体，表单标签页定任务流转的一页，功能操作项定页上的一次可点操作。四级递进，上级的形态是下级写实的前提。
- **节点整体分流**：它对应的 E2E职责已在 Y 中存在 → **复用**，走修订转换；尚无 → **新建**。优先级始终 复用 → 改进 → 新增。
- **X 侧语义不重判**：场景边界、文档清单、任务类型的划分是上游的事；本任务发现 X 的缺陷 → 标 `需biz01修订`，不在 Y 侧就地改。
- **Y 侧装不下时**：节点拆分，或横切式深化走独立分支并作影响面标注——动的是 Y 的节点。
- **改进 = 影响面复查**：对已有干枝做扩展／拆分／合并后，须复查其下已写实的文档与叶是否失配 → 批量重写实或回退。

### 4.2 要素生成判定（从 X 推导 Y 要素）

| 生成项 | 判定规则与判据出处 |
|--------|--------------------|
| 场景装配 | E2E职责承 X；写实单窗／双窗／下钻层级／面包屑，取自 91 号规范 §1.2 的交互模式 |
| 窗口标签页显示模式 | 读业务文档的正文数据类型与封面模式 → 定列表／单据／图示；图示再按数据源分指标与看板，取自 91 号规范 §1.1.1 |
| 封面映射 | 正式 → 封面实体字段映射；轻量 → 无封面、正文即文档 |
| 正文实体结构 | 承 X 的正文实体结构，逐文档展开为实体表与字段集，含类型与约束 |
| 支撑引擎权威值 | 上游候选全量 `[推断]` → 本任务确认／修正／推翻，**落定为本任务给出的校验权威值**，存疑标 `[推断]` |
| 数据权限 | 逐文档定角色与数据范围 |
| 表单标签页序列 | 一个任务节点一张；处理角色、可执行动作、状态变迁取自 X 的任务节点步骤，页面间流转规则本任务编排 |
| 功能操作项 | 取 X 叶节点的原文，不另拟名；形态与触发就地判定，一个用例场景一个操作项 |
| 任务关系引擎化 | 文档间流转顺序 → 输出文档序列；任务间触发规则 → 引擎触发规则 |
| 引擎能力对照 | 用例场景逐一对照**平台引擎**的能力清单；接不住的操作 → 记 `[引擎缺口]`，走引擎类补充原始需求 |
| 文档视图 | **以 X 的业务文档为准**——同一次序、同一个名称，不另立清单 |

### 4.3 修订转换（新需求并入已有 Y）

边界匹配检查，分 边界内／边界扩展／退回上游／宿主误匹配 → 业务链关系检测，分 确认／无新增／引擎判定变更／补充／过时 → 变更影响声明，分 无／增量／修订／结构 → 影响面复查。

概要与定义同为一棵树的两个形态，节点编号相同，故变更以节点为粒度落地：X 的新版本大于本任务消费版本时，比对节点版本差，按变更影响声明分型增量写实或重组。

### 4.4 缺口规则

覆盖自查检出缺口，**引擎类**一条通道：用例场景逐一对照**平台引擎**的能力清单，接不住的那些操作 → 记 `[引擎缺口]`；它指向的是引擎能力，不是业务数据，故不挂在任何一棵树上。

缺口生成**引擎类补充原始需求材料**，回原始需求处理，由它加工成引擎能力功能需求条目、归引擎路径。人类裁决「需要」→ 落地；「不要」→ 废弃。**本任务不脑补节点，也不代引擎设计**。

引擎能力对照的判据引 91 号规范 §4.4 的扩展规则，引用数据即平台引擎的能力清单。

> **两条边界**：**业务类缺口不在本任务**——"本批涉及的 WBS 包对照闭合模型，应有而缺失的产品数据"，锚在 P 树，归产品开发视角业务流程任务；**引擎能力使用需求与指标分配不在本任务**——逐业务页面形成能力使用需求、把 FR-BIZ 指标分配到引擎／配置单元并判定覆盖，锚在系统需求框架的枝梢，归系统需求框架设计任务。本任务只出"接不住"这一件事。

## 五、转换流程及检验规则

### 5.1 设计过程（Step 序列）

Step Start 与 Step End 两端由 [91 附录A](91-eos-biz-eng-spec.md) 统一承载，下表一并列出以便看全序列。受理判定按入口检验表特化；下表列定义引 00-doc-conventions §十三。

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|--------|
| Start | 前置校验与路由 | 变更感知 + 入口检测、受理判定、退回优先路由 | 无（AI 自动） | 统一 | 就绪 / 结束 | — |
| 1 | 设计材料加载 | 读待处理节点与其存量定义节点 | 无（AI 自动） | 统一 | 设计材料全景 | — |
| 2 | 反馈处理 | 处理人类修改意见与整体确认 | **有**——对话修改 / 整体确认 | 对话 | 人类反馈落账 | — |
| 3 | 逐级写实 | 场景装配 → 业务文档实现方式 → 表单标签页序列 → 叶定义，四级的界面形态与数据定义逐级落定 | 无（AI 产出，之后对话反馈） | 统一 | 场景标签页 + 窗口标签页方案 + 表单标签页序列 + 功能操作项 | — |
| 4 | 覆盖自查与补充引擎类原始需求 | X 的叶与详细定义逐一对上；用例场景对照平台引擎，接不住的操作生成引擎类补充原始需求材料 | **有**——裁决候选去留 | 对话 | 覆盖自查结论 + 引擎类补充原始需求材料 | — |
| 5 | 写回与落账 | 写回产品数据、推进状态、提交基线 | 无（AI 自动） | 统一 | 状态推进 + 基线 | 职责视角业务流程定义 |
| End | 运行结束输出 | 三区摘要输出 + 人类下一步操作提示 | **有**——查看摘要、对话反馈 | 对话 | 行动清单 | — |

#### 5.1.1 Step 1 · 设计材料加载

读 `可以srb设计` 或 `待补充srb设计` 的节点 + 同 E2E职责／同域存量定义节点 + 平台引擎的能力清单；加载按读取协议。

#### 5.1.2 Step 2 · 反馈处理

人类对话修改／整体确认／线下修订；反馈双轨按 91 号规范 §A.5 记录。

#### 5.1.3 Step 3 · 逐级写实

针对一个 E2E职责节点，自外向内四级写实：

- **场景标签页**：写实该场景的工作区形态——单窗初始态、双击下钻的分屏双窗、持续下钻的层级上限、面包屑导航；场景职责边界照搬 X；
- **窗口标签页**：逐业务文档写封面映射、正文实体结构、数据权限与显示模式；**校验支撑引擎候选**，把 `[推断]` 落定为权威值；
- **表单标签页**：逐任务节点写处理角色、可执行动作、状态变迁，编排页面间流转规则；同一文档的页按任务顺序成序列；
- **功能操作项**：逐用例场景取 X 的叶节点原文，写实形态、触发条件与执行结果，内联稳定标签随叶携带；
- 文档间的流转顺序引擎化为输出文档序列，任务间触发关系引擎化为触发规则；
- 有新增或改进 → 自下而上调树至收敛，判据是覆盖完整 + 兄弟互斥。

#### 5.1.4 Step 4 · 覆盖自查与补充引擎类原始需求

执行关口检查，其中**X 的叶与详细定义逐一对上**是本需求-方案对的关口——X 的每个叶节点都有一个详细定义与之对应，内联稳定标签逐一对上，无遗漏、无重号。

再以用例场景逐一对照平台引擎的能力清单，接不住的操作记 `[引擎缺口]`——它指向的是引擎能力、不是业务数据，故不挂在任何一棵树上。

缺口生成**引擎类补充原始需求材料**交原始需求处理，加工成引擎能力功能需求条目归引擎路径。候选去留由**人类裁决**。

#### 5.1.5 Step 5 · 写回与落账

职责视角业务流程定义落账 + 状态推进 + 基线，引 91 号规范 §A.3.3 与 §A.6。

### 5.2 检验规则

**入口检验，对 X**

| 校验条件 | 判定 | 动作 |
|---------|------|------|
| 节点状态 = `需biz01修订` | 不可处理 | 输出退回记录 → 退出 |
| 节点状态 ≠ `可以srb设计` 且 ≠ `待补充srb设计` | 不可处理 | 输出当前状态 → 退出 |
| 用例场景缺内联稳定标签，或同层重号 | 软限制 | 该节点挂 `[需确认]`，本批其余照常 |
| 业务文档缺封面模式 / 正文实体类型 / 支撑引擎候选 | 退回上游 | 输出缺项清单 → 标 `需biz01修订` → 退出 |
| 用例场景与所属任务节点不同指一个业务对象 | 退回上游 | 输出差异清单 → 标 `需biz01修订` → 退出 |
| 无待处理节点 + 无待反馈 + 无退回 | 无待处理对象 | 输出提示 → 退出 |

读 X 时取处于 `可以srb设计` 或 `待补充srb设计` 的节点，按 E2E职责聚集；按树定位、逐节点展开。加载遵循 91 号规范 §A.3.3 读取协议——处理节点优先、逐节点加载、按需扩大，不默认加载全文。节点状态为 `待补充srb设计` 且 X 版本大于本任务消费版本时，按上游的变更影响声明分型读增量部分。

叶的名称、次序、内联稳定标签由 X 给出，照搬不改；本任务不新增叶，发现应有而未列 → 走补充材料回路，不就地加。R 树的组装权在上游的职责视角业务流程任务：干枝、场景职责边界、封面模式、正文实体类型、支撑引擎候选，都由它制定并执行，**本任务不重长 R 侧干枝、不重定边界**。挂起的节点不算退回，下一轮重试。

**关口，对 Y**

- **叶与详细定义的对上检查**：X 的每个叶节点都有且只有一个详细定义与之对应，内联稳定标签一一对齐——这是本任务深化是否完整的判据，缺一个就说明有叶没拿到定义。
- **覆盖检查**，这是本需求-方案对的关口：**节点累计承接的**全部需求语义 ⊆ 其叶定义之并。同一节点的需求分多批到来，故检查范围累计——每批检新增部分；本批改动了已有干枝，另按影响面复查其下已写实的部分。EOS 实例化 = **界面闭合检查**——每个用例场景落在至少一个功能操作项上、每个任务节点落在至少一张表单标签页上、每张业务文档落在至少一个窗口标签页上、每个场景落在至少一页场景标签页上。缺口 → 以用例场景对照平台引擎生成引擎类补充原始需求材料 → 经原始需求处理补回，**不脑补节点**。
- **要素机械检查**：逐文档要素非空或合理空置 + 标注齐备，含 `[推断]`／`[待下游推断]`。
- **写实边界检查**：未越界定义组件规格与系统需求；功能操作项与用例场景一一对应，未并项、未拆项。
- **治理覆盖检查**：预置治理业务流程按角色预定文档集核对；无需求锚点的缺口标 `[治理缺口]`，提示人类渐进增补，不自动补。

### 5.3 状态推进与退回

```
待确认方案 ──人类确认──→ 可以srb设计 ──下游锁定──→ 在srb设计 ──下游完成──→ 已srb设计
     ↑                       ↑                      │
     │                       │          下游退回     │
     └── 本任务修订 ──── 需biz01cr修订 ←───────────────┘
```

上游变更，即概要汇入新版本，按状态分流：`可以srb设计`→版本递增，未消费；`在srb设计`→版本递增，增量处理；`已srb设计`→`待补充srb设计`→本任务补全。

反向一侧：X 的缺陷 → 节点标 `需biz01修订`，退职责视角业务流程任务；Y 被下游退回 → 本任务修订。

本任务的六态映射——`待确认方案`／`可以srb设计`／`在srb设计`／`已srb设计`／`待补充srb设计`／`需biz01cr修订`，节点生命周期与上游变更分流引 91 号规范 §A.6。

### 5.4 运行时特化参数

- **锚点需求** = 节点累计承接的全部业务功能需求条目，跨批追加
- **操作条目** = 场景装配 + 业务文档实现方式段 + 表单标签页序列 + 功能操作项 + 补充原始需求材料候选
- **推进目标** = `可以srb设计`
- **退回节点状态值** = `需biz01cr修订`，退回修订走修订转换
- **清除与级联条件**由状态机与上游分流定
- 其余运行时机制——Step Start／Step End、入口条件与优先级、反馈双轨状态机、git 基线、Step End 三区模板——按 91 号规范 附录A 执行；本任务的入口检验已就地成文

## 七、收尾

### 7.1 AI 标记约定

`[新增]`/`[变更]`/`[确认]`/`[需裁决]` + `[推断]`/`[待下游推断]`/`供人类确认`——标记的定义与使用、三区输出格式见 91 号规范 §A.3.1／§A.3.2；本任务增量清单对操作条目逐条标注；并附覆盖自查结论行。

### 7.2 自检清单

本任务自检——一次运行收尾前，按本任务流程分组逐项核对：

- **入口/受理**：入口检验已校验通过；退回优先，`需biz01修订` 时读缺失说明并退回上游；无待处理已退出。
- **载入与校验**：待处理节点 + 同 E2E职责／域存量定义节点已按 91 号规范 §A.3.3 加载、不全载全文；用例场景的内联稳定标签齐备且唯一。
- **写实**：四级写实完成——场景装配、业务文档实现方式、表单标签页序列、功能操作项；叶的名称与次序照搬 X，未新增、未改名、未重排；支撑引擎权威值已落定，未留全量 `[推断]`。
- **关口**：叶与详细定义的对上检查、覆盖检查已执行，后者检的是节点累计承接的全部需求语义，实例化为界面闭合；缺口以用例场景对照平台引擎产出补充原始需求材料交原始需求处理，候选去留有人类裁决，**不脑补节点**；治理覆盖已核对。
- **边界**：未越界定义组件规格与系统需求；未代引擎设计；业务类缺口与引擎能力指标分配均未越位。
- **写回**：R 树写进职责视角业务流程定义，状态推进 `可以srb设计`、X 的节点状态回写、AI 最近变更/可处理节点分节维护、基线提交。
