## 一、目的与目标

### 1.1 本任务在对/链上的位置

```
对①： X = 01 相关方需求（完整态）
        │  阶段一 biz01（承接设计）——产出 Y 概要 02（不含叶：场景枝→文档枝梢 + 分解源判据）
        ▼
      02 概要（业务流程概要）
        │  阶段二 本任务 biz02（分解/落叶）——按分解源判据把枝梢定义成完整态叶
        ▼
      04 = Y 完整态（业务流程方案，含叶）──(= 对② 的 X)──▶ biz03（对② 阶段一）→ 05 系统需求概要
```

- 本任务 = 对① 的**阶段二**：**不是新的"对"**，而是把同一份 Y（业务流程）从概要（02）完成到完整态（04）。
- 承接记录在阶段一已完成：01 的需求叶已落到 02 的场景/文档（承接判据），本任务不再承接新需求——它把"已承接的语义"**实现化**为叶定义。
- 人类门禁位置：本任务落叶/定义完成 → 人类"整体确认" → bpd-biz → `可以srh设计`（=04 完整态就绪，可作 对② 的 X）。
- 下游退回（biz03 检出缺陷 → `需biz02修订`）= 本对**完整态与下一对之间的反向迭代**；02 概要缺陷 → 退回 biz01（对内的反向迭代，见 §2.4）。

### 1.2 主要目的

取信于业务方——「你给出的业务方案是对的」。把 02 概要的业务语言（已承接的需求语义 + 分解源判据预告）落实为 04 的**架构语言**（引擎校验值、封面/正文结构、活动/条目叶定义、任务关系引擎化、A2 表单编排），为对②（biz03 转译功能表单/窗口标签页）提供可展开的完整态输入。

### 1.3 目标

1. **还原承接语义**：从 02 的承接记录与分解源判据还原每个枝梢"承接了什么需求、将分解成哪些叶"。
2. **校验引擎权威值**：在 04 上下文校验 biz01 的引擎候选（确认/修正/推翻）——引擎权威落在 bpd-biz 校验值，对② 消费以此为准。
3. **补全枝梢定义**：每个 PL5 文档枝梢——正式文档：封面 DocumentCover 映射 + 正文实体结构 + 支撑引擎 + 支持信息引用；轻量文档：正文实体结构 + 支撑引擎 + 支持信息引用。
4. **定义活动叶（PL6-A）**：消费 biz01 的任务类型与主要节点（业务语言）→ 映射引擎 CU（计划/流程/工单）；补系统自动节点/异常路径/超时。全量 `[推断]`。
5. **定义条目叶（PL6-B）**：先判正文集合性，再按三独立逐类判定；满足时定义名称/定义要素/生命周期。轻量原子正文行不展开。
6. **任务关系引擎化**：把 02 的任务关系转成引擎触发规则配置。
7. **A2 编排与覆盖**：落 SL3~SL5 角色场景 + 表单使用顺序；对每个枝梢做覆盖检查（承接语义 ⊆ 其叶定义之并），检出设计性缺口 → 补充材料回路。

### 1.4 本任务负责 / 不负责

**负责**：把 02 概要落叶成 04 完整态（A2+Bn 双视角）；引擎权威校验；文档/叶定义；覆盖检查与设计性缺口回路；人类确认后写回 23/24/27/28 与推进状态；处理下游退回（反向迭代）。

**不负责（路由指向）**：
- 引擎路径/平台能力（FR-ENG）→ `wft02-eng`；非功能（NFR）→ `wft04-nfr`
- **Bn 组装**（PL4 WBS 归组 / 23 一致性 / 结构性缺口推断）→ 已由 `biz01`（对① 阶段一）完成，本任务只消费不重做
- 结构性缺口定义（缺口文档的业务身份/链上定位）→ 须回 biz01/需求确认（§四.4）
- 对② 转译（功能表单/窗口标签页/字段级建模）→ `biz03`
- 业务人员确认 → 人类线下

> **ch2 输入两类语义（93 §三.2 已定案）**：本任务属**落叶型**——X=02 本对概要（对内中间形态），任务是落叶/实现化；对照**承接型**（X=上一对完整态，如 biz01 的 01、biz03 的 04）。更上游文档（01）只作覆盖锚点，不作 ch2 文档。

本任务运行时的**主处理对象** = X 中处于 `可以分解分配`/`待补充分解分配` 的 02 场景业务节点（业务链枝梢 + 分解源判据）。

## 三、输出文档结构及规则（Y = 04 业务流程方案 · 生产侧）

### 3.1 本任务产出的产品数据

本任务产出 **Y = 业务流程** 的**完整态（04）**——在 02 概要骨架上，把每个枝梢（PL5 文档）分解/定义为"叶已具"的方案。04 = 对① 完整态 = **对② 的 X**（biz03 输入）。叶 = PL6 活动节点（活动语义/状态变迁）与正文条目（名称/定义要素/生命周期）；枝梢属性补全 = 封面映射/正文结构/引擎权威值/权限。

### 3.2 04 的结构要点（schema 引用，不重述）

04 完整结构单源 = [91 规范 §11](../../91-eos-biz-eng-spec.md) + 04 数据文件自身；bpd-biz 资产与双文档结构特例见 91 §11 与 04 数据文件自身，不破通用规范特例。本任务产出节点类型 = **业务流程方案节点（bpd-biz-XXX）**，一个 bpd-biz 对应一个场景（同产品路径 + 用户角色归组）。

### 3.3 节点类型与结构知识（= Y 完整态的两视角 + 树坐标）

> 树坐标：04 = 02 概要 + **叶**。A2 侧：SL3 角色类型→SL4 角色职责→SL5 场景业务（末级枝干）→（SL6 功能表单属对②，非本任务）；Bn 侧：PL3 构件类型→PL4 WBS→**PL5 输出文档（枝梢）→ PL6-A/B（叶，本任务定义）**。两视角经"输出文档→功能表单"交汇（对② 实现）。

### 3.4 Y 侧规则（构建与收敛）

### 3.5 要素清单（写入 04 节点必须带齐）

| 任务关系 | 业务触发 → 引擎触发规则（触发条件/启动参数；可任意类型互相触发） | 91 §2.6 |
| A2 表单使用顺序 | 场景边界内 功能表单/主子表单 序列 + 依赖 | 91 §2.2 |
| 对齐判定 | 输出文档 → 23B/24/27/28 的 Q1/Q2/Q3（对齐判据之家待裁，引 23/91 §5.3） | §六 |

### 4.3 修订转换（Phase B / 上游变更）

- 新 02 枝梢/变更汇入 → 关系检测（确认/补充/矛盾/无新增）→ 增量落叶 → 变更影响声明（04 → 对②）。
- biz01 变更传播协议声明"修订型/结构型"时，本任务按声明范围增量/重组 04 节点。

### 4.4 边界：结构性缺口 vs 设计性缺口

- **结构性缺口**（构件产品数据清单缺文档）已由 biz01 处理——缺口文档的**业务身份**（链上位置/场景职责/前后序）只能在 02 层定，本任务不自行定义（否则断追溯链）；须回 biz01/需求确认后本任务才能设计该文档。
- **设计性缺口**（PL6-B/指标/活动节点级）由本任务检出 → 汇聚生成补充原始需求材料 → 经预处理链回 01 确认（人类确认 = 发起补充需求的签字，不绕过管道）。

## 五、转换流程及检验规则

### 5.1 设计过程（动作序列）

一次运行 = **入口 → 载 X(02) 与存量 Y(04) → 反馈处理 → 落叶循环 → 覆盖/完备检查 → 人类确认 → 推进 → 写回**：

1. **入口**：受理门槛（2.3）判定；退回优先（`需biz02修订` → 读缺失说明修订）；反馈；路由新 02 节点。
2. **载 X 与存量 Y**：02 场景节点 + 同路径同角色已有 04 节点（匹配/收敛）+ 01 锚点需求 + 23/24/25/27/28 资产。
3. **反馈处理**：对话/线下双轨（引 91 §A.5）。
4. **落叶循环**（对一组枝梢/节点）：
   - A2 装配（SL3~SL5 + 需求到文档分配 + 表单使用顺序）→ Bn 详设（文档方案 → 引擎校验 → 活动叶 → 条目叶 → 关系 → 权限）——两视角同落到 04；
   - 每个分解源判据展开项 → 对应叶定义，标签对上；
   - 影响面复查（若改既有 04 节点/叶）。
5. **覆盖/完备检查**（5.2 关口）。
6. **人类确认** → bpd-biz 推进 `可以srh设计`；02 场景 → `已分解分配`。
7. **写回与落账**（23/24/27/28 + 状态 + 基线；引 91 §A.3.3/§A.6）。

### 5.2 检验规则（关口）

- **覆盖检查**（本对实现层关口）：02 每个枝梢承接的需求语义 ⊆ 04 该枝梢叶定义之并——落实为"被承接的文档/预告的叶都在 04 被定义且语义覆盖"。缺口 → 设计性缺口回路（§四.4）/退回 biz01（若根因在 02 概要）。
- **单承接重检**：01 需求叶已在 02 单点承接；本任务落叶时发现某需求被多个文档实现且互不归属 → 标 `[需裁决]`。
- **要素机械检查**：3.5 要素齐备/合理空置；标注纪律（`[推断]`/`[待下游推断]`/`供人类确认`）。
- **追溯检查**：每正式文档可追溯 04→02 枝梢→01 需求。

### 5.3 状态推进与退回

```
bph-biz(02)： 可以分解分配 ──本任务锁定──→ 在分解分配 ──本任务完成──→ 已分解分配
bpd-biz(04)： 待确认方案 ──人类确认──→ 可以srh设计（=04 完整态就绪→对②可进入）
  上游变更（02 汇入）：可以srh设计→版本递增（未消费）/ 对② 消费后→待补充…（引 91 §A.6）
  下游退回：biz03 检出缺陷 → 需biz02修订 → 本任务修订 → 可以srh设计
```

（四态模型与写回范围引 91 §A.6，此处为本任务特化。）

### 5.4 运行时外壳（引 91 附录A，不重述）

Step Start/1~6/End、反馈双轨状态机、git 基线、Step End 三区 = 91 附录A 统一协议；本任务只保留特化参数（锚点 = 02 所承接的 01 需求 + 分解源判据；操作条目 = A2 场景/文档方案/叶定义；推进目标 = `可以srh设计`；级联/清除条件见 §5.3 状态机与上游分流，会话级清除引 91 §A.6）。
