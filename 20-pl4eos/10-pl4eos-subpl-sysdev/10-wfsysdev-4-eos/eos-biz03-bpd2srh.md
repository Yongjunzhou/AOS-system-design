## 一、目的与目标

### 1.1 本任务在对/链上的位置

```
需求-方案对①：01 需求 ──biz01──▶ 02 概要 ──biz02──▶ 04 完整态，业务流程
需求-方案对②：04，即需求-方案对① 完整态、也是本任务 X ──biz03 承接设计──▶ 05 系统需求概要，末级为 ⑤ 用例场景功能
        │  阶段二 移交：构件开发流水线把枝梢分解为构件/组件叶，即需求-方案对② Y 完整态
        ▼
      构件开发流水线，含 wft05-eng 消费 FR-BIZ 指标约束包
```

- 本任务 = **需求-方案对② 阶段一**：输入是**上一份完整态 04**，也就是跨需求-方案对取得的需求——"上一份完整态 = 下一份需求"的典型实例，见 20 号 §5.2／§4.3。
- 承接方式 = **承接 + 转译**：**承接源只取 04 的叶**，即活动节点/正文条目，认定依据是 [94 §1.2](94-eos-sys-dev-dbs.md) 依据三；落到 05 的枝梢，即 **⑤ 用例场景功能**。04 的**输出文档即枝梢 → 功能表单**是**页面视角的转译**、不是承接。
- **路径止点**：biz 路径止于本任务的 05 概要，枝梢＝**⑤ 用例场景功能**，携带**分解源判据**，即能分解出哪些构件/组件；阶段二把枝梢分解为叶即组件规格，由开发线执行——20 号 §5.4 的移交形态。**设计线链尾是需求-方案对③**，即 06→07，不是本任务，见 93 §4.3。
- 人类门禁：本任务 05 节点 → 人类"整体确认" → `可构件开发` → 开发线可进入。
- 退回：开发线检出缺陷 → `需biz03修订`；根因在 04 → `需biz02修订`。这是需求-方案对② 与需求-方案对① 的反向迭代。

### 1.2 主要目的

产出可交付构件开发的业务侧页面组件需求——证明 **04 即需求-方案对② 的需求，已被 05 的枝梢即 ⑤ 用例场景功能、及其页面视角制品即功能表单/窗口标签页完整承接**，这就是覆盖自查；并把 FR-BIZ 性能指标分配到支撑引擎或 CU 能力，对能力或指标缺口生成 FR-ENG 候选线索交 eng 路径。从 EOS 视角 = 业务配置需求；从配置业务系统视角 = 配置业务系统的产品概要末级，biz 不入 07。

### 1.3 目标

1. **还原承接语义**：从 04 读取每个输出文档即枝梢 + 活动/正文条目即叶 + 引擎权威值 + 任务关系——它们即本任务要转译承接的源。
2. **转译成 05 枝梢**：每个输出文档 → 实体需求 + 正文功能表单，并作 PL6-B 条目转化；活动叶 → 窗口标签页序列；任务关系与引用 → 触发规则与引用规则。
3. **编排三层页面**：菜单标签页 → 场景标签页即场景编排 → 窗口标签页即功能表单的承载者。这就是 05 概要的编排内容。
4. **引擎能力使用与指标分配**：逐页面形成能力使用需求，FR-BIZ 指标分配到既有引擎/CU 并判定覆盖；缺口 → FR-ENG 候选线索。biz 不设计 CU。
5. **覆盖自查**：证明 04 被 05 完整承接——承接了的一定被转译到功能表单或页面。
6. **止点判据**：每个枝梢即 ⑤ 用例场景功能写分解源判据，即将分解出的构件/组件类型，供开发线阶段二落叶。

### 1.4 本任务负责 / 不负责

**负责**：转译 04 → 05 概要，内容含 实体／功能表单／窗口标签页／任务关系与引用／引擎能力与指标分配；三层页面编排；覆盖自查；FR-ENG 候选线索；人类确认后推进 `可构件开发` 与写回；处理退回，根因分流到 04 或开发线。

**不负责，均指向其实际归属**：
- 引擎路径/平台能力即 FR-ENG，以及 CU 设计 → eng 路径 `wft03-eng`／`wft01-eng`／`wft02-eng`；NFR → `wft04-nfr`
- **pa-eng 组件设计、CU 设计** → `wft05-eng`；需求-方案对② 阶段二若属平台能力，走 eng 的 pa
- 实例配置与技术实现参数、功能表单的构件分解，即阶段二 → **构件开发流水线**
- 25/28/24 资产写回 → 仅只读参照；24 改进/新建建议全量 `[推断]`+`[需裁决]` 由 biz02 详设层写回
- 在 07 重复定义或另行命名 → biz 终止于本任务

## 三、输出文档结构及规则（Y = 05 系统需求概要 · 生产侧 · 链尾）

### 3.2 05 的结构要点（schema 引用，不重述）

05 完整结构单源 = [91 规范 §11](../../91-eos-biz-eng-spec.md) + 05/06 数据文件自身。本任务产出 srh-biz 节点 `srh-biz-XXX`，要素含：功能表单定义，双重构成为表单 + 功能；主子组装关系；三层页面编排；引擎能力使用需求；FR-BIZ 指标分配；FR-ENG 候选线索；覆盖自查结论。

### 3.3 节点类型与结构知识（= Y 概要 + 链尾判据）

> 树坐标：05 概要 = 不含叶的树；**末级枝梢 = ⑤ 用例场景功能**，见 [94 §2.3.1](94-eos-sys-dev-dbs.md)。**功能表单不属于本树**——它是「用户操作页面视角」对系统用例功能的聚合，见 [91 §7.3](91-eos-biz-eng-spec.md) 与 05 数据文件 §0.2；窗口标签页是功能表单的页面组件承载形式，分 列表／单据／图示 模式。枝梢之下在完整态将由开发线分解为构件/组件叶。**枝梢双向物理意义**：①承接判据——承接 04 的哪些叶，即活动节点/正文条目；②分解源判据——将被开发线分解成哪些构件/组件，这是移交接口。

- **功能表单，属页面视角制品，有双重身份**：EOS 业务配置需求 + 配置业务系统的产品概要末级——biz 不入 07，即 eng 的 pa。
- **实体与功能表单**：输出文档 → 正文功能表单；正式文档还含封面表单 + 1:1 主子；层级引用 → 1+N 下钻。
- **窗口标签页序列**：由 04 的 PL6-A 活动叶编排，体现流转规则与节点交互差异。
- **引擎能力使用需求 / 指标分配**：页面 → 引擎/CU 能力；覆盖不足 → FR-ENG 候选线索。

### 3.4 Y 侧规则（构建与收敛）

- **转译构建**：04 每个输出文档、活动、条目都被转译到至少一个功能表单或页面，无遗漏——覆盖自查是 05 构建的收敛判据。
- 三层页面编排，即 菜单→场景→窗口，作为 05 概要的编排骨架；功能表单挂到场景或窗口下。
- CU 仅作能力参照，不是本任务的设计产物；能力缺口交 eng 或 FR-ENG 候选。
- **止点收敛**：05 概要止于枝梢，即 ⑤ 用例场景功能，加分解源判据；叶即组件规格不在本任务——若本任务试图定义组件规格即越界，那是开发线或 eng pa 的事。

### 3.5 要素清单（写入 05 节点必须带齐）

- 菜单树方案，含层级 + 末级→场景业务映射；场景业务方案，含功能表单序列／显示顺序／依赖。
- 输出文档实体需求，含封面/正文实体字段；正文功能表单，含字段布局／交互／展示／FR-BIZ 指标；主子组装关系。
- 流程类需求，即 PL6-A → 窗口标签页序列 + 流转规则；任务关系与引用需求；支持信息引用。
- 引擎能力使用需求 + FR-BIZ 指标分配与覆盖结论 + FR-ENG 候选线索，按需。
- 每个枝梢即 ⑤ 用例场景功能的**承接判据 + 分解源判据**，这是给开发线的移交接口；覆盖自查结论；版本/状态。

### 3.6 传出承诺（给构件开发流水线 = 需求-方案对② 阶段二执行者）

本任务把 05 节点交给开发线时，承诺节点达到：

1. 状态 = `可构件开发`，在人类"整体确认"之后；
2. 要素清单见 3.5，齐备——功能表单／页面／能力／指标／编排已定义；
3. 覆盖自查结论落账——04 即需求-方案对① 完整态已被 05 功能表单完整承接，无"承接了但没转译"；
4. 每个枝梢即 ⑤ 用例场景功能带**分解源判据**——开发线按它把枝梢分解为构件需求/组件规格，即阶段二。

> **接口契约，链尾对侧在开发线**：开发线首 skill 即构件需求定义，受理本任务传出的 05 时将以 3.5/3.6 为对照；其受理前提对侧在开发线规范里。这正是 20 号 §5.4"链尾只移交阶段二、不需再造一份开发需求"的形态。

### 4.1 转换本质：转译承接（上一份完整态 → 本需求-方案对的概要）

### 4.3 修订转换（04 上游变更 / 开发线退回）

- 04 版本大于消费版本 → 按 biz02 变更影响声明分型，分 无／增量／修订／结构，增量或重组 05。

- 开发线退回 `需biz03修订` → 本任务修订；缺失根因在 04，如 PL6 定义缺失 → 转退 biz02。

### 4.4 链尾边界

- 功能表单分解成构件/组件 = 开发线阶段二；本任务只写分解源判据，不定义组件规格。

## 五、转换流程及检验规则

### 5.1 设计过程（动作序列）

一次运行 = **入口 → 载 X 即 04 与存量 Y 即 05 → 反馈处理 → 转译循环 → 覆盖自查 → 人类确认 → 推进 → 写回**：

1. **入口**：受理门槛判定，见 2.3；退回优先，`需biz03修订` 时读缺失说明、根因分流；反馈；路由新 04 节点。
2. **载 X 与存量 Y**：04 节点，含变更声明与消费版本；加已有 srh-biz 节点，用于匹配；加 25 引擎参照 + 约束包状态。
3. **反馈处理**：对话与线下双轨，引 91 §A.5。
4. **转译循环**——针对一组文档或活动：实体与正文功能表单 → 窗口标签页 → 三层编排 → 任务关系与引用 → 引擎能力与指标分配，作覆盖判定 → FR-ENG 候选线索，缺口时。每个 04 对象落到 05 枝梢并写承接判据与分解源判据。
5. **覆盖自查**，见 5.2 的关口。
6. **人类确认** → srh-biz 推进 `可构件开发`；bpd-biz 消费状态 → `已srh设计`。
7. **写回与落账**：05/06 + 状态 + 基线，引 91 §A.3.3／§A.6。

### 5.2 检验规则（关口）

- **覆盖检查**，这是本需求-方案对的承接层关口：04 的全部对象——文档／活动／条目——⊆ 05 功能表单/页面之并，落实为"04 已被功能表单和窗口标签页完整承接"。缺口 → 引擎能力缺口走 FR-ENG 候选、指标缺口走约束包；**不脑补页面**。
- **可转译性校验**：04 缺 IPO/引擎支撑信息 → `分解依据不足` 退回，见 §4.3。
- **要素机械检查**：3.5 齐备/合理空置；标注纪律。
- **链尾边界检查**：本任务未越界定义组件规格/未在 07 重复命名。

### 5.3 状态推进与退回

```
srh-biz 05： 待确认方案 ──人类确认──→ 可构件开发 ──开发线锁定──→ 在构件需求定义 ──完成──→ 已构件需求定义
bpd-biz 04： 可以srh设计 ──本任务锁定──→ 在srh设计 ──完成──→ 已srh设计，即消费版本与需求-方案对齐
  上游变更：bpd-biz 新版本 → 04 状态 `待补充srh设计` → 按变更声明增量/重组
  退回：开发线 → 需biz03修订；根因在 04 → 转 需biz02修订
```

四态与写回范围引 91 §A.6，本任务特化。

### 5.4 运行时外壳（引 91 附录A，不重述）

Step Start / 1~8 / End、反馈双轨状态机、git 基线、Step End 三区 = 91 附录A；本任务只保留特化参数——锚点 = 04 承接的语义 + 覆盖基线；操作条目 = 功能表单／窗口标签页／能力指标；推进目标 = `可构件开发`。级联与清除见 §5.3 状态机与上游分流，会话级清除引 91 §A.6。
