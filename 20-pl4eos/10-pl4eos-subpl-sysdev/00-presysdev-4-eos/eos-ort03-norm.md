## 二、规范化设计基础

**一句话**：本章讲本步的产出（OR 基线文档）结构、状态怎么追踪、反馈怎么检测与处理、入口规则和工程化原则；**怎么拆分/判定类型见 §2.4 拆分与类型判定规则**。

### 2.1 OR 基线文档结构

**一句话**：本步的产出是 OR 基线文档 `01-eos-original-requirements.md`（权威产出，两区结构：管理区 + 正文区），是三个 wft01 的唯一需求输入。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| 管理区 | OR 基线条目进展状态及处理建议一览表 | 从状态文档表 C 推导写入，展示父子行结构：源文件父行 + OR 条目子行 |
| 正文区 | 方案期为 `#role-list` + 来源原文 + 分析建议块 + 反馈区；确认后增加正式 OR 节点块 | 分析建议用于确认和来源证据；正式 OR 节点块是三个 wft01 的唯一需求输入 |

正文区结构：

```text
### 角色预汇总 `#role-list`

### {切分文件名} `#body-{seq}`
  源文件标识 / 状态
  原文内容
  ╔═ 分析建议块 ═...
  反馈区
```

正文区锚点：`#body-{seq}`。历史版本由 Git 管理，不在文档内归档旧版。

### 2.2 文档生命周期管理

**一句话**：本步通过状态文档推进规范化生命周期——表 B 控制切分文件是否进入规范化，表 C 追踪每条 OR 基线条目状态；反馈靠状态条件扫描直接检测与处理（无需 git diff）。

#### 状态模型（状态怎么追踪）

本步使用状态文档两张表：

| 表 | 粒度 | 本步职责 |
|----|------|---------|
| 表 B — 切分文件处理进度 | 切分文件级 | 控制切分文件是否进入规范化；生成方案后置 `待确认规范方案`；确认后置 `已规范化` |
| 表 C — OR 基线条目处理进度 | OR 条目级 | 人类确认后追加 OR 条目父子行，作为 OR 当前状态权威源 |

> **frontmatter.status 口径**：方案期（`待确认规范方案`）本步不写 status，保持 `clarified`；确认执行后置 `normalized`；终止置 `abandoned`。status 值域全链权威定义见 ort01 §2.2.2。

表 C OR 条目状态机：

| 状态 | 含义 | 设定者 |
|------|------|--------|
| 待处理 | ort03 已写入 OR 基线，等待人类选入 wft01-biz / wft01-eng / wft01-nfr | ort03 |
| 待确认方案 | wft01 已生成 STR 方案，等待人类确认；或上游资产变更触发回退 | wft01 |
| 已分配 | OR 已承接到 STR 节点 | wft01 |
| 验证中 | OR 承接链进入追溯验证 | t06 |
| 已验证冻结 | 全链验证通过 | t06 |
| 已废弃 | OR 被废弃 | 本步或下游 |

**同步契约**：先更新表 B / 表 C 权威源，再推导更新文档内嵌状态摘要表和 OR 基线管理区。若不一致，以状态文档为准。写回前检测表 B/表 C 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类。

#### 反馈机制（反馈怎么检测与处理）

**反馈检测（状态条件）**：ort03 的反馈载体即 OR 基线正文区（反馈区标记 + `#role-list` 操作反馈）与表 B/C（`人类决策`），AI 通过状态条件扫描直接发现并处理（状态自终止——处理后反馈区清理、状态转迁，条件不再成立，无需 `[已处理]` 记录分离）：

| OR 基线 / 表 B/C 状态条件 | 判读 | 处理 |
|------------------------|------|------|
| 反馈区有 `[同意执行]` | 同意 | 编号生成正式 OR 节点 → 表 C 追加 → 23/26 写回 → 表 B 已规范化 |
| 反馈区有 `[修改建议]` | 修改 | 解析意见 → 调整条目/字段 → 重检重匹配 → 重写分析建议块（表 B 保持待确认） |
| 反馈区有 `[废弃]` | 废弃 | 表 B → `已废弃`、status → `abandoned`，聚合排除 |
| `#role-list` 有 `[确认]`/`[修改]`/`[新增]`/`[删除]` | 角色操作 | 按操作更新角色清单并同步分析建议块 |

> 表 B `人类决策=同意规范化`、表 C `人类决策=同意分配` 为**选入/入口条件**（非反馈），分别见 §2.3 入口硬条件与 §2.7 wft01 入口契约。

**基线协议（链级不变式）**：每次运行结束 Step 7 用 `scripts/ai-commit.sh` 提交基线（author=EOS-AI + `[AI]` 前缀），并把新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段。ort03 自身检测用状态扫描、不读基线；提交的目的是把 ort03 的产出（OR 基线 + 23/26 资产 + 表 B/C 写入）落基线，为下游 git diff 步骤保持「diff 只含人类变更」的不变式。

### 2.3 入口与重进入规则

**一句话**：本步只处理人类在表 B 明确选入（`同意规范化`）且已澄清的切分文件；先处理已有反馈的方案，再处理新选入的。

Step 3 新增处理入口硬条件：

| 条件 | 说明 |
|------|------|
| 表 B `生命周期=已澄清` | 上游 ort02 已完成澄清 |
| 表 B `人类决策=同意规范化` | 人类明确选入本批规范化 |

`AI建议=可以规范化` 仅作为候选提示，不作为入口硬条件。

运行路由参考 `wft01-biz`：前置校验和 Step 1 资产加载完成后，**先处理表 B `生命周期=待确认规范方案` 的反馈/重入（Step 2），再处理 `生命周期=已澄清` + `人类决策=同意规范化` 的新增材料（Step 3）**。ort03 的新增处理入口落在 Step 3，是因为 Step 1 专门承担 OR 层资产加载、Step 2 优先处理反馈；语义上等价于 ort01/ort02 的新增入口。

资产前置分两级：23/26 用于业务和文档候选匹配；22 仅用于给 NFR OR 附加候选检索线索。三者缺失均不阻断 OR 规范化——23/26 缺失时对应匹配写 `候选线索=不可用`，22 缺失时写 `22 候选线索=不可用`，由下游 wft01/wft02 运行时处理；规范化核心（四单一拆分/类型判定/冲突检测）不依赖资产。

方案反馈分支（反馈条件→处理以 §2.2 反馈检测表为单源，本表只列入口路由与边界行）：

| 条件 | 处理 |
|------|------|
| 表 B `生命周期=待确认规范方案` + 正文区有分析建议块 + `[同意执行]` / `[修改建议]` / `[废弃]` / `#role-list` 操作反馈 | 按 §2.2 反馈检测表执行 |
| 有分析建议块 + 无反馈 | 跳过，等待人类 |
| 表 B `生命周期=待确认规范方案` 且 OR 基线正文区无分析建议块 | 数据不一致：提示人类核对，并按「修改建议」路径重新生成分析建议块（表 B 保持待确认） |
| 表 B `生命周期=已规范化` | 默认跳过；若正文区有反馈或 last_size 变化，进入重入变更检测 |

重入变更检测：

| 检测方法 | 说明 | 处理 |
|---------|------|------|
| 反馈文本检测 | 无论正文大小是否变化，优先检查反馈区是否新增 `[修改建议]` / `[废弃]` 等反馈 | 有反馈则按 Step 2 反馈分支执行 |
| last_size 对比 | 读取 OR 基线正文区当前字节数，与表 B `last_size` 比较 | 不一致且无明确反馈时，标记“疑似人工改动”，进入待确认重审 |
| 分析建议块字段变更 | 产品/组部件/文档/NFR 字段被改动 | 触发 Step 5/6 重新匹配，并刷新 23/26 匹配结果及 22 候选线索段 |
| 表 C 人类决策变化 | OR 从空变为 `同意分配`，或撤销/改变分配 | 按 OR 类型加入或移出对应 wft01 的 `AI可以处理节点` 分节，不改写 OR 语义 |
| 无变化 | 无反馈且 last_size 一致 | 跳过 |

检测优先级：有反馈文本 > 分析建议块字段变更 > last_size 变化 > 无变化跳过。last_size 一致不代表语义无变化，只有反馈文本才驱动确认后的写回动作。

### 2.4 拆分与类型判定规则

**一句话**：拆分就是把一条需求切成多条可独立确认的 OR——按四个"单一"原则判断，再判定类型（FR-BIZ/FR-ENG/NFR）。

四单一原则：

| 原则 | 检查问题 | 操作 |
|------|----------|------|
| 单一角色 | 是否涉及多个用户角色/相关方角色 | 拆到每条仅涉及一个角色 |
| 单一语义 | 是否描述多个独立功能、约束或关注点 | 拆到每条仅含一个独立语义 |
| 单一路径 | 是否混合 FR-BIZ / FR-ENG / NFR | 拆为不同类型条目 |
| 单一可确认性 | 是否可被相关方独立确认 | 不可独立确认则继续拆分或标记待确认 |

类型判定：

| 类型 | 判定 |
|------|------|
| FR-BIZ | 面向业务角色的业务能力诉求，不直接描述平台引擎能力配置 |
| FR-ENG | 角色为业务定义配置人员，且原文描述引擎/驱动/机制/配置页面/流程规则配置等引擎能力想象 |
| NFR | 性能、安全、可用性、合规、审计、数据保留等非功能约束 |

FR-ENG 引擎拆分：若一条 FR-ENG 涉及多个业务引擎，参考 25 平台引擎资产按引擎拆为多条；25 不可用或边界模糊时标注 `[推断]`，列候选引擎供人类裁决。

拆分纪律：

1. **不做合并**：本步只拆分，不把多个原始诉求合并成一个“更漂亮”的 OR
2. **保留原始出处**：每条 OR 记录提出方、原始表述、日期、源切分文件
3. **超额拆分优于不足**：遇到语义边界不确定时，倾向于拆细并标注待确认
4. **无法拆分标记待补全**：原文不完整、角色缺失或边界无法判定时，不强行规范化
5. **FR-BIZ 保持业务能力语义**：不得把业务能力诉求提前翻译成系统设计方案或引擎实现
6. **FR-ENG 仅处理引擎能力想象**：业务定义配置人员提出的业务结果诉求仍可能是 FR-BIZ，不能仅凭角色一票判定
7. **NFR 不混入 FR 条目**：指标、约束、审计、合规等非功能诉求独立成条

### 2.5 轻量资产标注规则

### 2.7 正式 OR 节点与 wft01 入口契约

**一句话**：方案确认后，每条 OR 必须生成独立正式节点块（91 规范 §11.4 格式），并同步维护元数据/索引/AI最近变更/AI可以处理节点，供三个 wft01 按类型拾取。

分析建议块是人类确认载体，不是 wft01 的正式输入。方案确认后，每条 OR 必须按 [91 规范 §11.4](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#114-节点块) 生成独立节点块：

```markdown
##### @or-001 线索自动分配规则
**业务编号**：OR-001
**类型**：OR.FR-BIZ
**父节点**：@or-source-chunk-001
**输入**：01-市场调研报告.chunk-001.md / 原文定位
**输出**：待对应 wft01 承接
**优先级**：P1
**角色**：销售代表
**业务/平台语境**：销售管理 / 线索分配
**候选资产上下文**：23/26 引用；22 候选线索（仅 NFR）
**原始表述**：...
**规范化表述**：...
**来源定位**：源文件 / 切分文件 / 原文锚点
**当前状态**：待处理
**确认状态**：[同意]
```

写入正式节点时必须同步维护：

1. 文档元数据、自描述索引、业务域/角色组索引和域节点数；未知业务域时进入“待归属 OR”域并标注 `[需裁决]`。
2. `## AI最近变更`，记录 ort03、节点 ID、类型判定和来源。
3. `## AI可以处理节点`：表 C `当前状态=待处理` 且 `人类决策=同意分配` 时，FR-BIZ/FR-ENG/NFR 分别加入“待 wft01-biz/eng/nfr 处理”；未同意分配时不加入。
4. 表 C 增加 `节点ID` 并与 `业务编号` 一一对应；wft01 使用节点 ID 定位正文，用业务编号进行人类沟通。
5. 同一 OR 只能进入一个 wft01 分节；类型变化时先从旧分节移出，再加入新分节。

### 2.8 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步产出的 OR 条目是设计链最高层级需求基线，后续 OR→SR/STR 以此为需求端起点 |

### 3.4 Step 3 · 新增处理

**一句话**：把你选入规范化的已澄清切分文件拆成 OR 条目、判定类型、轻量标注、生成分析建议块，写入 OR 基线正文区等你反馈。

每个切分文件独立一个 `#body-{seq}` 条目。若该条目已存在，直接覆盖写入新版本（历史版本由 Git 管理，不归档旧版）。

```markdown
**源文件**：01-市场调研报告.pdf · **状态**：待确认

```

**2. 生成分析建议块**

执行顺序不可逆：条目拆分 → 类型判定 → 轻量资产标注 → 规范化五项检查 → 冲突检测 → 优先级初判 → 23/26 匹配与 22 候选线索检索。

条目输出字段：

| 字段 | 说明 |
|------|------|
| 临时编号 | `C{切分序号}-{本片内序号}`，如 `C001-001` |
| 标题 | 用一句短语概括单条 OR 的业务/引擎/NFR 诉求 |
| 类型 | `FR-BIZ` / `FR-ENG` / `NFR` |
| 优先级 | `P0` / `P1` / `P2` / `P3` 初判，供人类确认 |
| 角色 | 用户角色或相关方角色，优先使用 `#role-list` 标准名 |
| 产品 / 组部件 / 文档 | 逐条轻量标注，供 Step 5 匹配 |
| 22 候选线索 | 仅 NFR 条目填写，供 wft01-nfr 重新判定；全量标注 `[推断]` |
| 原 / 规 / 出处 | 原始表述、规范化表述、来源信息 |

规范化五项标准：完整性、主体明确、客体可识别、边界可判定、可测试性。残留清晰性问题标为 `待确认`，由人类裁定是否退回 ort02。

冲突检测范围：

| 层 | 范围 | 处理 |
|----|------|------|
| 层 A | 同一切分内 OR 条目间 | 标记并列出双方原文 |
| 层 B | 同原始文件跨切分 OR 条目间 | 标记并列出影响 |
| 层 C | 与 OR 基线中既有 OR 的跨原始文件冲突 | 本步检出并标记双方节点 ID；不做裁决，避免不同 wft01 批次遗漏 |

冲突类型：

| 类型 | 说明 | 处理 |
|------|------|------|
| 直接冲突 | 两条 OR 无法同时满足 | 标记“需确认”，列出双方原文 |
| 间接冲突 | 各自可实现，但同时实现会导致行为不一致 | 标记“需调整”，说明潜在影响 |
| 部分内容冲突 | 一条 OR 的局部内容与另一条冲突 | 优先继续拆分；无法拆分时标记内部冲突 |

AI 不做冲突裁决，只做结构化呈现。
