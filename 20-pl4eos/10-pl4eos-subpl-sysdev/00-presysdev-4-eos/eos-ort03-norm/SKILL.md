## 二、操作流程

### Step Start · 前置校验

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 存在
2. 若状态文档已存在，校验表 B/表 C 表头与字段说明，与状态文档模板不符时按既有口径修正或提示
3. `10-raw-files/` 中存在 `.chunk-*.md`，且存在 `status=clarified` 的切分文件
4. `23-eos-output-architecture.md` 缺失时记录 `23 候选线索不可用`，不阻断规范化（与 26/22 对称）
5. `26-eos-document-definitions.md`、`22-eos-nfr-taxonomy.md` 缺失时记录对应候选线索不可用，不阻断规范化
6. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
7. **表 C 入口同步（优先）**：逐条比较表 C 与 `AI可以处理节点`，将 `当前状态=待处理` + `人类决策=同意分配` 的 OR 按类型加入对应 wft01 分节；状态不再为待处理/撤销同意/类型改变时，从原分节移出。不生成或修改 OR 语义。完成后更新 `AI最近变更`
8. 全部就绪且表 B 有任务 → Step 1；无任务 → Step End

**加载经济原则**：Step 1 用脚本/按需读取加载资产分节与 `#role-list`，不 Read 完整资产文件；22 按需读取一级类目和候选区，不可用即降级记录。

### Step 1 · OR 层资产加载

1. 读取 23 输出产品架构：已确认/疑似产品类型、E2E 项目、构件类型、关联文档
2. 读取 26 文档定义（如存在）：已定义文档清单
3. 按需读取 22 一级类目、分类维度和候选条目（仅 NFR OR 候选线索检索用；不可用记录不阻断）
4. 读取 `01-eos-original-requirements.md` 现有 `#role-list`（如存在）
5. 标记资产加载结果，供 Step 2~6 复用

### Step 2 · 反馈处理

**一句话**：扫 OR 基线反馈区与表 B/C 状态，发现反馈并直接处理——反馈载体即反馈区标记与表 B/C 字段，处理即状态转迁，完成后条件自动失效（无需 `[已处理]` 标记）。

| 反馈 | 处理 |
|------|------|
| `[同意执行]` | 统一分配 `@or-{seq}` 节点 ID 与 `OR-{seq}` 业务编号（跨源文件连续无跳号）→ 按 [人类方案 §2.7](../eos-ort03-norm.md#27-正式-or-节点与-wft01-入口契约) 生成正式 OR 节点块（附录 C）→ 写表 C（追加父子行，OR 初始 `待处理`）→ 更新索引/`AI最近变更`/`AI可以处理节点` → 23/26 同步写回（Q1 引用/Q2 扩展/Q3 新建）→ 22 不写回 → 表 B→`已规范化`、frontmatter.status→`normalized` |
| `[修改建议]` | 解析意见 → 管理区摘要记录调整结论（历史由 Git 管理）→ 调整条目与资产匹配 → 重跑检查及 23/26 匹配、22 线索检索 → 写新版分析建议块 → 表 B 保持 `待确认规范方案` |
| `[废弃]` | 表 B→`已废弃`，frontmatter.status→`abandoned`，正文区标记废弃并追加废弃说明块，Step 4~6 聚合时排除 |
| 无反馈 | 跳过，等待人类 |
| 表 B `生命周期=待确认规范方案` 且 OR 基线无分析建议块 | 数据不一致：提示人类核对，按「修改建议」路径重新生成分析建议块 |

写回前执行附录 B.1 冲突检查。

### Step 3 · 新增处理

读取表 B 中 `生命周期=已澄清` + `人类决策=同意规范化` 的切分文件（详细规则见 [人类方案 §2.4](../eos-ort03-norm.md#24-拆分与类型判定规则)）：

**1. 复制原文到 OR 基线正文区**——每个切分文件独立 `#body-{seq}` 条目；已存在则覆盖写入新版本（历史由 Git 管理）。

**2. 生成分析建议块**——执行顺序不可逆：条目拆分（四单一，附录 A.1）→ 类型判定（§一）→ 轻量资产标注（[人类方案 §2.5](../eos-ort03-norm.md#25-轻量资产标注规则)）→ 规范化五项检查 → 冲突检测 → 优先级初判 → 23/26 匹配与 22 候选线索检索（附录 A.3/A.4）。

**3. 更新状态**——写入分析建议块和反馈区（模板见 [人类方案 §4.1](../eos-ort03-norm.md#41-分析建议块模板)）后，表 B→`生命周期=待确认规范方案`、`AI建议=建议执行`，再推导更新 OR 切分文档状态表。

### Step 4 · 角色资产管理

汇总本轮所有 OR 的角色 → 去重并同义词归并 → `#role-list` 不存在时创建、存在时增量合并 → 分析建议块同义词角色写回为标准名 → 处理 `[确认]/[修改]/[新增]/[删除]` 操作反馈（有变更时追加角色修改记录）。

### Step 5 · 输出产品构成管理

使用 Step 1 已加载的 23/26 基准，逐条判定 23-Q1/Q2/Q3 与 26-Q1/Q2/Q3（附录 A.3），结果写入分析建议块 `### 23 资产匹配结果` 段；不直接写入 23/26，人类确认后由 Step 2 同步写回。

### Step 6 · 非功能候选线索管理

读取全部 NFR 条目的质量诉求原文（不生成系统指标），按 22 分类维度/候选区检索相关线索，全部标注 `[推断]`，写入分析建议块 `### 22 候选线索` 段；不判 Q、不扩展分类、不新增候选、不写回 22（附录 A.4）。

### Step 7 · 提交基线

把本轮 Step 1~6 的处理结果提交为 git 基线。

**为什么需要提交**：ort03 自身检测用状态扫描、不需要基线；但 ort03 的产出（OR 基线 + 23/26 资产 + 表 B/C 写入）若不落基线，会进入下游 git diff 步骤的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B/C、OR 基线、23/26 资产；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段
4. **无变更**：工作区无改动时跳过提交，基线不变

### Step End · 运行结束输出

输出行动清单（本次运行报告 + 下一步交接），**结束**——ort03 反馈全在反馈区与表 B/C，人类直接写 `[同意执行]`/`[修改建议]`/`[废弃]`、改表 B/C 即反馈，无需对话收集：

```text

  执行规范化：<文件名.chunk-002.md>（生成 OR-XXX~OR-YYY，表 C 当前状态=待处理）
  调整重生成：<文件名.chunk-003.md>（v{N-1}→v{N}，仍待确认）
  废弃材料：<文件名.chunk-004.md>（表 B 生命周期=已废弃）
资产落账：表 B/表 C/01 已同步；23/26 <已按确认写回 / 仅写入分析建议块待确认>；22=<仅候选线索，不写回>；基线已提交（<hash>）

一、待反馈（编辑反馈区/表 B/C 即反馈，AI 用状态扫描检测）
  A. 同意执行 → 在 OR 基线正文区反馈区填写 [同意执行]

  D. 资产裁决 → 在 #role-list 操作反馈列或 23/26 匹配段填写确认/修改意见；22 线索仅供 wft01-nfr 参考

二、下一步
```

## 三、AI 标记约定

**候选 vs 已确认**：`#role-list`、23/26、22 均分候选层和已确认层；下游可参考候选层，但不得作为已确认事实直接依赖。

**`[推断]` 标注**：角色/引擎/22 线索等无标准名匹配或边界模糊时，全量标注 `[推断]`，交由人类裁决或下游重判。

**22 线索纪律**：只写 `候选线索 + [推断]`，不判 Q1/Q2/Q3、不提出指标补充、不写回 22；正式分类对齐由 wft01-nfr 执行。

**增量标记**：正式 OR 节点块的 `确认状态` 字段在人类确认后追加 `[同意]`（本步反馈状态自终止，无需 `[已处理]` 记录分离）。

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 B / 表 C 是人类与 AI 共同维护的表，OR 基线（01）由下游 wft01 消费。AI 写回前执行冲突检查：

1. **快照**——读取待更新行（表 B 生命周期 / 表 C 当前状态与人类决策）的当前值
2. **复核**——写回前重新读取；若与快照不符（人类在本次运行期间手工修改），标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：AI 绝不覆盖非空的人类决策（人类编辑即反馈，AI 不代写）
4. **last_size 重入检测**——读取 OR 基线正文区对应 `#body-{seq}` 字节数，与表 B `last_size` 比较：不一致且无明确反馈时标记"疑似人工改动"，进入待确认重审

### B.2 写回顺序（同步契约）

1. **先更新表 B / 表 C**（权威源）
2. **再从表 B/表 C 推导**写入 OR 切分文档状态表和 OR 基线管理区
3. 同步维护 01 元数据、自描述索引、业务域/角色组索引、`AI最近变更`、`AI可以处理节点`、域节点数
4. 两者不一致时，以状态文档为准重建

## 四、重进入规则

| 场景 | 处理 |
|------|------|
| 新选入规范化 | 表 B `生命周期=已澄清` + `人类决策=同意规范化` → Step 3 新增处理 |
| 方案反馈/重入 | 表 B `生命周期=待确认规范方案` → Step 2 反馈分支 |
| 已规范化变更检测 | 表 B `生命周期=已规范化`：有反馈文本 → Step 2；分析建议块字段变更 → 重匹配；last_size 变化 → 待确认重审 |
| 表 C 人类决策变化 | OR 从空变 `同意分配` 或撤销/改分配 → 按类型加入或移出对应 wft01 的 `AI可以处理节点` 分节，不改写 OR 语义 |
