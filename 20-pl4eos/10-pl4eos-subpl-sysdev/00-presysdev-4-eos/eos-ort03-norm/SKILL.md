## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| 读取表 B 中 `生命周期=已澄清` + `人类决策=同意规范化` 的切分文件 | 文本化/切分/澄清 → ort00~ort02 |
| 四单一拆分（单一角色/语义/路径/可确认性）+ 类型判定（FR-BIZ/FR-ENG/NFR） | OR→STR 分解分配 → wft01-biz/eng/nfr |
| 轻量资产标注（角色/产品类型/组部件/文档/22候选线索） | STR/BP/SR/PA 下游设计决策 |
| 规范化五项检查 + 冲突检测 + 分析建议块输出 | 对冲突需求作裁决（本步只呈现冲突） |
| 人类确认 `[同意执行]` 后：生成正式 OR 节点块 + 表 C + AI可以处理节点 + 23/26 同步写回 | 写回 22（本步只保留候选线索，不写回） |
| 维护 `#role-list` + 23/26 匹配结果 + 22 候选线索 | — |

### OR 类型判定

| 类型 | 判定 |
|------|------|
| FR-BIZ | 面向业务角色的业务能力诉求 |
| FR-ENG | 角色为业务定义配置人员，描述引擎/配置页面/流程规则等引擎能力 |
| NFR | 性能/安全/可用性/合规/审计等非功能约束 |

## 二、操作流程

### Step Start · 前置校验

1. 状态文档存在、`.chunk-*.md` 存在、`status=clarified` 文件存在
2. 23 资产存在；26/22 不存在时降级继续（标记对应候选线索不可用）
3. 表 C 人类决策有变化 → 优先同步 AI可以处理节点
4. 全部就绪 → Step 1 → 优先检查 Step 3 反馈；无反馈再进入 Step 2

### Step 1 · OR 层资产加载

加载 23 输出产品架构、26 文档定义、按需加载 22 分类维度和候选区（不可用时记录但不阻断）、OR 基线现有 `#role-list`。

### Step 2 · 新增处理

读取表 B 中 `生命周期=已澄清` + `人类决策=同意规范化` 的切分文件。

**1. 四单一拆分**：

| 原则 | 操作 |
|------|------|
| 单一角色 | 拆到每条仅涉及一个角色 |
| 单一语义 | 拆到每条仅含一个独立语义 |
| 单一路径 | 拆分混在一起的 FR-BIZ/FR-ENG/NFR |
| 单一可确认性 | 不可独立确认则继续拆分或标记待确认 |

FR-ENG 涉及多个引擎 → 按引擎拆为多条（25 不可用时标注 `[推断]`）。

**2. 轻量资产标注**（逐条 OR）：

| 字段 | 参考源 | 标注规则 |
|------|--------|----------|
| 角色 | `#role-list` | 同名/同义使用标准名；无匹配推断新角色 |
| 产品类型 | 23 产品类型 | 匹配标准名优先 |
| 组部件 | 23 组部件清单 | 匹配标准名优先 |
| 文档 | 23/26 关联文档 | 优先匹配所属组部件已有文档 |
| 22 候选线索 | 22 分类资产 | 仅写候选线索+`[推断]`，不判 Q，不写回 22 |

**3. 23/26 匹配**（Q1/Q2/Q3 判定）写入分析建议块。

**4. 输出分析建议块 + 反馈区**，表 B→`待确认规范方案`。

### Step 3 · 方案反馈处理（优先）

| 反馈 | 处理 |
|------|------|
| `[同意执行]` | 分配节点ID/OR编号 → 生成正式 OR 节点块（@or-{seq}） → 写表 C → 更新索引和 AI可以处理节点 → 写回 23/26 → 表 B→`已规范化` |
| `[修改建议]` | 调整方案（历史由 Git 管理）→ 重检 → 写新版分析建议块 |
| `[废弃]` | 表 B→`已废弃`，正文区标记废弃 |
| 无反馈 | 跳过，等待人类 |

**正式 OR 节点块**包含：业务编号/类型/父节点/输入/输出/优先级/角色/业务语境/候选资产上下文/原始表述/规范化表述/来源定位/当前状态/确认状态。

表 C `当前状态=待处理` + `人类决策=同意分配` 时，按类型加入对应 wft01 的 `AI可以处理节点` 分节。同一 OR 只能进入一个 wft01 分节。

### Step 4 · 角色资产管理

汇总本轮所有 OR 的角色 → 去重 → 与既有 `#role-list` 比对：
- 同名/同义 → 使用标准名
- 新角色 → 追加候选行
- 角色定义变化 → 更新 `#role-list`

### Step 5 · 输出产品构成管理

将 Step 2 的 23/26 匹配结果（Q1/Q2/Q3）汇总写入分析建议块的资产建议段。人类确认后 Step 3 写回 23/26。

### Step 6 · 非功能候选线索管理

将 Step 2 的 22 候选检索线索写入分析建议块的 NFR 线索段。**不写回 22**——22 分类判定由 wft01-nfr/wft04-nfr 管理。

### Step End · 运行结束输出（含反馈等待）

按三区模板输出方案摘要：

```text
══════════════════════════════════════════
  eos-ort03 本轮完成
══════════════════════════════════════════

当前状态：<待确认规范方案 / 已规范化可分配>
  生成方案：[文件]（N条OR，待确认规范方案）
  已规范化：[文件]（M条OR→表C，待处理→待同意分配）

一、方案反馈
  A. 同意执行 → 回复「同意执行」，生成正式 OR 节点
  B. 修改建议 → 描述修改内容
  C. 废弃 → 终止处理

二、下一步
  本Skill → 继续选入规范化或处理待确认方案反馈
  后续    → OR→设人类决策=同意分配 → wft01-biz / wft01-eng / wft01-nfr
```

**输出后不要结束对话。** 等待人类反馈——人类可直接用自然语言回复修改意见：

> 以上是本轮规范化方案。直接回复修改意见即可：
> - "第3条 OR 拆成两条，分别归入 FR-BIZ 和 FR-ENG"
> - "同意执行"
> - "第5条的 22 候选线索改为 @nfr-sec-003"

**AI 处理反馈规则**：

| 人类输入 | AI 动作 |
|---------|--------|
| 显式修改指令（"X 改为 Y"） | 定位分析建议块 → 按反馈调整方案 → 重跑检查及 23/26 匹配和 22 线索检索 → 写新版分析建议块（历史由 Git 管理）→ 输出修改摘要 → 继续等待 |
| 整体确认（"同意执行"/"可以"） | 分配节点ID/OR编号 → 生成正式 OR 节点块（@or-{seq}）→ 写表 C → 更新索引和 AI可以处理节点 → 写回 23/26 → 表 B→`已规范化` → 结束 |
| 废弃（"废弃"/"终止"） | 表 B→`已废弃`，正文区标记废弃 → 结束 |
| 质疑/模糊意见 | 解释或追问 |
