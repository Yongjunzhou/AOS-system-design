## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step 1：状态扫描检出反馈区标记 / `#role-list` 操作反馈 / 表 B/C 变更 → 登记表 B 内容摘要（查重幂等） | 文本化/切分/澄清 → ort00~ort02 |

**核心原则**：AI 只做类型先行分治拆分与规范化、结构化呈现冲突，不做冲突裁决、不做设计决策；**反馈走「状态扫描 检出→登记→处理」（线下通道）与「对话交互（即时处理）+ 整体确认收尾」（Step 5/6 对话通道）双通道**——人类写 `[同意执行]`/`[修改建议]`/`[废弃]`、改表 B/C（线下，Step 1 检出登记、Step 2 处理），或 Step 5 对话给指示（AI 即时登记表 B 内容摘要、执行处理并追 `[已处理]`），无需 git diff。

### OR 类型判定（类型先行——先判类型再按类型分治）

| 类型 | 判定 | 天然单元 |
|------|------|---------|
| FR-BIZ | 面向业务角色的业务能力诉求，不直接描述平台引擎能力配置 | 场景为锚（主责角色 × 业务对象闭环），一场景可多条 OR |
| FR-ENG | 角色为业务定义配置人员，且描述引擎/驱动/机制/配置页面/流程规则配置等引擎能力 | 对一个平台引擎的一项能力诉求 |
| NFR | 性能/安全/可用性/合规/审计/数据保留等非功能约束 | 关注角色 × 分类维度 × 适用对象线索（四元组原子） |

## 二、操作流程

### Step Start · 前置校验 + 资产加载

**一句话**：确认前置就绪（状态文档/切分文件/资产/基线）并完成表 C 入口同步、加载匹配资产，有表 B 任务才进入 Step 1。

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 存在
2. 若状态文档已存在，校验表 B/表 C 表头与字段说明，与状态文档模板不符时按既有口径修正或提示
3. `10-raw-files/` 中存在 `.chunk-*.md`，且存在 `status=clarified` 的切分文件
4. `23-eos-output-architecture.md` 缺失时记录 `23 候选线索：不可用`，不阻断规范化（与 22/25 对称）
5. `22-eos-nfr-taxonomy.md`、`25-eos-engine-models.md` 缺失时记录对应候选线索不可用（25 缺失时 FR-ENG 引擎拆分降级 `[推断]`），不阻断规范化
6. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
7. **感知前置——扫描反馈载体**（[人类方案 §3.7](../eos-ort03-norm.md#37-反馈检测判据)）：①OR 基线正文区反馈区存在 `[同意执行]`/`[修改建议]`/`[废弃]` 标记；②`#role-list` 操作反馈列存在 `[确认]`/`[修改]`/`[新增]`/`[删除]`；③表 B/C `人类决策` 变化尚未处理。**存在任一反馈 → 即使表 B 无 `待确认规范方案` 记录也进入 Step 1 先检出反馈**（`#role-list` 操作反馈/表 B/C 人类决策变化不依赖该状态）
8. **表 C 入口同步（优先）**：逐条比较表 C 与 `AI可以处理节点`，将 `当前状态=待处理` + `人类决策=同意分配` 的 OR 按类型加入对应 wft01 分节；状态不再为待处理/撤销同意/类型改变时，从原分节移出。不生成或修改 OR 语义。完成后更新 `AI最近变更`
9. 全部就绪且表 B 有任务或已检出反馈 → 进入资产加载；无任务且无反馈 → Step End

**资产加载**（加载经济原则：用脚本/按需读取加载资产分节与 `#role-list`，不 Read 完整资产文件；22 按需读取一级类目和候选区，不可用即降级记录）：

1. 读取 23 输出产品架构：已确认/疑似产品类型、E2E 项目、构件类型
2. 按需读取 22 一级类目、分类维度和候选条目（仅 NFR OR 分类维度判定用；不可用记录不阻断）
3. 按需读取 25 平台引擎清单（仅 FR-ENG 引擎拆分参考用；不可用记录不阻断）
4. 读取 `01-eos-original-requirements.md` 现有 `#role-list`（如存在）
5. 标记资产加载结果，供 Step 2/3 复用 → Step 1

### Step 1 · 反馈检测与汇总

**一句话**：本轮开始先把你在运行间隙写的反馈（反馈区标记 / `#role-list` 操作反馈 / 表 B/C 变更）找出来，登记到表 B 内容摘要并汇总清单——之后 Step 2 基于登记处理。

1. 扫 OR 基线正文区反馈区，检出 `[同意执行]` / `[修改建议]` / `[废弃]` 标记
2. 扫 `#role-list` 操作反馈列，检出 `[确认]` / `[修改]` / `[新增]` / `[删除]`
3. 对每处反馈查重：表 B 内容摘要已有该文件同类型未处理登记？→ 无则登记 `反馈：<类型>（<文件>）`（格式见人类方案 §三 3.7）；已有则跳过（只汇总不重复登记）
4. 汇总表 B 内容摘要中既有未处理反馈记录（对话通道 Step 5 写入的），一并列入本轮反馈清单
5. 输出本轮反馈清单：已登记待处理（同意执行 N / 修改建议 K / 废弃 M / 角色操作 L）
6. 路由：有反馈登记 → Step 2；有新选入（`已澄清`+`同意规范化`）→ Step 3；全无 → 「无待处理对象」结束

> 反馈区标记与 `#role-list` 操作反馈保留至 Step 2 处理时清理；查重保证多次运行不重复登记（中断后残留标记下轮跳过）。

### Step 2 · 反馈处理

**一句话**：按表 B 内容摘要的反馈登记逐一处理——同意执行→编号生成正式节点、修改建议→调整重生成、废弃→终止、角色操作→更新角色清单，处理完追 `[已处理]`。

读表 B 内容摘要中「含 `反馈：` 且未追加 `[已处理]`」的记录，逐个处理：

| 反馈类型 | 处理 |
|---------|------|
| `反馈：同意执行（<文件>）` | 批量读取该文件待确认分析建议块 → 统一分配 `@or-{seq}` 节点 ID 与 `OR-{seq}` 业务编号（跨源文件连续无跳号）→ 按 [人类方案 §三 3.5](../eos-ort03-norm.md#35-正式-or-节点与-wft01-入口契约) 生成正式 OR 节点块（附录 C）→ 写表 C（追加父子行，OR 初始 `待处理`）→ 更新索引/`AI最近变更`/`AI可以处理节点` → 23 同步写回（Q1 引用/Q2 扩展/Q3 新建）→ 22 不写回 → 表 B→`已规范化`、frontmatter.status→`normalized`、last_size 写回 → 清理反馈区标记 → 追 `[已处理]` |
| `反馈：修改建议（<文件>：<要点>）` | 解析意见 → 管理区摘要记录调整结论（历史由 Git 管理）→ 调整条目与资产匹配 → 重跑规范化五项检查/冲突检测/23 匹配/NFR 分类维度判定 → 写新版分析建议块 → 表 B 保持 `待确认规范方案` → 清理旧反馈区标记 → 追 `[已处理]` |
| `反馈：废弃（<文件>）` | 表 B→`已废弃`、AI建议→`建议终止`、frontmatter.status→`abandoned` → 正文区标记废弃并追加废弃说明块 → 清理反馈区标记 → 追 `[已处理]` |
| `反馈：角色操作（<文件>：<动作>）` | 按 `[确认]`/`[修改]`/`[新增]`/`[删除]` 更新角色清单并同步分析建议块（有变更时追加角色修改记录）→ 追 `[已处理]` |

写回前执行附录 B.1 冲突检查；处理后按附录 B.2 同步契约推导更新文档内嵌状态摘要表与 OR 基线管理区。

**重入变更检测**：表 B `生命周期=待确认规范方案` 的既有条目按人类方案 §四 4.1 重入变更检测（反馈登记 / last_size / 分析建议块字段变更 / 表 C 人类决策变化）判定是否需要重处理。

### Step 3 · 新增处理

**一句话**：处理选入规范化的已澄清切分文件——复制原文、拆分判定、做规范化检查、聚合角色与 23/22 资产线索，生成完整分析建议块，表 B 置 `待确认规范方案`。

读取表 B 中 `生命周期=已澄清` + `人类决策=同意规范化` 的切分文件（详细规则见 [人类方案 §三 3.3](../eos-ort03-norm.md#33-拆分与类型判定规则)）：

**1. 复制原文到 OR 基线正文区**——每个切分文件独立 `#body-{seq}` 条目；已存在则覆盖写入新版本（历史由 Git 管理）。

**2. 识别与拆分**——执行顺序不可逆：识别业务对象与归属判定（[人类方案 §三 3.2](../eos-ort03-norm.md#32-识别与归属判定规则)——3.2.1 识别候选 / 3.2.2 归属判定；识别目标见 [§二 2.2](../eos-ort03-norm.md#22-识别业务输出产品及构件)）→ 按类型拆分（附录 A.1）→ 规范化检查与冲突检测（[人类方案 §三 3.4](../eos-ort03-norm.md#34-规范化检查与质量门禁)，附录 A.6）→ 优先级初判。

**3. 角色汇总**——读取全部分析建议块角色 → 去重并同义词归并 → `#role-list` 不存在时创建、存在时增量合并 → 同义词角色写回为标准名（有变更时追加角色修改记录）。`#role-list` 操作反馈由 Step 1 检出登记、Step 2 处理，本步只做汇总。

**4. 23 输出产品匹配**——使用 Start 已加载的 23 基准，逐条判定 23-Q1/Q2/Q3（附录 A.3），结果写入分析建议块 `### 23 资产匹配结果` 段；不直接写入 23，人类确认后由 Step 2 同步写回。

**5. NFR 分类维度判定**——读取全部 NFR 条目的质量诉求原文（不生成系统指标），逐条判定分类维度（@nfr-xxx）与适用对象线索，全部标注 `[推断]`，写入分析建议块 `### 22 分类维度` 段；不量化指标、不写回 22（附录 A.4）。

**6. 更新状态**——写入完整分析建议块和反馈区（模板见 [人类方案 §六 6.1](../eos-ort03-norm.md#61-分析建议块模板)）后，表 B→`生命周期=待确认规范方案`、`AI建议=建议执行`，再推导更新文档内嵌状态摘要表。

### Step 4 · 提交基线

**一句话**：提交本轮 Step 1~3 的处理结果为 git 基线（链级不变式）。

把本轮 Step 1~3 的处理结果提交为 git 基线。

**为什么需要提交**：ort03 自身检测用状态扫描、不需要基线；但 ort03 的产出（OR 基线 + 23 资产 + 表 B/C 写入）若不落基线，会进入下游 git diff 步骤的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B/C、OR 基线、23 资产；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段
4. **无变更**：工作区无改动时跳过提交，基线不变

**对话即处理**——AI 输出本摘要后**不结束对话**。人类在对话中直接说明反馈意图（如「同意」「chunk-002 废弃」「角色 X 改为 Y」），AI **即时理解并处理**：按 [人类方案 §三 3.7](../eos-ort03-norm.md#37-反馈检测判据) 反馈判据把反馈登记到表 B `内容摘要`（`反馈：同意执行（<文件>）` / `反馈：修改建议（<文件>：<要点>）` / `反馈：废弃（<文件>）` / `反馈：角色操作（<文件>：<动作>）`）并执行对应动作（同意→编号生成正式 OR 节点 + 23 写回；修改建议→修订分析建议；废弃→终止；资产裁决→按指示处理），追加 `[已处理]`，输出处理摘要，继续等待。**无需口令表**——AI 通过理解自然语言判断反馈意图（「打开状态文档」等辅助请求按自然语言处理）；对话反馈与线下编辑等价（线下编辑仍由 Step 1 检出登记、Step 2 处理）。反馈结束以「整体确认」为准（Step 6）。本步为**交互协议步骤**（执行模式=对话）。

### Step 6 · 反馈收尾（整体确认）

**一句话**：你表示反馈结束（「整体确认」/「可以了」）时，AI 确认本轮对话反馈均已处理、提交基线、推进状态。

**动作**：人类表示反馈结束（「整体确认」/「可以了」）时，AI **立即收尾一次**——确认本轮对话反馈均已处理（无未追加 `[已处理]` 的记录）→ **提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交，交接即完整基线）** → 推进状态 → 输出「已确认」摘要。

**为什么必须提交**：否则下次 Step 1 会把 AI 自己的处理误判为人类反馈（表 B 内容摘要登记、对话代写记录）。对话期间你对文档的静默编辑也随收尾一并纳入基线。

**兜底与路由**：本步为**交互协议步骤**（执行模式=对话）。此收尾**不替代 Step 1**——运行结束后你线下写反馈区标记的反馈，仍由 Step 1 下次状态扫描检出登记。**无需口令表**——「整体确认」为自然语言表达；如有仍未处理的已记录反馈，可自然语言要求「继续处理反馈」，AI 重跑 Step 2 后回到 Step 5。

### Step End · 运行结束输出

**一句话**：输出行动清单后结束——你后续可对话反馈（Step 5 即时处理），也可线下写反馈区标记 / 改表 B/C（下轮 Step 1 检出）。

输出行动清单（本次运行报告 + 下一步交接），**结束**：

## 三、AI 标记约定

**候选 vs 已确认**：`#role-list`、23、22 均分候选层和已确认层；下游可参考候选层，但不得作为已确认事实直接依赖。

**`[推断]` 标注**：角色/引擎/22 分类维度等无标准名匹配或边界模糊时，全量标注 `[推断]`，交由人类裁决或下游重判。

**22 分类维度纪律**：只判 `@nfr-xxx + [推断]`（无匹配写候选标注），不量化指标、不写回 22；正式写回由 wft01-nfr 评审后执行。

**反馈登记纪律**：反馈统一登记到表 B 内容摘要（`反馈：<类型>（<文件>）`，查重幂等），Step 2 处理完追 `[已处理]` 并清理反馈区标记；Step 5 对话反馈即时登记并处理、追加 `[已处理]`；Step 6「整体确认」提交基线；线下反馈仍由 Step 2 统一处理。

**确认状态标记**：正式 OR 节点块的 `确认状态` 字段在人类确认后追加 `[同意]`。

### A.1 拆分（类型先行，按类型分治）

| 类型 | 天然单元 | 拆分操作 |
|------|---------|---------|
| FR-BIZ | 场景为锚（主责角色 × 业务对象闭环），一场景可多条 OR | 场景为边界上限，成条依据 = 提出者 × 单一可确认性（不同用户分别提出各成一条）；场景内不设中间单元 |
| FR-ENG | 对一个平台引擎的一项能力诉求 | 涉及多个引擎 → 参考 25 资产按引擎拆；25 不可用/边界模糊标 `[推断]` |
| NFR | 关注角色 × 分类维度 × 适用对象线索（四元组原子） | 拆到单一关注角色 × 单一分类维度（22 @nfr-xxx）× 单一适用对象线索（STR-F/业务域/平台能力/全局对象）可独立确认 |

### A.6 规范化检查与冲突检测

**五项标准**：完整性、主体明确、客体可识别、边界可判定、可测试性（结构完整性——分支缺对应面/闭环缺端/引用对象缺失——已在 ort02 澄清检知，本步完整性聚焦 OR 条目表达完整）。残留清晰性问题标 `待确认` 分两类（见 [人类方案 §三 3.4](../eos-ort03-norm.md#34-规范化检查与质量门禁)）：条目不完整 → ort03 自解不回退；原文缺事实 → 标注 `需退回澄清`，人类设表 B `人类决策=需退回澄清` 后走反向路由（表 B 生命周期转 `澄清中`、清理 `#body-{seq}`，仅方案期）。按类型解读：NFR 的边界可判定 = 数值+单位+条件齐备（缺则标 `待确认`，本步不量化）、可测试性 = 可定位到验证判据（目标值由相关方经澄清确认；统计口径/测量方法/验收条件由 wft04-nfr 执行）。

**冲突检测范围**（只结构化呈现，不做裁决）：

| 层 | 范围 | 处理 |
|----|------|------|
| 层 A | 同一切分内 OR 条目间 | 标记并列出双方原文 |
| 层 B | 同原始文件跨切分 OR 条目间 | 标记并列出影响 |
| 层 C | 与 OR 基线既有 OR 的跨原始文件冲突 | 标记双方节点 ID，不做裁决 |

**冲突类型**：直接冲突（无法同时满足→`需确认`，列双方原文）/ 间接冲突（各自可行但行为不一致→`需调整`，说明影响）/ 部分内容冲突（局部冲突→优先拆分）。

**优先级初判**：P0 / P1 / P2 / P3 初判，供人类确认（语义与顺序判据见 [人类方案 §三 3.4](../eos-ort03-norm.md#34-规范化检查与质量门禁)：P0 合规/安全强制或系统基础能力被广泛依赖 / P1 核心闭环必要、可分期 / P2 常规增强 / P3 可延后待定；只用于分批排序与提示，不作交付承诺）。

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 B / 表 C 是人类与 AI 共同维护的表，OR 基线（01）由下游 wft01 消费。AI 写回前执行冲突检查：

1. **快照**——读取待更新行（表 B 生命周期 / 表 C 当前状态与人类决策）的当前值
2. **复核**——写回前重新读取；若与快照不符（人类在本次运行期间手工修改），标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：AI 绝不覆盖非空的人类决策（人类编辑即反馈，AI 不代写）
4. **last_size 重入检测**——读取 OR 基线正文区对应 `#body-{seq}` 字节数，与表 B `last_size` 比较：不一致且无明确反馈时标记"疑似人工改动"，进入待确认重审

### B.2 写回顺序（同步契约）

1. **先更新表 B / 表 C**（权威源）
2. **再从表 B/表 C 推导**写入文档内嵌状态摘要表和 OR 基线管理区
3. 同步维护 01 元数据、自描述索引、业务域/角色组索引、`AI最近变更`、`AI可以处理节点`、域节点数
4. 两者不一致时，以状态文档为准重建
