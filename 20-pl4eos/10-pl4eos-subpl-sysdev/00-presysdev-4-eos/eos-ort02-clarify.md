# 切分原始需求 → 已澄清切分文档 · 模糊标注与澄清迭代
**人类方案ID**: eos-ort02-clarify

> **概述**：把切分文件里的模糊表述找出来，交给人类确认——对人类选入澄清的文件做首轮全量模糊标注；再次运行时读取人类在正文区写的 `[✓已澄清]` 注释，生成清晰新正文并评估是否还需澄清。有未解决的模糊项时输出迭代报告等待人类处理。
>
> **输入 → 输出**：切分文件（`.chunk-{seq}.md`，`status=raw/annotated`）+ `01-eos-sysdev-status.md` 表 B → 已澄清切分文件（同文件原地更新，正文区为最新纯净版本，`status=clarified`）+ 表 B 生命周期/AI 建议/迭代计数更新
>
> **适用场景**：EOS 原始需求预处理链第 3 步；在规范化前消除原始需求中的术语、主体、边界、信息缺失等模糊问题。
>
> **接口设计**：本步通过状态文档表 B 和正文区标注状态驱动工作流。表 B 中 `生命周期=已切分` 且 `人类决策=同意澄清` 的文件进入首轮标注；`生命周期=澄清中` 的文件根据正文区 `[✓已澄清]` / `[⨯]` 状态进入迭代生成、继续等待或异常处理；完成后置 `生命周期=已澄清`，供 eos-ort03-norm 选入。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（Step Start、反馈优先、Step End 与变更传播通用协议）

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把切分文件从"能读"推进到"能规范化"——定位每处模糊，让人类确认后形成清晰完整的新正文，确保不再有歧义。
>
> **目标**：
> 1. **识别澄清对象**——读取表 B 中 `生命周期=已切分` 且 `人类决策=同意澄清` 的切分文件
> 2. **全量标注模糊项**——按五种子类型定位全部需澄清内容，写入 `[⨯]` 标记和模糊标注报告
> 3. **驱动人类澄清**——通过正文区 `[✓已澄清: ...]` 注释接收人类/相关方确认结果
> 4. **生成清晰正文**——按澄清注释生成新正文，变更结论摘要写入管理区（历史版本由 Git 管理）
> 5. **执行三项评估**——判断正文清晰完整、历史模糊已澄清、无新增模糊
> 6. **同步状态接口**——维护表 B 生命周期、AI 建议、frontmatter.status、迭代计数和未解决数量

本 Skill 负责：

1. **接收**——从表 B 读取本轮选入澄清的切分文件
2. **标注**——通读正文，按五类模糊子类型生成行内 `[⨯]` 标记
3. **报告**——输出首轮标注报告或迭代报告
4. **迭代**——读取 `[✓已澄清]` 注释，生成新正文（历史由 Git 管理，不归档旧版）
5. **评估**——按三项条件决定 `已澄清` 或继续 `澄清中`
6. **落账**——更新表 B、frontmatter.status 和 OR 切分文档状态表
7. **交接**——输出待选入澄清、待反馈标注、待选入规范化清单

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 语义切分和切分方案执行（由 eos-ort01-chunk 负责）
3. OR 条目规范化、编号、分类和冲突检测（由 eos-ort03-norm 负责）
4. 代替人类或需求提出方确认业务事实
5. 将澄清内容扩展为设计方案或下游需求分解

## 二、澄清设计基础

### 2.1 切分文档结构

**一句话**：本步原地处理切分文件（`{原始文件名}.chunk-{seq}.md`），把正文区的模糊表述澄清成清晰版本。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 更新 `status`（raw→annotated→clarified→abandoned） |
| 管理区 | 状态摘要、澄清决策记录 | 更新 OR 切分文档状态表，追加澄清决策记录 |
| 正文区 | 原文 + `[⨯]` 标注 + `[✓已澄清]` 注释 + 报告（临时） | 首轮写入标注和报告；迭代后替换为新正文；终态保持纯原文 |

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓]` 标记和临时报告。历史版本由 Git 管理，不在文档内归档旧版。

### 2.2 文档生命周期管理

**一句话**：本步通过状态文档表 B 推进切分文件的澄清生命周期——记录每个切分文件的澄清进度、迭代轮次和剩余模糊项。

表 B — 切分文件处理进度是本步权威源。一条记录的三要素与其他步骤一致：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段：`已切分` → `澄清中` → `已澄清` / `已废弃` |
| AI建议 | 提示字段：`可以澄清` / `需继续澄清` / `可以规范化` / `建议终止`（本步设置值；全集见状态文档表B） |
| 人类决策 | 批次控制字段：`同意澄清` / `同意规范化` / `已终止` / 空 |

澄清特有的追踪字段：

| 字段 | 职责 |
|------|------|
| last_size | 最近一次正文长度或标注规模记录 |
| iteration_count | 澄清迭代轮次 |
| unresolved_count | 当前未解决模糊项数量 |

**同步契约**：本步先更新状态文档表 B，再推导写入切分文件管理区状态表和 frontmatter.status。不一致时以表 B 为准重建派生状态。写回前检测表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类。

### 2.3 入口与重进入规则

**一句话**：本步只处理人类在表 B 明确选入（`同意澄清`）的切分文件；每次运行先处理已有澄清反馈的，再处理新选入的。

Step 1 的入口硬条件：

| 条件 | 说明 |
|------|------|
| `生命周期=已切分` | 上游 ort01 已完成切分 |
| `人类决策=同意澄清` | 人类明确选入本批澄清 |

`AI建议=可以澄清` 只是候选提示，不作为入口硬条件。

运行路由参考 `wft01-biz`：前置校验通过后，**先处理 `生命周期=澄清中` 的反馈/迭代，再处理 `生命周期=已切分` + `人类决策=同意澄清` 的新增首轮标注**。已存在的澄清反馈可能把文件推进为 `已澄清` 并开放 ort03 入口，应先落账。

表 B `人类决策` 是阶段性批次控制字段：文件从 `已切分` 进入澄清时可写 `同意澄清`；澄清完成后，人类可覆盖为 `同意规范化` 作为 ort03 入口。AI 不应把旧的 `同意澄清` 视为锁定值。

Step 2 的入口和分支：

| 条件 | 处理 |
|------|------|
| `生命周期=澄清中` + 正文区存在 `[✓已澄清: ...]` | 生成新正文（历史由 Git 管理）→ 三项条件评估 |
| `生命周期=澄清中` + 有 `[⨯]` 且无 `[✓已澄清]` | 输出迭代报告，等待人类处理 |
| `生命周期=澄清中` + 无任何标记 | 数据不一致：以正文区实际状态为准——正文已纯净 → 表 B 推进 `已澄清`、frontmatter.status 置 `clarified` 并提示人类；否则 → 提示数据不一致，等待人类核对 |
| `生命周期=已澄清` | 不处理正文，进入规范化选材提示 |
| `人类决策=已终止` | 表 B 置 `已废弃`，frontmatter.status 置 `abandoned` |

### 2.4 模糊标注规则

**一句话**：模糊标注就是把"没说清"的地方用 `[⨯]` 标出来，并告诉人类缺什么。

五种模糊子类型：

| 子类型 | 适用场景 | 标注示例 |
|--------|---------|---------|
| 术语模糊 | 非量化表述需明确度量方式 | `[⨯术语模糊: 高效→需量化处理能力指标]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明]提出该需求` |
| 边界模糊 | 条件、范围或指标缺少边界 | `[⨯边界模糊: 实时→需明确具体延迟上限]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→缺来源日期和提出方]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 术语+边界→非量化+缺时限]` |

标注格式：

```text
[⨯子类型: 原文片段→问题说明]
```

标注纪律：

1. 标“哪里不清楚”，不标“应该怎么做”
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致，报告中每项对应正文中的一处内联标注

### 2.5 三项条件

迭代生成新正文后，必须逐项判定：

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有非量化、主体不明、边界不清、信息缺失表述已替换为明确内容 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注 |

三项全满足 → `生命周期=已澄清`、`AI建议=可以规范化`、`status=clarified`。仍有未清晰项 → 追加新 `[⨯]` 标注，保持 `澄清中`。

### 2.6 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做需求澄清，不做需求分解、评价或设计决策 |
| 文档结对 | 本步不产生文档结对关系；已澄清切分文件是 eos-ort03-norm 的输入 |
| 基于资产 | 原始出处保留，变更结论摘要写入管理区；历史版本由 Git 管理，不复制旧版全文 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查状态文档和切分文件是否就绪 | 统一 | 就绪/结束 | — |
| 1 | 新增处理 | 读取表 B 选入材料，执行首轮全量模糊标注 | 统一 | `[⨯]` 标记 + 标注报告 | 表 B、切分文件 |
| 2 | 反馈处理 | 读取 `[✓已澄清]`，生成新正文并评估 | 统一 | 已澄清正文/新标注/迭代报告 | 表 B、切分文件 |
| End | 输出交互 | 输出三段式结果、澄清反馈指引和下一步交接 | 人类 | Step End 三区输出 | — |

核心驱动逻辑：每次运行先处理 `澄清中` 文件的正文区反馈，再处理表 B 中新选入澄清的切分文件，最后输出可进入规范化的候选清单。

### 3.1 Step Start · 前置校验

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示
3. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 中是否存在 `.chunk-*.md` 切分文件；不存在则提示先运行 `eos-ort01-chunk` 并结束
4. 全部就绪后先执行反馈入口检测：存在 `生命周期=澄清中` 的对象时进入 Step 2；无待处理反馈时再进入 Step 1

### 3.2 Step 1 · 新增处理

读取状态文档表 B，按以下规则分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 对应切分文件进入首轮标注 |
| `人类决策=已终止` | 表 B 生命周期置 `已废弃`，frontmatter.status 置 `abandoned` |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

首轮标注动作：

1. 通读切分文件正文区
2. 按五种子类型标注全部模糊项
3. 写入模糊标注报告
4. 有模糊项：frontmatter.status 置 `annotated`，表 B 更新为 `生命周期=澄清中`、`AI建议=需继续澄清`、`iteration_count=1`
5. 无模糊项：frontmatter.status 置 `clarified`，表 B 更新为 `生命周期=已澄清`、`AI建议=可以规范化`
6. 从表 B 推导更新 OR 切分文档状态表

### 3.3 Step 2 · 反馈处理

读取表 B 中 `生命周期=澄清中` 的文件，检测正文区标注状态。

**1. 检测到 `[✓已澄清]`**

1. 收集全部 `[✓已澄清: ...]` 注释
2. 在管理区摘要记录澄清结论（历史版本由 Git 管理，不归档旧版全文）
3. 按注释内容将模糊表述替换为明确内容，生成新正文
4. 清理临时标注和报告，使正文区进入新版本
5. 执行三项条件评估
6. 三项满足时：表 B 置 `已澄清`、`AI建议=可以规范化`、frontmatter.status 置 `clarified`
7. 仍有未清晰项时：在新正文对应位置追加新 `[⨯]` 标注，表 B 保持 `澄清中`、`AI建议=需继续澄清`
8. 更新 `last_size`、`iteration_count++`、`unresolved_count`
9. 推导更新管理区状态表并追加澄清决策记录

**2. 有 `[⨯]` 无 `[✓已澄清]`**

1. 输出迭代报告
2. 表 B 保持 `生命周期=澄清中`
3. 更新 `unresolved_count`（按当前 `[⨯]` 数）和最后更新时间
4. 若 `iteration_count >= 3`，在行动清单中提示优先处理

**3. 无任何标记**

1. 以正文区实际状态为准：正文已纯净 → 表 B 推进 `已澄清`、frontmatter.status 置 `clarified`，并提示人类
2. 否则 → 提示数据不一致，等待人类核对

### 3.4 Step End · 运行结束输出

Step End 参考 `wft01-biz` 的三区输出模板（结果 → 方案反馈 → 下一步），本 Skill 实例化如下：

```text
══════════════════════════════════════════
  eos-ort02-clarify 本轮完成
══════════════════════════════════════════

当前状态：<澄清中 / 已澄清可规范化 / 已废弃 / 无新增处理>
  首轮标注：<文件名.chunk-001.md>（发现 N 项模糊，表 B 生命周期=澄清中）
  迭代澄清：<文件名.chunk-001.md>（v{N-1}→v{N}，剩余 M 项模糊）
  已澄清：<文件名.chunk-002.md>（表 B 生命周期=已澄清，AI建议=可以规范化）
  废弃切分文件：<文件名.chunk-003.md>（frontmatter.status=abandoned）
资产落账：表 B 已同步；切分文件 frontmatter.status / 管理区状态表已同步

一、澄清反馈
  A. 补充澄清 → 在正文区对应 `[⨯]` 后追加 `[✓已澄清: ...]`
  B. 暂不处理 → 保持表 B `生命周期=澄清中`，下轮继续提示
  C. 终止材料 → 在表 B 对应记录设 `人类决策=已终止`

澄清注释示例：
  [✓已澄清: 处理后台响应时间 ≤200ms]
  [✓已澄清: 提出方=市场部张三，2026-06-01]
  [✓已澄清: 根据 QMS-003 号文件，时效为 48h]

二、下一步
  本 Skill → 继续选择表 B `生命周期=已切分` + `人类决策=同意澄清` 的切分文件，或处理 `澄清中` 文件的 `[✓已澄清]` 反馈
  后续    → 表 B `生命周期=已澄清` + `AI建议=可以规范化` 的切分文件，可设 `人类决策=同意规范化` 后进入 eos-ort03-norm
```

**交互方式**：按 [91 规范 §A.5](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a5-反馈交互协议) 反馈交互协议，**AI 不结束对话**——输出本摘要后保持对话，人类以自然语言回复口令，AI 代为更新状态文档与正文区标注。

| 口令 | AI 代执行 |
|------|----------|
| 「同意澄清 [切分文件]」 | 表 B 人类决策=同意澄清（选入首轮标注） |
| 「同意规范化 [切分文件]」 | 表 B 人类决策=同意规范化（选入 ort03） |
| 「[✓已澄清: ...]」 | 写入正文区澄清注释 |
| 「继续」 | 重跑本步 |
| 「打开状态文档」 | 输出路径和建议关注行 |

## 四、模板、产出与下游关系

### 4.1 OR 切分文档状态表

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 首轮标注完成 | 需继续澄清 | N 项模糊待解决（见行内 `[⨯]` 标记） | 追加 `[✓已澄清: ...]` 注释 |
| 澄清中 | 需继续澄清 | N 项模糊未解决（见行内 `[⨯]` 标记） | 追加 `[✓已澄清: ...]` 注释 |
| 已澄清 | 可以规范化 | 无 | 状态文档表 B → 该记录人类决策设为 `同意规范化` |
| 已废弃 | 建议终止 | 无 | 该文件不再进入下游处理 |
