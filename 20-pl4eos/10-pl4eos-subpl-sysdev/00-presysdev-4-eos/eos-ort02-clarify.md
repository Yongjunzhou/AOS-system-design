### 2.1 什么是模糊

**一句话**：模糊 = 需求表述里"没说清"的地方——读不出确切含义或无法衡量，下游（规范化/需求开发）无法直接使用；它是澄清要处理的对象。

按 [通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)，任何需求（FR/NFR）都由**需求描述**和**性能指标**构成，不可衡量则不成为需求。**模糊 = 需求的构成要素缺失或表述不清**——需求描述不清（读不出**术语含义**、**动作主体**、**边界范围**、**必要元信息**），或**性能指标缺失**（有描述没指标、无法衡量）。

六种模糊子类型（标注规则见 §三 3.2；结构完整性为独立第二类澄清对象，见下注）：

| 子类型 | 一句话 |
|--------|--------|
| 术语模糊 | 业务/领域术语表述不明确 |
| 主体/客体不明 | 动作主体或作用对象不可识别 |
| 边界模糊 | 条件、范围、时限等缺少边界 |
| 缺少定量指标 | 有需求描述但缺性能指标（数值+单位+条件）——FR/NFR 均适用 |
| 信息缺失 | 缺来源、时间、提出方等元信息 |
| 多重模糊 | 同一处存在两种以上模糊 |

> **缺少定量指标** = 需求缺"性能指标"中的定量指标部分（如"支持批量导入"缺单次上限、"实时响应"缺目标值）。功能需求与非功能需求同构适用——澄清时 AI 都向相关方要 数值+单位+条件（非功能分支还须澄清质量属性准确表述与适用对象，见 §三 3.2 纪律 5）。

> **结构完整性**（独立于六类模糊子类型的第二类澄清对象，标注规则见 §三 3.2 纪律 6）= 需求**整体缺席**一块——不是"表述不清"，而是文本结构上存在未兑现的期待：条件有正面缺对应面、业务对象闭环缺端、引用对象在材料集中无定义。AI 只在文本自证缺口时发问，不做模板式业务覆盖猜测。

### 2.2 什么是已澄清

**一句话**：已澄清 = 澄清迭代的完成态——正文里每处模糊都被相关方确认的明确内容替换干净，可以送规范化了。

判定需同时满足三项条件（正式判定口径见 §三 3.3）：

| 条件 | 判定要点 |
|------|---------|
| ① 正文清晰完整 | 模糊表述（术语不明、主体不明、边界不清、缺少定量指标、信息缺失）与结构完整性缺项（§三 3.2 纪律 6）已替换为明确内容，且**内容来自相关方确认**——AI 生成的澄清问题不算已澄清 |
| ② 历史模糊项已澄清 | 每处旧 `[⨯]` 都有对应 `[✓已澄清]` 注释 |
| ③ 无新增模糊 | 新正文通读后不再产生新的 `[⨯]` 标注 |

| 结果 | 状态落账 |
|------|---------|
| 三项全满足 → **已澄清** | 生命周期=`已澄清`、AI建议=`可以规范化`、frontmatter.status=`clarified`、正文区为纯净版本 |
| 任一未满足 → **澄清中** | 保持 `澄清中`、AI建议=`需继续澄清`，回到 §二 2.3 循环继续 |

> **"已澄清"≠"澄清中"**：已澄清 = 模糊项已全部由相关方确认、可送 ort03 规范化；澄清中 = 仍有未确认模糊项，继续迭代。

### 2.3 澄清怎么做

**一句话**：澄清 = 一轮「AI 出题 → 开发者问相关方要答案 → AI 成文」的循环，一次可能不干净，会反复多轮直到三项条件满足。

| 环节 | 谁做 | 动作 | 产物 |
|------|------|------|------|
| ① 标注 | AI | 标 `[⨯]` + 为每处生成「向相关方确认的问题」（六种模糊子类型 + 结构完整性，§三 3.2） | `[⨯]` 标记 + 问题清单报告 |
| ② 澄清 | 开发者（向相关方确认） | **双通道**：对话给答案 / 线下持问题清单向相关方问清后写 `[✓已澄清: <相关方确认内容>]`（§1.2） | `[✓已澄清]` 注释（相关方确认内容） |
| ③ 处理 | AI | 检出登记 → 按答案生成新正文 → 三项条件判定（判据 §三 3.3，操作 §五 5.3） | 清晰正文 / 保持 `澄清中` |

> 相关方是答案的来源，开发者负责问与写回；AI 只出问题、不提供答案（§三 3.2 纪律 1）。

澄清以**迭代**方式推进：处理完可能仍有未清晰项 → 追加新 `[⨯]` → 回到 ② 继续澄清，直到三项条件满足。

> **直觉走一遍**：原文「生产物料由**外购件**组成」→ AI 标 `[⨯术语模糊: 外购件→问题："外购件"的确切定义和范围是？]` → 你问采购相关方，答「外购件指需对外采购的原材料与标准件」→ 你在正文写 `[✓已澄清: 外购件指需对外采购的原材料与标准件]` → AI 检出登记、按答案生成新正文并评估。

### 2.4 AI 做哪些澄清工作

**一句话**：AI 跑「标注 → 检出登记 → 处理 → 评估 → 收尾」的自动化循环；四条红线划清边界——答案、指标、设计都由你把关。

**AI 自动做**（本步核心循环）：

| AI 做 | 一句话说明 |
|-------|-----------|
| 标注 | 标 `[⨯]` + 为每处生成向相关方确认的问题（六种模糊子类型 + 结构完整性，§三 3.2） |
| 检出登记 | 状态扫描检出 `[✓已澄清]` / 表 B 变更 → 登记表 B 内容摘要（§三 3.5 反馈检测判据） |
| 处理 | 按登记生成新正文 / 终止 / 重标，追 `[已处理]`（§五 5.3） |
| 评估 | 三项条件判定 `已澄清` 或继续 `澄清中`（判据 §三 3.3，操作 §五 5.3） |
| 交互收尾 | Step 5 对话即时处理 + Step 6「整体确认」提交基线（§五 5.6/5.7） |

**AI 绝不做**（四条红线）：

| AI 不做 | 为什么 |
|---------|--------|
| 代替开发者/相关方确认业务事实——只出问题、不提供答案（§三 3.2 纪律 1） | 业务事实只有相关方知道 |
| 给非功能需求发明指标数值——目标值由相关方确认（§三 3.2 纪律 5） | 指标由相关方定，AI 不发明 |
| 对话澄清答案未经确认不代写（§1.3） | 答案必须经你确认后才落正文 |
| 把澄清内容扩展为设计方案或下游需求分解（§1.3） | 本步只做需求澄清、不做设计 |

> 本表只列与「澄清工作」直接相关的边界；本步整体不负责的项（原始材料文本化、语义切分、OR 规范化）见 §1.3。

### 2.5 切分文档结构

**一句话**：本步原地处理切分文件（`{原始文件名}.chunk-{seq}.md`），把正文区的模糊表述澄清成清晰版本。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 更新 `status`（raw→annotated→clarified→abandoned） |
| 管理区 | 状态摘要、澄清决策记录 | 更新文档内嵌状态摘要表，追加澄清决策记录 |
| 正文区 | 原文 + `[⨯]` 标注 + `[✓已澄清]` 注释 + 报告（临时） | 首轮写入标注和报告；迭代后替换为新正文；终态保持纯原文 |

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓]` 标记和临时报告。历史版本由 Git 管理，不在文档内归档旧版。

### 2.6 文档状态模型

**一句话**：本节讲本步的状态体系**怎么追踪**——表 B 记三个流程字段 + 三个澄清字段（last_size / iteration_count / unresolved_count），写回顺序固定——先表 B、后派生状态；全链生命周期线由 ort01 §二 2.3.2 定义，本步只推进 `澄清中 → 已澄清`。

表 B — 切分文件处理进度是本步权威源。一条记录的三要素与其他步骤一致：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段：`已切分` → `澄清中` → `已澄清` / `已废弃` |
| AI建议 | 提示字段：`可以澄清` / `需继续澄清` / `可以规范化` / `建议终止`（本步生命周期段取值；全集见状态文档表B） |
| 人类决策 | 批次控制字段：`同意澄清` / `需退回澄清` / `同意规范化` / `已终止` / 空 |

澄清特有的追踪字段：

| 字段 | 职责 |
|------|------|
| last_size | 最近一次正文长度或标注规模记录 |
| iteration_count | 澄清迭代轮次 |
| unresolved_count | 当前未解决模糊项数量 |

**同步契约**：本步先更新状态文档表 B，再推导写入文档内嵌状态摘要表和 frontmatter.status。不一致时以表 B 为准重建派生状态。写回前执行竞态保护——检测表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类（Step 2/3 写回前均引用本条）。

> 反馈记录格式（`‖ 反馈：<类型>（<要点>）` + `[已处理]`）见 §三 3.5 反馈检测判据。

## 三、设计原理与判据

**一句话**：本章讲澄清的**设计逻辑与判定规则**——为什么用「出题→确认→成文」闭环（3.1 澄清原理）、怎么标模糊（3.2 模糊标注规则）、怎么判完成（3.3 三项条件）、哪些材料能进（3.4 入口规则）、反馈怎么检出与登记（3.5 反馈检测判据）、守住什么边界（3.6 工程化原则）；概念见 §二，演进见 §四。

### 3.1 澄清原理：为什么用「出题→确认→成文」闭环

**原始需求在切分后仍带着"说不清"的模糊**。一份已切分文件可能含术语不明、主体/客体不明、边界不清、缺定量指标、信息缺失等表述问题，甚至整体缺一块（条件有正面缺对应面、闭环缺端、引用对象无定义）。下游 ort03 规范化与 wft01 需求开发无法直接使用——本步把这些模糊定位出来、由相关方确认成明确内容，确保正文从"能读"推进到"能规范化"。

**答案来自相关方，AI 只出题不答题**。业务事实（术语定义、指标数值、边界条件）只有相关方知道。AI 替答会污染 OR 基线原始性、让确认主体错位（开发替业务脑补）。因此 AI 只做两件事——定位"哪里不清楚"（六类模糊 + 结构完整性扫描）并生成「向相关方确认的问题」；开发者持问题清单向相关方澄清后写回 `[✓已澄清]`。这正是本步核心闭环「AI 出题 → 开发者问相关方 → AI 成文」的由来（§二 2.3）。

**缺指标必须澄清目标值**。需求 = 需求描述 + 性能指标（[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)，不可衡量则不成为需求）。缺指标即缺"性能指标"的定量部分（如"支持批量导入"缺单次上限、"实时响应"缺目标值）——必须由相关方确认 数值+单位+条件，AI 不发明指标数值；系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 展开。

**结构完整性扫描堵住"整体缺席"缺口**。六类模糊解决"表述不清"，但需求还可能"整体缺席一块"——分支有正面缺对应面、业务对象闭环缺端、引用对象在材料集无定义。不检则这些结构缺口会带「已澄清→可规范化」认证穿过全链（ort03 单条级完整性门禁看不见跨片/跨条件缺口）。AI 只在文本自证缺口时发问（§三 3.2 纪律 6），不做模板式业务覆盖猜测——那已属需求开发职责。

### 3.2 模糊标注规则

**一句话**：模糊标注就是把"没说清"的地方用 `[⨯]` 标出来，并告诉开发者该向相关方确认什么——AI 生成问句，开发者持清单去澄清。

**标注路径**：通读正文区 → 逐处判定六类模糊（下表）→ 生成 `[⨯子类型: 原文→问题：<问句>]` → **做结构完整性扫描（纪律 6）** → 汇总入问题清单报告 → 你持清单去澄清。

六种模糊子类型：

| 子类型 | 适用场景 | 标注示例（AI 生成向相关方确认的问题） |
|--------|---------|---------|
| 术语模糊 | 业务/领域术语表述不明确 | `[⨯术语模糊: 外购件→问题："外购件"的确切定义和范围是？]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明: 提出该需求→问题：该需求的主体/提出方是谁？]` |
| 边界模糊 | 条件、范围、时限等缺少边界 | `[⨯边界模糊: 试运行期→问题：试运行期的起止条件和时长是？]` |
| 缺少定量指标 | 有需求描述但缺性能指标（定量：数值+单位+条件） | `[⨯缺少定量指标: 批量导入→问题：批量导入的单次上限（数值/单位/条件）是多少？]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→问题：该需求的来源日期和提出方是？]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 主体+边界→问题：该需求的主体是谁、适用时段/条件是？]` |

> 任何需求（FR/NFR）都含需求描述与性能指标（[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)）——缺指标即缺"性能指标"中的定量指标部分。非功能需求缺指标（质量诉求）除要数值外，还须澄清质量属性准确表述与适用对象（见标注纪律 5）。

标注格式（`问题` = 可直接向相关方确认的问句）：

```text
[⨯子类型: 原文片段→问题：<向相关方确认的问句>]
[⨯完整性: 原文/对象→问题：<向相关方确认的问句>]（结构完整性扫描，纪律 6）
[✓已澄清: <相关方确认后的明确内容>]
```

标注纪律：

1. 标“哪里不清楚”，并给出“向相关方确认的问题”；**不代替相关方提供答案或指标数值**
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致：报告中的问题清单与正文中的每处内联标注一一对应
5. **缺少定量指标（非功能分支）路由识别**——识别为非功能需求缺指标（质量诉求：实时/高效/安全/可靠等）时，标 `[⨯缺少定量指标]`，**向相关方澄清定量指标（数值+单位+条件）**；并按 NFR 归组四元组（[91 §九 STR-NFR 归组四元组](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#九非功能需求之系统设计)：关注角色 × 分类维度 × 适用对象线索；**业务/平台语境随 OR 场景归属带出、不单独作拆分维度**）额外澄清可在原文确认的维度，按需生成问句：
   - **质量属性准确表述**——"快"指响应时间还是吞吐量？（喂 ort03 分类维度判定）
   - **适用对象**——约束哪个场景/流程/系统整体？（喂 ort03 适用对象线索）
   - **关注角色/承受者**（必要时）——谁提出/承受该质量诉求？
   标注示例：`[⨯缺少定量指标: 实时→问题：本项为质量诉求。请确认：①质量属性准确表述（响应时间/吞吐量）？②适用对象（哪个场景/流程/系统整体）？③定量指标（目标值+单位+条件）？]`；目标值由相关方确认（不可衡量则不成为需求，[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)），系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 展开
6. **结构完整性扫描（需求结构自洽，独立于六种模糊子类型）**——六类标注完成后，对切分文件整体再扫一遍"文本自证的结构缺口"：只在文本自身制造了未兑现的期待时发问，标 `[⨯完整性: 原文/对象→问题：<问句>]`，三种可自证形态：
   - **分支缺对应面**——文中明确写了「当X时/正常情况」等条件或路径，但缺其对应面（排除：对应面可由上下文明显推出）。示例：`[⨯完整性: 仅描述"已审核"分支→问题：原文只写了已审核路径，"未审核/驳回"是否在需求范围内？]`
   - **闭环缺端**——文中明确描述了业务对象闭环的多个环节，但缺提出/处理/确认一端（对齐 ort01 完整闭环 [91 §1.4]）。示例：`[⨯完整性: 业务对象闭环→问题：文中含"提交/处理"环节，"确认/完结"端未出现——该环节是否存在、归属本片还是他片？]`
   - **引用对象缺失**——文内引用了实体/流程/文档，但全切分文件集无其定义。示例：`[⨯完整性: 引用"审批单"→问题：文中引用的"审批单"在材料集中无定义，是否已由其他需求覆盖或属外部对象？]`
   不标：不基于文本信号的业务覆盖猜测（如"该需求是否还应包含X功能"）——那是需求开发职责，AI 不做（同纪律 1：只出题、不提供答案；此处连"缺什么"也只在文本自证时指出）。

### 3.3 三项条件

**一句话**：每次生成新正文后，用三项条件逐项判定是否已澄清——全过 → 已澄清；任一不过 → 继续澄清。

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有模糊表述（术语不明、主体不明、边界不清、缺少定量指标、信息缺失）与结构完整性缺项已替换为明确内容，且**内容来自相关方确认**（`[✓已澄清]` 由开发者写入相关方答案）；AI 生成的澄清问题不构成已澄清 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注（六类模糊或结构完整性） |

三项全满足 → `生命周期=已澄清`、`AI建议=可以规范化`、`status=clarified`；任一未满足 → 追加新 `[⨯]`，保持 `澄清中`。缺少定量指标按 §三 3.2 纪律 5——定量指标（数值+单位+条件）需相关方确认后才算已澄清；系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 展开，不作为本步待办遗留。结构完整性缺项按 §三 3.2 纪律 6——需相关方确认后才算已澄清；AI 的完整性问句不构成已澄清。

### 3.4 入口规则

**一句话**：本节讲什么材料能进入本步（入口硬条件）、运行路由与批次控制；已进流程的材料再处理（迭代/退回/终止）见 §四 4.1 重进入规则。

**入口硬条件**（Step 3 新增处理）：

| 条件 | 说明 |
|------|------|
| `生命周期=已切分` | 上游 ort01 已完成切分 |
| `人类决策=同意澄清` | 人类明确选入本批澄清 |

`AI建议=可以澄清` 只是候选提示，不作为入口硬条件。`人类决策=空` 的文件跳过，列入待选入澄清提醒。

**运行路由**：前置校验通过后，**先处理已登记的反馈（Step 2），再处理 `生命周期=已切分` + `人类决策=同意澄清` 的新增首轮标注（Step 3）**。已登记的澄清反馈可能把文件推进为 `已澄清` 并开放 ort03 入口，应先落账。

**批次控制**：表 B `人类决策` 是阶段性批次控制字段——文件从 `已切分` 进入澄清时可写 `同意澄清`；澄清完成后，人类可覆盖为 `同意规范化` 作为 ort03 入口；ort03 退回时人类写 `需退回澄清` 触发重新标注（触发后清空）。AI 不应把旧的批次控制值视为锁定值。

> 反馈处理（Step 2）的入口、分支与处理详述见 §五 5.3 反馈处理（反馈类型判读以 §三 3.5 反馈检测判据表为定义单源）；此处只补路由要点：`生命周期=已澄清` 不处理正文、进入规范化选材提示。

### 3.5 反馈检测判据

**一句话**：你在线下/对话给的任何反馈，都统一登记到表 B 内容摘要（`反馈：<类型>`）、处理完追 `[已处理]`——一条路、不散落；Step 1 状态扫描检出，Step 2 按登记处理。

**反馈双通道与单源落点**——反馈统一登记到表 B `内容摘要`（`阶段摘要 ∥ 反馈：<类型>（<要点>）`），处理完追加 `[已处理]`：

| 反馈类型 | 来源 | 登记格式 | 处理 |
|---------|------|---------|------|
| 澄清 | 正文区 `[✓已澄清]`（线下）/ 对话答案（Step 5 AI 代写） | `反馈：澄清（<文件>）` | 读正文区答案 → 生成新正文 → 清理标记 → 三项条件判定 |
| 终止 | 表 B `人类决策=已终止` / 对话指示 | `反馈：终止（<文件>）` | 表 B → `已废弃`、status → `abandoned` |
| 重标 | 对话指示 | `反馈：重标（<文件>：<要点>）` | 重新标注 |

**检出规则**（Step 1，查重幂等）：状态扫描检出正文区 `[✓已澄清]` / 表 B `人类决策=已终止` → 若表 B 内容摘要尚无该文件同类型未处理登记则登记，已有则跳过（只汇总不重复登记）——正文区标记保留至 Step 2 处理时清理。

**多次运行与中断恢复**：`[已处理]` 前 = 待处理（Step 2 每次运行处理一次）；处理后追 `[已处理]` 并清理正文区标记 → 不重复。即使中途中断，下轮 Step 1 对残留标记查重跳过、Step 2 继续处理未 `[已处理]` 的登记。

**对话即处理**：Step 5 对话反馈即时登记到表 B 内容摘要（对话澄清答案由 AI 代写 `[✓已澄清: <答案>]` 到正文区并登记 `反馈：澄清`）并执行处理、追加 `[已处理]`；Step 6「整体确认」提交基线；线下反馈仍由 Step 2 统一处理。

> 本表为反馈类型的**定义单源**（§三 3.4、§五 5.3 引用，不重复定义）。入口状态条件（新选入）见 §三 3.4。

**基线协议（链级不变式）**：每次运行结束 Step 4 用 `scripts/ai-commit.sh` 提交基线（author=EOS-AI + `[AI]` 前缀），并把新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段。ort02 自身检测用状态扫描、不读基线；提交的目的是把 ort02 的产出（切分文件正文区 + 表 B 写入）落基线，为下游 git diff 步骤保持「diff 只含人类变更」的不变式。Step 6「整体确认」后同样提交基线（同 Step 4 机制），避免 AI 自写记录被下次检测误判。

### 3.6 工程化设计原则适配

**一句话**：本节对照四条工程化原则，确认本步的边界——只做需求澄清、不做设计。

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做需求澄清，不做需求分解、评价或设计决策 |
| 文档结对 | 本步不产生文档结对关系；已澄清切分文件是 eos-ort03-norm 的输入 |
| 基于资产 | 原始出处保留，变更结论摘要写入管理区；历史版本由 Git 管理，不复制旧版全文 |

## 四、材料演进：重进入与变更传播

**一句话**：本章讲已进流程的切分文件如何再处理——重进入三种场景（4.1 重进入规则）与变更传播约束（4.2）；状态模型见 §二 2.6，判据见 §三。

### 4.1 重进入规则

**一句话**：已进入澄清的材料再次处理按三种场景分流——澄清迭代（未完成继续）、反向路由（ort03 退回重标）、澄清中途终止。

| 场景 | 触发 | 处理 |
|------|------|------|
| 澄清迭代 | `生命周期=澄清中` + 有 `[✓已澄清]`（Step 1 检出登记） | Step 2 生成新正文 → 三项条件判定（§三 3.3），满足 → `已澄清`；未满足 → 追加新 `[⨯]` 保持 `澄清中` |
| 反向路由（退回重标） | `生命周期=澄清中` + `人类决策=需退回澄清`（ort03 退回） | 重新首轮标注（同首轮动作，见 §五 5.4；`人类决策` 触发后清空、`iteration_count` 重置为 1） |
| 澄清中途终止 | `人类决策=已终止` | 表 B → `已废弃`、AI建议 → `建议终止`、frontmatter.status → `abandoned` |

> 重进入按 91 规范 §A.7 变更传播协议处理（见 §四 4.2）：澄清变更正文影响下游时，必须列出受影响的 OR 与已消费 STR，不得静默声明"下游不受影响"。

### 4.2 变更传播约束

**变更传播约束**（按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议)）：澄清变更正文若影响下游，必须**列出受影响的 OR 与已消费 STR**，不得笼统说"下游不受影响"。反向退回场景中，由 ort03 清理 OR 基线正文区对应 `#body-{seq}`（含分析建议块），本步重新首轮标注后按 §三 3.3 重新判定。

## 五、操作流程

**一句话**：一次运行 = 反馈检测与汇总（Step 1）→ 反馈处理（Step 2）→ 新增处理（Step 3）→ 提交基线（Step 4）→ 反馈交互（Step 5）→ 反馈收尾（Step 6）。Step 1~4 你无需介入；Step 5 保持对话由你反馈、AI 即时处理，Step 6 以「整体确认」收尾（执行模式见白话注）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|-------|
| Start | 前置校验 | 检查状态文档、切分文件与基线就绪 | 无（AI 自动） | 统一 | 就绪/结束 | — |
| 1 | 反馈检测与汇总 | 状态扫描检出 `[✓已澄清]`/表 B 变更 → 登记表 B 内容摘要（查重幂等） | 无（检出你写的澄清/改的表 B） | 统一 | 反馈登记 + 汇总清单 | 表 B 内容摘要 |
| 2 | 反馈处理 | 读表 B 内容摘要未处理反馈 → 生成新正文/终止/重标 → 追 `[已处理]` | 无（AI 处理你已给的反馈） | 统一 | 已澄清正文/废弃记录 | 表 B、切分文件 |
| 3 | 新增处理 | 读取表 B 选入材料，首轮全量标注 + 问题清单 | 无（你之后对话/线下反馈） | 统一 | `[⨯]` 标记 + 标注报告 | 表 B、切分文件 |
| 4 | 提交基线 | ai-commit 提交本轮变更（链级不变式） | 无（AI 自动） | 统一 | 新基线 | git（基线） |
| 5 | 反馈交互 | 输出摘要后不结束对话，自然语言反馈即时处理 | **有**——看摘要、对话反馈 | 对话 | 三区摘要 + 处理摘要 | 表 B |
| 6 | 反馈收尾 | 「整体确认」→ 确认无未处理记录 + 提交基线 + 推进状态 | **有**——「整体确认」/「可以了」 | 对话 | 收尾摘要 | git |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 产出方案后保持对话，你自然语言反馈、AI 即时处理。Step 1~4 为**运行内自动步骤**；Step 5/6 为**交互协议步骤**，由你反馈并「整体确认」收尾。运行结束后你持问题清单线下向相关方澄清、写 `[✓已澄清]`，下轮 Step 1 状态扫描检出。

**反馈机制一句话**：检测用**状态扫描**（表 B + 正文区直接可读）、不用 git diff；处理走**记录 + `[已处理]`** 显式分界（§三 3.5 反馈检测判据）；每次运行**先处理反馈（Step 2）再处理新增（Step 3）**。

### 5.1 Step Start · 前置校验

**一句话**：先确认状态文档、切分文件与基线就绪，再进入 Step 1 反馈检测与汇总。

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示
3. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 中是否存在 `.chunk-*.md` 切分文件；不存在则提示先运行 `eos-ort01-chunk` 并结束
4. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
5. **感知前置确认**：本步反馈检测用**状态扫描**（正文区 `[✓已澄清]` / 表 B 变更，§3.5 反馈检测判据），Step Start 无「无待处理提前退出」判定——**全部就绪后无条件进入 Step 1 反馈检测与汇总**，先检出反馈（含纯线下写 `[✓已澄清]`，表 B 可能无登记）再判入口，不因表 B 无待处理登记而漏检
6. 全部就绪后进入 Step 1 反馈检测与汇总

### 5.2 Step 1 · 反馈检测与汇总

**一句话**：本轮开始先把你在运行间隙的澄清内容（正文区 `[✓已澄清]`）和表 B 变更找出来，登记到表 B 内容摘要并汇总清单——之后 Step 2 基于登记处理。

1. 扫表 B 中 `生命周期=澄清中` 的文件，逐份读正文区检出 `[✓已澄清]` 标记
2. 对每处 `[✓已澄清]`：查重（表 B 内容摘要已有该文件未处理「澄清」登记？）→ 无则登记 `反馈：澄清（<文件名>）`；已有则跳过（只汇总不重复登记）
3. 扫表 B：检出 `人类决策=已终止` 未登记 → 登记 `反馈：终止（<文件名>）`
4. 汇总表 B 内容摘要中既有未处理反馈记录（对话通道 Step 5 写入的），一并列入本轮反馈清单
5. 输出本轮反馈清单：已登记待处理（澄清 N / 终止 K）、待澄清（有 `[⨯]` 无 `[✓已澄清]`）、数据不一致
6. 路由：有反馈登记 → Step 2；有新选入（`已切分`+`同意澄清`）→ Step 3；全无 → 「无待处理对象」结束

> 正文区 `[✓已澄清]` 标记保留至 Step 2 处理时清理；查重保证多次运行不重复登记（中断后残留标记下轮跳过）。

### 5.3 Step 2 · 反馈处理

**一句话**：按表 B 内容摘要的反馈登记逐一处理——澄清→生成新正文、终止→废弃、重标→重新标注，处理完追 `[已处理]`。

读表 B 内容摘要中「含 `反馈：` 且未追加 `[已处理]`」的记录，逐个处理：

| 反馈类型 | 处理（澄清详述见下） |
|---------|------|
| `反馈：澄清（<文件>）` | 读正文区答案 → 生成新正文 → 三项条件判定 → 追 `[已处理]`（步骤见下） |
| `反馈：终止（<文件>）` | 表 B → `已废弃`、AI建议 → `建议终止`、status → `abandoned` → 追 `[已处理]` |
| `反馈：重标（<文件>：<要点>）` | 按要点重新标注 → 更新表 B 与标注报告 → 追 `[已处理]` |

**澄清反馈处理步骤**（对齐 §五 5.4 首轮标注编号模式）：

1. 读正文区 `[✓已澄清: <答案>]`（相关方确认内容）
2. 管理区摘要记录澄清结论（历史由 Git 管理）
3. 按答案替换模糊表述，生成新正文
4. 清理正文区标记与临时报告
5. **三项条件判定**（口径见 §三 3.3）：
   - 满足 → 表 B `已澄清`、AI建议=`可以规范化`、status=`clarified`
   - 未满足 → 追加新 `[⨯]`，表 B 保持 `澄清中`、AI建议=`需继续澄清`
6. 更新 `last_size` / `iteration_count++` / `unresolved_count`
7. 推导文档内嵌状态摘要表
8. 追 `[已处理]`

写回前执行 §二 2.6 同步契约竞态保护（快照/复核，命中 `[需确认]` 不覆盖）；处理后按 §二 2.6 同步契约推导更新文档内嵌状态摘要表。

**待澄清与数据不一致**（不登记不处理，仅在反馈清单中列出）：

- `生命周期=澄清中` + 有 `[⨯]` 无 `[✓已澄清]`：输出迭代报告，等待人类；`iteration_count >= 3` 时提示优先处理
- `生命周期=澄清中` + 无标记：正文已纯净 → 表 B 推进 `已澄清`、status=`clarified` 并提示人类；否则 → 提示数据不一致，等待人类核对

### 5.4 Step 3 · 新增处理

**一句话**：把你新选入澄清的切分文件做首轮全量模糊标注——有模糊进入 `澄清中` 等反馈，无模糊直接推进 `已澄清`。

读取状态文档表 B，按以下规则分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 对应切分文件进入首轮标注 |
| `生命周期=澄清中` + `人类决策=需退回澄清` | 对应切分文件重新首轮标注（同首轮动作；`人类决策` 触发后清空、`iteration_count` 重置为 1，见 §四 4.1 反向路由） |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

首轮标注动作：

1. 通读切分文件正文区
2. 按六种模糊子类型标注全部模糊项（规则见 §三 3.2），并为每处生成「向相关方确认的问题」
3. 做结构完整性扫描（规则见 §三 3.2 纪律 6），对文本自证缺口生成 `[⨯完整性]` 问句
4. 写入模糊标注报告（含待向相关方确认的问题清单）
5. 有模糊项或结构完整性缺项：frontmatter.status 置 `annotated`，表 B 更新为 `生命周期=澄清中`、`AI建议=需继续澄清`、`iteration_count=1`
6. 无模糊项且无结构完整性缺项：frontmatter.status 置 `clarified`，表 B 更新为 `生命周期=已澄清`、`AI建议=可以规范化`
7. 从表 B 推导更新文档内嵌状态摘要表

写回前执行 §二 2.6 同步契约竞态保护；写回顺序按 §二 2.6 同步契约（先表 B，后派生状态）。

### 5.5 Step 4 · 提交基线

**一句话**：AI 把本轮结果提交为 git 基线，维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式；你无需操作。

把本轮 Step 1~3 的处理结果提交为 git 基线。

**为什么需要提交**：ort02 自身检测用状态扫描、不需要基线；但 ort02 的产出（切分文件正文区 + 表 B 写入）若不落基线，会进入下游 git diff 步骤的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B、切分文件；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致）
4. **无变更**：工作区无改动时跳过提交，基线不变

### 5.6 Step 5 · 反馈交互

**一句话**：AI 输出本轮运行摘要后**不结束对话**——你说流程指示（终止/重标/再澄清）或澄清答案，AI 即时理解并处理、追加 `[已处理]`。

先输出三区摘要（本步开场，给人看本轮运行报告与反馈指引）：

```text
══════════════════════════════════════════
  eos-ort02-clarify 本轮完成
══════════════════════════════════════════

当前状态：<澄清中 / 已澄清可规范化 / 已废弃 / 无新增处理>
  处理澄清：<文件名.chunk-001.md>（v{N-1}→v{N}，剩余 M 项模糊）
  新增标注：<文件名.chunk-002.md>（发现 N 项模糊 + 问题清单）
  待澄清：<文件名.chunk-003.md>（有 [⨯] 待澄清）

资产落账：表 B 内容摘要已登记反馈；切分文件状态摘要已同步；基线已提交（<hash>）

一、待反馈（对话 / 线下均可）
  A. 对话反馈 → 直接说明流程指示或澄清答案，AI 即时处理并追加 [已处理]
  B. 线下澄清 → 持问题清单向相关方澄清，将答案写正文区 `[✓已澄清: <相关方确认内容>]`
```

**对话即处理**——AI 输出本摘要后**不结束对话**。人类在对话中直接说明流程指示（终止/重标/再澄清）或澄清答案（如「chunk-002 答案是 300 条/秒」），AI **即时理解并处理**：按 §三 3.5 反馈判据把反馈登记到表 B `内容摘要`（`反馈：澄清（<文件>）`/`反馈：终止（<文件>）`/`反馈：重标（<文件>：<要点>）`），对话澄清答案由 AI 代写 `[✓已澄清: <答案>]` 到正文区并登记 `反馈：澄清`，然后执行对应动作（生成清晰正文 / 终止 / 重标）、追加 `[已处理]`、输出处理摘要，继续等待。**无需口令表**——AI 通过理解自然语言判断反馈意图（「打开状态文档」等辅助请求按自然语言处理）；对话反馈与线下编辑等价（线下编辑仍由 Step 1 检出登记、Step 2 处理）。反馈结束以「整体确认」为准（Step 6）。本步为**交互协议步骤**（执行模式=对话）。

### 5.7 Step 6 · 反馈收尾（整体确认）

**一句话**：你表示反馈结束（「整体确认」/「可以了」）时，AI 确认本轮对话反馈均已处理、提交基线、推进状态。

**动作**：人类表示反馈结束（「整体确认」/「可以了」）时，AI **立即收尾一次**——确认本轮对话反馈均已处理（无未追加 `[已处理]` 的记录）→ **提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交，交接即完整基线）** → 推进状态 → 输出「已确认」摘要。

**为什么必须提交**：否则下次 Step 1 会把 AI 自己的处理误判为人类反馈（正文区代写的 `[✓已澄清]`、表 B 登记）。对话期间你对文档的静默编辑也随收尾一并纳入基线。

**兜底与路由**：本步为**交互协议步骤**（执行模式=对话）。此收尾**不替代 Step 1**——运行结束后你线下写 `[✓已澄清]` 的反馈，仍由 Step 1 下次状态扫描检出登记。**无需口令表**——「整体确认」为自然语言表达；如有仍未处理的已记录反馈，可自然语言要求「继续处理反馈」，AI 重跑 Step 2 后回到 Step 5。
