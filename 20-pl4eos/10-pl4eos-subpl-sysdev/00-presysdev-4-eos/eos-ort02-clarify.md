## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把切分文件从"能读"推进到"能规范化"——定位每处模糊，让人类确认后形成清晰完整的新正文，确保不再有歧义。
>
> **目标**（回答"本步要达到什么"；承担与边界见 §1.3）：
> 1. **识别澄清对象**——读取表 B 中 `生命周期=已切分` 且 `人类决策=同意澄清` 的切分文件（Step 3）
> 2. **全量标注模糊项**——按六种子类型定位全部需澄清内容，写入 `[⨯]` 标记，并为每处生成「向相关方确认的问题」、汇总入模糊标注报告（Step 3）
> 3. **检测并登记反馈**——状态扫描检出正文区 `[✓已澄清]` 与表 B 变更，登记到表 B 内容摘要（查重幂等）（Step 1）
> 4. **处理反馈**——按表 B 内容摘要登记生成清晰正文 / 终止 / 重标，追 `[已处理]`（Step 2）
> 5. **执行三项评估**——判断正文清晰完整、历史模糊已澄清、无新增模糊（Step 2）
> 6. **交互与汇总**——对话收集流程指示与澄清答案，「汇总」落账并提交基线（Step 5/6）
> 7. **同步状态接口**——维护表 B 生命周期、AI 建议、frontmatter.status、迭代计数和未解决数量（Step 1/2/4）

### 1.2 人机交接点总览

**一句话**：你在本步有四个参与点——选入澄清、**对话反馈**、**线下澄清**、终止/放行。AI 标注时给每处模糊配了「向相关方确认的问题」；你可在线下向相关方问清后把答案写回正文区 `[✓已澄清: <相关方确认内容>]`，也可在运行内 Step 5/6 对话中直接给流程指示或澄清答案——两条通道都会落账处理。

| 人类参与点 | 在哪操作 | 做什么 |
|-----------|---------|--------|
| ① 选入澄清 | 状态文档表 B | 对 `已切分` 切分文件设 `人类决策=同意澄清` |
| ② 对话反馈 | 对话（Step 5/6） | 给流程指示（终止/重标/再澄清）或澄清答案，AI 只收集，「汇总」后落表 B 内容摘要 |
| ③ 线下澄清 | 切分文件正文区 | 持问题清单向相关方澄清后写 `[✓已澄清: <相关方确认内容>]`（或保留 `[⨯]` 暂不处理） |
| ④ 终止 / 选入规范化 | 状态文档表 B | 对中止的文件设 `人类决策=已终止`；对 `已澄清` 文件设 `人类决策=同意规范化` → 进入 ort03 |

> AI 凭什么这么标（六种子类型）见 §3.4 模糊标注规则；反馈如何被检出、登记与处理见 §3.2 反馈机制。

### 1.3 本步负责与不负责

本 Skill 负责：

1. **接收**——从表 B 读取本轮选入澄清的切分文件（Step 3）
2. **标注**——通读正文，按五类模糊子类型生成行内 `[⨯]` 标记，并为每处生成「向相关方确认的问题」（Step 3）
3. **检测登记**——状态扫描检出正文区 `[✓已澄清]` / 表 B 变更，登记到表 B 内容摘要（查重幂等）（Step 1）
4. **报告**——输出首轮标注报告或迭代报告（Step 3/2）
5. **处理**——按表 B 内容摘要登记生成新正文 / 终止 / 重标，追 `[已处理]`（Step 2）
6. **评估**——按三项条件决定 `已澄清` 或继续 `澄清中`（Step 2）
7. **交互汇总**——Step 5 对话收集反馈，Step 6「汇总」落账并提交基线（Step 5/6）
8. **落账**——更新表 B、frontmatter.status 和文档内嵌状态摘要表（Step 2/3，同步契约见 §3.2）
9. **交接**——输出待选入澄清、待反馈、待选入规范化清单（Step End）

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 语义切分和切分方案执行（由 eos-ort01-chunk 负责）
3. OR 条目规范化、编号、分类和冲突检测（由 eos-ort03-norm 负责）
4. 代替开发者或需求提出方确认业务事实（AI 只生成问题、不提供答案；缺少定量指标由相关方确认目标值，AI 不发明指标数值）
5. 将澄清内容扩展为设计方案或下游需求分解

## 二、澄清核心概念与分工

**一句话**：本章回答四个问题——什么是"模糊"、什么是"已澄清"、澄清怎么做、AI 做哪些澄清工作；细节规则见后续章节（§三 设计基础、§四 操作流程、§五 模板）。

### 2.1 什么是模糊

**一句话**：模糊 = 需求表述里"没说清"的地方——读不出确切含义或无法衡量，下游（规范化/需求开发）无法直接使用；它是澄清要处理的对象。

按 [通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)，任何需求（FR/NFR）都由**需求描述**和**性能指标**构成，不可衡量则不成为需求。**模糊 = 需求的构成要素缺失或表述不清**——需求描述不清（读不出**术语含义**、**动作主体**、**边界范围**、**必要元信息**），或**性能指标缺失**（有描述没指标、无法衡量）。

六种子类型（标注规则见 §3.4）：

| 子类型 | 一句话 |
|--------|--------|
| 术语模糊 | 业务/领域术语表述不明确 |
| 主体/客体不明 | 动作主体或作用对象不可识别 |
| 边界模糊 | 条件、范围、时限等缺少边界 |
| 缺少定量指标 | 有需求描述但缺性能指标（数值+单位+条件）——FR/NFR 均适用 |
| 信息缺失 | 缺来源、时间、提出方等元信息 |
| 多重模糊 | 同一处存在两种以上模糊 |

> **缺少定量指标** = 需求缺"性能指标"中的定量指标部分（如"支持批量导入"缺单次上限、"实时响应"缺目标值）。功能需求与非功能需求同构适用——澄清时 AI 都向相关方要 数值+单位+条件（非功能分支还须澄清质量属性准确表述与适用对象，见 §3.4 纪律 5）。

### 2.2 什么是已澄清

**一句话**：已澄清 = 澄清迭代的完成态——正文里每处模糊都被相关方确认的明确内容替换干净，可以送规范化了。

判定需同时满足三项条件（正式判定口径见 §3.5）：

| 条件 | 判定要点 |
|------|---------|
| ① 正文清晰完整 | 模糊表述（术语不明、主体不明、边界不清、缺少定量指标、信息缺失）已替换为明确内容，且**内容来自相关方确认**——AI 生成的澄清问题不算已澄清 |
| ② 历史模糊项已澄清 | 每处旧 `[⨯]` 都有对应 `[✓已澄清]` 注释 |
| ③ 无新增模糊 | 新正文通读后不再产生新的 `[⨯]` 标注 |

| 结果 | 状态落账 |
|------|---------|
| 三项全满足 → **已澄清** | 生命周期=`已澄清`、AI建议=`可以规范化`、frontmatter.status=`clarified`、正文区为纯净版本 |
| 任一未满足 → **澄清中** | 保持 `澄清中`、AI建议=`需继续澄清`，回到 §2.3 循环继续 |

> **"已澄清"≠"澄清中"**：已澄清 = 模糊项已全部由相关方确认、可送 ort03 规范化；澄清中 = 仍有未确认模糊项，继续迭代。

### 2.3 澄清怎么做

**一句话**：澄清 = 一轮「AI 出题 → 开发者问相关方要答案 → AI 成文」的循环，一次可能不干净，会反复多轮直到三项条件满足。

| 环节 | 谁做 | 动作 | 产物 |
|------|------|------|------|
| ① 标注 | AI | 标 `[⨯]` + 为每处生成「向相关方确认的问题」（六种子类型，§3.4） | `[⨯]` 标记 + 问题清单报告 |
| ② 澄清 | 开发者（向相关方确认） | **双通道**：对话给答案 / 线下持问题清单向相关方问清后写 `[✓已澄清: <相关方确认内容>]`（§1.2） | `[✓已澄清]` 注释（相关方确认内容） |
| ③ 处理 | AI | 检出登记 → 按答案生成新正文 → 三项评估（§四 操作流程） | 清晰正文 / 保持 `澄清中` |

> 相关方是答案的来源，开发者负责问与写回；AI 只出问题、不提供答案（§3.4 纪律 1）。

澄清以**迭代**方式推进：处理完可能仍有未清晰项 → 追加新 `[⨯]` → 回到 ② 继续澄清，直到三项条件满足。

> **直觉走一遍**：原文「生产物料由**外购件**组成」→ AI 标 `[⨯术语模糊: 外购件→问题："外购件"的确切定义和范围是？]` → 你问采购相关方，答「外购件指需对外采购的原材料与标准件」→ 你在正文写 `[✓已澄清: 外购件指需对外采购的原材料与标准件]` → AI 检出登记、按答案生成新正文并评估。

### 2.4 AI 做哪些澄清工作

**一句话**：AI 跑「标注 → 检出登记 → 处理 → 评估 → 汇总」的自动化循环；四条红线划清边界——答案、指标、设计都由你把关。

**AI 自动做**（本步核心循环）：

| AI 做 | 一句话说明 |
|-------|-----------|
| 标注 | 标 `[⨯]` + 为每处生成向相关方确认的问题（§3.4） |
| 检出登记 | 状态扫描检出 `[✓已澄清]` / 表 B 变更 → 登记表 B 内容摘要（§3.2 反馈机制） |
| 处理 | 按登记生成新正文 / 终止 / 重标，追 `[已处理]`（§4.3） |
| 评估 | 三项条件判定 `已澄清` 或继续 `澄清中`（§4.3） |
| 交互汇总 | Step 5 对话收集 + Step 6「汇总」落账（§4.6/§4.7） |

**AI 绝不做**（四条红线）：

| AI 不做 | 为什么 |
|---------|--------|
| 代替开发者/相关方确认业务事实——只出问题、不提供答案（§3.4 纪律 1） | 业务事实只有相关方知道 |
| 给非功能需求发明指标数值——目标值由相关方确认（§3.4 纪律 5） | 指标由相关方定，AI 不发明 |
| 对话澄清答案未经确认不代写（§1.3） | 答案必须经你确认后才落正文 |
| 把澄清内容扩展为设计方案或下游需求分解（§1.3） | 本步只做需求澄清、不做设计 |

> 本表只列与「澄清工作」直接相关的边界；本步整体不负责的项（原始材料文本化、语义切分、OR 规范化）见 §1.3。

## 三、澄清设计基础

**一句话**：本章讲本步处理的切分文档结构、澄清生命周期怎么追踪（状态）、反馈怎么检测与处理、入口规则与工程化原则；**模糊标注与三项评估的具体规则见 §3.4/§3.5**。

### 3.1 切分文档结构

**一句话**：本步原地处理切分文件（`{原始文件名}.chunk-{seq}.md`），把正文区的模糊表述澄清成清晰版本。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 更新 `status`（raw→annotated→clarified→abandoned） |
| 管理区 | 状态摘要、澄清决策记录 | 更新文档内嵌状态摘要表，追加澄清决策记录 |
| 正文区 | 原文 + `[⨯]` 标注 + `[✓已澄清]` 注释 + 报告（临时） | 首轮写入标注和报告；迭代后替换为新正文；终态保持纯原文 |

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓]` 标记和临时报告。历史版本由 Git 管理，不在文档内归档旧版。

### 3.2 文档生命周期管理

**一句话**：本步通过状态文档表 B 推进切分文件的澄清生命周期——记录每个切分文件的澄清进度、迭代轮次和剩余模糊项。本章分两块看：**状态怎么追踪**（表 B 字段 + 同步契约）与**反馈怎么检测与处理**（正文区标记 + 表 B 人类决策）。

#### 状态模型（状态怎么追踪）

表 B — 切分文件处理进度是本步权威源。一条记录的三要素与其他步骤一致：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段：`已切分` → `澄清中` → `已澄清` / `已废弃` |
| AI建议 | 提示字段：`可以澄清` / `需继续澄清` / `可以规范化` / `建议终止`（本步生命周期段取值；全集见状态文档表B） |
| 人类决策 | 批次控制字段：`同意澄清` / `需退回澄清` / `同意规范化` / `已终止` / 空 |

澄清特有的追踪字段：

| 字段 | 职责 |
|------|------|
| last_size | 最近一次正文长度或标注规模记录 |
| iteration_count | 澄清迭代轮次 |
| unresolved_count | 当前未解决模糊项数量 |

**同步契约**：本步先更新状态文档表 B，再推导写入文档内嵌状态摘要表和 frontmatter.status。不一致时以表 B 为准重建派生状态。写回前执行竞态保护——检测表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类（Step 2/3 写回前均引用本条）。

#### 反馈机制（反馈怎么检出、登记与处理）

**反馈双通道与单源落点**——反馈统一登记到表 B `内容摘要`（`阶段摘要 ∥ 反馈：<类型>（<要点>）`），处理完追加 `[已处理]`：

| 反馈类型 | 来源 | 登记格式 | 处理 |
|---------|------|---------|------|
| 澄清 | 正文区 `[✓已澄清]`（线下）/ 对话答案（Step 6 AI 代写） | `反馈：澄清（<文件>）` | 读正文区答案 → 生成新正文 → 清理标记 → 三项评估 |
| 终止 | 表 B `人类决策=已终止` / 对话指示 | `反馈：终止（<文件>）` | 表 B → `已废弃`、status → `abandoned` |
| 重标 | 对话指示 | `反馈：重标（<文件>：<要点>）` | 重新标注 |

**检出规则（Step 1，查重幂等）**：状态扫描检出正文区 `[✓已澄清]` / 表 B `人类决策=已终止` → 若表 B 内容摘要尚无该文件同类型未处理登记则登记，已有则跳过（只汇总不重复登记）——正文区标记保留至 Step 2 处理时清理。

**多次运行与中断恢复**：`[已处理]` 前 = 待处理（Step 2 每次运行处理一次）；处理后追 `[已处理]` 并清理正文区标记 → 不重复。即使中途中断，下轮 Step 1 对残留标记查重跳过、Step 2 继续处理未 `[已处理]` 的登记。

**交互只记录不处理**：Step 5 对话反馈只收集；Step 6「汇总」一次性登记到表 B 内容摘要（对话澄清答案由 AI 代写 `[✓已澄清: <答案>]` 到正文区并登记 `反馈：澄清`）+ 提交基线；Step 2 统一处理。

> 本表为反馈类型的**定义单源**（§3.3、§4.3 引用，不重复定义）。入口状态条件（新选入）见 §3.3。

**基线协议（链级不变式）**：每次运行结束 Step 4 用 `scripts/ai-commit.sh` 提交基线（author=EOS-AI + `[AI]` 前缀），并把新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段。ort02 自身检测用状态扫描、不读基线；提交的目的是把 ort02 的产出（切分文件正文区 + 表 B 写入）落基线，为下游 git diff 步骤保持「diff 只含人类变更」的不变式。Step 6 汇总后同样提交基线（同 Step 4 机制），避免 AI 自写记录被下次检测误判。

### 3.3 入口与重进入规则

**一句话**：本步只处理人类在表 B 明确选入（`同意澄清`）的切分文件；每次运行先处理已登记的反馈（Step 2），再处理新选入的（Step 3）。

Step 3（新增处理）的入口硬条件：

| 条件 | 说明 |
|------|------|
| `生命周期=已切分` | 上游 ort01 已完成切分 |
| `生命周期=澄清中` + `人类决策=需退回澄清` | ort03 退回需重新澄清（反向路由） |
| `人类决策=同意澄清` | 人类明确选入本批澄清 |

`AI建议=可以澄清` 只是候选提示，不作为入口硬条件。

运行路由参考 `wft01-biz`：前置校验通过后，**先处理已登记的反馈（Step 2），再处理 `生命周期=已切分` + `人类决策=同意澄清` 的新增首轮标注（Step 3）**。已登记的澄清反馈可能把文件推进为 `已澄清` 并开放 ort03 入口，应先落账。

表 B `人类决策` 是阶段性批次控制字段：文件从 `已切分` 进入澄清时可写 `同意澄清`；澄清完成后，人类可覆盖为 `同意规范化` 作为 ort03 入口；ort03 退回时人类可写 `需退回澄清` 触发重新标注（触发后清空）。AI 不应把旧的批次控制值视为锁定值。

反馈处理（Step 2）的入口和分支——反馈类型判读以 §3.2 反馈机制表为定义单源，此处只补路由要点：

- 表 B 内容摘要「含 `反馈：` 且未追 `[已处理]`」的记录 → 按反馈类型处理（澄清/终止/重标）
- `生命周期=澄清中` + 有 `[⨯]` 无 `[✓已澄清]`：待澄清，不登记不处理，输出迭代报告等待人类
- `生命周期=澄清中` + 无标记：数据不一致——正文已纯净 → 表 B 推进 `已澄清` 并提示人类；否则 → 提示核对
- `生命周期=已澄清`：不处理正文，进入规范化选材提示

### 3.4 模糊标注规则

**一句话**：模糊标注就是把"没说清"的地方用 `[⨯]` 标出来，并告诉开发者该向相关方确认什么——AI 生成问句，开发者持清单去澄清。

六种模糊子类型：

| 子类型 | 适用场景 | 标注示例（AI 生成向相关方确认的问题） |
|--------|---------|---------|
| 术语模糊 | 业务/领域术语表述不明确 | `[⨯术语模糊: 外购件→问题："外购件"的确切定义和范围是？]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明: 提出该需求→问题：该需求的主体/提出方是谁？]` |
| 边界模糊 | 条件、范围、时限等缺少边界 | `[⨯边界模糊: 试运行期→问题：试运行期的起止条件和时长是？]` |
| 缺少定量指标 | 有需求描述但缺性能指标（定量：数值+单位+条件） | `[⨯缺少定量指标: 批量导入→问题：批量导入的单次上限（数值/单位/条件）是多少？]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→问题：该需求的来源日期和提出方是？]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 主体+边界→问题：该需求的主体是谁、适用时段/条件是？]` |

> 任何需求（FR/NFR）都含需求描述与性能指标（[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)）——缺指标即缺"性能指标"中的定量指标部分。非功能需求缺指标（质量诉求）除要数值外，还须澄清质量属性准确表述与适用对象（见标注纪律 5）。

标注格式（`问题` = 可直接向相关方确认的问句）：

```text
[⨯子类型: 原文片段→问题：<向相关方确认的问句>]
[✓已澄清: <相关方确认后的明确内容>]
```

标注纪律：

1. 标“哪里不清楚”，并给出“向相关方确认的问题”；**不代替相关方提供答案或指标数值**
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致：报告中的问题清单与正文中的每处内联标注一一对应
5. **缺少定量指标（非功能分支）路由识别**——识别为非功能需求缺指标（质量诉求：实时/高效/安全/可靠等）时，标 `[⨯缺少定量指标]`，**向相关方澄清定量指标（数值+单位+条件）**；并按 NFR 四元组（[91 §九 STR-NFR 归组四元组](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#9-非功能需求之系统设计)：关注角色 × 分类维度 × 适用对象线索）额外澄清可在原文确认的维度，按需生成问句：
   - **质量属性准确表述**——"快"指响应时间还是吞吐量？（喂 ort03 分类维度判定）
   - **适用对象**——约束哪个场景/流程/系统整体？（喂 ort03 适用对象线索）
   - **关注角色/承受者**（必要时）——谁提出/承受该质量诉求？
   标注示例：`[⨯缺少定量指标: 实时→问题：本项为质量诉求。请确认：①质量属性准确表述（响应时间/吞吐量）？②适用对象（哪个场景/流程/系统整体）？③定量指标（目标值+单位+条件）？]`；目标值由相关方确认（不可衡量则不成为需求，[通用设计规范 §1.2](../../../00-generalspec/01-generalspec-sysdev.md#12-需求详解)），系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 展开

### 3.5 三项条件

迭代生成新正文后，必须逐项判定：

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有模糊表述（术语不明、主体不明、边界不清、缺少定量指标、信息缺失）已替换为明确内容，且**内容来自相关方确认**（`[✓已澄清]` 由开发者写入相关方答案）；AI 生成的澄清问题不构成已澄清 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注 |

三项全满足 → `生命周期=已澄清`、`AI建议=可以规范化`、`status=clarified`。仍有未清晰项 → 追加新 `[⨯]` 标注，保持 `澄清中`。缺少定量指标按 §3.4 纪律 5 澄清——定量指标（数值+单位+条件）需相关方确认后才算已澄清；系统侧指标设计（统计口径/测量方法/验收条件）由 wft04-nfr 展开，不作为本步"未清晰"待办遗留。

### 3.6 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做需求澄清，不做需求分解、评价或设计决策 |
| 文档结对 | 本步不产生文档结对关系；已澄清切分文件是 eos-ort03-norm 的输入 |
| 基于资产 | 原始出处保留，变更结论摘要写入管理区；历史版本由 Git 管理，不复制旧版全文 |

## 四、操作流程

**一句话**：一次运行 = 反馈检测与汇总（Step 1）→ 反馈处理（Step 2）→ 新增处理（Step 3）→ 提交基线（Step 4）→ 交互收集反馈（Step 5）→ 变更汇总（Step 6）。运行内 AI 自动执行 Step 1~4；Step 5/6 为**交互协议步骤**，由你结束或触发；运行结束后你可**持问题清单线下向相关方澄清**，写 `[✓已澄清]` 由下轮 Step 1 检出（见 §1.2）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|-------|
| Start | 前置校验 | 检查状态文档、切分文件与基线就绪 | 无（AI 自动） | 统一 | 就绪/结束 | — |
| 1 | 反馈检测与汇总 | 状态扫描检出 `[✓已澄清]`/表 B 变更 → 登记表 B 内容摘要（查重幂等） | 无（AI 检出你在运行间隙写的澄清内容/改的表 B） | 统一 | 反馈登记 + 汇总清单 | 表 B 内容摘要 |
| 2 | 反馈处理 | 读表 B 内容摘要未处理反馈 → 生成新正文/终止/重标 → 追 `[已处理]` | 无（AI 处理你已给的反馈） | 统一 | 已澄清正文/废弃记录 | 表 B、切分文件 |
| 3 | 新增处理 | 读取表 B 选入材料，首轮全量标注 + 问题清单 | 无（AI 标注，你之后对话/线下反馈） | 统一 | `[⨯]` 标记 + 标注报告 | 表 B、切分文件 |
| 4 | 提交基线 | ai-commit 提交本轮变更（链级不变式） | 无（AI 自动） | 统一 | 新基线 | git（基线） |
| 5 | 反馈交互 | 输出本轮摘要 + 保持对话收集反馈（只记录不处理） | **有**——看摘要、对话反馈、辅助口令 | 对话 | 三区摘要 + 已收集反馈 | — |
| 6 | 变更汇总 | 「汇总」口令 → 对话反馈落表 B + 提交基线 | **有**——「汇总」/「继续」口令 | 口令触发 | 反馈汇总 | 表 B、正文区、git |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话/口令触发 = 需要你说句话（反馈或口令）AI 才继续。Step 1~4 为运行内自动步骤；Step 5/6 为交互协议步骤。运行结束后你持问题清单线下向相关方澄清、写 `[✓已澄清]`，下轮 Step 1 状态扫描检出。

核心驱动逻辑：Step 1 状态扫描检出并登记反馈 → **先处理反馈（Step 2）再处理新增（Step 3）** → Step 4 提交基线 → Step 5 输出摘要并对话收集 → Step 6「汇总」落账。反馈检测用**状态扫描**（表 B + 正文区直接可读）、不用 git diff；反馈处理走**记录 + `[已处理]`** 显式分界（见 §3.2 反馈机制）。

### 4.1 Step Start · 前置校验

**一句话**：先确认状态文档、切分文件与基线就绪，再进入 Step 1 反馈检测与汇总。

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示
3. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 中是否存在 `.chunk-*.md` 切分文件；不存在则提示先运行 `eos-ort01-chunk` 并结束
4. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
5. 全部就绪后进入 Step 1 反馈检测与汇总

### 4.2 Step 1 · 反馈检测与汇总

**一句话**：本轮开始先把你在运行间隙的澄清内容（正文区 `[✓已澄清]`）和表 B 变更找出来，登记到表 B 内容摘要并汇总清单——之后 Step 2 基于登记处理。

1. 扫表 B 中 `生命周期=澄清中` 的文件，逐份读正文区检出 `[✓已澄清]` 标记
2. 对每处 `[✓已澄清]`：查重（表 B 内容摘要已有该文件未处理「澄清」登记？）→ 无则登记 `反馈：澄清（<文件名>）`；已有则跳过（只汇总不重复登记）
3. 扫表 B：检出 `人类决策=已终止` 未登记 → 登记 `反馈：终止（<文件名>）`
4. 汇总表 B 内容摘要中既有未处理反馈记录（对话通道 Step 6 写入的），一并列入本轮反馈清单
5. 输出本轮反馈清单：已登记待处理（澄清 N / 终止 K）、待澄清（有 `[⨯]` 无 `[✓已澄清]`）、数据不一致
6. 路由：有反馈登记 → Step 2；有新选入（`已切分`+`同意澄清`）→ Step 3；全无 → 「无待处理对象」结束

> 正文区 `[✓已澄清]` 标记保留至 Step 2 处理时清理；查重保证多次运行不重复登记（中断后残留标记下轮跳过）。

### 4.3 Step 2 · 反馈处理

**一句话**：按表 B 内容摘要的反馈登记逐一处理——澄清→生成新正文、终止→废弃、重标→重新标注，处理完追 `[已处理]`。

读表 B 内容摘要中「含 `反馈：` 且未追加 `[已处理]`」的记录，逐个处理：

| 反馈类型 | 处理 |
|---------|------|
| `反馈：澄清（<文件>）` | 读正文区 `[✓已澄清: <答案>]` → 管理区摘要记录澄清结论（历史由 Git 管理）→ 按答案替换模糊表述生成新正文 → 清理正文区标记与临时报告 → **三项条件评估**：满足 → 表 B `已澄清`、`AI建议=可以规范化`、status=`clarified`；未满足 → 追加新 `[⨯]`，表 B 保持 `澄清中`、`AI建议=需继续澄清` → 更新 `last_size`/`iteration_count++`/`unresolved_count` → 推导文档内嵌状态摘要表 → 追 `[已处理]` |
| `反馈：终止（<文件>）` | 表 B → `已废弃`、AI建议 → `建议终止`、status → `abandoned` → 追 `[已处理]` |
| `反馈：重标（<文件>：<要点>）` | 按要点重新标注 → 更新表 B 与标注报告 → 追 `[已处理]` |

写回前执行 §3.2 同步契约竞态保护（快照/复核，命中 `[需确认]` 不覆盖）；处理后按 §3.2 同步契约推导更新文档内嵌状态摘要表。

**待澄清与数据不一致**（不登记不处理，仅在反馈清单中列出）：

- `生命周期=澄清中` + 有 `[⨯]` 无 `[✓已澄清]`：输出迭代报告，等待人类；`iteration_count >= 3` 时提示优先处理
- `生命周期=澄清中` + 无标记：正文已纯净 → 表 B 推进 `已澄清`、status=`clarified` 并提示人类；否则 → 提示数据不一致，等待人类核对

### 4.4 Step 3 · 新增处理

**一句话**：把你新选入澄清的切分文件做首轮全量模糊标注——有模糊进入 `澄清中` 等反馈，无模糊直接推进 `已澄清`。

读取状态文档表 B，按以下规则分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 对应切分文件进入首轮标注 |
| `生命周期=澄清中` + `人类决策=需退回澄清` | 对应切分文件重新首轮标注（同首轮动作；`人类决策` 触发后清空、`iteration_count` 重置为 1） |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

首轮标注动作：

1. 通读切分文件正文区
2. 按六种子类型标注全部模糊项，并为每处生成「向相关方确认的问题」
3. 写入模糊标注报告（含待向相关方确认的问题清单）
