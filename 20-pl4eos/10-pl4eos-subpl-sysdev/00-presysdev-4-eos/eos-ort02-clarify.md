## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把切分文件从"能读"推进到"能规范化"——定位每处模糊，让人类确认后形成清晰完整的新正文，确保不再有歧义。
>
> **目标**（回答"本步要达到什么"；承担与边界见 §1.3）：
> 1. **识别澄清对象**——读取表 B 中 `生命周期=已切分` 且 `人类决策=同意澄清` 的切分文件（Step 2）
> 2. **全量标注模糊项**——按五种子类型定位全部需澄清内容，写入 `[⨯]` 标记和模糊标注报告（Step 2）
> 3. **驱动人类澄清**——通过正文区 `[✓已澄清: ...]` 注释接收人类/相关方确认结果（Step 1）
> 4. **生成清晰正文**——按澄清注释生成新正文，变更结论摘要写入管理区（历史版本由 Git 管理）（Step 1）
> 5. **执行三项评估**——判断正文清晰完整、历史模糊已澄清、无新增模糊（Step 1）
> 6. **同步状态接口**——维护表 B 生命周期、AI 建议、frontmatter.status、迭代计数和未解决数量（Step 1/2）

### 1.2 人机交接点总览

**一句话**：你在本步有三个参与点——选入澄清、写澄清反馈、终止/放行。反馈走「正文区编辑 + 表 B 状态」——在正文区直接写 `[✓已澄清]`、改表 B `人类决策` 即反馈，AI 用状态扫描自动检出，不必另行说明。

| 人类参与点 | 在哪操作 | 做什么 |
|-----------|---------|--------|
| ① 选入澄清 | 状态文档表 B | 对 `已切分` 切分文件设 `人类决策=同意澄清` |
| ② 写澄清反馈 | 切分文件正文区 | 对 `[⨯]` 标注直接追加 `[✓已澄清: ...]` 注释（或保留 `[⨯]` 暂不处理） |
| ③ 终止 / 选入规范化 | 状态文档表 B | 对中止的文件设 `人类决策=已终止`；对 `已澄清` 文件设 `人类决策=同意规范化` → 进入 ort03 |

> AI 凭什么这么标（五种子类型）见 §2.4 模糊标注规则；反馈如何被检测与处理见 §2.2 反馈机制。

### 1.3 本步负责与不负责

本 Skill 负责：

1. **接收**——从表 B 读取本轮选入澄清的切分文件（Step 2）
2. **标注**——通读正文，按五类模糊子类型生成行内 `[⨯]` 标记（Step 2）
3. **报告**——输出首轮标注报告或迭代报告（Step 2/1）
4. **迭代**——读取 `[✓已澄清]` 注释，生成新正文（历史由 Git 管理，不归档旧版）（Step 1）
5. **评估**——按三项条件决定 `已澄清` 或继续 `澄清中`（Step 1）
6. **落账**——更新表 B、frontmatter.status 和文档内嵌状态摘要表（Step 1/2，同步契约见 §2.2）
7. **交接**——输出待选入澄清、待反馈标注、待选入规范化清单（Step End）

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 语义切分和切分方案执行（由 eos-ort01-chunk 负责）
3. OR 条目规范化、编号、分类和冲突检测（由 eos-ort03-norm 负责）
4. 代替人类或需求提出方确认业务事实
5. 将澄清内容扩展为设计方案或下游需求分解

## 二、澄清设计基础

**一句话**：本章讲本步处理的切分文档结构、澄清生命周期怎么追踪（状态）、反馈怎么检测与处理、入口规则与工程化原则；**模糊标注与三项评估的具体规则见 §2.4/§2.5**。

### 2.1 切分文档结构

**一句话**：本步原地处理切分文件（`{原始文件名}.chunk-{seq}.md`），把正文区的模糊表述澄清成清晰版本。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 更新 `status`（raw→annotated→clarified→abandoned） |
| 管理区 | 状态摘要、澄清决策记录 | 更新文档内嵌状态摘要表，追加澄清决策记录 |
| 正文区 | 原文 + `[⨯]` 标注 + `[✓已澄清]` 注释 + 报告（临时） | 首轮写入标注和报告；迭代后替换为新正文；终态保持纯原文 |

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓]` 标记和临时报告。历史版本由 Git 管理，不在文档内归档旧版。

### 2.2 文档生命周期管理

**一句话**：本步通过状态文档表 B 推进切分文件的澄清生命周期——记录每个切分文件的澄清进度、迭代轮次和剩余模糊项。本章分两块看：**状态怎么追踪**（表 B 字段 + 同步契约）与**反馈怎么检测与处理**（正文区标记 + 表 B 人类决策）。

#### 状态模型（状态怎么追踪）

表 B — 切分文件处理进度是本步权威源。一条记录的三要素与其他步骤一致：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段：`已切分` → `澄清中` → `已澄清` / `已废弃` |
| AI建议 | 提示字段：`可以澄清` / `需继续澄清` / `可以规范化` / `建议终止`（本步设置值；全集见状态文档表B） |
| 人类决策 | 批次控制字段：`同意澄清` / `同意规范化` / `已终止` / 空 |

澄清特有的追踪字段：

| 字段 | 职责 |
|------|------|
| last_size | 最近一次正文长度或标注规模记录 |
| iteration_count | 澄清迭代轮次 |
| unresolved_count | 当前未解决模糊项数量 |

**同步契约**：本步先更新状态文档表 B，再推导写入文档内嵌状态摘要表和 frontmatter.status。不一致时以表 B 为准重建派生状态。写回前执行竞态保护——检测表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类（Step 1/2 写回前均引用本条）。

#### 反馈机制（反馈怎么检测与处理）

**反馈载体即正文区标记与表 B 字段**：人类在正文区写 `[✓已澄清]` 注释（或保留 `[⨯]` 等待）、在表 B 改 `人类决策` 即反馈。AI 通过**状态条件扫描**直接发现并处理（状态自终止——处理后正文区回归纯净、表 B 转 `已澄清`，条件不再成立，无需 `[已处理]` 记录分离）：

| 表 B / 正文区 状态条件 | 判读 | 处理 |
|------------------------|------|------|
| `生命周期=澄清中` + 正文区有 `[✓已澄清]` | 澄清反馈 | 生成新正文 → 三项条件评估 |
| `生命周期=澄清中` + 有 `[⨯]` 无 `[✓已澄清]` | 待澄清 | 输出迭代报告，等待人类 |
| `生命周期=澄清中` + 无标记 | 数据不一致 | 以正文区实际状态为准：正文已纯净 → 表 B 推进 `已澄清`、status→`clarified` 并提示人类；否则 → 提示核对 |
| `人类决策=已终止` | 终止 | 表 B → `已废弃`、status → `abandoned` |
| `生命周期=已切分` + `人类决策=同意澄清` | 新选入 | 首轮标注（Step 2） |

> 本表为反馈/入口状态条件的**定义单源**（§2.3、§3.2 引用本表，不重复定义）。

**基线协议（链级不变式）**：每次运行结束 Step 3 用 `scripts/ai-commit.sh` 提交基线（author=EOS-AI + `[AI]` 前缀），并把新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段。ort02 自身检测用状态扫描、不读基线；提交的目的是把 ort02 的产出（切分文件正文区 + 表 B 写入）落基线，为下游 git diff 步骤（ort03 推广后）保持「diff 只含人类变更」的不变式。

### 2.3 入口与重进入规则

**一句话**：本步只处理人类在表 B 明确选入（`同意澄清`）的切分文件；每次运行先处理已有澄清反馈的，再处理新选入的。

Step 2（新增处理）的入口硬条件：

| 条件 | 说明 |
|------|------|
| `生命周期=已切分` | 上游 ort01 已完成切分 |
| `人类决策=同意澄清` | 人类明确选入本批澄清 |

`AI建议=可以澄清` 只是候选提示，不作为入口硬条件。

运行路由参考 `wft01-biz`：前置校验通过后，**先处理 `生命周期=澄清中` 的反馈/迭代（Step 1），再处理 `生命周期=已切分` + `人类决策=同意澄清` 的新增首轮标注（Step 2）**。已存在的澄清反馈可能把文件推进为 `已澄清` 并开放 ort03 入口，应先落账。

表 B `人类决策` 是阶段性批次控制字段：文件从 `已切分` 进入澄清时可写 `同意澄清`；澄清完成后，人类可覆盖为 `同意规范化` 作为 ort03 入口。AI 不应把旧的 `同意澄清` 视为锁定值。

Step 1（反馈处理）的入口和分支——状态条件判读以 §2.2 反馈机制表为定义单源，此处只补路由要点：

- `生命周期=澄清中` 的文件按正文区标记状态进入对应分支：有 `[✓已澄清]` → 生成新正文 → 三项条件评估；有 `[⨯]` 无 `[✓已澄清]` → 输出迭代报告，等待人类；无标记 → 数据不一致处理（正文已纯净 → 推进 `已澄清` 并提示人类；否则 → 提示核对）
- `生命周期=已澄清`：不处理正文，进入规范化选材提示
- `人类决策=已终止`：终止处理（表 B → `已废弃`、frontmatter.status → `abandoned`）

### 2.4 模糊标注规则

**一句话**：模糊标注就是把"没说清"的地方用 `[⨯]` 标出来，并告诉人类缺什么。

五种模糊子类型：

| 子类型 | 适用场景 | 标注示例 |
|--------|---------|---------|
| 术语模糊 | 非量化表述需明确度量方式 | `[⨯术语模糊: 高效→需量化处理能力指标]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明]提出该需求` |
| 边界模糊 | 条件、范围或指标缺少边界 | `[⨯边界模糊: 实时→需明确具体延迟上限]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→缺来源日期和提出方]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 术语+边界→非量化+缺时限]` |

标注格式：

```text
[⨯子类型: 原文片段→问题说明]
```

标注纪律：

1. 标“哪里不清楚”，不标“应该怎么做”
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致，报告中每项对应正文中的一处内联标注

### 2.5 三项条件

迭代生成新正文后，必须逐项判定：

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有非量化、主体不明、边界不清、信息缺失表述已替换为明确内容 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注 |

三项全满足 → `生命周期=已澄清`、`AI建议=可以规范化`、`status=clarified`。仍有未清晰项 → 追加新 `[⨯]` 标注，保持 `澄清中`。

### 2.6 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做需求澄清，不做需求分解、评价或设计决策 |
| 文档结对 | 本步不产生文档结对关系；已澄清切分文件是 eos-ort03-norm 的输入 |
| 基于资产 | 原始出处保留，变更结论摘要写入管理区；历史版本由 Git 管理，不复制旧版全文 |

## 三、操作流程

**一句话**：一次运行 = 扫反馈处理（Step 1）→ 处理新选入（Step 2）→ 提交基线（Step 3）→ 输出交接（End）。运行内全由 AI 自动执行；你在**运行外**参与——在表 B 选入、在正文区写 `[✓已澄清]`、在表 B 终止/选入规范化（见 §1.2）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|-------|
| Start | 前置校验 | 检查状态文档、切分文件与基线就绪 | 无（AI 自动） | 统一 | 就绪/结束 | — |
| 1 | 反馈处理 | 扫表 B + 澄清中正文区状态 → 迭代/不一致/终止 | 无（AI 处理你已给的澄清反馈） | 统一 | 已澄清正文/新标注/迭代报告 | 表 B、切分文件 |
| 2 | 新增处理 | 读取表 B 选入材料，执行首轮全量模糊标注 | 无（AI 标注，你之后在正文区反馈） | 统一 | `[⨯]` 标记 + 标注报告 | 表 B、切分文件 |
| 3 | 提交基线 | ai-commit 提交本轮变更（链级不变式） | 无（AI 自动） | 统一 | 新基线 | git（基线） |
| End | 输出交接 | 输出行动清单和下一步交接 | 无（AI 输出，你之后在正文区/表 B 反馈） | 统一 | 行动清单 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入。本步反馈全走「运行外编辑」——你在表 B 选入、在正文区写 `[✓已澄清]`、改 `人类决策`，运行中 AI 自动处理（见 §1.2 人机交接点）。

核心驱动逻辑：扫表 B 与澄清中文件正文区状态发现反馈（`[✓已澄清]`/`[⨯]`/终止）并处理 → 处理新选入澄清的切分文件（首轮标注）→ 提交基线 → 输出行动清单。反馈检测用**状态条件扫描**（表 B + 正文区直接可读），不用 git diff——ort02 的反馈载体就是正文区标记与表 B 字段（见 §2.2 反馈机制）。

### 3.1 Step Start · 前置校验

**一句话**：先确认状态文档、切分文件与基线就绪，再执行反馈检测分流——有反馈 → Step 1；无反馈有新增选入 → Step 2；全无 → 结束。

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示

4. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
5. 全部就绪后先执行反馈检测：扫表 B 与澄清中正文区状态，有反馈 → Step 1；无反馈有新增选入 → Step 2；全无 → 「无待处理对象」结束

### 3.2 Step 1 · 反馈处理

**一句话**：扫表 B 与澄清中文件正文区状态，发现反馈并直接处理——反馈载体即正文区标记与表 B 字段，处理即状态转迁，完成后条件自动失效（无需 `[已处理]` 标记）。

读取表 B 中 `生命周期=澄清中` 的文件，按 §2.2 反馈机制表判读状态条件，进入对应分支：

**1. 检测到 `[✓已澄清]`**

1. 收集全部 `[✓已澄清: ...]` 注释
2. 在管理区摘要记录澄清结论（历史版本由 Git 管理，不归档旧版全文）
3. 按注释内容将模糊表述替换为明确内容，生成新正文
4. 清理临时标注和报告，使正文区进入新版本
5. 执行三项条件评估
6. 三项满足时：表 B 置 `已澄清`、`AI建议=可以规范化`、frontmatter.status 置 `clarified`
7. 仍有未清晰项时：在新正文对应位置追加新 `[⨯]` 标注，表 B 保持 `澄清中`、`AI建议=需继续澄清`
8. 更新 `last_size`、`iteration_count++`、`unresolved_count`
9. 推导更新文档内嵌状态摘要表并追加澄清决策记录

**2. 有 `[⨯]` 无 `[✓已澄清]`**

1. 输出迭代报告
2. 表 B 保持 `生命周期=澄清中`
3. 更新 `unresolved_count`（按当前 `[⨯]` 数）和最后更新时间
4. 若 `iteration_count >= 3`，在行动清单中提示优先处理

**3. 无任何标记**

1. 以正文区实际状态为准：正文已纯净 → 表 B 推进 `已澄清`、frontmatter.status 置 `clarified`，并提示人类
2. 否则 → 提示数据不一致，等待人类核对

**4. 终止**：表 B `人类决策=已终止` → 生命周期置 `已废弃`、AI建议置 `建议终止`，frontmatter.status 置 `abandoned`。

写回前执行 §2.2 同步契约竞态保护（快照/复核，命中 `[需确认]` 不覆盖）；处理后按 §2.2 同步契约推导更新文档内嵌状态摘要表。

### 3.3 Step 2 · 新增处理

**一句话**：把你新选入澄清的切分文件做首轮全量模糊标注——有模糊进入 `澄清中` 等反馈，无模糊直接推进 `已澄清`。

读取状态文档表 B，按以下规则分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 对应切分文件进入首轮标注 |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

首轮标注动作：

1. 通读切分文件正文区
2. 按五种子类型标注全部模糊项
3. 写入模糊标注报告
4. 有模糊项：frontmatter.status 置 `annotated`，表 B 更新为 `生命周期=澄清中`、`AI建议=需继续澄清`、`iteration_count=1`
5. 无模糊项：frontmatter.status 置 `clarified`，表 B 更新为 `生命周期=已澄清`、`AI建议=可以规范化`
6. 从表 B 推导更新文档内嵌状态摘要表

写回前执行 §2.2 同步契约竞态保护；写回顺序按 §2.2 同步契约（先表 B，后派生状态）。

### 3.4 Step 3 · 提交基线

**一句话**：AI 把本轮结果提交为 git 基线，维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式；你无需操作。

把本轮 Step 1~2 的处理结果提交为 git 基线。

**为什么需要提交**：ort02 自身检测用状态扫描、不需要基线；但 ort02 的产出（切分文件正文区 + 表 B 写入）若不落基线，会进入下游 git diff 步骤（ort03 推广后）的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B、切分文件；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致）
4. **无变更**：工作区无改动时跳过提交，基线不变

### 4.1 文档内嵌状态摘要表

**一句话**：你在切分文件管理区看到的状态摘要，来自下面这张表——它告诉你看的是哪个阶段、下一步该做什么。

|------|--------|--------|---------|
