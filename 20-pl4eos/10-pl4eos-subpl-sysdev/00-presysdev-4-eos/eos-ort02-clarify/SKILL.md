## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step 1：扫表 B + 澄清中正文区状态 → 迭代/不一致/终止（状态扫描，直接处理） | 原始材料文本化 → `eos-ort00-textualize` |
| Step 2：读取表 B `已切分`+`同意澄清` 选入材料，首轮全量模糊标注 | 语义切分 → `eos-ort01-chunk` |
| 读取正文区 `[✓已澄清]` → 生成新正文 → 三项条件评估 | OR 条目规范化/分类/编号 → `eos-ort03-norm` |
| 维护表 B：生命周期/iteration_count/unresolved_count/frontmatter.status；Step 3 提交基线 | 代替人类确认业务事实 |

**核心原则**：AI 只定位"哪里不清楚"，不标"应该怎么做"、不替人类确认业务事实；**反馈载体即正文区标记与表 B 字段**——人类写 `[✓已澄清]` / 改表 B 即反馈，AI 扫状态条件直接处理，无需 git diff 与记录分离。

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `eos-ort01-chunk` | 表B `生命周期=已切分` + `人类决策=同意澄清` 的切分文件 |
| 下游 | `eos-ort03-norm` | 表B `生命周期=已澄清` + `AI建议=可以规范化` 的切分文件 → 设 `人类决策=同意规范化` 后进入 |

## 二、操作流程

### Step Start · 前置校验

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 存在；否则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 表头与字段说明，与状态文档模板不符时按既有口径修正或提示
3. `10-raw-files/` 中存在 `.chunk-*.md` 切分文件；否则提示先运行 `eos-ort01-chunk` 并结束
4. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
5. 全部就绪 → **优先反馈检测**：扫表 B + 澄清中正文区，有反馈 → Step 1；无反馈有新增选入 → Step 2；全无 → 「无待处理对象」结束

**加载经济原则**：用 `ls`/grep 定位切分文件与表 B 区域；标注分析时仅读取目标切分文件正文区（frontmatter.status 用 grep 读，不 Read 全文件）。

### Step 1 · 反馈处理

**一句话**：扫表 B 与澄清中文件正文区状态，发现反馈并直接处理——反馈载体即正文区标记与表 B 字段，处理即状态转迁，完成后条件自动失效（无需 `[已处理]` 标记）。

读取表 B 中 `生命周期=澄清中` 的文件，按附录 A.1 检测正文区标注状态：

| 条件 | 处理 |
|------|------|
| 有 `[✓已澄清]` | 管理区摘要记录澄清结论（历史由 Git 管理）→ 按注释生成新正文 → 清理临时标注与报告 → **三项条件评估**（附录 A.4） |
| 有 `[⨯]` 无 `[✓已澄清]` | 输出迭代报告，等待人类处理；`iteration_count >= 3` 时提示优先处理 |
| 无标记异常 | 数据不一致：以正文区实际状态为准——正文已纯净 → 表 B 推进 `已澄清`、status→`clarified`；否则提示数据不一致，等待人类核对 |
| `人类决策=已终止` | 表 B→`已废弃`、AI建议→`建议终止`，frontmatter.status→`abandoned` |

**三项条件评估**（判定口径见 [人类方案 §2.5](../eos-ort02-clarify.md#25-三项条件)）：

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 模糊表述已替换为明确内容 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 均有对应 `[✓已澄清]` |
| 无新增模糊 | 新正文通读后无新 `[⨯]` |

三项全满足 → `已澄清`、`可以规范化`、`status=clarified`。仍有未清晰项 → 追加新 `[⨯]`，保持 `澄清中`。更新 `last_size`、`iteration_count++`、`unresolved_count`。

写回前执行附录 B.1 冲突检查。

### Step 2 · 新增处理

读取表 B，按附录 A.2 分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 进入首轮标注 |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

**首轮标注**（详细规则见 [人类方案 §2.4](../eos-ort02-clarify.md#24-模糊标注规则)）：

1. 通读切分文件正文区
2. 按五种子类型标注全部模糊项（附录 A.3）
3. 写入模糊标注报告（模板见 [人类方案 §4.2](../eos-ort02-clarify.md#42-首轮标注报告模板)）
4. 有模糊项：frontmatter.status→`annotated`，表 B→`澄清中`、`AI建议=需继续澄清`、`iteration_count=1`
5. 无模糊项：frontmatter.status→`clarified`，表 B→`已澄清`、`AI建议=可以规范化`
6. 从表 B 推导更新 OR 切分文档状态表

写回前执行附录 B.1 冲突检查。

### Step 3 · 提交基线

把本轮 Step 1~2 的处理结果提交为 git 基线。

**为什么需要提交**：ort02 自身检测用状态扫描、不需要基线；但 ort02 的产出（切分文件正文区 + 表 B 写入）若不落基线，会进入下游 git diff 步骤（ort03 推广后）的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B、切分文件；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段
4. **无变更**：工作区无改动时跳过提交，基线不变

### Step End · 运行结束输出

输出行动清单（本次运行报告 + 下一步交接），**结束**——ort02 反馈全在正文区与表 B，人类直接写 `[✓已澄清]` / 改表 B 即反馈，无需对话收集：

```text
当前状态：<澄清中 / 已澄清可规范化 / 已废弃 / 无新增处理>
  首轮标注：<文件名.chunk-001.md>（发现 N 项模糊，表 B 生命周期=澄清中）
  迭代澄清：<文件名.chunk-001.md>（v{N-1}→v{N}，剩余 M 项模糊）
  已澄清：<文件名.chunk-002.md>（表 B 生命周期=已澄清，AI建议=可以规范化）
  废弃切分文件：<文件名.chunk-003.md>（frontmatter.status=abandoned）
资产落账：表 B 已同步；切分文件 frontmatter.status / 管理区状态表已同步；基线已提交（<hash>）

一、待反馈（编辑正文区/表 B 即反馈，AI 用状态扫描检测）
  A. 补充澄清 → 在正文区对应 `[⨯]` 后直接追加 `[✓已澄清: ...]`
  B. 暂不处理 → 保持表 B `生命周期=澄清中`，下轮继续提示
  C. 终止材料 → 在表 B 对应记录设 `人类决策=已终止`
  D. 选入规范化 → 对 `已澄清` 文件设 `人类决策=同意规范化` → 进入 ort03

二、下一步
  ① 待选入澄清的切分文件 → 表 B `生命周期=已切分` + `人类决策=同意澄清`
  ② 待选入规范化的切分文件 → 表 B `生命周期=已澄清` + `人类决策=同意规范化` → eos-ort03-norm
```

## 三、AI 标记约定

**标注格式**：

```text
[⨯子类型: 原文片段→问题说明]
[✓已澄清: 澄清后的明确内容]
```

**标注纪律**（详细规则见 [人类方案 §2.4](../eos-ort02-clarify.md#24-模糊标注规则)）：

1. 标"哪里不清楚"，不标"应该怎么做"
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致，报告中每项对应正文中的一处内联标注

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓已澄清]` 标记和临时报告。历史版本由 Git 管理。

## 附录A：判据速查

### A.1 正文区检测与分支

| 条件 | 处理 |
|------|------|
| `生命周期=澄清中` + 正文区存在 `[✓已澄清]` | 生成新正文 → 三项条件评估 |
| `生命周期=澄清中` + 有 `[⨯]` 且无 `[✓已澄清]` | 输出迭代报告，等待人类处理 |
| `生命周期=澄清中` + 无任何标记 | 数据不一致：以正文区实际状态为准——正文已纯净 → 表 B 推进 `已澄清`、status→`clarified`；否则提示数据不一致，等待人类核对 |
| `生命周期=已澄清` | 不处理正文，进入规范化选材提示 |
| `人类决策=已终止` | 表 B 置 `已废弃`，frontmatter.status 置 `abandoned` |

### A.2 表 B 分流

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 对应切分文件进入首轮标注 |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

> `人类决策=已终止` 属反馈（Step 1 处理），见 A.1。

### A.3 五项模糊子类型

| 子类型 | 适用场景 | 标注示例 |
|--------|---------|---------|
| 术语模糊 | 非量化表述需明确度量方式 | `[⨯术语模糊: 高效→需量化处理能力指标]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明]提出该需求` |
| 边界模糊 | 条件、范围或指标缺少边界 | `[⨯边界模糊: 实时→需明确延迟上限]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→缺来源日期和提出方]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 术语+边界→非量化+缺时限]` |

### A.4 三项条件判定

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有非量化、主体不明、边界不清、信息缺失表述已替换为明确内容 |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注 |

三项全满足 → `已澄清`；仍有未清晰项 → 追加新 `[⨯]`，保持 `澄清中`。

### A.5 表 B 取值与追踪字段

| 字段 | 取值 |
|------|------|
| 生命周期 | 已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃 |
| AI建议 | 可以澄清 / 需继续澄清 / 可以规范化 / 建议终止（本步设置值；全集见状态文档表B） |
| 人类决策 | 空 / 同意澄清 / 同意规范化 / 已终止 |
| last_size | 最近一次正文长度或标注规模 |
| iteration_count | 澄清迭代轮次 |
| unresolved_count | 当前未解决模糊项数量 |

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 B 是人类与 AI 共同维护的表。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **快照**——读取待更新行的 `生命周期` 与 `人类决策` 当前值
2. **复核**——写回前重新读取该行；若 `生命周期` 或 `人类决策` 与快照不符，标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：AI 绝不覆盖非空的人类决策（人类编辑即反馈，AI 不代写）

### B.2 写回顺序（同步契约）

1. **先更新状态文档表 B**（权威源）——生命周期 / AI建议 / last_size / iteration_count / unresolved_count
2. **再从表 B 推导**写入切分文件管理区状态表和 frontmatter.status
3. 两者不一致时，以表 B 为准重建派生状态

## 四、重进入规则

| 场景 | 处理 |
|------|------|
| 新选入澄清 | 表 B `生命周期=已切分` + `人类决策=同意澄清` → 首轮标注 |
