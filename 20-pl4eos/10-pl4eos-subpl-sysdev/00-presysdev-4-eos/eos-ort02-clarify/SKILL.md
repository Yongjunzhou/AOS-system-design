## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step 1：状态扫描检出正文区 `[✓已澄清]`/表 B 变更 → 登记表 B 内容摘要（查重幂等） | 原始材料文本化 → `eos-ort00-textualize` |
| Step 2：读表 B 内容摘要未处理反馈 → 生成新正文/终止/重标 → 追 `[已处理]` | 语义切分 → `eos-ort01-chunk` |
| Step 3：读取表 B `已切分`+`同意澄清` 选入材料，首轮全量模糊标注 + 结构完整性扫描 + 生成向相关方确认的问题 | OR 条目规范化/分类/编号 → `eos-ort03-norm` |
| Step 5/6：对话收集反馈（只记录不处理）→「汇总」落表 B + 提交基线 | 代替开发者/相关方确认业务事实（AI 只生成问题、不提供答案） |
| 维护表 B：生命周期/iteration_count/unresolved_count/frontmatter.status；Step 4 提交基线 | 对话澄清答案未经确认不代写 |

**核心原则**：AI 只定位"哪里不清楚"（六类模糊）与文本自证的结构缺口（结构完整性）并生成「向相关方确认的问题」，不替开发者/相关方提供答案或指标数值；**反馈双通道**——线下（正文区 `[✓已澄清]`/表 B 字段，状态扫描检出→登记表 B 内容摘要）＋对话（Step 5 收集→Step 6 汇总落账）；处理走**记录 + `[已处理]`** 显式分界，无需 git diff。

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `eos-ort01-chunk` | 表B `生命周期=已切分` + `人类决策=同意澄清` 的切分文件 |

## 二、操作流程

### Step Start · 前置校验

**一句话**：先确认状态文档、切分文件与基线就绪，再进入 Step 1 反馈检测与汇总。

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 存在；否则提示先运行 `eos-ort00-textualize` 并结束
2. 若状态文档已存在，校验表 B 表头与字段说明，与状态文档模板不符时按既有口径修正或提示
3. `10-raw-files/` 中存在 `.chunk-*.md` 切分文件；否则提示先运行 `eos-ort01-chunk` 并结束
4. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
5. **感知前置确认**：本步反馈检测用状态扫描（正文区 `[✓已澄清]` / 表 B 变更，[人类方案 §3.5](../eos-ort02-clarify.md#35-反馈检测判据)），Step Start 无「无待处理提前退出」判定——全部就绪后无条件进入 Step 1 先检出反馈再判入口，不因表 B 无待处理登记而漏检线下写 `[✓已澄清]`
6. 全部就绪 → 进入 Step 1 反馈检测与汇总

**加载经济原则**：用 `ls`/grep 定位切分文件与表 B 区域；标注分析时仅读取目标切分文件正文区（frontmatter.status 用 grep 读，不 Read 全文件）。

### Step 1 · 反馈检测与汇总

**一句话**：本轮开始先把你在运行间隙的澄清内容（正文区 `[✓已澄清]`）和表 B 变更找出来，登记到表 B 内容摘要并汇总清单——之后 Step 2 基于登记处理。

1. 扫表 B 中 `生命周期=澄清中` 的文件，逐份读正文区检出 `[✓已澄清]` 标记
2. 对每处 `[✓已澄清]`：查重（表 B 内容摘要已有该文件未处理「澄清」登记？）→ 无则登记 `反馈：澄清（<文件名>）`；已有则跳过（只汇总不重复登记）
3. 扫表 B：检出 `人类决策=已终止` 未登记 → 登记 `反馈：终止（<文件名>）`
4. 汇总表 B 内容摘要中既有未处理反馈记录（对话通道 Step 6 写入的），一并列入本轮反馈清单
5. 输出本轮反馈清单：已登记待处理（澄清 N / 终止 K）、待澄清（有 `[⨯]` 无 `[✓已澄清]`）、数据不一致
6. 路由：有反馈登记 → Step 2；有新选入（`已切分`+`同意澄清`）→ Step 3；全无 → 「无待处理对象」结束

> 正文区 `[✓已澄清]` 标记保留至 Step 2 处理时清理；查重保证多次运行不重复登记（中断后残留标记下轮跳过）。

### Step 2 · 反馈处理

**一句话**：按表 B 内容摘要的反馈登记逐一处理——澄清→生成新正文、终止→废弃、重标→重新标注，处理完追 `[已处理]`。

读表 B 内容摘要中「含 `反馈：` 且未追加 `[已处理]`」的记录，逐个处理：

| 反馈类型 | 处理 |
|---------|------|
| `反馈：澄清（<文件>）` | 读正文区 `[✓已澄清: <答案>]` → 管理区摘要记录澄清结论（历史由 Git 管理）→ 按答案替换模糊表述生成新正文 → 清理正文区标记与临时报告 → **三项条件判定**（附录 A.4）→ 追 `[已处理]` |
| `反馈：终止（<文件>）` | 表 B→`已废弃`、AI建议→`建议终止`，frontmatter.status→`abandoned` → 追 `[已处理]` |
| `反馈：重标（<文件>：<要点>）` | 按要点重新标注 → 更新表 B 与标注报告 → 追 `[已处理]` |

写回前执行附录 B.1 冲突检查。

**三项条件判定**（口径见 [人类方案 §三 3.3](../eos-ort02-clarify.md#33-三项条件)）：

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 模糊表述与结构完整性缺项已替换为明确内容，且内容来自相关方确认（`[✓已澄清]` 为开发者写入的相关方答案） |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 均有对应 `[✓已澄清]` |
| 无新增模糊 | 新正文通读后无新 `[⨯]`（六类模糊或结构完整性） |

三项全满足 → `已澄清`、`可以规范化`、`status=clarified`；仍有未清晰项 → 追加新 `[⨯]`，保持 `澄清中`。更新 `last_size`、`iteration_count++`、`unresolved_count`。

**待澄清与数据不一致**（不登记不处理，仅在反馈清单中列出）：

- `生命周期=澄清中` + 有 `[⨯]` 无 `[✓已澄清]`：输出迭代报告，等待人类处理；`iteration_count >= 3` 时提示优先处理
- `生命周期=澄清中` + 无标记：正文已纯净 → 表 B 推进 `已澄清`、status→`clarified` 并提示人类；否则 → 提示数据不一致，等待人类核对

### Step 3 · 新增处理

**一句话**：把你新选入澄清的切分文件做首轮全量模糊标注——有模糊进入 `澄清中` 等反馈，无模糊直接推进 `已澄清`。

读取表 B，按附录 A.2 分流：

| 表 B 状态 | 处理 |
|----------|------|
| `生命周期=已切分` + `人类决策=同意澄清` | 进入首轮标注 |
| `人类决策=空` | 跳过，列入待选入澄清提醒 |

**首轮标注**（详细规则见 [人类方案 §三 3.2](../eos-ort02-clarify.md#32-模糊标注规则)）：

1. 通读切分文件正文区
2. 按六种模糊子类型标注全部模糊项（附录 A.3），并为每处生成「向相关方确认的问题」
3. 做结构完整性扫描（附录 A.3），对文本自证缺口生成 `[⨯完整性]` 问句
4. 写入模糊标注报告（模板见 [人类方案 §六 6.2](../eos-ort02-clarify.md#62-首轮标注报告模板)）
5. 有模糊项或结构完整性缺项：frontmatter.status→`annotated`，表 B→`澄清中`、`AI建议=需继续澄清`、`iteration_count=1`
6. 无模糊项且无结构完整性缺项：frontmatter.status→`clarified`，表 B→`已澄清`、`AI建议=可以规范化`
7. 从表 B 推导更新文档内嵌状态摘要表

写回前执行附录 B.1 冲突检查。

### Step 4 · 提交基线

**一句话**：把本轮结果提交为 git 基线，维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

把本轮 Step 1~3 的处理结果提交为 git 基线。

**为什么需要提交**：ort02 自身检测用状态扫描、不需要基线；但 ort02 的产出（切分文件正文区 + 表 B 写入）若不落基线，会进入下游 git diff 步骤的视野。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 B、切分文件；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段
4. **无变更**：工作区无改动时跳过提交，基线不变

### Step 5 · 反馈交互

**一句话**：AI 输出本轮运行摘要后保持对话收集反馈——你说流程指示（终止/重标/再澄清）或澄清答案，AI 只收集不处理，反馈结束时「汇总」。

先输出三区摘要（本步开场）：

```text
══════════════════════════════════════════
  eos-ort02-clarify 本轮完成
══════════════════════════════════════════

当前状态：<澄清中 / 已澄清可规范化 / 已废弃 / 无新增处理>
  处理澄清：<文件名.chunk-001.md>（v{N-1}→v{N}，剩余 M 项模糊）
  新增标注：<文件名.chunk-002.md>（发现 N 项模糊 + 问题清单）
  待澄清：<文件名.chunk-003.md>（有 [⨯] 待澄清）
  废弃切分文件：<文件名.chunk-004.md>（表 B 生命周期=已废弃）
资产落账：表 B 内容摘要已登记反馈；切分文件状态摘要已同步；基线已提交（<hash>）

一、待反馈（对话 / 线下均可）
  A. 对话反馈 → 直接说明流程指示或澄清答案，AI 只记录不处理，「汇总」后落表 B
  B. 线下澄清 → 持问题清单向相关方澄清，将答案写正文区 `[✓已澄清: <相关方确认内容>]`

二、下一步
  ① 待选入澄清的切分文件 → 表 B `生命周期=已切分` + `人类决策=同意澄清`
  ② 待选入规范化的切分文件 → 表 B `生命周期=已澄清` + `人类决策=同意规范化` → eos-ort03-norm
```

**交互只记录，不处理**——AI 输出本摘要后保持对话，收集流程指示与澄清答案（不逐条即时写表）。本步为**交互协议步骤**（执行模式=对话），由人类结束（「汇总」/「继续」）。

### Step 6 · 变更汇总

**一句话**：你说「汇总」/「就这些」时，AI 把本次对话的反馈一次性落到表 B 内容摘要（澄清答案 AI 代写 `[✓已澄清]` 到正文区）并提交基线，不执行处理。

**动作**：人类表示反馈结束时（「汇总」/「就这些」）AI **立即汇总一次**——把本次对话全部反馈整理进表 B 内容摘要（`反馈：澄清/终止/重标`；对话澄清答案由 AI 代写 `[✓已澄清: <答案>]` 到正文区并登记 `反馈：澄清`），**提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交）**，输出「已汇总」摘要，**不执行处理**。

**为什么必须提交**：否则下次 Step 1 会把 AI 自己的汇总误判为人类反馈。对话期间你对文档的静默编辑也随汇总一并纳入基线。

**兜底与路由**：本步为**交互协议步骤**（执行模式=口令触发）。此汇总**不替代 Step 1**——运行结束后你线下写 `[✓已澄清]` 的反馈，仍由 Step 1 下次状态扫描检出登记。处理统一由 Step 2（「继续」后或下轮）基于登记执行。

**口令表**（按步骤分组）：

| 步骤 | 口令 | AI 代执行 |
|------|------|----------|
| Step 5 | **对话反馈**：「chunk-001 终止」「chunk-002 答案是 300 条/秒」… | 对话中收集，待「汇总」时统一登记到表 B 内容摘要（不逐条即时写表） |

| Step 6 | **辅助**：「继续」 | 有未汇总对话反馈时先汇总，再重跑 Step 1~4 处理已登记反馈（Step 2）与新增选入（Step 3） |

## 三、AI 标记约定

**标注格式**：

```text
[⨯子类型: 原文片段→问题：<向相关方确认的问句>]
[⨯完整性: 原文/对象→问题：<向相关方确认的问句>]（结构完整性扫描，纪律 6）
[✓已澄清: <相关方确认后的明确内容>]
```

**标注纪律**（详细规则见 [人类方案 §三 3.2](../eos-ort02-clarify.md#32-模糊标注规则)）：

1. 标"哪里不清楚"并给出「向相关方确认的问题」；不代替相关方提供答案或指标数值
2. 先通读后标注，避免局部视角导致重复或遗漏
3. 一条只标一个点；同处多维问题合并为多重模糊
4. 报告与内联一致：问题清单与每处内联标注一一对应
5. **缺少定量指标（非功能分支）路由识别**——识别为非功能需求缺指标（质量诉求：实时/高效/安全/可靠等）时，标 `[⨯缺少定量指标]`，**向相关方澄清目标值+单位+条件**；按 NFR 四元组额外澄清可在原文确认的维度：质量属性准确表述（喂 ort03 分类维度）/ 适用对象（哪个场景/流程/系统整体，喂 ort03 适用对象线索）/ 关注角色（必要时），标注示例 `[⨯缺少定量指标: 实时→问题：本项为质量诉求。请确认：①质量属性准确表述（响应时间/吞吐量）？②适用对象（哪个场景/流程/系统整体）？③定量指标（目标值+单位+条件）？]`（详见 [人类方案 §三 3.2](../eos-ort02-clarify.md#32-模糊标注规则) 纪律 5）
6. **结构完整性扫描（需求结构自洽，独立于六种模糊子类型）**——六类标注完成后，对切分文件整体再扫一遍"文本自证的结构缺口"：只在文本自身制造了未兑现的期待时发问，标 `[⨯完整性: 原文/对象→问题：<问句>]`——①**分支缺对应面**（文中明确写了「当X时/正常情况」等条件或路径但缺其对应面，排除上下文明显推出的）；②**闭环缺端**（明确描述了业务对象闭环多个环节但缺提出/处理/确认一端，对齐 ort01 完整闭环 [91 §1.4]）；③**引用对象缺失**（文内引用的实体/流程/文档在全切分文件集无定义）。**不标**模板式业务覆盖猜测（如"该需求是否还应包含X功能"）——那是需求开发职责（详见 [人类方案 §三 3.2](../eos-ort02-clarify.md#32-模糊标注规则) 纪律 6）

**正文区纯净终态**：`生命周期=已澄清` 时，正文区应为最新纯净版本，不保留 `[⨯]` / `[✓已澄清]` 标记和临时报告。历史版本由 Git 管理。

### A.1 反馈检出与登记（Step 1）

状态扫描检出正文区标记 / 表 B 变更 → 登记表 B 内容摘要（`阶段摘要 ∥ 反馈：<类型>（<要点>）`，查重幂等）：

|---------|------|------|

### A.2 表 B 分流（Step 3）

| 表 B 状态 | 处理 |
|----------|------|

### A.3 六项模糊子类型

| 子类型 | 适用场景 | 标注示例（AI 生成向相关方确认的问题） |
|--------|---------|---------|
| 术语模糊 | 业务/领域术语表述不明确 | `[⨯术语模糊: 外购件→问题："外购件"的确切定义和范围是？]` |
| 主体/客体不明 | 角色或对象不可识别 | `[⨯主体不明: 提出该需求→问题：该需求的主体/提出方是谁？]` |
| 边界模糊 | 条件、范围、时限等缺少边界 | `[⨯边界模糊: 试运行期→问题：试运行期的起止条件和时长是？]` |
| 缺少定量指标 | 有需求描述但缺性能指标（定量：数值+单位+条件） | `[⨯缺少定量指标: 批量导入→问题：批量导入的单次上限（数值/单位/条件）是多少？]` |
| 信息缺失 | 缺少来源、时间、提出方等元信息 | `[⨯信息缺失→问题：该需求的来源日期和提出方是？]` |
| 多重模糊 | 同处存在两种以上类型 | `[⨯多重模糊: 主体+边界→问题：该需求的主体是谁、适用时段/条件是？]` |

> 非功能需求缺指标（质量诉求）按标注纪律 5 路由：标 `[⨯缺少定量指标]`，向相关方澄清目标值+单位+条件 + 质量属性准确表述/适用对象（不发明指标数值）。

> 六类标注完成后做**结构完整性扫描**（独立类别，非第七子类型，标注纪律 6）：只在文本自证缺口时发问，标 `[⨯完整性: 原文/对象→问题：<问句>]`——①分支缺对应面（如"已审核"分支无"未审核/驳回"对应）；②闭环缺端（对齐 ort01 完整闭环，缺提出/处理/确认一端）；③引用对象缺失（文内引用的实体/流程/文档在全切分文件集无定义）。不标模板式业务覆盖猜测（如"是否还应包含X功能"）。

### A.4 三项条件判定

| 条件 | 判定口径 |
|------|---------|
| 正文内容清晰完整 | 所有模糊表述（术语不明、主体不明、边界不清、缺少定量指标、信息缺失）与结构完整性缺项已替换为明确内容，且内容来自相关方确认（AI 生成的问题不构成已澄清） |
| 历史模糊项已澄清 | 所有历史 `[⨯]` 在被替换前的旧版正文中均有对应 `[✓已澄清]` 注释 |
| 无新增模糊 | 新正文通读后不产生新的 `[⨯]` 标注（六类模糊或结构完整性） |

三项全满足 → `已澄清`；仍有未清晰项 → 追加新 `[⨯]`，保持 `澄清中`。

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 B 是人类与 AI 共同维护的表。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **快照**——读取待更新行的 `生命周期` 与 `人类决策` 当前值
2. **复核**——写回前重新读取该行；若 `生命周期` 或 `人类决策` 与快照不符，标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：AI 绝不覆盖非空的人类决策（人类编辑即反馈，AI 不代写）

### B.2 写回顺序（同步契约）

1. **先更新状态文档表 B**（权威源）——生命周期 / AI建议 / last_size / iteration_count / unresolved_count
2. **再从表 B 推导**写入切分文件文档内嵌状态摘要表和 frontmatter.status
3. 两者不一致时，以表 B 为准重建派生状态
