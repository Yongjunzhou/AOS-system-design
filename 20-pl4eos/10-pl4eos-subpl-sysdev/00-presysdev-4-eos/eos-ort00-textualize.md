# 原始需求材料 → 文本化文档 · 纯文本化与原料登记
**Skill ID**: eos-ort00-textualize

> **概述**：扫描原始需求材料目录，对尚未文本化的源文件执行纯格式转换（非文本/文本 → Markdown 工作副本），输出统一后缀 `.textualized.md` 的文本化文档，并同步更新 EOS OR 预处理状态文档表 A。本步只做载体转换、登记、查重和交接，不做语义分析、切分建议或需求规范化。
>
> **输入 → 输出**：原始材料文件（PDF/图片/邮件/纪要/已有 `.md` 等）→ 文本化 `.textualized.md` 文档（管理区：状态摘要；正文区：纯原文）+ `01-eos-sysdev-status.md` 表 A 更新（生命周期/AI 建议/操作指引）
>
> **适用场景**：EOS 原始需求预处理链入口；每轮扫描所有未文本化原始材料，支持新增材料后的重复运行。
>
> **接口设计**：本步与下游 eos-ort01-chunk 不设置独立接口文档，衔接载体是文本化文档的**正文区**。正文区存在纯原文且无切分方案块时，下游可进入切分处理。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（通用文档读写、反馈、生命周期与变更传播协议）
>
> **版本**：v0.7 | **修订**：2026-08-12 | **说明**：移除历史区——文本化文档由三区改为两区（管理区+正文区），历史追溯由 Git 管理（对齐 00-doc-conventions §14.7 不保留历史区）

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把各类原始需求材料转换为可被 OR 预处理链稳定读取的 Markdown 文本化工作副本，同时保留原始文件不变，建立材料级状态追踪入口。
>
> **目标**：
> 1. **初始化原料区**——确保 `00-origin-requirement-materials/10-raw-files/` 与 `01-eos-sysdev-status.md` 表 A/B/C 就绪
> 2. **发现待处理材料**——按固定后缀和状态表记录识别尚未文本化的原始文件
> 3. **执行纯文本化**——将源文件忠实转换为 Markdown 工作副本，保留原文结构与表达
> 4. **执行查重检测**——新文本化正文与既有文本化正文逐字比对，重复材料标记为废弃并输出软链接文档
> 5. **更新状态接口**——先更新状态文档表 A，再据此写入文本化文档管理区状态摘要
> 6. **输出行动清单**——提示人类选入切分、确认重复材料或进入下游 ort01

本 Skill 负责：

1. **接收**——扫描 `10-raw-files/` 中的原始材料文件，自动跳过本步/下游产物
2. **初始化**——首次运行时创建原料目录和 EOS OR 预处理状态文档基础表
3. **登记**——为新材料生成表 A 记录，维护源文件、文本化文档、生命周期、AI 建议和操作指引
4. **转换**——把 PDF/图片/扫描件/文本文件等转换为 Markdown 文本化文档
5. **查重**——正文区全文精确比对，重复材料生成定向引用文档并标记 `已废弃（重复）`
6. **交接**——输出待选入切分清单、重复材料通知和下一步操作指引
7. **重进入**——支持新增材料、重新文本化、重复误判重跑三类重进入

本 Skill 不负责：

1. OR 语义切分、切分方案生成或拆分建议（由 eos-ort01-chunk 负责）
2. 模糊需求澄清（由 eos-ort02-clarify 负责）
3. OR 条目规范化、分类、编号或冲突检测（由 eos-ort03-norm 负责）
4. 业务需求/引擎需求/非功能需求分配（由 wft01 系列负责）
5. 修改、摘要、解释或补充原始需求内容

## 二、文本化设计基础

### 2.1 文本化文档结构

文本化文档命名为 `{原始文件名}.textualized.md`，位于 `10-raw-files/`。原始文件保持只读不动，即使源文件本身已经是 `.md`，本步也生成独立工作副本。

| 区域 | 位置 | 内容 | 写入者 |
|------|------|------|--------|
| 管理区 | 文档顶部（正文前） | 状态摘要（阶段/AI 建议/待处理/操作指引）、迭代记录 | eos-ort00 写入状态摘要；下游追加迭代记录 |
| 正文区 | 管理区之后 | 纯原文内容（仅文本化后原文，无标注、无方案块） | eos-ort00 |

**正文区纯净原则**：正文区仅包含原文。所有切分方案块、模糊标注、分析建议块均由下游步骤写入并适时清理。本步不产生任何分析产物。

**历史追溯约定**：文档不设置历史区、归档区或旧版正文；历史版本由 Git 管理（[00-doc-conventions §14.7](../../../00-generalspec/00-doc-conventions.md#147-不保留历史区)）。需留痕的信息（如变更结论）摘要写入管理区，不得复制旧版全文。

### 2.2 文档生命周期管理

**一句话**：每份 OR 预处理文档都有自己的"生命周期"——从登记到废弃经历一系列阶段。本步用状态文档 `01-eos-sysdev-status.md` 作为统一登记表，追踪所有文档当前所处阶段、AI 建议和人类决策。

**状态文档按管理对象分三张表**：

| 表 | 管理对象 | 生命周期线 | 推进者 |
|----|---------|-----------|--------|
| 表 A | 原始材料 | 已登记 → 已文本化 → 切分方案待确认 → 已切分 → 已废弃 | ort00 → ort01 |
| 表 B | 切分文件（`.chunk-*.md`） | 已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃 | ort01 → ort02 → ort03 |
| 表 C | OR 基线条目 | 待处理 → 待确认方案 → 已分配 → 验证中 → 已验证冻结 → 已废弃 | ort03 → wft01 |

**一行记录 = 一份文档的生命状态**，由三个核心字段协同描述：

| 字段 | 含义 | 谁写 |
|------|------|------|
| 生命周期 | 文档当前所处阶段（流程状态的唯一依据） | 各步骤转迁 |
| AI建议 | AI 对下一步的推荐（供人参考，不作硬性入口判断） | 各步骤 |
| 人类决策 | 人类的选择（决定文档能否进入下一阶段） | 人类 |

示例（文本化完成后）：`生命周期=已文本化`、`AI建议=可以切分`、`人类决策=空`。人类设为 `同意切分` 后，下一轮 ort01 才接手切分。

**同步契约**：状态文档是**唯一权威源**。AI 每次写入时：

1. **先更新状态文档表**——如实记录文档所处阶段；
2. **再推导写内嵌状态表**——从状态文档推导写入各文档管理区状态表（给人快速看）。

若两者不一致，以状态文档为准重建。

**表 A 记录字段**（ort00 首次创建表 A 时使用）：

| 字段 | 写入者 | 说明 |
|------|--------|------|
| 记录ID | AI（首次登记） | 自动生成唯一标识，如 `ORT-YYYYMMDD-001`（含日期） |
| 内容摘要 | 各步更新 | 文档当前处理阶段的一句话摘要；重复时写 `与[源文件名]内容完全重复` |
| 源文件 | ort00 | 原始文件名（含扩展名） |
| 文本化文档 | ort00 / ort01 | ort00 写文本化 `.textualized.md` 文件名；ort01 切分后可更新为 `.chunk-{seq}.md` 名 |
| 生命周期 | 各步转迁 | 见上表 A 生命周期线；重复时置 `已废弃（重复）` |
| AI建议 | 各步更新 | 如 `可以切分` / `已废弃（重复）` |
| 人类决策 | 人类 | 空 / `同意切分` / `暂不切分` / `已终止` |
| 操作指引 | 各步更新 | 人类下一步应执行的操作 |
| 最后更新 | 各步更新 | 格式 `YYYY-MM-DD` |

**管理范围**：状态文档只管理 OR 预处理链（ort00~ort03）的文档生命周期。wft01~05 的设计产物（STR/BP/SysReq/PA）以各自产品文档管理区为权威源，不使用本表；wft 若补充生成原始需求材料，只登记到表 A（生命周期=`已登记`），仍由 ort00~ort03 进入预处理链。

### 2.3 文本化与查重规则

AI 在本步是“转录者”而非“理解者”。文本化只改变载体格式，不改变内容；任何超出格式转换的推断、补充、摘要均不允许。

| 场景 | 处理方式 |
|------|---------|
| PDF 中的表格 | 转为 Markdown 表格，保留行列结构和数值 |
| 图片/扫描件 | 识别文字内容，标注 `[AI 识别，待人工确认]` |
| 录音转写 | 标注发言人和时间戳，无法确认的内容标注 `[听写不清]` |
| 手写内容 | 可辨识内容写入文档并标注 `[AI 推测]`；不可辨识内容标注 `[原文模糊]` |
| 多语言混写 | 保留原文语种，必要时标注 `[中文/英文/...]` |
| 完全无法识别的图片 | 写入占位符 `[图片：无法识别文字内容]` |
| 文档明显不完整 | 在文档开头标注 `[文档疑似不完整：缺页/截断]` |

查重检测范围为新文本化正文区与所有既有文本化文档正文区（生命周期不为 `已废弃（重复）`）。匹配标准为全文逐字精确匹配，忽略行尾空白和连续空行差异；管理区状态表不参与比较。

### 2.4 跳过与重进入规则

AI 扫描 `10-raw-files/` 后，按以下规则判断每份文件是否需处理：

| 条件 | 处理 |
|------|------|
| 文件名以 `.textualized.md` 结尾 | 跳过（本步产物，不是原始材料） |
| 文件名包含 `.chunk-` 且以 `.md` 结尾 | 跳过（下游切分文档，不是原始材料） |
| 原始材料在表 A 中已有记录，生命周期为 `已登记` / `已文本化` / `已切分` / `澄清中` / `已澄清` / `已规范化` | 跳过（已在处理流程中） |
| 原始材料在表 A 中已有记录，生命周期为 `已废弃（重复）` | 跳过（重复关系已通过软链接文档记录） |
| 原始材料在表 A 中已有记录，生命周期为 `已废弃` | 跳过（如需重新启用，先清除表 A 生命周期值） |
| 原始材料在表 A 中无对应文本化记录 | 执行文本化，输出 `{原始文件名}.textualized.md` |
| 所有文件均跳过 | 输出“所有材料已文本化，无需本步操作”并结束 |

重进入场景：

| 场景 | 处理 |
|------|------|
| 新增原始材料 | 新文件在表 A 中无对应记录，进入文本化流程 |
| 重新文本化 | 先检查是否已有切分、澄清、OR 或 STR 下游消费；无下游消费时清除表 A 生命周期值并替换旧工作副本；已有下游消费时先形成变更影响声明并将相关下游对象标记为待重审，再重跑本步 |
| 重复文档误判 | 清除表 A 生命周期值，删除软链接文档，重跑本步 |

重进入按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议) 处理：新增材料不影响既有结果；重新文本化或重复关系纠正若改变正文、来源或有效性，必须列出受影响的切分文件、OR 和已消费 STR，不得静默声明“下游不受影响”。

### 2.5 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步不涉及需求/方案角色切换，纯格式转换步骤无需求相对性可言 |
| 详概分离 | 本步仅做格式转换和状态登记，不进行语义理解、切分分析或需求规范化 |
| 文档结对 | 本步不产生文档结对关系；文本化文档是 eos-ort01-chunk 的输入 |
| 基于资产 | 原始出处保留；文本化文档是原始文件的处理副本，不覆盖源文件 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查目录/状态文档/源文件是否就绪 | 统一 | 就绪/结束 | 目录结构、状态文档（首次） |
| 1 | 材料发现与登记 | 扫描源文件，对照表 A 分流并登记新材料 | 统一 | 待处理清单 | 表 A |
| 2 | 文本化与查重 | 执行格式转换、正文区查重、软链接处理 | 统一 | 文本化文档/软链接文档 | `10-raw-files/*.textualized.md` |
| End | 输出交互 | 输出行动清单和下一步交接 | 人类 | 行动清单 | — |

核心驱动逻辑：扫描原始材料目录，对尚未文本化的文件执行格式转换，输出文本化工作副本，并更新状态文档表 A。本步为”检测即执行”模式，每轮独立完成所有待处理材料。

### 3.1 Step Start · 前置校验

AI 按以下顺序执行前置校验。首次遇到未满足条件时处理该条件，然后根据场景继续或结束：

1. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/` 是否存在；不存在则创建目录结构
2. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则创建
3. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则创建状态文档模板
4. 若状态文档已存在，校验表 A/表 B/表 C 的表头和字段说明；不一致时按 §4.2 模板更新
5. 若 `10-raw-files/` 为空，输出“目录已就绪，请将原始材料放入 `10-raw-files/` 后重新启动本步”并结束
6. 全部就绪后进入 Step 1

### 3.2 Step 1 · 材料发现与登记

1. 扫描 `10-raw-files/` 中的文件
2. 按 §2.4 跳过规则过滤本步产物、下游产物和已进入流程的材料
3. 对表 A 中无对应记录的原始材料自动登记：
   - `记录ID`：自动生成唯一标识，如 `ORT-YYYYMMDD-001`（含日期）
   - `源文件`：原始文件名
   - `文本化文档`：预期 `{原始文件名}.textualized.md`
   - `生命周期`：`已登记`
   - `AI建议`：`可以切分`（文本化完成后生效；登记阶段作为预期建议）
   - `操作指引`：完成文本化后由人类决定是否选入切分
4. 若待处理清单为空，输出“所有材料已文本化，无需本步操作”并结束
5. 若存在待处理材料，进入 Step 2

### 3.3 Step 2 · 文本化与查重

**1. 文本化转换**

对每个待处理源文件执行格式转换：

- 非文本格式（PDF/图片/扫描件/录音转写等）转换为 Markdown
- 文本格式（`.md` / `.txt` 等）复制为独立文本化工作副本
- 保留原文结构（章节/段落/列表/表格）
- 不修改、不摘要、不解释原文表述
- 无法识别内容按 §2.3 标注占位符

**2. 查重检测**

将新文本化正文区与既有文本化文档正文区逐一比对：

| 结果 | 处理 |
|------|------|
| 无重复 | 输出完整文本化文档；表 A 更新为 `生命周期=已文本化`、`AI建议=可以切分` |
| 发现重复 | 输出软链接文档；表 A 更新为 `生命周期=已废弃（重复）`、`AI建议=已废弃（重复）`、`内容摘要=与[源文件名]内容完全重复` |

**3. 无重复文档写入**

文本化文档顶部写入 OR 文本化文档状态表：

```markdown
| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 文本化完成 | — | 在 状态文档 → 表A — 原始材料处理进度中确认入选本批材料 | 状态文档 → 表A — 原始材料处理进度 → 该记录 人类决策 字段设为"同意切分"（选入切分） |
```

> 文档内状态表的 `AI建议` 与表 A 的 `AI建议` 取值不同：文档内表面向当前阶段查看，文本化是机械转换，故填 `—`；表 A 的 `AI建议=可以切分` 面向下一步选材决策。

**4. 重复文档写入**

重复材料输出软链接文档，管理区写入：

```markdown
| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 已废弃（重复） | 与 [原始源文件名] 内容完全重复 | 确认无误后删除源文件 | — |
```

正文区写入定向引用：

```text
→ 本文件与 [原始源文件名] 内容完全重复，不持独立正文。
→ 原始文本化文档：[原始文本化文档文件名]
```

### 3.4 Step End · 运行结束输出

本步结束时输出行动清单，格式如下：

```text
══════════════════════════════════════════
  eos-ort00-textualize 本轮完成 · 行动清单
══════════════════════════════════════════

● 本轮已文本化：

  [文件名] → 文本化完成

● 本轮发现重复（已标记为已废弃（重复））：

  [文件名] → 与 [原始源文件名] 完全重复

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
待选入切分的文本化原始需求文档
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
打开 状态文档（01-eos-sysdev-status.md）→ 表A — 原始材料处理进度，对以上文档：
├─ 选入切分 → 设 人类决策=同意切分
└─ 暂不切分 → 设 人类决策=暂不切分（再次运行本步时会再次提示）
```

```text
  └─ 确认后：生成正式 OR 节点块、索引与 AI可以处理节点，分析建议作为来源证据保留
```
