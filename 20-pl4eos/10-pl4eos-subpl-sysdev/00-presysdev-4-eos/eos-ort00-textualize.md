# 原始需求材料 → 文本化文档 · 纯文本化与原料登记
**人类方案ID**: eos-ort00-textualize

> **概述**：扫描原始需求材料目录，把尚未文本化的源文件（PDF/图片/邮件/纪要/已有 `.md` 等）忠实转成统一后缀 `.textualized.md` 的 Markdown 工作副本，并同步更新 EOS OR 预处理状态文档的原始材料处理进度。人类通过**直接编辑状态文档表 A** 表达选材/终止/重跑等反馈（改 `人类决策`、清除 `生命周期`、删除源文件），AI 以**表 A 状态扫描**检测并处理。本步只做载体转换、登记、查重和交接，不做语义分析、切分建议或需求规范化。
>
> **输入 → 输出**：原始材料文件（PDF/图片/邮件/纪要/已有 `.md` 等）→ 文本化 `.textualized.md` 文档（管理区：状态摘要；正文区：纯原文）+ `01-eos-sysdev-status.md` 的原始材料处理进度更新（生命周期/AI 建议/操作指引）
>
> **适用场景**：EOS 原始需求预处理链入口；每轮扫描所有未文本化原始材料，支持新增材料后的重复运行。
>
> **接口设计**：本步与下游 eos-ort01-chunk 不设置独立接口文档，衔接载体是文本化文档的**正文区**。正文区存在纯原文且无切分方案块时，下游可进入切分处理。本步反馈走「**表 A 状态 + 文件系统**」——人类直接编辑状态文档表 A（改 `人类决策`、清除 `生命周期` 触发重跑、删除源文件确认重复），AI 每次运行**扫描表 A 状态条件**检测并直接处理，无需 git diff。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（通用文档读写、反馈、生命周期与变更传播协议）
>

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：为 OR 预处理链准备稳定可读的文本化工作副本——把各类原始需求材料忠实转成 Markdown，原始文件保持不动，并为每份材料登记处理状态。
>
> **目标**：
> 1. **初始化原料区**——确保 `00-origin-requirement-materials/10-raw-files/` 与 `01-eos-sysdev-status.md` 三张表（原始材料处理进度/切分文件处理进度/OR 基线条目处理进度）就绪
> 2. **发现待处理材料**——按固定后缀和状态表记录识别尚未文本化的原始文件
> 3. **执行纯文本化**——将源文件忠实转换为 Markdown 工作副本，保留原文结构与表达
> 4. **执行查重检测**——新文本化正文与既有文本化正文逐字比对，重复材料标记为废弃并输出软链接文档
> 5. **更新状态接口**——先更新状态文档的原始材料处理进度，再据此写入文本化文档管理区状态摘要
> 6. **输出行动清单**——提示人类选入切分、确认重复材料或进入下游 ort01

### 1.2 人机交接点总览

**一句话**：你在本步的参与点是选材、确认重复、终止、重跑——都通过**直接编辑状态文档表 A**（改 `人类决策`、清 `生命周期`）或删除源文件表达，AI 用 git 检出。

| 人类参与点 | 在哪操作 | 做什么 |
|-----------|---------|--------|
| ① 选材入切分 | 状态文档表 A | 对 `已文本化` 材料设 `人类决策=同意切分` → 进入 ort01 |
| ② 确认重复 | 状态文档表 A / 10-raw-files | **删除源文件即确认**（git 检出）；重复材料已标 `已废弃（重复）` |
| ③ 终止材料 | 状态文档表 A | 设 `人类决策=已终止` → 废弃处理 |
| ④ 重跑材料 | 状态文档表 A | 清除该行 `生命周期` 值（转换失败重试 / 重复误判 / 重新文本化）→ 触发重跑 |

> AI 凭什么判哪些材料进入/跳过见 §二 材料进入规则；反馈如何被检测与记录见 §2.2 与 §三。

### 1.3 本步负责与不负责

本 Skill 负责：

1. **接收**——扫描 `10-raw-files/` 中的原始材料文件，自动跳过本步/下游产物
2. **初始化**——首次运行时创建原料目录和 EOS OR 预处理状态文档基础表
3. **登记**——为新材料在原始材料处理进度中登记记录，维护源文件、文本化文档、生命周期、AI 建议和操作指引
4. **转换**——把 PDF/图片/扫描件/文本文件等转换为 Markdown 文本化文档
5. **查重**——正文区全文精确比对，重复材料生成定向引用文档并标记 `已废弃（重复）`
6. **交接**——输出待选入切分清单、重复材料通知和下一步操作指引
7. **重进入**——支持新增材料、重新文本化、重复误判重跑三类重进入

本 Skill 不负责：

1. OR 语义切分、切分方案生成或拆分建议（由 eos-ort01-chunk 负责）
2. 模糊需求澄清（由 eos-ort02-clarify 负责）
3. OR 条目规范化、分类、编号或冲突检测（由 eos-ort03-norm 负责）
4. 业务需求/引擎需求/非功能需求分配（由 wft01 系列负责）
5. 修改、摘要、解释或补充原始需求内容

## 二、文本化设计基础

### 2.1 文本化文档结构

文本化文档命名为 `{原始文件名}.textualized.md`，位于 `10-raw-files/`。原始文件保持只读不动，即使源文件本身已经是 `.md`，本步也生成独立工作副本。

| 区域 | 位置 | 内容 | 写入者 |
|------|------|------|--------|
| 管理区 | 文档顶部（正文前） | 状态摘要（阶段/AI 建议/待处理/操作指引）、迭代记录 | eos-ort00 写入状态摘要；下游追加迭代记录 |
| 正文区 | 管理区之后 | 纯原文内容（仅文本化后原文与转录占位标注，无切分标记、方案块或分析建议块） | eos-ort00 |

**正文区纯净原则**：正文区仅包含原文。所有切分方案块、模糊标注、分析建议块均由下游步骤写入并适时清理。本步不产生任何分析产物。

**历史追溯约定**：文档不设置历史区、归档区或旧版正文；历史版本由 Git 管理（[00-doc-conventions §14.7](../../../00-generalspec/00-doc-conventions.md#147-不保留历史区)）。需留痕的信息（如变更结论）摘要写入管理区，不得复制旧版全文。

### 2.2 文档生命周期管理

**一句话**：每份 OR 预处理文档都有自己的"生命周期"——从登记到废弃经历一系列阶段。本步用状态文档 `01-eos-sysdev-status.md` 作为统一登记表，追踪所有文档当前所处阶段、AI 建议和人类决策。

**状态文档按管理对象分三张表**：

| 表 | 管理对象 | 生命周期线 | 推进者 |
|----|---------|-----------|--------|
| 表 A（原始材料处理进度） | 原始材料 | 已登记 → 已文本化 → 切分方案待确认 → 已切分 → 已废弃（含已废弃（重复）） | ort00 → ort01 |
| 表 B（切分文件处理进度） | 切分文件（`.chunk-*.md`） | 已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃 | ort01 → ort02 → ort03 |
| 表 C（OR 基线条目处理进度） | OR 基线条目 | 待处理 → 待确认方案 → 已分配 → 验证中 → 已验证冻结 → 已废弃 | ort03 → wft01 |

**一行记录 = 一份文档的生命状态**，由三个核心字段协同描述：

| 字段 | 含义 | 谁写 |
|------|------|------|
| 生命周期 | 文档当前所处阶段（流程状态的唯一依据） | 各步骤转迁 |
| AI建议 | AI 对下一步的推荐（供人参考，不作硬性入口判断） | 各步骤 |
| 人类决策 | 人类的选择（决定文档能否进入下一阶段） | 人类 |

示例（文本化完成后）：`生命周期=已文本化`、`AI建议=可以切分`、`人类决策=空`。人类设为 `同意切分` 后，下一轮 ort01 才接手切分。

**同步契约**：状态文档是**唯一权威源**。AI 每次写入时：

1. **先更新状态文档表**——如实记录文档所处阶段；
2. **再推导写内嵌状态表**——从状态文档推导写入各文档管理区状态表（给人快速看）。

若两者不一致，以状态文档为准重建。

写回前检测状态文档是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 摘要输出时提示人类。

**基线协议（链级不变式）**：每次运行结束 Step 3 用 `scripts/ai-commit.sh` 提交基线（author=EOS-AI + `[AI]` 前缀），并把新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段。ort00 自身检测用**状态扫描**、不读基线；提交的目的是把 ort00 的产出（文本化文档全文 + 表 A 写入）落基线，避免进入下游 ort01 的 git diff 视野被误判为人类反馈。

**反馈检测（状态条件）**：ort00 的反馈载体就是状态表 A 与文件系统本身，AI 通过扫描状态条件发现反馈并**直接处理**（状态自终止——处理后生命周期转迁、条件不再成立，无需 `反馈：`+`[已处理]` 记录分离）：

| 表 A / 文件系统 状态条件 | 判读 | 处理 |
|------------------------|------|------|
| `人类决策=已终止` 且 生命周期≠`已废弃` | 终止 | 生命周期 → `已废弃`、AI建议 → `建议终止`，追加废弃说明 |
| `生命周期` 为空 且 `10-raw-files/` 有对应文件 | 重跑 | 按原状态重跑（重判 / 重文本化 / 重转换） |
| `生命周期=已废弃（重复）` 且 源文件不存在 | 确认重复 | 收尾（行动清单移除） |
| `人类决策=同意切分` | 选材 | 不处理；列入行动清单（ort01 入口） |
| `人类决策=暂不切分` | 暂不切分 | 不处理；保留行动清单 |

> **与 ort01 的差异**：ort01 的反馈活在文本化文档（方案块/反馈区），须用 git diff 检出并记录到表 A；ort00 的反馈即在表 A/文件系统，直接状态扫描，处理即状态转迁，无需 `[已处理]` 标记与记录分离。

**原始材料处理进度：记录字段**（ort00 首次创建时使用）：

| 字段 | 写入者 | 说明 |
|------|--------|------|
| 记录ID | AI（首次登记） | 自动生成唯一标识，如 `ORT-YYYYMMDD-001`（含日期） |
| 内容摘要 | 各步更新 | 该材料当前处理阶段的一句话摘要；重复时写 `与[源文件名]内容完全重复`；ort01 有已记录未处理反馈时以 `‖ 反馈：<类型>（<要点>）` 分段追加，处理完成后追 `[已处理]` |
| 源文件 | ort00 | 原始文件名（含扩展名） |
| 文本化文档 | ort00 | ort00 写文本化 `.textualized.md` 文件名；切分后仍指向该文件（切片清单由表 B `子文件` 列独揽，此列不重复） |
| 生命周期 | 各步转迁 | 见上文原始材料处理进度生命周期线；重复时置 `已废弃（重复）` |
| AI建议 | 各步更新 | 如 `可以切分` / `已废弃（重复）` |
| 人类决策 | 人类 | 空 / `同意切分` / `暂不切分` / `已终止` |
| 操作指引 | 各步更新 | 人类下一步应执行的操作 |
| 最后更新 | 各步更新 | 格式 `YYYY-MM-DD` |

**管理范围**：状态文档只管理 OR 预处理链（ort00~ort03）的文档生命周期。wft01~05 的设计产物（STR/BP/SysReq/PA）以各自产品文档管理区为权威源，不使用本表；wft 若补充生成原始需求材料，只登记到原始材料处理进度（生命周期=`已登记`），仍由 ort00~ort03 进入预处理链。

### 2.3 材料进入规则：筛选与转录

**一句话**：本步设计了两条材料进入规则——先筛选（哪些材料不进入本步），再转录（进入的材料如何忠实转成 Markdown）。

#### 2.3.1 筛选：哪些材料不进入本步

扫描后逐文件判断，以下情况直接跳过：

| 跳过原因 | 判定条件 |
|---------|---------|
| 不是原始材料 | 文件名以 `.textualized.md` 结尾（本步产物）；或含 `.chunk-`（下游切分文档） |
| 已在处理流程中 | 原始材料处理进度已有记录，生命周期为 `已文本化` / `切分方案待确认` / `已切分`（`已登记` 材料每轮重新进入转换：转换失败自动重试，中断材料继续处理） |
| 重复关系已记录 | 原始材料处理进度中生命周期为 `已废弃（重复）`（已通过软链接文档记录） |
| 已废弃 | 原始材料处理进度中生命周期为 `已废弃`（如需重新启用，先清除原始材料处理进度中该记录的生命周期值） |

> 注：`澄清中` / `已澄清` / `已规范化` 属于表B（切分文件处理进度）的生命周期取值，不会出现在表A（原始材料处理进度），故不参与表A 跳过判定。

只有"原始材料处理进度中无对应记录"的文件才是新材料，执行文本化并输出 `{原始文件名}.textualized.md`。若所有文件都跳过，输出"所有材料已文本化"并结束。

#### 2.3.2 转录：忠实转成 Markdown

**总原则**：只改载体、不改内容——不总结、不解释、不补充。绝大多数内容直接转录；只有内容识别不了或不确定时，才按下表处理：

| 场景 | 处理方式 |
|------|---------|
| 内容能识别（文本/表格/PDF 表格） | 直接转录为 Markdown，保留结构和数值 |
| 图片/扫描件 | 识别文字内容，标注 `[AI 识别，待人工确认]` |
| 录音转写 | 标注发言人和时间戳；听不清的标 `[听写不清]` |
| 手写内容 | 能辨识的标 `[AI 推测]`；不能辨识的标 `[原文模糊]` |
| 多语言混写 | 保留原文语种，必要时标注 `[中文/英文/...]` |
| 完全无法识别的图片 | 写占位符 `[图片：无法识别文字内容]` |
| 文档明显不完整 | 开头标注 `[文档疑似不完整：缺页/截断]` |
| 转换失败（损坏/加密/格式不受支持/转换器报错） | 不输出文本化文档；在原始材料处理进度登记失败：`内容摘要=转换失败：<原因>`、`生命周期=已登记`、`AI建议=待人工处理`、`操作指引=人工检查/替换源文件后清除生命周期值重跑` |
| 部分转换成功 | 能转部分正常转录；未转部分正文区标注 `[转换失败：<原因>]`；按 `已文本化` 进入下游 |

> **标注的意义**：标注 = "此处需人工确认"的提示牌，不是 AI 的加工结论。宁可用标注如实说明，也不凭空补全。

### 2.4 已有文档处理：查重与重进入

**一句话**：材料转成文本化文档后，要和已有文档去重（查重）；已进入流程的材料再次运行本步时，按重进入规则处理。

#### 2.4.1 查重：去重比对

**目的**：避免同一份材料被重复处理。

- **比什么**：正文区全文（管理区状态表不参与比对）；比对范围：所有生命周期≠`已废弃（重复）` 的既有文本化文档
- **怎么算重复**：全文逐字完全一致（忽略行尾空格和连续空行）
- **重复了怎么办**：标记 `已废弃（重复）`，不保留独立正文，正文区改用软链接指向原文档

#### 2.4.2 重进入：材料已进流程后的再处理

再次运行本步时可能遇到三种情况：

| 场景 | 处理 |
|------|------|
| 新增原始材料 | 原始材料处理进度中无对应记录，按新材料正常文本化 |
| 重新文本化 | 先检查这份材料是否已被下游消费（切分/澄清/OR/STR）。未被消费：清除原始材料处理进度生命周期值，替换旧工作副本重做。已被消费：先写变更影响声明，把受影响的下游对象标记为待重审，再重跑本步 |
| 重复文档误判 | 清除原始材料处理进度中该记录的生命周期值，删除软链接文档，重跑本步重新判定 |
| 转换失败重试 | 人工修复/替换源文件后，清除原始材料处理进度该行生命周期值，重跑本步重新转换 |

**变更传播约束**（按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议)）：新增材料不影响既有结果；但重新文本化或重复关系纠正若改变正文、来源或有效性，必须**列出受影响的切分文件、OR 和已消费 STR**，不得笼统说"下游不受影响"。

### 2.5 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步是纯格式转换，不涉及需求/方案角色切换，无需求相对性问题 |
| 详概分离 | 本步仅做格式转换和状态登记，不进行语义理解、切分分析或需求规范化 |
| 文档结对 | 本步不产生文档结对关系；文本化文档是 eos-ort01-chunk 的输入 |
| 基于资产 | 原始出处保留；文本化文档是原始文件的处理副本，不覆盖源文件 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |

| Start | 前置校验 | 检查目录/状态文档/源文件/基线就绪 | 统一 | 就绪/结束 | 目录结构、状态文档（首次） |

| 2 | 新增处理 | 发现登记新材料 + 文本化 + 查重 | 统一 | 文本化文档/软链接文档 | 表 A、10-raw-files |

### 3.1 Step Start · 前置校验

按顺序检查以下前置条件，缺什么补什么，然后根据情况继续或结束：

1. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/` 是否存在；不存在则创建目录结构
2. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则创建
3. 检查 `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则创建状态文档模板
4. 若状态文档已存在，校验三张表（原始材料处理进度/切分文件处理进度/OR 基线条目处理进度）的表头和字段说明；不一致时按 §4.2 模板更新
5. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
6. 若 `10-raw-files/` 为空，输出“目录已就绪，请将原始材料放入 `10-raw-files/` 后重新启动本步”并结束
7. 全部就绪后进入 Step 1

### 3.2 Step 1 · 反馈处理

**一句话**：扫表 A 的状态条件，发现人类反馈并直接处理——反馈载体就是状态表，处理即状态转迁，完成后条件自动失效（无需 `[已处理]` 标记）。

| 表 A / 文件系统 状态条件 | 判读 | 处理 |
|------------------------|------|------|
| `人类决策=已终止` 且 生命周期≠`已废弃` | 终止 | 生命周期 → `已废弃`、AI建议 → `建议终止`，追加废弃说明 |
| `生命周期` 为空 且 `10-raw-files/` 有对应文件 | 重跑 | 按原状态重跑：原软链接存在 → 删软链接+重新查重判定；原文本化文档存在 → 重新文本化（下游已消费先输出 91 §A.7 变更影响声明）；原转换失败 → 重新转换 |
| `生命周期=已废弃（重复）` 且 源文件不存在 | 确认重复 | 收尾：行动清单移除 |
| `人类决策=同意切分` | 选材 | 不处理；列入行动清单（ort01 入口） |
| `人类决策=暂不切分` | 暂不切分 | 不处理；保留行动清单 |

处理前执行附录 B.1 竞态保护（快照/复核，命中 `[需确认]` 不覆盖）；处理后按 §2.2 同步契约推导更新文本化文档管理区。无任何反馈与新材料时输出「无待处理对象」并结束。

### 3.3 Step 2 · 新增处理

**一句话**：处理新材料——发现未登记源文件、登记表 A、文本化、查重。

**1. 材料发现与登记**

1. 扫描 `10-raw-files/` 中的文件
2. 按 §2.3.1 跳过规则过滤本步产物、下游产物和已进入流程的材料
3. 对原始材料处理进度中无对应记录的原始材料自动登记：
   - `记录ID`：自动生成唯一标识，如 `ORT-YYYYMMDD-001`（含日期）
   - `源文件`：原始文件名
   - `文本化文档`：预期 `{原始文件名}.textualized.md`
   - `生命周期`：`已登记`
   - `AI建议`：`可以切分`（文本化完成后生效；登记阶段作为预期建议）
   - `操作指引`：完成文本化后由人类决定是否选入切分
4. 若待处理清单为空，输出“所有材料已文本化，无需本步操作”并结束

**2. 文本化与查重**

（1）**文本化转换**——对每个待处理源文件执行格式转换：

- 非文本格式（PDF/图片/扫描件/录音转写等）转换为 Markdown
- 文本格式（`.md` / `.txt` 等）复制为独立文本化工作副本
- 保留原文结构（章节/段落/列表/表格）；不修改、不摘要、不解释原文表述
- 无法识别内容按 §2.3.2 标注占位符
- 转换失败（损坏/加密/格式不受支持/转换器报错）：按 §2.3.2 处理——不输出文本化文档，在原始材料处理进度登记失败，不置 `已文本化`，列入 Step End 待人工处理清单
- 部分转换成功：能转部分转录，未转部分标注 `[转换失败：<原因>]`，仍按 `已文本化` 处理

（2）**查重检测**——新文本化正文区与既有文本化文档正文区逐一比对：

| 结果 | 处理 |
|------|------|
| 无重复 | 输出完整文本化文档；原始材料处理进度更新为 `生命周期=已文本化`、`AI建议=可以切分` |
| 发现重复 | 输出软链接文档；原始材料处理进度更新为 `生命周期=已废弃（重复）`、`AI建议=已废弃（重复）`、`内容摘要=与[源文件名]内容完全重复` |

（3）**两区文档写入**——文本化文档管理区写入 OR 文本化文档状态表（模板见 §4.1）；正文区仅纯原文与转录占位标注。

**写回顺序（同步契约）**：先更新状态文档表 A（权威源），再从表 A 推导写入文本化文档管理区。写回前执行附录 B.1 冲突检查。

### 3.4 Step 3 · 提交基线

把本轮 Step 1~2 的处理结果提交为 git 基线。

**为什么需要提交**：ort00 自身检测用状态扫描、不需要基线；但 ort00 的产出（新文本化文档全文 + 表 A 写入）若不落基线，会进入下游 ort01 的 git diff 视野，被误判为「正文区原文行被改」等反馈。提交基线维持「基线 = 最后 AI 提交，diff 只含人类变更」的链级不变式。

1. **提交范围**：本轮更新的表 A、文本化文档/软链接文档；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致）
4. **无变更**：工作区无改动时跳过提交，基线不变

### 3.5 Step End · 运行结束输出

输出行动清单（本次运行报告 + 下一步交接），**结束**——ort00 反馈全在表 A，人类直接改表 A 即反馈，无需对话收集：

```text

  本轮发现重复：[文件名] → 与 [原始源文件名] 完全重复，已标记 已废弃（重复）
  本轮转换失败：[文件名] → 转换失败：<原因>（表A 已登记，生命周期=已登记）
  处理反馈：[文件名]（终止 → 已废弃 / 重跑 → 重新转换/重新判定 / 确认重复 → 收尾）
资产落账：表 A 已同步；基线已提交（<hash>）

一、待反馈（编辑表 A 即反馈，AI 用状态扫描检测）
  A. 选材 → 表 A `人类决策=同意切分`（进入 ort01）
  B. 暂不切分 → 表 A `人类决策=暂不切分`
  C. 终止 → 表 A `人类决策=已终止`

二、下一步

  ② 有新原始材料 → 重跑本步继续文本化

| 已分配 | OR→STR 分配方案已通过，等待或进入下游承接 | wft01-*（STR 审阅通过时同步回写） |
| 验证中 | 该 OR 的承接链已进入全链追溯验证；本表仅保留只读同步状态 | 追溯验证 |
| 已验证冻结 | 全链验证通过；本表仅保留只读同步状态 | 追溯验证 |
| 已废弃 | OR 条目被废弃 | 本步/下游均可触发 |

**人类决策取值**：**同意分配**→选入当前批次进入 wft01-* 分解分配 | **—**→暂不处理

**控制流**：人类设 `人类决策=同意分配` → ort03 将符合条件的 OR 按类型加入对应 wft01 的 `AI可以处理节点` 分节；AI 在下一轮 wft01-* 中读取处理；wft01-* 首次生成方案后写为 `待确认方案`；相关 STR 节点审阅通过并进入 `可以分解分配` 时，对应 OR 同步更新为 `已分配`；追溯验证选入时推进到 `验证中`，验证通过后更新为 `已验证冻结`。
```
