# 文本化原始需求 → 切分文档 · 语义切分与反馈执行
**Skill ID**: eos-ort01-chunk

> **概述**：把已文本化的文档切成语义独立的片段——读取人类在状态文档表 A 选入的材料，分析结构后生成切分方案供人类确认；再次运行时读取反馈，执行切分、不切分、调整重生成或废弃。本步不做 OR 规范化，也不评价需求。
>
> **输入 → 输出**：文本化 `.textualized.md` 文档（正文区：纯原文）+ `01-eos-sysdev-status.md` 表 A → 切分文件（`.chunk-{seq}.md`）+ 文本化文档正文区更新（方案块/清理后纯原文）+ 状态文档表 A/表 B 更新
>
> **适用场景**：EOS 原始需求预处理链第 2 步；将已文本化材料拆成适合澄清和规范化的语义片段。
>
> **接口设计**：本步接口载体有两个：文本化文档正文区的**切分方案块**（写入=待确认，清理=已执行）和状态文档**表 A/表 B**（原料级+切分文件级进度追踪）。入口靠状态文档和方案块分流：无块生成方案，有块读取反馈并执行。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（Step Start、反馈优先、Step End 与变更传播通用协议）
>
> **版本**：v0.13 | **修订**：2026-08-12 | **说明**：Step End 尾部按 91 §A.5 反馈交互协议改造（AI 不结束对话、口令反馈、AI 代改表），语义不变

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把一份文本化文档切成多份语义独立、体量合适、能进入澄清的切分文件，保留原文出处，并让人类对切分方案把关。
>
> **目标**：
> 1. **识别选入材料**——读取表 A 中 `生命周期=已文本化` 且 `人类决策=同意切分` 的文本化文档
> 2. **生成切分方案**——基于结构、语义段落、体量和关联性形成切分/不切分建议
> 3. **建立反馈闭环**——将方案块和反馈提示区写入正文区，等待人类确认或调整
> 4. **执行切分输出**——按确认方案生成 `.chunk-{seq}.md` 文件，写入 YAML frontmatter 和状态表
> 5. **处理迭代反馈**——支持 `[调整]` 重生成、`[确认不拆分]` 单片输出、`[废弃]` 终止处理
> 6. **同步状态接口**——先更新状态文档表 A/表 B，再推导更新文本化文档和切分文件的状态摘要

本 Skill 负责：

1. **接收**——读取文本化文档和状态文档表 A，识别本轮选入切分的材料
2. **分析**——执行文档结构识别、语义段落识别、体量评估和关联性分析
3. **规划**——生成切分方案块或不切分方案块，并写入正文区反馈提示区
4. **执行**——根据反馈生成切分文件，或输出单片切分文件
5. **迭代**——根据人类调整意见重生成方案（历史由 Git 管理，不归档旧方案）
6. **落账**——更新表 A 的原料级状态，向表 B 追加切分文件级记录
7. **交接**——输出待反馈、待选入澄清、下一批选材的行动清单

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 模糊需求澄清和标注（由 eos-ort02-clarify 负责）
3. OR 条目规范化、编号、分类或冲突检测（由 eos-ort03-norm 负责）
4. 按 FR-BIZ / FR-ENG / NFR 分配到 wft01 系列
5. 修改原文语义、补充需求内容或作设计判断

## 二、切分设计基础

### 2.1 切分文档结构

**一句话**：本步在文本化文档（`{原始文件名}.textualized.md`）正文区写切分方案，人类确认后输出切分文件（`{原始文件名}.chunk-{seq}.md`）。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| 管理区 | 状态摘要、切分迭代记录、决策记录 | 写入/更新状态摘要，追加迭代记录和决策记录 |
| 正文区 | 原文 + 当前切分方案块 + 反馈提示区（临时） | 生成阶段写入方案块；执行阶段清理方案块和反馈区，使正文区回归纯原文 |

**正文区检测原则**：正文区中当前是否存在 `╔═ 切分方案` 块，是分流关键。历史版本由 Git 管理，旧方案不参与入口判断。

### 2.2 文档生命周期管理

**一句话**：本步通过状态文档推进切分文档的生命周期——表 A 记录原料级进度，表 B 记录每个切分文件的进度。

本步使用状态文档两张表：

| 表 | 粒度 | 本步职责 |
|----|------|---------|
| 表 A — 原始材料处理进度 | 文档级 | 读取选入切分材料；生成方案后置 `切分方案待确认`；执行后置 `已切分`；废弃后置 `已废弃` |
| 表 B — 切分文件处理进度 | 切分文件级 | 执行切分时为每个 `.chunk-{seq}.md` 追加记录，初始 `生命周期=已切分`、`AI建议=可以澄清` |

**记录三要素职责**（与 ort00 一致）：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段，供 AI 和流程判断使用 |
| AI建议 | 提示字段，仅供人类快速理解下一步建议，不参与 Step 入口硬判断 |
| 人类决策 | 批次控制字段，决定材料是否进入本轮处理 |

**同步契约**：生成方案分支先更新表 A；执行切分分支先追加/更新表 B 并更新表 A；再从权威源推导写入文本化文档和切分文件的内嵌状态表。不一致时以状态文档为准重建。

### 2.3 入口与重进入规则

**一句话**：本步只处理人类在表 A 明确选入（`同意切分`）且已完成文本化的材料；每次运行先处理人类已反馈的方案，再处理新选入的材料。

Step 1 的入口硬条件：

| 条件 | 说明 |
|------|------|
| `生命周期=已文本化` | 上游 ort00 已完成文本化 |
| `人类决策=同意切分` | 人类明确选入本批切分 |

`AI建议=可以切分` 只是候选提示，不作为入口硬条件。`已登记` 是 ort00 内部中间状态，不构成 ort01 入口条件。

运行路由参考 `wft01-biz`：前置校验通过后，**先处理表 A 中 `生命周期=切分方案待确认` 的反馈，再处理 `生命周期=已文本化` + `人类决策=同意切分` 的新增材料**。因为反馈可能改变表 A/表 B 状态和下游澄清入口，不能被新增材料抢先。

**两个"不切分"不是一回事**：表 A 的 `人类决策=暂不切分` 表示"本批不进入 ort01"；正文区反馈 `[确认不拆分]` 表示"已进入 ort01，但人类确认输出单片切分文件"。不得用 `不切分` 或 `暂搁置` 混用。

反馈处理入口：

| 条件 | 处理 |
|------|------|
| 表 A `生命周期=切分方案待确认` 且正文区有方案块，无反馈文本 | 跳过，等待人类反馈 |
| 有方案块 + `[同意执行]` | 按方案块执行切分 |
| 有方案块 + `[确认不拆分]` | 输出单片切分文件 |
| 有方案块 + `[调整]` 或明确修改意图 | 重生成方案（历史由 Git 管理） |
| 有方案块 + `[废弃]` | 表 A 置 `已废弃`，追加废弃记录 |

### 2.4 语义切分规则

**一句话**：判断一份文档"切不切、切成几片"的四步分析——先看清结构，再找语义段，评估体量，看关联性。

语义结构分析包含四步：

| # | 操作 | 说明 |
|---|------|------|
| 1 | 文档结构识别 | 识别章节、标题、子标题层级；无显式结构时按段落语义聚类 |
| 2 | 语义段落识别 | 根据主题转换点、章节边界、段落主题一致性识别自然语义段 |
| 3 | 体量评估 | 判断文档或段落是否超过单次处理的合理范围 |
| 4 | 关联性分析 | 判断概念定义、上下文依赖和跨段引用是否要求保持同片 |

切分判断：

| 条件 | 结论 | 输出 |
|------|------|------|
| 文档篇幅适中且语义单一 | 不切分 | 建议不切分，理由为篇幅适中/语义单一 |
| 文档篇幅大但语义不可分 | 不切分 | 建议不切分，并提示下游注意体量 |
| 文档篇幅大且含多个语义单元 | 切分 | 输出多片方案 |
| 文档篇幅小但含多个独立业务域 | 切分 | 输出多片方案 |

边界处理：

| 边界情况 | 处理方式 |
|---------|---------|
| 方案块行号边界落在段落中间 | 被截断段落完整归入起始片，并在行动清单中提示边界截断 |
| 连续两片之间有空白行 | 空白行归入前一片 |
| 切分内容为空 | 不输出空文件，视为无效标记 |

### 2.5 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做语义结构分析和边界识别，不评价需求内容、不展开设计决策 |
| 文档结对 | 本步不产生文档结对关系；切分文件是 eos-ort02-clarify 的输入 |
| 基于资产 | 切分文件是原始文档的派生资产，通过文件名、frontmatter、表 A/表 B 保持追溯 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查上游文本化文档和状态文档是否就绪 | 统一 | 就绪/结束 | — |
| 1 | 新增处理 | 读取表 A 选入材料，生成切分方案块 | 统一 | 方案块 + 反馈区 | 表 A、文本化文档 |
| 2 | 反馈处理 | 读取反馈，执行切分/不切分/调整/废弃 | 统一 | 切分文件/新版方案/废弃记录 | 表 A、表 B、切分文件 |
| End | 输出交互 | 输出三段式结果、反馈指引和下一步交接 | 人类 | Step End 三区输出 | — |

核心驱动逻辑：每次运行先处理待确认方案反馈，再处理新增选入材料。表 A 控制材料级状态，表 B 承接切分文件级状态。

### 3.1 Step Start · 前置校验

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
3. `10-raw-files/` 中是否存在 `.textualized.md` 文档；不存在则提示先运行 `eos-ort00-textualize` 并结束
4. 全部就绪后先执行反馈入口检测：存在 `生命周期=切分方案待确认` 的对象时进入 Step 2；无待处理反馈时再进入 Step 1

### 3.2 Step 1 · 新增处理

读取状态文档表 A，按以下规则分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 对应文本化文档进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`，追加废弃说明 |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

方案生成动作：

1. 读取文本化文档正文区纯原文
2. 执行语义结构分析（结构识别、语义段落、体量评估、关联性分析）
3. 形成切分/不切分建议
4. 在正文区原文之后写入切分方案块和反馈提示区
5. 更新表 A：`生命周期=切分方案待确认`、`AI建议=审核切分方案`
6. 从表 A 推导写入文本化文档管理区状态摘要

### 3.3 Step 2 · 反馈处理

读取表 A 中 `生命周期=切分方案待确认` 的文档，检测正文区方案块和反馈。

**1. 同意执行**

1. 读取切分方案块
2. 校验行号范围无重叠、无遗漏，语义标签完整
3. 按行号范围切分原文
4. 为每片写入 YAML frontmatter
5. 输出 `{原始文件名}.chunk-{seq}.md`
6. 清理正文区方案块和反馈区，使正文区回归纯原文
7. 表 B 为每片追加记录：`生命周期=已切分`、`AI建议=可以澄清`
8. 表 A 更新为 `生命周期=已切分`
9. 推导更新文本化文档和切分文件状态摘要，追加迭代记录和决策记录

**2. 确认不拆分**

1. 输出单片切分文件，`seq=1`、`total=1`
2. 清理正文区方案块和反馈区
3. 表 B 追加单片记录，表 A 更新为 `已切分`
4. 状态摘要写为 `不拆分已确认`、`AI建议=可以澄清`

**3. 调整重生成**

1. 解析人类反馈中的边界、标签、片数或范围调整意图
2. 在管理区摘要记录调整结论（历史版本由 Git 管理，不归档旧方案全文）
3. 写入新版方案块和新反馈提示区
4. 表 A 保持 `生命周期=切分方案待确认`
5. 管理区追加重生成记录

**4. 废弃**

1. 表 A 生命周期置 `已废弃`
2. 清理或保留方案块按人类反馈语义处理；若保留，需在管理区标注该材料已终止
3. 管理区追加废弃记录

### 3.4 Step End · 运行结束输出

Step End 参考 `wft01-biz` 的三区输出模板（结果 → 方案反馈 → 下一步），本 Skill 实例化如下：

```text
══════════════════════════════════════════
  eos-ort01-chunk 本轮完成
══════════════════════════════════════════

当前状态：<待确认切分方案 / 已切分可澄清 / 已废弃 / 无新增处理>
  生成切分方案：<文件名>（建议切分 N 片 / 建议不切分，等待反馈）
  执行切分输出：<文件名.chunk-001.md ...>（表 B 生命周期=已切分，AI建议=可以澄清）
  调整重生成：<文件名>（v{N-1}→v{N}，仍待确认）
  废弃材料：<文件名>（表 A 生命周期=已废弃）
资产落账：表 A/表 B 已同步；文本化文档正文区 <保留方案块 / 已清理为纯原文>

一、方案反馈
  A. 同意执行 → 在文本化文档反馈区填写 [同意执行]
  B. 局部调整 → 在反馈区填写 [调整]：如“002 范围扩到 L500”
  C. 确认不拆分 → 在反馈区填写 [确认不拆分]，输出 total=1 单片切分文件
  D. 废弃材料 → 在反馈区填写 [废弃]

二、下一步
  本 Skill → 继续选择表 A `生命周期=已文本化` + `人类决策=同意切分` 的材料，或处理 `切分方案待确认` 的反馈
  后续    → 表 B `生命周期=已切分` + `AI建议=可以澄清` 的切分文件，可设 `人类决策=同意澄清` 后进入 eos-ort02-clarify
```

**交互方式**：按 [91 规范 §A.5](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a5-反馈交互协议) 反馈交互协议，**AI 不结束对话**——输出本摘要后保持对话，人类以自然语言回复口令，AI 代为更新状态文档与正文区反馈。

| 口令 | AI 代执行 |
|------|----------|
| 「同意执行 / 调整 / 确认不拆分 / 废弃 [文件名]」 | 写入正文区反馈区对应触发词 |
| 「同意澄清 [切分文件]」 | 表 B 人类决策=同意澄清 |
| 「继续」 | 重跑本步 |
| 「打开状态文档」 | 输出路径和建议关注行 |

## 四、模板、产出与下游关系

### 4.1 切分方案块模板

切分场景：

```markdown
╔═ 切分方案 ═══════════════════════╗
║ 建议：切分为 3 片                 ║
║                                   ║
║ 001 · 市场部业务需求              ║
║   行号：L120~L340                ║
║   对应：§2.1~§2.5               ║
║   理由：同属市场部业务域，语义独立  ║
║                                   ║
║ 002 · 研发部开发流程              ║
║   行号：L341~L480                ║
║   对应：§3.1~§3.4               ║
║   理由：同属研发部业务域，语义独立  ║
╚═════════════════════════════════════╝
```

不切分场景：

```markdown
╔═ 切分方案 ═══════════════════════╗
║ 建议：不切分                     ║
║ 理由：文档语义单一，无需切分       ║
╚═════════════════════════════════════╝
```

反馈提示区：

```text
──────────────────────────────────────────
请在此处输入反馈意见：

  [同意执行] — 按当前方案执行切分
  [调整] — 描述需要调整的内容
  [确认不拆分] — 不应切分，输出单片
  [废弃] — 该材料应废弃

您的反馈：
```

### 4.7 与下游步骤的关系

```text
eos-ort01-chunk（本步：语义切分）
  ├─ 文本化文档正文区：方案确认后回归纯原文
  └─ 切分文件：含 YAML frontmatter + 切分正文

  ├─ 读取选入澄清的切分文件
  ├─ 对模糊内容做标注和澄清闭环
  └─ 达成已澄清后进入 eos-ort03-norm
```
