# 文本化原始需求 → 切分文档 · 语义切分与反馈执行
**人类方案ID**: eos-ort01-chunk

> **概述**：把已文本化的文档切成语义独立的片段——读取人类在状态文档表 A 选入的材料，分析结构后生成切分方案供人类确认；再次运行时读取反馈，执行切分、不切分、调整重生成或废弃。本步不做 OR 规范化，也不评价需求。
>
> **输入 → 输出**：文本化 `.textualized.md` 文档（正文区：纯原文）+ `01-eos-sysdev-status.md` 表 A → 切分文件（`.chunk-{seq}.md`）+ 文本化文档正文区更新（方案块/清理后纯原文）+ 状态文档表 A/表 B 更新
>
> **适用场景**：EOS 原始需求预处理链第 2 步；将已文本化材料拆成适合澄清和规范化的语义片段。
>
> **接口设计**：本步接口载体有两个：文本化文档正文区的**切分方案块**（写入=待确认，清理=已执行）和状态文档**表 A/表 B**（原料级+切分文件级进度追踪）。入口靠状态文档和方案块分流：无块生成方案；有块则读取反馈——有反馈执行、无反馈等待。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（Step Start、反馈优先、Step End 与变更传播通用协议）
>

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把一份文本化文档切成多份语义独立、能进入澄清的切分文件，保留原文出处，并让人类对切分方案把关。
>
> **目标**：
> 1. **识别选入材料**——读取表 A 中 `生命周期=已文本化` 且 `人类决策=同意切分` 的文本化文档
> 2. **生成切分方案**——以相关方端到端场景为主要边界，识别候选单元并形成切分/不切分建议
> 3. **建立反馈闭环**——将方案块和反馈提示区写入正文区，等待人类确认或调整
> 4. **执行切分输出**——按确认方案生成 `.chunk-{seq}.md` 文件，写入 YAML frontmatter 和状态表
> 5. **处理迭代反馈**——支持 `[调整]` 重生成、`[确认不拆分]` 单片输出、`[废弃]` 终止处理
> 6. **同步状态接口**——先更新状态文档表 A/表 B，再推导更新文本化文档和切分文件的状态摘要

本 Skill 负责：

1. **接收**——读取文本化文档和状态文档表 A，识别本轮选入切分的材料
2. **分析**——执行相关方与场景识别、场景内环节识别和关联性分析
3. **规划**——生成切分方案块（建议切分或建议不切分），写入正文区原文之后，并附反馈提示区
4. **执行**——根据反馈生成切分文件，或输出单片切分文件
5. **迭代**——根据人类调整意见重生成方案（历史由 Git 管理，不归档旧方案）
6. **落账**——更新表 A 的原料级状态，向表 B 追加切分文件级记录
7. **交接**——输出待反馈、待选入澄清、下一批选材的行动清单

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 模糊需求澄清和标注（由 eos-ort02-clarify 负责）
3. OR 条目规范化、编号、分类或冲突检测（由 eos-ort03-norm 负责）
4. 按 FR-BIZ / FR-ENG / NFR 分配到 wft01 系列
5. 修改原文语义、补充需求内容或作设计判断

## 二、切分设计基础

### 2.1 文本化文档结构

**一句话**：本步在文本化文档（`{原始文件名}.textualized.md`）正文区写切分方案；切分文件（`.chunk-{seq}.md`）的结构见 §2.3。

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| 管理区 | 文档顶部（正文前）：状态摘要、切分迭代记录、决策记录 | 写入/更新状态摘要，追加迭代记录和决策记录 |
| 正文区 | 原文 + 当前切分方案块 + 反馈提示区（均为临时，执行后清理） | 生成阶段写入方案块；执行阶段清理方案块和反馈区，使正文区回归纯原文 |

**正文区检测原则**：正文区中当前是否存在 `╔═ 切分方案` 块，是分流关键。历史版本由 Git 管理，旧方案不参与入口判断。

### 2.2 文本化文档生命周期管理

**一句话**：本步通过状态文档表 A 推进文本化文档的生命周期——本步负责 `切分方案待确认 → 已切分`，其余由上游 ort00 或人类决策推进。

**全链双轨状态模型**：OR 预处理链的所有文档都采用双轨——**外部轨道**记录"流程推进到哪一步"（状态文档表 A/B/C，供 AI 入口判断与人类批量选材），**内部轨道**记录"文档被处理到什么程度"（文本化文档 = 管理区状态摘要表；切分文件 = `frontmatter.status` + 管理区状态摘要表）。两条轨道由同步契约保持一致：先更新状态文档表（权威源），再推导写文档内嵌状态。

**文本化文档生命周期**（外部轨道表 A，内部轨道管理区状态摘要表）：

| 阶段（表 A） | 含义（这份文本化文档现在到哪了） | 由谁推进 |
|-------------|--------------------------------|---------|
| 已登记 | ort00 刚登记，尚未文本化 | ort00 登记 |
| 已文本化 | ort00 已完成纯文本化，等人类选入切分 | ort00 完成 |
| 切分方案待确认 | ort01 已生成切分方案块，等人类反馈 | ort01 生成方案 |
| 已切分 | 切分方案已确认并执行，切分文件已输出 | ort01 执行 |
| 已废弃（含已废弃（重复）） | 材料终止（或查重判重复），不再处理 | ort00 / ort01 / 人类决策 |

> 表 A 全链生命周期线由 ort00 §2.2 定义；本步只推进 `切分方案待确认 → 已切分`，`已文本化` 之前由上游 ort00 推进，`已废弃` 由本步/上游/人类决策触发。

**记录三要素职责**（与 ort00 一致）：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段，供 AI 和流程判断使用 |
| AI建议 | 提示字段，仅供人类快速理解下一步建议，不参与 Step 入口硬判断 |
| 人类决策 | 批次控制字段，决定材料是否进入本轮处理 |

**同步契约**：生成方案分支先更新表 A；执行切分分支先追加/更新表 B 并更新表 A；再从权威源推导写入文本化文档与切分文件管理区状态摘要（切分文件 `status` 同步写 frontmatter）。不一致时以状态文档为准重建。写回前检测表 A/表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step End 提示人类。

### 2.3 切分文件结构

**一句话**：切分文件（`.chunk-{seq}.md`）是切分产物，一份切片档案由**三段**构成——头顶元数据（frontmatter）、管理区（这张片的状态与决策记录）、正文（原文片段）。

| 段 | 内容 | 本步操作 |
|----|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 创建时写入，`status=raw` |
| 管理区 | 状态摘要表（阶段/AI建议/待处理/操作指引） | 创建时写入（阶段=切分已执行/不拆分已确认） |
| 正文区 | 原文片段（切分内容） | 创建时写入 |

模板与字段填写见 §4.2；切分文件的生命周期见 §2.4。

### 2.4 切分文件生命周期管理

**一句话**：本步执行切分时为每个切分文件登记表 B 生命周期，并在文件 frontmatter 写 `status=raw`；此后由 ort02/ort03 推进。

**切分文件生命周期**（外部轨道表 B，内部轨道 `frontmatter.status`；本表为全链权威定义）：切分文件是双轨模型的实例——表 B 管"流程推进到哪一步"（AI/人类驱动），`frontmatter.status` 管"文件被处理到什么深度"。

| 阶段（表 B） | 含义（这张切片现在到哪了） | `status` | 由谁推进 |
|-------------|--------------------------|----------|---------|
| 已切分 | ort01 刚切出来，等人类选入澄清 | `raw` | ort01 创建 |
| 澄清中 | ort02 正在标注模糊项 | `annotated` | ort02 首轮标注 |
| 已澄清 | 模糊项已全部澄清，可送规范化 | `clarified` | ort02 达成 |
| 待确认规范方案 | ort03 已给规范化方案，等人类确认 | `clarified`（保持） | ort03 方案期 |
| 已规范化 | OR 条目已写入基线 | `normalized` | ort03 确认 |
| 已废弃 | 不再处理 | `abandoned` | 任一步骤终止 |

> 下游各 Skill 文档只列本步更新的值，全量以本表为准。一张切片在任何时刻，你都可以通过「表 B 生命周期」问它在流程中到哪了、通过「frontmatter.status」问它被处理到什么深度。
>
> **status 写回口径**：`待确认规范方案` 期间 ort03 不写 status（保持 `clarified`）；确认执行时由 ort03 置 `normalized`；终止由任一步骤置 `abandoned`。

**本步对表 B 的职责**：执行切分时为每个 `.chunk-{seq}.md` 追加记录，初始 `生命周期=已切分`、`AI建议=可以澄清`。

### 2.5 入口与重进入规则

**一句话**：本步只处理人类在表 A 明确选入（`同意切分`）且已完成文本化的材料；每次运行先处理人类已反馈的方案，再处理新选入的材料。

Step 1 的入口硬条件：

| 条件 | 说明 |
|------|------|
| `生命周期=已文本化` | 上游 ort00 已完成文本化 |
| `人类决策=同意切分` | 人类明确选入本批切分 |

`AI建议=可以切分` 只是候选提示，不作为入口硬条件。`已登记` 是 ort00 内部中间状态，不构成 ort01 入口条件。

运行路由参考 `wft01-biz`：前置校验通过后，**先处理表 A 中 `生命周期=切分方案待确认` 的反馈，再处理 `生命周期=已文本化` + `人类决策=同意切分` 的新增材料**。因为反馈可能改变表 A/表 B 状态和下游澄清入口，不能被新增材料抢先。

**两个"不切分"不是一回事**：表 A 的 `人类决策=暂不切分` 表示"本批不进入 ort01"；正文区反馈 `[确认不拆分]` 表示"已进入 ort01，但人类确认输出单片切分文件"。不得用 `不切分` 或 `暂搁置` 混用。

**重新切分**（材料已 `已切分` 后人类要求重切）：

| 环节 | 处理 |
|------|------|
| 入口 | 表 A `生命周期=已切分`，人类表达重切意图（表 A 人类决策或正文区反馈标记） |
| 前置校验 | 确认该材料各切分文件在表 B 的生命周期均未被下游消费（澄清/规范化）；已消费时先按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议) 输出变更影响声明，列出受影响的切分文件、OR 与已消费 STR，不得静默声明"下游不受影响" |
| 执行 | 清除旧切分文件与表 B 对应记录 → 正文区回归纯原文 → 表 A 置 `切分方案待确认`，重新生成方案块（决策记录执行模式=重切） |

反馈处理入口：

| 条件 | 处理 |
|------|------|
| 表 A `生命周期=切分方案待确认` 且正文区有方案块，无反馈文本 | 跳过，等待人类反馈 |
| 表 A `生命周期=切分方案待确认` 且正文区无方案块 | 数据不一致：提示人类核对，并按「调整」路径重新生成方案块（表 A 保持待确认） |
| 有方案块 + `[同意执行]` | 按方案块执行切分 |
| 有方案块 + `[确认不拆分]` | 输出单片切分文件 |
| 有方案块 + `[调整]` 或明确修改意图 | 重生成方案（历史由 Git 管理） |
| 有方案块 + `[废弃]` | 表 A 置 `已废弃`，追加废弃记录 |

> **触发词选用**：方案块建议「不切分」且人类认可时用 `[同意执行]`（按方案块执行＝输出单片）；方案块建议「切分 N 片」而人类认为不应拆分时用 `[确认不拆分]`（否决切分建议，强制单片）。两者输出结果相同，语义分工不同——同意执行＝认可方案，确认不拆分＝否决切分。

### 2.6 语义切分规则

**一句话**：判断一份文档"切不切、切成几片"——以「单个相关方的单个端到端场景业务」为主要判断标准（参照场景业务定义 [91 §1.4]），数"相关方 × 场景"组合 = 候选单元；场景过大按环节细分，材料无明确角色场景时补用结构/主题锚点；最后按关联性复核。

**语义结构分析**（三步，产出相关方清单、场景清单与关联性结论）：

| # | 操作 | 说明 |
|---|------|------|
| 1 | 相关方与场景识别 | 识别材料描述的相关方（角色/岗位/人称）及其参与的端到端场景业务（谁、在什么场景做什么；一个角色一条端到端业务闭环，参照 [91 §1.4]） |
| 2 | 场景内环节识别 | 端到端场景内的业务环节/子流程，作为大场景细分的候选边界 |
| 3 | 关联性分析 | 判断概念定义、上下文依赖和跨段引用是否要求保持同片 |

> **语义单元的定义**：参照项目"场景业务"定义——**一个场景业务 = 一个角色（相关方）的一条端到端业务闭环**（从需求提出到需求被满足并确认的完整链路）[91 §1.4；wft01-biz-or2str]。语义单元即以此为边界：材料含多个相关方、或多个端到端场景业务、或单个场景内含多个可独立环节时，即多个语义单元；单个相关方的单个场景为最小单元。物理段落是排版单位，不构成语义单元。**界定优先级**：主标准为"相关方 × 端到端场景业务"；场景过大按环节细分；材料无明确角色场景（如技术说明、接口规范）时补用结构锚点（标题/编号）或主题转换点，AI 须在方案块写明理由。

**切分判定**（主标准：单个相关方 × 单个端到端场景）：

1. **候选单元界定**（主标准 + 视情补充）——
   - 主标准：数"相关方 × 端到端场景"组合 = 候选单元数（单个相关方单个场景 = 1；多个相关方或多个场景 = 多个）
   - 视情①：单个场景含多个可独立环节时，按环节细分候选单元
   - 视情②：材料无明确相关方场景（技术说明/接口规范等）时，退回结构锚点（数标题/编号）或主题转换点界定，AI 写明理由
2. **关联性复核**（语义，辅助）——候选单元间强关联则合并，判为「语义不可分」

| 候选单元数 | 关联性 | 结论 | 输出 |
|-----------|--------|------|------|
| 1（单个相关方单个场景） | — | 不切分 | 建议不切分，理由写「语义单一」 |
| >1（多相关方/多场景/多环节） | 强（拆开破坏完整性） | 不切分 | 建议不切分，理由写「语义不可分」 |
| >1 | 弱（可独立成片） | 切分 | 输出多片方案 |

> **判定逻辑**：候选单元数以「相关方 × 端到端场景业务」为主要界定（一个场景业务 = 一个角色一条端到端业务闭环 [91 §1.4]）——单个相关方单个场景 = 1 不切；多个相关方/场景/环节则 > 1，再查关联性——强则「语义不可分」不切，弱则切分。场景过大按环节细分；无明确角色场景时补用结构/主题锚点（AI 写明理由）。仅识别"谁、什么场景"作边界，不评价需求内容；由人类通过方案块行号范围复核。
> **「语义单一」与「语义不可分」的区分**：语义单一 = 单个相关方单个场景，本就是一个完整业务片段；语义不可分 = 多个候选单元但强关联、拆开破坏完整性，想切但切不得。

**AI 判断路径**（从读原文到出方案块的一次执行序列）：

| 步 | 动作 | 判定依据 |
|----|------|---------|
| 0 | 确认入口 | 正文区纯原文、表 A `已文本化`+`同意切分` |
| 1 | 通读识别 | 识别相关方与端到端场景业务（谁、什么场景做什么）；场景过大时识别环节 |
| 2 | 数候选单元 | "相关方 × 端到端场景业务"组合计数；无明确角色场景时退回结构锚点/主题转换 |
| 3 | 查关联性 | 候选单元间强关联（概念依赖/显式引用/结论被依赖）→ 判「语义不可分」 |
| 4 | 出判定 | 单元 = 1 不切（语义单一）；>1 强关联不切（语义不可分）；>1 弱关联切分 |
| 5 | 写方案块 | 每片行号范围（正文区基准）+ 语义标签 + 对应章节 + 理由；表 A → 切分方案待确认 |
| 6 | 交人类 | 等待反馈（同意执行/调整/确认不拆分/废弃） |

**判断示例**：

| 情形 | 识别结果 | 判定 |
|------|---------|------|
| 多相关方/多场景 | 如"业务架构管理员 + 数据治理员"两个角色各一治理场景 → 候选单元 2，弱关联 | 切分为 2 片 |
| 单相关方单场景 | 一个角色一个端到端场景 → 候选单元 1 | 建议不切分（语义单一） |
| 无角色场景 | 技术说明/接口规范 → 退回结构锚点数标题 | 按候选单元数判定 |

边界处理：

| 边界情况 | 处理方式 |
|---------|---------|
| 方案块行号边界落在段落中间 | 被截断段落完整归入起始片，并在行动清单中提示边界截断 |
| 连续两片之间有空白行 | 空白行归入前一片 |
| 切分内容为空 | 不输出空文件，视为无效标记 |

> **行号基准**：切分方案块中的「行号：Lxxx」相对**正文区**计数（正文区第 1 行 = L1），管理区行数变化不影响行号。行号校验与执行切分均以该基准为准。

### 2.7 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做业务场景识别和边界切分，不评价需求内容、不展开设计决策（仅识别"相关方/场景"作为边界锚点，不作需求判断） |
| 文档结对 | 本步不产生文档结对关系；切分文件是 eos-ort02-clarify 的输入 |
| 基于资产 | 切分文件是原始文档的派生资产，通过文件名、frontmatter、表 A/表 B 保持追溯 |

## 三、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查上游文本化文档和状态文档是否就绪 | 统一 | 就绪/结束 | — |
| 1 | 新增处理 | 读取表 A 选入材料，生成切分方案块 | 统一 | 方案块 + 反馈区 | 表 A、文本化文档 |
| 2 | 反馈处理 | 读取反馈，执行切分/不切分/调整/废弃 | 统一 | 切分文件/新版方案/废弃记录 | 表 A、表 B、切分文件 |
| End | 输出交互 | 输出三段式结果、反馈指引和下一步交接 | 人类 | Step End 三区输出 | — |

核心驱动逻辑：每次运行先处理待确认方案反馈，再处理新增选入材料。表 A 控制材料级状态，表 B 承接切分文件级状态。

### 3.1 Step Start · 前置校验

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
3. 若状态文档已存在，校验表 A/表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示（表 B 模板见 §4.4）
4. `10-raw-files/` 中是否存在 `.textualized.md` 文档；不存在则提示先运行 `eos-ort00-textualize` 并结束
5. 全部就绪后先执行反馈入口检测：存在 `生命周期=切分方案待确认` 的对象时进入 Step 2；无待处理反馈时再进入 Step 1

### 3.2 Step 1 · 新增处理

读取状态文档表 A，按以下规则分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 对应文本化文档进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`、AI建议置 `建议终止`，追加废弃说明 |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

方案生成动作：

1. 读取文本化文档正文区纯原文
2. 执行语义结构分析（相关方与场景识别、场景内环节识别、关联性分析）
3. 形成切分/不切分建议
4. 在正文区原文之后写入切分方案块和反馈提示区
5. 更新表 A：`生命周期=切分方案待确认`、`AI建议=审核切分方案`
6. 从表 A 推导写入文本化文档管理区状态摘要

### 3.3 Step 2 · 反馈处理

读取表 A 中 `生命周期=切分方案待确认` 的文档，检测正文区方案块和反馈。

**1. 同意执行**

1. 读取切分方案块，判断方案块建议类型：
   - **建议「不切分」**（语义单一，无行号范围）→ 按单片输出，复用「确认不拆分」规格：`seq=1`/`total=1`/`label=不切分（整份文档）`、管理区写「不拆分已确认」、表 B 追加单片记录、表 A→已切分、追加迭代/决策记录（执行模式=不拆分）
   - **建议「切分 N 片」**→ 继续第 2~9 步多片执行
2. 校验行号范围无重叠、无遗漏，语义标签完整
3. 按行号范围切分原文
4. 为每片写入 YAML frontmatter（`status=raw`）和管理区状态摘要（阶段=切分已执行、AI建议=可以澄清）
5. 输出 `{原始文件名}.chunk-{seq}.md`
6. 清理正文区方案块和反馈区，使正文区回归纯原文
7. 表 B 为每片追加记录：`生命周期=已切分`、`AI建议=可以澄清`
8. 表 A 更新为 `生命周期=已切分`
9. 推导更新文本化文档管理区状态摘要（追加切分迭代记录和决策记录），确认各切分文件管理区状态摘要与 `status=raw` 已写入

**2. 确认不拆分**

1. 输出单片切分文件，`seq=1`、`total=1`、`label=不切分（整份文档）`
2. 清理正文区方案块和反馈区
3. 表 B 追加单片记录，表 A 更新为 `已切分`
4. 在单片切分文件管理区写入状态摘要 `不拆分已确认`、`AI建议=可以澄清`（此值为文档内嵌摘要；表 B 生命周期仍为 `已切分`）
5. 追加切分迭代记录和决策记录（执行模式=不拆分）

**3. 调整重生成**

1. 解析人类反馈中的边界、标签、片数或范围调整意图
2. 在管理区摘要记录调整结论（历史版本由 Git 管理，不归档旧方案全文）
3. 写入新版方案块和新反馈提示区
4. 表 A 保持 `生命周期=切分方案待确认`
5. 管理区追加重生成记录

**4. 废弃**

1. 表 A 生命周期置 `已废弃`、AI建议置 `建议终止`
2. 清理或保留方案块按人类反馈语义处理；若保留，需在管理区标注该材料已终止
3. 管理区追加废弃记录

### 3.4 Step End · 运行结束输出

Step End 参考 `wft01-biz` 的三区输出模板（结果 → 方案反馈 → 下一步），本 Skill 实例化如下：

```text

══════════════════════════════════════════
```

### 4.2 切分文件结构与模板

**一句话**：切分文件（`.chunk-{seq}.md`）是切分产物，结构（三段：frontmatter + 管理区 + 正文）见 §2.3，生命周期见 §2.4。本节只给创建时的模板与字段填写。

```markdown
---
chunk:
  source: {原始文件名}.textualized.md
  original_source: {原始文件名}.{ext}
  seq: {序号}
  total: {总片数}
  label: {语义标签}
  range: {原文范围}
status: raw
---

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 切分已执行 / 不拆分已确认 | 可以澄清 | 无 | 运行 eos-ort02-clarify |

（切分正文内容）
```

字段说明：

| 字段 | 说明 |
|------|------|
| `source` / `original_source` | 文本化文档文件名 / 原始文件文件名（只读档案） |
| `seq` / `total` | 本片序号 / 本次切分总片数 |
| `label` | 语义标签，概括本片主题；不拆分单片填 `不切分（整份文档）` |
| `range` | 方案块中的行号范围（如 `L120~L340`），即切分执行依据 |
| `status` | 处理状态，初始 `raw`；下游按阶段更新 |

**切分文件生命周期**见 §2.4（表 B 生命周期 ↔ `status` ↔ 由谁推进的对照表）。

命名规则：

```text

├── 01-市场调研报告.pdf
├── 01-市场调研报告.textualized.md
├── 01-市场调研报告.chunk-001.md
├── 01-市场调研报告.chunk-002.md
└── 01-市场调研报告.chunk-003.md
```

> **不拆分单片**：确认不拆分时同样输出 `.chunk-{seq}.md`（`seq=1`、`total=1`），`label` 填 `不切分（整份文档）`，保证下游 ort02 以统一口径拾取。

### 4.3 OR 切分文档状态表

**一句话**：你在任何一份文档的管理区看到的状态摘要，都来自下面这张表——它告诉你看的是哪个阶段、在哪份文档的管理区、下一步该做什么。
