# 文本化原始需求 → 切分文档 · 语义切分与反馈执行
**人类方案ID**: eos-ort01-chunk

> **概述**：把已文本化的文档切成语义独立的片段——读取人类在状态文档表 A 选入的材料，识别其业务对象闭环后生成切分方案供人类审阅；人类通过**直接编辑文本化文档**表达反馈（改方案块=调整、写确认标记=同意/废弃），AI 以 git diff 检出变更、判读意图、**记录**到表 A，再由 Step 2 **基于记录**执行切分。本步不做 OR 规范化，也不评价需求。
>
> **输入 → 输出**：文本化 `.textualized.md` 文档（正文区：纯原文 + 方案块）+ `01-eos-sysdev-status.md` 表 A/表 B + git 基线 → 切分文件（`.chunk-{seq}.md`）+ 表 A/表 B 更新 + 反馈记录 + 新基线
>
> **适用场景**：EOS 原始需求预处理链第 2 步；将已文本化材料拆成适合澄清和规范化的语义片段。
>
> **接口设计**：本步反馈接口以 **git 为检测通道**——人类反馈 = 直接编辑**文本化文档**（方案块/反馈区）；切分文件是双方一致后的结果，不是反馈载体。AI 运行开始 `git diff <基线>` 检出变更、判读意图、**记录**到状态文档表 A；**处理**（执行/重生成/终止/重切）由 Step 2 基于表 A 记录执行，交互时不处理。入口靠表 A 与 git 变更分流：有反馈→Step 2、有新选入→Step 3。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（§1.4 业务对象概念、Step Start、反馈优先、输出交接（三区模板）与变更传播通用协议；本步反馈走「文档编辑 + git」特化，见 91 §A.5）
>
> **版本**：v0.41 | **修订**：2026-08-15 | **说明**：F2 裁决（B）——表 A「文本化文档」列始终指向 `.textualized.md`（切片清单归表 B）；Step 2 执行切分时内容摘要阶段摘要写「已切分 N 片（见表 B）」

## 一、职责定位

### 1.1 本 Skill 目的与目标

> **主要目的**：把一份文本化文档切成多份语义独立、能进入澄清的切分文件，保留原文出处，并让人类对切分方案把关。
>
> **目标**：
> 1. **识别选入材料**——读取表 A 中 `生命周期=已文本化` 且 `人类决策=同意切分` 的文本化文档（Step 3）
> 2. **生成切分方案**——以业务对象闭环为主要边界，识别候选单元并形成切分/不切分建议
> 3. **检测并记录反馈**——`git diff` 检出人类对文档/表 A 的变更，判读意图并记录到表 A（Step 1）
> 4. **执行切分输出**——基于表 A 反馈记录生成 `.chunk-{seq}.md` 文件，写入 YAML frontmatter 和状态表（Step 2）
> 5. **处理迭代反馈**——支持 `[同意执行]` 切分、`[调整]` 重生成、`[确认不拆分]` 单片、`[废弃]` 终止、`[重新切分]` 重切
> 6. **同步状态接口**——先更新状态文档表 A/表 B，再推导更新文本化文档和切分文件的状态摘要；Step 4 提交基线

### 1.2 人机交接点总览

**一句话**：你在本步有三个参与点——选材、审方案、选入澄清。审方案时**直接编辑文本化文档即反馈**（AI 用 git 检测），无需对话。

| 人类参与点 | 在哪操作 | 做什么 |
|-----------|---------|--------|
| ① 选材入切分 | 状态文档表 A | 对 `已文本化` 材料设 `人类决策=同意切分` |
| ② 审核切分方案 | 文本化文档正文区方案块 / 反馈区 | **直接编辑表达反馈**：改方案块=调整；反馈区写 `[同意执行]` / `[确认不拆分]` / `[废弃]` |
| ③ 选入澄清 | 状态文档表 B | 对 `已切分` 切分文件设 `人类决策=同意澄清` → 进入 ort02 |

> AI 凭什么这么切（判定依据）见 **§三 语义切分规则**；反馈如何被检测与记录见 §2.3 与 §四。

### 1.3 本步负责与不负责

本 Skill 负责：

1. **检测**——`git diff <基线>` 检出人类文档/表 A 变更，判读意图并记录到表 A（Step 1）
2. **接收**——读取文本化文档和状态文档表 A，识别本轮选入切分的材料（Step 3）
3. **分析**——执行业务对象与主责角色识别、场景内环节识别和关联性分析
4. **规划**——生成切分方案块（建议切分或建议不切分），写入正文区原文之后，并附反馈区
5. **执行**——基于表 A 反馈记录生成切分文件，或输出单片切分文件（Step 2）
6. **迭代**——基于反馈记录中的调整意见重生成方案（历史由 Git 管理，不归档旧方案）
7. **落账**——更新表 A 的原料级状态与反馈记录，向表 B 追加切分文件级记录
8. **交接**——提交基线（ai-commit），输出待反馈、待选入澄清、下一批选材的行动清单

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 模糊需求澄清和标注（由 eos-ort02-clarify 负责）
3. OR 条目规范化、编号、分类或冲突检测（由 eos-ort03-norm 负责）
4. 按 FR-BIZ / FR-ENG / NFR 分配到 wft01 系列
5. 修改原文语义、补充需求内容或作设计判断

## 二、切分设计基础

**一句话**：本章讲本步操作的两类文档（文本化文档/切分文件）、它们的状态怎么追踪、入口规则与工程化原则；**怎么判定切不切见 §三 语义切分规则**。

### 2.1 两类文档结构

**一句话**：本步处理两类文档——文本化文档（在其正文区写切分方案）和切分文件（切分产物）。

#### 2.1.1 文本化文档结构

文本化文档（`{原始文件名}.textualized.md`）分两区：

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| 管理区 | 文档顶部（正文前）：状态摘要、切分迭代记录、决策记录 | 写入/更新状态摘要，追加迭代记录和决策记录 |
| 正文区 | 原文 + 当前切分方案块 + 反馈区（均为临时，执行后清理） | 生成阶段写入方案块+反馈区；执行阶段清理，使正文区回归纯原文 |

**正文区检测原则**：正文区中当前是否存在 `╔═ 切分方案` 块，是分流关键（历史版本由 Git 管理，旧方案不参与入口判断）。**反馈载体**：方案块 = 「调整」的编辑对象（人类改行号/标签）；反馈区 = 人类确认标记的落点（写 `[同意执行]`/`[确认不拆分]`/`[废弃]`）。两者的人类改动均由 git diff 检测，**AI 不写入反馈区**。

#### 2.1.2 切分文件结构

切分文件（`.chunk-{seq}.md`）是切分产物，一份切片档案由**三段**构成——头顶元数据（frontmatter）、管理区（这张片的状态与决策记录）、正文（原文片段）：

| 段 | 内容 | 本步操作 |
|----|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 创建时写入，`status=raw` |
| 管理区 | 状态摘要表（阶段/AI建议/待处理/操作指引） | 创建时写入（阶段=切分已执行/不拆分已确认） |
| 正文区 | 原文片段（切分内容） | 创建时写入 |

> 切分文件模板与字段填写见 §5.2；生命周期见 §2.2。

### 2.2 文档状态与同步

**一句话**：本步通过状态文档表 A（材料级）/表 B（切分文件级）推进状态；**反馈内容记录在表 A（单源）**，文档内嵌状态从表 A 推导。本步负责 `切分方案待确认 → 已切分`，其余由上游 ort00 或人类决策推进。

**全链双轨状态模型**：OR 预处理链的所有文档都双轨——**外部轨道**（状态文档表 A/B/C）管"流程推进到哪一步 + 反馈记录"（供 AI 入口判断、人类批量选材、Step 2 处理输入），**内部轨道**（文档内嵌状态）管"文档被处理到什么程度"（文本化文档 = 管理区状态摘要表；切分文件 = `frontmatter.status` + 管理区状态摘要表）。

**反馈单源原则**（本步特化）：反馈内容**只**记录在表 A `内容摘要`（承载反馈记录），由 git diff 检出的文档变更聚合而来、或由交互轮对话记录写入；文档是反馈的**输入源**（人类编辑处），不是平行状态载体。因此表 A 反馈记录与文档状态不会不同步——反馈记录从文档变更聚合导出，无平行维护对象。

**`内容摘要` 双内容分段**：内容摘要 = 「阶段摘要 ∥ 反馈记录」——阶段摘要为当前处理阶段一句话（与 ort00/状态文档口径一致）；有已记录未处理反馈时以 `‖ 反馈：<类型>（<要点>）` 分段追加反馈记录（类型 = 调整/同意/确认不拆分/废弃/重新切分）。反馈记录未追加 `[已处理]` 前 = 已记录未处理（Step 2 入口依据）；Step 2 处理完成后在记录末追加 `[已处理]`，即转「已处理反馈」。

#### 2.2.1 文本化文档生命周期（表 A）

| 阶段（表 A） | 含义（这份文本化文档现在到哪了） | 由谁推进 |
|-------------|--------------------------------|---------|
| 已登记 | ort00 刚登记，尚未文本化 | ort00 登记 |
| 已文本化 | ort00 已完成纯文本化，等人类选入切分 | ort00 完成 |
| 切分方案待确认 | ort01 已生成切分方案块，等人类反馈 | ort01 生成方案 |
| 已切分 | 切分方案已确认并执行，切分文件已输出 | ort01 执行 |
| 已废弃（含已废弃（重复）） | 材料终止（或查重判重复），不再处理 | ort00 / ort01 / 人类决策 |

> 表 A 全链生命周期线由 ort00 §2.2 定义；本步只推进 `切分方案待确认 → 已切分`，`已文本化` 之前由上游 ort00 推进，`已废弃` 由本步/上游/人类决策触发。

**记录三要素职责**（与 ort00 一致）：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段，供 AI 和流程判断使用 |
| AI建议 | 提示字段，仅供人类快速理解下一步建议，不参与 Step 入口硬判断 |
| 人类决策 | 批次控制字段，决定材料是否进入本轮处理 |

#### 2.2.2 切分文件生命周期（表 B + status）

**切分文件生命周期**（外部轨道表 B，内部轨道 `frontmatter.status`；本表为全链权威定义）：

| 阶段（表 B） | 含义（这张切片现在到哪了） | `status` | 由谁推进 |
|-------------|--------------------------|----------|---------|
| 已切分 | ort01 刚切出来，等人类选入澄清 | `raw` | ort01 创建 |
| 澄清中 | ort02 正在标注模糊项 | `annotated` | ort02 首轮标注 |
| 已澄清 | 模糊项已全部澄清，可送规范化 | `clarified` | ort02 达成 |
| 待确认规范方案 | ort03 已给规范化方案，等人类确认 | `clarified`（保持） | ort03 方案期 |
| 已规范化 | OR 条目已写入基线 | `normalized` | ort03 确认 |
| 已废弃 | 不再处理 | `abandoned` | 任一步骤终止 |

> 下游各 Skill 文档只列本步更新的值，全量以本表为准。一张切片在任何时刻，你都可以通过「表 B 生命周期」问它在流程中到哪了、通过「frontmatter.status」问它被处理到什么深度。
>
> **status 写回口径**：`待确认规范方案` 期间 ort03 不写 status（保持 `clarified`）；确认执行时由 ort03 置 `normalized`；终止由任一步骤置 `abandoned`。

**本步对表 B 的职责**：执行切分时为每个 `.chunk-{seq}.md` 追加记录，初始 `生命周期=已切分`、`AI建议=可以澄清`。

**同步契约**：生成方案分支先更新表 A；执行切分分支先追加/更新表 B 并更新表 A；再从权威源推导写入文本化文档与切分文件管理区状态摘要（切分文件 `status` 同步写 frontmatter）。不一致时以状态文档为准重建。写回前检测表 A/表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step 4 摘要输出时提示人类。**反馈记录**：Step 1 把 git diff 检出的人类文档变更判读成反馈、按 §2.2 记录格式写入表 A `内容摘要`（`‖ 反馈：<类型>（<要点>）`）；Step 2 读取该记录执行处理，完成后在记录末追加 `[已处理]` 并转迁生命周期。

### 2.3 入口与重进入规则

**一句话**：本步处理两类对象——人类在表 A 明确选入（`同意切分`）且已完成文本化的材料（Step 3 新增），以及有已记录未处理反馈（内容摘要含 `反馈：` 且未追 `[已处理]`）的材料（Step 2 反馈）；每次运行先处理反馈，再处理新增选入。

**入口条件**（Step 3 新增处理）：

| 条件 | 说明 |
|------|------|
| `生命周期=已文本化` | 上游 ort00 已完成文本化 |
| `人类决策=同意切分` | 人类明确选入本批切分 |

`AI建议=可以切分` 只是候选提示，不作为入口硬条件。`已登记` 是 ort00 内部中间状态，不构成 ort01 入口条件。

**反馈检测**（Step 1 变更检测 → Step 2 处理）：反馈以「文档/表 A 变更」承载，由 git diff 检出并**记录**到表 A `内容摘要`（反馈记录，格式见 §2.2）；Step 2 处理表 A 中「含反馈记录（`反馈：`）且未追加 `[已处理]`」的对象——`生命周期=切分方案待确认` 的对象走调整/同意/不拆分/废弃分支，`生命周期=已切分` 的对象走重新切分分支。

运行路由参考 `wft01-biz`：**先处理反馈（Step 2），再处理新增选入（Step 3）**——反馈可能改变表 A/表 B 状态和下游澄清入口，不能被新增材料抢先。

**两个"不切分"不是一回事**：表 A 的 `人类决策=暂不切分` 表示"本批不进入 ort01"；反馈区 `[确认不拆分]` 表示"已进入 ort01，但人类确认输出单片切分文件"。不得用 `不切分` 或 `暂搁置` 混用。

**重新切分**（材料已 `已切分` 后人类要求重切）：

| 环节 | 处理 |
|------|------|
| 入口 | 人类在文本化文档正文区（已切分后为纯原文）追加 `[重新切分]` 标记；git diff 检出 → Step 1 记录 → Step 2 重切分支 |
| 前置校验 | 确认该材料各切分文件在表 B 的生命周期均未被下游消费（澄清/规范化）；已消费时先按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议) 输出变更影响声明，列出受影响的切分文件、OR 与已消费 STR，不得静默声明"下游不受影响" |
| 执行 | 清除旧切分文件与表 B 对应记录 → 移除 `[重新切分]` 标记 → 正文区回归纯原文 → 表 A 置 `切分方案待确认`，重新生成方案块（决策记录执行模式=重切） |

**反馈判读映射**（Step 1 从 diff 记录时判读意图）：

| 人类变更 | 判读意图 |
|---------|---------|
| 方案块行号/标签被改 | 调整（按新内容重生成方案） |
| 反馈区写 `[同意执行]` | 同意（照当前文档内容执行切分） |
| 反馈区写 `[确认不拆分]` | 确认不拆分（输出单片） |
| 反馈区写 `[废弃]` | 废弃 |
| 已切分后文本化文档写 `[重新切分]` | 重新切分 |
| 正文区原文行被改（非方案块/反馈区） | 非切分反馈——保留提交，不记录表 A，Step 5 提示人类 |
| 表 A 人类决策被改 | 选材 / 终止（走 Step 3 / 终止处理） |

> **触发词语义**：`[同意执行]`/`[确认不拆分]`/`[废弃]`/`[重新切分]` 均为**人类确认标记**，写于反馈区（或正文区），由 git diff 检测；**AI 不写入**这些标记。方案块建议「不切分」且人类认可时用 `[同意执行]`（按方案块执行＝输出单片）；方案块建议「切分 N 片」而人类认为不应拆分时用 `[确认不拆分]`（否决切分建议，强制单片）。**混合信号**：人类既改方案块又写 `[同意执行]` → 按改动后的当前文档内容执行（同意 = 照当前文档，非照原方案）。

### 2.4 工程化设计原则适配

| 原则 | 在本步中的体现 |
|------|--------------|
| 需求相对 | 本步仍处于原始需求预处理阶段，不涉及需求/方案角色切换 |
| 详概分离 | 本步只做业务对象识别和边界切分，不评价需求内容、不展开设计决策（仅识别"业务对象/主责角色"作为边界锚点，不作需求判断） |
| 文档结对 | 本步不产生文档结对关系；切分文件是 eos-ort02-clarify 的输入 |
| 基于资产 | 切分文件是原始文档的派生资产，通过文件名、frontmatter、表 A/表 B 保持追溯 |

## 三、语义切分规则

**一句话**：判断一份文档"切不切、切成几片"——以「单个主责角色的单个业务对象闭环」为主要判断标准（业务对象定义见 [91 §1.4]），一条业务对象闭环（由一个主责角色主导）就是一个候选单元；识别抓手为输出文档、切分单元为业务对象；场景过大按环节细分，材料无明确业务对象场景时补用结构/主题锚点；最后按关联性复核。

### 3.1 业务对象概念与确定

**业务对象定义**：

> **业务对象 = 场景业务的全部操作与输出文档所围绕的核心实体**——场景业务的创建、提交、审批、流转、确认等操作及其输出文档序列，都围绕该实体组织，记录其从需求提出到被满足确认的完整生命周期 [91 §1.4]。业务对象与主责角色一一对应。

**业务对象确定三步法**（产出业务对象清单与主责角色）：

| # | 操作 | 说明 |
|---|------|------|
| 1 | 候选对象提取 | 扫描材料核心动作（创建/提交/审批/确认等）的宾语——被操作对象，**以输出文档为识别抓手**（文档显式可数，如需求文档、方案文档、审批单、风险记录） |
| 2 | 独立生命周期验证 | 三问判定：能独立创建/提出？有独立完成/确认时点？有独立主责角色？——全"是"即独立业务对象；否则为子结构/文档型，归入所属主轴 |
| 3 | 主轴锚定 | 材料闭环（需求提出端 → 处理端 → 满足确认端）共同指向的实体 = 主轴业务对象；各输出文档归并到主轴，作为切分单元 |

**语义结构分析**（三步，产出业务对象清单、场景清单与关联性结论）：

| # | 操作 | 说明 |
|---|------|------|
| 1 | 业务对象与主责角色识别 | 按上述三步法识别业务对象闭环及其主责角色（谁提出需求/负责完成/确认结果）；配合角色标注为配合，不单独成候选 |
| 2 | 场景内环节识别 | 端到端场景内的业务环节/子流程，作为大场景细分的候选边界 |
| 3 | 关联性分析 | 判断概念定义、上下文依赖和跨段引用是否要求保持同片 |

**语义单元的定义**（一条业务对象闭环 = 一个候选单元）：

| 要素 | 内容 |
|------|------|
| **定义** | 一个场景业务 = 一个业务对象闭环 = 一个主责角色的端到端职责闭环（从需求提出到需求被满足并确认的完整链路）[91 §1.4；wft01-biz-or2str] |
| **边界** | 材料含多个业务对象闭环（多个主责角色）→ 多个语义单元；一条闭环为最小单元；配合角色是闭环内的流程环节，不产生独立单元；物理段落是排版单位，不构成语义单元 |
| **界定优先级** | 主标准 = 一条业务对象闭环（由一个主责角色主导）就是一个候选单元；场景过大按环节细分；材料无明确业务对象场景（技术说明/接口规范等）→ 结构锚点（标题/编号）或主题转换点，AI 须在方案块写明理由 |
| **识别抓手** | 识别抓手为输出文档、切分单元为业务对象——先数文档、再归并到业务对象（主轴），既显式可数又不丢整体 |

### 3.2 切分判定规则

**切分判定**（主标准：单个主责角色的单个业务对象闭环）：

1. **候选单元界定**（主标准 + 视情补充）——
   - 主标准：一条业务对象闭环（由一个主责角色主导）就是一个候选单元（单个主责角色单个业务对象闭环 = 1；多个业务对象闭环 = 多个）
   - 视情①：单个业务对象闭环含多个可独立环节时，按环节细分候选单元
   - 视情②：材料无明确业务对象场景（技术说明/接口规范等）时，退回结构锚点（数标题/编号）或主题转换点界定，AI 写明理由
2. **关联性复核**（语义，辅助）——候选单元间强关联则合并，判为「语义不可分」

| 候选单元数 | 关联性 | 结论 | 输出 |
|-----------|--------|------|------|
| 1（单主责角色单业务对象闭环） | — | 不切分 | 建议不切分，理由写「语义单一」 |
| >1（多业务对象闭环） | 强（拆开破坏完整性） | 不切分 | 建议不切分，理由写「语义不可分」 |
| >1 | 弱（可独立成片） | 切分 | 输出多片方案 |

**判定逻辑**（候选单元如何界定）：

| 要素 | 内容 |
|------|------|
| **计数** | 候选单元数 = 材料覆盖的业务对象闭环条数——一条业务对象闭环（由一个主责角色主导）就是一个候选单元（一个场景业务 = 一个业务对象闭环 = 一个主责角色的端到端职责闭环 [91 §1.4]） |
| **决策** | 单主责角色单业务对象闭环 = 1 不切；多业务对象闭环 > 1，再查关联性——强则「语义不可分」不切，弱则切分 |
| **确定方法** | 业务对象确定按三步法（文档抓手 → 生命周期三问 → 主轴锚定） |
| **层级与大小端到端** | 业务对象有层级（产品 → 构件 → 构件数据文档），大端到端含小端到端——取哪级由材料自然描述决定：完整闭环成片、仅环节归属大闭环、子对象被当独立生命周期管理则升格成片；完整闭合为成片底线、可独立设计（下游 wft01 STR-F 承接）为切分上限 |
| **边界纪律** | 仅识别业务对象与主责角色作边界，不评价需求内容；由人类通过方案块行号范围复核 |

**「语义单一」与「语义不可分」的区分**：

| 结论 | 含义 |
|------|------|
| 语义单一 | 单个主责角色的单个业务对象闭环，本就是一个完整业务片段 |
| 语义不可分 | 多个候选单元但强关联、拆开破坏完整性，想切但切不得 |

### 3.3 执行路径与边界

**AI 判断路径**（从读原文到出方案块的一次执行序列）：

| 步 | 动作 | 判定依据 |
|----|------|---------|
| 0 | 确认入口 | 正文区纯原文、表 A `已文本化`+`同意切分` |
| 1 | 通读识别 | 识别业务对象闭环及其主责角色（谁提出需求/负责完成/确认结果），配合角色标注为配合；场景过大时识别环节 |
| 2 | 数候选单元 | 一条业务对象闭环（由一个主责角色主导）就是一个候选单元；识别抓手 = 数输出文档并归并到业务对象；无明确业务对象时退回结构锚点/主题转换 |
| 3 | 查关联性 | 候选单元间强关联（概念依赖/显式引用/结论被依赖）→ 判「语义不可分」 |
| 4 | 出判定 | 单元 = 1 不切（语义单一）；>1 强关联不切（语义不可分）；>1 弱关联切分 |
| 5 | 写方案块 | 每片行号范围（正文区基准）+ 语义标签 + 对应章节 + 理由；表 A → 切分方案待确认 |
| 6 | 交人类 | 等待人类编辑文档反馈（同意执行/调整/确认不拆分/废弃） |

**边界处理**：

| 边界情况 | 处理方式 |
|---------|---------|
| 方案块行号边界落在段落中间 | 被截断段落完整归入起始片，并在行动清单中提示边界截断 |
| 连续两片之间有空白行 | 空白行归入前一片 |
| 切分内容为空 | 不输出空文件，视为无效标记 |

> **行号基准**：切分方案块中的「行号：Lxxx」相对**正文区**计数（正文区第 1 行 = L1），管理区行数变化不影响行号。行号校验与执行切分均以该基准为准。

### 3.4 判断示例

| 情形 | 识别结果 | 判定 |
|------|---------|------|
| 多业务对象闭环 | 如"业务架构管理员治理产品资产树 + 数据治理员治理数据标准"两个业务对象闭环（两个主责角色）→ 候选单元 2，弱关联 | 切分为 2 片 |
| 单业务对象闭环 | 一个业务对象闭环（一个主责角色，审批等配合角色参与）→ 候选单元 1 | 建议不切分（语义单一） |
| 无业务对象场景 | 技术说明/接口规范 → 退回结构锚点数标题 | 按候选单元数判定 |

## 四、操作流程

### Step 布局总览

| Step | 名称 | 职责 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|------|-------|
| Start | 前置校验 | 检查上游文本化文档、状态文档与基线就绪 | 统一 | 就绪/结束 | — |
| 1 | 变更检测与反馈汇总 | git diff 检变更 → 判读意图 → 记录表 A | 统一 | 反馈记录/变更清单 | 表 A |
| 2 | 反馈处理 | 读表 A 已记录反馈 → 执行切分/不拆分/调整/废弃/重切 | 统一 | 切分文件/新版方案/废弃记录 | 表 A、表 B、切分文件、文本化文档 |
| 3 | 新增处理 | 读取表 A 选入材料，生成切分方案块 | 统一 | 方案块 + 反馈区 | 表 A、文本化文档 |

核心驱动逻辑：Step 1 检测并记录反馈 → **先处理反馈（Step 2）再处理新增选入（Step 3）** → Step 4 提交基线 → Step 5 输出三区摘要并交互；Step 5/6 为**交互协议步骤**（对话收集 + 口令触发汇总）。表 A 控制材料级状态 + 反馈记录，表 B 承接切分文件级状态。

### 4.1 Step Start · 前置校验

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
3. 若状态文档已存在，校验表 A/表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示（表 B 模板见 §5.4）
4. `10-raw-files/` 中是否存在 `.textualized.md` 文档；不存在则提示先运行 `eos-ort00-textualize` 并结束
5. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
6. 全部就绪后进入 Step 1；无任何待处理对象时输出「无待处理对象」并结束

### 4.2 Step 1 · 变更检测与反馈汇总

**一句话**：本轮开始先把人类对文档/表 A 的改动找出来、判读成反馈、**记录**到表 A——之后 Step 2 基于这些记录处理，不读对话、不读正文区原文。

1. **取基线**：读状态文档 `HEAD @上次AI运行`（校验：`git log --author="EOS-AI" --format="%H" -1`，应一致）
2. **找变更**：`git diff --name-status <基线>` → 变更文件清单（含表 A 变更）；`git status --porcelain` 补 untracked
3. **按状态筛范围**：反馈判读只针对**文本化文档**变更（方案块/反馈区；`已切分` 时检 `[重新切分]` 标记）——切分文件是双方一致后的结果，不是反馈载体；表 A 变更单独检出（人类决策=选材/终止，见 step 6）
4. **读变更**：逐文件 `git diff <基线> -- <文件>` 读变更 hunk（加载经济：只读变更，不读整文件）
5. **判读意图**：按 §2.3 反馈判读映射（调整 / 同意 / 确认不拆分 / 废弃 / 重新切分 / 选材-终止）
6. **记录到表 A**：按 §2.2 记录格式把反馈记录（`‖ 反馈：<类型>（<要点>）`）追加到该材料行 `内容摘要`（分段追加，不覆盖既有阶段摘要）；人类对表 A 的直接修改（如 `人类决策` 变更）标记 `[需确认]`、不覆盖
7. **路由**：有反馈 → Step 2；有新选入 → Step 3；全无 → 「无待处理对象」结束

### 4.3 Step 2 · 反馈处理

读取表 A 中「内容摘要 含反馈记录（`反馈：`）且未追加 `[已处理]`」的对象，按生命周期分流：`生命周期=切分方案待确认` → 调整/同意/不拆分/废弃分支；`生命周期=已切分`（含 `[重新切分]` 反馈）→ 重新切分分支。按反馈意见执行：

| 反馈意见 | 处理 |
|---------|------|
| `[同意执行]` | 判方案块类型：建议不切分 → 按单片输出（规格同「确认不拆分」）；建议切分 → 校验行号范围（无重叠/无遗漏、标签完整）→ 逐片输出 `.chunk-{seq}.md` → 清理方案块与反馈区 → 表 B 每片追加记录（`已切分`/`可以澄清`）→ 表 A 生命周期 → `已切分` |
| `[确认不拆分]` | 输出单片（seq=1/total=1/label=`不切分（整份文档）`）→ 单片管理区写 `不拆分已确认` → 清理方案块与反馈区 → 表 A/B 同「同意执行」 → 追加迭代/决策记录（执行模式=不拆分） |
| `[调整]` / 方案块被改 | 按反馈记录中的人类改动更新/重生成方案（历史由 Git 管理）：方案块被改 → 保留人类改动并校验边界/标签一致性；反馈区 `[调整]`+描述 → 按描述重生成 → 写入新版方案块 → 表 A 保持 `切分方案待确认` → 管理区追加重生成记录 |
| `[废弃]` | 清理方案块与反馈区（正文区回归纯原文）→ 表 A 生命周期 → `已废弃`、AI建议 → `建议终止` → 管理区追加废弃记录 |
| `[重新切分]` | 按 §2.3 重新切分流程执行：前置校验（未消费直切；已消费先输出 91 §A.7 变更影响声明）→ 清除旧切分文件与表 B 记录 → 移除标记 → 表 A 置 `切分方案待确认` → 重生成方案块（决策记录执行模式=重切） |

执行切分（`[同意执行]`/`[确认不拆分]`）时，表 A `内容摘要` 的阶段摘要同步写「已切分 N 片（见表 B）」——材料级只记切片数，切片清单由表 B `子文件` 列独揽，此列不重复（F2 裁决 B）。

处理前执行附录 B.1 竞态保护（表 A/表 B 相关行与 Step 1 快照一致，命中 `[需确认]` 不覆盖）；处理中更新表 A `内容摘要`（在反馈记录末追加 `[已处理]`，转「已处理反馈」）；执行完成后按 §2.2 同步契约推导更新文本化文档/切分文件管理区状态摘要。

### 4.4 Step 3 · 新增处理

读取状态文档表 A，按以下规则分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 对应文本化文档进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`、AI建议置 `建议终止`，追加废弃说明 |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

方案生成动作：

1. 读取文本化文档正文区纯原文
2. 按 §三 语义切分规则执行语义结构分析（业务对象与主责角色识别、场景内环节识别、关联性分析）
3. 形成切分/不切分建议
4. 在正文区原文之后写入切分方案块和反馈区
5. 更新表 A：`生命周期=切分方案待确认`、`AI建议=审核切分方案`、`内容摘要`（记录方案要点）
6. 从表 A 推导写入文本化文档管理区状态摘要

### 4.5 Step 4 · 提交基线

把本轮 Step 1~3 的处理结果提交为 git 基线（供下次 Step 1 作 diff 基准）：

1. **提交范围**：本轮更新的文本化文档（方案块/反馈区）、切分文件、状态文档表 A/B；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致）
4. **无变更**：工作区无改动时跳过提交，基线不变

```text
  A. 审方案 → 直接编辑文本化文档：改方案块 = 调整；反馈区写 [同意执行] / [确认不拆分] / [废弃]
  B. 已切分重切 → 文本化文档正文区写 [重新切分]

```

**交互只记录，不处理**——AI 输出本摘要后保持对话。对话中人类说明反馈意图，AI **先收集**（不逐条即时写表）。本步为**交互协议步骤**（执行模式=对话），由人类结束（「汇总」/「继续」）。

### 4.7 Step 6 · 变更汇总

人类表示反馈结束时（「汇总」/「就这些」）AI **立即汇总一次**：把本次互动全部反馈按 §2.2 记录格式整理成表 A `内容摘要`（反馈记录）并**提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交，交接即完整基线）**，输出「已汇总」摘要，**不执行处理**。汇总必须提交——否则下次 Step 1 `git diff` 会把 AI 自己的汇总误判为人类反馈。**全量提交边界**：对话期间人类对文档的静默编辑随汇总一并纳入基线（交互窗内人类应口头说明反馈；文档编辑是**线下/运行后**通道），下次 Step 1 不再对该窗内编辑单独检出。本步为**交互协议步骤**（执行模式=口令触发）。此汇总**不替代 Step 1**——人类在运行结束后直接编辑文档的反馈，仍由 Step 1 在下次运行开始时以 `git diff` 检出兜底。处理统一由 Step 2（「继续」后）基于表 A 记录执行。

### 5.2 切分文件结构与模板

**一句话**：切分文件（`.chunk-{seq}.md`）是切分产物，结构（三段：frontmatter + 管理区 + 正文）见 §2.1.2，生命周期见 §2.2.2。本节只给创建时的模板与字段填写。

```markdown
---
chunk:
  source: {原始文件名}.textualized.md
  original_source: {原始文件名}.{ext}
  seq: {序号}
  total: {总片数}
  label: {语义标签}
  range: {原文范围}
status: raw
---

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 切分已执行 / 不拆分已确认 | 可以澄清 | 无 | 运行 eos-ort02-clarify |

（切分正文内容）
```

字段说明：

| 字段 | 说明 |
|------|------|
| `source` / `original_source` | 文本化文档文件名 / 原始文件文件名（只读档案） |
| `seq` / `total` | 本片序号 / 本次切分总片数 |
| `label` | 语义标签，概括本片主题；不拆分单片填 `不切分（整份文档）` |
| `range` | 方案块中的行号范围（如 `L120~L340`），即切分执行依据；不拆分单片无行号范围时填 `整份文档` |
| `status` | 处理状态，初始 `raw`；下游按阶段更新 |

**切分文件生命周期**见 §2.2.2（表 B 生命周期 ↔ `status` ↔ 由谁推进的对照表）。

命名规则：

```text
10-raw-files/
├── 01-市场调研报告.pdf
├── 01-市场调研报告.textualized.md
├── 01-市场调研报告.chunk-001.md
├── 01-市场调研报告.chunk-002.md
└── 01-市场调研报告.chunk-003.md
```

> **不拆分单片**：确认不拆分时同样输出 `.chunk-{seq}.md`（`seq=1`、`total=1`），`label` 填 `不切分（整份文档）`，保证下游 ort02 以统一口径拾取。

### 5.3 OR 切分文档状态表

**一句话**：你在任何一份文档的管理区看到的状态摘要，都来自下面这张表——它告诉你看的是哪个阶段、在哪份文档的管理区、下一步该做什么。

| 阶段 | 在哪份文档的管理区 | AI建议 | 待处理 | 操作指引 |
|------|------------------|--------|--------|---------|
| 待确认切分方案 | 文本化文档（方案块阶段，切分文件尚未生成） | 审核切分方案 | 审阅方案块后编辑反馈 | 审阅方案块 → 编辑方案块/反馈区表达反馈 |
| 已切分 | 文本化文档（切分执行后，正文区回归纯原文） | 可以澄清 | 无 | 切分文件见表 B，可送 ort02 澄清 |

| 不拆分已确认 | 切分文件（单片） | 可以澄清 | 无 | 运行 eos-ort02-clarify |

> 本表为**文档内嵌状态摘要**的阶段取值（给人快速看），非状态文档表 B 生命周期取值。同一时刻，你从表 B 读到的是流程进度（`已切分`/`澄清中`…），从文档管理区读到的是本表阶段值。表 B 中切分文件生命周期统一为 `已切分`（不拆分单片同值）；下游 ort02 以表 B `已切分` + `AI建议=可以澄清` 为入口，不区分切分来源。
