# 文本化原始需求 → 切分文档 · 语义切分与反馈执行
**人类方案ID**: eos-ort01-chunk

> **概述**：把一个已文本化的文档切成几份语义独立的切分文件，供后续逐份澄清、规范化。流程：读状态文档表 A 中人类选入的材料 → 识别其中包含几个「**业务对象闭环**」（一段由某个主责角色负责到底的完整业务，一个闭环即一个候选单元）和「**系统级非功能约束**」（适用对象为业务域/平台能力/全局对象的性能/安全/合规等约束，判定见 §三）→ 生成切分方案供人类审阅 → 人类**直接编辑文档**表达反馈（改方案块=调整、反馈区写 `[同意执行]`/`[确认不拆分]`/`[废弃]`）→ AI 用 git 检出改动、判读意图、**记录**到表 A → Step 2 **按记录**执行切分。本步只切分，不做 规范化需求 规范化，也不评价需求。
>
> **输入 → 输出**：文本化 `.textualized.md` 文档（正文区：纯原文 + 方案块）+ `01-eos-sysdev-status.md` 表 A/表 B + git 基线 → 切分文件（`.chunk-{seq}.md`）+ 表 A/表 B 更新 + 反馈记录 + 新基线
>
> **适用场景**：EOS 原始需求预处理链第 2 步；将已文本化材料拆成适合澄清和规范化的语义片段。
>
> **接口设计**：反馈以 **git 为检测通道**——人类反馈 = 直接编辑**文本化文档**（方案块/反馈区）；切分文件是双方一致后的结果，不是反馈载体。AI 每次运行开始时 `git diff <基线>` 检出变更、判读意图、**记录**到状态文档表 A；**处理**由 Step 2 基于表 A 记录执行。反馈通道双轨（对齐 wft §A.5）——**对话通道**：AI 产出方案后不结束对话，人类自然语言反馈，AI 即时登记到表 A `内容摘要` 并处理、追加 `[已处理]`；**线下通道**：编辑文本化文档，经 Step 1 `git diff` 检出登记、Step 2 处理。无需口令表。入口靠表 A 与 git 变更分流：有反馈→Step 2、有新选入→Step 3。
>
> **设计规范参考**：[91-eos-biz-eng-spec.md](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md)（§1.4 业务对象概念、Step Start、反馈优先、输出交接（三区模板）与变更传播通用协议；本步反馈走「文档编辑 + git」特化，见 91 §A.5）
>

## 一、职责定位

**一句话**：本章说明本步的定位——要达成什么（1.1 目的与目标）、你参与哪三个点（1.2 人机交接点）、本步负责与不负责（1.3）。

### 1.1 本 Skill 目的与目标

> **主要目的**：把一份文本化文档切成多份语义独立、能进入澄清的切分文件，保留原文出处，并让人类对切分方案把关。
>
> **目标**（回答"本步要达到什么"；承担与边界见 §1.3）：
> 1. **识别选入材料**——读取表 A 中 `生命周期=已文本化` 且 `人类决策=同意切分` 的文本化文档（Step 3）
> 2. **生成切分方案**——以业务对象闭环为主要边界、系统级非功能约束为并列候选，识别候选单元并形成切分/不切分建议（Step 3 方案生成）
> 3. **检测并记录反馈**——`git diff` 检出人类对文档/表 A 的变更，判读意图并记录到表 A（Step 1）
> 4. **执行切分输出**——基于表 A 反馈记录生成 `.chunk-{seq}.md` 文件，写入 YAML frontmatter 和状态表（Step 2）
> 5. **处理迭代反馈**——支持 `[同意执行]` 切分、`[调整]` 重生成、`[确认不拆分]` 单片、`[废弃]` 终止、`[重新切分]` 重切（Step 2 调整分支）
> 6. **同步状态接口**——先更新状态文档表 A/表 B，再推导更新文本化文档和切分文件的状态摘要；Step 4 提交基线

### 1.2 人机交接点总览

**一句话**：你在本步有三个参与点——选材、审方案、选入澄清。审方案时**直接编辑文本化文档即反馈**（AI 用 git 检测）——编辑本身就是反馈，不必另行说明。

| 人类参与点 | 在哪操作 | 做什么 |
|-----------|---------|--------|
| ① 选材入切分 | 状态文档表 A | 对 `已文本化` 材料设 `人类决策=同意切分` |
| ② 审核切分方案 | 文本化文档正文区方案块 / 反馈区 | **直接编辑表达反馈**：改方案块=调整；反馈区写 `[调整]`（附描述）或 `[同意执行]` / `[确认不拆分]` / `[废弃]` |
| ③ 选入澄清 | 状态文档表 B | 对 `已切分` 切分文件设 `人类决策=同意澄清` → 进入 ort02 |

> AI 凭什么这么切（判定依据）见 **§三 设计原理与判据**；反馈如何被检测与记录见 §三 3.6 反馈检测判据与 §五。

### 1.3 本步负责与不负责

本 Skill 负责：

1. **检测**——`git diff <基线>` 检出人类文档/表 A 变更，判读意图并记录到表 A（Step 1）
2. **接收**——读取文本化文档和状态文档表 A，识别本轮选入切分的材料（Step 3）
3. **分析**——按 §三 识别业务对象及其主责角色、识别非功能约束适用对象线索、判定候选与关联性（§3.2/§3.3）
4. **规划**——生成切分方案块（建议切分或建议不切分），写入正文区原文之后，并附反馈区（Step 3 方案生成）
5. **执行**——基于表 A 反馈记录生成切分文件，或输出单片切分文件（Step 2）
6. **迭代**——基于反馈记录中的调整意见重生成方案（历史由 Git 管理，不归档旧方案）（Step 2 调整分支）
7. **落账**——更新表 A 的原料级状态与反馈记录，向表 B 追加切分文件级记录（表 A/表 B）
8. **交接**——Step 4 提交基线（ai-commit），Step End 输出待反馈、待选入切分、待选入澄清的行动清单

本 Skill 不负责：

1. 原始材料文本化（由 eos-ort00-textualize 负责）
2. 模糊需求澄清和标注（由 eos-ort02-clarify 负责）
3. 规范化需求条目规范化、编号、分类或冲突检测（由 eos-ort03-norm 负责）
4. 按 FR-BIZ / FR-ENG / NFR 分配到 wft01 系列
5. 修改原文语义、补充需求内容或作设计判断

### 2.1 业务对象与候选单元

**一句话**：本节讲切分的分析锚点——什么是业务对象闭环、什么构成一个候选单元，以及命名约定与大小层级；怎么识别、怎么判定见 §三 3.2/3.3。

**业务对象** [91 §1.4]：场景业务的全部操作与输出文档围绕的核心实体（如审批单、产品资产树、订单）。它有一条由**主责角色**（提出需求 / 负责完成 / 确认结果的人）主导的端到端闭环——需求提出 → 处理 → 满足确认。

**候选单元 = 业务对象闭环 ∪ 系统级非功能约束**：

- 材料里有几条业务对象闭环，就是几个候选单元
- **系统级非功能约束**（适用对象为业务域/平台能力/全局对象的性能/安全/合规/数据保留等约束）单独成候选；附着于某业务对象闭环（bph-biz 场景）的非功能约束随该场景成片、不单独成候选（适用对象线索判定见 §三 3.2 步骤 4）
- 配合角色（审批/审核/协作）是闭环内的环节，不单独成候选
- 物理段落是排版单位，不构成候选
- **命名**：业务对象闭环片命名 = 主责角色 + 场景业务（如"业务架构管理员治理产品资产树"）；系统级非功能约束片按主题锚点命名（如"系统非功能约束：性能与合规"）；无业务对象的结构锚点片按标题/主题命名
- 无明确业务对象的材料（技术说明/接口规范等）→ 退回结构锚点（数标题/编号）或主题转换点，方案块写明理由

**业务对象有大小层级**（产品 → 构件 → 构件数据文档，大端到端含小端到端）：完整闭环成片；仅含部分环节的归入大闭环；被当独立生命周期管理的小对象升格成片。**取哪级由材料自然描述决定——完整闭合为成片底线，可独立设计（下游 wft01 bph-biz 承接）为切分上限**（取级判据执行见 §三 3.3 补充规则）。

### 2.2 两类文档结构

**一句话**：本步处理两类文档——文本化文档（在其正文区写切分方案）和切分文件（切分产物）；两区/三段的结构为什么这样设计见 §三 3.1 切分原理。

#### 2.2.1 文本化文档结构

文本化文档（`{原始文件名}.textualized.md`）分两区：

| 区域 | 内容 | 本步操作 |
|------|------|---------|
| 管理区 | 文档顶部（正文前）：状态摘要、切分迭代记录、决策记录 | 写入/更新状态摘要，追加迭代记录和决策记录 |
| 正文区 | 原文 + 当前切分方案块 + 反馈区（均为临时，执行后清理） | 生成阶段写入方案块+反馈区；执行阶段清理，使正文区回归纯原文 |

**正文区检测原则**：正文区中当前是否存在 `╔═ 切分方案` 块，是分流关键（历史版本由 Git 管理，旧方案不参与入口判断）。**反馈载体**：方案块 = 「调整」的编辑对象（人类改行号/标签）；反馈区 = 人类确认标记的落点（写 `[调整]`/`[同意执行]`/`[确认不拆分]`/`[废弃]`）。两者的人类改动均由 git diff 检测，**AI 不写入反馈区**。

#### 2.2.2 切分文件结构

切分文件（`.chunk-{seq}.md`）是切分产物，一份切片档案由**三段**构成——头顶元数据（frontmatter）、管理区（这张片的状态与决策记录）、正文（原文片段）：

| 段 | 内容 | 本步操作 |
|----|------|---------|
| frontmatter | YAML 元数据（`source`/`original_source`/`seq`/`total`/`label`/`range`/`status`） | 创建时写入，`status=raw` |
| 管理区 | 状态摘要表（阶段/AI建议/待处理/操作指引） | 创建时写入（阶段=切分已执行/不拆分已确认） |
| 正文区 | 原文片段（切分内容） | 创建时写入 |

> 切分文件模板与字段填写见 §六 6.2；生命周期见 §二 2.3。

### 2.3 文档状态模型

**一句话**：本节讲本步的状态体系**怎么追踪**——全链双轨状态模型（外部轨道表 A/B + 内部轨道文档内嵌状态），两类文档各自的生命周期，以及状态文档与文档内嵌状态的同步契约。

#### 全链双轨状态模型

**全链双轨状态模型**：规范化需求预处理链的所有文档都双轨——**外部轨道**（状态文档表 A/B/C）管"流程推进到哪一步 + 反馈记录"（供 AI 入口判断、人类批量选材、Step 2 处理输入），**内部轨道**（文档内嵌状态）管"文档被处理到什么程度"（文本化文档 = 管理区状态摘要表；切分文件 = `frontmatter.status` + 管理区状态摘要表）。

#### 2.3.1 文本化文档生命周期（表 A）

| 阶段（表 A） | 含义（这份文本化文档现在到哪了） | 由谁推进 |
|-------------|--------------------------------|---------|
| 已登记 | ort00 刚登记，尚未文本化 | ort00 登记 |
| 已文本化 | ort00 已完成纯文本化，等人类选入切分 | ort00 完成 |
| 切分方案待确认 | ort01 已生成切分方案块，等人类反馈 | ort01 生成方案 |
| 已切分 | 切分方案已确认并执行，切分文件已输出 | ort01 执行 |
| 已废弃（含已废弃（重复）） | 材料终止（或查重判重复），不再处理 | ort00 / ort01 / 人类决策 |

> 表 A 全链生命周期线由 ort00 §二 2.2 定义；本步只推进 `切分方案待确认 → 已切分`，`已文本化` 之前由上游 ort00 推进，`已废弃` 由本步/上游/人类决策触发。

**记录三要素职责**（与 ort00 一致）：

| 字段 | 职责 |
|------|------|
| 生命周期 | 流程状态字段，供 AI 和流程判断使用 |
| AI建议 | 提示字段，仅供人类快速理解下一步建议，不参与 Step 入口硬判断 |
| 人类决策 | 批次控制字段，决定材料是否进入本轮处理 |

#### 2.3.2 切分文件生命周期（表 B + status）

**切分文件生命周期**（外部轨道表 B，内部轨道 `frontmatter.status`；本表为全链权威定义）：

| 阶段（表 B） | 含义（这张切片现在到哪了） | `status` | 由谁推进 |
|-------------|--------------------------|----------|---------|
| 已切分 | ort01 刚切出来，等人类选入澄清 | `raw` | ort01 创建 |
| 澄清中 | ort02 正在标注模糊项 | `annotated` | ort02 首轮标注 |
| 已澄清 | 模糊项已全部澄清，可送规范化 | `clarified` | ort02 达成 |
| 待确认规范方案 | ort03 已给规范化方案，等人类确认 | `clarified`（保持） | ort03 方案期 |
| 已规范化 | 规范化需求条目已写入基线 | `normalized` | ort03 确认 |
| 已废弃 | 不再处理 | `abandoned` | 任一步骤终止 |

> 下游各 Skill 文档只列本步更新的值，全量以本表为准。一张切片在任何时刻，你都可以通过「表 B 生命周期」问它在流程中到哪了、通过「frontmatter.status」问它被处理到什么深度。
>
> **status 写回口径**：`待确认规范方案` 期间 ort03 不写 status（保持 `clarified`）；确认执行时由 ort03 置 `normalized`；终止由任一步骤置 `abandoned`。

**本步对表 B 的职责**：执行切分时为每个 `.chunk-{seq}.md` 追加记录，初始 `生命周期=已切分`、`AI建议=可以澄清`。

**同步契约**：

1. **写序**——生成方案分支先更新表 A；执行切分分支先追加/更新表 B 并更新表 A；再从权威源推导写入文本化文档与切分文件管理区状态摘要（切分文件 `status` 同步写 frontmatter）。
2. **重建规则**——两者不一致时，以状态文档为准重建。
3. **版本感知**——写回前检测表 A/表 B 是否有未预期的人工修改（相关行与本次运行快照不符），命中时标记 `[需确认]`、不覆盖，并在 Step 5 摘要输出时提示人类。

> 反馈记录格式（`‖ 反馈：<类型>（<要点>）` + `[已处理]`）见 §三 3.6 反馈检测判据。

## 三、设计原理与判据

**一句话**：本章讲切分的**设计逻辑与判定规则**——为什么按业务对象闭环切分（3.1 切分原理）、怎么识别业务对象与非功能约束（3.2）、怎么判定切不切（3.3）、怎么执行（3.4）、哪些材料能进（3.5）、反馈怎么判读与记录（3.6）、守住什么边界（3.7）；概念见 §二，演进见 §四。

### 3.1 切分原理：为什么按业务对象闭环切分

**原始需求是连续长文，下游需要可独立承接的语义片**。一份文本化文档可能是多页综合材料，无法逐份澄清、逐份规范化。本步按语义边界把材料切成独立片，每片能独立进入 ort02 澄清、ort03 规范化，并最终被 wft01 bph-biz 逐场景承接。

**承接单位 = 业务对象闭环，因为它是需求的自然单位**。一段完整业务由一个主责角色负责到底（提出 → 处理 → 满足确认），是「某角色对某业务对象做某段闭环的事」的完整表述——切分片的粒度天然对齐下游 wft01 按场景业务承接的粒度。这正是「完整闭合为成片底线、可独立设计为切分上限」的由来（§3.3）。

**系统级非功能约束独立成片**。适用对象为业务域/平台能力/全局对象的约束（性能/安全/合规/数据保留等）不附属于任何单一场景，随场景无法被完整承接，故独立成候选；附着于某业务对象闭环（bph-biz 场景）的约束随该场景成片（§3.2 适用对象线索判定）。

**只切分、不评价**。本步只按业务对象/适用对象线索划定文本归属边界，不评价需求内容、不判定是否 NFR（分类维度由 ort03 判定）——预处理链的详概分离，见 §3.7。

**两区/三段结构让下游以纯原文接手**。文本化文档正文区存纯原文，方案块/反馈区是临时写入、执行后清理回归纯原文（下游 ort02 以「正文区有原文」接手）；切分文件三段——frontmatter 元数据承载追溯（source/original_source/seq/range）、管理区状态给人看、正文原文片段给下游（结构见 §二 2.2）。

### 3.2 识别规则

**一句话**：本节讲怎么从材料里找出候选——识别业务对象闭环（前三步）与系统级非功能约束（第 4 步）；识别结果决定候选单元数（§3.3 判定）。

通读时识别业务对象闭环（前三步）与系统级非功能约束（第 4 步）：

| # | 操作 | 做法 |
|---|------|------|
| 1 | 找候选对象 | 看核心动作（创建/提交/审批/确认等）的宾语；**以输出文档为抓手**——先数文档（需求文档/审批单/风险记录…，显式可数），再归并到业务对象 |
| 2 | 验证独立性 | 三问：能独立提出？有独立完成/确认时点？有独立主责角色？——全"是"才独立；否则为子结构/文档型，归入所属主轴 |
| 3 | 锚定主轴 | 材料闭环（提出端 → 处理端 → 确认端）共同指向的实体 = 主轴业务对象 |
| 4 | 识别非功能约束 | 扫附录B/22 分类维度相关质量属性词（性能/安全/可用性/可靠性/易用性/可扩展性/可运维性/合规/数据保留等），判定每条非功能约束语句的**适用对象线索**（见下表） |

**非功能约束适用对象线索判定**（取值对齐 [91 §九 bph-nfr 归组四元组](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#九非功能需求之系统设计)的"适用对象线索"——可能约束的 bph-biz / bph-eng / 业务域 / 平台能力 / 全局对象；FR-ENG/bph-eng 未纳入本步，留同构扩展）：

| 适用对象线索 | 判定口径 | 归属 | 是否独立成候选 |
|------------|---------|------|---------------|
| bph-biz 场景（附着于业务对象闭环） | 明确指向该场景的业务对象/动作（如"线索查询响应 < 2s"→ 线索管理） | 随该场景片成片 | 否 |
| 业务域 / 平台能力 / 全局对象 | 适用对象为业务域、平台能力或全局对象（如"系统可用性 99.9%"、"所有业务数据保留 5 年"） | 独立成片 | 是 |
| 表述模糊无法判定 | 不强行归属 | 随其所处文本位置（场景段内 → 随场景；独立成段 → 独立片），方案块标注 | 视位置 |

> 识别非功能约束只是**结构识别**（判定适用对象线索以决定文本归属），不是需求分类——是否 NFR、分类维度（22 资产 @nfr-xxx）、如何拆 规范化非功能需求 由 ort03 判定。

### 3.3 判定规则

**一句话**：本节讲怎么判定切不切——数候选、查关联性，按决策表出结论；结果决定方案块「建议切分 N 片 / 建议不切分」。

**数候选**（业务对象闭环数 + 系统级非功能约束片数，§3.2），**查关联性**（强关联 = 拆开破坏完整性：概念定义被依赖、跨段显式引用），按表判定：

| 候选单元数 | 关联性 | 结论 | 理由 |
|-----------|--------|------|------|
| 1 | — | 不切分 | 语义单一 |
| >1 | 强（拆开破坏完整性） | 不切分 | 语义不可分 |
| >1 | 弱（可独立成片） | 切分 | 输出多片方案 |

补充规则：

- **场景过大**：单个业务对象含多个可独立环节 → 按环节细分候选
- **系统级非功能约束独立成片**：系统级非功能约束（适用对象为业务域/平台能力/全局对象）与业务对象闭环弱关联（拆开不破坏任何闭环完整性）→ 通常切分、独立成片；附着场景（bph-biz）的非功能约束不单独成片，随场景
- **层级取级**：业务对象有大小层级（§二 2.1）——**完整闭合为成片底线，可独立设计（下游 wft01 bph-biz 承接）为切分上限**；取哪级由材料自然描述决定
- **边界纪律**：只识别业务对象/主责角色/非功能约束适用对象作边界，不评价需求内容；切分边界由人类复核方案块行号

**理由取值**（方案块「理由」字段）：

- 不切分 → **语义单一** = 一个主责角色的一段完整业务（或一份系统级非功能约束材料），本就是独立一片；或 **语义不可分** = 多个候选但强关联，想切却切不得
- 切分 → 每片各写独立依据，如"语义独立（主责角色：市场经理）"或"语义独立（系统级非功能约束）"

### 3.4 执行与示例

**一句话**：本节讲从读原文到出方案块的执行路径（AI 判断路径）、边界处理与行号基准，并用三个情形和一份完整材料走查示例演示判定全过程。

**AI 判断路径**（从读原文到出方案块）：确认入口（正文区纯原文）→ 通读找业务对象、主责角色与非功能约束适用对象线索（§3.2）→ 数候选（§3.3 决策表）→ 查关联性 → 出判定 → 写方案块（行号范围+标签+章节+理由；标签按 §二 2.1 命名 = 业务对象闭环片"主责角色 + 场景业务"、系统级非功能约束片"主题锚点"；表 A→切分方案待确认）→ 交人类反馈。方案块与反馈区模板见 §六 6.1。

**边界处理**：

| 边界情况 | 处理 |

**示例**（三情形对照）：

| 情形 | 识别结果 | 判定 |

| 多业务对象闭环 | "业务架构管理员治理产品资产树 + 数据治理员治理数据标准"两个业务对象闭环（两个主责角色）→ 候选单元 2，弱关联 | 切分为 2 片 |

### 3.5 入口规则

**一句话**：本节讲什么材料能进入本步（入口条件）、两个「不切分」怎么区分，以及每次运行的顺序（先反馈后新增）。

**入口条件**（Step 3 新增处理）：

| 条件 | 说明 |
|------|------|
| `生命周期=已文本化` | 上游 ort00 已完成文本化 |
| `人类决策=同意切分` | 人类明确选入本批切分 |

`AI建议=可以切分` 只是候选提示，不作为入口硬条件。`已登记` 是 ort00 内部中间状态，不构成 ort01 入口条件。

**两个"不切分"不是一回事**：表 A 的 `人类决策=暂不切分` 表示"本批不进入 ort01"；反馈区 `[确认不拆分]` 表示"已进入 ort01，但人类确认输出单片切分文件"。不得用 `不切分` 或 `暂搁置` 混用。

**运行路由**：每次运行**先处理反馈（Step 2），再处理新增选入（Step 3）**——反馈可能改变表 A/表 B 状态和下游澄清入口，不能被新增材料抢先。

### 3.6 反馈检测判据

**一句话**：本节讲反馈**怎么检测与记录**——反馈载体是文档/表 A 变更（git diff 检出）、判读成反馈记录到表 A 单源、Step 2 按记录执行（记录 + `[已处理]` 显式分界）。

**反馈单源原则**（本步特化）：反馈内容**只**记录在表 A `内容摘要`（承载反馈记录），由 git diff 检出的文档变更聚合而来、或由对话反馈即时登记写入；文档是反馈的**输入源**（人类编辑处），不是平行状态载体。因此表 A 反馈记录与文档状态不会不同步——反馈记录从文档变更聚合导出，无平行维护对象。

**`内容摘要` 双内容分段**：内容摘要 = 「阶段摘要 ∥ 反馈记录」——阶段摘要为当前处理阶段一句话（与 ort00/状态文档口径一致）；有已记录未处理反馈时以 `‖ 反馈：<类型>（<要点>）` 分段追加反馈记录（类型 = 调整/同意/确认不拆分/废弃/重新切分）。反馈记录未追加 `[已处理]` 前 = 已记录未处理（Step 2 入口依据）；Step 2 处理完成后在记录末追加 `[已处理]`，即转「已处理反馈」。

**反馈聚合思路**（人类在各文档里的意见如何收拢到状态表）：人类反馈发生在**文档里**——方案块、反馈区、`[重新切分]` 标记等散布在各材料文档中；每条反馈天然带着"它属于哪份材料"（编辑发生在哪份材料对应的文档上，就归哪份材料）。AI 不逐份文档主动读，而是靠两条通道把散落的反馈收拢到表 A `内容摘要` 一处（两条通道殊途同归，Step 2 只认表 A，不分辨反馈来自离线编辑还是对话）：

```text
文档（反馈输入源，散布在各材料文档）
  │ 通道① 离线编辑：Step 1 运行开始 git diff <基线> 一次性检出全部改动
  │ 通道② 对话反馈：Step 5 对话即处理（即时登记 + `[已处理]`）
  ↓
表 A 内容摘要（单源落点：按材料追加 ‖ 反馈：<类型>（<要点>），处理完追 [已处理]）
  ↓
Step 2 只读表 A 记录执行处理
```

**为什么聚合到表 A、而不是"文档改了就地处理"**：
1. **可数**——人类可一次反馈多份文档、分几轮给意见；聚合到表 A 后，"还有哪些材料有未处理反馈"一眼可数（`[已处理]` 之前 = 未处理）。
2. **单源不漂移**——对话反馈即时登记、离线反馈经 Step 1 检出登记，反馈都只存表 A `内容摘要` 一处（处理完追 `[已处理]`）；文档是输入源而非平行状态载体，不会"文档改了但状态表不知道"。

**反馈检测**（Step 1 变更检测 → Step 2 处理）：反馈以「文档/表 A 变更」承载，由 git diff 检出并**记录**到表 A `内容摘要`（反馈记录，格式见上）；Step 2 处理表 A 中「含反馈记录（`反馈：`）且未追加 `[已处理]`」的对象——`生命周期=切分方案待确认` 的对象走调整/同意/不拆分/废弃分支，`生命周期=已切分` 的对象走重新切分分支。

**反馈判读映射**（Step 1 从 diff 记录时判读意图）：

| 人类变更 | 判读意图 |
|---------|---------|
| 方案块行号/标签被改 | 调整（按新内容重生成方案） |
| 反馈区写 `[调整]` + 描述 | 调整（按描述重生成方案） |
| 反馈区写 `[同意执行]` | 同意（照当前文档内容执行切分） |
| 反馈区写 `[确认不拆分]` | 确认不拆分（输出单片） |
| 反馈区写 `[废弃]` | 废弃 |
| 已切分后文本化文档写 `[重新切分]` | 重新切分 |
| 正文区原文行被改（非方案块/反馈区） | 非切分反馈——保留提交，不记录表 A，Step 5 提示人类 |
| 文本化文档管理区 / 切分文件被改 | 非切分反馈——保留提交，不记录表 A，Step 5 提示人类 |
| 表 A 人类决策被改 | 选材 / 终止（走 Step 3 / 终止处理） |
| 表 A `切分方案待确认` 但正文区无方案块 | 数据不一致——不判读为反馈；Step 5 提示人类校正（清生命周期或重建方案块） |

> **触发词语义**：`[同意执行]`/`[确认不拆分]`/`[废弃]`/`[调整]`/`[重新切分]` 均为**人类确认标记**，写于反馈区（或正文区），由 git diff 检测；**AI 不写入**这些标记。方案块建议「不切分」且人类认可时用 `[同意执行]`（按方案块执行＝输出单片）；方案块建议「切分 N 片」而人类认为不应拆分时用 `[确认不拆分]`（否决切分建议，强制单片）；需要调整方案时用 `[调整]`+描述（或直接改方案块行号/标签）。**混合信号**：人类既改方案块又写 `[同意执行]` → 按改动后的当前文档内容执行（同意 = 照当前文档，非照原方案）。

|------|--------------|

## 四、材料演进：重切分与变更传播

**一句话**：本章讲已进流程的材料如何再处理——重切分三步流程（4.1）与变更传播约束（4.2）；状态模型见 §二 2.3，判据见 §三。

### 4.1 重切分规则

**一句话**：材料已 `已切分` 后人类要求重切时，按「入口 → 前置校验 → 执行」三步走。

**重新切分**（材料已 `已切分` 后人类要求重切）：

| 环节 | 处理 |
|------|------|
| 入口 | 人类在文本化文档正文区（已切分后为纯原文）追加 `[重新切分]` 标记；git diff 检出 → Step 1 记录 → Step 2 重切分支 |
| 前置校验 | 确认该材料各切分文件在表 B 的生命周期均未被下游消费（澄清/规范化）；已消费时先按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议) 输出变更影响声明，列出受影响的切分文件、规范化需求 与已消费业务概要，不得静默声明"下游不受影响" |
| 执行 | 清除旧切分文件与表 B 对应记录 → 移除 `[重新切分]` 标记 → 正文区回归纯原文 → 表 A 置 `切分方案待确认`，重新生成方案块（决策记录执行模式=重切） |

### 4.2 变更传播约束

**变更传播约束**（按 [91 规范 §A.7](../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#a7-变更传播协议)）：重新切分若改变切分边界，必须**列出受影响的切分文件、规范化需求 与已消费业务概要**，不得笼统说"下游不受影响"。已消费（澄清/规范化）时先输出变更影响声明再重切（见 §四 4.1 前置校验）。

## 五、操作流程

**一句话**：一次运行 = 变更检测与反馈汇总（Step 1）→ 反馈处理（Step 2）→ 新增处理（Step 3）→ 提交基线（Step 4）→ 反馈交互（Step 5）→ 反馈收尾（Step 6）。Step 1~4 你无需介入；Step 5 保持对话由你反馈、AI 即时处理，Step 6 以「整体确认」收尾（执行模式见白话注）。

### Step 布局总览

| Step | 名称 | 职责 | 人类参与 | 执行模式 | 产出 | 写资产 |
|------|------|------|---------|---------|------|-------|
| Start | 前置校验 | 检查上游文本化文档、状态文档与基线就绪 | 无（AI 自动） | 统一 | 就绪/结束 | — |
| 1 | 变更检测与反馈汇总 | git diff 检变更 → 判读意图 → 记录表 A | 无（检出你运行间隙的编辑） | 统一 | 反馈记录/变更清单 | 表 A |
| 2 | 反馈处理 | 读表 A 已记录反馈 → 执行切分/不拆分/调整/废弃/重切 | 无（执行你已给的反馈） | 统一 | 切分文件/新版方案/废弃记录 | 表 A、表 B、切分文件、文本化文档 |
| 3 | 新增处理 | 读取表 A 选入材料，生成切分方案块 | 无（你之后审方案） | 统一 | 方案块 + 反馈区 | 表 A、文本化文档 |
| 4 | 提交基线 | ai-commit 提交本轮变更（新基线） | 无（AI 自动） | 统一 | 新基线 | git（基线） |
| 5 | 反馈交互 | 输出三区摘要后不结束对话，自然语言反馈即时处理 | **有**——看三区摘要、对话反馈 | 对话 | 三区摘要 + 处理摘要 | 表 A |
| 6 | 反馈收尾 | 「整体确认」→ 确认无未处理记录 + 提交基线 + 推进状态 | **有**——「整体确认」/「可以了」 | 对话 | 收尾摘要 | git |
| End | 运行结束输出 | 输出行动清单（本次运行报告 + 下一步交接）后结束 | 无（AI 自动） | 统一 | 行动清单 | — |

> **执行模式白话**：统一 = AI 自动跑完这步，不需你介入；对话 = AI 产出方案后保持对话，你自然语言反馈、AI 即时处理。Step 1~4 为**运行内自动步骤**；Step 5/6 为**交互协议步骤**，由你反馈并「整体确认」收尾，不参与 Step 1 的运行路由。

**反馈机制一句话**：检测用 `git diff`（检文档/表 A 变更）、判读成反馈记录到表 A（`反馈：<类型>`）；处理走**记录 + `[已处理]`** 显式分界（§三 3.6 反馈检测判据）；每次运行**先处理反馈（Step 2）再处理新增选入（Step 3）**；表 A 控材料级状态、表 B 承切分文件级状态。

### 5.1 Step Start · 前置校验

**一句话**：先确认文本化文档、状态文档与基线就绪，再进入 Step 1 变更检测。

按顺序检查以下前置条件，缺什么补什么：

1. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
2. `../../80-pl4eos-2-eosdata/00-origin-requirement-materials/01-eos-sysdev-status.md` 是否存在；不存在则提示先运行 `eos-ort00-textualize` 并结束
3. 若状态文档已存在，校验表 A/表 B 的表头和字段说明；与状态文档模板不符时按既有口径修正或提示（表 B 模板见 §六 6.4）
4. `10-raw-files/` 中是否存在 `.textualized.md` 文档；不存在则提示先运行 `eos-ort00-textualize` 并结束
5. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
6. **感知前置——git diff 检出人类线下修订**（§三 3.6 反馈检测判据）：`git diff --name-status <基线>` + `git status --porcelain` 检出文档/表 A 变更。**存在变更（含纯线下编辑方案块/反馈区，表 A 可能无记录）→ 进入 Step 1 变更检测**（先检出反馈再判入口，避免"表 A 无记录 + 文档已被人类编辑"时误判无待处理退出、反馈丢失）
7. 无任何变更且无待处理对象（表 A 无待切分材料、无已记录反馈）时输出「无待处理对象」并结束

### 5.2 Step 1 · 变更检测与反馈汇总

**一句话**：本轮开始先把人类对文档/表 A 的改动找出来、判读成反馈、**记录**到表 A——之后 Step 2 基于这些记录处理，不读对话、不读正文区原文。

1. **取基线**：读状态文档 `HEAD @上次AI运行`（校验：`git log --author="EOS-AI" --format="%H" -1`，应一致；不一致时以 `git log --author="EOS-AI" -1` 为准并按该值补写 HEAD 字段）
2. **找变更**：`git diff --name-status <基线>` → 变更文件清单（含表 A 变更）；`git status --porcelain` 补 untracked
3. **按状态筛范围**：反馈判读只针对**文本化文档**变更（方案块/反馈区；`已切分` 时检 `[重新切分]` 标记）——切分文件是双方一致后的结果，不是反馈载体；表 A 变更单独检出（人类决策=选材/终止，见 step 6）；状态文档 `HEAD @上次AI运行` 行为 AI 上一轮 Step 4 自写的元数据（未提交），检出后**跳过判读、不记录、不 `[需确认]`**
4. **读变更**：逐文件 `git diff <基线> -- <文件>` 读变更 hunk（加载经济：只读变更，不读整文件）
5. **判读意图**：按 §三 3.6 反馈判读映射（调整 / 同意 / 确认不拆分 / 废弃 / 重新切分 / 选材-终止）
6. **记录到表 A**：按 §三 3.6 反馈检测判据记录格式把反馈记录（`‖ 反馈：<类型>（<要点>）`）追加到该材料行 `内容摘要`（分段追加，不覆盖既有阶段摘要）；人类对表 A 的直接修改（如 `人类决策` 变更）标记 `[需确认]`、不覆盖
7. **路由**：有反馈 → Step 2；有新选入 → Step 3；全无 → 「无待处理对象」结束

> 以上 7 条为 AI 执行细则（git 检出 → 判读 → 记录 → 路由），人类可跳过；你的对应动作是「运行间隙编辑文档 / 表 A」，改动会被自动检出并记录。

### 5.3 Step 2 · 反馈处理

**一句话**：本步把你已记录的反馈逐一执行——切分 / 不拆分 / 调整 / 废弃 / 重切；你无需操作，执行结果在三区摘要（Step 5）里呈现。

读取表 A 中「内容摘要 含反馈记录（`反馈：`）且未追加 `[已处理]`」的对象，先按生命周期分流：

| 表 A 生命周期 | 走的分支 |
|--------------|---------|
| `切分方案待确认` | 调整 / 同意 / 不拆分 / 废弃 |
| `已切分`（含 `[重新切分]` 反馈） | 重新切分 |

再按反馈意见执行：

| 反馈意见 | 处理 |
|---------|------|
| `[同意执行]` | 判方案块类型：建议不切分 → 按单片输出（规格同「确认不拆分」）；建议切分 → 校验行号范围（无重叠/无遗漏、标签完整）→ 逐片输出 `.chunk-{seq}.md` → 清理方案块与反馈区 → 表 B 每片追加记录（`已切分`/`可以澄清`）→ 表 A 生命周期 → `已切分` |
| `[确认不拆分]` | 输出单片（seq=1/total=1/label=`不切分（整份文档）`）→ 单片管理区写 `不拆分已确认` → 清理方案块与反馈区 → 表 A/B 同「同意执行」 → 追加迭代/决策记录（执行模式=不拆分） |
| `[调整]` / 方案块被改 | 按反馈记录中的人类改动更新/重生成方案（历史由 Git 管理）：方案块被改 → 保留人类改动并校验边界/标签一致性；反馈区 `[调整]`+描述 → 按描述重生成 → 写入新版方案块 → 表 A 保持 `切分方案待确认` → 管理区追加重生成记录 |
| `[废弃]` | 清理方案块与反馈区（正文区回归纯原文）→ 表 A 生命周期 → `已废弃`、AI建议 → `建议终止` → 管理区追加废弃记录 |
| `[重新切分]` | 按 §四 4.1 重新切分流程执行：前置校验（未消费直切；已消费先输出 91 §A.7 变更影响声明）→ 清除旧切分文件与表 B 记录 → 移除标记 → 表 A 置 `切分方案待确认` → 重生成方案块（决策记录执行模式=重切） |

执行切分（`[同意执行]`/`[确认不拆分]`）时，表 A `内容摘要` 的阶段摘要同步写「已切分 N 片（见表 B）」——材料级只记切片数，切片清单由表 B `子文件` 列独揽，此列不重复（F2 裁决 B）。

处理前执行 §二 2.3 同步契约第 3 条竞态保护（版本感知：表 A/表 B 相关行与本次运行快照一致，命中 `[需确认]` 不覆盖）；处理中更新表 A `内容摘要`（在反馈记录末追加 `[已处理]`，转「已处理反馈」）；执行完成后按 §二 2.3 同步契约推导更新文本化文档/切分文件管理区状态摘要。

### 5.4 Step 3 · 新增处理

**一句话**：本步为你新选入的材料生成切分方案块并写入正文区；你之后直接编辑它表达反馈（改方案块=调整，反馈区写确认标记）。

读取状态文档表 A，按以下规则分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 对应文本化文档进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`、AI建议置 `建议终止`，追加废弃说明；若正文区留有方案块/反馈区（`切分方案待确认` 态）先清理使其回归纯原文；若已有切分文件（表 B），同步将各文件表 B 生命周期置 `已废弃`、AI建议置 `建议终止`、frontmatter `status=abandoned`（终止级联动，见下） |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

> **终止级联动**：材料被 `人类决策=已终止` 时，除表 A 置废外——若正文区留有方案块/反馈区（`切分方案待确认` 态），先清理使其回归纯原文；若该材料已有切分文件（表 B 有记录），同步将各切分文件表 B 生命周期置 `已废弃`、AI建议置 `建议终止`、frontmatter `status=abandoned`，防止下游 ort02 继续拾取已废弃材料的切片（与 §二 2.3.2「已废弃 | 任一步骤终止」口径一致）。

方案生成动作：

1. 读取文本化文档正文区纯原文
2. 按 §三 语义切分规则识别业务对象与非功能约束适用对象线索并判定（§3.2 识别 + §3.3 决策表）
3. 形成切分/不切分建议
4. 在正文区原文之后写入切分方案块和反馈区
5. 更新表 A：`生命周期=切分方案待确认`、`AI建议=审核切分方案`、`内容摘要`（记录方案要点）
6. 从表 A 推导写入文本化文档管理区状态摘要

### 5.5 Step 4 · 提交基线

**一句话**：AI 把本轮结果提交为 git 基线，作为下次检测你改动的基准；你无需操作。

把本轮 Step 1~3 的处理结果提交为 git 基线（供下次 Step 1 作 diff 基准）：

1. **提交范围**：本轮更新的文本化文档（方案块/反馈区）、切分文件、状态文档表 A/B；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致；该写入发生在提交后、呈未提交态，下次 Step 1 检出该行时跳过判读，见 Step 1 step 3）
4. **无变更**：工作区无改动时跳过提交，基线不变

### 5.6 Step 5 · 反馈交互

先输出三区摘要（本步开场，给人看本轮运行报告与反馈指引），再保持对话收集反馈：

```text
══════════════════════════════════════════
  eos-ort01-chunk 本轮完成
══════════════════════════════════════════

当前状态：<已记录反馈 / 已处理反馈 / 已生成方案 / 无新增处理>
  记录反馈：<文件名>（调整 / 同意 / 确认不拆分 / 废弃 / 重新切分）
  处理反馈：<文件名>（执行切分 → 表 B 已切分 / 重生成方案仍待确认 / 废弃）
  生成方案：<文件名>（建议切分 N 片 / 建议不切分，等待反馈）
  废弃材料：<文件名>（表 A 生命周期=已废弃）
资产落账：表 A/表 B 已同步；基线已提交（<hash>）

一、待反馈（对话 / 编辑文档均可）
  A. 对话反馈 → 直接说明流程指示（同意/调整/确认不拆分/废弃/重新切分），AI 即时处理并追加 [已处理]
  B. 编辑文档 → 改方案块 / 反馈区写 [同意执行] / [确认不拆分] / [废弃]，下轮 Step 1 git diff 检出 → Step 2 处理

二、下一步
  ① 待选入切分的材料 → 表 A `生命周期=已文本化` + `AI建议=可以切分` + `人类决策=空`：设 `人类决策=同意切分` 后重跑本步生成方案
  ② 待选入澄清的切分文件 → 表 B `生命周期=已切分` + `AI建议=可以澄清`：设 `人类决策=同意澄清` 后运行 eos-ort02-clarify
```

**对话即处理**——AI 输出本摘要后**不结束对话**。人类在对话中直接说明反馈意图（如「同意」「调整 002 范围…」「确认不拆分」「废弃」「重新切分」），AI **即时理解并处理**：按 §三 3.6 反馈判据把反馈登记到表 A `内容摘要`（`反馈：<类型>（<要点>）`）并执行对应动作（同意→执行切分 / 调整→重生成方案块 / 确认不拆分→输出单片 / 废弃→表 A 废弃 / 重新切分→重切流程），追加 `[已处理]`，输出处理摘要，继续等待。**无需口令表**——AI 通过理解自然语言判断反馈意图（「打开状态文档」等辅助请求按自然语言处理）；对话反馈与线下编辑等价（线下编辑仍由 Step 1 检出登记、Step 2 处理）。反馈结束以「整体确认」为准（Step 6）。本步为**交互协议步骤**（执行模式=对话）。

### 5.7 Step 6 · 反馈收尾（整体确认）

**一句话**：你表示反馈结束（「整体确认」/「可以了」）时，AI 确认本轮对话反馈均已处理、提交基线、推进状态。

**动作**：人类表示反馈结束（「整体确认」/「可以了」）时，AI **立即收尾一次**——确认本轮对话反馈均已处理（无未追加 `[已处理]` 的记录）→ **提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交，交接即完整基线）** → 推进状态 → 输出「已确认」摘要。

**为什么必须提交**：否则下次 Step 1 `git diff` 会把 AI 自己的处理误判为人类反馈。对话期间你对文档的静默编辑也随收尾一并纳入基线（交互窗内应口头说明反馈；文档编辑是**线下/运行后**通道），下次不再单独检出。

**兜底与路由**：本步为**交互协议步骤**（执行模式=对话）。此收尾**不替代 Step 1**——运行结束后你直接编辑文档的反馈，仍由 Step 1 下次运行时以 `git diff` 检出兜底，Step 2 基于表 A 记录处理。**无需口令表**——「整体确认」为自然语言表达；如有仍未处理的已记录反馈，可自然语言要求「继续处理反馈」，AI 重跑 Step 2 后回到 Step 5。

### 5.8 Step End · 运行结束输出

**一句话**：输出行动清单后结束——你后续可对话反馈（下轮 Step 5/6），也可直接编辑文档/表 A（下轮 Step 1 `git diff` 检出）。

```text
  B. 编辑文档 → 改方案块 / 反馈区写 `[调整]` / `[同意执行]` / `[确认不拆分]` / `[废弃]`，下轮 Step 1 `git diff` 检出
```

### 6.2 切分文件结构与模板

**一句话**：切分文件（`.chunk-{seq}.md`）是切分产物，结构（三段：frontmatter + 管理区 + 正文）见 §二 2.2.2，生命周期见 §二 2.3.2。本节只给创建时的模板与字段填写。

```markdown
---
chunk:
  source: {原始文件名}.textualized.md
  original_source: {原始文件名}.{ext}
  seq: {序号}
  total: {总片数}
  label: {主责角色 + 场景业务 / 系统级非功能约束主题}
  range: {原文范围}
status: raw
---

| 阶段 | AI建议 | 待处理 | 操作指引 |
|------|--------|--------|---------|
| 切分已执行 / 不拆分已确认 | 可以澄清 | 无 | 运行 eos-ort02-clarify |

（切分正文内容）
```

字段说明：

| 字段 | 说明 |
|------|------|
| `source` / `original_source` | 文本化文档文件名 / 原始文件文件名（只读档案） |
| `seq` / `total` | 本片序号 / 本次切分总片数 |
| `label` | 语义标签 = 主责角色 + 场景业务（如"业务架构管理员治理产品资产树"）；系统级非功能约束片按主题锚点命名（如"系统非功能约束：性能与合规"）；无业务对象的结构锚点片按标题/主题命名；不拆分单片填 `不切分（整份文档）` |
| `range` | 方案块中的行号范围（如 `L120~L340`），即切分执行依据；不拆分单片无行号范围时填 `整份文档` |
| `status` | 处理状态，初始 `raw`；下游按阶段更新 |

**切分文件生命周期**见 §二 2.3.2（表 B 生命周期 ↔ `status` ↔ 由谁推进的对照表）。

命名规则：

```text

├── 01-市场调研报告.textualized.md
├── 01-市场调研报告.chunk-001.md
```
