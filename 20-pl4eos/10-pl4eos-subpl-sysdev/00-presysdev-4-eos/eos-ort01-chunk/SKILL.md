## 一、职责定位

### 负责与不负责

| 负责 | 不负责（路由指向） |
|------|-------------------|
| Step 1：git diff 检变更 → 判读意图 → 记录表 A（反馈记录） | 原始材料文本化 → `eos-ort00-textualize` |
| Step 3：读取表 A 中 `生命周期=已文本化` + `人类决策=同意切分` 的材料，生成切分方案块 | 模糊需求澄清 → `eos-ort02-clarify` |
| 识别业务对象与非功能约束适用对象线索并判定切分（附录 A.3 + A.4 决策表） | OR 条目规范化/分类/编号 → `eos-ort03-norm` |
| Step 2：基于表 A 反馈记录执行：[同意执行]→切分 / [确认不拆分]→单片 / [调整]→重生成 / [废弃]→终止 / [重新切分]→重切 | 修改原文语义、补充需求内容 |
| 同步状态文档表 A（原料级 + 反馈记录）+ 表 B（切分文件级）；Step 4 提交基线 | — |

**核心原则**：AI 只做业务对象/非功能约束适用对象线索识别与边界切分 + 反馈记录与执行，不评价需求内容、不作设计判断（NFR 适用对象线索识别仅用于决定文本归属，是否 NFR、分类维度及如何拆 NFR OR 由 ort03 判定）；**交互只记录不处理**——对话反馈在交互结束时（「汇总」）统一记录到表 A，处理由 Step 2 基于记录执行。

### 上下游衔接

| 方向 | Skill | 交接内容 |
|------|-------|---------|
| 上游 | `eos-ort00-textualize` | 表A `生命周期=已文本化` + `人类决策=同意切分` 的文本化文档 |
| 下游 | `eos-ort02-clarify` | 表B `生命周期=已切分` + `AI建议=可以澄清` 的切分文件 → 设 `人类决策=同意澄清` 后进入 |

## 二、操作流程

### Step Start · 前置校验

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 存在；否则提示先运行 `eos-ort00-textualize` 并结束
2. `01-eos-sysdev-status.md` 存在；否则同上
3. 校验表 A/表 B 表头与字段说明，与状态文档模板不符时按既有口径修正或提示（表 B 模板见 [人类方案 §5.4](../eos-ort01-chunk.md#54-状态文档表-b-模板)）；否则同上
4. `10-raw-files/` 中存在 `.textualized.md` 文档；否则同上
5. 确认处于 git 仓库且 AI 基线可用：`scripts/ai-commit.sh` 存在；基线 = 状态文档 `HEAD @上次AI运行` 或最近 AI 提交（`git log --author="EOS-AI" -1`）
6. 全部就绪 → Step 1；无任何待处理对象时输出「无待处理对象」并结束

**加载经济原则**：用 `git diff --name-status` / `ls` / grep 扫描变更文件与状态文档表 A/表 B 区域，不 Read 整个状态文档；切分分析时仅读取目标文本化文档的正文区（管理区不参与语义分析）。

### Step 1 · 变更检测与反馈汇总

**一句话**：本轮开始先把人类对文档/表 A 的改动找出来、判读成反馈、**记录**到表 A——之后 Step 2 基于这些记录处理，不读对话、不读正文区原文。

1. **取基线**：读状态文档 `HEAD @上次AI运行`（校验：`git log --author="EOS-AI" --format="%H" -1`，应一致；不一致时以 `git log --author="EOS-AI" -1` 为准并按该值补写 HEAD 字段）
2. **找变更**：`git diff --name-status <基线>` → 变更文件清单（含表 A 变更）；`git status --porcelain` 补 untracked
3. **按状态筛范围**：反馈判读只针对**文本化文档**变更（方案块/反馈区；`已切分` 时检 `[重新切分]` 标记）——切分文件是双方一致后的结果，不是反馈载体；表 A 变更单独检出（选材/终止）；状态文档 `HEAD @上次AI运行` 行为 AI 上一轮 Step 4 自写的元数据（未提交），检出后**跳过判读、不记录、不 `[需确认]`**
4. **读变更**：逐文件 `git diff <基线> -- <文件>` 读变更 hunk
5. **判读意图**：按附录 A.1 反馈判读映射（调整 / 同意 / 确认不拆分 / 废弃 / 重新切分 / 选材-终止）
6. **记录到表 A**：按 [人类方案 §3.2](../eos-ort01-chunk.md#32-文档状态与同步) 记录格式把反馈记录（`‖ 反馈：<类型>（<要点>）`）追加到该材料行 `内容摘要`（分段追加，不覆盖阶段摘要）；人类对表 A 的直接修改标记 `[需确认]`、不覆盖
7. **路由**：有反馈 → Step 2；有新选入 → Step 3；全无 → 「无待处理对象」结束

### Step 2 · 反馈处理

**一句话**：只处理表 A 中「已记录未处理」的反馈——按生命周期分流执行对应分支，处理完在反馈记录末追加 `[已处理]`。

读取表 A 中「内容摘要 含反馈记录（`反馈：`）且未追加 `[已处理]`」的对象，先按生命周期分流：

| 表 A 生命周期 | 走的分支 |
|--------------|---------|
| `切分方案待确认` | 调整 / 同意 / 不拆分 / 废弃 |
| `已切分`（含 `[重新切分]` 反馈） | 重新切分 |

再按反馈意见执行：

| 反馈意见 | 处理 |
|---------|------|
| `[同意执行]` | 判方案块类型：建议不切分→按单片输出（seq=1/total=1/label=`不切分（整份文档）`，管理区写「不拆分已确认」，规格同确认不拆分）；建议切分→校验行号范围（无重叠/无遗漏，语义标签完整）→ 逐片输出 `.chunk-{seq}.md`（frontmatter 见附录 C）→ 清理方案块与反馈区 → 表 B 每片追加记录（`生命周期=已切分`、`AI建议=可以澄清`）→ 表 A→`已切分` |
| `[确认不拆分]` | 输出单片（seq=1, total=1，label=`不切分（整份文档）`）→ 单片管理区写状态摘要 `不拆分已确认` → 清理方案块 → 表 A/B 同上（`已切分`+`可以澄清`）→ 追加迭代/决策记录（执行模式=不拆分） |
| `[调整]` / 方案块被改 | 按反馈记录中的人类改动更新/重生成方案（历史由 Git 管理）：方案块被改→保留人类改动并校验边界/标签一致性；反馈区 `[调整]`+描述→按描述重生成 → 写入新版方案块 → 表 A 保持待确认 |
| `[废弃]` | 清理方案块与反馈区（正文区回归纯原文）→ 表 A→`已废弃`、AI建议→`建议终止`，管理区追加废弃记录 |
| `[重新切分]` | 按 [人类方案 §3.3](../eos-ort01-chunk.md#33-入口与重进入规则) 重新切分流程执行：前置校验（未消费直切；已消费先输出 91 §A.7 变更影响声明）→ 清除旧切分文件与表 B 记录 → 移除标记 → 表 A 置 `切分方案待确认` → 重生成方案块（决策记录执行模式=重切） |

执行切分（`[同意执行]`/`[确认不拆分]`）时，表 A `内容摘要` 阶段摘要同步写「已切分 N 片（见表 B）」——切片清单由表 B `子文件` 列独揽（人类方案 F2 裁决 B）。

处理前执行附录 B.1 竞态保护；处理中更新表 A `内容摘要`（在反馈记录末追加 `[已处理]`，转「已处理反馈」）；执行完成后按 [人类方案 §3.2](../eos-ort01-chunk.md#32-文档状态与同步) 同步契约推导更新文本化文档/切分文件管理区状态摘要。

### Step 3 · 新增处理

**一句话**：处理人类新选入切分的材料——读正文区纯原文、按 [人类方案 §二](../eos-ort01-chunk.md#二语义切分规则) 分析、写方案块与反馈区，表 A 置 `切分方案待确认`。

读取表 A，按附录 A.2 分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`、AI建议置 `建议终止`，追加废弃说明；若正文区留有方案块/反馈区先清理回归纯原文；若已有切分文件（表 B），同步将各文件表 B 置 `已废弃`、frontmatter `status=abandoned`（终止级联动，见 [人类方案 §4.4](../eos-ort01-chunk.md#44-step-3--新增处理)） |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

**方案生成**（详细规则见 [人类方案 §二](../eos-ort01-chunk.md#二语义切分规则)）：

1. 读取文本化文档正文区纯原文
2. 识别业务对象与非功能约束适用对象线索（附录 A.3）
3. 按切分判定表形成切分/不切分建议（附录 A.4）
4. 在正文区原文之后写入切分方案块 + 反馈区（模板见附录 C）
5. 表 A 更新：`生命周期=切分方案待确认`、`AI建议=审核切分方案`、`内容摘要`（记录方案要点）
6. 从表 A 推导写入文本化文档管理区状态摘要

### Step 4 · 提交基线

**一句话**：把本轮结果提交为 git 基线，作为下次 Step 1 检测人类改动的基准。

把本轮 Step 1~3 的处理结果提交为 git 基线（供下次 Step 1 作 diff 基准）：

1. **提交范围**：本轮更新的文本化文档（方案块/反馈区）、切分文件、状态文档表 A/B；人类未提交的编辑一并纳入（`git add -A`）
2. **执行提交**：`scripts/ai-commit.sh "<提交说明>"`——author=EOS-AI + `[AI]` 前缀 + Co-Authored-By，输出新基线 hash
3. **记录基线**：将新基线 hash 写入状态文档 `HEAD @上次AI运行` 字段（与 `git log --author="EOS-AI" -1` 一致；该写入发生在提交后、呈未提交态，下次 Step 1 检出该行时跳过判读，见 Step 1 step 3）
4. **无变更**：工作区无改动时跳过提交，基线不变

### Step 5 · 反馈交互

先输出三区摘要（本步开场，给人看本轮运行报告与反馈指引），再保持对话收集反馈：

```text
══════════════════════════════════════════
  eos-ort01-chunk 本轮完成
══════════════════════════════════════════

当前状态：<已记录反馈 / 已处理反馈 / 已生成方案 / 无新增处理>
  记录反馈：<文件名>（调整 / 同意 / 确认不拆分 / 废弃 / 重新切分）
  处理反馈：<文件名>（执行切分 → 表 B 已切分 / 重生成方案仍待确认 / 废弃）
  生成方案：<文件名>（建议切分 N 片 / 建议不切分，等待反馈）
  废弃材料：<文件名>（表 A 生命周期=已废弃）
资产落账：表 A/表 B 已同步；基线已提交（<hash>）

一、待反馈（编辑文档即反馈，AI 用 git 检测）
  A. 审方案 → 直接编辑文本化文档：改方案块 = 调整；反馈区写 [同意执行] / [确认不拆分] / [废弃]
  B. 已切分重切 → 文本化文档正文区写 [重新切分]

二、下一步
  ① 已记录反馈 → 回复「继续」运行本步执行处理（Step 2）
  ② 待选入切分的材料 → 表 A `生命周期=已文本化` + `AI建议=可以切分` + `人类决策=空`：设 `人类决策=同意切分` 后重跑本步生成方案
  ③ 待选入澄清的切分文件 → 表 B `生命周期=已切分` + `AI建议=可以澄清`：设 `人类决策=同意澄清` 后进入 eos-ort02-clarify
```

**交互只记录，不处理**——AI 输出本摘要后保持对话。对话中人类说明反馈意图，AI **先收集**（不逐条即时写表）。本步为**交互协议步骤**（执行模式=对话），由人类结束（「汇总」/「继续」）。

### Step 6 · 变更汇总

**动作**：人类表示反馈结束时（「汇总」/「就这些」）AI **立即汇总一次**——把本次互动全部反馈按 [人类方案 §3.2](../eos-ort01-chunk.md#32-文档状态与同步) 记录格式整理成表 A `内容摘要`（反馈记录），**提交基线（同 Step 4 机制——`scripts/ai-commit.sh` 全量提交，交接即完整基线）**，输出「已汇总」摘要，**不执行处理**。

**为什么必须提交**：否则下次 Step 1 `git diff` 会把 AI 自己的汇总误判为人类反馈。

**全量提交边界**：对话期间人类对文档的静默编辑随汇总一并纳入基线（交互窗内人类应口头说明反馈；文档编辑是**线下/运行后**通道），下次 Step 1 不再对该窗内编辑单独检出。

**兜底与路由**：本步为**交互协议步骤**（执行模式=口令触发）。此汇总**不替代 Step 1**——人类在运行结束后直接编辑文档的反馈，仍由 Step 1 在下次运行开始时以 `git diff` 检出兜底。处理统一由 Step 2（「继续」后）基于表 A 记录执行。

**AI 处理口令规则**（按步骤分组）：

| 步骤 | 人类输入 | AI 动作 |
|------|---------|--------|
| Step 5 | **对话反馈**：「调整 002 范围…」等 | 对话中收集，待「汇总」时统一记录到表 A（不逐条即时写表） |
| Step 5 | **辅助**：「同意澄清 [切分文件]」 | 表 B 人类决策=同意澄清 |
| Step 5 | **辅助**：「打开状态文档」 | 输出 `01-eos-sysdev-status.md` 路径和建议关注行 |
| Step 6 | **「汇总」/「就这些」** | 立即汇总本次互动全部反馈到表 A `内容摘要` + 提交基线，不处理 |
| Step 6 | **辅助**：「继续」 | 有未汇总对话反馈时先汇总，再重跑本步处理已记录反馈（Step 2）与新增选入（Step 3），并 Step 4 提交基线 |

### Step End · 运行结束输出

**一句话**：输出行动清单（本次运行报告 + 下一步交接）后结束。

输出行动清单后**结束**：

1. 当前状态：生成方案（建议切分 N 片/建议不切分）/ 已执行切分（表 B 生命周期=已切分）/ 已确认不拆分（total=1 单片）/ 废弃
2. 资产落账：表 A 已同步（含反馈记录）；切分文件 frontmatter.status / 管理区状态摘要已同步；基线已提交
3. 待反馈（编辑文档/对话均可）：A 对话反馈（调整/同意执行/确认不拆分/废弃/重新切分，「汇总」后落表 A）/ B 编辑文档（改方案块或反馈区写确认标记，下轮 Step 1 `git diff` 检出）/ C 终止材料（表 A `人类决策=已终止`）
4. 下一步：①待选入切分 → 表 A `已文本化`+`同意切分`；②待选入澄清 → 表 B `已切分`+`同意澄清` → eos-ort02-clarify

模板详见 [人类方案 §4.8](../eos-ort01-chunk.md)（Step End·运行结束输出）。

## 三、AI 标记约定

**正文区方案块状态**：方案块存在 = 待确认（Step 3 产物）；清理 = 已执行。历史版本由 Git 管理，旧方案不参与入口判断。

**反馈触发词（人类确认标记）**：`[同意执行]` / `[确认不拆分]` / `[废弃]` / `[调整]`（写反馈区，`[调整]` 附描述或直接改方案块行号/标签）、`[重新切分]`（已切分后写正文区）——由人类直接写入，**AI 不代写**；git diff 检出后判读意图并按人类方案 §3.2 记录格式（`‖ 反馈：<类型>（<要点>）`）记录到表 A `内容摘要`；处理完成后追加 `[已处理]`。

**意图判读**（Step 1 从 diff 记录时）：方案块行号/标签被改 = 调整；反馈区 `[调整]`+描述 = 调整（按描述重生成）；反馈区 `[同意执行]` = 同意（照当前文档内容执行）；`[确认不拆分]` = 单片；`[废弃]` = 废弃；正文区 `[重新切分]` = 重切；正文区原文行被改（非方案块/反馈区）= 非切分反馈（保留提交、不记录、提示人类）；管理区/切分文件被改 = 非切分反馈（同上）；表 A 人类决策被改 = 选材/终止；表 A `切分方案待确认` 但正文区无方案块 = 数据不一致（提示人类校正，不按反馈处理）。**混合信号**（既改方案块又写 `[同意执行]`）→ 按改动后的当前文档内容执行。**交互结束汇总**亦产出表 A 反馈记录——对话反馈经「汇总」统一记录，判读同本映射。

**状态摘要取值**：文档内嵌状态摘要的阶段值分两类宿主——文本化文档管理区用「待确认切分方案 / 已切分」；切分文件管理区用「切分已执行 / 不拆分已确认」；「已废弃」两者皆可（材料终止→文本化文档，片终止→切分文件）。表 B 生命周期不受其影响——切分文件（含不拆分单片）统一为 `已切分`。

**增量标记**：反馈处理中按 91 规范 §A.5 追加 `[已处理]` 作为处理记录。

### A.3 业务对象与非功能约束识别

（详细见 [人类方案 §二](../eos-ort01-chunk.md#二语义切分规则)）

| # | 操作 | 说明 |
|---|------|------|
| 1 | 找候选对象 | 核心动作（创建/提交/审批/确认等）的宾语；以输出文档为抓手——先数文档，再归并到业务对象 |
| 2 | 验证独立性 | 三问：独立提出？独立完成/确认时点？独立主责？全"是"才独立，否则归入所属主轴 |
| 3 | 锚定主轴 | 材料闭环（提出端→处理端→确认端）共同指向的实体 = 主轴业务对象 |
| 4 | 识别非功能约束 | 扫附录B/22 分类维度相关质量属性词（性能/安全/可用性/可靠性/易用性/可扩展性/可运维性/合规/数据保留等），判定每条非功能约束语句的适用对象线索（见下表） |

**非功能约束适用对象线索判定**（取值对齐 [91 §九](../../../10-wfsysdev-4-eos/91-eos-biz-eng-spec.md#9-非功能需求之系统设计) STR-NFR 归组四元组"适用对象线索"）：

| 适用对象线索 | 判定口径 | 归属 |
|------------|---------|------|
| STR-F 场景（附着于业务对象闭环） | 明确指向该场景的业务对象/动作 | 随该场景片成片（不独立成候选） |
| 业务域 / 平台能力 / 全局对象 | 适用对象为业务域、平台能力或全局对象 | 独立成片（独立候选） |
| 表述模糊无法判定 | 不强行归属 | 随所处文本位置（场景段内→随场景；独立成段→独立片），方案块标注 |

> 候选单元 = 业务对象闭环 [91 §1.4]（一个主责角色的端到端职责闭环）∪ 系统级非功能约束（适用对象为业务域/平台能力/全局对象）；配合角色不单独成候选；无明确业务对象场景退回结构/主题锚点（写明理由）。**命名**：业务对象闭环片 = **主责角色 + 场景业务**（如"业务架构管理员治理产品资产树"）；系统级非功能约束片 = 主题锚点（如"系统非功能约束：性能与合规"）；结构锚点片按标题/主题。业务对象有大小层级——完整闭合为成片底线、可独立设计（wft01 STR-F 承接）为切分上限。识别非功能约束仅为结构识别（定文本归属），不构成需求分类——分类维度（22 资产 @nfr-xxx）与 NFR 拆分由 ort03 判定。

### A.4 切分判定

**数候选**（业务对象闭环数 + 系统级非功能约束片数，A.3），**查关联性**（强关联 = 拆开破坏完整性：概念定义被依赖、跨段显式引用），按表判定：

| 候选单元数 | 关联性 | 结论 | 理由 |
|-----------|--------|------|------|
| 1 | — | 不切分 | 语义单一 |
| >1 | 强（拆开破坏完整性） | 不切分 | 语义不可分 |
| >1 | 弱（可独立成片） | 切分 | 输出多片方案 |

**补充**：场景过大（单个业务对象含多个可独立环节）→ 按环节细分候选；系统级非功能约束独立成片（与业务对象闭环弱关联、拆开不破坏完整性，附着场景（STR-F）的非功能约束不单独成片）；边界纪律——只识别业务对象/主责角色/非功能约束适用对象线索作边界，不评价需求。**理由取值**（方案块「理由」字段，见 [人类方案 §2.3](../eos-ort01-chunk.md#23-判定切不切)）：不切分 → `语义单一` / `语义不可分`；切分 → 每片写独立依据（如"语义独立（主责角色：市场经理）"或"语义独立（系统级非功能约束）"）。

**AI 判断路径**（完整版见 [人类方案 §二](../eos-ort01-chunk.md#二语义切分规则)）：确认入口（正文区纯原文）→ 通读找业务对象、主责角色与非功能约束适用对象线索（A.3）→ 数候选（A.4 决策表）→ 查关联性 → 出判定 → 写方案块（行号范围+标签+章节+理由，标签=业务对象闭环片"主责角色+场景业务"/系统级非功能约束片"主题锚点"）→ 交人类反馈。

### A.5 边界处理

| 边界情况 | 处理 |
|---------|------|
| 行号边界落在段落中间 | 被截断段落完整归入起始片，行动清单提示边界截断 |
| 连续两片之间有空白行 | 空白行归入前一片 |
| 切分内容为空 | 不输出空文件，视为无效标记 |

> **行号基准**：方案块「行号：Lxxx」相对**正文区**计数（正文区第 1 行 = L1），管理区行数变化不影响行号（详见 [人类方案 §二](../eos-ort01-chunk.md#二语义切分规则)）。

### A.6 表 A/表 B 取值

| 表 | 生命周期 | 人类决策 |
|----|---------|---------|
| 表 A | 已登记 → 已文本化 → 切分方案待确认 → 已切分 → 已废弃（含已废弃（重复）） | 空 / 同意切分 / 暂不切分 / 已终止 |
| 表 B | 已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃 | 空 / 同意澄清 / 同意规范化 / 已终止 |

## 附录B：版本感知与写回

### B.1 变更检测与写回前冲突检查

表 A/表 B 是人类与 AI 共同维护的表。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **运行开始（Step 1）**——`git diff <基线>` 检出人类对文档/表 A 的全部变更（含已提交与未提交），作为反馈记录与「需确认」标记的来源
2. **快照**——Step 1 记录待处理行 `生命周期` 与 `人类决策` 的当前值
3. **写回前复核**——写回前重新读取该行；若与快照不符（人类在本次运行期间手工修改），标记 `[需确认]`、不覆盖，在 Step 5 摘要输出时提示人类
4. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：除非人类通过 Step 5/6 口令明确指示（如「同意澄清」「汇总」「继续」），AI 绝不覆盖非空的人类决策

### B.2 写回顺序（同步契约）

1. 变更记录分支（Step 1）：**先写表 A `内容摘要`（反馈记录）**，不覆盖人类对表 A 的直接修改（标记 `[需确认]`）
2. 生成方案分支（Step 3）：**先更新表 A**（`切分方案待确认` + 内容摘要方案要点），再推导写入文本化文档管理区
3. 执行切分分支（Step 2）：**先追加/更新表 B 并更新表 A**，再推导写入文本化文档与切分文件管理区状态摘要（切分文件 `status=raw` 写 frontmatter）
4. 两者不一致时，以状态文档为准重建
