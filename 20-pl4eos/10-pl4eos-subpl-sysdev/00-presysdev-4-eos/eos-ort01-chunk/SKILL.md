## 二、操作流程

### Step Start · 前置校验

按顺序检查，首次遇缺即处理：

1. `../../../80-pl4eos-2-eosdata/00-origin-requirement-materials/10-raw-files/` 存在；否则提示先运行 `eos-ort00-textualize` 并结束
2. `01-eos-sysdev-status.md` 存在；否则同上
3. 校验表 A/表 B 表头与字段说明，与状态文档模板不符时按既有口径修正或提示（表 B 模板见 [人类方案 §4.4](../eos-ort01-chunk.md#44-状态文档表-b-模板)）；否则同上
4. `10-raw-files/` 中存在 `.textualized.md` 文档；否则同上
5. 全部就绪 → **优先检查反馈**：存在 `生命周期=切分方案待确认` 的对象 → Step 2；无 → Step 1

**加载经济原则**：用 `ls`/grep 扫描 `10-raw-files/` 与状态文档表 A/表 B 区域，不 Read 整个状态文档；切分分析时仅读取目标文本化文档的正文区（管理区不参与语义分析）。

### Step 1 · 新增处理

读取表 A，按附录 A.2 分流：

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃`，追加废弃说明 |
| `人类决策=暂不切分` | 跳过，保留在行动清单 |
| `人类决策=空` | 跳过，列入下一批选材提醒 |

**方案生成**（详细规则见 [人类方案 §2.6](../eos-ort01-chunk.md#26-语义切分规则)）：

1. 读取文本化文档正文区纯原文
2. 执行语义结构分析（附录 A.3）
3. 按切分判定表形成切分/不切分建议（附录 A.4）
4. 在正文区原文之后写入切分方案块 + 反馈提示区（模板见附录 C）
5. 表 A 更新：`生命周期=切分方案待确认`、`AI建议=审核切分方案`
6. 从表 A 推导写入文本化文档管理区状态摘要

### Step 2 · 反馈处理

读取表 A 中 `生命周期=切分方案待确认` 的文档，按附录 A.1 检测正文区方案块与反馈：

| 反馈 | 处理 |
|------|------|
| `[同意执行]` | 判方案块类型：建议不切分→按单片输出（seq=1/total=1/label=`不切分（整份文档）`，管理区写「不拆分已确认」，规格同确认不拆分）；建议切分→校验行号范围（无重叠/无遗漏，语义标签完整）→ 逐片输出 `.chunk-{seq}.md`（frontmatter 见附录 C）→ 清理正文区方案块与反馈区 → 表 B 每片追加记录（`生命周期=已切分`、`AI建议=可以澄清`）→ 表 A→`已切分` |
| `[确认不拆分]` | 输出单片（seq=1, total=1，label=`不切分（整份文档）`）→ 单片管理区写状态摘要 `不拆分已确认` → 清理方案块 → 表 A/B 同上（`已切分`+`可以澄清`）→ 追加迭代/决策记录（执行模式=不拆分） |
| `[调整]` | 解析边界/标签/片数/范围调整意图 → 管理区摘要记录调整结论（历史由 Git 管理）→ 写入新版方案块 → 表 A 保持待确认 |
| `[废弃]` | 表 A→`已废弃`，管理区追加废弃记录 |
| 无反馈 | 跳过，等待人类操作 |

写回前执行附录 B.1 冲突检查。

### Step End · 运行结束输出（含反馈等待）

按 91 规范 §A.3.2 三区模板输出：

```text
当前状态：<待确认切分方案 / 已切分可澄清 / 已废弃 / 无新增处理>
  生成切分方案：<文件名>（建议切分 N 片 / 建议不切分，等待反馈）
  执行切分输出：<文件名.chunk-001.md ...>（表 B 生命周期=已切分，AI建议=可以澄清）
  调整重生成：<文件名>（v{N-1}→v{N}，仍待确认）
  废弃材料：<文件名>（表 A 生命周期=已废弃）
资产落账：表 A/表 B 已同步；文本化文档正文区 <保留方案块 / 已清理为纯原文>

一、方案反馈（直接回复口令，AI 代为更新状态文档与正文区反馈）
  A. 同意执行 → 回复「同意执行 [文件名]」
  B. 局部调整 → 回复「调整 [文件名]：<调整内容>」
  C. 确认不拆分 → 回复「确认不拆分 [文件名]」
  D. 废弃材料 → 回复「废弃 [文件名]」

二、下一步（三类待办，可全做/做部分/全不做）
  ① 待反馈确认的切分方案 → 表 A `生命周期=切分方案待确认`：到文本化文档正文区方案块填写反馈
  ② 待选入切分的材料 → 表 A `生命周期=已文本化` + `AI建议=可以切分` + `人类决策=空`：设 `人类决策=同意切分` 后重跑本步
  ③ 待选入澄清的切分文件 → 表 B `生命周期=已切分` + `AI建议=可以澄清`：设 `人类决策=同意澄清` 后进入 eos-ort02-clarify
```

**交互方式**：按 91 规范 §A.5 反馈交互协议，**AI 不结束对话**——输出本摘要后保持对话，人类以自然语言回复口令，AI 代为更新状态文档与正文区反馈。

**AI 处理口令规则**：

| 人类输入 | AI 动作 |
|---------|--------|
| **方案反馈**：「同意执行 [文件名]」 | 正文区反馈区写入 `[同意执行]` → 执行切分输出 |
| **方案反馈**：「调整 [文件名]：...」 | 正文区反馈区写入 `[调整]` → 解析意图重生成方案 |
| **方案反馈**：「确认不拆分 [文件名]」 | 正文区反馈区写入 `[确认不拆分]` → 输出单片切分文件 |
| **方案反馈**：「废弃 [文件名]」 | 正文区反馈区写入 `[废弃]` → 表 A→`已废弃` |
| **辅助**：「同意澄清 [切分文件]」 | 表 B 人类决策=同意澄清 |
| **辅助**：「继续」 | 重跑本步 |
| **辅助**：「打开状态文档」 | 输出 `01-eos-sysdev-status.md` 路径和建议关注行 |

## 三、AI 标记约定

**正文区方案块状态**：方案块存在 = 待确认（Step 1 产物）；清理 = 已执行。历史版本由 Git 管理，旧方案不参与入口判断。

**反馈触发词**：`[同意执行]` / `[调整]` / `[确认不拆分]` / `[废弃]` 写入正文区反馈区，是反馈处理的唯一驱动。

**状态摘要取值**：文档内嵌状态摘要的阶段值分两类宿主——文本化文档管理区用「待确认切分方案 / 已切分」；切分文件管理区用「切分已执行 / 不拆分已确认」；「已废弃」两者皆可（材料终止→文本化文档，片终止→切分文件）。表 B 生命周期不受其影响——切分文件（含不拆分单片）统一为 `已切分`。

**增量标记**：反馈处理中按 91 规范 §A.5 追加 `[已处理]` 作为处理记录。

## 附录A：判据速查

### A.1 正文区检测与反馈分流

| 条件 | 处理 |
|------|------|
| 表 A `生命周期=切分方案待确认` 且正文区有方案块，无反馈文本 | 跳过，等待人类反馈 |
| 表 A `生命周期=切分方案待确认` 且正文区无方案块 | 数据不一致：提示人类核对，按「调整」路径重新生成方案块 |
| 有方案块 + `[同意执行]` | 按方案块执行切分 |
| 有方案块 + `[确认不拆分]` | 输出单片切分文件 |
| 有方案块 + `[调整]` 或明确修改意图 | 重生成方案（历史由 Git 管理） |
| 有方案块 + `[废弃]` | 表 A 置 `已废弃`，追加废弃记录 |

### A.2 表 A 分流

| 表 A 状态 | 处理 |
|----------|------|
| `生命周期=已文本化` + `人类决策=同意切分` | 对应文本化文档进入方案生成 |
| `人类决策=已终止` | 表 A 生命周期置 `已废弃` |
| `人类决策=暂不切分` | 跳过，保留行动清单 |
| `人类决策=空` | 跳过，下一批选材提醒 |

### A.3 语义结构分析三步

| # | 操作 | 说明 |
|---|------|------|
| 1 | 相关方与场景识别 | 相关方（角色/岗位/人称）+ 其参与的端到端场景业务（一个角色一条端到端业务闭环，[91 §1.4]） |
| 2 | 场景内环节识别 | 端到端场景内的业务环节/子流程 |
| 3 | 关联性分析 | 概念定义、上下文依赖、跨段引用 |

> 语义单元 = 一个角色（相关方）的一条端到端业务闭环 [91 §1.4]，是判定"切不切"的最小单位；场景过大按环节细分，无明确角色场景时补用结构/主题锚点（定义见 [人类方案 §2.6](../eos-ort01-chunk.md#26-语义切分规则)）。

### A.4 切分判定

**计量（主标准：相关方 × 端到端场景业务）**：候选单元数先按"单个相关方 × 单个端到端场景业务"计（一个场景业务 = 一个角色一条端到端业务闭环 [91 §1.4]；多相关方/多场景 → 多单元）；场景过大按环节细分；无明确角色场景时补用结构锚点或主题转换（写明理由）。仅识别"谁、什么场景"不评价需求。

| 候选单元数 | 关联性 | 结论 | 输出 |
|-----------|--------|------|------|
| 1（单个相关方单个场景） | — | 不切分 | 建议不切分（语义单一） |
| >1（多相关方/多场景/多环节） | 强（拆开破坏完整性） | 不切分 | 建议不切分（语义不可分） |
| >1 | 弱（可独立成片） | 切分 | 输出多片方案 |

**AI 判断路径**（完整版见 [人类方案 §2.6](../eos-ort01-chunk.md#26-语义切分规则)）：确认入口 → 通读识别（相关方/场景）→ 数候选单元（相关方 × 场景，无场景退回结构/主题锚点）→ 查关联性 → 出判定 → 写方案块（行号范围+标签+理由）→ 交人类反馈。

### A.5 边界处理

| 边界情况 | 处理 |
|---------|------|
| 行号边界落在段落中间 | 被截断段落完整归入起始片，行动清单提示边界截断 |
| 连续两片之间有空白行 | 空白行归入前一片 |
| 切分内容为空 | 不输出空文件，视为无效标记 |

> **行号基准**：方案块「行号：Lxxx」相对**正文区**计数（正文区第 1 行 = L1），管理区行数变化不影响行号（详见 [人类方案 §2.6](../eos-ort01-chunk.md#26-语义切分规则)）。

### A.6 表 A/表 B 取值

| 表 | 生命周期 | 人类决策 |
|----|---------|---------|
| 表 A | 已登记 → 已文本化 → 切分方案待确认 → 已切分 → 已废弃（含已废弃（重复）） | 空 / 同意切分 / 暂不切分 / 已终止 |
| 表 B | 已切分 → 澄清中 → 已澄清 → 待确认规范方案 → 已规范化 → 已废弃 | 空 / 同意澄清 / 同意规范化 / 已终止 |

## 附录B：版本感知与写回

### B.1 写回前冲突检查

表 A/表 B 是人类与 AI 共同维护的表。AI 写回前执行冲突检查，防止覆盖人类手工修改：

1. **快照**——读取待更新行的 `生命周期` 与 `人类决策` 当前值
2. **复核**——写回前重新读取该行；若 `生命周期` 或 `人类决策` 与快照不符（人类在本次运行期间手工修改），标记 `[需确认]`，不覆盖，在 Step End 提示人类
3. **人类决策保护**——`人类决策` 是唯一由人类写入的字段：除非人类通过 Step End 口令明确指示（如「同意执行」「同意澄清」），AI 绝不覆盖非空的人类决策

### B.2 写回顺序（同步契约）

1. 生成方案分支：**先更新表 A**（`切分方案待确认`），再推导写入文本化文档管理区
2. 执行切分分支：**先追加/更新表 B 并更新表 A**，再推导写入文本化文档与切分文件管理区状态摘要（切分文件 `status=raw` 写 frontmatter）
3. 两者不一致时，以状态文档为准重建

## 四、重进入规则

| 场景 | 处理 |
|------|------|
| 新选入材料 | 表 A `生命周期=已文本化` + `人类决策=同意切分` → 生成方案 |
